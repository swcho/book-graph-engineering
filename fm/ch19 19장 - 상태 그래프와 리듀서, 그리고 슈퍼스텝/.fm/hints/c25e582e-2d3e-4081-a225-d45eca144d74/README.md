# 「경계」 노드는 값을 바꾸러 온 게 아니다 — 자리를 만들러 왔다

**질문** — `ex2_superstep.py`의 '경계' 노드는 어떤 역할을 하는가?

**답** — A·B·C 이후 D·E 이전에 놓여 슈퍼스텝 경계를 만든다. 덕분에 D·E는 앞의 결과를 모두 본다.

---

## 1. 먼저 코드를 보자

`ex2_superstep.py`에서 그래프를 짜는 부분만 떼면 이렇다.

```python
b = StateGraph(S)
for n in ("A", "B", "C"):
    b.add_node(n, mk(n))
b.add_node("경계", bump)
b.add_node("D", mk("D"))
b.add_node("E", mk("E"))

b.add_edge(START, "A")
b.add_edge(START, "B")
b.add_edge(START, "C")
b.add_edge("A", "경계")
b.add_edge("B", "경계")
b.add_edge("C", "경계")
b.add_edge("경계", "D")
b.add_edge("경계", "E")
b.add_edge("D", END)
b.add_edge("E", END)
```

노드가 하는 일은 자기가 「본」 상태를 한 줄 적는 것뿐이다.

```python
def mk(name):
    def fn(s):
        # 이 노드가 «본» 상태를 기록한다. 같은 슈퍼스텝이면 같은 걸 본다.
        return {"seen": [f"{name}: step={s['step']}, seen={len(s['seen'])}개"]}
    return fn


def bump(s):
    return {"step": s["step"] + 1, "seen": ["--- 경계 ---"]}
```

여기서 헷갈리기 쉬운 게 `bump`다. `step`을 1 올리고 `--- 경계 ---`를 로그에 남기니까 「경계 노드는 step 카운터를 관리하는 노드」로 읽힌다. **아니다.** 저 두 줄은 사람이 출력을 눈으로 확인하라고 붙인 표식이다. 예제의 취지에 맞게 극단적으로 줄이면 이렇게 써도 그래프의 실행 순서는 **한 글자도 안 바뀐다.**

```python
def bump(s):
    return {}          # 상태를 아무것도 안 바꾼다. 그래도 경계는 그어진다.
```

## 2. 빈 dict를 돌려주는 노드가 왜 의미가 있나

노드의 값어치는 보통 **반환값**에 있다. 경계 노드만 예외다. 경계 노드의 값어치는 반환값이 아니라 **자기가 존재함으로써 그래프에 생기는 한 칸**에 있다.

LangGraph의 실행 모형(Pregel)에서 규칙은 두 줄이다.

1. 같은 슈퍼스텝에 들어간 노드들은 **같은 상태 사본**을 받는다. 서로가 쓴 걸 못 본다.
2. 한 슈퍼스텝이 끝나야 그 안의 갱신이 리듀서를 통해 합쳐지고, **다음** 슈퍼스텝이 그 결과를 본다.

그러니까 「D가 A의 결과를 보게 하고 싶다」는 요구는 값의 문제가 아니라 **위치의 문제**다. D를 A보다 뒤 슈퍼스텝에 놓기만 하면 된다. 경계 노드는 그 「뒤 슈퍼스텝」을 물리적으로 만들어 내는 장치다. 값은 안 건드려도 된다. 자리만 차지하면 된다.

> 목적은 노드의 **값**이 아니라 그 노드가 만드는 **동기화 지점(barrier)**이다.

이 관점이 서면 `return {}`이 이상해 보이지 않는다. `time.sleep(0)`이 아니라 `join()`에 가깝다.

## 3. BSP의 barrier synchronisation과의 대응

이건 LangGraph가 발명한 개념이 아니다. Valiant의 **벌크 동기 병렬(Bulk Synchronous Parallel, 1990)**과 그걸 그래프 계산에 적용한 구글의 **Pregel(2010)**이 그대로 물려준 성질이다. 두 논문 모두 이 장 키워드 표에 1차 출처로 실려 있다.

BSP에서 한 슈퍼스텝은 세 단계로 되어 있다.

| BSP 단계 | 뜻 | LangGraph에서 |
|---|---|---|
| **① 지역 계산** | 각 프로세서가 자기 로컬 사본만 보고 계산 | A·B·C가 각각 같은 상태 사본을 받아 노드 함수를 실행 |
| **② 통신** | 계산 결과를 서로에게 전달 | 각 노드가 돌려준 부분 갱신을 채널로 보냄 |
| **③ 배리어 동기화** | **전원이 도착할 때까지 대기.** 도착 후에야 다음 스텝 시작 | 슈퍼스텝의 모든 노드가 끝날 때까지 대기 → 리듀서로 병합 → 체크포인트 저장 → 다음 슈퍼스텝 |

BSP 배리어의 핵심 성질 두 개가 그대로 온다.

- **가시성 보장** — 배리어 이전의 모든 쓰기는 배리어 이후의 모든 읽기에 보인다. 그래서 D·E가 A·B·C의 결과를 「다」 본다.
- **가시성 차단** — 배리어 안쪽에서는 누가 먼저 썼는지 볼 수 없다. 그래서 A·B·C는 서로를 못 본다.

즉 배리어는 **순서를 만들어 주는 대신 그 안의 순서를 지워 버린다.** 예제 마지막 출력이 말하는 게 이거다.

```
A·B·C 가 전부 «seen=0개»를 봤다. 같은 슈퍼스텝이라 같은 상태 사본을 받았기 때문이다.
서로가 쓴 걸 못 본다. 이게 슈퍼스텝의 성질이다.
```

「안쪽의 순서를 못 정한다」는 성질은 19.3절 리듀서 교환법칙 얘기와 같은 뿌리다. `ex3_custom_reducer.py`에서 ERP를 먼저 등록했는데 CRM이 먼저 도는 것도 결국 같은 배리어 안이라 순서가 정해지지 않아서다. 순서가 필요하면 리듀서를 고치는 게 아니라 **배리어를 하나 더 그어야** 한다.

## 4. 슈퍼스텝 타임라인 — 경계가 있을 때 vs 없을 때

### (가) 경계 노드가 있는 지금 코드

`step`은 `bump`가 올리고, `seen`은 `Annotated[list, operator.add]`라 계속 이어 붙는다.

| 슈퍼스텝 | 실행 노드 | 노드가 **읽는** 상태 | 스텝 끝의 `seen` 길이 |
|---|---|---|---|
| 0 | (입력) | — | 0 |
| 1 | **A, B, C** (동시) | `step=0`, `seen=0개` — 셋 다 똑같이 | 3 |
| 2 | **경계** | `step=0`, `seen=3개` | 4 (`--- 경계 ---` 추가) |
| 3 | **D, E** (동시) | `step=1`, `seen=4개` — 둘 다 똑같이 | 6 |

출력은 이렇게 나온다.

```
    A: step=0, seen=0개
    B: step=0, seen=0개
    C: step=0, seen=0개
    --- 경계 ---
    D: step=1, seen=4개
    E: step=1, seen=4개
```

D·E가 본 `seen=4개`는 「A·B·C 세 줄 + 경계 한 줄」이다. **앞의 결과를 하나도 빠짐없이 봤다**는 증거다. 그리고 D와 E는 서로는 못 본다 — 둘은 같은 슈퍼스텝 3에 있으니까. 배리어는 딱 자기가 그은 선에서만 작동한다.

`app.get_state_history(cfg)`로 찍는 두 번째 블록이 이 표를 그대로 보여 준다. 체크포인트는 **슈퍼스텝 경계마다** 하나씩 찍히기 때문에, 스냅숏을 세는 것이 곧 슈퍼스텝을 세는 것이다.

```
    0. 다음에 갈 노드: A, B, C        seen 0개
    1. 다음에 갈 노드: 경계           seen 3개
    2. 다음에 갈 노드: D, E           seen 4개
    3. 다음에 갈 노드: (끝)           seen 6개
```

### (나) 경계 노드를 지우고 D·E를 A·B·C와 나란히 놓았다면

```python
# 잘못된 기대: "A 다음에 D가 도니까 D는 A를 보겠지"
b.add_edge(START, "A"); b.add_edge(START, "B"); b.add_edge(START, "C")
b.add_edge(START, "D"); b.add_edge(START, "E")
```

| 슈퍼스텝 | 실행 노드 | 노드가 읽는 상태 |
|---|---|---|
| 1 | **A, B, C, D, E** (전부 동시) | 다섯 개 전부 `step=0`, `seen=0개` |

```
    A: step=0, seen=0개
    B: step=0, seen=0개
    C: step=0, seen=0개
    D: step=0, seen=0개      ← 앞의 결과를 하나도 못 봤다
    E: step=0, seen=0개
```

D는 자기가 **앞**이라고 생각하는 A·B·C를 못 본다. 실행이 실패하지도 않고 예외도 안 난다. 그냥 조용히 빈 상태를 보고 계산한다. 저자가 「왜 B가 A의 결과를 못 보지」로 반나절을 썼다고 한 게 이 모양이다. **로그가 정상으로 보이는 버그**라서 오래 걸린다.

## 5. 경계를 만드는 다른 방법과 그 값

경계 노드는 배리어를 긋는 여러 방법 중 하나일 뿐이다. 셋을 비교하면 트레이드오프가 선명해진다.

### (1) 엣지 체인 — 아예 직렬로 늘어놓기

```python
b.add_edge("A", "B"); b.add_edge("B", "C"); b.add_edge("C", "D"); b.add_edge("D", "E")
```

- 경계가 노드 사이마다 그어진다. 뒤는 앞을 전부 본다.
- **비용이 가장 크다.** 슈퍼스텝이 5개 → 체크포인트 5번, 그리고 A·B·C의 **병렬성을 통째로 버린다.** 셋이 각각 LLM 호출이면 지연이 3배가 된다.
- 「경계가 필요하다」는 이유로 전부 직렬화하는 게 가장 흔한 과잉 대응이다.

### (2) fan-in 노드 — 다음 단계 노드가 직접 여러 엣지를 받게 하기

```python
for up in ("A", "B", "C"):
    for down in ("D", "E"):
        b.add_edge(up, down)      # D와 E가 각각 A·B·C 셋 다를 기다린다
```

- **추가 노드 없이** 배리어를 얻는다. D·E는 A·B·C가 전부 끝나야 돌고, 앞의 결과를 다 본다.
- 슈퍼스텝은 2개(A·B·C / D·E)로 지금 코드보다 **하나 적다.** 체크포인트도 한 번 덜 찍힌다.
- 대신 엣지가 **N × M**으로 늘어난다. 여기선 3×2 = 6개. 상류가 5개, 하류가 4개면 20개다. 나중에 상류 노드를 하나 추가할 때 하류 개수만큼 엣지를 빠짐없이 추가해야 하고, **하나 빠뜨리면 그 경로만 조용히 배리어가 깨진다.** 위 (나)와 똑같은 증상이 부분적으로 난다.
- 그래프 시각화에서 스파게티가 된다. 「여기가 단계 구분선이다」가 그림에 안 보인다.
- 상류 브랜치들의 **길이가 다르면** 함정이 하나 더 있다. 짧은 브랜치가 먼저 도착했을 때 fan-in 노드가 먼저 한 번 실행돼 버릴 수 있다. LangGraph는 이럴 때 `b.add_node("D", fn, defer=True)`로 「모든 선행 경로가 끝날 때까지 미뤄라」를 명시하게 해 준다. 길이가 다른 병렬 브랜치를 합칠 땐 이걸 확인하자.

### (3) 명시적 경계 노드 — 예제가 택한 방법

```python
b.add_edge("A", "경계"); b.add_edge("B", "경계"); b.add_edge("C", "경계")
b.add_edge("경계", "D"); b.add_edge("경계", "E")
```

- 엣지가 **N + M**으로 끝난다. 여기선 3 + 2 = 5개. 상류가 5개, 하류가 4개여도 9개다.
- 상류/하류를 추가할 때 엣지를 **하나만** 그으면 된다. 빠뜨릴 자리가 없다.
- 그래프를 그리면 「여기가 단계 구분선」이 한눈에 보인다. 이름이 `경계`니까 코드 리뷰에서 **의도가 문서로 남는다.**
- 경계 노드를 「값을 안 바꾸는 자리」로만 두지 않고 실제로 쓸 데도 많다. 병합 후 검증, 로깅, 여기 `bump`처럼 라운드 카운터 증가 — 모든 상류가 끝난 직후에만 할 수 있는 일들의 자연스러운 서식지다.

**치르는 값은 딱 하나다: 슈퍼스텝 하나 추가.** 그리고 슈퍼스텝 하나는 곧 **체크포인트 저장 한 번**이다. 19.5절과 `ex4_state_size.py`가 세는 그 비용이 그대로 붙는다.

- 상태가 8KB라면 한 번 더 직렬화·저장. 별것 아니다.
- 상태에 검색 결과 원문 84KB가 들어 있다면 얘기가 다르다. `ex4`가 계산하듯 진짜 값은 저장비(월 1,600원 수준)가 아니라 **직렬화 시간**이다. 18장에서 잰 체크포인트 40~120ms가 상태 크기에 비례해 몇 배가 된다.

### 고르는 기준

| 상황 | 권장 |
|---|---|
| 상류·하류가 각각 2개 이하, 한 번 쓰고 안 바뀜 | fan-in 엣지로 충분 |
| 상류나 하류가 늘어날 여지가 있음 / 팀이 같이 고침 | **경계 노드.** N+M이 N×M을 이긴다 |
| 병합 직후에 검증·로깅·카운터 증가가 필요 | **경계 노드.** 어차피 할 일이 있다 |
| 브랜치 길이가 제각각 | 경계 노드, 또는 fan-in + `defer=True` |
| 상태가 커서 체크포인트가 무거움 | fan-in을 먼저 검토. 다만 **상태를 줄이는 게 먼저다** |
| 병렬성이 애초에 필요 없음 | 엣지 체인. 단, 「필요 없다」를 진짜 확인하고 |

마지막 줄이 중요하다. 체크포인트가 아까워서 경계를 안 그으면 (나)의 조용한 버그를 사는 것이다. **경계 하나의 값은 체크포인트 한 번보다 거의 항상 싸다.** 상태가 무거워서 그 균형이 흔들린다면, 그건 경계를 줄일 신호가 아니라 상태를 줄일 신호다.

## 6. 한 줄로

경계 노드는 **아무것도 안 바꾸는 것이 정상인 노드**다. 그 노드가 반환하는 값이 아니라, 그 노드가 만들어 내는 **배리어 — A·B·C의 쓰기가 전부 병합되고 나서야 D·E의 읽기가 시작되게 하는 시간의 선** 이 목적이다. 그래서 `return {}`이어도 된다. 값이 아니라 자리가 일을 한다.
