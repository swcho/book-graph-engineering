# `ex1_lost_update.py`는 어떻게 세 노드를 같은 슈퍼스텝에 넣는가?

**정답: START에서 재무·법무·영업 세 노드로 각각 엣지를 연결한다. 동시에 시작되므로 같은 슈퍼스텝이 된다.**

---

## 1. 원본 코드에서 문제의 세 줄

`ex1_lost_update.py`의 `make()` 함수가 전부입니다. 노드를 등록하고, 엣지를 긋고, 컴파일합니다.

```python
def make(state_type):
    def worker(name):
        def fn(s):
            return {"logs": [f"{name} 실행"], "count": 1}
        return fn

    b = StateGraph(state_type)
    b.add_node("재무", worker("재무"))
    b.add_node("법무", worker("법무"))
    b.add_node("영업", worker("영업"))
    # 셋을 «동시에» 시작한다 — 같은 슈퍼스텝에 들어간다
    b.add_edge(START, "재무")
    b.add_edge(START, "법무")
    b.add_edge(START, "영업")
    b.add_edge("재무", END)
    b.add_edge("법무", END)
    b.add_edge("영업", END)
    return b.compile()
```

핵심은 이 세 줄입니다.

```python
b.add_edge(START, "재무")
b.add_edge(START, "법무")
b.add_edge(START, "영업")
```

`START`라는 **하나의 출발점에서 세 개의 엣지가 뻗어 나갑니다**. 이걸 팬아웃(fan-out)이라고 부릅니다. 어디에도 "병렬로 실행해라", "스레드를 세 개 띄워라" 같은 말은 없습니다. 그냥 엣지를 세 번 그었을 뿐인데 병렬이 됩니다. 그래프의 **모양**이 곧 실행 계획이기 때문입니다.

주의할 점: 노드를 등록한 순서(`재무` → `법무` → `영업`)는 실행 순서와 아무 관계가 없습니다. 실행 순서를 정하는 건 오직 엣지입니다. `ex3_custom_reducer.py`의 주석이 이 함정을 직접 언급합니다 — "저는 ERP를 먼저 등록했는데도" CRM이 먼저 왔다고요.

## 2. 왜 "엣지 세 개"가 "같은 슈퍼스텝"이 되는가

LangGraph의 실행기는 구글의 **Pregel** 계산 모형(그리고 그 바탕인 **벌크 동기 병렬**, BSP)을 따릅니다. 이 모형에서 실행은 연속된 시간이 아니라 **슈퍼스텝(superstep)이라는 이산적인 라운드의 연속**입니다.

한 슈퍼스텝은 이렇게 굴러갑니다.

1. **모으기** — 실행기가 지금 "활성화된(active)" 노드를 **한꺼번에** 잡습니다. 노드는 들어오는 엣지로 메시지를 받으면 활성화됩니다.
2. **한꺼번에 돌리기** — 잡힌 노드 집합을 전부 실행합니다. 이때 각 노드는 **슈퍼스텝 시작 시점의 상태 사본을 똑같이** 받습니다.
3. **모아서 커밋** — 모든 노드가 끝나기를 기다렸다가, 반환된 부분 갱신들을 리듀서로 합쳐 상태에 반영합니다. 이 지점에서 체크포인트가 저장됩니다.
4. **다음 라운드** — 갱신이 나간 엣지를 따라 다음 노드들이 활성화되고, 아무 노드도 활성화되지 않으면 그래프가 멈춥니다.

LangGraph 공식 문서의 표현이 이 인과를 그대로 요약합니다.

> "Nodes that run in parallel are part of the same super-step, while nodes that run sequentially belong to separate super-steps."
> (병렬로 도는 노드는 같은 슈퍼스텝에 속하고, 순차로 도는 노드는 서로 다른 슈퍼스텝에 속한다.)

그리고 START 팬아웃에 대해서는 이렇게 말합니다.

> "...will be run in parallel as a part of the next superstep."
> (…다음 슈퍼스텝의 일부로서 병렬로 실행된다.)

`ex1`에 적용해 봅시다. 그래프가 `invoke`되면 `START`가 메시지를 내보내고, 그 메시지는 세 엣지를 타고 재무·법무·영업에 **동시에** 도착합니다. 실행기가 1번 단계에서 활성 노드를 모을 때 셋이 한 번에 잡힙니다. 그래서 셋은 **선택의 여지 없이 같은 라운드**에 들어갑니다.

```
슈퍼스텝 0                        슈퍼스텝 1
  START                             (커밋)
   ├──► 재무 ─┐                       │
   ├──► 법무 ─┼─► [상태 갱신 합치기] ──┴──► END
   └──► 영업 ─┘
   ↑
   셋 다 같은 상태 사본을 받는다
```

즉 "동시에 시작된다"는 말은 "실행기가 셋을 같은 라운드에 잡았다"는 뜻이고, 그게 곧 같은 슈퍼스텝의 정의입니다. **동시 시작 = 같은 슈퍼스텝**은 우연이 아니라 동어반복에 가깝습니다.

한 가지 오해를 미리 정리하면, "같은 슈퍼스텝"은 반드시 물리적으로 같은 순간에 CPU에서 돈다는 뜻이 아닙니다. 동기 함수라면 실행기가 내부적으로 하나씩 호출할 수도 있습니다. 보장되는 건 **논리적 동시성** — 셋이 같은 입력 상태를 보고, 셋의 결과가 같은 시점에 함께 커밋된다는 것입니다. `ex3`에서 "실행기가 CRM을 먼저 돌려서"라는 관찰이 나오는 이유가 이겁니다. 내부 순서는 존재하지만, 여러분이 정할 수도 없고 기대서도 안 됩니다.

## 3. 순차 실행이 되게 하려면 무엇이 바뀌어야 하나

같은 세 노드를 순차로 돌리고 싶다면 **노드를 고칠 필요는 전혀 없습니다. 엣지만 바꾸면 됩니다.**

### 방법 A — 엣지를 체인으로 잇기

팬아웃을 체인으로 바꿉니다.

```python
# 병렬 (원본): START가 셋을 동시에 깨운다
b.add_edge(START, "재무")
b.add_edge(START, "법무")
b.add_edge(START, "영업")
b.add_edge("재무", END)
b.add_edge("법무", END)
b.add_edge("영업", END)

# 순차: 앞 노드가 끝나야 다음 노드가 깨어난다
b.add_edge(START, "재무")
b.add_edge("재무", "법무")
b.add_edge("법무", "영업")
b.add_edge("영업", END)
```

체인에서는 `법무`가 `재무`의 커밋을 받아야 비로소 활성화됩니다. 활성화 시점이 다르니 다른 라운드에 잡히고, 결국 슈퍼스텝이 0/1/2로 셋으로 쪼개집니다. 라운드가 다르면 같은 필드에 동시에 쓰는 일 자체가 일어나지 않습니다. 그래서 이 형태에서는 리듀서 없는 `NoReducer`도 예외 없이 통과합니다 — 매 라운드 그 필드에 값을 쓰는 노드가 하나뿐이니까요.

### 방법 B — 사이에 경계 노드를 두기

병렬성은 살리되 "여기까지는 끝난 뒤에"라는 순서만 강제하고 싶을 때 씁니다. 이 패턴이 `ex2_superstep.py`에 통째로 들어 있습니다.

```python
b.add_edge(START, "A")
b.add_edge(START, "B")
b.add_edge(START, "C")
b.add_edge("A", "경계")      # A·B·C가 전부 끝나야
b.add_edge("B", "경계")      # «경계»가 활성화된다 (팬인)
b.add_edge("C", "경계")
b.add_edge("경계", "D")      # 그 다음 D·E가 다시 병렬로
b.add_edge("경계", "E")
```

`ex2`가 뽑아 주는 결론이 이 장의 핵심 문장입니다.

> A·B·C가 전부 「seen=0개」를 봤다. 같은 슈퍼스텝이라 같은 상태 사본을 받았기 때문이다. 서로가 쓴 걸 못 본다. 이게 슈퍼스텝의 성질이다. D·E는 「경계」 노드가 끝난 뒤라 앞의 결과를 다 본다.

정리하면 이렇습니다.

| 목표 | 엣지 모양 | 슈퍼스텝 |
|---|---|---|
| 병렬 (원본 `ex1`) | `START → 재무 / 법무 / 영업` | 셋이 한 라운드 |
| 완전 순차 | `START → 재무 → 법무 → 영업` | 세 라운드 |
| 병렬 후 경계 | `START → A/B/C → 경계 → D/E` | 팬아웃-팬인-팬아웃 |

**순서가 필요하면 코드에 `sleep`이나 락을 넣지 말고 엣지를 다시 그으세요.** 실행 순서를 표현하는 언어는 그래프의 모양이지 노드 내부가 아닙니다.

## 4. "같은 슈퍼스텝"이 곧 lost update 위험인 이유

파일 이름이 `ex1_lost_update.py`인 건 우연이 아닙니다. 지금까지의 사실을 이으면 갱신 유실은 자동으로 따라옵니다.

1. 세 노드가 **같은 슈퍼스텝**에 있다.
2. 같은 슈퍼스텝이므로 셋 다 **똑같은 상태 사본**을 읽는다 (`logs: []`, `count: 0`).
3. 셋 다 그 사본을 기준으로 계산해 `{"logs": [...], "count": 1}`을 반환한다.
4. 커밋 시점에 **같은 키에 세 개의 값**이 동시에 도착한다.
5. 합치는 규칙이 없으면 → 하나만 남는다. 나머지 둘의 갱신은 **사라진다**.

이게 데이터베이스 이론에서 말하는 전형적인 **갱신 유실(lost update)** — read-modify-write가 겹칠 때 나중 쓰기가 앞 쓰기를 덮어 그 갱신이 없던 일이 되는 이상 현상입니다. 병렬 자체가 문제가 아니라 **"같은 사본을 읽고 각자 쓴다"**가 문제이고, 그 조건을 만드는 게 정확히 같은 슈퍼스텝입니다.

특히 `count`가 극적입니다. 노드마다 `1`을 더한 게 아니라 **`0`에서 출발해 `1`을 만들었을 뿐**입니다. 셋이 다 `1`을 냈으니 규칙 없이 하나만 고르면 답은 `3`이 아니라 `1`입니다. 두 건이 조용히 증발합니다.

여기서 LangGraph가 취하는 태도가 이 예제의 진짜 결론입니다.

```python
class NoReducer(TypedDict):      # A안 — 합치는 규칙 없음
    logs: list
    count: int

class WithReducer(TypedDict):    # B안 — 합치는 규칙 있음
    logs: Annotated[list, operator.add]
    count: Annotated[int, operator.add]
```

`NoReducer`로 돌리면 조용히 하나만 남는 게 아니라 **예외가 납니다**. `main()`의 `try/except`가 이걸 잡으려고 있는 것이고, 챕터 안내문도 못 박습니다 — "`ex1`은 일부러 **예외가 나는** 경우를 포함합니다. 그게 이 예제의 결과입니다."

`Annotated`가 없는 키에 한 슈퍼스텝에서 값이 둘 이상 도착하면 LangGraph는 `InvalidUpdateError`를 던집니다. 메시지 요지는 "한 스텝에 값을 하나만 받을 수 있다, 여러 값을 다루려면 `Annotated` 키를 쓰라"입니다.

> 리듀서가 없으면 LangGraph는 「같은 필드를 여럿이 쓰려 한다」고 막는다. 막아 주는 게 다행이다. 조용히 하나만 남기는 프레임워크도 있다.

`WithReducer`에서는 `operator.add`가 규칙이 되어 `logs`는 세 줄이 이어 붙고 `count`는 `3`이 됩니다. 그리고 `operator.add`는 리스트 이어 붙이기든 정수 덧셈이든 **순서가 바뀌어도 최종 결과가 같아지도록** 동작합니다(정수는 완전히 교환법칙, 리스트는 원소 집합이 보존되고 순서만 달라짐). 실행기 내부 순서를 우리가 정할 수 없으니, 리듀서는 순서에 기대지 않아야 합니다. `ex3`이 "순서에 기대는 리듀서는 「내가 예상한 답」을 안 낸다"며 `merge_dict`가 어떻게 기대와 반대 결과를 냈는지 실제로 보여 줍니다.

마지막으로, 저자가 강조하는 포인트는 리듀서를 붙였다는 사실 자체가 아닙니다.

> 여기서 중요한 건 「리듀서를 붙였다」가 아니라 「이 필드를 여럿이 쓴다는 걸 타입에 적었다」는 것이다. 타입을 읽으면 동시 쓰기 여부를 알 수 있다. 코드를 안 읽어도.

`add_edge(START, ...)`가 세 번 나온 걸 놓쳐도, `Annotated[list, operator.add]`라는 타입 선언 하나가 "이 필드는 같은 슈퍼스텝에서 여럿이 쓴다"를 문서화합니다. 그래프 모양(누가 언제 도는가)과 타입(누가 무엇을 쓰는가)이 서로를 설명하는 구조입니다.

## 5. 같은 슈퍼스텝 병렬을 만드는 다른 방법들

`ex1`은 정적 엣지 팬아웃을 썼지만, 결과가 같은 슈퍼스텝인 방식이 둘 더 있습니다. 시험 문제로는 `add_edge`가 답이지만, 실무에서 만나면 같은 lost update 위험을 안고 있으니 함께 알아 두세요.

### (1) 조건부 팬아웃 — `add_conditional_edges`가 **리스트**를 반환할 때

라우팅 함수가 노드 이름을 하나가 아니라 **리스트로** 반환하면 그 노드들이 전부 다음 슈퍼스텝에 병렬로 들어갑니다. 공식 문서 표현입니다.

> "the `routing_function`'s return value is used as the name of the node (or **list of nodes**) to send the state to next. All those nodes **will be run in parallel as a part of the next superstep**."

```python
def fan(s) -> list[str]:
    # 상태를 보고 실행 대상을 «런타임에» 정한다
    targets = ["재무", "법무"]
    if s["금액"] > 1_000_000:
        targets.append("영업")
    return targets

b.add_conditional_edges(START, fan, ["재무", "법무", "영업"])
```

`ex1`과의 차이는 **누가 정하느냐**뿐입니다. `ex1`은 컴파일 시점에 그래프 모양으로 고정, 이쪽은 실행 시점에 상태를 보고 결정. 하지만 선택된 노드들은 똑같이 한 라운드에 잡히고, 똑같이 같은 상태 사본을 보고, 똑같이 리듀서가 필요합니다. 참고로 `ex5_debug_state.py`도 `add_conditional_edges`를 쓰지만 거기서는 단일 문자열(`"검색"` 또는 `END`)을 반환하므로 분기일 뿐 병렬이 아닙니다 — **리스트를 반환할 때만** 팬아웃입니다.

### (2) 동적 팬아웃 — `Send` API

노드 개수를 코드 작성 시점에 알 수 없을 때(검색 결과 N건을 각각 요약하는 맵리듀스 같은 경우) `Send`를 씁니다. 조건부 엣지의 라우팅 함수가 `Send` 객체의 리스트를 반환하는 형태입니다.

```python
from langgraph.types import Send

def spread(s):
    # 항목 수만큼 «실행 시점에» 노드 인스턴스를 만든다
    return [Send("요약", {"문서": d}) for d in s["문서들"]]

b.add_conditional_edges("검색", spread, ["요약"])
```

`Send(노드이름, 그_노드에_넘길_상태)` 두 인자를 받습니다. 결정적인 차이는 각 인스턴스가 **전체 그래프 상태가 아니라 따로 만들어 준 상태를 받는다**는 점입니다. 그래도 실행 라운드는 하나 — 전부 같은 슈퍼스텝에서 병렬로 돌고, 실행기는 모든 갈래가 끝난 뒤에야 다음으로 넘어갑니다. 따라서 결과를 모으는 필드에는 반드시 리듀서(`Annotated[list, operator.add]` 등)가 있어야 합니다. 여기서는 팬아웃 폭이 데이터에 따라 달라지므로 "몇 개가 동시에 쓰는가"를 미리 알 수 없고, 그만큼 리듀서가 더 중요합니다.

**세 방식 비교**

| 방식 | 팬아웃 결정 시점 | 대상 개수 | 각 노드가 받는 상태 | 같은 슈퍼스텝? |
|---|---|---|---|---|
| `add_edge(START, ...)` × N (`ex1`) | 컴파일 시점(그래프 모양) | 고정 | 공유 상태 사본 | 예 |
| `add_conditional_edges` → 리스트 | 실행 시점 | 후보 중 선택 | 공유 상태 사본 | 예 |
| `Send` | 실행 시점 | 데이터에 따라 가변 | 갈래마다 지정한 상태 | 예 |

세 줄 모두 같은 결론으로 수렴합니다. **어떤 방식으로 만들었든 같은 슈퍼스텝에 여러 노드가 있으면 같은 필드에 대한 동시 쓰기가 생기고, 그 필드에는 합치는 규칙(리듀서)이 있어야 한다.** `ex1`은 그 사실을 가장 짧은 코드 — `add_edge(START, ...)` 세 줄 — 로 재현해 보인 예제입니다.

---

## 한 줄 정리

`add_edge(START, "재무")` / `add_edge(START, "법무")` / `add_edge(START, "영업")` — START에서 세 갈래로 뻗은 정적 엣지가 세 노드를 동시에 활성화시키고, LangGraph의 Pregel 실행기는 매 슈퍼스텝마다 활성 노드를 **한꺼번에** 잡아 돌리므로 셋은 같은 슈퍼스텝에 들어간다. 순차로 만들려면 엣지를 체인으로 잇거나 사이에 경계 노드를 두면 되고, 같은 슈퍼스텝이라는 사실은 곧 "셋이 같은 상태 사본을 읽고 각자 쓴다"는 뜻이라 리듀서가 없으면 갱신 유실(또는 `InvalidUpdateError`)로 이어진다.
