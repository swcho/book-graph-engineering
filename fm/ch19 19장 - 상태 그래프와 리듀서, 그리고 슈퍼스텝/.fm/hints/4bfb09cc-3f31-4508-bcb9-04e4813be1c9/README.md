# 19장의 리듀서와 14장의 생존 규칙은 어떤 관계인가?

> **답:** 같은 얘기다. 다만 14장은 배치로 병합하고 19장은 실행 중에 합친다.

이 문장은 19장 `ex3_custom_reducer.py`의 마지막 해설에 그대로 나옵니다.

> "필드마다 «합치는 규칙»이 다르다. 14장의 생존 규칙과 같은 얘기다.
> 다만 거기서는 배치로 병합했고 여기서는 실행 중에 합친다."

카드가 묻는 건 "왜 같은 얘기인가"와 "그럼 뭐가 다른가" 두 가지입니다. 아래에서 나눠 봅니다.

---

## 1. 같은 문제를 푼다 — 상충하는 값 여러 개를 하나로

두 장은 부(部)도 다르고 트랙도 다릅니다. 14장은 3부 지식 그래프 엔지니어링, 19장은 4부 에이전트 그래프 엔지니어링이죠. 그런데 핵심 문제는 문장 하나로 겹칩니다.

**같은 대상에 대해 서로 다른 값이 둘 이상 도착했다. 무엇을 남길 것인가.**

### 14장의 상황 — 같은 회사가 레코드 세 건

`content/ch14/code/ex5_survivorship.py`를 보면 「가온테크」한 곳이 세 개의 레코드로 앉아 있습니다.

| id | 출처 | 갱신일 | name | ceo | tel | addr |
|---|---|---|---|---|---|---|
| r01 | ERP | 2024-03-01 | 가온테크 | 김하늘 | 02-1234-5678 | 서울 강남구 테헤란로 1 |
| r02 | CRM | 2026-01-15 | (주)가온테크 | 박서준 | (빈 값) | 서울 강남구 테헤란로 1길 22 |
| r04 | 명함스캔 | 2025-07-09 | GAON TECH | (빈 값) | 02-1234-5679 | (빈 값) |

대표자가 「김하늘」과 「박서준」으로 갈렸습니다. 주소도 셋 다 다릅니다. 하나로 합쳐야 하는데, 무엇을 남길까요.

14장의 답은 **필드마다 규칙을 못 박아 두는 것**입니다.

```python
RULES = {
    "name": "가장 신뢰도 높은 출처",
    "ceo":  "가장 최근",
    "tel":  "가장 최근 중 비어 있지 않은 것",
    "addr": "가장 긴 값",
}
```

이게 **생존 규칙(survivorship rules)** 입니다. 14장 한 장 요약의 마지막 줄이 이걸 정리합니다.

> "생존 규칙은 필드마다 다르게 정합니다. 그리고 빈 값과 자리표시자는 절대 이기지 못하게 하세요. 한 줄인데 사고의 절반을 막습니다."

### 19장의 상황 — 노드 둘이 같은 필드에 동시에 쓴다

`ex3_custom_reducer.py`는 **똑같은 데이터**를 씁니다. 우연이 아니라 의도적인 대칭입니다.

```python
def src_erp(s):
    return {"담당": {"who": "김하늘", "at": "2024-03-01"},
            "분류": {"cat": "제조", "conf": 0.7},
            "속성": {"사업자번호": "123-45-67890", "등급": "A"},
            "태그": ["제조", "중견"]}

def src_crm(s):
    return {"담당": {"who": "박서준", "at": "2026-01-15"},
            "분류": {"cat": "유통", "conf": 0.9},
            "속성": {"등급": "B", "지역": "수도권"},
            "태그": ["중견", "수도권"]}
```

같은 김하늘/박서준, 같은 ERP/CRM, 같은 날짜입니다. 다만 이번엔 두 출처가 **그래프의 노드**가 되어 같은 슈퍼스텝에서 동시에 실행됩니다. 그리고 규칙은 타입 어노테이션에 붙습니다.

```python
class S(TypedDict):
    담당:   Annotated[dict, keep_latest]     # 가장 최근
    분류:   Annotated[dict, keep_best]       # 신뢰도 높은 쪽
    속성:   Annotated[dict, merge_dict]      # 키 단위 병합
    태그:   Annotated[list, collect_unique]  # 중복 뺀 이어 붙이기
```

`RULES` 딕셔너리가 `Annotated[...]` 로 이사했을 뿐, 하는 일은 같습니다. **필드마다 다른 합치기 규칙.** 그래서 "같은 얘기"입니다.

### 이름만 다른 같은 개념

| | 14장 | 19장 |
|---|---|---|
| 이름 | 생존 규칙 (survivorship rule) | 리듀서 (reducer) |
| 붙는 자리 | `RULES` 딕셔너리 / 병합 코드 | 상태 타입의 `Annotated[T, fn]` |
| 대상 | 레코드 여러 건의 같은 필드 | 노드 여러 개가 같은 필드에 낸 갱신 |
| 규칙 예 | 가장 최근 / 신뢰도 높은 출처 / 가장 긴 값 | `keep_latest` / `keep_best` / `merge_dict` |
| 없으면 | 개발자가 그때그때 정하고 6개월 뒤 아무도 모름 | 갱신이 사라지거나(운 나쁘면) 예외(운 좋으면) |

그리고 두 장 모두 같은 결론에 닿습니다. **"어떻게 합칠까"는 프레임워크가 정해 줄 수 없는 도메인 지식이다.** 14장은 "대표자는 바뀌는 값이니 최근이 맞고, 사업자번호는 안 바뀌는 값이니 신뢰도 높은 출처가 맞다"고 쓰고, 19장 ex3의 제목은 아예 "«어떻게 합칠까»가 도메인 지식이다"입니다.

## 2. 다른 것 — 언제 합치느냐

같은 규칙인데 **적용 시점**이 다릅니다. 그리고 이 시점 차이가 제약의 차이를 만듭니다.

### 배치 시점 병합 (14장)

`ex5_survivorship.py`의 `pick` 함수를 보면 결정적인 대목이 있습니다.

```python
def pick(field, rows):
    cand = [r for r in rows if r.get(field)]
    if not cand:
        return None, "값이 없다"
    rule = RULES[field]
    if rule == "가장 신뢰도 높은 출처":
        r = max(cand, key=lambda x: SOURCE_TRUST.get(x["src"], 0))
    elif rule == "가장 최근":
        r = max(cand, key=lambda x: x["updated"])
    ...
```

`rows`가 통째로 들어옵니다. `max(cand, ...)` 는 **후보 전체를 한 번에 보고** 하나를 고릅니다. 이게 배치 병합의 특권입니다.

- **오프라인이다.** 합칠 시점에 데이터는 이미 다 모여 있고, 더 들어오지 않습니다.
- **전체를 보고 결정한다.** "이 셋 중 가장 최근"을 판단하려면 셋을 다 봐야 하는데, 볼 수 있습니다.
- **순서를 개발자가 정한다.** `rows`를 `sorted(rows, key=...)` 로 정렬한 뒤 앞에서부터 접어도 되고, 신뢰도 순으로 훑어도 됩니다. 순서가 결과를 바꾼다면 **원하는 순서로 강제하면 그만**입니다.
- **빈 값 걸러내기가 공짜다.** `[r for r in rows if r.get(field)]` 한 줄로 자리표시자를 후보에서 통째로 뺍니다. 전체를 손에 쥐고 있으니까요.
- **애매하면 사람에게 미룰 수 있다.** 14장이 임계를 두 개 두고 "위는 자동, 아래는 무시, 사이는 사람에게" 하는 것도 배치라 가능합니다. 오프라인 작업은 멈춰서 기다려도 됩니다.

### 실행 중 병합 (19장)

리듀서의 시그니처는 이렇습니다.

```python
def keep_latest(old, new):
    ...
```

인자가 **둘뿐**입니다. 누적값 하나와 방금 도착한 갱신 하나. 여기서 배치의 특권이 전부 사라집니다.

- **온라인이다.** 그래프가 돌아가는 중에, 노드가 값을 낼 때마다 실행기가 즉시 호출합니다.
- **도착한 것만 본다.** 뒤에 무엇이 더 올지, 몇 개가 더 올지 리듀서는 모릅니다. `max(cand)` 를 쓸 수 있는 `cand` 자체가 없습니다.
- **순서를 정할 수 없다.** 이게 핵심입니다. 어느 노드가 먼저 끝나는지는 실행기가 정하고, 개발자는 개입할 수 없습니다. `ex3`의 해설이 이걸 아프게 기록합니다.

  > "«태그» 순서도 보라. `['중견', '수도권', '제조']` 다. CRM 이 먼저 왔다는 뜻이다. 저는 ERP 를 먼저 등록했는데도."

  그래프에 `add_node("ERP", ...)` 를 먼저 썼는데 CRM이 먼저 실행됐습니다. 등록 순서는 실행 순서가 아닙니다.
- **버전이 올라가면 순서가 또 바뀔 수 있다.** 오늘 통과한 테스트가 라이브러리 업그레이드 후에 깨질 수 있다는 뜻입니다.
- **사람에게 물을 슬롯이 없다.** 리듀서는 실행기가 부르는 순수 함수입니다. (에이전트 실행 중 사람을 끼워 넣는 이야기는 이 책에서 23장으로 따로 빠져 있습니다.)

### 나란히 놓으면

| | 14장 — 배치 병합 | 19장 — 실행 중 병합 |
|---|---|---|
| 시점 | 오프라인, 데이터가 다 모인 뒤 | 온라인, 그래프가 도는 중 |
| 입력 | 후보 전체 (`rows`) | 누적값 하나 + 갱신 하나 (`old, new`) |
| 시야 | 전체를 보고 결정 | 도착한 것만 보고 즉시 결정 |
| 순서 | 개발자가 정함 (정렬 가능) | 실행기가 정함, 개입 불가 |
| 필요한 성질 | 결정론적이면 충분 | **교환법칙까지 필요** |
| 되돌리기 | 원본 보존 + 포인터 (14.3절) | 체크포인트 되감기 (19.5절) |

## 3. 그래서 실행 중 병합에는 교환법칙이라는 제약이 붙는다

이게 이 카드의 진짜 결론입니다. 19장 한 장 요약이 못을 박습니다.

> "리듀서는 교환법칙을 지켜야 합니다. `f(a,b) == f(b,a)`가 아니면 실행 순서에 따라 답이 달라지고, **그 순서는 여러분이 못 정해요.** 값 안에 판단 근거(시각, 출처, 신뢰도)를 넣으세요."

논리 사슬은 이렇습니다.

1. 실행 순서를 정할 수 없다.
2. 그런데 리듀서가 순서에 따라 다른 답을 내면, 결과가 실행마다 달라진다.
3. 따라서 리듀서는 순서와 무관해야 한다 → `f(a,b) == f(b,a)`.

배치 병합에는 이 요구가 없습니다. 순서에 의존하는 규칙을 써도, 원하는 순서를 만들어서 먹이면 되니까요. **같은 규칙인데 실행 중으로 옮기면 제약이 하나 늘어난다** — 이게 두 장의 관계를 이해하는 핵심입니다.

### 통과하는 리듀서

```python
def keep_latest(old, new):
    if not old: return new
    if not new: return old
    return new if new["at"] > old["at"] else old
```

`at`(시각)이 **값 안에** 들어 있습니다. 그래서 누가 먼저 도착하든 더 늦은 `at`을 가진 쪽이 이깁니다. `keep_best`도 `conf`(신뢰도)를 값에 담아 같은 방식으로 동작합니다. 19장 ex3 해설의 마지막 줄이 이걸 확인합니다.

> "«담당»과 «분류»가 그렇게 돼 있다. 순서와 무관하게 같은 답이 나온다."

`collect_unique`도 집합 관점에서는 순서 무관입니다. 다만 **결과 리스트의 순서**는 도착 순서를 따라가므로, 순서가 의미를 갖는 필드라면 여전히 조심해야 합니다.

### 판단 근거를 값 안에 넣는다는 것

"시각, 출처, 신뢰도를 값 안에 넣으라"는 조언이 왜 해법인지 보면 명확합니다.

리듀서는 두 값만 봅니다. 그러니 **순위를 매길 근거가 값 바깥에 있으면 리듀서가 접근할 수 없습니다.** 근거를 값 안에 넣으면, 리듀서는 순서와 무관하게 "둘 중 어느 쪽이 위인가"를 결정할 수 있습니다. 그러면 `f(a,b)`든 `f(b,a)`든 답은 같습니다.

14장도 사실 같은 말을 합니다. 다만 이유가 다릅니다.

> "그리고 고른 값마다 «어디서 왔는지»를 같이 저장한다. 그게 있어야 «이 대표자 이름 왜 이래요» 라는 문의에 답할 수 있다."

14장에서 출처를 붙이는 이유는 **설명 가능성**(누가 물었을 때 답하려고)입니다. 19장에서는 여기에 **정확성**이라는 이유가 하나 더 붙습니다. 출처와 시각이 없으면 답 자체가 실행마다 달라지니까요.

## 4. 배치 규칙을 그대로 리듀서로 옮길 때 생기는 함정

핵심 함정은 하나입니다.

> **배치 규칙은 "전체를 볼 수 있다"를 전제로 쓰였는데, 리듀서에게는 그 전제가 없다.**

규칙이 그럴듯해 보여서 그대로 복사하면, 전제가 깨진 자리에서 조용히 틀린 답이 나옵니다.

### 함정 A — "새 것이 이긴다"의 «새 것»이 뒤집힌다

19장 ex3에 저자가 직접 밟은 함정이 실려 있습니다. `속성` 필드의 리듀서입니다.

```python
def merge_dict(old, new):
    """키 단위 병합. 겹치면 새 것이 이긴다."""
    out = dict(old or {})
    out.update(new or {})
    return out
```

ERP는 `등급: "A"`, CRM은 `등급: "B"`를 냅니다. 저자의 기대는 "나중 것이 이긴다"였는데, 실제 결과는 **A**였습니다.

> "«속성»을 보라. 등급이 A(ERP)와 B(CRM) 로 갈렸는데 «A»가 남았다.
> `merge_dict` 는 «새 것이 이긴다»로 짰는데, 실행기가 CRM 을 먼저 돌려서
> ERP 가 «새 것»이 되어 버렸다. 코드를 짤 때 제가 기대한 것과 반대다."

무슨 일이 벌어졌나 뜯어보면, `merge_dict`가 말하는 "새 것"은 **`new` 인자에 담긴 것**, 즉 **나중에 도착한 것**입니다. 개발자가 머릿속에 그린 "새 것"은 **갱신일이 최근인 것**(CRM, 2026-01-15)이었고요. 배치였다면 `updated`로 정렬해서 먹이면 둘이 일치했을 겁니다. 실행 중에는 도착 순서가 실행기 마음이라, 두 의미가 갈라졌습니다.

`merge_dict`는 교환법칙을 어깁니다. `merge_dict(erp, crm)["등급"] == "B"`, `merge_dict(crm, erp)["등급"] == "A"`. 그리고 어느 쪽이 나올지는 개발자가 못 정합니다.

> "이게 함정이다. 순서에 기대는 리듀서는 «내가 예상한 답»을 안 낸다.
> 그리고 실행기 버전이 올라가면 순서가 또 바뀔 수 있다."

### 함정 B — 동률 처리에 숨은 순서 의존

`keep_best`의 독스트링은 "신뢰도가 높은 쪽. 같으면 **먼저 온 쪽**"입니다.

```python
return new if new["conf"] > old["conf"] else old
```

신뢰도가 다르면 순서와 무관합니다. 그런데 **같으면** `old`가 남습니다. `old`는 "먼저 도착한 것"이고, 도착 순서는 실행기가 정합니다. 즉 **동률일 때는 여전히 실행 순서가 답을 정합니다.**

14장의 `"addr": "가장 긴 값"` 규칙도 똑같은 구멍을 갖고 있습니다. `max(cand, key=len)`은 파이썬에서 동률이면 먼저 나온 원소를 남깁니다. 배치에서는 `rows` 순서가 고정이니 결과가 재현되지만, 리듀서로 옮기면 "먼저"가 실행기 마음이 됩니다.

**대처:** 동률 깨기(tie-break)도 **값에서 뽑을 수 있는 결정적 기준**으로 정합니다. 출처 이름, 레코드 ID처럼 값 안에 있고 순서와 무관한 것이면 됩니다. "먼저 온 쪽"은 배치에서만 결정적인 표현이고, 실행 중에는 결정적이지 않습니다.

### 함정 C — "전부 중에 고르기" 규칙이 통째로 안 옮겨진다

14장의 `pick`은 `cand` 전체를 손에 쥐고 있어서 이런 규칙을 쓸 수 있습니다.

- 후보 중 **과반**이 동의하는 값 (다수결)
- 후보 **개수**가 임계 이상일 때만 자동 채택 (14.2절의 두 임계)
- 후보 전체의 **분포**를 보고 이상치 제거

이런 규칙은 정의상 전체를 봐야 합니다. 리듀서의 `(old, new)` 안에는 전체가 없습니다. 그대로 옮기면 "본 것만으로 다수결"이 되어 답이 도착 순서에 따라 흔들립니다.

**대처:** 결정을 미룹니다. 리듀서는 **모으기만** 하고(예: `operator.add`나 `collect_unique`로 후보를 이어 붙임), 최종 판단은 모두 모인 뒤의 슈퍼스텝에서 별도 노드가 합니다. 19장이 순서를 원할 때 쓰라고 한 처방과 같은 도구입니다.

> "같은 슈퍼스텝의 노드들은 서로가 쓴 걸 못 봅니다. 같은 사본을 받으니까요. 순서가 필요하면 사이에 노드를 넣어 경계를 만드세요."

즉 **경계 노드가 실행 중에 만드는 작은 배치 구간**입니다. 그 노드 안에서는 다시 14장식으로 전체를 보고 고를 수 있습니다.

### 함정 D — 빈 값 걸러내기가 안 따라온다

14장은 `cand = [r for r in rows if r.get(field)]` 한 줄로 빈 값과 자리표시자를 후보에서 뺍니다. 이게 한 장 요약이 "한 줄인데 사고의 절반을 막는다"고 한 그 한 줄입니다.

리듀서에는 이 전처리 단계가 없습니다. 빈 값도 갱신 하나로 똑같이 도착하고, 순서에 따라 멀쩡한 값을 덮어쓸 수 있습니다. 19장의 리듀서들이 하나같이 `if not old: return new` / `if not new: return old`로 시작하는 건 우연이 아닙니다. **배치의 전처리 필터를 리듀서 안으로 끌고 들어온 것**입니다. 이 가드가 있어야 빈 값이 절대 못 이깁니다.

### 옮길 때의 점검표

배치 생존 규칙을 리듀서로 옮긴다면, 규칙마다 이걸 확인합니다.

1. `f(a, b) == f(b, a)` 인가? 반례를 손으로 하나 만들어 본다.
2. 동률일 때 무엇이 이기는가? 그 기준이 **값 안에서** 나오는가, 도착 순서에서 나오는가?
3. 판단 근거(시각·출처·신뢰도)가 값 안에 들어 있는가? 밖에 있다면 값 안으로 옮긴다.
4. 빈 값·자리표시자가 이길 수 있는 경로가 있는가?
5. 규칙이 "전체 중에서"를 요구하는가? 그렇다면 리듀서는 모으기만 하고, 경계 노드 뒤로 판단을 미룬다.
6. 결과 순서 자체가 의미를 갖는 리스트인가? 그렇다면 리듀서 밖에서 결정적으로 정렬한다.

## 한 줄 정리

**같은 문제, 같은 규칙, 다른 시점.** 14장은 데이터가 다 모인 뒤 전체를 보고 골라서 순서를 개발자가 정할 수 있고, 19장은 도착한 갱신만 보고 즉시 결정해야 하며 순서를 정할 수 없습니다. 그래서 실행 중 병합에는 **교환법칙**이라는 제약이 하나 더 붙고, 그걸 만족시키는 방법이 **판단 근거를 값 안에 담는 것**입니다.
