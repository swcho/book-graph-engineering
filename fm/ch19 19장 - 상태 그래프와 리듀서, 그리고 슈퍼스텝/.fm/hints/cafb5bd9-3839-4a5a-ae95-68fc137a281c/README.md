# 체크포인트가 슈퍼스텝마다 저장되는 것이 왜 문제가 되는가

> **Q.** 체크포인트가 슈퍼스텝마다 저장되는 것이 왜 문제가 되는가?
> **A.** 84KB짜리 검색 결과 원문처럼 바뀌지 않는 값도 매번 통째로 다시 저장된다.

---

## 1. 체크포인트는 「스냅샷」이지 「델타」가 아니다

체크포인트의 정의부터 다시 보면 문제가 보입니다.

- 노드는 **바꾼 부분만** 돌려줍니다 (19.1절). 여기까지는 델타입니다.
- 그런데 리듀서가 그 델타를 합치고 나면, 실행기가 저장하는 것은 **합쳐진 상태 전체**입니다.
- 즉 「반환값은 델타, 저장은 스냅샷」입니다. 이 비대칭이 이 카드의 핵심입니다.

슈퍼스텝이 끝날 때마다 실행기는 그 시점의 상태를 하나의 시점 이미지로 남깁니다. 「이번 스텝에서 `logs`만 바뀌었으니 `logs`만 적어 두자」가 기본 동작이 **아닙니다**. 개념상 매 경계마다 상태 전체를 직렬화해 다시 씁니다.

그래서 `ex4_state_size.py`가 마지막에 이렇게 못을 박습니다.

```
«검색 결과 원문»이 84KB 다. 이게 슈퍼스텝마다 다시 저장된다.
안 바뀌는데도 매번 통째로.
```

「안 바뀌는데도」가 결정적입니다. 검색 결과 원문은 검색 노드가 한 번 채우고 나면 실행이 끝날 때까지 한 글자도 안 바뀝니다. 그런데도 그 뒤의 모든 슈퍼스텝이 그 84KB를 자기 스냅샷 안에 다시 품습니다. 변하지 않는 값에 대해 변화 이력을 열네 벌 만드는 셈입니다.

---

## 2. 비용 계산 — 상태 크기 × 슈퍼스텝 수 × 실행(스레드) 수

`ex4_state_size.py`의 필드 판정표가 그대로 계산의 입력입니다.

| 필드 | 크기 | 다음 노드가 읽나 | 상태에 둘까 |
|---|---:|---|---|
| 질문 | 220B | 다음 노드가 읽는다 | 예 |
| 검색 결과 원문 | **84,000B** | 요약만 있으면 된다 | 아니오 |
| 검색 결과 주소 | 180B | 필요하면 다시 읽는다 | 예 |
| 검색 결과 요약 | 1,800B | 다음 노드가 읽는다 | 예 |
| 모델 원본 응답 | 12,000B | 로그에만 쓴다 | 아니오 |
| 중간 계산 캐시 | 31,000B | 같은 노드 안에서만 쓴다 | 아니오 |
| 실행 로그 | 6,400B | 사람이 나중에 본다 | 아니오 |
| 재시도 횟수 | 8B | 라우팅이 읽는다 | 예 |
| 체크포인트 메타 | 140B | 실행기가 쓴다 | 예 |

판정 기준은 딱 하나, **「다음 노드가 읽는가」**입니다. 이 기준으로 거르면:

- 전부 담으면 **135,748B**
- 필요한 것만 담으면 **2,348B**
- 차이 **57.8배**

여기에 슈퍼스텝 수(가정 14회)와 하루 실행 수(가정 1,200회)를 곱합니다.

```
비용 = 상태 크기 × 슈퍼스텝 수 × 실행(스레드) 수
```

| | 실행당 | 하루 | 월 저장비(GB당 25원) |
|---|---:|---:|---:|
| 전부 담기 (135,748B) | 1,900,472B ≈ **1.9MB** | 2.28GB | 약 **1,593원** |
| 필요한 것만 (2,348B) | 32,872B ≈ **33KB** | 0.04GB | 약 **28원** |

특히 84KB 원문 한 필드만 따로 떼어 보면:

```
84,000B × 14 슈퍼스텝 = 1,176,000B ≈ 1.18MB
```

실행 한 번이 만드는 1.9MB 중 **약 62%가 「한 번도 안 바뀐 원문」의 열네 번째 복사본까지**입니다. 값이 늘어난 게 아니라 같은 값을 열네 번 적었을 뿐입니다.

곱셈의 세 번째 항인 「스레드 수」도 잊으면 안 됩니다. 체크포인트는 `thread_id` 단위로 쌓이므로, 동시 사용자가 늘거나 대화가 길어져 슈퍼스텝이 14회에서 40회로 늘면 저 숫자는 선형이 아니라 두 축에서 동시에 늘어납니다.

---

## 3. 진짜 값은 저장 용량이 아니라 「직렬화 지연」이다

여기서 카드를 얕게 읽으면 「디스크 낭비」로 끝납니다. 예제의 결론은 정반대입니다.

```
한 가지 덧붙이면, 저장비 자체는 큰 돈이 아니다. 월 1,600원이다.
진짜 값은 «직렬화 시간»이다. 1.9MB 를 슈퍼스텝마다 쓰고 읽으면
지연이 붙고, 그게 사용자가 기다리는 시간이 된다.
18장에서 잰 체크포인트 40~120ms 가 여기서 몇 배가 된다.
```

비용의 성격을 나눠 보면:

| 비용 종류 | 크기 | 누가 부담하나 |
|---|---|---|
| 저장 용량 | 월 1,600원 | 회사 (무시할 만함) |
| **직렬화/역직렬화 지연** | 슈퍼스텝마다 40~120ms의 몇 배 | **사용자 대기 시간** |

저장비는 배치로 지불되고 나중에 청구서로 옵니다. 직렬화 지연은 **실행 경로 위에서** 지불됩니다. 슈퍼스텝 경계는 노드가 다음으로 넘어가기 전에 반드시 지나야 하는 관문이고, 체크포인트 쓰기는 그 관문에서 일어납니다. 즉 매 경계마다 「1.9MB 직렬화 + 네트워크 왕복 + DB 쓰기」가 사용자가 답을 기다리는 시간에 그대로 더해집니다. 14번이면 14번 더해집니다.

부수 효과 하나가 더 있습니다. 상태가 작아지면 「이 노드가 무엇에 의존하는가」가 **타입 정의만 봐도** 보입니다. 큰 상태는 성능만 나쁜 게 아니라 읽기도 나쁩니다.

책의 실무 기준선:

> **상태 하나가 8KB를 넘으면 무엇을 뺄지 찾는다.**

## 4. 완화책 세 가지

`ex4`가 제시하는 두 가지에 운영 항목 하나를 더하면 셋입니다.

### (1) 오프로딩 — 상태에는 「주소」만 (권장)

원문 84,000B를 밖(객체 스토리지, 캐시, 문서 DB)에 두고 상태에는 주소 180B만 넣습니다. 표에서 「검색 결과 주소 / 필요하면 다시 읽는다 / 예」가 정확히 이 설계입니다.

```
1. 상태에 안 넣는다 — 원문은 밖에 두고 상태에는 «주소»만 (24장 오프로딩)
```

책은 이 방법이 **「1번이 확실하다」**고 못 박습니다. 어떤 체크포인터를 쓰든, 버전이 올라가든 상관없이 효과가 보장되는 유일한 방법이기 때문입니다.

### (2) 체크포인터가 「바뀐 것만」 저장하게 하기 — 구현이 지원해야 한다

```
2. 체크포인터가 «바뀐 것만» 저장하게 한다 — 구현이 지원해야 한다
```

「구현이 지원해야 한다」는 단서가 붙은 이유는 아래 5절에서 확인합니다. 같은 LangGraph 안에서도 체크포인터마다 다릅니다.

### (3) 보존 기간(TTL) 설정

이건 「한 실행이 만드는 양」이 아니라 「쌓인 양」을 줄이는 축입니다. LangGraph 공식 문서도 긴 대화에서 체크포인트가 누적되면 지연과 저장 비용이 늘어난다고 인정하며, **N일보다 오래된 체크포인트를 지우는 주기적 정리(cron 등)**를 권합니다. LangGraph Platform을 쓰면 `langgraph.json`의 `checkpointer.ttl` 블록(`default_ttl`, `sweep_interval_minutes`, `strategy`)으로 유휴 스레드를 백그라운드 스위퍼가 자동 정리합니다. TTL 시계는 스레드에 활동이 있을 때마다 초기화되므로 「생성 시점」이 아니라 「마지막 활동 시점」 기준입니다. 코드 레벨에서는 `BaseCheckpointSaver.delete_thread()` / `adelete_thread()`가 특정 스레드의 체크포인트와 writes를 통째로 지웁니다.

> 19장의 다른 조언과도 맞물립니다 — **켜는 코드와 지우는 코드를 같은 커밋에 쓰세요.**

## 5. LangGraph의 실제 checkpointer는 어떻게 저장하는가 (확인된 사실만)

「구현이 지원해야 한다」가 무슨 뜻인지, 실제 구현을 확인하면 이렇습니다.

### 공통 구조

체크포인트는 `thread_id` + `checkpoint_ns`(네임스페이스, 기본값 `''`) + `checkpoint_id`의 세 값으로 식별됩니다. 서브그래프가 있으면 `checkpoint_ns`가 갈립니다. 직렬화는 `JsonPlusSerializer`가 기본이고, 내부적으로 ormsgpack을 쓰되 LangChain/LangGraph 타입·datetime·enum 등은 확장 JSON 형식으로 폴백합니다.

### PostgresSaver — 채널별 blob 분리, 버전 단위 저장

`checkpoints`와 별개로 `checkpoint_blobs` 테이블이 있습니다.

```sql
CREATE TABLE IF NOT EXISTS checkpoint_blobs (
    thread_id TEXT NOT NULL,
    checkpoint_ns TEXT NOT NULL DEFAULT '',
    channel TEXT NOT NULL,
    version TEXT NOT NULL,
    type TEXT NOT NULL,
    blob BYTEA,
    PRIMARY KEY (thread_id, checkpoint_ns, channel, version)
);
```

기본키가 `(thread_id, checkpoint_ns, channel, version)`이라는 점이 핵심입니다. `checkpoint_id`가 들어 있지 **않습니다**. 즉 채널 값은 체크포인트마다가 아니라 **「채널 × 버전」마다 한 벌**만 저장됩니다. 그리고 `put()`은 `new_versions`에 들어 있는 채널만 순회하며 직렬화합니다 — 이번 슈퍼스텝에 버전이 바뀌지 않은 채널은 다시 쓰지 않습니다.

### InMemorySaver — 같은 전략

인메모리 구현도 blob 저장소가 `(thread_id, checkpoint_ns, channel, version) → (type, bytes)` 맵이고, `put()`은 `new_versions.items()`만 돌며 직렬화합니다. 즉 구조는 Postgres와 같습니다.

### SqliteSaver — 통짜 스냅샷

반면 `SqliteSaver`는 별도 채널 blob 테이블이 없습니다. `checkpoints` 테이블의 `checkpoint BLOB` 컬럼 하나에 `channel_values`를 **인라인으로 통째로** 직렬화해 넣습니다.

```sql
CREATE TABLE IF NOT EXISTS checkpoints (
    thread_id TEXT NOT NULL,
    checkpoint_ns TEXT NOT NULL DEFAULT '',
    checkpoint_id TEXT NOT NULL,
    parent_checkpoint_id TEXT,
    type TEXT,
    checkpoint BLOB,
    metadata BLOB,
    PRIMARY KEY (thread_id, checkpoint_ns, checkpoint_id)
);
```

여기서는 **카드의 진술이 문자 그대로 성립합니다** — 84KB 원문이 매 슈퍼스텝의 체크포인트 blob 안에 다시 들어갑니다.

### 그래서 정리하면

| 체크포인터 | 채널별 분리 | 안 바뀐 채널 재직렬화 |
|---|---|---|
| PostgresSaver | `checkpoint_blobs` 테이블, `(channel, version)` 키 | 안 함 (`new_versions`만 처리) |
| InMemorySaver | `(thread_id, ns, channel, version)` 맵 | 안 함 (`new_versions`만 처리) |
| SqliteSaver | 없음 — `checkpoint` BLOB에 인라인 | **함** |

**단정하지 말아야 할 것:** 위 표는 확인 시점의 오픈소스 구현 기준입니다. 다른 서드파티 체크포인터(Redis 등)나 향후 버전이 어느 전략을 쓰는지는 각 구현을 직접 확인해야 합니다. 그리고 값이 실제로 바뀌지 않아도 **노드가 그 채널에 쓰기를 하면 버전이 올라가므로**, Postgres/InMemory에서도 「매 슈퍼스텝마다 원문을 상태에 다시 써 넣는」 코드라면 재직렬화가 그대로 일어납니다. 채널별 분리는 「안 건드린 채널」을 아껴 줄 뿐, 「같은 값을 다시 쓰는 코드」를 구해 주지는 않습니다.

이래서 책이 1번(오프로딩)을 「확실하다」고 하는 것입니다. 2번은 어떤 체크포인터를 쓰는지, 노드가 그 필드에 쓰기를 하는지에 전부 달려 있습니다.

---

## 6. 한 줄 정리

체크포인트는 슈퍼스텝 경계마다 상태를 **스냅샷**으로 남기므로, 84KB짜리 검색 결과 원문처럼 실행 내내 한 번도 안 바뀌는 값도 매번 다시 저장됩니다. 실행 한 번에 1.9MB, 그 62%가 원문의 중복 사본입니다. 아픈 곳은 월 1,600원짜리 저장비가 아니라 **매 경계마다 사용자 대기 시간에 그대로 더해지는 직렬화/역직렬화 지연**이고, 가장 확실한 처방은 원문을 밖에 두고 상태에는 주소만 남기는 것입니다.
