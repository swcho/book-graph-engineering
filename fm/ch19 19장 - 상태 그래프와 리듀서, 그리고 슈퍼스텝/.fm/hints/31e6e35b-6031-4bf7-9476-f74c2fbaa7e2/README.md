# `merge_dict`가 저자의 기대와 반대로 동작한 이유

> **Q.** `merge_dict`가 저자의 기대와 반대로 동작한 이유는 무엇인가?
>
> **A.** "새 것이 이긴다"로 짰지만 실행기가 CRM을 먼저 돌려 ERP가 '새 것'이 되었다. 등급이 B가 아니라 A로 남았다.

출처: `content/ch19/code/ex3_custom_reducer.py` (19.3 「합치는 규칙이 도메인 지식이다」)

---

## 1. 문제의 코드

리듀서 본체는 세 줄입니다.

```python
def merge_dict(old, new):
    """키 단위 병합. 겹치면 새 것이 이긴다."""
    out = dict(old or {})
    out.update(new or {})
    return out
```

이 리듀서가 붙은 필드는 `속성` 하나입니다.

```python
class S(TypedDict):
    담당:   Annotated[dict, keep_latest]      # at 을 비교
    분류:   Annotated[dict, keep_best]        # conf 를 비교
    속성:   Annotated[dict, merge_dict]       # ← 문제의 필드
    태그:   Annotated[list, collect_unique]
```

두 노드가 같은 슈퍼스텝에서 `속성`에 각각 값을 씁니다.

```python
def src_erp(s):
    return {..., "속성": {"사업자번호": "123-45-67890", "등급": "A"}, ...}

def src_crm(s):
    return {..., "속성": {"등급": "B", "지역": "수도권"}, ...}

b = StateGraph(S)
b.add_node("ERP", src_erp)     # ← 저자는 ERP 를 «먼저» 등록했다
b.add_node("CRM", src_crm)
b.add_edge(START, "ERP")
b.add_edge(START, "CRM")       # ← 둘 다 START 에서 나가므로 «같은 슈퍼스텝»
```

저자가 상상한 시나리오는 이렇습니다. "ERP는 낡은 기간계, CRM은 최근에 영업이 고친 값이다. 겹치면 CRM(= 새 것)이 이겨야 하니까 `등급`은 **B**가 남는다."

실제 실행 결과는 반대였습니다. 책 본문의 해설이 그대로 정답입니다.

```
«속성»을 보라. 등급이 A(ERP)와 B(CRM) 로 갈렸는데 «A»가 남았다.
merge_dict 는 «새 것이 이긴다»로 짰는데, 실행기가 CRM 을 먼저 돌려서
ERP 가 «새 것»이 되어 버렸다. 코드를 짤 때 제가 기대한 것과 반대다.

«태그» 순서도 보라. ['중견', '수도권', '제조'] 다. CRM 이 먼저 왔다는 뜻이다.
저는 ERP 를 먼저 등록했는데도.
```

`태그`가 결정적인 물증입니다. `collect_unique`는 순서를 보존하는데, 결과가 `['중견', '수도권', '제조']`입니다. `중견`·`수도권`은 CRM이 낸 값이고 `제조`는 ERP가 낸 값이니, 실행기가 **CRM 갱신을 먼저 접었다(fold)**는 뜻입니다. `add_node("ERP", ...)`를 먼저 썼는데도 말이죠.

## 2. 핵심 - "나중 인자가 이긴다" ≠ "새 것이 이긴다"

`dict.update`(그리고 `{**a, **b}`)의 규칙은 딱 한 문장입니다.

> **키가 겹치면 인자 목록에서 오른쪽/나중에 온 쪽이 이긴다.**

여기서 "나중"은 **함수를 호출할 때의 인자 위치**입니다. 시간도, 신선도도, 도메인상의 최신성도 아닙니다. `{**a, **b}`에서 `b`가 이기는 건 `b`가 더 최근 데이터라서가 아니라, 그냥 코드에 두 번째로 적혀 있어서입니다.

`merge_dict(old, new)`의 파라미터 이름 `new`가 이 착각을 정확히 증폭시킵니다.

| 개발자가 읽은 뜻 | 실제 뜻 |
|---|---|
| `new` = 도메인상 더 최신인 데이터 (CRM) | `new` = 실행기가 이번 차례에 넘겨준 갱신 |
| `old` = 낡은 데이터 (ERP) | `old` = 지금까지 접어 온 누적값 |
| 승자를 내가 정한다 | 승자를 **실행기의 호출 순서**가 정한다 |

`docstring`에 "새 것이 이긴다"라고 적힌 순간, 코드가 실제로 표현하는 것("두 번째 인자가 이긴다")과 주석이 약속하는 것("도메인상 새 값이 이긴다") 사이에 틈이 생겼습니다. 그 틈을 메꿔 줄 근거가 값 안에 하나도 없습니다. `{"등급": "A"}`라는 값만 보고서는 이게 언제 것인지, 어디서 온 것인지 알 방법이 없으니까요.

반면 같은 파일의 `keep_latest`/`keep_best`는 인자 위치를 **전혀** 보지 않습니다.

```python
def keep_latest(old, new):
    return new if new["at"] > old["at"] else old      # at 이 판정한다

def keep_best(old, new):
    return new if new["conf"] > old["conf"] else old  # conf 가 판정한다
```

값 안에 `at`, `conf`라는 **판단 근거**가 들어 있어서, `old`와 `new`가 뒤바뀌어 들어와도 답이 같습니다. 그래서 책 마지막 줄이 "«담당»과 «분류»가 그렇게 돼 있다. 순서와 무관하게 같은 답이 나온다"인 겁니다.

## 3. 리듀서는 어떻게 접히는가 (fold)

한 슈퍼스텝에서 같은 채널(필드)에 갱신이 N개 들어오면, 실행기는 그 갱신들을 **왼쪽으로 접습니다**. 개념적으로:

```
값 = 이전_상태값
for 갱신 in 실행기가_정한_순서(갱신들):
    값 = reducer(값, 갱신)      # 누적값이 old, 다음 갱신이 new
```

즉 `functools.reduce(reducer, 갱신들, 이전값)`입니다. `old`는 "먼저 쓴 노드의 값"이 아니라 **지금까지의 누적값**이고, `new`는 "더 새 데이터"가 아니라 **다음 차례로 뽑힌 갱신**입니다.

이번 실행에서 실행기가 정한 순서는 `[CRM, ERP]`였습니다. 그러니 `속성` 채널은 이렇게 접혔습니다.

| 단계 | `old` (누적) | `new` (다음 갱신) | 결과 |
|---|---|---|---|
| 초기 | — | — | `{}` (invoke 초기값) |
| 1 | `{}` | CRM `{등급: B, 지역: 수도권}` | `{등급: B, 지역: 수도권}` |
| 2 | `{등급: B, 지역: 수도권}` | ERP `{사업자번호: …, 등급: A}` | `{등급: A, 지역: 수도권, 사업자번호: …}` |

2단계에서 ERP가 `new` 자리에 앉았고, `out.update(new)`가 `등급: B`를 `등급: A`로 덮었습니다. 이게 전부입니다.

**개발자가 이 순서를 정할 수 없다는 게 요점입니다.** 노드 등록 순서(`add_node`)도, 엣지 추가 순서(`add_edge`)도 계약이 아닙니다. 같은 슈퍼스텝의 노드들은 논리적으로 **동시**이고, 그 안에서 갱신이 큐에 담기는 순서는 실행기의 내부 사정(스케줄러, 태스크 완료 시각, 자료구조 순회 순서, 동기/비동기 여부)입니다. 저자가 ERP를 먼저 등록하고도 CRM이 먼저 접힌 게 바로 그 증거입니다.

그래서 19장 요약이 이렇게 못을 박습니다.

> 리듀서는 교환법칙을 지켜야 합니다. `f(a,b) == f(b,a)`가 아니면 실행 순서에 따라 답이 달라지고, 그 순서는 여러분이 못 정해요. 값 안에 판단 근거(시각, 출처, 신뢰도)를 넣으세요.

정확히는 세 가지가 필요합니다.

- **교환법칙** `f(a,b) == f(b,a)` — 어느 쪽이 먼저 접혀도 같은 답
- **결합법칙** `f(f(a,b),c) == f(a,f(b,c))` — 갱신이 셋 이상일 때 묶는 방식이 달라도 같은 답
- **멱등성** `f(a,a) == a` — 재시도로 같은 갱신이 두 번 들어와도 안전

`merge_dict`는 셋 중 첫 번째부터 어깁니다. `merge_dict(ERP, CRM)`은 `등급: B`, `merge_dict(CRM, ERP)`는 `등급: A`. 답이 두 개인 함수입니다.

## 4. 왜 이게 "조용한 버그"인가

이 버그가 위험한 이유는 **아무 신호도 남기지 않기 때문**입니다.

- **예외가 안 난다.** `ex1_lost_update.py`의 리듀서 없는 경우는 LangGraph가 "같은 필드를 여럿이 쓰려 한다"고 막아 주기라도 합니다. 여기는 리듀서가 **있으니** 프레임워크 입장에서는 정상 동작입니다. 개발자가 명시한 규칙대로 성실히 접었을 뿐이죠.
- **로그에 안 남는다.** 갱신이 유실된 것도 아니고, 경고가 뜨는 것도 아닙니다. 두 갱신 모두 정상 접수되었고 규칙대로 하나가 이겼습니다.
- **타입도 통과한다.** `속성: dict`는 A든 B든 똑같이 만족합니다.
- **틀린 건 결과값 하나뿐이다.** `등급`이 `B`여야 하는데 `A`입니다. 그것도 값의 "모양"은 완벽히 정상이라, 다운스트림에서 등급으로 할인율을 매기든 심사 라우팅을 하든 그냥 조용히 잘못된 분기를 탑니다.
- **재현이 어렵다.** 순서가 실행기 사정에 달렸으니 어떤 날은 B가 나올 수도 있습니다. "가끔 등급이 이상하다"는 티켓만큼 잡기 싫은 게 없습니다.

19장 도입부의 "누가 마지막이었는지도 매번 달랐거든요"가 이 감각입니다. 실패가 **예외**가 아니라 **값**의 형태로 나타나면, 테스트가 그 값을 콕 집어 단언하지 않는 한 프로덕션까지 그대로 흘러갑니다.

그리고 한 가지 더. 이 버그는 `merge_dict`를 아무리 노려봐도 안 보입니다. 세 줄짜리 함수 자체는 완벽히 옳거든요. 틀린 건 **함수와 실행기 사이의 암묵적 가정**이고, 그 가정은 코드 어디에도 적혀 있지 않습니다. 주석에만 적혀 있습니다.

## 5. 올바른 수정 - 판단 근거를 값 안으로

고치는 방향은 하나입니다. **병합 판정을 인자 위치에서 값 안의 근거로 옮긴다.** `keep_latest`/`keep_best`가 이미 하고 있는 그 방식을, 키 단위 병합에도 똑같이 적용합니다.

### 5-1. 값의 모양을 바꾼다

```python
# 전 — 판단할 근거가 없다
{"등급": "A", "사업자번호": "123-45-67890"}

# 후 — 셀마다 근거를 달고 다닌다
{"등급":       {"v": "A", "at": "2024-03-01", "src": "ERP"},
 "사업자번호": {"v": "123-45-67890", "at": "2024-03-01", "src": "ERP"}}
```

### 5-2. 키 단위로 근거를 비교한다

```python
# 출처 우선순위 — 같은 시각이면 어느 계통을 믿을지. 명시적으로 적어 둔다.
SRC_PRIORITY = {"CRM": 2, "ERP": 1}


def _rank(cell):
    """셀의 «강함»을 전순서(total order)로 만든다.

    1순위 갱신 시각, 2순위 출처 우선순위, 3순위 값 자체(완전 동률 깨기).
    3순위까지 두는 이유는 아래 «완전 동률» 항목 참고.
    """
    return (cell["at"], SRC_PRIORITY.get(cell["src"], 0), str(cell["v"]))


def merge_dict(old, new):
    """키 단위 병합. 겹치면 «인자 위치»가 아니라 «셀의 근거»가 이긴다."""
    out = dict(old or {})
    for k, cell in (new or {}).items():
        cur = out.get(k)
        # max 는 동률이면 첫 인자를 돌려준다. _rank 가 전순서라
        # 동률 = 실질적으로 같은 셀이므로 어느 쪽을 골라도 결과가 같다.
        out[k] = cell if cur is None else max(cur, cell, key=_rank)
    return out
```

이제 `속성` 채널은 CRM이 먼저 접히든 ERP가 먼저 접히든 `등급`에 대해 `at="2026-01-15"`인 CRM 셀을 고릅니다. 기대대로 **B**입니다. 겹치지 않는 `사업자번호`·`지역`은 양쪽 다 살아남고요.

### 5-3. 왜 3순위 동률 깨기까지 필요한가

동률일 때 "기존 것 유지"로 두면 다시 순서 의존이 됩니다.

```python
# 나쁜 동률 처리 — 겉보기엔 멀쩡하지만 교환법칙이 깨진다
if cand["at"] > cur["at"]:
    out[k] = cand          # 같으면 cur 유지 → f(a,b)=a, f(b,a)=b
```

`at`이 같고 `src` 우선순위도 같은 두 셀이 들어오면 `f(a,b)`는 `a`, `f(b,a)`는 `b`를 남깁니다. 다시 실행 순서가 답을 정하게 되는 겁니다. 그래서 `_rank`의 마지막 항으로 **값 자체**처럼 결정적인(deterministic) 키를 넣어 순서를 전순서로 닫아 둡니다. 임의적이지만 **재현 가능한** 승자가 나오는 편이, 재현 불가능한 승자보다 언제나 낫습니다.

### 5-4. 자기 점검 - 교환법칙을 테스트로 박아 둔다

리듀서는 순수 함수라 테스트가 싸게 먹힙니다. 리뷰어 눈을 믿지 말고 단언으로 못 박으세요.

```python
import itertools

def test_reducer_is_order_independent():
    updates = [
        {"등급": {"v": "A", "at": "2024-03-01", "src": "ERP"},
         "사업자번호": {"v": "123-45-67890", "at": "2024-03-01", "src": "ERP"}},
        {"등급": {"v": "B", "at": "2026-01-15", "src": "CRM"},
         "지역": {"v": "수도권", "at": "2026-01-15", "src": "CRM"}},
    ]
    results = []
    for perm in itertools.permutations(updates):
        acc = {}
        for u in perm:
            acc = merge_dict(acc, u)     # 실행기가 접는 방식 그대로 재현
        results.append(acc)
    assert all(r == results[0] for r in results)   # 순서를 바꿔도 같은 답
    assert results[0]["등급"]["v"] == "B"          # 기대한 도메인 규칙
```

첫 단언은 "실행 순서에 안 흔들린다", 둘째 단언은 "내가 의도한 승자가 맞다"를 잡습니다. **원래 `merge_dict`는 첫 단언에서 바로 실패합니다.** 즉 이 버그는 프로덕션 없이도 잡을 수 있었습니다.

### 5-5. 대안 - 순서 의존을 아예 없앤다

값 모양을 못 바꾸는 상황이라면 다른 선택지도 있습니다.

- **경계를 만든다.** ERP와 CRM을 같은 슈퍼스텝에 두지 말고 사이에 노드를 하나 넣어 순차로 만듭니다(19.2). 순서를 실행기가 아니라 **그래프 모양**이 정하게 하는 방식이라, 순서 의존 자체는 남지만 그게 명시적이 됩니다.
- **필드를 나눈다.** `속성_erp`, `속성_crm`처럼 채널을 분리해 애초에 충돌하지 않게 하고, 최종 판단은 뒤쪽 노드에서 한 번에 합칩니다.
- **다 모았다가 나중에 고른다.** 리듀서는 `collect_unique`처럼 모으기만 하고(모으기는 순서를 안 타게 만들기 쉽습니다) 승자 선택은 별도 노드에서 합니다.

## 6. 남은 위험 - 순서는 또 바뀐다

이번엔 CRM이 먼저였습니다. 다음번엔 아닐 수 있습니다. 책이 마지막에 남기는 경고가 이겁니다.

> 이게 함정이다. 순서에 기대는 리듀서는 «내가 예상한 답»을 안 낸다.
> 그리고 실행기 버전이 올라가면 순서가 또 바뀔 수 있다.

핵심은 **실행 순서가 공개된 계약이 아니라는 것**입니다. 예제의 확인 시점은 LangGraph 1.0.1인데, 이 순서는 문서에 보장된 동작이 아니라 그 시점 구현의 부산물입니다. 다음 중 무엇이든 순서를 뒤집을 수 있습니다.

- 실행기 버전 업 (스케줄러·태스크 큐 구현 변경)
- 동기 `invoke` → 비동기 `ainvoke` 전환, 혹은 병렬도 설정 변경
- 노드 내부가 I/O를 타면서 완료 시각이 뒤바뀌는 경우 (LLM 호출 지연, 캐시 히트/미스)
- 그래프를 조금 고쳐 노드가 하나 늘어난 경우

가장 나쁜 시나리오는 **버전을 올리기 전까지 우연히 맞는 답이 나오던 코드**입니다. 그동안 테스트가 초록이었으니 아무도 이 리듀서를 의심하지 않고, 순서가 바뀐 뒤에도 여전히 예외가 안 나므로 원인이 리듀서라는 데까지 도달하는 데 오래 걸립니다. 게다가 `pip install`로 버전 하나 올린 것과 "등급 필드가 이상하다"는 제보 사이에는 아무 인과의 흔적이 없습니다.

그래서 결론은 "이번 순서에 맞춰 `old`/`new`를 뒤집는다"가 **아닙니다**. 그건 다음 버전에서 또 뒤집힐 코드입니다. 순서에 대한 의존을 **없애는 것**만이 유효한 수정입니다.

## 한 줄 정리

`merge_dict`는 승패를 **인자 위치**로 정했고, 그 위치는 저자가 아니라 **실행기**가 정한다. 실행기가 CRM을 먼저 접는 바람에 ERP가 두 번째 인자(`new`)로 들어와 `등급`을 `B`에서 `A`로 덮었다. 고치려면 승패 판정을 위치가 아니라 값 안의 근거(`at`/`src`/`conf`)로 옮겨 `f(a,b) == f(b,a)`를 만들어야 한다.
