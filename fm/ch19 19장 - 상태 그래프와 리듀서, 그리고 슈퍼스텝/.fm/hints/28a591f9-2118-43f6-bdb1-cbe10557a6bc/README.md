# `keep_latest`와 `keep_best`가 순서와 무관한 이유

> **Q.** `keep_latest`와 `keep_best`가 순서와 무관한 이유는 무엇인가?
>
> **A.** 값 안에 `at`(시각)과 `conf`(신뢰도)가 들어 있어 어느 쪽이 먼저 오든 같은 답이 나온다.

---

## 1. 문제의 자리 — 리듀서는 "순서를 모르는 채로" 불린다

`ex3_custom_reducer.py`에서 `ERP`와 `CRM` 두 노드는 **같은 슈퍼스텝**에 들어갑니다.

```python
b.add_edge(START, "ERP")
b.add_edge(START, "CRM")
```

같은 슈퍼스텝에 있는 노드들은 서로가 쓴 값을 못 봅니다(19.2절). 둘 다 같은 상태 사본을 받고, 각자 부분 갱신을 돌려주고, 그 갱신들을 **리듀서가 접어서(fold)** 합칩니다. 리듀서 호출은 대략 이런 모양이 됩니다.

```
acc = 초기값
acc = reducer(acc, 갱신₁)
acc = reducer(acc, 갱신₂)
...
```

여기서 `갱신₁`, `갱신₂`가 ERP인지 CRM인지 — **그 순서를 정하는 건 실행기입니다.** 여러분이 `add_node`를 부른 순서도 아니고, `add_edge`를 부른 순서도 아닙니다. 예제 출력이 그걸 그대로 보여 줍니다.

```
«태그» 순서도 보라. ['중견', '수도권', '제조'] 다. CRM 이 먼저 왔다는 뜻이다.
저는 ERP 를 먼저 등록했는데도.
```

그리고 예제가 못 박듯이, 그 순서는 **실행기 버전이 올라가면 또 바뀔 수 있습니다.** 즉 순서는 여러분이 계약할 수 있는 대상이 아닙니다.

---

## 2. 두 부류로 갈리는 네 리듀서

`ex3`에는 리듀서가 넷 있습니다. 이걸 "순서를 보느냐 / 값을 보느냐"로 갈라 보면 답이 바로 나옵니다.

### 순서를 판단 근거로 쓰는 쪽 (❌ 순서 종속)

```python
def merge_dict(old, new):
    """키 단위 병합. 겹치면 새 것이 이긴다."""
    out = dict(old or {})
    out.update(new or {})
    return out
```

`"겹치면 새 것이 이긴다"`. 여기서 **"새 것"의 정의가 `new` 인자에 앉았다는 것뿐**입니다. `new`가 실제로 더 새로운 데이터라는 보장은 어디에도 없습니다. 값 안에 "새로움"을 알려 주는 게 하나도 없으니까요.

```python
"속성": {"사업자번호": "123-45-67890", "등급": "A"}   # ERP
"속성": {"등급": "B", "지역": "수도권"}                # CRM
```

그래서 예제가 이렇게 자백합니다.

```
«속성»을 보라. 등급이 A(ERP)와 B(CRM) 로 갈렸는데 «A»가 남았다.
merge_dict 는 «새 것이 이긴다»로 짰는데, 실행기가 CRM 을 먼저 돌려서
ERP 가 «새 것»이 되어 버렸다. 코드를 짤 때 제가 기대한 것과 반대다.
```

`collect_unique`도 결과 값 자체는 같은 원소 집합이지만 **순서**가 실행기에 종속됩니다(`['중견','수도권','제조']` vs `['제조','중견','수도권']`).

### 값을 판단 근거로 쓰는 쪽 (✅ 순서 무관)

```python
def keep_latest(old, new):
    """타임스탬프가 더 최근인 쪽을 남긴다."""
    if not old:
        return new
    if not new:
        return old
    return new if new["at"] > old["at"] else old


def keep_best(old, new):
    """신뢰도가 높은 쪽. 같으면 먼저 온 쪽."""
    if not old:
        return new
    if not new:
        return old
    return new if new["conf"] > old["conf"] else old
```

이 둘은 `old` / `new`라는 **자리(position)를 전혀 보지 않습니다.** `old["at"]`, `new["at"]`이라는 **값 안의 필드**를 꺼내서 비교할 뿐입니다. 그래서 두 인자를 서로 바꿔 넣어도 비교 결과가 뒤집히지 않습니다.

```python
"담당": {"who": "김하늘", "at": "2024-03-01"}   # ERP
"담당": {"who": "박서준", "at": "2026-01-15"}   # CRM
```

`"2026-01-15" > "2024-03-01"`은 어느 쪽이 `old`든 `new`든 참입니다. 따라서 답은 항상 박서준. 마찬가지로 `0.9 > 0.7`이므로 분류는 항상 `{"cat":"유통","conf":0.9}`입니다.

> 참고: `at`이 ISO-8601 `YYYY-MM-DD` 문자열이라 문자열 사전순 비교가 곧 시간순 비교가 됩니다. 이건 우연이 아니라 ISO-8601을 쓰는 이유 중 하나입니다. `"2026/1/15"` 같은 포맷을 섞으면 이 성질이 깨집니다.

## 3. 이게 곧 교환법칙 — `f(a, b) == f(b, a)`

19장의 한 장 요약이 요구하는 조건입니다.

```
리듀서는 교환법칙을 지켜야 합니다. f(a,b) == f(b,a)가 아니면 실행 순서에
따라 답이 달라지고, 그 순서는 여러분이 못 정해요.
값 안에 판단 근거(시각, 출처, 신뢰도)를 넣으세요.
```

**"값 안에 판단 근거를 넣는다"가 곧 "교환법칙을 만든다"입니다.** 순서 자체를 근거로 쓰면 뒤집었을 때 답이 뒤집히고, 값을 근거로 쓰면 뒤집어도 그대로입니다. 코드로 확인해 봅시다.

```python
ERP = {"who": "김하늘", "at": "2024-03-01"}
CRM = {"who": "박서준", "at": "2026-01-15"}

print(keep_latest(ERP, CRM) == keep_latest(CRM, ERP))   # True  ✅
print(keep_latest(ERP, CRM))                            # 박서준
print(keep_latest(CRM, ERP))                            # 박서준

A = {"cat": "제조", "conf": 0.7}
B = {"cat": "유통", "conf": 0.9}
print(keep_best(A, B) == keep_best(B, A))               # True  ✅

# 대조군
E = {"사업자번호": "123-45-67890", "등급": "A"}
C = {"등급": "B", "지역": "수도권"}
print(merge_dict(E, C) == merge_dict(C, E))             # False ❌
print(merge_dict(E, C)["등급"])                          # B
print(merge_dict(C, E)["등급"])                          # A
```

`merge_dict`는 인자를 바꾸면 `등급`이 B↔A로 뒤집힙니다. 그래서 실행 순서가 곧 답이 됩니다. `keep_latest`/`keep_best`는 뒤집어도 그대로입니다. 그래서 실행 순서를 몰라도 답을 예측할 수 있습니다.

### 왜 "값에 전순서를 매길 수 있는 필드"인가

수학적으로 이야기하면, 리듀서가 순서에 무관하려면 그 연산이 **교환법칙 + 결합법칙**을 만족해야 합니다(가환 반군, commutative semigroup). 갱신이 셋 이상이면 접는 방식(괄호)까지 달라질 수 있으니까요.

`keep_latest`는 `max_at`이라는 이름을 붙일 수 있는 연산입니다. `max`가 순서와 무관한 이유는 명확합니다 — **비교 대상 값들 위에 전순서(total order)가 정의돼 있고, 그중 최대는 유일하기 때문**입니다.

- 순서를 근거로 쓴다 = "누가 먼저 왔나"라는, 값 바깥에 있고 실행기가 정하는 축을 쓴다
- 값을 근거로 쓴다 = "`at`이 큰 쪽"이라는, 값 안에 있고 실행기가 못 건드리는 축을 쓴다

**요컨대 `at`과 `conf`는 "순서"라는 판단 축을 값 안으로 끌어들여 실행기로부터 회수한 것입니다.** 그래서 "순서 대신 값을 보게 만든다"가 이 장의 핵심 원리입니다.

## 4. ⚠️ 주의 — 완전히 순서 무관은 아니다

여기가 이 카드에서 가장 중요한 지점입니다. 위 코드는 **동률(tie)에서 다시 순서로 되돌아갑니다.**

### 구멍 ①: `keep_best`의 docstring이 이미 자백하고 있다

```python
def keep_best(old, new):
    """신뢰도가 높은 쪽. 같으면 먼저 온 쪽."""
```

`"같으면 먼저 온 쪽"` — 이 "먼저"가 바로 **실행기가 정하는 순서**입니다. 즉 `conf`가 같은 순간, 이 리듀서는 순서 종속으로 되돌아갑니다.

```python
A = {"cat": "제조", "conf": 0.8}
B = {"cat": "유통", "conf": 0.8}

keep_best(A, B)   # 0.8 > 0.8 이 거짓 → old 유지 → {"cat":"제조"}
keep_best(B, A)   # 0.8 > 0.8 이 거짓 → old 유지 → {"cat":"유통"}
# f(a,b) != f(b,a)  ❌ 교환법칙 붕괴
```

`keep_latest`도 똑같습니다. `at`이 둘 다 `"2026-01-15"`(날짜 단위라 하루 안에 들어오면 충돌하기 쉽습니다)면 결과는 실행 순서 그대로입니다.

### 구멍 ②: `>` 냐 `>=` 냐에 따라 답이 갈린다

동률 구간에서는 비교 연산자 하나가 답을 바꿉니다.

| 비교 | `conf` 동률일 때 | 성질 |
|---|---|---|
| `new["conf"] > old["conf"]` | `old`(먼저 온 쪽)가 이김 | 순서 종속 |
| `new["conf"] >= old["conf"]` | `new`(나중 온 쪽)가 이김 | 순서 종속 |

**둘 다 순서 종속입니다.** `>`를 `>=`로 바꿔도 문제는 해결되지 않고 승자만 반대편으로 옮겨 갑니다. 실제 사고는 여기서 납니다 — 리뷰에서 "`>`라 안전하다"고 넘기고, 나중에 동률 데이터가 들어오면서 답이 흔들립니다.

### 해법: 전순서 튜플 키 (tie-break chain)

동률을 **다음 값 필드로** 계속 넘겨서, 마지막 필드가 **절대 겹치지 않도록** 만듭니다. 마지막 칸에는 출처 ID처럼 유일성이 보장된 값을 둡니다.

```python
def rank(v):
    """값 하나를 전순서 튜플로 바꾼다. 마지막 src 가 유일하므로 동률이 없다."""
    return (v["conf"], v["at"], v["src"])


def keep_best_total(old, new):
    """신뢰도 → 시각 → 출처ID 순으로 비교. 동률이 없으므로 순서와 완전히 무관."""
    if not old:
        return new
    if not new:
        return old
    return new if rank(new) > rank(old) else old
```

노드는 값에 `src`를 같이 실어 보냅니다.

```python
def src_erp(s):
    return {"분류": {"cat": "제조", "conf": 0.8,
                     "at": "2026-01-15", "src": "erp"}}

def src_crm(s):
    return {"분류": {"cat": "유통", "conf": 0.8,
                     "at": "2026-01-15", "src": "crm"}}
```

이제 `conf`가 같고 `at`도 같아도 `("erp" < "crm")`에서 결판이 납니다. 실행기가 어느 쪽을 먼저 돌리든 항상 CRM이 이깁니다. 튜플 비교는 파이썬이 사전식(lexicographic)으로 처리하므로 `rank()` 한 줄이면 됩니다.

**핵심 규칙:** 튜플의 마지막 칸은 반드시 **모든 갱신에서 서로 다르다고 보장되는 값**이어야 합니다. 출처 ID, 노드 이름, 이벤트 UUID 같은 것들이요. 여기가 겹치면 tie-break 사슬은 다시 끊깁니다.

> 부가 이득: `rank()`가 진짜 전순서이면 이 리듀서는 `max`가 되고, 자동으로 **결합법칙**과 **멱등성(idempotency)**까지 얻습니다. 멱등이라는 건 같은 갱신이 재시도로 두 번 들어와도 답이 안 바뀐다는 뜻이라, 18장의 재시도 이야기와 그대로 이어집니다.

## 5. 실무 함정 — 시계를 믿을 수 있는가

`at`으로 순서를 정하는 순간 "시계는 정확하다"는 가정을 몰래 깔게 됩니다. 분산 환경에서는 이 가정이 잘 깨집니다. `keep_latest`는 사실 CRDT 문헌에서 말하는 **LWW-Register(Last-Write-Wins Register)**이고, 그 알려진 약점을 그대로 물려받습니다.

**함정 1 — 노드마다 시계가 다르다(clock skew).** 각 노드가 자기 호스트의 `datetime.now()`를 찍으면, NTP가 붙어 있어도 수 ms~수백 ms 어긋납니다. 실제로 나중에 일어난 갱신이 더 이른 타임스탬프를 달고 와서 **조용히 덮이는** 일이 생깁니다. 예외도 안 나고 로그도 안 남습니다.

**함정 2 — 시계가 뒤로 갈 수 있다.** NTP 보정, 서머타임, VM 스냅샷 복원으로 벽시계는 역행합니다. `time.time()` 대신 단조 시계(`time.monotonic()`)를 쓰면 역행은 막지만, 그건 프로세스 안에서만 의미가 있어서 노드 간 비교에는 못 씁니다.

**함정 3 — `at`이 무슨 시각인지 정의가 흐리다.** 원천 시스템의 갱신 시각인가, 조회 시각인가, 노드 실행 시각인가? ERP의 "2024-03-01"이 데이터 갱신일이고 CRM의 "2026-01-15"가 조회일이면 둘은 애초에 비교 가능한 값이 아닙니다. **비교하는 값은 같은 축 위에 있어야 합니다.** 이걸 안 맞추면 리듀서는 순서와 무관해지지만 대신 조용히 틀린 답을 냅니다.

**함정 4 — 타임스탬프 정밀도.** `ex3`처럼 날짜 단위(`YYYY-MM-DD`)면 같은 날 들어온 갱신은 전부 동률입니다. 4절의 구멍이 예제 코드에서 이미 현실인 셈입니다.

### 대안

| 방식 | 하는 일 | 쓸 자리 |
|---|---|---|
| **논리 시계(Lamport clock)** | 벽시계 대신 단조 증가 카운터로 "먼저/나중"을 만든다. 같은 값이 나오면 노드 ID로 tie-break | 인과 순서만 필요하고 실제 시각은 필요 없을 때 |
| **버전 벡터 / 벡터 시계** | 노드별 카운터 배열. **"동시에 일어났다(concurrent)"를 검출할 수 있다** — 한쪽을 조용히 버리는 대신 충돌을 드러낸다 | 갱신 유실이 치명적이라 사람이 보고 판단해야 할 때 |
| **HLC(Hybrid Logical Clock)** | 벽시계에 논리 카운터를 붙여, 사람이 읽을 수 있으면서 인과성도 지킨다 | 시각 표시도 필요하고 순서도 지켜야 할 때 |
| **출처 우선순위** | 시계를 아예 안 쓰고 "이 필드는 ERP가 진실" 같은 정적 우선순위를 값에 실어 비교 | 도메인상 신뢰 서열이 명확할 때(가장 단순하고 가장 안전) |

버전 벡터가 다른 셋과 근본적으로 다른 점은, **"둘 중 하나를 골라야 한다"는 전제를 버린다**는 것입니다. 동시 갱신을 감지하면 값을 둘 다 남기고(siblings) 상위 계층으로 올립니다. 실무에서는 이게 최선일 때가 많습니다 — 담당자가 두 명이라고 알려 주는 편이, 아무 말 없이 한 명을 지우는 것보다 낫습니다.

> 19장의 도메인은 배치 병합이 아니라 **한 실행 안**입니다. 그래서 슈퍼스텝 번호나 노드 이름처럼 실행기가 이미 알고 있는, 시계보다 훨씬 믿을 만한 tie-break 재료가 손에 있습니다. 시계에 손대기 전에 그걸 먼저 쓰세요.

## 6. 정리

1. **왜 순서와 무관한가** — `keep_latest`/`keep_best`는 `old`/`new`라는 **자리**가 아니라 `at`/`conf`라는 **값 안의 필드**를 비교 근거로 쓴다. 자리를 바꿔도 비교 결과가 안 바뀌므로 `f(a,b) == f(b,a)`가 성립한다.
2. **대조** — `merge_dict`("새 것이 이긴다")는 판단 근거가 인자 자리뿐이라, 실행기가 순서를 바꾸면 답이 바뀐다. 예제에서 실제로 기대와 반대 결과(`등급 A`)가 나왔다.
3. **주의** — 동률이면 다시 순서 종속으로 되돌아간다. `>`냐 `>=`냐가 승자를 정하고, 둘 다 순서 종속이다.
4. **해법** — `(신뢰도, 시각, 출처ID)` 같은 **전순서 튜플 키**를 쓰고, 마지막 칸에 유일성이 보장된 값을 둔다. 그러면 리듀서가 `max`가 되고 결합법칙·멱등성까지 따라온다.
5. **실무** — 시계는 어긋나고, 역행하고, 정밀도가 모자라고, 축이 다를 수 있다. 논리 시계 / 버전 벡터 / HLC / 정적 출처 우선순위를 검토하고, 가능하면 시계 대신 실행기가 아는 값(슈퍼스텝 번호, 노드 이름)을 쓴다.

**한 문장으로:** 순서를 못 정하겠으면 순서를 안 보게 만들어라 — 판단 근거를 값 안으로 옮기면 된다.
