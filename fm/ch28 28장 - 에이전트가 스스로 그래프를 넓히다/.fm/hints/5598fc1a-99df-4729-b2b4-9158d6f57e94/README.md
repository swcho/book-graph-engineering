# 넣을 때 안 거른 것은 꺼낼 때도 안 걸러진다

## 질문

"넣을 때 안 거른 것은 꺼낼 때도 안 걸러진다"는 말의 근거는 무엇인가?

## 답

조회는 있는 것을 전부 준다. 정산팀으로 물으면 틀린 엣지 두 개가 통째로 답이 된다.

---

## 한 줄로 줄이면

**그래프 조회에는 「진위 필터」가 없다.** `MATCH` 는 저장된 패턴을 전부 돌려줄 뿐, 그중 무엇이 맞고 무엇이 틀렸는지 판단하지 않는다. 그래서 품질 관문은 **쓰기 시점**에만 존재할 수 있다. 쓰기 때 안 걸렀다면 읽기 때 걸러 줄 사람은 아무도 없다.

## 근거가 되는 예제 — `ch28/code/ex1_write_loop.py`

이 예제는 추출기가 뽑아 낸 트리플을 **검증 없이 그대로** 10턴 동안 쓰는 루프다. 입력 데이터에는 일부러 맞는 사실과 틀린 사실이 섞여 있다.

```python
EXTRACTED = [
    [("박민수", "이끔", "결제팀", True)],
    [("이서연", "속함", "결제팀", True)],
    [("민수",   "이끔", "결제팀", True)],   # 같은 사람, 다른 이름
    [("이서연", "속함", "정산팀", False)],  # 잘못 뽑음
    [("박민수", "이끔", "정산팀", False)],  # 잘못 뽑음
    [("결제팀", "속함", "이서연", False)],  # 방향 뒤집힘
    [("박민수", "관리", "결제팀", True)],   # 같은 뜻, 다른 관계 이름
    [("이서연", "속함", "결제팀", True)],   # 중복
    [("PM",     "이끔", "결제팀", True)],   # 또 다른 이름
    [("박민수", "이끔", "결제팀", True)],   # 중복
]
```

쓰기 함수에는 어떤 검사도 없다. 노드가 없으면 만들고, 엣지는 무조건 `CREATE` 한다.

```python
def write(c, s, k, o):
    ensure(c, s)
    ensure(c, o)
    c.execute("MATCH (a:N {name:$s}),(b:N {name:$o}) "
              "CREATE (a)-[:R {kind:$k}]->(b)", {"s": s, "o": o, "k": k})
```

10턴이 끝난 뒤 두 가지 질문을 던진다.

### 질문 1 — "결제팀을 이끄는 사람은?" (반쯤 맞는 답)

```python
MATCH (p:N)-[e:R]->(t:N {name:'결제팀'})
WHERE e.kind IN ['이끔','관리'] RETURN DISTINCT p.name
```

→ `박민수`, `민수`, `PM` 세 명이 나온다. **실제로는 한 명**이다.

여기서 고약한 점: 이 셋을 만든 트리플은 **전부 맞는 사실**(`True`)이었다. 이름 표기가 달라서 노드가 셋으로 갈라진 것뿐이다(27장의 개체 해상도 문제). 그래서 "같은 사람의 다른 이름"이라는 관점에서는 셋 다 맞고, "몇 명인가"라는 관점에서는 셋 다 틀리다. **명백한 오류가 아니라 반쯤 맞는 상태**라서 조회 결과만 보고는 문제가 있는지 알 수 없다.

### 질문 2 — "정산팀은?" (통째로 틀린 답) ← 답의 핵심 근거

```python
MATCH (p:N)-[e:R]->(t:N {name:'정산팀'}) RETURN p.name, e.kind
```

정산팀에 붙어 있는 엣지는 딱 두 개다. 그런데 그 둘이 하필 **둘 다 잘못 뽑힌 것**이다.

| 엣지 | 진위 | 어떻게 들어왔나 |
|---|---|---|
| `이서연 -속함-> 정산팀` | 거짓 | 추출기가 잘못 뽑음 (4턴) |
| `박민수 -이끔-> 정산팀` | 거짓 | 추출기가 잘못 뽑음 (5턴) |

조회 결과는 `['이서연 -속함->', '박민수 -이끔->']`. 즉 **응답의 100%가 오답**이다. 결제팀 쪽처럼 맞는 사실에 섞여 희석되지도 않는다. 이 서브그래프에는 걸러 줄 참값 자체가 없다.

여기가 근거의 요점이다. 조회는 정산팀에 무엇이 붙어 있는지를 물었을 뿐이고, 데이터베이스는 **붙어 있는 것을 전부** 성실하게 돌려줬다. 저장된 것이 전부 오염돼 있으면 답도 전부 오염된다. 쿼리는 자기가 오염된 것을 돌려주고 있다는 사실을 모른다.

전체 통계로 보면 엣지 10개 중 3개(30%)가 틀렸지만, 그 30%가 **정산팀 하위 그래프에는 100% 몰려** 있다. 오류율은 그래프 전체에 고르게 퍼지지 않는다. 특정 질의 경로에서는 국소적으로 100%가 된다.

## 왜 이게 "읽기 쪽에서는 못 고친다"는 결론이 되는가

1. **조회 엔진에는 진위 개념이 없다.** `MATCH ... RETURN` 은 패턴 매칭이지 사실 검증이 아니다. 그래프 DB에 "틀린 엣지는 빼고 주세요"라는 절은 존재하지 않는다.
2. **틀린 엣지에 표식이 없다.** 예제 1의 스키마는 `R(FROM N TO N, kind STRING)` 이 전부다. `conf` 도 `src` 도 `alive` 도 없다. 읽는 쪽에서 필터링하고 싶어도 필터 걸 컬럼이 없다. (예제 3에서야 `src`/`conf`/`alive` 가 붙는다.)
3. **판단 근거가 이미 소실됐다.** 어떤 문장에서 뽑았는지, 확신도가 몇이었는지는 쓰기 시점에만 알 수 있는 정보다. 쓰면서 버리면 나중에 복원할 수 없다.
4. **상위 k 개를 뽑는 방식이면 더 나쁘다.** 오염된 엣지가 다른 엣지와 구별되지 않으니 상위 k 안에 아무렇지 않게 들어온다.

읽기 전용 그래프에서는 이 문제가 안 생긴다. 사람이 넣은 것만 있기 때문이다. **쓰기를 여는 순간 품질 관리가 곧 시스템의 일부**가 된다는 것이 이 장의 출발점이다.

## 그래서 무엇을 하나 — 관문을 쓰기 앞에 세운다

`ex2_write_gate.py` 는 같은 후보 목록에 관문 넷을 세운다. 관문은 전부 **쓰기 직전**에 있다.

| 관문 | 잡는 것 | 정산팀 엣지에 대해 |
|---|---|---|
| 1. 확신도 (`MIN_CONF = 0.65`) | 자신 없는 추출 | `이서연 -속함-> 정산팀` 은 0.42 → **여기서 막힘** |
| 2. 이름 정규화 (`ALIAS`, `CANON`) | 막지 않고 **고친다**. 민수/PM → 박민수 | — |
| 3. 스키마 (`ALLOWED`) | 타입이 안 맞는 관계, 뒤집힌 방향 | — (Person→Team 은 합법) |
| 4. 단일 값 충돌 (`SINGLE = {"이끔"}`) | 팀장이 둘이 되는 상황 | `박민수 -이끔-> 정산팀` 은 0.87로 확신도는 통과하지만, 이미 결제팀을 이끌고 있어 **여기서 막힘** |
| 5. 중복 | 정규화 뒤에 같아진 트리플 | — |

정산팀의 틀린 엣지 두 개가 **서로 다른 관문**에 잡힌다는 점이 중요하다. 확신도 하나만 뒀으면 0.87짜리 `박민수 -이끔-> 정산팀` 은 그대로 통과했을 것이다. 그래서 "하나만 두면 나머지가 샌다"는 말이 나온다.

또 하나, 정규화가 중복보다 **먼저** 돌아야 한다. 거꾸로 하면 `민수` 와 `박민수` 가 서로 다른 것으로 보여서 중복이 안 걸리고, 예제 1처럼 노드가 셋이 된다.

## 함께 기억할 것

- **확신도가 높은 오류가 존재한다.** `결제팀 -속함-> 이서연` 은 방향이 뒤집혔는데 확신도가 0.92다. 추출기는 잘못 읽을 때도 자신 있게 잘못 읽는다. 이건 스키마 관문이 잡는다.
- **단일 값 충돌은 자동으로 덮어쓰지 말 것.** 오답이 정답을 지운다. 둘 다 살려 두고 사람에게 보낸다.
- **출처를 붙이면 사후 정정이 가능해진다** (`ex3_provenance.py`). 오보 출처를 철회하면 거기 기댄 추론까지 연쇄로 죽는다. 그러나 이것도 **쓸 때 기록해 뒀을 때만** 가능하다. 나중에는 복원 못 한다.
- **깊은 홉의 결과는 대기열로** (`ex5_expansion_budget.py`). 4홉 정확도 38%짜리를 그래프에 바로 쓰면 정확히 예제 1의 상황이 재현된다.

## 한 문장 정리

조회는 저장된 것을 전부 돌려줄 뿐 진위를 가리지 않는다. 정산팀 질의가 오답 두 개를 그대로 답으로 내놓는 것이 그 증거이며, 따라서 필터는 읽기가 아니라 **쓰기 앞**에 있어야 한다.
