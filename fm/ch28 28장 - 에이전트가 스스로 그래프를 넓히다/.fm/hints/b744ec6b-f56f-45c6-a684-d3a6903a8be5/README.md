# '기댄 관계'는 언제 기록해야 하는가?

> **Q.** '기댄 관계'는 언제 기록해야 하는가?
>
> **A.** 추론할 때 그때그때 기록해야 한다. 나중에는 복원할 수 없다.

출처: 28장 「에이전트가 스스로 그래프를 넓히다」 28.3절 *어디서 온 사실인가* / `code/ex3_provenance.py`

---

## 1. 한 줄 요지

`DERIVED_FROM`은 **로그가 아니라 원본 데이터**입니다.

추론 결과 엣지를 쓰는 그 트랜잭션 안에서 같이 쓰지 않으면, 나중에 그래프를 아무리 뜯어봐도
"이 사실이 *실제로* 무엇에 기대서 생겼는지"는 나오지 않습니다. 왜냐하면 **같은 결론에 이르는
근거 조합이 여러 개**이고, 그중 어느 것을 썼는지를 구별하는 정보가 그래프 안에 남아 있지 않기
때문입니다. 사후에 하는 것은 복원이 아니라 **추측**입니다.

예제 3의 마지막 문단이 그래서 저런 경고로 끝납니다.

```python
# 예제 코드에서는 손으로 적어 뒀다
DERIVED_FROM = {
    ("이서연", "동료", "박민수"): [("이서연", "속함", "결제팀"),
                                   ("박민수", "이끔", "결제팀")],
    ("이서연", "이웃", "박민수"): [("이서연", "삶", "마포"),
                                   ("박민수", "삶", "마포")],
}
```

> "한 가지 주의. 이 예제는 «기댄 관계»를 손으로 적어 뒀다.
> 실무에서는 추론할 때 그때그때 기록해야 한다. 나중에는 복원 못 한다."

---

## 2. 왜 사후에 복원할 수 없는가

### 2.1 같은 결론, 여러 근거 조합 (핵심 이유)

`이서연 -이웃-> 박민수`를 낳을 수 있는 근거 조합을 세어 봅시다. 전부 같은 그래프 안에 있습니다.

| # | 근거 조합 | 성립하나 |
|---|---|---|
| A | `이서연 -삶-> 마포` + `박민수 -삶-> 마포` | 예 |
| B | `이서연 -동료-> 박민수` + "동료는 사택을 같이 쓴다"는 규칙 | 예 |
| C | `이서연 -속함-> 결제팀` + `박민수 -이끔-> 결제팀` + 팀 사무실 위치 | 예 |
| D | 사용자가 그냥 그렇게 말했다 (추론이 아님) | 예 |

사후에 그래프를 열면 **A·B·C·D 후보가 전부 보입니다.** 그런데 실제로 쓰인 건 A 하나입니다.
그걸 가려낼 정보가 그래프 어디에도 없습니다. 추론 시점의 선택이 결과 엣지에 흔적을 남기지
않았으니까요. 이건 "찾기 어렵다"가 아니라 **정보가 소실됐다**입니다. 손실 압축과 같습니다.

### 2.2 잘못 추측하면 두 방향으로 다 망가진다

`src4`(외부 기사)가 오보로 철회됐다고 합시다.

| 추측 결과 | 벌어지는 일 | 이름 |
|---|---|---|
| 실제로 안 쓴 근거를 근거로 오인 | 멀쩡한 사실이 같이 죽는다 | **과잉 철회** (over-retraction) |
| 실제로 쓴 근거를 놓침 | 오보에 기댄 사실이 살아남는다 | **과소 철회** (under-retraction) |

과소 철회가 더 고약합니다. 남은 사실은 "누가 봐도 멀쩡해 보이는데 근거가 이미 죽은" 좀비가
됩니다. 본문 표현으로는 *어디서 왔는지 아무도 모르는 사실*이고, 이게 쌓이면 그래프를 통째로
못 믿게 됩니다.

과잉 철회도 만만치 않습니다. "안전하게 넓게 지우자"는 곧 오보 하나에 그래프 절반이 날아가는
정책이 되고, 그러면 아무도 철회 버튼을 못 누릅니다.

### 2.3 "그때 그래프"와 "지금 그래프"가 다르다

추론은 **그 시점의 그래프 상태**에서 일어났습니다. 그 뒤로 근거 엣지가 갱신·정규화·삭제됐을 수
있습니다. 지금 그래프에서 근거를 찾으면,

- 이미 사라진 근거는 후보에 안 뜨고 (놓침),
- 나중에 들어온 사실이 그럴듯한 근거로 보입니다 (허위 근거).

시간 순서를 무시한 역추적은 구조적으로 틀립니다.

### 2.4 재실행은 재현이 아니다

"그럼 추론을 다시 돌려서 근거를 뽑으면 되지 않나"가 흔한 반론인데, 안 됩니다.

- LLM 추론은 비결정적입니다. 온도, 모델 버전, 컨텍스트 구성이 달라지면 **다른 근거로 같은
  결론**에 도달합니다. 이건 재현이 아니라 새 추론이고, 새로 만든 `DERIVED_FROM`은 원래 것과
  다릅니다.
- 그래프 상태가 이미 달라졌습니다 (2.3).
- 재실행 비용이 원래 추론 비용과 같습니다. 이 장의 수치로는 노드당 약 1,400토큰. 기록해 두는 데
  드는 비용의 수백 배입니다.

### 2.5 규칙 기반이어도 안전하지 않다

"우리는 LLM이 아니라 결정론적 규칙으로 추론하니 다시 돌리면 된다"도 부분적으로만 맞습니다.
규칙 버전이 바뀌면 끝입니다. 그리고 규칙이 여러 개면 **어느 규칙이 발화했는지**가 여전히
소실됩니다. 규칙 ID까지 같이 적어야 합니다.

### 2.6 로그는 대체재가 아니라 보조재

프롬프트/응답 원문 로그를 남기면 부분 복원이 가능하긴 합니다. 그런데,

- 자연어를 다시 파싱해야 하고, 텍스트 속 "박민수"를 그래프의 어느 엣지에 매핑할지는 또 추측입니다.
- 로그 보존 기간(보통 30~90일)이 그래프 수명보다 짧습니다.
- 정규화 전 이름으로 적혀 있어서 정규화 후 노드와 안 맞습니다.

로그는 감사(audit)용이지 철회 연쇄의 입력이 될 수 없습니다.

## 3. 언제 — 기록 시점

**추론 결과 엣지를 쓰는 것과 같은 트랜잭션 안에서**입니다. 규칙으로 적으면 이렇습니다.

1. 관문(28.2절)을 통과시킨다 — 확신도 → **정규화** → 스키마 → 단일 값 → 중복
2. **정규화된 형태**로 근거 키를 확정한다
3. 결과 엣지와 justification을 **한 트랜잭션**으로 커밋한다

2번이 함정입니다. 근거를 정규화 *전* 이름(`민수`, `PM`)으로 적어 두면, 나중에 그래프에는
`박민수`밖에 없어서 근거를 못 찾습니다. 기록은 반드시 정규화 뒤 canonical key로 합니다.

3번도 함정입니다. "엣지 먼저 쓰고 근거는 배치로 나중에"는 그 사이에 프로세스가 죽으면
`DERIVED_FROM` 없는 고아 추론 사실이 생깁니다. 그리고 그 고아는 영영 못 고칩니다 (2절 전체).

미루면 안 되는 것들을 정리하면,

| 미루는 방식 | 결과 |
|---|---|
| 하루치 모아서 야간 배치 | 그 사이 근거가 갱신되면 매핑 실패 |
| 엣지만 먼저 쓰고 나중에 채우기 | 크래시 시 고아 발생, 재현 불가 |
| "필요할 때 만들자" | 필요해지는 시점 = 철회할 때 = 이미 늦은 때 |

## 4. 무엇을 — 기록 단위

### 4.1 단위는 "사실"이 아니라 "도출 1회"

예제 3의 `dict`는 `(s, k, o) → 근거 리스트` 하나입니다. **한 사실에 근거 집합이 하나뿐**이라는
가정이 들어가 있습니다. 실무에서는 같은 사실이 여러 경로로 도출됩니다.

```
justification = (
    도출된 사실,          # (s, k, o) — 정규화된 키
    근거 사실 집합,        # [(s,k,o), ...]  ← 이 안은 AND
    방법 식별자,           # 규칙 ID 또는 모델 ID + 버전
    시각,
    확신도,
)
```

- **하나의 justification 안의 근거들은 AND** — 하나라도 죽으면 이 justification이 죽습니다.
- **한 사실에 붙은 여러 justification은 OR** — 전부 죽어야 사실이 죽습니다.

이게 진리 유지 시스템(TMS)의 IN/OUT 판정과 같은 구조입니다. 예제 3의 `retract()`가
`while changed` 루프를 도는 이유도 여기 있습니다. 하나 죽이면 거기 기대던 게 또 죽어서, 더 이상
변화가 없을 때까지 돌아야 고정점에 도달합니다.

예제 3을 실무형으로 고치면 값이 **리스트의 리스트**가 됩니다.

```python
DERIVED_FROM = {
    ("이서연", "이웃", "박민수"): [
        [("이서연", "삶", "마포"), ("박민수", "삶", "마포")],   # justification 1
        [("이서연", "동료", "박민수")],                         # justification 2
    ],
}
# 죽는 조건: 모든 justification이 죽었을 때 (any → all)
```

이 차이가 실제 동작을 바꿉니다. 예제 3처럼 justification이 하나라고 가정하면 `src4` 철회 때
`이웃`이 같이 죽지만, justification 2가 살아 있다면 `이웃`은 **살아남아야 맞습니다.**

### 4.2 저장 형태 — 엣지에 못 붙인다

`DERIVED_FROM`은 **엣지와 엣지의 관계**입니다. 대부분의 프로퍼티 그래프는 엣지를 엣지의 끝점으로
쓸 수 없습니다. 그래서 리이피케이션(reification)이 필요합니다.

```
(Justification) -[:SUPPORTS]-> (도출된 사실 노드)
(Justification) -[:USES]->     (근거 사실 노드) × N
(Justification) { method, ts, conf }
```

즉 **엣지를 노드로 승격**시킵니다. W3C PROV-O의 `prov:wasDerivedFrom` / `prov:Activity`가 같은
모양입니다.

여기서 전제 하나. **엣지 ID가 안정적이어야 합니다.** 근거를 `(s, k, o)` 튜플로만 잡으면 같은
튜플이 다른 출처로 또 들어왔을 때 어느 쪽에 기댔는지 다시 모호해집니다. 사실마다 불변 ID를
부여하고 justification은 그 ID를 가리키는 게 안전합니다.

### 4.3 확신도도 같이

본문 요약의 이 줄이 justification 없이는 계산이 안 됩니다.

> 추론 결과의 신뢰도는 근거 중 가장 약한 것보다 강할 수 없습니다.

`conf(도출) ≤ min(conf(근거들))`. 근거 집합을 모르면 min을 못 구합니다. 사후에 확신도를 다시
매기려는 시도가 실패하는 것도 같은 이유입니다.

예제 3의 `src3`(에이전트 추론)가 0.55인데, 그 근거인 `src4`(외부 기사)는 0.40입니다.
min 규칙대로면 `이웃`은 0.55가 아니라 **0.40 이하**여야 맞습니다. 예제는 출처 단위 신뢰도를
그대로 쓰느라 이 부분을 단순화했습니다.

## 5. 얼마나 드는가 — 비용

### 5.1 기록 비용은 작다

| 항목 | 규모 |
|---|---|
| 저장 | 추론 사실 1개당 근거 링크 평균 2~3개. 사실당 수십~수백 바이트 |
| 쓰기 지연 | 같은 트랜잭션에 엣지 N개 추가. 밀리초 단위 |
| 추론 자체 비용 | 노드당 약 **1,400토큰** (예제 5의 `COST_PER_EXPAND`) |

핵심은 **비율**입니다. 추론 한 번에 1,400토큰을 쓰면서, 그 결과가 무엇에 기댔는지를 적는 데는
토큰이 거의 안 듭니다(이미 추론 과정에서 알고 있는 정보라 추가 호출이 필요 없습니다).
**기록 비용은 추론 비용의 반올림 오차** 수준입니다.

주의할 것은 저장량이 아니라 **증가율**입니다. 본문대로 에이전트가 쓰기 시작하면 추론된 사실의
비율이 빠르게 오르므로, justification 테이블은 원본 사실 테이블보다 빨리 큽니다. 이건 정상이고
예상해 둬야 합니다.

### 5.2 안 기록했을 때의 비용은 무한대에 가깝다

| | 기록함 | 기록 안 함 |
|---|---|---|
| 오보 1건 발견 시 | 연쇄 철회 쿼리 한 번 | 영향 범위 산정 불가 |
| 최선의 대응 | 관련 사실만 정확히 무효화 | 그래프 통째로 폐기 후 재구축 |
| 비용 성격 | 선형, 예측 가능 | 확률적, 재앙적 |

기록은 보험입니다. 보험료는 매번 조금씩 내고, 사고는 가끔 나는데 그때 안 들어 뒀으면 전액
자기부담입니다. 그리고 이 보험은 **사후 가입이 불가능**하다는 게 이 카드의 요점입니다.

### 5.3 철회 연쇄의 비용

예제 3의 `retract()`는 `while changed` 안에서 `DERIVED_FROM` 전체를 매번 훑습니다.
파생 사실이 $D$개, 연쇄 깊이가 $L$이면 대략 $O(D \times L)$ 스캔입니다. 예제 규모라 괜찮지만
실무에서는 **근거 → 도출 역인덱스**를 두고 죽은 사실에서 BFS로 올라가야 합니다. 그러면
비용이 실제 영향받는 부분그래프 크기에 비례합니다.

```
kill(fact):
    for j in reverse_index[fact]:      # 이 사실을 근거로 쓰는 justification들
        j.alive = false
        if all justifications of j.target are dead:
            kill(j.target)             # 연쇄
```

### 5.4 비용을 줄이고 싶다면

기록 자체를 빼는 게 아니라 **범위를 좁힙니다.**

- 사용자 발화·위키처럼 **직접 사실은 출처(src)만** 답니다. justification은 추론 사실 전용입니다.
- 깊은 홉의 파생(28.5절, 3~4홉, 정확도 52%/38%)은 아예 그래프에 안 쓰고 **검토 대기열**로
  보냅니다. 대기열에 있는 동안은 justification 저장 부담도 없습니다.
- justification에 만료를 둡니다. 단, 만료된 것은 "근거를 모르는 사실"이 되므로 함께 사실도
  강등하거나 재검증 대상으로 표시해야 합니다. 그냥 지우면 좀비가 됩니다.

## 6. 한 장 정리

| 질문 | 답 |
|---|---|
| 언제 | 추론 결과를 쓰는 **바로 그 트랜잭션 안**. 관문 통과·정규화 **뒤** |
| 무엇을 | 도출 사실 / 근거 집합(AND) / 방법 ID·버전 / 시각 / 확신도 |
| 단위 | 사실 단위가 아니라 **도출 1회 = justification 1개**. 한 사실에 여러 개(OR) 가능 |
| 형태 | Justification을 **노드로 승격**(리이피케이션). 안정적 엣지 ID 필요 |
| 왜 나중엔 안 되나 | **같은 결론에 이르는 근거 조합이 여럿**이고, 어느 것을 썼는지가 그래프에 안 남음 |
| 비용 | 기록은 추론 비용의 반올림 오차. 미기록은 그래프 전체 신뢰 상실 |

### 체크리스트

- [ ] 추론 결과 엣지와 justification이 **한 트랜잭션**인가
- [ ] 근거 키가 **정규화 뒤** 이름인가
- [ ] 한 사실에 justification이 **여러 개** 붙을 수 있는가 (any/all 판정 확인)
- [ ] 근거가 `(s,k,o)` 튜플이 아니라 **불변 엣지 ID**인가
- [ ] 방법 식별자에 **모델/규칙 버전**이 들어가는가
- [ ] `근거 → 도출` **역인덱스**가 있는가
- [ ] 확신도가 `min(근거들)` 이하로 계산되는가
- [ ] justification 없는 추론 사실을 찾아내는 감시 쿼리가 있는가
