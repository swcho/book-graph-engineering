# 「틀린 것 30개 넘으면 중단」 정책의 한계와 보완책

> 출처: 28장 - 에이전트가 스스로 그래프를 넓히다 / `code/ex5_expansion_budget.py`

## 질문

'틀린 것 30개 넘으면 중단' 정책의 한계와 보완책은 무엇인가?

## 답

**30개를 넘고 나서 알기 때문에 이미 들어간 뒤다. 쓰기 전 대기열과 함께 써서 중단 조건에 걸리면 대기열을 통째로 버려야 한다.**

---

## 1. 이 정책이 어디서 나왔나

`ex5_expansion_budget.py`는 씨앗 노드 12개에서 그래프를 넓히는 정책 네 가지를 비교합니다.

```python
POLICIES = {
    "끝까지 (4홉)":        lambda h, g, w, t: True,
    "2홉까지":             lambda h, g, w, t: h <= 2,
    "토큰 예산 60,000":    lambda h, g, w, t: t < 60_000,
    "틀린 것 30개 넘으면 중단": lambda h, g, w, t: w < 30,
}
```

앞의 셋은 **구조**로 멈춥니다. 홉 수를 세거나 토큰을 셉니다. 마지막 하나만 **품질**로 멈춥니다. 틀린 사실이 몇 개 쌓였는지를 보고 판단하죠.

책이 이 정책을 "눈여겨보라"고 한 이유가 여기 있습니다. 20장의 「진전 없음」과 같은 발상이거든요. 정해진 횟수를 다 채우는 게 아니라, *성과가 나빠지면* 멈추는 겁니다. 홉 수는 도메인마다 적정값이 다르지만 "틀린 게 늘면 손해"는 어디서나 참이니, 훨씬 이식성 있는 기준입니다.

그런데 이 정책에는 다른 셋에는 없는 구멍이 하나 있습니다.

## 2. 한계 — 사후 탐지라서 이미 늦었다

`w`(틀린 것의 누적 수)는 **넓히기를 실행하고 결과를 그래프에 쓴 뒤에야** 계산됩니다. 조건 `w < 30`이 거짓이 되는 시점은 곧 "이미 30개 넘게 들어갔다"는 뜻입니다.

토큰 예산과 비교하면 차이가 분명합니다.

| 기준 | 값을 아는 시점 | 위반했을 때 상태 |
|---|---|---|
| 홉 수 `h` | 시작 전 (결정론적) | 위반 자체가 안 생김 |
| 토큰 `t` | 홉 시작 전 (누적치) | 예산 초과 — 돈만 더 씀 |
| 틀린 것 `w` | 홉 **실행 후** | 오염된 사실이 그래프에 **남아 있음** |

토큰을 초과하면 비용을 더 낸 것으로 끝납니다. 되돌릴 게 없어요. 그런데 틀린 사실을 초과하면, 초과분이 *데이터로 남습니다*. 중단 버튼을 눌러도 이미 들어간 것은 안 나갑니다.

같은 예제가 토큰 예산에서도 비슷한 지적을 합니다. "홉을 시작하기 전에만 검사하고 중간에는 안 봐서" 60,000 예산이 63,000을 썼다는 것이죠. 하지만 그건 **양적 초과**입니다. 품질 기준의 초과는 **성질이 다릅니다**. 초과분이 시스템 안에 잔류하니까요.

### 왜 잔류가 치명적인가

28장 전체가 이 잔류의 대가를 설명합니다.

- **ex1**: 검증 없이 10턴 쓰면 엣지 10개 중 3개가 틀립니다. 문제는 명백한 오류가 아니라 「반쯤 맞는」 상태라는 것. 조회 결과만 봐서는 문제가 있는지 알 수 없습니다.
- **ex5**: 4홉 정확도는 38%입니다. "정확도 38%짜리를 바로 쓰면 예제 1의 상황이 된다."
- **ex4**: 에이전트가 자기가 쓴 것을 다시 읽고 또 씁니다. 오염된 사실은 **다음 세대의 씨앗**이 됩니다.

마지막이 결정타입니다. `expand()` 안에서 `frontier = int(r)`, 즉 맞는 것만 다음 홉의 씨앗이 된다고 모델링했지만, 현실에서는 틀린 것도 씨앗이 됩니다. 그래프는 무엇이 맞는지 모르니까요. 그래서 30개 넘은 것을 알아챈 순간에는 30개가 아니라, 그 30개에서 파생된 것까지 이미 퍼져 있을 수 있습니다.

### 그리고 애초에 `w`를 어떻게 아는가

예제는 `YIELD_BY_HOP`에 홉별 정확도를 박아 두고 `wrong = new - new * acc`로 계산합니다. 시뮬레이션이니까 가능한 일입니다. 실무에서는 "이 사실이 틀렸다"를 판정하는 주체가 따로 있어야 합니다.

- 28.2의 관문 넷(확신도·정규화·스키마·단일 값 충돌)에서 걸린 수를 프록시로 쓰거나
- 사람 검토에서 반려된 수를 세거나
- 표본을 뽑아 검사한 뒤 전체로 추정하거나

어느 쪽이든 **판정에 시간이 걸립니다**. 판정 지연이 붙으면 "이미 들어간 뒤"의 간격은 더 벌어집니다. 사람 검토가 판정자라면 그 간격은 시간 단위, 하루 단위가 될 수도 있습니다.

## 3. 보완책 — 쓰기 전 대기열(스테이징)

책의 결론은 짧습니다.

> "그래서 이 정책은 «쓰기 전 대기열»과 같이 써야 한다. 일단 대기열에 쌓고, 중단 조건에 걸리면 대기열을 통째로 버린다."

핵심은 **넓히기와 커밋을 분리**하는 것입니다.

```
[기존]
  넓힌다 → 그래프에 쓴다 → w 를 센다 → 30 넘었나? → 중단
                  ↑ 이미 들어감            ↑ 여기서 알아봐야 소용없음

[보완]
  넓힌다 → 대기열에 쌓는다 → w 를 센다 → 30 넘었나?
                                          ├ 예   → 대기열 통째로 폐기 (그래프 무변화)
                                          └ 아니오 → 대기열 원자적 커밋
```

이러면 중단 조건이 **사후 탐지**에서 **사전 차단**으로 바뀝니다. 정확히는, 탐지는 여전히 사후지만 *탐지 대상이 그래프가 아니라 대기열*이 됩니다. 대기열은 버려도 되는 곳이니까요.

### 왜 "통째로" 버리나

이 부분이 미묘합니다. "틀린 30개만 골라 버리면 되지 않나"라는 생각이 들 텐데, 그렇게 하면 안 되는 이유가 둘 있습니다.

**첫째, 어느 것이 틀렸는지 정확히는 모릅니다.** 30개라는 숫자는 표본이나 관문 통과율에서 나온 *추정치*입니다. 어느 개별 사실이 틀렸는지 확정할 수 있었다면 애초에 그걸 안 쓰면 그만이지, 중단 정책이 필요 없었겠죠.

**둘째, 틀린 비율이 30개를 넘었다는 건 그 배치의 생성 과정 전체를 못 믿겠다는 신호입니다.** 3~4홉의 정확도가 52%, 38%라는 건 그 홉에서 나온 것 전부의 신뢰도가 낮다는 뜻입니다. 나머지가 우연히 맞았더라도, 그 배치를 남기면 "출처가 의심스러운 사실"이 그래프에 섞입니다. 28.3이 말하는 "어디서 왔는지 아무도 모르는 사실"이 되는 거죠.

그래서 **all-or-nothing**입니다. 트랜잭션의 원자성과 같은 발상입니다.

### 대기열의 구현 형태

몇 가지 선택지가 있고, 각각 트레이드오프가 다릅니다.

| 방식 | 방법 | 장점 | 단점 |
|---|---|---|---|
| 메모리 버퍼 | 후보 트리플을 리스트에 모았다가 통과하면 일괄 write | 가장 단순 | 배치가 크면 메모리 압박, 프로세스 죽으면 소실 |
| DB 트랜잭션 | 트랜잭션 열고 쓰다가 조건 위반 시 rollback | 원자성 보장, 재사용 쉬움 | 긴 트랜잭션이 락을 오래 잡음 |
| 스테이징 테이블 | 별도 `Staged` 노드/엣지 테이블에 쓰고, 통과 시 본 테이블로 승격 | 검사 중에도 대기열을 쿼리 가능, 크래시 내성 | 스키마가 두 벌, 승격 로직 필요 |
| `alive` 플래그 | ex3처럼 `alive:false`로 써 두고, 통과하면 true로 뒤집기 | ex3의 철회 메커니즘과 코드 공유 | 조회할 때마다 `WHERE e.alive` 를 빠뜨리면 안 됨 |

`ex3_provenance.py`가 이미 `alive BOOLEAN` 필드를 씁니다.

```python
c.execute("CREATE REL TABLE R(FROM N TO N, kind STRING, src STRING, "
          "conf DOUBLE, alive BOOLEAN)")
```

철회를 위해 만든 필드지만, 스테이징에도 그대로 쓸 수 있습니다. `alive:false`로 넣어 두면 조회에 안 잡히고, 통과하면 뒤집고, 걸리면 지우면 됩니다. 다만 "조회 시 `alive` 필터를 반드시 건다"는 규율이 필요합니다. 한 군데라도 빠뜨리면 스테이징이 무의미해집니다.

### 대기열 크기 자체에도 상한이 필요하다

한 가지 함정이 있습니다. 대기열에 무한정 쌓다가 마지막에 검사하면 메모리가 터집니다. 그리고 토큰 예산 버그와 똑같은 형태의 문제가 생기죠 — **검사 단위가 너무 크면 못 막습니다**.

그래서 실무에서는 홉 단위, 또는 홉 안의 N개 단위로 잘라서 검사합니다.

- 홉 하나가 끝날 때마다 그 홉의 대기열을 검사 → 통과하면 커밋, 아니면 폐기 후 중단
- 이러면 이전 홉에서 이미 커밋한 것은 남지만, 그건 검사를 통과한 것이므로 정당합니다

ex5가 토큰 예산에 대해 한 지적("홉 안에서 노드 단위로 검사하거나, 홉의 예상 값을 미리 재야 한다")이 여기에도 그대로 적용됩니다. 검사 주기가 곧 최대 오염량이라고 보면 됩니다.

### 폐기가 곧 신호다

대기열을 버렸다는 사실 자체가 기록할 값어치가 있는 정보입니다. "3홉에서 배치를 폐기함, 추정 오류 34개" 같은 로그가 쌓이면 `YIELD_BY_HOP`의 실제 값을 자기 도메인에서 재는 데이터가 됩니다. 책이 "여러분 도메인에서는 홉별 정확도를 직접 재서 넣으세요"라고 한 그 값이죠.

## 4. 이미 커밋된 뒤라면 — 연쇄 철회

대기열은 **아직 안 들어간 것**을 막습니다. 그런데 검사 주기가 길었거나, 판정이 늦게 도착했거나(사람 검토가 나중에 반려), 애초에 대기열 없이 운영하던 시기의 데이터가 있다면 — 이미 들어간 것을 걷어내야 합니다.

여기서 `ex3_provenance.py`의 메커니즘이 필요해집니다.

```python
def retract(c, src):
    """출처 하나를 철회한다. 거기 기댄 추론도 같이 죽인다."""
```

`retract`는 두 단계입니다.

1. **직접 철회**: 그 출처(`src`)에서 온 엣지를 전부 `alive = false`
2. **연쇄 철회**: `DERIVED_FROM`을 훑어, 죽은 사실에 기대고 있던 추론을 찾아 같이 죽임. 그리고 그 추론에 기댄 것이 또 있을 수 있으니 `while changed` 루프로 **더 이상 변화가 없을 때까지 반복**

예제에서는 엣지 하나(`박민수 -삶-> 마포`, 외부 기사 출처)를 지웠는데 둘이 사라집니다. 거기 기대던 `이서연 -이웃-> 박민수`가 같이 무너지거든요.

### 그래서 커밋 전에 무엇을 같이 써 둬야 하나

연쇄 철회가 가능하려면 커밋 시점에 두 가지가 엣지에 붙어 있어야 합니다.

- **출처(`src`)**: 어느 확장 배치/홉/실행에서 나왔는지. 이게 있어야 "3홉 배치를 통째로 철회"가 한 쿼리로 됩니다.
- **파생 근거(`DERIVED_FROM`)**: 추론된 사실이 어떤 사실에 기댔는지.

두 번째가 놓치기 쉽습니다. 예제도 이 점을 못박습니다.

> "이 예제는 «기댄 관계»를 손으로 적어 뒀다. 실무에서는 추론할 때 그때그때 기록해야 한다. **나중에는 복원 못 한다.**"

추론한 순간이 지나면 "왜 그렇게 믿었는지"는 사라집니다. 나중에 재구성하려 해도, 같은 결론에 이르는 경로가 여러 개면 어느 것이었는지 알 수 없습니다. 그래서 근거 기록은 사후 추가가 불가능한 유일한 정보입니다.

### 철회는 대기열보다 훨씬 비싸다

| | 대기열 폐기 | 연쇄 철회 |
|---|---|---|
| 대상 | 아직 안 들어간 후보 | 이미 들어간 사실 + 그것에 기댄 것들 |
| 필요한 사전 준비 | 스테이징 구조 | 출처 + 파생 근거를 **모든 엣지**에 기록 |
| 비용 | 리스트 하나 버리기 | 고정점 도달까지 그래프 순회 |
| 부수 피해 | 없음 | 맞는 사실도 근거가 죽으면 같이 죽음 |
| 놓치는 것 | 없음 | 근거 기록이 없는 파생은 **영영 안 걸림** |

마지막 줄이 중요합니다. 근거를 안 적어 둔 파생 사실은 철회에서 살아남습니다. 그리고 살아남아서 "어디서 왔는지 아무도 모르는 사실"이 됩니다. 그런 게 쌓이면 그래프를 통째로 못 믿게 되죠.

그래서 순서가 이렇습니다.

1. **먼저 대기열로 막는다** — 싸고, 부수 피해가 없고, 놓치는 게 없다
2. **그래도 새는 것을 철회로 걷어낸다** — 비싸고 불완전하지만, 대기열이 못 잡는 늦은 판정을 처리한다
3. **철회를 쓸 수 있으려면 커밋 시점에 출처와 근거를 반드시 남긴다** — 이건 나중에 못 한다

## 5. 정리

- **한계**: `w < 30`은 사후 탐지다. 조건이 깨진 걸 아는 시점에 이미 틀린 사실 30개가 그래프에 들어가 있다. 토큰 초과와 달리 초과분이 **데이터로 잔류**하고, 자기 학습 루프의 씨앗이 되어 더 퍼진다.
- **보완책 1 (예방)**: 쓰기 전 대기열. 넓히기와 커밋을 분리하고, 중단 조건에 걸리면 대기열을 **통째로** 폐기한다. 부분 선별이 아니라 all-or-nothing인 이유는 (a) 어느 게 틀렸는지 확정 못 하고 (b) 그 배치의 생성 과정 전체가 못 믿을 것이기 때문.
- **보완책 2 (검사 주기)**: 대기열을 무한정 키우면 토큰 예산 버그와 같은 형태가 된다. 홉 단위 또는 N개 단위로 잘라 검사한다. 검사 주기 = 최대 오염량.
- **보완책 3 (사후)**: 이미 커밋됐다면 연쇄 철회. 그러려면 **커밋 시점에** 출처와 파생 근거를 남겨 둬야 한다. 나중에는 복원 못 한다.
- **원칙**: 품질 기반 중단은 홉 수 기반보다 나은 발상이지만, 되돌릴 수 있는 구조와 짝을 이룰 때만 작동한다. 되돌릴 수 없으면 중단 조건은 사후 통보에 불과하다.
