# 스키마 관문만으로 막을 수 없는 것은 무엇인가?

> **Q.** 스키마 관문만으로 막을 수 없는 것은 무엇인가?
>
> **A.** 타입은 맞는 잘못된 사실이다. "박민수 -이끔-> 정산팀"은 Person→Team으로 타입이 맞아 단일 값 관문이 잡아야 한다.

출처: 28장 「에이전트가 스스로 그래프를 넓히다」 28.2절 *쓰기 앞에 관문 넷* / `code/ex2_write_gate.py`

---

## 1. 한 줄 요지

스키마는 **「이런 모양의 문장이 성립하는가」**를 봅니다.
단일 값은 **「그 문장이 이미 있는 사실과 같이 설 수 있는가」**를 봅니다.

`박민수 -이끔-> 정산팀` (0.87)은 **모양이 완벽합니다.**
Person이 Team을 이끄는 건 스키마가 허용하는 조합이니까요.
문제는 박민수가 **이미 결제팀을 이끌고 있다**는 것이고,
그건 후보 트리플만 들여다봐서는 절대 알 수 없습니다.

---

## 2. 관문 넷이 각각 잡는 오류 부류

`ex2_write_gate.py`의 `gate()`는 다섯 단계를 거칩니다(정규화는 막지 않고 고치므로 「관문 넷」).

| # | 관문 | 판정 근거 | 잡는 오류 부류 |
|---|---|---|---|
| 1 | 확신도 | 추출기의 점수 하나 | 추출기가 **스스로 자신 없는** 것 |
| 2 | 정규화 | 사전(ALIAS/CANON) | *막지 않고 **고친다*** — 표기 갈라짐 |
| 3 | **스키마** | 주어·목적어의 **타입** | **형태 오류** — 종류 착각, 방향 뒤집힘 |
| 4 | **단일 값** | **그래프에 이미 있는 엣지** | **내용 오류** — 타입은 맞는 거짓 |
| 5 | 중복 | 같은 엣지가 이미 있나 | 같은 사실의 재입력 |

핵심은 **각 관문의 판정에 필요한 정보의 범위가 다르다**는 점입니다.

```
확신도  → 점수만 본다            (트리플 밖을 안 본다)
스키마  → 타입 사전만 본다        (그래프를 안 본다)
단일 값 → 그래프에 질의를 날린다   (기존 상태를 봐야 한다)
중복    → 그래프에 질의를 날린다   (기존 상태를 봐야 한다)
```

스키마 관문은 **무상태(stateless)**입니다.
`(k, ts, to) not in ALLOWED` — 트리플 하나와 타입표만 있으면 답이 나옵니다.
그래서 **그래프가 비어 있을 때도, 100만 건이 들어 있을 때도 판정이 같습니다.**

단일 값 관문은 **유상태(stateful)**입니다.
`MATCH (a:N {name:$s})-[e:R {kind:$k}]->(b:N)` 를 실제로 실행해서
「박민수가 이미 누굴 이끌고 있나」를 확인해야 답이 나옵니다.
**같은 트리플이 그래프 상태에 따라 통과도 되고 막히기도 합니다.**

이게 스키마만으로 못 막는 이유의 전부입니다.
스키마는 원리적으로 볼 수 없는 정보를 근거로 하는 오류가 있고, 그게 단일 값 충돌입니다.

## 3. 후보 11개, 관문별 판정 전체

| 후보 | 확신 | 판정 | 왜 |
|---|---|---|---|
| 박민수 -이끔-> 결제팀 | 0.94 | ✅ 통과 | 첫 이끔 엣지 |
| 이서연 -속함-> 결제팀 | 0.91 | ✅ 통과 | |
| 민수 -이끔-> 결제팀 | 0.88 | 막힘 5.중복 | 정규화로 박민수가 된 뒤 중복 |
| 이서연 -속함-> 정산팀 | 0.42 | 막힘 1.확신도 | 0.65 미만 |
| **박민수 -이끔-> 정산팀** | **0.87** | **막힘 4.단일값충돌** | **★ 타입은 맞다** |
| 결제팀 -속함-> 이서연 | 0.92 | 막힘 3.스키마 | (속함, Team, Person) 불허 |
| 박민수 -관리-> 결제팀 | 0.83 | 막힘 5.중복 | 관리→이끔 정규화 후 중복 |
| 이서연 -속함-> 결제팀 | 0.90 | 막힘 5.중복 | |
| PM -이끔-> 결제팀 | 0.71 | 막힘 5.중복 | PM→박민수 정규화 후 중복 |
| 이서연 -선호-> 매운맛 | 0.86 | ✅ 통과 | |
| 박민수 -선호-> 결제팀 | 0.88 | 막힘 3.스키마 | Team은 Pref가 아니다 |

**11개 중 3개만 씀.** 관문별로 잡은 수: 확신도 1, 스키마 2, 단일값충돌 1, 중복 4.

관문 하나라도 빼면 그 칸의 숫자만큼 오염이 그대로 들어갑니다.

## 4. 스키마가 잡는 것 vs 단일 값이 잡는 것 — 나란히

### 스키마가 잡는 것: `결제팀 -속함-> 이서연` (0.92)

방향이 뒤집혔습니다. **확신도는 0.92로 아주 높습니다.**
추출기가 문장을 잘못 읽으면 「자신 있게」 잘못 읽기 때문에 확신도로는 못 잡습니다.
하지만 `(속함, Team, Person)`은 ALLOWED에 없습니다. Team이 Person에 속할 수는 없으니까요.
**타입만 보면 즉시 걸립니다.**

`박민수 -선호-> 결제팀` (0.88)도 같습니다. `(선호, Person, Team)` — Team은 Pref가 아닙니다.

### 단일 값이 잡는 것: `박민수 -이끔-> 정산팀` (0.87)

```python
TYPES["박민수"] == "Person"
TYPES["정산팀"] == "Team"
("이끔", "Person", "Team") in ALLOWED   # → True. 스키마는 통과시킨다
```

스키마 관문은 **이 트리플에 대해 할 말이 없습니다.** 형태가 완전히 정상이니까요.
그런데 `SINGLE = {"이끔"}` — 「팀장은 한 명」이라는 **개수 제약**이 걸려 있고,
그래프에는 이미 `박민수 -이끔-> 결제팀`이 있습니다. 목적어가 다릅니다. 충돌.

> **스키마가 문법 검사라면, 단일 값은 사실 관계 검사입니다.**
> 「박민수가 정산팀을 이끈다」는 문법적으로 흠 없는 문장입니다. 그냥 **틀렸을 뿐**입니다.

## 5. 왜 이 구분이 학계 용어로도 갈라져 있나

이건 이 책만의 분류가 아니라, 제약 언어들이 원래 나눠 놓은 축입니다.

| | 타입 제약 | 카디널리티 제약 |
|---|---|---|
| 묻는 것 | 무엇이 무엇에 붙을 수 있나 | 몇 개까지 붙을 수 있나 |
| SHACL | `sh:class`, `sh:nodeKind`, `sh:datatype` | `sh:maxCount 1`, `sh:minCount` |
| OWL | `rdfs:domain` / `rdfs:range` | `owl:FunctionalProperty` |
| RDBMS | 컬럼 타입, FK가 가리키는 테이블 | `UNIQUE`, `CHECK (count = 1)` |
| 판정 범위 | 트리플 1개 + 스키마 | 트리플 1개 + **기존 데이터 전체** |
| 오류 이름 | 형태 오류(shape violation) | 정합성 오류(consistency violation) |

관계형 DB로 비유하면 이렇습니다.
`manager_id`가 INTEGER이고 employee 테이블을 가리킨다는 건 **타입 제약**입니다.
한 팀에 팀장이 한 명뿐이라는 건 `UNIQUE(team_id)`, 즉 **카디널리티 제약**이고요.
컬럼 타입만 맞춰 놓고 UNIQUE를 안 걸면 팀장 두 명이 아무 저항 없이 들어갑니다.

28장이 「관문 넷」이라고 못 박은 이유가 여기 있습니다.
**한 축의 제약은 다른 축의 오류를 원리적으로 볼 수 없습니다.**

## 6. 여기서 놓치기 쉬운 것 — 잡은 다음이 더 중요하다

단일 값 충돌을 잡았다고 끝이 아닙니다. **무엇을 남길지**를 정해야 합니다.

이 예제의 코드는 「나중에 온 것을 막는다」입니다. 먼저 쓴 것이 이깁니다(first-write-wins).
그런데 만약 후보 순서가 뒤집혀 **`정산팀`(0.87)이 먼저 들어왔다면?**
정산팀이 자리를 잡고, **정답인 `결제팀`(0.94)이 막힙니다.**
같은 관문, 같은 데이터, 순서만 달라졌는데 결과가 뒤집힙니다.

그럼 「확신도 높은 쪽으로 덮어쓰자」는 자연스러운 해법이 떠오르는데, 28장은 이걸 말립니다.

> 단일 값 충돌을 **자동으로 덮어쓰지 마세요. 오답이 정답을 지웁니다.**
> 둘 다 살려 두고 사람에게 보내세요.

추출기의 확신도는 정답률과 정확히 비례하지 않습니다.
`결제팀 -속함-> 이서연`이 0.92였던 걸 떠올려 보세요 — **완전히 틀린 사실인데 두 번째로 높은 점수**였습니다.
그런 점수를 기준으로 덮어쓰기를 자동화하면, 확신 있게 틀린 사실이 조용히 정답을 밀어냅니다.
게다가 삭제는 로그에 흔적이 잘 안 남고, **덮어쓴 뒤에는 원래 뭐가 있었는지 복원이 안 됩니다.**

그래서 올바른 처리는 **막고 → 둘 다 보존하고 → 검토 대기로 올리는 것**입니다.
(이 「어느 쪽이 맞나」를 판단하는 재료가 28.3절의 출처 기록입니다.
근거가 붙어 있으면 사람이 둘 중 어느 쪽을 살릴지 판정할 수 있습니다.)

## 7. 관문 순서에도 규칙이 있다

부가로 짚어 둘 것 하나. 관문 순서는 임의가 아닙니다.

**정규화는 반드시 중복 검사보다 먼저** 돌아야 합니다.
`민수`, `PM`이 `박민수`로 바뀐 *뒤에야* 중복 관문이 「이미 있다」를 알아봅니다.
거꾸로 하면 셋이 서로 다른 문자열로 보여서 전부 통과하고,
28.1절처럼 **「박민수」 노드가 세 개**가 됩니다.

마찬가지로 **정규화는 단일 값 검사보다도 먼저**여야 합니다.
`PM -이끔-> 정산팀`이 들어왔을 때 정규화 전이면 「PM은 아직 아무도 안 이끈다」로 보여 충돌을 놓칩니다.

---

## 8. 한 문장으로

**스키마는 「말이 되는 문장인가」를, 단일 값은 「이미 아는 것과 앞뒤가 맞는가」를 봅니다.**
`박민수 -이끔-> 정산팀`은 말은 되는데 앞뒤가 안 맞는 경우라서,
타입 제약이 아니라 카디널리티 제약이 잡아야 합니다.
