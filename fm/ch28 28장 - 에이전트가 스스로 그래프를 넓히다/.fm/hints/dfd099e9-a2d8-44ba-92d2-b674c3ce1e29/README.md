# `ex1_write_loop.py` — 10턴 뒤 「박민수」가 세 명이 된 이유

**질문**: `ex1_write_loop.py`에서 10턴 뒤 '박민수'가 세 명이 된 이유는 무엇인가?

**답**: 박민수·민수·PM이 같은 사람인데 이름이 달라 노드가 셋으로 갈라졌다. 세 사실 모두 맞는 사실이었다.

---

## 한 줄 요약

노드의 정체성(identity)이 **문자열 이름**이기 때문이다. 세 번의 쓰기가 전부 사실로는 맞았지만, 표기가 「박민수」·「민수」·「PM」으로 달라서 그래프는 서로 다른 세 사람으로 받아들였다. 즉 **추출 정확도가 100%였어도 이 문제는 그대로 생긴다.**

## 1. 문제의 씨앗은 입력 데이터에 이미 있다

`EXTRACTED`는 10턴 분량의 추출 결과이고, 각 튜플의 네 번째 값이 「이게 맞는 사실인가」다.

```python
EXTRACTED = [
    [("박민수", "이끔", "결제팀", True)],
    [("이서연", "속함", "결제팀", True)],
    [("민수", "이끔", "결제팀", True)],            # 같은 사람, 다른 이름
    [("이서연", "속함", "정산팀", False)],          # 잘못 뽑음
    [("박민수", "이끔", "정산팀", False)],          # 잘못 뽑음
    [("결제팀", "속함", "이서연", False)],          # 방향 뒤집힘
    [("박민수", "관리", "결제팀", True)],            # 같은 뜻, 다른 관계 이름
    [("이서연", "속함", "결제팀", True)],           # 중복
    [("PM", "이끔", "결제팀", True)],               # 또 다른 이름
    [("박민수", "이끔", "결제팀", True)],           # 중복
]
```

「박민수」를 세 명으로 만든 것은 **1턴 / 3턴 / 9턴**이고, 셋 다 플래그가 `True`다. 반면 `False`인 4·5·6턴은 사람을 늘리는 데 아무 기여도 하지 않는다. 이 대비가 이 예제의 요점이다 — **틀린 사실 3개는 따로 있고, 노드 분열은 맞는 사실 3개가 만들었다.**

## 2. 왜 갈라지나 — `ensure()`가 문자열을 그대로 키로 쓴다

스키마부터 이름이 곧 기본키다.

```python
c.execute("CREATE NODE TABLE N(name STRING, PRIMARY KEY(name))")
```

그리고 노드를 만드는 쪽은 이 함수뿐이다.

```python
def ensure(c, name):
    r = c.execute("MATCH (n:N {name:$n}) RETURN n.name", {"n": name})
    if not r.has_next():
        c.execute("CREATE (:N {name:$n})", {"n": name})
```

`MATCH (n:N {name:$n})`은 **문자 그대로의 완전 일치**다. 별칭 사전도, 유사도 비교도, 정규화도 없다. 그래서

- `ensure(c, "박민수")` → 없음 → 새 노드 생성
- `ensure(c, "민수")` → 「박민수」와 다른 문자열 → **또 새 노드 생성**
- `ensure(c, "PM")` → 역시 다른 문자열 → **또 새 노드 생성**

`ensure`는 "이 이름의 노드가 있나"만 묻지 **"이 사람이 있나"는 묻지 못한다.** 여기가 결함 지점이다. 27장에서 다룬 개체 해상도(entity resolution)가 쓰기 경로에 하나도 없는 상태다.

## 3. 실제 실행 출력 (kuzu 0.11.3, Python 3.13)

```
  턴    노드    엣지  이번에 넣은 것
--------------------------------------------------------
  1     2     1  박민수 -이끔-> 결제팀
  2     3     2  이서연 -속함-> 결제팀
  3     4     3  민수 -이끔-> 결제팀
  4     5     4  이서연 -속함-> 정산팀  ← 틀린 사실
  5     5     5  박민수 -이끔-> 정산팀  ← 틀린 사실
  6     5     6  결제팀 -속함-> 이서연  ← 틀린 사실
  7     5     7  박민수 -관리-> 결제팀
  8     5     8  이서연 -속함-> 결제팀
  9     6     9  PM -이끔-> 결제팀
 10     6    10  박민수 -이끔-> 결제팀

10턴 뒤: 노드 6개, 엣지 10개. 그중 틀린 사실 3개.

«결제팀을 이끄는 사람»을 물으면: ['민수', '박민수', 'PM']
«정산팀» 을 물으면: ['박민수 -이끔->', '이서연 -속함->']   (전부 틀린 사실이다)
```

### 노드 수가 늘어나는 지점을 따라가면

| 턴 | 넣은 트리플 | 노드 수 | 늘어난 노드 |
|---|---|---|---|
| 1 | 박민수 -이끔-> 결제팀 | 2 | 박민수, 결제팀 |
| 2 | 이서연 -속함-> 결제팀 | 3 | 이서연 |
| 3 | **민수** -이끔-> 결제팀 | **4** | **민수 ← 분열 1회차** |
| 4 | 이서연 -속함-> 정산팀 | 5 | 정산팀 |
| 5~8 | (기존 이름만 등장) | 5 | — |
| 9 | **PM** -이끔-> 결제팀 | **6** | **PM ← 분열 2회차** |
| 10 | 박민수 -이끔-> 결제팀 | 6 | — |

최종 노드 6개 = {박민수, 민수, PM, 이서연, 결제팀, 정산팀}. 이 중 **앞의 셋이 같은 사람**이다. 실제 개체 수로 따지면 4개여야 하는데 6개가 됐다.

## 4. 조회 결과가 왜 「세 명」으로 보이나

```python
def leaders(c):
    r = c.execute("MATCH (p:N)-[e:R]->(t:N {name:'결제팀'}) "
                  "WHERE e.kind IN ['이끔','관리'] RETURN DISTINCT p.name")
```

`DISTINCT p.name`은 **이름 문자열 기준**의 중복 제거다. 「박민수 -이끔->」과 「박민수 -관리->」(7턴)와 「박민수 -이끔->」 재입력(10턴)은 이름이 같으니 하나로 접힌다. 하지만 「민수」와 「PM」은 문자열이 다르므로 접히지 않는다. 결과가 `['민수', '박민수', 'PM']` 세 줄이 되는 이유다.

주의할 점 — 이 셋은 **엣지 수가 아니라 노드 수 때문에** 셋이다. 중복 제거를 아무리 잘해도 노드가 셋이면 답은 셋이다.

## 5. 「반쯤 맞는 상태」가 왜 더 고약한가

예제가 마지막에 강조하는 대목이다.

- 「민수도 결제팀을 이끄나?」 → **맞다** (같은 사람의 다른 이름이므로)
- 「PM도 결제팀을 이끄나?」 → **맞다**
- 「결제팀을 이끄는 사람이 몇 명인가?」 → **답이 3인데 정답은 1이다. 틀렸다.**

각 엣지를 하나씩 검사하면 전부 통과한다. 그래서 **엣지 단위 정확도 지표로는 이 오류가 잡히지 않는다.** 오류는 개별 사실이 아니라 「개체가 하나로 모여 있는가」라는 그래프 구조 속성에 있다. 조회 결과만 보고 문제를 알아채기 어려운 것도 이 때문이다.

한편 `정산팀` 조회는 성격이 다르다.

```
«정산팀» 을 물으면: ['박민수 -이끔->', '이서연 -속함->']   (전부 틀린 사실이다)
```

이쪽은 4·5턴의 **명백히 틀린 사실**이 그대로 답이 된 경우다. 「조회는 있는 것을 전부 준다. 넣을 때 안 거른 것은 꺼낼 때도 안 걸러진다.」 즉 이 예제에는 두 가지 실패가 동시에 들어 있다.

| 실패 유형 | 원인 | 해당 턴 | 고치는 관문 |
|---|---|---|---|
| **노드 분열** (박민수 3명) | 맞는 사실 + 표기 불일치 | 1, 3, 9 | 이름 정규화(별칭) |
| **오답 유입** (정산팀 답변) | 잘못 뽑은 추출 결과 | 4, 5, 6 | 확신도 / 스키마 / 단일값 |

## 6. 그래서 어떻게 고치나 — `ex2_write_gate.py`

이어지는 예제 2가 쓰기 앞에 관문을 세운다. 노드 분열을 담당하는 것은 **정규화 관문**이다.

```python
ALIAS = {"민수": "박민수", "PM": "박민수"}
CANON = {"관리": "이끔", "리드": "이끔", "소속": "속함"}
...
    s = ALIAS.get(s, s)      # 막는 게 아니라 «고친다»
    k = CANON.get(k, k)
```

정규화는 후보를 **거절하는** 관문이 아니라 **고쳐서 통과시키는** 관문이다. 「민수」·「PM」이 「박민수」로 바뀌어 들어가므로 예제 1의 세 노드가 하나로 합쳐진다. 그리고 이름이 같아진 덕분에 그 다음의 **중복 관문**이 비로소 작동해서 반복 입력을 걸러 낸다.

여기서 예제 2가 못박는 순서 규칙이 나온다.

> 순서가 중요하다. 정규화를 먼저 하고 중복을 나중에 봐야 한다.
> 거꾸로 하면 «민수»와 «박민수»가 다른 것으로 보여서 중복이 안 걸린다.

관계 이름도 마찬가지다. 7턴의 「박민수 -관리-> 결제팀」은 「이끔」과 같은 뜻인데 예제 1에서는 별개 엣지로 남는다. `CANON`이 「관리 → 이끔」으로 정규화하면 이 역시 중복으로 걸린다.

## 7. 이 카드에서 꼭 가져갈 것

1. **노드 분열의 원인은 오답이 아니라 표기 불일치다.** 세 트리플 모두 `True`였다.
2. **추출 정확도를 올려도 안 고쳐진다.** 추출기는 문서에 적힌 대로 「민수」·「PM」을 정확히 뽑았을 뿐이다. 고칠 곳은 추출기가 아니라 **쓰기 경로의 정규화**다.
3. **정체성을 문자열로 두면 문자열 수만큼 개체가 생긴다.** `PRIMARY KEY(name)` + 완전 일치 `MATCH`가 구조적 원인이다.
4. **정규화 → 중복 검사 순서**를 지켜야 둘 다 효과가 난다.
5. 읽기 전용 그래프에서는 이 현상이 잘 안 생긴다. 사람이 넣은 것만 있기 때문이다. **쓰기를 여는 순간 품질 관리가 시스템의 일부**가 된다 — 28장 전체의 출발점.
