# `ex2_graphrag_lite.py`의 요약문은 어떻게 만들며, 그 이유는 무엇인가

## 한 줄 답

**규칙 기반**으로 만든다. 모델을 부르지 않으므로 매번 같은 결과가 나온다. 진짜 GraphRAG는 이 자리에 LLM을 쓰지만, 이 예제가 보여 주려는 것은 **요약 품질이 아니라 '언제 접느냐'**이기 때문이다.

---

## 1. 코드에서 실제로 무슨 일이 일어나는가

요약을 만드는 곳은 `summarize()` 하나뿐이다.

```python
def summarize(community, triples):
    """커뮤니티 요약. 규칙 기반이라 매번 같은 결과가 나온다."""
    members = set(community)
    causes = Counter(o for s, p, o in triples
                     if p == "원인" and s in members and o in members)
    docs = sorted(m for m in members if m.startswith("d"))
    top = ", ".join(f"{c}({n}건)" for c, n in causes.most_common(3))
    return {"문서": docs, "요약": f"문서 {len(docs)}건. 자주 나온 원인: {top or '없음'}",
            "원인분포": causes}
```

하는 일을 풀어 쓰면 세 줄이다.

1. 커뮤니티 안에 있는 트리플 중 `원인` 술어만 고른다.
2. `Counter`로 목적어(원인)를 센다.
3. 상위 3개를 f-string 템플릿(`"문서 N건. 자주 나온 원인: ..."`)에 끼워 넣는다.

즉 **세기(count) + 정렬 + 문자열 템플릿**이다. 자연어 생성이 아니라 집계 결과의 포맷팅이다. 커뮤니티 탐지도 마찬가지로 외부 라이브러리 없이 라벨 전파(label propagation)를 직접 구현했고, 챕터 README가 못 박아 둔 전제가 **"의존성 없음"**이다.

한 가지 놓치기 쉬운 디테일: 세는 범위가 `s in members and o in members`로 **커뮤니티 내부로 한정**된다. 전역 카운터가 아니라 뭉치마다 접어 둔 부분합이고, 질의 시점에 `main()`이 그 부분합들을 `total.update(...)`로 다시 합친다. 이 "부분합을 접어 두고 나중에 편다"는 구조 자체가 GraphRAG의 map-reduce식 전역 검색을 축소해 놓은 것이다.

---

## 2. 왜 굳이 규칙인가 — 교육용 예제의 설계 원칙

이 선택은 게으름이 아니라 의도된 제약이다. 세 가지를 얻는다.

| 원칙 | 규칙 기반이 주는 것 | LLM을 썼다면 |
|---|---|---|
| **결정성** | 같은 입력 → 같은 출력. 독자가 본 화면과 저자가 본 화면이 같다 | 온도·모델 버전·프롬프트에 따라 매번 다른 문장 |
| **의존성 0** | `python3 ex2_graphrag_lite.py` 한 줄. 표준 라이브러리만 | API 키, SDK 설치, 네트워크, 과금 계정 |
| **재현성** | 몇 년 뒤에도 돌아간다. 책의 코드 예제 수명이 모델 수명에 묶이지 않는다 | 모델이 폐기되면 예제가 죽는다 |

여기에 하나 더 있다. **관심의 초점을 지킨다.** 이 예제가 증명해야 하는 명제는 "요약문이 훌륭하다"가 아니라 "전역 질문은 색인 시점에 세어 두면 답할 수 있다"다. LLM 요약을 붙이면 독자의 시선이 "요약이 잘 됐나"로 옮겨 가고, 실패했을 때 그것이 **아키텍처의 실패인지 프롬프트의 실패인지 분간할 수 없게 된다**. 규칙 기반은 변수를 하나로 줄여, 성공하든 실패하든 그 원인이 오직 "언제 세었는가"에 있게 만든다.

## 3. 진짜 GraphRAG는 어떻게 다른가

Microsoft GraphRAG의 색인 파이프라인은 대략 이렇다.

```
원문 청크
  → (LLM) 엔티티·관계 추출
  → 지식 그래프 구성
  → 커뮤니티 탐지 (Leiden, 계층적)
  → (LLM) 커뮤니티 리포트 = 요약문 생성   ← ex2의 summarize() 자리
질의 시점: 커뮤니티 리포트들에 map-reduce → 전역 답변
```

`summarize()`가 있는 자리에 **LLM이 쓴 커뮤니티 리포트(community report)**가 들어간다. 그 대가로 세 가지 비용이 따라온다.

- **비용**: 커뮤니티 하나마다 LLM 호출이다. 계층 구조라 상위 레벨 요약까지 다시 부른다. 색인 한 번이 코퍼스 규모에 비례하는 토큰 청구서로 돌아온다. 챕터 요약이 "색인이 비싸고 갱신이 어렵습니다"라고 적은 그 비용이 여기서 나온다.
- **비결정성**: 같은 코퍼스를 두 번 색인하면 요약문이 달라진다. 회귀 테스트를 쓰기가 어렵고, 답이 바뀌었을 때 데이터가 바뀐 건지 모델이 다른 말을 한 건지 구분하기 힘들다.
- **환각 위험**: 요약문은 원문이 아니라 **모델이 생성한 2차 산출물**이다. 질의 시점에 읽는 것이 이 2차 산출물이므로, 색인 시점의 환각이 그대로 굳어 답변에 실린다. 원문 조각을 그대로 넣는 순수 RAG에는 없던 종류의 위험이다.

`ex2`는 이 세 가지를 전부 0으로 만든 대신, 요약문의 표현력도 0으로 만들었다. 트레이드오프를 의도적으로 한쪽 끝까지 밀어 둔 것이다.

## 4. 핵심 논점: 요약 품질이 아니라 '언제 세느냐'

이 카드의 진짜 요지는 여기다.

|  | 조각 검색 (`ex1`) | GraphRAG (`ex2`) |
|---|---|---|
| 전체를 훑는 시점 | 없음 | **색인 시점** (한 번) |
| 질의 시점에 보는 것 | top-k 조각 k개 | 접어 둔 커뮤니티 요약 |
| 「전부 몇 건인가」 | k개 밖은 모른다 → 못 셈 | 이미 세어 둔 것을 펴기만 함 |
| 비용이 실리는 곳 | 질의 시점 (싸다) | 색인 시점 (비싸다) |
| 데이터 갱신 | 바로 반영 | 다시 접어야 함 |

`ex1`이 보여 주는 벽의 실체는 "조각을 더 넣으면 된다"로 넘을 수 없다는 것이다. 문서 12건이면 k=12로 전부 넣으면 되지만, 12만 건이면 못 넣는다. 그래서 **세는 시점을 질의 시점에서 색인 시점으로 옮기는 것**이 유일한 풀이다.

요약문이 규칙으로 만들어졌든 LLM으로 만들어졌든 **이 시점 이동은 똑같이 성립한다.** 요약 품질은 접어 둔 것의 해상도를 바꿀 뿐, 접는 시점을 바꾸지 않는다. 그래서 예제는 요약 품질을 버리고 시점만 남겼다.

## 5. 직접 돌려 본 결과 (그리고 재현성에 난 실금 하나)

```
=== 색인 시점 (한 번만) ===
노드 37개 → 커뮤니티 10개

  커뮤니티 1: 문서 3건. 자주 나온 원인: 멱등성 없음(3건), 중복 요청(2건)
  커뮤니티 2: 문서 1건. 자주 나온 원인: 캐시 만료(1건)
  ...

=== 질의 시점 ===
커뮤니티 요약을 합친 결과 — 원인 순위
  멱등성 없음: 3건
  중복 요청: 2건
  ...
답: ['멱등성 없음', '중복 요청']
정답: ['멱등성 없음', '재시도']
맞았나: 아니오
```

여기서 짚어 둘 것이 두 가지 있다.

**(1) `summarize()`는 확실히 결정적이다.** 커뮤니티가 정해지면 같은 요약문이 나온다. 카드의 답이 말하는 "매번 같은 결과"는 이 함수에 대한 진술이고, 그건 맞다.

**(2) 다만 파이프라인 전체는 실행마다 흔들린다.** 20회 돌려 보면 `맞았나: 예`가 5회, `아니오`가 15회 나온다. 원인은 요약이 아니라 그 앞 단계인 `label_propagation()`에 있다.

```python
best = Counter(label[m] for m in adj[n]).most_common(1)[0][0]
```

`adj[n]`은 문자열 `set`이고, 파이썬은 실행마다 문자열 해시를 무작위화한다(`PYTHONHASHSEED`). 그래서 집합 순회 순서가 달라지고, `most_common(1)`의 **동점 처리 순서**가 흔들려 커뮤니티 분할이 달라진다. 실제로 `PYTHONHASHSEED=0`을 고정하면 출력이 완벽히 같아진다.

이것은 카드의 답을 뒤집지 않는다 — 오히려 **왜 결정성을 설계 목표로 삼는지**를 보여 준다. 규칙 기반이라 원인을 코드 한 줄까지 추적할 수 있었다. 같은 흔들림이 LLM 요약에서 났다면 어느 층에서 났는지 분간조차 어려웠을 것이다. 그리고 커뮤니티가 잘게 쪼개져 "재시도(3건)"가 여러 뭉치로 흩어지는 현상 자체가, **접어 두는 단위를 잘못 잡으면 전역 집계가 새어 나간다**는 GraphRAG의 실제 난점이기도 하다.

## 6. 헷갈리기 쉬운 지점

- ❌ "규칙 기반이라 GraphRAG를 제대로 구현 못 한 것" → ✅ 요약 생성기를 의도적으로 최소 부품으로 바꿔 끼워, **시점 이동이라는 변수만 남긴** 것이다.
- ❌ "LLM을 쓰면 이 예제가 더 좋아진다" → ✅ 답변 문장은 좋아지지만, 증명하려는 명제(전역 질문은 색인 시점에 접어야 답할 수 있다)에는 아무것도 더하지 않는다. 대신 비용·비결정성·환각이 붙는다.
- ❌ "GraphRAG가 RAG보다 항상 낫다" → ✅ 챕터 요약이 명시한다. 단순 사실 조회에서는 그래프를 붙인 쪽이 살짝 진다. **전역 질문 비율이 5%도 안 되면 안 붙이는 게 맞다.**

## 한 줄 정리

`summarize()`는 커뮤니티 안의 `원인` 트리플을 세어 템플릿에 끼우는 규칙 함수다. 결정성·의존성 0·재현성을 확보해 독자의 시선을 요약 품질이 아니라 **색인 시점 vs 질의 시점**이라는 단 하나의 축에 고정하기 위한 선택이며, 그 자리에 LLM이 들어간 것이 진짜 GraphRAG이고 그 대가가 비용·비결정성·환각이다.
