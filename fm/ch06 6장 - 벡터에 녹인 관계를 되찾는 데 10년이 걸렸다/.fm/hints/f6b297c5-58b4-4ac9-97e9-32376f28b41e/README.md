# 6장이 정직하게 밝히는 GraphRAG의 약점

> **질문** 6장이 정직하게 밝히는 GraphRAG의 약점은 무엇인가?
>
> **답** 사실 조회에서는 그래프를 붙인 쪽이 살짝 진다. 전역 질문 비율이 5%도 안 되면 붙이지 않는 것이 맞다.

원문의 「한 장 요약」 마지막 줄이 그대로 이 카드입니다.

> 그리고 정직하게 말하면, 사실 조회에서는 그래프를 붙인 쪽이 살짝 집니다. 전역 질문 비율이 5%도 안 되면 안 붙이는 게 맞습니다.

이 문장이 왜 「정직」한 문장인지부터 짚고 갑니다. 6장의 앞 세 줄은 전부 GraphRAG 쪽의 승리 선언입니다. 조각 검색은 전역 질문에 벽이 있고, 색인 시점에 접어 두면 그 벽을 넘고, 그래서 그래프를 다시 꺼냈다. 여기서 끝내면 홍보 문구가 됩니다. 네 번째 줄은 그 승리에 값이 붙어 있다고 밝히는 줄입니다. **이기는 구간이 있으면 지는 구간도 있고, 지는 구간이 대부분이면 붙이지 않는 게 맞다**는 것이 카드의 핵심입니다.

---

## 1. 용어부터 정확히

| 구분 | 뜻 | 6장 예시 |
|---|---|---|
| **사실 조회** (local factoid) | 답이 **한 조각 안에** 들어 있는 질문 | 「d01 결제 장애의 원인이 뭐였나?」 → d01 문서 한 줄이면 끝 |
| **전역 질문** (global / sensemaking) | 답이 **전체를 훑어야** 나오는 질문 | 「우리 장애 회고 전체에서 반복되는 원인은?」 → 12건 전부 세야 나옴 |

`corpus.py`가 이 대비를 위해 설계돼 있습니다. 주석에 대놓고 써 있습니다.

```
이 문서 묶음에는 «한 조각 안에 답이 들어 있지 않은» 질문이 숨어 있다.
전체를 훑어야 보이는 반복 패턴이 그것이다.
```

`GLOBAL_QUESTION = "우리 장애 회고 전체에서 반복되는 원인은 무엇인가?"`, `GROUND_TRUTH = {"멱등성 없음", "재시도"}`. 정답 「멱등성 없음」은 d01, d02, d06, d09 네 건에 흩어져 있습니다. 어느 한 조각도 이 답을 갖고 있지 않습니다.

**그런데 반대로 보면**: 「d05 정산 배치는 왜 중단됐나?」 같은 질문은 d05 한 줄 안에 답이 통째로 들어 있습니다. 이런 질문에 그래프는 **도울 것이 없습니다.** 도울 것이 없는데 비용은 그대로 드는 것 — 그게 「살짝 진다」의 출발점입니다.

## 2. 왜 사실 조회에서 지는가 — 다섯 갈래 메커니즘

「살짝 진다」는 한 가지 이유가 아니라 다섯 가지가 조금씩 겹쳐서 생깁니다.

### 2-1. 천장이 이미 닫혀 있다 (recall 1을 넘을 수 없다)

가장 근본적인 이유입니다. 사실 조회에서 벡터 검색은 **이미 정답 조각을 top-k 안에 넣습니다.** 재현율이 사실상 1입니다.

그래프 탐색이 하는 일은 **후보 집합을 넓히는 것**입니다. 이웃 노드를 따라가고, 2홉을 펴고, 커뮤니티 형제 문서를 끌어옵니다. 재현율을 올리는 연산입니다.

그런데 재현율이 이미 1인 문제에 재현율 연산을 붙이면?

```
얻는 것: 0  (이미 다 찾았으니까)
잃는 것: 정밀도  (안 필요한 이웃이 딸려 들어오니까)
```

이게 「살짝 진다」의 수학적 뼈대입니다. 상한이 닫힌 문제에 상한을 넓히는 도구를 쓰면 순손실입니다. 「도움이 안 된다」가 아니라 **구조적으로 손해**입니다.

### 2-2. 요약은 손실 압축이다 — 접으면 디테일이 날아간다

`ex2_graphrag_lite.py`의 `summarize()`가 무엇을 만드는지 보십시오.

```python
return {"문서": docs, "요약": f"문서 {len(docs)}건. 자주 나온 원인: {top or '없음'}",
        "원인분포": causes}
```

출력은 이런 모양입니다.

```
커뮤니티 1: 문서 4건. 자주 나온 원인: 멱등성 없음(4건), 재시도(2건)
```

원문에 있던 문장을 보십시오.

```
d01: "결제 서비스 장애. 재시도 로직이 중복 결제를 만들었다. 멱등 키가 없었다."
```

요약에 **「중복 결제」도 「멱등 키」도 없습니다.** 「멱등성 없음: 4건」이라는 숫자만 남았습니다. 「d01에서 정확히 무슨 일이 벌어졌나」를 물으면 커뮤니티 요약은 **답할 수 없습니다.** 원본 조각은 답할 수 있습니다.

접기(folding)는 **전역 질문에 답하기 위해 개별성을 버리는 거래**입니다. 세는 데는 좋고 짚는 데는 나쁩니다. 검색이 원본 조각 대신 요약을 물어 오면, 그 순간 사실 조회는 손해를 봅니다.

원문 주석이 이걸 미리 밝혀 둡니다. 「진짜 GraphRAG 는 요약문을 모델이 쓰지만, 여기서는 규칙으로 만든다. 보여 주려는 건 요약문의 품질이 아니라 «언제 접느냐»이다.」 — 모델이 써도 **접는다는 사실 자체는 그대로**입니다. 손실 압축이라는 성질은 요약자가 규칙이든 LLM이든 바뀌지 않습니다.

### 2-3. 6.1절과 똑같은 거래다 — 과평활의 다른 옷

이 장에서 가장 예쁜 대칭입니다. **`ex3`의 과평활과 `ex2`의 커뮤니티 요약은 같은 거래입니다.**

`ex3_message_passing.py`의 한 층:

```python
avg = [sum(feat[m][i] for m in nbrs) / len(nbrs) for i in range(len(v))]
out[n] = [round(w_self * v[i] + w_nbr * avg[i], 3) for i in range(len(v))]
```

자기 값에 이웃 평균을 섞습니다. 원문 결론:

```
얻는 것: 이웃이 비슷하면 벡터도 비슷해진다. 그래서 링크 예측이 된다.
잃는 것: 2층을 지나면 어느 이웃이 얼마나 기여했는지 되짚기 어렵다.
층을 깊게 쌓으면 모든 노드가 비슷해지기까지 한다(과평활, over-smoothing).
```

| | GNN (6.1) | GraphRAG (6.3) |
|---|---|---|
| 뭉치는 단위 | 노드 벡터 ← 이웃 평균 | 문서 조각 → 커뮤니티 요약 |
| 얻는 것 | 구조가 값에 녹아 예측이 된다 | 전체가 요약에 접혀 세기가 된다 |
| 잃는 것 | 개별 노드의 고유성 (과평활) | 개별 조각의 디테일 (사실 조회) |
| 관행적 방어 | 2~3층에서 멈춘다 | 원본 조각도 같이 보관한다 |

**뭉치면 전체가 보이고 개별이 흐려진다.** 6장 전체가 이 한 문장의 변주입니다. 카드의 「사실 조회에서 살짝 진다」는 이 원리가 검색 계층에서 나타난 형태일 뿐입니다.

### 2-4. 문맥 예산 경쟁 — 좋은 조각을 밀어낸다

컨텍스트 윈도는 유한합니다. 그래프를 붙이면 같은 예산 안에 새 손님이 들어옵니다.

- 추출된 트리플 (`("d01", "원인", "재시도")` 같은 것)
- 이웃 노드로 딸려 온 문서들
- 커뮤니티 요약문

사실 조회에서 이것들은 전부 **정답과 무관한 짐**입니다. 짐이 들어온 만큼 원본 조각이 밀려나거나, 남더라도 잡음 속에 묻힙니다. 모델은 문맥이 길어지고 산만해질수록 정답을 놓치기 쉽습니다(가운데 묻히는 현상). 정답 조각이 문맥 **안에** 있는데도 틀리는 실패가 여기서 나옵니다.

이 실패 유형이 특히 고약한 이유: 검색 로그만 보면 「정답 조각을 찾았다」고 나옵니다. 재현율 지표는 멀쩡한데 최종 정확도가 떨어집니다. 그래서 원인 추적이 어렵습니다.

### 2-5. 추출 오류가 한 단계 더 끼어든다

벡터 RAG의 경로는 짧습니다.

```
질문 → 임베딩 → top-k 조각 → 답
```

GraphRAG는 색인 시점에 단계가 하나 더 있습니다.

```
문서 → [엔티티/관계 추출] → 그래프 → [커뮤니티 탐지] → [요약] → 질의
```

대괄호 친 세 단계가 전부 **오류를 만들 수 있는 지점**입니다. 특히 첫 단계. 원문이 이걸 다음 장으로 넘깁니다. 「각 문서에서 뽑은 (문서, 관계, 개념) 트리플. **15장에서 이 추출 자체를 다룬다.**」

`corpus.py`의 `TRIPLES`는 **사람이 손으로 정확하게 써 놓은 것**입니다. 현실에서는 LLM이 뽑고, 틀립니다. 같은 개념을 「멱등성 없음」과 「멱등 키 부재」로 따로 뽑으면 노드가 갈라지고, 다른 개념을 같은 이름으로 뭉치면 없는 간선이 생깁니다(이게 5장 「문자열이 아니라 사물」이 다룬 동일성 문제입니다). 없는 간선 하나가 엉뚱한 문서를 문맥으로 끌고 들어옵니다.

벡터 검색에는 이 중간 단계가 아예 없습니다. **없는 단계는 틀리지 않습니다.** 파이프라인이 길수록 사실 조회처럼 「원래 잘 되던 일」에서 깎일 여지가 커집니다.

### 보너스: 표면 문자열은 그래프 스키마에 없다

사실 조회 질문은 종종 엔티티가 아니라 표면 문자열을 겨냥합니다. 「타임아웃이 몇 초였나」, 「어느 지역 스토리지였나」. 추출 스키마에 `원인`/`영역` 두 술어만 있으면 이런 정보는 **그래프에 존재하지 않습니다.** 그래프 탐색으로는 닿을 수 없고, 원본 조각으로만 닿습니다. 그래프는 여기서 도움이 0인 채로 지연과 토큰만 씁니다.

### 「살짝」이라는 단어가 중요한 이유

원문이 「크게 진다」가 아니라 **「살짝 집니다」**라고 쓴 것에 주의하십시오. 손실이 재앙급이면 판단이 쉽습니다 — 안 쓰면 됩니다. 손실이 몇 점 수준이라 **판단이 진짜로 애매해지는 것**이 문제입니다. 그래서 다음 절의 비율 계산이 필요해집니다.

## 3. 5% 기준의 의사결정 논리

### 3-1. 기댓값 한 줄

전역 질문 비율을 `p`, 전역에서 얻는 이득을 `G`, 사실 조회에서 잃는 손해를 `L`이라 두면:

```
순이득 = p × G − (1 − p) × L
```

손익분기점은 `순이득 = 0`, 즉:

```
p* = L / (G + L)
```

여기에 6장이 실제로 보여 준 값의 **성격**을 넣습니다.

- **`G`는 크다.** `ex1`이 보여 준 것은 점수 하락이 아니라 **불가능**입니다. 「전체 12건 중 4건만 봤다. 나머지 8건에 무엇이 있는지 모른다.」 전역 질문에서 조각 검색은 0점에 가깝고, GraphRAG는 `맞았나: 예`를 출력합니다. 이득이 **계단**입니다.
- **`L`은 작다.** 「살짝」입니다. 몇 점 수준.

`L`이 한 자릿수 초반이고 `G`가 수십 점이면:

```
L=3,  G=50  →  p* ≈ 5.7%
L=4,  G=50  →  p* ≈ 7.4%
L=2,  G=60  →  p* ≈ 3.2%
```

**손익분기점이 한 자릿수 퍼센트에 떨어집니다.** 5%라는 숫자는 여기서 나온 자릿수 감각입니다. 정밀하게 측정된 상수가 아니라 **어림 기준**으로 읽어야 맞습니다. 카드 답을 외울 때 「5%」라는 숫자보다 **「손해는 작고 이득은 계단이라서 분기점이 한 자릿수로 내려간다」**는 구조를 기억하는 편이 안전합니다.

### 3-2. 이 비대칭이 뜻하는 것

`p* ≈ 5%`라는 결과는 사실 **GraphRAG에 유리한 진술**입니다. 전역 질문이 스무 개 중 하나만 있어도 붙일 값어치가 있다는 뜻이니까요. 이 낮은 분기점은 `G ≫ L`이라는 비대칭에서 나옵니다.

그러니 기준선을 이렇게 읽으십시오.

- `p ≥ 5%` — 붙일 값어치가 있다. 사실 조회의 몇 점 손해를 전역 질문의 계단이 갚는다.
- `p < 5%` — **손해가 작다는 사실이 오히려 근거가 안 된다.** 작은 손해를 95% 이상의 질문에 매번 물리면서, 갚을 기회는 스무 번에 한 번도 안 온다.

### 3-3. 정확도 밖의 비용이 기준선을 밀어 올린다

위 계산은 정확도만 봤습니다. GraphRAG에는 정확도와 무관하게 **고정으로 드는 비용**이 있습니다. `ex2`의 마지막 문단이 이걸 명시합니다.

```
대가도 분명하다. 색인이 비싸고, 문서가 바뀌면 다시 접어야 한다.
그래서 자주 바뀌는 데이터에는 안 맞는다. 17장에서 이 손익을 따진다.
```

| 비용 | 성격 | 질문 비율과의 관계 |
|---|---|---|
| 초기 색인 | 전 문서에 대한 추출 + 요약 LLM 호출 | `p`와 **무관하게** 든다 |
| 재색인 | 문서 갱신 때마다 다시 접어야 함 | `p`와 무관, **갱신 빈도**에 비례 |
| 질의 지연 | 그래프 조회 + 요약 읽기 | 매 질의마다 |
| 운영 복잡도 | 그래프 저장소, 파이프라인, 스키마 관리 | 상시 |

`p`가 작을수록 이 고정비를 나눠 짊어질 「이득 보는 질문」이 적어집니다. **그래서 실무 기준선은 순수 정확도 분기점보다 조금 높아집니다.** 5%는 그 보정까지 대충 얹은 숫자로 보는 편이 실제에 가깝습니다.

여기서 **두 번째 축**이 나옵니다. 판단은 `p` 하나가 아니라 두 축입니다.

|  | 갱신 드묾 | 갱신 잦음 |
|---|---|---|
| **`p` 큼** | 붙인다 (교과서적 적합) | 재색인 비용 먼저 따진다 — 17장 |
| **`p` 작음** | 붙이지 않는다 | 붙이지 않는다 (제일 확실) |

전역 질문이 아무리 많아도 문서가 매시간 바뀌면 접어 둔 요약이 계속 상해서 이득이 증발합니다. 반대로 `p`가 작으면 갱신 빈도와 상관없이 답은 「붙이지 않는다」입니다.

### 3-4. `p`는 세는 것이지 짐작하는 게 아니다

이 기준을 쓰려면 `p`를 알아야 합니다. **직감으로 정하면 안 됩니다.** 아키텍트의 머릿속 `p`는 거의 항상 실제보다 큽니다 — 전역 질문이 기술적으로 재미있어서 기억에 남기 때문입니다.

실제로 하는 일:

1. 질의 로그를 실제로 뽑는다 (없으면 만들 때까지 그래프를 붙이지 말 것)
2. 대표 표본 200~500건을 분류한다: **사실 조회 / 전역·집계 / 다중 홉**
3. 분류 기준은 한 줄로 고정한다 — 「답이 **한 조각 안에** 들어 있는가?」
4. 전역·집계 비율이 `p`
5. 5% 근처면 그때 재본다 (파일럿 색인 + 두 유형 각각의 정확도 실측)

`ex1`이 세는 법의 축소판입니다. 「k 를 12로 올려 전부 넣으면? 이 예제에서는 된다. 문서가 12건이니까. 문서가 12만 건이면 못 넣는다. **그게 이 한계의 실체다.**」 — 한계가 나타나는 지점도 규모에 달려 있습니다. 남의 벤치마크가 아니라 자기 코퍼스와 자기 로그로 재야 합니다.

### 3-5. 라우팅이라는 세 번째 선택지

「붙인다/안 붙인다」는 사실 이분법이 아닙니다. 실무의 답은 대개 **질문 유형별 라우팅**입니다.

```
질문 → 분류기 → 사실 조회면 벡터 검색 (그래프 안 거침)
                → 전역 질문이면 커뮤니티 요약
```

이러면 이론적으로 사실 조회의 손해 `L`이 0이 되고 분기점도 내려갑니다. 다만 공짜는 아닙니다.

- 분류기가 틀리면 **두 경로 다 나쁜 답**을 냅니다 (오분류 비용)
- 두 파이프라인을 동시에 유지해야 합니다
- 색인 고정비는 그대로 듭니다 — 라우팅은 질의 시점 손해만 줄이지 색인 비용은 못 줄입니다

**그래서 `p < 5%`면 라우팅으로도 구제가 안 됩니다.** 스무 번에 한 번도 안 쓰는 경로를 위해 전 코퍼스 색인과 재색인 파이프라인을 유지하는 셈이니까요. 라우팅은 「`p`가 애매하게 걸칠 때 손해를 깎는 수단」이지 「`p`가 작아도 그래프를 정당화하는 수단」이 아닙니다.

## 4. 한눈 정리

```
사실 조회 (답이 한 조각 안에)
  벡터 검색: 재현율 ≈ 1, 이미 천장
  그래프 추가: 넓히는 연산 → 얻을 게 없고 정밀도만 깎임
              + 요약이 디테일 삭제
              + 문맥 예산 잠식
              + 추출 오류 단계 추가
  결과: 살짝 진다

전역 질문 (전체를 세야)
  벡터 검색: 구조적 불가 (top-k 밖은 모름)
  그래프 추가: 색인 시점에 접어 뒀으니 펴면 됨
  결과: 계단식 이득

→ 손해 작고(L) 이득 큼(G) ⇒ p* = L/(G+L) ≈ 한 자릿수 %
→ 색인·재색인 고정비 얹어 실무 기준 ≈ 5%
→ p < 5%면 붙이지 않는다
```

## 5. 자주 틀리는 지점

| 헷갈리는 답 | 왜 틀렸나 |
|---|---|
| 「GraphRAG는 색인이 비싼 게 약점」 | 맞는 말이지만 **이 카드의 답이 아닙니다.** 색인 비용은 요약 3번째 줄(「대신 색인이 비싸고 갱신이 어렵습니다」)의 내용이고, 4번째 줄은 **정확도가 진다**는 별개의 고백입니다. 카드가 묻는 「정직하게 밝히는」 대목은 후자입니다. |
| 「전역 질문에서 진다」 | 정반대입니다. 전역 질문은 GraphRAG가 **이기는** 구간입니다. 지는 쪽은 **사실 조회**입니다. |
| 「크게 진다 / 쓰면 안 된다」 | **「살짝」**입니다. 손해가 작기 때문에 판단이 애매해지고, 그래서 비율 기준이 필요해진 것입니다. |
| 「5%는 정확도 임계값」 | 아닙니다. **전역 질문이 전체 질의에서 차지하는 비율**입니다. 정확도가 아니라 질문 구성비입니다. |
| 「5% 넘으면 안 붙인다」 | 부등호 방향이 반대입니다. **5%도 안 되면** 안 붙입니다. 5% 이상이면 붙일 값어치가 있습니다. |

Microsoft GraphRAG 원 논문의 평가는 **전역 sensemaking 질의**에 초점을 맞추고 있습니다. 즉 그 논문이 잘한다고 보인 구간과 이 카드가 「진다」고 말하는 구간은 애초에 다릅니다. 후속 작업(LightRAG, HippoRAG 등)이 색인 비용과 갱신 문제를 줄이는 방향으로 갈라져 나온 것도 같은 맥락에서 읽으면 자연스럽습니다.

> 3-1절의 `L=3, G=50` 같은 숫자는 「손해는 몇 점, 이득은 수십 점」이라는 원문의 정성적 서술에서 자릿수 감각을 잡으려고 넣은 예시 값입니다. 특정 벤치마크의 실측치가 아닙니다. 실제 도입 판단은 반드시 자기 코퍼스와 자기 질의 로그로 재십시오 (3-4절).
