# GraphRAG의 질의 시점 처리

**질문** — GraphRAG 방식의 질의 시점 처리는 어떻게 이루어지는가?

**답** — 색인 시점에 만들어 둔 커뮤니티 요약들의 원인 분포를 합쳐 순위를 낸다. 원문을 다시 훑지 않는다.

---

## 1. 핵심은 「세는 시점을 옮겼다」는 것

6장의 한 장 요약이 이 카드의 뿌리입니다.

> 풀이는 **세는 시점을 옮기는 것**입니다. 색인 시점에 그래프를 만들고 뭉치마다 요약을 접어 두면, 질의 시점에는 **펴기만** 하면 됩니다.

같은 질문(「우리 장애 회고 전체에서 반복되는 원인은 무엇인가?」)을 두 방식이 어떻게 다르게 처리하는지가 전부입니다.

| | 조각 검색(RAG) | GraphRAG |
|---|---|---|
| 색인 시점 | 문서를 잘라 임베딩만 저장 | 그래프 구축 → 커뮤니티 탐지 → **커뮤니티마다 요약을 씀** |
| 질의 시점에 읽는 것 | 원문 조각 top-k개 | **커뮤니티 요약들** |
| 전체를 셀 기회 | 없음 (k개만 봄) | 색인 때 이미 다 셌음 |
| 색인 비용 | 싸다 | 비싸다 (전 문서 훑기 + LLM 요약) |
| 질의 비용 | 싸다 | 중간 (요약 개수에 비례) |

즉 GraphRAG는 질의 시점을 싸게 만든 게 아니라, **비싼 일을 색인 시점으로 옮겨 놓고 한 번만 지불**한 것입니다.

## 2. 질의 시점에 실제로 벌어지는 일 (`ex2_graphrag_lite.py`)

예제 코드에서 색인/질의 경계가 눈에 보이게 나뉘어 있습니다.

```python
# ── 색인 시점 (한 번만) ────────────────────
adj = build_graph(TRIPLES)              # 트리플 → 그래프
communities = label_propagation(adj)    # 커뮤니티 탐지
summaries = [summarize(c, TRIPLES) for c in communities]
#   summarize() 가 남기는 것:
#   {"문서": [...], "요약": "문서 3건. 자주 나온 원인: ...", "원인분포": Counter(...)}

# ── 질의 시점 ──────────────────────────────
total = Counter()
for s in summaries:
    total.update(s["원인분포"])         # ← 요약들의 원인 분포를 «합친다»
for cause, n in total.most_common(5):   # ← 그리고 «순위를 낸다»
    print(f"  {cause}: {n}건")
```

질의 시점 루프를 보세요. 등장하는 이름은 `summaries` 뿐입니다. **`DOCS`(원문)가 어디에도 없습니다.** 카드의 "원문을 다시 훑지 않는다"가 가리키는 게 정확히 이것입니다.

동작 순서를 말로 풀면:

1. 질문이 들어온다
2. (실제 GraphRAG라면) 어느 계층 레벨의 커뮤니티 요약을 쓸지 고른다
3. 그 요약들이 들고 있는 집계값(예제에서는 `원인분포` Counter)을 **합산**한다
4. 합산 결과를 **정렬해 순위**를 낸다
5. 상위 항목을 답으로 내놓는다

원문 접근 없음, 벡터 검색 없음, top-k 없음.

## 3. 비용이 N이 아니라 C에 비례한다

이 카드가 실제로 시험하는 성질입니다.

- `ex1_rag_limits.py`의 한계: 문서 12건짜리 장난감에서는 `k=12`로 전부 넣으면 답이 나온다. **문서가 12만 건이면 못 넣는다.** 컨텍스트 창은 N에 맞춰 커지지 않는다.
- GraphRAG의 질의 비용은 **문서 수 N이 아니라 커뮤니티(요약) 수 C에 비례**한다. 그리고 그래프를 잘 접었다면 **C ≪ N**이다.

예제를 돌리면 노드 37개가 커뮤니티 9~11개로 접힙니다. 문서 12건 → 요약 ~10개니 별 이득이 없어 보이지만, 실제 규모에서는 이 압축비가 요점입니다. 문서 12만 건이 커뮤니티 수백 개로 접히면 질의 시점에 읽을 양이 세 자릿수 배로 줄어듭니다.

```
조각 검색  : 질의 비용 = O(k),  단 k ≪ N 이면 답이 «틀린다»  (전역 질문에서)
전부 넣기  : 질의 비용 = O(N),  N 이 크면 «불가능»
GraphRAG   : 질의 비용 = O(C),  C ≪ N 이고 색인 때 N 을 이미 다 봤으므로 «답이 된다»
```

주의할 점 하나. C는 공짜로 작아지지 않습니다. **색인 시점 비용은 여전히 O(N)** 이고, 요약을 LLM이 쓴다면 LLM 호출도 O(커뮤니티 수)만큼 듭니다. 그 O(N)을 질의마다가 아니라 **한 번만** 내는 게 이 설계의 거래입니다. 그래서 문서가 자주 바뀌면 그 한 번을 계속 다시 내야 하고, 곧바로 손해로 돌아섭니다.

## 4. 실제 Microsoft GraphRAG와의 대응

예제의 `total.update(...)`는 실제 GraphRAG **global search**를 산수 한 줄로 축약한 것입니다. 실물은 이렇습니다.

### global search — 커뮤니티 리포트에 대한 map-reduce

- **map 단계**: 선택한 계층 레벨의 **커뮤니티 리포트(community report)** 들을 정해진 크기의 청크로 나누고, 청크마다 LLM을 호출해 중간 답변을 만든다. 중간 답변은 「요점(point) + 그 요점의 중요도 점수」 목록 형태다.
- **reduce 단계**: 중간 답변들을 모아 **랭킹 + 필터링**으로 추려 최종 답을 합성한다.
- 예제와의 대응: `s["원인분포"]`가 map 단계의 중간 답변, `total.update(...)` + `most_common(...)`이 reduce 단계의 집계와 랭킹입니다.
- **비용**: LLM 호출 수 = (map 단계의 커뮤니티 리포트 청크 수) + (reduce 1회). **문서 수와 무관**합니다. `concurrent_coroutines` 설정이 map 단계 병렬도를 조절합니다.
- **커뮤니티 레벨 선택**: 커뮤니티는 Leiden 등으로 만든 **계층**이라 레벨을 고를 수 있습니다. 낮은(=세분화된) 레벨일수록 리포트가 상세해 답이 충실해지지만 리포트 수가 늘어 시간과 LLM 비용이 커집니다. **C를 직접 조절하는 손잡이**가 이것입니다.

### local search — 이쪽은 원문을 봅니다

대비해서 알아 둬야 카드의 진술 범위가 명확해집니다.

- 질문에서 의미적으로 관련된 **엔티티**를 먼저 찾고, 그 엔티티를 그래프 진입점으로 삼습니다.
- 거기서 연결된 것들을 끌어옵니다: **텍스트 유닛(원문 조각)**, 커뮤니티 리포트, 이웃 엔티티와 관계, 공변량(covariate).
- 후보들을 랭킹 + 필터링해 컨텍스트 창에 맞게 담고 LLM에 넘깁니다.
- 「캐모마일의 효능은?」처럼 **엔티티 국소 질문**에 강합니다.

정리하면, **"원문을 다시 훑지 않는다"는 global search의 성질**입니다. local search는 텍스트 유닛을 컨텍스트에 넣으므로 원문을 봅니다. (둘을 섞은 DRIFT search도 있습니다.) 카드가 말하는 「전역 질문 → 커뮤니티 요약 합산」은 global search 경로입니다.

| 예제 `ex2` | 실제 GraphRAG |
|---|---|
| `label_propagation()` | Leiden 계층 커뮤니티 탐지 |
| `summarize()` (규칙 기반) | LLM이 쓰는 커뮤니티 리포트 |
| `s["원인분포"]` 꺼내기 | map: 리포트 청크별 LLM 중간 답변 + 중요도 점수 |
| `total.update()` + `most_common()` | reduce: 랭킹 + 필터링 후 최종 합성 |
| 커뮤니티 9~11개 | 레벨별 커뮤니티 리포트 수 (레벨로 조절) |

예제 주석이 못 박아 둔 대로, `ex2`가 보여 주려는 건 요약 품질이 아니라 **언제 접느냐**입니다.

## 5. "원문을 다시 훑지 않는다"의 대가 — 요약에 없으면 답할 수 없다

여기가 이 카드에서 제일 자주 놓치는 부분입니다. 원문을 안 보는 건 **공짜 최적화가 아니라 정보 손실을 감수한 거래**입니다.

**요약은 손실 압축입니다.** 색인 시점에 「무엇을 접어 둘지」 정하는 순간, 접지 않은 것에 대한 질문은 질의 시점에 답할 방법이 사라집니다. 되돌아가 볼 원문이 (그 경로에는) 없기 때문입니다.

예제에서 이게 눈에 보입니다. `summarize()`는 `원인분포`만 접어 둡니다.

```python
causes = Counter(o for s, p, o in triples
                 if p == "원인" and s in members and o in members)
```

두 가지가 즉시 따라옵니다.

**(a) 안 접은 축은 못 센다.** `TRIPLES`에는 `("d01", "영역", "결제")`처럼 **영역** 관계도 있지만 요약에는 원인만 들어갑니다. 「영역별로 장애가 몇 건인가」를 질의 시점에 물으면 답이 안 나옵니다. 원문에는 있는데 요약에 없어서입니다.

**(b) 커뮤니티 경계에서 잘린 것도 못 센다.** 위 조건 `s in members and o in members`는 **한 커뮤니티 안에 닫힌 트리플만** 셉니다. 걸쳐 있는 건 누락됩니다. 실제로 돌려 보면:

```
진짜 전체 원인 카운트 : 멱등성 없음 4건, 재시도 3건, 중복 요청 2건, 부분 실패 2건, ...
요약을 합친 결과      : 재시도 2건, 멱등성 없음 1건, 캐시 만료 1건, ...
```

**숫자가 맞지 않습니다.** 순위 상위 2개가 우연히 정답과 겹쳐 「맞았나: 예」가 나왔을 뿐입니다. 커뮤니티 분할이 조금만 달라지면 답도 흔들립니다 — 이 예제는 이웃 집합 순회 순서에 따라 분할이 달라지는데, 실행마다 이런 결과가 나옵니다.

```
커뮤니티 9개  → 답: ['멱등성 없음', '재시도']   맞았나: 예
커뮤니티 10개 → 답: ['재시도', '중복 요청']     맞았나: 아니오
커뮤니티 9개  → 답: ['재시도', '중복 요청']     맞았나: 아니오
커뮤니티 10개 → 답: ['멱등성 없음', '부분 실패'] 맞았나: 아니오
```

(실행 간 흔들림 자체는 이 장난감 구현의 성질입니다. 하지만 **「색인 시점에 어떻게 접었는지가 질의 시점 답의 상한을 정한다」**는 교훈은 실물 GraphRAG에도 그대로 적용됩니다. 커뮤니티 레벨을 무엇으로 잡았는지, 리포트에 무엇을 적었는지가 답할 수 있는 질문의 범위를 결정합니다.)

**대가 목록 정리**

| 대가 | 내용 |
|---|---|
| 표현력 제한 | 요약에 접어 두지 않은 축·사실은 질의 시점에 복구 불가 |
| 정밀도 손실 | 집계값이 근사가 됨. 정확한 카운트가 필요하면 안 맞음 |
| 경계 효과 | 커뮤니티를 가로지르는 관계가 누락될 수 있음 |
| 색인 비용 | 전 문서 훑기 + 커뮤니티마다 LLM 요약. 비싸다 |
| 갱신 취약 | 문서가 바뀌면 다시 접어야 함 → 자주 바뀌는 데이터에 부적합 (17장) |
| 출처 추적 | 요약을 거치므로 「어느 원문 때문인가」가 한 단계 흐려짐 |

## 6. 그래서 언제 쓰나

6장이 스스로 놓는 제동입니다.

> 정직하게 말하면, **사실 조회에서는 그래프를 붙인 쪽이 살짝 집니다. 전역 질문 비율이 5%도 안 되면 안 붙이는 게 맞습니다.**

- **전역/집계형 질문**(「전부 몇 건인가」, 「반복되는 주제 상위 5개는」)이 워크로드에서 유의미한 비중 → global search가 값을 함
- **엔티티 국소 사실 조회**가 대부분 → 그냥 조각 검색(또는 GraphRAG local search)이 더 싸고 더 정확함
- **문서가 자주 바뀜** → 색인을 계속 다시 접어야 하므로 손익이 무너짐

## 한 문장 정리

GraphRAG의 질의 시점은 **검색이 아니라 집계**입니다. 색인 때 접어 둔 커뮤니티 요약들을 펴서 합치고(map-reduce) 순위를 내며, 비용은 문서 수 N이 아니라 커뮤니티 수 C(≪ N)에 비례합니다. 그 대가로 **접어 두지 않은 것은 영영 답할 수 없습니다** — 되돌아가 볼 원문이 그 경로에는 없기 때문입니다.
