# `ex1_rag_limits.py`에서 top-k를 12로 올리면 답을 맞힐 수 있는가?

> **답**: 이 예제에서는 문서가 12건뿐이라 가능하다. 그러나 문서가 12만 건이면 넣을 수 없고, 그것이 이 한계의 실체다.

이 카드는 "**장난감 예제에서는 통하는 해법이 규모에서 무너진다**"는 논점을 다룬다.
질문에 "예"라고 답하는 것 자체는 맞지만, 그 "예"가 왜 해결이 아니라 오히려 한계의 증명인지가 핵심이다.

---

## 1. 예제가 실제로 하는 일

`ex1_rag_limits.py`는 1장과 같은 방식(글자 2-gram TF-IDF + 코사인 유사도)으로
장애 회고 12건 중 상위 `TOP_K = 4`건만 뽑아 전역 질문에 답해 보려 한다.

```python
TOP_K = 4

GLOBAL_QUESTION = "우리 장애 회고 전체에서 반복되는 원인은 무엇인가?"
GROUND_TRUTH = {"멱등성 없음", "재시도"}
```

정답이 `{"멱등성 없음", "재시도"}`인 이유는 `corpus.py`의 트리플을 세어 보면 나온다.

| 원인 | 등장 문서 | 건수 |
|---|---|---|
| 멱등성 없음 | d01, d02, d06, d09 | **4** |
| 재시도 | d01, d04, d11 | **3** |
| 중복 요청 | d02, d09 | 2 |
| 부분 실패 | d05, d11 | 2 |
| 캐시 만료 / 상태 불일치 / 롤백 없음 / … | 각 1건 | 1 |

즉 정답은 "어느 한 문서 안에 적혀 있는 사실"이 아니라 **12건을 전부 세어야 나오는 집계값**이다.
4건만 보면 나머지 8건에 무엇이 있는지 원리적으로 알 수 없다.

프로그램 자신이 이 점을 출력으로 못 박는다.

```
전체 12건 중 4건만 봤다. 나머지 8건에 무엇이 있는지 모른다.
정답은 ['멱등성 없음', '재시도'] 인데, 이건 전체를 세어야 나오는 답이다.
```

## 2. k=12로 올리면? — "된다"의 정확한 의미

문서가 12건인데 k를 12로 올리면 `search()`가 반환하는 것은 **전체 문서 집합**이다.

```python
scored.sort(reverse=True)
return scored[:k]        # k >= len(docs) 이면 정렬만 하고 전부 반환
```

이때 벌어지는 일을 정확히 짚어야 한다.

- **검색기가 사라진다.** 랭킹은 순서만 바꿀 뿐 아무것도 걸러내지 않는다. `search()`는 사실상 `sorted(DOCS)`가 된다.
- **RAG가 아니라 전수 조회(full scan)다.** 조각 검색으로 답을 찾은 게 아니라, 코퍼스 전체를 그냥 컨텍스트에 부어 넣은 것이다.
- **즉 k=N은 검색을 포기함으로써 검색의 한계를 회피한 것**이지, 검색의 한계를 극복한 것이 아니다.

> `k = N`은 "검색을 잘했다"가 아니라 "검색을 안 했다"이다.

덧붙여, 이 예제의 전역 질문은 랭킹 자체가 거의 무의미하다.
질문 문자열("우리 장애 회고 전체에서 반복되는 원인은 무엇인가?")과 개별 문서("결제 서비스 장애. 재시도 로직이 중복 결제를 만들었다…")는
겹치는 2-gram이 거의 없다. 점수는 사실상 잡음이고, 상위 4건이 정답에 기여하는 문서일 이유가 없다.
**전역 질문에서는 top-k의 k뿐 아니라 top 자체가 의미를 잃는다.**

## 3. 문서가 12만 건이면 — 세 겹의 벽

`k = N` 전략은 N이 작을 때만 성립한다. N이 커지면 세 가지가 순서대로 무너진다.

### (1) 컨텍스트 창

이 코퍼스의 문서 하나는 대략 30~50토큰이다. 12만 건이면 어림잡아

```
120,000건 × ~50토큰 ≈ 600만 토큰
```

현재 최상위 모델의 컨텍스트 창이 100만 토큰 수준이므로, **한 번의 요청에 애초에 들어가지 않는다.**
실무 문서(회고 문서 한 건이 수천 토큰인 경우)라면 격차는 수십~수백 배로 벌어진다.
"k를 조금 더 올린다"로 메울 수 있는 차이가 아니다.

### (2) 비용과 지연

설령 들어간다 해도, 질의 **한 건마다** 코퍼스 전체를 다시 읽는다.
입력 100만 토큰당 몇 달러 수준의 요금 체계에서 600만 토큰이면 질문 하나에 수십 달러다.
게다가 이 비용은 **캐시로 줄지 않는다** — 질문마다 뒤쪽 내용이 달라지고, 무엇보다 답은 매번 코퍼스 전체를 다시 세야 나온다.
지연 시간도 마찬가지로 토큰 수에 비례해 늘어난다.

### (3) lost-in-the-middle (중간 유실)

가장 조용하고 가장 위험한 벽이다.
컨텍스트에 넣기만 하면 모델이 다 읽는다는 가정은 사실이 아니다.
긴 컨텍스트에서 모델의 정확도는 **관련 정보가 입력의 앞이나 뒤에 있을 때 가장 높고, 가운데 있을 때 눈에 띄게 떨어진다**
(Liu et al., *Lost in the Middle: How Language Models Use Long Contexts*, 2023).

이 성질이 전역 질문에 특히 치명적인 이유는, 전역 질문의 답이 **전 구간에 고르게 분포**하기 때문이다.

- "d07의 원인은?" → 답이 한 조각에 있음. 그 조각만 앞쪽에 놓으면 된다.
- "전체에서 반복되는 원인은?" → d01, d02, d04, d06, d09, d11이 전부 필요. **그중 상당수는 반드시 가운데에 놓인다.**

그래서 컨텍스트를 늘릴수록 세기의 정확도는 조용히 떨어진다.
에러도 안 나고, 그럴듯한 오답이 나온다. 12건짜리 예제에서는 절대 관측되지 않는 실패 모드다.

```
문서 수 N →

  N=12      [전부 넣기]  ✅ 된다 (그래서 예제가 "된다"고 말한다)
  N=1,000   [전부 넣기]  ⚠️ 들어가지만 비싸고, 중간이 흐려지기 시작
  N=120,000 [전부 넣기]  ❌ 컨텍스트 초과 · 질의당 수십 달러 · 세기 신뢰 불가
```

## 4. 왜 "조각을 더 넣기"로는 절대 못 넘는가

문제를 한 층 더 내려가 보면, 이건 튜닝 파라미터의 문제가 아니라 **연산 종류의 불일치**다.

| | 조각 검색이 하는 일 | 전역 질문이 요구하는 일 |
|---|---|---|
| 연산 | **랭킹** — 질문과 가장 닮은 조각 k개 고르기 | **집계** — 전체를 훑어 세기 |
| 필요한 것 | 상위 몇 건 | 빠짐없는 전수 |
| k의 역할 | 크게 할수록 재현율↑ | k<N이면 원리적으로 틀림, k=N이면 검색이 사라짐 |

`k`는 "얼마나 많이 볼까"를 조절하는 손잡이지, "어떻게 셀까"를 바꾸는 손잡이가 아니다.
그래서 **k를 어떻게 돌려도 이 벽은 안 넘어간다.** 6장 요약이 그대로 말한다.

> 「전부 몇 건인가」 같은 전역 질문에는 벽이 있고, 그 벽은 조각을 더 넣어도 안 넘어집니다.

## 5. 대안: 세는 시점을 옮긴다 (색인 시점 접기)

풀이는 k를 키우는 게 아니라 **언제 세느냐를 바꾸는 것**이다. 이것이 `ex2_graphrag_lite.py`의 주제다.

| | 조각 검색 (`ex1`) | GraphRAG 방식 (`ex2`) |
|---|---|---|
| 전체를 훑는 시점 | 없음 (질의 시점에 k개만 봄) | **색인 시점** — 한 번만, 전부 |
| 질의 시점에 하는 일 | 코퍼스에서 k개 고르기 | 접어 둔 요약을 **펴기만** 하기 |
| 비용이 N에 비례하는 지점 | 질의마다 | 색인 때 한 번 |
| 전역 질문 | ❌ | ✅ |

`ex2`의 흐름:

1. **색인 시점** — 트리플로 그래프를 만들고, 라벨 전파(label propagation)로 커뮤니티를 찾고, 커뮤니티마다 원인 분포를 세어 **요약을 접어 둔다**.
2. **질의 시점** — 커뮤니티 요약들만 합쳐 원인 순위를 낸다. 문서 본문은 다시 읽지 않는다.

```python
total = Counter()
for s in summaries:
    total.update(s["원인분포"])       # 접어 둔 것을 펴서 합치기만 한다
found = {c for c, n in total.most_common(2)}
```

문서가 12만 건이어도 질의 시점에 읽는 것은 **커뮤니티 요약 수십~수백 개**다.
N에 비례하던 질의 비용이 커뮤니티 수에 비례하도록 바뀐 것 — 이것이 "접기"의 실체다.

**대가도 분명하다.** 색인이 비싸고, 문서가 바뀌면 다시 접어야 한다.
그래서 자주 바뀌는 데이터에는 안 맞는다(17장에서 이 손익을 따진다).
또 정직하게 말하면, 사실 조회에서는 그래프를 붙인 쪽이 살짝 진다 —
전역 질문 비율이 5%도 안 되면 안 붙이는 게 맞다.

---

## 6. 한 줄로 눌러 담기

> **k=12는 답이 아니라 진단이다.** 문서가 12건일 때만 통하는 해법이라는 사실 자체가,
> 이 한계가 파라미터의 문제가 아니라 **구조의 문제**임을 증명한다.
> 규모에서 살아남으려면 세는 시점을 질의 시점에서 색인 시점으로 옮겨야 한다.
