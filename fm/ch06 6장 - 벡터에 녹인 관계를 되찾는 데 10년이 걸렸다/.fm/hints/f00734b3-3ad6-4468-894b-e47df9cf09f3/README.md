# 전역 질문의 벽은 왜 「조각을 더 넣기」로 안 넘어지나

**질문** — 전역 질문의 벽을 '조각을 더 넣기'로 넘을 수 없는 이유는 무엇인가?

**답** — 전체를 세어야 나오는 답이기 때문이다. 문서 수가 커지면 컨텍스트에 전부 넣는 방법이 성립하지 않아, 색인 시점에 미리 접어 둬야 한다.

---

## 1. 유사도 검색은 '고르기'이지 '세기'가 아니다

조각 검색(RAG)의 검색 단계가 하는 일을 한 줄로 쓰면 이렇다.

```
score(q, d) 를 모든 조각에 대해 계산 → 정렬 → 상위 k개를 반환
```

`ex1_rag_limits.py` 의 `search()` 가 정확히 이 모양이다. 질의 벡터와 문서 벡터의 코사인 유사도를 재고, `scored.sort(reverse=True)` 로 정렬한 뒤 `scored[:k]` 를 잘라 낸다.

여기서 중요한 건 **마지막 슬라이싱**이다. 검색기는 내부적으로 전체를 훑을 수는 있어도(실제 벡터 DB는 ANN 색인 때문에 전체를 훑지도 않는다), 밖으로 내보내는 것은 언제나 상위 k개다. 즉 검색기의 출력 타입은

- 「이 질문과 제일 닮은 조각 k개」

이지, 결코

- 「이 조건을 만족하는 조각이 전부 몇 개인지」

가 아니다. **고르기(selection)와 세기(aggregation)는 다른 연산이다.** 유사도 순위는 순서 정보만 담고 있고, 개수·비율·전체 분포 정보는 순위를 매기는 순간 버려진다.

## 2. 전역 질문은 전수 스캔을 요구한다

6장이 쓰는 예시 질문은 이것이다.

> `GLOBAL_QUESTION = "우리 장애 회고 전체에서 반복되는 원인은 무엇인가?"`
> `GROUND_TRUTH = {"멱등성 없음", "재시도"}`

「반복되는」이라는 말 안에 이미 **집계(aggregation)** 가 들어 있다. 어떤 원인이 반복된다고 말하려면 그 원인이 몇 번 나왔는지 세야 하고, 몇 번 나왔는지를 알려면 안 나온 문서까지 포함해 전부를 봐야 한다. 이런 질문들이 한 부류를 이룬다.

| 유형 | 예시 | 필요한 것 |
|---|---|---|
| count | 「멱등성 문제로 인한 장애가 몇 건인가」 | 전수 스캔 |
| argmax / top-N | 「가장 흔한 원인은 무엇인가」 | 전수 스캔 후 비교 |
| 분포 | 「원인별 비중이 어떻게 되나」 | 전수 스캔 후 정규화 |
| 부재 증명 | 「이 문제를 한 번도 안 겪은 팀이 있나」 | 전수 스캔 |
| 요약·주제 | 「이 문서 묶음의 큰 주제 세 가지」 | 전수 스캔 후 군집화 |

공통점은 **정답이 어느 한 조각 안에 적혀 있지 않다**는 것이다. `corpus.py` 의 12건 어디를 펼쳐도 "멱등성 없음이 4건으로 제일 많다"라고 쓰인 문장은 없다. d01, d02, d06, d09를 **동시에** 보고 세어야 비로소 생기는 사실이다. 조각 검색이 잘 도는 질문(「d03에서 무슨 일이 있었나」)은 답이 한 조각 안에 통째로 들어 있는 국소(local) 질문이고, 전역(global) 질문은 정의상 그렇지 않다.

이것을 부재 증명 쪽에서 보면 더 선명하다. top-k가 돌려준 4건에 없는 것이 나머지 8건에 없다는 보장은 어디에도 없다. 검색기는 「이게 가장 닮았다」고만 말했지 「나머지에는 없다」고 말한 적이 없다. **top-k는 존재 증거는 되지만 부재 증거는 못 된다.**

## 3. 그래서 k를 키우면 되지 않나 — 안 되는 이유

`ex1_rag_limits.py` 의 마지막 출력이 이 반론을 미리 받아 친다.

```
k 를 12로 올려 전부 넣으면? 이 예제에서는 된다. 문서가 12건이니까.
문서가 12만 건이면 못 넣는다. 그게 이 한계의 실체다.
«조각을 더 넣기»로는 못 넘는 벽이고, 그래서 색인 시점에 미리 접어 둬야 한다.
```

「k를 늘린다」는 처방이 성립하려면 **k = N(전체 문서 수)** 이 되어야 한다. 전역 질문은 전수를 요구하니까 그보다 작은 k로는 원리적으로 정답을 보장할 수 없다. 그런데 k = N을 컨텍스트에 밀어 넣는 것은:

- **비용이 N에 선형으로 증가한다.** 12건이면 되고 12만 건이면 안 된다. 즉 이건 「조금 더 큰 모델」이나 「조금 더 긴 컨텍스트」로 해결되는 상수 배 문제가 아니라 스케일링 문제다. 컨텍스트 창이 10배 늘어도 문서가 100배면 다시 진다.
- **k를 키울수록 검색이 무의미해진다.** 전부 넣을 거면 애초에 검색기가 왜 필요한가. 이 처방은 RAG를 포기하는 것과 같다.
- **넣어도 잘 못 센다.** 긴 컨텍스트 안에서 모델은 중간 부분을 흘리고(lost in the middle), 수천 건을 정확히 카운트하는 것은 언어 모델이 원래 약한 작업이다. 정확한 집계는 확률적 생성이 아니라 결정적 계산이 할 일이다.

정리하면, **「조각을 더 넣기」는 국소 질문에서 재현율이 모자랄 때 듣는 처방**이다. 답이 어딘가 한 조각에 있는데 그 조각을 못 집어 온 상황이라면 k를 늘리면 잡힌다. 하지만 전역 질문은 재현율 문제가 아니라 **연산 종류가 다른 문제**다. 고르기 연산을 아무리 크게 키워도 세기 연산이 되지는 않는다. 양을 늘려 질을 바꾸려는 시도라서 벽이 안 넘어진다.

## 4. 유일한 구조적 해법 — 계산을 질의 시점에서 색인 시점으로 옮긴다

질의 시점에 전수 스캔을 못 한다면, **전수 스캔을 미리 해 두면 된다.** 6장의 표현으로는 「세는 시점을 옮긴다」, 「미리 접어 둔다」이다.

`ex2_graphrag_lite.py` 가 이 이동을 그대로 보여 준다.

```
=== 색인 시점 (한 번만) ===
트리플로 그래프를 만든다 → 라벨 전파로 커뮤니티를 찾는다 → 커뮤니티마다 요약을 접어 둔다
     (여기서 전체를 훑는다. 딱 한 번, 오프라인에서.)

=== 질의 시점 ===
접어 둔 커뮤니티 요약만 편다 → 합친다 → 답
     (전체를 안 봐도 된다. 전체를 본 결과가 이미 요약에 들어 있으니까.)
```

`summarize()` 가 만드는 `원인분포` Counter가 바로 「접어 둔 카운트」다. 질의 시점에는 커뮤니티 개수만큼의 요약만 합치면 되므로, 훑어야 하는 양이 N(문서 수)에서 C(커뮤니티 수)로 줄어든다. 문서가 12만 건이어도 커뮤니티 요약은 수백 개 수준으로 유지할 수 있고, 이건 컨텍스트에 들어간다. 이것이 Microsoft GraphRAG의 커뮤니티 요약(community summary) 계층이 하는 일이며, 6장 요약의 다음 문장이 가리키는 바다.

> 풀이는 세는 시점을 옮기는 것입니다. 색인 시점에 그래프를 만들고 뭉치마다 요약을 접어 두면, 질의 시점에는 펴기만 하면 됩니다.

## 5. 데이터베이스의 사전 집계와 같은 구조

이 해법은 새로운 발명이 아니라 데이터베이스가 수십 년 전에 정착시킨 패턴의 재발견이다.

| 데이터베이스 | GraphRAG 계열 |
|---|---|
| `SELECT category, COUNT(*) ... GROUP BY` 를 매번 돌리면 느리다 | 전역 질문마다 전 문서를 컨텍스트에 넣을 수 없다 |
| **구체화 뷰(materialized view)** 에 집계 결과를 미리 저장 | **커뮤니티 요약**에 집계·주제를 미리 접어 둠 |
| OLAP 큐브의 사전 집계, 롤업 테이블 | 계층적 요약(커뮤니티 → 상위 커뮤니티 요약) |
| 조회는 O(1)에 가깝게, 대신 갱신 시 뷰 재계산 필요 | 질의는 싸게, 대신 문서가 바뀌면 다시 접어야 함 |
| 뷰가 오래되면 stale — 갱신 정책이 설계의 핵심 | 색인이 비싸고 자주 바뀌는 데이터에 안 맞음 |

같은 트레이드오프가 같은 자리에 나타난다. **읽기 시점 계산(compute-on-read)을 쓰기 시점 계산(compute-on-write)으로 옮기면, 조회는 싸지고 갱신은 비싸진다.** 인덱스, 구체화 뷰, 캐시, 이벤트 소싱의 스냅숏이 전부 이 형태다. GraphRAG는 「문서 묶음에 대한 구체화 뷰」를 만드는 일이라고 봐도 크게 틀리지 않는다.

`ex2` 의 마무리가 그 대가를 정직하게 적어 둔다.

```
대가도 분명하다. 색인이 비싸고, 문서가 바뀌면 다시 접어야 한다.
그래서 자주 바뀌는 데이터에는 안 맞는다.
```

## 6. 그래서 언제 이 값을 치를 것인가

6장은 여기서 한 걸음 더 물러선다.

> 정직하게 말하면, 사실 조회에서는 그래프를 붙인 쪽이 살짝 집니다. 전역 질문 비율이 5%도 안 되면 안 붙이는 게 맞습니다.

전역 질문의 벽은 실재하지만, 그 벽을 넘는 비용(색인 파이프라인, 엔티티·관계 추출, 커뮤니티 탐지, 요약 생성, 재색인)도 실재한다. **워크로드에 전역 질문이 얼마나 섞여 있는가**가 판단 기준이다. 대부분이 국소 사실 조회라면 평범한 조각 검색이 더 빠르고 싸고 정확하다.

---

## 한 문장으로 다시

top-k 검색은 닮은 것을 **고르는** 연산이고, 전역 질문은 전부를 **세는** 연산이라서, k를 아무리 키워도(그리고 N이 커지면 애초에 키울 수도 없어서) 종류가 다른 연산으로 바뀌지 않는다. 그래서 세는 일을 질의 시점에서 색인 시점으로 옮겨 미리 접어 두는 것 — 데이터베이스의 구체화 뷰와 같은 수 — 이 유일한 구조적 해법이다.

## 헷갈리기 쉬운 지점

- **「컨텍스트가 길어지면 해결된다」** — 아니다. 상수 배 여유가 늘 뿐 N에 대한 선형 증가는 그대로다. 게다가 긴 컨텍스트 안에서 정확히 세는 것 자체가 별개의 실패 지점이다.
- **「그래프가 있어서 이기는 것이다」** — 정확히는 **색인 시점의 전수 집계**가 이기는 것이다. 그래프와 커뮤니티 탐지는 「무슨 단위로 접을지」를 정하는 좋은 방법이지 승리의 원인 자체는 아니다. 6장이 `ex2` 를 두고 "보여 주려는 건 요약 품질이 아니라 **언제 접느냐**"라고 못 박은 이유다.
- **「그럼 항상 GraphRAG를 쓰면 된다」** — 아니다. 색인 비용과 갱신 난이도가 대가이고, 국소 사실 조회에서는 오히려 진다.
