# `summarize()` 함수는 무엇을 계산하는가?

**답**: 커뮤니티 안에서 주어와 목적어가 **모두 구성원**인 '원인' 트리플을 세어 상위 3개를 문장으로 만들고, 원인 분포 `Counter`도 함께 반환한다.

출처: `content/ch06/code/ex2_graphrag_lite.py` (6장 예제 2, GraphRAG lite)

---

## 0. 이 함수가 서 있는 자리

6장의 논지는 한 문장입니다. **"달라진 건 «언제 세느냐»이다."**

- `ex1_rag_limits.py` — 질의 시점에 top-k 조각만 본다 → 「전부 몇 건인가」를 못 센다.
- `ex2_graphrag_lite.py` — **색인 시점**에 전부 훑어 접어 둔다 → 질의 시점에는 펴기만 한다.

`summarize()`는 그 **"접는" 동작 그 자체**입니다. 커뮤니티 하나를 받아, 나중에 펴서 쓸 수 있는 형태로 눌러 놓습니다. 그래서 이 함수의 설계 하나하나가 "무엇을 접고 무엇을 버리는가"의 결정입니다.

---

## 1. 코드 전문

```python
def summarize(community, triples):
    """커뮤니티 요약. 규칙 기반이라 매번 같은 결과가 나온다."""
    members = set(community)
    causes = Counter(o for s, p, o in triples
                     if p == "원인" and s in members and o in members)
    docs = sorted(m for m in members if m.startswith("d"))
    top = ", ".join(f"{c}({n}건)" for c, n in causes.most_common(3))
    return {"문서": docs, "요약": f"문서 {len(docs)}건. 자주 나온 원인: {top or '없음'}",
            "원인분포": causes}
```

다섯 줄이 전부입니다. 한 줄씩 따라갑니다.

### 1-1. `members = set(community)`

`community`는 `label_propagation()`이 돌려준 **노드 이름의 정렬된 리스트**입니다. 여기에 문서 노드(`d01`)와 개념 노드(`재시도`, `결제`)가 **섞여 있습니다.**

```
['d01', 'd02', 'd06', 'd09', '결제', '멱등성 없음', '알림', '재처리', '주문', '중복 요청', '프로모션']
```

`build_graph()`가 트리플을 무방향 그래프로 폈기 때문입니다.

```python
def build_graph(triples):
    adj = defaultdict(set)
    for s, p, o in triples:
        adj[s].add(o)     # d01 → 재시도
        adj[o].add(s)     # 재시도 → d01
    return adj
```

문서와 개념이 같은 노드 공간에 들어가 있고, 술어(`p`)는 그래프에서 아예 사라졌습니다. 이 손실을 나중에 `summarize()`가 원본 `triples`를 다시 받아서 메웁니다. **그래서 시그니처가 `summarize(community, triples)`인 것입니다** — 커뮤니티만으로는 "무엇이 원인이었는지"를 복원할 수 없습니다.

`list` → `set` 변환은 순전히 속도입니다. 아래 조건절이 트리플마다 두 번씩 멤버십 검사를 하므로 O(n) 대신 O(1)이어야 합니다.

### 1-2. `causes = Counter(...)` — 이 함수의 심장

```python
causes = Counter(o for s, p, o in triples
                 if p == "원인" and s in members and o in members)
```

세 개의 필터가 AND로 걸립니다.

| 조건 | 의미 |
|---|---|
| `p == "원인"` | 술어가 `원인`인 트리플만. `("d01", "영역", "결제")`는 버린다 |
| `s in members` | 주어(문서)가 이 커뮤니티 소속 |
| `o in members` | 목적어(원인)도 이 커뮤니티 소속 |

세고 있는 것은 `o` — **원인 이름**입니다. 결과는 `{"멱등성 없음": 4, "중복 요청": 2, "재처리": 1}` 같은 분포입니다.

뒤의 두 조건이 곧 **유도 부분그래프(induced subgraph)** 조건입니다. 아래 2절에서 따로 다룹니다.

### 1-3. `docs = sorted(...)`

```python
docs = sorted(m for m in members if m.startswith("d"))
```

섞여 있던 노드에서 문서만 골라냅니다. 판별 기준이 **접두사 `"d"`** 라는 점을 주목하세요. 이 코퍼스에서 문서 ID가 `d01`~`d12`이고 개념 이름이 전부 한글이라 우연히 동작합니다. 실전에서는 노드에 타입 라벨을 붙이거나 `(type, id)` 튜플로 관리해야 합니다. 7장(「노드 하나 잘못 그려서 3주를 날렸다」)이 정확히 이 이야기입니다.

### 1-4. `top = ", ".join(...)` — 사람용 문장

```python
top = ", ".join(f"{c}({n}건)" for c, n in causes.most_common(3))
```

`Counter.most_common(3)`이 빈도 내림차순 상위 3개를 뽑고, `"멱등성 없음(4건), 중복 요청(2건), 재처리(1건)"` 같은 문자열이 만들어집니다.

### 1-5. `return {...}` — 두 갈래의 출력

```python
return {"문서": docs,
        "요약": f"문서 {len(docs)}건. 자주 나온 원인: {top or '없음'}",
        "원인분포": causes}
```

`top or '없음'`은 빈 문자열 방어입니다. 커뮤니티 안에 원인 트리플이 하나도 살아남지 못하면 `top`이 `""`가 되고, `"자주 나온 원인: "`으로 끝나는 어색한 문장 대신 `"자주 나온 원인: 없음"`이 나옵니다. 2절에서 보겠지만 **이 경우는 실제로 발생합니다.**

`"요약"`은 사람이 읽을 문장, `"원인분포"`는 기계가 합칠 `Counter`. 3절에서 다룹니다.

## 2. 왜 `s in members`**와** `o in members`를 둘 다 요구하는가

### 유도 부분그래프란

노드 집합 S가 주어졌을 때, **양 끝점이 모두 S에 속하는 간선만** 남긴 그래프를 S의 유도 부분그래프(induced subgraph)라 합니다. `s in members and o in members`가 정확히 이 정의입니다.

`o in members`를 빼면 어떻게 되는지 생각해 보세요.

```python
# 만약 이랬다면
if p == "원인" and s in members
```

이러면 "이 커뮤니티에 속한 문서들의 **모든** 원인"을 셉니다. 원인 노드가 다른 커뮤니티에 있어도 셉니다.

### 그럼 왜 안 그러는가 — 요약의 자기완결성

접어 둔 요약의 계약(contract)은 **"이 요약은 이 커뮤니티 하나만 설명한다"** 입니다. 이 계약이 깨지면:

- **중복 계수**: 같은 원인 노드가 여러 커뮤니티 요약에 동시에 등장하고, 질의 시점의 `total.update()`가 그걸 다 더해 버립니다. 커뮤니티 요약을 합산하는 전제가 "커뮤니티끼리 겹치지 않는다"인데 그게 무너집니다.
- **경계 누수**: 커뮤니티 A의 요약이 커뮤니티 B에만 있는 개념을 언급합니다. 진짜 GraphRAG에서 이 요약문은 LLM에게 그대로 넘어가는 컨텍스트인데, "이 뭉치는 무엇에 관한 것인가"라는 신호가 흐려집니다.
- **커뮤니티 탐지가 무의미해짐**: 경계를 무시하고 셀 거라면 애초에 커뮤니티로 나눌 이유가 없습니다. 그냥 전체 트리플을 한 번 세면 됩니다.

즉 유도 부분그래프 조건은 **분할(partition)이 진짜 분할이 되게 하는 조건**입니다. 각 요약이 서로 겹치지 않는 조각을 담아야, 질의 시점에 단순 덧셈으로 전역 값을 복원할 수 있습니다.

### 대가 — 실측

대가는 **경계를 가로지르는 간선이 그냥 사라진다**는 것입니다. 어떤 요약에도 안 들어갑니다.

`corpus.py`의 `원인` 트리플은 총 **21개**. 실제로 돌려 보면 커뮤니티별 `원인분포`를 다 더해도 **16~18개**밖에 안 됩니다. 3~5개가 조용히 증발합니다.

한 실행의 예:

```
커뮤니티 1: ['d01','d02','d06','d09','결제','멱등성 없음','알림','재처리','주문','중복 요청','프로모션']
           원인분포 {'멱등성 없음': 4, '중복 요청': 2, '재처리': 1}
커뮤니티 3: ['d04','상태 불일치','재시도','회원']
           원인분포 {'재시도': 1, '상태 불일치': 1}
커뮤니티 4: ['d05','d11','롤백 없음','부분 실패','정산']
           원인분포 {'부분 실패': 2, '롤백 없음': 1}
```

`재시도`는 코퍼스 전체에서 d01, d04, d11 세 문서에 걸려 있어 **전역 카운트가 3**입니다. 그런데:

- `("d01", "원인", "재시도")` — d01은 커뮤니티 1, 재시도는 커뮤니티 3 → **버려짐**
- `("d04", "원인", "재시도")` — 둘 다 커뮤니티 3 → 세어짐
- `("d11", "원인", "재시도")` — d11은 커뮤니티 4, 재시도는 커뮤니티 3 → **버려짐**

합산 결과 `재시도: 1`. 정답이 `{멱등성 없음, 재시도}`인데 재시도가 3분의 1로 깎였습니다. 유도 부분그래프 조건이 **정확성을 위해 재현율을 희생**한 것입니다.

> **실행 시 주의**: `label_propagation()`이 `Counter(label[m] for m in adj[n]).most_common(1)`로 동점을 처리하는데, `adj[n]`이 `set`이라 순회 순서가 파이썬 프로세스마다 다릅니다(문자열 해시 랜덤화). 그래서 커뮤니티 분할이 실행마다 8~10개 사이로 바뀌고, 마지막 `맞았나` 판정도 실행마다 달라집니다. 재현하려면 `PYTHONHASHSEED=0 python3 ex2_graphrag_lite.py`처럼 고정하세요. 예제의 요지("색인 시점에 접으면 전역 질문을 셀 수 있다")는 유지되지만, 위 손실이 실제로 답을 흔들 만큼 크다는 점은 기억해 둘 만합니다.

### 실전에서의 완화책

Microsoft GraphRAG는 이 손실을 **계층적 커뮤니티**(Leiden 알고리즘의 여러 해상도 레벨)로 완화합니다. 낮은 레벨에서 끊긴 간선이 상위 레벨의 더 큰 커뮤니티 안에서는 내부 간선이 되기 때문입니다. 즉 "한 번만 자르는" 대신 "여러 굵기로 잘라서 다 접어 둡니다".

## 3. 왜 문장과 `Counter`를 **둘 다** 반환하는가

두 소비자가 서로 다른 것을 원하기 때문입니다.

### 소비자 A — 사람 (색인 시점 출력)

```python
for i, c in enumerate(communities, 1):
    s = summarize(c, TRIPLES)
    summaries.append(s)
    print(f"  커뮤니티 {i}: {s['요약']}")
```

```
커뮤니티 1: 문서 4건. 자주 나온 원인: 멱등성 없음(4건), 중복 요청(2건), 재처리(1건)
```

`Counter` 객체를 그대로 찍으면 `Counter({'멱등성 없음': 4, ...})`처럼 나옵니다. 사람이 훑기에 나쁘고, **진짜 GraphRAG에서는 이 자리에 LLM이 쓴 자연어 요약이 들어갑니다.** 실전에서 커뮤니티 요약은 질의 시점에 프롬프트로 들어가는 **텍스트**입니다. 그래서 텍스트 필드가 반드시 있어야 합니다.

### 소비자 B — 기계 (질의 시점 합산)

```python
total = Counter()
for s in summaries:
    total.update(s["원인분포"])       # ← 여기
print("커뮤니티 요약을 합친 결과 — 원인 순위")
for cause, n in total.most_common(5):
    print(f"  {cause}: {n}건")

found = {c for c, n in total.most_common(2)}
```

`Counter.update()`는 키별로 **값을 더합니다**(dict의 `update`처럼 덮어쓰는 게 아닙니다). 커뮤니티 A의 `{멱등성 없음: 4}`와 커뮤니티 B의 `{멱등성 없음: 1}`이 `{멱등성 없음: 5}`가 됩니다.

**이게 6장 전체의 핵심 동작입니다.** 전역 질문 「반복되는 원인은 무엇인가」의 답이, 색인 시점에 접어 둔 부분합들의 **덧셈 한 번**으로 나옵니다. 문서 12만 건이어도 커뮤니티가 200개면 200개만 더하면 됩니다. 원문을 다시 안 읽습니다.

### 문장만 반환했다면

`"문서 4건. 자주 나온 원인: 멱등성 없음(4건), 중복 요청(2건)"` 이 문자열들을 합산하려면:

1. 정규식으로 `이름(N건)` 패턴을 다시 파싱하고
2. `int()`로 되돌리고
3. 파싱 실패를 처리해야 합니다

사람이 읽으라고 만든 표현을 기계가 되읽는 것 — **파싱 왕복(round-trip)** 입니다. 포맷 문자열을 조금만 고쳐도 합산이 깨집니다. 진짜 GraphRAG처럼 요약문을 LLM이 쓰면 아예 불가능합니다. 문장 형태가 매번 달라지니까요.

### 그래서 이 함수의 계약

> **같은 정보를 두 표현으로 내보낸다. 사람용은 압축·정렬된 산문, 기계용은 손실 없는 구조체.**

Microsoft GraphRAG의 커뮤니티 리포트가 자연어 `summary`와 함께 `findings`, `rank` 같은 **구조화 필드**를 나란히 저장하는 것도 같은 이유입니다. 이 예제의 두 줄짜리 dict는 그 구조의 축소판입니다.

## 4. 상위 3개로 자르는 것의 손실

```python
top = ", ".join(f"{c}({n}건)" for c, n in causes.most_common(3))
```

### 이 예제에서는 무해하다

**절단은 `"요약"` 문자열에만 적용됩니다.** `"원인분포"`로 나가는 `causes`는 자르지 않은 전체 `Counter`입니다.

```python
return {..., "원인분포": causes}    # most_common(3)이 아니라 causes 통째로
```

그래서 질의 시점의 `total.update(s["원인분포"])`는 4위, 5위 원인도 다 받습니다. **기계 경로는 무손실, 사람 경로만 손실.** 이건 우연이 아니라 3절에서 말한 계약의 결과입니다 — 두 갈래로 내보내는 이유가 바로 "한쪽은 요약해도 되고 한쪽은 안 된다"입니다.

이 코퍼스에서는 애초에 커뮤니티당 서로 다른 원인이 3종을 잘 안 넘어서, 실행에 따라 절단이 한 번도 발동하지 않기도 합니다.

### 그런데 실전에서는 유해하다

진짜 GraphRAG에서 **질의 시점에 LLM에게 넘어가는 것은 요약문**입니다. `Counter`가 아닙니다. 그 순간 `most_common(3)`은 이렇게 바뀝니다:

- 4위 이하 원인은 **컨텍스트에 존재하지 않게 됩니다.** LLM은 그것들이 있었다는 사실조차 모릅니다. "없다"와 "안 보여줬다"를 구분할 수 없습니다.
- **긴 꼬리(long tail)가 통째로 사라집니다.** 「전부 몇 건인가」류 질문 중 상당수는 꼬리에 답이 있습니다. 「우리가 한 번도 안 다룬 원인은?」, 「드물지만 치명적인 원인은?」 — 상위 3개만으로는 답할 수 없습니다.
- **동점 처리가 임의적입니다.** 3위와 4위가 둘 다 2건이면 `Counter.most_common()`은 삽입 순서로 자릅니다. 어느 쪽이 잘릴지는 트리플 순서에 달렸습니다. 은근히 재현성이 없습니다.
- **합계를 알 수 없습니다.** `"멱등성 없음(4건), 중복 요청(2건), 재처리(1건)"`을 읽는 사람은 이게 전부인지 일부인지 모릅니다. `"… 외 5종"`이나 `"총 12건 중 상위 3종"` 같은 꼬리표가 없습니다.

### 왜 그래도 자르는가

**컨텍스트 예산** 때문입니다. 커뮤니티가 수백 개일 때 각 요약을 전부 펴서 프롬프트에 넣으면 토큰이 터집니다. 상위 k개로 자르는 것은 「접어 두기」의 본질 — **정보를 버려서 크기를 줄이는 것** — 그 자체입니다. 압축이 무손실이면 접은 게 아닙니다.

6장이 말하는 거래가 여기서도 반복됩니다.

| 얻는 것 | 잃는 것 |
|---|---|
| 질의 시점 비용이 커뮤니티 수에 비례 (문서 수가 아니라) | 색인 시점 비용이 비싸고, 문서가 바뀌면 다시 접어야 함 |
| 전역 질문에 답할 수 있음 | 경계 간선 소실(2절) + 꼬리 절단(4절) |

### 개선한다면

- 요약문에 `f"{top} (총 {sum(causes.values())}건, {len(causes)}종)"`처럼 **절단 사실을 명시**한다. LLM이 "이건 일부다"를 알 수 있게.
- 고정 3개 대신 **누적 비율 기반**(상위 80%를 덮는 만큼)으로 자른다.
- 절단 개수를 **커뮤니티 크기에 비례**시킨다. 문서 40건짜리 커뮤니티와 1건짜리를 같은 3개로 자를 이유가 없다.

## 5. 한눈에 다시 보기

```
TRIPLES (문서, 술어, 개념) 33개 = 원인 21 + 영역 12
        │
        ├─ build_graph()        무방향 그래프로 폄. 술어 p가 사라짐
        ├─ label_propagation()  이웃 최빈 라벨 전파 → 커뮤니티 8~10개
        │
        └─ summarize(community, TRIPLES)          ← 색인 시점, 커뮤니티마다 1회
             ① members = set(community)          문서·개념 섞인 노드 집합
             ② causes  = Counter(o | p=="원인" and s∈members and o∈members)
                                                 ↑ 유도 부분그래프. 경계 간선 소실
             ③ docs    = 접두사 "d"인 멤버
             ④ top     = causes.most_common(3)   ← 절단은 여기서만
             ⑤ return {"문서", "요약"(사람), "원인분포"(기계, 무손실)}
                                                    │
                                       질의 시점 ──┘
                                       total = Counter()
                                       for s in summaries:
                                           total.update(s["원인분포"])   ← 덧셈 한 번
                                       total.most_common(2) → 답
```

## 6. 스스로 확인해 보기

1. `o in members` 조건을 지우고 돌리면 합산 총합이 21에 가까워집니다. 그런데 왜 그게 "더 정확한" 답이 아닌가요? (힌트: 같은 원인 노드가 몇 개의 커뮤니티 요약에 나타나게 되는지 세어 보세요.)
2. `"원인분포"`를 반환하지 않고 `"요약"` 문자열만 준다면, `main()`의 질의 시점 코드를 어떻게 고쳐야 하나요? 그 코드는 무엇에 취약해지나요?
3. `most_common(3)`을 `most_common(1)`로 바꾸면 콘솔 출력은 달라지지만 최종 답은 달라지지 않습니다. 왜인가요?
4. `docs` 판별을 `m.startswith("d")`로 하고 있습니다. 문서 ID가 `doc-01`이 아니라 `01`이거나, 개념 이름에 `dead-letter queue`가 있으면 무슨 일이 벌어지나요?
5. 커뮤니티가 200개, 각 요약이 200토큰이라면 질의 시점 프롬프트는 4만 토큰입니다. 커뮤니티가 2만 개라면? GraphRAG가 계층적 커뮤니티를 쓰는 이유를 이 숫자로 설명해 보세요.
