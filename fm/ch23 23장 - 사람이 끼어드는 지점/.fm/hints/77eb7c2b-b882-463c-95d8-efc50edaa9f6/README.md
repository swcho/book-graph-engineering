# interrupt 앞에 둬도 괜찮은 코드

**질문:** interrupt 앞에 둬도 괜찮은 코드는 무엇인가?

**답:** **읽기만 하는 코드**다. **밖으로 나가는 것은 전부 뒤로** 밀어야 한다.

---

## 한 줄로

`interrupt()`가 있는 노드는 재개할 때 **노드의 처음부터 다시 실행**됩니다. 그래서 `interrupt()` 앞에 있는 코드는 **최소 두 번** 돕니다. 두 번 돌아도 세상이 그대로인 코드(= 읽기)만 앞에 둘 수 있고, 두 번 돌면 세상이 두 번 바뀌는 코드(= 부작용)는 전부 뒤로 밀어야 합니다.

## 왜 그런가 — 체크포인트는 노드 «경계»에 찍힌다

21장에서 본 규칙이 그대로 되돌아옵니다.

- 체크포인터는 **슈퍼스텝 경계**, 즉 노드가 **끝난 지점**에 상태를 저장합니다.
- `interrupt()`는 노드 **중간**에서 멈춥니다. 그런데 그 중간 지점은 저장 단위가 아닙니다.
- 그래서 `Command(resume=...)`로 재개하면 「멈춘 줄 다음」이 아니라 **그 노드의 첫 줄**로 돌아갑니다. 이번에는 `interrupt()`가 멈추지 않고 사람이 준 값을 즉시 반환하며, 그 뒤 코드가 이어서 돕니다.

즉 노드 본문은 이렇게 실행됩니다.

```
1회차:  [interrupt 앞 코드] → interrupt() 에서 멈춤 (뒤 코드는 실행 안 됨)
2회차:  [interrupt 앞 코드] → interrupt() 가 답 반환 → [interrupt 뒤 코드]
        ^^^^^^^^^^^^^^^^^^ 두 번째 실행
```

`interrupt` 앞은 2번, 뒤는 1번. 사람이 두 번 답을 고쳐 재개하면 앞쪽은 3번이 됩니다.

## 코드로 보기 (`ex2_node_reruns.py`)

```python
def 나쁜노드(s: S) -> S:
    호출수["메일"] += 1
    print(f"    → 담당자에게 «검토 요청» 메일 발송 (누적 {호출수['메일']}회)")
    답 = interrupt("승인하시겠습니까?")
    return {"승인": 답}


def 좋은노드(s: S) -> S:
    답 = interrupt("승인하시겠습니까?")      # 부작용 «앞»에 둔다
    호출수["조회"] += 1
    print(f"    → 결과 기록 (누적 {호출수['조회']}회)")
    return {"승인": 답}
```

실행하면 메일은 2회, 결과 기록은 1회입니다. **담당자가 검토 요청 메일을 두 번 받습니다. 그것도 승인을 «하고 나서» 한 번 더.** 메일이라 웃고 넘어가지만, 같은 자리에 결제·환불·배포·삭제가 있으면 22장이 다룬 「되돌릴 수 없는 일」이 두 번 나갑니다.

이 장의 결론 문장이 그래서 이렇습니다.

> 규칙은 하나다. «interrupt 앞에는 부작용을 두지 않는다.»
> 읽기만 하는 코드는 괜찮다. 밖으로 나가는 것은 전부 뒤로 민다.

## 「읽기만 하는 코드」의 정확한 뜻

「읽기」의 기준은 함수 이름이 `get_*`이냐가 아니라 **이 노드가 두 번 돌았다는 사실을 바깥에서 알아챌 수 있느냐**입니다. 알아챌 수 없으면 읽기, 알아챌 수 있으면 부작용입니다.

**앞에 둬도 되는 것 (전형적인 읽기)**

- 상태(state)에서 값 꺼내기, 파생 값 계산, 포매팅
- DB `SELECT`, 설정 파일 읽기, 사람에게 보여 줄 요약 만들기
- 순수 함수 호출, 검증·분기 판단

**반드시 뒤로 밀어야 하는 것 (밖으로 나가는 것)**

- 메일·슬랙·SMS·푸시 발송
- 결제·환불·송금·주문 확정
- 파일/객체 스토리지 쓰기, DB `INSERT`/`UPDATE`/`DELETE`
- 외부 API의 쓰기 호출, 메시지 큐 발행, 배포·롤백 트리거
- 프로세스 안이라도 **누적되는 전역 변수 갱신** (위 예제의 `호출수` 딕셔너리가 정확히 이 경우입니다. 네트워크로 나가지 않아도 중복 실행이 관측됩니다.)

## 경계가 애매한 사례들

실무에서 헷갈리는 것들입니다. 「읽기 같은데 사실 부작용」이 대부분입니다.

| 사례 | 판정 | 이유와 대처 |
|---|---|---|
| **로그 기록** | 대체로 허용 | 중복 로그는 정확성을 깨지 않습니다. 다만 「승인 요청 발송함」처럼 **감사 근거로 쓰이는 로그**는 중복되면 감사 기록이 거짓말을 합니다. 사실 기록용 로그는 뒤로 밀거나, 재실행 여부를 로그에 표시하세요. |
| **메트릭 카운터 증가** | 주의 | 대시보드의 「승인 요청 수」가 부풀려집니다. 게이지는 괜찮지만 카운터는 뒤로. |
| **캐시 쓰기(read-through)** | 대체로 허용 | 같은 키에 같은 값을 다시 쓰는 것이라 멱등입니다. 다만 **캐시가 다른 시스템의 입력**이거나 TTL 갱신이 비즈니스 의미(예: 잠금, 쿨다운)를 가지면 부작용입니다. |
| **조회 API의 rate limit** | 주의 | 정확성은 안 깨지지만 **호출 예산이 두 배**로 나갑니다. 사람이 여러 번 재개하면 그 배수만큼. 결과를 상태나 캐시에 담아 두고 재실행 시에는 그걸 쓰세요. |
| **호출당 과금되는 조회 API** (LLM 추론, 지도·신용 조회 등) | 주의 | 「읽기」인데 **돈이 나갑니다**. 무거운 조회는 별도 노드로 앞에 빼서 결과를 상태에 저장하고, interrupt 노드는 그 상태만 읽게 하세요. |
| **멱등성 키 발급** | 발급 시점에 따라 다름 | 노드 안에서 `uuid4()`로 새로 만들면 **재실행마다 다른 키**가 되어 멱등성 보호가 무력화됩니다. 키는 상태에 이미 있는 값(주문 ID + 노드명 + 시도 횟수)에서 **결정적으로 유도**하거나, interrupt 이전 노드에서 만들어 상태에 넣어 두세요. |
| **`datetime.now()` / `random`** | 주의 | 재실행 때 값이 달라져 「보여 준 내용」과 「실행할 내용」이 어긋납니다. 23.5절의 `state_hash`가 흔들리는 원인이 됩니다. 시각·난수는 앞 노드에서 뽑아 상태에 고정하세요. |
| **임시 파일 생성** | 조건부 허용 | 같은 경로에 덮어쓰면 대체로 무해합니다. 타임스탬프로 파일명을 만들면 재실행마다 쓰레기가 쌓입니다. |
| **분산 락 획득** | 부작용 | 사람을 기다리는 동안 락을 잡고 있으면 안 됩니다. 재실행 시 자기 자신과 데드락이 날 수도 있습니다. |

한 줄 판정 기준:
**「이 코드를 두 번 실행했을 때, 두 번 실행했다는 걸 누군가(사람·다른 시스템·청구서·감사 기록)가 알 수 있는가?」** 알 수 있으면 뒤로 미세요.

## 부작용이 꼭 앞에 있어야 한다면 — 노드를 쪼갠다

「사람에게 물어보기 전에 반드시 알림을 보내야 한다」처럼 부작용이 앞에 와야 하는 경우가 있습니다. 그때는 **노드를 둘로 쪼갭니다.**

```
[부작용 노드]  →  [interrupt 노드]
   알림 발송        interrupt() 로 멈춤
```

이러면 두 노드 **사이에 체크포인트 경계가 생깁니다.** 재개는 「interrupt 노드」의 처음으로만 돌아가고, 이미 끝난 「부작용 노드」는 다시 돌지 않습니다. 규칙을 뒤집으면 이렇게 정리됩니다.

> **하나의 노드 = 하나의 부작용 구간.** interrupt는 그 구간의 시작이거나 끝이지, 한가운데가 아니다.

보조 수단으로는:

- **멱등성 키**: 어차피 재실행이 일어난다면, 발송·결제 쪽이 키로 중복을 흡수하게 합니다. 단 키는 위 표대로 결정적으로 만드세요.
- **상태 가드**: `if not s.get("알림_보냄")` 같은 플래그. 다만 플래그를 쓰는 시점도 노드가 끝나야 저장되므로, 같은 노드 안에서 플래그를 세우고 그걸로 자기 자신을 막는 건 동작하지 않습니다. 반드시 **앞 노드에서 저장된** 플래그여야 합니다.

## 한 노드에 interrupt가 여러 개면

여러 개도 가능하지만, 재개 값은 **노드 안에서 등장한 순서(인덱스)로** 매칭됩니다. 그래서 앞쪽 코드가 조건 분기를 바꿔 `interrupt` 호출 순서나 개수가 달라지면, 사람이 준 답이 **엉뚱한 질문에 붙습니다.** 이것도 「앞에 둔 코드는 두 번 돈다」의 파생 문제입니다. 앞쪽을 순수 읽기로 유지하고 분기 근거를 상태에 고정해 두면 순서가 흔들리지 않습니다.

## 「읽기는 괜찮다」의 «괜찮다»는 어디까지인가

정확히는 **정확성이 깨지지 않는다**는 뜻이지, **공짜**라는 뜻이 아닙니다.

1. **비용**: 무거운 조회·LLM 호출은 재개 횟수만큼 다시 나갑니다.
2. **불일치**: 1회차에 읽은 값과 2회차에 읽은 값이 다를 수 있습니다. 사람은 1회차 화면을 보고 승인했는데, 실제 실행은 2회차 값으로 갑니다. → 23.5절이 `state_hash`(상태 지문)를 남기고 **지문이 다르면 다시 물으라**고 하는 이유가 이겁니다. 「사흘 전 승인으로 오늘 4,200,000원을 내보내면 안 된다.」

그래서 실무 권장 형태는 이렇습니다.

```
[수집 노드]        조회·계산을 여기서 다 하고 상태에 저장 (지문도 여기서)
     ↓
[interrupt 노드]   상태만 읽어 사람에게 보여 주고 멈춤
     ↓
[실행 노드]        승인 결과로 밖에 나가는 일을 수행
```

## 체크리스트

interrupt가 있는 노드를 리뷰할 때, `interrupt()` 위쪽 줄들만 보고 물어보세요.

- [ ] 네트워크로 **쓰기** 요청이 나가는가?
- [ ] DB에 `INSERT`/`UPDATE`/`DELETE`가 있는가?
- [ ] 파일·큐·스토리지에 무언가를 남기는가?
- [ ] 전역/모듈 변수, 카운터, 락을 건드리는가?
- [ ] 돈이 나가거나 rate limit를 소모하는 조회가 있는가?
- [ ] `now()`, `uuid4()`, `random` 처럼 **매번 값이 달라지는** 호출이 있는가?

하나라도 예면, 그 줄은 `interrupt` 뒤로 내리거나 **앞 노드로 잘라내야** 합니다.

## 자주 하는 오해

- **「interrupt는 예외니까 롤백되겠지」** — 아닙니다. 이미 나간 부작용은 되돌아오지 않습니다. `interrupt`는 정상적인 중단이고, 노드는 **재실행**될 뿐 트랜잭션처럼 취소되지 않습니다.
- **「멈춘 다음 줄부터 이어지겠지」** — 아닙니다. 노드의 **처음**부터입니다. 이게 이 카드의 전부입니다.
- **「메모리 체크포인터라 그런 것 아닌가」** — 아닙니다. 저장소 종류와 무관하게 저장 단위가 노드 경계라서 생기는 일입니다. 오히려 디스크 체크포인터를 쓰면 사흘 뒤 재개가 가능해져 「두 번째 실행」이 훨씬 나중에, 더 달라진 세상에서 일어납니다.
