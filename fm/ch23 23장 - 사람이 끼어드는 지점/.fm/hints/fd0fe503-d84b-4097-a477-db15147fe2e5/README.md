# 문턱을 금액만으로 잡으면 — 한계와 장점

> **Q.** 문턱을 금액만으로 잡는 것의 한계와 장점은 무엇인가?
>
> **A.** 신규 고객·반복 환불·이상 패턴 신호를 섞으면 같은 용량으로 더 잡을 수 있다. 다만 금액은 계산·설명·감사가 되므로 시작으로 좋다.

출처: 23장 「사람이 끼어드는 지점」 23.3 *어디에 문을 달 것인가* / `code/ex3_gate_policy.py`

---

## 1. 먼저 깔아 둘 전제 — 문턱은 취향이 아니라 용량이다

이 카드는 23.3의 결론 **뒤에 붙는 각주**입니다. 23.3의 본 결론은 이거예요.

> 검토 시간이 용량의 70%를 넘지 않는 문턱 중 **제일 낮은 것**을 고른다. 30%는 휴가·회의·급한 건을 위해 비워 둔다.

`ex3_gate_policy.py`를 실제로 돌리면 이런 표가 나옵니다 (seed 7, 1200건, 합계 73,893,625원, 검토 3분 × 2명 × 8시간 = 하루 320건 처리 가능).

| 문턱 | 사람이 볼 건수 | 검토 시간(분) | 용량 대비 | 자동 처리 위험액 |
|---|---:|---:|---:|---:|
| 전부 사람 | 1200 | 3600 | **375%** | 0원 |
| 50,000원 | 412 | 1236 | **129%** | 672,804원 |
| 100,000원 | 183 | 549 | **57%** | 1,306,610원 |
| 300,000원 | 32 | 96 | 10% | 2,291,931원 |
| 1,000,000원 | 1 | 3 | 0% | 2,881,208원 |
| 전부 자동 | 0 | 0 | 0% | 2,955,745원 |

70% 규칙을 적용하면 답은 **100,000원**입니다. 50,000원은 129%라 무너지고, 300,000원은 용량을 10%밖에 안 쓰면서 위험액만 키우니까요.

여기서 중요한 건 표의 **가운데 두 열이 사실상 고정**이라는 점입니다. 검토 용량은 사람 수 × 근무 시간이 정하고, 그건 문턱을 어떻게 설계하든 안 바뀝니다. 즉 이 문제는 이렇게 다시 쓸 수 있습니다.

> **하루에 사람이 볼 수 있는 건 183건뿐이다. 그 183칸을 무엇으로 채울 것인가?**

문턱을 금액으로 잡는다는 건 "183칸을 **금액 상위 183건**으로 채운다"는 선택입니다. 카드가 묻는 한계와 장점은 전부 이 한 문장에서 나옵니다.

## 2. 한계 — 금액은 위험의 대리 변수(proxy)일 뿐이다

### 2.1 정밀도-재현율로 번역하기

검토 용량이 고정된 문제는 머신러닝의 **고정 K 랭킹 문제**와 같은 모양입니다.

- **K = 183** (하루 검토 정원, 예산)
- **점수 함수 s(요청)** = 이 건이 얼마나 위험한가에 대한 추정
- 게이트 = s 기준 상위 K건을 사람에게 보내기

금액 단일 문턱은 `s(요청) = 금액` 이라고 놓은 것과 같습니다. `금액 ≥ 100,000` 이라는 규칙은 `금액` 으로 정렬해서 위에서 183개를 자르는 것과 정확히 같은 집합을 만들죠.

이때 성능은 두 지표로 갈립니다.

| 지표 | 이 상황에서의 의미 |
|---|---|
| **정밀도 (precision@K)** | 사람에게 보낸 183건 중 실제로 문제였던 비율. 낮으면 검토자가 멀쩡한 건만 보다가 지친다 |
| **재현율 (recall@K)** | 하루 전체 실제 문제 건 중 사람이 잡아낸 비율. 낮으면 게이트가 있으나 마나 |

K가 고정이면 **정밀도와 재현율은 서로 트레이드오프가 아니라 같이 움직입니다.** 183칸에 진짜 위험 건이 더 많이 들어가면 정밀도도 오르고 재현율도 오릅니다. 둘을 동시에 올리는 유일한 방법은 **점수 함수 s의 순위 품질을 올리는 것**뿐이고요. (K를 늘려서 재현율을 올리는 길은 이미 막혀 있습니다 — 용량이 없으니까요. 그게 23.3의 전제입니다.)

그래서 카드의 "같은 용량으로 더 잡는다"는 표현은 **K를 유지한 채 s를 바꿔서 recall@K를 올린다**는 뜻입니다.

### 2.2 금액이 순위를 틀리게 매기는 구체적 사례

`ERROR_RATE = 0.04`라는 상수가 문제를 숨기고 있습니다. 예제는 "잘못된 비율이 금액과 무관하게 일정하다"고 가정하죠. 그래서 자동 처리 위험액 = `합계 × 0.04`라는 단순 곱셈이 됩니다.

현실은 오류율이 금액이 아니라 **다른 것들과** 상관됩니다.

**위음성 (놓치는 것) — 소액인데 위험한 건**

- 가입 3일 된 계정이 8만 원씩 6번 환불 요청 → 개별로는 전부 문턱 아래, 합치면 48만 원
- 카드 도난 후 소액 결제로 유효성 테스트하는 패턴
- 같은 배송지·같은 기기 지문으로 서로 다른 계정 12개가 각각 7만 원 환불

**여기에 더해, 금액 문턱은 그 값이 공개되는 순간 게이밍당합니다.** 문턱이 10만 원이면 9만 9천 원짜리 요청이 늘어납니다. 자금세탁 방지 쪽에서 오래전부터 알려진 **구조화(structuring, smurfing)** 문제예요 — 고정된 신고 기준선 바로 아래로 거래를 쪼개는 행위입니다. 그래서 실무 AML 규제는 고정 금액 기준선만으로는 부족하다고 보고 **위험 기반 접근(risk-based approach)** 을 요구합니다. 자원을 "금액 순"이 아니라 "위험 순"으로 배분하라는 것이죠.

**위양성 (헛수고) — 고액인데 안전한 건**

- 5년 된 우량 고객의 정상 반품 80만 원 → 사람이 3분 쓰고 승인 버튼만 누름
- B2B 계약 정산 환불처럼 금액은 크지만 절차가 이미 검증된 건

위양성이 183칸을 잡아먹으면 **위음성이 그만큼 늘어납니다.** 정원이 고정이니까요. 이게 단일 신호 게이트의 진짜 비용입니다: 헛수고와 놓침이 별개 문제가 아니라 **같은 칸을 두고 다투는 하나의 문제**라는 것.

### 2.3 신호를 섞으면 무슨 일이 일어나는가

카드가 말한 세 가지 신호를 점수에 넣어 봅니다.

| 신호 | 왜 위험 순위를 개선하는가 |
|---|---|
| **신규 고객** | 계정 나이가 짧을수록 사기 기저율이 높다. 되찾을 이력·평판 자산이 없으니까 |
| **반복 환불** | 같은 사용자·기기·주소의 환불 빈도. 소액 분할(구조화)을 잡아내는 축 |
| **이상 패턴** | 그 사용자 자신의 평소 행동 대비 이탈. "금액 8만 원"이 아니라 "이 사람 평균의 12배" |

세 번째가 특히 중요합니다. **절대 금액이 아니라 상대 금액**을 보는 축이거든요. 절대 문턱은 모든 고객에게 같은 선을 긋지만, 평소 3천 원씩 쓰던 계정의 8만 원과 평소 50만 원씩 쓰던 계정의 8만 원은 위험이 다릅니다.

이 신호들을 섞으면 랭킹의 AUC / precision@K가 올라갑니다. 즉 **183칸을 더 잘 채웁니다.** 금액 30만 원짜리 우량 고객 정상 반품이 밀려나고, 그 자리에 신규 계정의 5번째 8만 원 환불이 들어옵니다. 검토 용량은 1분도 늘지 않았는데 잡히는 위험은 늘어나요.

구현은 대단할 필요 없습니다. 처음엔 이런 가산점 규칙으로 충분합니다.

```
score = 금액
      + (계정_나이 < 30일        ? 100_000 : 0)
      + (최근_30일_환불수 >= 3   ?  80_000 : 0)
      + (금액 > 사용자_평균 * 5  ?  50_000 : 0)

게이트 = score 상위 183건  (또는 score >= 용량으로 역산한 문턱)
```

용량 계산 로직(`evaluate`)은 그대로 두고 정렬 키만 바꾼 셈입니다. 70% 규칙도 그대로 적용되고요.

## 3. 장점 — 그런데도 왜 금액으로 시작하는가

예제의 마지막 세 마디가 이유를 정확히 짚습니다. **계산이 되고, 설명이 되고, 감사도 통과한다.**

### 3.1 계산이 된다 (콜드 스타트 없이 바로 시뮬레이션 가능)

`ex3_gate_policy.py`가 하는 일이 바로 이겁니다. 금액 분포만 있으면 **문턱을 바꿔 가며 사람이 볼 건수와 검토 시간을 미리 뽑아 볼 수 있습니다.** 아직 게이트를 켜지도 않았는데 "100,000원으로 하면 하루 183건, 용량의 57%"라는 숫자가 나오죠.

다중 신호 점수는 이게 훨씬 어렵습니다.

- 점수 분포가 어떻게 생겼는지 모르니 문턱을 역산하기 어렵고
- 위험을 학습하려면 라벨이 필요한데, **라벨은 사람이 검토한 건에서만 생깁니다.** 게이트를 통과해 자동 처리된 건은 진짜 문제였는지 알 수 없어요. 전형적인 선택 편향(selection bias) 문제이고, 그래서 초기 게이트는 "무엇이 위험인지" 배울 데이터를 만들어 주는 장치이기도 합니다
- 가중치가 바뀌면 검토 부하가 예고 없이 흔들립니다. 어제 180건이던 게 오늘 400건이 되면 23.3이 경고한 "밀린 건이 쌓이고 → 대충 보기 시작하고 → 전부 자동과 같아진다"로 직행합니다

금액 문턱은 **부하가 예측 가능**합니다. 이게 용량 기반 정책을 세우려면 필수 조건이에요.

### 3.2 설명이 된다

- 검토자에게: "10만 원 넘어서 올라온 겁니다"
- 고객에게: "10만 원 이상은 확인 절차가 있습니다" — 대기 이유를 그대로 말할 수 있음
- 팀에: "왜 100,000이냐" → "50,000이면 용량 129%라 무너집니다"

"위험 점수가 0.73이라서요"는 세 곳 어디에도 못 씁니다. 그리고 설명이 안 되는 게이트는 조용히 우회됩니다 — 누군가 예외 처리 경로를 만들거나, 검토자가 내용을 안 보고 누르기 시작하죠.

### 3.3 감사가 통과된다

23.5에서 승인 기록에 **「보여 준 내용」과 「상태 지문」** 을 남기라고 했습니다. 지문이 다르면 다시 묻고, 다만 **결정에 영향을 주는 필드만** 해시하라고요. 금액 문턱은 여기서 아주 유리합니다.

- 결정에 영향을 주는 필드가 **하나**입니다. 지문이 작고 안정적이에요
- 결정론적입니다. 같은 입력 → 같은 결과. 재현 가능하고 재계산 가능
- 모델 드리프트가 없습니다. 정책 문서에 "10만 원"이라고 적어 두면 6개월 뒤에도 같은 뜻입니다
- 규제·내부 통제 문서에 그대로 쓸 수 있고, **네 눈 원칙(four-eyes)** 같은 통제와도 바로 붙습니다

반대로 다중 신호 게이트는 23.5와 정면으로 부딪칠 수 있습니다. 점수에 쓰인 필드가 전부 결정 영향 필드가 되니까 **상태 지문이 커지고, 그중 하나만 바뀌어도 재질문이 발생합니다.** 사용자 활동으로 계속 변하는 필드(최근 환불 수, 평균 금액)를 지문에 넣으면 재질문이 폭증하고, 그러면 23.5가 경고한 그것이 옵니다 — **사람이 확인 없이 누르기 시작하는 상태.**

그리고 공정성 문제도 있습니다. "신규 고객"에 가산점을 주는 건 합리적이지만, 그건 곧 **신규 고객 전체가 체계적으로 더 오래 기다린다**는 뜻입니다. 이건 정책 결정이지 엔지니어링 결정이 아니라서, 근거를 설명할 준비가 안 된 상태로 켜면 안 됩니다.

## 4. 정리 — 순서가 결론이다

이 카드는 "금액이 나쁘다"도 "다중 신호가 정답이다"도 아닙니다. **순서**에 대한 이야기입니다.

| | 금액 단일 | 다중 신호 |
|---|---|---|
| 같은 용량으로 잡는 위험 (recall@K) | 낮음 | **높음** |
| 부하 예측 가능성 | **높음** | 낮음 |
| 설명 가능성 | **높음** | 낮음 |
| 감사·지문 안정성 | **높음** | 낮음 |
| 도입에 필요한 것 | 금액 분포만 | 라벨·피드백 루프·거버넌스 |
| 게이밍 저항성 | 낮음 (구조화) | 높음 |

권장 경로:

1. **금액 문턱으로 시작한다.** 용량 기반으로 70% 규칙에 맞춰 값을 잡는다 (여기 예제에선 100,000원)
2. **검토 결과를 라벨로 쌓는다.** 승인/반려와 그 사유를 기록한다 — 23.5의 감사 기록이 그대로 학습 데이터가 된다
3. **놓친 건을 사후에 센다.** 자동 처리 후 분쟁·차지백으로 돌아온 건들이 위음성의 실측치다
4. **신호를 하나씩 가산점으로 얹는다.** 얹을 때마다 검토 부하가 여전히 70% 안인지 다시 확인한다 — 문턱 자체가 아니라 **정렬 키**를 바꾸는 것이고, 용량 제약은 끝까지 그대로다
5. **점수에 쓴 필드가 상태 지문에 어떤 영향을 주는지 확인한다.** 재질문 폭증은 게이트를 무력화한다

그리고 23.3 전체를 관통하는 경고를 다시 붙여 둡니다.

> **전부 사람이 보는 정책은 결국 아무도 안 보는 정책이 된다.** 사람을 갈아 넣고 효과는 0인 상태 — 이게 제일 나쁜 결말이다.

신호를 정교하게 만드는 이유도 결국 이것 때문입니다. 사람의 주의는 하루 320건어치밖에 없는 유한 자원이고, 게이트 설계는 그 자원을 어디에 쓸지 정하는 일입니다.
