# `ex2_node_reruns.py`의 「나쁜노드」는 어떤 문제를 만드는가?

## 한 줄 답

메일 발송이 `interrupt()` **앞**에 있어서, 담당자가 검토 요청 메일을 **두 번** 받습니다. 한 번은 처음 멈출 때, 또 한 번은 사람이 **승인한 뒤** 노드가 재실행될 때.

---

## 문제의 코드

```python
호출수 = {"메일": 0, "조회": 0}

def 나쁜노드(s: S) -> S:
    호출수["메일"] += 1
    print(f"    → 담당자에게 «검토 요청» 메일 발송 (누적 {호출수['메일']}회)")
    답 = interrupt("승인하시겠습니까?")   # 부작용 «뒤»에서 멈춘다
    return {"승인": 답}


def 좋은노드(s: S) -> S:
    답 = interrupt("승인하시겠습니까?")   # 부작용 «앞»에 둔다
    호출수["조회"] += 1
    print(f"    → 결과 기록 (누적 {호출수['조회']}회)")
    return {"승인": 답}
```

두 노드는 똑같은 일을 하지만 **부작용과 `interrupt()`의 순서만** 다릅니다. 그런데 실행 결과가 갈립니다.

---

## 왜 두 번 실행되는가 — 체크포인트는 노드 「경계」에 찍힌다

이게 핵심입니다. 21장의 슈퍼스텝 경계 이야기가 그대로 돌아옵니다.

- LangGraph의 체크포인터는 **노드 경계**(슈퍼스텝 경계)에만 스냅샷을 남깁니다. 노드 안 3번째 줄 같은 위치에는 저장 지점이 없습니다.
- `interrupt()`는 노드 **중간**에서 멈춥니다. 하지만 그 중간 지점을 저장할 수 없으니, 재개할 때 엔진은 **직전 경계 = 그 노드의 처음**으로 돌아가 노드 함수를 **처음부터 다시 호출**합니다.
- 재실행 중 `interrupt()`를 다시 만나면, 이번엔 멈추지 않고 `Command(resume=...)`로 넘긴 값을 **즉시 반환**합니다. 그래서 사람 눈에는 「이어서 진행된 것」처럼 보이지만, 실제로는 노드 첫 줄부터 다시 돈 겁니다.

즉 함수 재진입 자체를 막을 방법이 없고, **`interrupt()` 앞의 코드는 항상 두 번(재개 횟수만큼 N+1번) 실행**됩니다.

### 시간 순서로 보면

| 시점 | 나쁜노드 | 좋은노드 |
|---|---|---|
| 1회차 invoke — 노드 진입 | 메일 발송 (1회) | — |
| `interrupt()` 도달 | 멈춤 | 멈춤 |
| 사람이 「승인」 | | |
| `Command(resume="승인")` — 노드 **재진입** | **메일 또 발송 (2회)** | — |
| `interrupt()` 재도달 | resume 값 반환 | resume 값 반환 |
| `interrupt()` 이후 | — | 결과 기록 (1회) |
| **총 부작용 횟수** | **2회** | **1회** |

`run()`이 하는 일도 딱 이 흐름입니다.

```python
app.invoke({"주문": "A-1024", "승인": ""}, cfg)   # 여기서 멈춤
print("    ...사람이 답한다...")
app.invoke(Command(resume="승인"), cfg)           # 여기서 노드가 처음부터 다시 돈다
```

실행하면 마지막에 이렇게 요약됩니다 — **메일 발송 2회, 결과 기록 1회.**

---

## 왜 이게 「그냥 메일 하나 더」로 안 끝나는가

메일이라 우스워 보이지만, 같은 자리에 오는 것들을 대입해 보면 성격이 달라집니다.

- 결제 승인 API 호출 → **이중 결제**
- 외부 시스템 티켓 생성 → 중복 티켓
- 재고 차감 / 쿠폰 소진 → 되돌리기 어려운 상태 변경 (22장의 보상 트랜잭션 영역)
- 알림/슬랙 발송 → 담당자 신뢰도 하락, 「또 왔네」 하고 무시하기 시작

게다가 타이밍이 고약합니다. 두 번째 메일은 **사람이 이미 승인한 뒤에** 날아갑니다. 받는 사람 입장에선 「방금 승인했는데 왜 또 요청이 오지?」가 되고, 승인 절차 자체에 대한 불신으로 이어집니다.

---

## 규칙과 해결책

### 규칙 하나

> **`interrupt()` 앞에는 부작용을 두지 않는다.**

- 읽기만 하는 코드(조회, 계산, 포맷팅)는 앞에 있어도 괜찮습니다. 두 번 돌아도 결과가 같으니까요.
- **밖으로 나가는 것**(메일, HTTP 호출, DB 쓰기, 파일 쓰기, 결제)은 전부 `interrupt()` **뒤로** 밉니다.
- 다만 앞에 두는 읽기도 비용이 두 배가 되고, 값이 달라지면 재실행 결과가 흔들릴 수 있으니 무겁거나 변동성 큰 조회는 주의합니다.

### 부작용이 꼭 앞에 있어야 하면 — 노드를 쪼갠다

「검토해 달라는 메일을 보내고 나서 물어야 한다」처럼 순서가 강제되는 경우가 있습니다. 그럴 땐 노드를 둘로 나눕니다.

```
[부작용 노드: 메일 발송] → [interrupt 노드: 승인 대기]
```

두 노드 **사이에 경계가 생기므로** 체크포인트가 그 자리에 찍히고, 재개는 `interrupt` 노드의 처음으로만 돌아갑니다. 메일 발송 노드는 이미 완료 처리되어 다시 돌지 않습니다.

```python
def 메일발송(s: S) -> S:
    호출수["메일"] += 1
    print("    → 담당자에게 «검토 요청» 메일 발송")
    return {}

def 승인대기(s: S) -> S:
    답 = interrupt("승인하시겠습니까?")
    return {"승인": 답}

g.add_edge("메일발송", "승인대기")
```

### 보조 장치

- 부작용을 **멱등**하게 만듭니다. 멱등 키(주문 ID + 단계)를 붙여 두면 두 번 호출돼도 한 번만 효과가 납니다.
- 노드 안에 여러 개의 `interrupt()`를 두면 재개 로직이 더 헷갈리므로, **노드 하나에 `interrupt()` 하나**를 기본으로 둡니다.

## 함께 기억할 것

- 이 예제는 `InMemorySaver`를 쓰지만, 운영에서는 21장에서 본 대로 **디스크에 저장하는 체크포인터**를 써야 사람이 사흘 뒤에 답해도 이어집니다.
- 멈춘 뒤 프로세스를 붙잡고 있을 필요는 없습니다(23.1). 중단은 예외가 아니라 정상적인 중단입니다.
- 재개 시점에 상태가 바뀌었을 수 있으므로, 승인 기록에 **보여 준 내용과 상태 지문**을 남기고 지문이 다르면 다시 묻습니다(23.5, `ex5_audit.py`).
