# 등급 올리기(escalation)의 본질

**질문:** 등급 올리기(escalation)의 본질은 무엇인가?

**답:** 판단을 올리는 장치가 아니라 **주의를 끄는 장치**다.

---

## 한 줄로

등급 올리기는 「이 결정을 더 높은 사람이 내리게 하자」가 아니라, **「아무도 안 보고 있다는 사실을 누군가에게 알리자」**입니다. 올라가는 것은 판단 권한이 아니라 **가시성(attention)**입니다.

## 왜 이 구분이 중요한가

23.4절의 출발점은 이 문장입니다.

> 무응답 정책이 없으면 기본값은 「영원히 기다림」입니다.

승인 대기 건이 2주 동안 묶여 있었다는 이 장의 도입부가 바로 그 결과예요. 아무도 「기다리는 정책」을 정하지 않았을 뿐인데, 시스템은 조용히 「영원히 기다린다」를 실행하고 있었던 겁니다.

여기서 등급 올리기를 **판단 장치**로 오해하면 이렇게 설계합니다.

- 「24시간 지나면 팀장이 대신 결정한다」
- 「72시간 지나면 임원이 승인한다」

이 설계의 문제는 두 가지입니다.

1. **책임 세탁**: 팀장은 원래 담당자보다 이 건에 대해 아는 게 더 적습니다. 맥락 없이 결정하면 판단 품질이 오히려 떨어져요. 「더 높은 사람 = 더 좋은 판단」이 아닙니다.
2. **원인을 안 고침**: 담당자가 답을 안 한 이유(휴가, 알림 못 봄, 큐가 밀림, 화면에 정보가 안 뜸)를 그대로 두고 결정만 위로 밀어냅니다. 다음 건도 똑같이 묶입니다.

반대로 **주의 장치**로 보면 목표가 달라집니다. 「이 건이 정상 경로에서 이탈했다」는 신호를 **볼 사람이 있는 곳까지 밀어 올리는 것**이 전부입니다. 결정은 여전히 그 결정을 내릴 자격과 맥락이 있는 사람이 합니다. Google SRE 워크북의 사고 대응(incident response)에서 escalation이 하는 일도 이것입니다. 사고를 대신 해결해 줄 사람을 부르는 게 아니라, **응답이 없는 상태를 깨뜨리는** 것이죠.

## 예제 코드에서 보이는 지점

`code/ex4_no_answer.py`는 같은 대기 목록에 네 가지 정책을 나란히 적용합니다.

```python
SLA = 24     # 시간

def p_escalate(_o, amount, h, risk):
    if h <= SLA:
        return "대기", "-"
    if risk == "낮음" and amount < 200_000:
        return "자동 승인", "소액·저위험만 통과"
    if h > 72:
        return "상급자 호출", "책임을 위로 올린다"
    return "담당자 재알림", "한 번 더 찌른다"
```

읽는 순서가 곧 설계 의도입니다.

| 조건 | 동작 | 성격 |
|---|---|---|
| `h <= SLA` (24시간 이내) | 대기 | 아직 정상 경로 |
| 저위험 + 소액 | 자동 승인 | 애초에 사람이 볼 가치가 없던 건 — 문턱 설정 실패를 회수 |
| 24 < h <= 72 | **담당자 재알림** | 「한 번 더 찌른다」 = 순수한 주의 끌기 |
| h > 72 | **상급자 호출** | 담당자를 못 깨웠다는 사실 자체를 위로 알림 |

핵심은 **24시간 다음 단계가 「팀장이 결정」이 아니라 「담당자 재알림」**이라는 점입니다. 첫 번째 반응은 결정권 이전이 아니라 **같은 사람에게 다시 알리기**예요. 그래도 안 되면 그때 위로 올라가는데, 그 호출의 내용도 「대신 결정하세요」가 아니라 「이 큐가 72시간째 막혀 있습니다」에 가깝습니다.

예제의 마무리 문장도 같은 얘기를 합니다.

> 시간이 지날수록 「다르게」 처리한다.
> 중요한 건 「무엇을 고르느냐」가 아니라 「골랐느냐」다.

## 다른 세 정책과 비교하면 더 뚜렷해진다

| 정책 | 시간이 지나면 | 문제 |
|---|---|---|
| 계속 기다린다 | 아무 일도 안 일어남 | 정책이 아니라 **정책 부재**. 200시간 묶인 건이 증거 |
| 자동 거절 | 전부 거절 | 안전해 보이지만 4,200,000원짜리를 이유 없이 거절, 고객이 화남 |
| 자동 승인 | 전부 승인 | 위험을 그대로 통과시킴 |
| 등급 올리기 | 단계별로 다르게 | 유일하게 **시간을 정보로 취급**함 |

앞의 세 개는 모두 「경과 시간」을 결정의 근거로 씁니다. 시간이 지났다는 사실만으로 거절하거나 승인해요. 등급 올리기만이 경과 시간을 **결정의 근거가 아니라 프로세스가 막혔다는 신호**로 읽습니다. 그래서 결과가 「승인/거절」이 아니라 「알림/호출」인 겁니다.

## 실무에서 잘못 만들어지는 형태

- **자동 승인의 위장**: 「N시간 지나면 상급자에게 올라가고, 상급자도 M시간 안 보면 통과」 — 결국 자동 승인인데 책임만 흩어 놓은 구조입니다.
- **에스컬레이션 체인이 곧 결재선**: 단계마다 결정 권한을 넘기면 최종 결정자는 맥락이 가장 없는 사람이 됩니다.
- **알림만 늘리기**: 주의를 끄는 게 목적이라면 **끌린 다음에 무엇을 봐야 하는지**가 같이 가야 합니다. 23.5절의 「보여 준 내용」이 여기와 맞물립니다. 상급자를 불러 놓고 판단 재료를 안 주면 그 사람도 확인 없이 누릅니다.
- **문턱 설계 실패의 땜빵**: 대기가 계속 쌓인다면 등급 올리기를 촘촘히 할 게 아니라 23.3절로 돌아가야 합니다. 검토 시간이 용량의 70%를 넘지 않는 문턱으로 다시 잡는 게 먼저예요. 등급 올리기는 **잔여 케이스용 안전망**이지 용량 문제의 해법이 아닙니다.

## 다른 절과의 연결

- **23.1 / 21장**: 멈춘 자리는 체크포인터에 남습니다. 프로세스를 붙잡고 있지 않으니 사흘, 200시간 대기가 물리적으로 가능해요. 그래서 **무응답 정책이 반드시 필요**해집니다. 기다림이 공짜라서 아무도 안 깨닫는 게 함정입니다.
- **23.3**: 「전부 사람이 보는 정책은 결국 아무도 안 보는 정책이 된다」 — 문턱이 잘못되면 등급 올리기가 상시 발동하고, 상시 발동하는 알림은 무시됩니다. 주의 장치는 **드물게 울려야** 작동합니다.
- **23.5**: 등급이 올라가서 다른 사람이 승인하게 되면, 그 사람이 무엇을 보고 결정했는지(`shown`)와 상태 지문(`state_hash`)이 더 중요해집니다. 72시간 전 상태로 오늘 승인하면 안 되니까요.

## 외울 문장

> 올라가는 것은 판단이 아니라 눈길이다. 등급 올리기가 답을 대신 정해 주기 시작하면, 그건 이미 자동 승인이거나 자동 거절이다.
