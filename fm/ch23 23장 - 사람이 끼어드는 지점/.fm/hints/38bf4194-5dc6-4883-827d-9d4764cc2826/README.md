# `ex1_interrupt.py`가 5만 원 환불에 사람을 부르지 않는 이유

## 질문

`ex1_interrupt.py`가 5만 원 환불에 사람을 부르지 않는 이유는 무엇인가?

## 답

**모든 것을 사람이 보는 정책은 아무것도 안 보는 정책과 같아지기 때문이다. 문턱은 10만 원이다.**

---

## 코드에서 확인하기

`ex1_interrupt.py`의 `사람확인` 노드가 문턱을 그대로 코드로 들고 있습니다.

```python
def 사람확인(s: S) -> S:
    if s["금액"] < 100_000:
        print("  [확인]  10만 원 미만이라 사람에게 안 묻는다")
        return {"승인": "자동"}

    # 여기서 그래프가 «멈춘다». 예외가 아니라 정상적인 중단이다.
    답 = interrupt({
        "물음": "이 환불을 승인하시겠습니까?",
        "금액": s["금액"],
        "근거": "고객 요청 · 상품 미개봉",
    })
    print(f"  [확인]  사람이 «{답}» 라고 했다")
    return {"승인": 답}
```

`main`에서 세 건을 돌립니다.

| 호출 | 금액 | 결과 |
|---|---|---|
| `run(50_000)` | 5만 원 | 문턱 미만 → `interrupt` 없이 `승인="자동"` |
| `run(300_000, 사람답변="승인")` | 30만 원 | 멈추고 사람에게 물음 → 승인 |
| `run(900_000, 사람답변="거절")` | 90만 원 | 멈추고 사람에게 물음 → 거절 |

그리고 예제 끝에서 직접 못을 박습니다.

> 50,000원짜리는 사람을 안 부른다. 부르면 안 된다.
> «모든 것을 사람이 본다»는 정책은 아무것도 안 보는 정책과 같아진다.

즉 5만 원을 통과시키는 것은 「귀찮아서」가 아니라 **의도된 정책**입니다.

---

## 왜 «전부 사람»이 «전부 자동»과 같아지는가 (23.3, `ex3_gate_policy.py`)

문턱은 취향이 아니라 **용량**으로 정합니다. `ex3_gate_policy.py`는 하루치 요청 분포를 깔아 놓고 문턱별로 「사람이 볼 건수」와 「자동 처리 위험액」을 계산합니다.

전제:

```python
REVIEW_MINUTES = 3        # 한 건 검토에 걸리는 시간
REVIEWERS = 2             # 검토 담당자 수
WORK_MINUTES = 8 * 60     # 하루 근무 시간
ERROR_RATE = 0.04         # 자동 처리 중 잘못된 비율 (실측 가정)
```

하루 요청 1,200건, 하루 처리 가능 320건(2명 × 480분 ÷ 3분). 실제로 실행하면 이렇게 나옵니다.

| 문턱 | 사람이 볼 건수 | 검토 시간(분) | 용량 대비 | 자동 처리 위험액 |
|---|---:|---:|---:|---:|
| 전부 사람 | 1200 | 3600 | **375%** | 0원 |
| 50,000원 | 412 | 1236 | **129%** | 672,804원 |
| **100,000원** | 183 | 549 | **57%** | 1,306,610원 |
| 300,000원 | 32 | 96 | 10% | 2,291,931원 |
| 1,000,000원 | 1 | 3 | 0% | 2,881,208원 |
| 전부 자동 | 0 | 0 | 0% | 2,955,745원 |

여기가 핵심입니다.

- **«전부 사람» = 용량의 375%.** 담당자 2명이 하루에 3,600분치 검토를 해야 합니다. 물리적으로 불가능하죠. 그래서 실제로는 밀린 건이 쌓이고 → 담당자가 대충 보기 시작하고 → 결국 눈으로만 훑고 전부 승인 버튼을 누릅니다. **결과가 «전부 자동»과 같아집니다.** 사람을 갈아 넣고 효과는 0인 상태, 이게 제일 나쁜 결말입니다.
- **5만 원 문턱조차 용량의 129%.** 1,200건 중 412건이 사람에게 갑니다. 여전히 못 감당합니다. 그래서 5만 원은 문턱이 될 수 없습니다.
- **10만 원 문턱은 57%.** 183건, 549분. 70% 이내로 들어오는 문턱 중 **제일 낮은** 값입니다.

### 선택 규칙

> **검토 시간이 용량의 70%를 넘지 않는 문턱 중 제일 낮은 것을 고른다.**
> 30%는 휴가·회의·급한 건을 위해 비워 둔다.

- **왜 «70%»인가** — 100%로 꽉 채우면 휴가 하루, 회의 한 번, 급한 건 한 건에 즉시 밀리기 시작합니다. 대기열은 이용률이 100%에 가까워질수록 대기 시간이 폭발합니다. 30%는 그 완충입니다.
- **왜 «제일 낮은 것»인가** — 문턱이 높아질수록 위험액이 커지기 때문입니다(10만 원 130만 원 → 30만 원 229만 원). 용량이 허락하는 한 최대한 많이 잡는 게 이득이므로, 70% 제약을 만족하는 것 중 가장 낮은 값을 고릅니다.

이 두 조건을 동시에 만족하는 값이 **10만 원**이고, 그래서 `ex1_interrupt.py`가 `100_000`을 들고 있는 것입니다. 5만 원 환불은 이 문턱 아래이므로 사람을 부르지 않습니다.

## 왜 이것이 «사람 개입» 설계의 핵심인가

23장 전체의 논지는 사람을 그래프 **밖의 예외**가 아니라 **안의 노드**로 넣는 것입니다. 그런데 노드로 넣는 순간, 그 노드는 유한한 자원(사람의 시간)을 소비합니다.

- `interrupt()`는 공짜가 아닙니다. 한 번 호출할 때마다 담당자 3분을 씁니다.
- 그 자원을 어디에 쓸지 정하는 것이 **문턱(gate)** 이고, 이건 취향이 아니라 **산술**입니다.
- 문턱을 안 정하거나 0으로 두면(=전부 사람), 시스템은 형식적으로만 안전하고 실질적으로는 무방비입니다. 승인 도장은 찍히는데 아무도 안 본 상태니까요. 감사 기록에는 «kim 승인»이 남지만 그 승인에는 정보가 없습니다.

이 마지막 지점이 `ex5_audit.py`의 「보여 준 내용」 칼럼과 이어집니다. 사람이 실제로 무엇을 보고 판단했는지가 남아야 승인이 의미를 갖는데, 용량을 초과한 문턱은 「보긴 봤다」는 기록만 양산합니다.

## 보충: 문턱을 금액으로만 잡는 게 최선은 아니다

`ex3_gate_policy.py`가 스스로 덧붙이는 단서입니다.

> 문턱을 «금액»으로만 잡는 게 최선은 아니다. 신규 고객, 반복 환불, 이상 패턴 같은 신호를 섞으면 같은 용량으로 더 잡는다. 다만 시작은 금액이 좋다. 계산이 되고, 설명이 되고, 감사도 통과한다.

즉 10만 원은 **최종 정답이 아니라 계산 가능한 출발점**입니다. 같은 183건의 예산으로 「9만 원짜리인데 3회차 환불」을 잡고 「12만 원짜리인데 첫 구매·미개봉」을 흘려보내는 게 더 나을 수 있습니다. 하지만 그건 신호를 더 붙인 다음 이야기고, 어느 쪽이든 **용량 70% 규칙**은 그대로 적용됩니다.

---

## 한 줄 정리

5만 원은 사람이 볼 만큼 위험하지 않아서가 아니라, **5만 원까지 사람이 보게 하면(용량의 129%) 검토 자체가 붕괴해서 10만 원짜리도 30만 원짜리도 아무도 안 보게 되기 때문에** 통과시킵니다. 문턱 10만 원은 「용량의 70%를 넘지 않는 문턱 중 최저」라는 규칙에서 나온 숫자입니다.
