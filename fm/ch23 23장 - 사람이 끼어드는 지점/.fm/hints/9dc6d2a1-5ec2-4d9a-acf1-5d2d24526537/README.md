# 등급 올리기(escalation) 정책 — 시간이 지날수록 다르게 처리한다

**Q. 등급 올리기 정책은 시간에 따라 어떻게 다르게 처리하는가?**

**A. 24시간 초과 시 소액·저위험(20만 원 미만, 위험 낮음)만 자동 통과하고 나머지는 담당자에게 재알림, 72시간 초과 시 상급자를 부른다.**

출처: 23장 23.4 「사람이 답을 안 하면」 / `code/ex4_no_answer.py`의 `p_escalate`

---

## 1. 왜 이 질문이 나오나 — 기본값은 「영원히 기다림」

23장은 사람을 그래프 *밖의 예외*가 아니라 *안의 노드*로 넣는 방법을 다룹니다. 중단점(interrupt)을 걸어 사람에게 승인을 물으면, 멈춘 자리는 체크포인터에 남고 프로세스는 놓아줘도 됩니다. 여기까지는 좋습니다.

문제는 **사람이 답을 안 할 때**입니다. 이때 무슨 일이 일어나는지 정하지 않으면 시스템의 기본 동작은 자동으로 「영원히 기다림」이 됩니다. 이 장의 도입부에 나오는 “승인 대기 건이 2주 동안 묶여 있었습니다”가 바로 그 결과예요.

> 무응답 정책이 없으면 기본값은 「영원히 기다림」입니다. 시간이 지날수록 다르게 처리하세요. 등급 올리기는 판단을 올리는 장치가 아니라 **주의를 끄는 장치**입니다. — 23장 한 장 요약

## 2. 네 가지 대기 정책 비교

`ex4_no_answer.py`는 같은 승인 대기 목록에 네 가지 정책을 나란히 적용해 봅니다. SLA(약속한 응답 시간)는 24시간입니다.

| 정책 | 함수 | 동작 | 문제 |
|---|---|---|---|
| 계속 기다린다 | `p_wait` | 무조건 대기 | 정책이 아니라 **정책을 안 정한 것**. 200시간 묶인 건이 증거 |
| 자동 거절 | `p_reject` | SLA 초과 시 전부 거절 | 안전해 보이지만 420만 원짜리도 거절. 고객은 이유도 모른 채 통보받음 |
| 자동 승인 | `p_approve` | SLA 초과 시 전부 승인 | 위험을 그대로 통과시킴 |
| **등급 올리기** | `p_escalate` | 시간·금액·위험도에 따라 **다르게** | 실무의 답에 가까움 |

## 3. `p_escalate`의 실제 코드

```python
SLA = 24     # 시간


def p_escalate(_o, amount, h, risk):
    if h <= SLA:
        return "대기", "-"
    if risk == "낮음" and amount < 200_000:
        return "자동 승인", "소액·저위험만 통과"
    if h > 72:
        return "상급자 호출", "책임을 위로 올린다"
    return "담당자 재알림", "한 번 더 찌른다"
```

### 판정 순서를 그대로 따라가면

1. **`h <= 24` (SLA 이내)** → `대기`. 아직 아무것도 하지 않습니다. 사람에게 준 시간을 존중하는 구간이에요.
2. **`risk == "낮음" and amount < 200_000`** → `자동 승인`. 24시간을 넘겼고, 잃을 게 적은 건만 흘려보냅니다. **손실 상한이 20만 원으로 명시적으로 묶여 있다**는 점이 핵심입니다.
3. **`h > 72`** → `상급자 호출`. 담당자를 찔러도 안 움직였다는 뜻이므로 책임을 위로 올립니다.
4. **그 외 (24 < h ≤ 72)** → `담당자 재알림`. 한 번 더 찌릅니다.

### 카드 답과 코드의 대응

- “24시간 초과 시 소액·저위험(20만 원 미만, 위험 낮음)만 자동 통과” → 2번
- “나머지는 담당자에게 재알림” → 4번
- “72시간 초과 시 상급자를 부른다” → 3번

## 4. 예제 데이터로 실제 판정 추적하기

```python
PENDING = [
    # (주문, 금액, 대기 시간(시간), 위험도)
    ("A-1024",   120_000,   2, "보통"),
    ("A-1031",   890_000,  26, "높음"),
    ("A-1044",   150_000,  73, "보통"),
    ("A-1050", 4_200_000, 121, "높음"),
    ("A-1066",   110_000, 200, "낮음"),
]
```

| 주문 | 금액 | 대기 | 위험 | 등급 올리기 결과 | 이유 |
|---|---:|---:|---|---|---|
| A-1024 | 120,000 | 2h | 보통 | 대기 | SLA 이내 |
| A-1031 | 890,000 | 26h | 높음 | 담당자 재알림 | 소액·저위험 아님, 72h 이하 |
| A-1044 | 150,000 | 73h | 보통 | 상급자 호출 | 20만 원 미만이지만 위험이 「낮음」이 **아님** → 72h 규칙으로 |
| A-1050 | 4,200,000 | 121h | 높음 | 상급자 호출 | 고액·고위험 장기 방치 |
| A-1066 | 110,000 | 200h | 낮음 | **자동 승인** | 소액·저위험 조건이 72h 규칙보다 **먼저** 걸림 |

### 놓치기 쉬운 두 가지

- **A-1044**: 15만 원으로 20만 원 미만이지만 위험도가 「보통」이라 자동 통과 대상이 아닙니다. 두 조건은 **AND**입니다. 금액만 보면 틀립니다.
- **A-1066**: 200시간이나 묶였는데도 상급자 호출이 아니라 자동 승인입니다. 코드에서 소액·저위험 검사가 `h > 72` 검사보다 **위에 있기 때문**입니다. 의도된 설계예요 — 11만 원짜리 저위험 건 때문에 상급자를 부르는 건 “주의를 끄는 장치”를 낭비하는 일이니까요. 조건 순서 자체가 정책의 일부입니다.

## 5. 왜 이렇게 설계하나 — 세 가지 관점

**① 등급 올리기는 판단을 올리는 게 아니라 주의를 끈다.**
상급자를 부르는 이유는 그 사람이 더 똑똑해서가 아니라, 아무도 안 보고 있다는 신호를 위로 보내기 위해서입니다. Google SRE Workbook의 사건 대응(incident response)에서 escalation을 다루는 관점과 같습니다.

**② 자동 통과는 「손실 상한」이 계산될 때만 허용한다.**
20만 원 × 위험 낮음이라는 조건은 “최악의 경우 얼마를 잃나”를 미리 정한 값입니다. 무제한 자동 승인(`p_approve`)이 위험한 이유는 이 상한이 없기 때문이에요.

**③ 문턱은 취향이 아니라 용량으로 정한다.**
바로 앞 절(`ex3_gate_policy.py`)의 결론과 이어집니다. 검토 시간이 팀 용량의 70%를 넘지 않는 문턱 중 제일 낮은 것을 고르고, 30%는 휴가·회의·급한 건을 위해 비워 둡니다. 전부 사람이 보는 정책은 결국 아무도 안 보는 정책이 됩니다. 24/72라는 숫자도 마찬가지로 자기 팀의 SLA와 용량에 맞춰 조정할 값이지 고정 상수가 아닙니다.
