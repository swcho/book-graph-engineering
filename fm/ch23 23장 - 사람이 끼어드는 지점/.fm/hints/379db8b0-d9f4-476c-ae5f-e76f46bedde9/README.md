# "전부 사람이 본다"는 정책의 결말

## 질문

「전부 사람이 본다」는 정책의 결말은 무엇인가?

## 답

**결국 아무도 안 보는 정책이 된다.** 밀린 건이 쌓이고, 담당자가 대충 보기 시작해서, 결과적으로 「전부 자동」과 같아진다.

---

## 왜 그렇게 되는가 — 산수로 확인하기

23장 `ex3_gate_policy.py`는 이 결말을 감정이 아니라 **숫자**로 보여줍니다. 하루치 환불 요청 분포를 놓고 승인 문턱(threshold)별로 「사람이 볼 건수」와 「검토 시간」을 계산합니다.

```python
REVIEW_MINUTES = 3        # 한 건 검토에 걸리는 시간
REVIEWERS = 2             # 검토 담당자 수
WORK_MINUTES = 8 * 60     # 하루 근무 시간
ERROR_RATE = 0.04         # 자동 처리 중 잘못된 비율 (실측 가정)

def evaluate(amounts, threshold):
    reviewed = [a for a in amounts if a >= threshold]
    auto     = [a for a in amounts if a <  threshold]
    load     = len(reviewed) * REVIEW_MINUTES
    capacity = REVIEWERS * WORK_MINUTES
    risk     = sum(auto) * ERROR_RATE
    return len(reviewed), load, capacity, risk
```

하루 요청 1,200건, 검토 담당자 2명이 8시간 일하면 처리 가능한 건수는 `2 × 480 / 3 = 320건`입니다. 그런데 「전부 사람」(문턱 = 0원)을 고르면 1,200건을 전부 봐야 하고, 검토 시간은 3,600분 — **용량의 3배가 넘습니다.**

여기서 핵심은 **초과분이 사라지지 않는다**는 점입니다. 하루에 880건씩 밀립니다. 그러면 사람은 둘 중 하나를 합니다.

1. **밀린 채로 방치** → `ex4_no_answer.py`의 「200시간 묶인 건」이 됩니다. 승인 대기가 2주 동안 서 있는 그 상태.
2. **속도를 올림** → 3분 걸리던 검토가 20초가 되고, 화면을 안 읽고 승인 버튼만 누릅니다.

2번이 곧 답의 후반부입니다. 담당자가 대충 보기 시작하면, 문턱은 형식적으로만 존재하고 **실질적으로는 「전부 자동」과 같아집니다.**

> «전부 사람»은 검토 시간이 용량의 3배가 넘는다. 실제로는 이렇게 된다.
> 밀린 건이 쌓이고, 담당자가 대충 보기 시작하고, 결국 «전부 자동»과 같아진다.
> 이게 제일 나쁜 결말이다. 사람을 갈아 넣고 효과는 0인 상태.
> — `ex3_gate_policy.py`

## 왜 이게 "제일 나쁜" 결말인가

「전부 자동」보다 나쁩니다. 비교해 보면 명확합니다.

| 정책 | 위험 차단 효과 | 사람이 드는 비용 | 결과 |
|---|---|---|---|
| 전부 자동 | 0 | 0 | 위험액이 그대로 노출. **정직하게 나쁨** |
| 전부 사람 (형해화 후) | 0 | 최대 | 위험은 그대로 + 인건비 소진. **거짓 안전감까지 추가** |
| 적정 문턱 | 큰 건은 잡음 | 용량 안 | 실무의 답 |

「전부 사람」이 무너진 상태는 「전부 자동」과 위험 노출이 같은데, 사람의 시간은 다 썼고, 게다가 **「우리는 전 건을 검토합니다」라는 문서가 남아 있습니다.** 감사와 경영진은 통제가 있다고 믿지만 실제로는 없습니다. 통제가 없는 것보다 「있다고 착각하는 통제」가 더 위험합니다.

## 같은 현상의 다른 이름들

이 결말은 소프트웨어 바깥에서 오래전부터 관찰된 것입니다. 개념을 연결해 두면 기억이 붙습니다.

- **고무도장 찍기 (rubber-stamping)** — 승인 절차가 남아 있지만 내용 검토 없이 기계적으로 통과시키는 것. 승인권자가 존재해도 승인 기능은 죽은 상태입니다. 이사회·감사 문헌에서 오래 쓰인 표현입니다.
- **경보 피로 (alert fatigue)** — 의료 기기 알람과 보안 관제(SOC)에서 잘 연구된 현상. 알람이 너무 많으면 담당자가 알람을 끄거나 무시하게 되고, **정작 진짜 알람도 놓칩니다.** 알람 수를 줄이는 것이 알람 정확도를 올리는 것보다 먼저인 이유입니다.
- **경보의 늑대 소년 효과 / 정상화된 일탈(normalization of deviance)** — 「어차피 대부분 문제없더라」는 경험이 쌓이면 규정을 지키지 않는 것이 팀의 새 기본값이 됩니다.
- **처리량 대비 도착률 (queueing theory)** — 도착률(λ)이 처리율(μ)을 넘으면 대기열은 **무한히** 자랍니다. 잠깐 초과가 아니라 구조적 초과이면 큐는 절대 안정되지 않습니다. `ex3`의 「용량 대비 300%」가 정확히 이 상태입니다.

## 그럼 문턱은 어떻게 정하는가

23장이 제시하는 규칙은 **취향이 아니라 용량**입니다.

> 검토 시간이 **용량의 70%를 넘지 않는 문턱 중 제일 낮은 것**을 고른다.
> 30%는 휴가·회의·급한 건을 위해 비워 둔다.

- **「제일 낮은 것」**인 이유: 문턱이 낮을수록 사람이 잡아 주는 건이 많아지므로, 용량이 허락하는 한 최대한 낮춥니다.
- **「70%」인 이유**: 100%로 꽉 채우면 휴가 하루, 장애 한 번에 바로 백로그가 생기고 위의 붕괴 경로로 들어갑니다. 여유 30%가 완충 장치입니다.
- **금액만이 기준은 아님**: 신규 고객, 반복 환불, 이상 패턴 같은 신호를 섞으면 같은 용량으로 더 위험한 건을 잡습니다. 다만 **시작은 금액이 좋습니다** — 계산되고, 설명되고, 감사도 통과합니다.

`ex1_interrupt.py`가 이 정책을 코드로 구현한 모습입니다.

```python
def 사람확인(s: S) -> S:
    if s["금액"] < 100_000:
        print("  [확인]  10만 원 미만이라 사람에게 안 묻는다")
        return {"승인": "자동"}
    답 = interrupt({...})
```

50,000원짜리는 사람을 안 부릅니다. **부르면 안 됩니다.** 소액 건이 검토 큐를 채우는 순간, 정작 900,000원짜리가 그 뒤에 줄을 서게 되니까요.

## 이어지는 같은 함정 — 매번 다시 묻기

23.5절에서 같은 실패 패턴이 한 번 더 나옵니다. 승인 기록의 `state_hash`(상태 지문)가 다르면 다시 물어야 하는데, **결정에 영향을 주지 않는 필드까지 해시에 넣으면** 사소한 변경마다 재승인을 요구하게 됩니다. 그러면?

> 매번 다시 물으면 사람이 확인 없이 누르기 시작한다.

원인은 다르지만(문턱이 낮아서 vs 재질문이 잦아서) 결말은 똑같습니다. **사람에게 묻는 횟수가 사람의 주의력 예산을 넘으면, 묻는 행위 자체가 무의미해집니다.** 이것이 23장을 관통하는 한 문장입니다.

## 한 줄 요약

사람의 검토는 **유한한 자원**이다. 무제한으로 소비하도록 설계하면 자원이 고갈되는 게 아니라 **품질이 0으로 떨어진다.** 「전부 사람이 본다」는 안전 정책처럼 보이지만, 용량을 초과하는 순간 「전부 자동 + 인건비 낭비 + 거짓 안전감」이 된다.
