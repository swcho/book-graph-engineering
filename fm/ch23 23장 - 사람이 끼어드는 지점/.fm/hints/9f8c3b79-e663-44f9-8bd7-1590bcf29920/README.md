# 중단점으로 멈춘 자리는 어디에 남는가?

> **답**: 체크포인터에 남는다. 그래서 프로세스를 붙잡고 있지 않아도 되고, 사람이 사흘 뒤에 답해도 이어진다.

---

## 한 줄 정리

`interrupt()` 로 멈춘 그래프의 「멈춘 자리」는 메모리 안의 콜스택이 아니라 **체크포인터(checkpointer)** 에 저장된다. 상태와 「다음에 실행할 노드」가 저장소에 있으니, 그 사이 프로세스는 죽어도 되고 서버를 재시작해도 된다.

## 왜 이게 중요한가 — 「사람을 기다리는 while 루프」와의 차이

사람 승인을 기다리는 가장 순진한 구현은 이렇다.

```python
while not 승인됐나():   # ← 프로세스가 여기 묶인다
    time.sleep(10)
```

이 방식은 기다리는 동안 **프로세스가 살아 있어야만** 한다. 워커 하나가 통째로 점유되고, 배포·재시작·OOM 한 번이면 대기 중이던 승인 건이 전부 증발한다. 승인 대기가 며칠 단위인 실무에서는 애초에 성립하지 않는다.

중단점 방식은 반대다. 멈추는 순간 실행을 **끝내고**, 어디까지 갔는지를 체크포인터에 적어 둔다. 프로세스는 해방된다. 재개는 나중에 다른 프로세스가 같은 `thread_id` 로 이어받으면 된다.

| | while 루프 대기 | 체크포인터 + 중단점 |
|---|---|---|
| 대기 중 프로세스 | 붙잡고 있어야 함 | 필요 없음 |
| 서버 재시작 | 대기 건 유실 | 그 자리에 그대로 |
| 대기 가능 기간 | 사실상 분~시간 | 며칠·몇 주 |
| 재개 주체 | 같은 프로세스 | 아무 프로세스나 (`thread_id` 로 찾음) |

## 코드로 보기 (`ex1_interrupt.py`)

멈추는 쪽:

```python
def 사람확인(s: S) -> S:
    if s["금액"] < 100_000:
        return {"승인": "자동"}

    # 여기서 그래프가 «멈춘다». 예외가 아니라 정상적인 중단이다.
    답 = interrupt({
        "물음": "이 환불을 승인하시겠습니까?",
        "금액": s["금액"],
        "근거": "고객 요청 · 상품 미개봉",
    })
    return {"승인": 답}
```

체크포인터를 붙이는 쪽 — **이게 없으면 멈춘 자리를 기억할 수 없다**:

```python
app = g.compile(checkpointer=InMemorySaver())
```

멈춘 자리를 읽고, 나중에 이어 가는 쪽:

```python
cfg = {"configurable": {"thread_id": f"환불-{금액}"}}
out = app.invoke({"금액": 금액, ...}, cfg)

if "__interrupt__" in out:
    물음 = out["__interrupt__"][0].value
    상태 = app.get_state(cfg)
    print(f"다음에 실행할 노드: {상태.next}")   # ← 멈춘 자리가 조회된다
    # ...사람이 답할 때까지 여기서 기다린다. 프로세스는 안 붙잡고 있어도 된다...
    out = app.invoke(Command(resume=사람답변), cfg)
```

핵심 세 조각:

1. **`thread_id`** — 멈춘 자리를 다시 찾아오는 열쇠. 체크포인터 안에서 이 대화/작업 한 건을 식별한다.
2. **`app.get_state(cfg).next`** — 체크포인터에 저장된 「다음에 실행할 노드」. 멈춘 자리가 실제로 조회 가능한 데이터라는 증거다.
3. **`Command(resume=답)`** — 사람이 준 값을 들고 그 자리부터 이어 간다. 첫 `invoke` 와 재개 `invoke` 는 **다른 프로세스여도 된다**.

## 운영에서의 함정 — 메모리 체크포인터

예제는 `InMemorySaver()` 를 쓴다. 학습용으로는 편하지만, 프로세스가 죽으면 「멈춘 자리」도 같이 죽는다. 즉 **메모리 체크포인터를 쓰면 「사흘 뒤에 답해도 이어진다」는 성질이 사라진다.**

원문도 이 점을 못 박는다.

> `ex1`, `ex2` 는 메모리 체크포인터를 씁니다. 운영에서는 21장에서 본 대로 디스크에 저장하는 체크포인터를 써야 사람이 사흘 뒤에 답해도 이어집니다.

정리하면, 「사흘 뒤에도 이어진다」는 두 조건이 다 있어야 성립한다.

- 멈춘 자리가 **체크포인터에 저장**될 것 (중단점 방식일 것)
- 그 체크포인터가 **프로세스 밖에 영속**될 것 (Postgres/SQLite 등 디스크 기반)

## 같이 따라오는 성질 — 재개하면 노드를 처음부터 다시 돈다

체크포인트는 **노드 경계**에 찍힌다(21장의 슈퍼스텝 경계). `interrupt()` 는 노드 *중간*에서 멈추지만, 저장된 지점은 그 노드의 시작이다. 그래서 재개하면 그 노드는 **처음부터 다시 실행**된다.

`ex2_node_reruns.py` 가 이걸 보여 준다.

```python
def 나쁜노드(s: S) -> S:
    호출수["메일"] += 1
    print("→ 담당자에게 «검토 요청» 메일 발송")   # 재개 시 두 번째 발송
    답 = interrupt("승인하시겠습니까?")
    return {"승인": 답}

def 좋은노드(s: S) -> S:
    답 = interrupt("승인하시겠습니까?")           # 부작용 «앞»에 둔다
    호출수["조회"] += 1
    return {"승인": 답}
```

담당자는 검토 요청 메일을 두 번 받는다. 승인을 *하고 나서* 한 번 더. 그래서 규칙은 하나다 — **`interrupt` 앞에는 부작용을 두지 않는다.** 읽기만 하는 코드는 괜찮다. 밖으로 나가는 것은 전부 뒤로 민다. 꼭 앞에 있어야 하면 노드를 둘로 쪼개서 「부작용 노드 → interrupt 노드」로 만들면 사이에 경계가 생긴다.

## 오래 멈춰 있는 것의 대가

멈춘 자리가 며칠씩 살아 있다는 건 좋은 성질이지만, 두 가지 후속 문제를 만든다.

- **무응답 정책** (`ex4_no_answer.py`): 정책을 안 정하면 기본값은 「영원히 기다림」이다. 200시간 묶인 건이 그 증거. 시간이 지날수록 다르게 처리해야 한다(24시간 → 소액·저위험만 자동 통과 + 재알림, 72시간 → 상급자 호출).
- **상태 지문** (`ex5_audit.py`): 사흘 전에 승인한 내용과 지금 실행할 내용이 다를 수 있다. 승인 기록에 「보여 준 내용」과 `state_hash`(그 순간의 상태 지문)를 남기고, 재개 시 지문이 다르면 다시 물어야 한다. 사흘 전 승인으로 오늘 4,200,000원을 내보내면 안 된다.

## 암기 포인트

- 멈춘 자리 = **체크포인터**에 저장 (콜스택 아님)
- 다시 찾는 열쇠 = **`thread_id`**
- 조회 = **`app.get_state(cfg).next`**
- 재개 = **`Command(resume=값)`**
- 프로세스 붙잡을 필요 **없음** → 사흘 뒤 응답도 OK (단, 영속 체크포인터일 때)
- 재개하면 노드는 **처음부터** → `interrupt` 앞에 부작용 금지
