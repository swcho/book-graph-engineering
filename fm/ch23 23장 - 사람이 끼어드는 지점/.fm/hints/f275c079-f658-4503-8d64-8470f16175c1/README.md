# 상태 지문(state_hash)이 다르면?

**질문**: 상태 지문이 다르면 어떻게 해야 하고, 무엇을 주의해야 하는가?

**답**: 다시 물어야 한다. 다만 결정에 영향을 주는 필드만 해시해야 하며, 매번 다시 물으면 사람이 확인 없이 누르기 시작한다.

---

## 1. 상태 지문이란 무엇인가

23.5절 「무엇을 보여 줬는지 남긴다」의 핵심 장치다. 승인 기록 테이블(`ex5_audit.py`)에는 결정만 남기지 않는다.

```sql
CREATE TABLE approval (
  ...
  shown        TEXT NOT NULL,   -- 사람에게 «실제로 보여 준» 내용
  state_hash   TEXT NOT NULL    -- 그 순간의 상태 지문
);
```

두 칸이 짝을 이룬다.

| 칸 | 무엇을 답하는가 |
|---|---|
| `shown` | 「담당자가 그때 화면에서 무엇을 보고 있었나」 |
| `state_hash` | 「그때의 상태와 지금의 상태가 같은가」 |

`shown`은 **과거를 해명**하는 칸이고, `state_hash`는 **현재를 검증**하는 칸이다.

## 2. 왜 다시 물어야 하는가 — 시간 격차

23장의 구조상 사람은 프로세스를 붙잡지 않는다. `interrupt()`로 멈춘 자리는 체크포인터에 남고, 서버를 재시작해도 그 자리에 있다. `ex1_interrupt.py`의 주석이 그 점을 강조한다.

> 상태가 체크포인터에 저장돼 있으니, 서버를 재시작해도 그 자리에 있다.
> 사람이 사흘 뒤에 답해도 이어서 간다.

이 장점이 그대로 위험이 된다. **승인한 시점과 실행하는 시점 사이에 며칠이 벌어질 수 있다.** 그 사이에 상태가 바뀌면 「사람이 승인한 것」과 「지금 실행하려는 것」이 다른 일이 된다.

```
09:02  물음 제시   금액 300,000 / 미개봉 / 첫 환불   → state_hash = a91c
                   ...사흘 경과, 그동안 금액 정정·환불 이력 갱신...
(3일 뒤) 재개      현재 상태 해시 = 4f21   ≠ a91c
```

`ex5_audit.py` 마지막 문단이 결론이다.

> `state_hash`는 그 순간의 상태 지문이다.
> 재개할 때 지문이 다르면 «승인한 그 내용»과 «지금 실행할 내용»이 다른 것이다.
> 그러면 다시 물어야 한다. 사흘 전 승인으로 오늘 4,200,000원을 내보내면 안 된다.

기록상 `A-1050`은 4,200,000원짜리 미응답 건이다(`ex4_no_answer.py`에서 121시간 대기 중인 그 건). 오래 묶여 있는 건일수록 지문이 어긋날 확률이 높고, 금액도 크다. 재확인이 가장 필요한 지점에 정확히 겹친다.

동작을 흐름으로 쓰면 이렇다.

```
재개(Command(resume=답))
  ↓
현재 상태에서 지문 재계산
  ↓
승인 시점 지문과 같은가?
  ├─ 같다  → 그대로 실행
  └─ 다르다 → 승인 무효화, 바뀐 내용을 붙여서 다시 interrupt
```

## 3. 첫 번째 주의: 「결정에 영향을 주는 필드만」 해시한다

상태 전체를 해시하면 지문이 **거의 항상** 달라진다. 그래프 상태에는 결정과 무관한 값이 잔뜩 섞여 있기 때문이다.

| 해시에 넣어야 하는 것 | 넣으면 안 되는 것 |
|---|---|
| 금액 | 마지막 갱신 시각 |
| 개봉 여부 | 재시도 횟수 |
| 환불 회차 | 로그·추적 ID, 트레이스 스팬 |
| 수취 계좌·대상 | 캐시된 중간 결과 |
| 승인 근거가 된 판단 필드 | 진행률, 내부 카운터 |

기준은 하나다. **그 값이 달랐다면 담당자가 다른 결정을 내렸겠는가?** 그렇다면 해시에 넣고, 아니면 뺀다.

`ex5_audit.py`의 `shown` 칸이 그대로 힌트가 된다. `"금액 300,000 / 미개봉 / 첫 환불"` — 사람에게 보여 준 그 세 필드가 곧 결정에 영향을 주는 필드다. 보여 준 것과 해시하는 것을 일치시키면 「보여 준 게 안 바뀌었으면 다시 안 묻는다」는 규칙이 자연스럽게 성립한다.

## 4. 두 번째 주의: 매번 다시 물으면 아무도 확인하지 않는다

해시 범위를 넓게 잡아 재확인이 남발되면, 23.3절에서 다룬 실패 방식이 그대로 재현된다.

`ex3_gate_policy.py`가 「전부 사람」 정책에 대해 내린 진단이다.

> 밀린 건이 쌓이고, 담당자가 대충 보기 시작하고, 결국 «전부 자동»과 같아진다.
> 이게 제일 나쁜 결말이다. 사람을 갈아 넣고 효과는 0인 상태.

재확인 팝업도 똑같다. 매번 뜨면 담당자는 내용을 읽지 않고 승인 버튼을 누르는 손동작만 학습한다. 확인 절차는 남아 있는데 확인은 사라진다 — 감사에는 통과하지만 실제로는 아무 방어도 하지 않는 상태, 즉 경보 피로(alert fatigue)다.

그래서 지문 검사는 **양날의 칼**이다.

| 해시 범위 | 결과 |
|---|---|
| 너무 넓다 | 매번 재확인 → 사람이 읽지 않고 누름 → 검사 무력화 |
| 너무 좁다 | 중요한 변화를 놓침 → 사흘 전 승인으로 오늘 4,200,000원이 나감 |
| 딱 맞다 | 재확인이 드물게 뜨고, 뜨면 사람이 실제로 읽는다 |

「드물게 뜨는 것」 자체가 이 장치의 신호 가치다. 자주 뜨는 경고는 경고가 아니다.

## 5. 재확인 화면에 무엇을 담을 것인가

다시 물을 때 처음과 똑같은 화면을 띄우면 사람은 차이를 알 수 없다. **무엇이 바뀌었는지**를 보여 줘야 재확인이 재확인 구실을 한다.

```
[다시 확인이 필요합니다]
  승인 당시(2026-03-14 09:05, kim)  금액 300,000 / 미개봉 / 첫 환불
  현재                              금액 300,000 / 미개봉 / 3회차 환불
                                                            ^^^^^^^^ 변경
```

그리고 이 재확인 자체도 새로운 승인 기록 한 줄이 된다. `asked_at`, `shown`, `state_hash`를 새로 적어 넣는다. 그래야 사후에 「어떤 화면을 보고 최종 결정했는가」를 되짚을 수 있다.

`ex5_audit.py`가 든 실제 사례가 이 필요성을 보여 준다.

> 실제로 저희는 이걸로 한 번 갈렸다. 승인은 났는데 사고가 났고,
> 화면에 «3회차 환불»이 안 떠 있었다는 게 기록으로 남아 있었다.
> 담당자 잘못이 아니라 화면 잘못이었다.

## 6. 구현 시 함께 챙길 것

- **부작용 위치**: 지문 불일치로 다시 `interrupt()`를 호출하면 그 노드는 처음부터 다시 돈다(`ex2_node_reruns.py`). 지문 계산은 읽기만 하므로 앞에 둬도 되지만, 알림 발송 같은 부작용은 `interrupt()` 뒤로 밀거나 노드를 쪼개야 한다.
- **해시 입력의 정규화**: 딕셔너리 키 순서, 숫자 타입, 공백 때문에 값이 같은데 해시가 달라지면 안 된다. 정렬된 직렬화(`json.dumps(..., sort_keys=True)`)를 거친 뒤 해시한다.
- **해시 정의 자체의 버전**: 「어떤 필드를 해시하는가」를 바꾸면 과거 기록과 비교가 깨진다. 해시 정의에 버전 태그를 붙여 함께 저장한다.
- **운영 체크포인터**: 메모리 체크포인터로는 사흘 뒤 응답을 받을 수 없다. 21장에서 본 디스크 기반 체크포인터를 쓴다.

## 7. 한 줄 정리

지문이 다르면 승인을 무효로 보고 다시 묻는다. 단, **결정을 바꿀 수 있는 필드만** 지문에 넣어야 한다. 범위를 넓게 잡아 매번 다시 물으면 사람이 읽지 않고 누르기 시작하고, 그 순간 확인 절차는 형식만 남는다.
