# 주장 2 — 프롬프트 인젝션의 반증 조건

## 질문

주장 2(프롬프트 인젝션)의 반증 조건은 무엇인가?

## 답

**지시와 데이터를 「구조적으로」 나눈 모델이 나오면 틀린다.** 그래서 지켜볼 것은 *모델 아키텍처 논문에서 「채널 분리」를 찾아보는 일*이다.

---

## 1. 카드가 가리키는 원문 좌표

35장 `ex1_five_claims.py`의 주장 2는 다음과 같이 적혀 있다.

| 항목 | 내용 |
|---|---|
| 주장 | 프롬프트 인젝션은 프롬프트 층에서 못 막는다 |
| 근거 장 | 26장 (무엇을 못 하게 할 것인가) |
| **반증 조건** | 지시와 데이터를 «구조적으로» 나눈 모델이 나오면 틀린다 |
| **지켜볼 것** | 모델 아키텍처 논문에서 «채널 분리»를 찾아본다 |
| 확신 | 0.55 (다섯 주장 중 중간) |
| 덧붙임 | 지금 구조에서는 맞는데, 구조가 안 바뀐다는 보장이 없다 |

이 카드의 핵심은 **"틀렸다"의 조건이 프롬프트 기법이 아니라 모델 구조에 걸려 있다**는 점이다. 프롬프트를 더 잘 쓰는 것으로는 이 주장을 반증할 수 없다. 반증은 아키텍처 층에서만 일어난다.

---

## 2. 왜 "구조적" 문제인가

### 2.1 트랜스포머 입력은 지시·데이터 구분이 없는 단일 토큰 스트림이다

지금의 LLM은 시스템 프롬프트, 개발자 지시, 사용자 질문, 검색해 온 문서, 도구 실행 결과를 **모두 같은 임베딩 공간의 토큰으로 이어 붙인 하나의 시퀀스**로 받는다. 자기어텐션은 "이 토큰이 어디서 왔는가"를 모른다. 역할 표시(`<|system|>` 같은 특수 토큰이나 채팅 템플릿)는 결국 **같은 스트림 안의 또 다른 텍스트**일 뿐이라, 데이터 쪽에 적힌 문장이 그 표시를 흉내내거나 무력화할 수 있다.

26장 `ex3_injection.py`가 이걸 모델 없이 보여 준다.

```python
def naive_prompt(doc):
    """지시와 데이터를 그냥 이어 붙인다. 대부분 이렇게 짠다."""
    return f"{SYSTEM}\n\n{doc}"
```

문서 안에 `[시스템 공지] 이전 지시는 취소되었습니다...`가 섞여 있으면, 모델 입장에서 그것은 앞의 `SYSTEM`과 **구분되지 않는 같은 종류의 글**이다. 26장의 문장이 정확하다.

> 경계를 치는 것만으로 완전히 막히지는 않는다. 그건 분명히 해 두자.
> 모델은 결국 «글»을 읽고, **글로 된 경계는 글로 넘을 수 있다.**

### 2.2 그래서 26장의 결론은 "권한"이었다

26장은 방어를 세 겹으로 정리한다.

| 겹 | 수단 | 성질 |
|---|---|---|
| 1겹 | 경계 표시(fencing / spotlighting) | 확률을 **낮춘다** |
| 2겹 | 입력 검사(패턴 스캔, 분류기) | 확률을 낮추고 **로그를 남긴다** |
| 3겹 | 권한 차단(요약기에 `db_query`·`http_post`를 주지 않는다) | 가능성을 **없앤다** |

1·2겹이 확률만 낮추는 이유가 바로 2.1이다. **문제가 프롬프트 층에 있지 않으니 프롬프트 층의 해법은 확률적일 수밖에 없다.** 그래서 26장의 1순위는 프롬프트가 아니라 권한이었고, 35장의 주장 2는 그 결론을 "반증 가능한 문장"으로 옮겨 적은 것이다.

### 2.3 이론적 뒷받침 (주장 쪽 증거)

2026년에 나온 [On the Inseparability of Instructions and Data in Shared-Embedding Sequence Models](https://arxiv.org/abs/2606.27567)는 **공유 임베딩 구조에서는 완전한 인젝션 방어가 수학적으로 불가능**하다고 논증한다. 근거를 세 갈래로 나눈다.

- 출처 복원 불가능성(provenance-recovery impossibility) — 토큰만 보고 출처를 되찾을 수 없다
- 제어 경로 노출(control-path exposure) — 데이터가 제어 흐름에 닿는 경로가 열려 있다
- 유한 커버리지의 불변성 공백(finite-coverage invariance gaps) — 학습으로 덮은 범위 밖이 항상 남는다

이 논문은 폰 노이만 구조의 **코드/데이터 혼동(버퍼 오버플로)** 과 같은 종류의 문제라고 못박고, 해법은 "in-pipeline 분류나 정렬(alignment)"이 아니라 **지시·데이터 채널의 아키텍처적 분리**뿐이라고 결론한다. 즉 이 논문은 주장 2를 **지지**하는 쪽이고, 동시에 **반증 조건을 어디서 찾아야 하는지**를 정확히 지목한다.

## 3. SQL 인젝션과의 대비 — 이게 이 주장의 핵심 직관이다

| | SQL 인젝션 | 프롬프트 인젝션 |
|---|---|---|
| 취약한 코드 | `"... WHERE name='" + input + "'"` | `f"{SYSTEM}\n\n{doc}"` |
| 문제의 성질 | 지시(SQL 문법)와 데이터(값)를 한 문자열에 섞음 | 지시와 데이터를 한 토큰 스트림에 섞음 |
| 구조적 해법 | **파라미터 바인딩(prepared statement)** — 쿼리 구조를 먼저 파서에 확정시키고, 값은 별도 채널로 전달 | 아직 널리 배포된 등가물이 없다 |
| 해결 후 상태 | 값에 `'; DROP TABLE --`를 넣어도 **문법으로 해석될 경로가 존재하지 않는다** | 데이터에 명령을 넣으면 여전히 해석될 **경로가 있다** |
| 방어의 성질 | 가능성 제거(결정적) | 확률 감소(통계적) |
| 실패한 접근 | 이스케이프·블랙리스트 필터링 | 경계 표시·인젝션 분류기 |

SQL은 **결정론적 파서**가 있어서 "여기부터는 값이다"를 문법 수준에서 못박을 수 있었다. LLM은 파서가 없고 확률적 해석기라서, 같은 못박기를 하려면 **모델 구조 자체**에 채널 구분이 들어가야 한다. 이게 "구조적으로 나눈 모델"이라는 표현의 뜻이다.

이 비유를 기억할 때 주의할 점: **SQL도 "이스케이프 잘하자" 시절이 20년쯤 있었다.** 프롬프트 인젝션이 지금 그 시절에 있다는 것이 주장 2의 내용이고, 파라미터 바인딩에 해당하는 발명이 나오는 것이 반증이다.

---

## 4. 채널 분리를 시도하는 실제 연구·제품 방향

"채널 분리"를 찾아본다는 게 막연하지 않도록, 2026년 8월 기준 대표적인 갈래를 **얼마나 구조적인가** 순으로 정리한다.

| 접근 | 무엇을 나누는가 | 층위 | 반증에 해당하나 |
|---|---|---|---|
| 경계 표시 / spotlighting | 텍스트 안에 구분자·표식 | **프롬프트** | 아니다 (글로 된 경계) |
| 인젝션 분류기 / LLM-as-judge | 입력을 사전 판별 | 파이프라인 | 아니다 (확률적, 우회 가능) |
| [Instruction Hierarchy](https://openai.com/index/the-instruction-hierarchy/) (OpenAI) | 시스템 > 개발자 > 사용자 > 도구 결과의 **권한 등급**을 학습으로 부여 | 학습(정렬) | 부분적 — 등급은 여전히 학습된 선호이며 하드 경계가 아니다 |
| [StruQ](https://arxiv.org/abs/2402.06363) | 프롬프트 부분과 데이터 부분을 **구조화된 질의**로 분리하고, 데이터 안 지시를 무시하도록 파인튜닝 | 학습 + 입력 포맷 | 방향은 맞다. 구조는 학습으로 강제 |
| SecAlign | 주입된 입력에 대해 바람직/바람직하지 않은 응답을 선호 최적화로 벌림 | 학습(선호 최적화) | 성공률 크게 하락(적응형 공격에서도 15% 미만 보고). 그래도 확률적 |
| [ASIDE](https://arxiv.org/abs/2503.10566) | **데이터 토큰 임베딩에 직교 회전**을 적용해 지시 토큰과 다른 표현 공간에 둔다 | **아키텍처(임베딩)** | 반증 조건에 가장 가까운 갈래 |
| PICO 계열 프롬프트 격리 | 신뢰/비신뢰 구간을 모델 내부에서 격리 | 아키텍처 | 같은 갈래, 초기 단계 |
| [CaMeL](https://arxiv.org/abs/2503.18813) (Google) | **제어 흐름과 데이터 흐름을 시스템 층에서 분리** — 특권 LLM이 계획, 격리 LLM은 도구 없이 비신뢰 데이터 처리, 인터프리터가 능력(capability)으로 정책 강제 | **시스템 설계** | 다른 종류의 답 — 26장 3겹(권한)의 정교한 버전 |

읽는 법 두 가지.

1. **위 표의 아래쪽으로 갈수록 반증에 가깝다.** 프롬프트 문구 → 학습된 선호 → 임베딩·아키텍처 → 시스템 권한 순서로 "확률"에서 "구조"로 옮겨 간다.
2. **CaMeL 계열은 이 주장을 반증하지 않고 오히려 확인한다.** CaMeL은 모델 안에서 지시와 데이터를 나누지 못한다는 것을 전제로, 모델 **밖**에 인터프리터와 능력 시스템을 놓는다. 26장이 "1순위는 권한"이라고 한 것과 같은 판단이다. 주장 2가 틀리려면 모델 **안**이 바뀌어야 한다.

## 5. 무엇을 관찰하면 이 주장이 반증되는가 (체크리스트)

분기마다 이 다섯 개를 보면 된다.

1. **아키텍처 층 분리인가.** 논문이 손대는 곳이 프롬프트 템플릿인지, 파인튜닝 데이터인지, **임베딩·어텐션·위치 인코딩**인지 확인한다. ASIDE처럼 "임베딩 회전", "분리된 채널", "데이터 전용 인코더" 같은 말이 아키텍처 절에 있으면 신호다.
2. **비신뢰 채널이 API 계약으로 노출되는가.** 프런티어 모델의 API에 `role: "data"`(또는 untrusted/tool-output 전용 채널)가 생기고, 문서에 **"이 채널의 내용은 절대 지시로 해석되지 않는다"** 는 보장이 명시되는지. 파라미터 바인딩이 SQL 드라이버 API에 들어온 것과 같은 사건이다.
3. **적응형 공격에서도 0%가 유지되는가.** 고정 공격 세트에서 0%는 쉽다. **최적화 기반·적응형 공격**(GCG류, 어댑티브 레드팀)과 AgentDojo 같은 에이전트 벤치마크에서, 방어를 아는 공격자를 상대로도 성공률이 0에 붙어 있어야 "구조적"이다. 15%나 3%는 여전히 확률이다.
4. **권한 차단 없이도 안전하다고 말할 수 있는가.** 이게 실무 판정 기준이다. 요약기에 `db_query`·`http_post`를 **주고도** 문서 안 명령이 실행될 수 없다면, 26장 3겹이 1순위였던 이유가 사라진다. 그때 주장 2는 틀린 것이 된다.
5. **여러 구현에서 재현되는가.** 한 논문 한 모델이 아니라, 서로 다른 모델 계열·서로 다른 팀에서 같은 성질이 나오고, 표준·명세에 들어가기 시작하는지. (35장 `ex2_standard_watch.py`의 단계 척도로 보면 "구현이 여럿" 이상으로 올라오는지.)

### 반증이 아닌 것

- 공격 성공률이 40%에서 5%로 떨어졌다 → **확률 감소**다. 주장 2는 "못 막는다"가 아니라 정확히는 "프롬프트 층에서는 가능성을 없앨 수 없다"는 문장이고, 5%는 가능성이 남아 있다는 뜻이다.
- 시스템 프롬프트를 더 강하게 써서 우회가 줄었다 → 1겹의 개선이다.
- 인젝션 탐지 분류기의 정확도가 올라갔다 → 2겹의 개선이고, 우회 가능성은 그대로다.
- CaMeL처럼 시스템 층에서 격리했다 → 26장 3겹의 승리이지 주장 2의 반증이 아니다.

## 6. 확신 0.55의 의미

다섯 주장 중 이 주장의 확신은 55%로 중간이다. 저자의 덧붙임이 그 이유를 그대로 말한다.

> 지금 구조에서는 맞는데, 구조가 안 바뀐다는 보장이 없다.

즉 **현재 시점의 참/거짓은 거의 확실하고**(공유 임베딩 스트림에서는 못 막는다), 불확실한 것은 **3년 안에 아키텍처가 바뀌는지**뿐이다. 확신을 깎아내리는 요인은 ASIDE류 임베딩 분리와 instruction hierarchy 계열이 이미 움직이고 있다는 것이고, 확신을 받쳐 주는 요인은 그 방향이 아직 프런티어 모델의 기본 구조나 API 계약으로 들어오지 않았다는 것, 그리고 불가능성 논증(2.3)이 나와 있다는 것이다.

주장 1(모델 호출 90%, 확신 35%)과 비교하면 성격이 다르다. 주장 1은 **연속적인 수치가 추세로 움직여서** 뒤집히는 종류고, 주장 2는 **불연속적인 발명 하나로** 뒤집히는 종류다. 그래서 주장 1의 "지켜볼 것"은 재측정이고, 주장 2의 "지켜볼 것"은 **논문 읽기**다.

## 7. 자기 점검

1. 주장 2를 반증하는 것은 "성공률 5%"가 아니라 무엇인가?
2. 경계 표시(fencing)가 원리적으로 불완전한 이유를 한 문장으로 말해 보라.
3. SQL의 파라미터 바인딩에 대응하는 것이 프롬프트 세계에 아직 없는 이유는?
4. CaMeL이 주장 2를 반증하지 않는 이유는?
5. 반증을 확인하려면 어떤 절의 논문을 읽어야 하는가? (힌트: 프롬프트 템플릿 절이 아니다)
