# [실험] 네 항목의 평균 단계 = 0.5 / 4

## 질문과 답

**질문** [실험]으로 분류된 네 항목의 평균 단계는 얼마인가?

**답** 4점 만점에 **0.5**다. 항목은 **에이전트 간 프로토콜, 에이전트 그래프 위상 이론, 그래프 기반 장기 기억, 자기수정 온톨로지** 넷이다.

---

## 1. 숫자가 어디서 나오나

출처는 35장 `code/ex2_standard_watch.py`다. 이 예제는 책에서 상태 라벨을 붙인 항목 12개를 "성숙도 단계" 0~4로 매기고, 라벨별로 세어 본다.

단계 축은 이렇게 정의돼 있다.

```
0 아이디어 → 1 구현이 여럿 → 2 명세 초안 → 3 공식 명세 → 4 널리 채택
```

[실험] 라벨이 붙은 항목만 뽑으면 넷이고, 단계는 이렇다.

| 항목 | 단계 | 왜 그 단계인가 | 지켜볼 신호 |
|---|:--:|---|---|
| 에이전트 간 프로토콜 | **1** | 돌아가는 구현이 여러 개 있다. 그런데 서로 말이 통하지는 않는다 | 구현이 둘 이상 상호운용되는지 |
| 에이전트 그래프 위상 이론 | **0** | 아이디어 단계. 공통 용어조차 없다 | 논문에 공통 용어가 생기는지 |
| 그래프 기반 장기 기억 | **1** | 구현은 여럿(Zep, Mem0 계열 등). 비교 기준이 아직 헐겁다 | 벤치마크가 생기는지 |
| 자기수정 온톨로지 | **0** | 논문은 있는데 운영 사례가 없다 | 운영 사례가 공개되는지 |

계산은 그냥 산술 평균이다.

```
(1 + 0 + 1 + 0) / 4 = 0.5
```

예제 코드에서 이 부분을 뽑는 로직이 아래 두 줄이다. 숫자를 외우기보다 **"[실험] 넷만 골라 평균"** 이라는 구조를 기억하는 게 낫다.

```python
exp = [i for i in ITEMS if i[2] == "실험"]
print(f"\n[실험] {len(exp)}개의 평균 단계: "
      f"{sum(i[1] for i in exp) / len(exp):.1f} / 4")
```

비교용으로, 같은 표에서 [표준] 다섯(RDF·OWL·SHACL 4, SPARQL 1.1 4, ISO GQL 3, SQL/PGQ 3, PROV-O 4)의 평균은 3.6이다. 0.5 대 3.6. 이 격차가 표의 요점이고, 저자가 "**두 트랙의 성숙도가 20년쯤 차이 난다**"고 쓴 근거다.

## 2. 네 항목이 각각 풀려는 문제

### (1) 에이전트 간 프로토콜 — 단계 1

**문제** 서로 다른 회사·프레임워크가 만든 에이전트가 어떻게 상대를 발견하고, 작업을 넘기고, 결과를 되받는가. 사람 없이. 서로 코드를 공유하지 않고.

**왜 1인가** "구현이 여럿"은 명백하다. 문제는 "명세 초안"(단계 2)에 필요한 조건 — *다른 팀이 만든 두 구현이 실제로 상호운용된다* — 이 아직 예외적이라는 것이다. 데모는 되고, 프로덕션에서 이종 벤더 간 위임은 드물다.

**2026년 8월 현재 실제 상황** (웹 확인)

- **MCP**는 이 표에서 [업계 표준]/단계 2로 따로 분류돼 있다. 프로토콜이지만 **에이전트↔도구** 축이라, **에이전트↔에이전트** 축과는 다른 문제를 푼다. 버전 이력은 `2024-11-05 → 2025-03-26 → 2025-06-18 → 2025-11-25 → 2026-07-28`로, 날짜 스탬프 방식이며 파괴적 변경을 여러 번 냈다. 2025년 12월 Anthropic이 Linux Foundation 산하 Agentic AI Foundation에 기부했다. 즉 거버넌스는 중립화됐지만 **명세는 아직 흔들린다** — 책이 적어 둔 "명세 버전이 얼마나 자주 바뀌는지"가 정확히 이 신호다.
- **A2A(Agent2Agent)**는 에이전트↔에이전트 축이다. 2025년 6월 Google이 Linux Foundation에 기부, 2026년 5월 v1.0.1(확장 메커니즘 추가), 2026년 4월 1주년 기준 150개 이상 조직 참여, Google·Microsoft·AWS 플랫폼 통합, 일부 산업(공급망·금융·보험·ITOps)에서 프로덕션 사례.

**해석 주의** A2A의 위 사실만 보면 단계 1보다 높게 볼 여지가 있다. 버전이 1.0.1로 찍혔고 재단이 관리하니 "명세 초안"(2)이나 그 위로 볼 수도 있다. 다만 단계 축의 기준은 *스펙 문서의 존재*가 아니라 **상호운용 실적**이고, "150개 조직이 지지 선언"과 "이종 구현 둘이 실제로 붙어서 돈다"는 다른 얘기다. 저자가 1을 준 건 후자 기준으로 보수적으로 잡은 것으로 읽힌다. 이 부분이 라벨 이의를 낼 만한 지점이며, 실제로 35장 끝에 "상태 라벨이 어긋났다면 라벨 이의로" 적어 달라는 링크가 있다. 시험 답으로는 책 값 **1**을 쓰고, 근거를 갖고 이견을 붙이는 게 이 장의 취지에 맞다.

### (2) 에이전트 그래프 위상 이론 — 단계 0

**문제** 에이전트를 여러 개 붙였을 때의 연결 구조(파이프라인, 팬아웃, 감독자-작업자, 순환, 합류)가 지연·비용·실패 확산에 어떤 영향을 주는가를 *구조 자체의 성질*로 예측하는 이론. 25장 팬아웃 이득 천장(1.57배) 같은 값이 왜 그 값인지를 사례 측정 없이 말할 수 있게 하는 것.

**왜 0인가** 구현은 널려 있다(모든 멀티에이전트 프레임워크가 사실상 위상을 정의한다). 그런데 **같은 것을 같은 이름으로 부르지 않는다**. "supervisor", "orchestrator", "router", "planner"가 논문마다 다른 것을 뜻한다. 공통 용어가 없으면 결과를 누적할 수 없고, 누적이 없으면 이론이 안 된다. 그래서 "구현이 여럿"(1)조차 주지 않고 0이다.

**지켜볼 신호** 논문에 공통 용어가 생기는지. 구체적으로는 서로 다른 그룹의 논문 두 편이 *같은 위상에 같은 이름*을 쓰고 서로를 인용하기 시작하는 순간.

### (3) 그래프 기반 장기 기억 — 단계 1

**문제** 에이전트가 세션을 넘어 기억하는 것을 벡터 뭉치가 아니라 그래프(엔티티·관계·시간)로 두면 무엇이 나아지는가. 특히 **갱신**("작년엔 A팀이었는데 지금은 B팀")과 **다중 홉 회상**을 벡터 유사도로 처리할 때 생기는 문제.

**왜 1인가** 돌아가는 구현이 여럿이다. 시간 지식 그래프 기반 Zep, 요약·추출 기반 Mem0 등. 실제로 붙여 쓰는 팀도 있다. 그런데 **"그래프가 더 낫다"를 결판낼 공통 잣대가 아직 정착 중**이다. LoCoMo, LongMemEval, BEAM 같은 벤치마크가 돌기 시작했고 수치도 나온다(대략 LoCoMo 90%대, LongMemEval 90%대에서 시스템들이 몰려 있음). 다만 정확도 축만 보면 서로 근접하고, **검색당 토큰 사용량**처럼 축을 하나 더 넣으면 순위가 크게 뒤집힌다는 보고가 있다(같은 비교에서 그래프 계열의 대화당 메모리 풋프린트가 수십만 토큰 대, 요약 계열이 수천 토큰 대로 보고된 사례). 즉 벤치마크는 생겼지만 **"무엇을 재야 공정한가"가 합의되지 않았다** — 명세 초안 수준의 합의는 아니라 1이 맞다.

**지켜볼 신호** 벤치마크가 생기는지. 2026년 기준으로는 **"생기는지"에서 "정확도 말고 무엇을 같이 재기로 합의했는지"로 질문을 옮겨야 하는 시점**이다. 정확도·지연·토큰·저장 비용을 한 표에 놓는 관행이 자리 잡으면 단계 2로 올릴 만하다.

### (4) 자기수정 온톨로지 — 단계 0

**문제** 스키마(온톨로지)를 사람이 고치지 않고, 시스템이 들어오는 데이터를 보고 스스로 고치게 하기. 새 관계 종류를 추가하고, 잘못 잡은 계층을 정리하고, 안 쓰이는 클래스를 접는 일.

**왜 0인가** 논문은 있다(35장 키워드 표의 `self-refining ontology`, arXiv 2404.13501). LLM 기반 온톨로지 구축·정제, 규칙으로 내부 불일치를 잡는 접근, SHACL/OWL로 검증하고 그래프를 계속 갱신하는 파이프라인 등이 계속 나온다. 그런데 **"우리는 이걸 운영에 넣어서 N개월 돌렸고 이렇게 됐다"는 공개 사례가 없다.** 32장(스키마 변경)과 28장(관문)의 논지대로, 스키마를 자동으로 고치면 되돌리기가 어렵고 의미가 조용히 바뀐다. 그래서 아무도 프로덕션에 안 넣고, 사례가 없으니 아이디어 단계에 머문다.

**지켜볼 신호** 운영 사례가 공개되는지. 특히 **롤백 얘기가 같이 나오는 사례**. 자동 변경을 자랑하는 글은 이미 많고, 되돌린 얘기가 있는 글이 신호다.

## 3. 평균 0.5가 실무적으로 뜻하는 것

이 숫자는 트리비아가 아니라 **의사결정 규칙**이다. 세 가지로 번역된다.

### (a) 직접 만들어야 한다

평균 0.5는 "이 영역에는 당신을 대신해 결정해 줄 명세가 없다"는 뜻이다. 트랙 1(RDF·SPARQL·GQL·PROV-O, 평균 3.6)에서는 "명세를 읽고 그대로 하면 된다"가 성립하고, 그래서 3부를 「이렇게 하면 된다」로 쓸 수 있었다. 트랙 2에서는 성립하지 않아서 4부가 「저는 이렇게 하는데 확신은 없습니다」가 됐다. 여러분의 코드베이스에서도 같은 비대칭이 나타난다. 에이전트 위상, 기억 구조, 스키마 진화는 **여러분이 설계하고 여러분이 책임지는 부분**이다.

### (b) 표준에 기대면 안 된다

기대는 두 방향으로 잘못된다.

- **기다리기** "곧 표준 나올 텐데 그때 하자" → 단계 0~1에서 단계 3까지는 보통 수년이다. 기다리면 그 기간 동안 아무것도 못 한다.
- **미리 결혼하기** 아직 흔들리는 명세에 아키텍처를 깊게 묶는 것 → MCP만 봐도 파괴적 변경이 여러 번 났다. 단계 2도 이렇다면 단계 0~1은 더하다.

실무적 타협은 **경계를 얇게 두기**다. 프로토콜·기억 저장소·스키마 진화 로직을 각각 어댑터 뒤에 두고, 갈아 끼울 수 있는 상태로 유지한다. 그러면 명세가 바뀌어도 바뀌는 곳이 한 파일이다.

### (c) 문서에 확신도를 같이 적어야 한다

35장 `ex1`이 주장마다 `confidence`를 붙인 것과 같은 이유다. 단계 0~1 영역의 설계 결정에는 "이건 이렇게 정했는데, 이 신호가 보이면 다시 본다"를 남긴다. 그 신호가 위 표의 "지켜볼 신호"다. 링크 하나 여는 데 5분, 그 5분이 "지금 이걸 도입해도 되나"의 답이 된다는 게 저자의 표현이다.

## 4. 자주 틀리는 지점

- **12개 전체의 평균과 헷갈리기** 0.5는 [실험] 넷만의 평균이다. 12개 전체 평균은 2.0(합 24 / 12)이다.
- **MCP를 [실험] 넷에 넣기** MCP는 [업계 표준]/단계 2로 별도다. GraphRAG 계열, Cypher 방언도 [업계 표준]이다. [실험]은 정확히 넷이다.
- **분모를 잘못 잡기** "4점 만점"의 4는 단계 축 상한(0~4)이고, 항목 수 4와 우연히 같다. 평균 계산의 분모는 항목 수 4, 만점 표기의 4는 단계 상한. 같은 숫자지만 다른 것이다.
- **네 항목 이름을 뭉개기** "에이전트 간 프로토콜"과 "에이전트 그래프 위상 이론"은 별개 항목이다. 앞은 상호운용, 뒤는 구조 이론.
- **0을 "아무것도 없다"로 읽기** 단계 0은 "아이디어"다. 논문도 프로토타입도 있다. 없는 것은 *여러 개의 실사용 구현*이다.

## 5. 한 줄 정리

[실험] 넷의 평균 단계 0.5는 "이 영역에는 기댈 명세가 없으니 직접 만들고, 대신 무엇을 보고 마음을 바꿀지 미리 적어 두라"는 지시로 읽어야 한다.
