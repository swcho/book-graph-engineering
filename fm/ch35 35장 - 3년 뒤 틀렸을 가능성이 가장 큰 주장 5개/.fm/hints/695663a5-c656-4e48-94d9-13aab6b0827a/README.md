# 하나만 다시 잰다면 — 33장의 지배 구간

**질문** 하나만 다시 재라면 무엇을 재야 하는가?

**답** 33장의 지배 구간이다. 재는 데 30분이면 되고 안 재면 3주를 쓴다.

---

## 1. 답을 한 줄로

35장은 「이 책의 숫자는 저자 환경의 것이니 여러분 환경에서 다시 재라」고 하면서 다시 재야 할 지표 **11개**를 표로 준다(`ex4_selfcheck.py`). 전부 재는 데 하루쯤 걸린다. 그런데 **하루가 없다면 딱 하나만 재라**고 말하고, 그 하나가 **33장의 「지배 구간」 — 응답 시간에서 모델 호출이 차지하는 비중**이다.

`ex4`의 마지막 문단이 그대로 답이다.

> 그리고 위에서 하나만 고르라면 «33장 지배 구간»이다.
> 이걸 안 재고 시작한 성능 작업은 대개 헛일이 된다.
> 재는 데 30분이면 되고, 안 재면 3주를 쓴다.

그리고 한 장 요약에도 같은 말이 있다.

> 이 책의 숫자는 자릿수와 방향으로만 쓰세요. 여러분 환경에서 다시 재는 데 하루면 됩니다. 하나만 고르라면 33장의 지배 구간입니다.

## 2. 「지배 구간(dominant segment)」이 무엇인가

한 요청의 처리 시간을 구간(segment)별로 쪼갰을 때, **혼자서 전체의 압도적 비중을 차지하는 구간**을 말한다. 33장 `ex5_where_time_goes.py`의 측정값이 교과서적인 예다.

| 구간 | 시간(ms) | 비중 | 최대 절감률 | 줄이면 |
|---|---:|---:|---:|---:|
| 입력 검증 | 3 | 0.2% | 0% | 0ms |
| 그래프 조회 ×4 | 9 | 0.5% | 50% | 4.5ms |
| 벡터 검색 | 11 | 0.6% | 40% | 4.4ms |
| 컨텍스트 조립 | 18 | 0.9% | 70% | 12.6ms |
| **모델 호출** | **1,820** | **94.8%** | 30% | 546ms |
| 응답 후처리 | 24 | 1.3% | 60% | 14.4ms |
| 체크포인트 쓰기 | 34 | 1.8% | 80% | 27.2ms |
| 합계 | 1,919 | 100% | — | — |

여기서 지배 구간은 「모델 호출」이고 비중은 **94.8%**다. 나머지 여섯 구간을 합쳐도 99ms, 5.2%밖에 안 된다.

핵심은 마지막 열이다. **모델 호출을 뺀 여섯 구간을 «각자 최대치까지» 다 줄여도 약 60ms, 전체의 3%다.** 1,919ms가 1,860ms가 된다. 사용자는 이 차이를 느끼지 못한다.

## 3. 왜 이 하나가 다른 모든 판단을 좌우하는가 — 암달의 법칙

이건 직관이 아니라 60년 된 정리다. 암달의 법칙(Amdahl's law, 1967)은 「전체 중 비율 `p`인 부분을 `s`배 빠르게 했을 때 전체 속도 향상」을 이렇게 준다.

```
전체 향상 = 1 / ( (1 - p) + p/s )
```

여기서 중요한 건 **극한**이다. 어떤 구간의 비중이 `p`일 때, 그 구간을 무한히 빠르게 해도(`s → ∞`) 얻을 수 있는 상한은

```
상한 = 1 / (1 - p)
```

33장의 숫자를 넣으면,

- 모델 호출 외 전부(`p = 0.052`)를 **완전히 0으로 만들어도** 상한은 `1/0.948 = 1.055`배. **최대 5.2% 개선.**
- 모델 호출(`p = 0.948`)을 2배 빠르게만 해도 `1/(0.052 + 0.474) = 1.90`배. **거의 2배.**

즉 **지배 구간의 비중 하나가 다른 모든 최적화의 «천장»을 정해 버린다.** 그래서 이 값을 모르면 어떤 최적화 후보에 대해서도 「해 볼 만한가」를 판단할 수 없다. 반대로 이 값 하나만 알면 나머지 10개 지표를 재기 전에도 후보 대부분을 걸러낼 수 있다. 다른 지표들은 「그 구간에서 얼마를 벌 수 있나」를 알려 주지만, 지배 구간은 「그 벌이가 애초에 의미가 있나」를 알려 준다. 층위가 다른 정보다.

이 논리 때문에 33장은 성능 작업 순서를 이렇게 못 박는다.

1. 모델 호출 **횟수**를 줄인다 — 캐시, 라우팅(25장), 종료 조건(20장)
2. 모델 호출 **시간**을 줄인다 — 짧은 프롬프트, 작은 모델, 스트리밍
3. **그다음에** 나머지를 본다

## 4. 30분 대 3주 — 비대칭은 어디서 오는가

### 왜 30분이면 되는가

측정이 싼 이유는 **필요한 정확도가 낮기 때문**이다.

- 알고 싶은 것은 「어느 구간이 지배적인가」라는 **순위와 자릿수**뿐이다. 94.8%인지 91%인지는 판단을 바꾸지 않는다. 5%인지 95%인지만 갈리면 된다.
- 그래서 분산 트레이싱도, 샘플링 인프라도 필요 없다. **주요 경계마다 시각을 찍어 차이를 로그에 남기는 것**이면 된다. 구간 일곱 개면 타임스탬프 여덟 개다.
- 요청 수십 건이면 답이 나온다. 지배 구간의 격차가 워낙 커서 노이즈에 강하다.
- 한 번 붙여 놓으면 이후 재측정은 공짜다. 35장이 「분기마다 다시 재라」고 할 수 있는 이유다.

정리하면 **비용이 한 번, 상한이 있고, 미리 알 수 있다.** 30분이라는 숫자가 나오는 근거다.

### 왜 안 재면 3주인가

안 재고 시작하면 사람들은 대개 **재기 쉽고 익숙하고 성과가 눈에 보이는 구간**을 고른다. 33장의 진단이 그것이다.

> 3번을 1번보다 먼저 하는 팀이 많다. 익숙하고, 재기 쉽고, 성과가 눈에 보여서다.
> 「쿼리를 9ms에서 4ms로 줄였습니다」는 보고하기 좋은 문장이다.
> 그런데 사용자는 1,919ms를 1,914ms로 줄인 것을 못 느낀다.

3주라는 값이 커지는 이유는 시간이 아니라 **피드백이 없다는 구조** 때문이다.

- **비용이 상한 없이 늘어난다.** 인덱스 설계, 쿼리 재작성, 캐시 계층 추가, 리뷰, 배포, 회귀 검증까지 한 사이클이 스프린트 단위로 붙는다.
- **작업 중에는 틀렸다는 신호가 오지 않는다.** 국소 지표는 계속 좋아진다. 쿼리는 실제로 2배 빨라졌다. 「일이 잘되고 있다」는 감각과 「일이 헛되다」는 사실이 동시에 성립한다.
- **끝까지 가야 드러난다.** 전체 지연을 보는 순간에야 3%임이 밝혀지고, 그때는 이미 3주가 지나 있다.
- 게다가 **되돌리기가 비싸다.** 추가한 인덱스와 캐시는 그 자체로 운영 부담과 정합성 문제를 남긴다. 헛일이 0으로 회수되지 않는다.

그래서 비대칭은 단순히 「30분 < 3주」가 아니다. **한쪽은 상한이 정해진 선불 비용이고, 다른 한쪽은 상한이 없고 사후에만 드러나는 손실**이다. 기대값을 따지면 30분을 안 쓸 이유가 없다. 이것이 관측(observability)을 최적화보다 먼저 두는 일반 원칙의 가장 선명한 사례다.

## 5. 놓치기 쉬운 두 가지

**(1) 「빠르게」와 「정확하게」는 다른 작업이다.** 지배 구간이 모델 호출이라고 해서 조회 최적화가 전부 무의미한 건 아니다. 조회를 **빠르게** 하는 것은 5% 구간 안의 일이지만, 조회를 **정확하게** 하면 모델 호출 «횟수»가 줄고 토큰이 줄어든다. 후자는 94.8% 구간에 직접 꽂힌다. 33장이 「쿼리를 빠르게 해도 비용은 그대로지만 정확하게 하면 토큰이 크게 준다」고 쓴 대목이고, 35장 `ex5`가 미해결로 남긴 「조회가 나빠서 모델을 한 번 더 부른 경우를 세는 법」이 바로 이 경로를 계량하는 문제다.

**(2) 지배 구간은 고정이 아니다.** 35장이 이 주장(1번 주장, 확신 **35%**)을 다섯 개 중 «제일 빨리 틀릴 것»으로 꼽은 이유가 여기 있다. 반증 조건은 「같은 작업의 모델 지연이 10분의 1이 되면 60% 아래로 내려간다」이고, 지켜볼 것은 「분기마다 구간별 시간을 다시 잰다」다. 모델이 빨라지면 지배 구간이 체크포인트 쓰기나 컨텍스트 조립으로 옮겨갈 수 있다. **한 번 재고 끝낼 값이 아니라 분기마다 갱신할 값**이다. 그래서 계측을 코드에 남겨 두는 것이 중요하다.

## 7. 한 줄 정리

지배 구간은 **다른 모든 성능 판단의 상한을 정하는 값**이고(암달의 법칙), 그 값을 얻는 비용은 **경계마다 시각을 찍는 30분**이며, 그 값을 모르고 시작한 최적화는 **작업이 끝날 때까지 틀렸다는 신호를 주지 않아 3주를 태운다.** 그래서 하나만 재라면 이것이다.
