# 커뮤니티 탐지에 '맞는 답'이 없는 이유

> **Q.** 커뮤니티 탐지에 '맞는 답'이 없는 이유는 무엇인가?
>
> **A.** 라벨 전파는 시드에 따라 흔들리고 모듈러리티는 해상도 한계로 작은 뭉치를 붙여 버린다. 개수는 알고리즘이 아니라 쓰임새로 정해야 한다.

---

## 한 줄로

커뮤니티 탐지는 「정답이 있는데 못 찾는 문제」가 아니라 **정답의 정의 자체가 없는 문제**입니다. 중심성처럼 "차수가 몇이냐"를 물으면 답이 하나로 정해지지만, "이 조직에 팀이 몇 개냐"는 질문은 무엇을 팀이라 부를지부터 사람이 정해야 합니다. 그래서 알고리즘마다, 실행마다 다른 답이 나옵니다.

---

## 1. 라벨 전파 — 빠른데 매번 흔들린다

### 어떻게 도는가

아이디어가 어이없을 만큼 단순합니다.

1. 모든 노드에 서로 다른 라벨을 하나씩 준다 (노드 20개면 라벨 20개)
2. 노드를 **무작위 순서로** 훑으면서, 각자 **이웃들 중 제일 많은 라벨**로 자기 라벨을 바꾼다
3. 아무도 안 바뀔 때까지 반복한다
4. 같은 라벨이 남은 노드들이 한 커뮤니티

10장 `ex4_communities.py`의 구현이 딱 이것입니다.

```python
def label_propagation(adj, seed=0, rounds=50):
    rnd = random.Random(seed)
    label = {v: i for i, v in enumerate(sorted(adj))}
    order = sorted(adj)
    for _ in range(rounds):
        rnd.shuffle(order)                       # ← 여기가 흔들림의 근원
        changed = False
        for v in order:
            if not adj[v]:
                continue
            cnt = Counter(label[u] for u in adj[v])
            best = max(cnt.items(), key=lambda x: (x[1], -x[0]))[0]
            if label[v] != best:
                label[v] = best; changed = True
        if not changed:
            break
```

시간 복잡도는 사실상 엣지 수에 선형(O(E) 근처)입니다. 커뮤니티 개수를 미리 알려줄 필요도 없습니다. 그래서 억 단위 엣지에서도 돌아갑니다.

### 왜 흔들리는가

문제는 `rnd.shuffle(order)` 한 줄입니다. **방문 순서가 결과를 바꿉니다.**

- 노드 A가 이웃 B보다 먼저 갱신되면 A가 B에게 라벨을 넘깁니다
- B가 먼저 갱신되면 반대 방향으로 넘어갑니다
- 이웃 라벨이 동점일 때 누구를 고르느냐도 임의입니다

즉 라벨 전파에는 **하나로 수렴하는 목적 함수가 없습니다.** 그냥 "아무도 안 바뀌는 상태"에 멈출 뿐이고, 그런 상태는 여러 개 존재합니다. 어느 것에 떨어지느냐는 시드가 정합니다.

예제를 시드 0, 1, 2로 세 번 돌려 보면 커뮤니티 **개수**부터, 크기 분포도, 모듈러리티 점수도 달라집니다.

```
라벨 전파 — 시드를 바꿔 세 번 돌린다
  seed=0: 커뮤니티 N개, 크기 [...], 모듈러리티 0.xxx
  seed=1: 커뮤니티 M개, 크기 [...], 모듈러리티 0.yyy
  seed=2: ...
```

극단적으로는 **그래프 전체가 라벨 하나로 뭉개지는** 경우도 있습니다. 연결이 촘촘한 그래프에서 라벨 전파가 자주 겪는 실패 모드예요.

### 실무에서의 대처

- **시드를 고정하고, 고정했다는 사실을 문서에 적는다.** 재현성이 없으면 "지난달 대비 커뮤니티가 3개 늘었습니다" 같은 보고를 못 씁니다. 늘어난 게 데이터 변화인지 시드 운인지 구분이 안 되니까요.
- 같은 논리가 9장/10장의 다른 근사 기법에도 적용됩니다. `ex3_betweenness_cost.py`도 표본 추출에 시드를 안 박으면 상위 순위가 매번 흔들린다고 못을 박아 둡니다.
- 여러 시드로 돌린 뒤 **합의(consensus) 클러스터링**을 하기도 합니다. "이 두 노드가 몇 번이나 같은 커뮤니티에 묶였나"를 세서 안정적인 코어만 남기는 방식이죠. 비용은 올라갑니다.

## 2. 모듈러리티 — 안정적인데 눈이 나쁘다

### 모듈러리티가 재는 것

모듈러리티 Q는 "이 분할이 **무작위 그래프였을 때 기대되는 것보다** 커뮤니티 안쪽 엣지를 얼마나 더 많이 갖고 있나"입니다.

```python
def modularity(adj, communities):
    m = sum(len(v) for v in adj.values()) / 2       # 전체 엣지 수
    q = 0.0
    for c in communities:
        s = set(c)
        lc = sum(1 for v in c for u in adj[v] if u in s) / 2   # 커뮤니티 내부 엣지
        dc = sum(len(adj[v]) for v in c)                        # 차수 합
        q += lc / m - (dc / (2 * m)) ** 2
    return q
```

수식으로는 이렇습니다.

> Q = Σ_c [ L_c / m − (d_c / 2m)² ]

- 앞항 `L_c/m`: 이 커뮤니티 안에 실제로 있는 엣지 비율 — **클수록 좋다**
- 뒷항 `(d_c/2m)²`: 차수만 보고 무작위로 이었을 때 기대되는 내부 엣지 비율 — **빼는 벌점**

Q가 높을수록 "무작위보다 확실히 뭉쳐 있다"는 뜻입니다. 라벨 전파와 달리 **명시적인 목적 함수가 있어서** 결과가 훨씬 안정적입니다. 예제의 `greedy_modularity()`는 노드 하나씩을 커뮤니티로 두고, Q가 제일 많이 오르는 쌍을 계속 병합합니다.

실무에서는 이 탐욕 병합 대신 **루뱅(Louvain)** 이나 **라이덴(Leiden)** 을 씁니다. 루뱅은 지역 이동 + 그래프 축약을 반복해 대규모에서도 빠르고, 라이덴은 루뱅이 만들어 내는 **끊어진(disconnected) 커뮤니티** 결함을 고치고 수렴 보장을 더한 개선판입니다.

### 그런데 해상도 한계가 있다

모듈러리티의 벌점항 `(d_c/2m)²`에는 **전체 엣지 수 m**이 들어 있습니다. 이게 문제의 뿌리입니다. 커뮤니티가 얼마나 잘 뭉쳤는지를 판단할 때, 그 커뮤니티 자체만 보는 게 아니라 **그래프 전체 크기와 비교**해 버립니다.

그래서 그래프가 커지면(m이 커지면) 작은 커뮤니티의 벌점이 상대적으로 사라지고, **작은 뭉치 두 개를 하나로 붙이는 쪽이 Q를 더 올립니다.** 실제 구조와 무관하게요.

이걸 **해상도 한계(resolution limit)** 라고 부릅니다. Fortunato–Barthélemy(PNAS 2007)가 정식화했고, 대략 **√(2m)** 보다 작은 커뮤니티는 모듈러리티 최대화로 안정적으로 분리되지 않는다고 알려져 있습니다.

### 예제로 확인하기

`ex5_resolution.py`가 이걸 가장 깔끔하게 보여 줍니다. **고리 모양으로 이어진 클리크들(ring of cliques)** 을 만듭니다.

```python
def ring_of_cliques(k, size):
    """크기 size 인 완전 그래프 k 개를 고리 모양으로 잇는다. 정답 커뮤니티 = k 개."""
    edges = []
    for c in range(k):
        base = c * size
        for i in range(size):
            for j in range(i + 1, size):
                edges.append((base + i, base + j))      # 뭉치 안은 완전 그래프
        edges.append((base, ((c + 1) % k) * size))      # 다음 뭉치와 다리 «하나»
    return edges
```

정답이 눈에 보입니다. 각 클리크가 커뮤니티 하나, 총 k개. 이보다 명백한 커뮤니티 구조는 없습니다. 그런데 「정답 = k개」와 「이웃끼리 둘씩 붙인 답 = k/2개」의 Q를 비교하면:

```
뭉치 크기 4, 고리 모양으로 이음

   뭉치 수      정답 Q    둘씩 붙인 Q     어느 쪽이 이기나
------------------------------------------------------
       4      0.xxxx       0.xxxx                 정답
       8      ...          ...                    정답
      16      ...          ...          붙인 쪽 (틀림)
      24      ...          ...          붙인 쪽 (틀림)
      32      ...          ...          붙인 쪽 (틀림)
```

뭉치 수가 늘어날수록 — 즉 그래프가 커질수록 — **틀린 답의 점수가 정답을 이깁니다.** 모듈러리티를 최대화하는 알고리즘은 성실하게 일할수록 틀린 답을 내놓게 됩니다.

> 이건 **버그가 아니라 지표의 성질**입니다. 구현을 고쳐도 안 사라집니다. 루뱅이든 라이덴이든 모듈러리티를 목적 함수로 쓰는 한 그대로 물려받습니다.

### 대처법과 그 한계

`ex5`가 제시하는 두 가지입니다.

**1) 해상도 매개변수 γ를 올린다**

```python
q += lc / m - gamma * (dc / (2 * m)) ** 2
```

벌점항에 γ를 곱합니다. γ가 크면 벌점이 커져서 **잘게** 나뉘고, 작으면 **크게** 뭉칩니다. 문제는 γ의 정답도 없다는 것. 실험으로 정해야 합니다. 해상도 한계를 **없애는** 게 아니라 **옮기는** 것뿐입니다.

**2) 계층적으로 다시 돌린다**

커뮤니티를 찾은 뒤, 각 커뮤니티를 독립 그래프로 보고 그 안에서 또 돌립니다. 부분 그래프에서는 m이 작아지니 해상도가 올라갑니다. 대신 **언제 멈출지**를 사람이 정해야 합니다.

두 대처 모두 「정답이 몇 개인지 모른다」는 근본 문제를 풀지 못합니다. 계층 어느 층을 고르느냐, γ를 얼마로 두느냐가 곧 "커뮤니티 개수를 사람이 정하는" 일이기 때문입니다.

## 3. 그래서 개수는 쓰임새로 정한다

두 알고리즘의 실패 방식이 **반대**라는 점이 핵심입니다.

| | 라벨 전파 | 모듈러리티 최적화 (루뱅/라이덴) |
|---|---|---|
| 목적 함수 | 없음 (지역 규칙만) | 있음 (Q 최대화) |
| 속도 | 매우 빠름 (≈ O(E)) | 느림 (탐욕 병합은 특히) |
| 재현성 | **시드마다 다름** | 시드 영향이 작음(루뱅은 약간 있음) |
| 커뮤니티 개수 | 매번 달라짐 | 안정적이지만 **해상도 한계로 과소 분할** |
| 대표 결함 | 결과가 흔들림, 전체 뭉개짐 | 작은 뭉치를 붙여 버림 |

"안정적인 쪽을 쓰면 되지 않나?"가 안 통합니다. 모듈러리티는 **안정적으로 틀립니다.** 어제도 오늘도 똑같이 작은 뭉치들을 붙여 놓고, 그게 정답인 양 보고합니다. 흔들리는 답보다 나은 것도 아닙니다.

그래서 10장의 결론은 알고리즘 선택 문제를 아예 다른 층위로 옮깁니다.

> **커뮤니티 개수는 알고리즘이 정하게 두지 말고 「쓰임새」로 정해라.**

- **각 커뮤니티를 LLM으로 요약할 것인가** → 요약 하나가 다룰 만한 크기로 자릅니다. 컨텍스트 창에 들어가는 노드 수가 상한이 됩니다. GraphRAG 계열이 계층적 커뮤니티 요약을 쓰는 이유가 이겁니다.
- **요청 라우팅에 쓸 것인가** → 라우팅 단위(샤드 수, 담당 팀 수)에 맞춥니다. 서버가 8대면 커뮤니티도 8개 근처여야 쓸모가 있습니다.
- **사람이 눈으로 볼 대시보드인가** → 화면에 올릴 수 있는 개수, 대략 5~15개.
- **이상 탐지에 쓸 것인가** → 작은 뭉치가 신호이므로 오히려 잘게 나눠야 합니다. 이때 모듈러리티의 해상도 한계는 치명적입니다.

같은 그래프인데 목적마다 정답 개수가 다릅니다. 이게 "맞는 답이 없다"의 진짜 의미입니다. 알고리즘이 부족해서가 아니라, **커뮤니티라는 개념이 목적에 종속적**이기 때문입니다.

## 4. 요구를 받았을 때 되물을 것

"우리 조직을 팀으로 나눠 주세요"라는 요청은 10장 첫 문장의 "제일 중요한 사람이 누군지 뽑아 주세요"와 같은 종류의 질문입니다. 되물어야 합니다.

1. **나눈 결과를 어디에 쓸 건가?** → 개수와 크기의 상한이 여기서 나옵니다.
2. **몇 개쯤 나올 거라고 기대하나?** → 기대치가 있으면 γ나 계층 깊이를 맞출 수 있습니다.
3. **같은 데이터에 같은 답이 나와야 하나?** → 그렇다면 시드 고정 + 문서화가 필수. 라벨 전파를 쓴다면 특히요.
4. **작은 뭉치를 놓치면 안 되나?** → 그렇다면 모듈러리티 단독으로는 부족합니다. γ를 올리거나 계층적으로 돌리거나, 소규모 탐지를 따로 붙여야 합니다.

이 네 개를 안 물어보고 라이브러리 기본값으로 돌린 결과는, 그럴듯해 보이지만 어디에도 쓸 수 없습니다.
