# `MergeStore.resolve()`와 `seen` 집합

> **질문** `MergeStore.resolve()`는 무엇을 하며 왜 `seen` 집합이 필요한가?
>
> **답** 노드의 대표 노드를 따라간다. `seen`은 canonical 포인터에 순환이 생겼을 때 무한 루프를 막는다.

출처: `content/ch14/code/ex3_reversible_merge.py` (14.3 「되돌릴 수 있게 병합하라」)

---

## 1. 코드

```python
class MergeStore:
    """병합을 «사건»으로 기록한다. 원본 노드는 절대 지우지 않는다."""

    def __init__(self, nodes):
        self.nodes = dict(nodes)                 # id -> 속성
        self.canonical = {k: k for k in nodes}   # id -> 대표 id
        self.events = []                         # 되돌리기용 이력

    def resolve(self, nid):
        seen = set()
        while self.canonical[nid] != nid and nid not in seen:
            seen.add(nid)
            nid = self.canonical[nid]
        return nid
```

`resolve()`가 서 있는 자리를 먼저 봐야 이 함수가 왜 중요한지 보인다. 14장의 병합은 **노드를 지우지 않는다.** 병합은 `canonical[drop] = keep` 이라는 **포인터 대입 한 번**이고, 원본 속성은 `self.nodes` 에 그대로 남는다. 그러면 대가가 생긴다. 이제 「r04 를 조회해라」는 요청은 곧바로 답할 수 없고, 항상 「r04 의 **현재 대표**가 누구냐」를 한 번 물어야 한다. 그 질문에 답하는 게 `resolve()` 다.

그래서 `resolve()`는 이 클래스의 모든 읽기 경로의 관문이다.

| 호출부 | resolve 호출 횟수 |
|---|---|
| `merge(a, b)` | 2회 (양쪽을 먼저 정규화) |
| `view(nid)` | 1 + N회 (`members` 를 구하려고 전체 노드를 훑는다) |
| `clusters()` | N회 (모든 노드) |

`clusters()`와 `view()`가 전체 노드를 훑으면서 `resolve()`를 부른다는 점을 기억해 두자. 뒤에서 이게 「사이클 하나가 노드 하나가 아니라 **서비스 전체**를 멈추는」 이유가 된다.

## 2. 포인터 체인을 따라가는 과정 — 단계별로

`canonical` 은 「자식 → 부모」 단방향 포인터 맵이고, 루트의 조건은 **자기 자신을 가리키는 것**(`canonical[x] == x`)이다. 즉 이 자료구조는 **정상 상태에서 숲(forest)** 이다.

### 2.1 1홉짜리 — 예제의 정상 경로

예제 데이터에서 `_richness`(비어 있지 않은 필드 수)는 r01 = 5, r04 = 2 다.

```python
s.merge("r01", "r04", by="auto", reason="사업자번호 일치")
# ca, cb = r01, r04  →  richness 5 >= 2  →  keep=r01, drop=r04
# canonical["r04"] = "r01"
```

이제 `resolve("r04")`:

| 반복 | `nid` | `canonical[nid]` | `nid != canonical[nid]`? | `nid in seen`? | 동작 |
|---|---|---|---|---|---|
| 진입 전 | `r04` | — | — | `seen = {}` | — |
| 1 | `r04` | `r01` | 예 | 아니오 | `seen = {r04}`, `nid ← r01` |
| 2 | `r01` | `r01` | **아니오** | — | 루프 종료 |
| 반환 | `r01` | | | | 대표는 r01 |

### 2.2 여러 홉짜리 체인은 어떻게 생기나

`merge()`는 항상 **루트끼리** 잇는다(`ca`, `cb` 는 이미 `resolve` 를 거친 값). 그러니 체인이 2홉 이상 깊어지는 건 **군집의 현재 루트가 나중에 온 더 풍부한 노드에게 대표 자리를 넘겨줄 때**다.

```
① merge(r01, r04)        canonical: r04 → r01,  r01 → r01
② 나중에 r02(6개 필드가 채워진 레코드)가 도착 → merge(r01, r02)
   ca=r01, cb=r02, richness(r02) > richness(r01) → keep=r02, drop=r01
   canonical: r04 → r01 → r02
```

`resolve("r04")` 추적:

| 반복 | `nid` | `canonical[nid]` | 판정 | `seen` |
|---|---|---|---|---|
| 1 | `r04` | `r01` | 계속 | `{r04}` |
| 2 | `r01` | `r02` | 계속 | `{r04, r01}` |
| 3 | `r02` | `r02` | 루트 → 종료 | — |

반환 `r02`. 방문한 노드가 **모두 서로 다르다.** 트리 경로에서는 그럴 수밖에 없고, 그래서 정상 상태에서는 `nid not in seen` 조건이 **한 번도 발동하지 않는다.** `seen` 은 순수한 방어 장치다.

### 2.3 사이클이 있을 때 — `seen` 이 발동하는 순간

`canonical = {A: B, B: A}` 라고 하자. `resolve("A")`:

| 반복 | `nid` | `canonical[nid]` | `nid != canonical[nid]`? | `nid in seen`? | 동작 |
|---|---|---|---|---|---|
| 1 | `A` | `B` | 예 | 아니오 | `seen = {A}`, `nid ← B` |
| 2 | `B` | `A` | 예 | 아니오 | `seen = {A, B}`, `nid ← A` |
| 3 | `A` | `B` | 예 | **예** | **루프 종료** |
| 반환 | `A` | | | | 루트가 아닌 값! |

여기서 반드시 짚어야 할 게 있다. **`seen` 은 「올바른 답」을 만들어 주지 않는다.** 종료할 때 `nid` 는 `canonical[nid] != nid` 인 채다. 즉 루트가 아닌 노드를 대표라고 반환한다. 실제로 돌려 보면:

```
resolve(A) = A        # A는 B를 가리키고 있는데도 자기가 대표라고 답한다
resolve(B) = B
clusters()  = {}      # 병합이 아예 없었던 것처럼 보인다
canonical[resolve(A)] == resolve(A)  →  False   ← 깨진 불변식
```

`view("A")` 도 같이 무너진다. `c = resolve("A") = "A"` 이고, `members = [k for k in self.nodes if self.resolve(k) == c]` 는 `["A"]` 만 잡는다. **병합해서 채워 넣었던 속성이 조회 결과에서 사라진다.** 3-사이클(`A→B→C→A`)도 마찬가지로 각 노드가 자기 자신을 반환해 군집이 통째로 증발한다.

정리하면 `seen` 이 하는 일은 이렇다.

> **살아 있음(liveness) 실패를 안전성(safety) 실패로 바꾼다.**

무한 루프(영원히 답이 없음)를 **틀린 답**으로 교환한다. 이게 좋은 거래인 이유는, 틀린 답은 검출·기록·경보가 가능하고 나머지 요청은 계속 처리되지만, 멈춘 스레드는 아무 신호도 남기지 않고 서비스를 갉아먹기 때문이다. 다만 **교환일 뿐 해결이 아니다.** 그래서 실무 코드라면 `seen` 이 발동한 그 지점에서 조용히 `return` 하지 말고 사이클 구성원(`seen` 의 내용)과 관련 이벤트 id를 함께 `ERROR` 로 남기거나 예외를 던져야 한다. 예제 코드는 교육용으로 짧게 쓴 것이고, 실서비스에서 이걸 조용히 넘기면 「군집이 왜 사라졌지」를 며칠 뒤에 데이터 담당자가 발견하게 된다.

## 3. 어떤 실수가 사이클을 만드나

먼저 좋은 소식. **정상 경로의 `merge()`는 사이클을 만들 수 없다.**

```python
def merge(self, a, b, by, reason):
    ca, cb = self.resolve(a), self.resolve(b)   # ← 양쪽을 루트로 정규화
    if ca == cb:
        return False                            # ← 같은 군집이면 아무것도 안 한다
    keep, drop = (ca, cb) if self._richness(ca) >= self._richness(cb) else (cb, ca)
    self.canonical[drop] = keep
```

`drop` 은 반드시 `resolve` 를 통과한 **루트**이므로 대입 직전까지 부모가 없다(자기 자신을 가리킴). 부모 없는 노드에 부모를 딱 하나 붙이는 연산은 숲을 숲으로 유지한다. 게다가 `ca == cb` 검사가 「이미 한 군집」인 경우를 걸러 낸다. `A`를 `B`에 병합한 뒤 `merge(B, A)` 를 불러도 `resolve(B) == resolve(A) == B` 라서 `False` 만 돌려주고 끝난다.

그러니까 사이클은 **이 경로를 우회했을 때만** 생긴다. 아래가 그 우회로들이다.

### 3.1 resolve 를 건너뛴 병합 (A를 B로, 그다음 B를 A로)

가장 흔한 초보 실수. 「병합이란 포인터 대입 아니냐」며 이렇게 쓴다.

```python
def merge_naive(self, a, b):
    self.canonical[a] = b          # resolve 없음, ca == cb 검사 없음
```

```
merge_naive("A", "B")   →  canonical[A] = B
merge_naive("B", "A")   →  canonical[B] = A      ← 사이클 완성
```

두 번째 호출이 왜 일어나느냐면, 14.1의 블로킹이 **전략마다 후보 쌍을 따로 만들고 합집합을 쓰기** 때문이다. 사업자번호 전략은 `(A, B)` 로, 이름 전략은 순서가 뒤집힌 `(B, A)` 로 같은 쌍을 뽑아 올 수 있다. 후보 쌍을 정렬해 중복을 제거하지 않았다면 같은 쌍이 두 방향으로 두 번 처리된다.

### 3.2 동점 + 병렬 병합 경쟁 — 진짜 무서운 것

`merge()` 는 사이클을 못 만든다고 했는데, 그건 **직렬 실행일 때만** 참이다. 여기 예제 데이터에 실제로 숨어 있는 함정을 보자.

```python
keep, drop = (ca, cb) if self._richness(ca) >= self._richness(cb) else (cb, ca)
```

`_richness("r06") == _richness("r07") == 5` 로 **동점**이다. 동점일 때 `>=` 는 참이므로 `keep = ca`, 즉 **먼저 넘긴 인자가 이긴다.** 다시 말해:

| 호출 | `ca`, `cb` | 동점 판정 | 결과 |
|---|---|---|---|
| `merge("r06", "r07")` | r06, r07 | `5 >= 5` 참 | `canonical["r07"] = "r06"` |
| `merge("r07", "r06")` | r07, r06 | `5 >= 5` 참 | `canonical["r06"] = "r07"` |

**같은 결정론적 코드가 인자 순서만 바뀌면 정반대 방향의 포인터를 쓴다.** 이 함수는 동점 구간에서 교환법칙을 만족하지 않는다. 직렬이라면 두 번째 호출이 `ca == cb` 에서 막히지만, 워커 두 개가 동시에 돌면:

```
워커1: resolve(r06)=r06, resolve(r07)=r07 → ca!=cb 통과 → keep=r06 결정
                          ┊  ← 이 사이가 경쟁 구간 (read-modify-write, 락 없음)
워커2: resolve(r07)=r07, resolve(r06)=r06 → ca!=cb 통과 → keep=r07 결정
워커1: canonical[r07] = r06
워커2: canonical[r06] = r07
                          → r06 → r07 → r06  사이클
```

`resolve()` 로 읽은 시점과 대입하는 시점 사이에 상태가 변했는데도 그 사실을 모른다. 전형적인 TOCTOU다. 게다가 두 워커가 「서로 다른 쌍」을 처리한다고 믿고 있어도 같은 결과가 난다. 한 워커는 `(r06, r07)`, 다른 워커는 `(r07, r06)` 이라는, 다른 블로킹 전략에서 온 같은 쌍이니까.

### 3.3 unmerge 도중 부분 실패

`unmerge()` 는 두 가지를 한다. **포인터 되돌리기**와 **이벤트 기록**이다.

```python
def unmerge(self, dropped):
    for i in range(len(self.events) - 1, -1, -1):
        e = self.events[i]
        if e["op"] == "merge" and e["drop"] == dropped:
            self.canonical[dropped] = dropped              # ① 상태 변경
            self.events.append({"op": "unmerge", "target": dropped, "undoes": i})  # ② 로그 기록
            return True
    return False
```

메모리 안의 dict 두 개라 예제에서는 원자적이지만, 실서비스에서 `canonical` 은 테이블이고 `events` 는 로그(또는 다른 테이블/토픽)다. 트랜잭션이 아니면 ①만 되고 ②가 실패하거나 그 반대가 된다. 그러면 **로그와 상태가 갈라지고**, 이후 「로그를 재생해 상태를 복원하는」 이벤트 소싱 경로(예제 주석의 「6부 이벤트 소싱의 축소판」)가 오염된 입력을 먹는다. 재생기가 `unmerge` 이벤트를 무시하거나, `merge` 이벤트를 **순서를 뒤섞어** 재생하면서 3.1처럼 `resolve` 없이 대입하면 사이클이 나온다.

부분 실패가 아니어도 이 `unmerge` 에는 알아 둘 구멍이 하나 더 있다. 체인 `r04 → r01 → r02` 에서 `unmerge("r01")` 을 하면 `canonical[r01] = r01` 이 되는데, **r01 아래에 매달려 있던 r04 는 아무도 손대지 않는다.** r04 는 여전히 r01 을 가리키므로 「r02 로 병합됐던 사실」이 취소되면서 r04 까지 조용히 r01 군집으로 딸려 내려온다. 사이클은 아니지만 「되돌리기 하나가 의도치 않은 노드를 함께 옮긴다」는 같은 계열의 불변식 사고다.

### 3.4 캐시가 만드는 사이클

`resolve()` 가 병목이라 결과를 캐싱했다고 하자. 캐시가 낡으면 `merge()` 는 **더 이상 루트가 아닌 노드**를 `ca` 로 받는다. 그 노드의 실제 조상 방향으로 새 포인터를 쓰면 사이클이다. 「대표 id 를 비정규화해 컬럼에 박아 두고 갱신을 놓쳤다」도 같은 사고다.

### 3.5 사람 손

운영 중 `canonical` 테이블을 직접 `UPDATE` 하는 경우, 서로 다른 시점의 백업을 부분 복원하는 경우, 「대표를 이 노드로 바꿔 달라」는 요청을 자손 여부 확인 없이 처리하는 일괄 스크립트. 대표를 재지정하는 배치와 병합 배치가 동시에 돌면 3.2 와 똑같은 구조가 된다.

### 요약

| 경로 | 사이클이 생기는 이유 | 막는 방법 |
|---|---|---|
| resolve 없는 대입 | 루트가 아닌 노드에 부모를 붙인다 | `merge()`처럼 항상 먼저 `resolve` |
| 동점 + 병렬 경쟁 | 인자 순서로 방향이 갈리고, 읽기-쓰기 사이에 락이 없다 | id 로 결정론적 동점 처리 + CAS/락 |
| unmerge 부분 실패 | 상태와 로그가 갈라진 뒤 잘못 재생된다 | 상태·로그를 한 트랜잭션으로 |
| 캐시/비정규화 낡음 | 낡은 루트 위에 새 포인터를 쓴다 | 캐시는 읽기 전용, 쓰기는 항상 원본 확인 |
| 수동 UPDATE·부분 복원 | 불변식을 아무도 검사하지 않는다 | 주기적 불변식 점검 + 경보 |

## 4. `seen` 이 없으면 — 증상

```python
def resolve(self, nid):            # seen 없는 버전
    while self.canonical[nid] != nid:
        nid = self.canonical[nid]
    return nid
```

`canonical = {A: B, B: A}` 에서 이걸 실행하면 dict 조회와 대입만 반복한다. CPU 제한(`ulimit -t 2`)을 걸고 돌려 보면 2초를 통째로 태우고 `SIGXCPU`(종료 코드 152)로 죽는다. 이 증상의 성질이 고약하다.

| 관측 지점 | 무엇이 보이나 |
|---|---|
| 예외·에러 로그 | **아무것도 없다.** 던지는 예외가 없다 |
| 메모리 | **늘지 않는다.** 할당이 없어서 OOM 킬러도 안 온다 |
| CPU | 코어 하나가 **100%** 에 붙어 있다 |
| 요청 스레드 | **영구 정지.** 타임아웃이 없으면 절대 반환하지 않는다 |
| 지표 | p99 지연과 스레드 수만 슬금슬금 오른다 |

즉 「죽지도 않고 알려 주지도 않는」 실패다. 에러율 대시보드는 초록색인데 서비스는 굳어 간다. 그리고 다음 두 가지 때문에 노드 하나의 문제로 끝나지 않는다.

1. **증폭.** `clusters()` 와 `view()` 는 모든 노드에 대해 `resolve()` 를 부른다. 사이클에 낀 노드가 단 두 개여도 **전체 스캔을 하는 모든 작업**(군집 목록 조회, 야간 배치, 익스포트, 검증 잡)이 그 노드에 닿는 순간 멈춘다. 조회하는 대상이 사이클과 무관해도 상관없다.
2. **연쇄.** 상단에 타임아웃이 있으면 클라이언트는 재시도한다. 그런데 타임아웃은 **호출자만 포기시키고 워커 스레드는 계속 돌린다.** 재시도마다 스레드 하나가 영구히 잠기고, 스레드 풀이 마르면 사이클과 전혀 상관없는 요청까지 전부 실패한다. 정지 하나가 장애 전체로 번지는 경로다.

여기에 재현의 어려움이 얹힌다. 사이클은 3.2 같은 경쟁이나 3.5 같은 수동 개입이 남긴 **데이터 상태**이지 코드 경로가 아니다. 코드를 다시 배포해도, 프로세스를 재시작해도 그대로 있다. 되살아난 인스턴스가 같은 자리에서 다시 굳는다.

## 5. 방어는 여러 층으로

`seen` 은 **최후 방어선**이다. 여기까지 왔다는 건 이미 데이터가 깨졌다는 뜻이므로, 앞쪽 층들이 더 중요하다.

### 층 1 — 쓰기 시점에 사이클 자체를 막는다 (가장 중요)

이미 예제가 하고 있는 일이다. `merge()` 는 **먼저 양쪽을 `resolve` 하고**, `ca == cb` 면 아무것도 하지 않고, **루트에만** 포인터를 쓴다. 이 세 가지가 지켜지면 자료구조는 정의상 숲을 벗어날 수 없다. 「`canonical` 에 쓰는 코드는 오직 `merge`/`unmerge` 뿐」이라는 규율(SQL 직접 접근 금지, 쓰기 경로 단일화)이 사실상 이 층의 전부다.

### 층 2 — 동시성: 결정론적 방향 + 원자적 쓰기

3.2 를 막으려면 두 가지가 필요하다.

**(가) 동점을 결정론적으로 깬다.** 인자 순서가 방향을 결정하게 두면 안 된다.

```python
keep, drop = (ca, cb) if (self._richness(ca), ca) >= (self._richness(cb), cb) else (cb, ca)
```

동점이면 id 가 큰 쪽이 이긴다. 이러면 `merge(a, b)` 와 `merge(b, a)` 가 **항상 같은 방향**을 쓰므로, 경쟁이 나도 두 워커가 같은 대입을 하고 사이클이 아니라 중복 쓰기가 된다.

**(나) 읽기-쓰기를 원자적으로 만든다.** 두 루트에 락을 잡거나, 조건부 갱신(CAS)으로 「그 사이에 안 바뀌었음」을 DB에 확인시킨다.

```sql
UPDATE canonical SET parent = :keep WHERE id = :drop AND parent = :drop;
```

`WHERE parent = :drop` 이 핵심이다. `drop` 이 그새 루트가 아니게 됐다면 0행이 갱신되고, 호출자는 다시 `resolve` 해서 재시도한다. 늦은 워커가 조용히 지는 구조다.

### 층 3 — 불변식 검사와 경보

쓰기 경로를 아무리 조여도 사람 손과 복원이 남는다. 주기적으로 돌리는 점검 잡이 필요하다.

```python
def check_invariants(store):
    problems = []
    for x in store.nodes:
        r = store.resolve(x)
        if store.canonical[r] != r:              # ① 루트가 아닌 것을 대표로 반환 → 사이클
            problems.append(("cycle", x, r))
    roots = {store.resolve(x) for x in store.nodes}
    for r in roots:                              # ② 각 군집에 루트는 정확히 하나
        assert store.canonical[r] == r
    return problems
```

①이 결정적이다. `seen` 덕분에 프로세스가 살아 있으므로 **이 검사를 실행할 수 있다.** `seen` 이 없으면 검사 잡 자체가 첫 사이클에서 멈춰 버려 아무도 알려 주지 못한다. 이 둘은 짝이다. `seen` 은 프로세스를 살려서 검사가 돌아가게 하고, 검사는 `seen` 이 감춘 「틀린 답」을 드러낸다.

같이 볼 것들: 병합/해제 건수 급변, 군집 크기 분포(14.2의 「군집 크기 상한을 두거나 커지면 사람에게 보낸다」와 같은 신호), 체인 길이 분포.

### 층 4 — 체인 길이 상한

```python
MAX_CHAIN = 32

def resolve(self, nid):
    for _ in range(MAX_CHAIN):
        if self.canonical[nid] == nid:
            return nid
        nid = self.canonical[nid]
    raise CanonicalChainTooLong(nid)     # 조용히 틀리지 않고, 크게 소리 낸다
```

`seen` 과 겹치는 것 같지만 잡는 게 다르다.

| 장치 | 잡는 것 | 못 잡는 것 | 공간 |
|---|---|---|---|
| `seen` 집합 | 사이클(정확히) | 사이클 아닌 긴 체인 | O(체인 길이) |
| 길이 상한 | 사이클 **과** 병리적으로 긴 체인 | 상한 이내의 사이클 | O(1) |

긴 체인은 유한해서 멈추긴 하지만 조회 지연을 조용히 올린다. 상한은 그것도 잡고, `seen` 이 사이클 길이만큼 쓰는 메모리도 없앤다. **한계 값과 함께 예외를 던지는 것**이 조용한 오답보다 낫다는 게 핵심이다.

덧붙여 `seen` 은 **정상 호출에서도 비용을 낸다.** 1홉짜리 조회 하나마다 `set` 을 새로 만든다. 대부분의 조회가 1~2홉인 뜨거운 경로라면 아깝다. 상한 카운터로 갈아타거나, 공간이 문제라면 플로이드의 토끼-거북(포인터 두 개로 O(1) 공간에 사이클 검출)을 쓸 수 있다. 예제가 `seen` 을 고른 건 **짧고, 정확하고, 사이클 구성원을 그대로 손에 쥐어 주기**(진단에 그대로 쓸 수 있다) 때문이다.

### 층 5 — 검출한 뒤 어떻게 고치나

사이클을 찾으면 `events` 로그가 있다. 그 노드들을 `drop` 으로 하는 `merge` 이벤트를 찾아 **늦게 들어온 쪽을 취소**하면 한쪽 간선이 끊어지고 체인이 복구된다. 원본 속성을 안 지웠고 이력이 남아 있으니 가능한 복구다. 노드를 실제로 삭제하고 속성을 합쳐 버린 설계에서는 이 복구가 불가능하다.

## 6. 왜 경로 압축을 하지 않나 — 유니온-파인드와의 대비

같은 장의 `ex2_scoring.py` 에는 교과서적인 유니온-파인드가 있다.

```python
parent = {k: k for k in BY_ID}
def find(x):
    while parent[x] != x:
        parent[x] = parent[parent[x]]; x = parent[x]   # ← 경로 절반 압축
    return x
def union(x, y):
    parent[find(x)] = find(y)
```

`MergeStore.resolve()` 와 골격이 똑같다. 다른 건 딱 한 줄, `parent[x] = parent[parent[x]]` 다. 지나가는 길에 **포인터를 루트 쪽으로 당겨 붙인다.** 유니온-파인드가 사실상 상수 시간(랭크 합침과 함께 쓰면 역-아커만)인 이유가 이거다. 그런데 이 압축은 **파괴적**이다. 「어느 병합이 이 노드를 어디에 붙였는지」를 지워 버린다.

두 코드가 왜 다른 선택을 하는지는 **각자의 수명**이 설명한다.

| | `ex2` 의 `find`/`union` | `MergeStore.resolve` |
|---|---|---|
| 무엇인가 | 쌍 목록에서 매번 새로 만드는 일회용 메모리 구조 | 영속 상태 + 감사 이력 |
| 목적 | 이행성으로 군집 계산 (14.2) | 되돌릴 수 있는 병합 (14.3) |
| 되돌리기 | 없음. 다시 계산하면 된다 | **필수 요구사항** |
| 경로 압축 | **한다** (속도) | **안 한다** (되돌리기) |

`MergeStore` 에서 **체인은 감사 이력 그 자체다.** `canonical[drop] = keep` 이라는 간선 하나는 `events` 의 병합 사건 하나와 정확히 1:1로 대응한다. 그래서 `unmerge` 가 대입 한 번이다.

```python
self.canonical[dropped] = dropped     # 그 사건이 만든 간선 하나만 끊는다
```

압축을 하면 이게 깨진다. `r04 → r01 → r02` 를 압축해 `r04 → r02`, `r01 → r02` 로 만들었다고 하자. 이제 「r01 을 r02 에 붙인 병합」을 취소해야 한다. **정답은 `r04 → r01` 이 남는 상태**다. 그런데 압축된 포인터는 r04 가 r02 를 가리킨다고만 말하고, r04 가 r01 을 경유했다는 사실은 어디에도 없다. 한 번의 대입으로 되돌릴 수 없고, 군집 전체를 이벤트 로그에서 재생해 재구성해야 한다. 대입 한 번이 전체 재구성이 되는 순간 「되돌리기가 싸다」는 전제가 무너지고, 14.4의 계산도 함께 무너진다.

> 오병합 하나 수습: 평균 2시간 → 되돌리기가 대입 한 번이면 **5분**
>
> 그래서 되돌리기가 싸면 임계를 더 낮게(공격적으로) 잡을 수 있다.

즉 압축을 포기한 대가로 얻는 게 「**되돌리기가 싸다 → 자동화를 공격적으로 할 수 있다**」이고, 이건 14장 전체를 떠받치는 전제다. 성능을 위해 압축을 넣으면 그 전제부터 사라진다. 6부 이벤트 소싱의 관점으로 말하면, 압축은 **상태를 로그에서 유도할 수 없게 만든다.**

값은 예제가 정직하게 적어 뒀다.

> 대가는 저장 공간과 조회 비용이다. 조회할 때마다 resolve 를 거쳐야 한다.
> 제 경우 노드 수가 1.4배가 됐고, 조회에 인덱스 조회 한 번이 더 붙었다.

그럼 성능이 진짜 문제가 되면 어떻게 하나. 세 가지 길이 있고 셋 다 「체인을 진실로 남기는」 원칙을 지킨다.

1. **읽기 캐시를 따로 둔다.** 별도의 대표 id 인덱스를 두고, 진실은 체인, 캐시는 유도된 값으로 취급한다. 병합 때 무효화한다(3.4 를 조심할 것 — 캐시를 쓰기 경로가 읽으면 안 된다).
2. **압축도 사건으로 기록한다.** 압축을 하되 「어떤 노드의 포인터를 무엇에서 무엇으로 바꿨는지」를 이벤트로 남기면 재생·되돌리기가 유지된다. 압축을 없애는 게 아니라 **이력화**하는 것이다.
3. **체인 길이에 상한을 두고**(층 4) 넘어가는 군집만 사람이 정리하거나 대표를 재지정한다.

## 7. 한 줄로

`resolve()` 는 「이 노드의 **현재** 대표는 누구냐」에 답하는 관문이고, 원본을 지우지 않는 병합 설계를 성립시키는 대가다. 체인을 압축하지 않고 남겨 두는 것은 **되돌리기를 대입 한 번으로 유지하기 위한 의도적 선택**이며, `seen` 은 그 체인이 어떤 이유로든(경쟁, 부분 실패, 수동 개입) 순환으로 오염됐을 때 **서비스가 조용히 굳는 대신 시끄럽게 틀리도록** 바꿔 주는 최후의 안전장치다. 정상 상태에서는 절대 발동하지 않으며, 발동했다면 그건 상위 층의 방어가 뚫렸다는 신호다.
