# `MergeStore.view()` — 병합된 값을 어떻게 합치는가

> **Q.** `MergeStore.view()`는 병합된 노드의 값을 어떻게 합치는가?
>
> **A.** 군집 구성원을 richness 내림차순으로 훑으며 비어 있지 않은 값을 먼저 채운다. 이미 채워진 필드는 덮어쓰지 않는다.

출처: 14장 「같은 사람이 노드 네 개로 앉아 있다」 / 14.3 되돌릴 수 있게 병합하라 / `code/ex3_reversible_merge.py`

## 1. 코드 그대로 보기

합치는 로직은 딱 열 줄이다. 그리고 그 열 줄이 **원본 노드를 한 글자도 건드리지 않는다**는 게 핵심이다.

```python
def _richness(self, nid):
    return sum(1 for v in self.nodes[nid].values() if v)   # 비어 있지 않은 필드 개수
```

```python
def view(self, nid):
    """대표 노드의 속성 + 병합된 것들의 속성을 채워 넣는다."""
    c = self.resolve(nid)                                   # (1) 대표 id 찾기
    merged = {}
    members = [k for k in self.nodes if self.resolve(k) == c]  # (2) 같은 군집 전원
    for m in sorted(members, key=lambda x: -self._richness(x)):  # (3) richness 내림차순
        for k, v in self.nodes[m].items():
            if v and not merged.get(k):                     # (4) 값이 있고 + 아직 빈 칸일 때만
                merged[k] = v
        return c, merged, members
```

정리하면 네 단계다.

| 단계 | 하는 일 | 코드 |
|---|---|---|
| 1 | 어떤 id로 물어도 대표 id로 환원 | `c = self.resolve(nid)` |
| 2 | 대표가 같은 노드 전부를 군집 구성원으로 모음 | `[k for k in self.nodes if self.resolve(k) == c]` |
| 3 | 구성원을 **채워진 필드 수(richness) 내림차순**으로 정렬 | `sorted(members, key=lambda x: -self._richness(x))` |
| 4 | 순서대로 훑으며 **빈 값은 건너뛰고**, **이미 채운 필드는 덮어쓰지 않음** | `if v and not merged.get(k)` |

즉 규칙은 두 개다. **빈 값은 절대 이기지 못한다**(`if v`), 그리고 **먼저 온 값이 이긴다**(`not merged.get(k)`). 순서를 richness가 정하니 결과적으로 "정보가 가장 많은 노드가 기준선, 나머지는 구멍 메꾸기"가 된다.

`merge()`에서 대표를 고르는 규칙도 같은 척도를 쓴다는 점을 같이 보면 그림이 맞아떨어진다.

```python
# 대표는 «정보가 더 많은» 쪽으로. 규칙을 못 박아 둔다.
keep, drop = (ca, cb) if self._richness(ca) >= self._richness(cb) else (cb, ca)
self.canonical[drop] = keep
```

## 2. 실제 레코드로 따라가기 — r01 + r04

`ex3_reversible_merge.py`의 `NODES`에서 `s.merge("r01", "r04", by="auto", reason="사업자번호 일치")`를 한 다음 `s.view("r04")`를 부른 경우다.

원본:

| id | name | bizno | addr | ceo | tel | `_richness` |
|---|---|---|---|---|---|---|
| r01 | 가온테크 | 123-45-67890 | 서울 강남구 테헤란로 1 | 김하늘 | 02-1234-5678 | **5** |
| r04 | GAON TECH | 123-45-67890 | (빈 값) | (빈 값) | (빈 값) | **2** |

`resolve("r04") → "r01"`, `members = ["r01", "r04"]`, 정렬 결과 `[r01(5), r04(2)]`.

훑는 과정을 필드 대입 단위로 펼치면 이렇다.

| 순서 | 노드 | 필드 | 값 | `if v` | `not merged.get(k)` | 결과 |
|---|---|---|---|---|---|---|
| 1 | r01 | name | 가온테크 | 통과 | 통과 | **채움** |
| 2 | r01 | bizno | 123-45-67890 | 통과 | 통과 | **채움** |
| 3 | r01 | addr | 서울 강남구 테헤란로 1 | 통과 | 통과 | **채움** |
| 4 | r01 | ceo | 김하늘 | 통과 | 통과 | **채움** |
| 5 | r01 | tel | 02-1234-5678 | 통과 | 통과 | **채움** |
| 6 | r04 | name | GAON TECH | 통과 | **탈락**(이미 «가온테크») | 무시 |
| 7 | r04 | bizno | 123-45-67890 | 통과 | **탈락** | 무시 |
| 8 | r04 | addr | `""` | **탈락**(빈 값) | — | 무시 |
| 9 | r04 | ceo | `""` | **탈락** | — | 무시 |
| 10 | r04 | tel | `""` | **탈락** | — | 무시 |

최종 반환값(실제 실행 확인):

```python
('r01',
 {'name': '가온테크', 'bizno': '123-45-67890',
  'addr': '서울 강남구 테헤란로 1', 'ceo': '김하늘', 'tel': '02-1234-5678'},
 ['r01', 'r04'])
```

명함스캔에서 온 `GAON TECH`라는 영문 표기는 **버려지지 않고 r04에 그대로 남아 있다.** `view()`가 화면에 안 보여줄 뿐이다. 이게 다음 절의 요점이다.

### 2-1. 구멍 메꾸기가 실제로 일어나는 경우

r04가 기여하려면 대표 쪽에 빈 칸이 있어야 한다. r01의 `tel`이 비어 있다고 가정하면:

| id | name | bizno | addr | ceo | tel | richness |
|---|---|---|---|---|---|---|
| r01 | 가온테크 | 123-45-67890 | 테헤란로 1 | 김하늘 | (빈 값) | 4 |
| r02 | (주)가온테크 | 123-45-67890 | 테헤란로 1길 22 | 박서준 | (빈 값) | 4 |
| r04 | GAON TECH | (빈 값) | (빈 값) | (빈 값) | 02-1234-5679 | 2 |

→ `view()` 결과: `name=가온테크, bizno=123-45-67890, addr=테헤란로 1, ceo=김하늘, tel=02-1234-5679`

`tel`만 richness 2짜리 명함스캔 레코드에서 올라왔다. 나머지는 r01이 다 선점했다. 이 결과가 다음 절의 한계 목록을 그대로 보여준다.

## 3. 왜 이게 중요한가 — 「읽는 시점에 계산하는 파생 뷰」

`view()`는 **저장된 것이 아니다.** 호출할 때마다 `resolve` → `members` 수집 → 정렬 → 대입을 다시 한다. 저장소에는 여전히 원본 노드 N개와 `canonical` 포인터, `events` 로그만 있다.

| | 파괴적 병합 (원본을 지우고 합친 값을 저장) | `view()` 방식 (읽는 시점 계산) |
|---|---|---|
| 저장되는 것 | 합쳐진 레코드 1개 | 원본 N개 + 포인터 + 이벤트 로그 |
| 되돌리기 | 사실상 불가 — 어느 값이 어디서 왔는지 모름 | `self.canonical[dropped] = dropped` — **대입 한 번** |
| 병합 규칙 변경 | 원본이 없으니 재계산 불가 | `view()`만 고치면 과거 전부에 소급 적용 |
| 조회 비용 | 없음 | `resolve` + 군집 스캔 + 정렬 |

장 본문의 표현이 정확하다.

> 핵심은 «원본을 안 지운다»는 것이다. r07 의 속성이 그대로 남아 있으니 되돌리기가 대입 한 번이다.
> 노드를 실제로 지우고 속성을 합쳐 버리면 이게 안 된다. 어느 값이 어디서 왔는지 모르니까 원래대로 쪼갤 수 없다.

그래서 14.4의 임계 계산까지 바뀐다. 오병합 하나 수습이 2시간이면 임계를 높게 잡아야 하지만, `unmerge`가 대입 한 번이면 그 값이 5분이 되고 훨씬 공격적으로 자동화할 수 있다. **되돌리기가 싸면 자동화가 대담해진다.** `view()`가 파생 뷰라는 설계가 그 싼 되돌리기를 가능하게 한다.

## 4. 한계 — richness 정렬로는 부족하다

이 방식은 「일단 무언가를 보여주는」 데는 충분하지만, 정답을 고르는 규칙으로는 세 군데가 약하다.

### (1) richness 순서는 필드별로 최적이 아니다

`_richness`는 **레코드 전체가 얼마나 채워졌나**만 센다. 필드마다 무엇이 옳은지는 전혀 모른다.

| 필드 | 성질 | 옳은 규칙 | richness가 주는 답 |
|---|---|---|---|
| `ceo` (대표자) | **바뀌는** 값 | 가장 최근 | 가장 꽉 찬 레코드의 값 — 오래된 값일 수 있다 |
| `bizno` (사업자번호) | 안 바뀌는 값 | 신뢰도 높은 출처 | 출처를 안 봄 |
| `addr` | 정밀도 차이 | 가장 긴/구체적인 값 | 길이를 안 봄 |

2-1의 예에서 `ceo`가 「김하늘」로 정해진 게 딱 그 문제다. 갱신일이 더 최근인 r02의 「박서준」이 맞을 수 있는데, richness가 같아도 `sorted`가 **안정 정렬**이라 동점이면 `self.nodes`의 **삽입 순서**가 승자를 정한다. 실제로 위 데이터에서 r02를 먼저 넣으면 결과가 `name=(주)가온테크, addr=테헤란로 1길 22, ceo=박서준`으로 **통째로 바뀐다.** 도메인 근거 없이 dict 순서가 답을 정하는 셈이다.

### (2) 프랑켄슈타인 레코드

`view()`는 필드를 **독립적으로** 채운다. 그래서 서로 다른 필드가 서로 다른 레코드에서 올라오면, **어느 원본에도 존재하지 않던 조합**이 만들어진다.

2-1의 결과가 그렇다. `addr`은 ERP의 옛 주소, `tel`은 명함스캔의 새 번호. 이 회사는 그 주소에서 그 번호를 쓴 적이 한 번도 없을 수 있다. 주소와 우편번호, 지번과 도로명처럼 **같이 움직여야 하는 필드 묶음**에서 특히 위험하다. 각 필드는 다 «어딘가에서 온 진짜 값»인데 합쳐 놓으면 거짓인 레코드가 된다.

### (3) 출처를 같이 저장하지 않으면 나중에 설명할 수 없다

`view()`가 돌려주는 `merged`는 값만 담는다. 「이 대표자 이름이 왜 김하늘인가」에 답하려면 그 값이 **r01에서, ERP 출처로, 어떤 규칙으로** 뽑혔는지가 필요하다. 지금 구조로는 매번 `_richness`를 손으로 재계산해 추리해야 한다. 장 본문이 못 박은 대로다.

> 그리고 고른 값마다 «어디서 왔는지»를 같이 저장한다. 그게 있어야 «이 대표자 이름 왜 이래요» 라는 문의에 답할 수 있다.

## 5. 그래서 14.5의 필드별 생존 규칙으로 발전한다

세 한계가 그대로 `ex5_survivorship.py`의 설계 요구사항이 된다. 단일 척도(richness) → **필드별 규칙 테이블**로 바뀐다.

```python
SOURCE_TRUST = {"ERP": 3, "CRM": 2, "명함스캔": 1}

RULES = {
    "name": "가장 신뢰도 높은 출처",
    "ceo":  "가장 최근",
    "tel":  "가장 최근 중 비어 있지 않은 것",
    "addr": "가장 긴 값",
}

def pick(field, rows):
    cand = [r for r in rows if r.get(field)]      # 빈 값은 여전히 후보에서 제외
    if not cand:
        return None, "값이 없다"
    rule = RULES[field]
    ...
    return r[field], f"{rule} → {r['id']}({r['src']}, {r['updated']})"   # 근거를 함께 반환
```

무엇이 이어지고 무엇이 달라졌는지:

| | `view()` (14.3) | `pick()` (14.5) |
|---|---|---|
| 승자 결정 | 레코드 richness 하나로 전부 | **필드마다 다른 규칙** (출처 신뢰도 / 최신성 / 길이) |
| 빈 값 처리 | `if v` — 이기지 못함 | `[r for r in rows if r.get(field)]` — **동일 원칙 유지** |
| 근거 | 없음 (값만 반환) | `why` 문자열로 **규칙 + 출처 id + 출처 + 갱신일** 반환 |
| 동점 처리 | dict 삽입 순서 (우연) | 규칙이 명시한 키로 `max` |

그리고 규칙을 코드에 박아 두는 이유가 본문에 있다.

> 중요한 건 규칙을 «필드마다» 정해서 코드에 박아 두는 것이다. 규칙이 없으면 개발자가 그때그때 정하고, 6개월 뒤에 아무도 이유를 모른다.

프랑켄슈타인 문제는 필드별 규칙만으로는 완전히 안 풀린다는 것도 기억하자. 필드가 독립적으로 뽑히는 구조 자체가 원인이니, 같이 움직여야 하는 필드는 **묶음 단위로 한 레코드에서 통째로** 가져오는 규칙이 따로 필요하다.

## 6. 읽기 시점 계산의 비용과 대안

`view()`는 호출마다 다시 계산한다. 비용은 대략 이렇다.

- `resolve()` — 포인터 체인을 따라간다. 경로 압축이 없어 체인이 길어지면 길이만큼 비례.
- `members` 수집 — `for k in self.nodes` 전체 스캔. **군집 하나 조회에 노드 전체를 훑는다.** 노드가 늘면 그대로 O(N)이라 가장 먼저 터지는 지점이다.
- `sorted(...)` — 정렬할 때마다 구성원마다 `_richness`를 재계산.

본문이 밝힌 실측 대가도 참고할 만하다.

> 대가는 저장 공간과 조회 비용이다. 조회할 때마다 resolve 를 거쳐야 한다. 제 경우 노드 수가 1.4배가 됐고, 조회에 인덱스 조회 한 번이 더 붙었다. 사흘짜리 사고를 다시 안 겪는 값으로는 쌌다.

선택지:

| 방식 | 내용 | 트레이드오프 |
|---|---|---|
| 그대로 계산 | 매번 `view()` | 항상 최신, 규칙 변경 즉시 반영 / 조회 비용 |
| **역인덱스 추가** | `canonical → members` 맵을 유지 | 전체 스캔 O(N)을 제거. 병합/해제 때만 갱신. 가장 값싼 개선 |
| **캐싱** | 대표 id별 `merged`를 캐시하고 병합·해제·속성 변경 시 무효화 | 조회는 빠름 / 무효화를 놓치면 오래된 값이 남음 |
| **머티리얼라이즈** | 합친 레코드를 실제 테이블로 굽고 배치로 갱신 | 읽기가 제일 빠름 / 원본은 여전히 살아 있으므로 되돌리기는 유지되지만, 갱신 지연만큼 뷰가 어긋남 |

중요한 건 **캐시든 머티리얼라이즈든 원본을 지우는 게 아니라는 점이다.** 파생 뷰를 굽는 것은 되돌리기를 포기하는 게 아니다. 원본 노드와 `events`가 남아 있으면 언제든 다시 구울 수 있다. 절대 하지 말아야 할 최적화는 「합쳤으니 원본 지우기」 하나다.

## 한 줄 정리

`view()`는 대표 노드로 환원한 뒤 군집 구성원을 richness 내림차순으로 훑으며 빈 값이 아닌 값을 선착순으로 채우는 **읽기 시점 파생 뷰**다. 원본을 안 건드리므로 되돌리기가 대입 한 번이지만, richness라는 단일 척도로는 필드별 정답도 출처 설명도 못 주고 프랑켄슈타인 조합을 만들 수 있어서 14.5의 필드별 생존 규칙으로 발전한다.
