# 노드를 실제로 지우고 속성을 합치면 왜 되돌릴 수 없는가

> **Q.** 노드를 실제로 지우고 속성을 합치면 왜 되돌릴 수 없는가?
>
> **A.** 어느 값이 어디서 왔는지 알 수 없어 원래대로 쪼갤 수 없다.

14.3절 「되돌릴 수 있게 병합하라」의 핵심입니다. `ex3_reversible_merge.py`의 마지막 문단이 한 줄로 못 박아 둔 문장이 바로 이것입니다.

```
노드를 실제로 지우고 속성을 합쳐 버리면 이게 안 된다.
어느 값이 어디서 왔는지 모르니까 원래대로 쪼갤 수 없다.
```

이 힌트에서는 「모른다」가 정확히 무엇을 모르는 것인지를 **세 층**으로 갈라서 봅니다. 층마다 잃는 것이 다르고, 되돌릴 수 없는 정도도 다릅니다.

---

## 0. 파괴적 병합이란 정확히 어떤 연산인가

「파괴적(destructive) 병합」은 두 단계로 이루어집니다.

1. **속성을 하나로 접는다** — 생존 규칙(survivorship rule)으로 필드마다 이길 값을 골라 새 속성 집합을 만든다.
2. **원본 노드를 지운다** — 진 값과 진 노드를 DB에서 `DELETE` 한다. 엣지는 살아남은 노드로 재배선한다.

여기서 되돌릴 수 없게 만드는 것은 1번이 아니라 **1번과 2번의 조합**입니다. 값을 고르는 것 자체는 죄가 없습니다. 고른 뒤에 안 고른 것을 지워 버리는 게 문제입니다.

비파괴적 병합은 같은 1번을 하지만 그것을 **저장하지 않고 조회할 때마다 계산**합니다. `ex3`의 `view()`가 그렇습니다. 원본은 사실로 남고, 합쳐진 모습은 파생으로만 존재합니다.

## 1층 — 값의 출처가 사라진다

### 다대일 사상에는 역함수가 없다

`ex5_survivorship.py`의 실제 레코드로 보겠습니다.

| id | 출처 | updated | name | ceo | tel | addr |
|---|---|---|---|---|---|---|
| r01 | ERP | 2024-03-01 | 가온테크 | 김하늘 | 02-1234-5678 | 서울 강남구 테헤란로 1 |
| r02 | CRM | 2026-01-15 | (주)가온테크 | 박서준 | *(빈값)* | 서울 강남구 테헤란로 1길 22 |
| r04 | 명함스캔 | 2025-07-09 | GAON TECH | *(빈값)* | 02-1234-5679 | *(빈값)* |

필드별 생존 규칙(`RULES`)을 적용하면 결과는 이렇습니다.

| 필드 | 규칙 | 살아남은 값 | 실제로 어디서 왔나 |
|---|---|---|---|
| name | 가장 신뢰도 높은 출처 | 가온테크 | r01 (ERP) |
| ceo | 가장 최근 | 박서준 | r02 (CRM) |
| tel | 가장 최근 중 비어 있지 않은 것 | 02-1234-5679 | r04 (명함스캔) |
| addr | 가장 긴 값 | 서울 강남구 테헤란로 1길 22 | r02 (CRM) |

**첫 번째 관찰: 병합 결과는 원본 어디에도 없는 레코드입니다.** `가온테크 / 박서준 / 02-1234-5679 / 테헤란로 1길 22` 조합을 가진 행은 r01도, r02도, r04도 아닙니다. 필드마다 독립적으로 승자를 뽑았으니 결과는 세 행을 가로로 오려 붙인 프랑켄슈타인입니다. 행 단위 사상이 아니라 **격자 전체를 섞은 뒤 한 줄만 남긴 것**입니다.

**두 번째 관찰: 셀 개수를 세어 보면 됩니다.** 입력은 3행 × 4필드 = 12칸, 출력은 4칸입니다. 8칸은 그냥 버려집니다. 원본 노드를 지우면 그 8칸을 되찾을 곳이 없습니다.

정보 이론으로 말하면 파괴적 병합은 **다대일(many-to-one) 사상**입니다. 정의역이 치역보다 크므로 단사(injective)가 아니고, 단사가 아니면 역함수가 존재하지 않습니다. 「구현이 어렵다」가 아니라 **원리적으로 불가능**합니다. 되돌리기를 아무리 잘 짜도, 잃어버린 8칸을 복원하는 함수는 수학적으로 없습니다.

### 남은 값조차 어디서 왔는지 모른다

더 미묘한 문제가 있습니다. 살아남은 4칸도 **출처 태그가 없으면 어느 행에서 왔는지 모릅니다.** 병합 후 노드를 열어 보면 그냥 `ceo: 박서준`입니다. 이게 CRM에서 온 값인지, ERP에서 온 값인지, 아니면 세 곳 모두 박서준이었는지 구별이 안 됩니다.

그래서 쪼개려 할 때 이런 질문에 답할 수 없습니다.

- r01을 되살릴 때 대표자에 뭘 넣나? 「박서준」은 r02 것인데, r01 것은 「김하늘」이었는지 빈값이었는지 병합 후 데이터에는 흔적이 없습니다.
- r04를 되살릴 때 주소를 넣어야 하나 비워야 하나? 원래 빈값이었다는 사실 자체가 소실됐습니다. **「값이 없었다」도 정보인데, 병합은 그 정보를 제일 먼저 버립니다.**

`ex5`의 마지막 문단이 이걸 짚습니다.

```
그리고 고른 값마다 «어디서 왔는지»를 같이 저장한다.
그게 있어야 «이 대표자 이름 왜 이래요» 라는 문의에 답할 수 있다.
```

출처를 같이 저장한다는 것이 곧 1층을 살려 두는 일입니다. 표준으로는 [PROV-O](https://www.w3.org/TR/prov-o/)의 `prov:wasDerivedFrom` / `prov:wasGeneratedBy`가 이 자리를 맡습니다.

### 최악의 사례 — 오류의 증거가 지워진다

`ex3`의 실제 사고 쌍으로 가 봅시다.

| id | name | bizno | addr | ceo | tel |
|---|---|---|---|---|---|
| r06 | 나루소프트 | **222-33-44444** | 서울 마포구 월드컵로 2 | 이서연 | 02-2222-3333 |
| r07 | 나루소프트(주) | **555-66-77777** | 서울 마포구 월드컵로 2 | 이서연 | 02-2222-3333 |

`records.py`의 주석대로 이 둘은 **주소·대표자·전화가 같아도 다른 법인**입니다. 다르다는 판정의 유일한 근거는 사업자번호입니다. 그런데 파괴적으로 병합하면 사업자번호는 한 칸뿐이므로 둘 중 하나만 남습니다.

```
병합 후 N: 나루소프트(주) / 222-33-44444 / 월드컵로 2 / 이서연 / 02-2222-3333
```

이제 「이 병합 잘못됐는데요」라는 제보가 들어와도 확인할 방법이 없습니다. **555-66-77777이라는 값이 데이터에서 사라졌으니까요.** 파괴적 병합은 오류를 되돌릴 수 없게 만들기 전에, 오류를 **발견할 수 없게** 만듭니다. 이게 사흘이 걸린 이유입니다. 되돌리는 작업이 어려웠던 게 아니라, 무엇을 어떻게 되돌려야 하는지를 백업과 원장과 사람 기억에서 재구성해야 했던 것입니다.

여기에 「합쳐 놓고 되돌려 보기」를 시도하면 답할 수 없는 질문 목록이 나옵니다.

| 질문 | 파괴적 병합 후 | 비파괴적 병합 후 |
|---|---|---|
| 원래 노드가 몇 개였나? | 모름 (2개인지 3개인지) | `clusters()`로 즉시 |
| 「나루소프트」라는 이름은 어디 갔나? | 소실 | `nodes["r06"]["name"]` |
| r07의 사업자번호는? | 소실 | `nodes["r07"]["bizno"]` |
| 주소를 둘 다 갖고 있었나, 한쪽만? | 모름 (값이 하나로 접혔음) | 둘 다 그대로 있음 |
| 누가 왜 언제 합쳤나? | 모름 | `events` 로그 |

## 2층 — 엣지의 소유가 사라진다

그래프에서는 속성보다 엣지가 더 아픕니다. 노드 두 개를 하나로 접으면 **양쪽에 붙어 있던 관계가 모두 대표 노드로 재배선**되고, 그러면서 「이 관계는 원래 누구 것이었나」가 지워집니다.

병합 전:

```
(r06 나루소프트)  -[:수주]->      (프로젝트 A)
(r06 나루소프트)  -[:소재]->      (월드컵로 2)
(r06 나루소프트)  -[:고용]->      (이서연)
(r07 나루소프트(주))-[:수주]->    (프로젝트 B)
(r07 나루소프트(주))-[:소재]->    (월드컵로 2)
(r07 나루소프트(주))-[:고용]->    (이서연)
```

파괴적 병합 후:

```
(N)-[:수주]->(프로젝트 A)
(N)-[:수주]->(프로젝트 B)
(N)-[:소재]->(월드컵로 2)      ← 엣지 2개가 1개로 «중복 제거»됨
(N)-[:고용]->(이서연)          ← 엣지 2개가 1개로 «중복 제거»됨
```

여기서 세 가지가 동시에 없어집니다.

1. **엣지의 원 소유자.** 프로젝트 A와 B가 각각 r06/r07 중 어디 것이었는지는 엣지에 `origin_node` 같은 흔적을 남기지 않았다면 복원 불가입니다. 되돌릴 때 「수주 계약을 반으로 나누세요」라는 문제가 되는데, 나눌 기준이 데이터에 없습니다.
2. **카디널리티.** `:소재`와 `:고용`은 중복 제거로 2 → 1이 됐습니다. 이제 「둘 다 그 주소였다」와 「r06만 그 주소였다」가 구별되지 않습니다. 되살린 r07에 주소 엣지를 다시 붙여야 하는지 아무도 모릅니다. 그래프에서는 **엣지의 존재 여부 자체가 사실**이므로, 중복 제거는 사실을 지우는 연산입니다.
3. **엣지 속성.** 두 `:수주` 엣지에 계약금액·서명일 같은 속성이 있고 그것까지 접었다면 1층 문제가 엣지에서 한 번 더 반복됩니다.

`ex2_scoring.py`가 경고하는 이행성 문제도 여기서 증폭됩니다.

```
이행성도 공짜가 아니다. 잘못된 병합 하나가 군집 전체를 오염시킨다.
```

r01+r02 → N1, N1+r04 → N2처럼 순차로 접어 나가면, 중간 상태 N1이 어떤 모습이었는지도 남지 않습니다. 잘못된 연결 하나만 끊고 싶어도 접힌 순서와 중간 결과가 없으니 군집 전체를 처음부터 재구성해야 합니다.

## 3층 — 병합 이후 태어난 데이터는 쪼갤 기준이 아예 없다

1층과 2층은 「원본을 어딘가 백업해 뒀다면」 이론적으로는 복구 가능성이 남습니다. 3층은 다릅니다. **백업으로도 해결되지 않습니다.**

병합 후에 세상은 N을 하나의 실체로 알고 굴러갑니다. 그리고 N을 참조하는 새 데이터가 계속 태어납니다.

```
2026-05  (N)-[:수주]->(프로젝트 C)        ← 병합 이후 체결된 신규 계약
2026-06  (거래처평가)-[:대상]->(N)         ← 심사 담당자가 N에 매긴 등급
2026-06  집계: "나루소프트 연매출 합계"     ← N 기준으로 계산된 리포트
2026-07  임베딩 벡터 / 검색 인덱스 / 캐시   ← N의 속성으로 만들어진 파생물
2026-07  외부 API 응답, CSV 내보내기       ← N의 id를 받아 간 하위 시스템
```

이제 unmerge를 시도합니다. **프로젝트 C는 r06 것입니까, r07 것입니까?**

이 질문에는 데이터로 답할 수 있는 정답이 없습니다. 그 계약은 「N이 하나의 회사」인 세계에서 태어났습니다. 담당자도 N을 보고 입력했고, 계약서에도 N의 통합된 이름이 적혔을 수 있습니다. 쪼갤 기준이 **데이터에서 사라진 게 아니라 애초에 생성되지 않았습니다.** 사람이 계약서 원본을 뒤져 판단하는 수밖에 없고, 그게 사흘의 대부분입니다.

같은 이유로 다운스트림 산출물도 전부 다시 만들어야 합니다. 집계, 임베딩, 인덱스, 추천 결과, 이미 외부로 나간 id까지. 특히 **외부 시스템이 캐시한 노드 id**는 파괴적 병합의 `DELETE`로 이미 댕글링 참조가 됐고, 나중에 같은 id로 노드를 다시 만들어도 그 사이 기간의 의미는 복원되지 않습니다.

그래서 「백업 복원」이라는 유혹은 함정입니다. 백업으로 되감으면 1층·2층은 돌아오지만 **병합 이후 생성된 정상 데이터가 같이 날아갑니다.** 파괴적 병합의 롤백은 사실상 시간 되감기밖에 없고, 시간 되감기는 무고한 데이터를 인질로 잡습니다. 이 딜레마 때문에 현실에서는 아무도 롤백을 못 하고 손으로 수습합니다.

### 비파괴적 병합에서 3층은 어떻게 되나

정직하게 말하면, 3층은 비파괴적 병합으로도 **자동 복구되지 않습니다.** 병합 이후 대표 노드를 보고 만들어진 데이터는 여전히 사람이 판단해야 합니다.

하지만 결정적인 차이가 있습니다. `events` 로그에 병합 시각이 남아 있으므로 **「병합 기간 중에 N을 참조해 생성된 것들」의 목록을 정확히 뽑을 수 있습니다.** 유한하고 특정된 작업 목록이 나오는 것입니다. 파괴적 병합에서는 그 목록조차 만들 수 없습니다. 언제 합쳐졌는지도 모르고, 어떤 엣지가 병합 전부터 있었고 어떤 게 후에 생겼는지 구별할 수 없으니까요.

「자동 복구 가능」과 「무엇을 손으로 고쳐야 하는지 목록이 나옴」과 「막막함」은 완전히 다른 상태입니다.

## 대비 — 비파괴적 병합에서 unmerge가 대입 한 번이 되는 이유

`ex3_reversible_merge.py`의 `MergeStore`는 세 가지를 분리해서 들고 있습니다.

| 자료구조 | 성격 | 지우는가 |
|---|---|---|
| `self.nodes` | **사실** — 각 원본이 관측된 그대로의 속성 | 절대 안 지운다 |
| `self.canonical` | **판단** — 지금 누가 누구의 대표인가 (id → id) | 언제든 바꾼다 |
| `self.events` | **이력** — 누가(`by`) 왜(`reason`) 합쳤나 | append만 한다 |

병합은 이 한 줄입니다.

```python
self.canonical[drop] = keep
```

되돌리기는 이 한 줄입니다.

```python
self.canonical[dropped] = dropped
```

이게 「대입 한 번」의 정체입니다. 복원할 값을 **어디서 찾아올 필요가 없습니다.** 애초에 잃지 않았기 때문입니다. `nodes["r07"]`에는 `555-66-77777`이 그대로 앉아 있고, 포인터를 자기 자신으로 돌리는 순간 r07은 자기 값을 그대로 되찾습니다.

그리고 「합쳐진 모습」은 저장하는 대신 **조회할 때 계산합니다.**

```python
def view(self, nid):
    """대표 노드의 속성 + 병합된 것들의 속성을 채워 넣는다."""
```

사용자에게는 여전히 하나의 회사로 보입니다. 다만 그 하나됨이 **저장된 물질(materialized)이 아니라 파생 뷰**라는 게 차이입니다. 파생은 언제든 다시 계산되고, 언제든 취소됩니다.

이걸 원칙 세 줄로 압축하면 이렇습니다.

1. **사실과 판단을 분리한다.** 원본 속성은 불변 사실, 병합은 가변 판단.
2. **파생은 저장하지 않고 계산한다.** 성능상 저장해야 하면 「캐시」로만 두고 언제든 버릴 수 있게 한다.
3. **판단은 append-only 로그로 남긴다.** 되돌리기는 기록의 삭제가 아니라 반대 사건의 추가다. `unmerge`도 `events`에 `{"op": "unmerge", "undoes": i}`로 쌓입니다.

### 대가와, 그 대가가 싼 이유

```
대가는 저장 공간과 조회 비용이다. 조회할 때마다 resolve 를 거쳐야 한다.
제 경우 노드 수가 1.4배가 됐고, 조회에 인덱스 조회 한 번이 더 붙었다.
사흘짜리 사고를 다시 안 겪는 값으로는 쌌다.
```

여기에 `ex4_threshold_tuning.py`의 계산을 겹치면 진짜 이득이 보입니다.

- 오병합 하나 수습 = 평균 2시간 → 검토 180건과 맞먹음 → 그래서 임계를 높게 잡아야 함
- **되돌리기가 대입 한 번이면 오병합 값이 2시간에서 5분으로 떨어짐** → 임계를 낮게 잡아도 됨

즉 되돌릴 수 있게 만드는 일은 안전장치가 아니라 **자동화의 가속 페달**입니다. 「한 장 요약」의 표현대로 *되돌릴 수 있으면 훨씬 공격적으로 자동화할 수 있고요.*

## 같은 모양의 일반 패턴들

노드 병합만의 이야기가 아닙니다. 「지우지 말고 표시하라」는 도처에 있는 패턴입니다.

| 패턴 | 하는 일 | 병합과의 대응 |
|---|---|---|
| **소프트 삭제** | `DELETE` 대신 `deleted_at` 컬럼을 채운다 | 원본 노드를 지우지 않고 `canonical` 포인터만 옮긴다 |
| **툼스톤(tombstone)** | 분산 DB·CRDT에서 삭제를 「삭제 표시 쓰기」로 기록. 삭제도 데이터다 | `unmerge` 이벤트를 로그에 추가하는 것과 같은 발상 |
| **이중 시간(bitemporal)** | valid time(현실에서 언제 참이었나) + transaction time(우리가 언제 그렇게 믿었나)을 따로 둔다 | 잘못된 병합은 현실이 바뀐 게 아니라 **우리 믿음이 틀렸던 것** → transaction time 축에서 정정하고, as-of 질의로 「3월 리포트가 왜 그랬는지」를 재현 |
| **이벤트 소싱** | 상태를 저장하지 않고 사건 로그의 접기(fold)로 얻는다 | `ex3`의 주석대로 「6부 이벤트 소싱의 축소판」 |
| **SCD Type 2** | 데이터 웨어하우스에서 차원 변경을 새 행으로 쌓는다 | 값을 덮어쓰지 않고 이력을 남긴다 |
| **git revert** | 커밋을 지우지 않고 반대 커밋을 쌓는다 | 되돌리기가 이력의 일부가 된다 |

지식 그래프 쪽 표준도 같은 방향입니다.

- [`owl:sameAs`](https://www.w3.org/TR/owl2-syntax/#Individual_Equality)는 논리적으로 매우 강한 선언이라 한번 주장하면 추론이 그래프 전체로 퍼집니다. 확신이 없으면 [`skos:closeMatch`](https://www.w3.org/TR/skos-reference/#mapping) 같은 느슨한 동일성을 쓰는 편이 안전합니다.
- 동일성 선언 자체를 리파이드(reify)해서 점수·근거·판정자·시각을 붙여 두면 그 선언을 **철회 가능한 하나의 사건**으로 다룰 수 있습니다. `events` 로그가 하는 일과 같습니다.
- [PROV-O](https://www.w3.org/TR/prov-o/)는 값 하나하나에 출처를 붙이는 표준 어휘를 줍니다. 1층을 살려 두는 도구입니다.

특히 **이중 시간 모델링**은 3층 문제에 대한 가장 좋은 답에 가깝습니다. 「2026년 3월부터 6월까지 우리는 r06과 r07을 같다고 믿었다」는 사실 자체를 기록해 두면, 그 기간에 생성된 데이터를 왜 그렇게 만들었는지 설명할 수 있고, 그 기간의 리포트를 재현할 수 있고, 무엇을 재작업해야 하는지 목록을 뽑을 수 있습니다.

## 한 줄 정리

파괴적 병합은 여러 값을 한 칸에 접어 넣는 **다대일 사상**이라 역함수가 없습니다. 값의 출처(1층), 엣지의 소유(2층)가 지워지고, 병합 이후 태어난 데이터(3층)에는 쪼갤 기준이 아예 생성되지 않습니다. 그래서 원본을 남기고 대표 노드를 **가리키게만** 하십시오. 그러면 되돌리기가 포인터 한 번 고치는 일이 되고, 되돌리기가 싸지면 자동화를 훨씬 과감하게 밀 수 있습니다.

### 체크리스트

- [ ] 병합할 때 원본 노드를 `DELETE` 하지 않는가
- [ ] 대표 노드는 별도 포인터(`canonical`)로만 표현되는가
- [ ] 「합쳐진 모습」은 저장된 값이 아니라 조회 시 계산되는 뷰인가
- [ ] 누가·왜·언제 합쳤는지 append-only 이력이 남는가
- [ ] 남긴 값마다 어느 원본에서 왔는지(출처)가 함께 저장되는가
- [ ] 엣지를 재배선할 때 원 소유 노드를 기록하는가, 중복 제거로 카디널리티를 지우지 않는가
- [ ] 병합 기간 중 대표 노드를 참조해 생성된 데이터 목록을 뽑을 수 있는가
- [ ] `unmerge`를 실제로 실행해 보고 값이 되돌아오는지 테스트했는가
