# 병합된 값마다 출처를 함께 저장해야 하는 이유

**질문** — 병합된 값마다 출처를 함께 저장해야 하는 이유는 무엇인가?

**답** — "이 대표자 이름 왜 이래요"라는 문의에 답하기 위해서다. 16장에서 자세히 다룬다.

---

## 1. 왜 이 질문이 14장 끝에 나오는가

14장 마지막 절(14.5 어느 값을 남길 것인가)은 생존 규칙(survivorship rule)을 다룹니다. 여러 레코드를 하나로 합칠 때 필드마다 **어느 쪽 값을 남길지** 정하는 규칙이죠. `ex5_survivorship.py`의 맺음말이 이 카드의 출처입니다.

> 그리고 고른 값마다 «어디서 왔는지»를 같이 저장한다.
> 그게 있어야 «이 대표자 이름 왜 이래요» 라는 문의에 답할 수 있다. 16장에서 다룬다.

핵심 논리는 이렇습니다. **생존 규칙은 값을 하나 고르는 순간 나머지를 지워 버립니다.** 규칙이 아무리 잘 설계돼 있어도 결과물만 남으면 "왜 이 값이 이겼는지"를 사후에 재구성할 수 없습니다. 규칙은 코드에 있고 데이터는 DB에 있지만, **둘을 이어 주는 기록**이 없으면 아무도 답을 못 합니다. 그 이음매가 값 단위 출처(provenance)입니다.

---

## 2. 실제로 답해 보기 — `ex5_survivorship.py` 대표자 선택

예제의 입력은 같은 회사의 세 레코드입니다.

| id | 출처(src) | updated | name | ceo | tel | addr |
|---|---|---|---|---|---|---|
| r01 | ERP (신뢰도 3) | 2024-03-01 | 가온테크 | 김하늘 | 02-1234-5678 | 서울 강남구 테헤란로 1 |
| r02 | CRM (신뢰도 2) | 2026-01-15 | (주)가온테크 | 박서준 | — | 서울 강남구 테헤란로 1길 22 |
| r04 | 명함스캔 (신뢰도 1) | 2025-07-09 | GAON TECH | — | 02-1234-5679 | — |

필드별 규칙(`RULES`)과 그 결과는 이렇게 갈립니다.

| 필드 | 규칙 | 선택된 값 | 이긴 레코드 |
|---|---|---|---|
| name | 가장 신뢰도 높은 출처 | 가온테크 | r01 (ERP, 2024-03-01) |
| ceo | 가장 최근 | **박서준** | r02 (CRM, 2026-01-15) |
| tel | 가장 최근 중 비어 있지 않은 것 | 02-1234-5679 | r04 (명함스캔, 2025-07-09) |
| addr | 가장 긴 값 | 서울 강남구 테헤란로 1길 22 | r02 (CRM, 2026-01-15) |

### "이 대표자 이름 왜 이래요"

담당자가 ERP만 보고 일하는 사람이라면, 화면에 뜬 대표자가 **박서준**인 게 이상합니다. ERP에는 김하늘이라고 적혀 있으니까요. 값 단위 출처가 있으면 답이 한 줄로 나옵니다.

```
ceo = "박서준"
  ← source: CRM / record r02 / updated 2026-01-15
  ← rule:   ceo = "가장 최근"
  ← 밀린 후보: "김하늘" (ERP / r01 / 2024-03-01)
```

즉 답은 **"틀린 게 아니라, 대표자는 바뀌는 값이라 최신 출처를 쓰기로 정해 뒀고 CRM이 2026-01-15에 더 최근이라 이겼습니다"** 입니다. 여기서 대화는 세 갈래로만 갈립니다.

1. 규칙이 맞고 데이터도 맞다 → 설명으로 종료. (문의 응대)
2. 규칙은 맞는데 CRM 값이 오입력이다 → 원본 수정 대상은 CRM r02. (데이터 품질 티켓)
3. 이 필드는 최신보다 신뢰도가 우선이어야 한다 → 규칙 변경 대상은 `RULES["ceo"]`. (설계 변경)

출처가 없으면 이 세 갈래를 **구분할 수가 없습니다.** 그래서 대화가 "일단 김하늘로 바꿔 주세요"로 끝나고, 다음 배치에서 다시 박서준으로 덮여서 같은 문의가 또 옵니다.

### 곁들여 보면 더 무서운 것 — 병합 결과는 어느 원본과도 같지 않다

위 표의 병합 결과는 `{가온테크, 박서준, 02-1234-5679, 서울 강남구 테헤란로 1길 22}`인데, **이 조합을 가진 레코드는 어디에도 없습니다.** name은 ERP, ceo와 addr은 CRM, tel은 명함스캔에서 왔습니다. 특히 tel은 신뢰도가 가장 낮은 명함스캔(1점)의 값인데, `tel` 규칙이 "가장 최근"이라 이겼습니다. 명함을 잘못 스캔해 끝자리가 9로 밀렸을 가능성이 꽤 있는 값입니다.

여기서 요점은 **"레코드 단위 출처"로는 부족하다**는 겁니다. "이 회사 정보는 r01/r02/r04를 합친 것"이라는 기록만으로는 전화번호가 명함에서 왔다는 걸 알 수 없습니다. 출처는 **값 단위**여야 쓸모가 있습니다.

## 3. 값 단위 출처로 가능해지는 일 — 용도별

카드의 답은 첫 번째 용도만 짚습니다. 실무에서는 다섯 갈래로 쓰입니다.

### (1) 설명 — 문의 응대
가장 흔하고, 카드가 말하는 그 용도입니다. "왜 이 값인가"에 즉답합니다. 값·출처·시각·규칙 네 개만 있으면 답이 완성됩니다. 이게 없으면 담당자가 파이프라인 코드를 읽고 재현해야 하고, 그러다 원인을 못 찾으면 값을 수동으로 덮어씁니다. **수동 덮어쓰기가 늘어나면 파이프라인은 신뢰를 잃고 결국 아무도 안 씁니다.**

### (2) 감사·규제 대응
"이 고객의 주소를 언제, 어느 시스템에서 받아 왔는가"에 답해야 하는 상황들이 있습니다. 개인정보 처리 이력, 삭제 요청(잊힐 권리) 대응, 금융·의료 데이터의 계보(lineage) 요구, 내부 감사. 이때 필요한 건 사람이 읽는 설명이 아니라 **기계가 뽑아 주는 목록**입니다. 값 단위 출처가 있으면 "출처 X에서 온 값 전부"를 질의로 뽑을 수 있습니다. 없으면 전수 조사입니다.

특히 삭제 요청은 값 단위여야 실행이 됩니다. 병합된 노드에서 특정 출처가 준 값만 지워야 하는데, 어느 값이 그 출처에서 왔는지 모르면 노드 전체를 지우거나 아무것도 못 지웁니다.

### (3) 디버깅 — 규칙이 잘못 골랐나 vs 원본이 틀렸나
이게 엔지니어에게 가장 값비싼 용도입니다. 잘못된 값을 봤을 때 원인은 딱 두 종류입니다.

- **원본이 틀렸다**: CRM에 대표자가 오입력돼 있다. → 고칠 곳은 CRM. 파이프라인은 정상 동작했다.
- **규칙이 잘못 골랐다**: 원본은 다 맞는데 `RULES["ceo"] = "가장 최근"`이 이 도메인에 안 맞았다. → 고칠 곳은 규칙. 같은 유형의 오류가 **다른 수천 건에도 똑같이 깔려 있다.**

두 번째가 진짜 무섭습니다. 하나를 보고 "이건 규칙 문제구나"를 알아채면 나머지 수천 건을 한 번에 잡을 수 있습니다. 출처에 `rule` 필드를 같이 남기는 이유가 이겁니다. **어떤 규칙이 이 값을 뽑았는지**를 알면 같은 규칙이 뽑은 값을 전부 재검토 대상으로 긁어올 수 있습니다.

```
# 출처에 rule 을 남겨 두면 이런 질의가 가능해진다
"ceo 필드에서 '가장 최근' 규칙이 명함스캔을 선택한 건수" → 규칙 오적용 범위 파악
"명함스캔이 이긴 tel 값 전부"                          → 저품질 출처 영향 범위
```

### (4) 신뢰도 갱신 — 어느 출처가 자주 틀리는지 측정
`ex5_survivorship.py`의 `SOURCE_TRUST = {"ERP": 3, "CRM": 2, "명함스캔": 1}`은 **손으로 적은 숫자**입니다. 처음에는 감으로 정할 수밖에 없습니다. 그런데 값 단위 출처를 쌓아 두면 이 숫자를 데이터로 바꿀 수 있습니다.

- 사람이 정정한 값이 있을 때, **정정 전 값이 어느 출처에서 왔는지** 집계합니다.
- "명함스캔이 이긴 값의 정정률 12%, ERP가 이긴 값의 정정률 0.8%" 같은 숫자가 나옵니다.
- 그 숫자로 `SOURCE_TRUST`를 갱신합니다. 필드별로 다르게 나오는 경우도 흔합니다(ERP는 사업자번호가 정확하지만 전화번호는 오래됐고, CRM은 반대).

이게 값 단위 출처의 진짜 복리 효과입니다. 출처를 기록하는 것만으로 **다음 라운드의 규칙 품질이 올라갑니다.** 기록이 없으면 신뢰도 숫자는 3년 뒤에도 처음 감으로 적은 값 그대로 있습니다. 14장 4절(임계 조정)과 같은 사고방식입니다. 측정할 수 없으면 조정할 수 없습니다.

### (5) 선택적 되돌리기 — 특정 출처만 무효화
14장 3절이 노드 단위 되돌리기(`unmerge`)를 다뤘습니다. 값 단위 출처는 여기서 한 칸 더 내려갑니다.

- "명함스캔 2025년 7월 배치가 OCR 설정 오류였다" → 그 배치가 이긴 값만 무효화하고 차순위 후보로 재선택.
- "CRM 마이그레이션 때 대표자 컬럼이 밀렸다" → CRM 출처의 `ceo` 값만 걷어 내고 재계산.
- 노드를 다시 쪼개지 않고, **필드 하나만 롤백**합니다.

`ex3_reversible_merge.py`의 `unmerge`는 "이 두 노드를 합친 게 잘못이었다"를 되돌립니다. 값 단위 출처는 "합친 건 맞는데 이 필드에서 저 출처를 쓴 게 잘못이었다"를 되돌립니다. 실무에서 후자가 훨씬 자주 필요합니다. 병합 판단은 대개 맞고, 틀리는 건 **어느 값을 남길지**니까요.

## 4. 저장 형태의 선택지

세 가지 방식이 실무에서 쓰입니다. 정답은 없고, 조회 패턴과 저장 예산이 정합니다.

### (A) 필드별 사이드카 — `{value, source, ts, rule}`

값 옆에 메타데이터를 나란히 붙입니다.

```json
{
  "id": "org:gaontech",
  "name": {"value": "가온테크", "source": "ERP/r01",  "ts": "2024-03-01",
           "rule": "trust_max", "losers": ["(주)가온테크@CRM/r02", "GAON TECH@명함스캔/r04"]},
  "ceo":  {"value": "박서준",   "source": "CRM/r02",  "ts": "2026-01-15",
           "rule": "recency_max", "losers": ["김하늘@ERP/r01"]},
  "tel":  {"value": "02-1234-5679", "source": "명함스캔/r04", "ts": "2025-07-09",
           "rule": "recency_nonempty", "losers": ["02-1234-5678@ERP/r01"]}
}
```

| | |
|---|---|
| **장점** | 조회가 조인 없이 끝난다. "이 값 왜 이래요"에 **한 번의 읽기**로 답한다. UI에 출처 배지를 붙이기 쉽다. 구현이 단순하고 스키마가 자기 설명적이다. |
| **단점** | 스키마가 값 하나에 4~5배로 부풀고, 필드마다 중첩 객체라 기존 질의를 전부 고쳐야 한다. 이력이 아니라 **최종 상태만** 남으므로 "지난달에는 어떤 값이었나"에 답 못 한다(`losers`를 넣어도 한 세대분뿐). 배열·다중값 필드에서 구조가 지저분해진다. |
| **언제** | 문의 응대와 UI 표시가 주 용도이고, 시계열 추적은 필요 없을 때. 대부분의 프로젝트가 여기서 시작하면 충분합니다. |

### (B) 병합 이벤트 로그에서 역추적

`ex3_reversible_merge.py`의 `self.events`를 필드 단위까지 확장합니다. 병합 결과 자체에는 값만 두고, "왜 그 값인지"는 로그를 재생해서 답합니다.

```python
events = [
  {"op": "merge", "keep": "r01", "drop": "r02", "by": "auto", "reason": "사업자번호 일치"},
  {"op": "pick",  "node": "r01", "field": "ceo", "rule": "recency_max",
   "won": {"src": "CRM/r02", "value": "박서준", "ts": "2026-01-15"},
   "lost": [{"src": "ERP/r01", "value": "김하늘", "ts": "2024-03-01"}]},
]
```

| | |
|---|---|
| **장점** | 저장이 **추가만** 하는 구조라 현재 상태 스키마를 건드리지 않는다. 시간축 전체가 남아서 "3월엔 왜 김하늘이었나"에도 답한다. 감사 대응에 가장 강하다. 되돌리기가 로그 재생으로 자연스럽게 나온다. 6부 이벤트 소싱과 그대로 이어진다. |
| **단점** | 답하려면 **재생·역추적이 필요**해서 조회가 느리다. 로그가 단조 증가하므로 보존 정책·압축·스냅샷이 필수다. 규칙 코드가 바뀌면 과거 로그의 `rule` 이름이 지금 코드와 안 맞는 문제(코드 버전 관리)가 생긴다. |
| **언제** | 감사 요구가 있거나, 되돌리기를 자주 하거나, 이미 이벤트 소싱을 쓰고 있을 때. 실무에서는 **(A)와 (B)를 같이** 두는 경우가 많습니다. 로그가 정본(source of truth)이고 사이드카는 조회용 투영(projection)입니다. |

### (C) RDF reification / PROV-O

그래프 표준으로 하는 방식입니다. "트리플에 대한 트리플"을 붙입니다.

```turtle
# PROV-O 로 값 하나의 유래를 기술
:ceo_assertion_001
    a prov:Entity ;
    rdf:subject :org_gaontech ; rdf:predicate :ceo ; rdf:object "박서준" ;
    prov:wasDerivedFrom :crm_record_r02 ;
    prov:wasGeneratedBy  :survivorship_run_20260115 ;
    prov:wasAttributedTo :crm_system ;
    prov:generatedAtTime "2026-01-15T00:00:00Z"^^xsd:dateTime .

:survivorship_run_20260115
    a prov:Activity ;
    :usedRule "ceo = recency_max" ;
    prov:used :erp_record_r01, :crm_record_r02, :card_scan_r04 .
```

| | |
|---|---|
| **장점** | **표준 어휘**라 도구·검증기·다른 조직과 호환된다([PROV-O](https://www.w3.org/TR/prov-o/)). Entity/Activity/Agent 삼분법이 "무엇이, 무슨 작업으로, 누구에 의해"를 강제해서 빠뜨리는 항목이 적다. 출처 자체에 대한 출처(이차 provenance)도 자연스럽게 표현된다. 값뿐 아니라 **관계(엣지)의 출처**도 같은 방식으로 붙는다. |
| **단점** | 저장 폭발이 가장 심하다. 고전적 RDF reification은 트리플 하나에 최소 4트리플이 붙고, PROV-O 어휘까지 붙이면 6~10트리플이 된다. 질의가 눈에 띄게 복잡해지고(원래 트리플 패턴 하나가 reification 조인 여러 개로), 대부분의 트리플스토어에서 성능이 떨어진다. 학습 곡선도 있다. |
| **언제** | 그래프가 정본이고 외부와 데이터를 교환하거나 규제 대응이 필요할 때. **중간 대안**을 먼저 검토하세요. 이름 붙은 그래프(named graph / 쿼드)로 "출처별 그래프"를 두면 출처 단위 격리·무효화가 훨씬 싸게 됩니다. RDF-star(따온 트리플)를 쓸 수 있는 스토어라면 reification 대비 문법과 저장량이 크게 줄어듭니다. |

### 저장 비용 — 곱셈으로 늘어난다

값 단위 출처의 대가는 정직하게 곱셈입니다.

- 사이드카: 필드마다 `{value, source, ts, rule}` → 값 하나가 **4~5배**. 밀린 후보(`losers`)까지 남기면 더 늘어납니다.
- 이벤트 로그: 저장이 단조 증가. 병합 대상 레코드 수 × 필드 수만큼 `pick` 이벤트가 쌓입니다.
- reification: 트리플 하나가 **5~10트리플**. 관계까지 덮으면 그래프가 한 자릿수 배로 커집니다.

14장 3절이 이미 같은 종류의 대가를 언급합니다. 원본을 안 지우는 대가로 노드 수가 1.4배가 됐고 조회에 인덱스 조회가 한 번 더 붙었다고요. 값 단위 출처는 그 위에 곱해집니다. 그래서 실무에서는 **전부 다 남기지 않습니다.**

- 문의가 실제로 들어오는 필드에만 붙입니다(대표자, 주소, 전화처럼 사람이 보는 필드). 내부 계산용 파생 필드는 생략.
- 밀린 후보(`losers`)는 상위 1~2개만.
- 시계열은 최근 N세대만 유지하고 그 이전은 압축·아카이브.
- 자동 병합과 사람 판정을 구분해서, 사람이 개입한 값은 절대 압축하지 않습니다(가장 비싼 정보니까요).

## 5. 14장과 16장의 역할 분담

카드의 답이 "16장에서 자세히 다룬다"로 끝나는 게 우연이 아닙니다. 두 장은 같은 문제의 앞뒤입니다.

| | **14장 — 생존 규칙** | **16장 — 출처 추적** |
|---|---|---|
| 묻는 것 | 어느 값을 **남길 것인가** | 남은 값이 **어디서 왔는가** |
| 시점 | 병합하는 순간 (쓰기) | 병합한 뒤 (읽기·감사) |
| 산출물 | 병합된 값 하나 | 그 값에 붙은 `{source, ts, rule}` |
| 표준·키워드 | survivorship rules [실험] | [PROV-O](https://www.w3.org/TR/prov-o/) [표준] |
| 답하는 질문 | "이 회사의 대표자는 누구인가" | "이 대표자 이름 왜 이래요" |
| 예제 | `ex5_survivorship.py` | 16장 |

14장은 **결정**을 다루고, 16장은 그 결정의 **기록**을 다룹니다. 14장만 있으면 값은 나오지만 설명이 안 되고, 16장만 있으면 기록할 결정이 없습니다.

그리고 5절 맺음말의 두 문장이 사실 같은 이야기입니다.

> 규칙이 없으면 개발자가 그때그때 정하고, 6개월 뒤에 아무도 이유를 모른다.
> 그리고 고른 값마다 «어디서 왔는지»를 같이 저장한다.

앞 문장은 **규칙을 코드에 못 박으라**는 요구(14장), 뒷 문장은 **적용 결과를 데이터에 남기라**는 요구(16장)입니다. 둘 다 목적이 하나입니다. **6개월 뒤에 이유를 알 수 있게 하는 것.** 규칙만 박아 두면 "우리 규칙은 최신 우선입니다"까지는 말할 수 있지만, **이 값**에 그 규칙이 어떻게 적용됐는지는 여전히 재현해 봐야 압니다. 값 단위 출처가 그 재현을 없앱니다.

## 6. 한 줄로

병합은 정보를 **버리는** 연산입니다. 버린 것 중 최소한 "무엇을 왜 골랐는지"만은 남겨 둬야 문의에 답할 수 있고, 그 기록이 있어야 디버깅·감사·신뢰도 갱신·선택적 되돌리기까지 딸려 옵니다. 대가는 저장량 곱셈이고, 그래서 **사람이 실제로 보는 필드에만** 붙이는 게 현실적인 타협입니다.
