# 병합할 때 원본을 지우지 말아야 하는 이유

> **Q.** 병합할 때 원본을 지우지 말아야 하는 이유는 무엇인가?
>
> **A.** 대표 노드를 가리키게만 하면 되돌리기가 포인터 하나 고치는 일이 된다. 되돌릴 수 있으면 훨씬 공격적으로 자동화할 수 있다.

14장 3절 「되돌릴 수 있게 병합하라」의 핵심입니다. 답이 두 문장인데, 뒤 문장이 진짜 결론입니다. 앞 문장은 기법이고, 뒤 문장은 그 기법이 바꿔 놓는 **의사결정 구조**입니다.

---

## 1. 상황: 엔티티 해상도는 반드시 틀린다

14장의 데이터는 같은 회사가 네 가지 표기로 앉아 있는 상황입니다.

| id | 이름 | 사업자번호 | 주소 | 대표자 |
|---|---|---|---|---|
| r01 | 가온테크 | 123-45-67890 | 서울 강남구 테헤란로 1 | 김하늘 |
| r04 | GAON TECH | 123-45-67890 | (없음) | (없음) |
| r06 | 나루소프트 | **222-33-44444** | 서울 마포구 월드컵로 2 | 이서연 |
| r07 | 나루소프트(주) | **555-66-77777** | 서울 마포구 월드컵로 2 | 이서연 |

- r01–r04는 **합쳐야 하는** 쌍입니다 (사업자번호 동일).
- r06–r07은 **합치면 안 되는** 쌍입니다. 주소·대표자·전화가 전부 같은데 사업자번호가 다릅니다. 모회사와 자회사예요.

점수 기반 매칭은 r06–r07에서 0.550을 냅니다. 애매 구간 바닥이죠. 저자는 실제로 자동 병합 임계를 0.55로 낮췄다가 이 둘을 합쳐 버렸고, **되돌리는 데 사흘**이 걸렸습니다. 즉 오병합은 "혹시" 일어나는 사고가 아니라 규모가 커지면 반드시 일어나는 일입니다. 그래서 질문은 "어떻게 안 틀릴까"가 아니라 "틀렸을 때 어떻게 되돌릴까"가 됩니다.

---

## 2. 기법: 지우지 않고 「가리키게」 한다

### 파괴적 병합 (하지 말아야 할 것)

```
r06 { name:"나루소프트",  bizno:"222-33-44444", ... }
r07 { name:"나루소프트(주)", bizno:"555-66-77777", ... }
        │
        ▼  속성을 골라 합치고 r07 은 DELETE
r06 { name:"나루소프트", bizno:"222-33-44444", ... }   ← r07 은 사라짐
```

r07의 `555-66-77777`이 어디에도 남아 있지 않습니다. 되돌리려면 원본 소스에서 다시 적재하거나, 로그를 파헤쳐 "이 값이 어디서 왔는지"를 역추적해야 합니다. 게다가 그동안 r07을 참조했던 관계·질의·다운스트림 결과까지 손으로 고쳐야 하죠. 그게 사흘입니다.

### 되돌릴 수 있는 병합 (`ex3_reversible_merge.py`)

원본 노드는 그대로 두고, `canonical`이라는 **대표 노드 포인터**만 옮깁니다.

```
nodes     : r06 { ... 222-33-44444 ... }   r07 { ... 555-66-77777 ... }   ← 절대 안 지운다
canonical : r06 → r06                     r07 → r06                      ← 여기만 바뀐다
events    : [ {op:"merge", keep:"r06", drop:"r07", by:"auto", reason:"주소·대표자·전화 일치"} ]
```

코드에서 병합의 본체는 사실상 한 줄입니다.

```python
self.canonical[drop] = keep          # 병합 = 포인터 대입
```

되돌리기도 정확히 대칭인 한 줄입니다.

```python
self.canonical[dropped] = dropped    # unmerge = 포인터 원복
```

조회는 `resolve()`가 포인터를 따라가 대표 id를 찾고, `view()`가 군집 구성원들의 속성을 「정보가 많은 순」으로 채워 넣어 병합된 것처럼 보여 줍니다. 즉 **보이는 결과는 병합, 저장된 실체는 원본 유지**입니다.

### 실제 실행 결과

```
1) 맞는 병합
   r04 를 조회하면 → 대표 r01, 구성원 ['r01', 'r04']
   합쳐진 값: 가온테크 / 123-45-67890 / 김하늘

2) 틀린 병합 — 모회사와 자회사를 합쳐 버렸다
   군집: {'r01': ['r01', 'r04'], 'r06': ['r06', 'r07']}

3) 되돌린다
   unmerge 성공: True
   군집: {'r01': ['r01', 'r04']}
   r07 이 자기 값을 되찾았나: 나루소프트(주) / 555-66-77777

4) 이력
   [0] {'op': 'merge', 'keep': 'r01', 'drop': 'r04', 'by': 'auto', 'reason': '사업자번호 일치'}
   [1] {'op': 'merge', 'keep': 'r06', 'drop': 'r07', 'by': 'auto', 'reason': '주소·대표자·전화 일치'}
   [2] {'op': 'unmerge', 'target': 'r07', 'undoes': 1}
```

3)에서 r07이 자기 사업자번호 `555-66-77777`을 **온전히** 되찾은 게 요점입니다. 파괴적 병합이었다면 이 값은 이미 없습니다.

이력(`events`)도 같이 보세요. 병합이 상태 변경이 아니라 **사건**으로 쌓입니다. `unmerge`조차 지우지 않고 `{"op":"unmerge", "undoes":1}`로 덧붙습니다. 파일 주석대로 "6부 이벤트 소싱의 축소판"이고, 덕분에 `by`(자동/사람)와 `reason`이 남아 "이 병합 누가 왜 했나"에 답할 수 있습니다.

## 3. 결론: 되돌릴 수 있으면 공격적으로 자동화할 수 있다

여기가 카드의 두 번째 문장이고, 시험에 나오면 이쪽이 답입니다.

임계를 정하는 계산은 결국 **오병합 하나의 비용 vs 사람 한 건 검토 비용**의 비교입니다. `ex4_threshold_tuning.py`의 저자 수치:

| 항목 | 비용 |
|---|---|
| 사람 한 건 검토 | 약 40초, 환산 400원 |
| 오병합 하나 수습 (파괴적 병합) | 평균 **2시간** (원인 파악 + 되돌리기 + 영향받은 질의 확인) |
| → 환산 | 오병합 1건 ≈ 검토 **180건** |

오병합이 검토 180건 값이면 임계를 높게 잡는 게 합리적입니다. 자동 병합을 줄이고 사람을 많이 보게 하는 쪽이죠. 임계별 트레이드오프는 이렇게 나옵니다.

```
자동임계  검토하한   정밀도   재현율   오병합    놓침   사람검토
  0.95     0.80    0.963   0.195       3     136      243
  0.90     0.70    0.911   0.357      14      35      514
  0.85     0.55    0.898   0.527      24       0    2,053
  0.75     0.55    0.701   0.797     136       0    1,833
  0.65     0.50    0.379   0.975     638       0    2,262
  0.55     0.50    0.175   1.000   1,888       0    1,002
```

그런데 되돌리기가 포인터 대입 한 번이면 **오병합 하나의 값이 2시간에서 5분으로 떨어집니다.** 분모가 24배 작아지니 같은 오병합 24건이 예전 오병합 1건 값밖에 안 됩니다. 그러면 임계를 0.90에서 0.75로 내려 재현율을 0.357 → 0.797로 끌어올리고 사람 검토를 줄이는 선택이 갑자기 합리적인 결정이 됩니다.

즉 인과의 방향은 이렇습니다.

```
원본을 안 지운다 → 되돌리기가 싸진다 → 오병합의 기대비용이 낮아진다
                → 임계를 낮춰도 된다 → 자동화 범위가 넓어진다
```

**되돌리기 설계가 자동화 범위를 결정합니다.** 안전장치를 먼저 만들면 더 과감해질 수 있다는 얘기고, 이건 롤백 가능한 배포가 배포 빈도를 올리는 것과 정확히 같은 구조입니다.

---

## 4. 대가는 무엇인가 (같이 알아야 하는 부분)

공짜는 아닙니다. 저자가 정직하게 적어 둔 비용:

- **저장 공간**: 원본을 안 지우니 노드 수가 **1.4배**가 됐습니다.
- **조회 비용**: 모든 조회가 `resolve()`를 거쳐야 합니다. 인덱스 조회 한 번이 더 붙었습니다.
- **구현 복잡도**: 대표 노드 선정 규칙(`_richness` — 정보가 더 많은 쪽), 포인터 체인 순환 방지(`seen` 집합), 군집 뷰 조립이 모두 필요합니다.

저자의 판정은 "사흘짜리 사고를 다시 안 겪는 값으로는 쌌다"입니다. 되돌릴 수 없는 파괴적 병합에서 사고 한 번이 사흘이면, 1.4배 저장 공간과 인덱스 조회 한 번은 싼 보험입니다.

## 5. 함께 묶어 두면 좋은 것들

- **대표 노드 선정 규칙을 못 박아라**: `keep`은 「정보가 더 많은」 쪽. 즉석에서 정하면 6개월 뒤 아무도 이유를 모릅니다(5절 생존 규칙과 같은 정신).
- **거부권 규칙**: 점수가 아무리 높아도 사업자번호가 다르면 다른 법인. r06–r07은 애초에 이 규칙으로 막는 게 정석이고, 되돌리기는 그 규칙이 못 막은 것에 대한 2차 방어선입니다.
- **이행성 오염**: 잘못된 병합 하나가 군집 전체를 오염시킵니다. 원본이 남아 있어야 오염된 군집을 다시 쪼갤 수 있습니다.
- **표준 어휘**: 「같다」를 파괴적으로 합치는 대신 `owl:sameAs`(강한 동일성)나 `skos:closeMatch`(느슨한 동일성)로 **선언**하는 것도 같은 발상입니다. 선언은 지울 수 있고, 삭제는 지울 수 없습니다.
- **출처 추적(PROV-O)**: 원본이 남아 있으면 "이 대표자 이름 왜 이래요"에 답할 수 있습니다(16장).

---

## 한 줄 정리

원본을 지우지 않고 대표 노드 포인터만 옮기면 병합은 `canonical[drop] = keep`, 되돌리기는 `canonical[drop] = drop` — 대입 한 번이 됩니다. 되돌리기가 2시간에서 5분이 되면 오병합의 기대비용이 무너지고, 그래서 임계를 낮춰 **더 공격적으로 자동화할 수 있게** 됩니다.
