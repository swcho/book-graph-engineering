# 자동 병합 임계를 0.55로 낮췄다면 무슨 일이 벌어졌는가?

> **답**: 모회사와 자회사를 합쳐 버렸을 것이다. 저자는 실제로 그렇게 했고, 되돌리는 데 사흘이 걸렸다.

---

## 1. 먼저 구조: 임계는 하나가 아니라 두 개다

14장 예제 2(`ex2_scoring.py`)는 임계를 두 개 둔다.

```python
HIGH, LOW = 0.85, 0.55
```

- `점수 >= HIGH(0.85)` → **자동 병합**
- `LOW(0.55) <= 점수 < HIGH` → **사람 검토**
- `점수 < LOW` → **무시**

질문이 말하는 "임계를 0.55로 낮췄다면"은 **HIGH를 0.55로 내렸다는 뜻**이다. 즉 원래 사람에게 보내려고 만들어 둔 애매 구간(0.55~0.85)을 전부 자동 병합으로 삼켜 버리는 것이다. 이 구간은 "자동화가 판단을 유보한 영역"이었는데, 그 유보를 없애 버린 셈이다.

점수 함수는 가중합이고, **한쪽이 비어 있는 필드는 «모름»으로 빼서 분모에서 제외**한다.

| 필드 | 가중치 | 비교 방식 |
|---|---|---|
| 사업자번호 | 0.45 | exact |
| 이름(법인격 표기 제거) | 0.25 | fuzzy(2-gram 자카드) |
| 주소 | 0.15 | fuzzy |
| 대표자 | 0.10 | exact |
| 전화(숫자만) | 0.05 | exact |

## 2. 임계를 0.85 → 0.55로 내리면 새로 자동 병합되는 쌍 (실제 점수)

`records.py`의 12개 레코드로 66쌍 전부 채점하면 0.4 이상은 아래 8쌍뿐이다.

| 쌍 | 점수 | 0.85 기준 | **0.55 기준** | 정답 |
|---|---|---|---|---|
| r01–r02 (가온테크 / (주)가온테크) | **1.000** | 자동 병합 | 자동 병합 | 같음 ✅ |
| r01–r03 (가온테크 / 가온테크 주식회사) | **0.973** | 자동 병합 | 자동 병합 | 같음 ✅ |
| r02–r03 | **0.973** | 자동 병합 | 자동 병합 | 같음 ✅ |
| r11–r12 (마루상사 / 머루상사) | **0.875** | 자동 병합 | 자동 병합 | 같음 ✅ |
| r01–r04 (가온테크 / GAON TECH) | **0.643** | 사람 검토 | **← 새로 자동 병합** | 같음 ✅ |
| r02–r04 | **0.643** | 사람 검토 | **← 새로 자동 병합** | 같음 ✅ |
| **r06–r07 (나루소프트 / 나루소프트(주))** | **0.550** | 사람 검토 | **← 새로 자동 병합** | **다름 ❌** |
| r08–r09 (다올물산 본사 / 부산지점) | 0.533 | 무시 | 무시 (간발의 차) | 다름 ✅ |

### 결과 군집 비교

```
정답(TRUTH)            : {r01,r02,r03,r04}, {r11,r12}

HIGH=0.85 자동 병합 4쌍 : {r01,r02,r03}, {r11,r12}
                          → r04 를 못 붙였다(사람 검토로 넘어감). 안전한 실패.

HIGH=0.55 자동 병합 7쌍 : {r01,r02,r03,r04}, {r11,r12}, {r06,r07}  ← 이게 사고다
                          → r04 는 공짜로 얻었지만, 별개 법인 두 개를 합쳤다.
```

**핵심 대비**: 임계를 내려서 얻은 것은 "r04를 사람 안 거치고 붙였다"는 편의 하나. 잃은 것은 **서로 다른 법인의 동일성을 그래프에 사실로 박아 넣은 것**이다. 얻은 쪽은 사람 40초를 아끼고, 잃은 쪽은 사흘이 든다.

### 왜 하필 0.550인가 — 우연이 아니다

r06–r07의 필드별 점수를 뜯어보면 이렇다.

| 필드 | 값 비교 | 점수 | 가중치 |
|---|---|---|---|
| 사업자번호 | `222-33-44444` vs `555-66-77777` | **0.00** | 0.45 |
| 이름 | `나루소프트` vs `나루소프트` (「(주)」 제거 후) | 1.00 | 0.25 |
| 주소 | `서울 마포구 월드컵로 2` 동일 | 1.00 | 0.15 |
| 대표자 | `이서연` 동일 | 1.00 | 0.10 |
| 전화 | `02-2222-3333` 동일 | 1.00 | 0.05 |

$$(0.25+0.15+0.10+0.05) / 1.00 = 0.55$$

**0.55는 「사업자번호만 다르고 나머지 전부 완전 일치」일 때 나오는 정확한 점수다.** 사업자번호 가중치 0.45가 이 설계의 유일한 방어선이었고, 자동 임계를 0.55로 내리는 순간 그 방어선이 **정확히, 딱 맞게** 무력화된다. 부동소수점으로도 정확히 `0.55`가 나오고 `>=` 비교라서 경계에서 통과한다.

그리고 이런 쌍은 실무에서 가장 흔한 유형이다. 모·자회사, 계열사, 인적분할 직후의 신설법인 — **같은 사무실, 같은 대표, 같은 대표전화, 사업자번호만 다름**. 임계 0.55는 "가장 헷갈리는 유형을 전부 자동 병합한다"와 같은 말이다.

r08–r09(0.533)가 0.017 차이로 살아남은 것도 운이다. 임계를 0.53으로 뒀다면 본사와 부산지점까지 한 노드가 됐을 것이다. **임계 0.02 차이가 도메인 결정을 뒤집는다** — 임계는 이렇게 미세한 손잡이라서, 여기에 안전을 걸어 두면 안 된다.

## 3. 왜 「사흘」이 걸리는가

오병합 하나를 수습하는 비용은 예제 4(`ex4_threshold_tuning.py`)에서 이렇게 적혀 있다.

```
사람 한 건 검토 : 약 40초, 인건비 환산 400원
오병합 하나 수습 : 평균 2시간 (원인 파악 + 되돌리기 + 영향 받은 질의 확인)
→ 오병합 하나 = 검토 180건
```

평균이 2시간인데 이 사건은 사흘이 걸렸다. 차이를 만드는 것이 아래 네 가지다.

### (a) 되돌리기 불가능한 병합 — 어느 값이 어디서 왔는지 모른다

노드를 실제로 지우고 속성을 합치는 방식(`DELETE` + 속성 머지)에서는 병합이 **비가역 연산**이 된다. 예제 3의 `view()`는 대표 노드 속성에 나머지 값을 "빈 칸만 채우는" 방식으로 합치는데, **충돌하는 값은 그냥 버려진다**.

r06/r07은 채워진 필드 수가 5개로 동률이므로 `_richness(ca) >= _richness(cb)`에 따라 `keep=r06`, `drop=r07`이 된다. 합쳐진 노드의 사업자번호는 `222-33-44444` 하나만 남고, **r07의 `555-66-77777`은 사라진다.**

여기서부터가 재앙이다.

- 남은 노드에 사업자번호가 하나뿐이니 **사후에 "이건 두 법인이 합쳐진 것"이라는 신호 자체가 없다.** 오병합을 탐지할 단서가 지워진 것이다.
- 이 사건을 발견하는 경로는 보통 그래프 내부가 아니라 **밖**이다. 세금계산서가 엉뚱한 법인 앞으로 나가거나, 영업이 "이 회사 매출이 왜 이래요"라고 문의하거나. 그러니 **발견 자체가 며칠 늦다.**
- 되돌리려면 사라진 값을 **원천 시스템(ERP/CRM/명함스캔)에서 다시 긁어와 재구성**해야 한다. 그 사이 원천 값이 갱신됐다면 "병합 당시의 값"을 복원할 방법이 없다.
- 생존 규칙(예제 5)이 필드마다 다르므로, 복원은 필드별 역추적이다. 이름은 신뢰도 높은 출처, 대표자는 가장 최근, 주소는 가장 긴 값 — **규칙이 다르면 역함수도 필드마다 다르고, 애초에 역함수가 없는 규칙도 있다.**

이것이 14장이 "**원본을 지우지 마세요**"를 한 장 요약의 첫 줄급으로 올려 둔 이유다.

### (b) 병합 이후에 만들어진 엣지

병합한 뒤에도 파이프라인은 계속 돈다. 합쳐진 대표 노드에 새 엣지가 붙는다.

```
(계약) ─┐
(발주) ─┼→ [나루소프트(합쳐진 노드)] ←─ (담당자)
(청구) ─┘                             ←─ (세금계산서)
```

되돌릴 때 문제는 이거다. **이 엣지들이 r06 것인지 r07 것인지 그래프 안에는 답이 없다.** 병합 이후에 생긴 엣지는 애초에 "합쳐진 하나의 회사"를 향해 붙었으니까. 판단하려면 그래프를 떠나 계약서·전표·원장을 사람이 대조해야 한다. **사흘의 대부분이 여기서 나간다.** 이건 자동화로 줄일 수 없는 시간이다.

거꾸로 병합 이전 엣지도 안전하지 않다. `drop` 노드에 붙어 있던 엣지를 `keep`으로 옮기는(rewire) 구현이라면, 옮기면서 원래 출발점 정보를 남기지 않았다면 그것도 복원 불가다.

### (c) 다운스트림 산출물 오염

그래프는 종점이 아니다. 오염이 흘러간 곳을 전부 되감아야 한다.

| 산출물 | 오염 형태 | 수습 |
|---|---|---|
| 집계/마트 테이블 | 두 법인 매출·거래건수 합산 | 재계산 (기간 전체) |
| 임베딩·검색 인덱스 | 합쳐진 속성으로 벡터화 | 재색인 |
| 캐시 / 머티리얼라이즈 뷰 | 잘못된 조회 결과 고정 | 무효화 + 재생성 |
| 리포트·대시보드 | 이미 배포된 숫자가 틀림 | 정정 공지 |
| 외부로 나간 API 응답 | 회수 불가 | 소비 측에 통보, 재동기화 요청 |
| ML 학습 데이터 | 라벨이 오염된 상태로 학습됨 | 재학습 |

이 중에 **되감을 수 없는 것이 하나라도 있으면 시간은 시간으로 안 끝난다.** 밖으로 나간 데이터는 회수가 아니라 통보와 협의의 문제가 되고, 그건 시간이 사람 일정에 묶인다.

그리고 재계산에는 **순서가 있다.** 그래프를 먼저 고치고 → 마트를 재계산하고 → 인덱스를 다시 만들고 → 캐시를 비운다. 순서를 어기면 방금 고친 그래프 위에 옛 캐시가 다시 얹힌다. 이 직렬 의존이 "2시간 작업"을 "사흘 작업"으로 늘린다.

### (d) 이행성이 오염을 군집 전체로 번지게 한다

예제 2는 자동 병합 쌍을 union-find로 묶는다.

```python
parent = {k: k for k in BY_ID}
def union(x, y): parent[find(x)] = find(y)
for a, b in auto:
    union(a, b)
```

여기서 **임계는 「쌍」 단위로 판정하는데 결과는 「군집」 단위로 나온다.** 이 불일치가 오염 증폭기다.

**메커니즘 1 — 나쁜 엣지 하나가 두 군집의 곱만큼 거짓을 만든다.**
r06 쪽에 표기 변종이 이미 3개 묶여 있고 r07 쪽에도 3개가 묶여 있었다면, r06–r07 엣지 **한 개**가 6개 노드를 한 군집으로 만든다. 이때 새로 주장된 거짓 동일성은 1개가 아니라 3 × 3 = **9쌍**이다. 일반적으로 |A| × |B|. 오염은 선형이 아니라 **곱으로** 번진다.

**메커니즘 2 — 다리(bridge)를 찾을 수 없다.**
병합이 끝난 뒤 남은 것은 군집이지 엣지 목록이 아니다. 이력을 남기지 않았다면 **어느 엣지를 끊어야 이 덩어리가 원래 두 군집으로 갈라지는지 알 수 없다.** 6노드 군집을 손으로 쪼개려면 15쌍을 사람이 전부 판정해야 한다. 예제 3이 `events` 리스트를 남기고 `unmerge(dropped)`가 그 이력을 역순으로 훑는 이유가 정확히 이것이다.

```python
def unmerge(self, dropped):
    for i in range(len(self.events) - 1, -1, -1):
        e = self.events[i]
        if e["op"] == "merge" and e["drop"] == dropped:
            self.canonical[dropped] = dropped   # ← 되돌리기가 대입 한 번
            ...
```

**메커니즘 3 — 연쇄가 임계를 우회한다.**
A–B가 0.90, B–C가 0.90이면 A–C는 실제 점수가 0.20이어도 같은 군집이 된다. 이행성은 점수를 다시 묻지 않는다. 즉 **군집 안에는 임계를 통과한 적이 없는 동일성 주장이 잔뜩 들어 있다.** 임계를 내리면 이런 연쇄가 붙는 확률이 급격히 오른다.

그래서 예제 2가 마지막에 이렇게 못을 박는다.

> 이행성도 공짜가 아니다. 잘못된 병합 하나가 군집 전체를 오염시킨다.
> 그래서 군집 크기에 상한을 두거나, 커지면 사람에게 보내는 게 안전하다.

### 규모로 보면 — 임계를 내린 대가

예제 4의 모의 분포(같은 쌍 400개, 다른 쌍 9,600개)로 임계별 결과를 뽑으면 이렇다.

| 자동 임계 | 검토 하한 | 정밀도 | 재현율 | **오병합** | 놓침 | 사람 검토 |
|---|---|---|---|---|---|---|
| 0.95 | 0.80 | 0.963 | 0.195 | 3 | 136 | 243 |
| 0.90 | 0.70 | 0.911 | 0.357 | 14 | 35 | 514 |
| **0.85** | **0.55** | **0.898** | **0.527** | **24** | **0** | **2,053** |
| 0.75 | 0.55 | 0.701 | 0.797 | 136 | 0 | 1,833 |
| 0.65 | 0.50 | 0.379 | 0.975 | 638 | 0 | 2,262 |
| **0.55** | **0.50** | **0.175** | **1.000** | **1,888** | **0** | **1,002** |

0.85 → 0.55로 내리면 오병합이 **24건 → 1,888건**, 정밀도가 **0.898 → 0.175**가 된다. 자동 병합의 다섯 중 넷이 틀린 상태다. 오병합 1건에 2시간이면 1,888건은 **3,776시간**. 아껴 준 사람 검토는 1,051건 × 40초 = 약 12시간. 교환비가 300배 넘게 어긋난다.

**그래서 사흘이 짧은 쪽이다.** 사흘은 "오병합 하나를 이행성·다운스트림까지 끌고 가서 수습한 실제 비용"이고, 임계를 그냥 내린 상태로 운영했다면 사흘로 안 끝난다.

## 4. 이 사고가 낳은 14장의 설계 결론 세 가지

이 사건은 세 개의 서로 다른 방어선을 각각 정당화한다. **세 개가 다 필요하다** — 어느 하나도 나머지를 대신하지 못한다.

### 결론 1 — 임계는 두 개 둔다 (14.2, 14.4)

> 위는 자동, 아래는 무시, 사이는 사람에게. 자동화가 할 일은 다 맞히는 게 아니라 **애매한 것을 골라내는** 것이다.

임계가 하나면 모든 쌍이 「병합」 아니면 「무시」다. 그러면 임계 위치 하나가 정밀도와 재현율을 동시에 결정해 버리고, **어느 위치에서도 둘 중 하나는 반드시 나쁘다.** 0.55는 재현율 1.000을 얻는 대가로 정밀도 0.175를 받았다. 0.95는 정밀도 0.963을 얻는 대가로 재현율 0.195를 받았다.

두 임계는 이 딜레마를 "제3의 선택지"로 푼다. **자동화의 출력이 「같다/다르다」가 아니라 「같다/다르다/모르겠다」가 된다.** 0.55는 자동 임계가 아니라 **검토 하한**이어야 했다.

- HIGH=0.85: 여기 넘는 것만 손 안 대고 붙인다.
- LOW=0.55: 여기 아래는 후보 목록에서 지운다.
- 0.55 ~ 0.85: 사람 몫. r01–r04(0.643), r02–r04(0.643), r06–r07(0.550) 세 쌍.

그 결과 12개 레코드에서 사람이 본 것은 **3쌍**이고, 사람 판정(`r04는 같음, r06/r07은 다름`)을 반영하면 군집이 정답과 정확히 일치한다. 66쌍 중 3쌍, 4.5%를 사람이 봐서 100% 정답에 도달한 것이다. **애매한 쌍은 원래 애매하다** — r04는 사업자번호는 같은데 이름이 영문이고 주소·대표자·전화가 전부 비어 있다. 그 정보만으로 기계가 단정하면 안 되는 게 맞다.

임계 위치는 도덕이 아니라 산수로 정한다: **「오병합 하나의 값」과 「사람 한 건 검토 비용」의 비율.** 이 사건에서는 2시간 대 40초, 즉 1:180이었으므로 임계를 높게 잡는 것이 옳았다.

### 결론 2 — 점수 위에 거부권(veto) 규칙을 둔다 (14.2 / 한 장 요약)

> 점수 위에 「절대 안 되는」 거부권 규칙을 두세요. **사업자번호가 다르면 다른 법인입니다. 다른 게 아무리 같아도요.**

이게 이 사고의 가장 근본적인 교훈이다. 왜냐하면 **거부권 규칙만이 임계 위치와 무관하게 작동하는 방어선**이기 때문이다.

가중합 점수의 구조적 결함은 이거다. **결정적 불일치를 사소한 일치들로 상쇄할 수 있다.** r06–r07은 "다른 법인"임을 증명하는 필드가 하나 있는데(사업자번호), 이름·주소·대표자·전화 네 개가 합쳐서 0.55를 만들어 그 증거를 덮었다. 점수는 증거를 **평균**하지만, 사업자번호 불일치는 평균에 들어갈 성질이 아니라 **논리적 배제**다.

```python
# 점수를 매기기 전에 먼저 묻는다
def veto(a, b):
    if a.bizno and b.bizno and a.bizno != b.bizno:
        return "사업자번호 불일치 — 별개 법인"
    return None
# veto 가 걸리면 점수가 0.99 여도 병합하지 않는다
```

거부권 규칙을 뒀다면 **임계를 0.55로 내렸어도 이 사고는 일어나지 않았다.** 이것이 임계 튜닝과 거부권 규칙의 결정적 차이다.

| | 임계 튜닝 | 거부권 규칙 |
|---|---|---|
| 성질 | 연속적 손잡이 | 이산적 금지 |
| 실패 양상 | 0.02 차이로 결론이 뒤집힘 | 위치와 무관 |
| 역할 | 정밀도/재현율 조절 | **안전 보장** |

**임계는 손잡이일 뿐 방어선이 아니다.** 방어선은 규칙이다.

거부권 규칙은 이행성 단계에서도 재검사해야 한다. 두 군집을 합칠 때 결과 군집 안에 서로 다른 사업자번호가 둘 이상 생긴다면 그 병합을 거부한다 — 이렇게 하면 메커니즘 1의 「곱으로 번지는 오염」을 병합 시점에 잡을 수 있다.

한계도 정직하게 봐야 한다. r08–r09(다올물산 본사/부산지점)는 **사업자번호가 같은데도 정답이 「다름」**이다. 별도 사업장으로 두기로 한 **도메인 결정**이다. 즉 거부권 규칙은 "다르다"는 쪽으로만 강하고, "같다"를 보장해 주지는 않는다. 그래서 결론 3이 필요하다.

### 결론 3 — 되돌릴 수 있게 병합한다 (14.3)

> 원본을 지우지 마세요. 대표 노드를 가리키게만 하면 되돌리기가 **포인터 하나 고치는 일**이 됩니다. **되돌릴 수 있으면 훨씬 공격적으로 자동화할 수 있고요.**

두 임계도 뚫리고 거부권 규칙도 못 잡는 케이스는 남는다(도메인 결정, 규칙 자체의 버그, 원천 데이터 오류). 그때 결과를 결정하는 건 **틀렸을 때의 복구 비용**이다.

구현은 세 가지 약속이다.

1. **원본 노드를 절대 지우지 않는다.** `self.nodes`는 그대로 두고 `canonical: id → 대표 id` 포인터만 바꾼다.
2. **병합을 사건으로 기록한다.** `{"op":"merge", "keep":…, "drop":…, "by":…, "reason":…}`. 누가·왜 합쳤는지가 남는다 → 다리 엣지를 찾을 수 있다(메커니즘 2 해소).
3. **조회는 `resolve()`를 거친다.** 어느 id로 물어도 대표 노드의 통합 뷰가 나온다.

그러면 `unmerge`는 이렇게 된다.

```python
self.canonical[dropped] = dropped   # 대입 한 번
```

r07의 속성이 지워지지 않고 그대로 있으니 자기 사업자번호 `555-66-77777`을 즉시 되찾는다. (a)의 "어느 값이 어디서 왔는지 모른다" 문제가 애초에 발생하지 않는다.

대가와 이득은 이렇게 적혀 있다.

| | 값 |
|---|---|
| 비용 | 노드 수 **1.4배**, 조회에 인덱스 조회 **한 번** 추가 |
| 이득 | 오병합 하나 수습 **2시간 → 5분** |
| 저자의 판정 | "사흘짜리 사고를 다시 안 겪는 값으로는 쌌다" |

그리고 여기서 **세 결론이 하나로 이어진다.**

> 되돌리기가 싸지면 임계를 어디 둘지의 계산이 바뀐다.

오병합 값이 2시간이면 검토 180건과 맞먹으니 임계를 높게 잡아야 한다. 오병합 값이 5분이면 검토 **7.5건**과 맞먹으니 임계를 훨씬 낮춰도 남는다.

**즉 「되돌릴 수 있는 병합」은 안전장치이면서 동시에 자동화 가속기다.** 되돌릴 수 없는 구조에서는 임계를 올려 방어할 수밖에 없고(= 사람이 계속 많이 본다), 되돌릴 수 있는 구조에서는 임계를 내려 공격적으로 자동화할 수 있다. 이 사고의 진짜 결론은 "임계를 0.55로 내리면 안 된다"가 아니라 **"0.55로 내려도 괜찮은 구조를 먼저 만들어라"**다.

## 5. 한 줄로 압축

**임계를 0.55로 내리는 것은 「사업자번호만 다르고 나머지가 전부 같은 쌍」(r06–r07, 정확히 0.550)을 자동 병합하겠다는 선언과 같다. 그 쌍이 바로 모·자회사·계열사이고, 되돌릴 수 없는 병합에서는 값의 출처가 사라지고 이후 엣지의 소유가 불명해지며 다운스트림이 오염되고 이행성이 그걸 군집 전체로 곱해서 번지게 하기 때문에 사흘이 걸린다. 방어선은 임계가 아니라 (1) 판단 유보 구간을 만드는 두 임계, (2) 임계와 무관하게 작동하는 거부권 규칙, (3) 실패 비용을 2시간에서 5분으로 바꾸는 되돌릴 수 있는 병합, 이 세 개다.**

## 6. 자주 헷갈리는 지점

- **「임계를 0.55로 낮췄다」는 LOW를 바꾼 게 아니다.** 원래 설계에 이미 0.55는 있다(검토 하한). 사고는 그 값을 **자동 병합 임계로** 쓴 것이다. 같은 숫자가 자리만 옮겨서 재앙이 된 사례.
- **정밀도만 떨어진 게 아니라 「사람 검토」도 줄었다.** 표에서 0.55/0.50 행의 검토가 1,002건으로 0.85/0.55의 2,053건보다 적다. 애매 구간이 좁아졌으니 당연하다. 즉 **오병합을 사람이 잡아 줄 마지막 기회까지 같이 사라진다.** 임계를 내리는 것은 자동화를 늘리는 게 아니라 감시를 끄는 것에 가깝다.
- **0.55는 "낮은 임계"가 아니라 "이 설계에서 가장 위험한 지점"이다.** 사업자번호 가중치 0.45의 여집합과 정확히 같은 값이라서, 하필 그 하나의 결정적 필드가 불일치하는 쌍이 전부 통과하는 자리다. 임계를 0.60으로만 뒀어도 r06–r07은 자동 병합되지 않았다.
- **r04(0.643)를 놓친 것은 실패가 아니다.** 자동 병합만으로 정답에 도달하지 못한 것은 정상이고 의도된 결과다. 그 정보만으로는 단정할 수 없으니 사람에게 간 것이다. 자동화의 목표는 정답률 100%가 아니라 **애매한 것을 정확히 골라내는 것.**
- **되돌릴 수 있는 병합은 성능 최적화의 반대편에 있다.** 노드 1.4배와 조회 한 번은 실제 비용이다. 이걸 "싸다"고 판정한 근거는 벤치마크가 아니라 **사고 비용의 실측치**다.
