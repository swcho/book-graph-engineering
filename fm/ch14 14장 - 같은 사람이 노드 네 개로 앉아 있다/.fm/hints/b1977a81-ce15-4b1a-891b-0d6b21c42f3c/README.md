# 블로킹 전략을 여러 개 쓰고 합집합을 취하는 이유

**질문** 블로킹 전략을 여러 개 쓰고 합집합을 취해야 하는 이유는 무엇인가?

**답** 전략 하나로는 놓치는 쌍이 생긴다. 사업자번호만 쓰면 번호가 없는 레코드를, 이름만 쓰면 영문 표기를 놓친다.

---

## 1. 왜 블로킹을 하는가 — 그리고 왜 실수가 비대칭인가

엔티티 해상도는 원칙적으로 모든 레코드 쌍을 비교해야 한다. 그런데 쌍의 개수는 제곱으로 늘어난다.

- 레코드 12개 → 쌍 66개 (`12×11/2`)
- 레코드 10만 개 → 쌍 **4,999,950,000개**. 14장 본문의 표현대로 "하루로 안 끝난다."

그래서 **블로킹(blocking)** 을 한다. 각 레코드에서 짧은 키를 뽑아 같은 키를 가진 것끼리만 한 칸(block)에 넣고, 그 칸 안에서만 점수를 매긴다. 후보 쌍이 66개에서 열 몇 개로 줄어든다.

여기서 핵심은 **블로킹에서 저지르는 두 종류의 실수가 전혀 대등하지 않다**는 것이다.

| 실수 | 결과 | 회복 가능성 |
|---|---|---|
| 안 닮은 쌍을 후보에 넣었다 (정밀도 손실) | 점수 계산이 조금 늘어난다 | 뒷단 점수 매기기 + 임계값이 걸러 준다 |
| **닮은 쌍을 후보에서 빠뜨렸다 (재현율 손실)** | 그 쌍은 **영영 비교되지 않는다** | 없음. 아무리 좋은 유사도 함수를 써도 못 만난다 |

블로킹의 성패는 재현율이다. 후보에 못 들면 영영 못 만난다. 뒤에 붙은 정교한 점수 모델(Fellegi-Sunter든 딥러닝 매처든)은 후보 쌍 위에서만 동작하므로, 블로킹 단계에서 잘린 쌍에 대해서는 아무 일도 할 수 없다. 이 실수는 조용하다 — 로그에도 안 남고, 그냥 두 노드가 영원히 따로 앉아 있게 된다.

이 비대칭 때문에 설계 방향이 정해진다. **한 전략의 정밀도를 높이려 애쓰는 대신, 성격이 다른 전략 여러 개를 돌리고 후보 쌍의 합집합을 취한다.** 재현율은 합집합에서 단조 증가하고, 늘어난 정밀도 손실은 뒷단이 흡수한다.

## 2. 14장 예제로 실제로 확인하기

`code/records.py`의 12개 레코드를 보자. 같은 회사가 네 가지 표기로 앉아 있는 것이 핵심 케이스다.

```
# id, 이름, 사업자번호, 주소, 대표자, 전화
("r01", "가온테크",        "123-45-67890", "서울 강남구 테헤란로 1",  "김하늘", "02-1234-5678"),
("r02", "(주)가온테크",     "123-45-67890", "서울 강남구 테헤란로 1",  "김하늘", "02-1234-5678"),
("r03", "가온테크 주식회사", "",             "서울 강남구 테헤란로 1길", "김하늘", "021234-5678"),
("r04", "GAON TECH",      "123-45-67890", "",                      "",      ""),
...
("r11", "마루상사",        "666-77-88888", "광주 서구 상무로 6",     "오세훈", "062-666-7777"),
("r12", "머루상사",        "666-77-88888", "광주 서구 상무로 6",     "오세훈", "062-666-7777"),
```

`ex1_blocking.py`가 돌리는 세 전략은 이렇다.

```python
def key_bizno(r):
    return r[2] or None                                   # 사업자번호 그대로

def key_name3(r):
    n = norm_name(r[1])                                   # (주)/주식회사/공백 제거
    return n[:3] if len(n) >= 3 else n or None            # 이름 앞 3글자

def key_addr(r):
    a = r[3]
    return " ".join(a.split()[:2]) if a else None         # 주소 앞 2어절
```

세 전략이 만드는 칸을 손으로 펼쳐 보면 놓침이 어디서 생기는지 그대로 보인다.

- **사업자번호**: `123-45-67890` → {r01, r02, r04} · `333-44-55555` → {r08, r09} · `666-77-88888` → {r11, r12}
  → **r03은 아예 칸에 못 들어간다.** 사업자번호 칸이 빈 문자열이라 `key_bizno`가 `None`을 돌려주고, 키가 없는 레코드는 블로킹에서 그냥 탈락한다.
- **이름 앞 3글자**: `가온테` → {r01, r02, r03, r05} · `나루소` → {r06, r07} · `다올물` → {r08, r09}
  → **r04(`GAON TECH`)는 키가 `GAO`라서 혼자 남는다.** 영문 병기 표기는 한글 표기와 문자 하나도 겹치지 않는다. 게다가 `마루상사`/`머루상사`는 첫 글자 오타 때문에 키가 `마루상`과 `머루상`으로 갈라져, **정답 쌍 r11–r12도 이름 전략만으로는 놓친다.**
- **주소 앞 2어절**: `서울 강남구` → {r01, r02, r03} · `서울 마포구` → {r06, r07} · `광주 서구` → {r11, r12}
  → r04는 주소가 비어 있어 또 탈락. 반대로 이 전략은 `테헤란로 1`과 `테헤란로 1길`의 뒷부분 차이를 무시하므로 r03을 r01·r02와 같은 칸에 넣어 준다.

사람이 확인한 정답 군집은 `{r01, r02, r03, r04}`와 `{r11, r12}`, 즉 정답 쌍 7개다. 전략별로 어느 정답 쌍을 건지는지 표로 보면 이렇다.

| 정답 쌍 | 사업자번호 | 이름 앞 3글자 | 주소 앞 2어절 |
|---|:--:|:--:|:--:|
| r01–r02 | O | O | O |
| r01–r03 | X (r03 번호 없음) | O | O |
| r01–r04 | **O** | X (`GAO`) | X (주소 없음) |
| r02–r03 | X | O | O |
| r02–r04 | **O** | X | X |
| r03–r04 | X | X | X |
| r11–r12 | O | X (마루/머루) | O |
| **재현율** | 4/7 ≈ 57% | 3/7 ≈ 43% | 5/7 ≈ 71% |

- 사업자번호 하나만 썼다면 r03(번호 없음)이 r01·r02·r04와 만날 길이 없었다.
- 이름 하나만 썼다면 r04(`GAON TECH`)를 놓쳤을 뿐 아니라 r11–r12도 놓쳤다.
- **셋을 합치면 후보 쌍 11개**(전수 66개의 약 17%)이고, 정답 쌍 7개 중 6개가 후보에 들어온다. **재현율 86%.** 어떤 단일 전략보다 높다.

각 전략의 약점이 겹치지 않기 때문에 합집합이 이긴다. 사업자번호는 **결측**에 약하고, 이름은 **표기 변형(영문 병기·오타)** 에 약하고, 주소는 **결측과 이사·지점** 에 약하다. 서로 다른 종류의 더러움을 서로 덮어 준다. 반대로 "이름 앞 3글자"와 "이름 앞 4글자"처럼 같은 필드에서 파생된 전략을 늘리는 것은 거의 이득이 없다. 합집합의 값은 개수가 아니라 **실패 모드의 독립성**에서 나온다.

## 3. 그래도 남는 한 쌍 — 합집합도 만능은 아니다

위 표에서 **r03–r04는 세 전략 모두 놓친다.** r03은 사업자번호가 없고, r04는 주소가 없고, 이름 키는 `가온테`와 `GAO`로 다르다. 공유하는 블로킹 키가 하나도 없다.

이 쌍은 `ex2_scoring.py`가 **이행성(transitivity)** 으로 주워 온다. r01–r03이 붙고 r01–r04가 붙으면, union-find로 묶는 과정에서 r03과 r04는 직접 비교되지 않고도 같은 군집에 들어간다. 즉 실무의 재현율은 `블로킹 합집합 + 이행성 클러스터링`이 함께 만든다.

단, 이행성은 공짜가 아니다. 잘못된 병합 하나가 군집 전체를 오염시키므로 군집 크기 상한을 두거나, 커지면 사람에게 보내는 편이 안전하다. 14장의 r04는 사업자번호는 같은데 이름이 영문이고 주소·대표자·전화가 비어 있어 점수가 0.643으로 애매 구간에 떨어졌고, 결국 사람 검토로 갔다.

## 4. 합집합의 대가 — 균형이 설계다

전략을 늘리면 재현율은 오르지만 후보 쌍도 늘어 느려진다. 그 균형이 설계다.

- **비용은 후보 쌍 수에 비례**한다. 블로킹의 효율 지표는 보통 **감축률(reduction ratio)** 과 **쌍 완전성(pair completeness, 곧 재현율)** 로 같이 본다. 12건 예제에서는 감축률 83%(66→11)에 재현율 86%였다.
- **거대 블록(block skew)을 경계**하라. 키가 너무 뭉툭하면 한 칸에 수만 건이 들어가고, 그 칸 하나가 전체 비용을 잡아먹는다. 예제에서도 주소를 "서울"까지만 잘랐다면 서울 전체가 한 칸이 됐을 것이다. 흔한 처방은 블록 크기 상한을 두거나, 뭉툭한 키를 다른 필드와 조합해(예: `시·군·구 + 이름 첫 글자`) 쪼개는 것이다.
- **중복은 감수하되 한 번만 센다.** `ex1_blocking.py`가 `set`에 쌍을 모으고 `unions |= p`로 누적하는 이유다. 여러 전략이 같은 쌍을 내놓으면 비교는 한 번만 하면 된다. 예제에서 주소 전략은 새로 보태는 쌍이 0개였다 — 12건 규모에서는 이름 전략과 거의 겹친다. 하지만 결측·오타가 많은 실데이터에서는 주소가 유일한 통로가 되는 레코드가 반드시 생긴다.
- **전략은 데이터를 보고 고른다.** 놓친 쌍(위의 r03–r04 같은 것)을 사람이 라벨한 정답과 비교해 계속 감사하고, 반복되는 놓침 패턴에 맞는 새 전략을 추가한다. 예: 영문 병기가 많으면 로마자 변환 키, 오타가 많으면 음성 키(Soundex/한글 자모 키)나 문자 n-gram 기반 **LSH/MinHash**, 순서 관계가 있으면 **정렬 이웃(sorted neighborhood)** 을 덧붙인다.

## 5. 한 문장으로

블로킹에서 잘린 쌍은 뒷단의 어떤 정교한 점수 모델로도 되살릴 수 없으므로, 서로 다른 방식으로 실패하는 전략 서너 개를 돌려 후보 쌍의 합집합을 취한다 — 결측에 약한 사업자번호, 표기 변형에 약한 이름, 이사·결측에 약한 주소가 서로의 구멍을 메운다.
