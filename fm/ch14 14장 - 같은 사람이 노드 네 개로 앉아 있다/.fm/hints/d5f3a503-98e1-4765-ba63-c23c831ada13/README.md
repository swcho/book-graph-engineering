# 점수 위에 두는 '거부권 규칙'

**Q. 점수 위에 두는 '거부권 규칙'이란 무엇인가?**

**A. 다른 항목이 아무리 같아도 절대 병합하면 안 되는 규칙이다. 사업자번호가 다르면 다른 법인이다.**

---

## 한 줄 정의

거부권 규칙(veto rule)은 **점수 계산의 결과를 무조건 덮어쓰는 하드 제약**이다.
"이 조건에 걸리면 점수가 0.99여도 병합하지 않는다"를 못 박아 둔 것.

파이프라인에서의 위치가 핵심이다.

```
후보 생성(블로킹)  →  [거부권 규칙]  →  점수 계산  →  임계 판정
                       └ 걸리면 여기서 끝. 점수를 아예 계산하지 않는다.
```

점수와 **같은 층에 있지 않다**. 점수는 가중 합이므로 다른 항목이 도와주면 만회되지만,
거부권은 만회 불가능하다. 그래서 "점수 위에 둔다"고 표현한다.

## 왜 필요한가 — 가중 합의 구조적 결함

14장 예제 2(`ex2_scoring.py`)의 점수 함수는 이렇게 생겼다.

| 필드 | 가중치 | 비교 방식 |
|---|---|---|
| 사업자번호 | 0.45 | exact |
| 이름 | 0.25 | fuzzy |
| 주소 | 0.15 | fuzzy |
| 대표자 | 0.10 | exact |
| 전화 | 0.05 | exact |

이 구조는 **보상적(compensatory)** 이다. 한 필드가 0점이어도 나머지 필드가 만점이면 총점이 올라간다.
결정적인 불일치 하나가 사소한 일치 여러 개에 묻히는 것이다.

문제의 그 쌍을 계산해 보면 정확히 그 일이 일어난다.

```python
("r06", "나루소프트",     "222-33-44444", "서울 마포구 월드컵로 2", "이서연", "02-2222-3333"),
("r07", "나루소프트(주)", "555-66-77777", "서울 마포구 월드컵로 2", "이서연", "02-2222-3333"),
```

- 사업자번호: **다름** → 0.0 × 0.45 = 0.00
- 이름: `norm_name`이 `(주)`를 떼어 내므로 `나루소프트` vs `나루소프트` → 1.0 × 0.25 = 0.25
- 주소: 완전 동일 → 1.0 × 0.15 = 0.15
- 대표자: 동일 → 1.0 × 0.10 = 0.10
- 전화: 동일 → 1.0 × 0.05 = 0.05

**총점 0.550.** 예제의 `LOW = 0.55` 에 딱 걸려서 간신히 "사람 검토"로 빠졌다.
`HIGH`를 0.55로 내렸다면 모회사와 자회사가 자동으로 합쳐졌을 것이고,
그게 저자가 실제로 겪은 **되돌리는 데 사흘 걸린** 그 사고다.

여기서 배울 점은 "0.55가 좋은 임계였다"가 아니다.
**임계 운(luck)에 안전을 맡기고 있었다**는 것이다. 거부권 규칙이 있었다면 임계가 몇이든 상관없다.

## 규칙의 실제 모양

```python
def veto(a, b):
    """걸리면 (True, 이유). 점수는 계산하지 않는다."""
    ba, bb = a["bizno"], b["bizno"]
    if ba and bb and ba != bb:          # 둘 다 있고, 다르면
        return True, "사업자번호 불일치 — 별개 법인"
    return False, None

def decide(a, b):
    blocked, why = veto(a, b)
    if blocked:
        return "병합 금지", why          # 점수를 보지 않는다
    s = score(a, b)
    ...
```

`if ba and bb` 조건이 중요하다. **한쪽이 비어 있으면 거부권을 발동하지 않는다.**
`r03`(사업자번호 없음)이나 `r04`(이름만 영문, 나머지 공란)처럼 값이 없는 레코드에까지
거부권을 적용하면 정답 군집 `{r01, r02, r03, r04}`를 영영 못 만든다.
"다르다"와 "모른다"는 다르게 취급해야 한다 — 점수 함수가 빈 값을 `None`(모름)으로 빼두는 것과 같은 원리다.

## 거부권 후보로 좋은 필드

| 조건 | 이유 |
|---|---|
| **식별자** (사업자번호, 법인등록번호, ISBN, 주민/사원번호) | 발급 기관이 유일성을 보증한다 |
| **시간적 모순** (설립일 이후에 폐업한 회사와 그 전에 폐업한 회사) | 물리적으로 같을 수 없다 |
| **배타적 분류** (개인사업자 vs 법인, 국가 코드) | 정의상 겹치지 않는다 |
| **명시적 부정 이력** (사람이 과거에 "다르다"고 판정한 쌍) | 같은 판단을 두 번 하게 하지 않는다 |

반대로 이름·주소·전화·대표자는 거부권에 넣으면 안 된다. 오타·이전·변경이 일상이라
"다르다"가 곧 "별개"를 뜻하지 않는다.

## 대칭 함정 — 거부권의 반대편

거부권 규칙이 매력적이라고 그 반대 방향, 즉 **"이 필드가 같으면 무조건 병합"** 이라는
강제 병합 규칙을 만들면 다시 사고가 난다. 같은 장의 데이터에 반례가 심어져 있다.

```python
("r08", "다올물산 본사",    "333-44-55555", "인천 연수구 송도로 3", ...),
("r09", "다올물산 부산지점", "333-44-55555", "부산 사하구 낙동로 8", ...),
```

사업자번호가 **같은데도** 정답(`TRUTH`)에는 같은 군집으로 묶여 있지 않다.
지점을 별도 사업장 노드로 두기로 한 **도메인 결정**이기 때문이다.

즉 사업자번호는
- 다르면 → 확실히 별개다 (거부권으로 쓸 수 있다)
- 같으면 → 같을 가능성이 크다 (점수의 큰 가중치로 쓴다. 결론은 아니다)

**부정 증거는 결정적일 수 있지만, 긍정 증거는 대개 확률일 뿐이다.** 이 비대칭이 거부권 규칙의 근거다.

## 운영 원칙

1. **개수를 적게, 하나하나 반례 검토를 거쳐서.** 거부권은 재현율을 깎는다. 규칙이 틀리면
   그 쌍은 사람 검토조차 못 받고 영원히 안 만난다. 임계 실수보다 복구가 어렵다.
2. **정규화 후에 비교한다.** `123-45-67890`과 `1234567890`을 "다르다"고 판정하는 거부권은 재앙이다.
3. **왜 막혔는지 로그를 남긴다.** 위 코드가 이유 문자열을 함께 반환하는 이유다.
   "왜 이 둘이 안 합쳐지나요"라는 문의에 답할 수 있어야 한다(16장 출처 추적과 이어진다).
4. **사람 판정도 거부권으로 승격시킨다.** `HUMAN = {("r06", "r07"): False}` 처럼 사람이 "다르다"고
   결론 낸 쌍은 다음 배치에서 다시 후보로 올라오지 않게 저장한다.
5. **거부권은 점수 튜닝과 독립이다.** 임계를 공격적으로 낮추는 실험을 해도 치명적 오병합만은
   막아 준다. 되돌릴 수 있는 병합(예제 3)과 함께 쓰면 자동화 비율을 훨씬 올릴 수 있다.

## 관련 개념

- **Fellegi-Sunter 확률적 레코드 연결**: 필드별 가중치 합으로 임계를 넘기는 고전 모델. 거부권 규칙은
  이 모델 밖에서 결과를 기각하는 장치다.
- **SHACL / 제약 검증(13장)**: 스키마 층에서 "이건 있을 수 없다"를 선언하는 것과 같은 사고방식.
- MDM 제품군에서는 보통 exclusion rule, must-not-match, negative rule, hard constraint 같은
  이름으로 불린다. 용어는 달라도 "점수를 무조건 이긴다"는 성질은 같다.

## 시험에 나오는 한 줄

> 점수는 증거를 더하고, 거부권 규칙은 증거를 **무효화**한다.
> 사업자번호가 다르면 주소·대표자·전화가 전부 같아도 다른 법인이다.
