# 되돌릴 수 있는 병합의 대가는 무엇인가?

**답**: 저장 공간과 조회 비용이다. 저자 경우 노드 수가 1.4배가 되고 조회에 인덱스 조회 한 번이 더 붙었지만, 사흘짜리 사고를 막는 값으로는 쌌다.

---

## 0. 무엇을 포기하고 무엇을 얻는 거래인가

되돌릴 수 있는 병합(reversible merge)은 `code/ex3_reversible_merge.py`의 `MergeStore`가 보여 주는 구조다. 핵심 문장은 딱 하나다.

> 원본 노드는 절대 지우지 않는다.

파괴적 병합(destructive merge)은 두 노드를 합쳐 하나만 남기고 나머지를 `DELETE`한다. 속성도 골라서 하나로 짜부라뜨린다. 결과는 깔끔하다 — 노드 하나, 속성 한 벌. 대신 되돌릴 수 없다. 예제의 표현대로 "어느 값이 어디서 왔는지 모르니까 원래대로 쪼갤 수 없다."

되돌릴 수 있는 병합은 그 깔끔함을 팔아서 **되돌리기 능력**을 산다. 판 것이 저장 공간과 조회 비용이고, 산 것이 `unmerge` 한 줄이다.

```python
def unmerge(self, dropped):
    ...
    self.canonical[dropped] = dropped   # 되돌리기 = 포인터 대입 한 번
```

아래에서 판 쪽(비용)을 항목별로 분해하고, 각 항목의 완화책을 붙이고, 마지막에 산 쪽(편익)과 금액으로 비교한다.

## 1. 비용 항목 ①: 원본 노드 유지로 인한 노드 수 증가 (1.4배)

### 1.4배는 무엇의 1.4배인가

이 숫자가 가장 오해받는다. **"병합 전 대비 1.4배"가 아니다.** 병합은 노드를 늘리는 연산이 아니니까 그럴 리가 없다.

정확히는 **"파괴적으로 병합했을 때 남을 노드 수" 대비 1.4배**다. 다시 말해 **원본 레코드 수 ÷ 실제 구별되는 엔티티 수 = 1.4**다.

| 세계 | 노드 수 | 설명 |
|---|---|---|
| 병합 전 (원본 적재 그대로) | 140 | 표기가 다른 중복이 섞여 있음 |
| 파괴적 병합 후 | 100 | 실제 회사 100곳. 40개는 삭제됨 |
| 되돌릴 수 있는 병합 후 | 140 | 대표 100 + `canonical` 포인터만 달린 종속 40 |

즉 저자의 데이터에서는 **회사 100곳이 레코드 140건으로 흩어져 있었다**. 중복률 약 29%(40/140), 엔티티당 평균 1.4개 표기. 14장 도입부의 "같은 사람이 노드 네 개로 앉아 있다"가 극단값이고(`records.py`의 r01/r02/r03/r04 — 가온테크가 네 표기), 전체 평균으로는 1.4개였다는 뜻이다.

`records.py`의 12건으로 직접 세어 보면 감각이 맞는다. `TRUTH`는 `{r01,r02,r03,r04}`와 `{r11,r12}` 두 군집. 파괴적으로 합치면 12 → 8건(4개가 1개로, 2개가 1개로 = -3 -1). 12/8 = **1.5배**. 저자의 1.4배와 거의 같은 수준이다.

### 이게 실제로 얼마인가

노드 수 40% 증가는 무섭게 들리지만, 늘어나는 것은 **이미 갖고 있던 원본 레코드**다. 어차피 원천 시스템(ERP, CRM, 명함스캔)에 남아 있고, 대부분의 조직은 스테이징 테이블에도 갖고 있다. 그래프에도 한 벌 두는 비용일 뿐이다.

거칠게 계산하면(회사 노드 10만 → 14만, 노드당 속성 500B 수준):

- 파괴적: 10만 × 500B = **50MB**
- 되돌릴 수 있는: 14만 × 500B = **70MB**
- 차이 **+20MB**

여기에 종속 노드가 붙들고 있는 엣지도 따라온다. 종속 노드의 관계를 대표로 옮기지 않고 원래 자리에 남겨 두는 설계라면(되돌리기를 온전히 하려면 이게 맞다) 엣지 수도 비슷한 비율로 남는다.

### 완화책

- **속성 잘라내기(attribute pruning)**: 종속 노드에는 되돌리기와 출처 추적에 필요한 최소 필드만 남기고, 파생 필드·임베딩·정규화 캐시는 대표 노드에만 둔다. 되돌릴 때 파생 필드는 재계산하면 된다.
- **콜드 스토리지 분리**: 종속 노드 본문을 그래프 밖(객체 스토리지, 열지향 테이블)으로 내리고 그래프에는 `canonical` 포인터와 ID만 둔다. 되돌리기 빈도가 낮으면(전체 병합의 1% 미만) 이쪽이 훨씬 싸다.
- **엣지는 대표로 승격, 원소속만 기록**: 엣지는 대표 노드에 매달고 `origin_node` 속성만 붙여 둔다. 되돌릴 때 `origin_node`로 되돌려 놓는다. 질의 성능과 되돌리기를 동시에 챙긴다.

## 2. 비용 항목 ②: canonical 포인터 인덱스

`MergeStore`에서 `self.canonical`은 파이썬 딕셔너리지만, 실제 그래프 DB나 RDB에서는 **모든 노드 ID에 대한 인덱스**다.

```python
self.canonical = {k: k for k in nodes}   # id -> 대표 id, 노드 전체에 대해
```

주의할 점: 이 인덱스는 병합된 40개만 담는 게 아니라 **14만 개 전부**를 담는다. 병합되지 않은 노드도 `canonical[x] == x`로 자기 자신을 가리켜야 `resolve()`가 분기 없이 돌아간다.

비용:

| 요소 | 규모 (14만 노드 가정) |
|---|---|
| 엔트리 수 | 140,000 |
| 엔트리당 (키 16B + 값 16B + B-tree 오버헤드) | 약 50~80B |
| 인덱스 크기 | 약 **7~11MB** |
| 쓰기 증폭 | 노드 삽입마다 인덱스 삽입 1회 추가 |
| 메모리 상주 | 핫 경로면 버퍼 풀에 상주해야 함 |

이 인덱스가 "조회에 인덱스 조회 한 번이 더 붙었다"의 그 인덱스다.

### 완화책

- **포인터 압축(path compression)** — 가장 중요하다. `ex3`의 `resolve()`는 압축을 하지 않는다.

  ```python
  def resolve(self, nid):
      seen = set()
      while self.canonical[nid] != nid and nid not in seen:
          seen.add(nid); nid = self.canonical[nid]
      return nid          # 매번 사슬을 다시 걷는다
  ```

  A→B→C→D 사슬이 생기면 조회마다 3홉이다. `ex2_scoring.py`의 union-find `find()`는 반대로 압축을 한다.

  ```python
  def find(x):
      while parent[x] != x:
          parent[x] = parent[parent[x]]; x = parent[x]   # 걸으면서 평탄화
      return x
  ```

  압축을 하면 사슬 깊이가 상수에 가깝게 눌려 인덱스 조회가 **정확히 1회**로 유지된다. 단, 압축은 원래 사슬 모양을 지우므로 **`events` 로그에 원래 부모를 남겨 둬야** 되돌리기가 온전하다. 압축은 "읽기 최적화 캐시", `events`는 "진실"이라고 역할을 갈라 두면 안전하다.
- **평탄화 배치 잡**: 야간에 모든 종속 노드의 `canonical`을 최종 대표로 직접 갱신해 깊이 1로 만든다. 압축을 온라인으로 하지 않기로 했다면 이쪽.
- **부재 항목 생략 + 폴백**: 인덱스에 병합된 노드만(4만 개) 넣고, 조회 결과가 없으면 자기 자신으로 간주한다. 인덱스가 1/3.5로 줄어든다. 대신 미스 판정 비용이 붙으므로 블룸 필터를 앞에 세운다.

## 3. 비용 항목 ③: 병합 이벤트 로그 누적

```python
self.events.append({"op": "merge", "keep": keep, "drop": drop,
                    "by": by, "reason": reason})
```

이게 되돌리기의 심장이다. `unmerge`가 하는 일은 이 로그를 뒤에서부터 뒤져 해당 병합을 찾아내는 것이다.

```python
for i in range(len(self.events) - 1, -1, -1):
    e = self.events[i]
    if e["op"] == "merge" and e["drop"] == dropped:
        ...
```

문제는 **로그가 단조 증가한다**는 점이다. `unmerge`조차 로그를 지우지 않고 `{"op": "unmerge", ...}`를 **추가**한다. 예제 주석대로 "6부 이벤트 소싱의 축소판"이므로, 이벤트 소싱의 비용 구조를 그대로 물려받는다.

| 요소 | 규모 |
|---|---|
| 초기 적재 병합 이벤트 | 4만 건 (14만 - 10만) |
| 이벤트당 크기 (keep, drop, by, reason, ts, score) | 200~400B |
| 초기 로그 | 약 **8~16MB** |
| 증분 | 신규 유입 + 재병합 + 취소 + 규칙 튜닝 재실행 |
| 진짜 위험 | **파이프라인 재실행**. 임계를 바꿔 전량 재계산할 때마다 수만 건이 다시 쌓인다 |
| `unmerge` 탐색 | 로그 역방향 선형 스캔 → **O(로그 길이)**. 이게 시간이 갈수록 느려진다 |

### 완화책

- **`drop` 기준 인덱스**: `unmerge`의 선형 스캔은 실서비스에서 못 쓴다. `drop` → 최신 미취소 병합 이벤트 하나를 가리키는 인덱스(또는 `active_merge` 테이블)를 두면 O(1)이 된다.
- **이벤트 로그 아카이빙**: "확정 창(window)"을 정한다. 예컨대 90일이 지나고 아무도 문제 제기하지 않은 병합은 취소 가능성이 사실상 없다고 보고, 이벤트를 압축 저장소(Parquet, 객체 스토리지)로 옮긴다. 온라인 로그에는 최근 창만 남긴다. 감사 요구가 있으면 아카이브를 조회한다.
- **스냅샷 + 델타**: 이벤트 소싱의 표준 처방. 분기마다 `canonical` 전체 스냅샷을 뜨고, 그 이후 델타만 온라인에 둔다. 재구성은 스냅샷 + 델타 재생.
- **재실행 이벤트는 별도 스트림**: 임계 튜닝 재계산은 "실험" 스트림에 쌓고, 채택된 결과만 본 로그에 커밋한다. 로그 오염을 막는다.
- **압축 표현**: `reason`을 자유 문자열이 아니라 규칙 ID(enum)로 두고, 점수는 정수로 양자화한다. 이벤트 크기가 절반 이하로 줄어든다.

## 4. 비용 항목 ④: resolve 한 홉 추가로 인한 읽기 지연

예제의 문장 그대로다.

> 조회할 때마다 resolve 를 거쳐야 한다. (…) 조회에 인덱스 조회 한 번이 더 붙었다.

파괴적 병합에서는 "r04를 달라" → 노드 조회 1회. 되돌릴 수 있는 병합에서는 "r04를 달라" → **`canonical` 인덱스 조회 1회 → 대표 노드 조회 1회**. 홉이 하나 늘었다.

| 상황 | 추가 지연 |
|---|---|
| 인덱스가 메모리/버퍼 풀에 있음 | 수 µs ~ 수십 µs. 사실상 공짜 |
| 인덱스가 디스크(SSD) | 0.1 ~ 1ms |
| 사슬 깊이 k (압축 안 함) | 위 값 × k |
| 분산 저장, 대표가 다른 샤드 | **네트워크 왕복 1회** — 여기가 진짜 아프다 |

체감 예시: p50 조회가 5ms인 API에 인덱스 조회 0.2ms가 붙으면 **+4%**. 그런데 한 요청에서 100개 엔티티를 resolve해야 하는 팬아웃 질의라면 0.2ms × 100 = **+20ms**로 이야기가 달라진다. 되돌릴 수 있는 병합의 지연 비용은 **단건 조회에서는 무시할 만하고, 팬아웃 질의에서 물린다.**

### 완화책

- **핫 경로 캐싱**: `canonical` 매핑을 애플리케이션 레벨 LRU나 Redis에 얹는다. ID→대표 매핑은 (a) 크기가 작고, (b) 변경이 드물고, (c) 변경 시 무효화 대상이 특정 가능하다 — 캐싱하기에 이상적인 데이터다. 히트율 99%는 어렵지 않다.
- **배치 resolve**: 팬아웃 질의에서 ID를 모아 한 번에 `WHERE id IN (...)`으로 조회한다. 왕복 100회가 1회가 된다. N+1 문제와 같은 처방이다.
- **포인터 압축**(§2와 동일): 사슬 깊이를 1로 고정해 홉이 늘어나지 않게 한다.
- **대표와 종속을 같은 샤드에 배치**: 샤드 키를 노드 ID가 아니라 **대표 ID(또는 병합 군집 ID)**로 잡는다. 네트워크 왕복이 사라진다. 되돌릴 수 있는 병합을 도입할 때 가장 먼저 결정해야 하는 설계다.
- **역방향 진입점 제거**: 쓰기 시점에 종속 ID를 대표 ID로 정규화해 저장하면(입구 정규화), 읽기 경로에서 resolve가 필요한 경우가 "외부에서 오래된 ID로 들어오는 요청"으로만 줄어든다.

## 5. 비용 항목 ⑤: `view()`가 읽기 시점에 값을 합치는 CPU 비용

이 항목이 가장 과소평가된다. 파괴적 병합은 **쓰기 시점에 한 번** 값을 합친다. 되돌릴 수 있는 병합은 원본을 그대로 두므로 **읽을 때마다** 합쳐야 한다.

```python
def view(self, nid):
    c = self.resolve(nid)
    merged = {}
    members = [k for k in self.nodes if self.resolve(k) == c]   # ← 전체 스캔!
    for m in sorted(members, key=lambda x: -self._richness(x)): # ← 정렬
        for k, v in self.nodes[m].items():
            if v and not merged.get(k):                          # ← 필드별 생존 판정
                merged[k] = v
    return c, merged, members
```

교육용 코드라 노골적이지만, 비용 구조는 실제와 같다.

| 하위 비용 | 예제에서 | 실서비스에서 |
|---|---|---|
| 군집 구성원 찾기 | `for k in self.nodes` — **O(전체 노드)**. 14만 노드면 조회 한 번에 14만 회 resolve | 반드시 역인덱스(대표 → 구성원) 필요 |
| 구성원 노드 읽기 | 딕셔너리 접근 | 구성원 수만큼 **랜덤 읽기** (평균 1.4, 최악 4+) |
| 우선순위 정렬 | `sorted(..., -richness)` | 생존 규칙 정렬. `_richness`도 매번 전 필드 스캔 |
| 필드별 생존 판정 | `if v and not merged.get(k)` | `ex5_survivorship.py`의 필드별 규칙(신뢰도/최신/최장) 적용 — 규칙이 복잡하면 여기가 지배적 |

`ex5`를 보면 생존 규칙이 필드마다 다르다. `name`은 출처 신뢰도, `ceo`는 최신, `addr`은 최장. 필드 30개에 규칙 4종이면 조회 한 번에 비교 연산이 수백 회다. 이걸 초당 수천 건 조회에 곱하면 CPU가 보인다.

### 완화책

- **머티리얼라이즈된 뷰(materialized view)** — 이 항목의 정답이다. 병합 결과를 **미리 계산해서 대표 노드 옆에 저장**한다. 읽기는 그 뷰만 읽는다. 원본은 그대로 남아 있으니 되돌리기 능력은 유지된다. **깔끔한 읽기와 되돌리기를 동시에 갖는다** — 대가는 저장 공간 한 벌 더와 갱신 복잡도.
  - 갱신 시점: `merge`/`unmerge`/원본 변경 이벤트에서 해당 군집의 뷰만 무효화·재계산한다. 군집이 작으므로(평균 1.4) 재계산은 싸다.
  - 이 구조에서 노드 수는 1.4배 + 대표 노드당 뷰 한 벌이 되어 약 1.4~1.5배로 수렴한다. §1에서 이미 지불한 비용에 조금 더 얹는 셈이다.
- **역인덱스(대표 → 구성원 목록)**: `view()`의 전체 스캔을 없애는 최소 조치. 머티리얼라이즈된 뷰를 안 만들더라도 이건 필수다.
- **핫 엔티티 결과 캐싱**: 합쳐진 뷰 자체를 캐싱한다. 엔티티 조회는 전형적인 지프 분포라 상위 1%가 트래픽 절반을 먹는다.
- **`_richness` 사전 계산**: 노드에 `richness` 속성을 물리적으로 저장하고 쓰기 시점에만 갱신한다. 정렬 키 계산 비용이 사라진다.
- **필드별 규칙 컴파일**: `ex5`의 규칙 테이블을 조회마다 해석하지 말고 부팅 시 함수로 컴파일한다.

## 6. 비용 총정리

| # | 비용 항목 | 성격 | 규모 감각 (10만 엔티티 / 14만 레코드) | 대표 완화책 |
|---|---|---|---|---|
| ① | 원본 노드 유지 | 저장 | 노드 1.4배, +20MB (+엣지) | 속성 잘라내기, 콜드 스토리지 분리 |
| ② | canonical 포인터 인덱스 | 저장 + 쓰기 | 14만 엔트리, 7~11MB | **포인터 압축**, 부재 항목 생략 |
| ③ | 병합 이벤트 로그 | 저장 (단조 증가) | 4만 건, 8~16MB, 재실행마다 증가 | **아카이빙**, 스냅샷+델타, drop 인덱스 |
| ④ | resolve 한 홉 | 읽기 지연 | 단건 +0.1~1ms(+4%), 팬아웃에서 ×N | **핫 경로 캐싱**, 배치 resolve, 동일 샤드 |
| ⑤ | `view()` 읽기 시점 합성 | 읽기 CPU | 구성원 조회 + 정렬 + 규칙 판정 | **머티리얼라이즈된 뷰**, 역인덱스 |

저장 비용 총합 약 **35~50MB**. 클라우드 스토리지 단가로 월 수백 원 수준이다. 읽기 비용은 캐싱과 머티리얼라이즈된 뷰를 넣으면 파괴적 병합과 거의 같아진다. **완화책을 다 적용하면 남는 비용은 사실상 저장 공간과 갱신 코드의 복잡도뿐이다.**

## 7. 편익: 사흘짜리 사고 1건의 값

`ex2_scoring.py`가 사고를 자백한다.

> 자동 병합 임계를 0.55 로 낮췄다면 모회사와 자회사를 합쳐 버렸을 것이다.
> 제가 실제로 그렇게 했고, 되돌리는 데 사흘 걸렸다.

`records.py`의 r06(나루소프트) / r07(나루소프트(주))이 그 쌍이다. 주소·대표자·전화가 전부 같고 사업자번호만 다르다. 점수 0.550.

사흘의 값을 `ex4_threshold_tuning.py`가 준 단가로 환산한다.

- 사람 한 건 검토: **40초 = 400원** → 시간당 36,000원
- 사흘 = 3일 × 8시간 = **24시간** → 인건비 약 **86만 원**

여기에 로그에 안 남는 비용이 붙는다.

| 숨은 비용 | 내용 |
|---|---|
| 오염 확산 | 이행성(transitivity)으로 잘못된 병합 하나가 군집 전체를 오염시킨다. `ex2`: "잘못된 병합 하나가 군집 전체를 오염시킨다" |
| 사흘 동안 나간 오답 | 모회사·자회사가 한 덩어리로 보이는 상태에서 나간 리포트·API 응답·의사결정 |
| 하류 재계산 | 오염된 노드를 참조한 파생 지표, 임베딩, 캐시 전부 |
| 신뢰 손실 | 정량화 불가. 실제로는 이게 제일 크다 |
| 기회 비용 | 그 사흘에 못 한 다른 일 |

**보수적으로도 사고 1건 = 100만 원 이상.** 그리고 이건 1건이다. 파괴적 병합을 쓰는 파이프라인은 사고를 반복한다.

## 8. 비용/편익 비교: 명시적으로

| | 되돌릴 수 있는 병합 (상시 비용) | 파괴적 병합 (사고 비용) |
|---|---|---|
| 성격 | **상시**, 예측 가능, 선형 | **간헐**, 예측 불가, 꼬리가 두꺼움 |
| 저장 | +35~50MB → 월 수백 원 | 0 |
| 읽기 | +0.1~1ms (캐싱 후 거의 0) | 0 |
| 개발 | `MergeStore` 한 클래스 + 뷰 갱신 로직 | 0 |
| 사고 1건 수습 | **5분** (`unmerge` = 포인터 대입) | **2시간~사흘** |
| 실제 발생 사고 | — | 1건 = **86만 원 이상** |

`ex4`가 이 대비를 숫자로 못 박는다.

> 오병합 하나 수습: 평균 2시간
> → 오병합 하나가 검토 180건과 맞먹는다
> 다만 이건 «되돌리기가 비싼» 경우다. (…) unmerge 가 대입 한 번이면 오병합 값이 2시간에서 5분이 된다.

**되돌리기 비용을 24배 낮춘다** (2시간 → 5분). 금액으로는 72,000원 → 3,000원. 오병합 1건이 검토 180건 맞먹던 것이 **검토 7.5건**으로 떨어진다.

그리고 상시 비용 쪽. 월 수백 원의 저장비를 사고 1건 값(86만 원)으로 나누면 **수백 개월분**이다. 조회 지연 +4%가 신경 쓰인다면, 사흘 동안 API가 틀린 답을 준 것과 비교하면 된다. 비교가 성립하지 않는다. 예제의 마지막 문장이 그래서 짧다.

> 사흘짜리 사고를 다시 안 겪는 값으로는 쌌다.

여기서 중요한 건 **비대칭**이다. 상시 비용은 작고 균일하고 예측 가능하며, 완화책으로 더 깎을 수 있다. 사고 비용은 크고 불규칙하며 최악값의 상한이 없다 — 이행성 때문에 오염 범위가 얼마나 번질지 사전에 알 수 없다. **작고 예측 가능한 비용으로 크고 예측 불가능한 비용의 꼬리를 자르는 거래**다. 이건 보험이고, 보험료가 사고 1건 값의 수백 분의 일이면 사는 게 맞다.

## 9. 2차 효과: 되돌릴 수 있음이 임계를 낮춰 자동화율을 올린다

여기가 이 카드의 진짜 결론이고, `ex4`가 던져 놓고 독자에게 넘긴 부분이다.

> 되돌리기가 싸면 계산이 달라진다.

한 장 요약도 같은 말을 한다.

> 되돌릴 수 있으면 훨씬 공격적으로 자동화할 수 있고요.

### 임계는 비용 비율의 함수다

`ex4`가 임계를 고르는 방법을 명시했다. "오병합 하나의 값"과 "사람 한 건 검토 비용"을 비교하는 것. 그러니 임계는 **그 비율**이 정한다. 되돌리기가 싸지면 비율이 24배 바뀌므로 **최적 임계가 아래로 움직인다.**

`ex4`의 실제 출력(같은 쌍 400개, 다른 쌍 9,600개):

| 자동임계 | 검토하한 | 정밀도 | 재현율 | 오병합 | 놓침 | 사람 검토 |
|---:|---:|---:|---:|---:|---:|---:|
| 0.95 | 0.80 | 0.963 | 0.195 | 3 | 136 | 243 |
| 0.90 | 0.70 | 0.911 | 0.357 | 14 | 35 | 514 |
| **0.85** | **0.55** | **0.898** | **0.527** | **24** | **0** | **2,053** |
| **0.75** | **0.55** | **0.701** | **0.797** | **136** | **0** | **1,833** |
| 0.65 | 0.50 | 0.379 | 0.975 | 638 | 0 | 2,262 |
| 0.55 | 0.50 | 0.175 | 1.000 | 1,888 | 0 | 1,002 |

0.85 → 0.75으로 내리면 **재현율 0.527 → 0.797**. 자동으로 처리되는 병합이 211건에서 319건으로 늘고(+108), 사람 검토는 2,053 → 1,833건으로 줄고, 오병합은 24 → 136건으로 는다(+112).

이 +112건이 감당 가능한지가 전부다.

| | 되돌리기 비싼 세계 (72,000원/건) | 되돌리기 싼 세계 (3,000원/건) |
|---|---|---|
| 임계 인하로 늘어난 오병합 비용 | 112 × 72,000 = **806만 원** | 112 × 3,000 = **34만 원** |
| 검토 절감 (220건) | 8.8만 원 | 8.8만 원 |
| 순 변화 | **+797만 원 → 절대 불가** | **+25만 원 → 협상 가능** |

되돌리기가 비싸면 임계 인하가 800만 원짜리 자살이다. 그래서 `ex4`는 "저는 임계를 높게 잡습니다"라고 쓴다. 되돌리기가 싸지면 같은 선택이 25만 원짜리 조정이 된다.

### 그리고 여기에 미해결 중복의 비용이 더해진다

순금액만 보면 25만 원이라도 지출이니 안 하는 게 나아 보인다. 하지만 위 표에는 빠진 항목이 두 개 있다.

1. **검토 큐의 처리 용량 상한.** 검토 인력이 하루 500건이면 2,053건은 4일 대기다. 대기 중인 엔티티는 중복 상태로 남아 있고, 그 사이 질의는 계속 틀린 답을 준다. 임계 인하로 검토가 2,053 → 1,833건으로 줄면 대기가 하루 가까이 짧아진다. 큐가 처리 용량을 만성적으로 초과하는 조직에서는 이 항목이 지배적이다.
2. **놓친 병합의 질의 오류 비용.** 재현율 0.527은 같은 회사의 절반 가까이가 여전히 여러 노드로 앉아 있다는 뜻이다. "가온테크의 총 거래액"이 세 조각으로 나뉘어 나온다. 이건 오병합만큼 눈에 안 띄지만 조용히 틀린 답을 계속 준다.

이 두 항목을 넣으면 재현율 0.527 → 0.797의 값이 34만 원을 넘어선다. **되돌릴 수 있는 병합은 그 재현율 개선을 살 수 있게 해 주는 전제 조건**이다.

### 그래서 인과 사슬은 이렇게 이어진다

```
원본을 지우지 않는다
  └─ 되돌리기 = 포인터 대입 한 번
      └─ 오병합 1건 수습 비용 2시간 → 5분 (24배 인하)
          └─ 오병합/검토 비용 비율 180:1 → 7.5:1
              └─ 최적 자동 병합 임계가 내려간다 (0.85 → 0.75)
                  └─ 재현율 0.527 → 0.797, 사람 검토 2,053 → 1,833건
                      └─ 자동화율 상승 + 검토 큐 대기 단축
                          └─ 미해결 중복이 줄어 질의 정확도가 오른다
```

그리고 되돌릴 수 있는 병합이 없으면 이 사슬은 첫 칸에서 끊긴다. **비용 항목 ①~⑤를 지불하는 진짜 이유가 여기 있다.** 저장 공간 35MB로 사고 보험을 사는 게 아니라, **자동화 임계를 내릴 수 있는 권리**를 사는 것이다. 사고를 막는 건 그 권리의 부산물이다.

## 10. 한 줄로

**되돌릴 수 있는 병합의 대가는 노드 1.4배·포인터 인덱스·이벤트 로그·resolve 한 홉·읽기 시점 합성 CPU이고, 각각 캐싱·압축·아카이빙·머티리얼라이즈된 뷰로 깎을 수 있다. 그 상시 비용은 월 수백 원과 지연 몇 %인데, 그것으로 사흘 86만 원짜리 사고를 5분으로 줄이고, 나아가 자동 병합 임계를 내려 재현율을 0.53에서 0.80으로 올릴 권리를 산다. 비대칭이 너무 커서 계산할 필요조차 없다.**

## 관련 카드로 이어지는 지점

- **§14.2 두 개의 임계** — 임계 선택이 되돌리기 비용의 함수라는 것이 이 카드의 2차 효과다.
- **§14.4 임계를 어디에 둘 것인가** — `ex4`의 단가 표가 그대로 여기 쓰인다.
- **§14.5 어느 값을 남길 것인가** — `view()`가 읽기마다 실행하는 생존 규칙이 곧 비용 항목 ⑤다.
- **16장 출처 추적** — `events` 로그와 `ex5`의 "고른 값마다 어디서 왔는지"가 같은 인프라를 공유한다. 즉 비용 항목 ③은 16장 요구사항이기도 해서, 되돌리기만의 비용이 아니다.
- **6부 이벤트 소싱** — `ex3` 주석이 "6부 이벤트 소싱의 축소판"이라고 밝힌다. 스냅샷, 아카이빙, 재생 같은 완화책은 전부 그쪽 표준 처방이다.
