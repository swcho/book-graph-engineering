# 참조 아키텍처를 어떤 형태로 적어야 하는가?

**답: 그림이 아니라 검사 가능한 형태로 적는다. 그림은 6개월이면 코드와 갈라진다.**

## 왜 그림이 문제인가

참조 아키텍처를 다이어그램(그림)으로만 남기면, 그림은 코드와 함께 진화하지 않습니다. 코드에 새 호출 경로가 추가되고 컴포넌트가 늘어나도 그림은 그대로 있어서, 6개월쯤 지나면 그림과 실제 코드가 서로 다른 이야기를 하게 됩니다.

이 문제에 대한 흔한 대응은 「그림을 갱신하자」입니다. 하지만 그림 갱신은 사람의 기억과 성실함에 의존하는 수작업이라 곧 다시 갈라집니다. 책의 표현대로:

> 그림으로만 있는 아키텍처는 6개월이면 코드와 갈라진다.
> 다들 겪는 일이고, 다들 «그림을 갱신하자»로 대응한다. 그러면 또 갈라진다.

## 검사 가능한 형태란 무엇인가

계층(layer)과 규칙(rule)을 **데이터와 코드로** 적고, 위반을 프로그램이 자동으로 찾게 만드는 것입니다. 29장의 `ex5_reference_arch.py`가 그 예시입니다.

- **계층을 데이터로**: `LAYERS = ["표현", "오케스트레이션", "도메인", "그래프", "저장"]`
- **구성 요소와 호출 관계를 데이터로**: 각 컴포넌트가 어느 계층에 속하고 무엇을 부르는지를 딕셔너리로 기록
- **규칙을 검사 함수로**: 지금까지 그림에 안 적히고 「머릿속에만 있던」 규칙들을 코드로 옮김
  1. **아래로만 부른다** — 순환 의존을 막는다
  2. **계층을 건너뛰지 않는다** — 오케스트레이터가 저장소를 직접 안 만진다
  3. **그래프 쓰기는 쓰기 관문을 거친다** — 관문을 우회하는 경로가 생기면 관문은 있으나 마나가 되는데, 그런 우회는 «급할 때» 생긴다 (28장의 쓰기 관문 패턴)

이렇게 적으면 `check()` 함수 하나로 전체 호출 관계를 순회하며 규칙 위반을 자동으로 찾아냅니다. 예제에는 일부러 위반(승인 게이트가 체크포인트 저장소를 직접 부르는 경로)을 하나 넣어 두었고, 검사가 이를 잡아냅니다.

## CI에 넣으면 생기는 일

검사 가능한 형태의 진짜 값어치는 **CI 파이프라인에서 자동으로 돌릴 수 있다**는 점입니다.

- 누군가 새 호출을 추가하면서 아키텍처 규칙을 어기면 **머지가 안 됩니다**.
- 아키텍처 위반이 코드 리뷰어의 눈썰미가 아니라 자동 검사에서 걸립니다.
- 이 발상은 업계에서 **아키텍처 적합성 함수(architectural fitness function)** 라고 불리는 사실상 표준 기법입니다 (ThoughtWorks, *Building Evolutionary Architectures*). 비슷한 도구로 Java의 ArchUnit, .NET의 NetArchTest 등이 있습니다.

## 방향이 중요하다: 코드 → 그림, 그림 → 코드는 불가

> 이 파일이 곧 아키텍처 문서다. 그림은 이걸로 «생성»하면 된다.
> 반대로 하면 안 된다. 그림에서 코드를 생성할 수는 없으니까.

- 검사 가능한 데이터(단일 진실)에서 다이어그램을 **생성**하는 것은 가능하고, 그러면 그림이 항상 최신입니다.
- 그림을 원본으로 삼으면 그림은 검사에 쓸 수 없고, 결국 장식이 됩니다.

## 이 장의 다른 조언과 연결

- 참조 아키텍처를 **처음부터 다 만들지 말 것**. 아픈 것부터 만들되, *나중에 넣기 어려운 것*(예: `Reads` 엣지 — 실행이 어떤 사실을 읽었는지의 계보)만 미리 넣는다.
- 검사 가능한 아키텍처는 29장 전체의 주제(지식과 실행을 한 백본으로 잇되, 쓰기 부하 때문에 절충하는 설계)를 **팀이 지켜지게 만드는 장치**입니다. 설계가 아무리 옳아도 우회 경로가 생기면 무너지는데, 그 우회를 CI가 막아 줍니다.

## 한 줄 정리

참조 아키텍처는 사람이 보는 그림이 아니라 **기계가 검사할 수 있는 데이터 + 규칙**으로 적는다. 그래야 CI에서 위반을 잡고, 그림은 그 데이터에서 생성한다.
