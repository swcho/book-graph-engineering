# 29장이 제시하는 절충안은 무엇인가?

**답: 상태 본문은 빠른 저장소에 두고, 그래프에는 링크만 남긴다.**

## 왜 절충이 필요한가

29장은 지식 그래프(사실)와 에이전트 실행 상태(워크플로)를 다루는 세 가지 구성을 비교합니다.

| 구성 | 교차 질의 | 한 트랜잭션 | 쓰기 부하 |
|---|---|---|---|
| 따로 (그래프 DB + 상태 저장소) | ✗ | ✗ | 낮음 (~90ms/s) |
| 완전히 합침 (한 그래프 DB) | ○ | ○ | **매우 높음 (~937ms/s, 거의 포화)** |
| **절충 (본문은 별도, 링크만 그래프)** | ○ | ✗ | 중간 (~191ms/s) |

- **따로 두면** 같은 사실이 두 곳에 존재해 에러 없이 갈라집니다(ex1: 사흘 승인 대기 중 팀장이 바뀌었는데, 옛 값으로 보고서를 보내는 사고).
- **완전히 합치면** 교차 질의와 계보 추적이 되지만, 실행 상태 쓰기가 지식 쓰기보다 훨씬 많아서(예제 워크로드에서 약 70배: 220/s 대 3/s) 쓰기 부하가 열 배로 뜁니다. 그래프 DB는 「관계를 따라가는」 데 최적화돼 있지, 「초당 수백 건의 작은 갱신」에 최적화돼 있지 않습니다. 슈퍼스텝마다 상태를 통째로 저장하는 패턴(21장)과 특히 안 맞습니다.

## 절충안의 구체적인 모습

- **상태 본문(체크포인트)** → SQLite·Postgres 같은 빠른 저장소에 저장.
- **그래프에는 링크만** → `Run` 노드 하나 + `Reads`/`Writes` 엣지 몇 개.

이렇게 하면:

1. **교차 질의는 유지된다** — 그래프에 링크가 있으므로 「이 실행이 어떤 사실을 읽었나」, 「이 사실이 틀리면 어떤 실행이 무너지나」 같은 계보(lineage) 질문에 한 쿼리로 답할 수 있다.
2. **쓰기 부하는 막힌다** — 부하가 「따로」의 두 배 수준으로 억제된다 (「합침」의 약 5분의 1).
3. **대신 「한 트랜잭션」은 포기한다** — 두 저장소를 한 트랜잭션으로 묶을 수 없으므로 갈라짐 가능성이 다시 생긴다. 그래서 30장의 이벤트 소싱과 31장의 낙관적 잠금으로 「갈라진 것을 감지」하는 장치가 필요해진다.

## 이것은 타협이 아니라 옳은 설계

지식과 실행 상태는 **수명이 다릅니다**. 지식은 오래 살고 실행 상태는 워크플로가 끝나면 대부분 필요 없어집니다. 저마다 최적화된 저장소에 두는 다중 저장소(polyglot persistence)가 자연스럽습니다. 던져야 할 질문은 「무엇을 같은 그래프에 둘까」가 아니라 **「무엇을 엣지로 이어야 하나」**이고, 그 답이 `Reads` 엣지입니다 — 나중에 넣기 어려우니 처음부터 넣어야 하는 것이기도 합니다.
