# 그래프 DB가 실행 상태 쓰기에 안 맞는 이유

## 질문
그래프 DB가 실행 상태 쓰기에 안 맞는 이유는 무엇인가?

## 답
관계를 따라가는 데 최적화되어 있고 초당 수백 건의 작은 갱신에 최적화되어 있지 않다. 슈퍼스텝마다 상태를 통째로 쓰는 21장 패턴과 특히 안 맞는다.

---

## 자세한 설명

### 워크로드가 근본적으로 다르다

29장은 "지식 그래프와 실행 상태를 한 저장소에 완전히 합치면 어떨까"를 검토하는데, 예제 4(`ex4_split_cost.py`)가 그 대가를 수치로 보여줍니다. 두 종류의 쓰기는 성격과 규모가 전혀 다릅니다.

| 워크로드 | 초당 건수 (예제 기준) | 성격 |
|---|---|---|
| 지식 갱신 (KG write) | 3/s | 드물고, 오래 남고, 관계 중심 |
| 실행 상태 쓰기 (Run state write) | 220/s | 잦고, 수명이 짧고, 덩어리(blob) 중심 |

실행 상태 쓰기가 지식 쓰기보다 **약 70배** 많습니다. 에이전트 워크플로는 슈퍼스텝(21장)마다 체크포인트로 상태 전체를 저장하기 때문입니다. 이 패턴은 "작은 갱신을 초당 수백 건" 쏟아붓는 워크로드이고, 그래프 DB가 잘하는 일이 아닙니다.

### 그래프 DB의 최적화 방향

그래프 DB는 **관계를 따라가는 것(traversal)** — "이 노드에서 엣지를 타고 몇 홉을 건너가라" — 에 최적화되어 있습니다. 인덱스 구조, 저장 레이아웃, 트랜잭션 처리 모두 읽기·순회 중심으로 설계됩니다. 반면 실행 상태 체크포인트는 관계 질의가 거의 필요 없는, 키 하나에 값 덩어리를 덮어쓰는 작업입니다. 키-값 저장소가 훨씬 잘하는 일이죠.

예제 4의 측정값(21장에서 잰 값을 단순화)이 이 차이를 보여줍니다.

- 그래프 DB 쓰기 1건: **4.2ms**
- 키-값 저장소 쓰기 1건: **0.35ms** (약 12배 차이)

### 완전히 합치면 포화한다

세 구성을 초당 쓰기 부하로 비교하면:

| 구성 | 초당 부하 | 교차 질의 | 한 트랜잭션 |
|---|---|---|---|
| 따로 (그래프 DB + 상태 저장소) | 90ms | 불가 | 불가 |
| **합침 (한 그래프 DB)** | **937ms** | 가능 | 가능 |
| 절충 (본문은 별도, 링크만 그래프에) | 191ms | 가능 | 불가 |

초당 처리 가능한 시간이 1,000ms이므로, "합침" 구성은 **937ms로 거의 포화 상태**입니다. 실행 상태 쓰기 220/s를 전부 4.2ms짜리 그래프 쓰기로 보내기 때문입니다. "따로"의 90ms보다 열 배가 넘습니다.

### 그래서 실무의 답은 절충

- **실행 상태 본문(체크포인트)**: SQLite·Postgres 같은 빠른 저장소에 둔다.
- **그래프에는 링크만**: Run 노드 하나 + `Reads`/`Writes` 엣지 몇 개만 남긴다.

이러면 교차 질의("이 실행이 어떤 사실을 읽었나", "이 사실이 틀리면 어떤 실행이 무너지나")는 그래프의 링크로 여전히 가능하면서, 부하는 191ms로 막힙니다. 대신 두 저장소를 한 트랜잭션으로 묶는 것은 포기하므로, 예제 1의 "갈라짐" 문제가 다시 생깁니다 — 이것이 30장의 이벤트 소싱과 31장의 낙관적 잠금이 필요해지는 이유입니다.

### 핵심 정리

1. 그래프 DB는 **관계 순회 최적화** 저장소이지, 고빈도 소규모 갱신용이 아니다.
2. 실행 상태는 슈퍼스텝마다 통째로 쓰이는 고빈도 워크로드라(지식 쓰기의 ~70배) 그래프 DB에 전부 보내면 쓰기 부하가 열 배로 뛰어 포화한다.
3. 이는 수명이 다른 데이터를 다른 저장소에 두는 폴리글랏 퍼시스턴스(polyglot persistence)의 전형적인 사례이며, "무엇을 같은 그래프에 둘까"가 아니라 "무엇을 엣지로 이어야 하나"를 물어야 한다.
