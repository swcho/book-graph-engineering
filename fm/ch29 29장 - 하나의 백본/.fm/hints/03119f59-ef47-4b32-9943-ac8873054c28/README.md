# 한 그래프에 지식과 실행을 두면 무엇이 새로 생기는가?

**답: 따로 뒀을 때 그릴 곳이 없던 엣지 — 즉 「이 실행이 저 사실을 읽었다」(`Reads`)는 관계가 생긴다.**

## 왜 "따로 두면 그릴 곳이 없는" 엣지인가

엣지는 양 끝 노드가 **같은 저장소 안에** 있어야 그릴 수 있다.

- 지식 그래프만 있는 저장소: `박민수 -[이끔]-> 결제팀` 같은 사실(지식) 엣지는 그릴 수 있다. 하지만 "누가 이 사실을 읽어갔나"는 모른다.
- 에이전트 상태 저장소(체크포인트): 실행이 "그때 읽은 값"을 들고 있지만, 다른 실행이 뭘 읽었는지, 그 값이 지식 그래프의 어느 노드였는지는 모른다.

즉 **실행(Run) 노드와 사실(Entity) 노드가 서로 다른 시스템에 살면, 둘을 잇는 엣지는 어디에도 존재할 수 없다.** 한 그래프에 두 종류의 노드를 같이 두는 순간에야 비로소 이 엣지를 그릴 자리가 생긴다.

## 이 장(29장)의 스키마로 보면

노드 종류는 나누되 저장소는 하나로 한다 (ex2_one_backbone.py):

```
Entity (지식: 사람, 팀, 문서)      Run (실행: 워크플로 인스턴스)
        └──────── Reads / Writes / About 엣지로 연결 ────────┘
```

- `Knows(Entity→Entity)`: 지식끼리의 관계 (기존에도 있던 것)
- **`Reads(Run→Entity, at, as_of)`: 실행이 사실을 읽었다는 관계 — 새로 생기는 엣지.** 읽은 시각(`at`)과 기준 시각(`as_of`)을 함께 적는다.
- `Writes`, `About`: 실행이 만든 것, 실행의 대상.

## 이 엣지가 있으면 새로 가능해지는 질문

1. **이 실행은 무엇을 근거로 했나?** — Run에서 Reads를 따라가면 근거 목록이 나온다.
2. **이 사실을 근거로 삼은 실행이 몇 개인가?** — 따로 두면 아예 못 하는 질문. 지식 그래프는 자기를 누가 읽었는지 모르고, 상태 저장소는 남의 실행을 모른다.
3. **재개하려는 실행이 그때 읽은 값이 아직 유효한가?** — `Reads`의 기준 시각으로 다시 조회해서 달라졌으면 멈춘다. 1번 예제의 "팀장이 바뀌었는데 옛 값으로 보고서를 보낸" 사고를 막는 방법이다.

## 엣지 → 계보, 계보의 두 방향

이 `Reads`(그리고 `Writes`, 기댐) 엣지들이 쌓이면 **계보(lineage)** 가 된다. 같은 엣지를 반대 방향으로 따라가면 서로 다른 운영 질문에 답한다:

- **정방향**: 「왜 이 답이 나왔나」 — 답 → 실행 → 읽은 사실 → 출처를 한 쿼리로 거슬러 올라간다.
- **역방향**: 「이 출처가 틀리면 뭐가 무너지나」 — 오염된 출처에 기댄 답·실행을 전부 찾는다.

## 주의점 두 가지

- **저절로 생기지 않는다.** 실행할 때마다 `Reads`·`Writes` 엣지를 명시적으로 만들어야 한다. 실행마다 엣지가 서너 개씩 늘어나는 게 그 값이다.
- **완전 통합은 비싸다.** 실행 상태 쓰기가 지식 쓰기보다 훨씬 많아(예제에선 70배) 전부 그래프 DB로 보내면 쓰기 부하가 열 배로 뛴다. 그래서 실무 절충은 **상태 본문은 빠른 저장소(SQLite/Postgres)에, 그래프에는 링크(Run 노드 + Reads/Writes 엣지)만** 남기는 것. 교차 질의는 살리고 부하는 막는다.

핵심 한 줄: 물을 것은 「무엇을 같은 그래프에 둘까」가 아니라 **「무엇을 엣지로 이어야 하나」**이고, 나중에 넣기 어려운 `Reads` 엣지는 처음부터 넣어야 한다.
