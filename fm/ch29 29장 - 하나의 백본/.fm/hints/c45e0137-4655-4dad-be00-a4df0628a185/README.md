# 완전히 합치면 무엇이 나빠지는가?

**답: 쓰기 부하가 열 배가 된다. 실행 상태 쓰기가 지식 쓰기보다 훨씬 많기 때문이다.**

## 왜 하필 「쓰기」가 문제인가

29장은 지식 그래프와 에이전트 실행 상태를 한 그래프에 합치자고 주장하는 장인데, 29.4절에서 스스로 브레이크를 겁니다. 합치는 게 공짜였으면 이 절이 없었을 거예요.

핵심은 **두 워크로드의 쓰기 빈도가 완전히 다르다**는 점입니다. 예제 4(`ex4_split_cost.py`)의 가정 워크로드를 보면:

| 항목 | 빈도 | 성격 |
|---|---|---|
| 지식 쓰기 (KG write) | 3/s | 팀장이 바뀌는 정도의 드문 갱신 |
| 실행 상태 쓰기 (Run write) | 220/s | 슈퍼스텝마다 상태를 통째로 저장 (21장의 체크포인트 패턴) |

실행 상태 쓰기가 지식 쓰기보다 **약 70배** 많습니다. 완전히 합치면 이 220/s가 전부 그래프 DB로 몰립니다.

## 숫자로 보면

쓰기 한 건의 비용이 저장소마다 다릅니다 (21장에서 잰 값을 단순화):

- 그래프 DB 쓰기: **4.2ms**
- 키-값 저장소 쓰기: **0.35ms** (약 12배 빠름)

세 구성을 비교하면:

| 구성 | 초당 쓰기 부하 | 교차 질의 | 한 트랜잭션 |
|---|---|---|---|
| 따로 (그래프 + 상태 저장소) | 약 90ms | 불가 | 불가 |
| **합침 (한 그래프 DB)** | **약 937ms** | 가능 | 가능 |
| 절충 (링크만 그래프에) | 약 191ms | 가능 | 불가 |

초당 1,000ms가 한계이므로 「합침」 구성은 이 워크로드에서 **거의 포화 상태**입니다. 「따로」의 90ms 대비 열 배가 넘는 부하죠. 이것이 답의 「쓰기 부하가 열 배」입니다.

## 근본 원인: 그래프 DB의 최적화 방향

그래프 DB는 **관계를 따라가는 읽기**에 최적화돼 있지, **초당 수백 건의 작은 갱신**에 최적화돼 있지 않습니다. 특히 슈퍼스텝마다 상태를 통째로 쓰는 21장의 체크포인트 패턴과는 궁합이 최악입니다. 수명도 다릅니다 — 지식은 오래 살고, 실행 상태는 워크플로가 끝나면 대부분 의미가 없어집니다.

## 그래서 절충안

실무의 답은 「절충」입니다:

- **실행 상태 본문**(체크포인트)은 빠른 저장소에 (SQLite·Postgres 등)
- **그래프에는 링크만**: Run 노드 하나 + `Reads`/`Writes` 엣지 몇 개

이러면 교차 질의(「이 실행이 무엇을 읽었나」)는 여전히 되면서 부하는 191ms — 「합침」의 5분의 1로 막힙니다. 대신 **한 트랜잭션은 포기**하므로, 갈라짐 문제가 다시 생기고 이를 31장의 낙관적 잠금과 30장의 이벤트 소싱으로 「감지」하게 됩니다.

저자는 이 절충이 타협이 아니라 옳은 설계라고 봅니다. 지식과 실행은 수명이 다르니, 물을 것은 「무엇을 같은 그래프에 둘까」가 아니라 **「무엇을 엣지로 이어야 하나」**라는 거죠. 이는 polyglot persistence(다중 저장소) 원칙 — 워크로드 특성에 맞는 저장소를 골라 쓰기 — 와 같은 맥락입니다.

## 암기 포인트

- 나빠지는 것: **쓰기 부하 (열 배)**
- 이유: **실행 상태 쓰기 ≫ 지식 쓰기** (예제에서 220/s vs 3/s, 약 70배)
- 그래프 DB는 잦은 소규모 쓰기에 약함 (4.2ms vs 키-값 0.35ms)
- 해법: 상태 본문은 빠른 저장소에, 그래프에는 링크(Run 노드 + Reads/Writes 엣지)만
