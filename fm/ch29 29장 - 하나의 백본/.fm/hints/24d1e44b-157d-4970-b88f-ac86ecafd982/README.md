# '그래프 쓰기는 관문을 거친다' 규칙이 특히 중요한 이유

## 질문

'그래프 쓰기는 관문을 거친다' 규칙이 특히 중요한 이유는 무엇인가?

## 답

**관문을 만들어 놓고 우회 경로가 생기면 관문이 있으나 마나가 된다. 그런 우회는 급할 때 생긴다.**

## 맥락 — 이 규칙은 어디서 나왔나

29장 예제 5(`ex5_reference_arch.py`)는 참조 아키텍처를 그림이 아니라 **검사 가능한 데이터**로 적는 방법을 보여줍니다. 계층(표현 → 오케스트레이션 → 도메인 → 그래프 → 저장)과 구성 요소, 그리고 호출 관계를 코드로 적고, 규칙 위반을 자동으로 찾아냅니다.

이때 검사하는 규칙 셋은 전부 "머릿속에만 있던 것"들입니다.

1. **아래로만 부른다** — 순환 의존을 막는다
2. **저장 계층을 건너뛰지 않는다** — 오케스트레이터가 저장소를 직접 안 만진다
3. **그래프 쓰기는 관문을 거친다** — 28장에서 온 규칙

코드로는 이렇게 표현됩니다.

```python
("그래프 쓰기는 쓰기 관문을 거친다",
 lambda a, b: not (b == "그래프 DB" and a not in
                   ("그래프 게이트웨이", "쓰기 관문"))),
```

즉 "그래프 DB"를 부를 수 있는 것은 "그래프 게이트웨이"와 "쓰기 관문"뿐이라는 뜻입니다.

## 왜 이 규칙이 '특히' 중요한가

### 1. 관문은 우회로가 하나만 생겨도 무력화된다

쓰기 관문(write gate)은 28장에서 다룬 장치입니다. 에이전트가 스스로 그래프에 쓰기 시작하면 "어디서 온 사실인가"(출처, 검증, 계보)가 품질 관리의 핵심이 되는데, 관문은 모든 쓰기가 반드시 지나가는 단일 지점으로서 검증·출처 기록·정합성 검사를 보장합니다.

그런데 이 보장은 **"모든" 쓰기가 지나갈 때만** 성립합니다. 단 하나의 컴포넌트라도 그래프 DB에 직접 쓰는 경로가 생기면:

- 검증을 안 거친 데이터가 그래프에 들어갈 수 있고,
- 출처(계보) 엣지가 안 붙은 사실이 생기고,
- "그래프에 있는 것은 전부 관문을 통과했다"는 전제 위에 세운 모든 것이 무너집니다.

보안의 방화벽과 같습니다. 문을 아무리 튼튼히 만들어도 옆에 개구멍이 하나 있으면 문은 장식입니다.

### 2. 우회는 '급할 때' 생긴다 — 사람의 규율로는 못 막는다

책이 강조하는 지점이 바로 이것입니다. 우회 경로는 평상시에 생기지 않습니다. 장애 대응 중에, 마감 직전에, "이번 한 번만 직접 고치자" 하는 순간에 생깁니다. 그때는 코드 리뷰도 느슨해지고, "나중에 정리하자"는 약속은 지켜지지 않습니다.

그래서 이 규칙은 문서나 컨벤션(머릿속 규칙)으로 두면 반드시 깨집니다. **CI에서 자동으로 검사되는 형태**로 적어야, 급할 때 누군가 그래프 DB를 직접 부르는 호출을 추가하면 머지 자체가 막힙니다. 사람의 의지가 가장 약해지는 순간에 기계가 대신 막아 주는 것이죠.

### 3. 다른 두 규칙보다 깨졌을 때의 피해가 조용하고 깊다

- "아래로만 부른다"가 깨지면 순환 의존 — 빌드나 설계 수준에서 비교적 빨리 드러납니다.
- "계층을 건너뛰지 않는다"가 깨지면 결합도 증가 — 리팩토링 비용 문제입니다.
- 그러나 "관문을 거친다"가 깨지면 **데이터 자체가 오염**됩니다. 에러 없이, 조용히. 그리고 그래프의 사실은 다른 실행들이 읽어 가므로(29장의 `Reads` 엣지) 오염이 계보를 따라 번집니다. 나중에 발견해도 어디까지 번졌는지 추적하기 어렵습니다.

## 예제 5가 보여주는 방식

예제 코드는 일부러 규칙 위반을 하나 심어 둡니다 — "승인 게이트"가 "체크포인트 저장소"(저장 계층)를 직접 부르는 호출입니다. 검사를 돌리면 이 위반이 자동으로 걸립니다. 이 파일을 CI에 넣으면 새 호출이 규칙을 어길 때 머지가 안 되고, 그림으로만 있던 아키텍처가 6개월 뒤 코드와 갈라지는 문제도 함께 해결됩니다.

## 기억할 한 줄

> 관문의 가치는 예외가 없다는 데서 나온다. 우회는 급할 때 생기므로, 규칙을 사람의 기억이 아니라 CI가 돌리는 검사로 적어야 한다.
