# 지식과 실행을 따로 두면 계보 추적이 왜 어려운가?

**한 줄 답**: 실행 로그와 지식 그래프가 따로 있어, 「답 → 실행 → 읽은 사실 → 출처」의 사슬을 사람이 두 시스템을 오가며 손으로 이어야 하기 때문이다.

## 계보(lineage)란 무엇인가

계보 추적은 어떤 결과물이 **무엇을 거쳐 나왔는지**를 거슬러 올라가는 것이다 (W3C PROV의 derivation 개념과 같은 뿌리). 29장 예제 3이 다루는 사슬은 이렇다.

```
답(Answer) → 실행(Run) → 단계(Step) → 읽은 사실(Fact) → 출처(Source)
```

예: 「3분기 환불률이 늘어난 이유는 배송 지연」이라는 답은
- 분석 워크플로 #4821(실행)이 만들었고,
- 그 실행의 각 단계가 「환불 사유 1위 = 배송 지연(41%)」, 「평균 배송일 4.2일」 같은 사실을 읽었으며,
- 각 사실은 주문 DB 스냅숏, 물류 대시보드 같은 출처에서 왔다.

## 따로 두면 왜 끊어지는가

지식과 실행을 분리하면 위 사슬이 **시스템 경계에서 두 동강** 난다.

| 구간 | 어디에 있나 |
|---|---|
| 답 → 실행 → 단계 | 실행 로그 / 에이전트 상태 저장소 |
| 사실 → 출처 | 지식 그래프 |
| **실행 → 읽은 사실** | **어디에도 없음** — 그릴 곳이 없는 엣지 |

핵심은 세 번째 줄이다. 「이 실행이 저 사실을 읽었다」는 관계는 두 저장소를 **가로지르는** 관계라서, 따로 두면 이 엣지를 저장할 자리 자체가 없다. 그래서:

- **지식 그래프는 자기를 누가 읽었는지 모른다.** 「이서연을 근거로 삼은 실행이 몇 개인가?」 같은 질문을 아예 못 한다.
- **실행 로그는 자신이 읽은 값이 지식 그래프의 어느 노드였는지 모른다.** 로그에는 값의 복사본만 남지, 그래프 노드로의 참조가 없다.
- 결국 감사·디버깅 때 사람이 실행 로그의 타임스탬프와 값을 보고, 지식 그래프를 따로 조회해서, 눈과 손으로 대조하며 이어 붙여야 한다. 느리고, 빠뜨리기 쉽고, 자동화가 안 된다.

## 합치면 무엇이 되는가

한 그래프(하나의 백본)에 `Entity`(지식)와 `Run`(실행)을 노드로 같이 두면, `Reads`/`Writes`/`기댐` 엣지로 두 세계를 이을 수 있고, 계보가 **쿼리 한 줄**이 된다.

```cypher
MATCH (a:Node {id:'ans1'})-[:Link*1..4]->(x:Node)
RETURN DISTINCT x.kind, x.label
```

같은 엣지를 반대로 따라가면 역방향 질문도 된다.

- **정방향**: 왜 이 답이 나왔나? (답 → 출처)
- **역방향**: 이 출처가 틀리면 뭐가 무너지나? (출처 → 영향받는 답·사실)

이 두 질문이 운영에서 제일 자주 나오는데, 특히 28장처럼 에이전트가 그래프에 직접 쓰기 시작하면 「어디서 온 사실인가」가 품질 관리의 핵심이 되어, 이 경로가 없으면 손을 못 쓴다.

## 주의: 공짜가 아니다

- 계보 엣지는 **저절로 생기지 않는다.** 실행할 때마다 `Reads`·`Writes`·`기댐` 엣지를 명시적으로 만들어야 하고, 실행마다 엣지가 서너 개씩 늘어난다.
- 완전히 한 저장소로 합치면 쓰기 부하가 폭증한다(실행 상태 쓰기가 지식 쓰기보다 훨씬 많음). 그래서 실무 절충은 **상태 본문은 빠른 저장소에, 그래프에는 링크(Run 노드 + Reads/Writes 엣지)만** 남기는 것이다. 이렇게 하면 교차 질의(계보)는 살리고 부하는 억제한다.
- 이 때문에 책은 `Reads` 엣지를 「나중에 넣기 어려운 것」으로 꼽는다 — 처음부터 안 넣으면 과거 실행의 계보는 영영 복원할 수 없다.
