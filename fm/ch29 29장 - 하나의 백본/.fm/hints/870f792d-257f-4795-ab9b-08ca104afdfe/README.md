# Reads 엣지에 `as_of`를 적는 이유

## 질문
Reads 엣지에 `as_of`를 적는 이유는 무엇인가?

## 답
재개할 때 그 기준 시각으로 다시 조회해 값이 달라졌으면 멈출 수 있다. 23장의 상태 지문과 같은 발상이다.

---

## 배경 — 예제 1의 사고

29장(29.1절)의 예제 1은 지식 그래프와 에이전트 상태를 **따로** 두면 생기는 사고를 보여줍니다.

1. **[t0]** 워크플로가 지식 그래프에서 "결제팀 팀장 = 박민수"를 읽어 에이전트 상태에 담는다.
2. **[t1]** 사람 승인을 기다리며 사흘을 멈춘다(23장의 human-in-the-loop).
3. **[t2]** 그 사이 팀장이 이서연으로 바뀐다. 지식 그래프만 갱신된다.
4. **[t3]** 승인이 나서 재개되고, 상태에 남아 있던 옛 값으로 보고서를 **박민수**에게 보낸다. 지금 팀장은 이서연인데.

두 저장소가 갈라졌고, **아무 에러도 나지 않았습니다**. 에이전트 상태는 "그때 읽은 값"을 들고 있고(체크포인트 덕에 사흘 뒤에도 그대로, 21장), 지식 그래프는 "지금 값"을 갖고 있습니다. 둘 다 자기 일을 제대로 했는데 결과가 틀린 거죠.

책이 제시하는 절충안이 바로 **"상태에 담되 «읽은 시각»을 같이 담고, 쓰기 전에 다시 확인한다"** 입니다. 그 "읽은 시각"을 그래프에 새기는 자리가 Reads 엣지의 `as_of` 속성입니다.

## 예제 2 — `as_of`가 하는 일

한 그래프에 지식(Entity/Knows)과 실행(Run)을 같이 두면, 실행이 어떤 사실을 읽었는지를 **엣지로** 그릴 수 있습니다.

```cypher
CREATE REL TABLE Reads(FROM Run TO Entity, at STRING, as_of STRING);
```

- `at`: 실제로 읽은 시각 (예: `2026-03-02T14:00`)
- `as_of`: 그 읽기가 유효하다고 본 **기준 시각** (예: `2026-03-02`)

실행 r2(연간 평가)는 3월 2일에 "팀장 = 박민수"를 읽고 승인 대기에 들어갔습니다. 5월에 재개하려는 시점에 이렇게 검사합니다.

```cypher
-- 지금(2026-05-23) 기준으로 팀장이 누구인지 다시 조회
MATCH (p:Entity)-[e:Knows {kind:'이끔'}]->(:Entity {id:'e3'})
WHERE e.vfrom <= '2026-05-23' AND e.vto > '2026-05-23'
RETURN p.name
```

그때 읽은 값(Reads 엣지에 적힌 것)과 지금 값을 비교합니다.

| 실행 | 워크플로 | 그때 읽은 값 | 기준 시각(as_of) | 지금 | 판정 |
|---|---|---|---|---|---|
| r1 | 보고서 발송 | 이서연 | 2026-05-20 | 이서연 | 진행해도 된다 |
| r2 | 연간 평가 | 박민수 | 2026-03-02 | 이서연 | **멈춤 — 다시 확인** |

r2가 걸렸습니다. 3월에 읽은 값으로 5월에 실행하려던 참이었죠. `as_of`가 없었다면 이 비교 자체를 할 수 없고, 예제 1의 사고가 그대로 재현됩니다.

## 23장 상태 지문과의 관계

이 검사는 23장의 **상태 지문**(state fingerprint)과 같은 발상입니다. 사람 승인을 기다리는 동안 세상이 바뀌었을 수 있으니, 재개 직전에 "승인 당시 전제가 아직 유효한가"를 확인하고 아니면 멈추는 것이죠.

차이점은 구현 방식입니다.

- **23장**: 판단의 전제가 된 값들을 해시로 뭉쳐 **지문을 따로 만들어** 저장하고, 재개 시 다시 계산해 비교.
- **29장**: 지문을 따로 만들지 않고 **그래프 자체로 비교**. Reads 엣지에 무엇을 언제 기준으로 읽었는지가 이미 적혀 있으므로, 같은 쿼리를 지금 시각으로 다시 돌려 값이 달라졌는지 보면 된다.

## 왜 "나중에 넣기 어려운 것"인가

이 장의 요약이 강조하듯, 아키텍처를 처음부터 다 만들 필요는 없지만 **Reads 엣지는 미리 넣어야 합니다**. 어떤 실행이 어떤 사실을 언제 기준으로 읽었는지는 읽는 그 순간에만 기록할 수 있고, 지나고 나서는 복원할 수 없기 때문입니다. 이는 데이터베이스의 read timestamp(PostgreSQL 트랜잭션 격리의 스냅숏 시각)나 W3C PROV의 계보(lineage) 추적과 같은 계열의 아이디어입니다.

## 핵심 정리

- `as_of` = 이 실행이 이 사실을 **어느 시점 기준으로** 읽었는지의 기록.
- 재개(resume) 시 그 기준 시각의 값과 지금 값을 **같은 쿼리로** 다시 비교 → 달라졌으면 멈추고 다시 확인.
- 23장 상태 지문과 같은 발상이되, 지문을 따로 만들지 않고 그래프 자체가 비교 근거가 된다.
- 사후에 복원할 수 없는 기록이므로, 백본을 점진적으로 만들더라도 Reads 엣지만은 처음부터 넣는다.
