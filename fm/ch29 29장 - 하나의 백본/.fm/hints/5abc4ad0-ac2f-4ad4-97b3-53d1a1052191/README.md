# "매번 최신을 읽기"가 답이 아닌 이유

## 카드 요약

- **질문**: "매번 최신을 읽기"가 답이 아닌 이유는 무엇인가?
- **답**: 워크플로 안에서 값이 바뀌면 판단이 앞뒤가 안 맞는다. 상태에 담는 것은 게으름이 아니라 의도적인 스냅숏이다.

## 문제의 배경 — 두 저장소가 갈라진다

29장은 지식 그래프(사실)와 에이전트 실행 상태(진행 중인 워크플로의 기억)를 따로 두면 생기는 사고에서 출발합니다. 예제 1(`ex1_two_stores.py`)의 시나리오가 전형적입니다.

1. **t0** — 워크플로가 시작하며 지식 그래프에서 "결제팀 팀장 = 박민수"를 읽어 상태에 담는다.
2. **t1** — 사람 승인을 기다리며 사흘을 멈춘다(23장의 휴먼 인 더 루프).
3. **t2** — 그사이 팀장이 이서연으로 바뀌고, 지식 그래프만 갱신된다.
4. **t3** — 승인이 나서 재개된 워크플로는 상태에 담긴 옛 값으로 실행한다. → **보고서를 박민수에게 보냈다. 그런데 지금 팀장은 이서연이다.**

핵심은 "아무 에러도 안 났다"는 점입니다. 상태는 «그때 읽은 값»을 들고 있는 게 자기 일이고, 그래프는 «지금 값»을 갖고 있는 게 자기 일입니다. 둘 다 제대로 했는데 결과가 틀렸습니다.

## 그럼 "상태에 담지 말고 매번 그래프에서 최신을 읽으면" 되지 않나?

직관적으로 떠오르는 첫 해법이지만, 책은 이것이 답이 아니라고 못 박습니다. 이유는 두 겹입니다.

### 1. 느리다 (부차적 이유)

읽을 때마다 그래프를 조회하면 조회 비용이 매 단계마다 붙습니다. 하지만 이건 부차적인 문제입니다.

### 2. 워크플로 안에서 값이 바뀌면 판단이 앞뒤가 안 맞는다 (본질적 이유)

사흘짜리 워크플로를 생각해 보세요. 매번 최신을 읽으면:

- **1단계**에서 "팀장 = 박민수"를 전제로 초안을 만들고,
- **4단계**에서 다시 읽었더니 "팀장 = 이서연"이 되어 있으면,
- 같은 실행 안에서 앞 단계의 판단과 뒤 단계의 판단이 **서로 다른 세계**를 전제로 하게 됩니다.

즉, 하나의 워크플로가 내부적으로 **일관성 없는 판단들의 조합**이 됩니다. 오래된 값으로 끝까지 일관되게 실행하는 것보다 더 진단하기 어려운 결과가 나올 수 있습니다. 앞부분은 박민수 기준, 뒷부분은 이서연 기준으로 만든 보고서는 누구 기준으로도 맞지 않으니까요.

이는 데이터베이스에서 트랜잭션 격리(예: PostgreSQL의 read timestamp / 스냅숏 격리)가 존재하는 이유와 같은 발상입니다. 하나의 논리적 작업 단위는 **한 시점의 일관된 스냅숏** 위에서 판단해야 앞뒤가 맞습니다.

## "상태에 담기"의 재해석 — 게으름이 아니라 의도적 스냅숏

그래서 읽은 값을 상태에 담는 것은 "매번 조회하기 귀찮아서 캐싱한 것"(게으름)이 아닙니다. **"이 실행은 이 시점의 세계를 기준으로 판단한다"는 의도적인 스냅숏 선언**입니다.

다만 스냅숏만으로는 예제 1의 사고를 못 막습니다. 그래서 책이 제시하는 실무 절충은:

> **"담아 두되, 쓰기 직전에 확인하기"** — 그러려면 값 옆에 **«읽은 시각»(as_of)**이 붙어 있어야 한다.

예제 2(`ex2_one_backbone.py`)가 이것을 구현합니다. `Run` 노드가 `Reads` 엣지로 읽은 사실을 가리키고, 엣지에 `at`(읽은 시각)과 `as_of`(기준 시각)를 적어 둡니다. 워크플로를 재개할 때 "그때 읽은 값이 아직 유효한가?"를 그래프로 다시 조회해서:

- 값이 그대로면 → **진행해도 된다**
- 달라졌으면 → **멈춤 — 다시 확인** (3월에 박민수를 읽고 5월에 재개하려던 r2가 여기서 걸림)

## 세 가지 선택지 정리

| 선택지 | 내용 | 평가 |
|---|---|---|
| 1. 매번 최신 조회 | 상태에 담지 않고 항상 그래프를 읽음 | 느리고, **워크플로 중간에 값이 바뀌면 판단이 앞뒤가 안 맞음** — 답이 아님 |
| 2. 담되 읽은 시각 기록 + 쓰기 전 재확인 | 스냅숏 + 유효성 검증 | **실무의 절충** |
| 3. 아예 한 저장소(하나의 백본) | 지식과 실행을 한 그래프에 | **목표** — 단, 완전 통합은 쓰기 부하 때문에 안 되고, 상태 본문은 빠른 저장소에 두고 그래프엔 링크만 남기는 절충으로 감 |

## 기억 포인트

- "매번 최신 읽기"의 치명상은 속도가 아니라 **실행 내부의 판단 비일관성**이다.
- 상태에 담기 = **의도적 스냅숏** (트랜잭션 격리의 read timestamp와 같은 발상).
- 완성형 해법은 "담아 두되 + 읽은 시각(as_of)을 함께 기록 + 쓰기 직전 재확인"이며, 이것이 `Reads` 엣지를 나중에 넣기 어려운 것으로서 처음부터 넣으라는 29장의 조언으로 이어진다.
