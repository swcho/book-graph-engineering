# 아키텍처를 만들 때 미리 넣어야 하는 것

**Q. 아키텍처를 만들 때 미리 넣어야 하는 것은 무엇인가?**

**A. 나중에 넣기 어려운 것만 미리 넣는다. `Reads` 엣지가 그렇다.**

## 핵심 원칙

29장(하나의 백본)의 마지막 조언은 이렇습니다.

> 그 아키텍처를 처음부터 다 만들지 마세요. **아픈 것부터** 만들되, ***나중에 넣기 어려운 것*만 미리 넣으세요.** `Reads` 엣지가 그렇습니다.

즉 판단 기준은 두 가지입니다.

1. **지금 아픈가?** — 아프지 않은 것은 아직 만들지 않는다 (과잉 설계 방지, YAGNI와 같은 정신).
2. **나중에 넣기 어려운가?** — 어렵다면 지금 당장 필요 없어 보여도 미리 넣는다.

대부분의 구성 요소는 나중에 붙여도 됩니다. 캐시, 게이트웨이, 별도 서비스 같은 것은 필요해질 때 추가할 수 있어요. 문제는 **"기록"** 성격의 것들입니다. 기록은 그 시점에 남기지 않으면 영원히 복원할 수 없습니다.

## 왜 `Reads` 엣지인가

`Reads` 엣지는 「이 실행(Run)이 저 사실(Entity)을 언제, 어느 기준 시각으로 읽었다」를 그래프에 남기는 엣지입니다.

```
CREATE REL TABLE Reads(FROM Run TO Entity, at STRING, as_of STRING);
```

이 엣지가 "나중에 넣기 어려운" 이유:

- **과거는 재구성할 수 없다.** 6개월 뒤에 계보 추적이 필요해져서 `Reads` 엣지를 추가해도, 이미 지나간 실행들이 무엇을 읽었는지는 아무 데도 남아 있지 않습니다. 스키마는 나중에 바꿀 수 있지만 데이터는 소급이 안 됩니다.
- **읽는 순간에만 잡을 수 있는 정보다.** 코드가 그래프를 읽는 그 시점에 엣지를 만들어야 합니다. 로그를 뒤져 복원하는 것은 사실상 불가능하거나 매우 부정확합니다.

## `Reads` 엣지가 사주는 것

이 엣지 하나가 29장의 핵심 능력 두 가지를 떠받칩니다.

**1. 갈라짐 감지 (예제 1·2)** — 상태에 담아 둔 값이 "그때 읽은 값"인데, 워크플로가 사흘 뒤 재개될 때 지식 그래프의 "지금 값"과 다를 수 있습니다. `Reads` 엣지에 기준 시각(`as_of`)이 적혀 있으니, 재개 시점에 그 시각으로 다시 조회해 달라졌으면 멈출 수 있습니다.

**2. 계보(lineage) 추적 (예제 3)** — 같은 엣지를 두 방향으로 따라갑니다.

- 정방향: 「왜 이 답이 나왔나」 (답 → 실행 → 읽은 사실 → 출처)
- 역방향: 「이 출처가 틀리면 뭐가 무너지나」 (출처 → 사실 → 실행 → 답)

이 경로는 저절로 생기지 않습니다. 실행할 때마다 `Reads`·`Writes`·`기댐` 엣지를 만들어야 하고, 그게 실행마다 엣지 서너 개씩의 비용입니다. 그 비용을 처음부터 지불하는 이유가 바로 "나중에 넣기 어렵기 때문"입니다.

## 함께 기억할 맥락

- 같은 절의 다른 조언: 참조 아키텍처는 그림이 아니라 **검사 가능한 형태**(코드/데이터 + 규칙 검사)로 적어 CI에서 돌린다. 그림은 6개월이면 코드와 갈라진다 (예제 5, fitness function).
- 저장 구성은 "절충"이 답: 실행 상태 본문은 빠른 저장소(SQLite/Postgres)에 두고, 그래프에는 Run 노드와 `Reads`/`Writes` **링크만** 남긴다. 그래도 교차 질의는 되고 쓰기 부하는 막힌다 (예제 4).
- 이는 W3C PROV의 derivation(파생) 개념, 즉 데이터 계보(data lineage) 표준 관행과 같은 발상입니다.

## 한 줄 정리

아키텍처는 아픈 것부터 점진적으로 만들되, **기록 성격이라 소급이 불가능한 것 — 대표적으로 `Reads` 엣지 — 만은 처음부터 넣는다.**
