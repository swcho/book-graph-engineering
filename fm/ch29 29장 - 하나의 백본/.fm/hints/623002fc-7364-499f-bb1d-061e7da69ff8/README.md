# 역방향 영향 분석은 어떻게 하는가?

## 핵심 답

출처 노드를 **도착점**으로 두고, 그 노드에 도달하는 모든 노드를 가변 길이 경로로 찾는다.

```cypher
MATCH (a:Node)-[:Link*1..4]->(s:Node {id:'s2'})
RETURN DISTINCT a.kind, a.label ORDER BY a.kind
```

여기서 `s2`는 「물류 대시보드 2026-10-01」이라는 **Source(출처)** 노드다. 이 쿼리는 "s2에 1~4홉 안에 도달하는 모든 노드 `a`"를 찾는다. 즉, **이 출처가 틀렸다면 무엇이 흔들리는가**에 대한 답이다.

## 정방향과 역방향 — 같은 엣지, 반대 방향

29장 예제 3(`ex3_lineage.py`)의 계보(lineage) 그래프에서 두 방향의 질문은 **같은 `Link` 엣지**를 반대로 따라간 것이다.

| 방향 | 쿼리 | 질문 |
|---|---|---|
| 정방향 (계보 추적) | `MATCH (a:Node {id:'ans1'})-[:Link*1..4]->(x:Node)` | 왜 이 답이 나왔나? (답 → 실행 → 사실 → 출처) |
| 역방향 (영향 분석) | `MATCH (a:Node)-[:Link*1..4]->(s:Node {id:'s2'})` | 이게 틀리면 뭐가 무너지나? (출처 ← 사실 ← 실행 ← 답) |

정방향은 시작 노드(`ans1`, 답)를 **출발점**으로 고정하고 화살표를 따라 내려가며 근거 전체를 뽑는다. 역방향은 출처 노드(`s2`)를 **도착점**으로 고정한다. 쿼리에서 화살표 방향(`->`)은 그대로 두고, 변수를 어느 쪽에 묶느냐만 바꾸면 된다.

## 예제 그래프에서의 실제 결과

계보 그래프의 경로는 다음과 같다.

```
ans1(답) --생성됨--> run1(실행) --포함--> step2 --읽음--> f2(사실) --출처--> s2(물류 대시보드)
                                                    f3 --기댐--> f2
```

따라서 `s2`가 틀렸다면 영향받는 노드는:

- `[Fact]` 3분기 평균 배송일 4.2일 — s2에서 직접 나온 사실 (`f2`)
- `[Fact]` 배송 지연과 환불의 상관 0.71 — f2에 「기댐」 엣지로 의존 (`f3`)
- `[Step]` 2. 배송 지표 조회 — f2를 읽은 단계
- `[Run]` 분석 워크플로 #4821 — 그 단계를 포함한 실행
- `[Answer]` 「3분기 환불률이 늘어난 이유는 배송 지연」 — 최종 답

출처 하나의 오류가 최종 답까지 전파되는 경로가 **쿼리 한 줄**로 드러난다.

## 쿼리 문법 풀이

- `[:Link*1..4]` — `Link` 타입 엣지를 최소 1홉, 최대 4홉 따라가는 **가변 길이 경로**(variable-length path). 답→실행→스텝→사실→출처의 깊이가 최대 4단계이므로 상한을 4로 잡았다.
- `(a:Node)` — 출발점을 특정하지 않고 변수로 열어 둔다. 조건은 도착점 `(s:Node {id:'s2'})`에만 건다.
- `DISTINCT` — 한 노드가 여러 경로로 s2에 도달할 수 있으므로(예: f3은 f1·f2 양쪽에 기댐) 중복을 제거한다.

## 왜 「한 백본」이어야 가능한가

이 분석이 되려면 지식(Fact/Source)과 실행(Run/Step)이 **한 그래프**에 있어야 한다. 따로 두면 실행 로그는 로그대로, 지식 그래프는 그래프대로 있어서 사람이 두 시스템을 오가며 손으로 이어야 한다. 합쳐 두면:

1. **정방향**(왜 이 답이 나왔나)과 **역방향**(이게 틀리면 뭐가 무너지나)이 운영에서 가장 자주 나오는 두 질문인데, 둘 다 같은 쿼리 언어로 답해진다.
2. 28장처럼 에이전트가 그래프에 쓰기 시작하면 「어디서 온 사실인가」가 품질 관리의 핵심이 되고, 이 경로가 없으면 오염된 출처의 파급 범위를 알 수 없다.

## 주의: 이 경로는 저절로 생기지 않는다

역방향 분석이 가능하려면 실행할 때마다 `Reads`·`Writes`·`기댐`(의존) 엣지를 **꼬박꼬박 만들어야** 한다. 실행마다 엣지가 서너 개씩 늘어나는 것이 그 값이다. 이것이 W3C PROV-O 표준의 파생(derivation) 추적 개념과 같은 발상이며, 책에서 「나중에 넣기 어려운 것은 미리 넣으라」고 강조하는 이유이기도 하다 — `Reads` 엣지는 사후에 복원할 수 없다.
