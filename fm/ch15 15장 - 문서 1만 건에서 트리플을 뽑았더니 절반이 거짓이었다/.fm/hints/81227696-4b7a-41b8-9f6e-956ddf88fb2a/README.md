# 목적어 포함 검사의 한계

## 카드

- **질문**: 목적어 포함 검사의 한계는 무엇인가?
- **답**: 목적어가 문장에 있기만 하면 통과하므로 관계가 뒤집힌 경우(A가 B를 인수 → B가 A를 인수)는 잡지 못한다. 그건 모델을 한 번 더 불러야 한다.

## 배경: 목적어 포함 검사란

15장(15.2절 "근거를 같이 내놓게 하라")의 근거 검사 파이프라인은 세 단계의 문자열 검사로 지어내기(hallucination)를 거른다.

| 검사 | 잡는 실패 유형 |
|---|---|
| 근거 문장 존재 | 모델이 근거 문장 자체를 지어낸 경우 |
| **목적어 포함** | 문장은 진짜인데 값(목적어)을 지어낸 경우 («업종: IT 서비스») |
| 단정 여부 | 원문이 «알려져 있으나»라고 했는데 사실로 바꾼 경우 |

이 중 목적어 포함 검사가 지어내기를 **제일 많이 잡는다**. 주어는 문서 전체에 흔하게 등장하므로 주어를 보는 건 의미가 없고, 목적어(값)가 근거 문장 안에 실제로 들어 있는지를 봐야 한다. 목적어가 근거 문장에 없으면 그 값은 그 문장에서 나온 게 아니기 때문이다.

책의 예제 코드(`ex2_grounding.py`)에서는 이렇게 구현된다.

```python
def supports(quote, subj, obj):
    """근거 문장이 그 트리플을 실제로 뒷받침하는가.
    핵심은 «목적어»다."""
    q = normalize(quote)
    def core(x):
        x = normalize(x)
        return re.sub(r"[0-9\-]", "", x)[:2] or x[:2]
    return core(obj) in q
```

이 검사가 싼 이유는 **모델을 한 번 더 부르지 않아서**다. 문자열 대조라 밀리초 단위로 끝나고, 결과가 매번 같다(결정적, deterministic).

## 한계: "있기만 하면" 통과한다

목적어 포함 검사는 결국 **부분 문자열 매칭**이다. 목적어가 근거 문장 안에 문자열로 존재하는지만 본다. 따라서 다음을 구분하지 못한다.

- 원문: «A가 B를 인수했다»
- 잘못 추출된 트리플: `(B, 인수, A)` — **관계 방향이 뒤집힘**

이 경우 근거 문장에는 A도 B도 모두 들어 있으므로, 목적어 포함 검사는 통과한다. 문장이 진짜이고 목적어도 문장 안에 있지만, **주어와 목적어의 역할(방향)이 바뀐 것**은 문자열 비교로는 알 수 없다. 문자열 검사는 "그 단어가 거기 있는가"만 답할 수 있고, "그 단어가 그 역할로 쓰였는가"는 답하지 못하기 때문이다.

같은 이유로 다음도 못 잡는다.

- 부정 표현: «A는 B를 인수하지 **않았다**» → 문장 안에 A, B, "인수"가 다 있으므로 통과할 수 있다.
- 술어 왜곡: 원문은 "협업"인데 트리플은 "인수"로 뽑은 경우 — 목적어만 검사하면 술어의 정확성은 보장되지 않는다.

## 해결책: 모델을 한 번 더 부른다

방향 뒤집힘을 잡으려면 문장의 **의미 구조**를 이해해야 하고, 그건 문자열 비교의 영역이 아니다. 책의 답은 간명하다.

> 그건 모델을 한 번 더 불러야 한다. 값이 두 배가 되고 정밀도가 오른다.

즉, 추출된 트리플과 근거 문장을 모델(또는 검증 전용 모델)에 다시 넣어 "이 문장이 이 트리플을 정말 뒷받침하는가"를 판정하게 하는 것이다. 비용(호출 수)이 두 배가 되는 대신 정밀도가 오른다. 이 트레이드오프가 이 카드의 핵심이다.

- **문자열 검사**: 싸고(밀리초), 결정적이고, 값 지어내기는 잘 잡지만 방향·부정·의미는 못 본다.
- **모델 재호출 검증**: 비싸고 비결정적이지만 의미 수준의 오류(방향 뒤집힘 등)를 잡는다.

그래서 실무에서는 **싼 검사를 먼저 돌려 대량으로 거르고, 통과한 것(또는 애매한 것)만 비싼 검증에 넘기는** 계단식(cascade) 구성이 일반적이다. 같은 장의 확신도 절에서 "여러 번 돌려 표 세기는 비싸니까 애매한 것에만 쓰라"고 하는 것과 같은 원리다.

## 참고: NLI/entailment 기반 검증

모델을 "한 번 더 부르는" 구체적 기법으로 **NLI(Natural Language Inference, 자연어 추론) 검증**이 널리 쓰인다.

- 근거 문장을 전제(premise), 트리플을 문장으로 편 것(예: "B가 A를 인수했다")을 가설(hypothesis)로 놓고, NLI 모델이 **함의(entailment) / 모순(contradiction) / 중립(neutral)** 을 판정한다.
- 방향이 뒤집힌 트리플은 전제가 가설을 함의하지 않으므로(중립 또는 모순) 여기서 걸린다. 부정 표현이 뒤집힌 경우는 모순으로 잡힌다.
- LLM 전체를 부르는 대신 DeBERTa 계열 등 작은 cross-encoder NLI 모델을 쓰면 비용을 크게 줄일 수 있다. 요약 사실성 검증에서 같은 아이디어를 쓰는 FactCC, SummaC, AlignScore 같은 계보가 있고, RAG 평가에서 "근거 문서가 답을 뒷받침하는가(groundedness)"를 재는 방식도 동일한 구조다.
- 이 장의 키워드 표에 있는 근거 기반 생성(grounded generation, RAG 논문)과 자기 일관성(self-consistency)도 같은 문제의식 — "모델의 출력을 출력 자체가 아니라 근거와의 관계로 검증한다" — 을 공유한다.

## 요약

1. 목적어 포함 검사는 "목적어가 근거 문장에 문자열로 존재하는가"만 본다 — 값 지어내기는 제일 많이 잡는 최고 가성비 검사다.
2. 그러나 목적어가 문장에 **있기만 하면 통과**하므로, 관계 방향이 뒤집힌 트리플(A가 B를 인수 ↔ B가 A를 인수)은 못 잡는다.
3. 방향·의미 오류는 모델을 한 번 더 불러(예: NLI/entailment 검증) 잡아야 하며, 비용이 두 배가 되는 대신 정밀도가 오른다. 싼 검사로 먼저 거르고 비싼 검증은 나중에 — 이것이 계단식 검증의 기본형이다.
