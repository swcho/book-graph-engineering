# 「여러 홉 잇기」에서 벡터가 우연히 맞은 것처럼 보인 이유

> **Q.** '여러 홉 잇기'에서 벡터가 우연히 맞은 것처럼 보인 이유는 무엇인가?
>
> **A.** 마포에 사는 사람이 한 명뿐이라 우연히 답이 맞았다. 열 명 중 우리 팀이 한 명이면 벡터는 고르지 못한다.

---

## 1. 어디서 나온 이야기인가

27장 27.2절 「벡터와 그래프는 다른 질문에 강하다」의 예제 `code/ex2_graph_vs_vector.py` 입니다.

같은 기억(메모 7줄)에 성격이 다른 질문 세 개를 던져서, 각각 어느 쪽이 이기는지 세어 보는 예제입니다.

| 질문 종류 | 질문 | 잘 하는 쪽 |
|---|---|---|
| 비슷한 것 찾기 | 「회식 장소 관련해서 뭐가 있었지」 | 벡터 (그래프는 따라갈 엣지가 아예 없음) |
| **여러 홉 잇기** | **「우리 팀에서 마포에 사는 사람」** | **그래프** |
| 전부 세기 | 「결제팀 사람이 몇 명이지」 | 그래프 (벡터에는 「전부」가 없음) |

이 카드는 가운데 줄, **여러 홉 잇기**에서 벌어진 착시를 다룹니다.

## 2. 무슨 일이 벌어졌나

예제의 「임베딩」은 손으로 적은 3차원 좌표입니다. 축은 `[사람관계, 장소, 취향]`.

```python
MEMO = [
    ("이서연 님이 결제팀에 새로 왔다",       [0.9, 0.1, 0.0]),
    ("이서연 님은 마포에 산다",             [0.6, 0.8, 0.0]),
    ("박민수 팀장은 매운 음식을 못 먹는다",   [0.5, 0.0, 0.9]),
    ("나는 채식을 한다",                   [0.2, 0.0, 0.9]),
    ("회식은 보통 강남에서 한다",           [0.1, 0.9, 0.3]),
    ("결제팀 팀장은 박민수다",              [0.9, 0.0, 0.1]),
    ("나는 강남에서 일한다",                [0.3, 0.9, 0.0]),
]

QUERIES = [
    ...
    ("여러 홉 잇기", "우리 팀에서 마포에 사는 사람", [0.7, 0.7, 0.0]),
    ...
]
```

질문 벡터 `[0.7, 0.7, 0.0]` — 「사람관계」와 「장소」를 반반 섞은 좌표입니다. 코사인 유사도로 상위 3개를 뽑으면 대략 이렇게 나옵니다.

| 순위 | 메모 | 코사인 |
|---|---|---|
| 1 | 이서연 님은 마포에 산다 | ≈ 0.99 |
| 2 | 나는 강남에서 일한다 | ≈ 0.89 |
| 3 | 이서연 님이 결제팀에 새로 왔다 | ≈ 0.78 |

1등이 「이서연 님은 마포에 산다」입니다. 정답이 이서연이니까, 겉보기에는 **벡터도 맞혔습니다.**

그래프 쪽은 사이퍼 한 줄로 구조를 그대로 밟습니다.

```cypher
MATCH (t:N {name:'결제팀'})<-[:R]-(p:N)-[e:R {kind:'삶'}]->(l:N {name:'마포'})
RETURN p.name
```

`결제팀 ← 속함 ← 사람 → 삶 → 마포`. 두 조건을 **동시에** 만족하는 노드만 남습니다. 결과는 `['이서연']`.

## 3. 벡터가 맞힌 게 아닌 이유

책의 결론 문장이 핵심입니다.

> 벡터가 준 건 「마포에 사는 사람」이지 「우리 팀에서」가 아니다.
> 2등이 「나는 강남에서 일한다」인 게 그 증거다. 조건 두 개 중 하나만 맞췄다.
> 여기서는 마포에 사는 사람이 한 명뿐이라 우연히 답이 맞았다.
> 마포 사는 사람이 열 명이고 그중 우리 팀이 한 명이면 벡터는 못 고른다.

정리하면 세 단계입니다.

**(1) 벡터는 조건을 「곱하지」 않고 「섞는다」.**
질문 벡터 `[0.7, 0.7, 0.0]`은 「팀」과 「마포」를 AND로 묶은 게 아니라, 두 방향의 평균 지점일 뿐입니다. 그 지점에 가까운 것은 *둘 다 조금씩 닮은 것*이거나 *한쪽을 아주 세게 닮은 것*입니다. 논리곱(AND)이 아니라 **가중 평균**입니다.

**(2) 2등이 증거다.**
「나는 강남에서 일한다」는 마포와 아무 상관이 없습니다. 그런데도 2등입니다. 장소 축(0.9)이 세서 질문 벡터와 방향이 비슷하기 때문입니다. 유사도 랭킹이 실제로 재고 있는 건 「두 조건을 만족하는가」가 아니라 「두 조건을 섞은 방향과 얼마나 나란한가」라는 뜻입니다.

**(3) 1등이 맞은 건 데이터가 작아서다.**
이 메모 7줄에서 마포가 나오는 문장은 「이서연 님은 마포에 산다」 딱 하나입니다. 후보가 하나뿐이면 어떤 랭킹을 써도 1등이 그것일 수밖에 없습니다. **후보 집합의 크기가 1이라 랭킹의 품질이 검증되지 않은 것**이지, 벡터가 두 조건을 이은 게 아닙니다.

### 반례를 상상해 보면 바로 무너진다

마포에 사는 사람이 열 명이고, 그중 우리 팀 사람은 한 명이라고 해 봅시다.

```
이서연 님은 마포에 산다   ← 우리 팀 (정답)
김OO 님은 마포에 산다     ← 다른 팀
정OO 님은 마포에 산다     ← 다른 팀
... (총 10줄)
```

열 줄의 임베딩은 서로 거의 같습니다. 문장 형태도 같고, 축 좌표도 같은 자리 근처입니다. 질문 벡터에서 보면 열 개가 사실상 동점입니다. **유사도만으로는 그중 누가 「우리 팀」인지 가려낼 정보가 없습니다.** 팀 소속은 그 문장 안에 없고 *다른 문장*에 적혀 있으니까요. 이걸 이으려면 두 줄을 동시에 봐야 하는데, 그게 바로 「홉」이고, 벡터에는 홉이 없습니다.

같은 이야기가 27.1절 예제(`ex1_memory_shapes.py`)에서는 평평한 텍스트로 반복됩니다.

> 「팀에 속한 사람」과 「마포에 산다」를 이으려면 두 줄을 동시에 봐야 하고,
> 일곱 줄일 때는 다섯을 다 줘도 되지만 7,000줄이면 못 준다.
> 그때 상위 다섯 줄에 그 둘이 같이 들어올 보장이 없다.

작을 때 통하는 것은 작아서 통하는 것이고, 규모가 커지면 그 이유가 사라집니다.

## 4. 이 카드가 말하려는 진짜 교훈

**작은 데이터에서 한 번 맞은 결과를 능력으로 착각하지 말 것.** 이 예제는 벡터를 깎아내리려고 만든 게 아니라, *벤치마크를 읽는 법*을 보여 주려고 만든 장치입니다. 정답이 하나뿐인 문제에서 정답을 맞힌 것은 근거가 되지 못합니다. 검증하려면 **틀릴 기회가 있는 조건**(후보 여러 개, 그중 하나만 정답)을 만들어야 합니다.

그리고 벡터와 그래프의 차이는 성능 차이가 아니라 **연산의 종류** 차이입니다.

| | 벡터 | 그래프 |
|---|---|---|
| 하는 일 | 「두 조건과 **비슷한** 것」 | 「두 조건을 **동시에 만족**하는 것」 |
| 근거 | 좌표 거리 (연속) | 엣지 연결 (이산) |
| 결과 | 항상 상위 k개를 돌려줌 | 조건에 맞는 것만, 없으면 0개 |
| 「전부」 | 못 함 (k를 얼마로 할지 모름) | 됨 (`count`) |
| 「없음」 | 못 함 (유사도 낮아도 뭔가는 나옴) | 됨 (빈 결과가 곧 「없음」) |

## 5. 그래서 하나만 고르라는 뜻인가

아닙니다. 예제의 마지막 결론이 명시적으로 그렇게 말합니다.

```
  비슷한 것        → 벡터
  이어진 것        → 그래프
  전부 / 세기 / 없음 확인 → 그래프
```

실무 패턴은 **하이브리드 2단계**입니다.

1. 질문에서 사람 이름·개념을 **벡터로** 찾아 시작 노드를 잡는다.
2. 거기서 **엣지를 따라** 넓힌다.

「비슷한 것 찾기」 질문에서는 반대로 그래프가 아예 답을 못 합니다. 「회식 장소 관련해서 뭐가 있었지」에는 따라갈 엣지가 없습니다. 유사도 문제지 경로 문제가 아니기 때문입니다. 두 도구는 서로의 사각지대를 메우는 관계입니다.

## 6. 한 줄 정리

> 벡터가 「우리 팀에서 마포에 사는 사람」을 맞힌 것처럼 보였지만, 실제로 답한 것은 「마포에 사는 사람」뿐이었다. 마포 거주자가 한 명이라 두 답이 같았을 뿐이고(2등이 「나는 강남에서 일한다」인 게 그 증거), 후보가 열 명으로 늘면 벡터는 그중 우리 팀 한 명을 고르지 못한다.
