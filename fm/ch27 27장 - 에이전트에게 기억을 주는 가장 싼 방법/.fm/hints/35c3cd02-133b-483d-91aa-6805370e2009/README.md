# 기억에 종류를 붙이는 판단은 어떻게 자동화하는가?

> **답**: 「~하지 마」·「~는 안 됩니다」·「절대」는 **제약**, 「좋아합니다」·「싫어합니다」·「선호」는 **선호**, 「팀장」·「소속」·「담당」은 **관계**, 나머지는 **일회성**으로 규칙화한다.

출처: `ch27` 예제 5 (`code/ex5_forgetting.py`) 마지막 설명 블록.

---

## 1. 왜 종류를 붙여야 하나

27.5절의 주장은 이것입니다. **무엇을 잊을지는 나이가 아니라 종류로 정한다.**

`ex5_forgetting.py`는 기억 400개를 만들어 세 가지 잊기 정책을 비교합니다. 실제로 돌려 본 결과입니다.

| 정책 | 남긴 수 | 남긴 비율 | 나중에 필요했던 것을 지킨 비율 |
|---|---:|---:|---:|
| 전부 남긴다 | 400 | 100% | 100% |
| 최근 30일만 | 67 | 17% | **19%** |
| 한 번이라도 쓴 것 | 192 | 48% | **45%** |
| 종류별로 다르게 | 250 | 62% | **97%** |

- **「최근 30일만」**은 83%를 버리면서 필요한 것의 81%를 같이 버립니다. 나이는 중요도와 별 관계가 없기 때문입니다.
- **「한 번이라도 쓴 것」**은 낫지만 여전히 55%를 잃습니다. 제일 아픈 실패는 *아직 한 번도 안 쓴 제약*을 버리는 것입니다. 「이 API는 부르면 안 된다」는 40번의 대화 동안 한 번도 안 쓰이다가 41번째에 결정적으로 필요합니다.
- **「종류별로 다르게」**는 *더 많이 남기면서* 보존율이 두 배가 넘습니다. 덜 버려서 이긴 게 아니라 **버릴 것을 골라서** 이겼습니다.

종류별 TTL은 예제에서 이렇게 잡혀 있습니다.

```python
keep_days = {"일회성": 7, "선호": 365, "관계": 365, "제약": 3650}
return [x for x in m if x["age"] <= keep_days[x["kind"]] or x["used"] >= 2]
```

| 종류 | 보존 기간 | 근거 |
|---|---|---|
| 일회성 | 7일 | 「어제 그 파일 경로」는 일주일이면 쓸모없다 |
| 선호 | 1년 | 사람은 잘 안 바뀐다 |
| 관계 | 1년 | 소속·직책은 바뀌지만 자주는 아니다 |
| 제약 | 3650일 (사실상 영구) | 지우면 사고가 난다 |

문제는 **이 표를 만들려면 넣을 때마다 종류를 판단해야 한다**는 점입니다. 그게 이 방식이 치르는 값입니다.

## 2. 그 판단을 규칙으로 자동화한다

책의 결론은 「다행히 그 판단은 규칙으로 상당 부분 된다」입니다. 한국어는 **의도가 어미와 어휘에 드러나기 때문에**, 표층 패턴만으로도 상당한 재현율이 나옵니다.

| 우선순위 | 종류 | 트리거 표현 | 언어적 성격 |
|---:|---|---|---|
| 1 | **제약** | 「~하지 마」, 「~는 안 됩니다」, 「절대」 | 금지 어미 + 부정 양태 + 강조 부사 |
| 2 | **관계** | 「팀장」, 「소속」, 「담당」 | 개체-개체를 잇는 역할·소속 명사 |
| 3 | **선호** | 「좋아합니다」, 「싫어합니다」, 「선호」 | 감정·기호 서술어 |
| 4 | **일회성** | (위 어디에도 안 걸리는 나머지) | 기본값(fallback) |

의사 코드로 쓰면 이 정도입니다.

```python
CONSTRAINT = ("하지 마", "하지 말", "안 됩니다", "안 돼", "절대", "금지")
PREFERENCE = ("좋아합니다", "좋아해", "싫어합니다", "싫어해", "선호")
RELATION   = ("팀장", "소속", "담당", "부서", "상사")

def classify(text: str) -> str:
    if any(t in text for t in CONSTRAINT):
        return "제약"          # 가장 먼저 검사한다 (3절 참고)
    if any(t in text for t in RELATION):
        return "관계"
    if any(t in text for t in PREFERENCE):
        return "선호"
    return "일회성"
```

**검사 순서가 정책 그 자체입니다.** 「매운 건 절대 못 먹어요」는 제약 트리거와 선호 트리거를 동시에 물기 때문에, 어느 쪽을 먼저 보느냐가 이 기억의 TTL을 7일에서 3650일 사이 어딘가로 결정합니다.

## 3. 규칙 기반의 한계

「상당 부분 된다」는 「다 된다」가 아닙니다. 표층 패턴 매칭이 무너지는 지점들입니다.

### (1) 키워드 없이 표현되는 제약 — 재현율 구멍

한국어에서 금지는 얼마든지 완곡하게 말할 수 있습니다.

- 「그건 좀 지양해 주세요」
- 「가급적 피해 주시는 게 좋겠습니다」
- 「굳이 건드릴 필요는 없어요」
- 「운영 DB는 읽기만 하시면 됩니다」 ← 쓰기 금지인데 부정어가 하나도 없다
- 「그 스크립트 돌리면 알림이 전사에 나가요」 ← 사실 진술의 형태를 한 제약

이 문장들은 전부 규칙에 안 걸려서 **일회성으로 떨어지고 7일 뒤 사라집니다.**

### (2) 부정어가 있어도 제약이 아닌 경우 — 정밀도 구멍

- 「지난주엔 절대 안 된다고 하셨는데 지금은 괜찮대요」 ← 해제된 제약
- 「팀장님이 절대 못 먹는 게 뭐였죠?」 ← 질문이지 사실이 아님
- 「고객이 절대 안 된다고 했다더라」 ← 전문(傳聞), 주체가 사용자가 아님

인용·과거·질문·조건절을 구분하지 못하는 게 문자열 매칭의 본질적 한계입니다.

### (3) 선호와 제약의 경계가 모호하다

「박민수 팀장은 매운 음식을 못 먹습니다」는 `ex1`에서 `Pref`(선호) 노드로 들어가 있습니다. 그런데 알레르기라면 이건 제약입니다. **같은 문장이 맥락에 따라 다른 종류가 됩니다.** 규칙은 맥락을 못 봅니다.

### (4) 주체가 누구인가

「이서연 님은 회식에 안 가십니다」는 제약이지만 *나*의 제약은 아닙니다. 종류만 붙이고 주체를 안 붙이면, 나중에 「내가 못 먹는 게 뭐지」에 남의 제약이 섞입니다.

### (5) 기본값이 「일회성」이라는 구조적 위험

규칙이 못 잡은 **모든 것**이 가장 짧은 TTL(7일)로 흘러갑니다. 즉 **규칙의 재현율 실패가 곧바로 삭제로 이어지는 구조**입니다. 이게 다음 절의 문제로 직결됩니다.

### (6) 시간 차원이 빠져 있다

종류는 「얼마나 오래 살아야 하나」만 말합니다. 「지금도 참인가」는 못 말합니다. 27.3절의 유효 시간(`vfrom`/`vto`)과 **함께** 써야 합니다. 「박민수가 팀장이다」는 관계(1년 보존)이면서 동시에 2026-03-31에 끝난 사실입니다.

## 4. 오분류 비용의 비대칭 — 이 카드의 핵심

규칙의 오류율이 문제가 아닙니다. **어느 방향으로 틀리느냐**가 문제입니다.

`ex5`의 데이터에서 종류별로 「나중에 실제로 필요해질 확률」은 이렇게 잡혀 있습니다.

```python
need_p = {"일회성": 0.03, "선호": 0.55, "관계": 0.62, "제약": 0.88}
```

**제약은 필요해질 확률이 0.88, 일회성은 0.03입니다. 약 30배 차이입니다.**

같은 400개 데이터에 한쪽 방향 오분류만 주입해 돌려 본 결과입니다.

| 시나리오 | 남긴 수 | 필요한 것 보존율 | 변화 |
|---|---:|---:|---|
| 정상 분류 | 250 | **97%** | (기준) |
| **제약 32개를 전부 일회성으로 오분류** | 224 | **76%** | **-21%p, 필요한 기억 23개 유실** |
| 일회성 226개를 전부 제약으로 오분류 | 400 | **100%** | 손실 0, 저장량만 +60% |
| 선호 71개를 전부 일회성으로 오분류 | 196 | 73% | -24%p |

읽는 법:

- **제약은 전체의 8%(32/400)에 불과한데**, 그것만 잘못 붙여도 보존율이 97%에서 76%로 무너집니다. 소수의 항목이 손실의 대부분을 차지합니다.
- **반대 방향은 손해가 없습니다.** 일회성을 제약으로 잘못 붙이면 정보 손실은 0이고, 늘어나는 건 저장량뿐입니다.
- 게다가 27.4절(`ex4`)이 보여 준 대로, **그래프에서 저장량은 컨텍스트 비용이 아닙니다.** 사실이 50개든 5,000개든 질의에 걸려 프롬프트에 들어가는 건 열 개 안팎이고, 조회 시간도 2~7ms에서 변하지 않습니다. 즉 **과보존의 한계 비용은 거의 0에 수렴합니다.**

한 줄로: **잊어서 생기는 손해는 사고이고, 안 잊어서 생기는 손해는 디스크입니다.**

「이 프로덕션 스크립트는 절대 실행하지 마」를 일회성으로 붙였다가 8일 뒤에 잊으면, 에이전트는 그 스크립트를 실행합니다. 26장에서 다룬 권한 얘기가 여기서 다시 걸립니다 — 기억의 만료가 사실상 **가드레일의 만료**로 작동합니다.

## 5. 그래서 규칙을 어떻게 설계하나

비용이 비대칭이면 분류기도 비대칭이어야 합니다.

1. **제약 규칙을 먼저, 가장 넓게 검사한다.** 정밀도를 희생하고 재현율을 삽니다. 위양성(일회성을 제약으로 봄)은 디스크 몇 바이트지만 위음성(제약을 일회성으로 봄)은 사고입니다.
2. **애매하면 위로 올린다.** 여러 규칙에 동시에 걸리면 TTL이 긴 쪽을 택합니다. `제약 > 관계 ≈ 선호 > 일회성` 순서가 곧 안전 순서입니다.
3. **「나머지 = 일회성」이라는 기본값을 재검토한다.** 규칙에 안 걸린 문장 중 명령형·부정형·양태 표현이 하나라도 있으면 일회성 대신 「미분류(보류)」로 두고 TTL을 30~90일쯤 주는 편이 안전합니다.
4. **사용 이력을 안전망으로 둔다.** 예제의 `or x["used"] >= 2`가 그것입니다. 종류를 잘못 붙였어도 실제로 두 번 이상 참조됐다면 살립니다. 다만 이 안전망은 「아직 한 번도 안 쓴 제약」을 못 구합니다 — 규칙 자체가 그걸 잡아야 하는 이유입니다.
5. **삭제 대신 만료를 적는다.** 27.3절의 교훈입니다. 잊기는 물리 삭제가 아니라 `vto`를 채우거나 검색 순위를 낮추는 것이어야 합니다. 그래야 오분류를 되돌릴 수 있고, 「2025년 3월에 팀장이 누구였지」 같은 정당한 과거 질문도 살아남습니다.
6. **2단계 분류 — 규칙 먼저, LLM은 애매한 것만.** 규칙이 확정적으로 잡는 다수는 규칙으로 공짜로 처리하고, 어디에도 안 걸리거나 여러 개에 걸린 소수만 LLM에게 넘깁니다. 이때 프롬프트도 「애매하면 제약 쪽으로」라고 편향시킵니다. 규칙의 값은 정확도가 아니라 **LLM 호출을 줄이는 것**에 있습니다.
7. **승격 경로를 만든다.** 잊혔던 기억이 다시 언급되거나, 만료된 기억을 사용자가 다시 상기시키면(「지난번에 말씀드렸는데요」) 종류를 한 단계 올립니다. 27장 첫 문장의 그 불평이 사실은 **분류 오류 신호**입니다.
