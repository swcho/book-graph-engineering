# 키-값 기억이 근본적으로 한계인 이유

**질문** — 키-값 기억이 근본적으로 한계인 이유는 무엇인가?

**답** — 미리 정한 칸만 답할 수 있고, 그런 칸을 미리 다 만들어 둘 수 없다. 질문은 무한하다.

---

## 한 줄로 줄이면

키-값은 **저장할 때 질문을 이미 알고 있어야 하는** 모양이다.
칸(key)을 만든다는 건 「이런 질문이 올 것이다」를 미리 선언하는 일이고,
선언하지 않은 질문은 데이터가 안에 있어도 꺼낼 방법이 없다.

## 27.1절의 맥락 — 기억의 세 가지 모양

이 장은 같은 대화 기억을 세 가지 모양으로 저장하고 같은 질문을 던진다
(`code/ex1_memory_shapes.py`).

| 모양 | 저장 방식 | 답할 수 있는 것 | 한계 |
|---|---|---|---|
| 평평한 텍스트 | 사실을 문장 그대로 이어 붙임 | 낱말이 걸리는 것 | 여러 줄을 **못 잇는다** |
| 키-값 | 미리 정한 칸에 값 | 칸이 있는 질문 | 칸에 **없는 질문은 못 한다** |
| 그래프 | 노드 + 엣지 | 이어진 것을 따라가는 질문 | 모호한 것을 못 담는다 |

저장된 사실은 셋 다 똑같다.

```
저는 서울 강남에서 일합니다
회사는 결제팀이고 팀장은 박민수입니다
박민수 팀장은 매운 음식을 못 먹습니다
지난주에 팀 회식을 마포에서 했습니다
저는 회식 때 채식만 합니다
이서연 님이 새로 팀에 왔습니다
이서연 님은 마포에 삽니다
```

## 갈림길이 되는 질문

세 가지 질문 중 세 번째가 결정적이다.

1. 「내가 어디서 일하지?」
2. 「회식 장소를 정할 때 피해야 할 것은?」
3. **「우리 팀에서 마포에 사는 사람은?」**

키-값 구현은 이렇게 생겼다.

```python
def keyed_search(q):
    """모양 2 — 키-값. 미리 정한 칸만 답할 수 있다."""
    # 미리 정해 둔 칸만 있다. 칸에 없는 질문은 답을 못 한다.
    kv = {"일하": ("근무지", "강남"), "식성": ("식성", "채식")}
    for key, (name, val) in kv.items():
        if key in q:
            return [f"{name}={val}"]
    return []
```

1번은 `근무지=강남`으로 답한다. 칸이 있으니까.
3번은 `✗ 칸 없음`이다. 「마포에 사는 팀원」이라는 칸을 안 만들어 뒀기 때문이다.

책의 문장 그대로:

> 키-값은 아예 답을 못 한다. 「마포에 사는 팀원」이라는 칸을 안 만들어 뒀으니까.
> 그리고 그런 칸을 미리 다 만들어 둘 수는 없다. **질문은 무한하다.**

## 「칸을 더 만들면 되지 않나」에 대한 반박

이게 이 카드의 핵심이다. 답은 **조합 폭발**이다.

- 사실이 7개뿐인데도 「팀 ∩ 마포」, 「팀 ∩ 채식」, 「매운맛 ∩ 회식 참석자」…
  조건을 두 개씩만 엮어도 칸이 수십 개가 된다.
- 조건 개수가 늘면 칸의 수는 지수적으로 늘어난다.
- 게다가 새 사실이 하나 들어올 때마다 **기존 칸들을 다시 계산**해야 한다.
  「이서연이 마포에 산다」가 들어오면 `마포_거주_팀원` 칸을 갱신해야 하는데,
  그런 칸이 애초에 있어야만 갱신도 한다.

즉 키-값의 한계는 「칸이 부족하다」가 아니라 **「칸이라는 개념 자체가 질문을
미리 아는 것을 전제한다」**는 구조적 문제다. 양을 늘려서 해결되지 않는다.

## 왜 그래프는 되는가

같은 질문을 그래프는 2홉 순회로 답한다.

```cypher
MATCH (t:N {name:'결제팀'})<-[:R]-(p:N)-[e:R]->(pl:N {name:'마포'})
WHERE e.kind='삶' RETURN p.name
```

저장된 것은 `이서연 -속함-> 결제팀`, `이서연 -삶-> 마포` 두 개의 엣지뿐이다.
「팀 → 팀원 → 사는 곳」이라는 **경로는 저장할 때 존재하지 않았다.
질문이 들어온 뒤에 만들어진다.**

이 장의 한 줄 결론이 여기서 나온다.

> 그래프를 기억으로 쓰는 이유는 한 문장이다. **저장할 때 질문을 몰라도 되기** 때문이다.

## 옆에 놓고 볼 것 — 평평한 텍스트의 한계는 다르다

혼동하기 쉬운데, 평평한 텍스트가 실패하는 이유는 키-값과 다르다.

- 평평한 텍스트는 3번 질문에 **원문 7줄 중 5줄**을 준다. 답이 그 안에 있긴 하다.
  「팀」과 「마포」가 둘 다 흔한 말이라 거의 다 걸린 것이다.
  문제는 **어느 줄과 어느 줄을 이을지**를 모델이 해야 한다는 것,
  그리고 7줄이면 다 줘도 되지만 **7,000줄이면 못 준다**는 것이다.
  상위 5줄 안에 필요한 두 줄이 같이 들어올 보장이 없다.
- 키-값은 「답을 못 고른다」가 아니라 **「애초에 답을 내놓을 통로가 없다」**이다.

정리하면:

- 평평한 텍스트 → **여러 줄을 못 잇는다** (recall은 되나 조합이 안 됨)
- 키-값 → **미리 정한 칸 밖은 못 답한다** (통로 자체가 없음)
- 그래프 → **저장할 때 몰랐던 경로를 따라간다**

## 실무에서의 함의

- 키-값(프로필 스키마, 고정 필드 메모리)은 **질의가 이미 알려진 도메인**에서는
  충분하고 가장 싸다. 「사용자 이름」, 「선호 언어」처럼 칸이 유한한 경우다.
- 대화 기억은 질의가 미리 정해지지 않는다. 그래서 이 장은
  **스키마를 위에서 설계하지 말고 아래서 자라게 하라**고 말한다.
  데이터가 먼저 쌓이고 스키마가 따라와야 한다.
- 다만 처음부터 그래프로 가라는 뜻은 아니다.
  사실 1,000개쯤부터 그래프가 값을 하고, 그 전에는 평평한 목록이 싸다
  (`code/ex4_memory_cost.py`). 옮기는 데는 이틀이면 된다.

## 외우는 방법

**「칸은 질문을 미리 아는 사람만 만들 수 있다.」**

키-값의 실패는 용량 문제가 아니라 시제(時制) 문제다.
칸은 *저장 시점*에 정해지고, 질문은 *조회 시점*에 온다.
그 사이의 간극을 메우는 것이 그래프의 순회다.
