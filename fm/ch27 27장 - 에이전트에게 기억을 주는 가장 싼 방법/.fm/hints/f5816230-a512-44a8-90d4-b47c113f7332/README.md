# 대화 기억의 스키마는 어떻게 만들어야 하는가?

## 한 줄 답

**위에서 설계하지 말고 아래서 자라게 한다.** 질의를 아는 도메인은 질의 우선(query-first)이 맞지만, 대화 기억은 **데이터가 먼저 쌓이고 스키마가 따라와야** 한다.

## 두 가지 방향

| | 위에서 설계 (top-down) | 아래서 자람 (bottom-up) |
|---|---|---|
| 출발점 | 답해야 할 질의 목록 | 실제로 쌓인 사실들 |
| 절차 | 역량 질문 → 어휘 → 노드/엣지 정의 → 적재 | 평평하게 적재 → 반복 패턴 관찰 → 관계 종류 승격 |
| 전제 | **질문을 미리 안다** | 질문을 미리 모른다 |
| 맞는 곳 | 상품 카탈로그, 조직도, 부품 BOM 같은 도메인 그래프 | 대화 기억 |

## 왜 도메인 그래프는 「질의 우선」이 맞나

12장에서 본 **역량 질문**(competency question)이 그 방법이다. 「이 온톨로지는 어떤 질문에 답할 수 있어야 하는가」를 다섯 개쯤 먼저 적고, 거기서 어휘를 뽑고, 그 어휘로 노드와 엣지를 정의한다.

이게 되는 이유는 단순하다. **그 도메인에서는 질의가 유한하고 미리 알려져 있기 때문**이다. 재고 시스템이 답해야 할 질문은 사업이 정해 준다. 질의를 알면 그 질의가 밟을 경로를 미리 깔아 둘 수 있고, 안 밟을 경로는 안 만들면 된다. 위에서 설계하는 편이 싸고 정확하다.

## 왜 대화 기억은 다른가

27장 `ex1_memory_shapes.py`가 그래프를 기억으로 쓰는 이유로 든 문장이 정확히 이 지점이다.

> 이게 그래프를 기억으로 쓰는 이유다. 저장할 때 «질문을 몰라도 된다».

대화 기억에서는 **저장 시점에 질문을 모르는 것이 정상 상태**다. 사용자가 두 달 동안 흘린 말이 나중에 어떤 질문으로 돌아올지는 알 수 없다.

```python
FACTS = [
    "저는 서울 강남에서 일합니다",
    "회사는 결제팀이고 팀장은 박민수입니다",
    "박민수 팀장은 매운 음식을 못 먹습니다",
    ...
]
```

이 문장들을 적을 때 「우리 팀에서 마포에 사는 사람은?」이라는 질문이 올 줄은 아무도 몰랐다. 그런데도 그래프는 답한다. 팀 → 팀원 → 사는 곳 경로를 **질문이 들어온 뒤에** 만들기 때문이다.

같은 이유로 **키-값 스키마는 여기서 무너진다.** 키-값은 미리 정한 칸에만 답할 수 있는, 전형적인 「위에서 설계한 스키마」다.

```python
def keyed_search(q):
    """모양 2 — 키-값. 미리 정한 칸만 답할 수 있다."""
    kv = {"일하": ("근무지", "강남"), "식성": ("식성", "채식")}
    ...
    return []   # 칸에 없는 질문은 답을 못 한다
```

「마포에 사는 팀원」이라는 칸을 안 만들어 뒀으니 답을 못 한다. 그리고 **그런 칸을 미리 다 만들어 둘 수는 없다. 질문은 무한하다.** 질의 목록을 못 적는데 질의 우선 설계를 하려 들면, 결국 상상으로 칸을 만들게 되고 그 칸들은 대부분 빈 채로 남는다.

## 그러면 실제로 어떻게 「자라게」 하나

27장이 권하는 순서는 이렇다.

1. **평평한 목록으로 시작한다.** 사실을 문장 그대로, 종류 라벨과 시각만 붙여서 쌓는다. `ex4_memory_cost.py`의 결론대로 사실이 적을 때는 전부 컨텍스트에 넣는 게 싸다(50개면 하루 911원). 그래프를 세울 이유가 없다.
2. **쌓인 데이터에서 반복되는 관계를 본다.** 「누가 어느 팀에 속함」, 「누가 무엇을 선호」, 「누가 어디 삶」 — 실제로 자주 등장하는 술어가 관찰된다.
3. **자주 나온 술어만 노드/엣지 종류로 승격한다.** `ex1`의 `속함 · 이끔 · 삶 · 일함 · 선호 · 못먹음`은 위에서 상상한 어휘가 아니라 저 일곱 문장에서 나온 어휘다.
4. **경계를 넘을 때 옮긴다.** 토큰 값만 보면 사실 20개부터 그래프가 싸지만, 세우고 유지하는 사람 시간을 넣으면 실제 기준은 **사실 1,000개** 언저리다. 옮기는 데는 이틀이면 되고, **그 이틀을 처음에 쓰면 대개 낭비가 된다.**

`ex5_forgetting.py`의 종류 체계(`일회성 · 선호 · 관계 · 제약`)도 같은 성격이다. 이론에서 나온 분류가 아니라 「낡는 속도가 다르더라」는 관찰에서 나온 네 칸이고, 규칙 몇 개로 자동 부착된다.

```
«~하지 마», «~는 안 됩니다», «절대» → 제약
«좋아합니다», «싫어합니다», «선호»  → 선호
«팀장», «소속», «담당»              → 관계
나머지                              → 일회성
```

## 「아래서 자란다」가 「스키마가 없다」는 뜻은 아니다

방치하면 같은 사람이 노드 네 개로 앉고(14장 개체 해상도), 같은 관계가 `속함 / 소속 / 멤버`로 갈라진다. 자라게 하되 다음은 처음부터 깔아 둔다.

- **유효 시간**: 관계마다 `vfrom · vto`를 둔다(`ex3_temporal_memory.py`). 스키마가 나중에 바뀌어도, 시각 칸이 없으면 과거를 되물을 수 없다.
- **단일 값 관계 목록**: 「팀장은 한 명」 같은 제약을 코드에 두고, 새 사실을 넣을 때 옛 사실의 `vto`를 닫는다.
- **정규화 주기**: 승격된 어휘를 가끔 합쳐 준다. 스키마를 바꾸는 날의 절차는 32장이다.
- **사용자가 말한 것 vs 내가 추론한 것**: 전자는 그래프로, 후자는 원문으로 둔다. 모호한 것을 그래프에 올리면 자라는 스키마가 오염된다.

## 기억할 것

- 질의를 아는 도메인 → **질의 우선(역량 질문)**. 대화 기억 → **데이터 우선**.
- 대화 기억의 본질은 「저장할 때 질문을 모른다」이고, 그래서 미리 칸을 파는 설계(키-값, 고정 스키마)가 실패한다.
- 평평한 목록 → 패턴 관찰 → 어휘 승격 → 사실 1,000개쯤에서 그래프로 이전. 이전 비용은 이틀.
- 자라게 하되 유효 시간·단일 값 제약·개체 해상도는 처음부터 둔다.
