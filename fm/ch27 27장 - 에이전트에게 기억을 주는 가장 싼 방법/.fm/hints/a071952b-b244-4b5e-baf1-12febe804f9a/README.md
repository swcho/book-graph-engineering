# 오래된 기억은 어떻게 처리해야 하는가?

> **답**: 지우는 게 아니라 **끝나는 시각을 적는다**. 새 사실을 넣을 때 옛 사실을 닫으며, **단일 값 관계 목록**을 코드에 두면 된다.

출처: 27장 「에이전트에게 기억을 주는 가장 싼 방법」 27.3절 *기억에는 시각이 붙어야 한다* / 예제 `code/ex3_temporal_memory.py`

---

## 1. 문제: 시간 칸이 없으면 모순이 같이 산다

에이전트 기억에 사실을 넣을 때 시간을 안 붙이면, 그래프는 이렇게 된다.

```
박민수 -이끔-> 결제팀
이서연 -이끔-> 결제팀
나     -선호-> 채식
나     -선호-> 육식
```

팀장이 둘이고, 채식과 육식을 동시에 선호한다. 사실이 틀린 게 아니다. **각각은 어느 시점엔 참이었다.** 다만 「언제」가 빠져 있어서 서로 모순되는 것들이 한 자리에 같이 앉아 있는 것이다.

이게 왜 위험한가. 사용자가 「팀장님께 보고서 보내 줘」라고 하면 **지금** 팀장에게 보내야 한다. 그런데 2024년 대화 요약이 기억에 들어가 있으면 박민수가 여전히 팀장으로 남아 있다. 요약은 시간 칸을 갖고 다니지 않기 때문이다(24장).

그리고 결정적인 실패 모드가 하나 더 있다.

> 모순된 기억을 받은 모델은 **「최근 것」이 아니라 「자주 나온 것」**을 고른다.
> 박민수가 2년간 팀장이었고 이서연이 두 달이면, 박민수가 이긴다.

기억이 쌓일수록 오래된 사실이 **더 유리해진다.** 이건 시간이 지나도 저절로 낫지 않고, 오히려 악화된다.

## 2. 왜 「지우기」가 답이 아닌가

가장 쉬운 해법은 옛 사실을 지우는 것이다. 그런데 지우면 **과거를 물을 수 없게 된다.**

「2025년 3월에 팀장이 누구였지?」는 정당한 질문이다. 감사(audit), 회고, 「그때 왜 그렇게 결정했지」 같은 질문은 전부 과거 시점의 사실을 필요로 한다. 지우는 순간 그 질문의 답이 영원히 사라진다.

또 하나. 지우기는 **되돌릴 수 없다.** 새로 들어온 사실이 오탐이었다면(사용자가 농담으로 한 말, 잘못 추출된 관계), 지운 옛 사실은 복구할 방법이 없다.

## 3. 답: 끝나는 시각을 적는다 (유효 시간, valid time)

관계마다 **언제부터 언제까지 참이었나**를 칸으로 갖는다. 15장의 이시간(bitemporal) 모델을 기억에 그대로 적용하는 것이다.

| 칸 | 뜻 |
|---|---|
| `vfrom` (유효 시작) | 세상에서 이 사실이 참이 되기 시작한 시각 |
| `vto` (유효 끝) | 참이기를 그만둔 시각. 아직 참이면 열려 있음(`None` / `9999-12-31`) |
| `recorded` (기록 시각) | 내가 이걸 **알게 된** 시각 |

`vfrom`/`vto`가 유효 시간(valid time), `recorded`가 기록 시간(transaction time)이다. 둘을 같이 가지면 「2025년 3월에 팀장이 누구였나」와 「2025년 3월에 **내가 팀장이라고 알고 있던** 사람은 누구였나」를 구별해서 물을 수 있다. 뒤늦게 알게 된 사실(2026-04-01에 바뀐 걸 2026-04-02에 기록)이 있기 때문에 두 축은 실제로 어긋난다.

예제(`ex3_temporal_memory.py`)의 사실 표는 이렇게 생겼다.

```python
# (주어, 관계, 목적어, 유효 시작, 유효 끝(None=지금도), 기록 시각)
FACTS = [
    ("박민수", "이끔",  "결제팀", "2024-01-01", "2026-03-31", "2024-01-05"),
    ("이서연", "이끔",  "결제팀", "2026-04-01", None,         "2026-04-02"),
    ("나",     "속함",  "결제팀", "2023-06-01", None,         "2023-06-01"),
    ("나",     "선호",  "채식",   "2025-09-01", None,         "2025-09-10"),
    ("나",     "선호",  "육식",   "2023-01-01", "2025-08-31", "2023-01-15"),
]
```

박민수 행은 **지워지지 않았다.** `vto`가 채워졌을 뿐이다.

## 4. 조회: 「그 시점에 참이었던 것」만 고른다

질의는 한 줄이면 된다. 시점 `$t`를 구간이 감싸는 엣지만 통과시킨다.

```cypher
MATCH (a:N)-[e:R]->(b:N)
WHERE e.vfrom <= $t AND e.vto >= $t
RETURN a.name, e.kind, b.name
```

같은 그래프인데 시점에 따라 답이 달라진다. **그게 맞는 것이다.**

| 물은 시점 | 답 |
|---|---|
| 2025-01-15 | 박민수 -이끔-> 결제팀 / 나 -선호-> 육식 / 나 -속함-> 결제팀 |
| 2026-05-20 | 이서연 -이끔-> 결제팀 / 나 -선호-> 채식 / 나 -속함-> 결제팀 |

구현 요령 두 가지.

- **열린 구간은 `None` 대신 `9999-12-31` 같은 센티널로 저장한다.** 예제가 `vt or "9999-12-31"`로 넣는 이유다. NULL을 그대로 두면 `e.vto >= $t` 비교가 NULL을 뱉어 현재 사실이 통째로 탈락한다.
- **날짜를 `YYYY-MM-DD` 문자열로 두면 문자열 비교가 곧 시간 비교가 된다.** 예제는 그래서 STRING을 쓴다. 실제 시스템에서는 DATE/TIMESTAMP 타입과 색인을 쓰는 게 낫다.
- 시점을 안 주면 기본값을 **`now()`**로 둔다. 「지금 팀장」이 압도적으로 흔한 질문이라서다.

## 5. 쓰기: 새 사실을 넣을 때 옛 사실을 닫는다

시간 칸을 만들어 놓는 것만으로는 부족하다. **닫는 사람이 없으면 아무도 안 닫힌다.** 그래서 쓰기 경로에 규칙이 하나 필요하다.

> 새 사실이 들어오면, 같은 (주어, 관계)의 **열려 있는** 옛 사실의 `vto`를 새 사실의 `vfrom` 직전으로 채운다.

이걸 자동으로 하려면 「이 관계는 동시에 하나만 참일 수 있다」를 알아야 한다. 그 목록을 **코드에 둔다.**

```python
# 동시에 값 하나만 참일 수 있는 관계 (단일 값 관계)
SINGLE_VALUED = {"이끔", "근무지", "선호_주식", "직급", "거주지"}
# 여러 개가 동시에 참일 수 있는 관계는 여기 넣지 않는다: "속함", "담당", "안다"

def upsert(conn, s, kind, o, vfrom, recorded):
    if kind in SINGLE_VALUED:
        conn.execute(
            "MATCH (a:N {name:$s})-[e:R {kind:$k}]->(:N) "
            "WHERE e.vto = '9999-12-31' AND e.vfrom < $vf "
            "SET e.vto = $prev",
            {"s": s, "k": kind, "vf": vfrom, "prev": day_before(vfrom)})
    conn.execute(
        "MATCH (a:N {name:$s}),(b:N {name:$o}) "
        "CREATE (a)-[:R {kind:$k, vfrom:$vf, vto:'9999-12-31', recorded:$r}]->(b)",
        {"s": s, "o": o, "k": kind, "vf": vfrom, "r": recorded})
```

**왜 목록을 코드에 두는가.** 「팀장은 한 명」은 데이터에서 배울 수 없는 지식이다. 데이터만 보면 팀장이 둘인 상태와 「팀장이 바뀌는 중」인 상태를 구별할 방법이 없다. 반면 이 목록은 짧고(대개 열 개 안팎), 스키마 마이그레이션 없이 고칠 수 있고, 리뷰에서 눈으로 확인된다. **비용 대비 효과가 압도적으로 큰 한 줄짜리 도메인 지식**이다.

목록 관리에서 흔한 실수:
- **`속함`을 단일 값에 넣는 것.** 사람은 팀 두 개에 동시에 속할 수 있다. 넣는 순간 멀쩡한 사실이 조용히 닫힌다.
- **`선호`를 통째로 단일 값에 넣는 것.** 「채식↔육식」은 배타지만 「매운 음식 싫어함」과 「채식」은 공존한다. 배타 축(식성, 언어, 근무지)을 관계 이름으로 쪼개야 한다.
- **닫을 때 `vfrom < 새 vfrom` 조건을 빼먹는 것.** 과거 사실을 뒤늦게 넣는 백필(backfill)에서 미래 사실을 잘못 닫는다.

## 6. 「닫기」와 「잊기」는 다른 일이다

같은 장 27.5절이 다루는 **잊기**와 헷갈리기 쉬운데, 둘은 층이 다르다.

| | 닫기 (27.3) | 잊기 (27.5) |
|---|---|---|
| 대상 | 더 이상 **참이 아닌** 사실 | 더 이상 **쓸모없는** 사실 |
| 하는 일 | `vto`를 채운다. 행은 남는다 | 실제로 지운다 |
| 기준 | 새 사실이 들어왔는가 | 나이가 아니라 **종류** (일회성 7일 / 선호·관계 1년 / 제약 사실상 영구) |
| 과거 조회 | 가능 | 불가능 |

즉 「박민수가 팀장이었다」는 **닫히지만 지워지지 않는다.** 지워지는 건 「어제 그 파일 경로」 같은 일회성 기억이고, 그것도 나이가 아니라 종류로 정한다. 나이로 자르면(최근 30일만) 83%를 버리면서 **정작 필요한 것의 81%도 같이 버린다.**

## 7. 한 줄 정리

- 오래된 기억은 **지우지 않는다**. `vto`를 적어 **닫는다**.
- 닫기는 쓰기 경로에서 자동으로 일어나야 하고, 그러려면 **단일 값 관계 목록**이 코드에 있어야 한다.
- 조회는 `vfrom <= t AND vto >= t` 한 줄. 시점을 안 주면 `now()`.
- 이걸 안 하면 기억이 쌓일수록 모순이 늘고, 모델은 최근 것이 아니라 **자주 나온 것**을 고른다.
