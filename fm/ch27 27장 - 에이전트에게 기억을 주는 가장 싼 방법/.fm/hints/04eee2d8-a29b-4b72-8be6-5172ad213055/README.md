# `ex4`의 조회 시간이 규칙 없이 오르내리는 이유

**질문** — `ex4`의 조회 시간이 규칙 없이 오르내리는 이유는 무엇인가?

**답** — 이 규모에서는 **측정 잡음이 지배**한다. 5,000개짜리가 50개짜리보다 빠르게 나오기도 하며, **그것이 요점**이다.

---

## 1. `ex4`가 무엇을 재는 예제인가

`ex4_memory_cost.py`는 "사실이 늘어날 때 두 방식의 하루 비용"을 나란히 찍는 예제다.

- **전부 컨텍스트에**: 사실 전부를 매 턴 프롬프트에 넣는다. 비용 = `사실 수 × 22토큰 × 200턴 × 단가`
- **그래프 조회**: 질문에 걸린 것만 넣는다. 대개 10개 안팎이라 사실 수가 늘어도 비용이 고정이다.

사실 수를 `50 → 200 → 1,000 → 5,000`으로 100배 키우면서 두 값을 찍고, 여기에 **그래프 조회 시간(ms)** 칸을 하나 더 붙인다. 바로 이 칸이 실행할 때마다 들쭉날쭉한 칸이다.

```
사실 수   전부 컨텍스트에   하루 비용   그래프 조회(ms)   조회한 사실   하루 비용
------------------------------------------------------------------------------
     50          220,000       911원            4.12            10       182원
    200          880,000     3,643원            2.87            10       182원
  1,000        4,400,000    18,216원            6.55            10       182원
  5,000       22,000,000    91,080원            3.41            10       182원
```

(숫자는 실행 예시다. **조회 시간 칸만** 매 실행마다 달라진다.)

## 2. 왜 규칙이 안 보이는가 — 측정 잡음

측정 대상 자체가 너무 빠르기 때문이다. 조회 코드는 이렇게 생겼다.

```python
def query_ms(c, reps=40):
    t0 = time.perf_counter()
    for _ in range(reps):
        r = c.execute("MATCH (a:N {name:'n5'})-[:R*1..2]->(b:N) RETURN b.name")
        while r.has_next():
            r.get_next()
    return (time.perf_counter() - t0) / reps * 1000
```

한 번 재는 데 걸리는 시간이 **2~7ms** 수준이다. 이 정도 시간대에서는 "실제 그래프 탐색 비용"보다 아래 것들이 더 크게 흔든다.

| 흔드는 요인 | 설명 |
|---|---|
| OS 스케줄러 | 다른 프로세스에 CPU를 뺏기는 순간이 밀리초 단위로 끼어든다 |
| CPU 캐시 / 메모리 지역성 | 직전 실행이 남긴 캐시 상태에 따라 배 가까이 차이가 난다 |
| 디스크·페이지 캐시 | DB 파일이 페이지 캐시에 올라와 있는지 여부 |
| CPU 주파수 변동 | 터보 부스트·발열 제어(thermal throttling) |
| GC·인터프리터 오버헤드 | Python 쪽 결과 순회 비용이 탐색 비용보다 클 수 있다 |
| 워밍업 | 처음 만든 DB와 나중 DB의 상태가 다르다 |

이 잡음의 크기(수 ms)가 **신호의 크기와 같거나 크다.** 그래서 40회 평균을 내도 순서가 뒤집힌다. 5,000개짜리가 50개짜리보다 빠르게 찍히는 일이 자연스럽게 생긴다.

## 3. 그런데 왜 "그게 요점"인가

여기서 저자가 강조하는 건 "측정이 부정확해서 미안하다"가 아니다. 정확히 반대다.

> 조회 시간 칸을 보시라. 사실이 100배 늘어도 2~7ms 사이에서 논다.
> 규칙 없이 오르내리는 건 이 규모에서는 «측정 잡음»이 지배해서다.
> 5,000개짜리가 50개짜리보다 빠르게 나오기도 한다. 그게 요점이다.
> 이 규모에서 조회 시간은 «사실 수와 무관»하다. 색인이 일하고 있다.

논리를 풀면 이렇다.

1. 만약 조회 비용이 사실 수에 비례했다면(`O(n)` 전체 스캔), 100배 늘렸을 때 조회 시간도 대략 100배로 커졌어야 한다. 그러면 잡음이 묻히고 **깨끗한 우상향 곡선**이 보였을 것이다.
2. 그런데 실제로는 신호가 잡음에 파묻혀 순서조차 뒤집힌다. 이는 **사실 수의 영향이 잡음보다 작다**는 뜻이다.
3. 즉, 무질서 그 자체가 "**색인이 일하고 있다**"는 증거다. 시작 노드 `n5`를 기본 키 색인으로 바로 찾고, 거기서 1~2홉만 따라간다. 그래프 전체 크기와 상관없이 **건드리는 데이터 양이 같다**.

정리하면 이 표에서 읽어야 할 것은 "몇 ms인가"가 아니라 "**사실 수와 무관하다**"는 사실 하나다. 무작위로 오르내리는 숫자는 그 무관함의 가장 솔직한 증거다.

## 4. 이 결론이 장 전체 주장으로 이어지는 방식

두 칸의 성질이 다르다는 게 27.4절의 전부다.

- **전부 컨텍스트에**: 사실 수에 **비례해서** 오른다. 50개 → 911원, 5,000개 → 91,080원(한 달 273만 원).
- **그래프 조회**: 사실 수와 **무관하게** 평평하다. 몇 개가 쌓이든 걸리는 건 10개쯤이므로 하루 182원 고정. 조회 시간도 평평하다.

그래서 결론이 나온다.

- 사실이 적을 때는 그냥 다 넣는 게 낫다. 50개면 하루 911원이니 그래프를 세울 이유가 없다.
- 토큰 값만 보면 사실 20개부터 그래프가 싸지만, **그래프를 세우고 유지하는 사람 시간**을 넣으면 실제 경계는 훨씬 뒤다. 저자는 **1,000개**를 기준으로 쓴다.
- 처음부터 그래프로 가지 마라. 평평한 목록으로 시작하고 하루 비용이 눈에 띄면 그때 옮긴다. 옮기는 데는 이틀이면 되고, 그 이틀을 처음에 쓰면 대개 낭비가 된다.

## 5. 헷갈리기 쉬운 지점

- **"조회가 느려서 문제인가?"** — 아니다. 2~7ms는 충분히 빠르고, 문제는 애초에 성능이 아니라 **토큰 비용**이다. 조회 시간 칸은 "그래프로 옮겨도 느려지지 않는다"를 확인하는 보조 지표일 뿐이다.
- **"측정을 더 정밀하게 하면 되지 않나?"** — 반복 횟수를 늘리고 워밍업을 넣으면 잡음을 줄일 수는 있다. 하지만 이 예제의 목적은 정밀한 벤치마크가 아니라 "이 규모에서는 잴 가치도 없을 만큼 차이가 없다"를 보이는 것이다.
- **"그럼 그래프는 영원히 안 느려지나?"** — 아니다. 이 예제는 `1..2`홉 제한이 걸린 좁은 질의다. 홉 수가 깊어지거나 팬아웃이 큰 그래프에서는 당연히 커진다. 주장의 범위는 "**이 규모, 이 질의 모양에서는**"이다.

---

### 한 줄 요약

`ex4`의 조회 시간이 규칙 없이 흔들리는 이유는 신호(사실 수의 영향)보다 잡음(스케줄러·캐시·주파수 등)이 크기 때문이고, 5,000개가 50개보다 빠르게 나오는 그 뒤집힘 자체가 "조회 비용은 사실 수와 무관하다 — 색인이 일하고 있다"는 증거다.
