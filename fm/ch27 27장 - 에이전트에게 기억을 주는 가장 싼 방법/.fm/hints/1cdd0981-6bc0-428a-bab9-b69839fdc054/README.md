# 그래프를 기억으로 쓰는 이유

**질문** — 그래프를 기억으로 쓰는 이유를 한 문장으로 말하면 무엇인가?

**답** — 저장할 때 질문을 몰라도 되기 때문이다.

---

## 한 줄의 뜻

기억을 저장하는 시점과 그 기억이 필요해지는 시점 사이에는 시차가 있습니다. 문제는 **저장하는 순간에는 나중에 어떤 질문이 들어올지 알 수 없다**는 것입니다.

- 평평한 텍스트도, 키-값도 결국 «저장할 때 질문을 얼마나 예상했느냐»에 성능이 묶여 있습니다.
- 그래프는 다릅니다. 저장할 때는 「A는 B에 속한다」, 「C는 D에 산다」 같은 **낱개 사실만** 넣습니다. 질문이 들어온 뒤에 그 사실들을 **이어서** 경로를 만듭니다. 즉 답으로 가는 경로는 저장 시점이 아니라 질의 시점에 생깁니다.

27장 본문의 표현 그대로:

> 이 경로는 저장할 때 몰랐던 것이다. 질문이 들어온 뒤에 만들어진다.
> 이게 그래프를 기억으로 쓰는 이유다. 저장할 때 «질문을 몰라도 된다».

## 세 가지 모양을 같은 사실로 시험한다 (ex1_memory_shapes.py)

같은 대화 기억 7줄을 세 모양으로 저장하고 세 질문을 던집니다.

저장한 사실(발췌):

```
저는 서울 강남에서 일합니다
회사는 결제팀이고 팀장은 박민수입니다
박민수 팀장은 매운 음식을 못 먹습니다
저는 회식 때 채식만 합니다
이서연 님이 새로 팀에 왔습니다
이서연 님은 마포에 삽니다
```

그래프로 옮기면 노드와 엣지는 이런 모양입니다.

```
        (나) --속함--> (결제팀) <--이끔-- (박민수) --못먹음--> (매운맛)
         |                  ^
        일함                속함
         v                  |
       (강남)            (이서연) --삶--> (마포)
         (나) --선호--> (채식)
```

### 갈림길이 되는 질문 — 「우리 팀에서 마포에 사는 사람은?」

| 모양 | 결과 | 왜 |
|---|---|---|
| 평평한 텍스트 | △ 원문 7줄 중 5줄을 던져 줌 | «팀»과 «마포»가 둘 다 흔한 말이라 거의 다 걸림. 답이 그 안에 있긴 하지만 어느 두 줄을 이을지는 모델의 몫 |
| 키-값 | ✗ 칸 없음 | «마포에 사는 팀원»이라는 칸을 미리 안 만들어 뒀음. 그리고 그런 칸을 전부 미리 만들 수는 없음(질문은 무한하다) |
| 그래프 | ○ 이서연 | 결제팀 → 팀원 → 사는 곳을 **따라가면** 됨 |

그래프의 질의는 이 한 줄입니다.

```cypher
MATCH (t:N {name:'결제팀'})<-[:R]-(p:N)-[e:R]->(pl:N {name:'마포'})
WHERE e.kind='삶' RETURN p.name
```

「결제팀 ← 속함 ← 사람 → 삶 → 마포」라는 이 2홉 경로는 **저장할 때 어디에도 적혀 있지 않았습니다.** 저장된 것은 「이서연은 결제팀에 속한다」와 「이서연은 마포에 산다」라는 서로 무관한 두 개의 엣지뿐이고, 둘을 잇는 일은 질문이 도착한 뒤에 일어납니다.

## 왜 다른 모양은 질문을 미리 알아야 하나

- **평평한 텍스트**: 여러 줄을 못 잇습니다. 7줄일 때는 5줄을 다 줘도 되지만 7,000줄이면 못 줍니다. 그때 상위 5줄 안에 필요한 두 줄이 **같이** 들어올 보장이 없습니다. 즉 검색 시점의 유사도가 「질문을 얼마나 잘 예상해 문장을 써 뒀나」에 좌우됩니다.
- **키-값**: 미리 만든 칸에만 답합니다. 칸을 만든다는 것은 곧 **질문을 미리 정하는 일**입니다. 질문이 무한하므로 칸을 다 만들 수 없습니다.
- **그래프**: 사실을 사실대로만 넣습니다. 질문은 나중에 경로로 표현됩니다.

## 벡터와 대조하면 더 선명해진다 (ex2)

「비슷한 것 찾기」는 벡터가 이깁니다. 「회식 장소 관련해서 뭐가 있었지」에는 따라갈 엣지가 없으니 유사도 문제지 경로 문제가 아닙니다. 반대로 그래프만 할 수 있는 것이 있습니다.

- **여러 홉 잇기**: 벡터는 «두 조건과 비슷한 것»을 주고, 그래프는 «두 조건을 동시에 만족하는 것»을 구조로 찾습니다. ex2에서 벡터가 우연히 「이서연 님은 마포에 산다」를 1등에 올렸지만, 2등이 「나는 강남에서 일한다」인 게 증거입니다. 조건 두 개 중 하나만 맞춘 것이고, 마포 사는 사람이 열 명이면 못 고릅니다.
- **전부 / 세기 / 없음**: 상위 k개를 주는 물건에는 «전부»가 없습니다. k를 얼마로 해야 다 나오는지 미리 알 방법이 없고, 「마포에 사는 팀원이 없다」는 확인도 못 합니다.

실무 결론은 «하나를 고르라»가 아니라 **벡터로 시작점을 찾고 그래프로 넓힌다**입니다.

## 이 문장의 한계 (같이 외워 둘 것)

이 한 문장은 그래프의 만능을 뜻하지 않습니다. 27장은 곧바로 단서를 답니다.

- **그래프는 모호한 것을 못 담습니다.** 사용자가 말한 것은 그래프로, 내가 추론한 것은 원문으로 두세요.
- **처음부터 그래프로 가지 마세요.** ex4 기준으로 사실 50개면 하루 911원이라 그래프를 세울 이유가 없고, 5,000개면 하루 91,080원(월 273만 원)이라 그때 값을 합니다. 토큰 값만 보면 20개부터 그래프가 싸지만 사람 시간을 넣으면 실질 경계는 **사실 1,000개쯤**입니다. 옮기는 데는 이틀이면 됩니다.
- **기억에는 유효 시각이 붙어야 합니다.** 지우지 말고 끝나는 시각(`vto`)을 적으세요(ex3).

## 외우는 요령

「저장할 때 **칸을 정한다** = 키-값 / 저장할 때 **문장을 남긴다** = 평평한 텍스트 / 저장할 때 **연결만 남긴다** = 그래프」로 나눠 두고, 마지막 것만이 질문을 몰라도 되는 방식이라고 기억하면 됩니다. 한 문장 답은 그대로: **저장할 때 질문을 몰라도 되기 때문이다.**
