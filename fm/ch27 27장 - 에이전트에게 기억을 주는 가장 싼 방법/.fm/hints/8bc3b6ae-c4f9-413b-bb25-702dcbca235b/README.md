# `ex1_memory_shapes.py`의 세 번째 질문이 갈림길인 이유

## 질문과 답

**Q.** `ex1_memory_shapes.py`에서 세 번째 질문이 갈림길인 이유는 무엇인가?

**A.** "우리 팀에서 마포에 사는 사람"은 두 조건을 이어야 하는데, 평평한 텍스트는 원문 여러 줄만 주고 키-값은 그 칸이 없어 답을 못 한다.

---

## 예제의 구조

`ex1_memory_shapes.py`는 **같은 기억을 세 가지 모양으로 저장**하고, **세 종류의 질문**을 똑같이 던집니다. 27.1절 "모양이 답할 수 있는 질문을 정한다"의 실험 장치입니다.

### 저장된 사실 7줄

```python
FACTS = [
    "저는 서울 강남에서 일합니다",
    "회사는 결제팀이고 팀장은 박민수입니다",
    "박민수 팀장은 매운 음식을 못 먹습니다",
    "지난주에 팀 회식을 마포에서 했습니다",
    "저는 회식 때 채식만 합니다",
    "이서연 님이 새로 팀에 왔습니다",
    "이서연 님은 마포에 삽니다",
]
```

### 세 가지 모양

| 모양 | 함수 | 저장 방식 |
|---|---|---|
| 평평한 텍스트 | `flat_search` | 원문 줄을 그냥 쌓아 두고 낱말로 검색 |
| 키-값 | `keyed_search` | 미리 정한 칸(`근무지`, `식성`)에만 값을 채움 |
| 그래프 | `graph_search` | 노드(사람·팀·장소·선호)와 엣지(속함·일함·삶·선호…)로 저장 |

### 세 가지 질문

```python
QUESTIONS = [
    ("내가 어디서 일하지?", ["강남"]),
    ("회식 장소를 정할 때 피해야 할 것은?", ["매운맛", "채식"]),
    ("우리 팀에서 마포에 사는 사람은?", ["이서연"]),
]
```

앞의 두 질문은 세 모양이 그럭저럭 다 넘어갑니다. **세 번째에서 갈립니다.**

---

## 왜 세 번째만 갈리는가 — 질문의 모양이 다르다

앞의 두 질문과 세 번째 질문의 결정적 차이는 **조건의 개수**입니다.

- 1번 "내가 어디서 일하지?" → 조건 **하나**. `나 —일함→ ?`. 원문 한 줄 안에 답이 통째로 들어 있습니다.
- 2번 "회식 장소를 정할 때 피해야 할 것은?" → 낱말 "회식"으로 걸리는 줄이 좁고, 키-값도 `식성` 칸으로 반쯤 답합니다.
- 3번 "우리 팀에서 마포에 사는 사람은?" → 조건이 **둘**입니다.
  1. **결제팀에 속한다**
  2. **마포에 산다**

그리고 이 두 조건은 **서로 다른 줄**에 흩어져 있습니다.

```
"이서연 님이 새로 팀에 왔습니다"   ← 조건 1 (소속)
"이서연 님은 마포에 삽니다"        ← 조건 2 (거주)
```

어느 한 줄도 혼자서는 답이 아닙니다. **두 줄을 «이서연»이라는 같은 사람으로 묶어야** 비로소 답이 나옵니다. 이게 갈림길의 정체입니다.

---

## 모양별로 무슨 일이 일어나는가

### 1. 평평한 텍스트 — △ 원문 5줄

`TERMS`에 등록된 찾을 말은 `["마포", "팀"]`입니다. 7줄 중 걸리는 줄을 세어 보면:

| 원문 | 걸림 | 이유 |
|---|---|---|
| 저는 서울 강남에서 일합니다 | ✗ | |
| 회사는 결제팀이고 팀장은 박민수입니다 | ✓ | "팀" |
| 박민수 팀장은 매운 음식을 못 먹습니다 | ✓ | "팀" |
| 지난주에 팀 회식을 마포에서 했습니다 | ✓ | "팀", "마포" |
| 저는 회식 때 채식만 합니다 | ✗ | |
| 이서연 님이 새로 팀에 왔습니다 | ✓ | "팀" |
| 이서연 님은 마포에 삽니다 | ✓ | "마포" |

**7줄 중 5줄**이 걸립니다. 「팀」과 「마포」가 둘 다 흔한 말이라서 거의 다 걸린 것입니다. 게다가 4번 줄("팀 회식을 마포에서 했습니다")은 **마포가 나오지만 거주와는 무관한 미끼**입니다.

핵심은 이겁니다. **답이 그 안에 있긴 한데, 어느 줄을 어떻게 이을지는 모델이 해야 합니다.** 기억의 모양이 답을 준 게 아니라, "재료가 여기 어딘가 있으니 알아서 하라"고 던진 것입니다.

7줄일 때는 5줄을 다 줘도 됩니다. 문제는 규모입니다.

> 일곱 줄일 때는 다섯을 다 줘도 되지만 **7,000줄이면 못 준다.**
> 그때 상위 다섯 줄에 그 둘이 같이 들어올 보장이 없다.

두 조건에 해당하는 줄이 **각각** 상위 k에 들어와야 하는데, 검색은 줄 하나하나의 점수로만 자르기 때문에 그 보장이 없습니다. 조건 하나만 강하게 맞는 미끼 줄(팀 회식 마포)이 오히려 위로 올라오기 쉽습니다.

### 2. 키-값 — ✗ 칸 없음

```python
def keyed_search(q):
    kv = {"일하": ("근무지", "강남"), "식성": ("식성", "채식")}
    for key, (name, val) in kv.items():
        if key in q:
            return [f"{name}={val}"]
    return []
```

"우리 팀에서 마포에 사는 사람은?"에는 `일하`도 `식성`도 들어 있지 않으니 **빈 리스트**가 돌아옵니다. 출력은 `✗ 칸 없음`.

여기서 진짜 문제는 "칸을 하나 더 만들면 되지 않나"가 아닙니다.

> 그런 칸을 미리 다 만들어 둘 수는 없다. **질문은 무한하다.**

「마포에 사는 팀원」칸을 만들면 다음엔 「강남에서 일하는 채식주의자」칸이 필요합니다. 조건을 조합하는 방식은 사실 개수에 대해 폭발적으로 늘어나므로, **저장 시점에 질문을 알아야만 답할 수 있는 구조**는 원리적으로 못 따라갑니다.

### 3. 그래프 — ○ 이서연

```python
elif "마포에 사는" in q:
    rows = conn.execute(
        "MATCH (t:N {name:'결제팀'})<-[:R]-(p:N)-[e:R]->(pl:N {name:'마포'}) "
        "WHERE e.kind='삶' RETURN p.name")
```

`결제팀 ← 속함 ─ p ─ 삶 → 마포` 라는 **경로 하나**로 두 조건을 동시에 겁니다. 미끼 줄(회식 장소로서의 마포)은 `kind='삶'`이 아니므로 애초에 경로에 들어오지 못합니다.

```
        속함              삶
결제팀 ←────── 이서연 ──────→ 마포
   ↑
   └── 나, 박민수 (마포 엣지 없음 → 탈락)
```

그리고 이 경로는 **저장할 때 만들어 둔 것이 아닙니다.**

> 이 경로는 저장할 때 몰랐던 것이다. **질문이 들어온 뒤에 만들어진다.**
> 이게 그래프를 기억으로 쓰는 이유다. 저장할 때 «질문을 몰라도 된다».

## 세 모양 요약

| 모양 | 3번 질문 결과 | 실패/성공의 원인 |
|---|---|---|
| 평평한 텍스트 | △ 원문 5줄 | 재료는 주지만 **잇는 일은 모델에 떠넘김**. 규모가 커지면 두 줄이 같이 안 뽑힘 |
| 키-값 | ✗ 칸 없음 | **저장 시점에 질문을 알아야** 함. 무한한 조합을 칸으로 못 만듦 |
| 그래프 | ○ 이서연 | 조건 둘을 **경로 하나**로 결합. 질문 시점에 경로를 만듦 |

한 장 요약의 문장이 정확히 이 표입니다.

> 평평한 텍스트는 여러 줄을 못 잇고, 키-값은 미리 만든 칸에만 답하고, 그래프는 저장할 때 몰랐던 경로를 따라갑니다.

## 함께 보면 좋은 것 — `ex2`의 벡터도 같은 함정에 빠진다

`ex2_graph_vs_vector.py`는 **같은 질문**("우리 팀에서 마포에 사는 사람")을 벡터 검색에 던집니다. 벡터는 1등으로 「이서연 님은 마포에 산다」를 올려서, 얼핏 맞춘 것처럼 보입니다. 하지만:

> 벡터가 준 건 «마포에 사는 사람»이지 «우리 팀에서»가 아니다.
> 2등이 «나는 강남에서 일한다»인 게 그 증거다. **조건 두 개 중 하나만 맞췄다.**
> 마포 사는 사람이 열 명이고 그중 우리 팀이 한 명이면 벡터는 못 고른다.

즉 평평한 텍스트를 임베딩으로 바꿔도 **두 조건을 «이어야» 하는 문제**는 그대로 남습니다. 낱말 검색이든 벡터 유사도든 "각 줄이 질문과 얼마나 비슷한가"만 재기 때문입니다.

> 그래프는 «두 조건을 동시에 만족하는 것»을 **구조로** 찾는다.
> 벡터는 «두 조건과 비슷한 것»을 찾는다. **그게 다른 일이다.**

## 오해하기 쉬운 지점

- **"평평한 텍스트가 완전히 실패한 것"이 아니다.** 출력이 `✗`가 아니라 `△ 원문 5줄`인 이유가 있습니다. 답의 재료는 다 줬습니다. 다만 **결합의 부담을 모델에게 넘겼고**, 7줄이 아니라 7,000줄이 되는 순간 그 재료조차 못 줍니다.
- **키-값은 게을러서 실패한 게 아니다.** 칸을 아무리 성실하게 늘려도 조건 조합은 무한합니다. 실패의 원인은 개수가 아니라 **"저장 시점에 질문을 알아야 하는" 구조 자체**입니다.
- **그래프가 만능이라는 뜻도 아니다.** 27장은 곧바로 단서를 답니다. 그래프는 모호한 것을 못 담고(사용자가 말한 것은 그래프로, 내가 추론한 것은 원문으로), 사실 1,000개쯤은 넘어야 값을 합니다(`ex4`). 처음부터 그래프로 가지 말라는 게 이 장의 실무 조언입니다.

## 한 줄로

세 번째 질문은 **조건이 둘이고 그 둘이 서로 다른 줄에 흩어져 있는 첫 질문**이라, 「이을 수 있는가」를 시험합니다. 평평한 텍스트는 재료만 던지고, 키-값은 그 조합의 칸이 없어 침묵하며, 그래프만 저장할 때 몰랐던 경로를 질문 시점에 따라가 답합니다.
