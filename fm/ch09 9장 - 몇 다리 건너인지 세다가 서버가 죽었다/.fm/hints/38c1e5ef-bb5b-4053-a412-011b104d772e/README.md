# 다익스트라에 음수 가중치를 넣으면 어떻게 되는가?

> **답**: 예외 없이 조용히 틀린 답을 낸다. 확률에 로그를 취하는 곳이 있으면 특히 조심해야 한다.

이 카드의 핵심은 「틀린다」가 아니라 **「조용히」** 입니다. 크래시도, 스택 트레이스도, 경고 로그도 없습니다. 숫자 하나가 그냥 잘못된 채로 API 응답에 실려 나갑니다.

---

## 1. 왜 틀리나 — 다익스트라의 전제

다익스트라는 **탐욕(greedy) 알고리즘**입니다. 근거가 되는 불변식은 하나뿐입니다.

> 우선순위 큐에서 거리가 가장 작은 노드를 꺼냈다면, 그 노드의 거리는 **이미 최종값이다**.

왜 최종값인가? 앞으로 밟게 될 어떤 경로든 최소 한 개의 간선을 더 지나야 하는데, 모든 가중치가 0 이상이면 거리는 **줄어들 수 없기** 때문입니다. 그래서 "확정"하고 두 번 다시 안 봅니다.

에셋 예제(`ex3_dijkstra_negative.py`)에서 이 "확정"은 다음 두 줄에 들어 있습니다.

```python
if u in done:
    continue
done.add(u)                      # 한 번 확정하면 다시 안 본다
```

음수 간선이 하나라도 있으면 **"더 지나면 늘어난다"가 거짓**이 됩니다. 나중에 더 짧은 길이 발견될 수 있는데, 확정된 노드는 다시 펼쳐지지 않으므로 그 개선이 **뒤쪽 노드로 전파되지 않습니다.**

## 2. 4개 간선짜리 반례

에셋의 그래프는 노드 4개, 간선 4개가 전부입니다.

```python
EDGES = [("A", "C", 1), ("A", "B", 2), ("B", "C", -5), ("C", "D", 1)]
```

```
        2         -5
   A ───────► B ──────► C ───────► D
   │                    ▲     1
   └────────────────────┘
             1
```

실행 추적(직접 돌려 확인):

| 단계 | 큐에서 꺼낸 것 | 하는 일 | 거리표 상태 |
|---|---|---|---|
| 1 | `(0, A)` | A 확정. C=1, B=2 기록 | A0, B2, C1 |
| 2 | `(1, C)` | **C 확정**. D = 1+1 = 2 기록 | A0, B2, C1, **D2** |
| 3 | `(2, B)` | B 확정. A→B→C = 2−5 = **−3** 발견 → 거리표 갱신, `(-3, C)` 재삽입 | A0, B2, **C−3**, D2 |
| 4 | `(-3, C)` | C는 `done`에 있음 → **그냥 버림** | 변화 없음 |
| 5 | `(2, D)` | D 확정. 나가는 간선 없음 | 끝 |

최종 비교:

| 노드 | 다익스트라 | 벨만-포드(정답) | 같나 |
|---|---:|---:|---|
| A | 0 | 0 | 예 |
| B | 2 | 2 | 예 |
| C | −3 | −3 | 예 |
| D | **2** | **−2** | **아니오** |

음수 사이클은 **없습니다**. 즉 최단 경로가 잘 정의된 정상적인 그래프인데도 다익스트라가 틀립니다.

### 이 버그가 고약한 진짜 이유

**C는 맞고 D만 틀립니다.**

- C의 거리표 값은 3단계에서 −3으로 **갱신은 됐습니다**. 갱신을 막는 코드가 없으니까요. 막힌 것은 "그 갱신을 D 쪽으로 다시 밀어내는 일"뿐입니다.
- 그래서 시작점 근처만 찍어 보면 전부 정답으로 보입니다. **틀린 건 항상 확정된 노드의 하류(downstream)** 쪽입니다.
- 단위 테스트를 "A에서 인접 노드까지 거리가 맞나"로 짰다면 이 버그는 영원히 통과합니다.

## 3. 왜 예외가 안 나나

음수를 거부할 **책임 주체가 어디에도 없기 때문**입니다.

- `heapq`는 음수 키를 정상적인 값으로 받습니다. 정렬만 하면 되니까요.
- `nd = d + w` 는 그냥 뺄셈입니다.
- `if u in done: continue` 는 "중복 방지"라는 정상 동작으로 보입니다. 이게 사실은 오답을 만드는 지점인데, 코드만 보면 최적화처럼 읽힙니다.
- 가중치가 실제로 음수인지 **아무도 검사하지 않습니다.**

즉 실패가 예외가 아니라 **잘못된 반환값**으로 나타납니다. 이런 버그는 로그·알람·모니터링에 전혀 걸리지 않고, 몇 달 뒤 "왜 이 추천 경로가 이상하지?"로 발견됩니다.

> 참고: `networkx`는 `single_source_dijkstra_path_length`에 가드가 있어서, 확정된 노드가 나중에 개선되면 `ValueError('Contradictory paths found:', 'negative weights?')`를 던집니다(3.2.1에서 위 예제로 확인). 다만 이건 문서상 보장된 음수 검출기가 아니고, **직접 구현한 다익스트라나 여러 그래프 DB·엔진에는 그런 가드가 없습니다.** 라이브러리가 잡아 줄 거라고 기대하면 안 됩니다.

## 4. 실무에서 음수 가중치가 몰래 생기는 자리

에셋이 꼽는 세 가지입니다.

1. **할인·환급을 "음수 비용"으로 모델링할 때**
   물류/정산 그래프에서 "이 경유지를 거치면 리베이트 3원"을 `w = -3`으로 넣는 순간 끝입니다.
2. **유사도를 `1 - 거리`로 바꿨는데 유사도가 1을 넘을 때**
   정규화 안 된 점수, 코사인 유사도의 부동소수 오차(1.0000001), 가중합 스코어 등에서 흔합니다.
3. **로그를 취했는데 값이 1보다 작을 때 — `log 0.5 = -0.69`**
   책이 "제일 자주 봤다"고 하는 케이스입니다.

### 확률 × 로그가 위험한 이유 (제일 중요)

"경로 확률이 최대인 길"을 찾고 싶을 때 쓰는 아주 흔한 기법이 있습니다. 곱을 합으로 바꾸는 것이죠.

```
maximize  p1 · p2 · p3        (곱)
   ⇕  로그
maximize  log p1 + log p2 + log p3      ← 전부 음수!
   ⇕  부호 반전
minimize  (−log p1) + (−log p2) + (−log p3)   ← 최단 경로 문제
```

여기서 **부호를 뒤집는 마지막 단계가 필수**입니다.

- `w = -log p` : `p ∈ (0, 1]` 이면 `w ≥ 0` → 다익스트라 **안전**.
- `w = log p` : 항상 `w ≤ 0` → 다익스트라 **전부 오답**. 그런데 절댓값이 그럴듯해서 눈으로는 안 보입니다.

게다가 안전해 보이는 `-log p` 조차 **`p`가 진짜 확률일 때만** 안전합니다. 아래는 전부 음수를 만듭니다.

| 상황 | 결과 |
|---|---|
| 정규화 안 한 스코어라 `p > 1` (예: 1.4) | `-log 1.4 = -0.34` → 음수 |
| 신뢰도 보정/부스팅으로 값이 1을 살짝 넘음 | 음수 |
| 로그 밑이 뒤바뀜, `log`와 `log1p` 혼용 | 부호 뒤집힘 |
| `p = 0` | `-log 0 = inf` → 별개의 사고 |
| 임베딩 점수를 "확률처럼" 그대로 사용 | 상한 보장 없음 → 음수 |

정리하면 **`-log p` 파이프라인의 안전성은 전적으로 "p ≤ 1"이라는 불변식에 얹혀 있는데, 그 불변식은 코드 어디에도 적혀 있지 않은 경우가 대부분**입니다.

## 5. 그럼 어떻게 하나

### (1) 입구에서 막는다 — 가장 싸고 확실한 방법

```python
if w < 0:
    raise ValueError(f"음수 가중치: {a}→{b} = {w}")
```

가중치를 만드는 자리(로그 변환 직후, 스코어 정규화 직후)에 단언문 하나면 됩니다. 이 버그는 **탐지가 어렵지 알아채기만 하면 고치는 건 쉽습니다.**

### (2) 알고리즘을 바꾼다

| 상황 | 알고리즘 | 복잡도 | 비고 |
|---|---|---|---|
| 모든 가중치 ≥ 0 | 다익스트라 | `O(E log V)` | 기본값 |
| 음수 있음, 사이클 가능 | **벨만-포드** | `O(V·E)` | 음수 사이클 검출까지 해 준다 |
| 음수 있고 그래프가 DAG | 위상 정렬 후 1패스 완화 | `O(V+E)` | 음수여도 정확. 9.5절의 위상 정렬이 여기 쓰인다 |
| 음수 있고 전체 쌍이 필요 | 존슨(Johnson) | `O(V·E + V·E log V)` | 포텐셜로 재가중해 다익스트라를 되살린다 |
| 목적지를 알고 휴리스틱이 있음 | A* | — | 휴리스틱이 admissible해야 하며, 음수 간선에서는 이 역시 깨진다 |

에셋의 벨만-포드는 마지막에 한 바퀴를 더 돕니다. 이게 **음수 사이클 검출**입니다.

```python
for a, b, w in edges:                # 한 바퀴 더 돌아 음수 사이클 검사
    if dist[a] + w < dist[b]:
        return dist, True
```

`V-1`번 완화하면 최단 경로는 반드시 수렴해야 합니다. `V`번째에도 여전히 줄어들면 돌 때마다 짧아지는 사이클이 있다는 뜻이고, 그때는 **최단 경로 자체가 정의되지 않습니다**(−∞).

### (3) 하지 말아야 할 "해결책"

**모든 가중치에 상수를 더해 음수를 없애는 것.** 흔히 나오는 아이디어인데 **틀립니다.** 간선 `k`개짜리 경로에는 `k·C`가 더해지므로, 간선 수가 많은 경로가 부당하게 불리해져 **최단 경로의 정답 자체가 바뀝니다.** 상수 이동이 아니라 노드별 포텐셜을 쓰는 존슨 알고리즘이 정답입니다(포텐셜 `h`로 `w' = w + h(u) − h(v)`로 재가중하면 경로 합의 대소 관계가 보존됩니다).

## 6. 검증 체크리스트

이 버그는 "터지길 기다리는" 방식으로는 절대 못 잡습니다. 능동적으로 봐야 합니다.

- [ ] 가중치를 만드는 코드에 `assert w >= 0` 이 있나
- [ ] 로그 변환에 `-log p` 인가 `log p` 인가 (부호 확인)
- [ ] `p ≤ 1` 이 실제로 보장되나, 아니면 "그럴 것이다"인가
- [ ] 테스트가 시작점 근처만 보고 있지 않나 → **하류 노드를 봐야 한다**
- [ ] 의심되면 작은 부분 그래프에서 벨만-포드와 **결과를 대조**하라 (에셋 예제가 하는 일이 정확히 이것)
- [ ] 데이터 파이프라인이 바뀌었을 때 최소 가중치를 모니터링하는가 (`min(w)` 알람)

## 한 줄 정리

다익스트라의 "한 번 확정하면 다시 안 본다"는 **모든 가중치가 0 이상**이라는 조건 위에서만 성립한다. 음수가 섞이면 예외 대신 **하류 노드부터 조용히 틀린 값**이 나오고, 그 음수는 보통 `log p`(p < 1)나 정규화 안 된 유사도에서 들어온다.
