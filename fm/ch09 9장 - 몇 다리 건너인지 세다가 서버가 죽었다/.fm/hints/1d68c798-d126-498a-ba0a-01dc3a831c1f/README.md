# 슈퍼스텝 실행 시간은 어떻게 계산하는가?

> **답**: 각 층에서 가장 오래 걸리는 작업 시간을 층마다 더한다. 층 안의 나머지 작업은 그 시간에 묻힌다.

---

## 1. 한 줄 수식

위상 정렬로 만든 층(레이어)들을 $L_1, L_2, \dots, L_k$ 라 하고, 작업 $t$ 의 소요 시간을 $d_t$ 라 하면

$$T_{\text{super}} \;=\; \sum_{\ell=1}^{k} \; \max_{t \in L_\ell} d_t$$

핵심은 **합 안에 최댓값이 들어 있다**는 것입니다. 층 안에서는 `max`(같이 돌리니까 제일 느린 놈만 보면 된다), 층 사이에서는 `sum`(앞 층이 **전부** 끝나야 다음 층이 시작한다).

비교 대상 두 개도 같은 언어로 적어 두면 관계가 선명해집니다.

$$T_{\text{serial}} = \sum_{t} d_t
\qquad
T_{\text{cp}} = \max_{P \in \text{경로}} \sum_{t \in P} d_t$$

그리고 언제나 다음 부등식이 성립합니다.

$$T_{\text{cp}} \;\le\; T_{\text{super}} \;\le\; T_{\text{serial}}$$

- 오른쪽 부등식이 "층으로 나누면 빨라진다"는 이야기.
- **왼쪽 부등식이 이 카드의 진짜 요점**입니다. 슈퍼스텝 실행은 임계 경로(critical path)보다 결코 빠를 수 없고, 보통은 **느립니다**.

`ex5_toposort.py` 의 구현이 정확히 이 수식입니다.

```python
serial   = sum(cost.values())
parallel = sum(max(cost[t] for t in l) for l in layers)   # ← Σ max
```

## 2. 에셋 예제로 단계별 계산

`code/ex5_toposort.py` 의 `TASKS` 는 그래프 파이프라인 8개 작업의 의존 관계입니다.

| 작업 | 의존(선행) | 비용 $d_t$ |
|---|---|---|
| 외부 API 예열 | — | 40분 |
| 데이터 적재 | — | 20분 |
| 스키마 검증 | 데이터 적재 | 5분 |
| 엔티티 병합 | 데이터 적재 | 30분 |
| 관계 추출 | 스키마 검증, 엔티티 병합 | 15분 |
| 품질 검사 | 관계 추출 | 8분 |
| 색인 생성 | 관계 추출 | 25분 |
| 배포 | 품질 검사, 색인 생성, 외부 API 예열 | 3분 |

### 2-1. 층 만들기 (칸 알고리즘)

진입 차수 0인 것을 한꺼번에 꺼내고, 그 층을 통째로 제거한 뒤 다시 진입 차수 0인 것을 꺼냅니다. 이게 `supersteps()` 함수이고, 나오는 층이 곧 슈퍼스텝입니다.

| 층 | 작업 | 각 비용 | $\max_{t \in L_\ell} d_t$ |
|---|---|---|---|
| 1차 | 데이터 적재, 외부 API 예열 | 20, **40** | **40분** |
| 2차 | 스키마 검증, 엔티티 병합 | 5, **30** | **30분** |
| 3차 | 관계 추출 | **15** | **15분** |
| 4차 | 색인 생성, 품질 검사 | **25**, 8 | **25분** |
| 5차 | 배포 | **3** | **3분** |

### 2-2. 합산

$$T_{\text{super}} = 40 + 30 + 15 + 25 + 3 = \mathbf{113\ \text{분}}$$

$$T_{\text{serial}} = 40+20+5+30+15+8+25+3 = \mathbf{146\ \text{분}}$$

$$\frac{T_{\text{serial}}}{T_{\text{super}}} = \frac{146}{113} \approx 1.3\ \text{배 단축}$$

"층 안의 나머지 작업은 그 시간에 묻힌다"가 이 표에서 눈에 보입니다. 1차 층의 **데이터 적재 20분은 계산식에 아예 등장하지 않습니다.** 40분짜리 외부 API 예열 뒤에 숨었으니까요. 2차 층의 스키마 검증 5분도, 4차 층의 품질 검사 8분도 마찬가지입니다. 이 세 작업의 비용을 0으로 만들어도 총 시간은 113분 그대로입니다. 반대로 **각 층의 1등을 1분 줄이면 총 시간이 정확히 1분 줄어듭니다.** 최적화 노력을 어디에 쓸지가 여기서 결정됩니다.

### 2-3. 임계 경로와 비교

`critical_path()` 는 각 작업의 완료 시각을 $f(t) = d_t + \max_{u \in \text{deps}(t)} f(u)$ 로 재귀 계산합니다.

| 작업 | 가장 빠른 시작 | 완료 $f(t)$ |
|---|---|---|
| 데이터 적재 | 0 | 20 |
| 외부 API 예열 | 0 | 40 |
| 스키마 검증 | 20 | 25 |
| 엔티티 병합 | 20 | **50** |
| 관계 추출 | 50 | **65** |
| 품질 검사 | 65 | 73 |
| 색인 생성 | 65 | **90** |
| 배포 | 90 | **93** |

$$T_{\text{cp}} = \mathbf{93\ \text{분}} \quad (\text{데이터 적재} \to \text{엔티티 병합} \to \text{관계 추출} \to \text{색인 생성} \to \text{배포})$$

$$T_{\text{super}} - T_{\text{cp}} = 113 - 93 = \mathbf{20\ \text{분}}\ \text{손해}$$

### 2-4. 20분은 정확히 어디서 새는가

층별 시작·종료 시각을 두 방식으로 나란히 놓으면 범인이 딱 하나로 좁혀집니다.

| | 층 배리어 방식 | 의존 단위(as-soon-as-ready) |
|---|---|---|
| 데이터 적재 | 0 → 20 | 0 → 20 |
| 외부 API 예열 | 0 → 40 | 0 → 40 |
| **엔티티 병합** | **40 → 70** | **20 → 50** |
| 관계 추출 | 70 → 85 | 50 → 65 |
| 색인 생성 | 85 → 110 | 65 → 90 |
| 배포 | 110 → 113 | 90 → 93 |

엔티티 병합은 선행 작업(데이터 적재)이 20분에 이미 끝났는데도, **같은 층의 외부 API 예열이 40분에 끝날 때까지 20분을 놀고 기다립니다.** 그리고 이 20분 지연이 임계 사슬을 타고 끝까지 그대로 밀려 93 → 113이 됩니다. 낭비가 중간에 흡수되지 않는다는 게 배리어의 성질입니다.

더 얄궂은 건, 외부 API 예열의 **유일한 후행 작업은 5차 층의 배포**라는 점입니다. 논리적으로는 40분짜리 예열을 언제 돌리든 90분 시점까지만 끝나면 됩니다. 그런데 위상 정렬은 그것을 "진입 차수 0"이라는 이유만으로 1차 층에 넣었고, 배리어는 그 층 전체를 40분으로 못 박았습니다. **의존 관계가 없는 작업이 서로를 붙잡는 것** — 이게 층 배리어가 만드는 가짜 의존(false dependency)입니다.

### 2-5. 놀고 있는 시간 총량

작업자가 층 폭만큼 있다고 보면, 유휴 시간은 층마다 $\sum_{t \in L_\ell}\left(\max_{u \in L_\ell} d_u - d_t\right)$ 입니다.

| 층 | 유휴 |
|---|---|
| 1차 | (40−20) + (40−40) = 20 |
| 2차 | (30−5) + (30−30) = 25 |
| 3차 | 0 |
| 4차 | (25−8) + (25−25) = 17 |
| 5차 | 0 |
| **합** | **62 작업자·분** |

총 확보 용량 $\sum_\ell |L_\ell| \cdot \max_{t \in L_\ell} d_t = 208$ 작업자·분 중 실제 일한 건 146. **가동률 70%**. 나머지 30%는 배리어 앞에서 대기한 시간입니다.

## 3. 왜 이런 모델을 쓰는가 — BSP

이 계산 구조는 우연이 아니라 **BSP(Bulk Synchronous Parallel)** 모델 그 자체입니다. Leslie Valiant가 1990년 `A Bridging Model for Parallel Computation`(CACM)에서 제안했고, 한 슈퍼스텝의 비용을

$$T_{\text{step}} = \max_i w_i \;+\; g \cdot \max_i h_i \;+\; L$$

로 정의합니다. $w_i$ 는 프로세서 $i$ 의 지역 계산량, $h_i$ 는 주고받은 메시지 수, $g$ 는 통신 대역폭 계수, $L$ 은 배리어 동기화 비용입니다. **여기에도 `max` 가 두 번 등장합니다.** 우리가 위에서 쓴 $\sum_\ell \max_t d_t$ 는 통신·배리어 항을 0으로 둔 축약형입니다. 실제 분산 시스템에서는 $g\max h_i + L$ 이 더해지므로 **손해가 더 커지지 덜해지지 않습니다.**

BSP가 이겨 온 이유는 성능이 아니라 **추론 가능성**입니다.

- 슈퍼스텝 안에서는 서로 간섭이 없으니 락도, 경쟁 조건도, 데드락도 없습니다.
- 배리어마다 일관된 전역 상태가 존재하니 그 지점에서 체크포인트를 찍고, 죽은 워커를 재시작하고, 수렴을 판정할 수 있습니다.
- 진행 상황이 "지금 3차 슈퍼스텝"으로 딱 떨어져 관측·디버깅이 쉽습니다.

에셋의 마지막 문장이 이 트레이드오프를 정확히 요약합니다. "층 단위는 구현이 쉽고, 의존 단위는 빠르다."

### 실제 시스템 대응표

| 시스템 | 배리어 단위 | 비고 |
|---|---|---|
| **Pregel** (Google, SIGMOD 2010) | 슈퍼스텝 | "think like a vertex". 슈퍼스텝 $s$ 에서 보낸 메시지는 $s+1$ 에서 읽힘 |
| **Apache Giraph** | 슈퍼스텝 | Pregel의 오픈소스 구현. 페이스북 그래프 처리에 쓰임 |
| **Spark / GraphX** | 스테이지 | 셔플 경계가 배리어. 스테이지는 가장 느린 태스크가 끝나야 종료 |
| **MapReduce** | Map→Reduce | 모든 map이 끝나야 reduce 시작. 원조 층 배리어 |
| **Airflow / Argo Workflows** | 태스크 의존 | 배리어 없이 의존이 풀리는 대로 실행 → 임계 경로에 근접 |
| **GraphLab / PowerGraph (async)** | 없음 | 비동기 실행으로 배리어 제거. 대신 일관성 모델을 직접 관리해야 함 |

### 낙오자(straggler) 문제로 이어진다

$\max$ 구조의 진짜 위험은 평균이 아니라 **꼬리**입니다. 층 안 작업 100개 중 99개가 1초, 하나가 100초면 그 층은 100초입니다. 분산 그래프 처리에서 이 낙오자를 만드는 주범이 바로 이 장의 다른 주제인 **슈퍼 노드**입니다. 차수 편중(degree skew) 때문에 팔로워 1억 명짜리 노드를 맡은 워커 하나가 모든 슈퍼스텝을 붙잡습니다. PowerGraph의 **vertex-cut**(고차수 정점을 여러 머신에 쪼개기)이나 Spark의 **speculative execution**이 이 꼬리를 자르려는 시도입니다.

또 하나: 반복형 그래프 알고리즘(PageRank, 최단 경로 등)에서는 이 손해가 **매 반복마다** 곱해집니다. 슈퍼스텝당 1초 낭비는 30회 반복이면 30초입니다.

## 4. 자주 하는 실수

- **"층 개수 = 병렬 실행 속도"로 착각한다.** 층이 5개라고 5단위 시간이 아닙니다. 층마다 폭(span)이 다릅니다. 층 개수는 통신 라운드 수를 알려 줄 뿐입니다.
- **평균을 더한다.** $\sum_\ell \text{avg}(L_\ell)$ 은 항상 실제보다 짧게 나옵니다. 반드시 `max` 입니다.
- **임계 경로 = 슈퍼스텝 실행이라고 믿는다.** 두 값이 같아지는 건 각 층의 최댓값 작업들이 하나의 경로로 이어질 때뿐입니다. 위 예제에서는 1차 층의 최댓값(외부 API 예열)이 임계 경로 위에 없기 때문에 어긋납니다.
- **작업자 수 제약을 잊는다.** $\sum_\ell \max_t d_t$ 는 각 층의 모든 작업을 **동시에** 돌릴 수 있다는 가정입니다. 작업자가 부족하면 층 안에서도 순차 실행이 생기고, 실제 시간은 더 길어집니다.

## 5. 한 문장으로

$$T_{\text{super}} = \sum_{\ell} \max_{t \in L_\ell} d_t$$

**층마다 1등만 세어 더한다. 나머지는 공짜로 묻히지만, 그 대신 1등을 기다리느라 임계 경로보다 느려진다.** 예제에서는 113분 대 93분, 20분 차이입니다.
