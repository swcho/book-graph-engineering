# "모든 경로를 보여 줘"에 되물어야 할 세 가지

## 정답 한 줄

1. **정말 전부인가, 아니면 「가장 짧은 것 몇 개」인가** (개수 = K)
2. **길이 상한이 있나** (깊이 = depth)
3. **중간에 반드시 지나야 할 노드가 있나** (경유 = waypoint)

외울 때는 **K / 깊이 / 경유**, 즉 「몇 개, 얼마나 멀리, 어디를 거쳐」로 묶으면 됩니다.

---

## 왜 되물어야 하나 — 문제의 급이 다르다

9장 `ex4_path_explosion.py`가 보여 주는 게 정확히 이겁니다. 방향이 오른쪽·아래뿐인 n×n 격자에서
`(0,0) → (n-1,n-1)` 경로를 세면:

| 격자 | 최단 경로 길이 | 서로 다른 경로 수 |
|---|---|---|
| 3×3 | 4 | 6 |
| 5×5 | 8 | 70 |
| 8×8 | 14 | 3,432 |
| 11×11 | 20 | 184,756 |
| 15×15 | 28 | 40,116,600 |
| 20×20 | 38 | 35,345,263,800 |

최단 경로 **길이**는 `2(n-1)`로 선형인데, 경로 **개수**는 `C(2(n-1), n-1)`로 조합 폭발합니다.
20×20에서 이미 353억 개예요. 세는 건 DAG 위의 DP라 순식간이지만(`count_paths`의 memo),
**나열은 못 합니다.** 한 줄 100바이트로 잡아도 3.5TB짜리 응답입니다.

정리하면:

| 요구 | 복잡도 | 대표 알고리즘 |
|---|---|---|
| 최단 경로 **하나** | 다항. BFS `O(V+E)`, 다익스트라 `O(E + V log V)` | BFS / 다익스트라 / A* |
| 최단 경로 **K개** | 다항 × K | Yen's KSP, Eppstein |
| 길이 ≤ L인 경로 | `O(d^L)` — L이 상한이라 제어 가능 | 깊이 제한 DFS/BFS, 가변 길이 패턴 질의 |
| **모든** (단순) 경로 | 지수. 개수 세기는 #P-완전, 나열은 출력 크기에 비례 | 백트래킹 열거 (사실상 금지) |

앞의 셋은 「계산 문제」이고 마지막 하나는 「출력 문제」입니다. 아무리 좋은 알고리즘을 써도
출력이 353억 줄이면 방법이 없습니다. 그래서 **알고리즘을 고르기 전에 요구사항을 깎는 것**이
유일한 해법이고, 그 깎는 도구가 이 세 질문입니다.

본문의 장애 사례가 그대로 이겁니다. 「영향 범위를 다 보여 줘」를 모든 경로 열거로 구현했고,
평소엔 잘 돌다가 **어느 날 노드 하나가 슈퍼 노드가 되면서** 서버가 죽었습니다.
질의는 안 바뀌었는데 데이터가 바뀌어서 터진 케이스라, 코드 리뷰로는 절대 안 잡힙니다.

## 질문 1 — "정말 전부인가, 아니면 가장 짧은 것 몇 개인가"

### 무엇을 물어보는 건가

요구자가 실제로 원하는 건 대개 「전부」가 아니라 **「대표적인 것 몇 개」**입니다.
UI에 353억 개를 그릴 리가 없으니까요. 화면을 먼저 물어보면 답이 나옵니다.
"이거 화면에 몇 줄 보여 주실 거예요?" → "한 10개쯤요." → 끝났습니다. K = 10.

### 이어지는 알고리즘: K-최단 경로 (K-Shortest Paths)

- **Yen's algorithm** — 단순 경로(같은 노드 재방문 없음) K개를 짧은 순서로. 최단 경로를 하나 구한 뒤,
  그 경로의 각 노드를 「분기점(spur node)」으로 삼아 이미 쓴 엣지를 막고 다시 최단 경로를 구하는 식으로
  후보를 모읍니다. 복잡도는 대략 `O(K · V · (E + V log V))`. K가 상수면 다항입니다.
- **Eppstein's algorithm** — 단순 경로 제약을 빼면(= 노드 재방문 허용) `O(E + V log V + K)`로 훨씬 빠릅니다.
  「루프가 섞여도 되나」를 한 번 더 물어봐야 하는 이유입니다.
- **모든 최단 경로만** — 길이가 최소인 것들만 전부 원하는 경우라면 K-최단이 아니라
  BFS/다익스트라의 선행자(predecessor) DAG를 만들어 역추적하면 됩니다.
  Neo4j의 `allShortestPaths`, NetworkX의 `all_shortest_paths`가 이겁니다.
  단, 이것도 동률 경로가 조합적으로 많으면 폭발할 수 있으니 `LIMIT`은 필수입니다.

### 질의로 쓰면

```cypher
// Neo4j GDS — Yen's K-shortest paths
CALL gds.shortestPath.yens.stream('myGraph', {
  sourceNode: a, targetNode: b, k: 10, relationshipWeightProperty: 'cost'
})
YIELD index, totalCost, nodeIds, path
RETURN index, totalCost, path
ORDER BY index;

// 길이 동률인 최단 경로만, 개수 제한
MATCH p = allShortestPaths((a:Service {id:$a})-[:CALLS*..6]->(b:Service {id:$b}))
RETURN p LIMIT 20;
```

```python
# NetworkX
from networkx.algorithms.simple_paths import shortest_simple_paths
from itertools import islice
top10 = list(islice(shortest_simple_paths(G, s, t, weight="cost"), 10))
```

> `shortest_simple_paths`는 제너레이터입니다. **`list()`로 통째로 감싸지 말고 `islice`로 잘라 쓰세요.**
> 감싸는 순간 「모든 경로 열거」로 돌아갑니다. 실무에서 이 한 줄로 장애 납니다.

## 질문 2 — "길이 상한이 있나"

### 무엇을 물어보는 건가

9.1절의 결론이 여기에 걸립니다. 평균 차수 12짜리 그래프에서는 한 홉마다 약 11배씩 늘어서,
**5홉이면 전체의 68%, 6홉이면 사실상 전부**입니다. 즉 **상한 없는 순회 = 전체 스캔**이에요.
서버가 죽는 건 알고리즘이 나빠서가 아니라 상한이 없어서입니다.

그리고 상한은 성능 장치이기 전에 **의미 장치**입니다. 「8홉 건너 연결된 사람」은 대부분 아무 의미가 없어요.
비즈니스적으로 의미 있는 거리를 물으면 상한은 대개 2~4로 수렴합니다.

### 이어지는 알고리즘: 홉 상한 순회 / 가변 길이 경로 질의

- **깊이 제한 BFS/DFS** — `ex2_bidirectional.py`의 `bfs_path(adj, s, t, max_hop=8)`처럼 인자로 못을 박습니다.
- **가변 길이 패턴** — Cypher `[:REL*1..3]`, SQL 재귀 CTE의 `WHERE depth < 3`.
- **양방향 탐색** — 출발지와 도착지를 **둘 다 알 때** 반지름 d짜리 공 하나 대신 d/2짜리 공 두 개를 그립니다.
  공 크기가 지수라 절반으로 줄이면 방문 수가 제곱근이 됩니다. 본문 실측 75~88배 감소.
  단 **도착지를 알아야** 씁니다. 「이 사람과 3다리 안에 있는 사람 전부」는 도착지가 없어서 양방향으로 못 풉니다.
- **결과 개수 상한도 별도로** — 깊이 상한만으로는 슈퍼 노드를 못 막습니다.
  차수 100만짜리 노드 하나가 끼면 2홉도 터져요. `LIMIT` + 질의 타임아웃 + 차수 상한(고차수 노드 가지치기)을 함께 겁니다.

### 질의로 쓰면

```cypher
-- 상한 없음: 사실상 전체 스캔. 리뷰에서 반려 대상
MATCH p = (a)-[:DEPENDS_ON*]->(b) RETURN p;

-- 상한 있음
MATCH p = (a:Service {id:$a})-[:DEPENDS_ON*1..4]->(b:Service {id:$b})
RETURN p LIMIT 100;
```

```sql
-- SQL 재귀 CTE: depth 컬럼으로 못을 박는다
WITH RECURSIVE walk(src, dst, depth) AS (
  SELECT src, dst, 1 FROM edges WHERE src = :start
  UNION ALL
  SELECT w.src, e.dst, w.depth + 1
  FROM walk w JOIN edges e ON e.src = w.dst
  WHERE w.depth < 4                      -- 이 줄이 없으면 서버가 죽는다
)
SELECT * FROM walk LIMIT 1000;
```

## 질문 3 — "중간에 반드시 지나야 할 노드가 있나"

### 무엇을 물어보는 건가

이게 셋 중 가장 자주 놓치는 질문이고, 동시에 **가장 크게 후보를 깎는** 질문입니다.
「A에서 B로 가는 경로 전부」는 353억 개지만 「A에서 결제 게이트웨이를 거쳐 B로 가는 경로」는 수십 개일 수 있어요.
요구자가 진짜 궁금한 건 대개 「전체 지도」가 아니라 **「저 위험한 노드를 통과하는 경로가 있느냐」**입니다.

역으로 「거치면 안 되는 노드」(제외 조건)를 묻는 것도 같은 계열입니다.
장애 노드를 뺀 우회 경로가 있는지 보는 질의가 여기 해당합니다.

### 이어지는 알고리즘: 경유 노드 제약 (waypoint)

- **경유지 1개, 워크(walk) 허용** — `s→w→t`를 `sp(s,w) + sp(w,t)`로 분해합니다.
  최단 경로 두 번이니 여전히 다항이에요. 가장 흔하고 가장 싼 해법입니다.
- **단순 경로를 강제하면** 이야기가 달라집니다. 두 구간이 노드를 공유하면 안 되므로
  「정점 서로소 두 경로의 길이 합 최소화」 문제가 되고, 일반 그래프에서 NP-난해입니다.
  실무에서는 대개 워크로 타협하거나, 겹치면 버리고 다음 후보를 보는 식으로 처리합니다.
- **경유지 여러 개, 순서 고정** — `sp(s,w1) + sp(w1,w2) + ... + sp(wk,t)`로 그냥 이어 붙입니다.
- **경유지 여러 개, 순서 자유** — 경유지 사이 최단 거리로 완전 그래프를 만든 뒤 방문 순서를 정해야 하므로
  TSP(외판원 경로)가 됩니다. 경유지가 10~15개 넘어가면 정확해는 포기하고 휴리스틱으로 갑니다.
- **제외 제약** — 해당 노드/엣지를 걷어낸 부분 그래프에서 최단 경로를 구하거나, 순회 중 필터로 거릅니다.

### 질의로 쓰면

```cypher
// 경유 노드 고정 — 양쪽 다 홉 상한을 걸어야 한다
MATCH p = (a:Service {id:$a})-[:CALLS*1..3]->(w:Service {id:$waypoint})-[:CALLS*1..3]->(b:Service {id:$b})
RETURN p LIMIT 50;

// 특정 노드를 피해 가는 경로
MATCH p = shortestPath((a)-[:CALLS*..6]->(b))
WHERE none(n IN nodes(p) WHERE n.id = $broken)
RETURN p;
```

## 실무 대화 예시

### 사례 1 — 영향 범위 분석 (본문 장애의 원형)

> **요청자**: 이 서비스 장애 나면 영향받는 경로를 전부 보여 주세요.
> **엔지니어**: 「전부」가 353억 개일 수 있어서요, 세 가지만 확인할게요.
> ① 화면에 몇 개 띄우실 거예요?
> **요청자**: 대시보드 카드로 열 개쯤이요.
> **엔지니어**: ② 몇 홉까지 보실 거예요? 6홉이면 사내 서비스 거의 전부가 잡힙니다.
> **요청자**: 아, 그럼 3홉이면 충분해요. 그 이상은 어차피 저희 팀 책임이 아니라서요.
> **엔지니어**: ③ 반드시 거쳐야 하는 지점이 있나요? 예를 들어 결제 게이트웨이 통과 여부.
> **요청자**: 맞아요, 결제 통과하는 것만 따로 봐야 해요. 그게 사실 제일 궁금한 거고요.

→ 「모든 경로 열거(지수)」가 **「결제 GW 경유, 3홉 이내, 상위 10개(다항)」**로 바뀝니다.
세 질문 다 던지고 나니 요청자 본인이 원래 원하던 걸 더 정확히 말해 줬다는 점도 눈여겨보세요.
이게 이 되묻기의 진짜 값어치입니다. 성능은 부산물이에요.

### 사례 2 — 사기 탐지 연결 고리

> **요청자**: 이 계정이랑 저 계정이 어떻게 이어져 있는지 전부요.
> **엔지니어**: 심사관이 실제로 보는 건 몇 개예요?
> **요청자**: 가장 가까운 연결 세 개 정도면 판단이 돼요.
> **엔지니어**: 그럼 K=3 최단 경로로 갈게요. 홉 상한은요?
> **요청자**: 4홉 넘으면 우연이라 안 봐요.
> **엔지니어**: 공용 디바이스나 공용 IP 같은 허브 노드를 거치는 건 어떻게 할까요?
> **요청자**: 그건 노이즈예요. 빼 주세요. 아 근데 같은 계좌를 거치는 건 반드시 보여 주세요.

→ Yen's KSP(K=3) + 4홉 상한 + 고차수 노드 제외 + 계좌 노드 경유 표시.
**허브/슈퍼 노드 제외**는 세 번째 질문의 반대 방향이고, 성능과 정확도를 동시에 살립니다.

### 사례 3 — 되묻지 않았을 때

> **요청자**: 의존성 경로 전부 보여 주세요.
> **엔지니어**: 네.

→ 3개월 잘 돌다가, 공통 로깅 라이브러리가 전사 표준이 되면서 차수 4만짜리 슈퍼 노드가 생깁니다.
질의 하나가 힙을 다 먹고 OOM. **질의는 안 바뀌었는데 데이터가 바뀌어서 터진 것**이라
롤백할 커밋도 없습니다. 상한은 「지금 느려서」가 아니라 「나중에 데이터가 변해도 안 죽으려고」 겁니다.

## 리뷰 체크리스트

- [ ] 경로 질의에 **홉 상한**이 있나 (`*1..3`, `depth <`, `max_hop=`)
- [ ] **결과 개수 상한**(`LIMIT`, `islice`, `k=`)이 있나 — 깊이 상한만으로는 슈퍼 노드를 못 막는다
- [ ] 「모든 경로」를 세기만 하면 되는데 나열하고 있진 않나 (세는 건 DP로 싸다)
- [ ] 제너레이터를 `list()`로 통째로 감싸지 않았나
- [ ] 도착지가 정해져 있다면 **양방향 탐색**을 쓰고 있나
- [ ] 최악의 차수를 가진 노드로 이 질의를 한 번 돌려 봤나 (평균이 아니라 **최대 차수**로)
- [ ] 질의 타임아웃이 걸려 있나
