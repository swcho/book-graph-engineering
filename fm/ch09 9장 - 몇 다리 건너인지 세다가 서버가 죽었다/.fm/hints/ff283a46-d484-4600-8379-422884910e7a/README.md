# 다익스트라 음수 가중치 버그가 고약한 이유

> **질문** 다익스트라 음수 가중치 버그가 특히 고약한 이유는 무엇인가?
>
> **답** C는 맞고 D만 틀리는 식으로 **일부만** 어긋난다. 시작점 근처만 검증하면 정상으로 보이며 **예외도 발생하지 않는다**.

---

## 1. 한 줄 요약

음수 가중치를 넣은 다익스트라는 **터지지 않는다**. 크래시도, 예외도, 무한 루프도 없다. 그냥 **답의 일부만 조용히 틀린다**. 그것도 하필 **검증하기 쉬운 앞쪽은 맞고, 검증을 안 하는 뒤쪽이 틀리는** 방향으로 틀린다. 이게 "고약하다"는 말의 정확한 뜻이다.

---

## 2. 9장 예제(`ex3_dijkstra_negative.py`)의 실제 동작

### 그래프

```
        2          -5
   A ────────► B ────────► C ────────► D
   │                       ▲      1
   └───────────────────────┘
              1
```

| 엣지 | 가중치 |
|---|---|
| A → C | 1 |
| A → B | 2 |
| B → C | **-5** |
| C → D | 1 |

정답(벨만-포드): A=0, B=2, **C=-3**, **D=-2**
다익스트라: A=0, B=2, **C=-3**, **D=2** ← D만 틀림

### 우선순위 큐 추적

실제로 돌려 본 팝(pop) 순서다.

| # | 큐에서 꺼낸 것 | 결과 | 그 순간의 거리표 |
|---|---|---|---|
| 1 | `(0, A)` | 확정. C=1, B=2 기록 | `A:0, C:1, B:2` |
| 2 | `(1, C)` | **확정**. D=1+1=2 기록 | `A:0, C:1, B:2, D:2` |
| 3 | `(2, B)` | 확정. B→C가 2-5=**-3** → 거리표 갱신, 큐에 push | `A:0, C:-3, B:2, D:2` |
| 4 | `(-3, C)` | **`done`에 이미 있음 → skip** | 변화 없음 |
| 5 | `(2, D)` | 확정. 이웃 없음 | 최종 |

핵심은 4번 줄이다. `-3`이라는 더 좋은 거리를 들고 C를 다시 꺼내지만, C는 2번에서 이미 확정(`done`)됐기 때문에 `continue`로 버려진다.

```python
d, u = heapq.heappop(pq)
if u in done:
    continue          # ← 여기서 -3짜리 개선이 통째로 버려진다
done.add(u)           # 한 번 확정하면 다시 안 본다
```

### 그래서 왜 "C는 맞고 D만 틀린가"

| 노드 | 값 | 왜 |
|---|---|---|
| C | -3 (**맞음**) | 3번 단계에서 `dist[C] = -3`으로 **거리표는 갱신됐다** |
| D | 2 (**틀림**) | 그 갱신이 **아래로 전파되지 않았다**. C가 다시 안 펼쳐지니 D는 옛날 값 2에 그대로 남는다 |

이걸 **죽은 갱신(dead update)** 이라고 부를 수 있다. 값은 고쳐졌는데 그 결과를 아무도 물려받지 못한 상태. 그래서 거리표를 눈으로 훑으면 **음수 엣지의 도착점 C까지는 완벽하게 정답**이고, 오염은 정확히 **C의 하류(downstream)에서만** 나타난다.

> **왜 이런 방향으로 틀리는가 — 깨진 불변식**
> 다익스트라의 정당성은 "큐에서 꺼낸 최솟값은 더 이상 줄어들 수 없다"는 데 있다. 이 명제는 **가중치가 음이 아닐 때만** 성립한다. 가중치가 0 이상이면 경로를 따라가며 거리가 단조 증가하므로, 이미 꺼낸 값보다 작은 값이 나중에 만들어질 수 없다. 음수 엣지 하나가 이 단조성을 깨뜨리고, 깨진 순간부터 "확정"은 그냥 **잘못된 조기 종료**가 된다.

## 3. 왜 예외가 안 나는가

버그가 조용한 이유를 하나씩 뜯어보면 이렇다.

| 방어선이 될 뻔한 것 | 왜 안 걸리나 |
|---|---|
| 타입/런타임 오류 | `heapq`는 음수 정수 튜플을 아무 문제 없이 정렬한다. 음수는 파이썬에서 완전히 정상적인 숫자다 |
| 무한 루프 | `done` 집합이 각 노드를 최대 한 번만 확장하므로 **음수 사이클이 있어도 종료한다**. 아이러니하게도 방어 장치가 버그를 더 조용하게 만든다 |
| `inf` / `None` 같은 이상값 | 나오지 않는다. D=2는 멀쩡한 유한값이다 |
| 경로 유효성 검사 | 반환된 A→C→D는 **실제로 존재하는 경로**다. 비용 2도 그 경로의 진짜 비용이다. 틀린 건 **최적성**뿐이라 "경로가 유효한가" 검사는 100% 통과한다 |
| 알고리즘 진입부의 입력 검증 | 교과서 구현에는 `assert w >= 0`이 대개 없다. 음수를 넣으면 안 된다는 건 **문서에만** 있는 전제다 |

즉 "값이 틀렸다"를 알아채려면 **정답을 따로 알고 있어야** 한다. 크래시는 정답을 몰라도 보이지만, 최적성 위반은 정답을 알아야만 보인다. 이 차이가 전부다.

## 4. 테스트로 왜 안 잡히나 — 부분 오답의 탐지 난이도

부분 오답은 "전부 틀림"보다 훨씬 잡기 어렵다. 이유가 층층이 있다.

### 4.1 테스트 그래프가 너무 작고 너무 얕다

단위 테스트에 넣는 그래프는 보통 노드 3~5개다. 그런데 이 버그는 **음수 엣지의 하류에 노드가 있어야만** 드러난다. 위 예제에서 D를 빼고 A, B, C만 두면 다익스트라와 벨만-포드의 결과가 **완전히 일치한다**. 테스트는 초록불이고 버그는 그대로 있다.

> 체크: 테스트 그래프에 "음수 엣지 → 그 도착점 → 그 다음 노드"라는 **3단 하류**가 존재하는가?

### 4.2 검증 지점이 시작점 근처에 몰려 있다

사람이 손으로 기대값을 계산할 때는 자연스럽게 **1~2홉짜리부터** 쓴다. 그런데 이 버그는 정의상 **오염이 시작되는 지점보다 뒤에서만** 보인다. 검증 밀도와 버그 발현 위치가 정확히 반대로 분포한다.

### 4.3 눈으로 보면 "잘 돌고 있네"로 보인다

거리표를 출력해 보면 A=0, B=2, C=-3 — 세 개 다 맞다. 4개 중 3개가 맞으면 사람 눈에는 **정상 동작**이다. 오히려 "음수도 잘 처리하네"라는 **잘못된 확신**을 준다. 전부 틀리는 버그였다면 5초 만에 잡혔을 것이다.

### 4.4 무작위 그래프 테스트에서는 통계에 묻힌다

`graph.py`의 `weighted(allow_negative=True)`는 엣지의 5%만 음수로 만든다.

```python
if allow_negative and rnd.random() < 0.05:
    w = -rnd.randint(1, 5)
```

무작위 노드 쌍 100개를 뽑아 비교하면 대부분은 우연히 정답이 나온다. 불일치가 몇 건 나와도 "부동소수점 오차겠지", "타이 브레이크 차이겠지"로 넘어가기 쉽다. **불일치율이 0이 아니라 낮다**는 게 가장 나쁜 조건이다.

### 4.5 골든 테스트가 버그를 봉인한다

가장 흔한 자해 패턴. 기대값을 **현재 구현의 출력으로 만들어** 스냅샷을 뜨면, 그 순간 D=2가 정답으로 못 박힌다. 이후 누가 벨만-포드로 고치면 **테스트가 빨간불이 되고** 수정이 롤백된다. 기준선은 반드시 **독립적인 참조 구현**에서 나와야 한다.

### 4.6 운영 지표로는 절대 안 보인다

모니터링하는 건 지연시간, 처리량, 에러율, 5xx 비율이다. **정답률은 관측 대상이 아니다.** 추천 결과가 미묘하게 이상하다는 사용자 신고가 몇 달 뒤 들어오고, 그때는 이미 어느 배포가 원인인지 특정할 수 없다.

### 4.7 음수가 "몰래" 들어온다

9장이 짚는 실무 발생 지점이다. 개발자가 `-5`를 타이핑하는 게 아니라 **파이프라인이 음수를 만들어낸다.**

| 자리 | 어떻게 음수가 되나 |
|---|---|
| 할인/환급을 "음수 비용"으로 모델링 | 의도적으로 음수를 넣는 경우. 그나마 눈에 보임 |
| 유사도를 `1 - 거리`로 변환 | 거리가 1을 넘는 순간 음수. 정규화 안 된 임베딩에서 자주 발생 |
| **확률에 로그를 취함** | `log(0.5) = -0.69`. **0과 1 사이 확률이면 로그는 항상 음수다** |

책이 "마지막이 제일 자주 봤다"고 적은 게 로그다. 확률의 **곱**을 최대화하는 문제를 로그의 **합**을 최소화하는 최단 경로로 바꾸는 건 표준 기법인데, `log p`를 그대로 쓰면 전 엣지가 음수가 된다. 더 무서운 건 이 코드가 **처음엔 잘 돌았을 수도 있다**는 점이다. 확률 모델을 갈아끼우거나 스무딩을 바꿔서 값 분포가 이동하는 순간 버그가 활성화된다. 그때 배포된 건 알고리즘이 아니라 **데이터**라서 아무도 알고리즘을 의심하지 않는다.

## 5. 실무 방어책

우선순위 순으로 정리한다.

### 5.1 최적성 인증서 검사 (가장 강력, 반드시 넣을 것)

결과가 나온 뒤 **모든 엣지에 대해** 삼각 부등식을 확인한다. `O(E)` 한 번이면 되고, **전체 정답을 수학적으로 보증한다**.

```python
def assert_optimal(dist, edges):
    """dist[v] <= dist[u] + w 가 모든 엣지에서 성립해야 최단 거리다."""
    for u, v, w in edges:
        du, dv = dist.get(u, float("inf")), dist.get(v, float("inf"))
        if du + w < dv:
            raise AssertionError(f"최적성 위반: {u}→{v}(w={w})  {du}+{w} < {dv}")
```

예제에 적용하면 C→D에서 `-3 + 1 = -2 < 2` → **즉시 걸린다**. 참조 구현도, 정답 데이터도, 큰 테스트 그래프도 필요 없다. 부분 오답을 **정확히 그 지점에서** 잡아내는 유일한 저비용 수단이다.

### 5.2 입력 게이트를 알고리즘 진입부에 둔다

```python
def dijkstra(edges, start):
    if any(w < 0 for _, _, w in edges):
        raise ValueError("다익스트라에 음수 가중치. 벨만-포드나 존슨 재가중을 쓸 것")
    ...
```

"문서에 적힌 전제"를 **실행되는 계약**으로 바꾸는 것. 데이터가 바뀌어 음수가 흘러들어온 날 조용히 틀리는 대신 **시끄럽게 죽는다**. 이 버그에 관한 한 크래시가 정답보다 낫다.

### 5.3 애초에 음수가 안 생기게 변환한다

| 상황 | 처방 |
|---|---|
| 확률 곱 최대화 | `log p`가 아니라 **`-log p`** 를 가중치로. 0<p≤1이면 항상 0 이상이고, 합의 최소화가 곱의 최대화와 동치다 |
| 할인/환급 | 비용에서 빼지 말고 **상한에서 뺀 값**(offset)으로 이동시켜 전 구간을 0 이상으로 |
| `1 - 거리` 유사도 | 거리를 먼저 정규화하거나 `max(0, 1-d)`로 클램프. 단, 클램프는 정보 손실이므로 정규화가 우선 |

이게 근본 해결이다. 알고리즘을 바꾸는 것보다 **문제 표현을 고치는 쪽**이 항상 싸다.

### 5.4 음수가 불가피하면 알고리즘을 바꾼다

- **벨만-포드** — `O(V·E)`. 느리지만 음수를 정확히 처리하고, 예제처럼 **음수 사이클 검출**까지 해 준다. 사이클이 있으면 최단 경로 자체가 정의되지 않으므로 이 검출은 필수다.
- **존슨(Johnson) 재가중** — 벨만-포드로 포텐셜 `h`를 한 번 구한 뒤 `w'(u,v) = w + h(u) - h(v)`로 모든 가중치를 0 이상으로 옮기고 다익스트라를 돌린다. 전쌍 최단 경로에서 다익스트라의 속도를 유지하는 표준 처방.
- 그래프 DB/라이브러리 대부분(Neo4j GDS 등)도 **음수 가중치는 미지원 또는 동작 미정의**로 문서화되어 있다. 라이브러리를 쓴다고 안전한 게 아니다.

### 5.5 테스트를 이 버그가 보이는 모양으로 설계한다

- **하류를 포함시킨다.** 음수 엣지의 도착점에서 최소 1홉 이상 더 나가는 노드를 반드시 검증 대상에 넣는다. C만 보지 말고 D를 봐라.
- **참조 구현과 대조한다.** 작은 무작위 그래프 수백 개에 대해 벨만-포드와 결과를 비교하는 property 테스트. 기준선은 **다른 알고리즘**이어야지, 어제의 자기 출력이면 안 된다.
- **회귀 테스트 기대값을 손으로 계산한다.** 스냅샷으로 자동 생성하지 않는다(4.5 참조).
- **거리뿐 아니라 경로도 비교한다.** 값이 우연히 같아도 경로가 다르면 신호다.
- 운영이라면 **샤도우 검증**: 샘플 트래픽에 대해 벨만-포드를 비동기로 돌려 불일치율을 지표로 뽑는다. 불일치율은 0이어야 하고, 0이 아니면 즉시 알람.

## 6. 한 걸음 뒤에서 — 이 버그가 주는 일반 교훈

이 사례가 9장에 실린 이유는 다익스트라 얘기를 하려는 게 아니라, **버그의 시끄러움과 위험도가 반비례한다**는 걸 보여주기 위해서다.

| | 전부 틀리는 버그 | 부분만 틀리는 버그 |
|---|---|---|
| 발견 시점 | 첫 실행 | 몇 달 뒤, 또는 영영 |
| 발견 경로 | 예외 스택트레이스 | 사용자 신고 → 원인 특정 실패 |
| 신뢰도에 주는 손상 | 작음 | 큼 (그동안 나간 결과 전부가 의심 대상) |
| 필요한 방어 | 없음 (알아서 드러남) | **불변식 검사를 명시적으로 심어야 함** |

전제 조건이 있는 알고리즘(다익스트라의 비음수, 이진 탐색의 정렬, 유니온-파인드의 경로 압축 순서 등)을 쓸 때는, 그 전제를 **주석이 아니라 실행되는 검사로** 남겨야 한다. 그리고 가능하면 **출력에 대한 사후 검증**(5.1의 인증서)을 붙인다. 전제를 지켰는지 확인하는 것보다 답이 맞았는지 확인하는 게 더 확실하다.

## 7. 암기 포인트

- **틀리는 방식**: C(음수 엣지의 도착점)는 맞고 D(그 하류)만 틀린다 → **부분 오답**
- **왜 C는 맞나**: 거리표는 `-3`으로 갱신됐지만 C가 `done`이라 **재확장되지 않아 전파가 끊긴다**
- **왜 안 걸리나**: 예외 없음 + 시작점 근처는 정답 + 반환 경로는 실제로 유효 + 값이 유한
- **깨진 불변식**: "꺼낸 최솟값은 확정" — 이건 가중치가 0 이상일 때만 참
- **음수 유입 경로**: 할인, `1-거리` 유사도, **로그 확률**(가장 흔함)
- **최고의 방어책**: 모든 엣지에 대한 `dist[v] <= dist[u] + w` 검사 (`O(E)`, 전체 정답 보증)
- **근본 처방**: `log p` 대신 **`-log p`**, 또는 벨만-포드 / 존슨 재가중
