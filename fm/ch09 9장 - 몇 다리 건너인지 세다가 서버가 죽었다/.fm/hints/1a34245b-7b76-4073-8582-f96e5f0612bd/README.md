# `_join()` 함수는 무엇을 하는가?

> **답**: 만난 노드에서 정방향 부모를 거슬러 올라간 왼쪽 경로와, 역방향 부모를 따라간 오른쪽 경로를 이어 전체 경로를 만든다.

---

## 1. 어디에 쓰이는 함수인가

9장 예제 `code/ex2_bidirectional.py`의 양방향 탐색(bidirectional search)에서 쓰인다.

양방향 탐색은 출발지 `s`에서 앞으로 걸어오는 BFS와, 도착지 `t`에서 뒤로 걸어오는 BFS를 번갈아 한 레벨씩 돌린다. 두 탐색이 어느 노드에서 **만나면(meet)** 거기서 멈추는데, 이때 손에 남는 건 완성된 경로가 아니라 **부모 맵 두 개**뿐이다.

```python
fwd, bwd = {s: None}, {t: None}   # 각각의 BFS 트리(부모 포인터)
...
seen[v] = u
if v in other:                     # 반대편 탐색이 이미 밟은 노드다 = 만났다
    return _join(v, fwd, bwd), len(fwd) + len(bwd)
```

`_join()`은 이 부모 맵 두 개를 실제 노드 나열(`[s, ..., t]`)로 되살리는 **경로 복원(path reconstruction)** 함수다. 탐색 알고리즘 자체가 아니라, 탐색이 남긴 흔적을 사람이 읽을 수 있는 답으로 바꾸는 뒤처리다.

## 2. 코드

```python
def _join(meet, fwd, bwd):
    left = [meet]
    while fwd[left[-1]] is not None:      # ① meet → s 방향으로 거슬러 올라감
        left.append(fwd[left[-1]])
    right = []
    cur = bwd[meet]                       # ② meet 자신은 건너뛰고 시작
    while cur is not None:                # ③ meet 다음 노드 → t 방향으로 따라감
        right.append(cur)
        cur = bwd[cur]
    return list(reversed(left)) + right   # ④ 왼쪽만 뒤집어서 이어 붙임
```

## 3. 단계별 동작

`s = A`, `t = F`, 실제 경로가 `A-B-C-D-E-F`이고 `C`에서 만났다고 하자. 만난 시점의 두 맵은 이렇다.

```
fwd = {A: None, B: A, C: B}          # 값 = "s 쪽으로 한 칸 앞"
bwd = {F: None, E: F, D: E, C: D}    # 값 = "t 쪽으로 한 칸 뒤"
```

### ① 왼쪽 절반 — 정방향 부모를 거슬러 올라간다

`meet`에서 시작해 `fwd[...]`를 계속 따라가면 출발지 `s`에 도달한다. `fwd[s] is None`이 종료 조건이다.

```
left = [C]  →  [C, B]  →  [C, B, A]     # fwd[A] is None 이므로 정지
```

이 리스트는 **`meet` → `s`** 방향, 즉 우리가 원하는 것의 **역순**이다.

### ② 만난 노드 중복 제거

오른쪽 절반은 `cur = bwd[meet]`, 즉 **`meet`의 한 칸 뒤부터** 시작한다. `meet`는 이미 `left`의 첫 원소로 들어가 있기 때문이다.

만약 `right = [meet]`로 시작했다면 결과가 `[A, B, C, C, D, E, F]`가 되어 `C`가 두 번 나오고, 경로 길이(`len(path) - 1`)도 1만큼 부풀려진다. **양쪽 반이 공유하는 유일한 노드가 `meet`이고, 그 소유권을 왼쪽에 준다** — 이게 이 함수에서 가장 놓치기 쉬운 한 줄이다.

### ③ 오른쪽 절반 — 역방향 부모를 따라간다

```
cur = bwd[C] = D  →  right = [D]
cur = bwd[D] = E  →  right = [D, E]
cur = bwd[E] = F  →  right = [D, E, F]
cur = bwd[F] = None → 정지
```

`bwd[F] is None`(도착지)이 종료 조건이다.

### ④ 왼쪽만 뒤집는 이유 — 부모 포인터의 방향이 서로 반대다

여기가 이 함수의 핵심이자 함정이다. 두 맵은 **같은 자료구조지만 반대 의미**를 담고 있다.

| 맵 | 뿌리 | `map[x]`의 뜻 | `meet`에서 따라가면 | 원하는 순서인가 |
|---|---|---|---|---|
| `fwd` | `s` | `x`의 **s 쪽** 이웃 | `meet → s` | 아니오 → `reversed` 필요 |
| `bwd` | `t` | `x`의 **t 쪽** 이웃 | `meet → t` | 예 → 그대로 사용 |

그래서 `list(reversed(left)) + right`처럼 **한쪽만** 뒤집는다. 습관적으로 양쪽 다 `reversed`를 걸면 오른쪽이 `[F, E, D]`가 되어 `[A, B, C, F, E, D]` 같은, 인접하지도 않은 노드가 나열된 경로가 나온다. 더 나쁜 건 이게 예외를 던지지 않는다는 점이다 — 길이도 그럴듯하고 노드 집합도 맞아서, 엣지 존재 여부를 검증하지 않으면 조용히 통과한다.

같은 파일의 단방향 `bfs_path()`와 비교해 보면 대비가 뚜렷하다. 거기는 부모 맵이 하나뿐이라 `list(reversed(path))` 한 번으로 끝난다.

```
        ← fwd 부모를 거슬러 올라감          bwd 부모를 따라감 →
   A ─── B ─── C ═══ meet ═══ D ─── E ─── F
   s                                        t
   └──── reversed(left) ────┘└─ right ─┘
                            (meet는 왼쪽 소유)
```

### 최종 결과

```
list(reversed([C, B, A])) + [D, E, F]
= [A, B, C] + [D, E, F]
= [A, B, C, D, E, F]
```

## 4. 왜 이런 복원이 필요한가 (양방향 탐색의 맥락)

9장의 요지는 **한 홉마다 11배**다. 단방향 BFS는 반지름 `d`짜리 공 하나를 그리고, 양방향은 반지름 `d/2`짜리 공 두 개를 그린다. 공의 크기가 지수라서 반지름을 절반으로 줄이면 방문 수가 제곱근이 된다(예제 실측 75~88배 절감).

그 대가로 얻는 게 **반쪽짜리 답 두 개**다. 탐색이 중간에서 만나 끝나기 때문에 `s`에서 `t`까지의 완성된 경로를 그 자리에서 손에 쥘 수 없다. `_join()`은 이 구조적 대가를 치르는 함수다. 양방향 탐색을 직접 구현할 때 버그가 가장 자주 나는 곳도 알고리즘 본체가 아니라 이 복원부다.

## 5. 경계 조건과 함정

**`meet == s`인 경우** — `left = [s]`(`fwd[s] is None`이라 즉시 정지), `right`는 `bwd[s]`부터 `t`까지. 결과는 `[s, ..., t]`로 정상이다.

**`meet == t`인 경우** — `right`는 `bwd[t] is None`이라 빈 리스트가 되고, 결과는 `reversed(left)` 그대로 `[s, ..., t]`. 정상이다. (단, `s == t`는 `bidi_path()` 진입부에서 미리 걸러진다.)

**`meet`는 반드시 두 맵 모두에 있어야 한다** — `bidi_path()`는 정방향 확장 중이든 역방향 확장 중이든 똑같이 `_join(v, fwd, bwd)`를 호출한다. 인자 순서를 방향에 따라 바꾸지 않는다. 이게 성립하는 이유는 만남 조건이 `seen[v] = u` **직후**의 `if v in other`이기 때문이다. 즉 이 시점에 `v`는 방금 자기 쪽 맵에 기록됐고 반대쪽 맵에는 이미 있었다. 어느 쪽에서 발견했든 `fwd[v]`와 `bwd[v]`가 둘 다 존재하는 것이 보장된다. 만약 `seen[v] = u`보다 **먼저** 만남을 검사했다면 `fwd[meet]` 또는 `bwd[meet]`에서 `KeyError`가 난다.

**무방향 그래프라서 성립한다** — `graph.py`의 `make()`는 `adj[a].append(b)`와 `adj[b].append(a)`를 함께 넣어 무방향 인접 리스트를 만든다. 그래서 역방향 BFS도 같은 `adj`를 그대로 쓸 수 있다. **유방향 그래프에서는 역방향 BFS가 역인접 리스트(in-edges)를 따라가야 한다.** 이걸 안 고치고 같은 `adj`를 쓰면 `_join()`은 아무 불평 없이 경로를 내놓지만, 오른쪽 절반의 엣지들이 실제로는 반대 방향이라 존재하지 않는 경로가 된다. 앞서 말한 "조용히 틀리는" 실패다.

**이 구현에서는 첫 만남이 곧 최단이다** — "양방향 탐색은 만나자마자 멈추면 최단이 아닐 수 있으니 레벨을 끝까지 돌려 만남 후보 중 최솟값을 골라야 한다"는 경고를 흔히 보는데, `bidi_path()`에는 해당하지 않는다. `_join()`이 돌려주는 경로는 항상 최단이다.

성립하는 이유는 `for _ in range(len(q))`가 **큐 길이를 스냅숏으로 떠서 한 층을 통째로** 확장하기 때문이다. 덕분에 "`fwd`는 깊이 `i`까지 빠짐없이 채워져 있다"는 불변식이 유지되고, 다음이 따라온다.

- 반복 `k`의 **정방향** 단계 진입 시점에 `fwd`는 깊이 `≤ k`, `bwd`는 깊이 `≤ k`가 완전하다. 여기서 만나면 경로 길이는 `(k+1) + db(v) ≤ 2k+1`.
- 이어지는 **역방향** 단계에서는 `fwd`가 깊이 `≤ k+1`까지 차 있으므로 만남 길이는 `(k+1) + df(v) ≤ 2k+2`.
- 실제 최단 거리를 `D`라 하면, **`D = 2m`**(중간 노드 `w`, `df(w) = db(w) = m`)일 때 위 상한상 반복 `m-1`의 역방향 단계 이전에는 만남이 물리적으로 불가능하고, 그 단계에서 `w`가 `bwd`에 들어가는 순간 `w ∈ fwd`가 이미 참이라 반드시 검출된다. **`D = 2m+1`**(중간 엣지)이면 같은 논리로 반복 `m`의 정방향 단계가 처음이자 확실한 검출 지점이다.
- 그 단계에서 잡히는 **모든** 만남 후보는 상한이 `D`이고 실제 경로이므로 `≥ D`, 따라서 정확히 `D`다. 같은 층 안에서 어느 것을 먼저 잡든 길이가 같다.

실제로 확인도 해 봤다. 무작위 소형 그래프 300개에 대해 쌍 4,224건(`bidi_path` 결과 vs 단방향 BFS 최단 거리)과 예제의 20만 노드 그래프에서 무작위 200쌍을 비교했고, 경로 유효성(인접 엣지 존재·노드 중복 없음)까지 포함해 **불일치 0건**이었다.

그럼 그 경고는 언제 참인가. 전제 세 가지 — **무방향·비가중·층 단위 교대** — 중 하나라도 깨질 때다.

| 조건 | 첫 만남 = 최단? | 필요한 조치 |
|---|---|---|
| 무방향 · 비가중 · 층 단위 교대 (이 구현) | 예 | 없음. 즉시 `return`해도 된다 |
| 층을 끝내지 않는 **노드 단위 교대** (한 번에 한 노드씩 pop) | 아니오 | "깊이 `i`까지 완전" 불변식이 깨진다. 만남 후보를 모아 최솟값 선택 |
| **가중 그래프**(양방향 다익스트라) | 아니오 | 최선값 `μ`를 갱신하며 `top_f + top_b ≥ μ` 같은 정지 조건까지 계속 |
| 프런티어 크기 기준 교대(작은 쪽 먼저) | **층을 끝까지 확장하면 예** | 층을 쪼개 확장할 때만 위 조치 필요 |

즉 위험한 건 "빨리 멈추는 것" 자체가 아니라 **층의 완전성을 깨는 것**이다. 이 예제는 층을 깨지 않는다.

**양방향 탐색은 도착지를 알아야 쓸 수 있다** — 예제가 직접 못 박은 조건이다. "이 사람과 3다리 안에 있는 사람 전부" 같은 질의는 `t`가 없으므로 양방향으로 풀 수 없고, 따라서 `_join()`이 등장할 자리도 없다.

## 6. 한 줄 정리

`_join(meet, fwd, bwd)`는 양방향 BFS가 만난 지점에서, **정방향 부모 체인을 거슬러 올라 뒤집은 `[s..meet]`** 과 **역방향 부모 체인을 그대로 따라간 `[meet 다음..t]`** 를 이어 붙여 `s`부터 `t`까지의 전체 경로를 복원한다. 중복 제거는 오른쪽을 `bwd[meet]`부터 시작해서, 순서 정합은 왼쪽만 뒤집어서 해결한다.
