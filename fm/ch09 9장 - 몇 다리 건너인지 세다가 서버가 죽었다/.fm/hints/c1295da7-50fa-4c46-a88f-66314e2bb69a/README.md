# 층 단위 실행과 의존 단위 실행의 트레이드오프는 무엇인가

**답:** 층 단위는 구현이 쉽고, 의존 단위는 빠르다. 층 단위는 배리어 한 줄이면 끝나고 결정론적이지만 층마다 제일 느린 작업을 기다린다. 의존 단위는 임계 경로까지 내려가지만 진입 차수 카운터, 완료 이벤트, 워커 풀, 우선순위 정책을 직접 들고 있어야 한다. **19장에서 다시 다룬다.**

---

## 1. 두 방식이 무엇인가

`ex5_toposort.py`의 마지막 출력이 이 카드의 원문이다.

> 슈퍼스텝 실행이 임계 경로보다 느릴 수 있다는 게 요점이다.
> 같은 층의 제일 느린 작업을 기다리기 때문이다.
> 층 단위로 기다리지 않고 «의존이 풀리는 대로» 시작하면 임계 경로까지 내려간다.
>
> 2장의 오케스트레이터가 실제로 고르는 지점이 이거다.
> 층 단위는 구현이 쉽고, 의존 단위는 빠르다. 19장에서 다시 본다.

같은 DAG, 같은 위상 정렬 결과를 놓고 **실행 스케줄만** 다르게 뽑는 두 방식이다.

| | 층 단위 (슈퍼스텝 / BSP) | 의존 단위 (이벤트 기반 / 리스트 스케줄링) |
|---|---|---|
| 시작 조건 | **이전 층 전체**가 끝남 | **내 선행 작업들**이 끝남 |
| 동기화 지점 | 층 경계마다 전역 배리어 | 없음 (작업별 완료 이벤트) |
| 완료 시각 | $\sum_{\text{층}} \max(\text{층 안 비용})$ | 임계 경로 길이 (워커 무한 시) |
| 상태 | 「지금 몇 층인가」 정수 하나 | 진입 차수 표 + 준비 큐 + 실행 중 집합 |

## 2. 예제 숫자로 확인하기

`ex5_toposort.py`의 `TASKS`와 `cost`를 그대로 쓴다.

```
외부 API 예열(40)   데이터 적재(20)
                        ├── 스키마 검증(5)  ─┐
                        └── 엔티티 병합(30) ─┴── 관계 추출(15) ─┬── 품질 검사(8) ─┐
                                                                └── 색인 생성(25) ┤
외부 API 예열 ────────────────────────────────────────────────────────────────────┴── 배포(3)
```

`supersteps()`가 만드는 층은 5개다.

| 층 | 작업 | 층 소요 (= 층 안 최댓값) |
|---|---|---:|
| 1차 | 데이터 적재(20), 외부 API 예열(40) | **40** |
| 2차 | 스키마 검증(5), 엔티티 병합(30) | **30** |
| 3차 | 관계 추출(15) | **15** |
| 4차 | 색인 생성(25), 품질 검사(8) | **25** |
| 5차 | 배포(3) | **3** |

- 순차 실행: 40+20+5+30+15+8+25+3 = **146분**
- 층 단위 실행: 40+30+15+25+3 = **113분** (1.3배 단축)
- 임계 경로: 데이터 적재 → 엔티티 병합 → 관계 추출 → 색인 생성 → 배포 = 20+30+15+25+3 = **93분**

**113 vs 93. 20분이 어디로 샜는가.** 1차 층에서 「데이터 적재」는 20분에 끝나는데, 옆에서 도는 「외부 API 예열」이 40분이라 배리어 앞에서 20분을 서 있는다. 그 20분이 그대로 자손 전체에 밀린다. 손실이 정확히 20분인 게 우연이 아니다 — 「외부 API 예열」은 배포 직전까지 아무도 기다리지 않는 작업인데, 층 구조가 억지로 앞줄에 세워 놓은 것이다.

의존 단위로 돌리면 20분 시점에 「엔티티 병합」이 바로 출발하고, 「외부 API 예열」은 자기 페이스로 40분에 끝나서 93분의 배포에 여유 있게 도착한다. 이게 **여유 시간(slack)**이다. 층 단위는 slack을 못 쓴다.

### 층 단위가 최악이 되는 경우

층 하나에 「1초짜리 999개 + 1시간짜리 1개」가 같이 들어가면 그 층은 1시간이다. 층 수가 $L$, 층당 최대 지연이 $\Delta$면 최대 손실은 $O(L \cdot \Delta)$까지 쌓인다. 반대로 **층 안의 비용이 균일하면 두 방식의 차이는 0**이다. 층 단위가 나쁜 게 아니라, **비용 분산이 큰 층**이 나쁘다.

## 3. 구현 복잡도 — 배리어 한 줄 대 상태 기계

### 3.1 층 단위: 이게 전부다

```python
for layer in supersteps(TASKS):          # 위상 정렬 결과
    with ThreadPoolExecutor(K) as pool:  # 또는 pool.map / joblib / xargs -P
        list(pool.map(run, layer))       # ← 이 한 줄이 배리어다
```

`pool.map`이 반환되는 순간이 곧 전역 배리어다. 동기화 코드를 **한 줄도 쓰지 않는다**. 심지어 셸로도 된다.

```bash
for layer in 1 2 3 4 5; do
  xargs -P 8 -n 1 ./run.sh < layer_$i.txt   # 층이 끝나야 다음 루프
done
```

- 경합 조건이 구조적으로 없다. 층 안 작업끼리는 의존이 없다는 게 위상 정렬의 보장이므로 공유 상태를 안 건드리면 레이스가 안 난다.
- 층 경계가 **자연스러운 일관성 지점**이다. 여기서 스냅샷을 찍으면 「모든 작업이 어중간하지 않은」 상태가 나온다.

### 3.2 의존 단위: 최소한 이 정도는 있어야 한다

```python
indeg   = {t: len(d) for t, d in TASKS.items()}   # 진입 차수 카운터
child   = 역방향 인접 리스트                        # 완료 시 누구를 깨울지
ready   = 우선순위 큐(t for t in indeg if indeg[t] == 0)
running = set()
done_q  = Queue()                                  # 완료 이벤트 채널
lock    = Lock()                                   # indeg 감산 보호

while ready or running:
    while ready and len(running) < K:              # 워커 풀 상한
        t = ready.pop()                            # ← 어느 걸 먼저? = 정책
        running.add(t); pool.submit(run, t, done_q)

    t = done_q.get()                               # 블로킹 대기
    with lock:
        running.discard(t)
        for c in child[t]:
            indeg[c] -= 1                          # ← 원자성 필요
            if indeg[c] == 0:
                ready.push(c)
```

층 단위 대비 새로 생긴 것들:

1. **진입 차수 카운터의 원자적 감산.** 두 선행 작업이 동시에 끝나면 `indeg[c] -= 1`이 겹친다. 잃어버린 갱신이 나면 자식이 **영원히 안 깨어난다**. 잠금을 잘못 걸면 반대로 자식이 **두 번 실행된다**. 분산 환경이면 이 카운터를 어디에 둘지(Redis? DB 행 잠금? 컨센서스?)가 곧 아키텍처 결정이다.
2. **완료 이벤트 채널.** 작업이 죽거나, 노드가 사라지거나, 이벤트가 유실되면 스케줄러는 그냥 멈춰 선다. 그래서 실전에서는 이벤트 대신/에 더해 **주기적 재조정 루프(reconcile)**를 돌린다 — 「진입 차수 0인데 안 도는 애 있나」를 되묻는 것이다.
3. **워커 풀 상한과 선택 정책.** `ready`에서 어느 걸 먼저 꺼내는가. 여기서 성능이 갈린다(4절).
4. **종료 판정.** 층 단위는 층 리스트를 다 돌면 끝. 의존 단위는 `ready`와 `running`이 **동시에** 비어야 끝이다. 이 조건을 잘못 쓰면 조용히 조기 종료하거나 영원히 안 끝난다.

한 줄 요약: **층 단위는 배리어에 동기화를 아웃소싱하고, 의존 단위는 동기화를 직접 소유한다.**

## 4. 자원 상한이 있을 때 — 여기서 얘기가 뒤집힌다

워커가 무한하다는 가정은 실무에 없다. 워커 $K$개일 때를 보자.

**$K = 1$이면 두 방식은 완전히 같다.** 둘 다 146분. 차이는 0이다.

**$K = \infty$면 113분 대 93분.** 위에서 본 그대로.

**중간이 재밌다.** $K = 2$로 의존 단위를 돌려 보면:

| 시각 | 워커 A | 워커 B |
|---|---|---|
| 0–20 | 데이터 적재 | 외부 API 예열 |
| 20–50 | **엔티티 병합** | (계속 40까지) |
| 40–45 | | 스키마 검증 |
| 50–65 | 관계 추출 | |
| 65–90 | 색인 생성 | 품질 검사(65–73) |
| 90–93 | 배포 | |

**93분. 워커 2개로 임계 경로를 달성했다.** 층 단위는 같은 $K=2$에서 여전히 113분이다.

그런데 20분 시점에 「스키마 검증(5)」을 먼저 골랐다면?

```
20–25 스키마 검증 → 25–55 엔티티 병합 → 55–70 관계 추출 → 70–95 색인 생성 → 95–98 배포
```

**98분.** 5분 손해다. 즉 의존 단위는 **선택 정책이 성능의 일부**다. 대표적으로:

- **HLF / 임계 경로 우선**: `critical_path()`가 계산하는 「나부터 끝까지 남은 최장 길이」가 큰 순으로 꺼낸다. 위 표에서 엔티티 병합(50) > 스키마 검증(25)이라 올바른 선택이 나온다.
- **최장 작업 우선(LPT)**: 비용만 보고 큰 것부터. 간단하고 대체로 나쁘지 않다.
- **아무거나(FIFO)**: 목록 스케줄링의 최악 보장은 Graham 경계로 최적 대비 $2 - 1/K$배 안쪽이다. 즉 아무 정책이나 써도 2배는 안 넘는다 — **이게 의존 단위를 실용적으로 만드는 정리**다.

층 단위는 이 정책을 **쓸 수가 없다**. 어차피 층 전체를 기다릴 거라 순서가 무의미하기 때문이다. 대신 층 단위에도 자원 상한 특유의 병리가 있다: **층 크기가 $K$보다 크면 그 층이 여러 배치로 쪼개지고, 마지막 배치는 워커가 텅 빈 채로 돈다.** 999개짜리 층을 $K=8$로 돌리면 125번째 배치는 7개가 놀고 있다. 이 「꼬리」가 층마다 생긴다.

정리하면 자원이 빡빡할수록 **층 단위의 손해는 두 겹**이다 — 층 안 최대 비용 대기 + 배치 꼬리 낭비.

## 5. 디버깅·재시도·관측

이 절이 층 단위가 살아남는 진짜 이유다. 성능만 보면 의존 단위가 이겼는데 현장에는 층 단위가 널려 있다.

### 5.1 재현성

- **층 단위**: 실행 순서가 결정론적이다. 층 $i$의 결과는 층 $i-1$까지의 결과에만 의존한다. 같은 입력이면 같은 출력이고, **버그가 재현된다**.
- **의존 단위**: 인터리빙이 매 실행마다 다르다. 「어제는 됐는데 오늘 안 되는」 부류의 버그가 여기서 나온다. 숨어 있던 미선언 의존(작업 A가 사실은 B의 부산물을 읽고 있었다)이 층 단위에서는 우연히 항상 통과하다가, 의존 단위로 바꾼 첫날 터진다. 이건 의존 단위의 결함이 아니라 **DAG 선언이 틀렸다는 사실을 드러내는 것**이지만, 드러나는 시점이 하필 마이그레이션 직후라 원인 지목이 어렵다.

### 5.2 재시도

- **층 단위**: 실패하면 **층 단위로 되감으면 된다**. 「3차 층부터 다시」가 의미 있는 문장이다. 층 경계에 체크포인트를 두면 복구 지점이 자명하다.
- **의존 단위**: 실패한 작업의 **하위 트리만** 골라 재실행해야 한다(그게 이점이기도 하다 — 낭비가 적다). 대신 복구 지점을 계산하려면 어디까지 성공했는지를 작업별로 영속화해야 하고, 부분 실패 상태에서 진입 차수 표를 어떻게 복원할지가 문제가 된다. **작업 결과가 멱등하지 않으면** 재시도가 곧 이중 실행이다.

### 5.3 관측

- **층 단위**: 진행률이 「$i$ / $L$ 층」 정수 하나다. 어느 층이 병목인지 로그만 봐도 안다(`ex5_toposort.py`가 층마다 `span`을 찍는 이유). 대시보드가 5줄이다.
- **의존 단위**: 진행률은 「완료 $m$ / 전체 $n$」인데, 남은 시간은 개수가 아니라 **남은 임계 경로 길이**로 봐야 한다. 개수 기반 진행률은 90%에서 30분 멈춰 있는다. 「지금 왜 워커가 놀고 있나」에 답하려면 `ready`가 빈 이유 — 어느 작업이 blocking인지 — 를 추적하는 별도 계측이 필요하다.

### 5.4 낙수 지연(straggler)

층 단위의 고질병이다. 층 안 한 놈이 느리면 전원 대기. 완화책은 두 갈래인데 둘 다 공짜가 아니다.

- **투기적 실행(speculative execution)**: 느린 복제본을 다른 노드에서 하나 더 돌리고 먼저 끝난 걸 쓴다. Spark, MapReduce가 쓴다. 자원을 두 배 쓰고, 작업이 멱등해야 한다.
- **층 쪼개기/합치기**: 비용 분산이 큰 층을 손으로 나눈다. 결국 의존 단위로 한 걸음 가는 것이다.

## 6. 실제 시스템은 어느 쪽인가

이 트레이드오프는 이름만 바꿔 가며 여기저기에 나온다. **같은 제품 안에 두 모드가 다 있는 경우**가 특히 교훈적이다.

### 6.1 층 단위 쪽

| 시스템 | 층에 해당하는 것 | 배리어 |
|---|---|---|
| **Pregel / Giraph / Spark GraphX** | 슈퍼스텝 | 슈퍼스텝 끝 전역 배리어. 이번 스텝에서 보낸 메시지는 **다음 스텝**에 도착한다 |
| **Spark 스테이지** | 셔플 경계로 잘린 스테이지 | 스테이지의 모든 태스크가 끝나야 다음 스테이지 시작 |
| **MapReduce** | map 단계 / reduce 단계 | map 전부 끝나야 reduce 시작 |
| **Kubernetes Job (`completions`/`parallelism`)** | Job 하나 | Job 하나가 Complete 돼야 다음 단계를 사람이/컨트롤러가 건다. **Job 자체에는 DAG 개념이 없다** |
| **GitLab CI `stages`** | build → test → deploy | 스테이지 전원 통과해야 다음 스테이지 |
| **Argo Workflows `steps:`** | 스텝 목록 (안쪽 리스트는 병렬) | 스텝 그룹 경계 |

BSP의 배리어는 **성능을 포기하고 산 것**이다. 대가로 얻는 게 명확하다: 메시지 전달 결정론, 슈퍼스텝 경계 체크포인팅, 「지금 몇 번째 스텝」이라는 단일 전역 시계. Pregel 논문이 비동기 대신 BSP를 고른 이유가 정확히 이거다.

### 6.2 의존 단위 쪽

| 시스템 | 트리거 | 비고 |
|---|---|---|
| **Airflow** | upstream 태스크가 성공하면 downstream이 `scheduled` | 진입 차수 대신 `TriggerRule`(all_success/one_success/all_done…)을 태스크마다 설정 |
| **Argo Workflows `dag:`** | `dependencies:` 만족 시 | 같은 제품이 `steps:`(층)와 `dag:`(의존)를 **둘 다** 제공한다 |
| **GitLab CI `needs:`** | 스테이지 무시하고 지정 잡만 기다림 | 문서가 이 기능을 대놓고 "Directed Acyclic Graphs"라 부른다. 스테이지 모델의 대기 낭비를 없애려고 나중에 추가된 기능 |
| **GitHub Actions `needs:`** | 지정 잡 완료 시 | 처음부터 DAG 모델 |
| **`make -j`, Bazel, Ninja** | 파일 의존이 최신이면 | 빌드 시스템은 대부분 처음부터 의존 단위다. 40년 된 아이디어 |
| **Tekton `runAfter`** | 지정 태스크 완료 시 | |
| **비동기 그래프 엔진** (PowerGraph/GraphLab async, GRAPE 등) | 이웃 갱신 시 | 배리어를 없애 낙수 지연을 지우지만, 수렴 판정과 재현성을 잃는다 |

**GitLab의 `stages` → `needs` 진화**가 이 카드의 실물 증거다. 처음엔 스테이지(층 단위)로 만들었고 — 구현이 쉬우니까 — 파이프라인이 커지자 「왜 내 빠른 잡이 남의 느린 잡을 기다리나」가 문제가 됐고, DAG 모드를 얹었다. Argo도 같은 이유로 두 문법을 병행한다.

**Kubernetes 쪽 대비**도 깔끔하다. `Job`은 층 단위 원시 자원이다 — 「이 작업 $n$개를 $p$개씩 병렬로, 다 끝나면 Complete」. DAG가 필요하면 Argo/Tekton/Kubeflow 같은 걸 **위에 얹는다**. 즉 플랫폼은 배리어까지만 주고, 의존 단위 스케줄링은 별도 컨트롤러의 일이라고 선을 그은 것이다. 그 컨트롤러들이 하는 일이 정확히 3.2절의 코드 — 진입 차수 카운터를 etcd에 두고, 완료 이벤트를 watch로 받고, 놓칠 걸 대비해 reconcile 루프를 돌린다.

## 7. 그래서 어느 쪽을 고르나

층 단위로 충분한 신호:

- 층 안 작업들의 **비용이 비슷하다** (분산이 작다) → 손해가 애초에 없다
- 층 수가 적다 (손해가 $O(L\Delta)$이므로 $L$이 작으면 상한이 작다)
- **재현성·감사 로그·체크포인트**가 성능보다 중요하다
- 작업이 멱등하지 않아 이중 실행이 위험하다
- 팀이 작고, 스케줄러 버그를 감당할 여력이 없다

의존 단위로 가야 하는 신호:

- 층 안에 **극단적으로 느린 작업**이 섞여 있다 (「외부 API 예열 40분」 같은 것)
- `parallel / critical_path` 비가 1.2를 넘는다 → **측정부터 하라**. `ex5_toposort.py`가 두 값을 나란히 찍는 이유가 이 판단을 하라는 것이다
- 작업 수가 많고 워커가 비싸다 (배치 꼬리 낭비가 쌓인다)
- 재시도 비용이 크다 (하위 트리만 재실행하는 이득이 크다)

**중간 지대도 있다.** 층 단위를 유지하되 「층을 지나치게 넓게 잡지 않기」, 「느린 작업을 별도 파이프라인으로 빼기」, 「층 안에서만 투기적 실행 켜기」로 손해의 상당 부분을 회수할 수 있다. 대개는 스케줄러를 다시 쓰는 것보다 싸다.

## 8. 한 줄로 남길 것

**층 단위는 배리어에게 동기화를 맡기고 대기 시간으로 값을 치른다. 의존 단위는 대기 시간을 없애는 대신 진입 차수 카운터·완료 이벤트·재시도·관측을 직접 떠안는다.** 워커가 1개면 차이가 없고, 층 안 비용이 균일해도 차이가 없다. 차이가 나는 건 **층 안 비용 분산이 클 때**뿐이므로, 바꾸기 전에 `층 단위 실행 시간 / 임계 경로`를 재 보는 게 먼저다.

19장에서 이 결정을 오케스트레이터 설계 관점으로 다시 연다.
