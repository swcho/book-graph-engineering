# `graph.py`의 `weighted(allow_negative=True)` — 5% 확률로 음수를 심는 실험 스위치

## 한 줄 답

**엣지를 하나 만들 때마다 가중치를 먼저 1~20에서 뽑고, 5% 확률로 그 값을 −1~−5 사이 음수로 *덮어쓴다*.
9.3절의 "다익스트라는 음수 가중치에서 조용히 틀린다"를 작은 예제(`ex3`)가 아니라 수천 개 엣지 규모에서
직접 재현해 보라고 열어 둔 훅이다.**

## 코드 그대로

`/Users/swcho/projects/swcho/book-graph-engineering/content/ch09/code/graph.py:16-28`

```python
def weighted(n=2_000, avg_deg=8, seed=7, allow_negative=False):
    rnd = random.Random(seed)
    edges = []
    for a in range(n):
        for _ in range(avg_deg // 2):        # 노드마다 4번 뽑는다
            b = rnd.randrange(n)
            if a == b:
                continue                     # 자기 루프는 버린다
            w = rnd.randint(1, 20)           # ① 먼저 양수를 뽑고
            if allow_negative and rnd.random() < 0.05:
                w = -rnd.randint(1, 5)       # ② 5% 추첨에 걸리면 통째로 갈아끼운다
            edges.append((a, b, w))          # ③ 한 방향만 넣는다
    return edges
```

읽을 때 놓치기 쉬운 세 가지가 있다.

| 지점 | 사실 |
|---|---|
| ① → ② | 음수는 양수에서 **빼는 게 아니라 치환**이다. `w = rnd.randint(1,20)`으로 뽑은 값은 버려진다 (다만 난수는 이미 소비됐다). |
| 값의 범위 | 양수는 `1..20`(평균 10.5), 음수는 `-1..-5`(평균 −3). **비대칭이다.** 음수의 절댓값이 양수보다 훨씬 작다. |
| ③ | `edges.append((a, b, w))`가 **한 줄뿐**이다. 반환값은 무향이 아니라 **유향 엣지 리스트**다. 이 한 줄이 이 함수의 설계 전부를 결정한다 (아래 3절). |

### 실측 — 기본 파라미터

`weighted(n=2000, avg_deg=8, seed=7, allow_negative=True)`

```
allow_negative=False : 엣지 7,995개, 음수 0개
allow_negative=True  : 엣지 7,996개, 음수 383개 → 4.79%
```

`avg_deg // 2 = 4`이므로 최대 8,000개, 자기 루프(`a == b`, 기대 1건)와 중복 미제거로 실제 7,99x개다.
383/7996 = 4.79%로 명목 5%에 잘 붙는다. 시드를 바꿔도 4.70 ~ 5.28% 범위다.

## 1. 왜 하필 5%인가

### 1-1. 실측으로 본 확률의 스윗스팟

`n=40, avg_deg=8` 그래프를 시드 200개씩 만들고, 음수 확률 `p`만 바꿔 다익스트라와 벨만-포드를 비교했다
(음수 사이클이 생긴 그래프는 정답 자체가 정의되지 않으므로 제외하고 평균).

| `p` | 200개 중 음수 사이클 발생 | 남은 그래프의 다익스트라 오답률 | 실험 재료로서의 평가 |
|---|---|---|---|
| 0.00 | 0 | 0.00% | 버그가 없다. 볼 게 없다. |
| 0.01 | 5 | 0.43% | 너무 희소하다. 어느 시드는 오답이 0건이라 "잘 되는데?"로 끝난다. |
| **0.05** | **30 (15%)** | **4.07%** | **오답은 확실히 나오고, 85%의 그래프는 여전히 유효한 문제로 남는다.** |
| 0.10 | 106 (53%) | 12.97% | 절반이 음수 사이클. "다익스트라가 틀린다"가 아니라 "문제가 깨졌다"가 된다. |
| 0.20 | 196 (98%) | 26.28% | 사실상 전부 무효. 실험이 성립하지 않는다. |

즉 5%는 **오답을 안정적으로 만들어 내는 하한**과 **그래프를 음수 사이클로 망가뜨리는 상한** 사이에서 고른 값이다.
`p`를 키우면 오답률이 올라가서 좋아 보이지만, 동시에 "다익스트라가 틀린 것"과 "애초에 최단 경로가 없는 것"이
뒤섞여 버려서 원래 보여 주려던 현상이 사라진다.

### 1-2. 희소함 자체가 재현하려는 현상이다

에셋의 `ex3`가 뽑은 결론은 "틀린다"가 아니라 **"조용히 틀린다"**다.

> 예외가 안 난다는 게 이 버그의 성질이다. 답이 그냥 조용히 틀린다.
> 거리표만 찍어 보면 C 가 맞으니 «잘 돌고 있네» 싶다. 틀린 건 그 뒤쪽이다.

5%(+ 음수 크기 −1~−5)라는 설정은 그 "조용함"을 그대로 만들어 낸다.
`weighted(allow_negative=True)`의 기본 그래프에서 노드 0을 시작점으로 실측하면:

```
도달 노드 1,961개 중 다익스트라 오답 458개 = 23.4%
다익스트라가 과대평가한 양: 평균 3.89, 최대 13
벨만-포드 거리 범위: 0 ~ 64
거리가 음수로 나온 노드: 0개
```

- 거리표에 **음수가 하나도 없다.** 눈으로 스캔해도 이상한 값이 안 보인다.
- 오차가 평균 4 남짓이다. 거리 30이 34로 나온다. **"대충 이 정도겠지" 범위 안**이라 리뷰에서 안 걸린다.
- 그런데 넷 중 하나가 틀렸다.

음수 엣지를 20%씩 깔면 거리표에 음수가 튀고 값이 눈에 띄게 이상해져서, 오히려 **버그가 시끄러워진다.**
5%는 "실무에서 할인 정책 하나, `log(0.5)` 한 줄이 섞여 들어간" 상황의 밀도이고, 그게 이 코드가 노린 지점이다.

### 1-3. 조용함의 증거 — 홉별 오답률

같은 실측을 시작점으로부터의 홉 수로 쪼개면 이렇다.

| 홉 | 노드 수 | 오답 | 오답률 |
|---|---|---|---|
| 0~2 | 21 | 0 | **0.0%** |
| 3 | 62 | 10 | 16.1% |
| 4 | 224 | 37 | 16.5% |
| 5 | 616 | 142 | 23.1% |
| 6 | 732 | 187 | 25.5% |
| 7 | 268 | 71 | 26.5% |
| 8+ | 38 | 11 | 28.9% |

**시작점에서 2홉 안쪽은 오답이 한 건도 없다.** 3홉부터 터지기 시작해서 6~8홉에서 26% 근처로 수렴한다.
`ex3`의 "C 는 맞고 D 는 틀렸다", "검증할 때 시작점 근처만 보면 놓친다"가 8천 엣지 규모에서 똑같이 재현된다.
스모크 테스트로 이웃 몇 개만 찍어 보는 검증이 왜 이 버그를 절대 못 잡는지가 이 표다.

## 2. 음수 가중치 × 무방향 = 즉시 음수 사이클

### 2-1. 문제

무방향 엣지 `{u, v}`에 가중치 `w`가 붙어 있다는 말은, 유향으로 풀면 `u→v`와 `v→u`가 **둘 다** `w`라는 뜻이다.
그러면 `w < 0`인 순간

```
u → v → u  =  w + w  =  2w  <  0
```

길이 2짜리 음수 사이클이 **엣지 하나당 하나씩** 즉시 생긴다. 이건 확률 문제가 아니라 정의상 자동이다.
음수 사이클이 있으면 최단 경로 문제 자체가 정의되지 않는다. 사이클을 한 바퀴 더 돌 때마다 거리가 계속 내려가서
하한이 없다. 벨만-포드조차 "정답"을 못 주고 `has_cycle=True`만 보고할 수 있을 뿐이다
(`ex3`의 `bellman_ford`가 마지막에 한 바퀴 더 도는 그 검사다).

그래서 **"음수 가중치 무방향 그래프에서 최단 경로"는 근본적으로 다른 문제**가 된다.
NP-난해한 최소 가중 완전 매칭(T-join)으로 푸는 영역이지, 다익스트라/벨만-포드 이야기가 아니다.

### 2-2. 이 코드가 그걸 어떻게 다루는가 — 표현을 바꿔서 피한다

같은 파일 안의 두 생성 함수를 나란히 놓고 보면 의도가 드러난다.

```python
def make(...):                      # graph.py:5-14   ← ex1, ex2 가 쓴다
    ...
    adj[a].append(b)                # 양방향
    adj[b].append(a)                # 양방향
    return {k: sorted(set(v)) ...}  # 인접 리스트, 가중치 없음, 무방향

def weighted(...):                  # graph.py:16-28
    ...
    edges.append((a, b, w))         # 한 방향뿐
    return edges                    # 엣지 리스트, 가중치 있음, 유향
```

`make()`는 무방향인데 **가중치가 없다**. `weighted()`는 가중치가 있는데 **무방향이 아니다.**
음수 가중치와 무방향이 절대 같은 그래프에서 만나지 않도록 갈라 놓은 것이다.
`weighted()`가 인접 리스트가 아니라 `(a, b, w)` 튜플 리스트를 반환하는 이유도 여기에 있다.
`ex3`의 `bellman_ford(edges, start, nodes)`가 정확히 이 형태를 요구한다.

**만약 `weighted()`가 `make()`처럼 양방향을 넣었다면** 어떻게 되는지 실측했다.
반환된 엣지를 그대로 양방향으로 복제하니:

```
엣지 7,996 → 15,992개
길이 2짜리 음수 사이클: 383개 (음수 엣지 개수와 정확히 일치)
벨만-포드 음수 사이클 탐지: True
예)  (2, 1999, -2)  →  2→1999→2 = -4
```

음수 엣지 383개가 그대로 음수 사이클 383개가 된다. 실험이 시작도 못 하고 끝난다.

### 2-3. 그렇다고 방어하지는 않는다 — 정직하게 말하면 운에 맡긴 부분이 있다

유향으로 만들면 **길이 2짜리 자동 사이클**은 사라진다. 하지만 **더 긴 유향 사이클**은 여전히 우연히 생길 수 있고,
`weighted()`에는 그걸 검사하거나 거부하는 코드가 **한 줄도 없다.**

먼저 왜 대체로 안 생기는지. 사이클 길이 `k`짜리 경로의 기대 가중치는

$$\mathbb{E}[W_k] = k\,\bigl(0.95 \times 10.5 + 0.05 \times (-3)\bigr) \approx 9.83k \;>\; 0$$

이라 **평균적으로는 한참 양수**다. 음수 사이클이 되려면 짧은 사이클에 음수가 몰려야 한다.
실제로 기본 시드에서 상호 엣지쌍(`(a,b)`와 `(b,a)`가 둘 다 있는 경우)은 7개뿐이고, 그중 합이 음수인 건 0개였다.

그런데 시드를 바꾸면 이야기가 달라진다. `n=2000`, 시드 1~15로 전수 검사한 결과:

```
음수 사이클이 생긴 시드: 1, 4, 5, 12, 13  → 5/15 (33%)
```

실제로 찾아낸 사이클은 전부 길이 4~6짜리였다.

| 시드 | 사이클 길이 | 가중치 | 합 |
|---|---|---|---|
| 1 | 4 | −2, 2, 2, −4 | **−2** |
| 4 | 5 | −1, −3, 2, 2, −4 | **−4** |
| 5 | 6 | 1, 2, 5, 1, −5, −5 | **−1** |

**기본값 `seed=7`은 우연히 깨끗한 시드다.** 그래서 시드가 `graph.py:16`에 하드코딩돼 있고 파일 첫 줄 독스트링이
`"시드 고정"`이라고 못을 박아 둔 것이다. 재현성을 위한 고정이기도 하지만, 결과적으로 **음수 사이클이 없는 인스턴스를
고정하는 역할**도 겸한다.

정리하면 이 코드의 음수 사이클 대응은 이렇게 계층적이다.

| 층위 | 수단 | 막는 것 | 남는 위험 |
|---|---|---|---|
| 표현 | 유향 엣지 리스트 (`append` 한 줄) | 길이 2 자동 사이클 383개 | — |
| 확률 | `p=0.05`, 음수 크기 −1~−5 (양수 1~20보다 작음) | 긴 사이클이 음수가 될 확률을 낮게 유지 | 확률적으로 남음 |
| 시드 | `seed=7` 고정 | 남은 확률을 뽑기 전에 결과를 고정 | **다른 시드/`n`을 쓰면 33% 확률로 깨진다** |

직접 파라미터를 바꿔 실험할 생각이라면, `ex3`의 `bellman_ford`가 반환하는 `has_cycle`을
**먼저 확인하고 나서** 다익스트라와 비교해야 한다. 그러지 않으면 "다익스트라가 틀렸다"와
"애초에 답이 없다"를 구분할 수 없다.

## 3. 그래서 `ex3`는 이 함수를 쓰지 않는다

저장소 전체를 뒤져 보면 `weighted`를 호출하는 코드가 **없다.**

```
content/ch09/code/graph.py:16   def weighted(...)      ← 정의
content/ch09/code/ex1_bfs_explosion.py:11   from graph import make
content/ch09/code/ex2_bidirectional.py:12   from graph import make
```

`ex3_dijkstra_negative.py`는 `graph`를 import조차 하지 않고, 엣지 4개를 파일 안에 박아 둔다.

```python
EDGES = [("A", "C", 1), ("A", "B", 2), ("B", "C", -5), ("C", "D", 1)]
```

의도적인 선택이다. 8천 엣지에서 "23.4%가 틀렸다"는 결과는 **현상의 규모**는 보여 주지만
**원인**은 못 보여 준다. 4개짜리 그래프라야 "C를 먼저 확정했고, 나중에 −5를 발견했지만 C는 `done`에 들어가서
다시 안 펼쳤다"는 인과가 손으로 따라가진다.

그러니 `weighted(allow_negative=True)`의 위치는 이렇다.

- `ex3`: **왜** 틀리는가 — 손으로 검산 가능한 최소 반례
- `weighted(allow_negative=True)`: **얼마나** 틀리는가 — 독자가 직접 규모를 키워 확인해 보는 훅

`ex3`의 결론 "실무에서 음수 가중치가 생기는 자리 — 할인/환급, `1 - 거리`, `log 0.5 = -0.69`" 중
마지막이 특히 5%와 맞물린다. 확률 곱을 최단 경로로 바꾸는 기법에서 대부분의 확률은 1에 가까워
`log`가 0 근처 음수이고, **가끔** 확률이 뚝 떨어져 큰 음수가 나온다. 그 "가끔"이 5%다.

## 4. 숨은 함정 — 같은 시드인데 그래프가 달라진다

```python
if allow_negative and rnd.random() < 0.05:
```

파이썬의 `and`는 단락 평가(short-circuit)다. `allow_negative`가 `False`면 **`rnd.random()`이 아예 호출되지 않는다.**
`True`면 엣지마다 난수를 하나 더 소비한다. 결과적으로 두 호출의 난수 스트림이 첫 엣지부터 어긋난다. 실측:

```
weighted(seed=7)                     → 엣지 7,995개
weighted(seed=7, allow_negative=True)→ 엣지 7,996개
(a, b) 쌍 순서가 같은가              → 아니오
가중치까지 같은 엣지                  → 7,995개 중 1개
```

**"같은 그래프에 음수만 얹은 것"이 아니다. 완전히 다른 그래프다.**
따라서 `weighted(seed=7)`와 `weighted(seed=7, allow_negative=True)`의 결과를 나란히 놓고
"음수 때문에 이만큼 달라졌다"고 말하면 틀린다. 양수 가중치도, 엣지 구성도 전부 다르다.

깨끗한 A/B가 필요하면 추첨을 항상 뽑고 사용만 조건부로 하면 된다.

```python
w = rnd.randint(1, 20)
flip = rnd.random()                       # 항상 소비 → 스트림이 어긋나지 않는다
if allow_negative and flip < 0.05:
    w = -rnd.randint(1, 5)                # 다만 이 randint 도 조건부라 여전히 어긋난다
```

엄밀하게 하려면 음수 값도 미리 뽑아 두어야 한다 (`neg = rnd.randint(1, 5)`를 무조건 실행).
이 코드는 통계적 경향만 보면 되는 실험용이라 거기까지 가지 않았다.

| 오해 | 사실 |

| "5%만큼 가중치를 깎는다" | 아니다. 엣지의 5%를 **골라서** 값을 통째로 음수로 바꾼다. 나머지 95%는 그대로 1~20이다. |
| "음수 폭이 양수와 대칭이다" | 아니다. 양수 1~20(평균 10.5), 음수 −1~−5(평균 −3). 음수 쪽이 훨씬 작다. 그래서 거리표에 음수가 안 나온다. |
| "`weighted()`는 무방향 그래프를 만든다" | 아니다. `make()`만 무방향이다. `weighted()`는 `(a, b, w)` 한 방향만 넣는 **유향 엣지 리스트**다. 이게 음수 2-사이클을 막는 장치다. |
| "음수 가중치가 있으면 벨만-포드는 항상 옳다" | 음수 **사이클**이 없을 때만이다. 시드에 따라 이 생성기도 33% 확률로 음수 사이클을 만든다. `has_cycle` 반환값을 먼저 봐야 한다. |
| "`ex3`가 이 함수를 쓴다" | 안 쓴다. `weighted`는 저장소 어디에서도 호출되지 않는 미사용 훅이다. `ex3`는 엣지 4개를 하드코딩한다. |
| "오답률이 높으면 검증에서 잡힌다" | 23.4%가 틀렸는데도 거리값에 음수가 하나도 없고 평균 오차가 3.89다. 그리고 **2홉 안쪽은 오답률 0%**다. 스모크 테스트로는 못 잡는다. |
| "확률을 20%로 올리면 더 좋은 실험이 된다" | 반대다. 200개 중 196개가 음수 사이클이 되어 최단 경로 문제 자체가 정의되지 않는다. |

## 한 문장으로

`allow_negative=True`는 "음수 가중치가 실무에 섞여 드는 밀도"를 5%로 고정하고,
**유향 엣지 리스트라는 표현 선택 하나로** 무방향이 자동으로 만들어 내는 음수 사이클을 피한 뒤,
다익스트라가 예외 없이 조용히 23% 틀리는 장면을 재현할 수 있게 열어 둔 스위치다.
남은 위험(긴 음수 사이클)은 `seed=7` 고정으로 덮어 뒀을 뿐이니, 파라미터를 만지려면 사이클 검사부터 붙여야 한다.
