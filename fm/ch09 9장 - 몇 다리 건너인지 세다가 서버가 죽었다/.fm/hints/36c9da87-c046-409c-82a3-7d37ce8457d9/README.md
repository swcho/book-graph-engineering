# `critical_path()`는 무엇을 계산하는가?

**답:** 각 작업까지의 최장 누적 소요 시간이다. 병렬로 돌려도 이 시간 밑으로는 내려갈 수 없다.

---

## 1. 한 줄로 줄이면

`critical_path()`는 **DAG 위의 최장 경로(longest path)** 를 푼다. "가장 짧은 길"이 아니라 "가장 긴 길"이다.

의존 그래프에서 어떤 작업 `t`가 시작될 수 있는 가장 이른 시각은, `t`의 모든 선행 작업이 전부 끝난 뒤다. 그러니 `t`가 **끝나는** 가장 이른 시각은

```
finish(t) = max( finish(d) for d in deps(t) ) + cost(t)
```

이고, 선행이 없으면 `max(...)`는 0이다. 전체 작업 중 `finish` 값이 가장 큰 것이 프로젝트 전체의 최소 완료 시간이다. 이게 **임계 경로 길이**다.

여기서 `max`가 핵심이다. 최단 경로였다면 `min`이 들어갔을 자리다. 의존 관계는 "아무 선행이나 하나 끝나면 된다"가 아니라 "선행이 **전부** 끝나야 한다"이므로, 병목이 되는 건 제일 늦게 끝나는 선행이다. 그래서 `max`다.

---

## 2. 에셋의 실제 코드

`content/ch09/code/ex5_toposort.py`:

```python
def critical_path(tasks, cost):
    """제일 오래 걸리는 경로. 병렬로 돌려도 이 시간 밑으로는 못 내려간다."""
    memo = {}
    def go(t):
        if t in memo:
            return memo[t]
        best = max((go(d) for d in tasks[t]), default=0)
        memo[t] = best + cost[t]
        return memo[t]
    end = max(tasks, key=go)
    return go(end), end
```

한 줄씩 읽으면:

| 코드 | 의미 |
|---|---|
| `memo = {}` | `go(t)`의 결과 = "t까지의 최장 누적 시간". 작업마다 딱 한 번만 계산한다. |
| `go(d) for d in tasks[t]` | `tasks[t]`는 t의 **선행 목록**이다. 즉 의존 간선을 거꾸로(자식→부모) 타고 올라간다. |
| `max(..., default=0)` | 선행 중 **제일 늦게 끝나는** 것을 고른다. 선행이 없으면(진입 차수 0) 0에서 시작. |
| `memo[t] = best + cost[t]` | 자기 자신의 작업 시간을 더한다. 노드에 가중치가 붙은 형태(node-weighted). |
| `end = max(tasks, key=go)` | 모든 작업의 `go` 값 중 최댓값을 갖는 작업. 이게 마지막에 끝나는 작업이다. |
| `return go(end), end` | (임계 경로 길이, 마지막 작업). memo 덕에 `go(end)`는 딕셔너리 조회 한 번. |

### 반환값이 "경로"가 아니라 "시간"이라는 점

이름은 `critical_path`이지만 실제로 돌려주는 건 **길이와 끝 작업**이지 경로 자체가 아니다. 경로를 복원하려면 `max`를 고를 때 어느 선행이 뽑혔는지 부모 포인터로 기록해 두면 된다.

```python
best_dep = max(tasks[t], key=go, default=None)   # 이 값을 저장해 두면 역추적 가능
```

## 3. 왜 이게 "위상 순서 위의 DP"인가

`critical_path()`에는 `supersteps()`처럼 명시적인 위상 정렬 루프가 없다. 그런데도 위상 정렬 DP가 맞다. **DFS + 메모이제이션은 위상 순서를 암묵적으로 만들어 내기 때문**이다.

- `go(t)`는 자기 값을 확정하기 전에 반드시 `go(d)`를 **전부** 끝낸다.
- 즉 `memo`에 값이 채워지는 순서는 항상 "선행이 먼저, 후행이 나중" — 정확히 위상 순서다.
- 재귀 종료(=`memo` 확정) 시점의 역순 후위 순회(reverse postorder)가 위상 정렬이라는 게 표준 사실이고, 이 코드는 그걸 그대로 쓰고 있다.

명시적 위상 정렬로 쓰면 이렇게 된다. 값은 동일하다.

```python
def critical_path_explicit(tasks, cost):
    finish = {}
    for layer in supersteps(tasks):       # 위상 순서로 층을 하나씩
        for t in layer:
            finish[t] = max((finish[d] for d in tasks[t]), default=0) + cost[t]
    end = max(finish, key=finish.get)
    return finish[end], end
```

**"위상 순서에서 DP가 성립한다"는 말의 정확한 뜻**: DP가 성립하려면 `finish[t]`를 계산하는 시점에 `finish[d]`가 이미 **최종값**이어야 한다. 위상 순서는 모든 간선이 앞→뒤 방향만 향하도록 노드를 일렬로 세운 순서이므로, 앞에서부터 훑으면 이 조건이 공짜로 보장된다. 나중에 뒤에서 앞으로 되돌아와 값을 고치는 일이 절대 없다 — **재방문·재완화(relaxation)가 필요 없다**. 그래서 한 번의 스캔, `O(V + E)` 선형 시간이다.

### 복잡도

- 각 작업마다 `go`는 최초 1회만 본체를 실행 → `V`번.
- 각 의존 간선은 정확히 한 번씩 순회 → `E`번.
- 합쳐서 **O(V + E)**, 메모리 O(V).

`max(tasks, key=go)`는 V번 `go`를 호출하지만 전부 memo 히트라 O(V)로 끝난다.

## 4. 왜 DAG에서만 다항 시간인가 (일반 그래프는 NP-난해)

여기가 이 카드에서 제일 중요한 이론적 포인트다.

### 최단 경로와 최장 경로의 비대칭

직관적으로는 "가중치 부호를 뒤집고 최단 경로를 구하면 최장 경로 아닌가?" 싶다. 실제로 **DAG에서는 그게 맞다**. 가중치를 음수로 뒤집어 DAG 최단 경로를 풀면 최장 경로가 나오고, DAG 최단 경로는 위상 순서 한 번 훑기로 선형 시간에 풀린다.

문제는 **사이클이 있는 일반 그래프**다.

- 부호를 뒤집는 순간 **음수 사이클**이 생긴다. 음수 사이클이 있으면 최단 경로 자체가 정의되지 않는다(무한히 돌면 −∞). 다익스트라는 애초에 음수를 못 쓰고(같은 장 `ex3_dijkstra_negative.py`가 그 함정을 보여 준다), 벨만-포드는 음수 사이클을 **탐지만** 하고 포기한다.
- 그래서 "같은 노드를 두 번 지나지 않는 최장 경로"(simple path)로 문제를 좁히게 되는데, 이 순간 문제의 성격이 바뀐다.

### NP-난해성의 근거

**최장 단순 경로(longest simple path) 문제는 NP-난해**다. 증명은 한 줄이다.

> **해밀턴 경로 문제**(모든 정점을 정확히 한 번씩 지나는 경로가 존재하는가?)는 NP-완전으로 알려져 있다. 모든 간선 가중치를 1로 둔 그래프에서 최장 단순 경로의 길이가 `V - 1`이면, 그건 정확히 해밀턴 경로다. 따라서 최장 경로를 다항 시간에 풀 수 있다면 해밀턴 경로도 다항 시간에 풀리고, P = NP가 된다.

즉 해밀턴 경로가 최장 경로의 특수한 경우로 그대로 환원된다. 근사조차 어려워서, 일반 그래프의 최장 경로는 상수 비율 근사도 (P = NP가 아닌 한) 불가능하다고 알려져 있다.

### DAG는 왜 빠져나가는가

DAG에는 **사이클이 없으므로 모든 경로가 자동으로 단순 경로**다. "같은 노드를 두 번 밟지 말라"는 제약이 그래프 구조 자체에 이미 내장돼 있어서, 별도로 강제할 필요가 없다. NP-난해성을 만들어 내던 조합적 폭발이 사라진다.

여기에 위상 순서라는 전역 순서가 붙어서, 부분 문제 사이에 순환 의존이 없어진다. `finish[t]`가 `finish[d]`에 의존하는데 `finish[d]`가 다시 `finish[t]`에 의존하는 일이 없다. **DP가 성립할 조건 그 자체다.**

| | 최단 경로 | 최장 경로 |
|---|---|---|
| **DAG** | O(V+E), 위상 순서 DP | **O(V+E), 위상 순서 DP** ← `critical_path()` |
| 음수 없는 일반 그래프 | O(E log V), 다익스트라 | NP-난해 |
| 일반 그래프 | O(VE), 벨만-포드 | NP-난해 |

정리하면 — `critical_path()`가 8줄짜리 재귀로 끝나는 건 알고리즘이 영리해서가 아니라, **입력이 DAG라는 전제가 어려운 부분을 통째로 없애 줬기 때문**이다. 같은 코드를 사이클 있는 그래프에 던지면 무한 재귀에 빠져 `RecursionError`로 죽는다. (참고로 같은 파일의 `supersteps()`는 `done != len(tasks)`를 검사해 `ValueError("사이클")`을 명시적으로 던진다. `critical_path()`에는 그 방어가 없다.)

## 5. "병렬로 돌려도 이 시간 밑으로는 못 내려간다" — 전제는 무한 병렬 자원

임계 경로가 하한(lower bound)인 이유는 단순하다. 임계 경로 위의 작업들은 **일렬로 묶여 있어서 어떤 방법으로도 겹칠 수 없다**. 워커를 아무리 늘려도 앞 작업이 끝나야 뒤 작업을 시작할 수 있으니, 그 사슬의 길이가 그대로 바닥이 된다.

다만 임계 경로가 **달성 가능한** 값이 되려면 전제가 필요하다.

### 전제 1. 워커 수가 무제한 (또는 충분히 많음)

임계 경로 93분을 실제로 달성하려면, 임계 경로 밖의 작업들이 임계 경로를 절대 지연시키지 않아야 한다. 즉 "준비되는 즉시 아무나 잡아서 시작"이 가능해야 하고, 그러려면 동시에 실행 가능한 작업 수만큼 워커가 있어야 한다.

워커가 `m`개로 제한되면 하한이 하나 더 생긴다. 실제 완료 시간(makespan)은

```
makespan ≥ max( 임계 경로,  전체 작업량 합 / m )
```

예제로 확인해 보면 전체 작업량 합이 146분이므로, 워커가 1개면 146분(순차 실행 값과 일치), 2개면 최소 73분인데 임계 경로 93분이 더 크므로 93분이 하한이다. 이 두 하한 중 큰 쪽이 진짜 바닥이다. (Graham의 리스트 스케줄링 결과에 따르면, 아무 욕심쟁이 스케줄러라도 최적값의 `2 − 1/m` 배 안에는 들어온다.)

### 전제 2. 작업 시간이 고정이고 미리 알려져 있음

`cost` 딕셔너리가 상수로 주어진다는 게 전제다. 실제로는 데이터 크기·캐시 상태·재시도에 따라 흔들리고, 그러면 임계 경로가 실행 도중에 **다른 경로로 옮겨 갈** 수 있다. 여유(slack)가 작은 준임계 경로들도 같이 봐야 하는 이유다.

### 전제 3. 통신/기동 비용, 자원 경합 없음

작업 사이의 데이터 전달, 컨테이너 기동, 락 경합 같은 건 모델에 없다. 실제 시스템에서는 이런 오버헤드가 임계 경로에 얹힌다.

### 전제 4. 선점 없음, 작업 분할 없음

한 작업을 쪼개서 여러 워커에 나눠 주는 건 없다고 본다.

## 6. 예제로 확인 — 임계 경로 93분 vs 슈퍼스텝 113분

`ex5_toposort.py`의 의존 그래프와 비용:

```
외부 API 예열(40) ────────────────────────────────┐
                                                  ↓
데이터 적재(20) ┬→ 스키마 검증(5) ─┐              │
                └→ 엔티티 병합(30) ┴→ 관계 추출(15) ┬→ 품질 검사(8) ─┐
                                                    └→ 색인 생성(25) ┴→ 배포(3)
```

`go()`가 계산하는 값(= 각 작업까지의 최장 누적 시간, 곧 그 작업이 끝나는 가장 이른 시각):

| 작업 | 계산 | `go` 값 | 여유(slack) |
|---|---|---|---|
| 외부 API 예열 | 0 + 40 | 40 | 50 |
| 데이터 적재 | 0 + 20 | 20 | **0** |
| 스키마 검증 | 20 + 5 | 25 | 25 |
| 엔티티 병합 | 20 + 30 | **50** | **0** |
| 관계 추출 | max(25, **50**) + 15 | **65** | **0** |
| 품질 검사 | 65 + 8 | 73 | 17 |
| 색인 생성 | 65 + 25 | **90** | **0** |
| 배포 | max(73, **90**, 40) + 3 | **93** | **0** |

`max(tasks, key=go)` → `배포`(93). 반환값은 `(93, "배포")`.

여유가 0인 작업들을 이으면 임계 경로가 나온다:

```
데이터 적재(20) → 엔티티 병합(30) → 관계 추출(15) → 색인 생성(25) → 배포(3) = 93분
```

`스키마 검증`은 5분짜리라 25분의 여유가 있고, `외부 API 예열`은 40분이나 걸리지만 배포 직전까지만 끝나면 되므로 여유가 50분이나 된다. **오래 걸린다고 임계 경로 위에 있는 게 아니다.**

### 실행 결과 (실측)

```
작업 8개 → 슈퍼스텝 5개

  1차 (40분): 데이터 적재, 외부 API 예열
  2차 (30분): 스키마 검증, 엔티티 병합
  3차 (15분): 관계 추출
  4차 (25분): 색인 생성, 품질 검사
  5차 (3분): 배포

순차 실행     146분
슈퍼스텝 실행 113분  (1.3배 단축)
임계 경로     93분 (끝나는 작업: 배포)
```

### 세 값의 관계

```
임계 경로 93분  ≤  슈퍼스텝 실행 113분  ≤  순차 실행 146분
```

- **순차 146분** = `sum(cost.values())`. 병렬성을 하나도 안 쓴 값.
- **슈퍼스텝 113분** = `sum(층별 max)` = 40+30+15+25+3. 층 단위 배리어 동기화.
- **임계 경로 93분** = 이론적 하한. "의존이 풀리는 대로 즉시 시작" 스케줄로만 도달한다.

**93 vs 113의 20분 차이가 어디서 나오나.** 1차 층을 보면 `데이터 적재`(20분)와 `외부 API 예열`(40분)이 같은 층에 묶여 있다. 층 단위 실행은 배리어를 치므로, `데이터 적재`가 20분에 끝나도 `외부 API 예열`이 끝나는 40분까지 **아무도 다음 층으로 못 넘어간다**. 실제로는 `엔티티 병합`이 20분 시점에 바로 시작할 수 있는데도 20분을 놀린다. 이게 그대로 20분의 손실이 된다.

`외부 API 예열`은 `배포`만 필요로 하는데, 위상 층 계산은 "진입 차수 0"만 보므로 1차에 배치해 버린다. 층 구조가 실제 의존을 과하게 보수적으로 해석한 셈이다.

## 7. 실무 맥락

- 이 계산은 **CPM(Critical Path Method)** 으로 1950년대부터 공정 관리에서 쓰던 것과 같다. 표에 넣은 여유(slack/float)는 정방향 패스(ES/EF)와 역방향 패스(LS/LF)를 각각 돌려 `LS − ES`로 구한다. `critical_path()`가 하는 건 정방향 패스다.
- 빌드 시스템(Bazel, Make의 `-j`), CI 파이프라인, DAG 오케스트레이터(Airflow, Dagster), 데이터 파이프라인의 스케줄러가 전부 같은 계산을 한다.
- **최적화할 곳을 고르는 도구**로 쓰인다. 임계 경로 위에 있지 않은 작업을 아무리 빨리 만들어도 전체 시간은 1초도 안 줄어든다. 위 예제에서 `외부 API 예열`을 40분→10분으로 줄여도 임계 경로는 그대로 93분이다. 반면 `엔티티 병합`(30분)을 줄이면 바로 전체가 줄어든다.
- 단, 임계 경로 위의 작업을 충분히 줄이면 **임계 경로가 다른 경로로 옮겨 간다**. 최적화는 한 번으로 끝나지 않고 반복해야 한다.
- 에셋 본문의 결론: "층 단위로 기다리지 않고 «의존이 풀리는 대로» 시작하면 임계 경로까지 내려간다. 층 단위는 구현이 쉽고, 의존 단위는 빠르다."

## 8. 코드의 한계 (읽을 때 같이 보면 좋은 것)

| 항목 | 내용 |
|---|---|
| 사이클 | `supersteps()`는 `ValueError("사이클")`을 던지지만 `critical_path()`는 무한 재귀 → `RecursionError`. |
| 재귀 깊이 | 의존 사슬이 길면(파이썬 기본 한계 1000) 터진다. 실무에서는 명시적 위상 정렬 루프로 바꾸는 게 안전하다. |
| 경로 미반환 | 길이와 끝 작업만 준다. 경로 자체는 부모 포인터를 따로 기록해야 복원된다. |
| 누락 키 | `tasks[t]`에 없는 의존 이름이 들어 있으면 `KeyError`. `cost[t]`도 마찬가지. |
| 노드 가중치 | 간선이 아니라 노드에 시간이 붙는 모델이다. 간선 가중 모델과 상호 변환은 되지만 식이 조금 다르다. |

## 핵심 정리

1. `critical_path()`는 `finish(t) = max(finish(선행들)) + cost(t)` 를 DP로 계산해 **각 작업까지의 최장 누적 시간**을 구하고, 그 최댓값과 해당 작업을 돌려준다.
2. DFS + 메모이제이션이 곧 **위상 순서 DP**다. 선행이 항상 먼저 확정되므로 재완화가 없고 **O(V+E)** 로 끝난다.
3. 최장 경로가 다항 시간에 풀리는 건 **DAG이기 때문**이다. 일반 그래프의 최장 단순 경로는 해밀턴 경로를 포함하므로 NP-난해다. 사이클이 없다 = 모든 경로가 단순 경로다 = 어려움이 사라진다.
4. "이 시간 밑으로 못 내려간다"는 **무한 병렬 자원, 고정 작업 시간, 오버헤드 없음**을 전제로 한 하한이다. 워커가 `m`개면 `총작업량/m`이라는 하한이 하나 더 붙는다.
5. 예제에서 임계 경로 93분 < 슈퍼스텝 113분. 차이는 층 단위 배리어가 같은 층의 제일 느린 작업을 기다리기 때문에 생긴다.
