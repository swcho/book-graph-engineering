# `graph.py`의 `make()`는 어떤 그래프를 만드는가?

## 정답 요약

노드 n개에 대해 각 노드마다 `avg_deg // 2`번 무작위 이웃을 붙이고, 마지막에 중복을 제거해 정렬된 인접 리스트로 반환한다. 시드는 20260801로 고정된다.

## 코드

```python
"""9장 공통 그래프. 의존성 없음. 시드 고정."""
import random
from collections import defaultdict

def make(n=200_000, avg_deg=12, seed=20260801):
    rnd = random.Random(seed)
    adj = defaultdict(list)
    for a in range(n):
        for _ in range(avg_deg // 2):
            b = rnd.randrange(n)
            if a != b:
                adj[a].append(b)
                adj[b].append(a)
    return {k: sorted(set(v)) for k, v in adj.items()}
```

9장 예제 중 `ex1_bfs_explosion.py`(홉 폭발)와 `ex2_bidirectional.py`(양방향 탐색)가 이 함수를 `from graph import make`로 가져다 쓴다. 둘 다 `N = 200_000`으로 호출하고, 문서에 "메모리 1GB 정도 씁니다"라고 적힌 그 그래프가 여기서 나온다.

## 한 줄씩 뜯어보기

| 줄 | 하는 일 |
|---|---|
| `rnd = random.Random(seed)` | 전역 `random` 대신 **독립 인스턴스**를 만든다. 다른 코드가 `random.seed()`를 건드려도 영향받지 않는다. |
| `adj = defaultdict(list)` | 키가 없으면 빈 리스트를 자동 생성. `if a in adj` 검사를 생략하려는 것. |
| `for a in range(n)` | 모든 노드를 한 번씩 "출발점"으로 삼는다. |
| `for _ in range(avg_deg // 2)` | 노드당 엣지를 **평균 차수의 절반**만 만든다. 핵심. |
| `b = rnd.randrange(n)` | 이웃을 **완전 균등 무작위**로 고른다. 거리·유사도·인기도 같은 편향이 전혀 없다. |
| `if a != b` | 자기 루프를 만들지 않고 **그냥 건너뛴다**. 다시 뽑지 않는다. |
| `adj[a].append(b)` / `adj[b].append(a)` | 양쪽에 넣어서 **무방향(대칭)** 그래프로 만든다. |
| `sorted(set(v))` | 중복 엣지 제거 + 정렬. 반환 타입도 `defaultdict` → 평범한 `dict`로 바뀐다. |

## 왜 `avg_deg // 2`인가 — 무방향 엣지 하나가 차수를 둘 올린다

이 부분이 이 카드의 핵심입니다.

무방향 그래프에서 엣지 `(a, b)` **하나**는 `a`의 차수도 1 올리고 `b`의 차수도 1 올립니다. 그래서 차수의 총합은 항상 엣지 수의 두 배입니다. 그래프 이론에서 **악수 정리(handshaking lemma)** 라고 부르는 그것입니다.

```
Σ deg(v) = 2 × |E|
```

따라서 평균 차수는

```
평균 차수 = Σ deg(v) / n = 2|E| / n
```

목표 평균 차수를 `avg_deg`로 맞추려면 필요한 엣지 수는

```
|E| = n × avg_deg / 2
```

루프는 노드 n개를 각각 한 번씩 돌면서 노드당 `avg_deg // 2`개의 엣지를 만듭니다. 그러니 총 엣지 수가 정확히 `n × avg_deg / 2`가 되고, 평균 차수는 `avg_deg`가 됩니다.

기본값으로 넣어 보면:

```
avg_deg = 12  →  노드당 12 // 2 = 6개 생성
n = 200,000   →  엣지 200,000 × 6 = 1,200,000개
차수 총합     →  1,200,000 × 2 = 2,400,000
평균 차수     →  2,400,000 / 200,000 = 12  ✓
```

**흔한 오해:** "노드당 6개씩 붙였으니 차수도 6 아닌가?" 아닙니다. 노드 `a`는 **자기가 만든 6개**(나가는 쪽)에 더해, **다른 노드들이 `a`를 무작위로 골라서 붙인 것**(들어오는 쪽)도 받습니다. 이 "받는" 개수의 기댓값도 6입니다. 노드 하나가 총 `n × 6`번의 추첨 중 하나에 뽑힐 확률이 `1/n`이니 기댓값 `n × 6 × (1/n) = 6`이죠. 그래서 6 + 6 = 12가 됩니다.

이걸 실측으로 확인하면 최소 차수가 정확히 **6**으로 나옵니다. 모든 노드가 자기 몫 6개는 무조건 만들기 때문입니다. 차수 분포는 사실상 `6 + Poisson(6)` 모양이 됩니다.

### `//`(정수 나눗셈)의 부작용

`avg_deg`가 **홀수**면 조용히 내림됩니다.

| `avg_deg` | `avg_deg // 2` | 실제 평균 차수 |
|---|---|---|
| 12 | 6 | 12 |
| 11 | 5 | **10** |
| 8 | 4 | 8 |
| 1 | **0** | **0 (엣지 없음)** |

`avg_deg=11`을 넘기면 11이 아니라 10짜리 그래프가 나옵니다. 예제용으로는 문제가 안 되지만, 이 함수를 재사용할 때는 알고 있어야 하는 함정입니다. `avg_deg=1`이면 `1 // 2 = 0`이라 루프가 한 번도 안 돌고, `adj`가 비어 `len(adj)`가 0이 되어 호출부의 나눗셈에서 `ZeroDivisionError`가 납니다.

## 실제 평균 차수는 목표보다 아주 조금 낮다

이론값 12에 정확히 도달하지 못하는 이유가 둘 있습니다.

**1. 자기 루프를 버린다.** `b = rnd.randrange(n)`이 하필 `a`와 같으면 `if a != b`에서 걸려 그냥 넘어갑니다. **다시 뽑지 않습니다.** 그 노드는 엣지 하나를 못 만든 채 끝납니다. 확률은 매 추첨마다 `1/n`이니, 총 `n × avg_deg/2`번의 추첨에서 평균 `avg_deg/2`개(n과 무관한 상수)가 사라집니다.

**2. 중복 엣지를 제거한다.** `set(v)`가 같은 쌍을 두 번 이상 뽑은 경우를 하나로 접습니다. `a`가 `b`를 두 번 뽑았거나, `a→b`와 `b→a`가 각각 생겼을 수도 있죠. 두 번 세어진 만큼이 손실입니다. 중복 쌍의 기댓값은 대략 `n × (avg_deg/2)² / n = (avg_deg/2)²` 규모로, 역시 n에 거의 비례하지 않습니다.

결국 잃는 엣지 수는 **n에 비례하지 않고 상수에 가깝기 때문에**, n이 커질수록 손실 비율은 급격히 작아집니다. 실측하면 이렇습니다.

| n | 실제 평균 차수 | 목표(12) 대비 손실 |
|---|---|---|
| 100 | 11.16 | 7.0% |
| 1,000 | 11.90 | 0.80% |
| 10,000 | 11.99 | 0.063% |
| 200,000 | **11.9995** | **0.004%** |

그래서 `ex1_bfs_explosion.py`가 출력하는 "평균 차수"는 12.0으로 반올림되어 보입니다. 작은 n으로 이 함수를 테스트하면 눈에 띄게 낮게 나온다는 점만 기억하면 됩니다.

**정리:** 실제 평균 차수는 항상 목표 이하입니다. 절대 초과하지 않습니다 — 이 코드에는 엣지를 더 만드는 경로가 없기 때문입니다.

## 정렬과 중복 제거가 하는 다른 일

`sorted(set(v))`는 평균 차수를 낮추는 부작용만 있는 게 아닙니다. 실용적인 이유가 세 개 있습니다.

1. **단순 그래프 보장.** 다중 엣지가 없으니 BFS에서 같은 이웃을 여러 번 확인하는 낭비가 사라집니다. `ex1`의 "이번 홉 새 노드" 집계도 왜곡되지 않습니다.
2. **결정적 순회 순서.** 인접 리스트가 정렬되어 있으니 BFS가 이웃을 방문하는 순서가 항상 같습니다. 최단 경로가 여러 개일 때 `ex2_bidirectional.py`가 어느 것을 고를지도 실행마다 동일합니다.
3. **8장과의 연결.** 정렬된 인접 리스트는 8장에서 다룬 메모리 배치 이야기와 이어집니다. 정렬 상태는 이진 탐색이나 CSR 압축의 전제 조건입니다.

한편 `list` → `set` → `sorted(list)` 변환은 200,000노드 × 12이웃 규모에서 메모리 피크를 만듭니다. 문서의 "메모리 1GB" 안내가 이 지점을 가리킵니다.

## 시드 20260801을 박아 둔 이유

`random.Random(20260801)`은 **같은 인자로 호출하면 언제 어디서 돌려도 완전히 동일한 그래프**를 만듭니다. 파일 첫 줄 독스트링이 "시드 고정"이라고 못 박은 이유입니다. 실제로 `make(5000) == make(5000)`은 `True`입니다.

책 예제에서 이게 왜 중요한가요.

- **본문의 숫자가 재현된다.** 9장은 "5홉이면 전체의 68%", "양방향 탐색이 75~88배 줄었다" 같은 **구체적인 수치**를 주장합니다. 시드가 흔들리면 독자가 돌릴 때마다 다른 숫자가 나와서 본문과 어긋납니다. 실제로 시드 20260801, n=200,000으로 0번 노드에서 BFS를 돌리면 5홉 누적 136,415개(68.2%), 6홉에 199,997개(100.0%)가 나옵니다. 본문 그대로입니다.
- **비교가 공정해진다.** `ex2`는 단방향 BFS와 양방향 BFS의 방문 노드 수를 비교합니다. 두 알고리즘이 **같은 그래프**를 봐야 배수가 의미를 가집니다. 그래프를 두 번 따로 생성했다면 비교 자체가 성립하지 않습니다.
- **버그 재현이 가능해진다.** 특정 노드 쌍에서 이상한 결과가 나왔을 때, 시드가 고정되어 있으면 그 상황을 언제든 다시 만들 수 있습니다.
- **회귀 테스트가 가능해진다.** 코드를 고친 뒤 출력이 달라졌다면, 그건 그래프가 바뀌어서가 아니라 알고리즘이 바뀌어서입니다.

**주의:** 시드를 고정해도 재현성이 100% 보장되는 건 아닙니다. `random.Random`의 Mersenne Twister 알고리즘 자체는 Python 버전 간에 안정적이지만, `randrange` 같은 상위 API의 구현이 바뀌면 결과가 달라질 수 있습니다(과거 `random.sample`, `random.shuffle` 등에서 실제로 있었던 일입니다). 그래서 문서가 "Python 3.9 이상", "확인 시점 2026년 8월"이라고 환경을 함께 적어 둔 것입니다.

`weighted()` 함수는 시드가 `7`로 따로 잡혀 있습니다. `make()`와 다른 그래프를 쓰겠다는 뜻입니다.

## 한계 — 이건 에르되시-레니 계열이고, 실제 소셜 그래프가 아니다

이 부분이 이 함수를 이해할 때 가장 중요한 대목입니다.

`rnd.randrange(n)`은 **모든 노드를 똑같은 확률로 고릅니다.** 인기 있는 노드를 더 자주 고르지 않습니다. 이건 **에르되시-레니(Erdős–Rényi) 랜덤 그래프** 계열의 성질입니다. 정확히는 노드마다 나가는 엣지 수를 고정한 "random k-out" 변형이지만, "연결 상대를 균등 무작위로 고른다"는 본질은 같습니다.

그 결과 차수 분포가 **평균 주위에 좁게 몰립니다.** n=200,000에서 실측하면:

| 차수 | 노드 비율 |
|---|---|
| 6 (최소) | 0.26% |
| 9 | 9.00% |
| 11 | 16.00% |
| 12 | 15.96% |
| 15 | 6.83% |
| 26 (최대) | ~0.00% |

**최대 차수가 26**입니다. 평균의 두 배를 조금 넘는 수준이죠. 차수 60짜리 노드는 아예 존재하지 않습니다.

실제 소셜 그래프는 전혀 이렇지 않습니다. 팔로워 분포는 **멱법칙(power law) / 스케일 프리(scale-free)** 에 가깝습니다. 대부분은 차수가 한 자리인데, 소수의 **허브(hub)** 가 수만~수백만 차수를 가집니다. 이런 분포는 **바라바시-알버트(Barabási–Albert) 선호적 연결(preferential attachment)** 모델이 훨씬 잘 설명합니다. 이미 연결이 많은 노드가 새 연결을 더 잘 받는다는 규칙이죠.

이 차이가 실무에서 만드는 결과는 이렇습니다.

| | `make()`의 ER 계열 그래프 | 실제 소셜 그래프 (멱법칙) |
|---|---|---|
| 차수 분포 | 푸아송 형태, 좁게 몰림 | 두꺼운 꼬리(heavy tail) |
| 최대 차수 (n=20만) | 26 정도 | 수만~수십만 가능 |
| 슈퍼 노드 | **없음** | **있음** |
| BFS 성능 | 어느 시작점에서 돌려도 비슷 | 시작점에 따라 수천 배 차이 |
| 홉당 증가 | 균일하게 약 11배 | 허브를 만나면 한 홉에 폭발 |

**즉 `make()`는 홉 폭발을 오히려 온건하게 보여 줍니다.** 균등 그래프에서도 5홉이면 68%가 나오는데, 허브가 있는 실제 그래프에서는 그보다 더 빨리, 더 예측 불가능하게 터집니다. 9장이 "상한 없는 순회는 사실상 전체 스캔"이라고 말하는 근거가, 최악의 경우가 아니라 **가장 얌전한 경우**에서 나온 숫자라는 뜻입니다. 논지가 약해지는 게 아니라 오히려 강해집니다.

반대로 이 그래프로는 **검증할 수 없는 것**도 있습니다.

- **슈퍼 노드 장애 재현.** `ex4_path_explosion.py` 말미의 "어느 날 노드 하나가 슈퍼 노드가 됐다"는 회고는 `make()`가 만드는 그래프에서는 절대 일어나지 않습니다. 그래서 `ex4`는 `make()`를 안 쓰고 격자 그래프를 따로 만듭니다.
- **꼬리 지연(tail latency).** 실제 서비스에서 p99 지연을 만드는 건 허브를 지나는 소수의 질의인데, 이 그래프에는 그런 노드가 없어서 지연 분포가 지나치게 평탄합니다.
- **파티셔닝/샤딩 전략 평가.** 허브가 없으면 어떤 분할이든 비슷하게 잘 동작합니다. 실제 문제는 허브를 어느 샤드에 둘지에서 시작합니다.
- **연결성 가정.** 최소 차수가 6이라 고립 노드가 없고, n=200,000에서 노드 0번에서 200,000개 전부에 닿습니다. 즉 **단일 거대 연결 요소**입니다. 실제 그래프의 파편화된 작은 요소들은 나타나지 않습니다.

그럼 왜 이 모델을 쓰나요. **의존성 없이 20줄로 200,000노드 그래프를 만들 수 있기 때문**입니다. 문서가 "의존성 없음"을 강조하는 게 이 장의 설계 원칙입니다. 홉 폭발과 양방향 탐색의 제곱근 효과라는 **두 가지 논지를 보이는 데는 이 정도로 충분하고**, 실제 워크로드 벤치마크에는 부족하다 — 이 선을 아는 것이 요점입니다.

## 자주 틀리는 지점 체크리스트

- [ ] `avg_deg // 2`인 이유는 무방향 엣지 하나가 **양쪽 차수를 모두** 올리기 때문 (악수 정리, `Σ deg = 2|E|`)
- [ ] 노드의 차수는 "자기가 만든 6개 + 남이 자기를 고른 약 6개" = 12
- [ ] 자기 루프는 **재추첨 없이 그냥 버린다** → 엣지가 조금 준다
- [ ] `set()` 중복 제거로도 조금 준다 → 실제 평균 차수는 목표보다 **항상 낮다** (n=20만에서 11.9995)
- [ ] 손실량은 n에 비례하지 않아서 n이 클수록 오차 비율이 무시할 만해진다
- [ ] `avg_deg`가 홀수면 조용히 내림된다 (11 → 실제 10)
- [ ] 시드 고정은 본문 수치 재현 + 알고리즘 간 공정 비교 + 버그 재현을 위한 것
- [ ] 균등 무작위 선택 → 에르되시-레니 계열 → **허브가 없다** → 실제 소셜 그래프의 멱법칙 분포와 다르다
- [ ] 그래도 논지는 성립한다. 가장 얌전한 그래프에서도 5홉이면 68%다
