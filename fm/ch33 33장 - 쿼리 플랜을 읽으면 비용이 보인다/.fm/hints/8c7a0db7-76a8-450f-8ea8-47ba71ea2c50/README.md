# 총 시간 기준 상위 세 쿼리의 공통점은?

**답**: 권한 계산·팀 구성원·이름 찾기 셋이 전체의 87%를 먹는데, 셋 다 1~3ms짜리 「빠른」 쿼리다.

---

## 1. 무엇을 묻는 질문인가

33.3절(「제일 느린 것과 제일 아픈 것은 다르다」)의 핵심입니다. 쿼리를 줄 세우는 기준이 두 개 있어요.

| 기준 | 뜻 | 잡히는 것 |
|---|---|---|
| **1회 지연** | 한 번 돌 때 몇 ms | 사용자가 「기다린다」고 느끼는 것 |
| **총 시간** = 1회 지연 × 호출 수 | 하루에 이 쿼리가 CPU를 몇 시간 먹나 | 인프라를 「먹는」 것 |

느린 쿼리 로그는 앞의 기준으로만 줄을 세웁니다. 그런데 청구서와 코어 수를 결정하는 건 뒤의 기준이에요. 이 카드는 뒤의 기준으로 줄을 세웠을 때 **위쪽에 올라온 쿼리들의 공통 성질**을 묻고 있습니다.

---

## 2. ex4 수치 — 실제로 줄을 세워 보면

`code/ex4_hot_query.py`의 입력은 쿼리 일곱 개입니다.

```
QUERIES = [
    # 이름                    1회 ms   하루 호출 수
    ("팀 구성원 조회",            2.1,   4_200_000),
    ("2홉 이웃 탐색",           18.0,     140_000),
    ("전체 조직도 렌더",        820.0,       1_400),
    ("사용자 권한 계산",          3.4,   2_800_000),
    ("월간 감사 리포트",      12_000.0,          30),
    ("이름으로 사람 찾기",        1.2,   6_100_000),
    ("커뮤니티 탐지",         31_000.0,           2),
]
```

### 1회 지연 순 (느린 쿼리 로그가 보는 세계)

| 순위 | 쿼리 | 1회 ms |
|---|---|---|
| 1 | 커뮤니티 탐지 | 31,000.0 |
| 2 | 월간 감사 리포트 | 12,000.0 |
| 3 | 전체 조직도 렌더 | 820.0 |
| 4 | 2홉 이웃 탐색 | 18.0 |

### 하루 총 시간 순 (인프라가 실제로 먹는 세계)

`총 시간 = ms × 호출 수 / 1000 / 3600` (시간 단위)

| 순위 | 쿼리 | 1회 ms | 하루 호출 | 하루 총 시간 | 비중 |
|---|---|---|---|---|---|
| 1 | **사용자 권한 계산** | 3.4 | 2,800,000 | 2.64h | **32%** |
| 2 | **팀 구성원 조회** | 2.1 | 4,200,000 | 2.45h | **30%** |
| 3 | **이름으로 사람 찾기** | 1.2 | 6,100,000 | 2.03h | **25%** |
| 4 | 2홉 이웃 탐색 | 18.0 | 140,000 | 0.70h | 8% |
| 5 | 전체 조직도 렌더 | 820.0 | 1,400 | 0.32h | 4% |
| 6 | 월간 감사 리포트 | 12,000.0 | 30 | 0.10h | 1% |
| 7 | 커뮤니티 탐지 | 31,000.0 | 2 | 0.017h | 0% |
|  | **합계** |  |  | **8.26h** |  |

- 상위 셋의 비중 합: 32 + 30 + 25 = **87%** (표시 반올림 기준. 반올림하지 않은 실제 값은 7.13h / 8.26h = 86.25%)
- 두 줄 세우기의 **1위가 완전히 뒤집힙니다.** 지연 1위였던 커뮤니티 탐지는 총 시간 순위에서 꼴찌(0.2%)입니다. 31초씩 걸리지만 하루 두 번밖에 안 돌거든요.
- 반대로 총 시간 1위인 권한 계산은 지연 순위에서 **5위 밖**입니다. 3.4ms니까요.

### 왜 상위 셋이 「빠른 쿼리」인가

우연이 아니라 **구조적**입니다. 이 셋은 전부 「모든 요청 경로마다 한 번씩 도는」 부류예요.

- **사용자 권한 계산** — 거의 모든 API 호출 앞에 붙는 인가 체크
- **팀 구성원 조회** — 화면 하나 그릴 때마다 붙는 목록 조회
- **이름으로 사람 찾기** — 렌더링할 때마다 ID를 사람 이름으로 바꾸는 조회

이런 쿼리는 **애초에 빠를 수밖에 없습니다.** 매 요청마다 도는데 100ms씩 걸리면 시스템이 못 버티니까 이미 튜닝돼 있어요. 즉 「1~3ms짜리」라는 건 방치의 결과가 아니라 **이미 최적화가 끝났다는 증거**입니다. 그리고 바로 그 최적화된 쿼리들이 호출 수 때문에 총 시간의 87%를 먹고 있는 거죠.

## 3. 그래서 어떻게 고치나 — 쿼리 튜닝이 아니다

여기가 이 카드의 진짜 요점입니다. **상위 셋을 쿼리 튜닝으로 고치려는 시도는 거의 막힙니다.**

### 여지가 없다

1.2ms짜리 쿼리에서 뽑아낼 수 있는 게 얼마나 될까요. 33.2절(`ex2_index_effect.py`)이 이미 답을 줍니다. 수천~수만 노드 규모에서는 **쿼리 파싱과 계획 수립의 고정 비용이 지배**하고 실제 찾기는 1ms도 안 걸립니다. 인덱스를 더 얹어도 배수가 1.1 언저리에서 안 움직여요. 이미 1.2ms인 쿼리에서 인덱스로 짜낼 여지가 사실상 없다는 뜻입니다.

### 반면 호출 수는 여지가 크다

총 시간은 `지연 × 호출 수`인 곱셈입니다. 지연 쪽이 바닥을 쳤으면 **남은 손잡이는 호출 수뿐**이에요.

| 수단 | 하는 일 | 이 워크로드에 대입하면 |
|---|---|---|
| **캐시** | 같은 답을 두 번 묻지 않는다 | 권한 계산 결과를 요청/세션 단위로 캐시. 히트율 70%면 호출 280만 → 84만, 총 시간 2.64h → 0.79h |
| **배치** | N번 호출을 1번으로 합친다 | 목록 50줄 그리며 이름을 50번 찾는 대신 ID 50개를 한 번에 조회(N+1 제거). 610만 호출의 상당 부분이 증발 |
| **비정규화** | 매번 계산하던 것을 미리 저장해 둔다 | 권한을 그래프 순회로 매번 계산하는 대신 유효 권한을 노드/엣지 속성으로 굳혀 둔다. 계산 자체가 사라짐 |

책이 든 산술이 대비를 정확히 보여 줍니다.

- 권한 계산을 3.4ms → 1.7ms (절반으로!) → 하루 **1.3시간** 절감
- 커뮤니티 탐지를 31초 → 15초 (절반으로!) → 하루 **0.00003시간** 절감

같은 「절반으로 줄이기」인데 효과가 4만 배 차이납니다. 그런데 후자가 훨씬 눈에 띄고, 보고하기 좋고, 슬로우 쿼리 로그에 빨갛게 찍혀 있어요. 그래서 많은 팀이 후자를 먼저 합니다.

그리고 지연을 절반으로 줄이는 것보다 **캐시로 호출을 70% 없애는 게 대개 더 쉽고 효과도 큽니다.** 3.4ms를 1.7ms로 만드는 건 어렵지만, 같은 요청 안에서 권한을 세 번 묻는 코드를 한 번으로 줄이는 건 어렵지 않거든요.

## 4. 느린 쿼리 로그의 함정

이 워크로드에 흔한 설정인 **임계값 100ms**짜리 슬로우 쿼리 로그를 걸면 어떻게 될까요.

| 쿼리 | 총 시간 비중 | 100ms 로그에 찍히나 |
|---|---|---|
| 사용자 권한 계산 (3.4ms) | 32% | **안 찍힘** |
| 팀 구성원 조회 (2.1ms) | 30% | **안 찍힘** |
| 이름으로 사람 찾기 (1.2ms) | 25% | **안 찍힘** |
| 커뮤니티 탐지 (31,000ms) | 0.2% | 찍힘 |
| 월간 감사 리포트 (12,000ms) | 1% | 찍힘 |
| 전체 조직도 렌더 (820ms) | 4% | 찍힘 |

**총 시간의 87%가 로그에 한 줄도 안 나옵니다.** 로그를 아무리 노려봐도 제일 아픈 쿼리는 보이지 않아요. 그래서 두 지표를 나눠서 봐야 합니다.

- **느린 쿼리 로그 / p99 지연** → 사용자가 「기다린다」고 느끼는 것을 찾는다
- **쿼리별 총 시간 순위** → 인프라를 「먹는」 것을 찾는다

둘 다 봐야 하고, 고치는 순서는 대개 후자가 먼저입니다.

## 5. 한 발 더 — 총 시간 1등이라도 청구서 1등은 아니다

주의할 게 하나 있어요. 33.4절(`ex3_cost_model.py`)은 같은 논리를 **돈**에 적용하면 또 다른 그림이 나온다는 걸 보여 줍니다. 그래프 조회가 월 3.6억 회로 제일 많이 도는데도 비용 비중은 아주 작고, 월 158만 회뿐인 모델 호출이 청구서를 압도합니다. 토큰 단가가 CPU 시간 단가와 자릿수가 다르기 때문이에요.

정리하면 세 층입니다.

| 목적 | 봐야 할 지표 | 손대야 할 곳 |
|---|---|---|
| 사용자 체감 지연 | p99, 느린 쿼리 로그 | 오래 걸리는 쿼리 (플랜, `CROSS_PRODUCT`, 인덱스) |
| 인프라 코어 수 | 쿼리별 **총 시간** | **자주 도는 쿼리의 호출 횟수** (캐시·배치·비정규화) |
| 청구서 | 토큰 비용 | 모델 호출 횟수·호출당 토큰 |

이 카드는 가운데 줄의 이야기입니다. 그리고 세 줄 모두 결국 같은 형태의 교훈이에요 — **비중을 먼저 재고 나서 고쳐라.** 33장이 암달의 법칙을 인용하는 이유가 이겁니다. `ex5_where_time_goes.py`에서 모델 호출이 94.8%를 차지할 때 나머지 여섯 구간을 전부 최대로 줄여도 3%밖에 안 주는 것과 똑같은 구조입니다.

---

## 외우는 방식

> **총 시간 상위 = 자주 도는 것 = 이미 빠른 것.**
> 빠른 쿼리는 더 못 깎으니, 손잡이는 지연이 아니라 **횟수**다.
> 캐시·배치·비정규화. 그리고 이 셋은 느린 쿼리 로그에 안 찍힌다.

숫자 앵커: **87% (32+30+25)**, **1~3ms**, 권한 계산 3.4ms × 280만 회 = **2.6시간 = 32%**, 커뮤니티 탐지 31초 × 2회 = **0.2%**.
