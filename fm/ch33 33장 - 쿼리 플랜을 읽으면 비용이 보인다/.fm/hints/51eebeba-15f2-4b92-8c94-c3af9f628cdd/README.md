# "제일 느린 것"과 "제일 아픈 것"은 어떻게 구별하는가?

> **답**: 총 시간(1회 지연 × 호출 수)으로 줄 세운다. 느린 쿼리 로그는 제일 아픈 것을 잡지 못한다.

출처: 33장 「쿼리 플랜을 읽으면 비용이 보인다」 33.3절 — 제일 느린 것과 제일 아픈 것은 다르다 / `code/ex4_hot_query.py`

---

## 1. 두 단어가 재는 것이 서로 다르다

| | 제일 느린 것 | 제일 아픈 것 |
|---|---|---|
| 측정값 | **1회 지연** (max, p99) | **총 시간** = 1회 지연 × 호출 수 |
| 단위 | ms / 회 | 시간 / 일 (또는 코어·시) |
| 찾아내는 문제 | 사용자가 "기다린다"고 느끼는 것 | 인프라를 "먹는" 것 |
| 도구 | 느린 쿼리 로그, p99 대시보드 | 쿼리별 총 시간 순위 (`pg_stat_statements` 류) |
| 고치는 이유 | 체감 지연 | 용량·비용 |

핵심은 **두 순위가 서로 다른 축**이라는 것이다. 지연은 쿼리 하나의 성질이고, 총 시간은 쿼리와 **워크로드**의 곱이다. 호출 수라는 항이 빠지면 랭킹이 통째로 뒤집힌다.

```
총 시간 = 1회 지연 × 호출 수
          ↑ 프로파일러가 보는 것   ↑ 로그가 안 세는 것
```

## 2. ex4_hot_query.py 실측 — 랭킹이 실제로 뒤집힌다

예제는 쿼리 일곱 개에 각각 1회 지연과 하루 호출 수를 붙여 두고, 두 가지로 줄을 세운다.

```python
QUERIES = [
    # 이름                    1회 ms   하루 호출 수
    ("팀 구성원 조회",            2.1,   4_200_000),
    ("2홉 이웃 탐색",           18.0,     140_000),
    ("전체 조직도 렌더",        820.0,       1_400),
    ("사용자 권한 계산",          3.4,   2_800_000),
    ("월간 감사 리포트",      12_000.0,          30),
    ("이름으로 사람 찾기",        1.2,   6_100_000),
    ("커뮤니티 탐지",         31_000.0,           2),
]
```

### 2-1. 1회 지연 순 (= "제일 느린 것")

| 순위 | 쿼리 | 1회 ms |
|---|---|---|
| 1 | 커뮤니티 탐지 | 31,000.0 |
| 2 | 월간 감사 리포트 | 12,000.0 |
| 3 | 전체 조직도 렌더 | 820.0 |
| 4 | 2홉 이웃 탐색 | 18.0 |

### 2-2. 하루 총 시간 순 (= "제일 아픈 것")

`ms * n / 1000 / 3600` 으로 계산한 값. 합계 **8.3시간/일**.

| 순위 | 쿼리 | 1회 ms | 하루 호출 | 하루 총 시간 | 비중 |
|---|---|---|---|---|---|
| 1 | 사용자 권한 계산 | 3.4 | 2,800,000 | **2.6h** | **32%** |
| 2 | 팀 구성원 조회 | 2.1 | 4,200,000 | 2.5h | 30% |
| 3 | 이름으로 사람 찾기 | 1.2 | 6,100,000 | 2.0h | 25% |
| 4 | 2홉 이웃 탐색 | 18.0 | 140,000 | 0.7h | 8% |
| 5 | 전체 조직도 렌더 | 820.0 | 1,400 | 0.32h | 4% |
| 6 | 월간 감사 리포트 | 12,000.0 | 30 | 0.10h | 1% |
| 7 | 커뮤니티 탐지 | 31,000.0 | 2 | **0.017h** | **0.2%** |

**두 표에 겹치는 이름이 하나도 없다.** 지연 1위인 커뮤니티 탐지는 총 시간 꼴찌(7위)이고, 총 시간 1위인 권한 계산은 지연으로는 아래에서 두 번째다.

> 제일 느린 것은 «커뮤니티 탐지»다. 31초 걸린다.
> 그런데 하루에 두 번 돈다. 총 시간은 0.02시간이다.
>
> 제일 아픈 것은 «사용자 권한 계산»이다. 3.4ms 밖에 안 걸리는데
> 하루 280만 번 돌아서 총 2.6시간, 전체의 32%다.
>
> 상위 셋(권한 계산·팀 구성원·이름 찾기)이 전체의 87%를 먹는다.
> 셋 다 «빠른» 쿼리다. 1~3ms 짜리들이다.

상위 셋 합계는 정확히는 **86.3%**(2.644 + 2.450 + 2.033 = 7.13h / 8.26h)이고, 출력에 찍히는 반올림 값(32% + 30% + 25%)으로 87%가 된다. 어느 쪽이든 요점은 같다. **1~3ms짜리 "빠른" 쿼리 셋이 전체 인프라 시간의 6분의 5를 먹는다.**

## 3. 튜닝 투자 수익률(ROI)도 뒤집힌다

같은 노력(지연을 절반으로)을 들였을 때 돌아오는 것:

| 대상 | 개선 | 하루 절감 | 총 시간 대비 |
|---|---|---|---|
| 사용자 권한 계산 | 3.4ms → 1.7ms | **1.32시간** | 16.0%p |
| 커뮤니티 탐지 | 31s → 15s | 0.0089시간 (32초) | 0.1%p |

**약 150배 차이**다. 노력은 오히려 반대다. 31초짜리 배치 그래프 알고리즘을 절반으로 줄이는 일이 3.4ms짜리 권한 조회를 1.7ms로 줄이는 일보다 훨씬 어렵다. 즉 **어려운 쪽이 보상이 작다.**

> 참고: 본문에는 커뮤니티 탐지 절감이 "하루 0.00003시간"으로 적혀 있는데, 실제 계산은 16s × 2회 = 32초 = 0.0089시간이다. 자릿수가 다르지만 결론(무시할 만한 값)은 그대로다. 힌트로 외울 때는 **"1.3시간 vs 32초"** 로 기억하면 안전하다.

이 구조는 33.5절 `ex5_where_time_goes.py`의 **암달의 법칙**과 같은 모양이다. 거기서는 한 요청의 1,919ms 중 모델 호출이 94.8%라서 나머지 여섯 구간을 전부 최대로 줄여도 3%밖에 안 준다. 여기서는 축이 "구간 비중"이 아니라 "쿼리별 총 시간 비중"일 뿐, **비중이 작은 것은 아무리 줄여도 전체가 안 변한다**는 같은 법칙이다.

## 4. 느린 쿼리 로그의 구조적 맹점

### 4-1. 왜 못 잡나 — 임계값은 '1회 지연'만 본다

느린 쿼리 로그(MySQL `slow_query_log`, PostgreSQL `log_min_duration_statement`, Neo4j `query.log` 임계값)는 **한 번의 실행 시간이 임계값을 넘었는가**만으로 기록 여부를 정한다. 판정식에 호출 수라는 항이 없다.

```
기록 조건:  1회 실행 시간 ≥ 임계값        ← 호출 수가 안 들어간다
아픔 정도:  1회 실행 시간 × 호출 수        ← 로그가 재지 않는 값
```

그래서 **호출 수가 아무리 커도 임계값 아래면 로그에는 단 한 줄도 남지 않는다.** 로그는 "이 쿼리는 존재한 적이 없다"고 말한다.

> 느린 쿼리 로그(slow query log)의 함정이 여기 있다.
> 임계값을 100ms 로 잡으면 1.2ms 짜리는 «한 번도 안 찍힌다».
> 제일 아픈 쿼리가 로그에 아예 안 나온다.

### 4-2. 임계값별로 로그가 커버하는 비중

ex4의 워크로드에 임계값을 대입해 본 결과:

| 임계값 | 로그에 찍히는 쿼리 | 커버하는 총 시간 | 놓치는 총 시간 |
|---|---|---|---|
| 100ms (공격적으로 낮춘 값) | 조직도 렌더, 감사 리포트, 커뮤니티 탐지 | 0.44h → **5.3%** | **94.7%** |
| 10s (MySQL `long_query_time` 기본값) | 감사 리포트, 커뮤니티 탐지 | 0.12h → **1.4%** | **98.6%** |

임계값을 100ms까지 내려도 로그는 인프라 시간의 **5%만** 본다. 기본값인 10초로 두면 **1.4%**다. 여기서 "느린 쿼리 로그를 다 비웠습니다"라고 보고해도 청구서와 CPU 사용률은 그대로다. 반대로 임계값을 1ms까지 내려서 모든 걸 잡으려 하면 하루 1,300만 줄이 쌓여서 로그 쓰기 자체가 새로운 부하가 된다. **임계값을 어디에 두든 이 도구로는 답이 안 나온다** — 잘못 설정한 게 아니라, 애초에 다른 질문에 답하는 도구다.

### 4-3. 그래서 무엇을 봐야 하나

> 그래서 봐야 할 지표는 «p99 지연»만이 아니라 «쿼리별 총 시간»이다.
>   느린 쿼리 로그  → 사용자가 «기다린다»고 느끼는 것을 찾는다
>   총 시간 순위    → 인프라를 «먹는» 것을 찾는다
>
> 둘 다 봐야 하고, 고치는 순서는 대개 후자가 먼저다.

버려야 할 도구가 아니라 **역할이 다른 도구**다. 둘 다 켜 두되, 튜닝 순서는 총 시간이 먼저다.

실무에서 총 시간을 얻는 방법:

- **PostgreSQL**: `pg_stat_statements` 확장. `calls`, `mean_exec_time`, 그리고 이미 곱해진 `total_exec_time`이 그대로 들어 있다. `ORDER BY total_exec_time DESC LIMIT 20`이 사실상 이 절 전체의 실행판이다.
- **MySQL**: Performance Schema의 `events_statements_summary_by_digest`(`COUNT_STAR`, `SUM_TIMER_WAIT`). 또는 slow log를 `pt-query-digest`로 돌리면 다이제스트별 합계를 내주는데, **임계값 위로 올라온 것만** 집계한다는 한계는 그대로다.
- **Neo4j / Kùzu 등**: 쿼리 로그를 다이제스트(파라미터를 뺀 쿼리 모양)로 정규화해서 `sum(duration)`으로 집계한다. 임계값 로깅이 아니라 **샘플링 + 합산**이 맞는 방식이다.
- **APM/트레이싱**: 스팬 이름별 `sum(duration)` 및 `count`. 여기서도 p99만 보지 말고 합계 컬럼을 정렬하라.

## 5. 왜 사람들이 계속 틀리나

이 실수는 게을러서 나오는 게 아니라 **도구와 보고 문화가 지연 쪽으로 편향돼 있어서** 나온다.

1. **눈에 띄는 것이 느린 것이다.** 31초짜리는 대시보드에서 빨갛게 튀고, 1.2ms짜리는 아무 색도 아니다.
2. **로그가 지연만 기록한다.** 4-1의 구조적 맹점. 데이터가 없으면 순위가 안 만들어진다.
3. **개선폭이 보고하기 좋다.** 33장 도입부의 문장 — "3주 동안 쿼리를 튜닝했습니다. 평균 지연이 9ms에서 4ms로 줄었어요." 그리고 33.5절의 지적 — "「쿼리를 9ms 에서 4ms 로 줄였습니다」는 보고하기 좋은 문장이다. 그런데 사용자는 1,919ms 를 1,914ms 로 줄인 것을 못 느낀다."
4. **1~3ms짜리는 이미 "빠르니까" 튜닝 대상이 아니라고 넘긴다.** 정확히 이 판단이 전체의 86%를 시야에서 지운다.

## 6. 한 걸음 더 — 총 시간도 최종 답은 아니다

33.4절(`ex3_cost_model.py`)이 곧바로 이 장면을 한 번 더 뒤집는다. 총 시간으로 줄을 세우면 인프라를 먹는 쿼리를 찾을 수 있지만, **청구서의 큰 칸은 대개 쿼리가 아니라 토큰**이다. 예제 워크로드에서 그래프 조회는 월 3.6억 회로 호출 수 1위인데 비용 비중은 아주 작고, 모델 호출은 월 158만 회(전체 호출의 0.1% 미만)로 비중이 압도적이다.

정리하면 **줄 세우는 축이 목적마다 다르다**:

| 목적 | 정렬 키 | 예제 |
|---|---|---|
| 사용자 체감 지연 줄이기 | p99 / max 지연 | 느린 쿼리 로그 |
| 인프라(코어) 아끼기 | 쿼리별 **총 시간** = 지연 × 호출 수 | `ex4_hot_query.py` |
| 청구서 줄이기 | 항목별 **비용** = 호출 수 × 단가(토큰 포함) | `ex3_cost_model.py` |
| 요청 전체를 빠르게 | 구간별 **비중** (암달의 법칙) | `ex5_where_time_goes.py` |

넷 다 "무엇을 먼저 고칠까"에 답하지만, 넷의 1위가 서로 다르다. 이 카드가 다루는 것은 두 번째 줄이고, 실수는 **첫 번째 줄의 도구(느린 쿼리 로그)로 두 번째 줄의 질문에 답하려 할 때** 생긴다.

## 7. 30초 요약

- **제일 느린 것** = 1회 지연이 큰 것. **제일 아픈 것** = 1회 지연 × 호출 수가 큰 것.
- ex4 실측: 제일 느린 커뮤니티 탐지(31초)는 하루 2번 돌아 총 0.017시간(0.2%). 제일 아픈 사용자 권한 계산(3.4ms)은 하루 280만 번 돌아 총 2.6시간(32%).
- 상위 셋이 86%를 먹는데 셋 다 1~3ms짜리 "빠른" 쿼리다.
- 권한 계산을 반으로 줄이면 하루 1.3시간, 커뮤니티 탐지를 반으로 줄이면 32초. 약 150배 차이.
- 느린 쿼리 로그는 **1회 지연만으로 기록 여부를 정하므로** 호출 수가 판정식에 없다. 100ms 임계값은 총 시간의 5%만, MySQL 기본값 10초는 1.4%만 커버한다.
- 둘 다 봐라. 다만 고치는 순서는 대개 총 시간이 먼저다.
