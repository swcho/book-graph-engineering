# `ex1`, `ex2`가 `COPY`로 적재하는 이유

**질문** — `ex1`, `ex2`가 데이터를 `COPY`로 적재하는 이유는 무엇인가?

**답** — 한 건씩 넣는 것보다 훨씬 빠르다. 그 자체가 33장에서 다루는 일괄 적재 이야기이기도 하다.

---

## 1. 원문이 말하는 것

33장 README의 실행 가이드에 이렇게 적혀 있습니다.

> `ex1`, `ex2` 는 데이터를 만드는 데 몇 초 걸립니다. `COPY` 로 일괄 적재해서
> 한 건씩 넣는 것보다 훨씬 빠릅니다. 그 자체가 33장에서 다루는 얘기이기도 합니다.

그리고 「한 장 요약」에도 같은 줄이 있습니다.

> 한 건씩 넣지 마세요. 일괄 적재가 수십 배 빠릅니다. 「그래프 DB가 느리다」는 결론의 상당수가 여기서 나옵니다.

즉 답이 두 겹입니다.

1. **실용적 이유** — 벤치마크 준비 단계가 몇 초 안에 끝나야 실험이 성립한다.
2. **자기 참조적 이유** — 준비 코드 자체가 33장이 가르치려는 교훈의 시연이다.

---

## 2. 코드가 실제로 하는 일

### `ex1_read_plan.py`

```python
c.execute("CREATE NODE TABLE Person(id INT64, name STRING, city STRING, PRIMARY KEY(id))")
c.execute("CREATE NODE TABLE Team(id INT64, name STRING, PRIMARY KEY(id))")
c.execute("CREATE REL TABLE Member(FROM Person TO Team, since STRING)")

for i in range(N_TEAMS):                       # 팀 80개는 CREATE 루프
    c.execute("CREATE (:Team {id:$i, name:$n})", {"i": i, "n": f"팀{i}"})

# 사람 8,000명 + 소속 엣지 8,000개는 CSV로 써 놓고 COPY
c.execute(f"COPY Person FROM '{d}/p.csv'")
c.execute(f"COPY Member FROM '{d}/m.csv'")
```

여기서 눈여겨볼 것은 **같은 코드 안에서 두 방식을 갈라 쓴다**는 점입니다.

| 대상 | 건수 | 방식 | 왜 |
|---|---|---|---|
| `Team` | 80 | `CREATE` 루프 | CSV 파일을 만드는 수고가 이득보다 큼 |
| `Person` | 8,000 | `COPY` | 건별이면 눈에 띄게 느려짐 |
| `Member` | 8,000 | `COPY` | 위와 같음 |

임계값 감각이 그대로 드러납니다. 수십 건이면 아무 방식이나 상관없고, 수천 건부터 갈라집니다.

### `ex2_index_effect.py`

```python
SIZES = [2000, 8000, 32000, 128000]
...
c.execute(f"COPY Person FROM '{d}/p{n}.csv'")
```

`ex2`는 크기가 다른 DB를 **네 개** 만듭니다. 합쳐서 2,000 + 8,000 + 32,000 + 128,000 = **170,000건**입니다. 그리고 README는 여기서 한 걸음 더 나가라고 권합니다.

> `SIZES` 를 백만 단위로 키우면 갈라집니다. 다만 실행이 오래 걸립니다.

백만 단위로 키우라는 권유가 성립하려면 적재가 선형으로만 늘어야 합니다. 건별 `CREATE`였다면 이 권유 자체가 불가능한 조언이 됩니다.

---

## 3. Kuzu `COPY FROM`은 왜 빠른가

`COPY`는 "`CREATE`를 대신 반복해 주는 편의 문법"이 아닙니다. 경로가 아예 다릅니다.

### 3.1 벌크 파서 — 문장 단위가 아니라 파일 단위

건별 `CREATE`는 매 건마다 전체 사이클을 다시 탑니다.

```
파싱 → 바인딩 → 플랜 수립 → 실행 → 커밋
```

8,000건이면 이 사이클을 8,000번 돕니다. `timed()`가 `reps=12`, `reps=40`으로 재는 그 쿼리 실행 비용을, 적재에서 8,000번 지불하는 셈입니다.

`COPY`는 **한 문장**입니다. 파싱·바인딩·플랜은 딱 한 번이고, 그 뒤로는 CSV 파일을 읽는 전용 리더가 돌 뿐입니다. Kuzu의 CSV 리더는 파일을 블록으로 쪼개 **여러 스레드가 병렬로 파싱**합니다. (그래서 따옴표 안에 개행이 든 CSV처럼 블록 경계를 안전하게 자를 수 없는 입력에는 병렬 경로가 안 걸린다는 제약이 알려져 있습니다.)

### 3.2 컬럼 단위 일괄 추가

Kuzu는 컬럼 기반 저장을 씁니다. `COPY`는 파싱한 값을 컬럼별 청크에 모아 두었다가 통째로 디스크에 붙입니다. 건별 `CREATE`는 행마다 각 컬럼 파일을 조금씩 건드립니다. 같은 바이트를 쓰더라도 쓰기 횟수와 페이지 접근 패턴이 완전히 다릅니다.

### 3.3 기본 키 인덱스를 마지막에 한꺼번에

`CREATE NODE TABLE Person(..., PRIMARY KEY(id))`는 기본 키 해시 인덱스를 만듭니다. 건별 삽입이면 인덱스에 **8,000번 개별 삽입**하고, 그때마다 재해시·리밸런싱 가능성이 붙습니다. `COPY`는 전체 키 집합을 알고 나서 인덱스를 **일괄 구축**할 수 있습니다. 크기를 미리 알고 짓는 자료구조가 한 건씩 자라는 자료구조보다 빠른 건 당연합니다.

### 3.4 트랜잭션과 WAL 고정비용

건별 `CREATE`를 `execute()`로 하나씩 부르면, Kuzu는 각각을 **자동 커밋 트랜잭션**으로 처리합니다. 트랜잭션 시작·WAL 기록·커밋·플러시가 건당 한 세트 붙습니다. `COPY`는 전체가 트랜잭션 하나입니다.

### 3.5 Python ↔ C++ 왕복

`ex1`, `ex2`는 Python 바인딩을 씁니다. `c.execute(...)`는 건당 FFI 경계를 넘고, 파라미터 딕셔너리를 Kuzu 값 타입으로 변환합니다. 8,000건이면 8,000번입니다. `COPY`는 한 번 넘어가고, 그다음은 전부 C++ 안에서 끝납니다.

### 3.6 정리

| 항목 | 건별 `CREATE` × N | `COPY` 1회 |
|---|---|---|
| 파싱·플랜 | N번 | 1번 |
| 트랜잭션/WAL | N번 | 1번 |
| FFI 왕복 | N번 | 1번 |
| 파싱 병렬화 | 없음 | 있음 (파일 블록 분할) |
| PK 인덱스 | 건별 삽입 N번 | 일괄 구축 1번 |
| 디스크 쓰기 | 행 단위 산발 | 컬럼 청크 단위 |

Kuzu 문서의 권고도 이 표와 같은 결론입니다. `CREATE`/`MERGE`는 "수천 노드 규모의 작은 그래프, 또는 산발적인 소량 추가·수정"용이고, 수백만 규모의 적재는 `COPY FROM`이 가장 빠른 길입니다.

## 4. 벤치마크 준비 코드로서의 실용적 이유

이게 이 카드의 핵심입니다. **`ex1`, `ex2`가 재려는 건 적재가 아닙니다.**

- `ex1`이 재려는 것: 같은 답을 내는 쿼리 A/B/C의 **플랜과 지연**. `CROSS_PRODUCT`가 3.4배를 만든다는 사실.
- `ex2`가 재려는 것: 기본 키 조회와 속성 조회의 **배수**. 그리고 그 배수가 작은 규모에서는 안 갈라진다는 사실.

측정 자체는 `timed()`가 `build()`와 분리돼 있으니 적재 시간이 결과 숫자를 오염시키지는 않습니다. 그럼에도 적재가 느리면 세 가지가 망가집니다.

**(1) 아무도 안 돌린다.** README가 "몇 초 걸립니다"라고 안내하는 것과 "몇 분 걸립니다"라고 안내하는 것은 예제의 성격을 바꿉니다. 독자가 `python3 ex2_index_effect.py`를 치고 결과를 기다릴 마음이 드는 임계가 있습니다.

**(2) 규모를 키우라는 권유가 무의미해진다.** `ex2`의 결론은 "이 규모에서는 파싱·계획 고정비용이 지배해서 인덱스 효과가 안 보인다"이고, 처방은 "`SIZES`를 백만 단위로 키워라"입니다. 적재가 건별이면 백만 건에서 준비만 수십 분이 됩니다. 실험 자체가 죽습니다.

**(3) 반복 실행이 안 된다.** 성능 측정은 한 번 재고 끝나지 않습니다. 조건을 바꿔 가며 여러 번 돌려야 하는데, 매 회차의 앞머리가 길면 반복이 끊깁니다.

이게 33장 전체를 관통하는 **암달의 법칙** 감각과 정확히 같은 모양입니다. `ex5`가 "모델 호출이 94.8%면 나머지를 다 줄여도 3%"라고 말하듯, 실험 스크립트에서도 "준비가 95%면 측정 구간을 아무리 다듬어도 체감이 안 바뀝니다".

## 5. 「그래프 DB가 느리다」는 오해의 상당수가 여기서 나온다

한 장 요약의 이 줄이 이 카드의 그림자입니다.

> 한 건씩 넣지 마세요. 일괄 적재가 수십 배 빠릅니다. 「그래프 DB가 느리다」는 결론의 상당수가 여기서 나옵니다.

흔한 실패 서사가 이렇습니다.

1. 그래프 DB를 처음 써 본다.
2. 파이썬 for 루프로 `CREATE`를 100만 번 돈다.
3. 30분이 지나도 안 끝난다.
4. "그래프 DB는 느리다"고 결론 내고 관계형으로 돌아간다.

측정한 건 그래프 DB의 조회 성능이 아니라 **자동 커밋 100만 번의 고정비용**입니다. 정확히 `ex2`가 가르치는 오해의 짝입니다. `ex2`는 "고정비용이 지배하는 규모에서 인덱스 효과를 재면 틀린 결론이 나온다"고 하고, 여기서는 "고정비용이 지배하는 방식으로 적재하고 DB를 평가하면 틀린 결론이 나온다"고 합니다. 둘 다 **측정 설계가 결론을 만든 경우**입니다.

관계형 세계에도 같은 짝이 있습니다. PostgreSQL의 `COPY`도 건별 `INSERT` 대비 자릿수 차이를 냅니다. 그래프 특유의 함정이 아니라, **일괄 경로를 가진 모든 저장소의 공통 사실**입니다.

## 6. `COPY`를 쓸 때 알아야 할 제약

`ex1`의 순서가 우연이 아닙니다.

```python
c.execute(f"COPY Person FROM '{d}/p.csv'")   # 먼저 노드
c.execute(f"COPY Member FROM '{d}/m.csv'")   # 그다음 엣지
```

- **엣지보다 노드가 먼저.** 관계 테이블 CSV의 앞 두 컬럼은 `FROM`/`TO` 노드의 **기본 키**입니다. 해당 노드가 아직 없으면 적재가 실패합니다. `ex1`의 `m.csv`가 `[i, i % N_TEAMS, "2026-01-01"]` 형태인 것도 이 규칙 때문입니다 — Person id, Team id, 그리고 `since` 속성.
- **파일 원본이 필요하다.** `COPY`는 CSV/Parquet 같은 파일(또는 지원 데이터소스)에서 읽습니다. 그래서 `ex1`, `ex2`가 굳이 `csv.writer`로 임시 CSV를 먼저 쓰는 것입니다. 메모리에 있는 데이터를 넣으려면 파일로 내리는 한 단계가 붙습니다 — 그럼에도 이 편이 빠릅니다.
- **기본 키가 있어야 한다.** Kuzu 노드 테이블은 기본 키를 요구하고, 그 위에 조회용 인덱스를 만듭니다. `COPY`는 이 인덱스를 일괄 구축합니다.
- **`COPY`는 빈 테이블에 넣을 때 가장 잘 듣는다.** 기존 테이블에 덧붙이는 것도 가능하지만, 최고 성능은 처음 채울 때 나옵니다. `ex1`, `ex2`는 매번 `tempfile.mkdtemp()`로 새 DB를 만들기 때문에 항상 이 최선 경로를 탑니다.
- **적재 후 정리도 함께.** 두 예제 다 끝에서 `shutil.rmtree(tmp, ignore_errors=True)`로 임시 DB와 CSV를 지웁니다.

## 7. 실무 체크리스트

- 초기 적재·마이그레이션·벤치마크 준비는 **무조건 일괄 적재**부터 검토한다.
- 건별 `CREATE`/`MERGE`는 **운영 중 산발적 소량 변경**에만 쓴다.
- 부득이하게 건별로 넣어야 하면, 최소한 **명시적 트랜잭션으로 묶어** 건당 커밋을 없앤다.
- 적재 시간이 아프면 먼저 물을 것은 "DB가 느린가"가 아니라 **"내가 일괄 경로를 쓰고 있나"**다.
- 벤치마크 스크립트를 쓸 때는 **측정 구간과 준비 구간의 시간 비율**을 먼저 보라. 준비가 지배하면 그 실험은 반복도 확장도 안 된다.

---

## 8. 한 줄 정리

`COPY`는 파싱·플랜·트랜잭션·FFI·인덱스 구축의 **고정비용을 건당이 아니라 파일당 한 번**만 지불하게 만듭니다. `ex1`, `ex2`가 이걸 쓰는 이유는 (1) 준비가 몇 초로 끝나야 예제가 실제로 돌아가고 규모를 키워 볼 수 있기 때문이고, (2) 그 선택 자체가 33장의 "한 건씩 넣지 마세요"를 코드로 보여 주기 때문입니다.
