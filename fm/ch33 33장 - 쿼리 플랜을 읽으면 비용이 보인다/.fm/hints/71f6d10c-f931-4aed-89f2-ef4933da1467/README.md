# 비용 모델의 예외 항목 — 체크포인트 쓰기

**Q. 비용 모델에서 예외적으로 인프라 비중을 키울 수 있는 항목은 무엇인가?**

**A. 체크포인트 쓰기다. 월 5억 4천만 회로 돌고, 쿼리가 아니라 구조(슈퍼스텝 줄이기)를 고쳐야 준다.**

---

## 1. 33장의 큰 그림 — "청구서의 큰 칸은 대개 다른 곳이다"

33.4절(`ex3_cost_model.py`)의 결론은 한 문장입니다.

> 쿼리를 *빠르게* 해도 비용은 거의 그대로다. 청구서의 큰 칸은 토큰이다.

예제의 월 워크로드를 그대로 계산하면 이렇게 나옵니다.

| 항목 | 월 호출 | 1회 ms | 코어 | 월 인프라 | 월 토큰 | 합계 비중 |
|---|---:|---:|---:|---:|---:|---:|
| 그래프 조회 | 360,000,000 | 2.4 | 0.3 | 14,880원 | 0원 | 0.0% |
| 벡터 검색 | 230,000,000 | 8.0 | 0.7 | 31,689원 | 0원 | 0.1% |
| 모델 호출(판단) | 1,400,000 | 1800 | 1.0 | 43,400원 | 35,935,200원 | **81.3%** |
| 모델 호출(추출) | 180,000 | 2400 | 0.2 | 7,440원 | 8,197,200원 | **18.5%** |
| **체크포인트 쓰기** | **540,000,000** | **4.2** | **0.9** | **39,060원** | 0원 | 0.1% |
| 이벤트 로그 쓰기 | 540,000,000 | 0.9 | 0.2 | 8,370원 | 0원 | 0.0% |
| 합계 | | | | 144,839원 | 44,132,400원 | 100% |

토큰이 **99.7%**, 인프라 전체가 **0.3%**입니다. 그래서 "쿼리 2ms → 1ms" 튜닝은 청구서를 안 바꿉니다.

**그런데 인프라 칸만 따로 줄을 세우면 순위가 달라집니다.**

| 인프라 항목 | 월 인프라 | 인프라 내 비중 |
|---|---:|---:|
| 모델 호출(판단) — 대기 시간 | 43,400원 | 30.0% |
| **체크포인트 쓰기** | **39,060원** | **27.0%** |
| 벡터 검색 | 31,689원 | 21.9% |
| 그래프 조회 | 14,880원 | 10.3% |
| 이벤트 로그 쓰기 | 8,370원 | 5.8% |
| 모델 호출(추출) | 7,440원 | 5.1% |

모델 호출이 차지하는 인프라는 "응답을 기다리는 동안 워커가 붙잡혀 있는 값"이라 사실상 모델 항목의 부속물입니다. 그걸 빼면 **체크포인트 쓰기가 인프라 1위**입니다. 그래프 조회(0.3코어)의 **3배**인 0.9코어를 혼자 먹습니다.

이게 "예외"라는 말의 뜻입니다.

- 규칙: 비용 = 토큰. 인프라는 반올림 오차.
- 예외: 체크포인트 쓰기. 지금은 0.1%지만 **인프라를 키우는 유일한 지렛대**이고, 이 항목만 호출 수가 구조적으로 늘어납니다.

원문의 마무리도 정확히 그렇게 조건부로 적혀 있습니다.

> 한 가지 예외가 있다. 체크포인트 쓰기가 월 5억 4천만 회로 도는데, **이게 늘어나면** 인프라 비중이 확 커진다. 21장에서 잰 그 값이다. 그리고 이건 «쿼리»가 아니라 «구조»를 고쳐야 준다. 슈퍼스텝을 줄이는 것이다.

## 2. 왜 호출 횟수 1위급인가 — 에이전트 스텝마다 상태를 저장하니까

전체 호출 16억 7,158만 회 중 체크포인트 쓰기가 **5억 4천만 회, 32.3%**입니다. 초당 **약 208회**를 쉬지 않고 씁니다.

숫자의 출처를 보면 왜 이렇게 큰지 바로 보입니다.

**체크포인트 쓰기 횟수 = 사용자 요청 수가 아니라, 슈퍼스텝(superstep) 경계 수입니다.**

에이전트 그래프는 요청 한 번에 노드를 여러 번 지납니다. 계획 → 도구 선택 → 그래프 조회 → 검증 → 재시도 → 응답 조립… 이 각각이 슈퍼스텝이고, **경계마다 체크포인터가 상태 스냅샷을 씁니다.**

```
사용자 요청 1회
  └─ 슈퍼스텝 12~30회
       └─ 각 경계마다 체크포인트 쓰기 1회
            └─ 이벤트 로그 쓰기 1회   ← 그래서 둘 다 540M으로 같다
```

예제에서 체크포인트 쓰기와 이벤트 로그 쓰기가 **똑같이 540,000,000회**인 게 힌트입니다. 둘 다 같은 이벤트(슈퍼스텝 완료)에 붙어 있으니까 횟수가 같습니다.

반대편과 비교하면 격차가 드러납니다.

| 비교 | 배수 |
|---|---:|
| 체크포인트 쓰기 ÷ 모델 호출 전체(158만) | **약 342배** |
| 체크포인트 쓰기 ÷ 그래프 조회(3.6억) | 1.5배 |
| 체크포인트 쓰기가 전체 호출에서 차지하는 비율 | 32.3% |

즉 "제일 많이 도는 것"은 그래프 조회가 아니라 **체크포인트 쓰기**입니다. 33장 본문이 "그래프 조회가 월 3억 6천만 회로 제일 많이 도는데"라고 말한 건 *조회* 계열 중에서 그렇다는 얘기고, 쓰기까지 합치면 순위가 뒤집힙니다.

그리고 **이 항목은 에이전트가 똑똑해질수록 늘어납니다.** 자율성을 높이는 방향(더 많은 도구 호출, 더 긴 추론 루프, 재시도·검증 단계 추가)이 전부 슈퍼스텝 수를 늘립니다. 다른 항목은 사용자 수에 비례해서 늘지만, 체크포인트 쓰기는 **사용자 수 × 요청당 슈퍼스텝 수**로 늘어서 증가율이 제일 가파릅니다.

## 3. 왜 쿼리 튜닝으로는 안 줄어드는가

비용 공식이 이렇습니다.

```
인프라 코어 = 월 호출 수 × 1회 지연(ms) ÷ 1000 ÷ (월 시간 × 3600)
              ~~~~~~~~~~   ~~~~~~~~~~~~~
              구조가 정함    쿼리·엔진이 정함
```

쿼리 튜닝은 오른쪽 `ms`만 건드립니다. 그런데 **체크포인트 쓰기의 `ms`에는 바닥이 있습니다.**

21장에서 실측한 결과가 그 바닥의 정체입니다.

> 32KB 까지는 배수가 2.0~2.8 로 거의 평평하다. 그 뒤에 꺾인다.
> 작은 구간에서는 «쓰기 호출 자체»가 지배하기 때문이다.
> **슈퍼스텝마다 트랜잭션을 여는 값이 상태 크기와 무관하게 붙는다.**
>
> 32KB 미만 — 상태를 줄여도 소용없다. «슈퍼스텝 수»를 줄여야 한다
> 32KB 이상 — 상태를 줄이는 게 바로 듣는다 (19장)

4.2ms의 대부분은 "무엇을 쓰느냐"가 아니라 **"트랜잭션을 여닫는 고정비"**입니다. 인덱스를 걸어도, 플랜을 고쳐도, 페이로드를 줄여도 이 고정비는 안 없어집니다. 33.2절에서 잰 "수천 개 규모에서는 파싱·계획 값이 지배해서 인덱스 효과가 안 보인다"와 정확히 같은 형태의 문제예요 — **고정비가 지배하는 구간에서는 가변비 최적화가 안 듣습니다.**

산수로 확인해 보면 이렇습니다.

- 4.2ms → 2.1ms로 **절반**을 깎았다고 치면: 39,060원 → 19,530원. 월 44,277,239원 청구서에서 **19,530원**, 즉 **0.04%p** 절감. 아무 일도 안 일어납니다.
- 반면 540,000,000회 → 180,000,000회로 **슈퍼스텝을 1/3**로 줄이면: 39,060원 → 13,020원 + **지연도 같이 1/3**로 줍니다. 그리고 이건 체크포인트만이 아니라 **이벤트 로그 쓰기(같은 540M), 스텝마다 붙는 모델 호출·그래프 조회까지 동시에** 줄입니다.

핵심: **`ms`를 반으로 줄이면 그 항목만 반이 되지만, 슈퍼스텝 수를 반으로 줄이면 슈퍼스텝에 매달린 모든 항목이 반이 됩니다.** 그래서 지렛대가 구조 쪽에 있습니다.

## 4. 21장 연결 — 슈퍼스텝 줄이기와 재실행 창의 맞교환

21장의 첫 문장이 "체크포인트는 슈퍼스텝 경계에만 찍힌다"입니다. 33장의 예외 항목은 그 문장의 청구서 버전이에요.

같은 사실을 두 방향에서 읽으면 이렇게 됩니다.

| 노드를 | 체크포인트 횟수 | 재실행 창(죽었을 때 다시 하는 일) | 인프라 비용 |
|---|---|---|---|
| **잘게** 쪼갬 | 늘어남 | 좁아짐 (좋음) | 커짐 (나쁨) |
| **굵게** 합침 | 줄어듦 | 넓어짐 (나쁨) | 작아짐 (좋음) |

21장 요약이 직접 경고합니다.

> 노드를 잘게 쪼개면 그 창이 좁아지지만 0이 되진 않습니다. **그리고 체크포인트 횟수가 늘어서 느려져요.**

그래서 "슈퍼스텝을 줄인다"는 건 공짜 최적화가 아니라 **내구성(durability)과 비용의 맞교환**입니다. 21장이 제시한 탈출구가 여기서 다시 쓰입니다.

> 창을 없애는 대신 *다시 해도 되게* 만듭니다. 그게 **멱등성**입니다.

멱등성을 확보하면 재실행 창이 넓어져도 안전하니까, **노드를 굵게 합쳐서 체크포인트 횟수를 줄일 수 있습니다.** 멱등성 → 굵은 노드 → 적은 슈퍼스텝 → 적은 체크포인트 쓰기, 이 순서입니다. 멱등성 없이 노드부터 합치면 장애 시 부작용이 두 번 나갑니다.

33장 예제 5(`ex5_where_time_goes.py`)에서도 같은 항목이 등장합니다.

| 구간 | ms | 비중 | 최대 절감 | 방법 |
|---|---:|---:|---:|---|
| 모델 호출 | 1,820 | 94.8% | 30% | 짧은 프롬프트·작은 모델 |
| **체크포인트 쓰기** | **34** | **1.8%** | **80%** | **상태 줄이기·슈퍼스텝 줄이기** |
| 응답 후처리 | 24 | 1.3% | 60% | 스트리밍 |
| 컨텍스트 조립 | 18 | 0.9% | 70% | 24장 — 참조만 싣기 |

한 요청 1,919ms 중 체크포인트 쓰기가 **두 번째로 큰 구간**이고, 절감 여지(80%)는 전 구간 중 제일 큽니다. 원문 마무리도 같습니다.

> 체크포인트 쓰기가 34ms 로 두 번째다. 여기는 «구조»를 고치면 크게 준다. 21장의 슈퍼스텝 얘기다. **그리고 이건 쿼리 튜닝이 아니라 그래프 설계 문제다.**

물론 암달의 법칙이 여기도 적용됩니다. 모델 호출을 그대로 두고 체크포인트만 27ms 깎아 봐야 전체의 1.4%입니다. **순서는 여전히 ① 모델 호출 횟수 → ② 모델 호출 시간 → ③ 나머지**입니다. 체크포인트 쓰기는 ③ 안에서 1등일 뿐입니다.

## 5. 완화책 — 구조 우선, 그다음이 쓰기 방식

효과가 큰 순서대로.

### (1) 슈퍼스텝 수 줄이기 — 유일한 근본 대책

- 연달아 돌면서 상태를 거의 안 바꾸는 노드들을 **하나로 합칩니다.** 검증 3단계를 한 노드에서 처리하면 체크포인트 3회가 1회가 됩니다.
- 루프 종료 조건을 조입니다(20장). 도는 횟수가 곧 체크포인트 횟수입니다.
- 라우팅으로 불필요한 분기를 건너뜁니다(25장).
- 선행 조건: **멱등성**(21장). 합친 노드가 중간에 죽어도 재실행이 안전해야 합니다.

### (2) 상태 크기 줄이기 — 단, 32KB 위에서만 듣습니다

- 21장 실측: **32KB 미만이면 상태를 줄여도 소용없습니다.** 먼저 재 보고, 어느 구간에 있는지 확인한 다음 손대세요.
- 32KB 이상이면 바로 듣습니다. 큰 페이로드를 상태에 넣지 말고 **참조(포인터)만 싣습니다**(19장, 24장). 원본은 오브젝트 스토리지·DB에 두고 키만 체크포인트에 넣는 식이죠.
- 매 스텝 전체 스냅샷 대신 **변경분만 쓰는(delta / 채널 단위 쓰기)** 체크포인터를 고릅니다.

### (3) 배치 쓰기

- 슈퍼스텝 N개분을 모아 **트랜잭션 한 번**으로 커밋합니다. 21장이 지목한 고정비(트랜잭션 여닫기)를 N분의 1로 나눕니다.
- **대가**: 배치 경계 사이에서 죽으면 그 N스텝이 통째로 날아갑니다. 재실행 창이 N배로 넓어집니다. 사실상 (1)의 "노드 합치기"를 런타임에서 하는 것이라, 필요한 안전장치도 같습니다 — 멱등성.

### (4) 비동기 / 지연 쓰기

- 체크포인트 쓰기를 큐에 넣고 그래프는 다음 스텝으로 진행합니다. **지연(ms)은 확실히 줍니다.**
- **대가가 큽니다.** "쓰기 완료"와 "진행"이 분리되는 순간, 프로세스가 죽으면 큐에 남은 체크포인트는 사라집니다. 21장이 경고한 그 실패 모드에 가까워집니다.

  > 메모리 체크포인터는 체크포인터가 아니라 캐시입니다. 개발 중에는 완벽하게 동작하고 배포하는 날 죽습니다.

  비동기 쓰기는 "약간의 캐시화"입니다. **내구성이 정말 필요한 경계(외부 부작용 직전·직후)에서는 반드시 동기로 씁니다.**

### (5) 쓰기 자체를 싸게 만들기

- **WAL 모드**(SQLite `journal_mode=WAL`)로 트랜잭션 고정비를 낮춥니다.
- 체크포인트 저장소를 워크로드에 맞게 고릅니다. 21장 실측으로 SQLite는 메모리 대비 2.0~2.8배(32KB 초과 시 4.8배)입니다. Postgres·Redis 등 선택지가 다릅니다.
- **체크포인트 이력 정리(pruning / TTL)**. 스레드마다 모든 스텝의 스냅샷을 영구 보관하면 저장 비용이 계속 쌓입니다. 33장 모델에는 스토리지 단가(33원/GB·월)가 잡혀 있지만 워크로드에 반영이 안 돼 있는데, 실제로는 여기가 조용히 자랍니다.
- 필요 없는 채널은 **체크포인트 대상에서 제외**합니다(휘발 채널 / `ephemeral` 지정).

### (6) 그리고 재 봅니다

- 33장의 원칙 그대로 **"제일 느린 것"이 아니라 "총 시간이 큰 것"**으로 줄을 세웁니다. 4.2ms짜리 체크포인트 쓰기는 느린 쿼리 로그 임계값 100ms에 **한 번도 안 찍힙니다.** 5억 4천만 번 도는 항목이 로그에 아예 안 나오는 거죠.
- 21장의 마무리도 잊지 마세요. **`kill -9` 한 번**으로 완화책이 내구성을 망가뜨리지 않았는지 확인합니다. 배치·비동기 쓰기를 넣었다면 특히요.

## 6. 한 줄 정리

| | |
|---|---|
| **무엇** | 체크포인트 쓰기 |
| **왜 예외** | 청구서의 99.7%는 토큰인데, 인프라 칸에서는 이게 1위급(27%)이고 유일하게 구조적으로 증가한다 |
| **왜 그렇게 많나** | 사용자 요청당이 아니라 **슈퍼스텝 경계마다** 찍히므로 월 5.4억 회, 전체 호출의 32.3% |
| **왜 쿼리 튜닝이 안 듣나** | 4.2ms의 대부분이 **상태 크기와 무관한 트랜잭션 고정비**(21장) — 가변비를 깎아도 안 내려간다 |
| **무엇을 고치나** | **슈퍼스텝 수**. 노드를 합치고 루프를 조인다. 선행 조건은 멱등성(21장) |
| **완화책** | 슈퍼스텝 줄이기 > 상태 줄이기(32KB 초과 시) > 배치 쓰기 > WAL·저장소 선택 > 비동기 쓰기(내구성 대가 큼) |
| **잊지 말 것** | 그래도 모델 호출이 94.8%다. 암달의 법칙 — 순서는 ① 모델 호출 횟수, ② 모델 호출 시간, ③ 나머지 |
