# 쿼리 B와 C의 성능이 거의 같은 이유

## 질문

쿼리 B(팀에서 시작)와 C(사람에서 시작)의 성능이 거의 같은 이유는 무엇인가?

## 답

엔진이 어느 쪽에서 시작할지 알아서 정한다. 저자도 이걸 오래 튜닝 포인트로 알았지만 재 보니 아니었다.

---

## 무엇을 비교한 실험인가

`ex1_read_plan.py`는 사람 8,000명, 팀 80개, 소속 엣지 8,000개를 만들어 놓고
**같은 답을 내는 쿼리 셋**의 시간과 플랜을 나란히 놓습니다. 셋 다
「마포에 사는 팀7 구성원 수」를 세고, 답은 셋 다 100입니다.

```cypher
-- A. 두 끝을 따로 찾음
MATCH (p:Person), (t:Team)
WHERE t.name = '팀7' AND p.city = '마포'
  AND EXISTS { MATCH (p)-[:Member]->(t) }
RETURN count(p)

-- B. 팀에서 시작
MATCH (t:Team {name:'팀7'})<-[:Member]-(p:Person)
WHERE p.city = '마포'
RETURN count(p)

-- C. 사람에서 시작
MATCH (p:Person {city:'마포'})-[:Member]->(t:Team)
WHERE t.name = '팀7'
RETURN count(p)
```

결과:

| 쿼리 | 답 | 상대 시간 |
|---|---|---|
| A. 두 끝을 따로 찾음 | 100 | B·C의 약 3.4배 |
| B. 팀에서 시작 | 100 | 기준 |
| C. 사람에서 시작 | 100 | B와 거의 동일 |

B와 C는 **패턴을 쓴 방향이 정반대**입니다. B는 팀 1개에서 출발해 엣지를
거슬러 올라가고, C는 마포 사람 2,000명에서 출발해 엣지를 따라 내려갑니다.
「작은 쪽에서 시작하라」는 통념대로면 B가 압도적으로 빨라야 합니다.
그런데 거의 같습니다.

---

## 왜 같은가 — 작성 순서는 실행 순서가 아니다

핵심은 이겁니다.

> **쿼리에 쓴 순서는 「무엇을 원하는가」이지 「어떻게 하는가」가 아니다.**

Cypher, SQL 같은 선언형 질의 언어에서 `MATCH` 절에 쓴 순서는 **결과의 정의**일
뿐입니다. 그걸 실제 연산 순서로 바꾸는 것은 사람이 아니라 엔진 안의
**쿼리 옵티마이저(query planner/optimizer)**입니다.

B와 C는 논리적으로 완전히 같은 것을 요구합니다.

```
{ (p, t) | p:Person, t:Team, (p)-[:Member]->(t), p.city='마포', t.name='팀7' }
```

이 집합의 정의에는 「누가 먼저」가 없습니다. 방향을 어느 쪽으로 썼든 옵티마이저는
같은 논리 표현으로 정규화한 뒤 **자기가 유리하다고 판단한 순서로 다시 짭니다.**
그래서 B와 C의 최종 물리 플랜은 사실상 같은 모양이 되고, 시간도 같습니다.

`ex1`이 EXPLAIN에서 연산자만 뽑아 아래에서 위로(= 실행 순서로) 찍어 보는 것도
이걸 눈으로 확인시키려는 장치입니다. **쓴 순서와 찍히는 순서가 다릅니다.**

---

## 옵티마이저는 무엇으로 판단하나 — 비용 기반 최적화

요즘 엔진은 대부분 **비용 기반 옵티마이저(CBO, cost-based optimizer)**입니다.
동작 얼개는 이렇습니다.

### 1. 통계를 갖고 있다

엔진은 카탈로그에 **카디널리티 통계(cardinality statistics)**를 유지합니다.

- 각 노드 테이블의 행 수 (Person 8,000, Team 80)
- 각 관계 테이블의 엣지 수 (Member 8,000)
- 속성별 선택도(selectivity) — `city='마포'`이 전체의 몇 분의 1인지,
  `name='팀7'`이 몇 건을 남기는지
- 관계의 팬아웃(평균 차수) — 팀 하나에 사람 몇 명이 달려 있는지

### 2. 후보 플랜의 비용을 추정한다

같은 결과를 내는 여러 실행 순서(조인 순서, 조인 알고리즘, 스캔 방식)를
열거하고, 각각에 대해 **중간 결과 크기 × 처리 단가**로 비용을 추정합니다.

이 예제에서 옵티마이저가 보는 것은 대략 이렇습니다.

| 시작점 | 첫 필터 후 크기 | 그다음 |
|---|---|---|
| Team에서 `name='팀7'` | 80 → **1** | 엣지 100개 확장 → city 필터 → 100 |
| Person에서 `city='마포'` | 8,000 → **2,000** | 엣지 2,000개 확장 → 팀 필터 → 100 |

숫자만 보면 Team 쪽이 훨씬 싸 보입니다. 그래서 옵티마이저는
**C처럼 써 놓아도 Team 쪽을 시작점으로 고르는 플랜**을 선택할 수 있습니다.
결과적으로 B와 C가 같은 플랜으로 수렴합니다.

### 3. 조인 순서를 재작성한다

이게 관계형 DB의 **조인 순서 최적화(join reordering)**와 정확히 같은 얘기입니다.
`A JOIN B JOIN C`를 쓴 순서대로 실행하는 DB는 없습니다. 옵티마이저가
선택도가 높은(= 남는 게 적은) 조인을 먼저 밀어 중간 결과를 줄입니다.
그래프 엔진에서는 이 조인이 「관계 확장(expand)」이라는 이름으로 나타날 뿐,
원리는 동일합니다.

그래서 이 장의 한 줄 요약이 이렇게 됩니다.

> 「작은 쪽에서 시작하라」는 요즘 엔진에서는 대개 상관없습니다.
> 플래너가 알아서 정해요. **순서를 고민하기 전에 플랜을 보세요.**

### 4. 다만 「대개」다 — 통계가 틀리면 플랜도 틀린다

옵티마이저의 판단은 통계 추정에 얹혀 있습니다. 그래서:

- 통계가 오래됐거나 없으면 → 추정이 빗나가고 나쁜 플랜을 고릅니다.
- 속성 사이에 상관관계가 있으면 → 독립 가정으로 곱한 선택도가 실제와 크게 어긋납니다.
- 여러 홉을 지나면 → 추정 오차가 홉마다 곱해져서 커집니다.

그리고 결정적으로, 데이터가 자라면 **엔진의 선택 자체가 바뀝니다.**
본문의 마지막 문장이 그 얘기입니다.

> 팀이 80개가 아니라 80만 개가 되면 엔진의 선택이 바뀐다.
> 데이터가 자라면 플랜도 다시 봐야 한다.

즉 「B와 C가 같다」는 것은 **이 데이터 분포에서 옵티마이저가 잘 골랐다**는
관찰이지, 영원한 법칙이 아닙니다. 그래서 결론은 「순서를 신경 쓸 필요 없다」가
아니라 「순서를 손으로 고민하는 대신 **플랜을 재라**」입니다.

## 그럼에도 플래너가 못 고치는 것 — 쿼리 A와 CROSS_PRODUCT

B와 C가 같은데, A만 3.4배 느립니다. 여기가 이 카드의 진짜 대비 지점입니다.

```cypher
MATCH (p:Person), (t:Team)          -- 두 패턴이 쉼표로 분리되어 있다
WHERE t.name = '팀7' AND p.city = '마포'
  AND EXISTS { MATCH (p)-[:Member]->(t) }
RETURN count(p)
```

A의 플랜에는 **`CROSS_PRODUCT`**가 들어 있습니다. 곱집합입니다.
사람 8,000명 × 팀 80개 = 640,000쌍을 만들어 놓고 거기서 거릅니다.

### 왜 플래너가 이건 못 고치나

B·C와 A의 차이는 **최적화 난이도가 아니라 쿼리가 표현한 구조**입니다.

- B·C: `MATCH` 안에서 두 노드가 **하나의 연결된 패턴**으로 묶여 있습니다.
  `(t)<-[:Member]-(p)` 는 「이 엣지를 따라가라」는 명시적 경로입니다.
  옵티마이저는 이 엣지를 **조인 조건**으로 알아보고, 어느 끝에서 출발할지만
  고르면 됩니다. 어느 쪽을 골라도 중간 결과가 폭발하지 않습니다.

- A: `(p:Person), (t:Team)` 는 **연결되지 않은 두 패턴**입니다.
  둘을 잇는 조건이 `MATCH` 절이 아니라 `WHERE` 안의 `EXISTS { ... }`
  서브쿼리 안에 숨어 있습니다. 플래너 입장에서 `MATCH` 절이 요구한 것은
  「모든 Person과 모든 Team의 조합」이고, 그 위에 필터가 얹힌 형태입니다.
  이걸 「사실은 조인이었다」고 되돌리려면 서브쿼리를 풀어헤쳐 조인 조건으로
  끌어올리는(decorrelation / subquery unnesting) 재작성이 필요한데,
  이건 엔진마다 되기도 하고 안 되기도 합니다. 안 되면 곱집합이 그대로 남습니다.

정리하면 이렇게 대비됩니다.

| | 플래너가 고쳐 주는 것 | 사람이 고쳐야 하는 것 |
|---|---|---|
| 무엇 | **실행 순서** (어느 쪽에서 시작할지, 조인 순서) | **쿼리가 표현한 구조** (연결되지 않은 패턴, 숨은 조인 조건) |
| 근거 | 카디널리티 통계 + 비용 추정 | 사람이 관계를 명시적으로 써 주는 것 |
| 증상 | (증상 없음 — 알아서 됨) | 플랜의 `CROSS_PRODUCT` |
| 예 | B ↔ C | A |
| 데이터가 자라면 | 플랜을 다시 고름 | **곱으로 커짐** |

### 왜 이게 무서운가

`CROSS_PRODUCT`는 지금 3.4배지만 **곱으로 커집니다.**
사람 8,000 × 팀 80 = 64만이 사람 80만 × 팀 80 = 6,400만이 됩니다.
쿼리는 안 바꿨는데 데이터가 100배 되면 비용은 100배가 아니라 그 이상으로
튑니다. 반면 B·C 같은 연결된 패턴은 시작점 하나를 인덱스로 찾고 나머지는
관계를 따라가므로 실제로 만나는 데이터 양에 비례해서만 늡니다.

그래서 이 장은 플랜에서 볼 것을 셋으로 정리합니다.

1. **`CROSS_PRODUCT`가 있나** — 있으면 거기부터 고친다
2. **`SCAN`이 무엇을 훑나** — 인덱스를 타나, 전체를 훑나
3. **`FILTER`가 `SCAN` 앞인가 뒤인가** — 뒤면 훑고 나서 버리는 것이다

`CROSS_PRODUCT`가 1번인 이유가 이겁니다. 2·3번은 대체로 정도의 문제인데,
1번은 데이터가 자라면 차수 자체가 달라지는 문제입니다.

### CROSS_PRODUCT를 유발하는 패턴

사람이 눈으로 잡아야 하는 신호들입니다.

- `MATCH (a), (b)` — 쉼표로 나열했는데 둘을 잇는 관계 패턴이 없다
- 연결 조건을 `MATCH`가 아니라 `WHERE`나 `EXISTS { }` 안에 넣었다
- `MATCH (a)-[]->(b) MATCH (c)-[]->(d)` — 두 `MATCH` 블록이 변수를 공유하지 않는다
- `OPTIONAL MATCH`나 `WITH` 뒤에서 실수로 바인딩이 끊겼다

고치는 방법은 하나입니다. **두 끝을 잇는 관계를 `MATCH` 패턴 안에 명시적으로
써 준다.** A를 B나 C처럼 고치면 됩니다. 어느 쪽으로 쓰든 상관없다는 게
바로 이 카드의 답이니까요.

## 이 카드가 말하는 실무 태도

저자가 「오래 이걸 튜닝 포인트로 알고 있었는데, 재 보니 아니었다」고 쓴 게
이 장 전체의 태도입니다. 7부 운영의 첫 규칙이 **재고 나서 고치기**입니다.

- **머릿속 모델을 튜닝 대상으로 삼지 않는다.** 「작은 쪽에서 시작하라」는
  옵티마이저가 미숙하던 시절의 규칙이고, 지금은 대부분 엔진이 알아서 합니다.
  손으로 방향을 바꿔 가며 튜닝하는 시간은 대개 버리는 시간입니다.
- **대신 플랜을 읽는다.** `EXPLAIN`을 붙여 연산자를 보면
  「엔진이 이미 해 준 것」과 「엔진이 못 해 준 것」이 갈립니다.
  못 해 준 것만 고치면 됩니다.
- **그리고 잰다.** 33장의 다른 예제들이 이어서 말하는 것도 같습니다.
  인덱스 효과는 규모를 키워야 보이고(`ex2`), 「제일 느린 것」과
  「제일 아픈 것」은 다르며(`ex4`), 애초에 쿼리 튜닝이 청구서를 바꾸는
  일이 아닐 수도 있습니다(`ex3`, `ex5`).

한 줄로:

> **엔진이 순서는 알아서 정한다. 사람이 할 일은 엔진이 못 고치는 구조,
> 즉 플랜에 찍힌 `CROSS_PRODUCT`를 없애는 것이다.**
