# `ex5_where_time_goes.py`에서 모델 호출은 전체 시간의 몇 %인가?

**답: 94.8%.** 나머지 여섯 구간을 전부 최대로 줄여도 약 60ms(정확히는 63.1ms), 총 1,919ms의 3%밖에 안 준다.

---

## 1. 예제가 가정한 한 요청의 시간 분해

`ex5_where_time_goes.py`의 `SEGMENTS`는 (구간, 1회 ms, 최대 절감률, 방법) 네 값을 갖는다.
「최대 절감률」은 그 구간을 **현실적으로 최대한 다듬었을 때** 줄일 수 있는 비율이다.

| 구간 | ms | 비중 | 최대 절감률 | 줄이면 | 방법 |
|---|---:|---:|---:|---:|---|
| 입력 검증 | 3 | 0.16% | 0% | 0ms | 이미 최소 |
| 그래프 조회 ×4 | 9 | 0.47% | 50% | 4.5ms | 인덱스·플랜 |
| 벡터 검색 | 11 | 0.57% | 40% | 4.4ms | 차원 축소·근사 |
| 컨텍스트 조립 | 18 | 0.94% | 70% | 12.6ms | 24장 — 참조만 싣기 |
| **모델 호출** | **1,820** | **94.84%** | 30% | 546ms | 짧은 프롬프트·작은 모델 |
| 응답 후처리 | 24 | 1.25% | 60% | 14.4ms | 스트리밍 |
| 체크포인트 쓰기 | 34 | 1.77% | 80% | 27.2ms | 상태 줄이기·슈퍼스텝 줄이기 |
| **합계** | **1,919** | 100% | — | 609.1ms | — |

비중 계산: 1820 / 1919 = 0.94841… → **94.8%**.

---

## 2. 「나머지 전부」의 상한이 왜 3%인가 — 산수

### (a) 현실적 상한: 각 구간을 자기 최대 절감률까지

```
4.5 + 4.4 + 12.6 + 14.4 + 27.2 + 0 = 63.1 ms
63.1 / 1,919 = 3.288%  →  약 3%
```

코드의 마지막 출력이 이 값이다.

```python
all_save = sum(ms * r for _n, ms, r, _h in SEGMENTS)   # 609.1
print(all_save - 1820 * 0.3)                           # 609.1 - 546 = 63.1ms → 3.3%
```

요청 시간은 1,919ms → 1,855.9ms가 된다. 사용자는 이 차이를 느끼지 못한다.

### (b) 물리적 상한: 나머지 여섯을 **0ms**로 만들어도

```
3 + 9 + 11 + 18 + 24 + 34 = 99 ms
99 / 1,919 = 5.16%
```

즉 검증·조회·검색·조립·후처리·체크포인트를 **전부 공짜로 만드는 마법**이 있어도 5.2%다.
「3%」는 현실적 상한, 「5.2%」는 이론적 천장이다. 어느 쪽이든 두 자릿수가 안 나온다.

### (c) 반대로 모델 호출만 30% 줄이면

```
546 / 1,919 = 28.5%   →  1,919ms → 1,373ms
```

한 구간을 30% 손봤을 뿐인데 나머지 여섯을 이론적 극한까지 짜낸 것의 **5배 이상**이다.

### (d) 도입부의 「9ms → 4ms」

3주짜리 쿼리 튜닝 무용담이 이 표에서는 「그래프 조회 ×4」 한 줄이다.
9ms → 4ms는 5ms 절감, 1,919 → 1,914ms, **0.26%**. 보고서에는 "지연 55% 감소"라고 쓸 수 있고, 그건 거짓말이 아니다. 다만 분모가 틀렸을 뿐이다.

## 3. 형식화 — 암달의 법칙

이 계산은 즉흥적인 산수가 아니라 1967년 진 암달(Gene Amdahl)이 정리한 법칙 그대로다.

$$S = \frac{1}{(1-p) + \dfrac{p}{s}}$$

- $p$ : 전체 시간 중 **개선 대상이 차지하는 비율**
- $s$ : 그 부분을 몇 배 빠르게 만드는가 (speedup factor)
- $S$ : 전체 시스템의 speedup

핵심 성질은 극한에 있다. $s \to \infty$ 여도

$$S_{\max} = \frac{1}{1-p}$$

즉 **손대지 않은 $1-p$ 가 천장을 못 박는다.**

### 이 예제에 대입

**케이스 1 — 모델 호출을 빼고 전부 최적화** ($p = 99/1919 = 0.0516$)

- 무한히 빠르게 해도: $S_{\max} = 1/(1-0.0516) = 1/0.9484 = \mathbf{1.054}$ → 5.4% 개선이 천장
- 현실 절감(63.1ms)만 반영하면: $S = 1919/1855.9 = \mathbf{1.034}$ → 3.4%

**케이스 2 — 모델 호출만 30% 단축** ($p = 0.948$, $s = 1/0.7 = 1.4286$)

$$S = \frac{1}{0.0516 + \frac{0.948}{1.4286}} = \frac{1}{0.0516 + 0.6637} = \frac{1}{0.7153} = \mathbf{1.398}$$

1,919 / 1.398 = 1,373ms. 위 (c)의 산수와 정확히 일치한다.

**케이스 3 — 모델 호출을 캐시로 아예 없앰** ($s \to \infty$, $p = 0.948$)

$$S_{\max} = 1/(1-0.948) = \mathbf{19.4\times}$$

그래서 33.5절의 순서가 이렇게 나온다.

1. 모델 호출 **횟수**를 줄인다 — 캐시, 라우팅(25장), 종료 조건(20장)
2. 모델 호출 **시간**을 줄인다 — 짧은 프롬프트, 작은 모델, 스트리밍
3. 그다음에 나머지를 본다

3번을 1번보다 먼저 하는 팀이 많다. 익숙하고, 재기 쉽고, 성과가 눈에 보여서다.

## 4. 선행 조건 — 구간별 계측(트레이싱·스팬)이 없으면 이 표 자체가 없다

이 장에서 조용히 지나가지만 사실 제일 중요한 전제다. **94.8%라는 숫자는 재야 나온다.**

- 전체 요청 시간(1,919ms) 하나만 찍혀 있으면 알 수 있는 건 "느리다"뿐이다. 어디가 느린지는 모른다.
- 모르면 **아는 곳**을 고친다. 그리고 엔지니어가 아는 곳은 대개 자기가 짠 쿼리다. 그래서 3주 동안 9ms를 4ms로 줄이는 일이 벌어진다.
- 그래서 성능 작업의 0단계는 튜닝이 아니라 **구간별 스팬(span)을 심는 것**이다. 요청 하나를 트레이스(trace)로 잡고, 검증·조회·검색·조립·모델·후처리·체크포인트를 각각 자식 스팬으로 나눠 시간을 붙인다. OpenTelemetry 같은 분산 트레이싱이 표준적인 도구다.
- 스팬이 있어야 $p$ 를 실측할 수 있고, $p$ 가 있어야 암달의 법칙을 적용할 수 있고, 그래야 **어디를 고칠지**가 정해진다. 순서는 **계측 → 분해 → $p$ 산출 → 튜닝**이지, 그 반대가 아니다.
- 병렬 구간이 있으면 스팬 시간의 단순 합이 총 시간과 다를 수 있으니, 크리티컬 패스 기준으로 봐야 한다. (이 예제는 순차 파이프라인으로 단순화했다.)

## 5. 33장 안에서의 위치 — ex3·ex4와 같은 뼈대

세 예제는 전부 「분모를 먼저 보라」는 같은 말을 다른 축으로 한다.

| 예제 | 축 | 줄 세우는 값 | 결론 |
|---|---|---|---|
| `ex3_cost_model.py` | 돈 | 인프라비 + 토큰비 | 청구서의 큰 칸은 쿼리가 아니라 **토큰**이다 |
| `ex4_hot_query.py` | 인프라 시간 | 1회 지연 × 호출 수 | 「제일 느린 것」(커뮤니티 탐지 31초, 하루 2회)과 「제일 아픈 것」(권한 계산 3.4ms, 하루 280만 회, 전체의 32%)은 다르다 |
| `ex5_where_time_goes.py` | 사용자 체감 지연 | 구간별 시간 비중 | **94.8%를 차지하는 구간을 안 건드리면 안 빨라진다** |

한 가지 덧붙이면, 두 번째로 큰 구간은 **체크포인트 쓰기 34ms(1.77%)**이고 절감 여지가 80%로 제일 크다. 다만 27.2ms다. 그리고 이건 쿼리 튜닝으로 주는 게 아니라 상태를 줄이고 슈퍼스텝을 줄이는 **그래프 설계 문제**다(21장).

## 한 줄 정리

**94.8%.** 나머지 여섯 구간을 최대로 줄여봐야 63.1ms(3.3%), 0ms로 만들어도 99ms(5.2%)다. 암달의 법칙 $S = 1/((1-p)+p/s)$ 에서 $1-p = 0.052$ 가 천장을 5.4배… 가 아니라 1.054배로 못 박는다. 그리고 이 $p$ 를 알려면 구간별 트레이싱이 먼저 있어야 한다.
