# `ex3`~`ex5`의 숫자를 어떻게 다뤄야 하는가?

> **한 줄 답**
> 저자 환경 실측을 단순화한 **예시 워크로드**다. 그대로 인용하지 말고 자기 시스템 값을 넣어 다시 돌려야 한다.
> **구조가 요점이지 숫자가 요점이 아니다.**

원문(README 실행 가이드)에 이렇게 적혀 있다.

> `ex3`~`ex5` 의 숫자는 저자 환경의 실측을 단순화한 "예시 워크로드"입니다.
> 여러분 시스템의 값을 넣어서 다시 돌려 보세요. 구조가 요점이지 숫자가 요점이 아닙니다.

`ex1`, `ex2`는 실제로 Kuzu를 띄워 **재는** 코드다. 반면 `ex3`~`ex5`는 의존성이 없다 — 파일 맨 위 상수 테이블에 이미 답이 박혀 있고, 코드는 그 상수를 산술로 굴려서 보여줄 뿐이다. 그러니까 이 셋은 **측정 도구가 아니라 계산기 템플릿**이다. 당신이 넣을 입력이 비어 있는 상태로 배포된 계산기다.

---

## 1. 왜 그대로 쓰면 안 되는가 — 통째로 흔들리는 축들

`ex3`~`ex5`의 상수는 최소 다섯 개 축에서 환경 의존적이다.

### (a) 하드웨어·런타임 → `ms` 값

`ex3`의 `그래프 조회 2.4ms`, `ex5`의 `그래프 조회 ×4 = 9ms`는 저자의 머신에서 임베디드 DB(같은 프로세스)로 잰 값이다. 당신 환경이 이렇게 다르면 그대로 안 맞는다.

- **네트워크 홉**: DB가 별도 서버면 왕복 RTT가 붙는다. 2.4ms짜리가 사내망만 타도 3~5ms가 되고, 리전이 다르면 수십 ms가 된다.
- **데이터 규모**: `ex1`/`ex2`가 직접 보여준 교훈이다. 수천 건에서는 파싱·플래닝 고정비가 지배해서 인덱스 효과가 안 보인다. 규모가 백만 단위로 커지면 `ms` 값의 서열 자체가 바뀐다.
- **콜드/웜, 캐시 히트율, 동시성**: 무경합 단일 스레드 벤치와 p99 경합 상태는 다른 숫자다.

### (b) 모델 단가 → `TOKEN_KRW_PER_1K`

```python
KRW = 1_380
TOKEN_KRW_PER_1K = 3.0 / 1000 * KRW      # 입력 기준 → 4.14원/1K 토큰
```

이 한 줄에 가정이 세 개나 숨어 있다.

1. **1M 입력 토큰당 $3** — 중급 모델 기준값이다. 경량 모델을 쓰면 1/10 이하, 플래그십이면 몇 배다. 게다가 모델 단가는 몇 달 단위로 개정된다.
2. **입력만 센다** — `WORKLOAD`에 `tokens` 필드가 하나뿐이다. 출력 토큰은 보통 입력의 3~5배 단가이므로, 출력이 긴 워크로드(생성·요약)라면 이 모델은 비용을 **과소**추정한다.
3. **환율 1,380원/달러** — 환율은 그냥 흔들린다.

여기에 프롬프트 캐싱(캐시 읽기 토큰은 훨씬 쌈), 배치 API 할인, 볼륨 약정 같은 게 들어오면 실효 단가는 정가표와 또 달라진다.

### (c) 인프라 단가 → `CPU_KRW_PER_CORE_HOUR = 62`

온디맨드/스팟/예약 인스턴스/온프레 감가상각 중 무엇이냐에 따라 몇 배가 갈린다. 그리고 이 모델은 **가동률 100%**를 가정한다.

```python
def cpu_cores(calls, ms):
    return calls * ms / 1000.0 / (HOURS * 3600)
```

이건 "일이 완벽히 균등하게 퍼져서 코어가 쉬는 시간이 없다"는 뜻이다. 실제 서비스는 피크가 있어서 피크 기준으로 프로비저닝하므로, 실무 코어 수는 이 값을 목표 가동률(예: 0.4)로 **나눈** 값에 가깝다. 즉 인프라 비용은 이 모델이 체계적으로 낮게 잡는다.

### (d) 트래픽 패턴 → `calls`

`그래프 조회 3억 6천만 회/월`, `체크포인트 쓰기 5억 4천만 회/월` 같은 값은 저자 시스템의 부하 프로파일이다. 에이전트 시스템에서 이 비율은 **아키텍처가 결정한다** — 슈퍼스텝 수, 재시도 정책, 캐시 히트율, 툴 호출 루프의 평균 반복 횟수가 다르면 호출 수 비율이 통째로 달라진다.

### (e) 절감 가능률 → `ex5`의 세 번째 컬럼

```python
("컨텍스트 조립",    18,    0.7,  "24장 — 참조만 싣기"),
("모델 호출",     1_820,   0.3,  "짧은 프롬프트·작은 모델"),
```

`0.7`, `0.3` 같은 값은 측정치가 아니라 **저자의 낙관/비관 추정**이다. 재는 값이 아니라 거는 값이다. 이 컬럼은 특히 자기 값으로 바꿔야 한다.

### (f) 아예 빠져 있는 항목

`ex3`에는 `STORAGE_KRW_PER_GB_MONTH = 33`이 선언돼 있지만 **`main()`에서 한 번도 쓰이지 않는다.** 스토리지 비용은 이 모델에 없다. 마찬가지로 네트워크 이그레스, 벡터 인덱스 상주 메모리, 관측·로그 파이프라인 비용, 매니지드 서비스 고정비도 없다. 자기 청구서로 옮길 때 반드시 행을 추가해야 하는 자리다.

## 2. 그럼에도 불변인 것 — 숫자를 갈아 끼워도 안 바뀌는 구조

숫자가 다 흔들려도 남는 게 있다. 이 셋이 이 장의 진짜 내용이다.

### 구조 1 — 총 시간 = 1회 지연 × 호출 수 (`ex4`)

이건 산수라서 환경 무관이다. 그리고 여기서 나오는 결론도 무관하다: **「제일 느린 것」과 「제일 아픈 것」은 대체로 다르다.**

`ex4` 예시값으로 계산하면:

| 쿼리 | 1회 지연 | 하루 호출 | 하루 총 시간 | 비중 |
|---|---:|---:|---:|---:|
| 사용자 권한 계산 | 3.4 ms | 2,800,000 | 2.64 h | 32.0% |
| 팀 구성원 조회 | 2.1 ms | 4,200,000 | 2.45 h | 29.6% |
| 이름으로 사람 찾기 | 1.2 ms | 6,100,000 | 2.03 h | 24.6% |
| 2홉 이웃 탐색 | 18 ms | 140,000 | 0.70 h | 8.5% |
| 전체 조직도 렌더 | 820 ms | 1,400 | 0.32 h | 3.9% |
| 월간 감사 리포트 | 12,000 ms | 30 | 0.10 h | 1.2% |
| **커뮤니티 탐지** | **31,000 ms** | 2 | **0.02 h** | **0.2%** |

지연 1위(커뮤니티 탐지, 31초)가 총 시간 꼴찌다. 상위 셋이 87%인데 셋 다 1~3ms짜리 「빠른」 쿼리다.

**여기서 안 바뀌는 것**: 호출 수 분포가 롱테일이면(웹/에이전트 서비스는 거의 항상 그렇다) 지연 순위와 총 시간 순위는 어긋난다. 그리고 **느린 쿼리 로그는 구조적으로 이걸 못 잡는다** — 임계값 100ms짜리 로그에 1.2ms 쿼리는 영원히 안 찍힌다. 당신 숫자를 넣어도 이 함정은 그대로 있다.

- 느린 쿼리 로그 → 사용자가 「기다린다」고 느끼는 것을 찾는 도구
- 총 시간 순위 → 인프라를 「먹는」 것을 찾는 도구
- 둘 다 봐야 하고, 고치는 순서는 대개 후자가 먼저다

### 구조 2 — 암달의 법칙 (`ex5`)

1967년 진 암달(Gene Amdahl)의 논문에서 나온 그 법칙이다. 전체 중 비율 `p`인 구간만 `s`배 빨라질 때 전체 속도 향상은

```
전체 배속 = 1 / ((1 - p) + p/s)
```

`s → ∞`여도 상한은 `1 / (1 - p)`다. **손 못 대는 구간이 상한을 못 박는다.**

`ex5` 예시값에서 모델 호출이 1,820 / 1,919 = **94.8%**다. 그러면 나머지 여섯 구간을 **무한대로** 빠르게 해도 상한은 `1 / 0.948 ≈ 1.054배`, 즉 5.2% 개선이 천장이다. 실제 절감률(0.4~0.8)을 넣으면 63ms, **3.3%**다.

**여기서 안 바뀌는 것**: 당신 시스템에서 모델 호출 비중이 94.8%가 아니라 70%든 99%든, "지배 구간을 안 건드리면 나머지를 다 최적화해도 (1−p) 안에 갇힌다"는 명제는 그대로다. 바뀌는 건 천장의 높이지 천장의 존재가 아니다. 그래서 순서가 정해진다.

1. 모델 호출 **횟수**를 줄인다 — 캐시, 라우팅(25장), 종료 조건(20장)
2. 모델 호출 **시간**을 줄인다 — 짧은 프롬프트, 작은 모델, 스트리밍
3. 그다음에 나머지를 본다

3번을 1번보다 먼저 하는 팀이 많다. 익숙하고, 재기 쉽고, 성과가 눈에 보여서다. "쿼리를 9ms에서 4ms로 줄였습니다"는 보고하기 좋은 문장이지만, 사용자는 1,919ms가 1,914ms 된 걸 못 느낀다.

### 구조 3 — 단가 격차는 자릿수 문제다 (`ex3`)

`ex3` 예시값을 끝까지 돌리면:

| 항목 | 월 인프라 | 월 토큰 | 합계 |
|---|---:|---:|---:|
| 모델 호출(판단) | 43,400원 | 35,935,200원 | 35,978,600원 |
| 모델 호출(추출) | 7,440원 | 8,197,200원 | 8,204,640원 |
| 체크포인트 쓰기 | 39,060원 | 0 | 39,060원 |
| 벡터 검색 | 31,689원 | 0 | 31,689원 |
| 그래프 조회 | 14,880원 | 0 | 14,880원 |
| 이벤트 로그 쓰기 | 8,370원 | 0 | 8,370원 |
| **합계** | **144,839원** | **44,132,400원** | **44,277,239원** |

토큰이 **99.67%**다. 그래프 조회는 월 3억 6천만 회로 호출 수 1위인데 비중은 0.03%고, 모델 호출은 전체 호출의 0.1%도 안 되는데 비중이 압도적이다.

호출 **1회당** 원가로 보면 이유가 선명하다.

- 그래프 조회 1회 ≈ 62원/코어시 × 2.4ms = **0.0000413원**
- 모델 판단 호출 1회 ≈ 6,200토큰 × 4.14원/1K = **25.67원**

약 **62만 배**다. 이건 몇 배 차이가 아니라 자릿수 차이라서, 단가가 좀 흔들려도 결론이 안 뒤집힌다. 민감도를 실제로 재 보면:

| 토큰 단가 가정 | 토큰 비중 |
|---|---:|
| 예시 그대로 | 99.7% |
| 1/10 (경량 모델) | 96.8% |
| 1/100 | 75.3% |
| 1/1000 | 23.4% |

**토큰 단가가 100배 싸져야** 인프라가 겨우 경쟁 상대가 된다. 그래서 "청구서의 큰 칸은 대개 토큰이다"는 이 예시 워크로드가 아니라 자릿수 격차에서 나오는 결론이고, 그만큼 잘 안 뒤집힌다.

### 구조 4 — 지연 축과 비용 축은 다른 작업이다

- **쿼리 튜닝 → 지연을 줄인다.** 사용자가 기다리는 시간.
- **토큰 줄이기 → 비용을 줄인다.** 청구서.

쿼리를 *빠르게* 해도 비용은 거의 그대로다. 다만 쿼리를 *정확하게* 하면(필요한 것만 정확히 집어 오면) 컨텍스트가 줄고 토큰이 크게 준다. 이건 속도 작업이 아니라 정확도 작업이다. 느리다고 불평이 오면 쿼리를 보고, 청구서가 아프면 토큰을 본다.

### 구조 5 — 재고 나서 고친다

7부 운영의 첫 규칙이자, `ex3`~`ex5`가 계산기 형태로 배포된 이유다. 상수를 갈아 끼우는 행위 자체가 이 장이 요구하는 훈련이다.

## 3. 자기 수치를 넣으려면 무엇을 계측해야 하나 — 체크리스트

### `ex3` (비용 모델)에 넣을 값

- [ ] **호출 수 (`calls`)** — 워크로드 종류별 30일 누적. 애플리케이션 계층 메트릭(카운터)에서 뽑을 것. DB 자체 통계로 세면 캐시로 걸러진 호출이 안 잡혀 과소 집계된다.
- [ ] **평균 지연 (`ms`)** — **p50이 아니라 산술 평균**을 쓴다. `총 시간 = 평균 × 호출 수`가 성립하는 건 평균일 때뿐이다. p50/p99는 SLO용 별도 축으로 따로 본다.
- [ ] **입력 토큰 (`tokens`)** — 모델 API 응답의 `usage.input_tokens`를 호출마다 로깅해서 평균을 낸다. 추정하지 말 것.
- [ ] **출력 토큰 컬럼 추가** — `usage.output_tokens`. 단가가 입력의 3~5배이므로 별도 행/컬럼으로 분리한다.
- [ ] **캐시 토큰 분리** — 프롬프트 캐시를 쓴다면 캐시 읽기/쓰기 토큰을 따로 세고 각자 단가를 적용한다. 캐시 읽기는 아주 싸고, 캐시 쓰기는 약간 비싸다.
- [ ] **실효 토큰 단가** — 정가표보다 **지난달 청구서 ÷ 지난달 토큰 수**가 진실이다. 배치 할인·약정·캐싱이 다 녹아 있다.
- [ ] **환율** — 최근값으로.
- [ ] **코어 단가** — (인스턴스 시간당 요금 ÷ vCPU 수). 스팟/약정 비율을 가중평균한다.
- [ ] **목표 가동률** — `cpu_cores()` 결과를 목표 가동률로 나눠서 실제 프로비저닝 코어 수를 낸다. 그리고 **피크 배수**(최대 RPS ÷ 평균 RPS)도 같이 재둔다.
- [ ] **빠진 행 추가** — 스토리지(선언만 되고 안 쓰이는 그 상수를 실제로 연결), 네트워크 이그레스, 벡터 인덱스 메모리, 로그·관측 파이프라인, 매니지드 서비스 고정비.

### `ex4` (핫 쿼리)에 넣을 값

- [ ] **쿼리별 태깅** — 쿼리 텍스트를 정규화(리터럴 → 파라미터)해서 지문(fingerprint)으로 묶는다. 안 묶으면 같은 쿼리가 수천 개로 흩어져 총 시간이 안 보인다.
- [ ] **쿼리별 (평균 지연, 호출 수)** — 이 둘만 있으면 된다. 대부분의 APM/트레이싱 백엔드에서 바로 뽑을 수 있다.
- [ ] **총 시간 순 정렬** — 그리고 이 순위를 느린 쿼리 로그 순위와 **나란히** 놓고 얼마나 어긋나는지 본다. 어긋남 자체가 발견이다.
- [ ] **임계값 아래 쿼리 확인** — 느린 쿼리 로그 임계값보다 빠르면서 호출 수가 큰 것들. 여기에 보통 1위가 숨어 있다.

### `ex5` (구간 분해)에 넣을 값

- [ ] **분산 트레이싱 스팬** — OpenTelemetry 등으로 요청 하나를 구간별로 쪼갠다. 스팬 이름을 `SEGMENTS`의 구간 이름과 맞춰 두면 그대로 대입된다.
- [ ] **대표 요청 정의** — 무엇의 평균인가? 요청 유형이 섞여 있으면 유형별로 따로 돌린다. 섞으면 아무 구간도 지배적으로 안 보인다.
- [ ] **합이 총 시간과 맞는지 검증** — 구간 합 ≠ 전체 지연이면 계측 안 된 구간(큐 대기, 커넥션 풀 대기, GC, 콜드 스타트)이 있다는 뜻이다. 그 차이가 종종 진짜 범인이다.
- [ ] **절감 가능률은 추정하지 말고 실험으로** — 한 구간만 실제로 줄여 보고 재서 채운다. 추정값으로 채운 컬럼은 결론이 아니라 가설이라고 적어 둔다.
- [ ] **암달 상한 먼저 계산** — 지배 구간 비율 `p`를 넣고 `1/(1−p)`를 구한다. 이 숫자가 작으면(예: 1.05) 그 구간을 손대기 전엔 어떤 튜닝도 시작하지 않는다.

### 다시 돌려야 하는 시점 (재검증 트리거)

- 모델을 바꿨을 때 / 모델 단가가 개정됐을 때
- 프롬프트 캐싱·배치 API를 도입했을 때
- 트래픽이 2배 이상 변했을 때, 또는 피크 패턴이 바뀌었을 때
- 데이터 규모가 자릿수로 커졌을 때 (플랜이 바뀐다 — `ex1`의 마지막 문단)
- 슈퍼스텝 수·재시도 정책 등 **구조**를 바꿨을 때 (체크포인트 쓰기 호출 수가 통째로 움직인다)

## 4. 결론이 뒤집히는 지점을 찾는 법 (권장 사용법)

숫자를 갈아 끼운 뒤 바로 "우리는 몇 %네"로 끝내지 말고, **어디까지 흔들려야 결론이 바뀌는지**를 한 번 계산해 보는 게 이 예제를 제일 잘 쓰는 법이다.

- 토큰 단가를 몇 분의 1로 낮춰야 인프라가 1위가 되나?
- 그래프 조회 호출 수가 몇 배가 되어야 토큰을 넘어서나?
- 모델 호출 비중이 몇 % 아래로 떨어져야 나머지 구간 튜닝이 의미 있어지나? (`1/(1−p)`가 1.5는 되려면 `p < 0.33`이다)

예시 워크로드에서는 이 임계점들이 대부분 **자릿수 단위로 멀리** 있다. 그게 "구조가 요점"이라는 말의 실질적 의미다 — 결론이 숫자의 소소한 오차에 안 흔들리도록 설계된 예제라는 뜻이지, 숫자가 아무래도 좋다는 뜻이 아니다.

## 요약

| | 환경 따라 통째로 달라짐 | 어떤 환경에서도 불변 |
|---|---|---|
| **무엇** | `ms`, `calls`, `tokens`, 토큰/코어 단가, 환율, 절감 가능률, 누락 항목(스토리지·이그레스) | 총 시간 = 지연 × 호출 수 · 암달의 법칙 · 토큰과 CPU의 자릿수 단가 격차 · 지연 축 ≠ 비용 축 |
| **왜** | 하드웨어, 배치(임베디드/원격), 데이터 규모, 모델 선택과 가격 개정, 트래픽 프로파일, 아키텍처 | 산술 항등식 / 수학 정리 / 원가 구조의 자릿수 차이 |
| **어떻게** | 계측해서 갈아 끼운다 (위 체크리스트) | 갈아 끼운 뒤에도 그대로 성립하는지 확인하는 데 쓴다 |

그래서 답은 이렇다. **`ex3`~`ex5`의 숫자는 인용할 결론이 아니라 채워 넣을 빈칸이다.** 채워 넣은 뒤에도 남는 세 구조 — 총 시간 산식, 암달의 법칙, 단가 자릿수 격차 — 가 이 장이 전하려는 것이다.
