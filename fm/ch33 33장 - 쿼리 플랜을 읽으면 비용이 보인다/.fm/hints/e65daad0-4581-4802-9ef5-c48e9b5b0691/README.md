# 에이전트 시스템 성능 튜닝의 첫 사실

> **Q.** 에이전트 시스템 성능 튜닝의 첫 사실은 무엇인가?
>
> **A.** 모델 호출 앞뒤를 아무리 다듬어도 모델 호출이 줄지 않으면 빨라지지 않는다.

출처: 33장 「쿼리 플랜을 읽으면 비용이 보인다」 §33.5 / `code/ex5_where_time_goes.py`

---

## 1. 숫자로 보는 근거 — ex5의 94.8%

`ex5_where_time_goes.py`는 에이전트 요청 **한 건**의 시간을 구간별로 쪼갭니다. 예시 워크로드의 실측 단순화 값입니다.

| 구간 | 시간(ms) | 비중 | 최대 절감률 | 절감 가능(ms) | 방법 |
|---|---:|---:|---:|---:|---|
| 입력 검증 | 3 | 0.2% | 0% | 0 | 이미 최소 |
| 그래프 조회 ×4 | 9 | 0.5% | 50% | 4.5 | 인덱스·플랜 |
| 벡터 검색 | 11 | 0.6% | 40% | 4.4 | 차원 축소·근사 |
| 컨텍스트 조립 | 18 | 0.9% | 70% | 12.6 | 24장 — 참조만 싣기 |
| **모델 호출** | **1,820** | **94.8%** | 30% | 546 | 짧은 프롬프트·작은 모델 |
| 응답 후처리 | 24 | 1.3% | 60% | 14.4 | 스트리밍 |
| 체크포인트 쓰기 | 34 | 1.8% | 80% | 27.2 | 상태 줄이기·슈퍼스텝 줄이기 |
| **합계** | **1,919** | 100% | | 609 | |

핵심 계산 세 줄입니다.

- 모델 호출 = 1,820 / 1,919 = **94.8%**
- 나머지 여섯 구간의 시간 총합 = 99ms = **5.2%**
- 나머지 여섯 구간을 **전부, 각자의 최대치까지** 줄여도 4.5 + 4.4 + 12.6 + 14.4 + 27.2 = 약 **63ms**. 1,919ms의 **3%** 남짓입니다.

사용자가 체감하는 변화는 1,919ms → 약 1,856ms. 인지 문턱에도 못 미칩니다. 33장 도입부의 "3주 동안 쿼리를 튜닝했습니다. 평균 지연이 9ms에서 4ms로 줄었어요"라는 대사는 이 표에서 **9 → 4**, 즉 5ms 개선이고, 전체의 0.26%입니다.

## 2. 왜 모델 호출이 지배 구간인가

앞뒤 구간이 ms 단위인데 모델 호출만 초 단위인 데는 구조적인 이유가 있습니다.

**(1) 토큰 생성은 본질적으로 순차적입니다.**
자기회귀(autoregressive) 디코딩은 *n*번째 토큰을 만들려면 1..*n-1*번째 토큰이 이미 나와 있어야 합니다. 입력 처리(prefill)는 병렬화가 되지만, 출력 토큰 생성(decode)은 토큰 하나당 순전파 한 번을 되풀이하는 직렬 루프입니다. 출력이 500토큰이면 순전파를 500번 도는 것이고, 코어를 아무리 늘려도 이 사슬 자체는 짧아지지 않습니다. 그래프 조회 4번이 서로 독립이라 병렬화·캐시로 접히는 것과 성질이 다릅니다.

**(2) 네트워크 왕복과 큐 대기가 붙습니다.**
모델 호출은 대개 프로세스 밖, 보통은 데이터센터 밖으로 나가는 원격 호출입니다. 연결 수립, 요청 전송, 서버 측 배치 큐 대기, 첫 토큰까지의 지연(TTFT), 스트리밍 응답 수신이 모두 한 호출 안에 들어 있습니다. 로컬 그래프 엔진 호출이 μs~ms 단위인 것과 자릿수가 다릅니다.

**(3) 그래서 절감률의 상한도 낮습니다.**
표에서 모델 호출의 최대 절감률만 30%로 잡혀 있는 이유입니다. 체크포인트 쓰기는 구조를 바꾸면 80%까지 줄지만, 모델 호출은 프롬프트를 줄이고 작은 모델로 바꿔도 "생성해야 할 토큰 수 × 토큰당 순전파"라는 바닥이 남습니다.

## 3. 앞뒤 구간 최적화의 이론적 상한 — 암달의 법칙

이 카드의 문장은 감각적 조언이 아니라 **암달의 법칙**(Amdahl, 1967)의 직접적인 따름정리입니다.

전체 중 비율 *p*만 개선 가능하고 그 구간을 *s*배 빠르게 만들 때, 전체 속도 향상은

```
speedup = 1 / ( (1 - p) + p/s )
```

여기에 대입해 봅니다. 개선 대상이 "모델 호출을 뺀 나머지"이므로 *p* = 0.052, 손댈 수 없는 부분 (1 − *p*) = 0.948입니다.

| 시나리오 | *s* | 전체 speedup | 남는 시간 |
|---|---:|---:|---:|
| 나머지를 표의 최대치까지 개선 | 약 2.6배 | 1.033배 | 1,856ms |
| 나머지를 10배 빠르게 | 10 | 1.047배 | 1,833ms |
| **나머지를 0ms로 완전히 없앰** | ∞ | **1.055배** | **1,820ms** |

**즉, 모델 호출을 건드리지 않는 한 어떤 마법을 부려도 5.5% 이상 빨라질 수 없습니다.** 이것이 "이론적 상한"의 의미입니다. 인덱스를 다시 걸든, 벡터 검색을 근사로 바꾸든, 체크포인트를 통째로 없애든, 상한은 1,820ms에 걸려 있습니다.

그래서 33장이 제시하는 순서가 이렇게 됩니다.

1. 모델 호출 **횟수**를 줄인다 — 캐시, 라우팅(25장), 종료 조건(20장)
2. 모델 호출 **시간**을 줄인다 — 짧은 프롬프트, 작은 모델, 스트리밍
3. 그다음에 나머지를 본다

1번이 먼저인 이유는, 횟수를 줄이는 것만이 *p*가 아니라 (1 − *p*)를 직접 깎는 유일한 수단이기 때문입니다. 호출 2번을 1번으로 줄이면 1,820ms가 통째로 사라집니다. 앞뒤 여섯 구간을 전부 없애서 얻는 63ms의 29배입니다.

3번을 1번보다 먼저 하는 팀이 많은 이유도 책이 짚습니다. 익숙하고, 재기 쉽고, 성과가 눈에 보여서입니다. "쿼리를 9ms에서 4ms로 줄였습니다"는 보고하기 좋은 문장이지만, 사용자는 1,919ms가 1,914ms가 된 것을 느끼지 못합니다.

## 4. 그런데도 앞뒤 구간을 고쳐야 하는 이유 — 지연과는 **다른** 목표

여기서 헷갈리면 반대쪽으로 틀립니다. "앞뒤는 손댈 필요 없다"가 아닙니다. **지연 목표로는 헛일이지만, 다른 목표로는 여전히 유효**합니다. 33장이 명시적으로 분리하는 지점입니다.

### (a) 비용 — 청구서의 큰 칸은 토큰이다

`ex3_cost_model.py`가 같은 시스템의 월 비용을 항목별로 쪼갭니다.

| 항목 | 월 호출 수 | 성격 |
|---|---:|---|
| 체크포인트 쓰기 | 5억 4,000만 | 인프라만 |
| 그래프 조회 | 3억 6,000만 | 인프라만 |
| 벡터 검색 | 2억 3,000만 | 인프라만 |
| 모델 호출(판단) | 140만 | 인프라 + 토큰 6,200개/회 |
| 모델 호출(추출) | 18만 | 인프라 + 토큰 11,000개/회 |

모델 호출은 전체 호출의 **0.1%도 안 되는데** 비용 비중은 압도적입니다. 예시 단가(입력 1K토큰당 약 4.14원)로 계산하면 전체 월 비용의 대부분이 토큰 값이고, CPU 인프라는 십수만 원 수준으로 소수점 취급입니다.

그래서 두 작업의 목적이 갈립니다.

| 작업 | 줄이는 것 | 누가 아파하나 |
|---|---|---|
| 쿼리 튜닝 | **지연** | 사용자 — 기다리는 시간 |
| 토큰 줄이기 | **비용** | 재무 — 청구서 |

쿼리를 *빠르게* 해도 비용은 거의 그대로입니다. 다만 쿼리를 **정확하게** 하면(= 필요한 것만 뽑아서 컨텍스트에 싣으면) 토큰이 크게 줍니다. 24장의 컨텍스트 얘기가 여기서 돈으로 돌아옵니다. 표에서 "컨텍스트 조립"이 지연으로는 18ms짜리 곁가지지만, 그 구간이 결정하는 **입력 토큰 수**는 청구서의 주역입니다. 같은 코드를 고치는데 지연 장부와 비용 장부에서 값어치가 정반대인 셈입니다.

### (b) 안정성·구조 — 인프라를 먹는 것

`ex4_hot_query.py`가 짚는 축입니다. "제일 느린 것"과 "제일 아픈 것"은 다릅니다. 커뮤니티 탐지는 31초 걸리지만 하루 2번 돌아 총 0.02시간이고, 사용자 권한 계산은 3.4ms인데 하루 280만 번 돌아 총 2.6시간, 전체의 32%를 먹습니다. 상위 셋이 87%인데 셋 다 1~3ms짜리 "빠른" 쿼리입니다.

이 총 시간은 지연 체감이 아니라 **용량**입니다. 코어를 몇 개 사야 하는지, 트래픽이 두 배 되면 큐가 터지는지가 여기서 결정됩니다. 마찬가지로 ex5에서 두 번째로 큰 구간인 체크포인트 쓰기(34ms, 최대 80% 절감)는 사용자 체감으로는 1.8%지만, 월 5억 4,000만 회로 도는 쓰기 부하이자 장애 시 복구 지점입니다. 그리고 이건 쿼리 튜닝으로 줄지 않고 **구조**를 고쳐야 줍니다 — 21장의 슈퍼스텝 줄이기, 즉 그래프 설계 문제입니다.

## 5. 세 가지를 섞지 말 것 (정리)

| 무엇이 아픈가 | 어디를 보나 | ex5 기준 기대치 |
|---|---|---|
| 사용자가 느리다고 한다 | **모델 호출 횟수 → 시간** | 호출 1회 제거 = −1,820ms |
| 청구서가 아프다 | **컨텍스트·토큰** (24장) | 쿼리를 빠르게가 아니라 정확하게 |
| 인프라가 터진다 | **총 시간 상위 쿼리·체크포인트 구조** (21장) | 쿼리별 총 시간 순위로 줄 세우기 |

그리고 이 셋을 재기 전에 **먼저 구간별로 쪼개 보는 것**이 33장의 마지막 조언입니다. 95%를 차지하는 구간이 있으면 나머지를 전부 최적화해도 3%입니다. 60년 된 암달의 법칙이 에이전트 시스템에도 그대로 적용됩니다.

## 한 줄 암기

> **1,820 / 1,919 = 94.8%.** 나머지 여섯 구간을 전부 0으로 만들어도 5.5%밖에 못 빨라진다. 그러니 모델 호출 **횟수**부터 줄인다. 앞뒤 구간은 지연이 아니라 **비용과 안정성** 때문에 고친다.
