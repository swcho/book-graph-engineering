# 33장 도입부의 일화가 시사하는 것

> **Q.** 33장 도입부의 일화가 시사하는 것은 무엇인가?
>
> **A.** 3주 튜닝으로 평균 지연을 9ms에서 4ms로 줄였지만, 전체 요청 시간에서 그 비중은 미미했다는 것이다.

---

## 1. 일화의 원문

33장은 이 한 줄로 시작합니다.

> 3주 동안 쿼리를 튜닝했습니다. 평균 지연이 9ms에서 4ms로 줄었어요.

읽으면 성공담처럼 들립니다. **절반 이상 줄였다**는 얘기니까요. 상대적 개선율만 보면 44% 감소입니다. 보고서에 쓰기 좋고, 스프린트 회고에서 박수받기 좋은 문장이죠.

33장의 도입부는 곧바로 이렇게 받습니다.

> 운영의 첫 규칙은 *재고 나서 고치기*입니다. 이 장은 두 가지를 다룹니다. 쿼리 플랜을 읽는 법과, **그 플랜이 청구서에서 차지하는 자리를 아는 법**이요. **후자가 더 중요합니다.**

즉 이 일화는 "튜닝을 잘했다"는 자랑이 아니라, **분모를 안 보고 분자만 최적화한 3주**에 대한 반성문입니다.

---

## 2. 정확한 산수 — 5ms는 전체의 0.26%

일화의 분모는 33.5절(`ex5_where_time_goes.py`)에 나옵니다. 한 요청의 구간별 시간표입니다.

| 구간 | ms | 전체 비중 | 최대 절감률 | 최대 절감(ms) | 절감분의 전체 대비 |
|---|---:|---:|---:|---:|---:|
| 입력 검증 | 3 | 0.156% | 0% | 0.0 | 0.000% |
| **그래프 조회 ×4** | **9** | **0.469%** | 50% | 4.5 | 0.234% |
| 벡터 검색 | 11 | 0.573% | 40% | 4.4 | 0.229% |
| 컨텍스트 조립 | 18 | 0.938% | 70% | 12.6 | 0.657% |
| **모델 호출** | **1,820** | **94.841%** | 30% | 546.0 | 28.452% |
| 응답 후처리 | 24 | 1.251% | 60% | 14.4 | 0.750% |
| 체크포인트 쓰기 | 34 | 1.772% | 80% | 27.2 | 1.417% |
| **합계** | **1,919** | 100% | — | 609.1 | 31.74% |

일화의 "9ms"가 바로 **`그래프 조회 ×4` = 9ms** 칸입니다. 3주짜리 튜닝의 무대는 이 칸 하나였습니다.

### 산수

```
전체 요청 시간            = 3 + 9 + 11 + 18 + 1,820 + 24 + 34 = 1,919 ms
튜닝 대상 구간의 비중      = 9 / 1,919                          =  0.469 %
튜닝으로 줄인 시간         = 9 ms - 4 ms                        =  5 ms
전체 대비 개선            = 5 / 1,919                          =  0.2606 %
사용자가 체감하는 변화     = 1,919 ms → 1,914 ms  (속도 배수 1.0026배)
```

**5ms 절감은 전체 요청 시간의 0.26%입니다.** 33장 본문의 표현 그대로:

> 「쿼리를 9ms에서 4ms로 줄였습니다」는 보고하기 좋은 문장이다.
> 그런데 사용자는 **1,919ms를 1,914ms로 줄인 것을 못 느낀다.**

### 상한선까지 따져도

가혹하게 보면 이렇습니다. 만약 그래프 조회를 **0ms, 즉 무한히 빠르게** 만들었다 해도 —

```
암달의 법칙:  최대 속도 향상 = 1 / (1 - p)   (p = 개선 대상 구간의 비중)
p = 9 / 1,919 = 0.00469
최대 속도 향상 = 1 / (1 - 0.00469) = 1.0047배   →  개선 상한 0.47%
```

**3주를 쓰기 전에 이미 성과의 천장이 0.47%로 정해져 있었습니다.** 그리고 실제로 얻은 건 그 절반인 0.26%였고요. 이건 튜닝 실력의 문제가 아니라 **대상 선정의 문제**입니다.

### 한 걸음 더 — 모델 호출을 빼면 전부 해도 3%

시간표에서 모델 호출을 제외한 여섯 구간의 합은 99ms, 전체의 5.16%입니다. 이 여섯 개를 **전부, 각자의 최대 절감률까지** 밀어붙여도:

```
절감 총합 = 4.5 + 4.4 + 12.6 + 14.4 + 27.2 + 0.0 = 63.1 ms
전체 대비 = 63.1 / 1,919 = 3.29 %
```

3주가 아니라 3분기를 써서 그래프·벡터·컨텍스트·후처리·체크포인트를 **모두** 이론적 최선까지 다듬어도 3%입니다. 반대로 모델 호출 구간 하나만 30% 줄이면 546ms, 전체의 28.5%가 사라집니다.

> 60년 된 암달의 법칙이 지금도 그대로 적용됩니다.
> (Amdahl, 1967 — https://dl.acm.org/doi/10.1145/1465482.1465560)

## 3. 33장은 이 일화를 어떻게 일반화하는가 — 4단 지도

일화 한 줄이 장 전체의 설계도입니다. 33장은 "왜 3주가 헛돌았나"를 네 단계로 확장해서, **매번 같은 실수를 반복하지 않는 절차**로 바꿉니다.

```
          ┌──────────────────────────────────────────────────────┐
          │  일화: "3주 튜닝, 9ms → 4ms"                          │
          │  = 분자만 보고 분모를 안 봤다                          │
          └───────────────────────┬──────────────────────────────┘
                                  │
   ┌──────────────┬───────────────┼───────────────┬──────────────┐
   ▼              ▼               ▼               ▼              ▼
[33.1~33.2]   [33.3]          [33.4]          [33.5]
플랜 읽기      총 시간 순위     비용 모델        구간 분해
"어떻게        "어느 쿼리를     "이게 청구서를   "애초에 여기를
 고치나"        고치나"          바꾸나"          고치는 게 맞나"
   │              │               │               │
   └──────────────┴───────────────┴───────────────┘
                  실행 순서는 정반대: 33.5 → 33.4/33.3 → 33.1
```

### 33.1 플랜에서 볼 것은 세 가지다 — *어떻게* 고치나 (기술)

`ex1_read_plan.py`. 같은 답을 내는 쿼리 셋의 EXPLAIN을 나란히 놓습니다.

1. **`CROSS_PRODUCT`가 있나** — 있으면 거기부터. "두 끝을 따로 찾아서 붙이고 있다"는 뜻이고 데이터가 자라면 곱으로 커진다.
2. **`SCAN`이 무엇을 훑나** — 인덱스를 타나, 전체를 훑나.
3. **`FILTER`가 `SCAN` 앞인가 뒤인가** — 뒤면 훑고 나서 버리는 것.

부수적으로 무너지는 미신: **「작은 쪽에서 시작하라」는 요즘 엔진에선 대개 상관없습니다.** 팀에서 시작(B)과 사람에서 시작(C)이 거의 같았고, 플래너가 알아서 정합니다. 차이를 만든 건 곱집합이 낀 A(3.4배)뿐이었죠. 순서를 고민하기 전에 플랜부터 보라는 얘기입니다.

### 33.2 인덱스는 언제 안 듣나 — *어떻게*의 함정 (기술)

`ex2_index_effect.py`.

- **규모를 충분히 키워야 보입니다.** 수천 개에서는 파싱·계획 세우는 고정 비용이 지배해서 배수가 1.1 언저리에 머뭅니다. "인덱스 효과 없네"라고 결론 내면 틀리고, 반대로 수천 개짜리에 인덱스를 붙이며 튜닝하는 것도 헛일입니다.
- **인덱스는 찾는 방식에 맞아야 듭니다.** `=` → 해시, `<`/`>`·`STARTS WITH` → 정렬, `CONTAINS` → 어느 것도 안 듦(전문 검색 필요).
- **그래프의 특례**: 관계를 따라가는 데는 인덱스가 필요 없습니다. 이미 이어져 있으니까요. 그래서 첫 질문은 "인덱스를 걸까"가 아니라 **"시작점 하나만 인덱스로 찾고 나머지는 관계로 갈 수 있나"**입니다.
- 적재도 마찬가지. 한 건씩 넣지 말고 **일괄 적재(`COPY`)**. "그래프 DB 느리다"는 결론의 상당수가 여기서 나옵니다.

### 33.3 제일 느린 것과 제일 아픈 것은 다르다 — *어느 쿼리*를 고치나 (순위)

`ex4_hot_query.py`. **총 시간 = 1회 지연 × 호출 수**로 줄 세웁니다.

| 쿼리 | 1회 ms | 하루 호출 | 하루 총 시간 | 비중 |
|---|---:|---:|---:|---:|
| 사용자 권한 계산 | 3.4 | 2,800,000 | 2.64h | **32.0%** |
| 팀 구성원 조회 | 2.1 | 4,200,000 | 2.45h | **29.7%** |
| 이름으로 사람 찾기 | 1.2 | 6,100,000 | 2.03h | **24.6%** |
| 2홉 이웃 탐색 | 18.0 | 140,000 | 0.70h | 8.5% |
| 전체 조직도 렌더 | 820.0 | 1,400 | 0.32h | 3.9% |
| 월간 감사 리포트 | 12,000.0 | 30 | 0.10h | 1.2% |
| 커뮤니티 탐지 | 31,000.0 | 2 | **0.017h** | 0.2% |

- 제일 **느린** 건 커뮤니티 탐지(31초). 하루 두 번 돌아서 총 0.017시간.
- 제일 **아픈** 건 권한 계산(3.4ms). 하루 280만 번 돌아서 총 2.64시간, 전체의 32%.
- 상위 셋이 전체의 **86%**(책 표기 87%)를 먹는데, 셋 다 1~3ms짜리 "빠른" 쿼리입니다.
- 권한 계산을 반으로 줄이면 하루 1.3시간이 절약되고, 커뮤니티 탐지를 반으로 줄이면 하루 0.00003시간이 절약됩니다.

**느린 쿼리 로그의 함정**: 임계값을 100ms로 잡으면 1.2ms짜리는 한 번도 안 찍힙니다. 제일 아픈 쿼리가 로그에 아예 안 나와요.

> - 느린 쿼리 로그 → 사용자가 "기다린다"고 느끼는 것을 찾는다
> - 총 시간 순위 → 인프라를 "먹는" 것을 찾는다
>
> 둘 다 봐야 하고, 고치는 순서는 대개 후자가 먼저다.

### 33.4 청구서의 큰 칸은 대개 다른 곳이다 — *비용 모델* (돈)

`ex3_cost_model.py`. 월 단위 청구서를 항목별로 쪼갠 결과(계산 검증치):

| 항목 | 월 호출 | 코어 | 월 인프라 | 월 토큰 | 합계 | 비중 |
|---|---:|---:|---:|---:|---:|---:|
| 모델 호출(판단) | 1,400,000 | 0.97 | 43,400원 | 35,935,200원 | 35,978,600원 | **81.26%** |
| 모델 호출(추출) | 180,000 | 0.17 | 7,440원 | 8,197,200원 | 8,204,640원 | **18.53%** |
| 체크포인트 쓰기 | 540,000,000 | 0.88 | 39,060원 | 0 | 39,060원 | 0.088% |
| 벡터 검색 | 230,000,000 | 0.71 | 31,689원 | 0 | 31,689원 | 0.072% |
| **그래프 조회** | **360,000,000** | 0.33 | **14,880원** | 0 | **14,880원** | **0.034%** |
| 이벤트 로그 쓰기 | 540,000,000 | 0.19 | 8,370원 | 0 | 8,370원 | 0.019% |
| **합계** | | | | | **44,277,239원** | 100% |

- 그래프 조회는 **월 3억 6천만 회**로 제일 많이 도는데 청구서 비중은 **0.034%**입니다.
- 모델 호출은 월 158만 회, 전체 호출의 0.1%도 안 되는데 비중은 **99.8%**입니다.
- 그래프 조회를 2.4ms → 1.2ms로 **반토막** 내면? 월 7,440원, 전체 청구서의 **0.017%**가 줄어듭니다.

**결정적 구분** — 두 작업은 목적이 다르고, 헷갈리면 엉뚱한 데 시간을 씁니다.

| | 줄이는 것 | 무엇을 손대나 | 언제 |
|---|---|---|---|
| 쿼리 튜닝 | **지연** (사용자 대기 시간) | 플랜, 인덱스, 적재 | 느리다고 불평이 올 때 |
| 토큰 줄이기 | **비용** (청구서) | 컨텍스트, 호출 횟수 | 청구서가 아플 때 |

> 쿼리를 *빠르게* 해도 비용은 거의 그대로예요. 다만 쿼리를 *정확하게* 하면 토큰이 크게 줍니다. 둘은 다른 작업입니다.

한 가지 예외: 체크포인트 쓰기가 월 5억 4천만 회. 이게 늘면 인프라 비중이 확 커지는데, **쿼리가 아니라 구조(슈퍼스텝)를 고쳐야** 줍니다.

### 33.5 어디를 먼저 볼 것인가 — *구간 분해*, 일화의 정산 (전략)

`ex5_where_time_goes.py`. 위 §2의 표가 여기입니다. 이 절이 도입부 일화를 정면으로 정산합니다.

> 3번을 1번보다 먼저 하는 팀이 많다. 익숙하고, 재기 쉽고, 성과가 눈에 보여서다.

우선순위는 이렇습니다.

1. 모델 호출 **횟수**를 줄인다 — 캐시, 라우팅(25장), 종료 조건(20장)
2. 모델 호출 **시간**을 줄인다 — 짧은 프롬프트, 작은 모델, 스트리밍
3. **그다음에** 나머지를 본다

일화의 주인공은 3주 동안 **3번**을 했습니다. 그것도 3번 중에서 비중이 두 번째로 작은 칸(9ms)을요.

## 4. 3주를 쓰기 **전에** 무엇을 했어야 하나

일화가 가르치는 실용적 교훈은 "쿼리 튜닝을 하지 마라"가 아닙니다. **측정 순서를 뒤집으라**는 것입니다. 33장의 배치 순서(33.1 → 33.5)와 실제 실행 순서(33.5 → 33.1)가 정반대라는 게 핵심이고요.

### Day 0 (반나절) — 한 요청을 구간별로 쪼갠다

3주짜리 작업을 시작하기 전에 **반나절**이면 되는 일입니다.

- 대표 요청 하나에 구간별 타이머를 심습니다(입력 검증 / 그래프 조회 / 벡터 검색 / 컨텍스트 조립 / 모델 호출 / 후처리 / 체크포인트).
- 각 구간의 **절대 ms**와 **전체 대비 비중**을 표로 뽑습니다.
- 각 구간에 "현실적으로 몇 %까지 줄일 수 있나"를 붙입니다.

이 표만 있었으면 `그래프 조회 = 9ms / 1,919ms = 0.47%`가 첫 줄에 나왔을 겁니다. **암달 상한이 0.47%인 작업에 3주를 쓸지 말지**는 그 자리에서 결정됩니다.

### Day 0 (같은 날) — 암달 상한을 계산해서 손익분기를 정한다

```
개선 상한 = p            (구간을 0으로 만들었을 때의 전체 절감 비율)
목표 개선  ≥ 사용자가 체감하는 최소 단위 (보통 수십~수백 ms)
```

체감 가능한 최소 단위를 **50ms**로 잡았다면, 9ms짜리 구간은 아무리 잘해도 그 문턱을 넘을 수 없습니다. **후보에서 즉시 탈락시킬 근거**가 생기죠.

### Day 0.5 — 목표가 지연인지 비용인지 못 박는다

- "사용자가 느리다고 한다" → 지연 문제 → 33.5의 구간 분해 → 큰 칸부터
- "청구서가 아프다" → 비용 문제 → 33.4의 비용 모델 → 토큰부터

일화의 주인공은 이 질문에 답하지 않은 채 손에 익은 도구(쿼리 튜닝)를 집었습니다. **둘 중 어느 쪽이든 그래프 조회 9ms는 1순위가 아니었습니다.**

### Day 1 — 쿼리를 고치기로 했다면, 총 시간 순위부터

쿼리 계층 안에서도 순서가 있습니다. 느린 쿼리 로그가 아니라 **`1회 지연 × 호출 수`**로 줄을 세웁니다. 임계값 로그는 1.2ms짜리 hot query를 절대 못 잡으니까요.

### Day 2 — 그제서야 EXPLAIN

대상이 정해진 뒤에야 플랜을 엽니다. `CROSS_PRODUCT` → `SCAN` → `FILTER` 위치 순으로 보고, 규모를 충분히 키워서 재고, 인덱스는 "시작점 하나"에만 있으면 되는지 확인합니다.

### 요약 — 뒤집힌 순서

| 잘못된 순서 (일화) | 옳은 순서 (33장) |
|---|---|
| ① 익숙한 계층(쿼리)을 고른다 | ① 한 요청을 **구간별로 쪼갠다** |
| ② EXPLAIN을 연다 | ② **암달 상한**을 계산해 후보를 거른다 |
| ③ 3주 튜닝 | ③ **지연이냐 비용이냐** 목표를 못 박는다 |
| ④ 9ms → 4ms | ④ 쿼리라면 **총 시간 순위**로 대상 선정 |
| ⑤ …전체의 0.26% | ⑤ 그다음에 **EXPLAIN** |

---

## 5. 한 줄로

**분자(9ms → 4ms, 44% 감소)는 훌륭했지만 분모(1,919ms)를 안 봤다.** 최적화는 언제나 **비중이 정해 주는 상한** 안에서만 의미가 있고, 그 상한은 3주를 쓰기 전 반나절의 구간 분해로 알 수 있었습니다. 33장 전체는 이 반나절을 절차로 만든 장입니다 — 플랜 읽기(어떻게) 위에 총 시간 순위(어느 것)를 얹고, 그 위에 비용 모델(돈이 되나)을 얹고, 맨 위에 구간 분해(애초에 여기가 맞나)를 얹은 4층 구조요.
