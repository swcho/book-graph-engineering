# 배수 1.1의 정체 — 고정 비용이 지배하면 모든 배수는 1로 눌린다

> **Q.** `ex2_index_effect.py`에서 기본 키 조회와 속성 조회 배수가 1.1 언저리인 이유는 무엇인가?
>
> **A.** 이 규모에서는 쿼리를 파싱하고 계획을 세우는 고정 비용이 지배한다. 실제 찾기는 둘 다 1ms도 안 걸린다.

---

## 1. 무엇을 재려고 했고, 실제로 무엇을 쟀나

`ex2_index_effect.py`가 재려던 것은 **알고리즘의 차이**입니다.

| 쿼리 | 접근 방식 | 이론적 복잡도 |
|---|---|---|
| `MATCH (p:Person {id:$i})` | 기본 키 = 해시/인덱스 조회 | O(1) |
| `MATCH (p:Person) WHERE p.name = $n` | 인덱스 없는 속성 = 전체 훑기 | O(n) |
| `WHERE p.name STARTS WITH $n` | 앞부분 일치, 인덱스 없음 = 전체 훑기 | O(n) |

n = 128,000이면 O(n)과 O(1)의 차이는 **수만 배**여야 합니다. 그런데 출력은 1.1배쯤에서 꿈쩍도 안 합니다.

배신당한 건 이론이 아니라 **측정 대상**입니다. `timed()`가 재는 것은 `conn.execute()` 한 번의 벽시계 시간(wall clock)이고, 그 안에는 "찾기" 말고도 훨씬 많은 것이 들어 있습니다.

```python
def timed(c, q, params, reps=40):
    c.execute(q, params)                 # 워밍업 1회 (측정 제외)
    t0 = time.perf_counter()
    for _ in range(reps):
        r = c.execute(q, params)         # ← 여기에 파싱·바인딩·플래닝이 매번 들어 있다
        while r.has_next():
            r.get_next()                 # ← 여기에 FFI 왕복과 파이썬 객체 생성이 들어 있다
    return (time.perf_counter() - t0) / reps * 1000
```

## 2. 측정된 시간의 분해

한 번의 `execute()`가 쓰는 시간을 쪼개면 이렇게 됩니다.

```
측정된 시간 T(n) = F (고정 비용)  +  V(n) (가변 비용)
```

### F — 데이터 크기와 무관하게 매번 내는 값

| 구간 | 하는 일 | 크기에 비례하나 |
|---|---|---|
| **파싱(parse)** | Cypher 문자열 → 토큰 → AST | 아니오 (쿼리 길이에만 비례) |
| **바인딩(bind)** | 카탈로그 조회. `Person`이라는 테이블이 있나, `name`이 있나, 타입이 맞나 | 아니오 |
| **플래닝(plan)** | 논리 플랜 생성 → 카디널리티 추정 → 조인 순서 → 물리 플랜 선택 | 아니오 |
| **실행 준비** | 파이프라인 구성, 연산자 객체 할당, 벡터 버퍼 잡기, 스레드 배분 | 아니오 |
| **프로토콜/바인딩 오버헤드** | Python ↔ C++ FFI 왕복, 파라미터 딕셔너리 마샬링, `QueryResult` 객체 생성, `has_next()`/`get_next()` 호출당 파이썬 객체 변환 | 아니오 (결과 행 수에만 비례) |

세 쿼리 모두 결과가 **1건**입니다(`target = n // 2`, 이름은 유일). 그래서 프로토콜 쪽 비용조차 셋이 사실상 동일합니다. **F는 세 쿼리에서 거의 같은 값**입니다.

### V(n) — 실제로 데이터를 만지는 값

| 쿼리 | V(n) |
|---|---|
| 기본 키 | 해시 계산 1회 + 페이지 1~2개 읽기 ≈ **상수, 마이크로초 단위** |
| 속성 `=` | 전체 컬럼 훑기. Kuzu는 컬럼 저장 + 벡터화 실행 + 멀티스레드라 한 행당 **나노초 단위** |
| 속성 `STARTS WITH` | 같은 훑기 + 행마다 접두사 비교 (조금 더 비쌈) |

여기가 함정의 핵심입니다. **O(n)이 느리다는 뜻은 아닙니다.** 상수가 아주 작은 O(n)일 뿐입니다. 초당 수억 행을 훑는 엔진에서 128,000행은 1ms도 안 걸립니다. 답안이 말하는 "실제 찾기는 둘 다 1ms도 안 걸린다"가 바로 이것입니다.

## 3. 배수가 1로 눌리는 산수

우리가 화면에서 읽는 배수는 이겁니다.

```
        T_속성(n)     F + V_속성(n)
R(n) = ─────────── = ────────────────
        T_키(n)       F + V_키
```

`V_키`는 사실상 0이므로:

```
R(n) ≈ 1 + V_속성(n) / F
```

한 줄로 정리하면 이렇습니다.

> **관측 배수 = 1 + (알고리즘 차이) / (고정 비용)**
>
> 고정 비용이 크면 분수가 0으로 죽고, 배수는 1로 수렴한다.

### 숫자를 넣어 보면

아래는 실제 실측이 아니라 **구조를 보이기 위한 예시**입니다. `F = 3.0ms`, 훑기 비용을 행당 `2.3ns`로 잡아 봅니다.

| 노드 수 n | F (고정) | V_속성 (가변) | T_키 | T_속성 | 관측 배수 | 순수 배수 (F를 뺀 값) |
|---:|---:|---:|---:|---:|---:|---:|
| 2,000 | 3.000 | 0.005 | 3.001 | 3.005 | **1.00x** | ~5x |
| 8,000 | 3.000 | 0.018 | 3.001 | 3.018 | **1.01x** | ~18x |
| 32,000 | 3.000 | 0.074 | 3.001 | 3.074 | **1.02x** | ~74x |
| 128,000 | 3.000 | 0.294 | 3.001 | 3.294 | **1.10x** | ~294x |
| 1,000,000 | 3.000 | 2.30 | 3.001 | 5.30 | **1.77x** | ~2,300x |
| 4,000,000 | 3.000 | 9.20 | 3.001 | 12.20 | **4.07x** | ~9,200x |
| 16,000,000 | 3.000 | 36.8 | 3.001 | 39.8 | **13.3x** | ~36,800x |

같은 데이터, 같은 순간에 **1.1배**와 **294배**가 동시에 참입니다. 어느 쪽을 보느냐의 차이일 뿐입니다.

여기에 측정 잡음이 ±0.1ms만 있어도 앞의 세 줄(1.00 / 1.01 / 1.02)은 실행할 때마다 0.97~1.05 사이를 헤엄칩니다. 그래서 화면에서는 "**배수가 1.1 언저리에서 거의 안 변한다**"로 보입니다. 신호가 잡음에 잠긴 것입니다.

### 배수가 갈라지기 시작하는 지점

`R(n) = 2`가 되는 규모, 즉 **가변 비용이 고정 비용과 같아지는 손익분기점**은:

```
n* ≈ F / a          (a = 행당 훑기 비용)
   = 3.0ms / 2.3ns
   ≈ 1,300,000 행
```

README에 적힌 "`SIZES`를 백만 단위로 키우면 갈라집니다"가 정확히 이 값입니다. `SIZES = [2000, 8000, 32000, 128000]`은 손익분기점보다 **한 자릿수에서 세 자릿수 아래**에 있습니다. 인덱스가 안 드는 게 아니라, 인덱스가 드는 구간에 아예 도달하지 못한 겁니다.

### 이건 암달의 법칙이다

33장 요약의 마지막 줄과 같은 이야기입니다. 고정 비용 F는 **최적화가 손댈 수 없는 직렬 구간**이고, V(n)은 **가속 가능한 구간**입니다. 인덱스를 걸어 V를 ∞배 빠르게 해도(V → 0) 얻을 수 있는 최대 속도 향상은:

```
S_max = (F + V) / F = 1 + V/F
```

n = 128,000에서 V/F = 0.098이므로 **아무리 잘해도 1.1배**가 상한입니다. `ex5_where_time_goes.py`에서 "모델 호출을 뺀 나머지를 전부 줄여도 3%"라고 말하는 것과 똑같은 산수입니다. 무대만 밀리초 단위로 바뀌었습니다.

## 4. 이 착시를 피하는 측정법

### (1) 규모를 키운다 — 손익분기점을 넘겨라

가장 정직한 방법입니다. `n* ≈ F / a`를 어림잡고 그 **10배 이상**에서 재세요.

```python
SIZES = [10_000, 100_000, 1_000_000, 10_000_000]   # 로그 스케일로 자릿수를 훑는다
```

- **자릿수 단위로** 늘리세요. 2,000 → 8,000처럼 4배씩 늘리면 곡선의 모양이 안 보입니다.
- 점을 로그-로그로 찍으면 O(1)은 **기울기 0**, O(n)은 **기울기 1**인 직선이 됩니다. 기울기가 알고리즘을 말해 줍니다. 단일 배수 숫자는 안 말해 줍니다.
- 대가: `ex2`의 `build()`가 CSV를 쓰고 `COPY`하는 데 시간이 걸립니다. README가 "실행이 오래 걸립니다"라고 경고하는 이유입니다.

### (2) 준비된 문(prepared statement) — 파싱·플래닝을 루프 밖으로 뺀다

`c.execute(q, params)`를 루프 안에서 부르면 매 반복마다 파싱·바인딩·플래닝이 다시 돕니다. 이걸 한 번만 하도록 분리하면 F에서 그 몫이 빠집니다.

```python
ps = c.prepare("MATCH (p:Person) WHERE p.name = $n RETURN p.id")  # 파싱·플래닝 1회
t0 = time.perf_counter()
for _ in range(reps):
    r = c.execute(ps, {"n": target_name})    # 실행만 반복
    while r.has_next():
        r.get_next()
```

주의할 점:
- Kuzu 최신 API 문서는 **`prepare` + `execute`를 나눠 쓰는 방식을 deprecated**로 표시하고 있습니다. 엔진이 내부적으로 플랜을 캐시하기 때문입니다. 버전에 따라 이 분리가 이미 무의미할 수 있으니, **효과가 있는지부터 재 보세요**.
- 준비된 문은 F를 **줄이지, 없애지 않습니다.** FFI 왕복, 실행 준비, 결과 객체 생성은 그대로입니다. 배수가 1.1에서 1.4로 올라갈 뿐 여전히 착시입니다.
- 운영 관점에서는 이게 그 자체로 이득이기도 합니다. 같은 모양의 쿼리를 초당 수천 번 던진다면, 인덱스보다 준비된 문이 먼저 효과를 냅니다.

### (3) 고정 비용을 따로 재서 빼라 — 가장 확실한 방법

**F를 직접 측정해서 빼면** 순수 가변 비용의 배수가 나옵니다. 방법이 셋 있습니다.

**a. 엔진이 알려 주는 값을 쓴다 (권장)**

Kuzu의 `QueryResult`는 컴파일 시간과 실행 시간을 나눠서 보고합니다. 벽시계 대신 이걸 쓰면 분해가 공짜입니다.

```python
r = c.execute(q, params)
while r.has_next():
    r.get_next()
print(f"컴파일 {r.get_compiling_time():.3f}ms  실행 {r.get_execution_time():.3f}ms")
```

`get_compiling_time()`이 F의 대부분(파싱·바인딩·플래닝)이고, `get_execution_time()`이 V(n)에 해당합니다. 두 열을 나란히 찍어 보면 컴파일 시간은 n이 100배가 되어도 평평하고, 실행 시간만 자랍니다. 그 순간 표가 스스로 답을 말합니다. (메서드 이름은 버전에 따라 다를 수 있으니 `dir(r)`로 확인하세요.)

**b. 빈 쿼리로 바닥을 잰다 (null probe / no-op baseline)**

엔진 계측이 없을 때 쓰는 방법입니다. 데이터를 전혀 만지지 않는 쿼리를 같은 경로로 재서 바닥값을 구합니다.

```python
floor = timed(c, "RETURN 1", {})                    # 파싱+플래닝+FFI만
# 또는 존재하지 않는 키를 조회해 인덱스 미스만 재기
print(f"순수 배수: {(at - floor) / max(pk - floor, 1e-9):.0f}x")
```

`ex2`의 예시 수치에 이걸 적용하면 128,000에서 `(3.294 - 3.000) / (3.001 - 3.000) = 294배`가 나옵니다. 화면의 1.1배와 같은 데이터에서요.

**c. 배치로 가변 비용을 증폭한다**

한 번의 `execute()` 안에 조회를 K번 밀어 넣으면 F는 1회분만 내고 V는 K배가 됩니다. 신호 대 잡음비를 K배 올리는 것입니다.

```python
c.execute("UNWIND $ids AS i MATCH (p:Person {id:i}) RETURN count(p)",
          {"ids": list(range(0, n, n // 1000))})    # 조회 1,000건을 한 번에
```

작은 데이터에서도 알고리즘 차이를 드러낼 수 있고, 실제 애플리케이션에서도 왕복 수를 줄이는 정석이라 일석이조입니다.

### (4) 잊기 쉬운 조건 두 가지

- **선택도(selectivity)를 고정하세요.** n이 커질 때 결과 행 수도 같이 커지면, 늘어난 시간이 "찾기 비용"인지 "결과 전송 비용"인지 구분이 안 됩니다. `ex2`는 `target = n // 2`로 항상 1건만 맞히므로 이 부분은 잘 설계돼 있습니다.
- **캐시 상태를 의식하세요.** `timed()`는 워밍업 1회 후 40회를 반복하므로 데이터가 전부 버퍼 풀 안에 있습니다. 그런데 **인덱스의 실전 가치 중 큰 몫은 디스크 I/O를 안 하는 것**입니다. 메모리에 다 들어가는 데이터로만 재면 인덱스의 이득을 구조적으로 과소평가하게 됩니다. 반대로 캐시가 차갑고 데이터가 메모리보다 크면, 배수는 1.1이 아니라 수백 배로 벌어집니다.

## 5. 이 결과에서 내려도 되는 결론과 안 되는 결론

**내리면 안 되는 결론**

> ~~"인덱스는 별 효과가 없다."~~

이 벤치마크는 인덱스가 안 듣는다는 걸 보여준 게 아니라, **인덱스를 측정하는 데 실패했다**는 걸 보여줬습니다. 도구가 신호를 못 잡은 겁니다.

**내려도 되는 결론 셋**

1. **수천~수십만 건 규모에서는 인덱스 튜닝이 헛일이다.** 여기서 지배하는 건 고정 비용이니, 손댈 곳은 인덱스가 아니라 **호출 횟수와 왕복 수**입니다. 배치로 묶고, 준비된 문을 쓰고, 아예 안 부르는 쪽이 이득입니다.
2. **"인덱스 효과 측정"에는 최소 규모가 있다.** 손익분기점 `n* ≈ F/a`를 넘기지 못한 벤치마크는 어떤 결론도 지지하지 않습니다.
3. **모든 벤치마크는 먼저 자기 바닥값(floor)을 알아야 한다.** F를 모르는 채 읽은 배수는 알고리즘이 아니라 하네스를 잰 숫자일 수 있습니다.

## 한 줄 요약

측정 시간은 `고정 비용 F(파싱·바인딩·플래닝·프로토콜) + 가변 비용 V(n)(실제 탐색)`이고, 관측 배수는 `1 + V(n)/F`다. 수천~십만 건 규모에서 Kuzu의 V(n)은 1ms 미만이고 F는 그 열 배쯤이라 배수가 1.1로 눌린다. 규모를 손익분기점 `n*≈F/a`(백만 단위) 위로 올리거나, 준비된 문으로 F를 깎거나, `get_compiling_time()`/`get_execution_time()`으로 F를 따로 재서 빼면 같은 데이터에서 수백 배가 나온다.
