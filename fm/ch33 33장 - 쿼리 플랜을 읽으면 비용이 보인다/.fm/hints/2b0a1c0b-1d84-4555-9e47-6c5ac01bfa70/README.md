# 쿼리를 빠르게 하는 것 vs 비용을 줄이는 것

> **Q.** 쿼리를 빠르게 하는 것과 비용을 줄이는 것의 관계는 무엇인가?
>
> **A.** 청구서의 큰 칸은 대개 토큰이므로 쿼리를 빠르게 해도 비용은 거의 그대로다. 다만 쿼리를 **정확하게** 하면 토큰이 크게 준다.

핵심은 "관계가 없다"가 아니라 **"둘은 서로 다른 레버다"** 입니다. 같은 손잡이를 다르게 당기는 게 아니라, 아예 다른 손잡이예요. 그리고 쿼리 작업 중에서도 *빠르게*와 *정확하게*는 또 다른 레버입니다.

---

## 1. 먼저 숫자를 봅니다 — `ex3_cost_model.py`

33장 예제 3(`code/ex3_cost_model.py`)은 그래프 기반 에이전트 시스템의 월 비용을 항목별로 쪼갭니다. 워크로드 가정은 이렇습니다.

| 항목 | 월 호출 수 | 1회 지연 | 1회 입력 토큰 |
|---|---:|---:|---:|
| 그래프 조회 | 360,000,000 | 2.4 ms | 0 |
| 벡터 검색 | 230,000,000 | 8.0 ms | 0 |
| 모델 호출(판단) | 1,400,000 | 1,800 ms | 6,200 |
| 모델 호출(추출) | 180,000 | 2,400 ms | 11,000 |
| 체크포인트 쓰기 | 540,000,000 | 4.2 ms | 0 |
| 이벤트 로그 쓰기 | 540,000,000 | 0.9 ms | 0 |

단가는 코어시당 62원, 입력 토큰 1K당 3.0 USD/1M → 약 4.14원, 스토리지 GB월 33원(환율 1,380원 가정).

### 결과: 항목별 비중

```
  모델 호출(판단)      81.3%  ████████████████████████████████████████
  모델 호출(추출)      18.5%  █████████
  체크포인트 쓰기       0.09%
  벡터 검색            0.07%
  그래프 조회          0.03%
  이벤트 로그 쓰기      0.02%
  ─────────────────────────────
  합계             약 4,428만 원/월
```

- **모델 호출 두 줄이 합쳐서 99.8%.** 그중 순수 토큰 값만 **99.67%**(약 4,413만 원)이고, CPU·인프라 전부를 합쳐도 **0.33%**(약 14.5만 원)입니다.
- 그런데 모델 호출은 전체 호출 16억 7,158만 건 중 **158만 건, 0.09%**뿐입니다. 호출 수로는 1,000분의 1도 안 되는 항목이 청구서의 99.8%를 먹습니다.
- **그래프 조회는 월 3억 6천만 회로 두 번째로 많이 도는데 비중은 0.03%**, 금액으로 월 14,880원입니다.

### "쿼리를 빠르게" 하면 얼마나 절약되나

그래프 조회를 **2.4ms → 1.2ms로 반토막** 냈다고 해 봅시다. 지연이 절반이면 필요한 코어도 절반이니 인프라 비용도 절반입니다.

```
14,880원  →  7,440원   (절감 7,440원)
전체 4,428만 원 대비  →  0.02%
```

3주를 갈아 넣어 쿼리를 2배 빠르게 만들었는데 청구서는 **0.02% 줄었습니다.** 이 장 도입부의 "3주 동안 쿼리를 튜닝했습니다. 평균 지연이 9ms에서 4ms로 줄었어요"가 왜 씁쓸한 문장인지가 여기 있습니다.

### "토큰을 줄이면" 얼마나 절약되나

같은 시스템에서 호출당 입력 토큰을 줄이면 이렇습니다.

```
토큰 30% 절감  →  월 1,324만 원 절감  (전체의 29.9%)
토큰 50% 절감  →  월 2,207만 원 절감  (전체의 49.8%)
```

체감을 위해 단위 비용을 나란히 놓아 보면 더 선명합니다.

- 모델 호출(판단) 1회 = 6,200토큰 × 4.14원/1K = **약 25.7원**
- 그래프 조회 1회 = **약 0.0000413원**
- 즉 **모델 호출 한 번이 그래프 조회 약 62만 회분**입니다.

쿼리 62만 개를 아끼는 것과 모델 호출 한 번을 아끼는 것이 같습니다. 어느 쪽 레버가 무거운지는 명확해요.

## 2. 그래서 "지연을 줄인다"와 "비용을 줄인다"는 다른 레버다

예제 3의 결론 문장이 이 카드의 뼈대입니다.

```
쿼리 튜닝  → «지연»을 줄인다. 사용자가 기다리는 시간
토큰 줄이기 → «비용»을 줄인다. 청구서

둘을 헷갈리면 엉뚱한 데 시간을 쓴다.
느리다고 불평이 오면 쿼리를 보고, 청구서가 아프면 토큰을 본다.
```

| | 지연(latency) 레버 | 비용(cost) 레버 |
|---|---|---|
| 무엇을 줄이나 | 사용자가 기다리는 시간 | 청구서 금액 |
| 어디를 만지나 | 쿼리 플랜, 인덱스, 배치, 캐시 | 모델 호출 **횟수**, 호출당 **토큰** |
| 신호 | "느려요" 불평, p99 지연, 총 시간 순위 | 월 청구서, 토큰 사용량 대시보드 |
| 33장 근거 | `ex4`, `ex5` | `ex3` |

증상별로 어디를 열어야 하는지가 정해져 있습니다. **느리다는 불평 → 쿼리와 플랜. 청구서가 아프다 → 토큰.** 이 매핑을 뒤집으면 3주를 쓰고 0.02%를 얻습니다.

### 다만 "지연 레버"도 안에서 또 갈린다 — `ex5_where_time_goes.py`

지연 쪽으로 붙었다고 해도 쿼리부터 만지면 또 헛발질입니다. 예제 5는 한 요청 1,919ms를 구간별로 쪼갭니다.

| 구간 | ms | 비중 |
|---|---:|---:|
| 모델 호출 | 1,820 | **94.8%** |
| 체크포인트 쓰기 | 34 | 1.8% |
| 응답 후처리 | 24 | 1.3% |
| 컨텍스트 조립 | 18 | 0.9% |
| 벡터 검색 | 11 | 0.6% |
| 그래프 조회 ×4 | 9 | 0.5% |
| 입력 검증 | 3 | 0.2% |

모델 호출을 뺀 나머지 여섯 구간을 **전부 최대치로** 줄여도 60ms, 총 시간의 **3%**입니다. 60년 된 암달의 법칙이 그대로 적용돼요. 비중 95%짜리 구간을 안 건드리면 나머지를 다 갈아도 상한이 5%입니다.

그러니까 실제 구조는 이렇습니다.

```
비용 청구서 99.8%  →  모델 호출(토큰)
요청 지연  94.8%  →  모델 호출(시간)
```

**비용도 지연도 같은 곳에 몰려 있습니다.** 다만 비용은 "토큰 수"에, 지연은 "호출 횟수 × 호출 시간"에 걸려 있어서 고치는 방법이 다를 뿐입니다.

## 3. 그럼 왜 "정확한 쿼리"는 토큰을 줄이는가

여기가 이 카드에서 제일 중요한 반전입니다. 쿼리 작업이 비용에 닿는 경로가 **딱 하나** 있습니다. 그건 *속도*가 아니라 *정확도*입니다.

### 경로

```
부정확한 쿼리
   → 필요 없는 행까지 결과에 딸려 온다
   → 그 결과가 컨텍스트에 통째로 실린다
   → 입력 토큰이 는다
   → 청구서가 는다        (비중 99.67%인 그 칸)
```

```
정확한 쿼리
   → 필요한 행만 나온다
   → 컨텍스트에 실리는 양이 준다
   → 입력 토큰이 준다
   → 청구서가 준다
```

쿼리를 빠르게 하는 것은 **인프라 칸(0.33%)** 을 건드립니다. 쿼리를 정확하게 하는 것은 **토큰 칸(99.67%)** 을 건드립니다. 같은 "쿼리 튜닝"이라는 이름을 쓰지만 닿는 칸이 완전히 다릅니다.

### 무엇이 "부정확한 쿼리"인가 — `ex1`, `ex2`가 준 재료

예제 1의 쿼리 A가 딱 그 모양입니다.

```cypher
-- A. 두 끝을 따로 찾음
MATCH (p:Person), (t:Team)
WHERE t.name = '팀7' AND p.city = '마포'
  AND EXISTS { MATCH (p)-[:Member]->(t) }
RETURN count(p)
```

플랜에 `CROSS_PRODUCT`가 뜹니다. 사람 8,000명 × 팀 80개 = 64만 조합을 만들어 놓고 거기서 거르는 겁니다. B·C 대비 3.4배 느립니다. 여기서는 `count(p)`로 끝나서 결과가 숫자 하나지만, 실무에서 `RETURN p`로 행을 뽑아 컨텍스트에 넣는 순간 이야기가 달라집니다.

부정확한 쿼리의 전형은 이런 것들입니다.

- **조건을 나중에 거는 쿼리** — `FILTER`가 `SCAN` *뒤*에 있는 플랜. 훑고 나서 버립니다. 애플리케이션 코드에서 버리면 DB는 이미 다 보낸 뒤고, 그걸 그대로 프롬프트에 넣으면 토큰이 됩니다.
- **`LIMIT` 없이 다 긁는 쿼리** — "일단 다 가져와서 모델한테 판단시키자"가 제일 비쌉니다. 6,200토큰이 12,400토큰이 되면 그 항목 비용이 그대로 2배입니다.
- **관계를 안 쓰고 곱집합으로 붙이는 쿼리** — 33장 32절의 `CROSS_PRODUCT` 얘기. 예제 2의 결론대로 **"관계를 따라가는 것에는 인덱스가 필요 없습니다. 시작점 하나만 인덱스로 찾으면 그다음은 공짜"** 예요. 시작점을 정확히 집으면 결과 집합 자체가 작아집니다.
- **필요 없는 속성까지 다 반환하는 쿼리** — `RETURN p`와 `RETURN p.name, p.city`는 토큰 수가 몇 배 차이납니다.
- **2홉·3홉을 무작정 펼치는 쿼리** — 홉이 늘면 결과 행이 곱으로 늡니다. 그 행이 전부 프롬프트로 갑니다.

### 24장이 여기서 돈으로 돌아온다

예제 3의 주석에 이런 줄이 있습니다.

> 비용을 줄이려면 «모델 호출 횟수»나 «호출당 토큰»을 줄여야 한다.
> 24장의 컨텍스트 얘기가 여기서 돈으로 돌아온다.

그리고 예제 5의 "컨텍스트 조립" 구간 방법 칸에도 **"24장 — 참조만 싣기"** 가 적혀 있습니다. 즉 정확한 쿼리 → 작은 결과 집합 → 참조만 싣는 컨텍스트 → 적은 토큰 → 싼 청구서. 이 사슬 전체가 33장이 말하는 "비용 레버"입니다.

**"컨텍스트 조립을 최적화한다"는 건 문자열 붙이는 코드를 빠르게 만드는 게 아니라, 애초에 컨텍스트에 들어갈 게 적어지도록 쿼리를 정확하게 짜는 일입니다.**

## 4. 예외 하나 — 인프라 칸이 커지는 경우

예제 3이 붙여 놓은 단서도 같이 기억해야 균형이 맞습니다.

> 한 가지 예외가 있다. 체크포인트 쓰기가 월 5억 4천만 회로 도는데,
> 이게 늘어나면 인프라 비중이 확 커진다. 21장에서 잰 그 값이다.
> 그리고 이건 «쿼리»가 아니라 «구조»를 고쳐야 준다. 슈퍼스텝을 줄이는 것이다.

체크포인트 쓰기는 이 워크로드에서 인프라 비용의 **27%**(39,060원 / 144,839원)로 인프라 항목 중 1위이고, 지연에서도 34ms로 모델 호출 다음 2위입니다. 호출 수가 지금보다 한두 자릿수 더 커지면 인프라 칸이 무시할 수 없는 크기가 됩니다.

다만 이건 **쿼리 튜닝으로 못 고칩니다.** 슈퍼스텝 수를 줄이는 **구조 변경**, 즉 21장의 그래프 설계 문제입니다. 그래서 레버는 최종적으로 세 개입니다.

| 레버 | 만지는 것 | 줄어드는 것 | 근거 장 |
|---|---|---|---|
| 쿼리를 **빠르게** | 플랜, 인덱스, 배치 | 지연(그중 5% 구간) | 33장 `ex1`·`ex2` |
| 쿼리를 **정확하게** | 결과 집합 크기, 컨텍스트 | **토큰 = 비용** | 33장 `ex3` + 24장 |
| **구조**를 바꾼다 | 슈퍼스텝, 상태 크기 | 체크포인트 인프라·지연 | 21장 |

## 5. 실무 체크리스트

**"청구서가 아프다"** 고 왔을 때:

1. 먼저 **비중을 재라.** 예제 3처럼 항목별로 쪼개기 전에는 손대지 마세요. 재고 나서 고치는 게 7부 운영의 첫 규칙입니다.
2. 토큰 칸이 크면(대개 큽니다) → **모델 호출 횟수**(캐시, 라우팅 — 25장, 종료 조건 — 20장)와 **호출당 토큰**(컨텍스트 다이어트 — 24장)을 봅니다.
3. 컨텍스트를 줄이려면 **쿼리 결과를 줄여야** 합니다. `LIMIT`, 필요한 속성만 `RETURN`, 조건을 앞으로, `CROSS_PRODUCT` 제거, 시작점을 인덱스로 정확히 집기.
4. **쿼리 지연 튜닝은 이때 하지 마세요.** 그건 다른 증상의 약입니다.

**"느려요"** 라고 왔을 때:

1. 구간별로 쪼갭니다(`ex5`). 모델 호출이 95%면 나머지 최적화의 상한은 3%입니다.
2. 모델 호출 **횟수 → 시간 → 그다음 나머지** 순서.
3. 쿼리 차례가 오면 **총 시간(1회 지연 × 호출 수)** 으로 줄 세웁니다(`ex4`). 느린 쿼리 로그의 임계값이 100ms면 1.2ms짜리 핫 쿼리는 한 번도 안 찍힙니다. 제일 아픈 쿼리가 로그에 아예 안 나와요.
4. 그다음에 플랜을 읽습니다. `CROSS_PRODUCT`가 있나, `SCAN`이 무엇을 훑나, `FILTER`가 앞인가 뒤인가.

## 한 줄 요약

**빠른 쿼리는 사용자를 덜 기다리게 하고, 정확한 쿼리는 청구서를 줄인다.** 예제 3의 워크로드에서 쿼리를 2배 빠르게 해도 비용은 0.02%밖에 안 줄지만, 토큰을 30% 줄이면 비용이 약 30% 줍니다. 청구서의 99.67%가 토큰이기 때문입니다. 쿼리 튜닝이 비용에 닿는 유일한 경로는 "정확한 쿼리 → 작은 결과 집합 → 작은 컨텍스트 → 적은 토큰"이고, 그건 속도 튜닝과는 다른 작업입니다.
