# 느린 쿼리 로그의 함정

> **Q.** 느린 쿼리 로그의 함정은 무엇인가?
>
> **A.** 임계값을 100ms로 잡으면 1.2ms짜리는 한 번도 안 찍힌다. 제일 아픈 쿼리가 로그에 아예 나오지 않는다.

출처: 33장 「쿼리 플랜을 읽으면 비용이 보인다」 33.3절 — *제일 느린 것과 제일 아픈 것은 다르다* / `code/ex4_hot_query.py`

---

## 1. 한 줄 요약

느린 쿼리 로그는 **"느리다"는 조건으로 필터링한 표본**이다. 그런데 우리가 알고 싶은 것은 **"인프라를 많이 먹는다"**이고, 이 둘은 `총 시간 = 1회 지연 × 호출 수`라는 곱에서 서로 다른 항이다. 임계값은 곱의 **왼쪽 항만** 보고 자르기 때문에, 오른쪽 항이 거대한 쿼리는 구조적으로 로그에서 사라진다.

```
총 시간 = 지연 × 호출 수
          ↑           ↑
      로그가 보는 곳   로그가 못 보는 곳
```

---

## 2. 왜 "함정"인가 — 생존 편향의 구조

이건 로그 설정을 잘못한 실수가 아니다. **임계값 기반 로깅이라는 방식 자체가 만들어내는 편향**이다.

제2차 세계대전 때 아브라함 발드(Abraham Wald)의 폭격기 이야기가 정확히 같은 구조다. 돌아온 폭격기의 총알 자국을 지도에 찍어 보니 날개와 동체에 몰려 있었다. "여기를 보강하자"는 결론이 나왔다. 발드는 반대로 말했다. **그 데이터는 "돌아온 비행기"만의 데이터다.** 엔진과 조종석에 자국이 없는 이유는 거기를 맞으면 돌아오지 못했기 때문이다. 보강해야 할 곳은 자국이 **없는** 곳이었다.

느린 쿼리 로그도 똑같다.

| | 폭격기 | 느린 쿼리 로그 |
|---|---|---|
| 필터 | 기지로 돌아온 기체만 관측 | 임계값을 넘은 실행만 기록 |
| 보이는 것 | 살아남은 손상 | 느린 쿼리 |
| 안 보이는 것 | 치명상을 입은 기체 | 자주 도는 빠른 쿼리 |
| 잘못된 결론 | 날개를 보강하자 | 커뮤니티 탐지를 튜닝하자 |

핵심은 **관측 필터와 관심 지표가 상관은 있지만 같지 않다**는 점이다. 지연과 총 시간은 양의 상관이 있어 보이지만, 호출 수가 6자리·7자리로 갈리는 실제 워크로드에서는 그 상관이 쉽게 뒤집힌다. 그리고 뒤집히는 쪽이 하필 **제일 비싼 쪽**이다.

한 가지 더 고약한 점: 이 편향은 **자기 강화적**이다. 로그에 안 나오니까 아무도 의심하지 않고, 의심하지 않으니까 계측을 추가하지 않고, 계측이 없으니까 여전히 로그에 안 나온다.

## 3. ex4 수치로 계산 — 100ms 임계값은 총 시간의 몇 %를 보는가

`ex4_hot_query.py`의 워크로드 7종이다.

| 쿼리 | 1회 지연 | 하루 호출 | 하루 총 시간 | 비중 | 100ms 로그에 찍히나 |
|---|---:|---:|---:|---:|:---:|
| 사용자 권한 계산 | 3.4 ms | 2,800,000 | 2.64 h | **32.0%** | ✗ |
| 팀 구성원 조회 | 2.1 ms | 4,200,000 | 2.45 h | **29.6%** | ✗ |
| 이름으로 사람 찾기 | 1.2 ms | 6,100,000 | 2.03 h | **24.6%** | ✗ |
| 2홉 이웃 탐색 | 18.0 ms | 140,000 | 0.70 h | 8.5% | ✗ |
| 전체 조직도 렌더 | 820 ms | 1,400 | 0.32 h | 3.9% | ✓ |
| 월간 감사 리포트 | 12,000 ms | 30 | 0.10 h | 1.2% | ✓ |
| 커뮤니티 탐지 | 31,000 ms | 2 | 0.02 h | 0.2% | ✓ |
| **합계** | | **13,241,432** | **8.26 h** | 100% | |

### 결과

- **임계값 100ms가 커버하는 총 시간: 5.3%** (0.44h / 8.26h)
  → 나머지 **94.7%는 로그에 단 한 줄도 남지 않는다.**
- **로그에 찍히는 실행 건수: 1,432건 / 13,241,432건 = 0.011%**
- 총 시간 상위 3위(권한 계산·팀 구성원·이름 찾기)가 **전체의 86.3%**를 먹는데, 셋 다 1~3ms짜리라 **셋 다 안 찍힌다.**
- 로그를 가득 채우는 「커뮤니티 탐지」(31초)는 전체의 **0.2%**다. 이걸 절반으로 줄여도 하루 **0.009시간**이 준다.
- 반면 「사용자 권한 계산」을 3.4ms → 1.7ms로 줄이면 하루 **1.32시간**이 준다. 약 **150배** 차이의 투자 대비 효과인데, 한쪽은 로그 1등이고 한쪽은 로그에 없다.

### 임계값을 낮추면 되지 않나 — 낮춰 본 결과

| 임계값 | 잡히는 쿼리 | **총 시간 커버율** | 하루 로그 줄 수 | 초당 |
|---:|---:|---:|---:|---:|
| 100 ms | 3종 | 5.3% | 1,432 | 0.02/s |
| 10 ms | 4종 | 13.7% | 141,432 | 1.6/s |
| 5 ms | 4종 | 13.7% | 141,432 | 1.6/s |
| 3 ms | 5종 | 45.7% | 2,941,432 | 34/s |
| 2 ms | 6종 | 75.4% | 7,141,432 | 83/s |
| 1 ms | 7종 | **100%** | 13,241,432 | 153/s |

**커버율이 계단식으로 튄다.** 10ms에서 5ms로 낮춰도 커버율은 13.7%로 그대로다(그 구간에 쿼리가 없어서). 그러다 3ms를 지나는 순간 13.7% → 45.7%로 점프한다. 즉 임계값을 "적당히" 조절해서 원하는 커버율을 얻는 건 불가능하다 — **워크로드의 지연 분포를 이미 알고 있어야 임계값을 제대로 잡을 수 있는데, 그걸 알려고 로그를 켠 것이다.** 닭과 달걀이다.

그리고 100%를 보려면 임계값을 1ms로 내려야 하는데, 그러면 **하루 1,300만 줄, 초당 153줄**이 쏟아진다. 줄당 250바이트만 잡아도 **하루 3.3GB**다. 여기서 두 번째 함정이 나온다.

### 두 번째 함정 — 관측이 대상을 바꾼다

임계값을 0으로 내리면(MySQL `long_query_time=0`, PostgreSQL `log_min_duration_statement=0`) 모든 실행이 기록된다. 그런데:

- 1.2ms짜리 쿼리에 동기 디스크 쓰기 로그를 붙이면 **로깅 비용이 쿼리 비용에 필적한다.** 측정값 자체가 오염된다.
- 로그 쓰기가 직렬화 지점이 되어 고동시성 구간에서 락 경합을 만든다.
- 파싱·전송·저장·인덱싱 비용이 실제 워크로드보다 비싸질 수 있다.

**"전부 기록한다"는 고빈도 쿼리에 대해서는 답이 아니다.** 그래서 다른 계측이 필요하다.

## 4. 대안 계측 — 편향 없이 총 시간을 보는 세 가지 방법

### 4-1. 쿼리 지문(fingerprint)별 집계 — 가장 직접적인 답

리터럴을 정규화해 같은 모양의 쿼리를 하나의 **지문/다이제스트**로 묶고, 엔진 내부에서 **호출 수와 누적 시간을 카운터로 더한다.** 개별 실행을 한 줄씩 기록하지 않으므로 저장 비용이 O(쿼리 종류)로 고정된다. 1,300만 줄이 아니라 **7행짜리 표**가 된다.

임계값이 없으므로 **1.2ms짜리도 빠짐없이 누적된다.** 이게 정확히 ex4의 표를 실시간으로 만들어 주는 도구다.

**PostgreSQL — `pg_stat_statements`**

```sql
-- 총 시간 순위. ex4의 "하루 총 시간 순"과 같은 뷰
SELECT
  queryid,
  calls,
  round(total_exec_time / 1000 / 3600, 2) AS total_hours,
  round(mean_exec_time, 3)                AS mean_ms,
  round(100 * total_exec_time
        / sum(total_exec_time) OVER (), 1) AS pct,
  left(query, 60)                          AS q
FROM pg_stat_statements
ORDER BY total_exec_time DESC
LIMIT 20;
```

`total_exec_time DESC`가 핵심이다. `mean_exec_time DESC`로 정렬하면 느린 쿼리 로그와 똑같은 함정에 다시 빠진다.

**MySQL — `performance_schema` 다이제스트**

```sql
SELECT
  DIGEST_TEXT,
  COUNT_STAR,
  SUM_TIMER_WAIT / 1e12 / 3600 AS total_hours,   -- 피코초 단위
  AVG_TIMER_WAIT / 1e9         AS avg_ms
FROM performance_schema.events_statements_summary_by_digest
ORDER BY SUM_TIMER_WAIT DESC
LIMIT 20;
```

**그 외 엔진**
- MongoDB: `$currentOp` / 프로파일러 대신 `db.aggregate([{$queryStats:{}}])` 계열의 지문 집계
- Neo4j: 쿼리 로그 임계값을 0으로 두고 외부에서 집계하거나(비용 주의), APOC/드라이버 계층에서 지문별 카운터를 직접 붙인다. 버전마다 제공 범위가 다르니 확인이 필요하다.
- Kùzu 등 임베디드 엔진: 내장 집계가 없다. **애플리케이션 계층에서 직접 감싸는 것이 사실상 유일한 방법**이다 (4-3 참고).

**이 방법의 한계도 알아 둘 것**
- **평균이 분포를 감춘다.** 같은 지문인데 파라미터에 따라 1ms와 500ms로 갈리는(bimodal) 쿼리는 평균만 보면 안 보인다. → 백분위/히스토그램을 함께 봐야 한다.
- **엔트리 수 상한과 축출.** `pg_stat_statements.max`(기본 5000)를 넘으면 오래된 항목이 밀려난다. 애드혹 쿼리가 많은 시스템에서는 지문이 폭발한다.
- **정규화 실패.** 리터럴을 그대로 박은 동적 SQL은 실행마다 다른 지문이 되어 집계가 흩어진다. 프리페어드 스테이트먼트/파라미터 바인딩이 전제다.
- **누적 카운터라 리셋 시점 관리가 필요하다.** 두 시점의 차이를 떠서 "구간 총 시간"을 봐야 의미가 있다.

### 4-2. 샘플링 — 편향 없이, 비용은 고정으로

**임계값 필터는 관심 변수(지연)에 상관된 필터**라서 편향이 생긴다. **무작위 샘플링은 지연과 무관한 필터**라서 편향이 없다. 이게 통계적 요점이다.

- **요청 단위 균등 샘플링 (1/N)**: 실행 중 N개에 1개만 기록한다. 표본 총합에 N을 곱하면 모집단 총 시간의 불편추정량(unbiased estimator)이 된다. 하루 1,300만 건에서 1/1000을 뜨면 13,000줄이고, 1.2ms짜리도 13,000분의 1의 비율로 **분명히 표본에 들어온다.** 100ms 임계값에서는 확률 0이었다.
- **연속 프로파일러 (wall-clock/CPU 샘플링)**: `perf`, `py-spy`, eBPF 기반 도구, 상용 continuous profiler. 일정 주기로 스택을 찍기 때문에 **표본이 자연스럽게 소요 시간에 비례해서 뽑힌다.** 하루 2.64시간을 먹는 권한 계산 스택은 하루 62초짜리 커뮤니티 탐지 스택보다 **약 150배 많이 잡힌다.** 별도 계산 없이 프로파일 그래프의 막대 길이가 곧 ex4의 총 시간 순위다.
- **테일 기반 샘플링 트레이싱**: 트레이스를 일단 버퍼링한 뒤 "느린 것"과 "무작위 표본"을 **둘 다** 남기는 정책. 느린 쿼리 로그의 용도와 총 시간 관측을 하나의 파이프라인에서 얻는다.

샘플링의 핵심 장점은 **비용이 QPS와 무관하게 상한이 있다**는 것이다. 임계값 로그는 워크로드가 느려지면 로그가 폭증하는데(가장 곤란한 순간에 부하가 추가된다), 샘플링은 그렇지 않다.

주의: 샘플링은 **드문 사건(하루 2번 도는 커뮤니티 탐지)을 놓친다.** 그래서 샘플링과 임계값 로그는 배타적이지 않고 **상보적**이다.

### 4-3. 총 시간 순위 대시보드 — 매일 보는 화면 하나

지문별 집계든 애플리케이션 계측이든, 최종 산출물은 **총 시간 내림차순 표 하나**여야 한다. 사람이 매일 열어 보는 화면이 `p99 지연`뿐이면 아무리 좋은 계측을 깔아도 소용없다.

Prometheus 히스토그램을 쓴다면 핵심 지표는 `_sum`이다.

```promql
# 쿼리 종류별 "초당 소비한 초" = 평균적으로 상시 점유하는 코어 수
topk(10,
  sum by (query_name) (
    rate(query_duration_seconds_sum[5m])
  )
)
```

`rate(..._sum[5m])`은 **"초당 몇 초의 작업을 소비했나"**이고, 이는 곧 리틀의 법칙에서의 평균 동시성 — **그 쿼리가 상시 점유하는 코어 수**다. ex4의 "하루 총 시간"과 정확히 같은 양이다. 반면 흔히 대시보드에 거는

```promql
histogram_quantile(0.99, rate(query_duration_seconds_bucket[5m]))   # p99
```

는 사용자 체감을 보여줄 뿐 **비용에 대해서는 아무것도 말해 주지 않는다.** `_sum`과 `_count`가 이미 히스토그램에 들어 있는데도 안 보는 팀이 많다.

애플리케이션 계층에서 직접 감쌀 때의 최소 구현은 이 정도면 된다.

```python
from collections import defaultdict
import time, threading

_stats = defaultdict(lambda: {"calls": 0, "total_ms": 0.0, "max_ms": 0.0})
_lock = threading.Lock()

def run(conn, name, q, params=None):
    """name = 쿼리 지문. 리터럴이 아니라 «쿼리 종류» 이름을 붙인다."""
    t0 = time.perf_counter()
    try:
        return conn.execute(q, params or {})
    finally:
        ms = (time.perf_counter() - t0) * 1000
        with _lock:
            s = _stats[name]
            s["calls"] += 1
            s["total_ms"] += ms                 # ← 임계값 없이 «전부» 더한다
            s["max_ms"] = max(s["max_ms"], ms)

def report():
    total = sum(s["total_ms"] for s in _stats.values()) or 1
    for name, s in sorted(_stats.items(), key=lambda r: -r[1]["total_ms"]):
        print(f"{name:<22}{s['calls']:>12,}"
              f"{s['total_ms']/s['calls']:>10.2f}ms"
              f"{s['total_ms']/1000/3600:>10.2f}h"
              f"{s['total_ms']/total:>8.1%}")
```

포인트는 `if ms > THRESHOLD:`가 **어디에도 없다**는 것이다. 한 줄에 하나씩 기록하지 않고 **누적만** 하기 때문에 초당 153건이 들어와도 메모리는 지문 개수만큼만 쓴다. 임계값 로그의 두 가지 문제(편향, 볼륨)를 동시에 피한다.

## 5. 정리 — 두 지표는 다른 질문에 답한다

| | 느린 쿼리 로그 / p99 | 총 시간 순위 |
|---|---|---|
| 답하는 질문 | 사용자가 **기다린다**고 느끼는 게 뭔가 | 인프라를 **먹는** 게 뭔가 |
| 편향 | 지연에 상관된 필터 → 고빈도 쿼리 누락 | 없음(전수 누적) 또는 무편향 표본 |
| ex4에서 1위 | 커뮤니티 탐지 (31초) | 사용자 권한 계산 (3.4ms) |
| 고쳤을 때 효과 | 하루 0.009h | 하루 1.32h |
| 비용 | 임계값 낮추면 폭증 | 지문 수에 비례(고정) |

**둘 다 필요하다. 다만 고치는 순서는 대개 후자가 먼저다.**

그리고 이 순위를 만든 다음에도 33.5절의 암달의 법칙이 남는다. 총 시간 32%를 먹는 권한 계산을 **0ms로 만들어도** 전체는 32%밖에 안 준다. `ex5_where_time_goes.py`가 보여주듯, 그래프 조회 전체가 한 요청 1,919ms 중 9ms(0.5%)라면 — 쿼리 순위표에서 1등을 완전히 없애도 사용자는 아무것도 못 느낀다. **순위표는 "무엇을 고칠지"를 알려 주지, "고칠 가치가 있는지"를 알려 주지 않는다.** 그건 한 단계 위에서 구간을 쪼개 봐야 안다.

## 6. 자주 나오는 오해

**"임계값을 0으로 두면 되잖아요."**
편향은 사라지지만 볼륨과 관측자 효과가 생긴다. 초당 153줄, 하루 3.3GB, 그리고 1.2ms 쿼리에 붙는 로깅 오버헤드가 측정 대상을 바꾼다. 카운터 누적(4-1)이나 샘플링(4-2)이 정답이다.

**"p99을 보면 되잖아요."**
p99은 여전히 **지연의** 분포다. 호출 수를 곱하지 않으므로 총 시간에 대해서는 말해 주지 않는다. 하루 2번 도는 쿼리와 하루 610만 번 도는 쿼리가 p99 계산에서 같은 취급을 받으면 안 된다(전자는 표본이 2개뿐이라 p99 자체가 무의미하기도 하다).

**"제일 아픈 게 항상 제일 자주 도는 것인가요?"**
아니다. `총 시간 = 지연 × 호출 수`의 곱이다. ex4에서 호출 1위는 「이름으로 사람 찾기」(610만)지만 총 시간 1위는 「사용자 권한 계산」(280만)이다. **어느 한쪽 항으로 줄 세우면 안 되고, 곱으로 줄 세워야 한다.** 느린 쿼리 로그는 왼쪽 항만, 호출 카운터는 오른쪽 항만 본다.

**"그럼 느린 쿼리 로그는 꺼도 되나요?"**
아니다. 하루 2번이라도 31초를 기다리는 사용자는 실재한다. 타임아웃·락 홀딩·커넥션 고갈 같은 **가용성** 문제는 총 시간 순위에서 절대 안 보이고 느린 쿼리 로그에서만 보인다. 용도가 다른 두 도구를 하나로 착각하는 것이 함정이지, 도구 자체가 나쁜 게 아니다.
