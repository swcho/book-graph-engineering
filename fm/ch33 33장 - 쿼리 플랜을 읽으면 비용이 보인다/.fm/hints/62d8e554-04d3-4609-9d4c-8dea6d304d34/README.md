# "작은 쪽에서 시작하라"는 조언은 요즘 엔진에서 유효한가?

**답: 대개 상관없다. 플래너가 알아서 정하므로, 순서를 고민하기 전에 플랜을 봐야 한다.**

---

## 1. 그 조언은 어디서 왔나

「작은 쪽에서 시작하라」는 그래프 쿼리 튜닝의 오래된 격언입니다.
`MATCH (t:Team)<-[:Member]-(p:Person)` 처럼 쓸 때, 팀(80개)에서 시작하면
80개만 훑고 관계를 따라가면 되지만, 사람(8,000명)에서 시작하면 8,000명을 훑는다는 논리죠.
카디널리티가 작은 쪽을 앵커(시작점)로 잡으라는 말입니다.

논리 자체는 틀리지 않았습니다. 문제는 **그 결정을 사람이 해야 하느냐**입니다.

## 2. 재 보면 차이가 없다

33장 `ex1_read_plan.py` 는 「마포에 사는 팀7 구성원 수」를 세는 쿼리 세 개를
같은 데이터(사람 8,000명, 팀 80개, 소속 엣지 8,000개)에서 나란히 잽니다.

| 쿼리 | 형태 | 결과 |
|---|---|---|
| A. 두 끝을 따로 찾음 | `MATCH (p:Person), (t:Team) WHERE ... AND EXISTS { MATCH (p)-[:Member]->(t) }` | B·C의 **3.4배** 느림 |
| B. 팀에서 시작 (작은 쪽) | `MATCH (t:Team {name:'팀7'})<-[:Member]-(p:Person)` | 기준 |
| C. 사람에서 시작 (큰 쪽) | `MATCH (p:Person {city:'마포'})-[:Member]->(t:Team)` | B와 **거의 같음** |

세 쿼리의 답은 셋 다 100으로 동일합니다.

핵심은 **B와 C가 거의 같다**는 것입니다. 「작은 쪽(팀)에서 시작」한 B와
「큰 쪽(사람)에서 시작」한 C의 성능 차이가 사실상 없습니다.
왜냐면 엔진이 쿼리를 파싱한 뒤 **어느 쪽에서 시작할지를 알아서 다시 정했기** 때문입니다.
즉 내가 쓴 순서가 실제 실행 순서가 아닙니다.

저자의 말: "저는 오래 이걸 튜닝 포인트로 알고 있었는데, 재 보니 아니었다."

## 3. 왜 그런가 — 플래너(planner)의 역할

현대 쿼리 엔진(Neo4j, Kùzu, PostgreSQL 등)은 **선언형 쿼리 → 실행 플랜** 사이에
플래너/옵티마이저 단계를 둡니다. 플래너는 통계(각 라벨의 노드 수, 속성 값의 분포,
관계 밀도 등)를 보고 비용을 추정해서 조인 순서와 시작점을 스스로 고릅니다.

그러니까 **작성 순서는 힌트조차 아닙니다.** 플래너가 통계를 갖고 있는 한
B로 쓰든 C로 쓰든 같은(또는 거의 같은) 플랜으로 수렴합니다.

이게 SQL에서도 똑같습니다. `FROM a, b` 와 `FROM b, a` 가 성능이 다르던 시절은
비용 기반 옵티마이저(CBO)가 자리잡기 전 얘기입니다.

## 4. 그러면 진짜 차이를 만드는 건 뭔가

A입니다. A는 3.4배 느린데, 이유는 순서가 아니라 **플랜에 `CROSS_PRODUCT`(곱집합)가
들어 있어서**입니다. 두 끝(Person, Team)을 각각 따로 찾아 놓고 8,000 × 80 = 64만 조합을
만든 뒤에 거기서 거릅니다.

이건 순서 문제가 아니라 **쿼리를 관계로 잇지 않고 두 조각으로 써 버린 구조 문제**입니다.
그리고 데이터가 자라면 곱으로 커집니다. 지금은 3.4배지만 사람이 80만 명이면 배수가 훨씬 커집니다.

## 5. 그래서 플랜에서 볼 것은 세 가지

```
1. CROSS_PRODUCT 가 있나  — 있으면 거기부터 고친다 (제일 먼저 찾을 단어)
2. SCAN 이 무엇을 훑나     — 인덱스를 타나, 전체를 훑나
3. FILTER 가 SCAN 앞인가 뒤인가 — 뒤면 훑고 나서 버리는 것이다
```

「어느 쪽에서 시작할까」를 머릿속으로 굴리는 시간에 `EXPLAIN` 을 한 번 돌리는 게 낫습니다.
추측이 아니라 엔진이 실제로 무엇을 하는지가 나오니까요.

## 6. 단, 「한 번 보고 끝」은 아니다

플래너의 선택은 **통계에 의존**합니다. 그래서:

- 팀이 80개가 아니라 80만 개가 되면 엔진의 선택이 바뀝니다.
- 데이터가 자라면 플랜도 **다시** 봐야 합니다.
- 통계가 낡았거나(ANALYZE 미실행), 데이터 분포가 심하게 치우쳤거나,
  플래너가 추정하기 어려운 형태(복잡한 서브쿼리, 상관 조건)면 플래너가 틀릴 수 있습니다.
  그럴 때 비로소 힌트나 쿼리 재작성이 등장합니다 — 하지만 **그것도 플랜을 본 다음**입니다.

## 7. 한 줄 정리

> 「작은 쪽에서 시작하라」는 요즘 엔진에서는 대개 상관없다.
> 플래너가 알아서 정한다. 순서를 고민하기 전에 플랜을 보라.
> 정말 아픈 건 순서가 아니라 `CROSS_PRODUCT` 다.

## 관련 개념 (같은 장)

- **인덱스**: 걸면 다 빨라지는 게 아니라 「찾는 방식」에 맞아야 듭니다.
  그리고 그래프에서 관계를 따라가는 데는 인덱스가 필요 없습니다 — 시작점 하나만
  인덱스로 찾으면 그다음은 공짜입니다.
- **암달의 법칙**: 쿼리를 아무리 튜닝해도 모델 호출이 전체의 94.8%면 나머지를
  전부 최적화해도 3%입니다. 튜닝 전에 구간별로 쪼개 보세요.
