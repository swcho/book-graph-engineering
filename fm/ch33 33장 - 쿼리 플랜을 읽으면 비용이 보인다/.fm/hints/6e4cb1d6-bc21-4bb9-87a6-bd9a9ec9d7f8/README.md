# 「그래프 DB가 느리다」는 결론은 대개 적재에서 나온다

**Q. "그래프 DB가 느리다"는 결론의 상당수가 어디서 나오는가?**

**A. 한 건씩 넣는 적재다. 일괄 적재가 수십 배 빠르다.**

---

## 1. 무슨 장면인가

새 그래프 DB를 처음 만져 보는 사람이 가장 먼저 하는 일은 데이터를 넣어 보는 것입니다.
그리고 가장 자연스럽게 쓰는 코드는 이겁니다.

```python
for row in rows:                                  # 100만 건
    conn.execute("CREATE (:Person {id:$i, name:$n, city:$c})", row)
```

이게 30분 걸립니다. 그러면 결론이 이렇게 납니다.

> "그래프 DB 느리네. 관계형으로 갔으면 벌써 끝났을 텐데."

그런데 같은 데이터를 이렇게 넣으면 몇 초입니다.

```python
conn.execute("COPY Person FROM 'p.csv'")
```

33장 예제가 실제로 이 방식을 씁니다. `ex1_read_plan.py`는 사람 8,000명과 소속 엣지
8,000개를 CSV로 쓴 뒤 `COPY Person FROM ...`, `COPY Member FROM ...`으로 밀어 넣습니다.
장 서두의 실행 가이드에도 이렇게 적혀 있어요.

> `ex1`, `ex2`는 데이터를 만드는 데 몇 초 걸립니다. `COPY`로 일괄 적재해서
> 한 건씩 넣는 것보다 훨씬 빠릅니다. 그 자체가 33장에서 다루는 얘기이기도 합니다.

즉 **느린 것은 DB가 아니라 적재 방식**입니다. 벤치마크의 대상을 잘못 잡은 것이죠.

---

## 2. 왜 그렇게 차이가 나나 — 고정비용의 정체

한 건을 넣을 때 실제로 "저장"에 쓰이는 시간은 아주 작습니다. 문제는 그 앞뒤에
붙는 **건마다 반복되는 고정비용**입니다.

| 단계 | 건별 INSERT | 일괄 적재(COPY/import) |
|---|---|---|
| 네트워크 왕복 | 100만 번 | 1번(또는 파일 경로만 전달) |
| 쿼리 문자열 파싱 | 100만 번 | 1번 |
| 바인딩·의미 분석 | 100만 번 | 1번 |
| 쿼리 플래닝 | 100만 번 | 1번 |
| 트랜잭션 시작/커밋 | 100만 번 | 1번(또는 배치 단위) |
| WAL 기록 + `fsync` | 100만 번 | 배치 단위 / 우회 |
| 인덱스 갱신 | 건마다 한 개씩 | 마지막에 정렬 후 한 번에 구축 |
| 페이지 캐시 flush | 산발적 랜덤 I/O | 순차 대량 쓰기 |

특히 무거운 두 가지가 있습니다.

**(1) 커밋마다의 디스크 동기화.**
자동 커밋(autocommit)으로 돌면 `CREATE` 한 줄이 곧 트랜잭션 하나입니다. 트랜잭션이
"끝났다"고 말하려면 로그를 물리 디스크에 확실히 내려야(`fsync`) 해요. 이게 장치에 따라
수백 마이크로초에서 수 밀리초입니다. 여기에 100만을 곱하면 그 자체로 수십 분입니다.
저장할 데이터가 몇십 바이트든 상관없습니다. **내구성 보장의 값이지 데이터 양의 값이 아니기 때문**입니다.

**(2) 파싱·플래닝 고정비용.**
이건 33장이 다른 절에서 이미 재 본 값입니다. `ex2_index_effect.py`의 결론을 보세요.

> 이 규모에서는 «쿼리를 파싱하고 계획을 세우는» 값이 지배하기 때문이다.
> 실제 찾기는 둘 다 1ms도 안 걸리는데, 그 앞뒤에 붙는 고정 값이 훨씬 크다.

조회에서 인덱스 효과를 가려 버린 그 고정비용이, 적재에서는 **건수만큼 곱해집니다.**
조회에서는 "인덱스가 안 듣는 것처럼 보이는" 정도의 착시였지만, 적재에서는
"이 DB는 못 쓰겠다"는 결론까지 갑니다.

## 3. 상각(amortization) 구조로 정리하면

같은 이야기를 식 하나로 쓸 수 있습니다. `F`를 문장 하나당 고정비용(파싱 + 플래닝 +
왕복 + 커밋 fsync), `v`를 레코드 하나를 실제로 기록하는 비용이라고 하면,

```
건별 INSERT :  T = N × (F + v)
일괄 적재   :  T = F + N × v'        (v' ≤ v, 순차 I/O + 인덱스 일괄 구축)
```

건별에서는 `F`가 `N`에 **곱해지고**, 일괄에서는 `F`가 `N`으로 **나뉩니다(상각)**.
그리고 현실에서 `F ≫ v`이므로 건별의 총 시간은 사실상 `N × F`입니다.
데이터를 쓰는 시간이 아니라 **의식(ceremony)을 치르는 시간**이 전부인 셈이죠.

배수가 "수십 배"로 표현되는 이유도 여기 있습니다. `F/v` 비율이 그대로 배수가 되는데,
디스크·네트워크 상황에 따라 수십 배에서 수백 배까지 벌어집니다.

## 4. 그래서 어떻게 넣나 — 단계별 선택지

한 가지 방법만 있는 게 아닙니다. 상황에 맞게 고르면 됩니다.

| 방법 | 상대 속도 | 언제 쓰나 |
|---|---|---|
| 자동 커밋 단건 `CREATE` | 1× (기준) | 몇십 건. 그 이상은 쓰지 말 것 |
| 트랜잭션으로 묶기 (수천 건 단위 커밋) | 수× ~ 수십× | 애플리케이션에서 스트리밍 유입 |
| 파라미터 배치 (`UNWIND $rows AS r CREATE ...`) | 수십× | 온라인 상태에서 대량 유입. 파싱·플래닝도 1회로 상각 |
| `COPY FROM` / `LOAD CSV` (Kuzu, Postgres 등) | 수십× ~ | 초기 적재, 재적재 |
| 오프라인 임포터 (`neo4j-admin import` 등) | 수백× | 빈 DB에 초기 대량 적재. 트랜잭션 계층 자체를 건너뛰고 저장 파일을 직접 만든다 |

`UNWIND` 배치가 특히 중요합니다. 서비스가 돌고 있어서 오프라인 임포터를 못 쓸 때,
쿼리 텍스트는 하나로 두고 파라미터만 배열로 넘기는 방식이에요. 파싱·플래닝·왕복·커밋이
전부 배치 크기만큼 상각됩니다. 배치 크기는 보통 1,000~10,000행 정도에서
"메모리와 트랜잭션 롤백 비용" 사이 균형이 잡힙니다.

한 가지 덧붙이면, 33장의 `ex1_read_plan.py`는 팀 80개는 그냥 `CREATE` 루프로 넣고
사람 8,000명과 엣지 8,000개만 `COPY`로 넣습니다. **규모에 따라 골라 쓰는 게 맞다**는
실제 예시입니다. 80건짜리에 CSV를 만드는 건 오히려 번잡하니까요.

## 5. 이 카드가 33장에서 갖는 의미

33장의 큰 주제는 "재고 나서 고치기"입니다. 그런데 이 카드는 그중에서도
**측정 자체가 틀린 경우**를 다룹니다.

- `ex2`: 수천 개 규모에서 재고 "인덱스가 별 효과 없네"라고 결론 → 규모가 작아서 틀린 결론
- 이 카드: 건별 적재로 재고 "그래프 DB가 느리네"라고 결론 → 적재 방식이 틀려서 틀린 결론

둘 다 같은 실수의 변주입니다. **고정비용이 지배하는 구간에서 재고, 그 결과를
시스템의 본질적 성능으로 착각하는 것.** 33장이 반복해서 경고하는 게 이거예요.
플랜을 읽든 비용을 쪼개든, 먼저 "내가 지금 재고 있는 게 무엇인가"를 물어야 합니다.

---

## 6. 한 줄 정리

> 건별 INSERT는 파싱·플래닝·트랜잭션 커밋이라는 고정비용을 **건수만큼 곱하고**,
> 일괄 적재는 그 고정비용을 **건수로 나눈다.** 그 차이가 수십 배이고,
> 그래서 "그래프 DB가 느리다"는 결론의 상당수는 DB가 아니라 적재 방식의 문제다.

**연관 키워드:** 일괄 적재(bulk load), `COPY`, `UNWIND` 배치, 자동 커밋, `fsync`,
쿼리 플래닝 고정비용, 상각(amortization)
