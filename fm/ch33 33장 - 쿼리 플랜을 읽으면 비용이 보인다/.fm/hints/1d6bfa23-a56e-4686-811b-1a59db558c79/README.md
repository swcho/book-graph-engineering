# 많은 팀이 순서를 거꾸로 하는 이유는 무엇인가?

## 정답

쿼리 튜닝은 **익숙하고, 재기 쉽고, 성과가 눈에 보입니다.**
「9ms에서 4ms로 줄였습니다」는 보고하기 좋은 문장이지만,
사용자는 1,919ms가 1,914ms가 된 것을 못 느낍니다.

---

## 1. 먼저 "순서"가 무엇인지

33.5절(`ex5_where_time_goes.py`)이 제시하는 올바른 순서는 이렇습니다.

1. 모델 호출 **횟수**를 줄인다 — 캐시, 라우팅(25장), 종료 조건(20장)
2. 모델 호출 **시간**을 줄인다 — 짧은 프롬프트, 작은 모델, 스트리밍
3. 그다음에 나머지를 본다

그런데 **3번을 1번보다 먼저 하는 팀이 많다**는 것이 이 카드가 묻는 "거꾸로 된 순서"입니다.
1번을 건너뛰고 3번(쿼리 튜닝, 인덱스, 직렬화, 커넥션 풀)부터 손대는 것이죠.

## 2. 왜 거꾸로 가나 — 측정 가능성 편향

세 가지가 겹칩니다.

| 이유 | 내용 |
|---|---|
| **익숙하다** | EXPLAIN 읽기, 인덱스 걸기는 엔지니어가 이미 훈련받은 기술입니다. 모델 호출 횟수를 줄이는 건 아키텍처를 다시 그리는 일이라 낯설고 무섭습니다. |
| **재기 쉽다** | 쿼리 지연은 마이크로초 단위로 반복 측정이 되고, 분산이 작고, before/after가 깔끔합니다. "모델 호출을 3회에서 2회로 줄였을 때 품질이 유지되는가"는 재기가 훨씬 어렵습니다. |
| **성과가 보인다** | "9ms → 4ms, 2.25배 개선"은 슬라이드 한 장에 들어갑니다. 스프린트 리뷰에서 박수받기 좋습니다. |

이것이 **측정 가능성 편향(measurability bias)** 입니다.
*재기 쉬운 지표를 최적화하는 경향.* 관련 이름으로는 이런 것들이 있습니다.

- **맥나마라 오류(McNamara fallacy)** — 측정 가능한 것만 의사결정에 넣고, 측정 어려운 것은 없는 셈 치는 것.
- **가로등 효과(streetlight effect)** — 열쇠를 잃어버린 곳이 아니라 밝은 곳에서 찾는 것. 최적화할 곳이 아니라 계측기가 붙어 있는 곳을 최적화합니다.
- **굿하트의 법칙(Goodhart's law)** — 지표가 목표가 되는 순간 좋은 지표이기를 멈춘다. "쿼리 평균 지연"을 팀 목표로 걸면, 사용자 체감과 무관하게 그 숫자만 내려갑니다.

핵심은 **최적화 대상이 "가장 아픈 곳"이 아니라 "가장 재기 쉬운 곳"으로 끌려간다**는 것입니다.

## 3. 국소 지표와 전역 지표의 괴리 — 숫자로

`ex5`의 한 요청 시간 분해입니다. 총 **1,919ms**.

| 구간 | ms | 전체 비중 | 최대 절감 | 절감 가능 ms |
|---|---:|---:|---:|---:|
| 입력 검증 | 3 | 0.16% | 0% | 0 |
| **그래프 조회 ×4** | **9** | **0.47%** | 50% | 4.5 |
| 벡터 검색 | 11 | 0.57% | 40% | 4.4 |
| 컨텍스트 조립 | 18 | 0.94% | 70% | 12.6 |
| **모델 호출** | **1,820** | **94.84%** | 30% | 546.0 |
| 응답 후처리 | 24 | 1.25% | 60% | 14.4 |
| 체크포인트 쓰기 | 34 | 1.77% | 80% | 27.2 |

### 9ms → 4ms의 산수

- **국소 지표(구간 지연)**: 9ms → 4ms = **55.6% 개선**. 2.25배 빨라졌습니다. 훌륭한 숫자입니다.
- **전역 지표(엔드투엔드 지연)**: 1,919ms → **1,914ms**.
  `5 / 1919 = 0.002606` → **0.26% 개선**.

같은 작업이 보고서에서는 **55.6% 개선**이고 사용자에게는 **0.26% 개선**입니다.
두 자릿수 배율의 괴리가 국소 지표와 전역 지표 사이에 벌어져 있습니다.

암달의 법칙으로 확인해도 같습니다. 개선 대상 비중 `p = 9/1919 = 0.0047`, 속도향상 `s = 2.25`:

```
전체 속도향상 = 1 / ((1 - p) + p/s) = 1.00261  →  0.26%
```

3주를 써서 얻은 것이 0.26%입니다.

### 사람이 5ms를 느끼는가

못 느낍니다. 인간의 시각 변화 인지 하한은 보통 수십 ms 수준이고, UI 응답에서 "즉시"로 느끼는 경계는 100ms 안팎으로 잡습니다(Nielsen의 고전적 응답시간 구간: 0.1초 / 1초 / 10초). 1,919ms처럼 이미 "기다리는 중"인 구간에서 5ms는 측정 노이즈보다도 작습니다. 실제로 이 시스템의 요청 간 지터가 5ms를 넘으면, 개선분은 **잡음 속에 완전히 묻힙니다.**

### 반대편 — 전역 지표를 보고 고르면

- 나머지 여섯 구간을 **전부 최대치로** 줄여도 63.1ms, 전체의 **3.3%**입니다.
- 모델 호출 하나만 30% 줄이면 546ms, 전체의 **28.5%**입니다.

즉, 3번(나머지 전부)을 완벽하게 해내는 것보다 1~2번(모델 호출)을 어중간하게 하는 것이 **9배 낫습니다.**

## 4. 이 장 안의 다른 사례들 — 같은 병

이 편향은 33장 전체에 반복됩니다.

- **33.3 제일 느린 것 vs 제일 아픈 것** (`ex4`)
  느린 쿼리 로그 임계값을 100ms로 잡으면, 1.2ms짜리 「이름으로 사람 찾기」는 **한 번도 안 찍힙니다.** 그런데 하루 610만 번 돕니다. 상위 셋(권한 계산·팀 구성원·이름 찾기)이 전체 총 시간의 87%를 먹는데 **셋 다 1~3ms짜리 "빠른" 쿼리**입니다. 계측기(느린 쿼리 로그)가 보여주는 것만 고치면, 정작 인프라를 먹는 것은 영원히 안 보입니다.
  - 권한 계산 3.4ms → 1.7ms: 하루 **1.3시간** 절감
  - 커뮤니티 탐지 31초 → 15초: 하루 **0.00003시간** 절감

- **33.4 청구서의 큰 칸** (`ex3`)
  그래프 조회는 월 3.6억 회로 제일 많이 도는데 비용 비중은 아주 작습니다. 모델 호출은 월 158만 회(전체 호출의 0.1% 미만)인데 청구서를 지배합니다. "쿼리를 2ms에서 1ms로" 줄여도 청구서는 거의 그대로입니다.
  - 쿼리 튜닝 → **지연**을 줄인다 (사용자가 기다리는 시간)
  - 토큰 줄이기 → **비용**을 줄인다 (청구서)
  - 둘을 헷갈리면 엉뚱한 데 시간을 씁니다.

- **33.2 인덱스 효과** (`ex2`)
  수천 개 규모에서 재고 "인덱스가 별 효과 없네"라고 결론 내리면 틀립니다. **측정 규모가 잘못되면 재기 쉬운 숫자조차 거짓말을 합니다.**

## 5. 이걸 막는 조직적 장치

개인의 각성으로는 안 고쳐집니다. 편향이 아니라 **인센티브 구조**의 문제이기 때문입니다. 장치로 막아야 합니다.

### (1) 목표를 전역 지표로 건다

팀 OKR/SLO에 거는 숫자를 바꿉니다.

| 걸지 말 것 (국소) | 걸 것 (전역) |
|---|---|
| 평균 쿼리 지연 | **엔드투엔드 p95 요청 지연** |
| DB CPU 사용률 | **요청당 총 비용(원)** |
| 인덱스 히트율 | **요청당 모델 호출 횟수 / 요청당 토큰 수** |
| 느린 쿼리 개수 | **쿼리별 총 시간(지연 × 호출 수) 상위 N** |

국소 지표는 **진단용 계기판**으로만 남기고, **목표로는 걸지 않습니다.** 목표로 걸리는 순간 굿하트의 법칙이 작동합니다.

### (2) 개선 보고 시 "전체 대비 비중"을 반드시 병기한다

성능 개선 보고 템플릿을 강제합니다.

```
[개선 항목] 그래프 조회 쿼리 플랜 수정
[국소]  9ms → 4ms  (-55.6%)
[전역]  1,919ms → 1,914ms  (-0.26%)   ← 이 줄이 없으면 리뷰 반려
[비용]  월 청구서 변화: -0.02%
[근거]  이 구간의 전체 요청 시간 대비 비중: 0.47%
```

"국소 %"만 적힌 보고는 받지 않습니다. **분모를 항상 전체로** 두게 하면, 3주짜리 0.26% 작업은 **착수 전에** 스스로 걸러집니다.

### (3) 착수 전 게이트 — 암달 상한을 먼저 계산한다

성능 작업 티켓을 열 때 첫 칸에 이걸 적게 합니다.

> "이 구간이 전체의 몇 %인가? 이 구간을 **0ms로 만들어도** 전체는 몇 % 좋아지는가?"

`ex5`의 「그래프 조회 ×4」라면 답은 "0.47%"입니다. 상한이 0.47%인 작업에 3주를 배정할 사람은 없습니다. **이 한 칸이 대부분의 잘못된 순서를 막습니다.**

### (4) 프로파일 우선 규칙 — "재고 나서 고치기"

7부(운영)의 첫 규칙입니다. 최적화 PR은 **구간별 시간 분해 결과를 첨부해야** 리뷰에 올라갑니다. 분포를 모르고 시작한 최적화는 거의 항상 가장 익숙한 구간을 향합니다.

### (5) 계측기의 사각지대를 정기 점검한다

느린 쿼리 로그의 임계값이 무엇을 못 보게 하는지 주기적으로 확인합니다. **"총 시간 순위" 대시보드**를 느린 쿼리 로그와 나란히 두는 것이 `ex4`의 결론입니다.
- 느린 쿼리 로그 → 사용자가 「기다린다」고 느끼는 것
- 총 시간 순위 → 인프라를 「먹는」 것
- 둘 다 봐야 하고, **고치는 순서는 대개 후자가 먼저**입니다.

### (6) 낯선 작업에 별도 예산을 배정한다

모델 호출 횟수 줄이기(캐시·라우팅·종료 조건)는 성과가 늦게 나고 측정이 어렵습니다. 스프린트 성과로 경쟁시키면 항상 집니다. **"측정하기 어렵지만 비중이 큰 작업"에 별도 트랙과 별도 평가 기준**을 주지 않으면 조직은 계속 쉬운 쪽을 고릅니다.

---

## 한 줄 정리

거꾸로 가는 이유는 무능이 아니라 **인센티브**입니다. 익숙하고, 재기 쉽고, 보고하기 좋은 일이 자동으로 먼저 선택됩니다. 「9ms → 4ms」는 국소적으로 55.6% 개선이지만 전역적으로는 **1,919ms → 1,914ms, 0.26%** 이고, 사용자는 그것을 느끼지 못합니다. 이를 막는 것은 각성이 아니라 **전역 지표를 목표로 걸고, 개선 보고에 전체 대비 비중을 병기하도록 강제하는 장치**입니다.
