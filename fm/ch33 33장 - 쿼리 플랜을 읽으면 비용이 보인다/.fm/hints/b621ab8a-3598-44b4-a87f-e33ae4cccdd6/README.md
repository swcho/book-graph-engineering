# 그래프 튜닝의 첫 질문

> **Q.** 그래프 튜닝의 첫 질문은 무엇인가?
>
> **A.** 「인덱스를 걸까」가 아니라 **「시작점을 인덱스로 찾고 나머지는 관계로 갈 수 있나」**다.

---

## 1. 한 줄로 줄이면

그래프 DB에서 인덱스는 **전 구간을 빠르게 하는 장치가 아니라, 첫 발을 딛는 장치**입니다.

- 한 번 발을 딛고 나면(= 앵커 노드를 잡고 나면) 그다음 홉은 인덱스 없이 갑니다. 이미 이어져 있으니까요.
- 그래서 튜닝의 질문이 「이 컬럼에 인덱스를 걸까?」에서 **「이 쿼리에 앵커가 있나?」**로 바뀝니다.

33장 예제 2(`ex2_index_effect.py`)의 마지막 문단이 이 카드의 원문입니다.

```
그리고 그래프에서는 하나 더 있다.
«관계를 따라가는 것»에는 인덱스가 필요 없다. 이미 이어져 있으니까.

그래서 그래프 튜닝의 첫 질문은 «인덱스를 걸까»가 아니라
«시작점을 인덱스로 찾고 나머지는 관계로 갈 수 있나»다.
시작점 하나만 인덱스로 찾으면 그다음은 공짜다.
```

---

## 2. 왜 질문이 달라지는가 — 관계형 사고 vs 그래프 사고

### 관계형 사고: 「모든 조인 컬럼에 인덱스」

관계형 DB에서 관계는 **값**으로 표현됩니다. `member.person_id = person.id` 같은 식이죠.
조인이란 결국 「이 값과 같은 값을 가진 행을 저쪽 표에서 찾아라」이고, 그 「찾아라」가 매번 발생합니다.

그래서 관계형 튜닝의 기본기는 이렇게 생겼습니다.

- 조인에 쓰이는 모든 컬럼에 인덱스를 건다.
- 외래 키에 인덱스가 없으면 조인마다 전체 스캔이 난다.
- 홉이 늘면 조인이 늘고, 조인이 늘면 인덱스 탐색이 늘어난다 — **깊이에 비례해 비용이 는다.**

3홉을 가려면 조인 3번, 인덱스 탐색 3번(정확히는 행 수만큼 반복)입니다. 홉이 깊어질수록 인덱스가 더 절실해집니다.

### 그래프 사고: 「앵커 하나만 인덱스, 나머지는 인접 리스트」

그래프 DB에서 관계는 **값이 아니라 물리적 포인터**로 저장됩니다. 이걸 흔히
**index-free adjacency**(무인덱스 인접성)라고 부릅니다.

- 노드 레코드가 자기 엣지 리스트의 위치를 직접 들고 있습니다.
- 이웃으로 가는 데 「어디 있지?」를 되묻지 않습니다. 주소를 따라가면 끝입니다.
- 한 홉의 비용이 **그래프 전체 크기와 무관**하게, 그 노드의 차수(degree)에만 비례합니다.

그러니 비용 구조가 이렇게 갈립니다.

| | 시작점 찾기 | 한 홉 이동 | 전체 크기의 영향 |
|---|---|---|---|
| 관계형 조인 | 인덱스 탐색 | 인덱스 탐색(매 행마다) | 표가 커지면 탐색 비용 증가 |
| 그래프 순회 | **인덱스 탐색 1회** | 포인터 추적 | 시작점 이후는 **거의 무관** |

> **핵심**: 그래프에서 인덱스가 하는 일은 딱 하나 — **「그래프 어디로 들어갈지」를 정하는 것**입니다.
> 진입한 뒤의 이동은 인덱스의 관할이 아닙니다.

---

## 3. 앵커가 없으면 무슨 일이 일어나나

앵커란 **인덱스나 기본 키로 소수의 노드로 좁혀지는 시작점**입니다.
앵커가 없으면 엔진은 들어갈 문을 못 찾고, 두 가지 나쁜 길로 떨어집니다.

### (a) 전체 `SCAN`

패턴의 어느 쪽에도 선택도 높은 조건이 안 붙으면, 엔진은 그 레이블의 노드를 **전부 훑습니다.**
`FILTER`가 `SCAN` **뒤**에 오는 플랜이 그 신호예요. 훑고 나서 버리는 겁니다.

```
SCAN(Person)  →  FILTER(p.city = '마포')   ← 훑고 나서 버린다
```

### (b) `CROSS_PRODUCT` (곱집합)

더 나쁜 경우입니다. **패턴의 두 끝을 서로 이어지지 않은 채 따로 찾으면** 엔진은
양쪽을 각각 만든 다음 곱해 놓고 거기서 거릅니다.

33장 예제 1(`ex1_read_plan.py`)이 이걸 실측으로 보여 줍니다. 세 쿼리 모두
「마포에 사는 팀7 구성원 수」를 세고, **답은 셋 다 같습니다.**

```cypher
-- A. 두 끝을 따로 찾음  ← 여기서 CROSS_PRODUCT가 난다
MATCH (p:Person), (t:Team)
WHERE t.name = '팀7' AND p.city = '마포'
  AND EXISTS { MATCH (p)-[:Member]->(t) }
RETURN count(p)

-- B. 팀에서 시작  ← 앵커: Team
MATCH (t:Team {name:'팀7'})<-[:Member]-(p:Person)
WHERE p.city = '마포'
RETURN count(p)

-- C. 사람에서 시작  ← 앵커: Person
MATCH (p:Person {city:'마포'})-[:Member]->(t:Team)
WHERE t.name = '팀7'
RETURN count(p)
```

측정 결과(사람 8,000명, 팀 80개):

- **A는 B·C의 3.4배** 느립니다. 플랜에 `CROSS_PRODUCT`가 있어서, 사람 8,000명 × 팀 80개
  = 64만 조합을 만들어 놓고 거기서 거릅니다.
- **B와 C는 거의 같습니다.** 「작은 쪽에서 시작하라」는 옛 조언이 무색하게, 요즘 플래너는
  어느 쪽에서 시작할지 알아서 정합니다. 저자도 오래 이걸 튜닝 포인트로 알고 있었는데
  재 보니 아니었다고 적고 있습니다.

> **여기서 진짜 무서운 대목**: 3.4배는 「지금 규모에서」의 숫자입니다.
> 곱집합은 데이터가 자라면 **곱으로** 커집니다. 사람이 80만 명이 되면 배수가 훨씬 커져요.
> 오늘 안 아픈 A가 내년에 장애를 냅니다.

**A와 B·C의 차이는 인덱스가 아닙니다.** 세 쿼리 모두 같은 스키마, 같은 인덱스 위에서 돕니다.
차이는 오직 **「앵커를 잡고 관계로 갔느냐, 두 끝을 따로 찾아 붙였느냐」**입니다.
이게 「인덱스를 걸까」가 첫 질문이 아닌 이유예요.

## 4. 인덱스를 걸어도 안 듣는 경우들

「인덱스를 걸까」가 첫 질문이 되면 안 되는 이유가 하나 더 있습니다.
**인덱스는 「찾는 방식」에 맞아야 듭니다.**

| 찾는 방식 | 듣는 인덱스 |
|---|---|
| 같음 비교 `=` | 해시 인덱스가 듣는다 |
| 범위 비교 `<`, `>` | 정렬 인덱스가 듣는다. 해시는 안 듣는다 |
| 앞부분 일치 `STARTS WITH` | 정렬 인덱스가 듣는다 |
| 가운데 일치 `CONTAINS` | **어느 것도 안 듣는다.** 전문 검색(full-text)이 필요하다 |

그리고 하나 더 — **규모가 작으면 인덱스 효과 자체가 안 보입니다.**
예제 2에서 노드를 2,000 → 128,000까지 키우며 「기본 키로 찾기 : 속성으로 찾기」 배수를 쟀는데,
배수가 **1.1 언저리에서 거의 안 변합니다.** 이 규모에서는 쿼리 파싱·계획 수립의 고정 비용이
지배하기 때문이에요. 실제 찾기는 둘 다 1ms도 안 걸리는데 앞뒤 고정 값이 훨씬 큽니다.

여기서 두 방향의 착각이 다 나옵니다.

- 수천 개에서 재고 「인덱스가 별 효과 없네」라고 결론 내면 **틀립니다.**
- 반대로 수천 개짜리 데이터에 인덱스를 붙이며 튜닝하는 것도 **헛일입니다.**

## 5. 실전 체크리스트

### 쿼리를 쓸 때 (설계 시점)

1. **이 쿼리의 앵커는 무엇인가?** 한 문장으로 답할 수 있어야 합니다.
   「Team 노드를 name으로 잡고 거기서 Member를 역방향으로 편다」처럼요.
2. **앵커가 충분히 선택도가 높은가?** `WHERE t.active = true` 같은 조건은 앵커가 아닙니다.
   절반이 걸리는 조건으로 시작하면 시작 안 한 거나 마찬가지예요.
3. **앵커에서 목표까지 관계로 이어지는가?** 패턴이 하나의 연결된 그래프여야 합니다.
   `MATCH (a), (b)`처럼 콤마로 끊긴 패턴이 보이면 곱집합 신호입니다.
4. **앵커가 정말 없으면**, 그건 쿼리 문제가 아니라 **모델링 문제**일 수 있습니다.
   진입점 노드를 만들거나(예: `(:City {name})` 노드를 세워 `Person`을 매달기),
   자주 쓰는 조건을 별도 레이블로 승격하는 걸 검토하세요.

### 플랜을 읽을 때 (검증 시점)

`EXPLAIN` / `PROFILE`을 걸고 **세 가지만** 찾습니다 (33.1절).

1. **`CROSS_PRODUCT`가 있나** — 있으면 **거기부터** 고칩니다. 다른 걸 보기 전에요.
2. **`SCAN`이 무엇을 훑나** — 인덱스를 타는지, 레이블 전체를 훑는지.
   앵커가 잡혔다면 시작 연산자는 인덱스 탐색이어야 합니다.
3. **`FILTER`가 `SCAN` 앞인가 뒤인가** — 뒤면 훑고 나서 버리는 겁니다.

### 그리고 잊기 쉬운 것

- **플랜은 한 번 보고 끝이 아닙니다.** 팀이 80개가 아니라 80만 개가 되면 엔진의 선택이 바뀝니다.
  데이터가 자라면 플랜도 다시 봐야 합니다.
- **인덱스 효과 측정은 충분히 큰 규모에서.** 수천 건짜리 벤치마크는 파싱 비용을 재는 것입니다.
- **한 건씩 넣지 마세요.** 일괄 적재(`COPY` / `neo4j-admin import`)가 수십 배 빠릅니다.
  「그래프 DB가 느리다」는 결론의 상당수가 여기서 나옵니다.

## 6. 한 발 물러서서 — 이 튜닝이 청구서를 바꾸는가

33장의 나머지 절이 던지는 찬물입니다. 앵커를 잡아 쿼리를 2ms에서 1ms로 줄여도
**청구서는 거의 안 바뀝니다.** 예제 3에서 그래프 조회는 월 3억 6천만 회로 제일 많이 도는데
비중은 아주 작고, 월 158만 회뿐인 모델 호출이 비용을 압도합니다.

그래서 목적을 구분해야 합니다.

- **쿼리 튜닝** → 「지연」을 줄인다. 사용자가 기다리는 시간.
- **토큰 줄이기** → 「비용」을 줄인다. 청구서.

다만 이 카드의 질문은 여전히 유효합니다. 왜냐하면 **곱집합은 「1ms를 0.5ms로」가 아니라
「선형을 제곱으로」의 문제**이기 때문입니다. 미세 튜닝이 아니라 **폭발 방지**예요.
그리고 쿼리를 *정확하게* 만들면(불필요한 조합을 안 만들면) 모델에 실어 보내는
컨텍스트도 함께 줄어서 토큰까지 줍니다.

---

## 외우는 문장

> 인덱스는 **문**이지 **길**이 아니다.
> 문 하나만 인덱스로 열고, 나머지는 관계로 걸어라.
> 문이 없으면 엔진은 벽을 다 훑거나(`SCAN`) 곱집합을 만든다(`CROSS_PRODUCT`).
