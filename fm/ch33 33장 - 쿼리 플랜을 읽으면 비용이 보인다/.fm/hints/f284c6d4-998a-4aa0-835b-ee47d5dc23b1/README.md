# 권한 계산 vs 커뮤니티 탐지 — 같은 "절반"인데 왜 효과가 다른가

## 질문

권한 계산을 절반으로 줄이는 것과 커뮤니티 탐지를 절반으로 줄이는 것의 효과 차이는 얼마인가?

## 답

권한 계산은 하루 1.3시간이 줄고, 커뮤니티 탐지는 하루 0.00003시간이 준다.

(이 뒤 숫자는 33장 `code/ex4_hot_query.py` 의 워크로드에서 나온다. 다만 커뮤니티 탐지 쪽 수치에는 자릿수 문제가 있다 — 아래 **주의** 참고.)

---

## 1. 핵심 산수 한 줄

```
개선의 가치 = 총 시간 × 개선율
총 시간     = 1회 지연 × 호출 수
∴ 개선의 가치 = 1회 지연 × 호출 수 × 개선율
```

여기서 중요한 건 **개선율(50%)은 두 쿼리가 똑같다**는 점이다. 같은 값이 양쪽에 곱해지므로, 절감량의 비는 그냥 **총 시간의 비**가 된다.

```
절감량_A / 절감량_B = (총시간_A × 0.5) / (총시간_B × 0.5) = 총시간_A / 총시간_B
```

즉 "몇 % 개선했나"는 순위를 못 정한다. 순위를 정하는 건 **그 앞에 곱해져 있는 총 시간**이다. 이게 이 카드의 전부다.

## 2. ex4 워크로드로 직접 계산

`ex4_hot_query.py` 의 표(1회 ms, 하루 호출 수)와 `총 시간 = ms × 호출수 / 1000 / 3600` (시간 단위):

| 쿼리 | 1회 ms | 하루 호출 | 하루 총 시간 | 비중 | 절반으로 줄이면 |
|---|---:|---:|---:|---:|---:|
| 사용자 권한 계산 | 3.4 | 2,800,000 | **2.644h** | 32.0% | **−1.322h** |
| 팀 구성원 조회 | 2.1 | 4,200,000 | 2.450h | 29.7% | −1.225h |
| 이름으로 사람 찾기 | 1.2 | 6,100,000 | 2.033h | 24.6% | −1.017h |
| 2홉 이웃 탐색 | 18.0 | 140,000 | 0.700h | 8.5% | −0.350h |
| 전체 조직도 렌더 | 820.0 | 1,400 | 0.319h | 3.9% | −0.159h |
| 월간 감사 리포트 | 12,000.0 | 30 | 0.100h | 1.2% | −0.050h |
| 커뮤니티 탐지 | 31,000.0 | 2 | **0.0172h** | 0.2% | **−0.0086h** |
| **합계** | | | **8.264h** | 100% | |

- 권한 계산: `3.4ms × 2,800,000 = 9,520,000ms = 9,520초 = 2.644시간` → 절반이면 **1.32시간 절감**. (책의 "하루 1.3시간" 과 일치)
- 커뮤니티 탐지: `31,000ms × 2 = 62,000ms = 62초 = 0.0172시간` → 절반이면 **0.0086시간 절감** (약 31초).

비는 `2.644 / 0.0172 ≈ 154배`. 같은 "50% 개선"인데 한쪽이 **150배 이상** 값어치가 크다.

> **주의**
> 카드 답변(그리고 asset의 `ex4_hot_query.py` 본문 해설)에 적힌 **"0.00003시간"은 자릿수가 맞지 않는다.**
> 같은 파일 앞부분이 커뮤니티 탐지의 하루 총 시간을 **"0.02시간"** 이라고 밝히고 있으므로, 그것을 절반으로 줄이면 당연히 **약 0.0086시간(≈0.009시간, 31초)** 이어야 한다. 0.00003시간은 0.108초에 불과해서 asset 자신의 0.02시간 진술과도 약 290배 어긋난다.
> 밀리초/초 단위를 한 번 더 나눈 1000배급 단위 혼동으로 보인다(예: 62,000ms 대신 62를 ms로 넣으면 0.0000172시간이 나온다).
> 카드 파일은 그대로 두고, 학습할 때는 **정정값 0.0086시간(약 31초), 권한 계산 대비 약 154배 차이** 로 기억하면 된다.
> 어느 숫자를 쓰든 결론은 바뀌지 않는다: 절대 절감량은 총 시간에 비례하고, 총 시간이 0.2%인 쿼리를 아무리 반으로 줄여도 청구서·인프라에는 거의 보이지 않는다.

## 3. "제일 느린 것"과 "제일 아픈 것"

`ex4` 가 만든 두 개의 줄 세우기가 완전히 다르다는 게 요점이다.

**1회 지연 순 (느린 순)**

1. 커뮤니티 탐지 31,000ms
2. 월간 감사 리포트 12,000ms
3. 전체 조직도 렌더 820ms
4. 2홉 이웃 탐색 18ms

**하루 총 시간 순 (아픈 순)**

1. 사용자 권한 계산 2.64h (32%)
2. 팀 구성원 조회 2.45h (30%)
3. 이름으로 사람 찾기 2.03h (25%)
4. 2홉 이웃 탐색 0.70h (8%)

지연 순 1·2위(커뮤니티 탐지, 감사 리포트)는 총 시간 순에서 꼴찌 근처다. 반대로 총 시간 상위 셋은 전부 **1~3ms짜리 "빠른" 쿼리**인데 합쳐서 전체의 87%를 먹는다.

호출 수가 이 역전을 만든다.

- 커뮤니티 탐지: 하루 **2회**
- 권한 계산: 하루 **280만 회** (140만 배)

1회 지연이 9,000배 느려도 호출 수가 140만 배 적으면 총 시간에서는 진다.

## 4. 왜 이걸 놓치는가 — 느린 쿼리 로그의 함정

느린 쿼리 로그(slow query log)는 **임계값 초과 건**만 남긴다. 임계값을 100ms로 잡으면:

- 커뮤니티 탐지(31,000ms) → 매번 찍힌다. 눈에 띈다. 튜닝하고 싶어진다.
- 권한 계산(3.4ms) → **하루 280만 번 돌지만 단 한 줄도 안 찍힌다.**

즉 제일 아픈 쿼리가 로그에 아예 등장하지 않는다. p99 지연도 마찬가지다. 3.4ms 쿼리의 p99는 여전히 몇 ms라 알람이 울리지 않는다.

그래서 봐야 할 지표가 하나 더 필요하다.

| 지표 | 찾아 주는 것 |
|---|---|
| 느린 쿼리 로그 / p99 지연 | 사용자가 "기다린다"고 느끼는 것 |
| 쿼리별 **총 시간** (지연 × 호출 수) | 인프라를 "먹는" 것 |

둘 다 봐야 하고, 고치는 순서는 대개 **후자가 먼저**다. 이 총 시간 계산에 필요한 건 지연 히스토그램이 아니라 **호출 수 카운터**다. 계측할 때 쿼리 이름별 호출 수를 안 남기고 있으면 이 표 자체를 만들 수 없다.

## 5. 이건 암달의 법칙이다

같은 장의 `ex5_where_time_goes.py` 가 같은 산수를 요청 내부 구간에 적용한다. 한 요청 1,919ms 중 모델 호출이 1,820ms(94.8%)라, 나머지 여섯 구간을 **전부 최대로** 줄여도 60ms, 즉 3%밖에 안 준다.

암달의 법칙(1967)이 말하는 게 정확히 이거다. 전체 개선율은 **개선한 부분이 차지하던 비중**에 갇힌다.

```
전체 개선 상한 = 그 부분의 비중 × 그 부분의 개선율
```

- 커뮤니티 탐지 비중 0.2% × 개선율 50% → 전체의 **0.1%** 개선. 상한이 이미 0.2%다.
- 권한 계산 비중 32% × 개선율 50% → 전체의 **16%** 개선.

"절반으로 줄였습니다"는 두 경우 모두 같은 문장이지만, 하나는 16%이고 하나는 0.1%다.

## 6. 실무에서 쓰는 순서

1. **호출 수를 먼저 계측한다.** 쿼리별 (1회 지연 × 호출 수) 표를 만들 수 없으면 우선순위를 못 정한다.
2. **총 시간으로 줄 세운다.** 비중까지 같이 본다.
3. **상위 2~3개만 손댄다.** 나머지는 다 고쳐도 한 자릿수 %다.
4. **개선율이 아니라 절감량으로 보고한다.** "50% 개선"이 아니라 "하루 1.3시간 / 코어 몇 개분"이 의사결정에 쓰이는 숫자다.
5. **예외: 사용자 체감.** 총 시간이 작아도 사용자가 매번 31초를 기다리는 화면이라면 UX 관점에서 고칠 이유가 있다. 다만 그건 **비용/인프라 작업이 아니라 UX 작업**이고, 예산을 따로 잡아야 한다. 33장이 "쿼리 튜닝 → 지연, 토큰 줄이기 → 비용"으로 목적을 갈라 놓은 것과 같은 구분이다.

## 7. 한 문장으로

같은 50% 개선이라도 절대 절감량은 **총 시간에 비례**한다. 총 시간 = 1회 지연 × 호출 수이므로, 하루 280만 번 도는 3.4ms 쿼리(2.64h)를 반으로 줄이면 1.3시간이 떨어지고, 하루 2번 도는 31초 쿼리(0.017h)를 반으로 줄이면 9초 남짓(약 0.009시간)이 떨어진다 — 150배 넘는 차이다.
