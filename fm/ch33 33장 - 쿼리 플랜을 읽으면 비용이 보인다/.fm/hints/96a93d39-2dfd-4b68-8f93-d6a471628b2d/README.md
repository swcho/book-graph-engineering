# 쿼리 플랜을 한 번 보고 끝내면 안 되는 이유

> **Q.** 쿼리 플랜을 한 번 보고 끝내면 안 되는 이유는 무엇인가?
>
> **A.** 팀이 80개에서 80만 개가 되면 엔진의 선택이 바뀐다. 데이터가 자라면 플랜도 다시 봐야 한다.

---

## 1. 한 문장으로

**플랜은 쿼리의 성질이 아니라 「쿼리 × 데이터」의 함수다.**

쿼리 텍스트를 한 글자도 안 고쳐도, 데이터가 자라면 엔진이 고르는 실행 경로가 바뀐다.
그러니까 "플랜 봤어요"는 시점이 붙어야 의미가 있는 말이다.
"작년 3월 데이터 기준으로 플랜 봤어요"가 정확한 문장이고, 그 말은 **지금은 모른다**는 뜻이다.

---

## 2. 왜 바뀌나 — 비용 기반 플래너의 구조

요즘 엔진(Neo4j, Kùzu, PostgreSQL 등)은 대부분 **비용 기반 옵티마이저(CBO)** 다. 동작은 이렇다.

```
쿼리 텍스트
   │
   ├─ 파싱 → 논리 플랜 후보 여러 개 생성
   │
   ├─ 각 후보의 비용 추정  ←── 통계(statistics)를 읽는다
   │      · 라벨별 노드 수
   │      · 관계 타입별 엣지 수
   │      · 속성값의 선택도(selectivity), 히스토그램
   │      · 인덱스 존재 여부와 카디널리티
   │
   └─ 제일 싼 후보를 물리 플랜으로 확정 → 실행
```

여기서 **통계는 입력값**이다. 입력값이 바뀌면 출력(플랜)이 바뀌는 게 당연하다.
버그가 아니라 설계된 동작이다.

Neo4j 문서도 같은 말을 한다 — "Cypher 쿼리 플래너는 효율적인 플랜을 만들기 위해 정확한 통계에 의존하며, 이 통계는 데이터베이스가 변화함에 따라 최신으로 유지된다."
즉 **엔진은 스스로 마음을 바꾸도록 만들어져 있다.**

### 대표적인 전환점

| 데이터 변화 | 플래너가 바꾸는 선택 |
|---|---|
| 팀 80개 → 80만 개 | "팀 전체를 훑고 조인" → "팀 인덱스로 시작점 찾기"로 뒤집힘 (또는 그 반대) |
| 특정 속성값이 희소 → 흔해짐 | 인덱스 스캔 → 전체 스캔 (인덱스가 오히려 손해가 되는 지점) |
| 조인 양쪽의 크기 비가 역전 | 어느 쪽을 빌드 사이드로 쓸지 뒤집힘 |
| 데이터 편중(skew) 심화 | 평균 카디널리티 추정이 빗나가면서 해시 조인 → 중첩 루프 오판 |
| 인덱스 추가/삭제, 스키마 변경 | 가능한 후보 집합 자체가 바뀜 |
| DB 버전 업그레이드 | 플래너 알고리즘·비용 상수가 바뀜 |
| 통계 갱신 지연/누락 | 실제와 추정이 벌어지며 엉뚱한 플랜 고정 |

**중요한 건 마지막 두 줄이다.** 데이터가 안 자라도 플랜은 바뀔 수 있다.
DB를 업그레이드하거나, 인덱스를 하나 지우거나, 통계 수집이 밀리기만 해도 바뀐다.

## 3. 33장 예제(ex1)에서 실제로 벌어진 일

`ex1_read_plan.py`는 **답이 완전히 같은** 세 쿼리를 나란히 놓는다.
데이터는 사람 8,000명, 팀 80개, 소속 엣지 8,000개다.

```python
QUERIES = {
    "A. 두 끝을 따로 찾음": (
        "MATCH (p:Person), (t:Team) "
        "WHERE t.name = '팀7' AND p.city = '마포' "
        "AND EXISTS { MATCH (p)-[:Member]->(t) } RETURN count(p)"),
    "B. 팀에서 시작": (
        "MATCH (t:Team {name:'팀7'})<-[:Member]-(p:Person) "
        "WHERE p.city = '마포' RETURN count(p)"),
    "C. 사람에서 시작": (
        "MATCH (p:Person {city:'마포'})-[:Member]->(t:Team) "
        "WHERE t.name = '팀7' RETURN count(p)"),
}
```

결과는 셋 다 100. 시간은 **A가 B·C의 3.4배.** B와 C는 거의 같다.

- **B ≈ C인 이유**: 엔진이 "어느 쪽에서 시작할지"를 알아서 정했다.
  「작은 쪽에서 시작하라」는 옛 격언은 요즘 플래너에서는 대개 의미가 없다.
- **A만 느린 이유**: 플랜에 `CROSS_PRODUCT`가 있다.
  8,000명 × 80팀 = **64만 개 조합**을 만들어 놓고 거기서 거른다.

그리고 여기가 이 카드의 핵심이다.

```
지금은 3.4배지만 사람이 80만 명이면 배수가 훨씬 커진다.
...
그리고 이건 «한 번 보고 끝»이 아니다.
팀이 80개가 아니라 80만 개가 되면 엔진의 선택이 바뀐다.
데이터가 자라면 플랜도 다시 봐야 한다.
```

곱집합의 비용은 **곱으로** 큰다. 8,000 × 80 = 64만이지만, 80만 × 80만 = 6,400억이다.
같은 쿼리, 같은 플랜인데 배수는 3.4배에서 수천 배가 된다.
**작을 때 넘어간 플랜은 클 때 죽는다.** 그리고 죽는 순간은 배포 시점이 아니라 어느 화요일 오후다.

### 반대 방향도 있다

"작을 땐 괜찮았는데 커져서 망가진다"만 있는 게 아니다.
**작을 땐 안 보이던 게 커지면서 좋아지는 경우도 있다.** `ex2_index_effect.py`가 그걸 보여준다.

```
제가 기대한 건 «기본 키는 평평하고 속성은 비례해서 는다»였다. 아니었다.
배수가 1.1 언저리에서 거의 안 변한다. 둘 다 비슷하게 늘어난다.

이 규모에서는 «쿼리를 파싱하고 계획을 세우는» 값이 지배하기 때문이다.
```

수천 건 규모에서는 파싱·플래닝 고정비가 지배해서 인덱스 효과가 **측정되지 않는다**.
여기서 "인덱스 별 효과 없네"라고 결론 내면 틀린다.
이건 같은 동전의 다른 면이다 — **측정 시점의 데이터 규모가 결론을 바꾼다.**

## 4. 플랜 회귀(plan regression)란

같은 쿼리가 **어느 날 갑자기** 다른(더 나쁜) 플랜으로 실행되는 것.

증상이 특히 고약한 이유:

1. **배포와 무관하게 터진다.** 코드 커밋이 없으니 롤백할 대상이 없다.
2. **점진적이지 않다.** 비용 추정이 임계값을 넘는 순간 플랜이 **계단식으로** 갈아탄다.
   어제 4ms, 오늘 4,000ms.
3. **재현이 안 된다.** 스테이징의 1만 건짜리 데이터로는 프로덕션 플랜이 안 나온다.
4. **느린 쿼리 로그에 안 잡힐 수도 있다.** 33장 `ex4`가 지적한 그 함정 —
   임계값 100ms로 잡으면 1.2ms → 8ms로 6배 나빠진 쿼리는 **한 줄도 안 찍힌다.**
   그런데 그게 하루 610만 번 도는 쿼리라면 인프라는 확실히 아프다.

> 그래서 봐야 할 지표는 «p99 지연»만이 아니라 «쿼리별 총 시간»이다.
> — `ex4_hot_query.py`

## 5. 실무 — 언제, 어떻게 감시할 것인가

### 5.1 감시 대상을 먼저 좁힌다 (33장 ex4의 총 시간 순위)

전 쿼리를 감시하면 아무도 안 본다. **총 시간 = 1회 지연 × 호출 수**로 줄 세워
상위 몇 개만 회귀 테스트에 올린다.

```python
rows = [(name, ms, n, ms * n / 1000 / 3600) for name, ms, n in QUERIES]
by_total = sorted(rows, key=lambda r: -r[3])
```

`ex4`의 예시 워크로드에서 상위 셋(권한 계산·팀 구성원·이름 찾기)이 전체의 **87%** 를 먹는다.
셋 다 1~3ms짜리 "빠른" 쿼리다. **플랜 감시 대상은 느린 쿼리가 아니라 이 셋이다.**

### 5.2 CI에서 EXPLAIN 스냅샷 회귀 테스트

플랜을 **골든 파일로 커밋**해 두고, PR마다 다시 뽑아 diff한다.

```python
# tests/test_plan_snapshot.py  (개념 예시)
import re, pathlib, pytest

GOLDEN = pathlib.Path(__file__).parent / "plans"

def plan_ops(conn, q):
    """EXPLAIN 출력에서 «연산자 순서»만 뽑는다. 숫자·주소·폭은 버린다."""
    r = conn.execute("EXPLAIN " + q)
    text = "".join(str(r.get_next()[0]) for _ in iter(r.has_next, False))
    ops = re.findall(r"([A-Z_]{4,})\[\d+\]", text)
    return list(reversed(ops))          # 아래→위가 실행 순서

@pytest.mark.parametrize("name,q", HOT_QUERIES.items())
def test_plan_unchanged(conn, name, q):
    got = plan_ops(conn, q)
    golden = (GOLDEN / f"{name}.txt").read_text().split()
    assert got == golden, (
        f"플랜이 바뀌었다.\n  이전: {golden}\n  지금: {got}\n"
        f"의도한 변경이면 골든 파일을 갱신하고 PR 설명에 근거를 적을 것."
    )
```

**핵심은 "정규화(normalize)"다.** 실행 시간, 행 수 추정치, 메모리, 스레드 수처럼
환경마다 흔들리는 값을 그대로 스냅샷하면 테스트가 매번 깨져서 아무도 안 본다.
`EXPLAIN` 출력은 DB 버전이 올라가면 포맷 자체가 바뀌기도 하니, **연산자의 종류와 순서**만
남기고 나머지는 마스킹한다.

| 스냅샷할 것 | 버릴 것 |
|---|---|
| 연산자 이름과 트리 구조 | 실행 시간(ms), 실제 행 수 |
| 인덱스를 탔는지 (`INDEX_SCAN` vs `SCAN_NODE_TABLE`) | 추정 행 수의 정확한 숫자 |
| `FILTER`의 위치(스캔 앞/뒤) | 메모리 사용량, 버퍼 히트 |
| 조인 방식(Hash / NestedLoop / CrossProduct) | 워커/스레드 수, 임시 파일 경로 |

PostgreSQL 진영에는 이걸 도구화한 것도 있다.
[RegreSQL](https://github.com/boringsql/regresql)은 쿼리 결과 스냅샷 + EXPLAIN 플랜 베이스라인을
픽스처로 커밋하고 CI에서 diff한다.

### 5.3 금지 연산자 게이트 — `CROSS_PRODUCT` 검출

스냅샷 diff는 "바뀌었다"만 알려준다. 그와 별개로 **절대 나오면 안 되는 연산자**를 하드 실패시킨다.
33장이 말한 "플랜에서 제일 먼저 찾을 단어"를 그대로 규칙으로 만든 것이다.

```python
FORBIDDEN = {
    "CROSS_PRODUCT",      # Kùzu
    "CARTESIANPRODUCT",   # Neo4j (CartesianProduct)
    "NESTED LOOP",        # Postgres — 조인 조건 없는 경우
}

def test_no_cartesian_product(conn, name, q):
    ops = plan_ops(conn, q)
    bad = [o for o in ops if o.upper() in FORBIDDEN]
    assert not bad, (
        f"[{name}] 플랜에 곱집합이 있다: {bad}\n"
        f"두 끝을 따로 찾아서 붙이고 있다는 뜻이다. "
        f"데이터가 자라면 곱으로 커진다. 패턴 하나로 이어 쓸 것."
    )
```

33장의 세 가지 체크를 그대로 테스트로 옮기면 이렇게 된다.

1. **`CROSS_PRODUCT`가 있나** → 있으면 실패 (위 게이트)
2. **`SCAN`이 무엇을 훑나** → 인덱스 스캔이어야 할 자리에 전체 스캔이 오면 실패
3. **`FILTER`가 `SCAN` 앞인가 뒤인가** → 뒤면 "훑고 나서 버리는 것", 경고

```python
def test_filter_pushed_down(conn, name, q):
    ops = plan_ops(conn, q)
    if "FILTER" in ops and "SCAN_NODE_TABLE" in ops:
        assert ops.index("FILTER") < ops.index("SCAN_NODE_TABLE"), \
            f"[{name}] FILTER 가 SCAN 뒤다 — 다 훑고 버리는 중."
```

### 5.4 CI의 근본 문제 — "작은 DB에서 뽑은 플랜은 프로덕션 플랜이 아니다"

이 카드가 지적하는 바로 그 함정이 CI에 그대로 있다.
**팀 80개짜리 테스트 DB에서 EXPLAIN을 돌려 봐야 팀 80만 개일 때의 플랜은 안 나온다.**

해결책 세 가지, 비용 오름차순:

1. **통계만 이식한다 (제일 실용적).**
   PostgreSQL 17+의 `pg_restore_relation_stats` / `pg_restore_attribute_stats`를 쓰면
   **실제 데이터를 한 줄도 복사하지 않고** 프로덕션 통계만 테스트 DB에 심을 수 있다.
   그러면 작은 DB인데도 플래너는 프로덕션 규모로 판단한다. 개인정보 문제도 피한다.
   (Oracle의 `DBMS_STATS.EXPORT_SCHEMA_STATS`, SQL Server의 `STATS_STREAM`도 같은 개념.)

2. **프로덕션 스케일 시드로 나이틀리(nightly)를 돌린다.**
   PR마다는 비싸니 야간 배치로. 33장 `ex1`이 `COPY`로 일괄 적재하는 이유가 이것 —
   한 건씩 넣으면 시드 만드는 데만 수십 배 걸린다.

3. **미래 규모 시나리오 테스트.**
   현재 규모만이 아니라 **10배·100배 시드**로도 플랜을 뽑아 본다.
   "지금은 인덱스 스캔인데 10배에서 전체 스캔으로 갈아탄다"를 미리 알면
   그게 곧 **용량 계획(capacity planning)** 이 된다. 이게 이 카드의 정답을 실무로 옮긴 형태다.

### 5.5 프로덕션에서의 상시 감시

CI는 "코드가 바뀔 때"만 돈다. 그런데 플랜은 **코드가 안 바뀌어도** 바뀐다.
그래서 런타임 감시가 따로 필요하다.

- **플랜 해시(plan fingerprint)를 메트릭으로 뽑는다.**
  쿼리 ID별로 현재 플랜의 해시를 주기적으로 기록하고, **해시가 바뀌는 순간 알림**을 쏜다.
  플랜이 바뀌었다는 사실 자체가 이벤트다.
- **추정 vs 실측 카디널리티 비율을 본다.**
  `PROFILE`(Neo4j) / `EXPLAIN ANALYZE`(Postgres)에서 estimated rows와 actual rows가
  10배 이상 벌어지면 통계가 썩었다는 신호다. 플랜 회귀의 **선행 지표**다.
- **쿼리별 총 시간 대시보드.**
  p99만 보지 말고 `sum(latency)` 를 쿼리 ID로 그룹핑해서 본다.
  1.2ms → 8ms 회귀는 p99 알람에 안 걸리지만 총 시간 그래프에서는 계단으로 보인다.
- **정기 리뷰 트리거를 이벤트에 건다.** 달력이 아니라 사건에 건다.
  - 노드/엣지 수가 직전 기준선 대비 2배(또는 10배)를 넘었을 때
  - 스키마 마이그레이션·인덱스 변경을 배포했을 때 (32장)
  - DB 메이저 버전을 올렸을 때
  - 새 테넌트/대형 고객이 들어와 데이터 분포가 바뀌었을 때
- **플랜 고정은 최후 수단.** Postgres `pg_hint_plan`, Oracle SQL Plan Baseline,
  Neo4j 인덱스 힌트 같은 것들. 회귀를 즉시 멈추는 데는 쓸모 있지만,
  **데이터가 더 자라면 그 고정이 다시 문제가 된다.** 응급처치로만 쓰고 기한을 붙여 둔다.

## 6. 이 카드가 33장 전체에서 놓인 자리

33장은 "재고 나서 고치기"가 주제다. 이 카드는 그 문장에 **시제**를 붙인다.

| 33장의 교훈 | 시간을 넣으면 |
|---|---|
| 플랜에서 볼 것은 셋 (`CROSS_PRODUCT` / `SCAN` / `FILTER` 위치) | 셋 다 **데이터가 자라면 답이 바뀐다** |
| 「작은 쪽에서 시작하라」는 대개 상관없다 | 플래너가 정하니까 — 그런데 플래너의 판단 근거가 통계다 |
| 인덱스 효과는 규모를 키워야 보인다 | 측정 규모가 결론을 바꾼다 = 측정 시점도 결론을 바꾼다 |
| 제일 느린 것 ≠ 제일 아픈 것 | 회귀 감시 대상은 **총 시간 상위** 쿼리다 |
| 청구서의 큰 칸은 대개 토큰이다 | 플랜 회귀는 **지연** 문제지 청구서 문제가 아니다 — 목적을 헷갈리지 말 것 |

마지막 줄이 균형추다. 플랜을 다시 보는 건 **사용자 지연**을 지키기 위한 것이다.
청구서가 아프면 봐야 할 곳은 플랜이 아니라 모델 호출 횟수와 토큰이다 (`ex3`, `ex5`).
`ex5`의 계산대로, 모델 호출이 전체의 94.8%인 시스템에서는
**나머지 여섯 구간을 전부 최대로 줄여도 3%밖에 안 준다.** 60년 된 암달의 법칙 그대로다.

## 7. 실전 체크리스트

- [ ] 총 시간 상위 5~10개 쿼리를 골라 **핫 쿼리 목록**으로 코드에 박아 둔다.
- [ ] 각 쿼리의 **정규화된 EXPLAIN 플랜을 골든 파일로 커밋**한다.
- [ ] CI에서 diff → 플랜이 바뀌면 실패시키고, **의도한 변경이면 근거와 함께 골든을 갱신**한다.
- [ ] `CROSS_PRODUCT` / `CartesianProduct` 는 **무조건 실패**로 게이트한다.
- [ ] `FILTER`가 `SCAN` 뒤에 오면 경고한다.
- [ ] 테스트 DB에 **프로덕션 통계를 이식**하거나, 나이틀리로 프로덕션 스케일 시드를 돌린다.
- [ ] **10배·100배 시드**로도 한 번 뽑아 본다 → 플랜이 갈아타는 지점을 미리 안다.
- [ ] 프로덕션에서 **플랜 해시 변경**과 **추정/실측 카디널리티 괴리**를 알림으로 건다.
- [ ] 데이터 2배 증가 / 스키마 변경 / DB 업그레이드 때 **플랜 리뷰를 강제**한다.

---

## 8. 한 줄 정리

플랜은 **읽는 것**이 아니라 **감시하는 것**이다.
한 번 읽어서 얻은 건 스냅샷이고, 데이터는 계속 움직인다.
"팀 80개일 때 옳았던 플랜"은 "팀 80만 개일 때 옳은 플랜"과 다르며,
그 사이 어딘가에 아무도 배포하지 않은 장애가 하나 놓여 있다.
