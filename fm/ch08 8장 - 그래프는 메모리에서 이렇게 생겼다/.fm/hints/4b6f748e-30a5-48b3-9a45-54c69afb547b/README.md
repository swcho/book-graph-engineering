# 지역성의 임계값은 왜 16인가

> **질문** 캐시 한 줄과 정수 크기로 볼 때 지역성의 임계값은 얼마인가?
>
> **답** 캐시 한 줄 64바이트에 4바이트 정수 16개가 들어오므로, 이웃 번호 차이가 평균 16 미만이면 같은 줄에 들어올 확률이 생긴다.

## 1. 숫자 하나로 끝나는 계산

```
캐시 한 줄 64바이트 ÷ 정수 하나 4바이트 = 16개
```

이게 전부입니다. 임계값 16은 알고리즘에서 나온 값이 아니고, 하드웨어 상수 두 개를 나눈 값입니다. 그래서 **하드웨어가 바뀌면 임계값도 바뀝니다.** 이 문서의 뒷부분 절반이 그 이야기입니다.

8장 `code/ex4_relabel.py`가 바로 이 판정을 코드로 박아 뒀습니다.

```python
# 4바이트 정수, 캐시 한 줄 64바이트 = 16개가 한 번에 온다
f"이웃 번호가 평균 {after:,.0f} 만큼 떨어져 있으면 "
f"{'같은 줄에 들어올 확률이 있다' if after < 16 else '거의 매번 새 줄을 가져온다'}"
```

그리고 지역성의 정의 자체도 같은 파일에 있습니다. 엣지 양 끝 번호 차이의 평균입니다.

```python
def locality(edges):
    """엣지 양 끝 번호 차이의 평균. 작을수록 좋다."""
    return sum(abs(a - b) for a, b in edges) / len(edges)
```

## 2. 캐시 줄이 「전송의 최소 단위」라는 것

CPU는 바이트 하나를 달라고 해도 바이트 하나를 가져오지 않습니다. 캐시 줄(cache line) 단위로 가져옵니다. 64바이트가 표준이라면, `nbr[1000]` 하나를 읽는 순간 `nbr[992]`부터 `nbr[1007]`까지 16개가 캐시에 함께 올라옵니다.

여기서 두 가지가 따라 나옵니다.

1. **공짜 이웃 15개.** 다음에 읽을 값이 그 줄 안에 있으면 메모리를 다시 안 갑니다.
2. **낭비되는 60바이트.** 그 줄에서 4바이트만 쓰고 버리면, 대역폭의 15/16을 버린 셈입니다.

CSR이 빠른 이유가 여기 있습니다. `offset[u]`부터 `offset[u+1]`까지를 순서대로 읽는 루프는 1번을 최대로 씁니다.

```python
for i in range(offset[u], offset[u + 1]):     # 연속 구간 그대로 읽기
    v = nbr[i]
```

`nbr` 배열을 훑는 이 접근은 어느 그래프에서든 연속입니다. 문제는 그렇게 읽어 낸 **값** `v`로 다시 무언가를 조회할 때입니다. `seen[v]`, `dist[v]`, `offset[v]` 같은 접근은 `v`가 튀는 만큼 메모리를 튑니다. 그래서 「이웃 번호 차이」가 성능 지표가 됩니다. 이 차이가 곧 다음 임의 접근의 점프 거리입니다.

## 3. 임계값이 「확률」인 이유 — 16은 절벽이 아니다

카드의 답이 「같은 줄에 들어온다」가 아니라 **「들어올 확률이 생긴다」**라고 말한 게 정확한 표현입니다. 차이가 16 미만이어도 항상 같은 줄은 아닙니다.

캐시 줄은 64바이트 경계에 정렬돼 있습니다. `nbr` 배열이 정렬된 주소에서 시작하면 인덱스 $i$는 $\lfloor i/16 \rfloor$번째 줄에 들어갑니다. 그러니까 인덱스 15와 16은 차이가 1인데도 **다른 줄**입니다. 경계를 넘었기 때문입니다.

- 차이 $d = 1$: 16개 위치 중 15곳에서 같은 줄 → 확률 15/16
- 차이 $d = 8$: 확률 8/16
- 차이 $d = 15$: 확률 1/16
- 차이 $d \geq 16$: 확률 0 — **여기가 진짜 절벽입니다**

일반식은 $\max(0,\ (16-d)/16)$입니다. 유도는 `hi.md`에 확률 문제로 정리해 뒀습니다.

즉 16은 「그 아래는 좋고 위는 나쁘다」의 경계가 아니라, **이득이 0이 되는 지점**입니다. 이득은 $d$가 1에서 16으로 가는 동안 선형으로 깎여 나갑니다.

### 평균으로 판정하는 것의 함정

`ex4_relabel.py`는 평균 차이 하나로 판정하지만, 평균은 정보를 잃습니다. 확률 함수 $p(d) = \max(0, 1 - d/16)$는 아래로 볼록(convex)하기 때문에, 옌센 부등식으로

$$\mathbb{E}[p(d)] \geq p(\mathbb{E}[d])$$

가 성립합니다. **평균으로 계산한 히트율은 실제 히트율의 하한**이라는 뜻입니다. 실무적으로 중요한 결론입니다.

- 평균 차이가 10,000인 무작위 그래프에도 차이가 3인 엣지는 있습니다. 그 엣지들은 여전히 캐시 히트를 냅니다.
- 그래서 평균이 16을 훌쩍 넘어도 히트율이 0은 아닙니다. 「거의 매번 새 줄」이 「항상 새 줄」은 아닙니다.
- 거꾸로, 재배치 효과를 제대로 재려면 평균 대신 **차이의 분포**(예: $d < 16$인 엣지의 비율)를 보는 게 맞습니다. 커뮤니티 구조가 있는 그래프는 이 비율이 확 뜁니다.

## 4. 이 절벽이 얼마나 비싼가 — 지연 계층

임계값을 넘느냐 마느냐가 왜 중요한지는, 캐시를 놓쳤을 때의 벌금을 봐야 압니다. 대략적인 자릿수입니다(기계마다 다르니 **배수**만 보세요).

| 계층 | 대략 지연 | L1 대비 | 크기 규모 |
|---|---|---|---|
| L1 데이터 캐시 | 4~5 사이클, 약 1ns | 1배 | 32~128KB |
| L2 | 12~20 사이클, 약 4ns | 4배 | 0.5~4MB |
| L3 (있으면) | 40~50 사이클, 약 15ns | 15배 | 8~64MB |
| DRAM | 200~300 사이클, 약 80~100ns | **80배** | GB |
| NVMe SSD | 약 100μs | 100,000배 | TB |

핵심은 마지막 두 줄 사이의 간격이 아니라 **L1과 DRAM 사이의 80배**입니다. 이웃 번호 차이를 16 아래로 끌어내리는 재배치가 노리는 게 이 80배입니다. 알고리즘을 한 글자도 바꾸지 않고 상수 배수를 먹는 최적화라서, 8장이 「대용량 그래프 처리 도구들이 적재할 때 재배치를 먼저 한다」고 말하는 겁니다.

한 단계 더 있습니다. **TLB와 페이지 지역성**입니다. 4KB 페이지에는 4바이트 정수 1,024개가 들어갑니다. 번호 차이가 1,024를 넘으면 캐시 줄만 놓치는 게 아니라 페이지 테이블 조회(TLB 미스)까지 유발합니다. 즉 지역성 임계값은 하나가 아니라 계층마다 하나씩 있습니다. 16(캐시 줄), 1,024(페이지), 그리고 L2/L3에 들어가느냐 마느냐의 작업 집합 크기.

## 5. 하드웨어별 캐시 줄 크기 — 16이 항상 16은 아니다

| 아키텍처 | 캐시 줄 | int32 임계값 | int64 임계값 |
|---|---|---|---|
| x86-64 (Intel, AMD) | 64B | 16 | 8 |
| ARM64 일반 (Cortex-A, Graviton) | 64B | 16 | 8 |
| **Apple Silicon (M1~M4)** | **128B** | **32** | **16** |
| IBM POWER, s390x | 128B | 32 | 16 |
| GPU (워프 단위 병합 접근) | 32B 섹터 / 128B 트랜잭션 | 별도 모델 | 별도 모델 |

이 문서를 만든 기계에서 직접 확인한 값입니다.

```
$ sysctl hw.cachelinesize hw.pagesize machdep.cpu.brand_string
hw.cachelinesize: 128
hw.pagesize: 16384
machdep.cpu.brand_string: Apple M1 Pro
```

즉 **Apple Silicon에서 8장 예제를 돌리면 실제 임계값은 32이고, 페이지도 4KB가 아니라 16KB입니다.** `ex4_relabel.py`의 `after < 16` 판정은 이 기계에서 보수적으로(엄격하게) 동작합니다. 평균 차이가 20이면 코드는 「거의 매번 새 줄」이라고 출력하지만, 실제로는 확률 $(32-20)/32 = 37.5\%$로 같은 줄에 들어옵니다.

한 가지 주의. Apple Silicon의 128B는 「x86보다 두 배 좋다」는 뜻이 아닙니다. 줄이 크면 순차 접근에는 유리하지만, 임의 접근에서는 버리는 바이트가 두 배로 늘고 거짓 공유(false sharing)의 사정거리도 두 배가 됩니다. 트레이드오프입니다.

확인 명령입니다.

```bash
# macOS
sysctl hw.cachelinesize hw.pagesize hw.l1dcachesize hw.l2cachesize

# Linux
getconf LEVEL1_DCACHE_LINESIZE
lscpu | grep -i cache
cat /sys/devices/system/cpu/cpu0/cache/index0/coherency_line_size
```

**하드코딩하지 마세요.** C에서는 `std::hardware_destructive_interference_size`(C++17)나 런타임 조회를, Python에서는 위 명령의 출력을 읽는 편이 안전합니다.

## 6. int32냐 int64냐 — 임계값을 반토막 내는 선택

분자(캐시 줄)만 임계값을 바꾸는 게 아닙니다. 분모도 바꿉니다.

```
64B ÷ 4B (int32) = 16
64B ÷ 8B (int64) =  8   ← 임계값이 절반
```

노드 ID를 64비트로 잡으면 **지역성 요구가 두 배로 엄격해집니다.** 같은 그래프, 같은 재배치, 같은 CPU인데 히트율만 떨어집니다. 대역폭 소모도 두 배입니다.

8장 예제가 `array("i", ...)`를 쓴 게 이 선택입니다.

```python
offset = array("i", [0] * (n + 1))   # "i" = signed int, 4바이트
nbr = array("i", [0] * offset[n])
```

`"i"`는 4바이트, `"q"`는 8바이트입니다. 파이썬 `list`를 썼다면 원소마다 포인터 8바이트 + `int` 객체 28바이트 이상이라 계산이 아예 성립하지 않습니다. 「CSR은 정수 배열 두 개다」라는 말의 무게가 여기에 있습니다.

int32를 쓸 수 있는 조건과 대응책입니다.

- **한계.** 부호 있는 32비트는 약 21억(2³¹−1). 노드 21억 개, 엣지 21억 개까지입니다. 대부분의 실무 그래프는 여기 안에 들어옵니다.
- `nbr` 배열이 int32여도 `offset` 배열은 엣지 수를 담아야 하므로, 엣지가 21억을 넘으면 `offset`만 int64가 필요할 수 있습니다. **둘을 따로 고를 수 있습니다.**
- 그것도 모자라면 차이 부호화(delta encoding) + 가변 길이 정수를 씁니다. 정렬된 이웃 목록의 차이는 대개 작아서 1~2바이트로 줄고, 임계값이 32~64로 **올라갑니다**. 대신 압축을 푸는 CPU 비용을 냅니다. WebGraph 같은 도구가 이 길입니다.

## 7. 프리페처가 이 논의를 무의미하게 만드는 구간

지금까지의 계산에는 빠진 게 있습니다. CPU는 다음에 읽을 주소를 **예측해서 미리 가져옵니다**(하드웨어 프리페처).

- **다음 줄 프리페처(next-line).** 어떤 줄을 읽으면 다음 줄도 가져옵니다.
- **스트라이드 프리페처.** 일정 간격 접근 패턴을 감지해 앞질러 갑니다.
- 보통 페이지 경계 안에서만 동작하고, 여러 스트림을 동시에 추적합니다.

결과가 뭐냐면, **완전 순차 접근에서는 캐시 미스 벌금이 거의 사라집니다.** 미스는 여전히 세지만, 데이터가 필요해지기 전에 도착하므로 지연이 계산과 겹쳐 감춰집니다.

그래서 CSR을 볼 때 두 접근을 구분해야 합니다.

| 접근 | 패턴 | 프리페처 | 임계값 16이 의미 있나 |
|---|---|---|---|
| `nbr[i]`를 `offset[u]`~`offset[u+1]` 훑기 | 완전 순차 | **잘 먹는다** | 별로. 이미 감춰짐 |
| `seen[v]`, `dist[v]` (v는 읽어 온 이웃 번호) | 데이터 의존 임의 접근 | **못 먹는다** | **여기가 본질** |
| dict of list의 포인터 추적 | 포인터 체이싱 | 못 먹는다 | 최악 |

**프리페처가 못 감추는 건 「주소가 데이터에 의존하는」 접근입니다.** 다음 주소를 알려면 지금 값을 먼저 읽어야 하니 미리 가져올 수가 없습니다. 그래프 순회의 비용이 바로 이것이고, 이걸 「포인터 체이싱」이라고 부릅니다. 재배치가 노리는 것도 정확히 이 접근입니다.

이게 8장 `ex2_csr_walk.py`가 파이썬에서 CSR과 dict의 시간 차이를 별로 못 본 이유와도 이어집니다.

```
파이썬에서는 차이가 크지 않다. 인터프리터 오버헤드가 지배하기 때문이다.
같은 코드를 C 나 Rust 로 옮기면 CSR 쪽이 보통 3~10배 빨라진다.
```

파이썬에서는 한 번의 `nbr[i]` 접근에 바이트코드 디스패치와 객체 박싱 비용이 수십~수백 나노초 붙습니다. 80나노초짜리 DRAM 미스가 그 안에 묻힙니다. **임계값 16의 효과를 관측하려면 메모리 지연이 지배하는 언어여야 합니다.** 파이썬에서 CSR을 쓰는 이유는 속도가 아니라 메모리(8배)입니다.

## 8. 흔한 오해 정리

- **「16 미만이면 캐시 히트」** → 아닙니다. 확률이 $(16-d)/16$입니다. 정렬 경계 때문에 $d=1$도 15/16입니다.
- **「16은 어디서나 16」** → 아닙니다. Apple Silicon은 32, int64를 쓰면 8입니다.
- **「평균이 16을 넘으면 지역성 이득이 0」** → 아닙니다. 옌센 부등식으로 평균 기준 추정치는 하한입니다.
- **「CSR이라 연속이니 다 해결」** → `nbr` 훑기만 연속입니다. 읽어 낸 이웃 번호로 하는 조회는 여전히 임의 접근입니다.
- **「무작위 그래프도 재배치하면 좋아진다」** → 원래 구조가 없으면 끌어낼 지역성도 없습니다. 커뮤니티가 뚜렷한 실제 그래프(소셜, 웹, 도로망)에서 효과가 납니다.
- **「슈퍼 노드도 재배치로 해결」** → 다른 문제입니다. 차수 제곱합 문제는 8.3절, 지역성은 8.2절입니다. 섞지 마세요.

## 9. 한 줄로 다시

임계값 16은 $\dfrac{\text{캐시 줄 크기}}{\text{노드 ID 크기}}$이고, 이웃 번호 차이 $d$에 대한 캐시 히트 확률은 $\max\!\left(0, 1 - \dfrac{d}{16}\right)$입니다. 미스 한 번의 벌금이 L1 대비 80배라서, 이 확률을 올리는 재배치가 알고리즘을 안 건드리고도 상수 배수를 먹습니다.
