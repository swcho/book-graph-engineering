# `clustered()`는 왜 번호를 일부러 뒤섞는가

> **질문** `clustered()` 함수가 번호를 일부러 뒤섞는 이유는 무엇인가?
>
> **답** 적재 순서가 구조와 무관한 현실을 흉내 내기 위해서다. 그래야 재배치의 효과를 정직하게 측정할 수 있다.

## 1. 코드가 직접 말하고 있다

`code/ex4_relabel.py`의 독스트링에 이유가 한 줄로 박혀 있습니다.

```python
def clustered(n=N, groups=60, avg_deg=12, seed=7):
    """커뮤니티가 뚜렷한 그래프. 실제 소셜·웹·도로망이 이쪽에 가깝다.
    단, 번호는 일부러 뒤섞어 둔다. 적재 순서가 구조와 무관한 현실을 흉내 낸다."""
    import random
    rnd = random.Random(seed)
    perm = list(range(n)); rnd.shuffle(perm)   # <-- 이 한 줄이 핵심
    size = n // groups
    edges = set()
    for g in range(groups):
        members = [perm[i] for i in range(g * size, min((g + 1) * size, n))]
        for a in members:
            for _ in range(avg_deg // 2):
                b = rnd.choice(members)
                if a != b:
                    edges.add((min(a, b), max(a, b)))
```

읽는 순서가 중요합니다.

1. `perm`을 뒤섞는다.
2. 뒤섞인 `perm`을 **연속 구간으로 잘라** 커뮤니티를 만든다 (`perm[g*size : (g+1)*size]`).
3. 커뮤니티 **안에서만** 엣지를 뿌린다.

즉 **구조(커뮤니티)는 그대로 있고, 그 구조에 붙은 번호만 무작위**입니다. 30,000개 노드가 500명씩 60개 커뮤니티로 나뉘어 있는데, 한 커뮤니티의 구성원 번호는 `[17, 28931, 4102, 9, 20044, ...]` 처럼 전 구간에 흩어져 있습니다.

이게 정확히 이 예제가 재려는 대상입니다. `locality()`는 «구조»를 재는 게 아니라 «구조와 번호가 얼마나 맞아떨어지는가»를 잽니다.

```python
def locality(edges):
    """엣지 양 끝 번호 차이의 평균. 작을수록 좋다."""
    return sum(abs(a - b) for a, b in edges) / len(edges)
```

## 2. 뒤섞지 않으면 무슨 일이 벌어지나 — 실측

`rnd.shuffle(perm)` 한 줄만 빼고(즉 `perm = list(range(n))`) 나머지는 원본과 동일하게 두고 돌려 봤습니다. 시드도 `seed=7` 그대로입니다.

| 그래프 | 엣지 | 재배치 전 | 재배치 후 | «개선» |
|---|---|---|---|---|
| 무작위 그래프 (`make`) | 179,964 | 10,008.7 | 8,823.5 | 1.1배 |
| **커뮤니티 + 번호 뒤섞음 (원본 `clustered()`)** | 178,216 | **10,003.4** | **2,892.6** | **3.5배** |
| 커뮤니티 + 뒤섞지 않음 | 178,283 | **201.0** | 2,892.8 | **0.1배** |

세 번째 줄을 보세요. 뒤섞지 않으면 **재배치 전 지역성이 이미 201**입니다. 재배치 효과가 「0에 가깝게」 나오는 게 아니라, **아예 손해로 나옵니다**. 이 표를 그대로 보고서에 넣으면 결론은 이렇게 됩니다.

> 「BFS 재배치를 적용하니 지역성이 201에서 2,892로 **14배 나빠졌다**. 그래프 재배치는 쓸모없는 최적화다.」

완전한 거짓말입니다. 그런데 숫자는 하나도 조작하지 않았습니다. 뒤섞기 한 줄을 뺐을 뿐입니다.

### 201이라는 숫자의 정체

우연이 아니고 계산됩니다. 커뮤니티 하나의 크기는 `n // groups = 30000 // 60 = 500`. 뒤섞지 않으면 커뮤니티 0은 번호 0~499, 커뮤니티 1은 500~999... 로 **번호가 이미 커뮤니티별로 뭉쳐 있습니다**. 그리고 엣지는 커뮤니티 안에서만 생기니까, 엣지 양 끝은 같은 500칸 구간 안의 두 점입니다.

- 폭 500 구간에서 무작위 두 점의 거리 기댓값 = `500/3 ≈ 166.7`
- 여기에 커뮤니티 사이 다리 `n // 50 = 600`개가 섞입니다. 이건 전 구간 무작위라 거리 기댓값이 `n/3 ≈ 10,000`
- `(166.7 × 177,683 + 10,000 × 600) / 178,283 ≈ 166 + 34 = 200`

즉 뒤섞지 않은 `clustered()`의 번호는 **이미 사람이 손으로 최적화해 놓은 배치**입니다. BFS 재배치가 개선할 여지가 남아 있지 않은 게 당연합니다. 재배치 알고리즘한테 「이미 정답인 답안지」를 주고 「더 잘해 봐」라고 시킨 셈이죠.

### 뒤섞으면 10,003 — 무작위 그래프와 똑같아진다

두 번째 줄의 「전 10,003.4」와 첫 번째 줄의 「전 10,008.7」을 비교해 보세요. 거의 같습니다. 둘 다 `n/3 = 10,000`입니다.

이게 뒤섞기의 의도입니다. **커뮤니티가 뚜렷한 그래프인데도, 번호만 보면 무작위 그래프와 구별이 안 되는 상태**. 번호가 구조에 대해 정보를 **0비트** 갖고 있는 상태. 이게 「적재 순서가 구조와 무관한 현실」의 정확한 정의입니다.

그러고 나서야 두 그래프의 재배치 결과가 갈립니다. 무작위 그래프는 1.1배(사실상 효과 없음), 커뮤니티 그래프는 3.5배. 예제 4가 마지막에 하려는 말이 바로 이 대비입니다.

```
무작위 그래프에서는 재배치 효과가 크지 않다. 원래 구조가 없으니까.
커뮤니티가 뚜렷한 실제 그래프(소셜, 웹, 도로망)에서는 훨씬 크게 준다.
```

뒤섞지 않으면 이 문장을 뒷받침할 수 없습니다. 출발점이 이미 달라서 대비 자체가 성립하지 않으니까요.

## 3. 왜 이게 «벤치마크의 거짓말»인가

표에서 눈여겨볼 게 하나 더 있습니다. **「재배치 후」 값이 2,892.6과 2,892.8로 사실상 같습니다.**

이건 우연이 아닙니다. `bfs_order()`는 그래프의 **연결 구조만** 보고 번호를 다시 매깁니다.

```python
def bfs_order(edges, n):
    """BFS 로 만난 순서대로 번호를 다시 매긴다. 제일 싼 재배치 방법."""
```

들어온 번호가 뭐였든 결과는 구조가 결정합니다. 그래서 이런 관계가 성립합니다.

- **「후」 값 = 그래프 구조의 성질** (실험자가 못 바꾼다)
- **「전」 값 = 번호 붙이기의 성질** (실험자가 마음대로 정한다)
- **「개선 배수」 = 전 / 후** → 분모가 고정이니, **실험자가 분자를 골라서 원하는 배수를 만들 수 있다**

바로 이 지점에서 벤치마크가 거짓말이 됩니다. 재배치의 효과를 잰다고 하면서, 실제로는 **자기가 정한 초기 번호가 얼마나 나빴는지**를 재고 있는 겁니다.

- 초기 번호를 구조 순서로 만들면 → 개선 0배 근처, 심하면 손해 (「재배치는 무의미」)
- 초기 번호를 완전 무작위로 만들면 → 정직한 배수 (3.5배)
- 초기 번호를 구조에 **역행**하도록 일부러 배치하면 → 부풀린 배수 (「재배치는 마법」)

세 결과 모두 같은 그래프, 같은 알고리즘에서 나옵니다. `rnd.shuffle(perm)`은 이 자유도를 없애서, 측정값이 «재배치 알고리즘의 능력»만 반영하도록 고정하는 장치입니다.

한 줄로: **뒤섞기는 노이즈를 넣는 게 아니라, 기준선을 복원하는 것입니다.**

## 4. 현실에서 노드 번호는 실제로 어떻게 정해지나

「적재 순서가 구조와 무관하다」는 게 편의상의 가정이 아니라 기본값이라는 걸 확인해 봅시다. 내부 정수 ID는 대개 이 셋 중 하나로 정해집니다.

### (1) 가입 순 / 생성 순 — auto-increment

Postgres `SERIAL`/`BIGSERIAL`, MySQL `AUTO_INCREMENT`, Neo4j 내부 노드 ID처럼 **레코드가 만들어진 순서대로** 번호가 붙습니다. 사용자 42번은 42번째로 가입한 사람이고, 그 사람의 친구들은 3년 뒤에 가입해서 890만 번대 번호를 받습니다.

가입 시각과 그래프 커뮤니티의 관계는? 거의 없습니다. 서울 강남에 사는 30대 개발자 모임이 «가입 순으로 연속된 번호»를 받을 이유가 없죠. 번호 차이는 그냥 «가입 시점 차이»입니다.

(다만 완전히 0은 아닙니다. 초대 링크 타고 들어온 친구들은 몇 초 차이로 가입해서 연속 번호를 받습니다. 실제 소셜 그래프의 지역성은 표의 10,000과 201 사이 어딘가에 있고, 대개 10,000 쪽에 훨씬 가깝습니다.)

### (2) UUID / 해시 — 설계상 구조와 무관

UUIDv4는 정의상 난수이고, `hash(uuid) % shard_count` 같은 식으로 파티션을 정합니다. 문자열 키를 정수로 바꾸려고 `sorted(set(all_keys))`를 쓰면 결과는 **UUID 문자열의 사전순**, 즉 사실상 난수 순서입니다.

해시는 **일부러** 구조를 지웁니다. 핫스팟을 없애서 샤드에 고르게 뿌리는 게 목적이니까요. 지역성 관점에서는 최악의 번호 붙이기이고, 이건 버그가 아니라 의도된 트레이드오프입니다. (UUIDv7처럼 시간 순서를 넣은 변종도 결국 (1)번, 즉 생성 시각 순서로 돌아갑니다.)

### (3) 적재 순 — 파일의 줄 번호, 카프카 오프셋

가장 흔한 경우입니다. CSV/Parquet을 읽어서 «처음 본 순서대로» 0, 1, 2... 를 붙입니다.

```python
node_id = {}
for line in open("edges.csv"):
    a, b = line.split(",")
    for k in (a, b):
        if k not in node_id:
            node_id[k] = len(node_id)   # 처음 본 순서 = 노드 번호
```

이러면 노드 번호는 **파일에 줄이 정렬된 순서**에 종속됩니다. 그리고 그 순서는 대개 «시간순 이벤트 로그», «카프카 파티션에서 소비한 순서», «`GROUP BY` 없이 뽑은 쿼리 결과 순서» 입니다. 그래프 구조와는 무관합니다.

### 예외가 있고, 그게 함정이다

한 가지 중요한 예외: **웹 크롤 데이터셋**. 크롤러는 BFS로 링크를 따라가면서 페이지를 만나므로, 크롤 순서대로 붙인 ID는 **이미 BFS 재배치가 적용된 상태**입니다. 같은 사이트 페이지들이 연속 번호를 받습니다.

즉 공개 그래프 데이터셋을 그대로 받아서 재배치 실험을 하면, 어떤 데이터셋은 위 표의 「뒤섞지 않음」 줄처럼 행동하고 어떤 데이터셋은 「뒤섞음」 줄처럼 행동합니다. **알고리즘 성능이 아니라 데이터셋의 출처가 결과를 정하는** 겁니다. 이건 8장이 걸어 둔 출처인 [Gorder (arXiv:1602.08820)](https://arxiv.org/abs/1602.08820) 계열 연구가 실제로 겪은 문제이고, Balaji & Lucia의 [When is Graph Reordering an Optimization? (IISWC 2018)](https://brandonlucia.com/pubs/iiswc18-lws.pdf)는 경량 재배치의 성능 이득이 **입력 그래프의 구조적 성질에 강하게 종속된다**는 것을 정면으로 다뤘습니다. 이 장의 키워드 표에서 «그래프 재배치»가 [표준]이나 [사실상 표준]이 아니라 **[실험]** 라벨을 달고 있는 이유도 여기 있습니다.

## 5. 정리

- `rnd.shuffle(perm)`는 **구조는 남기고 번호만 무작위로** 만든다. 커뮤니티는 그대로 60개, 500명씩 있다.
- 뒤섞지 않으면 커뮤니티가 번호 구간(0~499, 500~999, ...)과 일치해서 **초기 지역성이 201**, 즉 이미 최적 배치다. 재배치가 개선할 게 없다.
- `bfs_order()`의 결과(「후」 값 ≈ 2,892)는 초기 번호와 무관하게 구조가 결정한다. 그래서 **「개선 배수」는 실험자가 초기 번호를 어떻게 정하느냐로 조작 가능하다**. 뒤섞기는 그 조작 여지를 없앤다.
- 뒤섞은 뒤의 초기 지역성 10,003은 무작위 그래프의 10,008과 같다. 번호가 구조 정보를 0비트 가진 상태 = 현실의 기본값.
- 현실의 노드 번호는 가입 순(auto-increment), UUID/해시, 적재 순(파일 줄·카프카 오프셋)으로 정해지고, 셋 다 그래프 구조와 무관하다.
- 예외는 BFS 크롤 순서로 정렬된 웹 데이터셋. 이런 데이터를 기준선으로 쓰면 재배치 효과가 사라지고, 잘못된 결론(「재배치는 무의미」)이 나온다.

### 한 문장

같은 알고리즘으로 **1.1배도, 3.5배도, 0.1배도** 만들 수 있다면 그 벤치마크는 알고리즘을 재는 게 아니다. `rnd.shuffle(perm)`은 그중 «현실에 해당하는 하나»를 골라 고정하는 장치다.
