# `deep_size()` 함수는 무엇을 하며 왜 `seen` 집합을 쓰는가?

> **정답**: 중첩 컨테이너의 크기를 재귀적으로 더한다. `id()`를 `seen`에 기록해 같은 객체를 두 번 세지 않는다.

## 한 줄 핵심

`sys.getsizeof()`는 **그 객체 하나**의 크기만 준다. 안에 들어 있는 것들은 「포인터 8바이트」로만 계산되고 실제 내용은 빠진다. `deep_size()`는 그 빠진 부분을 재귀로 따라가서 더하는 함수다. 그런데 그래프처럼 객체가 **공유되고 순환하는** 구조를 재귀로 따라가면 같은 것을 여러 번 세거나 아예 돌아오지 못한다. `seen`이 그 두 사고를 동시에 막는다.

## 실제 구현

8장 예제 1(`code/ex1_three_forms.py`)의 원본이다.

```python
def deep_size(obj, seen=None):
    """중첩 컨테이너까지 대략 더한다."""
    seen = seen if seen is not None else set()
    if id(obj) in seen:
        return 0
    seen.add(id(obj))
    size = sys.getsizeof(obj)
    if isinstance(obj, dict):
        size += sum(deep_size(k, seen) + deep_size(v, seen) for k, v in obj.items())
    elif isinstance(obj, (list, tuple, set)):
        size += sum(deep_size(x, seen) for x in obj)
    return size
```

한 줄씩 하는 일이다.

| 줄 | 하는 일 |
|---|---|
| `seen = seen if seen is not None else set()` | 최초 호출에서만 새 집합을 만든다. 재귀 호출은 **같은 집합을 넘겨받아** 공유한다 |
| `if id(obj) in seen: return 0` | 이미 센 객체는 0을 반환하고 **더 내려가지 않는다**. 재귀 종료 조건 |
| `seen.add(id(obj))` | 내려가기 **전에** 표시한다. 자기 자신을 포함하는 구조에서도 안전하다 |
| `size = sys.getsizeof(obj)` | 이 객체 자체의 얕은 크기 |
| `isinstance(obj, dict)` 분기 | 키와 값을 **둘 다** 따라간다. `dict`는 키도 객체다 |
| `list, tuple, set` 분기 | 원소를 따라간다 |
| 그 밖 (`int`, `str`, `bytearray`, `array`…) | 재귀 없이 얕은 크기만. 이들은 내부에 파이썬 객체 참조가 없거나 버퍼가 자기 크기에 이미 포함된다 |

`seen`이 기본 인자로 `set()`이 아니라 `None`인 것도 의도적이다. 파이썬의 기본 인자는 **함수 정의 시 한 번만** 평가되므로 `def deep_size(obj, seen=set())`로 쓰면 호출 사이에 집합이 살아남아 두 번째 측정이 전부 0으로 나온다.

## 왜 `sys.getsizeof()`만으로는 안 되는가

`getsizeof`는 「이 객체가 자기 몫으로 잡은 바이트」만 돌려준다. 참조를 따라가지 않는다(공식 문서도 *"only the memory consumption directly attributed to the object, not the memory consumption of objects it refers to"*라고 못 박는다).

Python 3.9(64비트)에서 직접 재 본 값이다.

| 표현식 | `getsizeof` | 왜 그 값인가 |
|---|---|---|
| `[]` | 56 | 빈 리스트 헤더 |
| `[0] * 1000` | 8,056 | $56 + 8 \times 1000$. **포인터만** 세고 안의 정수는 안 센다 |
| `{}` | 64 | 빈 dict |
| `sys.getsizeof(5)` | 28 | 작은 정수 하나가 28바이트다 |
| `array("i", [0]*1000)` | 4,064 | 버퍼가 **포함**된다. 재귀 불필요 |
| `bytearray(1000)` | 1,057 | 역시 포함 |

여기서 8장의 핵심 대비가 나온다.

- **인접 행렬**은 `bytearray` 하나 → `sys.getsizeof(m)` 한 번으로 끝.
- **CSR**은 `array("i", ...)` 두 개 → `sys.getsizeof(off) + sys.getsizeof(nbr)`로 끝.
- **인접 리스트**만 `dict` → `list` → `int`로 세 겹 중첩이라 **`deep_size(adj)`가 필요하다**.

그래서 예제 1의 비교 표가 이렇게 생겼다.

```python
rows = [
    ("인접 행렬 (비트)", sys.getsizeof(m)),
    ("인접 리스트 (dict of list)", deep_size(adj)),
    ("CSR (배열 2개)", sys.getsizeof(off) + sys.getsizeof(nbr)),
]
```

`adj`에 `getsizeof`만 쓰면 어떻게 되는지 재 봤다. 노드 1,000개·각 이웃 2개인 `dict of list`에서

| 방식 | 바이트 |
|---|---|
| `sys.getsizeof(adj)` (얕게) | 36,960 |
| `deep_size(adj)` | 178,564 |

**4.8배** 차이다. 얕게 재면 「dict of list가 무겁다」는 이 장의 결론 자체가 안 나온다. 무거운 원인이 바로 그 「안 세어진 부분」, 즉 원소마다 붙는 파이썬 객체이기 때문이다.

## `seen`이 막는 것 1 — 같은 객체 이중 계산

그래프에서 객체 공유는 예외가 아니라 기본이다. 무방향 엣지 `(a, b)`는 `adj[a]`와 `adj[b]` 양쪽에 등장하고, 노드 번호 정수는 수십 번 재사용된다.

`seen`을 뺀 판(`no_seen`)과 비교해 봤다.

```python
inner = [0] * 100
outer = [inner, inner, inner]   # 리스트 하나를 세 번 참조
```

| 측정 | 바이트 | 평가 |
|---|---|---|
| 실제 할당량 (`getsizeof(outer) + getsizeof(inner)`) | 936 | 기준 |
| `deep_size(outer)` | 960 | 정확 (936 + 공유 정수 `0` 24바이트) |
| `seen` 없는 재귀 | 9,848 | **10배 과대 계상** |

`inner`는 메모리에 **하나만** 있다. `outer`가 세 번 가리키는 건 8바이트 포인터 세 개일 뿐이고, 그 포인터는 이미 `getsizeof(outer)`에 들어 있다. `seen` 없이 세면 존재하지 않는 리스트 두 개를 발명하는 셈이다.

앞의 1,000노드 그래프에서도 `seen` 없는 판은 192,948바이트가 나왔다(정답 178,564 대비 약 8% 과대). 그래프가 조밀해지고 공유가 늘수록 이 오차는 커진다.

## `seen`이 막는 것 2 — 순환 참조와 무한 재귀

그래프 자료구조는 순환이 정상이다. 노드 객체가 서로를 참조하는 구조, `adj` 안에 `adj`가 들어가는 구조, 자기 자신을 담은 리스트 모두 실제로 나온다.

```python
c = []
c.append(c)      # 자기 자신을 담았다
```

| 측정 | 결과 |
|---|---|
| `deep_size(c)` | 88 (정상 종료) |
| `seen` 없는 재귀 | `RecursionError` |

`seen.add(id(obj))`를 **재귀 호출 전에** 하기 때문에 `c` 안의 `c`를 만나는 순간 `id(c) in seen`이 참이 되어 0을 반환하고 멈춘다. 순서가 뒤바뀌어 `size` 계산 후에 `add`했다면 여전히 터진다. 이 함수의 `seen`은 곧 8장 예제 2의 BFS에 나오는 `seen = bytearray(n)`과 **같은 역할**이다. 그래프를 걷는 코드는 방문 표시 없이는 돌아온다.

## `seen`이 막지 못하는 것과 `id()`의 함정

### 왜 객체 자체가 아니라 `id()`인가

`seen`은 `set`이고 `set`은 원소가 해시 가능해야 한다. 그런데 `list`, `dict`, `set`은 **unhashable**이라 `seen.add(obj)`가 바로 `TypeError`다. 게다가 우리가 알고 싶은 건 「값이 같은가(`==`)」가 아니라 **「메모리에 있는 그 객체인가(`is`)」**다. `[1,2,3]`이 두 개 따로 있으면 값은 같아도 메모리는 두 배로 쓴다. `id()`는 정확히 그 「동일성」을 정수 키로 바꿔 준다.

### `id()` 재사용

CPython의 `id()`는 대개 메모리 주소다. 객체가 해제되면 **그 주소가 재사용될 수 있다.**

```python
a = [1, 2, 3]; ia = id(a)
del a
b = [4, 5, 6]
ia == id(b)      # True 가 나온다
```

`seen`은 id 정수만 들고 있어서 객체를 살려 두지 못한다. 순회 중에 임시 객체가 생기고 사라지면 엉뚱한 객체를 「이미 셌다」고 판정해 **과소 계상**될 수 있다. `deep_size`가 도는 동안 대상 객체들은 컨테이너가 참조하고 있어 살아 있으므로 실전에서는 거의 문제가 안 되지만, 이래서 제대로 만든 구현(`pympler.asizeof` 등)은 방문한 객체 자체를 리스트에 붙잡아 둔다.

### 재귀 한도

`seen`은 **순환**을 막지만 **깊이**는 못 줄인다. 서로 다른 객체가 3,000단계 중첩된 리스트를 넣으면 `RecursionError`가 난다(기본 `sys.getrecursionlimit()`은 1,000). 다행히 그래프 인접 리스트는 `dict` → `list` → `int`로 깊이가 3에서 끝난다.

### `__dict__`를 안 본다

사용자 정의 객체는 분기에 없어서 얕은 크기만 잡힌다.

```python
class N:
    def __init__(self): self.x = [1, 2, 3]
```

`getsizeof(n)`은 48인데 `n.__dict__`만 104바이트다. 7장식으로 노드를 클래스로 감싼 그래프를 이 함수로 재면 **한참 과소 계상**된다. 도크스트링이 「대략 더한다」라고, 파일 도크스트링이 「정확한 값은 아니고 «자릿수»를 보는 용도」라고 미리 밝히는 이유다.

## small int 캐시 — 같은 그래프가 노드 번호에 따라 다르게 재진다

CPython은 `-5`부터 `256`까지의 정수를 인터프리터 시작 시 미리 만들어 **모두가 공유**한다. 그래서 `id(100) == id(100)`이 참이고, 이 정수들은 `seen` 덕분에 그래프 전체에서 **딱 한 번만** 계상된다.

모양이 완전히 똑같은 200노드 그래프를 노드 번호만 바꿔 재 봤다.

| 노드 번호 | `deep_size` | 차이 |
|---|---|---|
| `0..199` (캐시된 작은 정수) | 29,308 | 기준 |
| `1000000..1000199` (매번 새 객체) | 40,512 | **+38%** |

구조는 동일하다. 정수 하나 크기(28바이트)도 동일하다. 차이는 오직 **공유되느냐**다. 작은 번호는 전 그래프에 정수 객체 200개면 되고, 큰 번호는 등장 횟수만큼 별개 객체가 생긴다.

이건 버그가 아니라 **진짜 메모리 차이**다. 다만 두 가지 함의가 있다.

1. 작은 테스트 그래프(노드 몇백 개)로 잰 「인접 리스트 메모리」는 실서비스(노드 번호가 수백만)로 갈 때 **더 나빠진다**. 예제 1이 `N = 20_000`을 쓰는 이유이기도 하다. 캐시 범위 밖 번호가 대부분이라 현실적인 값이 나온다.
2. CSR은 이 문제에서 자유롭다. `array("i")`는 정수를 **4바이트 raw 값**으로 담는다. 파이썬 정수 객체가 아예 안 만들어지므로 노드 번호가 1이든 1,000,000이든 4바이트다. 리스트 슬롯이 포인터 8바이트 + 정수 객체 28바이트를 쓰는 것과 비교하면 원소당 **9배** 차이다. 8장이 「dict of list 는 편한데 무겁다. 파이썬 객체가 원소마다 붙기 때문이다」라고 말하는 것의 정체가 이 숫자다.

## 자주 하는 오해

- **「`seen`은 성능 최적화다」** → 아니다. **정확성**과 **종료**를 위한 것이다. 공유 객체를 중복 계상하면 값이 틀리고, 순환이 있으면 아예 끝나지 않는다. 부수 효과로 빨라지긴 한다.
- **「`seen`에 객체를 넣으면 되지」** → `list`/`dict`/`set`은 unhashable이라 `TypeError`다. 그리고 `==` 기반 비교는 우리가 원하는 「같은 객체」 판정이 아니다.
- **「`deep_size`가 정확한 메모리다」** → 아니다. gc 헤더, 할당자 패딩(pymalloc의 8/16바이트 정렬), 문자열 인터닝, `__slots__`, 확장 타입의 내부 버퍼가 반영되지 않는다. **배수**를 보는 도구다. 예제 실행 가이드가 「측정값은 기계마다 다릅니다. **배수**만 보세요」라고 적은 것과 같은 취지다.
- **「`seen` 하나면 순환이든 깊이든 안전하다」** → 순환만 안전하다. 깊게 중첩된 서로 다른 객체는 여전히 `RecursionError`다.
- **「`bytearray`/`array`도 재귀로 따라가야 한다」** → 필요 없다. `getsizeof`가 버퍼를 이미 포함한다. 반대로 `numpy` 배열은 뷰(view)일 수 있어 `getsizeof`가 버퍼를 빼기도 하므로 `arr.nbytes`를 따로 봐야 한다.

## 실무에서는

한 번 쓰는 측정용이면 이 함수로 충분하다. 진지하게 재려면 이미 만들어진 것을 쓴다.

| 도구 | 성격 |
|---|---|
| `pympler.asizeof` | `deep_size`의 완성형. 객체를 붙잡아 두고, `__dict__`·`__slots__`·확장 타입까지 처리한다 |
| `tracemalloc` | 함수가 아니라 **할당을 추적**한다. 스냅샷 차이로 「이 코드가 몇 바이트 늘렸나」를 본다 |
| `gc.get_referents` | 재귀 대상을 타입 분기 대신 gc에게 묻는 방식. 타입 목록을 손으로 열거하지 않아도 된다 |
| OS 관점 (`RSS`) | 결국 서버가 죽는 기준. 파편화와 free-list 때문에 위 합계와 안 맞는 게 정상이다 |
