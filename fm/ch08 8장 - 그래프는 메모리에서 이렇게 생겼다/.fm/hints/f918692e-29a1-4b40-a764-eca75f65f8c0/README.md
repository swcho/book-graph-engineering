# 방문 표시는 왜 `set`이 아니라 `bytearray`인가 — 번호가 곧 주소다

> **Q.** `bfs_csr()`에서 방문 표시를 `bytearray`로 두는 이유는 무엇인가?
> **A.** 노드 수만큼의 1바이트 플래그 배열이라 set보다 조밀하고 인덱스 접근이 상수 시간이다.

## 한 줄로

**CSR이 노드 번호를 `0..n-1`로 조밀하게 만들어 놨으니, 방문 표시도 조밀한 배열이면 된다. 노드 번호가 그대로 배열 첨자다.**

set은 "임의의 키를 담는" 자료구조라서 해시를 계산하고, 빈 슬롯을 찾고, 키 객체를 붙잡아 둔다. CSR에서는 그 세 가지가 전부 낭비다. 키가 이미 `0`부터 시작하는 연속 정수이므로 **자리를 계산할 필요 없이 자리가 이미 정해져 있다.**

측정하면 노드 5만 개 기준 **48.9KB 대 3.3MB, 약 70배**다.

## 문제의 코드 — 두 BFS의 첫 줄

`ex2_csr_walk.py`는 같은 그래프를 두 방식으로 순회하며, 두 함수는 **방문 표시 자료구조가 다르다.**

```python
def bfs_csr(offset, nbr, start, n):
    seen = bytearray(n)                            # ← 노드 수만큼의 1바이트 플래그
    seen[start] = 1
    q = deque([start])
    visited = 0
    while q:
        u = q.popleft()
        visited += 1
        for i in range(offset[u], offset[u + 1]):     # 연속 구간 그대로 읽기
            v = nbr[i]
            if not seen[v]:                        # ← 첨자 한 번
                seen[v] = 1
                q.append(v)
    return visited
```

```python
def bfs_dict(adj, start):
    seen = {start}                                 # ← set
    q = deque([start])
    visited = 0
    while q:
        u = q.popleft()
        visited += 1
        for v in adj.get(u, ()):                       # 객체를 따라 점프
            if v not in seen:                      # ← 해시 + 탐침
                seen.add(v)
                q.append(v)
    return visited
```

`bfs_csr`의 `seen[v]`와 `bfs_dict`의 `v not in seen`이 이 카드의 전부다. 나머지 골격은 똑같다.

## ① 조밀함 — 5만 노드에서 48.9KB 대 3.3MB

`ex2_csr_walk.py`의 `N = 50_000` 기준으로 실측한 값이다. (Python 3.9.6, arm64)

| 방문 표시 방식 | 바이트 | 노드당 | `bytearray` 대비 |
|---|---:|---:|---:|
| `bytearray(n)` | **50,057** | 1.0 B | **1.0x** |
| `array('b', n)` | 53,192 | 1.06 B | 1.06x |
| `[False] * n` | 400,056 | 8.0 B | 8.0x |
| `set` (해시 테이블만) | 2,097,368 | 41.9 B | 41.9x |
| `set` + 붙잡힌 `int` 객체 | **3,497,364** | 69.9 B | **69.9x** |

`bytearray(50_000)`은 50,000바이트 페이로드 + 57바이트 헤더다. **정보량이 그대로 크기다.** 반면 set은 두 겹으로 부푼다.

### 첫째 겹 — 슬롯 자체가 16바이트

CPython의 `setentry`는 이렇게 생겼다.

| 필드 | 크기 | 설명 |
|---|---:|---|
| `PyObject *key` | 8 B | 키 객체를 가리키는 포인터 |
| `Py_hash_t hash` | 8 B | 캐시된 해시값 |

슬롯 하나가 **16바이트**다. 플래그 하나에 1비트면 충분한 자리에 16바이트를 쓴다. 실측이 정확히 들어맞는다.

```
2,097,368 - 216(헤더) = 2,097,152 = 131,072 슬롯 × 16 B
```

### 둘째 겹 — load factor 0.6과 4배 성장

문제는 슬롯 수가 원소 수보다 **훨씬 많다**는 것이다. CPython `Objects/setobject.c`의 `set_add_entry()`가 이렇게 판단한다.

```c
if ((size_t)so->fill*5 < mask*3)
    return 0;                                  /* 아직 여유 있다 */
...
return set_table_resize(so, so->used>50000 ? so->used*2 : so->used*4);
```

- `fill*5 >= mask*3` → **load factor 상한 0.6**. 60%를 넘기면 재배치한다.
- 재배치 목표가 `used*4` (5만 이하) → 한 번 커지면 **점유율이 0.15로 떨어진다.**

즉 set의 실제 점유율은 **0.15에서 0.6 사이를 오간다.** 5만 원소를 넣은 시점의 실측 load factor는 **0.381**이었다. 슬롯 하나당 16바이트인데 그중 38%만 쓰는 셈이니, 원소당 실효 비용이 `16 / 0.381 ≈ 42바이트`가 된다.

성장 흔적을 그대로 찍어 보면 이렇다.

| 원소 수 | 테이블 바이트 | 슬롯 수 |
|---:|---:|---:|
| 0 | 216 | 8 |
| 5 | 728 | 32 |
| 19 | 2,264 | 128 |
| 77 | 8,408 | 512 |
| 307 | 32,984 | 2,048 |
| 1,229 | 131,288 | 8,192 |
| 4,915 | 524,504 | 32,768 |
| 19,661 | 2,097,368 | 131,072 |

5만 노드에 도달하기까지 **재배치가 8번** 일어난다. 마지막 점프를 보면 `used = 19,661`에서 터졌는데, 이는 `0.6 × 32,767 ≈ 19,660`과 정확히 맞는다. 그리고 재배치는 매번 **살아 있는 전체 원소를 다시 해싱해 옮긴다.**

`bytearray(n)`은 재배치가 없다. 처음부터 최종 크기다.

### 셋째 겹 — set은 `int` 객체를 붙잡아 둔다

이게 자주 놓치는 부분이다. `nbr`은 `array("i")`이므로 `v = nbr[i]`는 매번 **새 `int` 객체를 만든다.** 차이는 그 객체의 수명이다.

- **`bytearray`**: `seen[v] = 1`은 값 1을 바이트 한 칸에 쓴다. `v`는 반복이 끝나면 참조 카운트가 떨어져 사라진다. `seen`에는 **파이썬 객체가 하나도 없다.**
- **`set`**: `seen.add(v)`는 `v`의 참조를 붙잡는다. 그래서 방문한 노드 수만큼의 `int` 객체가 **BFS가 끝날 때까지 살아 있다.** 하나당 `sys.getsizeof` 기준 28바이트(pymalloc의 8바이트 정렬로 실제 점유는 32바이트)다.

```
50,000 × 28 = 1,399,996 B  ← 테이블 2.0MB 위에 얹히는 1.3MB
```

합쳐서 3.3MB, `bytearray`의 **69.9배**다. (`0..256`은 CPython이 캐시하는 작은 정수라 이 부분만 예외다.)

## ② 인덱스 접근이 상수 시간 — "평균 O(1)"과 다르다

둘 다 흔히 O(1)이라 부르지만 내용이 다르다.

| | `bytearray` `seen[v]` | `set` `v in seen` |
|---|---|---|
| 주소 계산 | `base + v` 덧셈 한 번 | `hash(v)` → `& mask` → 탐침 |
| 해시 | 없음 | 필요 (`int`는 싸지만 0은 아니다) |
| 충돌 | **없음.** 자리가 유일하다 | 선형/의사난수 탐침 반복 |
| 키 비교 | 없음 | 슬롯마다 `==` 검사 |
| 최악의 경우 | **O(1) 확정** | O(n) (충돌 몰림) |
| 재배치 | 없음 | 8번, 그때마다 전체 재해싱 |

`bytearray`는 **평균이 아니라 최악까지 상수 시간**이다. 첨자에서 주소로 가는 길이 덧셈 하나뿐이라 분기도 탐색도 없다.

실측 (무작위 첨자 10만 회, 최소값)

| 연산 | ns/op |
|---|---:|
| `bytearray` 읽기 `seen[v]` | **15.3** |
| `list` 읽기 `seen[v]` | 15.4 |
| `set` 조회 `v in seen` | 27.5 |
| `bytearray` 쓰기 `seen[v] = 1` | **20.4** |
| `set` 삽입 `seen.add(v)` | 40.4 |

조회 **1.8배**, 삽입 **2.0배** 차이다. 초기화 비용은 격차가 더 크다.

| 초기화 | 시간 |
|---|---:|
| `bytearray(50_000)` | **0.6 us** |
| `set(range(50_000))` | 642.5 us |

**약 1,000배**다. `bytearray(n)`은 OS에서 0으로 채워진 페이지를 받아 오는 것에 가깝고, set은 5만 번의 해싱과 8번의 재배치를 실제로 수행한다.

## ③ 캐시 지역성 — 이 장의 주제와 같은 이유

8.2절의 논지가 "CSR이 빠른 이유는 알고리즘이 아니라 메모리를 읽는 방식"이다. `seen`도 정확히 같은 이야기다. 캐시 한 줄은 **64바이트**다(`ex4_relabel.py`의 기준과 동일).

| 방식 | 캐시 한 줄에 담기는 플래그 | 5만 노드 전체 크기 |
|---|---:|---|
| `bytearray` | **64개** | 48.9KB |
| `[False]*n` (포인터 8B) | 8개 | 390KB |
| `set` (슬롯 16B, 무작위 탐침) | 4개, 실질 1개 | 2.0MB |

두 가지가 겹쳐서 유리해진다.

1. **작업 집합이 작다.** 48.9KB면 방문 배열 **전체**가 캐시에 얹힌다. 2.0MB짜리 set 테이블은 상당수 x86의 L2를 넘겨 L3까지 내려간다. 배수만 보면 된다 — 작업 집합이 40배 차이라는 사실이 핵심이다.
2. **접근 순서가 CSR과 같은 방향이다.** `nbr[offset[u]:offset[u+1]]`을 순서대로 훑으며 그 값으로 `seen`을 찌른다. 이웃 번호가 가까이 모여 있으면 `seen[v]`도 같은 캐시 줄 안에서 여러 번 맞는다. 이게 `ex4_relabel.py`가 재배치로 "이웃 번호 차이 평균"을 줄여서 얻으려는 이득인데, **`seen`이 조밀한 배열일 때만 그 이득이 전달된다.** set의 해시는 번호의 근접성을 일부러 흩어 버리므로 재배치 효과를 그대로 날려 버린다.

set을 쓰면 CSR로 애써 만든 지역성이 방문 검사 지점에서 새는 것이다.

## ④ 대안: bitarray로 8배 더 줄일 수 있다 — 그런데

플래그가 참/거짓 하나면 1비트로 충분하다. 8개를 한 바이트에 밀어 넣으면 된다.

```python
seen = bytearray((n + 7) // 8)          # 6,250 B — bytearray(n) 의 1/8
seen[start >> 3] |= 1 << (start & 7)    # 세우기
if not (seen[v >> 3] >> (v & 7)) & 1:   # 검사
```

이 기법은 이 장에 이미 나온다. `ex1_three_forms.py`의 인접 행렬이 정확히 같은 트릭을 쓴다.

```python
def build_matrix(edges, n):
    """인접 행렬. n×n 비트. 여기서는 bytearray 한 줄에 n비트씩."""
    row_bytes = (n + 7) // 8
    m = bytearray(row_bytes * n)
    for a, b in edges:
        m[a * row_bytes + (b >> 3)] |= 1 << (b & 7)
```

### 얻는 것

| | 바이트 | 캐시 줄당 플래그 |
|---|---:|---:|
| `bytearray(n)` | 50,000 | 64 |
| 비트 배열 | **6,250** | **512** |

**정확히 8배**다. 5만 노드에서는 48.9KB → 6.1KB. 그리고 캐시 한 줄에 512개가 오므로 지역성은 더 좋아진다. 10억 노드 규모에서 이 8배는 결정적이다 — 1GB와 125MB의 차이다.

### 잃는 것 — 실측하면 파이썬에서는 2.4배 느리다

같은 그래프(노드 50,000, 엣지 299,958)로 `seen`만 바꿔 5회 최소값을 재면 이렇다.

| `seen` 구현 | BFS 시간 | 메모리 |
|---|---:|---:|
| **`bytearray(n)` (원본)** | **41.3 ms** | 48.9KB |
| `set` | 45.8 ms (+11%) | 3.3MB |
| 비트 배열 | 98.4 ms (**2.4배**) | 6.1KB |

단위 연산으로 봐도 같다.

| 연산 | ns/op | `bytearray` 대비 |
|---|---:|---:|
| `bytearray` 읽기 | 15.3 | 1.0x |
| 비트 검사 `(seen[v>>3]>>(v&7))&1` | 95.1 | **6.2x** |
| `bytearray` 쓰기 | 20.4 | 1.0x |
| 비트 세우기 `seen[v>>3] \|= 1<<(v&7)` | 111.2 | **5.5x** |

이유는 이 장이 이미 말한 것과 같다.

> 파이썬에서는 차이가 크지 않다. 인터프리터 오버헤드가 지배하기 때문이다.

비트 조작은 CPU에서는 사실상 무료지만, **파이썬에서는 시프트·마스크·OR가 각각 바이트코드 명령이고 중간 결과마다 `int` 객체가 생긴다.** 플래그 하나 읽는 데 명령 4~5개를 더 쓰니 6배가 된다. 캐시로 번 것을 인터프리터가 다 뱉어 낸다.

### 트레이드오프 정리

| 기준 | `bytearray` | 비트 배열 |
|---|---|---|
| 메모리 | 1 B/노드 | **1 bit/노드 (8배 이득)** |
| 파이썬 속도 | **기준** | 2.4배 느림 |
| C/Rust 속도 | 기준 | 대개 더 빠름 (작업 집합이 작아서) |
| 코드 명료성 | `seen[v]` | `(seen[v>>3]>>(v&7))&1` |
| 병렬 BFS | **바이트 단위 원자적 쓰기 가능** | 한 바이트를 8스레드가 공유 → read-modify-write 경쟁, 원자적 연산이나 락 필요 |
| 카운터로 확장 | 0~255 값 저장 가능 (거리·색깔 등) | 참/거짓만 |

마지막 두 줄이 실무에서 자주 결정적이다. 비트 배열에서 `seen[v>>3] |= ...`는 **읽고-고치고-쓰기**이므로, 이웃한 8개 노드를 다른 스레드가 동시에 표시하면 갱신이 사라진다. 바이트 단위면 그런 경쟁이 없다. 또 `bytearray`는 0/1만 담는 게 아니라 **BFS 깊이(0~255)를 그 자리에 그대로 적을 수도 있다** — 별도 거리 배열이 필요 없어진다.

**정리**: 파이썬 단일 스레드에서는 `bytearray`가 정답이다. 노드가 수억을 넘어 8배가 생존을 가르거나, C/Rust로 옮겨 인터프리터 오버헤드가 사라진 뒤에 비트 배열을 고려한다.

## ⑤ 전제 조건 — `bytearray`는 CSR이라서 쓸 수 있다

여기가 이 카드의 숨은 핵심이다. `bfs_dict`가 `set`을 쓰는 것은 게을러서가 아니다.

```python
def build_adjlist(edges):
    adj = defaultdict(list)   # 키가 무엇이든 된다. 문자열이어도, 띄엄띄엄한 정수여도
```

`dict of list`의 키는 **조밀할 필요가 없다.** 노드 번호가 `[3, 91, 1000000]`이든 `"alice"`든 상관없다. 그래서 방문 표시도 임의의 키를 받는 `set`이어야 한다. `bytearray`를 쓰려면 첨자가 `0..n-1` 범위의 정수여야 하고, 아니면 `IndexError`가 난다.

CSR은 그 조건을 **구조적으로 보장한다.**

```python
offset = array("i", [0] * (n + 1))     # 첨자가 노드 번호 그 자체
nbr = array("i", [0] * offset[n])      # 값도 0..n-1 범위의 노드 번호
```

`offset`의 첨자가 노드 번호이므로, CSR을 만드는 순간 노드는 이미 `0`부터 시작하는 연속 정수로 다시 번호가 매겨진 상태다. `nbr`에 담긴 값도 같은 공간의 번호다. 그러니 `bytearray(n)`의 첨자로 **아무 변환 없이 그대로** 쓸 수 있다.

이게 CSR이 조밀한 진짜 이유와 같다. **번호를 조밀하게 만들면 번호가 곧 주소가 되고, 주소를 찾는 자료구조(해시 테이블, 색인)가 전부 필요 없어진다.** `offset`이 노드→이웃목록 색인을 없앤 것과 `bytearray`가 노드→방문여부 해시를 없앤 것은 같은 아이디어의 두 적용이다.

동시에 이것이 CSR의 대가이기도 하다. 조밀한 번호를 유지해야 하므로 **노드 추가·삭제가 어렵다.** 그리고 8.4절이 지적하듯 "이름으로 시작 노드를 찾는" 일에는 여전히 별도 색인이 필요하다.

## 한 걸음 더

**Q. `array('b', ...)`나 NumPy는 어떤가?**
`array('b')`는 53,192바이트로 `bytearray`와 거의 같지만 리터럴이 번거롭다. NumPy `np.zeros(n, dtype=np.uint8)`도 1B/노드인데, 스칼라 하나 읽을 때마다 `np.uint8` 객체를 만들어 파이썬 루프에서는 오히려 느리다. 이 장의 예제는 "의존성 없음"이 원칙이므로 `bytearray`가 맞다. NumPy는 루프를 벡터화해 파이썬 밖으로 밀어낼 때 값을 한다.

**Q. `set`이 언제 더 나은가?**
방문하는 노드가 전체의 극소수일 때다. 노드 10억 개 그래프에서 1,000개만 방문하고 멈추는 질의라면 `bytearray`는 1GB를 미리 잡지만 `set`은 수십 KB로 끝난다. 손익분기는 대략 **방문 비율 1.5%** 근처다(노드당 1B 대 70B). BFS는 보통 연결 요소 전체를 훑으므로 `bytearray` 쪽이고, 깊이 제한이 걸린 짧은 탐색이면 `set`을 볼 만하다.

**Q. 매 질의마다 `bytearray(n)`을 새로 만드는 비용은?**
0.6us라 무시할 수 있다. 그래도 아까우면 배열 하나를 재사용하고 세대 번호를 쓰는 방법이 있다. 0/1 대신 질의 번호를 적고 `seen[v] == gen`으로 비교하면, 256번 질의마다 한 번만 `bytearray`를 0으로 밀면 된다. 1바이트라 이런 여유가 생기는 것이고, 비트 배열에서는 불가능하다.

## 정리

| 물음 | 답 |
|---|---|
| 왜 `bytearray`인가 | CSR이 노드를 `0..n-1`로 조밀하게 만들어 놨으니 **번호가 곧 첨자**다 |
| 조밀함 | 1 B/노드. `set`은 슬롯 16B ÷ load factor 0.38 + `int` 객체 28B = **70 B/노드** |
| 5만 노드 실측 | **48.9KB 대 3.3MB, 69.9배** |
| 상수 시간 | `base + v` 덧셈 하나. 해시·충돌·재배치가 전부 없어 **최악까지 O(1)** |
| 속도 실측 | 조회 15.3ns 대 27.5ns, 초기화 0.6us 대 642us(**1,000배**) |
| 캐시 | 캐시 줄 64B에 플래그 64개. 배열 전체가 캐시에 얹히고 CSR의 지역성이 그대로 전달됨 |
| 비트 배열 대안 | 메모리 **8배** 이득(6.1KB)이지만 파이썬에서 **2.4배 느림**, 병렬 쓰기 경쟁, 카운터로 못 씀 |
| 전제 | 조밀한 0-based 정수 ID. `bfs_dict`는 이 보장이 없어서 `set`을 써야 한다 |

측정값은 기계마다 다르다. **배수**만 보면 된다.
