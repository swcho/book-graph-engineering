# 인덱스 없는 인접성에 대해 자주 잊는 점은 무엇인가?

> **정답**: 시작 노드를 찾는 일에는 여전히 색인이 필요하다는 것이다. 이름으로 노드를 찾는 것은 색인 없이는 전체 훑기다.

## 한 줄 핵심

「인덱스 없는 인접성(index-free adjacency)」이라는 이름은 **딱 한 가지 연산**에 대한 약속이다. **노드에서 그 이웃으로 가는 연산**. 그래프를 걷는 일은 색인이 필요 없다는 뜻이지, **그래프에 들어가는 일**까지 색인이 필요 없다는 뜻이 아니다. 질의는 항상 두 부분으로 쪼개진다.

$$
C_{\text{total}} \;=\; \underbrace{C_{\text{entry}}}_{\text{진입점: 이름} \to \text{노드}} \;+\; \underbrace{C_{\text{traverse}}}_{\text{홉: 노드} \to \text{이웃}}
$$

두 번째 항만 색인이 없어도 되고, 첫 번째 항은 **여전히 색인 없으면 $O(N)$** 이다. 이걸 잊으면 「그래프 DB인데 왜 느리냐」는 문장이 나온다.

`ex5_index_free.py`가 마지막에 굳이 두 줄을 더 붙인 이유가 이것이다.

```
다만 «시작 노드를 찾는» 일에는 여전히 색인이 필요하다.
이름으로 노드를 찾는 건 색인 없이는 전체 훑기다. 이 점을 자주 잊는다.
```

---

## 1. 예제가 실제로 무엇을 측정했나

`ex5_index_free.py`는 이웃 조회 두 방식을 비교한다.

| 방식 | 구현 | 이론 비용 |
|---|---|---|
| 색인 방식 | 정렬된 `(src, dst)` 배열 + `bisect_left` | $O(\log E)$ |
| 직접 방식 | `adj[u]` — 노드에서 이웃 목록으로 바로 | $O(1)$ |

출력에 찍히는 「이론 색인 깊이」는 $\log_2(\text{rows})$ 다. `make(avg_deg=12)`는 노드 하나당 6번 붙이므로 엣지가 약 $6N$, 양방향으로 펼치면 `rows` $\approx 12N$ 이다.

| 노드 $N$ | `rows` $\approx 12N$ | 이론 색인 깊이 $\log_2$ |
|---:|---:|---:|
| 10,000 | 약 120,000 | 약 **16.9** |
| 100,000 | 약 1,200,000 | 약 **20.2** |

노드가 10배 늘었는데 깊이는 3.3만 늘었다. 로그니까. **직접 방식은 0이 늘었다.** 이게 인덱스 없는 인접성의 이득이고, 여기까지는 정답의 앞부분이 아니라 뒷부분에서 다루는 이야기다.

### 예제가 감춘 것 — `adj[u]` 자체가 해시 색인이다

솔직하게 짚어야 하는 대목이다. `neighbors_direct(adj, u)`의 `adj`는 파이썬 `dict`고, `dict` 조회는 **해시 색인 조회**다. 상수 시간이긴 하지만 「색인이 없다」와는 다르다. 진짜 인덱스 없는 인접성은 이렇다.

- **Neo4j**: 노드 레코드가 고정 길이라 `node_id * record_size` **산수**로 파일 오프셋이 나온다. 그 레코드 안에 첫 관계의 오프셋이 들어 있고, 관계 레코드는 다음 관계의 오프셋을 들고 있다. 탐색 구조를 타는 게 아니라 **주소를 따라간다**.
- **CSR** (8.1~8.2절): `offset[u]`부터 `offset[u+1]`까지가 $u$의 이웃이다. 인덱스 계산 한 번. 8장이 CSR을 먼저 보여 준 뒤 인덱스 없는 인접성을 설명하는 순서가 우연이 아니다. **CSR은 인덱스 없는 인접성의 가장 벗은 형태다.**

그리고 바로 여기서 진입점 문제가 드러난다. CSR로 이웃을 얻으려면 **정수 $u$가 먼저 있어야** 한다. 「김철수」라는 문자열에서 $u$를 얻는 매핑 — 그 `dict`가 바로 **진입점 색인**이다. CSR 배열 두 개는 그 매핑을 대신해 주지 못한다. 7장에서 본 「문자열이 아니라 사물」의 대가를 여기서 치른다.

## 2. Neo4j에서 진입점 색인이 없으면 실행 계획이 이렇게 떨어진다

이 절이 이 카드의 실전 부분이다. Cypher는 `EXPLAIN`(실행하지 않고 계획만)과 `PROFILE`(실행하고 실제 db hits까지)로 계획을 볼 수 있다.

### 문제의 질의

```cypher
PROFILE
MATCH (p:Person {name: '김철수'})-[:KNOWS]-(f)
RETURN f.name
```

### 색인이 없을 때

```
+-----------------------+----------------+------+---------+
| Operator              | Details        | Rows | DB Hits |
+-----------------------+----------------+------+---------+
| +ProduceResults       | f.name         |   28 |      28 |
| +Expand(All)          | (p)-[:KNOWS]-(f)| 28  |      29 |
| +Filter               | p.name = $auto |    1 | 5000000 |   <-- 여기
| +NodeByLabelScan      | p:Person       | 5e6  | 5000000 |   <-- 여기
+-----------------------+----------------+------+---------+
```

읽는 법.

- **`NodeByLabelScan`**: `:Person` 라벨이 붙은 노드를 **전부** 꺼낸다. 노드 500만 개면 행 500만 개.
- **`Filter`**: 그 500만 개마다 `name` 속성을 읽어 비교한다. 속성 읽기가 또 500만 번.
- **`Expand(All)`**: 실제 그래프 걷기. 살아남은 노드 1개에서 이웃 28개. **db hits 29.**

숫자를 보라. 우리가 그래프 DB를 쓰는 이유인 홉은 **29**를 썼고, 「그 노드를 찾는 일」이 **10,000,000**을 썼다. 진입점이 전체의 99.9997%다. 인덱스 없는 인접성이 얼마나 훌륭해도, 이 계획에서는 아무 의미가 없다.

더 나쁜 계층도 있다. 라벨조차 안 쓰면 `AllNodesScan`으로 떨어진다.

```cypher
MATCH (p {name: '김철수'})-[:KNOWS]-(f) RETURN f   -- AllNodesScan. 라벨도 안 걸렀다
```

역설 하나. 「인덱스 없는」 DB인 Neo4j도 **라벨 색인은 유지한다** — `NodeByLabelScan`이 전체 노드를 훑지 않고 라벨 인덱스를 읽는다는 게 그 증거다. 인덱스 없는 인접성의 「없는」은 오직 **관계 순회**에만 걸리는 수식어다.

### 색인을 만든 뒤

```cypher
CREATE INDEX person_name IF NOT EXISTS FOR (p:Person) ON (p.name);
```

또는 유일성이 보장되는 키라면 제약 조건 쪽이 낫다. 제약 조건은 **뒤에 색인을 자동으로 만들어 준다**.

```cypher
CREATE CONSTRAINT person_id IF NOT EXISTS FOR (p:Person) REQUIRE p.id IS UNIQUE;
```

같은 질의의 계획이 이렇게 바뀐다.

```
+-----------------------+---------------------------+------+---------+
| Operator              | Details                   | Rows | DB Hits |
+-----------------------+---------------------------+------+---------+
| +ProduceResults       | f.name                    |   28 |      28 |
| +Expand(All)          | (p)-[:KNOWS]-(f)          |   28 |      29 |
| +NodeIndexSeek        | p:Person(name) WHERE ...  |    1 |       2 |   <-- 2
+-----------------------+---------------------------+------+---------+
```

**`NodeByLabelScan` + `Filter`가 사라지고 `NodeIndexSeek` 하나로 접힌다.** db hits가 10,000,000에서 **2**로 줄었다. Neo4j 문서가 드는 예에서도 같은 규모의 축소(120,000 → 2)가 나온다.

### 진입점 연산자 계층 — 좋은 쪽에서 나쁜 쪽으로

`PROFILE` 첫 줄(맨 아래 리프 연산자)이 무엇인지가 사실상 진입점 비용이다.

| 연산자 | 언제 나오나 | 대략 비용 |
|---|---|---|
| `NodeByElementIdSeek` / `NodeByIdSeek` | `elementId(n) = ...` | 산수 1회, 1 db hit |
| `NodeUniqueIndexSeek` | 유일 제약 조건의 백업 색인 | 1~2 db hits |
| `NodeIndexSeek` | RANGE 색인 + 등가 조건 | 1~2 db hits |
| `NodeIndexSeekByRange` | RANGE 색인 + `<`, `>`, `STARTS WITH` | 매칭 범위만큼 |
| `NodeIndexContainsScan` / `NodeIndexEndsWithScan` | `CONTAINS`, `ENDS WITH` | **색인 항목 전체 훑기** |
| `NodeIndexScan` | 색인은 있으나 조건이 seek 불가 | 색인 항목 전체 훑기 |
| `NodeByLabelScan` | 진입점 색인 없음 | 라벨 노드 전체 |
| `AllNodesScan` | 라벨조차 없음 | **노드 전체** |

여기서 잊기 쉬운 두 번째 함정. **색인을 만들었는데도 seek가 안 나올 수 있다.**

- `WHERE p.name CONTAINS '철수'` — RANGE 색인으로는 seek이 안 된다. `NodeIndexContainsScan`이다. 부분 문자열 검색이 필요하면 TEXT 색인이나 전문 검색(full-text) 색인을 따로 만들어야 한다.
- `WHERE p[$prop] = '김철수'` — 속성 키가 동적이면 계획기가 색인을 고를 수 없다. Neo4j가 「동적 속성 때문에 색인 조회가 불가능하다」는 알림을 준다.
- 계획기가 색인을 안 쓰는지 확신이 안 서면 `SHOW INDEXES`로 존재와 상태(`ONLINE`인지, `POPULATING`인지)를 먼저 확인하고, 그 다음 `EXPLAIN`을 본다. 강제하고 싶으면 `USING INDEX p:Person(name)` 힌트를 붙이는데, **힌트가 안 먹으면 질의가 실패하거나 경고를 내므로** 이건 진단 도구로 쓰는 게 낫다.

## 3. 왜 「자주 잊는가」 — 구조가 잊게 만든다

핵심 구조는 이것이다. **진입점 비용은 홉 수와 무관한 상수고, 순회 비용은 홉 수에 대해 지수로 자란다.** 그래서 홉이 깊어질수록 진입점이 전체에서 차지하는 비중이 **저절로 줄어든다.**

평균 차수를 $\bar d$, 홉 수를 $k$라 하면 순회가 훑는 엣지 수는

$$
C_{\text{traverse}}(k) \;=\; \sum_{i=1}^{k} \bar d^{\,i} \;=\; \frac{\bar d^{\,k+1} - \bar d}{\bar d - 1} \;\approx\; \bar d^{\,k}
$$

진입점이 전체에서 차지하는 비중은

$$
\rho_k \;=\; \frac{C_{\text{entry}}}{C_{\text{entry}} + C_{\text{traverse}}(k)}
\;\approx\; \frac{C_{\text{entry}}}{C_{\text{entry}} + \bar d^{\,k}}
$$

$C_{\text{entry}}$가 $k$에 안 들어 있다는 게 전부다. $k$가 커지면 분모만 커지고 $\rho_k \to 0$이다.

### 숫자로 — 노드 $N = 5\times 10^6$(`:Person`), 평균 차수 $\bar d = 30$

| 홉 $k$ | 순회 비용 $\approx$ | 색인 있음 ($C_e = 2$) 진입점 비중 | 색인 없음 ($C_e = 10^7$) 진입점 비중 |
|---:|---:|---:|---:|
| 1 | 30 | 6.3% | **99.9997%** |
| 2 | 930 | 0.21% | **99.99%** |
| 3 | 27,900 | 0.007% | **99.7%** |
| 4 | 838,000 | 0.0002% | **92.3%** |
| 5 | 25,100,000 | 0.00001% | 28.5% |
| 6 | 754,000,000 | — | 1.3% |

이 표에서 두 가지를 동시에 읽어야 한다.

**(가) 색인이 있으면 진입점은 1홉에서도 이미 사소하다.** 8장 요약의 「인덱스 없는 인접성은 두 번째 홉부터 이득이다」가 여기서 나온다. 1홉이면 관계형 조인 한 번과 크게 다르지 않지만, 2홉부터는 3장의 「중간 결과가 안 곱해진다」가 겹쳐서 격차가 벌어진다.

**(나) 색인이 없으면 진입점이 5홉쯤까지 전체를 지배한다.** 그리고 순회 비용이 진입점을 따라잡는 지점은

$$
\bar d^{\,k^*} \approx N \quad\Longrightarrow\quad k^* \approx \log_{\bar d} N
$$

$\bar d = 30$, $N = 5\times10^6$이면 $k^* \approx \dfrac{\ln(5\times10^6)}{\ln 30} \approx \dfrac{15.42}{3.40} \approx 4.5$ 다.

여기서 잔인한 사실. **실제 그래프의 지름은 대개 6 근처**(작은 세상)이고, 우리가 실무에서 쓰는 질의는 거의 **1~3홉**이다. 즉 $k^*$는 언제나 우리가 쓰는 홉 범위 **바깥**에 있다. **전체 훑기가 순회에 가려질 만큼 홉을 깊게 파는 질의는 현실에 거의 없다.** 결론: 진입점 색인이 없으면 그건 절대 숨지 않는다.

### 그런데도 잊는 이유

1. **홉이 깊어지면 비중이 줄어든다는 구조**가 「진입점은 사소하다」로 잘못 일반화된다. 사소한 건 **색인이 있을 때만**이다.
2. **작은 데이터에서는 색인이 있으나 없으나 같다.** 노드 1만 개에서 label scan은 밀리초다. 색인이 없다는 사실은 데이터가 100배 될 때, 즉 운영에서 처음 드러난다.
3. **이름이 오해를 부른다.** "index-free"라는 마케팅 친화적인 문구가 "no indexes needed"로 읽힌다.
4. **`EXPLAIN`을 안 본다.** 계획을 한 번만 보면 `NodeByLabelScan`이 맨 아랫줄에 뻔히 보인다. 안 보면 안 보인다.

### 8.3절과 겹치는 함정

$\bar d^{\,k}$는 **차수가 고른 경우의 근사**다. 8.3절이 보여 준 대로 실제 비용은 차수의 제곱합 $\sum_v d_v^2$가 정한다. 슈퍼 노드를 지나가면 순회 비용이 폭발하면서 진입점 비중이 **더 빨리** 줄어든다. 하지만 그건 좋은 소식이 아니다. 「진입점 비중이 1%로 떨어졌다」가 「질의가 30초 걸린다」의 다른 표현일 수 있다. 비중은 절대 비용을 대신하지 않는다.

## 4. 자주 하는 오해 정리

| 오해 | 사실 |
|---|---|
| 그래프 DB는 색인이 필요 없다 | 관계 순회만 필요 없다. 진입점 조회는 색인이 필요하다 |
| 인덱스 없는 인접성이니 스키마 설계만 잘하면 된다 | 진입점이 될 속성(`name`, `email`, 외부 ID)마다 색인/제약 조건이 필요하다 |
| 색인을 만들었으니 끝 | 조건 형태에 따라 seek 대신 scan으로 떨어질 수 있다. `EXPLAIN`으로 확인 |
| 진입점 비중이 작으니 무시해도 된다 | 색인이 있을 때만 작다. 없으면 5홉까지 지배한다 |
| 홉을 깊게 하면 진입점 비용이 묻힌다 | 이론상 맞지만 $k^* \approx \log_{\bar d} N \approx 4.5$. 실무 질의(1~3홉)는 거기 못 간다 |

## 5. 실무 체크리스트

1. **진입점 목록을 먼저 쓴다.** 애플리케이션이 그래프에 들어가는 지점은 보통 손에 꼽는다. 사용자 ID, 문서 URL, 사번, 주문 번호.
2. **그 각각에 색인이나 유일 제약 조건을 만든다.** 유일하다면 제약 조건 쪽 — 데이터 정합성과 색인을 한 번에 얻는다.
3. **모든 진입 질의에 `EXPLAIN`을 한 번씩 돌린다.** 리프 연산자가 `NodeByLabelScan`이나 `AllNodesScan`이면 색인이 없거나 안 쓰이고 있다.
4. **`PROFILE`로 db hits 배분을 본다.** 진입점 db hits가 순회 db hits보다 자릿수로 크면 그게 병목이다.
5. **`SHOW INDEXES`로 상태를 확인한다.** 대량 적재 직후 색인이 `POPULATING`이면 아직 계획기가 못 쓴다.
6. **부분 문자열/전문 검색은 별도 색인**으로 처리한다. RANGE 색인에 `CONTAINS`를 던지면 색인 전체 훑기다.
7. **적재 파이프라인에서는 순서를 바꾼다.** 대량 `MERGE` 전에 제약 조건을 먼저 만들어야 한다. 안 그러면 `MERGE`마다 label scan이 돌아 적재가 제곱으로 느려진다. 이게 인덱스 없는 인접성을 잊은 대가가 가장 아프게 나타나는 지점이다.

## 6. 한 문장 정리

**인덱스 없는 인접성은 「걷는 비용」의 약속이지 「들어가는 비용」의 약속이 아니다.** 걷는 비용은 홉 수에 대해 지수로 자라니 상수인 진입점 비용은 홉이 깊어지면 비중이 줄고, 그래서 잊힌다. 하지만 실무 질의의 홉은 얕고, 얕은 홉에서는 색인 없는 진입점이 전체 비용 그 자체다.
