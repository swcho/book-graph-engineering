# 파이썬에서 CSR BFS와 dict BFS의 속도 차이가 크지 않은 이유는 무엇인가?

> **정답**: 인터프리터 오버헤드가 지배하기 때문이다. 같은 코드를 C나 Rust로 옮기면 CSR 쪽이 보통 3~10배 빨라진다.

## 한 줄 핵심

CSR의 장점은 **캐시 미스를 줄이는 것**인데, 파이썬에서는 그 캐시 미스가 전체 비용의 작은 조각일 뿐이다. 이웃 하나를 보는 데 인터프리터가 이미 수십 나노초를 쓰고 있으니, 메모리 쪽에서 아무리 잘해도 **줄일 수 있는 몫 자체가 작다.** 인터프리터를 걷어내면(C, Rust, scipy) 그 조각이 갑자기 전체의 대부분이 되고, 그때 CSR의 배수가 드러난다.

> 아래 측정값은 모두 한 기계(Apple M1 Pro, CPython 3.9.6) 것이다. 8장의 원칙대로 **절대값은 무시하고 배수만 보시라.** 다른 기계에서는 ms 값이 다 달라지지만, 배수의 방향과 자릿수는 재현된다.

## 1. 예제 2가 실제로 보여 주는 것

`ex2_csr_walk.py`는 노드 5만, 엣지 약 30만(이웃 슬롯 60만)짜리 그래프에서 같은 BFS를 두 그릇으로 돌린다. 실제로 네 번 돌려 보면 이렇다.

| 회차 | CSR | dict of list | 배수 |
|---|---|---|---|
| 1 | 44.3 ms | 70.6 ms | 1.6x |
| 2 | 43.1 ms | 48.7 ms | 1.1x |
| 3 | 41.1 ms | 56.4 ms | 1.4x |
| 4 | 44.0 ms | 50.7 ms | 1.2x |

CSR이 이기기는 한다. 그런데 **1.1~1.6배**다. 회차 간 흔들림이 두 그릇의 차이와 비슷한 크기라는 것이 이미 신호다. 예제 자신도 이렇게 결론을 내린다.

```
파이썬에서는 차이가 크지 않다. 인터프리터 오버헤드가 지배하기 때문이다.
같은 코드를 C 나 Rust 로 옮기면 CSR 쪽이 보통 3~10배 빨라진다.
```

CSR의 「연속이라서 캐시가 좋다」는 이야기가 8.2절의 핵심인데, 정작 8장 예제에서 그게 1.2배로 나오는 이유를 이해하는 게 이 카드다.

## 2. 비용 두 개를 나란히 놓아 보기

이웃 하나를 처리할 때 드는 비용은 크게 둘이다.

### (가) 인터프리터가 바이트코드를 돌리는 비용

`bfs_csr`의 안쪽 루프를 `dis`로 까 보면, 이웃 **하나당** 이 바이트코드들이 돈다.

```
 72 FOR_ITER            ← range 이터레이터 전진
 74 STORE_FAST    i
 76 LOAD_FAST     nbr
 78 LOAD_FAST     i
 80 BINARY_SUBSCR       ← nbr[i]  (여기서 새 PyLong 객체가 만들어진다)
 82 STORE_FAST    v
 84 LOAD_FAST     seen
 86 LOAD_FAST     v
 88 BINARY_SUBSCR       ← seen[v]
 90 POP_JUMP_IF_TRUE
   ── 처음 보는 이웃이면 아래 9개가 더 붙는다 ──
 92 LOAD_CONST / 94 LOAD_FAST / 96 LOAD_FAST / 98 STORE_SUBSCR   ← seen[v] = 1
100 LOAD_FAST / 102 LOAD_METHOD / 104 LOAD_FAST / 106 CALL_METHOD / 108 POP_TOP  ← q.append(v)
```

이웃 하나당 **바이트코드 10~19개**. 바이트코드 하나는 계산된 goto 디스패치 7개 명령 + 실제 동작 1~4개 명령, 대략 8~11개 기계 명령어에 분기 예측 실패까지 얹힌다. 게다가 `BINARY_SUBSCR` 두 번은 단순 명령이 아니라 타입 확인·범위 확인·객체 생성을 포함한 C 함수 호출이다.

실측하면 CSR BFS는 이웃 하나당 **약 71 ns**다(42.6 ms ÷ 59.9만). 바이트코드당 6 ns 정도, 3 GHz 기준 20 사이클쯤. 파이썬치고는 오히려 준수한 수치다.

### (나) 메모리에서 데이터를 실어 오는 비용

이쪽의 표준적인 사다리는 이렇다(M1 계열 실측 기준).

| 계층 | 지연 |
|---|---|
| L1 데이터 캐시 | 3~4 사이클 (≈ 1 ns) |
| L2 | 10여 사이클 |
| 시스템 레벨 캐시(L3 역할) | 18 사이클 + 10~15 ns |
| DRAM | 18 사이클 + 약 91 ns → **≈ 100 ns** |

**즉 최악의 캐시 미스 한 번이 100 ns 급이고, 이웃 하나당 인터프리터 비용이 71 ns 급이다.** 같은 자릿수다. 여기서 이미 「CSR로 미스를 다 없애도 2배 이상은 못 번다」는 상한이 보인다.

그리고 캐시 미스는 이웃마다 한 번씩 나지도 않는다. M1의 캐시 줄은 128바이트라 4바이트 정수가 **32개**씩 한 번에 온다(8장 예제 4는 64바이트/16개를 가정하는데, 기계에 따라 이렇게 다르다). CSR에서 한 노드의 이웃은 연속이므로, 평균 차수 12짜리 그래프라면 한 노드의 이웃 전체가 대개 **줄 한두 개**에 담긴다. 100 ns를 12개가 나눠 내니 이웃당 실효 메모리 비용은 10 ns 아래로 떨어진다.

## 3. 바닥값을 재 보면: 87%가 순수 인터프리터

주장을 그냥 믿지 말고 분해해 보자. BFS 로직을 다 떼고 CSR 전체를 「훑기만」 하는 루프, 그리고 아무 일도 안 하는 빈 루프를 같은 횟수로 돌려 봤다.

| 실험 | 시간 | 이웃당 | CSR BFS 대비 |
|---|---|---|---|
| CSR BFS (원본) | 42.6 ms | 71.0 ns | 100% |
| CSR 전체 훑기만 (`total += nbr[i]`) | 37.2 ms | 61.9 ns | **87%** |
| 빈 루프 59.9만 회 (`total += 1`) | 18.1 ms | 30.2 ns | **43%** |

읽어 낼 것이 세 가지다.

1. **빈 루프만으로 이미 43%.** `for` 한 바퀴 도는 것 자체가 BFS 전체 시간의 절반 가까이다. 여기엔 그래프도 메모리 접근도 없다.
2. **`nbr[i]`을 더하는 것까지 하면 87%.** 그릇의 종류와 무관하게 「파이썬으로 60만 개를 훑는다」는 사실만으로 시간의 대부분이 결정된다.
3. **BFS의 본질적인 일(방문 표시, 큐 조작)이 13%뿐.** 그릇 설계가 개입할 여지가 그 안에 있다.

## 4. 암달 관점 — 상한이 정해져 있다

암달의 법칙은 「전체 중 비중 $p$인 부분을 $s$배 빠르게 하면 전체는 얼마나 빨라지나」를 말한다.

$$\text{전체 배속} = \frac{1}{(1 - p) + \dfrac{p}{s}}$$

메모리 접근이 전체의 $p = 0.13$이라고 하자. CSR이 그 부분을 **완벽하게** 없애서 $s \to \infty$가 되어도

$$\frac{1}{1 - 0.13} = 1.15\text{배}$$

**최대 1.15배.** 실측된 1.1~1.6배와 딱 맞는 상한이다. 이게 「차이가 크지 않다」의 정확한 의미다. CSR이 일을 못 해서가 아니라, **잘할 수 있는 구간이 전체의 13%밖에 없어서** 그렇다.

반대로 인터프리터를 없애서 $1 - p$ 쪽이 0에 가까워지면, 같은 $p$가 갑자기 분모의 전부가 된다. 그래서 C/Rust에서는 같은 개선이 배수로 튄다. 뒤에서 이걸 숫자로 확인한다.

## 5. 결정적 실험: 지역성을 일부러 파괴해도 안 변한다

「인터프리터가 지배한다」를 한 방에 확인하는 방법이 있다. **노드 번호를 무작위로 섞어서** CSR을 다시 만드는 것이다. 알고리즘·자료구조·연산 횟수는 완전히 그대로인데, 메모리 접근 패턴만 망가진다. 캐시가 병목이라면 확 느려져야 한다.

| 실험 (노드 5만) | 시간 | 배수 |
|---|---|---|
| CSR BFS (원래 번호) | 42.6 ms | 1.00x |
| CSR BFS (번호 무작위로 섞음) | 42.8 ms | **1.01x** |

**1%.** 지역성을 통째로 부숴도 측정 노이즈 수준이다. 파이썬 레벨에서 캐시 지역성은 이 규모에서 사실상 보이지 않는다.

여기엔 이 규모의 이유도 하나 겹쳐 있다. 노드 5만이면 `nbr` 배열이 2.3 MB, `seen`이 49 KB다. M1 Pro의 L2가 4 MB이므로 **작업 집합이 애초에 캐시 안에 다 들어간다.** 없앨 미스가 별로 없는 상태에서 CSR을 써도 벌 게 없는 것이다. 8장 예제들이 5만·2만 규모인 것은 「의존성 없이 몇 초 안에 돌아야 한다」는 제약 때문인데, 그 크기가 캐시 효과를 감추는 방향으로도 작용한다.

## 6. 반전: 파이썬에서는 dict이 CSR보다 빠를 수도 있다

`bfs_dict`가 느린 이유가 정말 「객체를 따라 점프해서」인지 확인하려면, 두 함수의 **다른 차이**를 지워 봐야 한다. 원본 코드에서 `bfs_csr`은 방문 표시에 `bytearray`를 쓰고 `bfs_dict`는 `set`을 쓴다. `set`은 원소마다 해시를 계산한다. 그릇의 차이가 아니라 방문 표시 방식의 차이다.

그래서 `seen`만 `bytearray`로 바꾼 dict 버전을 만들어 재 봤다.

| 실험 (노드 5만) | 시간 | 이웃당 | CSR 대비 |
|---|---|---|---|
| CSR BFS | 42.6 ms | 71.0 ns | 1.00x |
| dict BFS (`set` seen, 원본) | 49.7 ms | 82.9 ns | 1.17x |
| dict BFS (`bytearray` seen) | **38.0 ms** | 63.3 ns | **0.89x** |

**dict 쪽이 더 빠르다.** 원본에서 관찰된 차이의 상당 부분은 CSR의 연속성이 아니라 `set` 해싱이었다.

왜 CSR이 지는가. 파이썬에서 `array("i")`의 조밀함은 **읽을 때마다 되돌려 갚는다.**

```
array("i") 순회 12.9 ms (21.5 ns/개)
list      순회  6.2 ms (10.4 ns/개)  → array 가 2.07x 느리다
```

`array("i")`에는 4바이트 생짜 정수가 들어 있으므로, `nbr[i]`을 할 때마다 CPython은 **PyLong 객체를 새로 만들어야 한다**(박싱). 작은 정수 캐시는 -5~256뿐이라 노드 번호 50,000은 매번 새 객체다.

```python
array("i", [100])[0] is 100      # True  ← 캐시된 작은 정수
array("i", [50000])[0] is 50000  # False ← 매번 새로 할당된다
```

반면 `dict of list`는 **이미 만들어진 PyLong의 포인터**를 들고 있어서 순회할 때 참조 카운트만 올린다. 8장 예제 1이 잰 「dict of list가 CSR보다 7.8배 무겁다」는 바로 그 객체들의 무게인데, 그 무게를 미리 낸 대가로 읽기가 싸진 것이다. 그리고 **힙 할당 한 번은 캐시 미스 한 번보다 비싸다.** CSR이 절약한 100 ns급 미스를 박싱으로 다시 토해내는 구조다.

CSR의 안쪽 루프가 `range()` + 인덱스 산술을 도는 것도 불리하다. `for v in adj[u]`는 리스트 이터레이터가 포인터를 전진시키는 반면, `for i in range(offset[u], offset[u+1])`는 `range` 객체를 만들고 정수 `i`를 만들고 그걸로 다시 첨자를 탄다.

## 7. 규모를 키우면 CSR이 나오기 시작한다

암달의 $p$는 고정된 상수가 아니다. 작업 집합이 캐시를 넘어서면 메모리 비중이 커진다. 노드를 40만(이웃 슬롯 480만, `nbr` 18.3 MB → L2 4 MB 초과)으로 올려 같은 실험을 반복했다.

| 실험 | 노드 5만 (캐시 안) | 노드 40만 (캐시 초과) |
|---|---|---|
| CSR BFS | 42.6 ms · 71.0 ns/이웃 | 417.1 ms · 86.9 ns/이웃 |
| dict BFS (`set` seen) | 1.17x | **2.64x** |
| dict BFS (`bytearray` seen) | 0.89x | **1.35x** |
| CSR BFS (번호 섞음) | 1.01x | **1.13x** |

세 줄 다 같은 방향으로 움직인다.

- dict 대비 CSR의 우위가 1.17배 → **2.64배**로 벌어진다.
- 방문 표시를 똑같이 맞춰도(bytearray) 0.89배 → **1.35배**로 뒤집힌다. 이 규모에서는 박싱 비용보다 포인터 추적 비용이 커진다.
- 지역성 파괴 페널티가 1% → **13%**로 올라온다. 캐시가 드디어 보이기 시작한다.

**즉 「차이가 크지 않다」는 파이썬만의 성질이 아니라 「파이썬 × 이 규모」의 성질이다.** 이 점에서 8장의 예제는 CSR에 다소 불리한 조건에서 재고 있다고 봐야 한다.

## 8. C로 내려보내면 왜 차이가 드러나는가 — 숫자로

같은 CSR 배열을 그대로 `scipy.sparse.csgraph.breadth_first_order`에 넘겼다. 알고리즘도 자료 배치도 동일하고, **BFS 루프만 C로 돌아간다.**

| | 파이썬 CSR BFS | scipy(C) CSR BFS | C가 빠른 배수 |
|---|---|---|---|
| 노드 5만 | 42.6 ms (71.0 ns/이웃) | 5.2 ms (8.7 ns/이웃) | **8.2배** |
| 노드 40만 | 417.1 ms (86.9 ns/이웃) | 116.4 ms (24.3 ns/이웃) | **3.6배** |

정답의 「3~10배」가 그대로 재현된다. 그런데 진짜 볼 것은 마지막 열이 아니라, **캐시를 넘어설 때 각 언어가 얼마나 다쳤는가**다.

| | 5만 → 40만 이웃당 비용 | 늘어난 절대량 | 늘어난 비율 |
|---|---|---|---|
| 파이썬 CSR | 71.0 → 86.9 ns | **+15.9 ns** | +22% |
| C CSR (scipy) | 8.7 → 24.3 ns | **+15.6 ns** | **+179%** |

**늘어난 절대량이 거의 같다(약 16 ns).** 하드웨어가 부과한 메모리 벌금은 두 언어에 동일하게 매겨졌다. 다른 것은 분모뿐이다. 71 ns를 이미 쓰고 있던 파이썬에서는 22% 손실이고, 8.7 ns로 달리던 C에서는 179% 손실이다.

암달의 법칙을 이보다 깔끔하게 보여 주는 예를 찾기 어렵다. **CSR이 파이썬에서 안 통하는 게 아니라, 파이썬이 비교 대상을 전부 느리게 만들어서 차이를 덮고 있는 것이다.** C에서는 메모리가 곧 병목이므로, 이웃이 연속인지 아닌지가 성능을 지배한다. 그래서 C/Rust로 내리면 CSR 대 포인터 추적의 격차가 3~10배로 벌어진다(Rust의 `Vec<Vec<u32>>`도 이 비교에서 포인터 추적 쪽이다).

## 9. 그래서 파이썬에서는 어떻게 할 것인가

CSR을 파이썬에서 쓰되, **루프를 파이썬에 두지 않는 것**이 요령이다. 위 표에서 확인된 것처럼 이득은 인터프리터를 벗어나는 순간 나온다.

| 방법 | 성격 | 언제 |
|---|---|---|
| `scipy.sparse` + `scipy.sparse.csgraph` | CSR을 그대로 쓰는 검증된 C 구현(BFS, 최단 경로, 연결 요소) | 표준 알고리즘이면 첫 선택 |
| numpy 벡터화 (프론티어 단위 처리) | 파이썬 루프를 홉 수만큼으로 줄인다. 노드 하나 단위 루프를 없애는 것이 요점 | 직접 구현이 필요한 순회류 |
| Numba `@njit` | 같은 CSR 루프를 그대로 JIT 컴파일. `array`/numpy 배열이면 잘 먹는다 | 알고리즘이 표준에 없을 때 |
| Rust/C 확장 (PyO3, Cython) | 핵심 루프만 내리고 CSR 배열은 그대로 공유(제로 카피) | 반복 실행되는 핫 패스 |

이 목록에서 방법마다 다른 점은 하나뿐이다. **이웃 하나당 바이트코드 10~19개를 없애는 것.** 그걸 없애야 CSR이 원래 하려던 일(캐시 줄 하나로 이웃 32개 가져오기)이 성능에 반영된다.

## 10. 그래도 파이썬에서 CSR을 쓰는 이유

예제 2가 속도 이야기를 끝내고 곧바로 붙이는 문장이 이것이다.

```
그래도 파이썬에서 CSR 을 쓸 이유가 있다. 메모리다.
앞 예제에서 8배 차이였다. 메모리에 안 들어가면 속도 논쟁은 의미가 없다.
```

예제 1을 실제로 돌리면(노드 2만, 엣지 12만) 이렇게 나온다.

| 표현 | 바이트 | 배수 |
|---|---|---|
| 인접 행렬 (비트) | 50,000,057 | 48.1x |
| 인접 리스트 (dict of list) | 8,116,284 | 7.8x |
| CSR (배열 2개) | 1,039,844 | **1.0x** |

속도는 1.2배 차이인데 메모리는 7.8배 차이다. **파이썬에서 CSR의 진짜 값은 속도가 아니라 용량이다.** 그리고 이 둘은 연결되어 있다. 7절에서 봤듯이 메모리를 덜 쓰면 작업 집합이 캐시에 들어가고, 더 나아가 **스왑에 나가지 않는다.** 스왑이 시작되면 100 ns 급 이야기가 아니라 마이크로초~밀리초 급 이야기가 된다. 그 지점에서는 인터프리터 오버헤드가 오히려 무시할 만한 값이 된다.

## 정리

| 질문 | 답 |
|---|---|
| 왜 차이가 작은가 | 이웃 하나당 인터프리터 비용 71 ns가 캐시 미스 100 ns와 같은 자릿수이고, 실제 미스는 캐시 줄 하나에 정수 32개가 담겨 분산된다 |
| 인터프리터 비중은 얼마인가 | BFS 로직 없이 CSR을 훑기만 해도 전체 시간의 **87%**, 빈 루프만으로 **43%** |
| 그래서 상한은 | 메모리 몫이 13%면 완벽히 없애도 $1/(1-0.13) = 1.15$배. 관찰값 1.1~1.6배와 일치 |
| 증명 | 노드 번호를 섞어 지역성을 파괴해도 노드 5만에서 **1.01배**밖에 안 느려진다 |
| 함정 | 원본 비교의 차이 일부는 CSR의 연속성이 아니라 `set` 해싱. `seen`을 맞추면 5만 규모에서는 dict이 오히려 **0.89배**로 빠르다 (`array("i")` 읽기마다 PyLong 박싱) |
| C로 내리면 | 같은 CSR로 scipy가 **3.6~8.2배** 빠르다. 캐시 초과 벌금은 두 언어 모두 약 +16 ns/이웃이지만, 파이썬은 +22%, C는 **+179%** |
| 파이썬에서 CSR을 쓸 이유 | 메모리 **7.8배**. 안 들어가면 속도 논쟁 자체가 성립하지 않는다 |
| 8장의 원칙 | 측정값은 기계마다 다르다. **배수만 보라** |
