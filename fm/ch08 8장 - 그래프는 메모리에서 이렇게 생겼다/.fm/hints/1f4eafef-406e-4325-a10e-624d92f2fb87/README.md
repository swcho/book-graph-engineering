# 인덱스 없는 인접성은 언제부터 이득인가?

> **정답**: 두 번째 홉부터다. 시작 노드를 찾는 데는 여전히 색인이 필요하다.

## 한 줄 핵심

인덱스 없는 인접성(index-free adjacency)은 **「이미 손에 든 노드에서 이웃으로 가는」 비용을 없앤다**. 그런데 첫 노드를 손에 쥐는 일은 그 대상이 아니다. 이름으로 노드를 찾는 건 색인이 하는 일이고, 색인이 없으면 전체 훑기다. 그래서 이득이 시작되는 지점은 **첫 홉을 밟은 다음**이다.

## 두 방식의 비용 구조

8장 예제 5(`ex5_index_free.py`)가 정확히 이 둘을 나란히 재 본다.

| | 이웃을 찾는 방법 | 한 번의 비용 |
|---|---|---|
| 색인 방식 (관계형) | 정렬된 엣지 테이블에 이진 탐색 (`bisect_left`) | $O(\log m)$ — 데이터가 늘면 깊어진다 |
| 직접 방식 (그래프) | 노드가 이웃 목록의 주소를 들고 있다 | $O(1)$ — 전체 크기와 무관 |

예제는 노드 10,000개와 100,000개로 같은 측정을 반복한다. 색인 방식은 노드가 10배 늘 때 이론 탐색 깊이 $\log_2(2m)$가 약 17에서 약 20으로 늘어나지만, 직접 방식은 **거의 그대로**다. 이게 「데이터가 커져도 순회 비용이 안 변한다」는 그래프 데이터베이스의 주장이다.

## 그런데 왜 「첫 홉」이 아니라 「두 번째 홉」인가

$k$홉 질의를 분해해 보자. 평균 차수를 $d$라 하면 각 단계에서 이웃을 찾아야 하는 노드 수는 이렇게 늘어난다.

| 단계 | 이웃 조회 횟수 | 색인 방식이 내는 추가 비용 |
|---|---|---|
| 시작 노드 찾기 | 1 | **양쪽 모두 색인 사용** — 차이 없음 |
| 1홉 (시작 노드의 이웃) | 1 | $\log m$ 한 번 |
| 2홉 | $d$ | $d \log m$ |
| 3홉 | $d^2$ | $d^2 \log m$ |
| $k$홉 | $d^{k-1}$ | $d^{k-1} \log m$ |

$k$홉 전체를 합치면 색인 방식의 초과 비용은

$$C_{\text{색인}} - C_{\text{직접}} \;\approx\; \log m \cdot \sum_{i=0}^{k-1} d^{i} \;=\; \log m \cdot \frac{d^{k}-1}{d-1}$$

핵심은 이 식이 $k$에 대해 **지수적으로 커진다**는 점이다. 평균 차수 $d = 12$라면

- 1홉: 색인 탐색 1번을 아낀다 → 체감이 없다. 시작 노드를 찾을 때 이미 색인을 탔으므로 총 색인 사용은 2번 대 1번, 상수 차이다.
- 2홉: 12번을 아낀다.
- 3홉: 144번.
- 4홉: 1,728번.

그래서 **1홉 질의만 하는 워크로드라면 인덱스 없는 인접성은 거의 이득이 아니다**. 관계형 DB에 인덱스 잘 걸어 두면 사실상 동급이다. 이득은 홉이 깊어질 때 복리로 쌓인다.

## 나머지 절반: 중간 결과가 안 곱해진다

예제 5의 마지막 설명이 짚는 대로, 그래프 데이터베이스가 조인보다 빠른 이유의 **절반만** 인덱스 없는 인접성이다.

- **절반**: 홉마다 $\log m$ 색인 탐색이 사라진다 (이 카드의 내용).
- **나머지 절반**: 3장에서 본 「중간 결과가 안 곱해진다」. 관계형 다중 홉은 셀프 조인이고, 조인 결과 집합이 단계마다 물리적으로 부풀어 오른다. 그래프 순회는 프런티어를 들고 포인터를 따라가므로 중간 테이블을 만들지 않는다.

두 효과가 같은 방향으로 겹치기 때문에 깊은 홉에서 격차가 자릿수로 벌어진다.

## 시작 노드는 여전히 색인이다 — 실무에서 자주 잊는 지점

「그래프 DB는 인덱스가 필요 없다」는 흔한 오해다. 정확히는 **인접성에 인덱스가 필요 없다**는 뜻이고, 진입점(anchor) 탐색에는 인덱스가 필수다.

```cypher
MATCH (p:Person {name: '조성우'})-[:KNOWS*2]->(friend)
RETURN friend
```

- `name` 프로퍼티에 인덱스가 없으면 `NodeByLabelScan`으로 `:Person` 전체를 훑는다. 노드가 1,000만 개면 순회를 시작하기도 전에 질의가 끝난다.
- 인덱스가 있으면 `NodeIndexSeek`으로 진입점을 잡고, 그 뒤 `*2` 확장은 인덱스 없이 포인터만 따라간다.

즉 그래프 질의의 성능 프로파일은 이렇게 갈린다.

$$C_{\text{전체}} \;=\; \underbrace{O(\log n)\ \text{또는}\ O(n)}_{\text{진입점 — 인덱스가 결정}} \;+\; \underbrace{O(\textstyle\sum_{i} d^{i})}_{\text{확장 — 인접성이 결정}}$$

앞부분을 방치하면 뒷부분을 아무리 최적화해도 소용없다. 실무에서 「그래프 DB로 옮겼는데 안 빨라졌다」의 상당수가 진입점 인덱스 누락이다.

## 자주 하는 오해

- **「그래프 DB는 인덱스가 아예 필요 없다」** → 진입점에는 필요하다. 인접성에만 필요 없다.
- **「1홉도 그래프가 빠르다」** → 상수 배 차이다. 1홉 위주 워크로드는 이 논거로 마이그레이션을 정당화하기 어렵다.
- **「홉이 깊으면 항상 이긴다」** → 슈퍼 노드가 끼면 $d^{k}$의 $d$가 폭발한다. 8.3절의 차수 제곱합 $\sum_v d_v^2$ 문제가 인덱스 없는 인접성의 이득을 그냥 삼켜 버린다. 저장 방식 이전에 차수 쏠림을 봐야 한다.
- **「포인터니까 디스크에서도 $O(1)$」** → 메모리 안에서는 그렇다. 디스크·페이지 캐시로 내려가면 임의 접근 한 번이 페이지 폴트 한 번이 될 수 있다. 그래서 8.2/8.4절이 지역성과 그래프 재배치를 같이 다룬다. 이웃이 연속으로 놓여 있어야 포인터의 이론적 이득이 실제 속도로 나온다.

```bash
cd content/ch08/code
python3 ex5_index_free.py   # 색인 방식 vs 직접 방식, 노드 수를 10배 늘려 가며
```

출력의 **배수와 추세**만 보면 된다. 절대값은 기계마다 다르다. 노드 수가 늘 때 색인 방식의 시간과 이론 색인 깊이가 함께 커지는지, 직접 방식은 평평한지를 확인하는 게 핵심이다.
