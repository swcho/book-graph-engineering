# 파이썬에서도 CSR을 쓸 이유는 무엇인가?

> **정답**: 메모리다. 메모리에 들어가지 않으면 속도 논쟁은 의미가 없다.

## 한 줄 핵심

파이썬에서 CSR의 **속도 이득은 인터프리터가 먹어 버린다**. 바이트코드 디스패치 비용이 캐시 미스 비용보다 훨씬 커서, 루프를 아무리 잘 배치해도 차이가 상수 배로 눌린다. 그런데 **메모리 이득은 인터프리터가 먹지 못한다**. 8배는 자료 구조가 만든 숫자이고, 자료 구조는 어떤 언어로 쓰든 같은 바이트를 차지한다. 그래서 파이썬에서 CSR을 고르는 근거는 「빠르다」가 아니라 「들어간다」다.

## 8장이 실제로 잰 숫자

`ex1_three_forms.py`를 노드 20,000개 / 엣지 119,964개(평균 차수 12)로 돌린 실측이다.

| 표현 | 바이트 | 배수 |
|---|---:|---:|
| 인접 행렬 (비트) | 50,000,057 | **48.1x** |
| 인접 리스트 (dict of list) | 8,116,284 | **7.8x** |
| CSR (`array("i")` 두 개) | 1,039,844 | 1.0x |

노드 50,000개 / 엣지 299,958개로 키우면 배수가 더 벌어진다. dict of list가 21,508,836바이트, CSR 인덱스 배열 두 개가 2,599,668바이트로 **8.3배**다. `ex2_csr_walk.py`의 마지막 문장이 말하는 「앞 예제에서 8배 차이였다」가 이 숫자다.

그리고 8장이 여는 문장 — **같은 그래프가 한쪽에서 4.1GB, 다른 쪽에서 380MB**(약 10.8배) — 도 정확히 같은 현상의 라이브러리 버전이다.

### 8배가 어디서 나오는지 — 원소 하나당 산수

측정값을 원소로 나누면 근거가 드러난다. 방향을 펼친 이웃 항목이 599,916개니까,

| | 이웃 항목 1개당 |
|---|---:|
| dict of list | 약 **35.9바이트** |
| CSR (`indices` + `indptr`) | 약 **4.33바이트** |

파이썬 `int` 객체는 64비트에서 하나가 28바이트다(`sys.getsizeof(300)`). 여기에 리스트가 그 객체를 가리키는 포인터 8바이트, 리스트 객체 헤더와 과할당(over-allocation), dict 엔트리 오버헤드가 얹힌다. 즉 **4바이트짜리 노드 번호 하나를 담으려고 36바이트를 쓴다.** CSR은 `array("i")` 안에서 그냥 4바이트 정수다. 오프셋 배열이 노드당 4바이트를 더 쓰지만 이웃 수로 나누면 0.33바이트다.

## 그런데 속도는 왜 안 벌어지나

`ex2_csr_walk.py`로 같은 그래프(노드 50,000 / 엣지 299,958)에 BFS를 돌린 실측이다.

```
  CSR            방문 50,000개      42.1 ms
  dict of list   방문 50,000개      49.7 ms
```

**1.18배.** 8배 조밀한 자료 구조를 썼는데 속도는 20%도 못 벌었다. 이유는 병목이 메모리가 아니라 인터프리터에 있기 때문이다. 한 이웃을 처리하는 동안 CPython은

- 바이트코드를 디스패치하고 (`FOR_ITER`, `BINARY_SUBSCR`, `COMPARE_OP` …)
- `array` 원소를 꺼낼 때마다 **파이썬 `int` 객체를 새로 만들고**(박싱)
- 참조 카운트를 올리고 내리고

를 반복한다. 이게 수십~수백 나노초다. 반면 캐시 미스 한 번은 100나노초 수준이다. 즉 **CSR이 아끼는 비용이 인터프리터가 쓰는 비용에 묻힌다.** 8장이 「같은 코드를 C나 Rust로 옮기면 CSR 쪽이 보통 3~10배 빨라진다」고 적은 이유다. 그쪽에는 묻어 버릴 오버헤드가 없다.

### 논지를 정확히 세우면

$$\text{총 비용} \;\approx\; \underbrace{c_{\text{언어}}}_{\text{인터프리터가 결정}} \;+\; \underbrace{c_{\text{접근}} \cdot (\text{캐시 미스 수})}_{\text{배치가 결정}}, \qquad \text{메모리} \;=\; \underbrace{f(\text{표현})}_{\text{언어와 무관}}$$

- **속도의 배수는 언어에 달렸다.** 파이썬에서는 $c_{\text{언어}}$가 지배해서 CSR의 이득이 1.2배로 눌린다. C에서는 사라져서 3~10배로 드러난다.
- **메모리의 배수는 언어에 달리지 않았다.** 4바이트 정수 60만 개는 파이썬에서도 C에서도 2.4MB다. 그걸 객체로 감싸면 파이썬에서도 C에서도 부풀어 오른다(C로 `struct Node { struct Node **nbrs; }`를 쓰면 똑같이 낭비한다). **배수를 결정하는 건 «표현»이고, 상수를 결정하는 게 «언어»다.**

그래서 「파이썬은 어차피 느리니까 자료 구조 신경 쓸 필요 없다」는 결론이 틀린다. 느린 건 상수뿐이고, 8배는 그대로 남아 있다.

## 파이썬에서 CSR을 쓰는 실제 경로

8장 예제는 의존성을 없애려고 표준 라이브러리 `array` 모듈로 직접 만들었다. 실무에서는 보통 이렇게 쓴다.

### 1. `scipy.sparse.csr_matrix` / `csr_array`

```python
import numpy as np
import scipy.sparse as sp

# 무방향 그래프: 엣지를 양방향으로 펼쳐서 COO로 넣고 CSR로 변환
row = np.concatenate([a, b])          # a, b 는 int32 엣지 배열
col = np.concatenate([b, a])
data = np.ones(len(row), dtype=np.int8)          # ← dtype 이 중요하다
csr = sp.coo_matrix((data, (row, col)), shape=(n, n)).tocsr()

csr.indptr    # 오프셋 배열  (8장 예제의 offset)
csr.indices   # 이웃 배열    (8장 예제의 nbr)
csr.data      # 가중치
```

`indptr` / `indices`가 그대로 8장의 `offset` / `nbr`이다. 이름만 다르고 같은 구조다.

**함정 1 — `data` 배열이 세 배를 먹는다.** scipy CSR은 값 배열을 반드시 들고 있다. 노드 50,000 / 엣지 299,958로 실측하면,

| 구성 | 바이트 |
|---|---:|
| `indices` + `indptr`만 (구조 정보) | 2,599,668 |
| + `data`가 `int8` | 3,199,584 |
| + `data`가 **`float64`** (`np.ones()` 기본값) | 7,398,996 |

`np.ones(len(row))`라고만 쓰면 float64가 되어 **구조 정보의 2.8배**를 쓴다. 가중치 없는 그래프라면 `dtype=np.int8`이나 `np.bool_`로 잡아야 한다. dict of list 대비 배수가 8.3배에서 6.7배로 줄어드는 게 이 한 줄 차이다.

**함정 2 — 인덱스 dtype이 int64로 올라가면 두 배가 된다.** scipy는 `nnz`와 차원이 `2**31`을 넘지 않으면 `indices`/`indptr`을 int32로 쓴다. 그런데 구형 `csr_matrix`는 **값을 보고** 축소해 주는 반면, 신형 `csr_array`는 **입력 배열의 dtype을 보고** 정한다. 파이썬 리스트나 `np.arange()`를 그냥 넘기면 기본이 int64라서 `csr_array`에서는 인덱스 배열이 그대로 int64가 되고, 메모리가 두 배로 뛴다. 엣지 배열을 만들 때 `dtype=np.int32`를 명시하거나 `scipy.sparse.get_index_dtype()` / `safely_cast_index_arrays()`를 쓴다.

### 2. `array` 모듈 / `numpy` 배열 직접

8장 예제가 하는 방식이다. scipy를 못 깔거나, 값 배열이 아예 필요 없거나, `indptr`/`indices`를 손으로 다루고 싶을 때 쓴다. 정수 배열 두 개뿐이니 `np.save`로 그대로 덤프하고 `np.load(mmap_mode="r")`로 **메모리 매핑**해서 열 수도 있다. 이건 dict of list로는 흉내 낼 수 없는 선택지다 — 피클은 통째로 역직렬화해서 객체를 다시 만들어야 한다.

### 3. 보너스: 루프까지 C로 내려가면 속도도 온다

메모리 때문에 CSR을 골랐는데, CSR이면 순회를 C 구현에 넘길 수 있다. 같은 그래프에서,

| BFS 구현 | 시간 |
|---|---:|
| `scipy.sparse.csgraph.breadth_first_order` (C) | **5.5 ms** |
| 파이썬 `dict of list` BFS | 49.2 ms |

**약 9배.** 8장이 예고한 「C나 Rust로 옮기면 3~10배」가 파이썬 안에서 그대로 재현된다. $c_{\text{언어}}$를 없애 주면 CSR의 이득이 드러난다는 증거이기도 하다. 즉 파이썬에서 CSR의 진짜 값은 **메모리 + C 루틴으로 넘길 수 있는 표현**이라는 두 가지고, 순수 파이썬 루프에서의 속도는 처음부터 이득이 아니었다.

## 「메모리에 안 들어가면」이 실제로 무슨 뜻인가

여기가 답의 핵심이다. 메모리 초과는 **점진적으로 느려지는** 게 아니라 **붕괴**다.

| 접근 | 지연 | DRAM 대비 |
|---|---:|---:|
| DRAM 임의 접근 | 약 80~100 ns | 1x |
| NVMe SSD 4KiB 임의 읽기 (QD1) | 약 100 µs | 약 **1,000x** |
| 회전 디스크 탐색 | 약 10 ms | 약 **100,000x** |

그래프 순회는 스왑이 가장 싫어하는 워크로드다. BFS 프런티어 확장은 정의상 **임의 접근**이라 미리 읽기(prefetch)가 듣지 않는다. 위 실측에서 dict BFS가 49ms에 이웃 60만 개를 읽었다. 이게 상주 메모리에서 밀려나 페이지 폴트가 절반만 걸려도 $3 \times 10^5 \times 100\,\mu s = 30$초다. **1.2배 논쟁을 하던 자리에 600배가 들어온다.**

그리고 스왑 상황에서는 8배가 8배로 끝나지 않는다.

- **CSR**: 4KiB 페이지 하나에 4바이트 정수 **1,024개**가 들어온다. 폴트 한 번이 이웃 1,024개를 갚는다.
- **dict of list**: 이웃 하나를 읽으려면 dict 엔트리 → 리스트 객체 → `int` 객체로 **세 번 점프**하고, 이 객체들은 힙 전체에 흩어져 있다. 페이지 하나가 갚아 주는 유효 이웃 수가 훨씬 적고, 폴트 기회는 3배다.

그래서 상주 메모리에서는 1.2배였던 격차가 스왑을 타는 순간 자릿수로 벌어진다. **CSR은 「빠른 자료 구조」가 아니라 「스왑을 안 타게 해 주는 자료 구조」라서 이득이다.** 리눅스라면 그 전에 OOM killer가 프로세스를 죽이거나, 컨테이너라면 cgroup 한계에서 `OOMKilled`로 끝난다. 이 경우 속도는 측정 자체가 불가능하다.

### 절벽이 어디에 있는지 (봉투 뒷면 계산)

평균 차수 12, 위 실측 단가로 노드당 필요량은 dict of list 약 430바이트, CSR 약 52바이트다. 가용 메모리 8GB로 잡으면,

| 표현 | 담을 수 있는 노드 수 |
|---|---:|
| dict of list | 약 **1,900만** |
| CSR (`indices` + `indptr`) | 약 **1억 5,400만** |

8장 8.3절의 제목 — 「100만에서 멀쩡하고 10만에서 죽는 이유」 — 는 차수 쏠림 이야기지만, 그릇을 잘못 고르면 같은 절벽이 **8배 이른 지점**으로 당겨진다. 기계를 8배 큰 걸로 바꾸는 것보다 `array("i")` 두 개로 바꾸는 게 싸다.

## 자주 하는 오해

- **「파이썬은 어차피 느리니 CSR은 무의미하다」** → 속도만 보면 실측 1.18배로 맞는 말에 가깝다. 그런데 CSR을 고르는 이유가 속도가 아니다. 8배는 언어와 무관하게 남는다.
- **「메모리는 나중에 서버 키우면 된다」** → 8배는 서버 등급을 세 단계 올리는 것과 같다. 그리고 절벽 직전 구간(스왑 시작)에서는 성능이 선형으로 나빠지지 않고 수백 배 무너진다. 「조금 느려서 참고 쓰는」 구간이 없다.
- **「`scipy.sparse.csr_matrix`로 만들었으니 최적이다」** → `data`를 float64로 두면 구조 정보의 2.8배, `csr_array`에 int64 인덱스를 물리면 또 두 배다. 실측 3.2MB가 7.4MB, 14MB로 자란다. dtype을 확인해야 한다.
- **「CSR로 바꾸면 파이썬 순회도 빨라진다」** → 순수 파이썬 루프로는 거의 안 빨라진다. 빨라지는 건 `scipy.sparse.csgraph` 같은 **C 구현에 넘겼을 때**다(실측 9배). 이때 이득은 CSR이 아니라 「인터프리터를 빠져나간 것」에서 온다 — CSR은 빠져나갈 자격을 준 것이다.
- **「CSR이면 무조건 이긴다」** → 변경이 잦으면 아니다. CSR에 엣지 하나를 끼우면 `indices` 뒷부분을 전부 밀어야 한다($O(m)$). 8장이 CSR을 「그릇」으로 소개하는 건 **읽기 위주 / 한 번 적재하고 여러 번 순회하는** 워크로드 전제다. 쓰기가 섞이면 인접 리스트로 만들어 두고 순회 직전에 CSR로 굽는(build once) 방식이 흔하다.
- **「인접 행렬은 밀도가 낮으니 안 쓴다」** → 이유가 밀도가 아니라 노드 수다. 실측에서 인접 행렬은 CSR의 48배인데, **엣지가 몇 개든 그 값이 안 변한다**. $n^2/8$바이트라서 20,000노드에 48MB, 100,000노드면 1.25GB다. 8장이 「수천 이하에서만」이라고 못 박은 이유다.
