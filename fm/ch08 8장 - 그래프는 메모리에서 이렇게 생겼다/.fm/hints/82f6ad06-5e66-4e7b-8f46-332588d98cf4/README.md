# `build_csr()`의 `cursor` 배열은 왜 필요한가

## 한 줄 답

**각 노드의 이웃을 채워 넣을 "다음 쓰기 위치"를 추적하기 위해서다.** `offset`의 시작값을 복사해 두고, 그 노드에 이웃 하나를 쓸 때마다 1씩 올린다.

---

## 실제 구현

`ex1_three_forms.py`의 `build_csr()`이다.

```python
def build_csr(edges, n):
    """오프셋 배열 + 이웃 배열. 정수 배열 두 개가 전부다."""
    deg = [0] * n
    for a, b in edges:                       # (1) 차수 세기
        deg[a] += 1
        deg[b] += 1
    offset = array("i", [0] * (n + 1))
    for i in range(n):                       # (2) 누적합 → 구간 경계 확정
        offset[i + 1] = offset[i] + deg[i]
    cursor = list(offset[:n])                # (3) 쓰기 커서 = 각 구간의 시작점 복사
    nbr = array("i", [0] * offset[n])
    for a, b in edges:                       # (4) 엣지를 다시 훑으며 채우기
        nbr[cursor[a]] = b; cursor[a] += 1
        nbr[cursor[b]] = a; cursor[b] += 1
    return offset, nbr
```

`ex2_csr_walk.py`에도 같은 함수가 이름만 `cur`로 줄어서 들어 있다 (`cur = list(offset[:n])`). 즉 이 커서는 우연히 등장한 임시 변수가 아니라, CSR을 만드는 표준 3-패스 관용구(count → prefix sum → scatter)의 3번째 패스에 반드시 따라오는 장치다.

---

## 왜 없으면 안 되는가 — 세 가지 이유

### 1. 엣지가 노드 순서대로 들어오지 않는다

`nbr` 배열은 "노드 0의 이웃들, 노드 1의 이웃들, …"이 **순서대로 붙어 있는** 하나의 평평한 배열이다. 그런데 입력 `edges`는 `(0,2), (7,3), (2,5) …` 처럼 노드 순서와 무관하게 섞여 있다.

그래서 엣지 `(a, b)`를 하나 처리할 때마다 **서로 멀리 떨어진 두 구간**(a의 칸, b의 칸)에 각각 한 개씩 흩뿌려 넣어야 한다(scatter). 같은 노드는 자기 차수만큼 여러 엣지에 걸쳐 다시 등장하므로, "이 노드 구간은 지금까지 몇 칸 채웠지?"를 노드별로 기억하는 상태가 필요하다. 그 상태가 `cursor[v]`다.

### 2. `offset`은 읽기 전용 경계라서 훼손할 수 없다

`cursor` 없이 `offset[a]`를 직접 증가시키고 싶은 유혹이 있지만, 그러면 `offset`이 파괴된다. `offset`은 완성된 뒤에 탐색에서 이렇게 쓰인다 (`bfs_csr()`):

```python
for i in range(offset[u], offset[u + 1]):     # 연속 구간 그대로 읽기
    v = nbr[i]
```

`offset[u]`가 증가해 버렸다면 이 구간의 왼쪽 경계가 사라져 노드 `u`의 이웃을 되찾을 수 없다. 그래서 **`offset`은 불변의 경계로 남기고, 증가하는 쪽은 복사본인 `cursor`로 분리**한다. `list(offset[:n])`의 `list(...)`가 바로 그 "복사해 둔다"에 해당한다.

### 3. 대안이 전부 더 비싸다

| 방식 | 비용 |
|---|---|
| 노드마다 `edges` 전체를 다시 스캔해 자기 이웃만 골라 담기 | O(n × E) — 5만 노드 × 30만 엣지면 사실상 불가능 |
| `edges`를 (노드, 이웃)으로 펼쳐 정렬한 뒤 순서대로 쓰기 | O(E log E) + 추가 메모리 |
| **`cursor` 사용** | **O(n + E), 추가 메모리는 정수 n개** |

`cursor`는 정수 배열 하나를 얹는 대가로, 엣지 목록을 **한 번만 더** 훑고 끝낸다. CSR이 "제일 조밀하다"는 장점을 만드는 과정 자체도 싸야 의미가 있다.

## 손으로 따라가 보기

`n = 4`, `edges = [(0,2), (1,2), (2,3)]` (무방향).

**(1) 차수** — `deg = [1, 1, 3, 1]`

**(2) 누적합** — `offset = [0, 1, 2, 5, 6]`
→ 노드 0은 `nbr[0:1]`, 노드 1은 `nbr[1:2]`, 노드 2는 `nbr[2:5]`, 노드 3은 `nbr[5:6]` 을 쓸 자리로 예약받았다.

**(3) 커서 초기화** — `cursor = [0, 1, 2, 5]` (각 구간의 시작점)

**(4) 엣지 순회**

| 처리 | 쓰기 | `cursor` 변화 | `nbr` 상태 |
|---|---|---|---|
| 시작 | | `[0, 1, 2, 5]` | `[_, _, _, _, _, _]` |
| `(0,2)` | `nbr[0]=2`, `nbr[2]=0` | `[1, 1, 3, 5]` | `[2, _, 0, _, _, _]` |
| `(1,2)` | `nbr[1]=2`, `nbr[3]=1` | `[1, 2, 4, 5]` | `[2, 2, 0, 1, _, _]` |
| `(2,3)` | `nbr[4]=3`, `nbr[5]=2` | `[1, 2, 5, 6]` | `[2, 2, 0, 1, 3, 2]` |

노드 2가 세 엣지에 모두 등장하면서 `cursor[2]`가 `2 → 3 → 4 → 5`로 한 칸씩 전진한 것이 핵심이다. 커서가 없다면 세 번 모두 `nbr[2]`에 덮어써서 이웃 두 개를 잃는다.

결과 검증:

```
노드 0 → nbr[0:1] = [2]        ✓
노드 1 → nbr[1:2] = [2]        ✓
노드 2 → nbr[2:5] = [0, 1, 3]  ✓
노드 3 → nbr[5:6] = [2]        ✓
```

## 불변식 두 개 (이해 점검용)

루프 도중 항상 성립한다.

```
offset[v] <= cursor[v] <= offset[v+1]
```

즉 커서는 절대 자기 구간을 넘어 이웃 노드의 칸을 침범하지 않는다. 침범한다면 `deg` 계산이 틀렸다는 뜻이다.

그리고 루프가 끝난 시점에는

```
cursor[v] == offset[v+1]   (모든 v에 대해)
```

즉 `cursor`는 결국 `offset`을 한 칸 왼쪽으로 밀어놓은 배열이 된다(위 예제의 최종 `cursor = [1,2,5,6]` = `offset[1:5]`). **완성 후 `cursor`의 값 자체는 쓸모가 없고, 채워 넣는 도중의 중간 상태만이 목적**이다. 그래서 `build_csr()`은 `offset, nbr`만 반환하고 `cursor`는 버린다.

> 참고: 이 성질을 이용해 커서를 아예 없애는 변형 구현도 있다. `offset`을 직접 증가시켜 채운 뒤, 마지막에 `offset`을 오른쪽으로 한 칸 밀고 `offset[0] = 0`으로 되돌리는 방식이다. 메모리를 정수 n개만큼 아끼지만 읽기가 어려워서, 책의 예제는 의도를 그대로 드러내는 `cursor` 쪽을 택했다.

---

## 왜 `offset[:n]`이고 `offset[:n+1]`이 아닌가

`offset`의 길이는 `n + 1`인데 커서는 `n`개만 만든다. 마지막 원소 `offset[n]`은 "전체 이웃 개수(= 2E)"를 나타내는 **감시 값(sentinel)**일 뿐, 어떤 노드의 쓰기 시작점도 아니다. 실제로 `nbr = array("i", [0] * offset[n])`처럼 배열 크기를 정하는 데만 쓰인다. 쓰기 대상은 노드 `0 … n-1`이므로 커서도 그만큼만 있으면 된다.

---

## 한 문장으로 정리

`offset`은 **어디부터 어디까지가 누구 자리인지**를 말하는 고정된 지도이고, `cursor`는 그 지도를 보면서 **지금 이 노드는 어디까지 채웠는지**를 기억하는 연필이다. 지도를 연필로 고쳐 쓰면 지도를 잃으므로, 시작값을 복사해 따로 둔다.
