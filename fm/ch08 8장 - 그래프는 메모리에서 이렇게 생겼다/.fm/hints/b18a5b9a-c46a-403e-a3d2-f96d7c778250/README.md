# 대용량 그래프 처리 도구가 적재할 때 재배치를 먼저 하는 이유는 무엇인가?

> **정답**: 이웃을 메모리에서 가까이 모아 캐시 지역성을 높이기 위해서다. 커뮤니티 구조가 있는 실제 그래프에서 효과가 크다.

## 한 줄 핵심

재배치(graph reordering)는 **노드 번호를 다시 매기는 일**이다. 엣지 하나도 지우거나 더하지 않고, 그래프의 위상은 그대로다. 바뀌는 건 「이 노드의 데이터가 메모리 어디에 있느냐」뿐이다. 그런데 그것이 성능을 정한다. 그래서 도구들은 **적재 시점에 한 번 비용을 내고, 이후 모든 질의에서 조금씩 회수하는** 구조를 택한다. 핵심은 이게 **공짜가 아니라 amortization 거래**라는 것이고, 그 거래가 성립하려면 (1) 질의를 충분히 많이 던져야 하고 (2) 그래프에 원래 모을 만한 구조가 있어야 한다.

## 1. 재배치가 정확히 무엇을 고치는가 — CSR의 두 번째 층

8.2절이 이미 말했다. CSR은 `offset[u]`부터 `offset[u+1]`까지가 **연속**이라서 이웃을 훑을 때 캐시 한 줄에 여러 개가 함께 온다. 그럼 이미 다 해결된 것 아닌가? 아니다. 랜덤 접근이 한 층 더 있다.

```
for i in range(offset[u], offset[u + 1]):   # ← 여기는 연속. 이미 빠르다.
    v = nbr[i]
    if not seen[v]:                          # ← 여기가 랜덤. v가 아무 숫자나 될 수 있다.
        ...
```

BFS의 `seen[v]`, PageRank의 `rank[v]`, 2홉 탐색의 `offset[v]`·`nbr[offset[v]]` — 이웃 번호 `v`를 **인덱스로 써서 다른 배열을 찌르는 순간** 접근은 다시 흩어진다. `nbr` 배열을 순서대로 읽는 것과, 그 안에 든 값으로 점프하는 것은 별개다.

재배치가 고치는 건 이 두 번째 층이다. 목표는 「엣지 `(a, b)`에 대해 `|번호(a) - 번호(b)|`를 작게」다. `ex4_relabel.py`가 지역성을 **이웃 번호 차이의 평균**으로 재는 이유가 여기 있다. 이 값이 작으면 `v`를 찌를 때 이미 캐시에 올라온 줄을 다시 쓴다.

### 숫자로 — 왜 16이 기준선인가

`ex4_relabel.py`의 마지막 계산이다.

| 항목 | 값 |
|---|---|
| 캐시 줄 크기 | 64바이트 |
| `array("i")` 원소 크기 | 4바이트 |
| 한 줄에 들어오는 정수 개수 | **16개** |

즉 이웃 번호 차이 평균이 **16보다 작으면** 같은 줄에 들어올 여지가 있고, 그보다 훨씬 크면 사실상 매번 새 줄을 가져온다 — 64바이트를 읽어 4바이트만 쓰는 셈이다. 대역폭의 15/16을 버린다.

무작위 그래프에서 이 값이 얼마인지는 계산할 수 있다. 노드 번호를 `[0, N)`에서 균일하게 두 개 뽑으면 차이의 기대값은 `N/3`이다. `ex4_relabel.py`의 `N = 30,000`이면 **약 10,000**. 16의 600배가 넘는다. 재배치를 해도 무작위 그래프에서는 이 값이 크게 줄지 않는다.

## 2. 왜 「커뮤니티 구조가 있는 실제 그래프에서 효과가 크다」인가

재배치는 결국 **그래프를 1차원 정수 축에 끼워 넣는(embedding)** 문제다. 순열 `π`를 찾아 `Σ|π(a) - π(b)|`를 최소화하는 것 — 조합 최적화에서 말하는 대역폭·선형 배열 문제와 같은 형태다. 그런데 **이 값을 낮게 만들 수 있느냐 자체가 그래프의 성질**이다.

- **무작위 그래프(Erdős–Rényi 계열)** — 어떤 순열을 써도 대부분의 엣지가 길게 남는다. 임의의 절단선을 그으면 양쪽을 잇는 엣지가 항상 많이 걸리는 구조(확장자, expander 성질)이기 때문이다. **좋은 순서가 아예 존재하지 않는다.** 알고리즘이 나빠서가 아니다.
- **커뮤니티가 뚜렷한 그래프(소셜, 웹, 도로망)** — 커뮤니티를 연속된 번호 블록에 몰아넣으면 커뮤니티 **내부** 엣지는 전부 짧아진다. 그리고 이런 그래프에서 엣지의 대부분이 커뮤니티 내부에 있다.

`ex4_relabel.py`의 `clustered()`가 이 대비를 만든 장치다. 노드 30,000개를 60개 그룹으로 나누고(그룹당 500개), 엣지를 그룹 안에서 만들고, 그룹 사이는 `n // 50 = 600`개 다리만 놓는다. 그리고 **번호를 일부러 뒤섞는다** — 함수 주석 그대로 「적재 순서가 구조와 무관한 현실을 흉내 낸다」.

여기서 상한을 추정할 수 있다.

| | 이웃 번호 차이 평균 (추정) |
|---|---:|
| 뒤섞인 상태 | ≈ `N/3` = 10,000 |
| 커뮤니티를 완벽히 블록으로 모은 이상적 순서 | ≈ `c/3` = 500/3 ≈ **167** |
| 이론상 개선 배수 | ≈ `N/c` = **60배** |

`bfs_order()`는 커뮤니티 경계를 명시적으로 알지 못하고 BFS가 만난 순서로만 번호를 매기므로 실측 개선 배수는 이 60배보다 작다. 정확한 실측치는 `python3 ex4_relabel.py`를 돌려야 나온다 — **이 문서에서는 실행하지 않았으므로 구체적 수치는 확인 필요.** 다만 무작위 그래프와 커뮤니티 그래프 중 **어느 쪽이 크게 줄어드는가**는 위 구조에서 이미 결정되어 있다.

**핵심 요약**: 재배치가 하는 일은 구조를 **만드는** 게 아니라, 이미 그래프에 있는 구조를 **번호에 반영하는** 것이다. 구조가 없으면 반영할 것도 없다.

## 3. amortization — 한 번 내고 질의마다 회수한다

여기가 이 카드의 진짜 알맹이다. 재배치는 **비용이 앞에 몰려 있고 이득이 뒤에 흩어져 있는** 거래다.

기호를 정하자.

| 기호 | 뜻 |
|---|---|
| `R` | 재배치 비용 (적재 시 한 번) |
| `T` | 재배치 **전** 작업(질의·알고리즘 실행) 1회 비용 |
| `s` | 재배치로 얻은 속도 향상 배수 (`s > 1`), 재배치 후 1회 비용 = `T / s` |
| `q` | 재배치 이후 실제로 수행할 작업 횟수 |

**재배치가 이득인 조건:**

```
R + q · (T / s)  <  q · T
```

정리하면

```
R  <  q · T · (1 − 1/s)
```

`q`에 대해 풀면 **손익분기 횟수**가 나온다.

```
        R        s
q*  =  ─── · ───────
        T      s − 1
```

`R/T`(재배치가 「작업 몇 회분」인가)와 `s/(s−1)`(이득이 얼마나 얄팍한가)의 곱이다. 두 번째 항이 무섭다.

| `R/T` (재배치 = 작업 n회분) | `s = 2.0` | `s = 1.3` | `s = 1.05` |
|---:|---:|---:|---:|
| 5 | 10회 | 22회 | 105회 |
| 20 | 40회 | 87회 | 420회 |
| 100 | 200회 | 434회 | **2,100회** |

`s`가 1에 가까워지면 `s/(s−1)`이 발산한다. **5% 이득은 20배 더 많은 질의를 요구한다.** 그래서 「재배치했더니 조금 빨라졌다」는 보고는, 재배치 비용을 포함해서 세지 않으면 의미가 없다.

### 갱신이 있으면 `q`의 정의가 바뀐다

위 식은 재배치를 **한 번만** 한다고 가정했다. 그래프가 갱신되면 새 노드·새 엣지가 번호 질서를 깨므로 지역성이 서서히 썩는다. 주기 `P`마다 재배치를 다시 돌린다면, `q`는 「전체 질의 수」가 아니라 **「재배치 사이의 질의 수」**다.

```
q_P  >  (R / T) · s / (s − 1)        # 매 주기마다 이 조건을 다시 만족해야 한다
```

읽기 : 쓰기 비율이 낮은 워크로드에서 재배치가 잘 안 먹히는 이유가 이것이다. 정적 스냅샷 분석(그래프를 한 번 만들고 배치로 여러 알고리즘을 돌리는 형태)에서 재배치가 가장 잘 맞는다.

## 4. 회수가 안 되는 경우 — 다섯 가지

`q*` 식의 각 항이 깨지는 방식으로 정리하면 이렇다.

### (1) `q`가 작다 — 한 번 훑고 버리는 워크로드

ETL, 일회성 통계, 그래프를 만들자마자 한 번 순회하고 버리는 파이프라인. 이때는 재배치 비용을 회수할 기회 자체가 없다. **Balaji & Lucia (IISWC 2018)** 가 정면으로 다룬 문제다. 정교한 재배치 기법들이 실행 시간을 줄이긴 하는데, 재배치 오버헤드를 포함하면 **종단간(end-to-end) 시간이 오히려 늘어나는** 경우가 있어서, 그래프를 몇 번밖에 처리하지 않는 상황에는 적용할 수 없다는 것이다. 이들의 처방은 「구조를 저비용으로 먼저 진단해서, 이득이 날 그래프만 골라 경량 재배치를 적용한다」이고 최대 **1.75배** 속도 향상에 **느려지는 경우는 0.1% 이내**로 억제했다고 보고한다.

### (2) `s`가 1에 가깝다 — 모을 구조가 없거나, 이미 모여 있다

- **구조가 없다**: 무작위 그래프. 2절에서 본 이유로 좋은 순서가 존재하지 않는다. `ex4_relabel.py`의 결론 문장 그대로 「원래 구조가 없으니까」.
- **이미 모여 있다**: 도로망처럼 공간 좌표 순으로 적재된 그래프, URL 사전순으로 크롤된 웹 그래프. 적재 순서가 이미 구조를 반영하고 있으면 재배치가 개선할 여지가 적다. (웹 그래프의 사전순 URL 정렬은 사실상 **공짜 재배치**다.)
- **작아서 상관없다**: 작업 집합 전체가 마지막 단계 캐시(LLC)에 들어가면 어떻게 배치해도 미스가 거의 없다. 캐시 지역성 최적화는 **데이터가 캐시보다 클 때만** 의미가 있다.

### (3) 병목이 캐시가 아니다

`ex2_csr_walk.py`가 이 함정을 직접 보여준다. 파이썬에서 CSR과 dict of list의 BFS 시간 차이가 크지 않은 이유는 「인터프리터 오버헤드가 지배하기 때문」이고, 같은 코드를 C나 Rust로 옮기면 CSR 쪽이 보통 **3~10배** 빨라진다. 캐시 미스가 전체 시간의 5%인 환경에서 캐시 미스를 반으로 줄이면 `s ≈ 1.026`이다. `q*` 표의 마지막 열을 보라.

같은 논리가 네트워크·디스크 바운드 분산 처리, JVM/파이썬 런타임, 코디네이션이 지배하는 시스템에 다 적용된다.

### (4) 접근 패턴이 재배치가 최적화한 것과 다르다 — 슈퍼 노드는 재배치로 안 풀린다

이건 놓치기 쉬운데 중요하다. **재배치는 노드 번호의 순열이므로, 차수 분포를 바꾸지 못한다.** `ex3_degree_skew.py`가 「2홉 비용은 차수의 제곱합에 비례한다」고 했는데, 그 제곱합 `Σ d(v)²`는 **번호를 어떻게 다시 매겨도 불변**이다.

즉 슈퍼 노드 때문에 죽는 질의는 재배치로 구원되지 않는다. 그건 `ex3`이 제시한 대처법 세 가지(슈퍼 노드를 질의에서 피한다 / 차수 상한을 두고 쪼갠다 / 2홉을 미리 계산한다)의 영역이다. 재배치는 **훑는 엣지 수당 비용**을 줄이고, 슈퍼 노드 문제는 **훑는 엣지 수 자체**의 문제다. 다른 축이다.

비슷하게, 「이름으로 노드를 찾는」 시작점 조회는 재배치와 무관하다 — `ex5_index_free.py`의 마지막 경고대로 그건 여전히 색인의 일이다.

### (5) 재배치가 부가 비용을 새로 만든다

- **ID 매핑 계층**: 재배치하면 내부 번호가 외부 ID와 달라지므로 `외부 ID ↔ 내부 번호` 매핑이 필요하다. 그 매핑 조회 자체가 랜덤 접근이고, 결과를 사용자에게 돌려줄 때마다 발생한다. 벤치마크에서는 잘 안 세는 비용이다.
- **적재 시점 피크 메모리**: 제자리 재배치가 아니면 원본과 재배치본이 잠깐 동시에 존재한다. 8장의 주제가 「그릇 크기」인데, 적재 순간에 메모리가 두 배로 튀어서 OOM이 나면 4.1GB냐 380MB냐 논쟁이 무의미해진다.
- **결정론·디버깅**: 노드 번호가 적재마다 달라지면 로그와 재현이 어려워진다.

## 5. 실제 도구·기법에서 어떻게 나타나는가

| 기법 / 도구 | 재배치의 성격 | 무엇을 회수하나 | 근거 상태 |
|---|---|---|---|
| **WebGraph BV 압축** (Boldi–Vigna) | 인접 리스트를 **이웃 번호 차이(gap) + 참조 복사**로 인코딩. 압축률이 노드 번호 순서에 직접 의존한다. 웹 그래프를 URL 사전순으로 번호 매기면 지역성·유사성이 생겨 gap이 작아진다 | 저장 공간, 그리고 줄어든 I/O | 널리 알려진 사실. 구체적 압축률 수치는 확인 필요 |
| **재귀적 이분(Recursive Graph Bisection)** — 자산이 인용한 [arXiv:1602.08820](https://arxiv.org/abs/1602.08820) | 지역성을 높이는 재배치를 **재귀적 그래프 이분**으로 푼다. 이론적 근거를 갖춘 알고리즘이고 병렬·분산 구현이 가능하다 | **압축률** (캐시가 아니다 — 아래 주의 참고) | 제목·저자 확인됨: Dhulipala, Kabiljo, Karrer, Ottaviano, Pupyrev, Shalita (2016) |
| **Ligra / Ligra+ / GBBS** | 공유 메모리 그래프 처리 프레임워크. CSR 기반이고, 압축 변형은 이웃 번호의 차분을 인코딩하므로 번호 순서에 의존한다 | 메모리 발자국 + 캐시 지역성 | 프레임워크 성격은 널리 알려진 사실. 각 버전이 재배치를 기본으로 켜는지는 확인 필요 |
| **Rabbit Order** | **커뮤니티 구조를 이용한 계층적 재배치**. 설계 의도가 `R`을 낮추는 쪽 — 병렬로 빠르게 재배치해서 손익분기 `q*`를 앞으로 당긴다 | 캐시 지역성 | 「커뮤니티 기반 + 병렬」이라는 성격은 널리 알려진 사실. 구체적 배수·재배치 시간은 확인 필요 |
| **Gorder** | 슬라이딩 윈도우 안에서 함께 접근되는 노드가 많아지도록 탐욕적으로 순서를 정한다. `s`는 크게 만들지만 `R`도 크다 — amortization 관점에서 가장 위험한 조합 | 캐시 지역성 | 성격은 널리 알려진 사실. 전처리 비용·속도 향상 수치는 확인 필요 |
| **BFS 순서** (`ex4_relabel.py`의 `bfs_order`) | 만난 순서대로 번호를 다시 매긴다. 8장 표현대로 「제일 싼 재배치 방법」 | 캐시 지역성 | 자산 코드에 구현되어 있음 |
| **선택적 경량 재배치** (Balaji & Lucia, IISWC 2018) | 저비용 분석으로 입력 그래프의 구조를 먼저 판정하고, **이득이 날 그래프만** 재배치한다 | 종단간 시간 | 최대 1.75배 향상 / 느려짐 0.1% 이내, 논문 요약으로 확인됨 |
| **그래프 DB(Neo4j 등)의 적재 시 자동 재배치** | — | — | **확인 필요.** index-free adjacency에서 저장 파일 배치 순서가 적재 순서를 따른다는 점은 구조상 자연스럽지만, 특정 제품이 「적재 시 자동 재배치」를 표준 기능으로 수행한다는 근거를 이 작업에서 확인하지 못했다 |

### 주의 하나 — 자산의 출처 링크는 캐시 논문이 아니다

8장의 키워드 표는 「그래프 재배치 [실험]」의 출처로 arXiv:1602.08820을 걸어두었는데, 확인해 보면 그 논문은 *Compressing Graphs and Indexes with Recursive Graph Bisection*이다. 즉 **압축률**을 목표로 한 재배치다. 재배치의 이득에는 결이 다른 두 가지가 있다는 뜻이다.

| | 목표 | 회수 단위 |
|---|---|---|
| **캐시형 재배치** (Rabbit Order, Gorder) | 캐시 미스 감소 | 질의·알고리즘 실행 1회마다 |
| **압축형 재배치** (BV 인코딩, 재귀적 이분) | 저장·전송 크기 감소 | 파일을 저장·전송·읽을 때마다 |

둘은 겹치지만 같지 않다. `Σ|π(a) − π(b)|`를 줄이는 것이 gap 인코딩에도 좋고 캐시에도 좋아서 방향은 같은데, 최적화 목적 함수와 「회수」의 의미가 다르다. 압축형은 파일 하나로 배포하면 읽는 모든 사람이 회수하므로 `q`가 훨씬 커지고, 그래서 비싼 재배치도 정당화되기 쉽다.

---

## 6. 이 카드를 한 문단으로

대용량 그래프 도구가 적재 때 재배치를 먼저 하는 이유는, **적재는 한 번이고 질의는 여러 번**이기 때문이다. `R + q·T/s < q·T`, 즉 `q > (R/T)·s/(s−1)`을 만족할 만큼 질의가 반복되는 워크로드에서, 재배치는 이웃을 메모리에서 가까이 모아 `v`로 다른 배열을 찌를 때의 캐시 미스를 줄인다. 이 거래가 성립하는 전제는 **그래프에 원래 커뮤니티 구조가 있어야 한다**는 것이다 — 재배치는 구조를 만들지 못하고 번호에 반영만 한다. 무작위 그래프에서는 좋은 순서가 존재하지 않아 `s ≈ 1`이 되고, 그러면 `s/(s−1)`이 발산해서 어떤 `q`로도 회수되지 않는다.
