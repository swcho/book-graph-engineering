# 라우터가 틀리면 무엇이 문제인가?

## 카드 요약

**Q.** 라우터가 틀리면 무엇이 문제인가?

**A.** 빈 답이 아니라 **그럴듯한 오답**이 나온다. 빈 답은 사용자가 알아채지만, 그럴듯한 답은 그냥 믿는다.

## 배경 — 여기서 라우터란

17장의 검색 시스템은 질문을 세 유형으로 나눠 각기 다른 엔진에 보낸다.

| 질문 유형 | 예시 | 담당 엔진 |
|---|---|---|
| 사실조회 | "배송 조회 지연의 원인은?" | 벡터 검색 (TF-IDF 유사도) |
| 다중홉 | "김하늘이 담당한 장애의 공통 원인은?" | 그래프 순회 |
| 전역집계 | "전체에서 가장 자주 나온 원인은?" | 전역 집계 (전체 카운트) |

라우터는 이 분류를 맡는 관문이다. 예제 코드(`ex1_routing.py`)에서는 "전체", "가장", "자주" 같은 단어가 있으면 전역집계로, "공통", "누구" 같은 단어가 있으면 다중홉으로 보내는 단순 규칙이다.

## 왜 "그럴듯한 오답"이 무서운가

라우터가 질문을 엉뚱한 엔진에 보내도, **그 엔진은 실패하지 않는다**. 자기 방식대로 성실하게 계산해서 답을 내놓는다. 문제는 그 답이 형식상 완전히 멀쩡하다는 것이다.

책의 실험이 이걸 직접 보여준다. "전체에서 가장 자주 나온 원인은?"(정답: 멱등성 없음, 전역집계 질문)을 일부러 다른 엔진에 보내면:

- **사실조회(벡터)로 보내면** → 질문과 글자가 비슷한 문서 1건을 찾아 그 문서의 원인을 반환. "캐시 만료" 같은, 전체 통계와 무관하지만 실제 존재하는 원인이 나온다.
- **다중홉(그래프)으로 보내면** → 질문에서 사람/원인 엔티티를 못 찾으면 빈 답이거나, 우연히 매칭되면 엉뚱한 부분 집합이 나온다.

원문의 결론:

> 라우터가 틀리면 «틀린 엔진이 그럴듯한 답»을 낸다. 이게 무섭다.
> 빈 답이면 사용자가 알아채는데, 그럴듯한 답이면 그냥 믿는다.

즉 오류의 위험도는 "답이 안 나옴"이 아니라 **"틀렸다는 신호가 없음"**에 있다. 빈 답은 시스템이 스스로 실패를 드러내는 것이고, 그럴듯한 오답은 실패를 숨기는 것이다. 사용자에게 검증 계기가 사라진다.

## 그래서 설계가 이렇게 된다

1. **애매할 때 어느 쪽으로 기울일지가 설계다.** 저자는 벡터(사실조회) 쪽으로 기울인다. 벡터가 틀리면 **근거 문서가 같이 나와서** 사용자가 "어, 이거 아닌데"를 알아챌 여지가 있다. 반면 그래프 집계는 숫자만 나와서 검증할 방법이 없다. → 틀려도 **검증 가능한 형태로 틀리는 쪽**을 기본값으로.
2. **규칙 → 모델 → 캐시.** 규칙으로 먼저 거르고, 애매한 것만 모델에게 보내고, 결과를 캐시해서 같은 질문이 항상 같은 곳으로 가게 한다(장 요약).
3. **라우터 정확도가 낮으면 라우팅 대신 융합.** 잘못 보내는 것보다 두 엔진을 다 돌리고 순위 융합(RRF)으로 합치는 게 낫다(예제 4). 실전 구조는 "라우터가 확신하면 한쪽만, 애매하면 둘 다" — 애매한 20%만 두 배 비용을 낸다.

## 기억 포인트

- 라우팅 오류의 산출물 = **silent failure**. 시스템은 정상 동작한 것처럼 보이고, 답도 형식상 멀쩡하다.
- 빈 답(눈에 보이는 실패)보다 그럴듯한 오답(안 보이는 실패)이 더 해롭다 — 사용자가 믿어버리기 때문.
- 대응은 두 축: (a) 틀려도 근거가 노출되는 엔진 쪽으로 기울이기, (b) 확신이 낮으면 라우팅 대신 둘 다 돌려 융합하기.
