# 지수 백오프만으로는 봉우리가 사라지지 않는 이유

## 질문

지수 백오프만으로는 봉우리가 사라지지 않는 이유는 무엇인가?

## 답

**간격만 벌렸을 뿐 '다 같이'는 그대로다.** 클라이언트 200개가 다 같이 1초 뒤에 오고, 다 같이 3초 뒤에 온다. 몰려오는 시점 사이의 간격만 늘어났지, 한 시점에 몰리는 양은 줄지 않는다.

## 왜 그런가 — 동기화가 문제의 본질

### 장애가 재시도를 '동기화'시킨다

봉우리(부하 스파이크)의 근본 원인은 재시도 횟수도, 재시도 간격도 아니라 **재시도 시각의 동기화**다. 서버가 잠깐 죽으면 그 순간 요청을 보내던 클라이언트 전부가 **같은 시각에** 실패를 겪는다. 즉 장애 자체가 수백 개 클라이언트의 시계를 하나로 맞춰 버린다.

이 상태에서 모든 클라이언트가 **같은 결정적(deterministic) 공식**으로 다음 재시도 시각을 계산하면:

- 고정 간격 1초: 전원이 t=1, 2, 3, 4, 5초에 도착
- 지수 백오프(1, 2, 4, 8, 16초): 전원이 t=1, 3, 7, 15, 31초에 도착

공식이 뭐든 **입력(실패 시각)이 같고 계산이 같으면 출력(재시도 시각)도 같다**. 지수 백오프는 봉우리와 봉우리 사이를 벌려줄 뿐, 각 봉우리의 **높이**(한 구간에 몰리는 요청 수)는 200 그대로다. 서버가 이미 아픈데 용량의 몇십 배가 한꺼번에 때리는 상황이 반복된다.

### 책의 시뮬레이션(ex1_backoff.py)이 보여주는 것

클라이언트 200개, 재시도 5회, 0.25초 구간마다 도착 요청을 세고 서버는 구간당 10건까지 받는 설정:

| 전략 | 구간 최대 | 특징 |
|---|---|---|
| 고정 간격 1초 | 200 | 매초 200개가 한 구간에 몰림 |
| 지수 백오프 | 200 | **봉우리 높이는 똑같이 200.** 간격만 1→2→4초로 벌어짐 |
| 지수 백오프 + 흔들기 | 크게 낮아짐 | 봉우리가 흩어져 평평해짐 |

핵심 관찰: **총 요청 수는 셋 다 1000건으로 같다.** 다른 건 '언제' 오느냐뿐인데, 그것만으로 서버가 죽고 산다. 부하 문제는 총량 문제가 아니라 **분포 문제**다.

## 해법 — 흔들기(jitter)

동기화를 깨려면 클라이언트마다 **다른** 재시도 시각이 나와야 한다. 그래서 대기 시간을 결정적 값이 아니라 **0 ~ 계산된 백오프값 사이의 무작위 값**으로 뽑는다 (AWS Builders' Library의 "full jitter"):

```python
def schedule_jitter(rng):
    """지수 백오프 + 흔들기 — 0~대기시간 사이 무작위."""
    t, out = 0.0, []
    for i in range(MAX_TRIES):
        t += rng.uniform(0, min(BASE * (2 ** i), CAP))
        out.append(t)
    return out
```

무작위성이 클라이언트마다 다른 값을 만들어 200개의 재시도가 시간축 위에 고르게 퍼진다. **한 줄인데 봉우리가 사라진다.**

### 흔들기는 '늦추는' 장치가 아니라 '흩는' 장치

주의할 직관: 흔들기를 쓰면 첫 재시도가 오히려 **더 빨리** 오기도 한다. 0~1초 사이에서 뽑으니 평균 0.5초로, 고정 간격 1초보다 이르다. 즉 흔들기의 목적은 재시도를 지연시키는 게 아니라 재시도 시각의 **동기화를 깨서 분산**시키는 것이다.

## 역할 분담으로 정리

| 장치 | 해결하는 것 | 해결 못 하는 것 |
|---|---|---|
| 지수 백오프 | 재시도 **빈도**를 줄여 총부하를 완화, 서버에 회복 시간 제공 | 동시 도착(동기화) — 봉우리 높이 |
| 흔들기(jitter) | 동기화를 깨서 봉우리를 **평평하게** 분산 | 재시도 총량 자체 |

둘은 대체재가 아니라 보완재다. 그래서 실무 표준은 **지수 백오프 + 흔들기**의 조합이다. 이 현상은 여러 프로세스가 한 사건에 깨어나 동시에 몰리는 **thundering herd** / **재시도 폭풍(retry storm)** 문제의 한 형태다.
