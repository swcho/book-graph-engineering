# 되돌릴 수 없는 단계는 어디에 배치해야 하는가

## 질문
되돌릴 수 없는 단계를 어디에 배치해야 하는가?

## 답
**최대한 뒤로 민다.** 코드를 고치지 않고 순서만 바꿔도 위험이 사라진다.

---

## 1. 왜 "뒤로 미는가" — 사가 패턴의 전제

사가(saga) 패턴은 긴 트랜잭션을 여러 단계로 쪼개고, 각 정방향 단계마다 **되갚는 동작(보상 트랜잭션, compensating transaction)** 을 짝지어 둔다. 중간 단계가 실패하면 이미 성공한 단계들을 **역순으로** 되갚아서 세상을 원래 상태로 되돌린다.

- 재고 차감 ↔ 재고 복구
- 쿠폰 사용 ↔ 쿠폰 반환
- 결제 ↔ 환불

그런데 이 구조에는 구멍이 하나 있다. **되갚는 동작이 아예 존재하지 않는 단계**다. 대표적인 예가 "확정 메일 발송"이다. 밖으로 나간 메일은 회수할 수 없다. 코드로 표현하면 `undo = None`인 단계다.

```python
mail = Step("확정 메일",
        lambda: (..., world["메일함"].append("주문 확정")),
        None, "")   # 보낸 메일은 회수할 수 없다
```

이런 단계가 사가 **중간에** 있으면, 그 뒤 단계가 실패했을 때 되갚기 체인이 그 지점에서 막힌다. "되돌릴 수 없음 → 사람에게 넘긴다"가 되고, 취소된 주문인데 확정 메일을 받은 손님이 생긴다.

## 2. 순서가 만드는 차이 — 같은 코드, 같은 실패, 다른 결과

책 예제(ex3_saga.py)는 같은 4단계를 두 가지 순서로 돌린다.

| 순서 | 결제 실패 시 결과 |
|---|---|
| 재고 → 쿠폰 → 결제 → **메일(마지막)** | 재고·쿠폰 모두 되갚아 **완전 원상 복구** |
| 재고 → **메일(두 번째)** → 쿠폰 → 결제 | 재고·쿠폰은 복구되지만 **메일함에 "주문 확정"이 남음** |

같은 코드, 같은 실패 지점이다. 다른 건 **단계 순서**뿐이다. 여기서 규칙이 나온다.

> **되돌릴 수 없는 단계는 최대한 뒤로 민다.**

## 3. 왜 위험이 "사라지는가"

되돌릴 수 없는 단계를 **맨 뒤**에 두면:

1. 그 단계는 **앞의 모든 단계가 성공한 뒤에만** 실행된다.
2. 따라서 그 단계가 실행된 시점에는 "앞 단계 실패 때문에 이걸 되갚아야 하는" 시나리오 자체가 생기지 않는다.
3. 즉 보상(undo)이 불가능하다는 약점이 **드러날 기회 자체가 없어진다.**

되갚는 코드를 새로 짜는 게 아니다. 보상 로직을 더 정교하게 만드는 것도 아니다. 실행 순서라는 배치만 바꿔서 "되갚아야 할 상황"을 구조적으로 제거하는 것이다.

물론 그 마지막 단계 **자체가** 실패할 수는 있다(메일 발송 실패). 하지만 그때는 앞 단계들이 이미 커밋된 상태에서 "메일만 다시 보내면 되는" 문제이고, 이는 재시도(멱등 키 포함)로 풀 수 있는 종류의 실패다. "회수 불가능한 걸 이미 내보냈는데 되돌려야 한다"는 종류의 실패가 아니다.

## 4. 핵심 통찰: 리팩터링이 아니라 순서 바꾸기

이 원칙이 값진 이유는 비용 대비 효과다.

- 보상 트랜잭션을 새로 설계하는 건 어렵다. 메일 회수, SMS 취소, 외부 API 되돌리기 — 애초에 불가능한 것도 많다.
- 반면 단계 순서 재배치는 **리스트 한 줄**이다.

```python
# 메일을 마지막으로: 위험이 사라진다
return [stock, coupon, pay, mail]
```

"코드를 고치지 않고 순서만 바꿔도 위험이 사라진다"는 답의 문구가 정확히 이 지점을 가리킨다. 되갚기 능력을 **늘리는** 대신, 되갚기가 **필요한 상황을 줄이는** 설계다.

## 5. 일반화 — 어떤 단계를 뒤로 미나

우선순위를 매기면:

1. **되돌릴 수 있는 단계**(재고, 쿠폰, 잔액 등 우리 DB 안의 일)를 앞에 둔다. 실패해도 보상으로 복구된다.
2. **되돌리기 어려운/비싼 단계**(외부 결제 등)는 그다음.
3. **되돌릴 수 없는 단계**(메일·알림 발송, 외부로 나가는 부수효과, 물리적 배송 지시)는 맨 뒤에 둔다.

한 줄 기준: **"밖으로 나간 일은 롤백이 안 된다."** 우리 시스템 경계 밖으로 효과가 새어 나가는 단계일수록 뒤로 민다.

## 6. 그래도 실패하면 (연결되는 다음 주제)

순서를 아무리 잘 배치해도 되갚기 자체가 실패할 수 있다(환불 API가 503). 그때는:

- 상한까지 재시도하고,
- 안 되면 **되갚기 대기열(데드레터 큐)** 에 적어 둔다.

되갚기는 "지금 성공해야 하는 일"이 아니라 "언젠가 반드시 성공해야 하는 일"이기 때문이다. 하지만 이건 22.4~22.5절의 주제이고, 이 카드의 요점은 그 앞 단계 — **되갚을 일 자체를 순서 재배치로 줄이는 것**이다.
