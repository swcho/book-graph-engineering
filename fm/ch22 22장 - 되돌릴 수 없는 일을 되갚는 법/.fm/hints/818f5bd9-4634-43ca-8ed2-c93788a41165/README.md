# 예산 방식(`run_budget`)의 단계별 허용 시간 계산

## 질문
예산 방식(`run_budget`)은 각 단계의 허용 시간을 어떻게 계산하는가?

## 답
남은 예산에서 뒤에 남은 단계들의 **최소 필요분**을 먼저 떼어 놓고, 그 나머지를 이번 단계에 허용한다.

---

## 계산식

```
allowed = remaining_budget - sum(min_needs of later stages)
```

즉, 단계 `i`를 시작할 때마다:

1. **reserved** = 뒤에 남은 단계들(`i+1` 이후)의 최소 필요분 합계
2. **allow** = `max(0, remaining - reserved)` — 이번 단계에 허용할 시간
3. **took** = `min(need, allow)` — 실제로 쓴 시간 (필요 시간이 허용보다 크면 여기서 잘린다)
4. **remaining -= took** — 예산 갱신 후 다음 단계로

책의 예제 코드(`code/ex2_timeout_budget.py`)에서 핵심 부분:

```python
def run_budget():
    """남은 예산을 보고 각 층의 타임아웃을 그때그때 정한다."""
    remaining, log = OUTER_TIMEOUT, []
    for i, (name, need, _min) in enumerate(STEPS):
        # 뒤에 남은 단계들의 «최소 필요분»을 먼저 떼어 놓는다
        reserved = sum(m for _, _, m in STEPS[i + 1:])
        allow = max(0.0, remaining - reserved)
        took = min(need, allow)
        remaining -= took
```

## 단계별 수치 예시

설정: 전체 예산(바깥 타임아웃) **15초**.
단계 정의 `(이름, 실제 필요 시간, 최소 필요분)`:

| 단계 | 실제 필요 | 최소 필요분 |
|------|----------|------------|
| 검색 | 4.0초 | 1.0초 |
| 요약 | 3.0초 | 1.0초 |
| 초안 | 9.0초 | 3.0초 |
| 검토 | 2.0초 | 2.0초 |

계산 과정:

| 단계 | 남은 예산 | reserved (뒤 단계 최소분 합) | allow = 남은 예산 − reserved | 실제 사용 took | 결과 |
|------|-----------|------------------------------|------------------------------|----------------|------|
| 검색 | 15.0 | 1+3+2 = 6.0 | 15 − 6 = **9.0** | min(4, 9) = 4.0 | 완료 |
| 요약 | 11.0 | 3+2 = 5.0 | 11 − 5 = **6.0** | min(3, 6) = 3.0 | 완료 |
| 초안 | 8.0 | 2.0 | 8 − 2 = **6.0** | min(9, 6) = 6.0 | **잘림 — 부분 결과 반환** |
| 검토 | 2.0 | 0.0 | 2 − 0 = **2.0** | min(2, 2) = 2.0 | 완료 |

총 사용 시간 = 4 + 3 + 6 + 2 = **15.0초 / 약속 15.0초** — 예산을 정확히 지킨다.

## 왜 이렇게 하는가 — 순진한 방식과의 대비

- **순진한 방식(`run_naive`)**: 각 단계가 자기 타임아웃(10초)만 본다. 검색 4 + 요약 3 + 초안 9 = 16초 시점에 바깥 타임아웃(15초)이 먼저 끊긴다. **아무 단계도 자기 규칙을 어기지 않았는데 전체가 실패**하고, 검토 단계에는 아예 도달하지 못한다.
- **예산 방식**: 뒤 단계의 최소 필요분을 미리 예약해 두므로, 앞 단계(초안)가 시간을 다 잡아먹지 못한다. 초안은 6초에서 잘리지만 검토는 필요한 2초를 온전히 받는다.

핵심 통찰:

- 뒤 단계 몫을 **선(先)예약**하는 것이 이 방식의 본질이다. "남은 시간을 그냥 다 준다"가 아니라 "뒤에서 최소한 필요한 만큼은 빼고 준다".
- 이 방식은 「완성 안 된 초안 + 검토 완료」와 「초안만 있고 검토 못 함」 중 어느 쪽을 택할지 **고를 수 있게** 만들어 준다. 어느 쪽이 나은지는 도메인이 정하지만, 선택지가 생기는 것 자체가 가치다.
- 책의 규칙: **각 층의 타임아웃 합이 바깥 타임아웃보다 크면 그 설정은 «거짓말»이다** — 아무도 지킬 수 없는 약속이다. (예제에서 단계별 타임아웃 10초 × 4 = 40초 vs 바깥 15초)

이 패턴은 분산 시스템에서 **timeout budget / deadline propagation**이라 불리는 기법과 같은 발상이다. gRPC의 deadline 전파처럼, 고정 타임아웃 대신 "남은 마감 시간"을 호출 체인을 따라 내려보내는 방식이다.
