# 데드레터 큐 항목에 반드시 넣어야 할 것

**Q. 데드레터 큐 항목에 반드시 넣어야 할 것은 무엇인가?**

**A. 멱등 키다. 항목만 보고 재실행할 수 있어야 한다.**

---

## 1. 핵심 원칙: 항목의 자기완결성

22장 요약의 원문은 이렇습니다.

> 데드레터 큐는 항목만 보고 재실행할 수 있어야 합니다. 멱등 키를 반드시 넣으세요.

데드레터 큐(DLQ)의 존재 이유는 「지금 실패한 작업을 **나중에 다시 실행**하는 것」입니다.
그런데 「나중에」는 원래 실행 문맥이 이미 사라진 시점입니다.

- 실패 당시의 프로세스는 죽었고,
- 요청을 만들었던 메모리 상의 변수·객체도 없고,
- 재처리하는 사람(또는 소비자 프로세스)은 원래 코드 경로를 밟지 않습니다.

그래서 DLQ 항목은 **자기완결적(self-contained)**이어야 합니다. 항목 하나만 꺼내 봐도
「무슨 작업을, 어떤 입력으로, 왜 실패했고, 몇 번 시도했는지」를 알 수 있고,
그 정보만으로 재실행 버튼을 누를 수 있어야 합니다.
외부의 다른 로그나 DB를 뒤져야 재실행이 가능하다면 그건 큐가 아니라 그냥 로그입니다.

예제 4(`ex4_undo_fails.py`)에서 대기열에 적는 항목이 좋은 축소판입니다.

```python
queued = {"작업": "환불", "주문": "A-1024", "금액": 50_000, "시도": 3}
```

무엇을(환불), 무엇에 대해(주문 A-1024), 얼마나(50,000), 몇 번 해 봤는지(3)가
항목 안에 전부 들어 있습니다.

예제 5(`ex5_dlq.py`)의 스키마도 같은 구조입니다.

```sql
CREATE TABLE dlq (
  id        INTEGER PRIMARY KEY,
  job       TEXT NOT NULL,     -- 무슨 작업인가
  reason    TEXT NOT NULL,     -- 왜 실패했나
  kind      TEXT NOT NULL,     -- 일시적 / 영구적 / 모름
  tries     INTEGER NOT NULL,  -- 몇 번 시도했나
  payload   TEXT NOT NULL,     -- 재실행에 필요한 입력 전부
  status    TEXT NOT NULL      -- 대기 / 완료 / 포기
);
```

`payload`에 재실행 입력이 통째로 들어가 있어서, 소비자는 이 행 하나만 읽고 재처리를 돌립니다.

## 2. 왜 하필 「멱등 키」인가

자기완결성만으로는 부족합니다. DLQ에서 꺼내 재실행하는 순간, 이런 질문이 반드시 생깁니다.

- 원래 시도가 **정말 실패했는가, 아니면 성공했는데 응답만 못 받았는가?**
  (타임아웃·연결 오류는 「서버가 처리를 마쳤는지」를 말해 주지 않습니다)
- 소비자 둘이 같은 항목을 동시에 집으면?
- 재처리 도중 소비자가 죽어서 같은 항목을 또 집으면?

DLQ에 들어오는 작업은 환불, 결제, 메일 발송처럼 **밖으로 나가는, 되돌릴 수 없는 일**인
경우가 많습니다(이 장의 주제가 바로 그것입니다). 이런 작업을 「혹시 이미 됐는지 모르는 채로」
다시 실행하면 이중 환불, 이중 결제가 됩니다. 장애를 복구하려다 새 장애를 만드는 셈입니다.

**멱등 키(idempotency key)**가 이 문제를 끊습니다.

- 작업마다 고유한 키(예: `refund:A-1024` 같은 값)를 항목에 박아 둡니다.
- 받는 쪽(환불 API 등)은 같은 키로 온 요청을 **한 번만** 처리하고,
  두 번째부터는 처음의 결과를 그대로 돌려줍니다.
- 그러면 재실행은 「몇 번을 해도 한 번 한 것과 같은」 연산이 됩니다.

즉 멱등 키는 재실행의 의미를 바꿉니다.
「위험할 수도 있는 다시 하기」가 「**언제든, 몇 번이든 안전한 다시 하기**」가 됩니다.
그래야 비로소 DLQ의 재처리 전략 — 상한까지 재시도하고, 남으면 나중에 또 꺼내고,
사람이 수동으로 재실행 버튼을 누르는 것 — 이 전부 안전해집니다.

멱등 키가 없으면 정반대입니다. 재실행할 때마다 「이거 이미 처리된 건 아닐까?」를
사람이 다른 시스템을 뒤져 확인해야 하고, 그 순간 DLQ는 자동 재처리가 불가능한
「수동 조사 대상 목록」으로 전락합니다.

## 3. 21~22장의 흐름 속에서 보기

- 21장: 「다시 하면 된다」— 작업을 내구성 있게 기록하고 재실행하는 전제.
- 22장: 그 전제가 배신하는 곳 — 다시 하면 문제가 커지는 경우(재시도 폭풍),
  애초에 다시 할 수 없는 경우(밖으로 나간 일).
- 되갚기(보상 트랜잭션)마저 실패하면 대기열(DLQ)에 적는다. (22.4~22.5절)
- 그 대기열이 제 몫을 하려면 두 가지가 필요하다:
  1. **항목만 보고 재실행 가능** — 자기완결성 + 멱등 키 (이 카드의 답)
  2. **누가 보는지 정해져 있어야 함** — 「쌓이기만 하고 아무도 안 보는 큐는 로그와 똑같다」

같은 요약 문장의 뒷부분 — 「알림은 늘리지 말고 줄이세요. 아무도 안 보는 알림은 없는 것과
같습니다」 — 도 같은 맥락입니다. DLQ는 저장이 목적이 아니라 **언젠가 반드시 성공시키는 것**이
목적이고, 멱등 키는 그 「언젠가, 몇 번이든」을 기술적으로 가능하게 하는 열쇠입니다.

## 4. 실무 메모

- Stripe 등 결제 API가 `Idempotency-Key` 헤더를 표준처럼 쓰는 이유가 정확히 이것입니다.
  네트워크 오류 후 재시도가 이중 청구가 되지 않게 하려는 것.
- 멱등 키는 「요청을 만들 때」 정해서 항목에 함께 저장해야 합니다.
  재실행 시점에 새로 만들면 받는 쪽에는 새 요청으로 보여서 의미가 없습니다.
- 좋은 키는 작업의 자연 식별자에서 나옵니다: `작업종류 + 대상 ID`(예: 주문번호)면
  같은 주문에 대한 환불이 몇 번 큐에 들어와도 한 번만 실행됩니다.

## 한 줄 정리

> DLQ 항목은 그것만 보고 재실행할 수 있어야 하고(자기완결성),
> 그 재실행이 몇 번이든 안전하려면 **멱등 키**가 항목 안에 반드시 있어야 한다.
