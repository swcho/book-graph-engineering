# 되갚기가 실패하면 어떻게 하는가?

**답: 대기열에 적는다. 그건 우리 DB 안의 일이라 거기서 멈추므로 무한히 내려가지 않는다.**

## 질문의 배경 — 왜 이런 문제가 생기나

22장(22.3절)의 전제는 이렇습니다. 밖으로 나간 일(결제, 메일 발송, 외부 API 호출)은 롤백이 안 되므로, 각 정방향 단계에 **되갚는 동작(보상 트랜잭션, compensating transaction)** 을 짝지어 두고 실패하면 역순으로 실행합니다. 사가(saga) 패턴입니다.

그런데 여기서 자연스러운 다음 질문이 나옵니다(22.4절).

> 되갚기 자체가 실패하면? 예를 들어 결제는 됐는데 주문이 취소돼서 환불을 해야 하는데, **환불 API가 503을 돌려주면?**

이대로 두면 재귀적인 질문이 무한히 이어질 것 같습니다. "되갚기의 되갚기는? 그것도 실패하면 그것의 되갚기는?" — 이 하강이 어디서 멈추는지가 이 카드의 핵심입니다.

## 세 가지 대응의 비교 (ex4_undo_fails.py)

환불 API가 세 번째 호출까지 503을 돌려주는 상황에서:

| 대응 | 결과 | 문제 |
|---|---|---|
| 한 번 해 보고 포기 | 돈이 묶임 — 로그만 남음 | 로그는 아무도 안 본다. 사실상 유실 |
| 상한까지 재시도 (3회) | 돈이 묶임 — 재시도 소진 | 상한을 5로 올려도 "이번 장애 길이"에만 맞춘 숫자. 다음 장애가 10분이면 또 실패 |
| **재시도 + 되갚기 대기열** | 대기열 소비자가 나중에 다시 시도해 복구 | — |

세 번째 전략의 요점은 **상한을 안 늘리면서 포기하지도 않는다**는 것입니다. 3번 실패하면 되갚기 작업(작업 종류, 주문 번호, 금액, 시도 횟수, 멱등 키)을 대기열에 적어 두고 **지금 흐름은 끝냅니다**. 대기열 소비자가 나중에 다시 꺼내서 시도합니다.

## 핵심 통찰 — 왜 무한히 내려가지 않는가

"되갚기가 실패하면 되갚기의 되갚기가 필요한 것 아닌가?"라는 재귀 하강은 **한 층에서 끝납니다**. 이유는 실패 처리의 성격이 바뀌기 때문입니다.

- **되갚기(환불 호출)** 는 *바깥 세상*에 대한 동작입니다. 외부 API가 죽어 있으면 지금 당장은 성공시킬 방법이 없습니다.
- **"대기열에 적기"** 는 *우리 DB 안*의 동작입니다. 로컬 트랜잭션 한 번이면 되고, 우리 DB가 살아 있는 한 거의 실패하지 않습니다. 실패하더라도 그건 "외부 시스템 장애"가 아니라 "우리 시스템 전체 장애"라서 전혀 다른(그리고 이미 다른 층에서 다루는) 문제입니다.

즉 **신뢰할 수 없는 원격 호출을 신뢰할 수 있는 로컬 기록으로 바꿔치기**하는 순간 재귀가 멈춥니다. "지금 성공해야 하는 일"을 "언젠가 반드시 성공해야 하는 일"로 변환한 것이고, 그 둘은 설계가 다릅니다:

- 지금 성공해야 하는 일 → 타임아웃, 재시도 상한, 실패 시 즉시 처리
- 언젠가 반드시 성공해야 하는 일 → 내구성 있는 기록 + 별도 소비자가 계속 시도 (최종 일관성)

이 발상은 트랜잭셔널 아웃박스(transactional outbox) 패턴과 같은 뿌리입니다. "외부에 해야 할 일"을 외부에 직접 하는 대신 로컬 DB에 먼저 적고, 별도 프로세스가 그 기록을 보고 실제 실행을 책임집니다.

## 데드레터 큐로의 연결 (22.5절, ex5_dlq.py)

대기열에 적는 것으로 끝이 아닙니다. 쌓아 두는 곳(데드레터 큐, DLQ)에는 조건이 붙습니다.

1. **항목만 보고 재실행할 수 있어야 한다** — payload에 작업 종류, 대상(주문 번호), 금액 등 재실행에 필요한 전부를 담는다. 원래 요청 컨텍스트를 뒤져야 하면 실패한 설계.
2. **멱등 키를 반드시 넣는다** — 소비자가 재시도하다 중복 실행될 수 있으므로, 같은 환불이 두 번 나가지 않게 멱등 키로 막는다.
3. **실패 원인을 분류한다** — HTTP 상태 코드로 대부분 갈린다:
   - 429, 500, 502, 503, 504, 연결 오류 → **일시적** (재시도 가치 있음)
   - 400, 402, 404, 409, 422 → **영구적** (재시도 무의미, 호출 없이 바로 사람에게)
   - 그 밖 / 응답 없음 → **모름** (재시도 조금 더 주고 사람에게)
4. **누가 보는지가 정해져 있어야 한다** — "쌓이기만 하고 아무도 안 보는 큐는 로그와 똑같다." 알림은 늘리지 말고 줄여야 한다. 아무도 안 보는 알림은 없는 것과 같다.

## 한 줄 정리

되갚기 실패의 최종 방어선은 "더 센 재시도"가 아니라 **신뢰할 수 있는 로컬 기록(대기열)** 이다. 외부 세계의 불확실한 일을 우리 DB 안의 확실한 한 줄로 바꾸는 순간, "실패의 실패의 실패…"라는 무한 하강이 거기서 멈춘다. 남은 것은 그 기록을 반드시 소비하는 것 — 그래서 데드레터 큐에는 멱등 키, 원인 분류, 그리고 담당자가 필요하다.
