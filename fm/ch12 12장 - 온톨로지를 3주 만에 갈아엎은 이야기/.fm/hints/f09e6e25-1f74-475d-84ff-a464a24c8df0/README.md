# 스키마 없이 시작해도 되는 경우는 언제인가?

**답: 혼자 일할 때와 버릴 데이터일 때뿐이다.**

출처: 12장 「온톨로지를 3주 만에 갈아엎은 이야기」 — 12.3절 *스키마를 언제 못 박을 것인가*, 예제 `ex3_when_schema.py`

---

## 한 줄로

> 스키마 없이 시작해도 되는 건 혼자일 때와 버릴 데이터일 때뿐입니다.
> 그리고 문서만 있고 검사가 없는 게 제일 위험해요. 지키고 있다고 착각하게 됩니다.
> — 12장 한 장 요약

「스키마 없이 시작한다」는 선택은 **속도를 위해 미래의 나(또는 남)에게 빚을 지는 것**입니다.
그 빚을 갚지 않아도 되는 경우가 딱 두 가지입니다.

---

## 왜 이 두 가지뿐인가

두 조건은 각각 **스키마가 하는 일 하나씩**을 무력화합니다.

| 스키마의 역할 | 이 역할이 필요 없어지는 조건 |
|---|---|
| **사람 사이의 약속** — 「이 필드 이름이 뭐였죠?」를 없앤다 | **혼자 일할 때**. 규칙이 내 머릿속에만 있어도 어긋날 상대가 없다 |
| **시간을 건너는 계약** — 6개월 뒤에도 같은 뜻으로 읽히게 한다 | **버릴 데이터일 때**. 그 6개월이 오지 않는다 |

즉 스키마는 **여러 사람 × 긴 시간**이라는 두 축에서만 값을 합니다.
두 축이 모두 사라지면 스키마 유지 비용이 이득을 넘습니다.

거꾸로 말하면, **둘 중 하나라도 깨지는 순간 답은 「스키마를 둔다」로 바뀝니다.**

- 혼자 하던 프로토타입에 팀원이 한 명 붙었다 → 이제 약속이 필요하다
- 「일회용」이라고 만든 적재 스크립트의 결과를 누군가 대시보드에 물렸다 → 이제 버릴 데이터가 아니다

실무에서 사고가 나는 지점이 바로 여기입니다. 시작할 때는 두 조건을 만족했는데, **아무도 조건이 깨진 순간을 알려 주지 않기 때문**입니다.

---

## 위험 순위: 「문서만 있고 검사가 없는 것」이 최악

이 카드에서 놓치기 쉬운 두 번째 문장입니다. 상태는 셋이 아니라 넷입니다.

| 상태 | 실제 안전도 | 체감 안전도 | 문제 |
|---|---|---|---|
| 스키마 강제 (적재 시점) | 높음 | 높음 | 파이프라인이 멈출 수 있다 |
| 검증 (SHACL 등, 배치) | 중간 | 중간 | 어긋난 데이터가 잠시 들어와 있다 |
| **문서만 있고 검사 없음** | **낮음** | **높음** | **지키고 있다고 착각한다 — 최악** |
| 아무것도 없음 | 낮음 | 낮음 | 최소한 「모른다」는 걸 안다 |

「없음」은 정직하게 위험합니다. 「문서만 있음」은 **위험한데 안전해 보입니다.** 설계 문서에 필드 목록이 적혀 있으니 다들 지켜지고 있다고 믿지만, 아무도 검사하지 않으므로 실제 데이터는 조용히 갈라집니다(스키마 드리프트).

그래서 12.5절의 결론이 이어집니다 — **문서는 거짓말을 하고 데이터는 안 한다.** 문서만 두었다면 최소한 `ex5_schema_drift.py` 같은 감사 배치(30줄이면 충분)를 주기적으로 돌려 선언과 실제를 대조해야 합니다.

## 스키마를 「언제」 못 박을 것인가 — 세 방식의 차이는 「언제 아느냐」

`ex3_when_schema.py`는 같은 **잘못된 데이터**를 세 방식에 넣어 보고 언제 걸리는지 비교합니다.

```
BAD_ROWS = [
    ("등급이 규칙 밖", "가온테크", "Z"),   # 등급은 A/B/C 여야 하는데 Z
    ("이름이 비었다",   "",        "A"),   # name 이 빈 문자열
]
```

**방식 1 — 스키마 강제 (Kuzu 같은 타입 강제 엔진, 적재 시점)**

```python
conn.execute("CREATE NODE TABLE Company(name STRING, grade STRING, PRIMARY KEY(name))")
```

타입 위반은 즉시 거부합니다. 다만 **값의 범위**(등급이 A/B/C 중 하나여야 함)는 못 막습니다. 이 엔진에는 `CHECK` 제약이 없기 때문입니다 — 엔진마다 다릅니다.

**방식 2 — SHACL 검증 (적재는 되고, 나중에 보고서)**

```turtle
ex:CompanyShape a sh:NodeShape ;
    sh:targetClass ex:Company ;
    sh:property [ sh:path ex:name  ; sh:minCount 1 ; sh:minLength 1 ; sh:datatype xsd:string ] ;
    sh:property [ sh:path ex:grade ; sh:in ("A" "B" "C") ] .
```

`sh:in`으로 값 범위까지 잡습니다. 데이터는 이미 들어가 있고, `pyshacl.validate()`가 위반 보고서를 냅니다.

**방식 3 — 스키마 없음**

> 아무것도 안 걸린다. **6개월 뒤에 발견한다.**

정리하면:

| 방식 | 언제 아느냐 | 대가 |
|---|---|---|
| 적재 시점 | 즉시 | 적재가 실패하니 파이프라인이 멈춘다 |
| 검증 시점 | 배치가 돌 때 | 데이터는 들어가 있고 보고서로 안다 |
| 없음 | **사용자가 알려 준다** | — |

**저자 기준 한 줄:** 되돌릴 수 없는 것은 적재 시점에, 나머지는 검증 시점에.
적재를 너무 엄격하게 잡으면 데이터가 아예 안 들어와서 그것대로 문제가 됩니다.

## 함께 붙여 외우면 좋은 12장의 다른 규칙

- **온톨로지 = 도메인의 진리가 아니라, 지금 우리 질의가 필요로 하는 최소 어휘.** 위에서 아래로 지으면 끝나는 조건이 없고, 질의(역량 질문)에서 거꾸로 뽑으면 「질의가 돌면 끝」이 된다. (질문 다섯 개 → 어휘 10개 vs 전문가 분류 214개)
- **분류를 나누는 근거는 「다른 물건인가」가 아니라 「다른 속성을 갖는가」.** 종류가 많거나 자주 늘면 클래스 말고 속성으로.
- **공개 어휘는 적합도를 숫자로 매겨 판단.** 임계값 0.7 넘으면 재사용, 아니면 우리 것으로 만들고 `owl:sameAs` / `skos:closeMatch`로 이어 둔다.
- **문서는 거짓말을 하고 데이터는 안 한다.** 드리프트 감사를 배치로.

---

## 자주 하는 오답

- ❌ 「프로토타입이면 스키마 없이 시작해도 된다」 → 프로토타입이라도 **여럿이 붙었으면** 안 됩니다. 조건은 「단계」가 아니라 「혼자인가 / 버릴 것인가」입니다.
- ❌ 「데이터가 적으면 괜찮다」 → 양이 아니라 **수명과 공유 범위**의 문제입니다.
- ❌ 「설계 문서에 스키마를 적어 뒀으니 괜찮다」 → 검사 없는 문서는 **가장 위험한 상태**입니다.
