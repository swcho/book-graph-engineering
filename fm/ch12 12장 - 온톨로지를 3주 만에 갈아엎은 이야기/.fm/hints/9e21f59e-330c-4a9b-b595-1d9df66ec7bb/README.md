# 스키마 드리프트를 발견하는 방법

> **Q.** 스키마 드리프트를 발견하는 방법은 무엇인가?
> **A.** 문서 대신 데이터에게 물어본다. 드리프트 감사를 배치로 돌리면 되고 30줄이면 충분하다.

출처: 12장 「온톨로지를 3주 만에 갈아엎은 이야기」 12.5절 *문서 말고 데이터에게 물어보라*, 예제 `code/ex5_schema_drift.py`

---

## 1. 스키마 드리프트란

**선언한 스키마(설계 문서·모델 문서에 적힌 것)** 와 **실제 데이터에 나타나는 구조** 가 시간이 지나면서 벌어지는 현상입니다.

드리프트는 두 방향으로 생깁니다.

| 방향 | 증상 | 예 |
|---|---|---|
| **선언에 없는 키가 늘어난다** | 누군가 급해서 필드를 하나 얹고 문서를 안 고쳤다 | `legacy_code`, `temp_flag`, `recall_reason`, `note` |
| **선언한 키가 실제로는 없다** | 파이프라인이 바뀌면서 조용히 안 채워졌다 | `Part`에 `category`가 빠진 행, `Product`에 `released_on`이 빠진 행 |

핵심 문장은 이겁니다.

> **문서는 거짓말을 한다. 데이터는 안 한다.**

문서는 사람이 손으로 갱신해야 하니 반드시 뒤처집니다. 반대로 데이터는 실제로 무슨 일이 일어났는지를 그대로 들고 있습니다. 그래서 "우리 스키마가 어떻게 생겼나"를 알고 싶으면 문서를 열어 볼 게 아니라 **데이터를 스캔해서 실제 키 분포를 세면** 됩니다.

## 2. 왜 "문서 + 검사 없음"이 제일 위험한가

12장 요약에 이런 줄이 있습니다.

> 스키마 없이 시작해도 되는 건 혼자일 때와 버릴 데이터일 때뿐입니다. 그리고 **문서만 있고 검사가 없는 게 제일 위험해요. 지키고 있다고 착각하게 됩니다.**

- 스키마가 아예 없으면 → 아무도 믿지 않으니 매번 확인합니다. 불편하지만 착각은 없습니다.
- 문서만 있고 검사가 없으면 → 다들 문서를 믿고 질의를 짭니다. 그런데 데이터가 문서와 다르면 질의는 **에러를 내지 않고 조용히 빈 결과**를 냅니다. 이게 제일 나쁩니다.

그래서 드리프트 감사는 "문서를 잘 쓰자"의 문제가 아니라 **"문서와 데이터가 아직 같은지 기계로 확인하자"** 의 문제입니다.

## 3. 30줄이면 되는 감사 로직

예제 `ex5_schema_drift.py`의 뼈대입니다. 의존성 하나 없이 표준 라이브러리 `Counter`, `defaultdict`만 씁니다.

```python
# 설계 문서에 적힌 스키마
DECLARED = {
    "Part":     {"id", "name", "category"},
    "Product":  {"id", "name", "released_on"},
    "Supplier": {"id", "name"},
}

def audit(declared, rows):
    seen = defaultdict(Counter)   # 라벨 → 키 → 등장 횟수
    counts = Counter()            # 라벨 → 전체 건수
    for label, keys in rows:
        counts[label] += 1
        for k in keys:
            seen[label][k] += 1

    report = {}
    for label, want in declared.items():
        got, n = seen[label], counts[label]
        extra   = {k: v for k, v in got.items() if k not in want}          # 문서에 없는 키
        missing = {k: n - got.get(k, 0) for k in want if got.get(k, 0) < n}  # 빠진 키
        report[label] = {"건수": n, "선언에 없는 키": extra, "빠진 키": missing}
    return report
```

알고리즘은 딱 두 개의 집합 연산입니다.

1. `실제 키 − 선언 키` = **`+` (문서에 없는 키)**
2. `선언 키 − 실제 키` = **`−` (누락된 키)** — 단순히 있냐 없냐가 아니라 **몇 건에서 빠졌는지**를 셉니다. `n - got.get(k, 0)`이 그 계산입니다.

출력은 이런 모양이 됩니다.

```
[Part]  5건
    + legacy_code    2건 — 문서에 없다
    + temp_flag      1건 — 문서에 없다
    + note           1건 — 문서에 없다
    - category       1건에서 누락
```

**"30줄이면 충분하다"** 의 뜻은 정교한 도구가 필요 없다는 겁니다. 그래프 DB든 문서 DB든 JSON 로그든, 레코드마다 (라벨, 키 집합)만 뽑아낼 수 있으면 위 함수가 그대로 돌아갑니다.

## 4. 감사 결과를 어떻게 처리하나

### `+` 표시 — 선언에 없는 키

셋 중 하나로 **반드시 결론을 냅니다.** 그대로 두면 다음 주에 또 같은 줄이 뜹니다.

1. **정식으로 스키마에 넣는다** — `recall_reason`처럼 실제로 필요해서 생긴 것. 문서를 고쳐 현실을 따라갑니다.
2. **지운다** — `temp_flag`처럼 임시로 넣고 잊은 것.
3. **별도 영역으로 옮긴다** — `legacy_code`처럼 이전 시스템 잔재. 지울 수는 없지만 본 스키마에서는 분리합니다.

### `−` 표시 — 빠진 키

**이쪽이 더 급합니다.** 선언상 필수인 키가 실제로는 없다는 뜻이고, 그 위에서 도는 질의가 **조용히 빈 결과**를 내고 있을 가능성이 높습니다. 에러가 안 나니 아무도 모른 채 리포트 숫자만 틀립니다.

## 5. 왜 "배치"인가 — 검사 시점의 선택

12.3절(예제 `ex3_when_schema.py`)이 정리한 세 가지 시점과 이어집니다.

| 방식 | 언제 아는가 | 대가 |
|---|---|---|
| 적재 시점 강제 (타입 있는 그래프 DB 등) | 즉시 | 적재가 실패해 파이프라인이 멈춤 |
| 검증 시점 (SHACL 등 배치 검증) | 배치가 돌 때 | 데이터는 이미 들어가 있음, 보고서로 확인 |
| 없음 | 사용자가 알려 줄 때 | 6개월 뒤에 발견 |

책의 기준은 **"되돌릴 수 없는 것은 적재 시점에, 나머지는 검증 시점에"** 입니다. 적재를 너무 엄격하게 잡으면 데이터가 아예 안 들어와서 그것대로 문제가 됩니다.

드리프트 감사는 **검증 시점** 쪽 도구입니다. 데이터가 들어오는 것을 막지 않으면서, **주 1회 배치**로 돌려 "쌓이기 전에" 보이게 합니다. 드리프트는 사건이 아니라 축적이라서, 발견 주기가 곧 최대 피해 크기입니다.

## 6. 실제 엔진에서 (라벨, 키 집합) 뽑기

예제는 `ACTUAL_ROWS` 상수로 데이터를 흉내 냈지만, 실무에서는 엔진에 물어봅니다.

**RDF / SPARQL** — 클래스별 실제 술어 분포:

```sparql
SELECT ?cls ?p (COUNT(*) AS ?n)
WHERE { ?s a ?cls ; ?p ?o . }
GROUP BY ?cls ?p
ORDER BY ?cls DESC(?n)
```

**Neo4j** — 실제 데이터에서 관측된 라벨·속성 목록:

```cypher
CALL db.schema.nodeTypeProperties()
```

**Kuzu처럼 스키마가 강제되는 엔진** — 선언 자체는 `CALL show_tables()` / `CALL table_info('Part')`로 볼 수 있습니다. 다만 이런 엔진에서는 *키의 유무*는 이미 막히므로, 드리프트는 "선언에 없는 키"보다 **선언은 있는데 값이 전부 NULL/빈 문자열인 컬럼** 쪽으로 나타납니다. 감사 대상을 키 존재 여부 대신 **비어 있지 않은 값의 비율**로 바꿔서 같은 로직을 돌리면 됩니다.

값의 *범위*까지 보고 싶으면(등급이 A/B/C 중 하나인지 등) SHACL 같은 형태 제약 언어를 같이 씁니다. 12.3절 예제가 보여 주듯, 타입 강제만으로는 값의 범위를 못 막습니다.

## 7. 한 줄 정리

**스키마 드리프트는 문서를 읽어서 찾을 수 없습니다.** 문서는 드리프트의 한쪽 당사자니까요. 데이터를 스캔해 실제 키 분포를 세고, 선언과의 차집합 두 개(`+`, `−`)를 뽑아, 그걸 주기적인 배치로 돌리는 것 — 이게 전부이고 30줄이면 됩니다.
