# 214개 중 204개가 필요 없던 이유

## 카드

**질문** — 도메인 전문가가 제시한 214개 분류 중 대부분이 필요 없던 이유는 무엇인가?

**답** — 204개는 정확한 분류였지만 답하려는 질문에 필요가 없었다. 'M6스테인리스육각볼트'는 틀린 분류가 아니라 지금 필요 없는 분류다.

---

## 핵심 한 줄

**틀렸느냐가 아니라 쓰이느냐가 기준이다.**

온톨로지 리뷰에서 사람들이 습관적으로 던지는 질문은 「이 분류가 맞나?」입니다. 전문가가 만든 214개 분류는 이 질문에 전부 통과합니다. 볼트는 실제로 체결부품이고, 육각볼트는 실제로 볼트의 하위 종류이며, M6스테인리스육각볼트는 실제로 존재하는 규격입니다. 도메인적으로 하나도 틀린 게 없습니다.

문제는 질문 자체가 틀렸다는 겁니다. 물어야 할 것은 「이 분류가 맞나」가 아니라 **「이 분류가 없으면 못 답하는 질의가 있나」**입니다. 이 기준으로 다시 재면 204개가 탈락합니다.

---

## 어떻게 10개가 나왔나 — 역량 질문에서 거꾸로

12.1절의 방법은 위에서 아래로 분류 체계를 짓는 대신, 답해야 할 질문(역량 질문, competency question) 다섯 개를 먼저 적고 거기서 낱말을 뽑는 것입니다.

`code/questions.py`에 그 다섯 문장이 그대로 있습니다.

```python
QUESTIONS = [
    "부품 X 를 쓴 제품 중 리콜된 것은?",
    "공급사 A 가 납품한 부품이 들어간 제품은?",
    "리콜 사유가 «과열»인 제품에 공통으로 들어간 부품은?",
    "부품 X 의 대체 부품은 무엇이고, 언제부터 대체 가능한가?",
    "제품 P 의 부품 목록을 3단계까지 펼치면?",
]
```

여기에 밑줄을 긋고 뽑아낸 어휘가 전부입니다.

```python
VOCAB_FROM_QUESTIONS = {
    "클래스": ["부품", "제품", "공급사", "리콜"],
    "관계": ["사용한다", "납품한다", "리콜되었다", "대체가능하다"],
    "속성": ["이름", "사유", "유효시작일"],
}
```

클래스 4 + 관계 4 + 속성 3 = **11개**. 214개가 아니라 열 개 남짓입니다. 다섯 질문 어디에도 「M6」도 「스테인리스」도 「N채널MOSFET」도 나오지 않습니다. 나오지 않는 낱말은 어휘에 넣을 근거가 없습니다.

| | 위에서 아래로 (전문가 방식) | 질의에서 거꾸로 |
|---|---|---|
| 출발점 | 도메인 전체를 빠짐없이 기술 | 답해야 할 질문 N개 |
| 크기 결정 | 도메인의 크기가 결정 | 질문의 개수가 결정 |
| 끝나는 조건 | **없음** (항상 더 세분화할 수 있음) | 「질의가 돌면 끝」 |
| 탈락 기준 | 「틀렸다」 | 「지금 안 쓰인다」 |

「끝나는 조건이 없다」가 4장에서 6개월짜리 온톨로지가 아무에게도 안 쓰인 이유이기도 합니다. 완성 판정을 내려 줄 사람이 없으니 계속 자랍니다.

## 「틀린 분류」와 「지금 필요 없는 분류」를 갈라야 하는 이유

이 구분이 없으면 대화가 이렇게 흘러갑니다.

> 「M6스테인리스육각볼트를 빼자」
> 「왜? 실제로 그런 부품이 있는데?」
> 「…맞긴 하죠」 → 남는다

전문가는 정확성을 방어하고, 그건 이길 수 없는 방어입니다. 실제로 정확하니까요. 그래서 논점을 **정확성에서 비용으로** 옮겨야 합니다. `ex1_vocab_from_questions.py`의 마지막 출력이 정확히 그 문장입니다.

```
«M6스테인리스육각볼트» 는 틀린 분류가 아니다. 정확한 분류다.
다만 이 다섯 질문에 답하는 데는 필요가 없다.

필요해지는 순간이 오면 그때 넣으면 된다.
그때 넣는 비용보다, 안 쓰는 분류 190개를 유지하는 비용이 크다.

온톨로지는 도메인의 진리가 아니라 «지금 우리 질의가 필요로 하는 최소 어휘»다.
```

즉 삭제가 아니라 **연기**입니다. 「틀렸으니 버린다」가 아니라 「필요해질 때 넣는다」. 전문가의 지식을 부정하지 않으면서 지금의 스키마에서만 빼는 방식이라, 실무에서 합의를 얻기가 훨씬 쉽습니다.

> 참고: 본문은 다섯 질문에서 뽑히지 않은 것을 204개(214 − 10)로 셉니다. 예제 코드의 「190개」는 그중 최종적으로 폐기하기로 한 몫을 가리키는 수치로, 둘 다 「대부분이 안 쓰인다」는 같은 이야기입니다. 카드에서 답할 숫자는 **204**입니다.

## 안 쓰는 분류를 유지하는 비용이 왜 큰가

「어차피 안 쓰는 건데 그냥 두면 안 되나」에 대한 답이 12.2절(`ex2_deep_vs_flat.py`)입니다. 안 쓰는 분류는 가만히 있지 않고 계속 비용을 청구합니다.

깊은 분류(A안)는 종류마다 노드 테이블과 관계 테이블을 따로 만듭니다. 그래서 「제품 P1이 쓰는 부품 전부」라는 아주 단순한 질의가 이렇게 됩니다.

```cypher
MATCH (p:Product {id:'P1'})-[:UsesBolt]->(x:Bolt)      RETURN x.name AS 부품
UNION
MATCH (p:Product {id:'P1'})-[:UsesNut]->(x:Nut)        RETURN x.name AS 부품
UNION
MATCH (p:Product {id:'P1'})-[:UsesResistor]->(x:Resistor) RETURN x.name AS 부품
UNION
MATCH (p:Product {id:'P1'})-[:UsesCapacitor]->(x:Capacitor) RETURN x.name AS 부품
```

얕은 분류(B안)는 한 줄입니다.

```cypher
MATCH (p:Product {id:'P1'})-[:Uses]->(x:Part) RETURN x.name AS 부품
```

| 항목 | A안 (깊게) | B안 (얕게) |
|---|---:|---:|
| 노드 테이블 수 | 5 | 2 |
| 관계 테이블 수 | 4 | 1 |
| 질의문 줄 수 | 8 | 1 |
| **부품 종류 추가 시 고칠 곳** | **3** | **0** |

마지막 줄이 핵심입니다. A안에서 「와셔」를 추가하려면 노드 테이블 하나, 관계 테이블 하나, 그리고 기존 「부품 전부」 질의마다 UNION 한 줄씩을 더 넣어야 합니다. B안에서는 행 하나를 넣으면 끝입니다. 214개짜리 분류 체계는 이 유지 비용을 214갈래로 곱해 놓은 상태입니다.

## 다만 「얕게가 항상 옳다」는 아니다

여기서 오해하기 쉬운데, 12.2절이 말하는 건 「깊은 분류는 나쁘다」가 아닙니다.

> **분류를 나누는 기준은 「다른 속성을 갖는가」이지 「다른 물건인가」가 아니다.**

볼트에만 있는 속성(나사산 규격, 인장 강도 같은 것)이 여러 개이고 실제로 그걸로 질의한다면, 볼트를 별도 클래스로 두는 A안이 맞습니다. 반대로 이름과 카테고리만 있고 나머지가 똑같다면 종류가 아무리 많아도 클래스가 아니라 `category` 속성으로 두는 게 맞습니다.

214개 분류가 문제였던 건 깊어서가 아니라, **그 깊이가 질의에도 속성 차이에도 근거가 없었기** 때문입니다. 근거는 오직 「도메인에 그런 구분이 존재한다」였습니다.

## 예상 반문과 답

**「나중에 질문이 늘어나면 어떡하나?」**
그때 넣습니다. 어휘를 나중에 추가하는 비용은 유한하고 국소적이지만, 안 쓰는 분류 204개를 계속 유지·문서화·검증·마이그레이션하는 비용은 매 변경마다 반복됩니다.

**「전문가의 지식을 버리는 거 아닌가?」**
버리는 게 아니라 지금 스키마에 싣지 않을 뿐입니다. 214개 목록 자체는 남겨 두고, 필요해질 때 꺼내 쓰는 후보 목록으로 둡니다.

**「그럼 어디까지가 완성인가?」**
「질의가 돌면 끝」입니다. 이게 위에서 아래로 짓는 방식에 없던 유일한 것이고, 4장의 6개월과 이 장의 3주를 가르는 지점입니다.

## 한 문장 정리

214개는 전부 옳았지만 그중 204개는 다섯 개의 역량 질문 어디에도 등장하지 않았고, 등장하지 않는 분류는 「틀린 분류」가 아니라 「**지금 비용만 발생시키는 분류**」이므로 필요해지는 순간까지 미룬 것입니다.

## 곁가지 — 이 장의 나머지 절

- **12.3 스키마를 언제 못 박을 것인가**: 적재 시점(즉시 거부) / 검증 시점(SHACL 보고서) / 없음(사용자가 알려 줌)의 차이는 「언제 아느냐」다. 되돌릴 수 없는 것은 적재 시점에, 나머지는 검증 시점에.
- **12.4 남의 어휘를 가져다 쓸까**: 적합도를 숫자로 매겨 0.7 이상이면 재사용, 아니면 우리 것으로 만들고 `owl:sameAs` / `skos:closeMatch`로 이어 둔다.
- **12.5 문서 말고 데이터에게**: 선언된 스키마와 실제 키를 비교하는 드리프트 감사를 배치로 돌린다. 문서는 거짓말을 하고 데이터는 안 한다.
