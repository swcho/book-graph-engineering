# 안 쓰는 분류를 「유지하는 비용」 vs 「나중에 넣는 비용」

**질문** — 안 쓰는 분류를 유지하는 비용과 나중에 넣는 비용은 어느 쪽이 큰가?

**답** — 안 쓰는 분류 190개를 유지하는 비용이 더 크다. 필요해지는 순간에 넣으면 된다.

---

## 1. 원문이 말하는 것

12장 예제 1(`code/ex1_vocab_from_questions.py`)의 마지막 출력이 이 카드의 원문입니다.

> «M6스테인리스육각볼트» 는 틀린 분류가 아니다. 정확한 분류다.
> 다만 이 다섯 질문에 답하는 데는 필요가 없다.
>
> 필요해지는 순간이 오면 그때 넣으면 된다.
> **그때 넣는 비용보다, 안 쓰는 분류 190개를 유지하는 비용이 크다.**
>
> 온톨로지는 도메인의 진리가 아니라 «지금 우리 질의가 필요로 하는 최소 어휘»다.

핵심은 「틀렸으니 빼라」가 **아니라는** 점입니다. `M6스테인리스육각볼트`는 도메인상 완벽히 정확한 분류입니다. 그런데도 빼라고 하는 이유는 **정확성이 아니라 비용** 때문입니다. 판단 축이 「맞나 틀리나」에서 「비용을 내고 있나」로 옮겨간 것이 이 카드의 전부입니다.

### 숫자의 출처

| 숫자 | 어디서 나왔나 |
|---|---|
| 214개 | 도메인 전문가가 처음 제시한 클래스 수 (`EXPERT_TAXONOMY` 주석) |
| 10개쯤 | 역량 질문 5개에서 밑줄 그어 뽑은 어휘 (`VOCAB_FROM_QUESTIONS` — 클래스 4 + 관계 4 + 속성 3) |
| 204개 / 190개 | 나머지, 즉 다섯 질문에 답하는 데 **쓰이지 않는** 분류 |

> 참고: 장 도입부는 「나머지 204개」, 예제 출력 문구는 「190개」로 적혀 있습니다. 세는 기준(관계·속성 포함 여부, `EXPERT_TAXONOMY`가 214개 중 일부만 나열한 샘플이라는 점)이 달라 생긴 차이이고, 카드가 말하는 바는 동일합니다 — **쓰지 않는 분류가 200개 안팎**이라는 규모감입니다. 시험 문제처럼 숫자를 외울 필요는 없고, 「10개 쓰려고 214개를 짊어지고 있었다」는 비율을 기억하면 됩니다.

---

## 2. 유지 비용은 구체적으로 어디서 나가는가

「안 쓰는 클래스는 그냥 거기 가만히 있는 것 아닌가」가 흔한 반문입니다. 아닙니다. 스키마에 선언된 분류는 **다음 여섯 군데에 계속 세금을 매깁니다.**

### (1) 적재 코드 — 매번 「어디에 넣지?」를 판정해야 한다

분류가 214개면 들어오는 원천 데이터 한 줄마다 214갈래 중 하나를 골라야 합니다. 그 판정 로직(문자열 규칙, 매핑 표, 분류기)이 코드에 눌러앉고, 원천 시스템이 바뀔 때마다 같이 흔들립니다. 더 나쁜 건 **경계가 애매한 항목**입니다. `스테인리스육각볼트`인가 `M6스테인리스육각볼트`인가는 원천 데이터에 답이 없을 때가 많고, 그럴 때마다 사람이 판단합니다. 판단이 사람마다 다르면 같은 물건이 두 클래스에 흩어져 앉습니다.

### (2) 질의문 — 분류가 깊을수록 질의가 길어지고, 조용히 틀린다

예제 2(`code/ex2_deep_vs_flat.py`)가 이걸 실측합니다. 「제품 P1이 쓰는 부품 전부」라는 **같은 질문**을 두 설계로 풀어 본 결과입니다.

| 항목 | A안 (깊은 분류) | B안 (얕은 분류) |
|---|---:|---:|
| 노드 테이블 수 | 5 | 2 |
| 관계 테이블 수 | 4 | 1 |
| 질의문 줄 수 | 8 | 1 |
| **부품 종류 추가 시 고칠 곳** | **3** | **0** |

A안에서는 부품 종류마다 `UNION` 한 줄이 붙습니다.

```cypher
MATCH (p:Product {id:'P1'})-[:UsesBolt]->(x:Bolt)           RETURN x.name AS 부품
UNION
MATCH (p:Product {id:'P1'})-[:UsesNut]->(x:Nut)             RETURN x.name AS 부품
UNION
MATCH (p:Product {id:'P1'})-[:UsesResistor]->(x:Resistor)   RETURN x.name AS 부품
UNION
MATCH (p:Product {id:'P1'})-[:UsesCapacitor]->(x:Capacitor) RETURN x.name AS 부품
```

B안은 한 줄입니다.

```cypher
MATCH (p:Product {id:'P1'})-[:Uses]->(x:Part) RETURN x.name AS 부품
```

여기서 진짜 비용은 줄 수가 아니라 **누락이 에러를 내지 않는다**는 점입니다. `UsesWasher`를 빠뜨린 A안 질의는 예외를 던지지 않고 그냥 와셔가 빠진 결과를 돌려줍니다. 분류가 214개면 「전부」를 묻는 모든 질의가 214갈래를 빠짐없이 열거해야 하고, 하나 빠지면 **조용한 오답**이 됩니다. 이건 안 쓰는 분류가 만드는 비용 중 가장 비쌉니다. 틀린 걸 아무도 모르니까요.

### (3) 문서 — 214개 항목이 설계 문서에 살고, 늙는다

각 클래스에는 정의문, 상위/하위 관계, 예시가 붙습니다. 실제로 쓰이지 않는 190여 개는 **아무도 읽지 않으면서 아무도 지우지 못하는** 상태로 남습니다. 지우려면 「정말 안 쓰나」를 확인해야 하는데, 확인 비용이 방치 비용보다 커 보이니 계속 방치됩니다. 이 눈덩이가 4장에서 6개월짜리 온톨로지가 아무에게도 안 쓰인 이유이기도 합니다.

### (4) 교육/온보딩 — 새 사람이 들어올 때마다 214개를 설명한다

신규 인원은 「우리 도메인 모델」을 익혀야 하는데, 그 모델의 90% 이상이 실제 질의에 등장하지 않습니다. 학습 시간이 늘어날 뿐 아니라, **어휘가 클수록 사람마다 다르게 이해합니다.** 10개짜리 어휘는 회의에서 한 번에 합의되지만 214개짜리는 합의된 적이 없습니다. 그리고 이 비용은 일회성이 아니라 **인원이 바뀔 때마다 반복**됩니다.

### (5) 검증 — 제약도 클래스 수만큼 늘어난다

예제 3(`code/ex3_when_schema.py`)이 보여주듯 스키마는 선언만으로 끝나지 않고 **검사가 따라붙어야 의미가 있습니다.** SHACL이라면 클래스마다 `sh:NodeShape`가 하나씩 필요합니다.

```turtle
ex:CompanyShape a sh:NodeShape ;
    sh:targetClass ex:Company ;
    sh:property [ sh:path ex:name ; sh:minCount 1 ; sh:minLength 1 ] ;
    sh:property [ sh:path ex:grade ; sh:in ("A" "B" "C") ] .
```

이런 shape을 214개 유지하면 검증 배치 시간도, shape 자체의 유지보수도 214배 방향으로 갑니다. 반대로 shape을 안 쓰는 클래스에는 안 붙이면 어떻게 되냐면 — 12장이 「제일 위험하다」고 지목한 상태가 됩니다. **문서만 있고 검사가 없는 스키마.** 지키고 있다고 착각하게 되니까요.

### (6) 드리프트 감사 — 감사 표면적이 선언 크기에 비례한다

예제 5(`code/ex5_schema_drift.py`)의 감사는 `DECLARED`(문서에 적힌 스키마)와 실제 데이터를 대조합니다.

```python
for label, want in declared.items():
    got = seen[label]
    extra   = {k: v for k, v in got.items() if k not in want}
    missing = {k: n - got.get(k, 0) for k in want if got.get(k, 0) < n}
```

`declared`가 커질수록 감사 대상이 커지고, **실제 데이터가 0건인 클래스들이 리포트를 채웁니다.** 매주 돌리는 리포트에 「어차피 아무도 안 쓰는 항목」이 섞이기 시작하면 사람은 리포트 자체를 안 보게 됩니다. 안 쓰는 분류는 감사의 신호 대 잡음비를 깎아서, 진짜 드리프트까지 같이 묻어버립니다.

### 유지 비용의 성질: 재고 비용이다

여섯 항목을 관통하는 성질은 **반복성**입니다.

- 스키마를 한 번 바꿀 때마다 → 안 쓰는 클래스도 같이 마이그레이션 대상
- 「전부」 질의를 하나 쓸 때마다 → 열거 누락 위험
- 사람이 한 명 들어올 때마다 → 설명 비용
- 감사를 한 번 돌릴 때마다 → 잡음

즉 **한 번 내고 끝나는 값이 아니라 매 주기마다 다시 나가는 값**입니다. 안 쓰는 분류 190개는 자산이 아니라 **창고에 쌓인 재고**이고, 재고에는 보관료가 붙습니다.

## 3. 「나중에 넣는」 비용은 왜 작은가

### (1) 얕은 설계에서는 추가가 행 하나다

예제 2의 마지막 줄이 정확히 이 지점입니다.

> A안에서 «와셔»를 추가하려면 노드 테이블 하나, 관계 테이블 하나,
> 그리고 «부품 전부» 질의에 UNION 한 줄을 더 넣어야 한다.
> **B안에서는 행 하나를 넣으면 끝난다.**

「부품 종류 추가 시 고칠 곳: A안 3, B안 0」이라는 측정값이 「나중에 넣는 비용」의 실제 크기입니다. 질의에서 뽑은 최소 어휘로 시작하면 대개 B안 모양이 되고, 그때 추가 비용은 **스키마 변경이 아니라 데이터 입력**으로 내려옵니다.

### (2) 그때는 「추측」이 아니라 「실제 질의」가 설계를 정해 준다

지금 넣는 190개는 **아직 존재하지 않는 질문을 상상해서** 만든 것입니다. 상상으로 만든 분류는 정작 질문이 도착했을 때 안 맞을 확률이 높고, 그러면 **유지 비용은 다 내고 재작업까지 하게 됩니다.** 반대로 필요해진 순간에 넣으면 요구가 구체적입니다 — 어떤 질의가, 어떤 속성으로 필터하는지가 이미 손에 있습니다.

그래서 12장의 분할 기준이 「다른 물건인가」가 아니라 **「다른 속성을 갖는가」**인 겁니다. 나사산 규격처럼 볼트에만 있는 속성이 생기고 그걸로 질의하게 된 시점에 `Bolt`를 쪼개면, 그 쪼갬은 근거가 있습니다. 그 시점 전에 쪼개면 근거 없이 비용만 냅니다.

### (3) 끝나는 조건이 생긴다

위에서 아래로 지으면 **언제 끝났는지 알 방법이 없습니다.** 214개가 맞는지 500개가 맞는지 판정할 기준이 없으니까요. 질의에서 거꾸로 뽑으면 종료 조건이 「질의가 돌면 끝」로 명확해집니다. 「나중에 넣는다」는 게으름이 아니라 **결정을 근거가 생기는 시점까지 미루는 것**이고, 소프트웨어 쪽 용어로는 YAGNI(You Aren't Gonna Need It)와 「가장 늦게 책임질 수 있는 순간(last responsible moment)에 결정하기」에 해당합니다.

### (4) 미룬다고 정보가 사라지지 않는다

214개짜리 분류표는 지운다고 소멸하지 않습니다. 도메인 전문가의 머릿속과 회의록에 그대로 있습니다. 필요해지면 다시 꺼내면 됩니다. **없앨 수 없는 지식을 스키마에 박아두는 대가로 유지비를 내고 있을 뿐**입니다.

## 4. 언제 이 판단이 뒤집히는가 (그냥 외우면 안 되는 부분)

「나중에 넣으면 된다」가 **항상** 옳은 건 아닙니다. 12장 자체가 반대 방향의 기준도 같이 줍니다.

- **되돌릴 수 없는 것은 미루면 안 된다.** 예제 3의 결론이 「되돌릴 수 없는 것은 적재 시점에, 나머지는 검증 시점에」입니다. 식별자 체계, 병합해 버리면 복원 불가능한 구분 같은 건 나중에 넣는 비용이 폭증합니다. 볼트와 너트를 한 테이블에 합치는 건 되돌릴 수 있지만(속성으로 구분값을 남겼다면), 애초에 구분 정보를 **버리고 적재했다면** 되돌릴 수 없습니다. → **분류는 미뤄도, 원천 정보는 버리지 마라.**
- **이미 쌓인 데이터에 소급해야 한다면** 나중에 넣기가 비쌉니다. 새 분류를 도입하면서 과거 100만 행을 재분류해야 하는 경우입니다. 다만 이 비용도 얕은 설계에서는 「행의 `category` 값 업데이트」지, 깊은 설계에서는 「테이블 간 데이터 이동 + 관계 재생성」이라 여전히 얕은 쪽이 유리합니다.
- **속성이 실제로 갈린다면** 쪼개는 게 맞습니다. 예제 2가 A안을 무조건 나쁘다고 하지 않는 이유입니다. 「볼트에만 있는 속성이 많고 그걸로 질의한다면 A안이 맞다.」

## 5. 실무 체크리스트

새 클래스를 스키마에 넣자는 제안이 왔을 때 순서대로 물어보면 됩니다.

1. **이 분류를 쓰는 역량 질문이 지금 있나?** 없으면 보류.
2. **이 분류만 갖는 속성이 있나?** 없으면 클래스가 아니라 속성(`category` 같은) 값으로.
3. **종류가 앞으로 자주 늘 것 같나?** 늘 것 같으면 클래스로 두지 말 것. 늘 때마다 스키마·질의·검증을 고쳐야 하니까.
4. **넣는다면 검사(SHACL shape, 제약, 감사 규칙)도 같이 넣을 수 있나?** 못 넣으면 문서만 있고 검사 없는 상태 — 12장이 제일 위험하다고 한 그 상태.
5. **지금 안 넣으면 정보가 영구히 소실되나?** 소실된다면 지금 넣거나, 최소한 원천값을 남겨둘 것.

---

## 6. 한 줄로 압축

> 안 쓰는 분류는 **틀려서** 빼는 게 아니라 **보관료가 붙어서** 뺀다. 190개의 보관료는 적재 코드·질의문·문서·교육·검증·감사에서 매 주기 반복해서 나가고, 필요해진 순간에 넣는 비용은 (얕은 설계라면) 행 하나다.
