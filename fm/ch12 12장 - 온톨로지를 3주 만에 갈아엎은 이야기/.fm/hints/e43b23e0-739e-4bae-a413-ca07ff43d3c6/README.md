# 드리프트 감사에서 `-` 표시가 더 급한 이유

**질문** — 드리프트 감사에서 `-` 표시가 더 급한 이유는 무엇인가?

**답** — 선언한 필수 키가 실제로 없다는 뜻이며, 질의가 조용히 빈 결과를 내고 있을 가능성이 높다.

---

## 1. 드리프트 감사가 뭘 하는 물건인가

12.5절 「문서 말고 데이터에게 물어보라」의 예제 `code/ex5_schema_drift.py`는 30줄짜리 배치입니다. 하는 일은 딱 두 가지 집합을 비교하는 것뿐입니다.

- `DECLARED` — 설계 문서에 적힌 스키마. 사람이 쓴 것, 즉 **주장**.
- `ACTUAL_ROWS` — 운영 6개월 뒤 실제 데이터에 나타난 키. 파이프라인이 만든 것, 즉 **사실**.

```python
DECLARED = {
    "Part":    {"id", "name", "category"},
    "Product": {"id", "name", "released_on"},
    "Supplier":{"id", "name"},
}
```

`audit()`은 라벨별로 두 종류의 차이를 뽑습니다.

| 표시 | 코드상 이름 | 뜻 |
|---|---|---|
| `+` | `선언에 없는 키` (`extra`) | 문서에 없는데 데이터에는 있다 |
| `-` | `빠진 키` (`missing`) | 문서에 있는데 데이터의 일부/전부에 없다 |

`missing` 계산식이 이 카드의 핵심입니다.

```python
missing = {k: n - got.get(k, 0) for k in want if got.get(k, 0) < n}
```

`want`(선언된 키) 중에서 **전체 건수 `n`보다 적게 나타난 키**를 세고, 몇 건에서 빠졌는지까지 셉니다. 예제 데이터로 돌리면 `Part`는 5건 중 1건에서 `category`가 없고, `Product`는 3건 중 1건에서 `released_on`이 없습니다. 즉 "전부 없음"이 아니라 **일부만 없음**이 잡히는데, 뒤에서 볼 이유로 이 부분 누락이 오히려 더 고약합니다.

---

## 2. 왜 `-`가 더 급한가 — 조용한 실패(silent failure)

### 그래프 질의에서 누락 속성은 예외가 아니다

관계형 DB에서 없는 컬럼을 참조하면 SQL은 즉시 에러를 던집니다. `column "category" does not exist`. 파이프라인이 멈추고, 알림이 오고, 누군가 고칩니다. **시끄러운 실패(loud failure)**입니다.

그래프 질의는 다릅니다. Cypher/GQL의 `MATCH`나 SPARQL의 기본 패턴은 본질적으로 **패턴 매칭**입니다. 속성이 없는 노드는 "오류가 있는 노드"가 아니라 그냥 "패턴에 안 맞는 노드"입니다.

```cypher
MATCH (p:Part) WHERE p.category = '체결류' RETURN p
```

`category` 속성이 없는 노드에서 `p.category`는 `null`로 평가되고, `null = '체결류'`는 참이 아니므로 그 노드는 결과에서 **조용히 빠집니다**. SPARQL도 마찬가지로 `?part ex:category ?c .` 라는 트리플 패턴에 매칭되는 트리플이 없으면 해(solution)가 하나 줄어들 뿐, 경고 한 줄 나오지 않습니다. LPG든 RDF든 스키마리스 성향의 엔진일수록 이 성질이 강합니다.

즉 `-` 표시가 뜻하는 상황은 이렇습니다.

> 질의는 성공한다. 200 OK가 나간다. 로그는 깨끗하다. 그런데 답이 틀렸다.

### 왜 이게 오류보다 위험한가

1. **탐지 지연이 길다.** 오류는 발생 시점에 알려집니다. 조용한 실패는 "결과가 좀 적네" 하는 위화감을 누군가 느끼기 전까지 무한정 갑니다. 12.3절 예제 3의 마지막 정리 그대로 "없음 — 사용자가 알려 준다"입니다. 6개월 뒤에 발견합니다.
2. **오염이 하류로 번진다.** 빈/부분 결과가 리포트, 대시보드, 재고 계산, 추천, LLM 컨텍스트로 흘러갑니다. 에러였다면 아무것도 안 나갔을 자리에 **그럴듯하게 틀린 값**이 나갑니다. 이 사이에 내려진 의사결정은 사후에 되돌리기 어렵습니다.
3. **부분 누락은 통계적으로 위장한다.** 전부 없으면 결과가 0건이라 눈에 띕니다. 예제처럼 5건 중 1건만 빠지면 결과는 4건, 여전히 "그럴듯한 숫자"입니다. 리콜 대상 부품 목록에서 조용히 하나가 빠지는 식이라 육안 검토로는 절대 안 잡힙니다.
4. **신뢰를 태운다.** 사용자가 먼저 발견한 오류는 숫자 하나가 아니라 그래프 전체에 대한 신뢰를 깎습니다. 4장에서 아무도 안 쓰던 온톨로지가 그렇게 됩니다.

### 12.3절과 이어지는 지점

한 장 요약의 "문서만 있고 검사가 없는 게 제일 위험해요. 지키고 있다고 착각하게 됩니다"가 정확히 이 얘기입니다. `-` 표시는 **문서가 거짓말을 하고 있다는 증거**이고, 그 거짓말을 믿고 짜인 질의들이 이미 배포되어 돌고 있다는 뜻입니다. 필수라고 선언했기 때문에 아무도 `OPTIONAL MATCH`나 `coalesce()`를 안 썼을 것이고, 그래서 방어 장치가 없습니다.

## 3. `+`와 `-`의 위험도 비대칭

같은 감사 보고서에 나란히 찍히지만 두 표시의 성격은 다릅니다.

| | `+` (선언에 없는 키) | `-` (빠진 키) |
|---|---|---|
| 데이터 상태 | 정보가 **더** 있다 | 정보가 **덜** 있다 |
| 기존 질의에 미치는 영향 | 없음. 아무도 읽지 않으므로 무시된다 | 있음. 조건·반환값이 조용히 탈락한다 |
| 드러나는 방식 | 스토리지 증가, 문서와의 괴리, 나중에 의미 충돌 | 결과 누락. 아무 신호 없음 |
| 되돌릴 수 있나 | 예 — 값이 남아 있으니 언제든 정식화·삭제·이관 가능 | 아니오 — 원천이 사라졌으면 값을 복원 못 할 수도 있다 |
| 성격 | 부채(debt) — 쌓이면 아프다 | 사고(incident) — 지금 답이 틀리고 있다 |
| 대응 속도 | 다음 스프린트, 정기 정리 | 즉시 |

`+`에 대해서는 예제가 셋 중 하나를 고르라고 합니다.

1. 정식으로 스키마에 넣는다 — `recall_reason`처럼 실제로 필요해서 누군가 추가한 것
2. 지운다 — `temp_flag`처럼 임시로 넣고 잊은 것
3. 별도 영역으로 옮긴다 — `legacy_code`처럼 이전 시스템 잔재

셋 다 **여유 있게 판단할 수 있는 선택**입니다. 잘못 골라도 데이터는 그대로 있습니다. 반면 `-`에는 선택지가 없습니다. 원인을 찾아 메우는 것 하나뿐입니다.

비대칭을 한 줄로: **`+`는 문서를 고치면 되고, `-`는 데이터와 질의를 둘 다 고쳐야 합니다.**

한 가지 덧붙이면, `+`도 완전히 무해하지는 않습니다. 문서에 없는 키를 누군가 발견해서 질의에 쓰기 시작하면 그때부터는 아무도 보장하지 않는 필드에 시스템이 의존하게 됩니다. 그래서 `+`도 방치하지 말고 정기적으로 처리하되, 우선순위는 `-` 다음입니다.

## 4. `-`를 발견했을 때 즉시 취할 조치

### 4.1 영향 받는 질의 식별 (오늘)

가장 먼저 할 일은 백필이 아니라 **피해 범위 파악**입니다. 없어진 키를 참조하는 질의를 전부 찾습니다.

- 저장된 질의문, 애플리케이션 코드, BI 대시보드, ETL 스크립트를 그 속성명으로 전수 검색합니다.
- 각 질의에 대해 "이 키가 null이면 결과가 어떻게 되는가"를 판정합니다. `WHERE` 조건이나 필수 패턴에 들어 있으면 **행이 통째로 사라지고**, 반환 컬럼에만 있으면 값만 비는 정도로 끝납니다. 전자가 급합니다.
- 12장의 역량 질문 다섯 개(`code/questions.py`)를 회귀 테스트로 다시 돌려 봅니다. "부품 X를 쓴 제품 중 리콜된 것은?" 같은 질문의 답 건수가 지난달과 달라졌는지 확인합니다.
- 이미 나간 리포트·알림·하류 시스템이 있으면 **정정 공지가 필요한지** 판단합니다. 조용한 실패는 침묵했던 기간만큼 오염 범위가 넓습니다.

동시에 **원인**을 찾습니다. 이 키를 채우던 업스트림이 언제부터 안 채웠는지, 소스 시스템 필드명이 바뀐 것인지, 신규 적재 경로가 스키마를 몰랐던 것인지. 원인을 못 막으면 백필해도 다음 주에 다시 생깁니다.

### 4.2 백필 (원인 차단 후)

- 먼저 **누출을 막습니다.** 원천에서 키를 다시 채우도록 파이프라인을 고칩니다. 그러지 않으면 백필이 밑 빠진 독입니다.
- 누락 레코드에 값을 채웁니다. 원천 시스템·로그·이전 스냅샷에서 복원하는 게 최선입니다.
- 복원이 불가능한 레코드는 **추측해서 채우지 마세요.** 명시적인 "미상" 표식이나 별도 영역으로 격리하는 편이 낫습니다. 잘못된 값은 없는 값보다 더 조용하게 틀립니다.
- 백필은 되돌릴 수 있게 배치로, 결과 건수를 기록하면서 돌립니다. 백필 전후로 4.1의 회귀 질의를 다시 돌려 답이 정상으로 복귀했는지 확인합니다.

### 4.3 검증 규칙 추가 (재발 방지)

발견이 감사 배치였다는 사실 자체가 "검사가 없었다"는 증거입니다. 같은 일이 다시 조용히 일어나지 않도록 규칙을 심습니다. 12.3절의 세 층 중 어디에 둘지는 되돌릴 수 있느냐로 정합니다.

| 층 | 수단 | 언제 아느냐 | 어디에 쓰나 |
|---|---|---|---|
| 적재 시점 | 엔진 스키마 강제 (Kuzu의 `CREATE NODE TABLE`, GQL 스키마 선언) | 즉시. 대신 적재가 실패해 파이프라인이 멈춘다 | 되돌릴 수 없는 것 |
| 검증 시점 | SHACL `sh:minCount 1`, `sh:in`, `sh:minLength` 등 | 배치가 돌 때. 데이터는 들어가 있고 보고서로 안다 | 나머지 대부분 |
| 없음 | — | 사용자가 알려 준다 | 쓰지 말 것 |

구체적으로는,

- 진짜 필수인 키에는 SHACL `sh:minCount 1`을 걸어 **누락을 위반 건수로 세게** 만듭니다. 조용한 실패를 시끄러운 보고서로 바꾸는 작업입니다.
- 되돌릴 수 없는 키(식별자, 관계 키)는 적재 시점에 막습니다. 다만 예제의 경고대로 "적재를 너무 엄격하게 잡으면 데이터가 아예 안 들어와서 그것대로 문제"가 되니 전부 적재 시점으로 올리지는 마세요.
- 드리프트 감사 자체를 **주간 배치**로 고정하고, `-`가 하나라도 나오면 알림이 울리게 합니다. `+`는 리포트로만 모아 두고 정기 회의에서 처리합니다. 위험도 비대칭을 알림 정책에 그대로 반영하는 겁니다.
- 이번에 문제가 됐던 역량 질문을 **결과 건수 회귀 테스트**로 만들어 둡니다. 스키마 검증이 못 잡는 의미 수준의 누락은 이쪽에서 걸립니다.
- 마지막으로 문서를 데이터에 맞춰 갱신합니다. `-`는 문서가 틀렸다는 뜻이기도 하므로, "필수라고 선언만 하고 아무도 강제하지 않던 키"를 진짜 필수로 만들지 아니면 선택 항목으로 내릴지 결론을 내립니다.

---

## 5. 한 문장 정리

`+`는 문서가 데이터를 못 따라간 부채라 나중에 처리해도 되지만, `-`는 그래프 질의가 예외를 던지지 않고 조용히 빈/부분 결과를 내보내고 있다는 신호라서 — 지금 이 순간에도 틀린 답이 나가고 있으므로 — 영향 질의를 먼저 찾고, 원인을 막은 뒤 백필하고, 검증 규칙으로 다시는 조용해지지 않게 만들어야 합니다.

> 문서는 거짓말을 한다. 데이터는 안 한다. 문서 말고 데이터에게 물어보시라.
