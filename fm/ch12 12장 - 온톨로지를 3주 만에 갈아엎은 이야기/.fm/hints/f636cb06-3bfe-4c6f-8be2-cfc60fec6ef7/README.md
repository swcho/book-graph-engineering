# 스키마 관리에서 가장 위험한 상태

> **Q.** 스키마 관리에서 가장 위험한 상태는 무엇인가?
>
> **A.** 문서만 있고 검사가 없는 상태다. 지키고 있다고 착각하게 된다.

## 한 줄 정리

「스키마 없음」보다 「문서만 있음」이 더 위험하다. 스키마가 없으면 최소한 **없다는 걸 알고** 조심하지만, 문서가 있으면 **지켜지고 있다고 믿고** 조심하지 않는다. 위험의 크기는 결함의 크기가 아니라 **결함과 믿음의 차이**에서 나온다.

## 세 가지 상태를 늘어놓고 보기

12장 12.3절(「스키마를 언제 못 박을 것인가」)은 같은 잘못된 데이터를 세 방식에 넣어 보고 **언제 걸리는지**를 비교한다. 예제 `code/ex3_when_schema.py`의 결론 부분이 이렇다.

```
세 방식의 진짜 차이는 «언제 아느냐»다.
  적재 시점  — 즉시. 대신 적재가 실패하니 파이프라인이 멈춘다.
  검증 시점  — 배치가 돌 때. 데이터는 들어가 있고 보고서로 안다.
  없음       — 사용자가 알려 준다.
```

여기에 실무에서 가장 흔한 **네 번째 상태**를 끼워 넣으면 카드의 답이 나온다.

| 상태 | 위반이 발견되는 시점 | 팀이 믿는 것 | 실제 |
|---|---|---|---|
| 적재 시점 강제 (Kuzu 타입 스키마, GQL `CREATE NODE TABLE`) | 즉시 | 지켜진다 | 지켜진다 |
| 검증 시점 (SHACL 배치, 드리프트 감사) | 배치 주기 | 지켜지는지 **보고서로 안다** | 알고 있다 |
| **문서만 있음 (위키·설계서에만 존재)** | **영영 안 걸림** | **지켜진다** | **아무도 모른다** ← 가장 위험 |
| 스키마 없음 | 사용자 클레임 | 안 지켜진다 | 안 지켜진다 |

세 번째 줄만 **믿음과 실제가 어긋나 있다.** 나머지 세 줄은 어긋나지 않는다. 네 번째(스키마 없음)조차 어긋나지 않는다 — 안 지켜진다는 걸 다들 알기 때문에 질의를 짤 때 방어 코드를 넣고, 값을 의심하고, 확인한다.

## 왜 「착각」이 실질적 피해가 되는가

문서를 믿는 팀은 문서를 전제로 **다음 결정들을 쌓는다.**

1. **질의를 무방비로 짠다.** 「`category`는 필수라고 문서에 적혀 있으니 항상 있다」고 보고 `WHERE p.category = '체결'` 같은 조건을 건다. 실제로 `category`가 빠진 행이 있으면 그 행은 **에러 없이 조용히 결과에서 빠진다.** 에러가 났으면 고쳤을 텐데, 빈 결과는 「해당 없음」과 구분되지 않는다.
2. **다운스트림이 문서를 계약으로 삼는다.** 대시보드, 리포트, 다른 팀의 파이프라인이 문서를 읽고 붙는다. 강제되지 않는 계약 위에 계약이 쌓인다.
3. **드리프트가 누적된다.** 아무도 안 보는 사이 임시 키가 들어오고, 필수 키가 빠지고, 이전 시스템 잔재가 섞인다. 6개월 뒤에 발견되면 그때는 이미 「어느 게 맞는 상태인지」 판단할 근거조차 사라져 있다.

12장 예제 `code/ex5_schema_drift.py`가 딱 이 상황을 재현한다. 설계 문서에 적힌 스키마는 이렇게 깔끔하다.

```python
DECLARED = {
    "Part":    {"id", "name", "category"},
    "Product": {"id", "name", "released_on"},
    "Supplier":{"id", "name"},
}
```

운영 6개월 뒤 실제 데이터에서는 `legacy_code`, `temp_flag`, `note`, `recall_reason`, `contact`, `tier`가 들어와 있고, `Part`에서는 `category`가, `Product`에서는 `released_on`이 빠진 행이 나온다. **문서는 그 6개월 동안 한 글자도 바뀌지 않았다.** 문서가 틀린 게 아니라, 문서가 **아무것도 하지 않았다**는 게 문제다.

## 해법 — 검사를 붙여 상태를 옮긴다

「문서만 있음」에서 벗어나는 길은 두 방향이다. 문서를 지우는 게 아니라 **문서에 이빨을 달아 주는 것**이다.

### (1) 되돌릴 수 없는 것은 적재 시점으로

12장의 저자 기준은 한 줄이다.

> 되돌릴 수 없는 것은 적재 시점에, 나머지는 검증 시점에.
> 적재를 너무 엄격하게 잡으면 데이터가 아예 안 들어와서 그것대로 문제가 된다.

즉 전부 다 적재 시점에 막는 게 정답은 아니다. 파이프라인이 멈추는 비용이 있기 때문이다. 게다가 엔진마다 막을 수 있는 범위가 다르다. 예제 3에서 보듯 Kuzu는 **타입은 막지만 값의 범위(등급이 A/B/C 중 하나)는 못 막는다.** CHECK 제약이 없기 때문이다. 그래서 (2)가 필요하다.

### (2) 나머지는 검증 시점으로 — 문서를 실행 가능한 형태로

RDF라면 SHACL(Shapes Constraint Language)이 정확히 이 자리에 들어간다. 문서로 적었을 「이름은 필수, 등급은 A·B·C 중 하나」를 **기계가 검사할 수 있는 형태**로 옮긴다.

```turtle
ex:CompanyShape a sh:NodeShape ;
    sh:targetClass ex:Company ;
    sh:property [ sh:path ex:name ; sh:minCount 1 ; sh:minLength 1 ;
                  sh:datatype xsd:string ] ;
    sh:property [ sh:path ex:grade ; sh:in ("A" "B" "C") ] .
```

이러면 적재는 되지만 배치가 돌 때 위반 보고서가 나온다. **믿음과 실제가 다시 붙는다.**

### (3) 스키마 언어가 없어도 — 드리프트 감사 30줄

SHACL도 타입 스키마도 못 쓰는 상황이라면, **선언한 키 집합과 실제 데이터의 키 집합을 비교하는 배치**만으로도 충분하다. 12장은 이걸 「30줄이면 된다」고 말한다. 핵심 로직은 정말 짧다.

```python
extra   = {k: v for k, v in got.items() if k not in want}          # 문서에 없는 키
missing = {k: n - got.get(k, 0) for k in want if got.get(k, 0) < n}  # 선언했는데 빠진 키
```

그리고 결과를 읽는 법도 정해져 있다.

- **`+` (선언에 없는 키)** — 셋 중 하나를 정한다. ① 정식으로 스키마에 넣는다(`recall_reason`처럼 실제로 필요한 것) ② 지운다(`temp_flag`처럼 임시로 넣고 잊은 것) ③ 별도 영역으로 옮긴다(`legacy_code`처럼 이전 시스템 잔재).
- **`-` (선언했는데 빠진 키)** — **더 급하다.** 필수라고 선언한 키가 실제로는 없다는 뜻이고, 질의가 조용히 빈 결과를 내고 있을 가능성이 높다.

## 스키마 없이 시작해도 되는 경우

12장은 「스키마 없음」을 무조건 나쁘다고 하지 않는다. 허용되는 경우는 딱 둘이다.

- **혼자 쓸 때** — 계약을 맺을 상대가 없으므로 어긋날 믿음도 없다.
- **버릴 데이터일 때** — 드리프트가 누적될 시간이 없다.

이 둘 중 어느 쪽도 아니라면(= 여러 사람이 쓰고 오래 남을 데이터라면) 검사는 선택이 아니다. 그리고 이때 **문서만 얹는 것이 최악의 절충**이다. 비용은 문서 작성만큼 들고, 안전은 하나도 못 얻으면서, 안전하다는 느낌만 얻기 때문이다.

## 시험에 나올 만한 대비 문장

- 「스키마가 없는 것」보다 「문서만 있고 검사가 없는 것」이 더 위험하다.
- 이유는 하나: **지키고 있다고 착각하게 된다.**
- 세 방식의 진짜 차이는 「강한가 약한가」가 아니라 **「언제 아느냐」**다. 문서만 있으면 답이 「영영 모른다」가 된다.
- 문서는 거짓말을 하고, 데이터는 안 한다. **문서 말고 데이터에게 물어보라.**
