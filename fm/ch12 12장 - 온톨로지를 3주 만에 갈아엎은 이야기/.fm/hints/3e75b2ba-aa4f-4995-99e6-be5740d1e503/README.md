# `questions.py`의 역량 질문 다섯 개

## 한 줄 답

```
1. 부품 X 를 쓴 제품 중 리콜된 것은?
2. 공급사 A 가 납품한 부품이 들어간 제품은?
3. 리콜 사유가 «과열»인 제품에 공통으로 들어간 부품은?
4. 부품 X 의 대체 부품은 무엇이고, 언제부터 대체 가능한가?
5. 제품 P 의 부품 목록을 3단계까지 펼치면?
```

## 이 다섯 문장이 왜 파일 하나로 따로 있나

`code/questions.py`는 12장 예제들이 공유하는 **공통 상수 모듈**입니다. 여기에 세 덩어리가 들어 있어요.

| 상수 | 내용 |
|---|---|
| `QUESTIONS` | 역량 질문 5개 (위 목록) |
| `VOCAB_FROM_QUESTIONS` | 그 5개에서 뽑아낸 어휘 — 클래스 4 + 관계 4 + 속성 3 = **11개** |
| `EXPERT_TAXONOMY` | 도메인 전문가가 처음 제시한 214개 클래스 중 21개 발췌 |

모듈 독스트링이 이 장 전체의 주장을 그대로 담고 있습니다.

> 온톨로지 설계는 «세상을 정확히 기술하는» 일이 아니라 «이 다섯 질문에 답하는 최소 어휘를 정하는» 일이다.

즉 다섯 질문은 **설계의 입력이자 종료 조건**입니다. 위에서 아래로 지으면 "언제 끝났지?"를 판정할 수 없지만, 질의에서 거꾸로 뽑으면 「다섯 질의가 다 돌면 끝」이라는 명확한 스톱 사인이 생깁니다.

역량 질문(competency question)은 12장 키워드 표에서 **[사실상 표준]**으로 분류돼 있고, 1차 출처는 스탠퍼드의 *Ontology Development 101*입니다. 명세는 없지만 온톨로지 공학에서 널리 쓰이는 관행이죠.

## 질문별 어휘 분해

`VOCAB_FROM_QUESTIONS`의 전체 어휘는 다음 11개뿐입니다.

```python
VOCAB_FROM_QUESTIONS = {
    "클래스": ["부품", "제품", "공급사", "리콜"],
    "관계": ["사용한다", "납품한다", "리콜되었다", "대체가능하다"],
    "속성": ["이름", "사유", "유효시작일"],
}
```

이제 질문 하나하나가 이 중 무엇을 요구하는지 봅니다.

### 질문 1 — 부품 X 를 쓴 제품 중 리콜된 것은?

| 종류 | 필요한 것 |
|---|---|
| 클래스 | `부품`, `제품`, `리콜` |
| 관계 | `사용한다` (제품 → 부품), `리콜되었다` (제품 → 리콜) |
| 속성 | `이름` (부품 X 를 지목하는 데 필요) |

```cypher
MATCH (p:Product)-[:Uses]->(x:Part {name: 'X'}),
      (p)-[:Recalled]->(:Recall)
RETURN p
```

**이 질문이 만들어 내는 설계 결정**: "리콜된"이라는 말이 제품의 불리언 플래그로 충분한지, 별도 노드가 필요한지가 여기서는 아직 안 갈립니다. 질문 3이 그걸 결정합니다.

### 질문 2 — 공급사 A 가 납품한 부품이 들어간 제품은?

| 종류 | 필요한 것 |
|---|---|
| 클래스 | `공급사`, `부품`, `제품` |
| 관계 | `납품한다` (공급사 → 부품), `사용한다` (제품 → 부품) |
| 속성 | `이름` (공급사 A 지목) |

```cypher
MATCH (s:Supplier {name: 'A'})-[:Supplies]->(x:Part)<-[:Uses]-(p:Product)
RETURN DISTINCT p
```

**설계 결정**: 이 질문 하나가 `공급사` 클래스와 `납품한다` 관계의 **유일한 존재 근거**입니다. 이 질문이 없으면 어휘에서 둘 다 빠져야 합니다. 그리고 이건 2-hop 경로라서, `납품한다`가 공급사→제품이 아니라 공급사→**부품**을 향한다는 방향까지 여기서 정해집니다.

### 질문 3 — 리콜 사유가 «과열»인 제품에 공통으로 들어간 부품은?

| 종류 | 필요한 것 |
|---|---|
| 클래스 | `리콜`, `제품`, `부품` |
| 관계 | `리콜되었다`, `사용한다` |
| 속성 | **`사유`** |

```cypher
MATCH (r:Recall {reason: '과열'})<-[:Recalled]-(p:Product)-[:Uses]->(x:Part)
WITH x, count(DISTINCT p) AS n, ...
```

**설계 결정 두 가지**가 여기서 나옵니다.

1. **`리콜`이 클래스로 승격되는 지점.** 리콜에 `사유`라는 자기 속성이 붙어야 하므로, 제품의 불리언 플래그로는 답할 수 없습니다. 12.2절 기준 그대로예요 — 쪼개는 근거는 「다른 물건인가」가 아니라 **「다른 속성을 갖는가」**입니다. 리콜은 사유·일자 같은 자기 속성을 갖기 때문에 클래스가 됩니다.
2. **집합 연산(교집합)이 필요하다**는 것. 앞의 두 질문은 단순 경로 탐색이지만, 이건 "공통으로"라는 집계가 붙습니다. 어휘는 안 늘지만 질의 능력 요구는 한 단계 올라갑니다.

### 질문 4 — 부품 X 의 대체 부품은 무엇이고, 언제부터 대체 가능한가?

| 종류 | 필요한 것 |
|---|---|
| 클래스 | `부품` (양쪽 끝이 모두 부품 — 재귀 관계) |
| 관계 | **`대체가능하다`** (부품 → 부품) |
| 속성 | **`유효시작일`** — 노드가 아니라 **관계에 붙는 속성** |

```cypher
MATCH (x:Part {name: 'X'})-[r:Substitutable]->(y:Part)
RETURN y.name, r.valid_from
```

**설계 결정**: 이 질문이 다섯 개 중 가장 까다롭습니다. "언제부터"라는 조각이 **부품 X의 속성도, 대체 부품 Y의 속성도 아니라 둘 사이 관계의 속성**이기 때문입니다. 모델링 방식이 엔진에 따라 갈립니다.

- **LPG(Kuzu/Neo4j 등)**: 엣지 속성으로 그냥 붙습니다. `CREATE REL TABLE Substitutable(FROM Part TO Part, valid_from DATE)`.
- **RDF**: 삼항 관계를 표현할 수단이 필요합니다 — 관계 자체를 노드로 만드는 reification, singleton property, 또는 RDF-star.

이 한 조각이 11장(같은 질문, 세 가지 언어)에서 언어별 표현력 차이가 드러나는 대표 사례이기도 합니다. 그리고 `대체가능하다`는 12장 예제 4의 판정에서 **공개 어휘에 없어서 직접 만들어야 하는 항목**(적합도 0.0)으로 분류됩니다.

### 질문 5 — 제품 P 의 부품 목록을 3단계까지 펼치면?

| 종류 | 필요한 것 |
|---|---|
| 클래스 | `제품`, `부품` |
| 관계 | `사용한다` — **가변 길이·재귀 순회** |
| 속성 | `이름` |

```cypher
MATCH (p:Product {id: 'P'})-[:Uses*1..3]->(x:Part)
RETURN DISTINCT x.name
```

**설계 결정**: 새 어휘를 하나도 안 만들지만, 기존 어휘의 **정의역·치역을 뒤집습니다.** 예제 2의 얕은 스키마는 `CREATE REL TABLE Uses(FROM Product TO Part)`인데, 3단계로 펼치려면 부품이 부품을 쓸 수 있어야 하므로 `Part → Part` 방향도 허용돼야 합니다. 이 질문이 없었다면 그 사실을 6개월 뒤에 알았을 겁니다.

그리고 이 질문 때문에 **깊은 분류가 특히 비싸집니다.** 예제 2의 A안처럼 `UsesBolt` / `UsesNut` / `UsesResistor`로 관계를 쪼개 두면, 1단계에서도 이미 UNION 네 줄인데 3단계 재귀는 조합 폭발이 납니다. B안(단일 `Uses` + `category` 속성)이면 `[:Uses*1..3]` 한 줄이죠.

## 어휘 커버리지 — 고아가 하나도 없다

역량 질문 방식이 제대로 작동했는지 검사하는 방법은 간단합니다. **어휘 11개 각각이 최소 한 질문에 추적되는가**를 보면 됩니다.

| 어휘 | 종류 | 근거 질문 |
|---|---|---|
| 부품 | 클래스 | 1, 2, 3, 4, 5 |
| 제품 | 클래스 | 1, 2, 3, 5 |
| 공급사 | 클래스 | 2 |
| 리콜 | 클래스 | 1, 3 |
| 사용한다 | 관계 | 1, 2, 3, 5 |
| 납품한다 | 관계 | 2 |
| 리콜되었다 | 관계 | 1, 3 |
| 대체가능하다 | 관계 | 4 |
| 이름 | 속성 | 1, 2, 5 |
| 사유 | 속성 | 3 |
| 유효시작일 | 속성 | 4 |

고아 어휘가 없습니다. 반대로 `EXPERT_TAXONOMY` 쪽을 보면, 21개 발췌 중 이 다섯 질문이 실제로 쓰는 건 **`부품` 하나뿐**입니다. 나머지 20개(기계부품·전자부품·볼트·너트·와셔·리벳·육각볼트·M6스테인리스육각볼트·MOSFET·N채널MOSFET …)는 전부 미사용이고, 원래 214개 기준으로는 204개가 놀고 있는 셈입니다.

예제 1(`ex1_vocab_from_questions.py`)이 하는 일이 정확히 이 계산입니다 — 질문에서 뽑은 어휘 집합을 만들고, 전문가 분류에서 그 집합에 없는 항목을 세어 보여 줍니다.

```python
used = set()
for words in VOCAB_FROM_QUESTIONS.values():
    used.update(words)
unused = [t for t in EXPERT_TAXONOMY if t not in used]
```

## 오해하면 안 되는 것

예제 1의 마무리 문장이 중요합니다.

> «M6스테인리스육각볼트» 는 틀린 분류가 아니다. **정확한** 분류다. 다만 이 다섯 질문에 답하는 데는 필요가 없다.

즉 이 장은 전문가의 분류가 **틀렸다**고 말하는 게 아니라, **비용이 편익을 넘었다**고 말합니다. 필요해지는 순간에 넣는 비용보다, 안 쓰는 분류 190여 개를 계속 유지하는 비용이 크다는 판단이죠. 그리고 그 판단을 내리려면 "필요한지 아닌지"를 물어볼 기준이 있어야 하는데, 그 기준이 바로 이 다섯 문장입니다.

## 12장 다른 절과의 연결

| 절 | 이 다섯 질문이 어떻게 쓰이나 |
|---|---|
| 12.1 질의에서 거꾸로 뽑는다 | 다섯 질문 → 어휘 11개. 예제 1 |
| 12.2 쪼갤 것인가 속성으로 둘 것인가 | 질문 5가 깊은 분류의 비용을 드러냄. 예제 2 |
| 12.3 스키마를 언제 못 박을 것인가 | 질문이 요구하는 필수 속성(`사유`, `유효시작일`)이 제약 대상. 예제 3 |
| 12.4 남의 어휘를 가져다 쓸까 | 어휘 11개를 schema.org 적합도로 채점(임계 0.7). `리콜`·`대체가능`은 0.0이라 직접 제작. 예제 4 |
| 12.5 문서 말고 데이터에게 물어보라 | 선언한 스키마 대 실제 키를 대조하는 드리프트 감사. 예제 5 |

## 외워 두면 좋은 골격

다섯 질문을 통째로 암기하기보다, **각 질문이 어휘의 어느 부분을 책임지는가**로 잡으면 재구성이 쉽습니다.

1. 부품 X → 리콜된 제품 …… `사용한다` + `리콜되었다` (기본 2-hop)
2. 공급사 A → 제품 …… `공급사` + `납품한다` (공급망 방향)
3. 리콜 사유 «과열» → 공통 부품 …… `사유` 속성 + 교집합 (리콜을 클래스로 승격시키는 질문)
4. 대체 부품 + 언제부터 …… `대체가능하다` + `유효시작일` (관계에 붙는 속성)
5. 3단계 펼치기 …… `사용한다`의 재귀 (Part → Part 허용을 강제하는 질문)
