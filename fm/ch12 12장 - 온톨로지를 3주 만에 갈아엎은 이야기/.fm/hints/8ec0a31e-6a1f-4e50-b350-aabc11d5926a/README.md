# 공개 어휘 사용에서 가능한 두 가지 실수

> **질문**: 공개 어휘 사용에서 가능한 두 가지 실수는 무엇인가?
>
> **답**: 억지로 맞춰 써서 "부품인데 왜 가격이 있지" 같은 혼란을 만드는 것과, 아예 무시하고 다 새로 만들어 외부와 매번 변환하는 것이다.

출처: 12장 12.4절 「남의 어휘를 가져다 쓸까」, 예제 `code/ex4_reuse_or_build.py`

---

## 1. 왜 이 문제가 생기나 — 「부품」이라는 낱말 하나

12장의 역량 질문 다섯 개에서 뽑은 클래스는 `부품`, `제품`, `공급사`, `리콜` 네 개였습니다. 이 중 앞의 셋은 schema.org 같은 공개 어휘에 이미 비슷한 게 있습니다. 그래서 자연스럽게 "이미 있는 걸 왜 또 만드나"라는 질문이 나옵니다.

문제는 **이름은 겹치는데 뜻이 다른** 경우입니다. 예제 4의 적합도 표를 보면:

| 우리 개념 | 공개 어휘 | 적합도 | 판정 |
|---|---|---|---|
| 제품 | `schema.org/Product` | 0.9 | 그대로 쓴다 |
| 공급사 | `schema.org/Organization` | 0.8 | 그대로 쓴다 |
| 납품 | `schema.org/seller` | 0.5 | 만들고 이어 둔다 |
| **부품** | `schema.org/Product` | **0.4** | **만들고 이어 둔다** |
| 리콜 | 없음 | 0.0 | 만든다 |
| 대체가능 | 없음 | 0.0 | 만든다 |

`제품`과 `부품` 둘 다 후보가 `schema.org/Product`인데 적합도가 0.9와 0.4로 갈립니다. 이유는 이렇습니다.

- schema.org의 `Product`는 **판매·거래되는 상품**을 전제로 설계된 클래스입니다. `offers`, `price`, `sku`, `review`, `aggregateRating` 같은 상거래 속성이 딸려 옵니다.
- 우리에게 `부품`은 **다른 제품 안에 들어가는 것**이고, 판매 단위가 아닙니다. 가격도 리뷰도 없습니다.

같은 낱말이 같은 뜻이 아닙니다. 이 어긋남을 어떻게 처리하느냐에서 두 갈래의 실수가 나옵니다.

---

## 2. 실수 (가) — 억지로 맞춰 쓴다

**증상**

부품을 `schema.org/Product`로 그냥 선언해 버립니다. 처음엔 아무 일도 안 일어납니다. 잘 돌아가는 것처럼 보입니다. 그러다 이런 것들이 하나씩 올라옵니다.

- "부품인데 왜 `price`가 있지?" — 스키마상 존재하지만 우리 도메인에서는 의미 없는 필드
- "이 `Product` 노드는 리뷰가 있고 저건 없는데, 버그인가요?" — 판매 상품과 부품이 같은 클래스에 섞여 있어서 생기는 질문
- "부품 목록 뽑았는데 완제품이 같이 나와요" — 같은 타입이니 같이 걸립니다
- 검증 규칙을 쓸 때 "단, 부품인 경우는 제외" 절이 붙기 시작합니다

**누적되는 비용: 예외 조항의 축적**

핵심 비용은 코드가 아니라 **규칙에 붙는 단서 조항**입니다. 부품과 제품을 한 타입으로 묶는 순간, 둘을 구분해야 하는 모든 자리마다 예외가 하나씩 생깁니다.

- 질의: `MATCH (x:Product) WHERE x.isPart = false ...` 같은 조건이 어디에나 붙습니다
- 검증: SHACL 형태를 쓴다면 `Product`에 `price` 필수를 걸 수 없습니다. 부품에는 가격이 없으니까요. 결국 필수 제약을 포기하거나, `sh:or`로 분기 형태를 만들어야 합니다
- 문서: "여기서 Product는 완제품만 말합니다", "이 표의 Product에는 부품이 포함됩니다" 같은 각주가 늘어납니다
- 신규 입사자: 매번 "이 Product는 어느 쪽 Product인가요"를 물어봅니다

이 비용의 성질은 **분산되어 있고 잘 안 보인다**는 것입니다. 어느 한 파일을 고쳐서 되돌릴 수가 없습니다. 예외가 스키마에 붙은 게 아니라 사람들의 머릿속과 수십 개 질의문에 흩어져 붙기 때문입니다. 12장 한 장 요약의 "억지로 맞춰 쓰면 예외 조항이 쌓입니다"가 이 이야기입니다.

그리고 이건 12장 전체 주제와도 이어집니다. 남의 분류 체계에 우리를 끼워 맞추는 것은, 전문가가 준 214개 분류를 그대로 받아 쓰는 것과 같은 실수의 다른 얼굴입니다. 둘 다 **우리 질의가 기준이 아닌** 어휘를 쓰는 것입니다.

---

## 3. 실수 (나) — 아예 무시하고 다 새로 만든다

**증상**

"schema.org는 우리랑 안 맞아"라며 전부 `ex:Product`, `ex:Organization`, `ex:Part`로 자체 정의합니다. 내부적으로는 아주 깔끔합니다. 예외 조항이 하나도 없습니다. 우리 도메인에 정확히 맞는 어휘니까요.

문제는 **경계에서** 터집니다.

- 공급사에서 받은 제품 카탈로그가 schema.org 형식 → 변환기 필요
- 우리 데이터를 외부 파트너에게 제공 → 역변환기 필요
- 검색엔진 노출을 위한 JSON-LD 마크업 → 또 매핑
- 새 공급사 온보딩 → 또 매핑 표 한 벌
- 공개 데이터셋(SKOS 어휘, 산업 분류 코드 등)과 조인 → 또 변환

**누적되는 비용: 변환 코드의 축적**

이쪽 비용은 (가)와 성질이 정반대입니다. **잘 보이지만 계속 늘어납니다.**

- 매핑 로직이 소스 개수에 비례해서 늘어납니다. 소스 N개면 최악의 경우 N개의 어댑터
- 변환 코드는 그 자체로 유지보수 대상입니다. schema.org가 바뀌면 어댑터도 바꿔야 합니다
- 변환 과정에서 정보가 새거나 왜곡됩니다. 왕복 변환이 원본과 같다는 보장이 없습니다
- 매핑 규칙이 코드 안에만 있으면 기계가 읽을 수 없습니다. "우리 `ex:Part`가 저쪽 뭐랑 같냐"는 질문에 답하려면 사람이 코드를 읽어야 합니다

여기서 흔한 오해 하나. 실수 (나)는 "자체 어휘를 만든 것"이 아닙니다. 예제 4에서 `리콜`과 `대체가능`은 공개 어휘에 아예 없으니 **당연히 만들어야** 합니다. (나)의 잘못은 만든 것이 아니라 **아무것도 연결해 두지 않은 것**입니다.

## 4. 두 실수의 대비

| | (가) 억지로 맞춰 쓴다 | (나) 다 새로 만든다 |
|---|---|---|
| 내부 모델 | 남의 어휘 | 우리 어휘 |
| 초기 비용 | 낮다 (그냥 쓰면 됨) | 중간 (설계해야 함) |
| 누적되는 것 | **예외 조항** | **변환 코드** |
| 어디에 쌓이나 | 질의·검증·문서·사람 머릿속 | 경계의 어댑터 계층 |
| 보이는가 | 안 보인다, 흩어져 있다 | 보인다, 파일이 늘어난다 |
| 늘어나는 속도 | 질의·규칙 수에 비례 | 연동 대상 수에 비례 |
| 되돌리기 | 어렵다 (전면 재모델링) | 상대적으로 쉽다 (어댑터 교체) |
| 실패하는 순간 | "부품인데 왜 가격이 있지" | "이 필드가 저쪽 뭐에 대응하죠" |

한 줄로 줄이면: **(가)는 우리 내부가 오염되고, (나)는 우리 경계가 비대해집니다.**

## 5. 중간 해법 — 우리 어휘 + 매핑

예제 4의 결론은 이렇습니다.

> 중간이 답이다. 우리 것으로 만들되, 공개 어휘와 «대략 같음»을 걸어 둔다.
> RDF 라면 owl:sameAs 나 skos:closeMatch, LPG 라면 속성으로 매핑 표를 둔다.

**왜 (가)를 피하는가**

내부 모델은 우리 도메인 그대로입니다. `ex:Part`에는 `price`가 없고 `Product`와 섞이지 않습니다. 그러니 "부품인 경우는 제외" 같은 단서 조항이 아예 생길 자리가 없습니다. 질의는 짧아지고, 검증 형태는 분기 없이 단순해집니다.

**왜 (나)를 피하는가**

매핑을 **선언으로 남기기** 때문입니다. 변환 로직을 코드에 숨기는 대신 그래프 안에 데이터로 적어 둡니다.

```turtle
ex:Product  owl:sameAs      schema:Product .      # 적합도 0.9 — 같다고 봐도 된다
ex:Supplier owl:sameAs      schema:Organization .  # 적합도 0.8
ex:Part     skos:closeMatch schema:Product .       # 적합도 0.4 — 비슷하지만 같지는 않다
ex:Supplies skos:relatedMatch schema:seller .      # 적합도 0.5
ex:Recall   ...                                    # 대응 없음. 우리 것만 있다
```

이렇게 두면:

- 어댑터를 **하나** 쓸 수 있습니다. 소스마다 손으로 쓴 변환기 대신, 매핑 표를 읽어서 도는 범용 변환기 한 벌이면 됩니다
- 매핑이 바뀌면 **데이터만** 고칩니다. 코드 배포가 아니라 트리플 수정입니다
- 기계가 읽을 수 있습니다. 외부 도구가 "당신들 Part가 뭐랑 비슷하냐"를 그래프에 물어볼 수 있습니다
- 적합도가 **문서로 남습니다**. `sameAs`인지 `closeMatch`인지가 곧 "얼마나 믿고 변환해도 되는가"입니다

**정확성의 등급을 구분하는 것이 핵심**

이게 중간 해법의 진짜 장치입니다. (가)는 모든 관계를 강제로 "같다"로 만들고, (나)는 모든 관계를 "모른다"로 둡니다. 중간 해법은 등급을 나눕니다.

- `owl:sameAs` — 완전히 같은 것. 아무 데나 바꿔 써도 된다 (강한 주장이니 남발 금지)
- `owl:equivalentClass` — 클래스 외연이 같다. 개체 동일성보다 안전한 선택
- `skos:exactMatch` — 개념 체계 사이에서 서로 바꿔 쓸 수 있다
- `skos:closeMatch` — 비슷하다. 단, **전이되지 않는다**. 「부품 ~ Product」에 딱 맞는 자리
- `skos:relatedMatch` — 관련은 있지만 대체 불가

`부품`에 `sameAs`가 아니라 `closeMatch`를 거는 것이 요점입니다. 연결은 해 두되, "가격을 넘겨받아도 된다"는 결론까지 추론되지는 않게 막습니다. SKOS의 `closeMatch`가 의도적으로 전이적이지 않게 정의된 것도 이 때문입니다.

**LPG(속성 그래프)라면**

RDF가 아니면 술어를 붙일 자리가 없으니, 매핑을 별도 데이터로 둡니다.

```
// 노드 속성으로
(:Part {id:'B1', name:'M6 볼트', ext_schema_org:'Product', ext_confidence:0.4})

// 또는 매핑 노드로
(:VocabMapping {local:'Part', external:'schema.org/Product',
                relation:'closeMatch', fitness:0.4})
```

어느 쪽이든 원칙은 같습니다. **매핑은 코드가 아니라 데이터다.**

## 6. 판단 기준 — 적합도 0.7

예제 4는 `THRESHOLD = 0.7`이라는 숫자 하나로 세 갈래를 가릅니다.

```
공개 어휘 없음        → 만든다              (리콜, 대체가능)
적합도 >= 0.7        → 그대로 가져다 쓴다    (제품, 공급사)
적합도 <  0.7        → 만들고 이어 둔다      (부품 0.4, 납품 0.5)
```

예제의 마지막 줄이 중요합니다.

> 0.7 은 제 감이다. 중요한 건 «숫자를 정해 두고 매번 같은 기준으로 판단하는 것»이다.

숫자 자체는 근거가 없습니다. 요점은 **팀이 하나의 기준을 공유해서 매번 같은 방식으로 결정한다**는 것입니다. 기준이 없으면 어떤 개념은 억지로 맞추고 어떤 개념은 이유 없이 새로 만드는, (가)와 (나)가 섞인 최악이 됩니다. 실제로 적합도를 매길 때는 이런 것들을 봅니다.

- 필수 속성이 겹치는 비율
- 정의역·치역이 충돌하지 않는가
- 딸려 오는 속성 중 우리 도메인에서 의미 없는 게 얼마나 되는가 (`price`, `review` …)
- 기수 제약이 맞는가

## 7. 외우기

- 실수 둘: **억지로 맞춘다** / **아예 무시한다**
- 쌓이는 것 둘: **예외 조항** / **변환 코드**
- 답: **우리 것으로 만들되 «대략 같음»을 걸어 둔다**
- 판단: **적합도 0.7** — 숫자보다 "숫자를 정해 뒀다"는 사실이 중요
