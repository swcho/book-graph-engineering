# 검증을 전부 막으면 어떤 최악의 결과가 생기는가?

**답**: 데이터가 안 들어와 사람들이 검증을 우회하고, 결국 **우회 경로가 주 경로가 된다**.

---

## 한 줄로

검증을 빡빡하게 걸어서 생기는 최악은 「데이터가 안 들어오는 것」이 아닙니다.
데이터가 안 들어오면 사람들은 일을 멈추지 않고 **옆길을 냅니다**. 그 옆길이 굳어져 정상 경로가 되는 순간, 검증기는 아무것도 지키지 못하는 장식품이 됩니다.

---

## 왜 이렇게 되는가 — 고장의 순서

13장 도입부가 이 사고를 그대로 기록합니다.

> 적재를 막았더니 데이터가 안 들어왔습니다.
> 다음 날 저는 검증을 껐습니다. 그리고 3개월 뒤에 다시 켤 때까지, 데이터는 다시 썩었습니다.

전개는 항상 같은 순서로 갑니다.

| 단계 | 벌어지는 일 |
|---|---|
| 1 | 「깨끗한 그래프」를 목표로 모든 위반을 차단으로 건다 |
| 2 | 사소한 위반(표시 이름 없음 등) 하나에 파이프라인이 선다 |
| 3 | 적재가 막혀 화면·리포트가 비고, 현업이 항의한다 |
| 4 | 사람들이 우회한다 — 검증 없는 백도어 적재, 수기 INSERT, 스테이징 DB 직접 쓰기, 「임시」 예외 플래그 |
| 5 | **우회가 편하니 다들 그 길만 쓴다. 우회 경로가 주 경로가 된다** |
| 6 | 검증기는 켜져 있지만 실제 데이터는 그 앞을 지나가지 않는다 |

3단계에서 멈추면 그냥 불편한 것입니다. 되돌릴 수 있어요. **5단계까지 가면 되돌릴 수 없습니다.** 조직의 습관과 도구가 이미 우회 경로 위에 세워졌기 때문입니다. 검증을 아예 껐던 것(3개월간 데이터가 썩음)보다 나쁜 이유는, 껐다는 사실은 모두가 알지만 우회는 **켜져 있다고 착각하게 만들기** 때문입니다.

---

## 코드에서 보이는 함정 — `ok` 한 개만 보면 안 된다

`ex1_shacl_severity.py`의 핵심 경고가 이겁니다.

```python
ok, report, _ = validate(data, shacl_graph=shapes, inference="none", advanced=True)
```

```
«전체 통과 여부»가 False 인 게 함정이다.
기록 등급 하나만 걸려도 False 가 나온다. 그래서 이 값만 보고
적재를 막으면 «표시 이름이 없다» 때문에 파이프라인이 선다.
```

`data.ttl`에는 이런 노드가 있습니다.

```turtle
# 기록 — 표시 이름이 없다
ex:Daol a ex:Company ;
    ex:bizNumber "333-44-55555" ; ex:grade "B" ; ex:signed ex:C4 .
```

사업자번호도 멀쩡하고 등급도 정상인데 `rdfs:label`만 없습니다. 심각도는 `sh:Info`(기록)인데도 `validate()`의 불리언 반환값은 `False`입니다. **`if not ok: reject()` 한 줄이 전부 막는 파이프라인의 정체**입니다.

## 처방 — 심각도 셋, 차단 기준은 하나

이 장의 답은 「검증을 느슨하게 하라」가 아니라 **「막는 것과 알리는 것을 나눠라」**입니다. SHACL이 `sh:severity`를 표준으로 제공하는 이유가 이것입니다.

| 심각도 | SHACL 값 | 처리 | 판단 기준 |
|---|---|---|---|
| 차단 | `sh:Violation` | 적재 거부. 사람이 원천을 고쳐야 한다 | 되돌릴 수 없는가 |
| 경고 | `sh:Warning` | 적재는 하고 대시보드에 올린다 | 질의 답이 틀리는가 |
| 기록 | `sh:Info` | 주간 보고서에 숫자만. 추세 나빠지면 본다 | 보기 나쁠 뿐인가 |

**차단 기준은 「되돌릴 수 없는가」 하나입니다.** 「나중에 고칠 수 있는 것」은 차단하지 않습니다. 나중에 고칠 수 있는 것까지 차단하면 4단계(우회)가 시작됩니다.

`shapes.ttl`이 이 기준을 실제로 어떻게 적용했는지 보면 감이 옵니다.

```turtle
# 차단 — 사업자번호가 없으면 이 노드는 다른 것과 병합될 수 없다
sh:property [ sh:path ex:bizNumber ; sh:minCount 1 ; sh:maxCount 1 ;
    sh:pattern "^[0-9]{3}-[0-9]{2}-[0-9]{5}$" ;
    sh:severity sh:Violation ; sh:message "사업자번호가 없거나 형식이 틀렸다" ] ;

# 경고 — 등급으로 필터하는 질의가 조용히 빈 결과를 낸다
sh:property [ sh:path ex:grade ; sh:minCount 1 ; sh:in ("A" "B" "C") ;
    sh:severity sh:Warning ; sh:message "등급이 없거나 A/B/C 밖이다" ] ;

# 기록 — 화면에 빈칸이 보일 뿐
sh:property [ sh:path rdfs:label ; sh:minCount 1 ;
    sh:severity sh:Info ; sh:message "표시 이름이 없다" ] .
```

- 사업자번호는 **식별자**입니다. 틀린 채로 들어오면 엉뚱한 노드와 병합되고, 병합은 되돌리기 어렵습니다 → 차단.
- 등급은 나중에 채울 수 있습니다. 다만 그 사이 질의가 조용히 틀립니다 → 경고.
- 표시 이름은 화면 빈칸일 뿐입니다 → 기록.

계약의 고아 노드(`ex:C9`)도 차단인데, 소유자 없는 계약이 그래프에 남으면 나중에 누구 것인지 복원할 수 없기 때문입니다.

---

## 자주 하는 오해

- **「차단을 늘릴수록 그래프가 깨끗해진다」** — 아닙니다. 차단이 늘면 우회가 늘고, 우회한 데이터는 아예 검사받지 않으므로 그래프는 **더** 더러워집니다.
- **「그럼 검증을 끄면 되지 않나」** — 저자가 실제로 그렇게 했고, 3개월 만에 데이터가 다시 썩었습니다. 끄는 것도 답이 아니라 반대쪽 극단입니다.
- **「경고는 무시해도 되는 것」** — 경고는 「지금 막지 않을 뿐, 질의가 틀리고 있다」는 뜻입니다. 대시보드에 올려 추세를 봐야 합니다(`ex5`가 경고 210 → 1,310건으로 6배 늘어난 사례를 보여 줍니다).
