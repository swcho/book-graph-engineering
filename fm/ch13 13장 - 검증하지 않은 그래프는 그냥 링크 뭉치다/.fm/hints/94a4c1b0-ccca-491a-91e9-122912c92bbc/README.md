# 다중 소속 스멜이 왜 「위반」이 아닌가

## 한 줄 답

카테고리가 둘 이상인 게 **정당한 경우가 있어서**입니다. 정당한지 아닌지는 데이터 모양이 아니라 **도메인이** 정합니다. 그래서 2층 스멜 검사는 자동으로 고치지 않고 **목록만 뽑아** 사람에게 넘깁니다.

예제 3의 마무리 문장 그대로예요.

> 다중 소속 — 위반이 아닐 수도 있다. 도메인이 정한다
>
> 2층은 자동으로 고치지 않는다. 목록만 뽑아 주는 게 일이다.

---

## 코드부터

`code/ex3_graph_smells.py`에서 다중 소속을 재는 함수는 이것 하나입니다.

```python
def smell_multi_parent(edges, rel):
    cnt = Counter(a for a, r, _ in edges if r == rel)
    return [(v, n) for v, n in cnt.items() if n > 1]
```

호출부.

```python
    mp = smell_multi_parent(EDGES, "IN_CATEGORY")
    print(f"\n[다중 소속] 카테고리가 둘 이상 — {len(mp)}건")
    for v, n in mp:
        print(f"    {v} 카테고리 {n}개")
```

하는 일은 정말 이게 전부입니다. `IN_CATEGORY` 엣지의 **출발점을 세어서 2 이상인 노드를 돌려준다.** 판정도, 등급도, 수정도 없습니다.

이 데이터셋에서 걸리는 건 딱 하나예요.

```python
    ("n6", "IN_CATEGORY", "cat1"), ("n6", "IN_CATEGORY", "cat2"),
```

`cat1`은 「체결」, `cat2`는 「전자」입니다. `n6`은 체결 부품이면서 전자 부품입니다.

이게 오류일까요? **볼트라면 오류지만, 전자식 잠금 액추에이터라면 정답입니다.** 코드는 이 차이를 알 방법이 없습니다. 엣지 개수만 보이니까요.

> 세부 구현 참고 — `Counter`는 중복 엣지도 그대로 셉니다. 실제 그래프에서 같은 `(n6, IN_CATEGORY, cat1)` 트리플이 두 번 적재됐다면 「카테고리 2개」로 잡히지만 사실은 중복 적재 문제예요. 실무에 옮길 때는 `set`으로 목적지를 모아 세는 편이 낫습니다. 예제는 스멜의 개념을 보여 주는 데 집중해서 이 부분을 단순화했습니다.

## 「스멜」이라는 단어 자체가 답을 담고 있다

이 장 키워드 표에서 **그래프 스멜**은 `[실험]`으로 표시돼 있습니다. 표준 명세가 없다는 뜻이고, 이름을 빌려 온 곳은 소프트웨어 쪽의 **코드 스멜(code smell)**입니다.

- 용어를 만든 사람은 **켄트 벡(Kent Beck)**이고, 널리 퍼진 건 마틴 파울러의 *Refactoring*(1999) 3장 「Bad Smells in Code」를 통해서입니다. 그 장은 벡과 공저예요.
- 벡의 할머니가 기저귀를 보고 했다는 말 — *"If it stinks, change it."* 냄새가 나면 **들여다보라**는 것이지, 냄새 = 고장이라는 게 아닙니다.
- 파울러가 반복해 강조한 단서: 스멜은 **빨리 알아챌 수 있는 표면 징후**지만 **항상 문제를 뜻하지는 않는다.** 그래서 「규칙(rule)」이 아니라 「냄새(smell)」라고 이름 붙인 겁니다.

정리하면 이렇게 갈립니다.

| | 위반(violation) | 스멜(smell) |
|---|---|---|
| 판정 | 참/거짓이 분명 | 「이상하다」는 신호 |
| 근거 | 선언한 제약 | 통계·경험칙 |
| 오탐 | 있으면 제약이 틀린 것 | **정상적으로 존재** |
| 후속 조치 | 자동 처리 가능 | 사람이 본다 |
| 이 장의 층 | 1층 SHACL | 2층 스멜 |

「다중 소속」이 2층에 있는 이유가 4번 줄입니다. 오탐이 정상적으로 섞여 있는 검사예요. 그런 검사에 「위반」이라는 이름을 붙이면 두 가지 중 하나가 벌어집니다. 잘못 막거나, 사람들이 무시하기 시작하거나. 13.2절이 말한 그 실패죠 — 전부 막으면 사람들이 검증을 우회합니다.

## 판정이 갈리는 진짜 축: 분류 체계인가, 분면인가

「카테고리 둘」이 오류인지 아닌지는 그 카테고리 축이 무엇으로 설계됐느냐에 달려 있습니다. 두 가지가 완전히 다른 물건입니다.

### 1. 배타적 분류 체계 (taxonomy)

하나의 축으로 세상을 **겹치지 않게** 나눈 트리입니다. 생물 분류학이 전형이에요. 하나의 종은 하나의 속에만 속합니다.

- 형식적으로는 **상호 배타(disjoint)** + **단일 부모**입니다.
- RDF/OWL로는 `owl:disjointWith`, `owl:AllDisjointClasses`로 선언합니다.
- 이렇게 **도메인이 배타성을 선언했다면** 다중 소속은 진짜 위반입니다.

그리고 선언했다면 굳이 2층에서 세고 있을 필요가 없어요. 1층으로 내려서 SHACL로 잡으면 됩니다.

```turtle
ex:PartShape a sh:NodeShape ;
    sh:targetClass ex:Part ;
    sh:property [
        sh:path ex:inCategory ;
        sh:minCount 1 ; sh:maxCount 1 ;
        sh:severity sh:Violation ;
        sh:message "부품은 카테고리를 정확히 하나 가져야 한다" ] .
```

`shapes.ttl`에서 사업자번호에 `sh:maxCount 1`을 건 것과 똑같은 모양입니다. **참/거짓이 분명해지는 순간 스멜은 제약으로 승격됩니다.**

### 2. 다중 분면 (facet)

여러 개의 **독립된 축**으로 같은 대상을 동시에 기술하는 방식입니다. 랑가나단(S. R. Ranganathan)의 콜론 분류법이 원조이고, 요즘 커머스 사이트의 필터 UI가 전부 이겁니다.

`n6`을 분면으로 보면 이렇습니다.

| 분면 | 값 |
|---|---|
| 기능 | 체결 |
| 기술 영역 | 전자 |
| 재질 | 스테인리스 |
| 조달 | 국산 |

이 경우 「카테고리 2개」는 정상일 뿐 아니라 **부족한** 겁니다. 네 개여야 하니까요. 여기에 `sh:maxCount 1`을 걸면 데이터가 못 들어옵니다. 13장 첫 줄의 그 상황이죠 — 적재를 막았더니 데이터가 안 들어왔습니다.

### 3. 그리고 대개는 「아직 안 정했다」

현실에서 가장 흔한 세 번째 경우입니다. `IN_CATEGORY` 하나에 기능·영역·재질이 뒤섞여 들어와 있고, 아무도 이 축이 배타적이어야 하는지 결정한 적이 없습니다. `n6`이 두 카테고리를 가진 건 **모델링 결정이 빠졌다는 증거**지, 데이터가 틀렸다는 증거가 아닙니다.

이때 스멜 목록의 값어치는 「고쳐야 할 노드 목록」이 아니라 **「도메인 전문가에게 물어봐야 할 질문 목록」**입니다.

> 「n6, n41, n77이 카테고리를 두 개 갖고 있습니다. 카테고리는 하나만 가져야 하는 축인가요, 아니면 축을 쪼개야 하나요?」

12장에서 온톨로지를 갈아엎게 만든 것도 이런 질문이었고, 그 답이 나오면 결과는 셋 중 하나입니다.

| 도메인의 답 | 결과 |
|---|---|
| 배타적이다 | `sh:maxCount 1` 추가 → 1층으로 이동, 진짜 위반 |
| 분면이다 | `IN_CATEGORY`를 `HAS_FUNCTION` / `IN_DOMAIN`으로 분리 → 스멜 자체가 사라짐 |
| 원칙은 하나인데 예외가 있다 | 스멜로 유지 + 예외 목록 관리 → 계속 2층 |

세 답 모두 **코드가 낼 수 없는 답**입니다. 그래서 도메인이 정한다고 하는 거예요.

## 자동 수정이 왜 위험한가: 되돌릴 수 없는 정보 손실

`smell_multi_parent`가 `n6`에 대해 「고친다」면 뭘 해야 할까요. 엣지 하나를 지워야 합니다. 그런데 **어느 쪽을요?**

```python
    ("n6", "IN_CATEGORY", "cat1"),   # 체결 — 이걸 지우나
    ("n6", "IN_CATEGORY", "cat2"),   # 전자 — 이걸 지우나
```

코드가 고를 수 있는 기준은 전부 도메인과 무관합니다. 먼저 들어온 것, ID가 작은 것, 자식이 많은 카테고리, 임의의 하나. 어느 걸 골라도 **동전 던지기**고, 문제는 결과가 비대칭이라는 점입니다.

**손실이 한쪽으로만 흐릅니다.**

- 지운 엣지는 「이런 엣지가 있었다」는 기록을 남기지 않습니다. 지워진 자리에는 아무것도 안 남아요.
- 다음번 검사는 `n6`을 **깨끗하다고** 판정합니다. 스멜이 사라졌으니까요. 문제를 지운 게 아니라 **증상을 지웠고**, 증거까지 같이 지웠습니다.
- 원천 시스템이 「체결 + 전자」를 계속 보내면 매 적재마다 조용히 절반을 버립니다. 로그에는 「자동 정리 1건」만 남고요.
- 6개월 뒤 도메인이 「그건 분면이었다」고 답하면 복구할 원본이 없습니다. 원천을 다시 훑는 수밖에 없고, 원천이 이미 덮어써졌다면 그것도 끝입니다.

반대 방향의 비용을 보면 차이가 분명합니다.

| 선택 | 오탐일 때 비용 | 놓쳤을 때 비용 |
|---|---|---|
| 목록만 뽑는다 | 사람이 한 줄 읽고 「정상」 판단 | 다음 주 보고서에 또 나옴 |
| 자동으로 지운다 | **정당한 데이터가 영구 소실** | — |

오탐이 정상적으로 섞이는 검사에서는 이 비대칭이 결론을 강제합니다. **되돌릴 수 있는 쪽으로 기울여라.** 13.2절의 차단 기준 — 「되돌릴 수 없는가」 — 이 그대로 여기에도 적용되는 겁니다. 자동 수정은 되돌릴 수 없는 쪽이니 하지 않습니다.

### 예제 4가 이걸 실물로 보여 준다

`ex4_regression.py`의 `migrate()`가 정확히 「좋은 뜻의 자동 수정」입니다.

```python
def migrate(rows):
    out = []
    for r in rows:
        r = dict(r)
        if r.get("type") == "부품" and not r.get("category"):
            r["category"] = "미분류"
        out.append(r)
    return out
```

카테고리 빈칸을 「미분류」로 채웠습니다. 결과는 이랬죠.

> «카테고리 없음»을 «미분류»로 채웠더니 «카테고리 없는 부품» 질의가 빈 답을 낸다.
> 데이터는 더 깨끗해졌고, 형태 검사도 통과하고, 노드 수도 그대로다.
> 그런데 그 질의에 기대던 화면이 조용히 비었다.

**형태 검사도 통과하고 노드 수도 같습니다.** 자동 수정이 위험한 건 티가 나서가 아니라 **티가 안 나서**예요. 「없음」과 「미분류로 채워짐」의 구분이 사라졌고, 그 구분에 의존하던 질의가 조용히 죽었습니다. 다중 소속을 자동으로 지웠을 때 벌어질 일도 정확히 같은 모양입니다.

그리고 예제 3의 `NODES`를 보면 「미분류」 허브가 30개 엣지를 받는 **슈퍼 노드**로 이미 등장합니다. 자동 수정 하나가 다른 스멜을 키운 셈이죠.

```python
    "hub":  {"label": "Category", "name": "미분류"},
```

### 다음 장으로 이어지는 같은 논리

13장 끝의 예고가 이 논리의 확장입니다.

> 같은 사람이 노드 네 개로 앉아 있는 상황을 어떻게 푸는지, 그리고 **왜 자동 병합이 위험한지** 제대로 봅니다.

「중복 의심」도 「다중 소속」과 같은 이유로 2층입니다. 지우는 대신 합칠 뿐, 잘못 합치면 되돌릴 수 없다는 성질이 똑같아요. `smell_duplicate`가 `가온테크`와 `가온테크(주)`를 묶어 주긴 하지만, 그건 **같은 회사라는 판정이 아니라 같은 회사인지 확인해 달라는 요청**입니다.

## 다섯 스멜이 2층인 이유는 각각 다르다

예제 3의 마무리를 표로 정리하면 「다중 소속」이 왜 특별한지가 보입니다.

| 스멜 | SHACL로 못 잡는 이유 | 성격 |
|---|---|---|
| 슈퍼 노드 | 「평균의 5배」는 그래프 전체를 봐야 나오는 **상대값** | 전역 통계 |
| 고아 노드 | 잡히긴 하는데 종류가 많아 일일이 못 씀 | 규모 문제 |
| 사이클 | SHACL에 「순환 없음」 제약이 **없음** | 표현력 부족 |
| 중복 의심 | 「비슷하다」는 판정이라 참/거짓이 아님 | 근사 판정 |
| **다중 소속** | **위반이 아닐 수도 있음. 도메인이 정함** | **정책 미결정** |

앞의 넷은 「그래프가 어떤가」를 못 재는 문제입니다. 재는 방법이 없거나, 값이 상대적이거나, 애매하거나.

다중 소속만 성격이 다릅니다. **재는 건 완벽하게 됩니다.** `Counter` 한 줄이면 끝나요. 못 하는 건 **판정**입니다. 필요한 정보가 그래프 안이 아니라 사람 머릿속에 있으니까요.

그래서 다중 소속은 다섯 중 유일하게 **정답이 정해지면 1층으로 승격되는** 스멜입니다. 도메인이 「배타적이다」라고 답하는 순간 `sh:maxCount 1`이 되고, 그 뒤로는 스멜이 아니라 위반이에요.

## 외워 두면 좋은 골격

1. **스멜 ≠ 위반.** 벡의 할머니 — 냄새가 나면 **들여다보라**. 냄새 자체가 고장이라는 게 아니다.
2. **판정 기준은 축의 성격.** 배타적 분류(taxonomy)면 위반, 다중 분면(facet)이면 정상. 코드는 엣지 개수만 보이므로 이걸 구분할 수 없다.
3. **가장 흔한 건 「아직 안 정했다」.** 이때 스멜 목록은 고칠 목록이 아니라 **물어볼 목록**이다.
4. **자동 수정은 비가역.** 어느 엣지를 지울지 고를 근거가 없고, 지우면 증상과 증거가 함께 사라지며, 다음 검사는 「깨끗하다」고 보고한다.
5. **정해지면 승격.** 도메인이 배타성을 선언하는 순간 2층 스멜 → 1층 `sh:maxCount 1` + `sh:Violation`으로 내려간다.
