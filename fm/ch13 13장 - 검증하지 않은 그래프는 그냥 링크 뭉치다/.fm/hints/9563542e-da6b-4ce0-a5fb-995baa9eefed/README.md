# `ex4_regression.py`의 골든 데이터셋

## 한 줄 답

**손으로 만든 작은 표본이고, 답을 사람이 확인해 고정해 둔 것**입니다. `ex4_regression.py`에서는 **부품 3건과 제품 2건, 모두 5건**으로 구성됩니다.

---

## 1. 실제 코드

`content/ch13/code/ex4_regression.py`의 첫머리에 그대로 박혀 있습니다.

```python
# 골든 데이터셋 — 손으로 만든 작은 표본. 답을 사람이 확인해 뒀다.
GOLDEN = [
    {"id": "P1", "type": "부품", "category": "체결", "supplier": "가온테크"},
    {"id": "P2", "type": "부품", "category": "전자", "supplier": "나루소프트"},
    {"id": "P3", "type": "부품", "category": None,   "supplier": "가온테크"},
    {"id": "D1", "type": "제품", "parts": ["P1", "P2"], "recalled": True},
    {"id": "D2", "type": "제품", "parts": ["P2", "P3"], "recalled": False},
]
```

세 가지 성질을 모두 갖고 있어야 「골든」입니다.

| 성질 | 이 코드에서 |
|---|---|
| **손으로 만든다** | 운영 데이터를 덤프한 게 아니라 사람이 한 줄씩 적었다 |
| **작다** | 5건. 사람이 눈으로 전부 훑고 답을 셀 수 있는 크기 |
| **답이 고정돼 있다** | 아래 `EXPECTED`가 사람이 확인한 정답 |

### 답을 고정하는 부분

```python
# 역량 질의 — 12장에서 뽑은 그것. 이 답이 바뀌면 안 된다.
def q_recalled_with(rows, part): ...
def q_by_supplier(rows, sup): ...
def q_uncategorized(rows): ...

QUERIES = {
    "P2 를 쓴 리콜 제품":   lambda rows: q_recalled_with(rows, "P2"),
    "가온테크 납품 부품":    lambda rows: q_by_supplier(rows, "가온테크"),
    "카테고리 없는 부품":    q_uncategorized,
}

# 기대값 — 처음 만들 때 사람이 확인하고 고정한다
EXPECTED = {name: fn(GOLDEN) for name, fn in QUERIES.items()}
```

즉 골든 데이터셋은 **「데이터 5건」이 아니라 「데이터 5건 + 그 위에서의 정답」 한 쌍**입니다. 데이터만 있고 기대값이 없으면 그냥 샘플이지 골든이 아닙니다.

> 예제에서는 `EXPECTED`를 실행 시점에 `GOLDEN`으로부터 계산해 보여 주지만(교보재라 짧게 쓴 것입니다), 실제 회귀 테스트에서는 **기대값을 파일에 문자열로 박아 두고 커밋**해야 합니다. 그래야 질의 함수 자체가 바뀌었을 때도 잡힙니다.

### 이 데이터셋이 잡아내는 것

예제의 스키마 변경은 「카테고리 없음을 `None` 대신 `미분류`로 채운다」입니다.

```python
def migrate(rows):
    ...
    if r.get("type") == "부품" and not r.get("category"):
        r["category"] = "미분류"
```

결과는 이렇게 갈립니다.

| 검사 | 결과 |
|---|---|
| 1. SHACL류 형태 검사 (카테고리 누락 0건) | **통과** |
| 2. 노드·엣지 수 검사 (5건, 타입 분포 동일) | **통과** |
| 3. 역량 질의 「카테고리 없는 부품」 | **실패** — 전 `['P3']` → 후 `[]` |

데이터는 더 깨끗해졌고, 형태 검사도 통과하고, 노드 수도 그대로인데 **그 질의에 기대던 화면이 조용히 비었습니다.** 이게 회귀 테스트에 「형태」뿐 아니라 「질의」가 들어가야 하는 이유이고, 골든 데이터셋이 존재하는 이유입니다.

## 2. 왜 30~50건이면 충분한가 — 크기보다 경계 사례

이 장의 요약은 이렇게 못 박습니다.

> 골든 데이터셋은 30~50건이면 충분하고, 크기보다 경계 사례가 중요해요.

### 크게 만들어도 이득이 없는 이유

- **회귀 테스트는 통계가 아니다.** 「평균적으로 잘 동작하는가」를 재는 게 아니라 「이 입력에 이 답이 나오는가」를 고정하는 겁니다. 같은 모양의 평범한 행 1만 건은 1건과 정보량이 같습니다. 10만 건을 넣어도 잡히는 건 첫 1건이 잡는 것과 똑같습니다.
- **정답을 사람이 확인할 수 있어야 한다.** 골든의 정의 자체가 「사람이 답을 확인해 고정했다」입니다. 1만 건짜리 표본의 정답은 아무도 손으로 못 셉니다. 그러면 기대값이 **그때 코드가 뱉은 값**이 되고, 버그가 있으면 버그째로 고정됩니다. 이건 테스트가 아니라 스냅숏 박제입니다.
- **실패했을 때 원인이 보여야 한다.** 5건짜리에서 `['P3'] → []`가 나오면 원인이 즉시 보입니다. 1만 건에서 「3,142건 → 2,987건」이 나오면 디버깅이 다시 시작됩니다. 테스트의 가치는 실패를 알리는 데 있는 게 아니라 **원인을 가리키는 데** 있습니다.
- **CI에서 매 커밋 돌아야 한다.** 크면 느리고, 느리면 안 돌리게 되고, 안 돌리면 없는 것과 같습니다. 5건짜리 예제가 「의존성 없음 / `python3 ex4_regression.py`」로 끝나는 게 우연이 아닙니다.
- **손으로 유지해야 한다.** 골든은 스키마가 바뀌면 사람이 고칩니다(4절 참고). 50건은 고칠 수 있고 5,000건은 못 고칩니다. 못 고치면 방치되고, 방치된 골든은 곧 꺼집니다.

### 그래서 30~50건이라는 숫자

의미 있는 경계 사례 유형이 대략 그 정도 개수이기 때문입니다. 유형당 1~2건씩 담다 보면 자연히 그 부근에서 멈춥니다. **「30~50건을 채워야 한다」가 아니라 「경계 사례를 다 담았더니 30~50건이더라」**가 맞는 방향입니다. 경계 사례를 다 담고 20건이면 20건으로 충분하고, 100건인데 전부 평범한 행이면 0건짜리와 다를 게 없습니다.

**판단 기준은 개수가 아니라 이겁니다: 「골든에 없는 모양의 데이터 때문에 운영에서 사고가 났는가?」** 났다면 그 모양을 골든에 추가합니다. 이게 골든이 커지는 유일하게 정당한 이유입니다.

## 3. 골든 데이터셋이 갖춰야 할 경계 사례 유형

평범한 행이 아니라 **「여기서 갈린다」 지점**을 담아야 합니다. 예제의 5건도 이 원칙으로 짜였습니다.

### 예제가 이미 담고 있는 것

| 경계 사례 | 예제에서 |
|---|---|
| **널 / 빈 값** | `P3`의 `category: None` — 이 한 줄이 3절 마이그레이션 회귀를 통째로 잡아냅니다 |
| **다중 참조(공유 노드)** | `P2`가 `D1`, `D2` 양쪽에 들어감 — 한쪽만 고치는 변경을 잡습니다 |
| **불리언 양쪽** | `recalled: True`(D1)와 `False`(D2) 둘 다. 한쪽만 있으면 필터가 뒤집혀도 안 걸립니다 |
| **그룹당 복수/단수** | 가온테크 2건(`P1`, `P3`), 나루소프트 1건(`P2`) — 그룹 집계가 1건일 때 깨지는 버그를 잡습니다 |
| **타입 혼재** | 부품·제품이 한 리스트에 — `type` 필터가 빠져도 답이 같아 보이는 상황을 막습니다 |

### 실제 그래프에서 더 넣어야 하는 유형

- **널·빈 값·빈 문자열의 구분** — `None`, `""`, `"  "`, 속성 자체가 없음. 이 넷은 다른 겁니다. 마이그레이션은 늘 이 사이에서 사고를 냅니다.
- **다중 소속** — 한 노드가 카테고리 두 개, 부서 두 개에 걸린 경우. 13.3절이 SHACL로는 위반인지 아닌지 판정 못 한다고 한 그 유형입니다. 골든에 하나 박아 두면 「단일 소속 가정」을 몰래 넣는 변경이 걸립니다.
- **고아 노드** — 어디에도 안 연결된 노드. 조인 방식을 inner에서 outer로 바꾸는(또는 그 반대) 변경에서 답이 갈립니다.
- **경계 날짜 / 경계 수치** — 구간의 시작·끝 정확히 그 값(`>=`냐 `>`냐), 자정, 월말, 윤일, 타임존 경계, 0, 음수, 최대 길이.
- **사이클** — A→B→C→A. 재귀 질의가 무한 루프에 빠지는지, 깊이 제한이 답을 자르는지 확인합니다.
- **자기 참조** — A→A. 사이클보다 앞서 깨지는 경우가 많습니다.
- **중복 의심 쌍** — 이름만 다르고 같은 실체로 보이는 노드 둘. 14장 개체 해소로 이어집니다.
- **동명이인 / 동명이물** — 이름이 같은 서로 다른 노드. 위와 정반대 방향의 함정입니다.
- **슈퍼 노드** — 연결이 유난히 많은 노드 하나. 성능뿐 아니라 상위 N개 자르기 로직에서 답이 갈립니다.
- **유니코드·인코딩** — 한글, 이모지, 결합 문자, 대소문자, 전각/반각. 정규화 규칙을 바꾸면 여기서 터집니다.
- **극단 카디널리티** — 0건, 정확히 1건, 그리고 여러 건. 특히 **0건과 1건**은 별개로 넣어야 합니다.
- **의도적 위반 1건** — 검증이 잡아야 하는 데이터. 검증기를 끄거나 규칙을 느슨하게 만든 변경이 조용히 지나가지 않게 합니다.

**규칙 하나:** 각 행에는 **「이 행이 왜 여기 있는지」 주석을 답니다.** 이유가 적혀 있지 않은 행은 나중에 아무도 못 지우고, 못 지우면 골든이 계속 부풀기만 합니다.

## 4. 골든 데이터는 낡는다

이게 골든 데이터셋의 진짜 비용이고, 대개 도입할 때 계산에 안 넣는 부분입니다.

### 무엇이 낡는가

- **스키마가 바뀌면 골든이 컴파일부터 안 된다.** 속성 이름이 바뀌고, 타입이 쪼개지고, 관계 방향이 뒤집힙니다. 그때마다 골든 데이터와 기대값을 **손으로** 고쳐야 합니다.
- **도메인 자체가 변한다.** 예제로 치면 「리콜」의 정의가 바뀌거나, 「미분류」가 정식 카테고리로 승격되는 식입니다. 그러면 예전 기대값은 정답이 아니게 됩니다.
- **운영 데이터의 모양이 골든과 멀어진다.** 골든은 만든 날의 세계에 고정돼 있는데, 실제 데이터에는 새 소스, 새 패턴, 새 이상값이 계속 들어옵니다. 어느 순간 **골든은 다 통과하는데 운영은 계속 터지는** 상태가 됩니다. 이게 낡은 골든의 전형적인 증상입니다.

### 낡으면 벌어지는 일

1. 스키마를 바꿀 때마다 골든 테스트가 실패한다.
2. 원인을 따지기 귀찮으니 **기대값을 새 출력으로 덮어쓴다**(「골든 갱신」 버튼).
3. 몇 번 반복하면 아무도 기대값을 읽지 않는다. 테스트는 늘 초록불이다.
4. 이제 골든은 **회귀를 못 잡는다.** 13.2절의 「검증을 우회하면 우회 경로가 주 경로가 된다」와 정확히 같은 실패 구조입니다.

### 갱신 규칙 — 언제 고치고 언제 안 고치는가

기대값이 바뀌었을 때 던져야 하는 질문은 딱 하나입니다.

> **이 답의 변화는 의도한 것인가?**

| 상황 | 조치 |
|---|---|
| **의도한 변화** (도메인 정의가 실제로 바뀌었다) | 기대값을 갱신한다. 단, **변경 이유를 커밋 메시지에 남기고 사람이 리뷰한다.** 「왜 `['P3']`이 `[]`가 되는 게 맞는지」가 적혀 있어야 한다 |
| **의도하지 않은 변화** (모양만 맞추다 뜻이 달라졌다) | 기대값이 아니라 **코드/마이그레이션을 고친다.** 예제의 「미분류」 사례가 여기 해당한다 |
| **판단이 안 선다** | 갱신하지 말고 사람에게 올린다. 애매한 걸 자동으로 통과시키는 순간 골든은 죽는다 |

### 유지 비용을 낮추는 방법

- **기대값 갱신은 자동으로 하되, 자동으로 커밋되지 않게 한다.** `--update-golden` 같은 플래그는 diff를 만들 뿐이고, 그 diff는 사람이 읽고 승인해야 합니다.
- **골든을 작게 유지한다.** 30~50건이라는 상한은 정확도 기준이 아니라 **유지 가능성 기준**입니다.
- **행마다 이유 주석을 단다.** 스키마가 바뀌었을 때 「이 행이 지키려던 게 뭐였는지」를 알아야 옳게 고칠 수 있습니다.
- **사고가 나면 골든에 행을 추가한다.** 골든이 자라는 건 이 경로로만 허용합니다. 운영 사고 → 재현하는 최소 행 1건 추가 → 다시는 안 나게 고정.
- **주기적으로 「운영 데이터에는 있는데 골든에는 없는 모양」을 뽑아 본다.** 13.3절의 그래프 스멜 목록을 그대로 쓸 수 있습니다. 이게 골든이 낡았는지 재는 가장 실용적인 지표입니다.

## 5. 정리

- 골든 데이터셋 = **사람이 손으로 만든 작은 표본 + 사람이 확인해 고정한 정답**.
- `ex4_regression.py`에서는 **부품 3건(`P1`, `P2`, `P3`) + 제품 2건(`D1`, `D2`) = 5건**.
- 크기는 30~50건이면 충분하다. **평범한 행을 늘리는 게 아니라 경계 사례를 채우는 게 일이다.**
- 필수 경계 사례: 널/빈 값, 다중 소속, 고아 노드, 경계 날짜·수치, 사이클, 중복 의심, 0건/1건, 의도적 위반.
- 골든은 낡는다. **의도한 변화면 이유를 적고 갱신하고, 의도하지 않은 변화면 골든이 아니라 코드를 고친다.** 기대값을 습관적으로 덮어쓰기 시작하면 그 골든은 이미 죽은 것이다.
