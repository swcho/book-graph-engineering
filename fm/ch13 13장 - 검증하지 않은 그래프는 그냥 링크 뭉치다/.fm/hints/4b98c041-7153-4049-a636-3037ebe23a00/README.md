# 중복 의심 스멜이 SHACL로 판정 불가능한 이유

## 질문과 답

**Q.** 중복 의심 스멜이 SHACL로 판정 불가능한 이유는 무엇인가?

**A.** '비슷하다'는 판정이라 참/거짓이 아니기 때문이다. 예제는 "(주)"와 공백을 제거해 정규화한 이름이 같은지를 본다.

---

## 1. 어디서 나온 이야기인가

13장 3절 「SHACL로 못 잡는 것들」입니다. 예제 `ex3_graph_smells.py`는 스키마 검증으로는 안 잡히고 **세어 봐야 보이는** 다섯 가지 그래프 스멜을 다룹니다.

| 스멜 | SHACL로 못 잡는 이유 |
|---|---|
| 슈퍼 노드 | 「평균의 5배」는 데이터 전체를 봐야 나오는 상대값이다 |
| 고아 노드 | 형태 제약으로 잡히긴 하는데, 종류가 많아 일일이 못 쓴다 |
| 사이클 | SHACL에 「순환 없음」 제약이 없다 |
| **중복 의심** | **「비슷하다」는 판정이라 참/거짓이 아니다** |
| 다중 소속 | 위반이 아닐 수도 있다. 도메인이 정한다 |

각각 이유가 **다르다**는 게 이 표의 핵심입니다. 「SHACL이 약해서」가 아니라, 이유가 다섯 가지로 갈립니다. 중복 의심은 그중 「참/거짓 판정이 아니다」에 해당합니다.

## 2. 예제의 정규화 코드

```python
def smell_duplicate(nodes):
    def norm(s):
        return (s or "").replace("(주)", "").replace(" ", "").strip()
    groups = defaultdict(list)
    for v, a in nodes.items():
        if "name" in a:
            groups[(a["label"], norm(a["name"]))].append(v)
    return {k: v for k, v in groups.items() if len(v) > 1}
```

입력 데이터는 이렇습니다.

```python
"dupA": {"label": "Supplier", "name": "가온테크"},
"dupB": {"label": "Supplier", "name": "가온테크(주)"},
```

`norm("가온테크")`도 `"가온테크"`, `norm("가온테크(주)")`도 `"가온테크"`. 그래서 `(Supplier, "가온테크")` 키에 `dupA`, `dupB`가 함께 묶이고, 크기가 2 이상인 그룹만 남겨서 「중복 의심」으로 보고합니다.

```
[중복 의심] 이름을 정규화하면 같음 — 1건
    Supplier «가온테크» : dupA, dupB
```

`(a["label"], norm(a["name"]))` 튜플이 키라는 점도 봐 두세요. **라벨이 다르면 이름이 같아도 묶지 않습니다.** 이름이 같은 `Supplier`와 `Part`를 같은 것으로 볼 이유는 없으니까요.

### 이게 블로킹 키(blocking key)다

이 `norm()` 결과가 엔티티 해소에서 말하는 **블로킹 키**입니다. N개 노드를 전부 짝지어 비교하면 N²/2번인데(노드 10만 개면 50억 번), 정규화 키가 같은 것끼리만 후보로 좁히면 비교 횟수가 확 줄어듭니다. 즉 이 코드는 「중복이다」를 판정하는 게 아니라 **「사람이 볼 후보를 추린다」**가 목적입니다. 14장에서 이 이름이 그대로 나옵니다.

## 3. 「결정론적 규칙인데 왜 SHACL이 아닌가」

여기가 이 카드의 함정입니다. 반문이 나올 만합니다.

> `"(주)" 제거 + 공백 제거 후 문자열 비교`는 완전히 결정론적이잖아. 같으면 참, 다르면 거짓. 참/거짓이 분명한데 왜 SHACL 제약이 아닌가?

이유가 두 가지입니다.

### (1) 쌍(pair) 단위 비교라 focus node 하나로 판정이 안 된다

SHACL의 실행 모델은 **focus node 하나를 잡고 그 노드의 값들이 shape에 맞는지 본다**입니다. `sh:minCount`, `sh:pattern`, `sh:datatype`, `sh:in` — 13장 `shapes.ttl`의 제약을 보면 전부 그렇습니다.

```turtle
sh:property [
    sh:path ex:bizNumber ;
    sh:minCount 1 ; sh:maxCount 1 ;
    sh:pattern "^[0-9]{3}-[0-9]{2}-[0-9]{5}$" ;
    sh:severity sh:Violation ;
    sh:message "사업자번호가 없거나 형식이 틀렸다" ] ;
```

`ex:Naru` 하나만 보면 `"1234567890"`이 패턴에 안 맞는다는 걸 판정할 수 있습니다. 이웃도, 다른 회사도 볼 필요가 없습니다.

그런데 중복 의심은 다릅니다. `dupA`만 놓고 보면 「가온테크」는 아무 문제가 없습니다. `dupB`만 놓고 봐도 「가온테크(주)」는 멀쩡합니다. **위반은 노드에 있는 게 아니라 두 노드의 관계에 있습니다.** 그리고 SHACL 보고서(`sh:ValidationResult`)는 `sh:focusNode`가 하나입니다. 「이 둘이 서로 중복 같다」를 적을 자리가 구조적으로 없습니다.

13장 예제 1이 보고서를 읽는 코드를 보면 이 구조가 그대로 드러납니다.

```python
node = str(report.value(r, SH.focusNode)).rsplit("/", 1)[-1]
```

한 결과에 노드 하나. 둘 중 누구를 「위반자」로 적을 건가요? 둘 다 적으면 같은 사실이 두 번 보고되고, 한쪽만 적으면 어느 쪽이 진짜인지를 검증기가 결정한 셈이 됩니다. 검증기가 할 일이 아닙니다.

슈퍼 노드가 「데이터 전체를 봐야 나오는 상대값」이라 안 되는 것과 같은 계열의 문제입니다. **SHACL은 지역적(local)이고, 중복 의심은 전역적(global)입니다.**

> 정확히 하자면, SHACL-AF의 `sh:sparql` 제약으로 다른 노드를 훑는 질의를 억지로 짜 넣을 수는 있습니다. 기술적으로 불가능하다는 뜻은 아닙니다. 하지만 그렇게 짜도 성능이 무너지고(사실상 전체 조인), 보고서가 여전히 focus node 하나에 매달리며, 무엇보다 아래 (2)번 문제가 그대로 남습니다.

### (2) 임계·유사도 선택이 도메인 판단이다

`norm()`의 규칙을 보세요.

- `"(주)"`를 지운다 → 왜 `(주)`만? `㈜`, `주식회사`, `(유)`, `Co., Ltd.`는?
- 공백을 지운다 → 대소문자는? 전각/반각은? 유니코드 정규화(NFC/NFKC)는?
- 완전 일치만 본다 → 「가온테크」와 「가온테그」는? 편집 거리 1이면 같은 회사인가?

이 선택지 하나하나가 **도메인 판단**입니다. 제조사 부품 공급업체 목록에서 「가온테크」와 「가온테크(주)」는 십중팔구 같은 회사입니다. 하지만 법인 등기 데이터베이스라면 법인격이 다른 별개의 실체일 수 있습니다. 같은 규칙이 도메인에 따라 정답이기도 하고 오답이기도 합니다.

그리고 규칙을 유사도 점수로 바꾸는 순간 **임계값**이 필요합니다. 0.85 이상이면 중복인가, 0.9인가? 이 숫자는 명세에서 나오는 게 아니라 「오탐을 얼마나 감수할 것인가」라는 운영 판단에서 나옵니다. 정밀도를 올리면 놓치는 중복이 늘고, 재현율을 올리면 엉뚱한 병합이 늘어납니다.

**참/거짓이 아니라는 말의 진짜 뜻이 이겁니다.** 계산 결과가 불확실하다는 뜻이 아니라, **「같다」의 정의 자체가 조직이 정하는 것**이라는 뜻입니다. SHACL 제약으로 굳혀 버리면 그 임의의 선택이 「표준 위반」이라는 권위를 얻고, 파이프라인이 그걸 근거로 적재를 막습니다. 13장 2절이 경고하는 바로 그 상황 — 사람들이 검증을 우회하고, 우회 경로가 주 경로가 되는 — 이 만들어집니다.

## 4. 그래서 두 겹으로 간다

```
1층 SHACL — 참/거짓이 분명한 형태 제약
2층 스멜  — 세어 보고 «이상하면 사람이 본다»
2층은 자동으로 고치지 않는다. 목록만 뽑아 주는 게 일이다.
```

중복 의심은 2층입니다. 그리고 2층의 출력은 **차단이 아니라 목록**입니다. `smell_duplicate()`가 병합을 하지 않고 `{키: [노드들]}` 딕셔너리만 반환하는 게 그 설계입니다.

여기서 `sh:severity`를 떠올릴 수 있습니다. 「중복 의심을 `sh:Warning`으로 넣으면 되지 않나?」 심각도로 낮추는 건 (2)번의 도메인 문제를 완화하긴 하지만 (1)번은 그대로입니다. focus node가 하나라는 구조는 심각도를 바꿔도 변하지 않습니다.

## 5. 14장으로 이어지는 지점

13장 말미가 명시적으로 넘깁니다.

> **다음 장에서 뒤집히는 것:** 이 장에서 「중복 의심」을 스멜로만 다뤘습니다. 다음 장이 그 본편이에요. 같은 사람이 노드 네 개로 앉아 있는 상황을 어떻게 푸는지, 그리고 왜 자동 병합이 위험한지 제대로 봅니다.

14장 「같은 사람이 노드 네 개로 앉아 있다」가 **엔티티 해소(entity resolution)** 편입니다. 13장이 남긴 세 가지가 그대로 14장의 출발점이 됩니다.

| 13장이 남긴 것 | 14장이 다루는 것 |
|---|---|
| `norm()` 한 줄짜리 정규화 | 블로킹 전략, 유사도 함수, 임계값 튜닝 |
| 쌍 단위라 SHACL에 못 넣음 | 후보 쌍 생성과 쌍 단위 매칭 파이프라인 |
| 「자동으로 고치지 않는다」 | 자동 병합이 왜 위험한가, 사람 검토(human-in-the-loop) |

13장이 「검증기로는 여기까지」라는 **경계선을 긋는** 장이라면, 14장은 그 경계 바깥을 다루는 별도 파이프라인의 장입니다. 검증(validation)과 해소(resolution)는 다른 문제이고, 다른 도구가 필요합니다 — 13장 1절의 「추론기와 검증기는 다른 물건이다」와 정확히 같은 형태의 교훈입니다.

## 6. 한 줄로 외울 것

**중복 의심은 노드 하나가 아니라 노드 쌍의 성질이고, 「같다」의 기준을 도메인이 정한다. SHACL은 focus node 하나에 대한 참/거짓만 말할 수 있으므로 여기서 손을 뗀다. 정규화 키는 판정이 아니라 사람이 볼 후보를 추리는 장치(블로킹 키)이며, 그 본편이 14장 엔티티 해소다.**

## 자주 헷갈리는 것

- **「SHACL이 문자열 비교를 못 해서」가 아닙니다.** `sh:pattern`으로 정규식도 씁니다. 문제는 비교 대상이 **다른 노드**라는 것입니다.
- **「불확실해서」보다 「기준이 도메인 소관이라서」가 정확합니다.** `norm()` 자체는 100% 결정론적입니다. 결정론적이지 않은 건 `norm()`의 **규칙을 무엇으로 할지**입니다.
- **고아 노드와 헷갈리지 마세요.** 고아 노드는 SHACL로 실제로 잡힙니다(`shapes.ttl`의 `sh:inversePath ex:signed` + `sh:minCount 1`). 못 잡는 게 아니라 「종류가 많아 일일이 못 쓴다」가 이유입니다.
