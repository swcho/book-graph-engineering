# 회귀 테스트에 질의가 들어가야 하는 이유

> **Q.** 회귀 테스트에 질의가 들어가야 하는 이유는 무엇인가?
>
> **A.** 형태만 검사하면 '모양은 맞는데 뜻이 달라진' 변경을 잡지 못하기 때문이다. 화면이 조용히 비는 사고가 이렇게 생긴다.

---

## 1. 한 문장으로

**스키마 검증은 "데이터가 규칙대로 생겼는가"를 묻고, 질의 회귀 테스트는 "그 데이터가 여전히 같은 답을 내놓는가"를 묻는다.** 앞의 질문에 전부 통과하면서 뒤의 질문에서 떨어지는 변경이 있고, 그게 제일 조용하게 사고를 낸다.

---

## 2. 이 장의 예제가 보여 주는 사고 시나리오

`code/ex4_regression.py`가 만든 상황을 그대로 따라가 보자.

### 골든 데이터셋 (변경 전)

| id | type | category | supplier |
|---|---|---|---|
| P1 | 부품 | 체결 | 가온테크 |
| P2 | 부품 | 전자 | 나루소프트 |
| **P3** | 부품 | **None** | 가온테크 |

### 변경 내용

> "카테고리가 비어 있으면 보기 안 좋으니 `None` 대신 `"미분류"`로 채우자."

누가 봐도 **데이터를 개선하는** 마이그레이션이다. 널을 없애고 기본값을 채우는, 흔하디흔한 정리 작업.

```python
def migrate(rows):
    for r in rows:
        if r.get("type") == "부품" and not r.get("category"):
            r["category"] = "미분류"   # None → "미분류"
```

### 세 겹의 검사 결과

| 검사 | 무엇을 보는가 | 결과 |
|---|---|---|
| ① SHACL류 **형태 검사** | `category` 누락 건수 | **통과** (누락 0건 — 오히려 좋아졌다) |
| ② **노드·엣지 수 검사** | 노드 수, 타입 분포 | **통과** (전후 완전히 동일) |
| ③ **역량 질의 검사** | 질의 3개의 답 | **1건 실패** |

실패한 질의는 "카테고리 없는 부품":

```
[실패] 카테고리 없는 부품
      전: ['P3']
      후: []
```

`q_uncategorized()`는 `not r.get("category")`로 판정한다. `None`은 falsy이지만 `"미분류"`는 truthy다. **질의는 한 줄도 안 고쳤는데 답이 `['P3']`에서 `[]`로 바뀌었다.**

### 왜 이게 무서운가

- 어디에도 **오류가 안 난다.** 예외도, 위반 보고서도, 로그도 없다.
- 데이터는 **객관적으로 더 깨끗해졌다.** 널이 사라졌으니까.
- 통계 지표는 **미동도 없다.** 노드 수도, 타입 분포도 그대로.
- 다만 "카테고리 미입력 부품 처리 대기" 대시보드가 **조용히 빈 화면**이 된다. 담당자는 "이번 주는 밀린 게 없구나"라고 읽는다. 실제로는 P3이 영원히 처리되지 않는다.

이게 예제 마지막 줄이 말하는 그것이다.

> 이게 회귀 테스트에 «질의»가 들어가야 하는 이유다.
> 형태만 검사하면 «모양은 맞는데 뜻이 달라진» 변경을 못 잡는다.

## 3. 역량 질의(competency question)란 무엇인가

### 정의

**역량 질의(CQ, competency question)** 는 온톨로지/지식 그래프가 **답할 수 있어야 하는 질문의 목록**이다. Grüninger & Fox의 방법론(1995)에서 시작해 Uschold & King, Ontology Development 101(Noy & McGuinness, Stanford Protégé), NeOn 방법론 등 거의 모든 온톨로지 공학 방법론이 채택한 개념이다.

핵심 아이디어는 이렇다.

> 온톨로지의 **범위와 성공 기준을 "무엇을 모델링할까"가 아니라 "무엇에 답할 수 있어야 하는가"로 정의한다.**

역량 질의는 자연어로 먼저 쓰인다.

- "P2 부품을 사용한 리콜 제품은 무엇인가?"
- "가온테크가 납품한 부품 목록은?"
- "카테고리가 지정되지 않은 부품은 무엇인가?"

그리고 이것이 SPARQL/Cypher 같은 **실행 가능한 질의**로 번역된다. 예제 4의 `QUERIES` 딕셔너리가 바로 그 번역 결과다.

```python
QUERIES = {
    "P2 를 쓴 리콜 제품":   lambda rows: q_recalled_with(rows, "P2"),
    "가온테크 납품 부품":    lambda rows: q_by_supplier(rows, "가온테크"),
    "카테고리 없는 부품":    q_uncategorized,
}
```

### 역량 질의의 두 가지 인생

역량 질의는 원래 **설계 단계의 도구**였다. "이 질문에 답이 안 나오면 온톨로지가 덜 만들어진 것"이라는 완성도 판정 기준.

이 장이 말하는 건 그 다음이다. **설계가 끝난 뒤에도 역량 질의를 버리지 말고, 회귀 테스트 스위트로 승격시켜라.** 12장에서 뽑아 놓은 그 질의들이 그대로 13장의 테스트 케이스가 된다.

```
12장: 역량 질의로 온톨로지 범위를 정한다   (설계 도구)
        ↓ 같은 목록을 재활용
13장: 역량 질의로 회귀를 감시한다          (검증 도구)
```

이 재활용이 공짜에 가깝다는 게 실무적으로 중요하다. 별도로 테스트를 발명할 필요가 없다. 이미 있는 문서를 `assert`로 감싸기만 하면 된다.

> 참고: 키워드 표에서 "역량 질의 회귀 테스트"는 **[실험]** 라벨이다. 역량 질의 개념 자체는 온톨로지 공학의 정착된 개념이지만(1차 출처: [Ontology Development 101](https://protege.stanford.edu/publications/ontology_development/ontology101.pdf)), 이를 CI 회귀 스위트로 상시 운영하는 관행은 아직 표준화된 도구/명세가 없다는 뜻이다.

## 4. 형태 검증 vs 의미 검증

| | **형태(스키마) 검증** | **의미(질의) 검증** |
|---|---|---|
| 질문 | "이 데이터가 규칙대로 **생겼는가**?" | "이 데이터가 여전히 같은 **답**을 내는가?" |
| 도구 | SHACL, ShEx, JSON Schema, DB 제약 | 역량 질의 + 골든 데이터셋 + `assert` |
| 판정 단위 | 노드 하나, 속성 하나 | 질의 하나의 **결과 집합 전체** |
| 잡아내는 것 | 필수 속성 누락, 형식 위반, 카디널리티 위반, 고아 노드 | 값 도메인 변경, 기본값 주입, 관계 방향 반전, 클래스 계층 재편, 매핑 규칙 변경 |
| **못 잡는 것** | **의미 변경** (예제 4의 사고) | 골든 셋에 없는 형태 오류 |
| 실행 시점 | 적재 시(게이트) | 스키마/파이프라인 변경 시(CI) |
| 비유 | 컴파일러 / 타입 체커 | 통합·인수 테스트 |

### SHACL이 원리적으로 잡을 수 없는 이유

SHACL은 **"각 노드가 이 형태를 만족하는가"** 를 노드 단위로 본다. `P3.category == "미분류"`는 어떤 형태 제약으로도 위반이 아니다. 오히려 `sh:minCount 1`을 걸어 두었다면 **변경 전이 위반이고 변경 후가 통과**다.

SHACL이 알 수 없는 것은 이거다.

> **"카테고리 없음"이라는 상태에 업무적 의미가 실려 있었고, 그 의미를 소비하는 질의가 있었다.**

이 정보는 스키마 어디에도 안 적혀 있다. 질의에만 적혀 있다. 그래서 **질의를 테스트에 넣지 않으면 그 지식은 검증 대상 밖으로 나간다.**

13.3절이 말한 SHACL의 한계(슈퍼 노드, 사이클, 중복 의심 같은 그래프 스멜)와는 또 다른 층위다. 정리하면 검증은 세 겹이다.

```
1층  SHACL 형태 제약     — 참/거짓이 분명한 노드 단위 규칙
2층  그래프 스멜         — 세어 봐야 보이는 것. 사람이 판단
3층  역량 질의 회귀      — 답이 그대로인가. 의미 보존 검사
```

## 5. 소프트웨어 테스트 비유: 유닛 테스트 vs 인수 테스트

이 비유가 가장 직관적이다.

| 소프트웨어 | 지식 그래프 |
|---|---|
| **타입 체커 / 린터** | SHACL 형태 제약 |
| **유닛 테스트** — 함수 하나가 규약대로 동작하는가 | 노드/속성 단위 제약 검사 |
| **인수(수용) 테스트** — 사용자가 원하던 일이 실제로 되는가 | **역량 질의 회귀 테스트** |
| **골든/스냅샷 테스트** — 출력이 기준값과 같은가 | 골든 데이터셋 + 기대 답 고정 |

### 리팩터링 비유

`migrate()`는 코드로 치면 **리팩터링**이다. "동작은 그대로 두고 내부만 정리한다"고 믿고 하는 작업.

리팩터링이 안전한 유일한 이유는 **테스트 스위트가 동작 보존을 증명해 주기 때문**이다. 테스트가 없으면 그건 리팩터링이 아니라 그냥 변경이다.

데이터/스키마 마이그레이션도 똑같다.

- 형태 검사만 있다 = **타입만 맞으면 통과시키는 상태.** "컴파일은 되네" 수준.
- 질의 회귀가 있다 = **동작이 보존됐음을 증명한 상태.**

컴파일이 된다고 프로그램이 맞게 도는 게 아니듯, SHACL을 통과했다고 그래프가 맞는 답을 내는 게 아니다.

### "조용한 실패"의 계보

소프트웨어에서도 제일 잡기 어려운 버그는 크래시가 아니라 **잘못된 값을 조용히 반환하는 것**이다. 예제 4의 빈 결과가 정확히 그 부류다. 예외를 던졌다면 오히려 다행이었을 것이다.

## 6. 실무 지침: 무엇을 회귀에 넣을 것인가

### 6.1 대시보드가 실제로 쏘는 질의를 넣어라

가장 강력한 원칙이다. 상상 속의 질의가 아니라 **프로덕션이 실제로 실행하는 질의**를 테스트에 넣는다.

- BI 대시보드 백엔드 쿼리
- API 엔드포인트가 내부적으로 실행하는 SPARQL/Cypher
- 정기 배치 리포트의 집계 질의
- 다른 팀이 붙여 쓰는 공개 질의

**찾는 법**: 질의 로그에서 빈도 상위 N개를 뽑으면 된다. 트리플스토어/그래프 DB의 쿼리 로그, API 게이트웨이 액세스 로그, BI 툴의 저장된 쿼리 목록. 상위 20~30개가 보통 트래픽의 대부분을 차지한다.

이유는 단순하다. **깨졌을 때 사람이 보게 되는 화면이 있는 질의만이 사고가 된다.** 아무도 안 쓰는 질의가 깨지는 건 사고가 아니다.

### 6.2 0건이 정상 답인 질의를 반드시 넣어라 ★

이게 가장 놓치기 쉽고 가장 중요한 항목이다.

**"결과가 있어야 한다"만 검사하면, 결과가 있어야 정상인 질의만 지켜진다.** 예제 4의 실패는 정반대 방향이었다. 있어야 할 답이 사라진 것.

두 방향 모두 테스트해야 한다.

| 유형 | 예 | 깨지는 방식 |
|---|---|---|
| **비어 있으면 안 되는 질의** | "가온테크 납품 부품" → `['P1','P3']` | 매핑 누락, 관계 방향 반전 → 빈 결과 |
| **비어 있어야 정상인 질의** | "사업자번호 형식이 틀린 회사" → `[]` | 검증 우회 경로 생김 → 갑자기 결과가 생김 |
| **0건이 정상 답인 도메인 질의** | "카테고리 없는 부품" → 데이터에 따라 `['P3']` 또는 `[]` | 기본값 주입 → 조용히 `[]` |

특히 세 번째가 예제 4의 사고 유형이다. **"답이 없는 것도 답이다."** 빈 결과 자체가 유의미한 정보를 나르는 질의는, 그 빈 결과가 "정말 없어서 빈 것"인지 "질의가 망가져서 빈 것"인지 구별할 수 없다. 그래서 골든 데이터셋에 **일부러 해당 케이스를 하나 심어 두고**, 그 질의가 정확히 그 하나를 반환하는지 검사한다.

예제 4가 P3(카테고리 `None`)을 골든 셋에 넣어 둔 이유가 이거다. P3이 없었다면 이 사고는 영원히 안 잡혔다.

### 6.3 골든 데이터셋은 30~50건, 크기보다 경계 사례

이 장 요약의 원문 지침이다.

> 골든 데이터셋은 30~50건이면 충분하고, 크기보다 경계 사례가 중요해요.

- **왜 작아야 하는가**: 사람이 손으로 답을 확인해야 하기 때문이다. 답을 사람이 검증할 수 없으면 그건 골든 셋이 아니다. 또 CI에서 매번 빠르게 돌아야 한다.
- **무엇을 넣어야 하는가**: 평범한 케이스는 한두 건이면 충분하다. 나머지 자리는 전부 **경계**에 준다.
  - 널/빈 값 (P3의 `category: None`)
  - 참/거짓 양쪽 (D1 `recalled: True`, D2 `recalled: False`)
  - 다중 소속 (카테고리가 둘인 노드)
  - 관계가 하나도 없는 고아 노드
  - 이름이 비슷한 중복 의심 쌍
  - 0, 음수, 최대값 같은 수치 경계

예제의 골든 셋이 딱 5건인데도 사고를 잡아낸 건 **P3을 의도적으로 심었기 때문**이다. 5만 건짜리 무작위 표본이었어도 못 잡았을 수 있다.

### 6.4 기대값은 처음 만들 때 사람이 확인하고 고정한다

```python
EXPECTED = {name: fn(GOLDEN) for name, fn in QUERIES.items()}
```

예제에서는 편의상 코드로 뽑았지만, **실무에서는 이 값을 파일로 커밋해야 한다.** 그래야 두 가지가 가능하다.

1. 실행할 때마다 계산하면 "현재 동작이 곧 기대값"이 되어 회귀를 영원히 못 잡는다.
2. 기대값이 바뀌었을 때 **diff가 리뷰에 올라온다.** 이게 핵심이다.

**기대값 변경은 코드 리뷰 대상이다.** 테스트가 깨졌을 때 취할 수 있는 행동은 둘 중 하나뿐이다.

- **의도하지 않은 회귀** → 마이그레이션을 고친다.
- **의도한 의미 변경** → 기대값을 갱신하고, **왜 바꿨는지 커밋 메시지에 남기고, 그 질의를 쓰는 소비자에게 알린다.**

두 번째를 아무 설명 없이 하는 순간 테스트는 무의미해진다. "빨간불 나면 기대값 고치기"는 검증을 우회하는 것이고, 13.2절이 경고한 **"우회 경로가 주 경로가 되는" 최악의 패턴**이다.

### 6.5 실패 메시지는 diff로 보여라

```
[실패] 카테고리 없는 부품
      전: ['P3']
      후: []
```

"실패했다"만 찍으면 아무도 안 고친다. **무엇이 어떻게 달라졌는지**가 한눈에 보여야 원인 추적이 시작된다. 결과 집합은 정렬해서 비교한다(예제의 `sorted(...)`) — 순서 차이로 인한 가짜 실패를 없애기 위해서다.

### 6.6 언제 돌리는가

| 시점 | 이유 |
|---|---|
| 온톨로지/스키마 변경 PR | 가장 중요. 의미 변경이 여기서 들어온다 |
| ETL·매핑 규칙 변경 PR | 매핑 한 줄이 결과 집합을 통째로 바꾼다 |
| 데이터 마이그레이션 실행 전후 | 예제 4의 상황 그 자체 |
| 그래프 DB / 추론기 버전 업그레이드 | 추론 결과가 조용히 달라진다 |
| 정기(야간) 배치 | 원천 데이터 변화로 인한 드리프트 감지 |

### 6.7 넣지 말아야 할 것

- **결과가 매번 달라지는 질의** — 현재 시각, 랜덤 샘플, `LIMIT` 없는 전체 스캔. 고정할 수 없으면 골든 테스트가 안 된다. 시간 의존 질의는 기준 시각을 주입해서 고정한다.
- **프로덕션 전체 데이터에 대고 도는 질의** — 느리고, 답이 계속 바뀌어서 기대값을 고정할 수 없다. 골든 셋이라는 별도의 작은 고정 데이터에 대고 돌려야 한다.
- **너무 많은 질의** — 200개를 넣으면 아무도 실패를 안 본다. 대시보드 상위 20~30개 + 경계 사례 질의 몇 개면 충분하다.

## 7. 체크리스트

- [ ] 12장에서 뽑은 역량 질의 목록이 코드로 존재하는가
- [ ] 프로덕션 질의 로그 상위 N개가 회귀 스위트에 들어 있는가
- [ ] **0건이 정상 답인 질의**가 최소 하나 이상 있는가
- [ ] 그 0건 케이스를 유발하는 데이터가 골든 셋에 실제로 심겨 있는가
- [ ] 골든 데이터셋이 30~50건 이내이고 경계 사례 위주인가
- [ ] 기대값이 파일로 커밋되어 있고, 변경 시 diff가 리뷰에 뜨는가
- [ ] 실패 메시지가 전/후 diff를 보여 주는가
- [ ] 스키마 변경 PR에서 이 테스트가 자동으로 도는가

## 8. 함께 볼 것

- **13.1 추론기 vs 검증기** — OWL은 없으면 있다고 결론 내고, SHACL은 없으면 위반이라고 적는다. 도구를 잘못 고르면 3주가 날아간다.
- **13.3 SHACL로 못 잡는 것들** — 슈퍼 노드, 사이클, 중복 의심. 세어 봐야 보이는 2층 검증.
- **13.5 품질을 한 숫자로 만들지 마라** — 종합 점수는 좋아지는데 링크 유효율은 떨어진다. 절대 개수와 비율을 둘 다 적어라.
- **12장** — 역량 질의를 뽑는 쪽. 여기서 만든 목록이 13장의 테스트가 된다.
