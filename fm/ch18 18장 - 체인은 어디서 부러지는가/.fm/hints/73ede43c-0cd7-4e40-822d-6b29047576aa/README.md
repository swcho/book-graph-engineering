# 병렬 작업 중 하나가 실패할 때 체인의 한계는 무엇인가?

## 핵심 답

**세 가지 선택지를 표현할 자리가 없다.** 체인에서는 병렬 작업 중 하나가 실패하면 예외가 위로 던져지고 그걸로 끝이다. 반면 상태 그래프에서는 **합류 노드(join node)** 가 부분 실패를 어떻게 다룰지 결정하는 책임을 맡는다.

## 상황 설정

18장 18.3절("병렬로 돌렸는데 하나만 실패했다")의 예제 상황을 보자. 작업 4개를 병렬로 돌렸는데 하나가 실패했다.

| 작업 | 결과 | 값 |
|---|---|---|
| 재무 자료 조회 | 성공 | 매출 84.2억 |
| 법무 검토 | **실패** | — |
| 영업 이력 조회 | 성공 | 계약 12건 |
| 리스크 평가 | 성공 | 중간 |

이때 "어떻게 할 것인가"에는 정답이 하나가 아니라 **세 가지 선택지**가 있다.

## 세 가지 선택지

1. **전부 아니면 없음 (all-or-nothing)** — 하나라도 실패하면 전체를 실패로 처리하고 결과를 버린다.
   - 결재 서류처럼 「불완전하면 안 되는」 산출물에 맞다.
2. **되는 것만 (best-effort)** — 성공한 작업의 결과만 모아서 부분 완료로 진행한다.
   - 대시보드처럼 「있는 만큼 보여 주면 되는」 것에 맞다.
3. **빈칸을 표시하고 진행 (graceful degradation)** — 실패한 항목을 "확인 불가"로 표시하고 나머지와 함께 완료한다.
   - 보고서처럼 「무엇이 빠졌는지 보여야 하는」 것에 맞다.

책의 지적: **셋 다 맞는 답이고, 상황이 정한다.** 그리고 세 번째가 대개 제일 나은데도 제일 안 쓰인다 — "확인 불가"를 화면에 그리는 일이 귀찮아서다.

## 왜 체인에는 이 선택을 표현할 자리가 없는가

- 체인은 단계를 한 줄로 이어 붙인 구조다. 각 단계의 출력이 다음 단계의 입력으로 곧장 흘러간다.
- 어느 단계(또는 병렬 분기 중 하나)에서 실패하면 **예외가 호출 스택 위로 전파되고 실행이 끝난다.** "일부는 성공했으니 그것만으로 계속 갈지, 빈칸을 표시할지, 전부 버릴지"를 판단하는 코드가 놓일 위치 자체가 구조에 없다.
- 억지로 넣으려면 try/except와 if 문을 파이프라인 곳곳에 흩뿌려야 하고, 그 결정 로직이 어디에 있는지 아무도 알 수 없게 된다.

## 그래프에서는 합류 노드가 결정을 맡는다

- 상태 그래프에서는 병렬 분기(fan-out)가 끝나는 지점에 **합류 노드(fan-in / join)** 가 명시적으로 존재한다.
- 각 분기의 성공/실패 결과가 상태(state)에 모이고, 합류 노드는 그 상태를 보고 세 가지 전략 중 하나를 실행한다.
- 즉 **"부분 실패를 어떻게 다룰지"가 노드 하나의 책임**이 된다. 결정이 코드 한 곳에 모여 있으니 읽기 쉽고, 테스트하기 쉽고, 나중에 전략을 바꾸기도 쉽다.

## 기억할 것

- 체인의 한계는 실패 자체가 아니라 **실패 이후의 선택지를 담을 구조적 자리가 없다는 것**이다.
- 구조를 그래프로 바꿔도 실패율은 줄지 않는다. 줄어드는 것은 **실패의 값(비용)** 이다 — 이 구분이 이 장 전체를 관통하는 주제다.
