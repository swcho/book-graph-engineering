# 상태 그래프에서 합류 노드의 책임

## 질문

상태 그래프에서 합류 노드의 책임은 무엇인가?

## 답

**부분 실패를 어떻게 다룰지 결정하는 것**이다. 그 결정이 노드 하나의 책임으로 명시된다.

---

## 왜 이 질문이 나오는가 — 병렬 작업과 부분 실패

18장 18.3절의 상황은 이렇다. 작업 네 개를 병렬로 돌렸는데 그중 하나만 실패했다.

| 작업 | 결과 |
|---|---|
| 재무 자료 조회 | 성공 — "매출 84.2억" |
| 법무 검토 | **실패** |
| 영업 이력 조회 | 성공 — "계약 12건" |
| 리스크 평가 | 성공 — "중간" |

이때 시스템이 할 수 있는 선택은 세 가지다.

1. **전부 아니면 없음 (all-or-nothing)** — 하나라도 실패하면 전체 실패로 처리한다. 결재 서류처럼 *불완전하면 안 되는* 산출물에 맞다.
2. **되는 것만 (best effort)** — 성공한 결과만 모아서 진행한다. 대시보드처럼 *있는 만큼 보여 주면 되는* 것에 맞다.
3. **빈칸을 표시하고 진행 (graceful degradation)** — 실패한 항목을 "확인 불가"로 표시하고 계속 간다. 보고서처럼 *무엇이 빠졌는지 보여야 하는* 것에 맞다.

셋 다 맞는 답이고, 상황이 정한다. 책은 세 번째가 대개 제일 낫지만 "확인 불가"를 화면에 그리는 일이 귀찮아서 제일 안 쓰인다고 지적한다.

## 체인에는 이 결정을 표현할 자리가 없다

체인(프롬프트 연쇄)은 단계를 한 줄로 이어 붙인 구조라서, 병렬 작업 중 하나가 실패하면 **예외가 위로 던져지고 끝**이다. "부분 실패를 어떻게 다룰까"라는 질문 자체를 코드 어디에도 둘 곳이 없다. 그래서 51초를 기다린 사용자에게 "다시 시도해 주세요"가 나가는 것이다 — 성공한 세 작업의 결과까지 함께 버려진 채로.

## 합류 노드가 그 자리를 만든다

상태 그래프에서는 병렬로 갈라진 가지들이 다시 만나는 지점에 **합류 노드**(fan-in / join 노드)를 둔다. 이 노드의 책임이 바로 위의 세 전략 중 하나를 고르는 것이다.

- 합류 노드는 각 가지의 성공/실패 결과를 상태로 받아서, "전부 아니면 없음 / 되는 것만 / 빈칸 표시" 중 무엇으로 합칠지 **명시적으로 결정**한다.
- 이 결정이 익명의 예외 처리 코드나 프레임워크 기본값에 숨지 않고, **그래프 위의 노드 하나**로 드러난다. 즉 설계 리뷰에서 "부분 실패 정책이 어디 있나?"라고 물으면 가리킬 수 있는 위치가 생긴다.
- LangGraph 같은 도구에서는 병렬 가지들의 결과가 리듀서(reducer)로 상태에 모이고, 그 다음 노드가 합류 지점 역할을 하며 이 정책을 구현한다.

## 기억할 문장

> 체인에는 이 선택을 표현할 자리가 없다. 실패하면 예외가 위로 던져지고 끝이다.
> 상태 그래프에서는 «합류 노드»가 이 결정을 맡는다.
> 부분 실패를 어떻게 다룰지가 노드 하나의 책임이 되는 것이다.

핵심은 "합류 노드가 실패를 없애 준다"가 아니라는 점이다. 이 장의 결론과 같은 맥락으로, 구조를 바꿔도 실패율은 안 줄어든다 — **실패의 값(비용)이 줄고, 실패를 다루는 결정이 코드 안에 자리를 얻을 뿐**이다.
