# 재생 시간은 무엇으로 정해지는가?

**답:** 데이터 양이 아니라 **스냅숏 주기**로 정해진다. 그리고 그 주기는 **복구 목표 시간에서 거꾸로 계산**한다.

---

## 1. 왜 이 질문이 나오는가

30장의 흐름은 이렇습니다.

1. 현재 상태만 저장하면 「3월엔 누가 팀장이었나」, 「누가 넣고 누가 지웠나」 같은 질문에 답을 못 한다 (`ex1_no_history.py`).
2. 그래서 **이벤트를 원본으로 쌓고 상태는 재생해서 만든다**(이벤트 소싱).
3. 그런데 이 방식은 값을 치릅니다. **저장 공간과 재생 시간**이요.

여기서 자연스럽게 나오는 걱정이 「이벤트가 백만 개, 천만 개가 되면 재생이 하염없이 느려지는 것 아닌가」입니다. 이 카드는 그 걱정이 **틀렸다**는 것과, 왜 틀렸는지를 다룹니다.

## 2. 순진한 재생 — 데이터 양에 비례한다

스냅숏 없이 「처음부터 끝까지」 재생하면, 재생 시간은 이벤트 수에 정직하게 비례합니다. O(N)이에요.

```python
def replay(events, start_state=None):
    st = set(start_state) if start_state else set()
    for _i, s, k, o, op in events:
        if op == "추가":
            st.add((s, k, o))
        else:
            st.discard((s, k, o))
    return st
```

`ex2_replay_cost.py`의 측정값(본문 기준):

| 이벤트 수 | 처음부터 재생 | 스냅숏 이후만 재생 | 재생할 이벤트 |
|---|---|---|---|
| 10,000 | 빠름 | 비슷하거나 더 느림 (배수 ≈ 0.8) | 10,000 |
| 1,034,000 | 약 395ms | 약 16ms | 최대 50,000 |

백만 개면 395ms. 천만 개면 4초. 이대로면 이벤트 소싱은 시간이 갈수록 스스로 망가지는 구조가 됩니다.

## 3. 스냅숏이 바꾸는 것 — 「상한」이 생긴다

해법은 주기적으로 **그 시점까지 접은 상태를 통째로 저장**해 두는 것입니다. 그게 스냅숏이에요. 그러면 재생은 이렇게 바뀝니다.

```
[처음부터]  ev[0] ────────────────────────────────────────► 지금
[스냅숏]    ev[0] ──────► 스냅숏(50만 번째) ──────► 지금
                          여기서 시작            ↑ 여기까지만 재생
```

예제 코드의 핵심 부분입니다.

```python
SNAPSHOT_EVERY = 50_000
...
last_snap = (n // SNAPSHOT_EVERY) * SNAPSHOT_EVERY
snap_state = replay(ev[:last_snap]) if last_snap else set()
tail = ev[last_snap:]          # 재생할 것은 이것뿐
tail_ms, st2 = timed(replay, tail, snap_state)
assert st == st2               # 답은 똑같다
```

여기서 결정적인 낱말이 **상한(upper bound)** 입니다.

> 이벤트가 백만 개든 천만 개든 재생할 것은 최대 5만 개다.
> 그러니 재생 시간이 「데이터 양」이 아니라 「스냅숏 주기」로 정해진다.

즉 재생 비용은 O(전체 이벤트 수)가 아니라 **O(스냅숏 주기)** 입니다. 주기가 상수면 재생 시간도 상수예요. 전체 로그가 아무리 커져도 최악의 재생 시간은 안 변합니다. **이 문장이 카드의 답 그 자체입니다.**

### 첫 줄에서 배수가 1보다 작게 나오는 이유

1만 개 줄은 배수가 0.8쯤 나옵니다. 아직 5만 개에 도달하지 않아 스냅숏이 **한 번도 안 찍혔기** 때문이에요. 결국 처음부터 재생하는 것과 같은 일을 하고, 거기에 측정 잡음만 얹힌 겁니다. 스냅숏은 **데이터가 충분히 쌓인 뒤에** 값을 하기 시작합니다.

## 4. 그러면 주기는 어떻게 잡나 — 복구 목표 시간에서 역산

주기를 정하는 건 두 값의 교환(trade-off)입니다.

| 주기 | 얻는 것 | 잃는 것 |
|---|---|---|
| **짧게** (예: 1만 개마다) | 재생이 빠르다 = 복구가 빠르다 | 스냅숏 저장 공간이 늘어난다, 스냅숏 찍는 부담도 잦다 |
| **길게** (예: 100만 개마다) | 공간을 아낀다 | 복구가 느려진다 |

책이 제시하는 결정 방법은 **목표에서 거꾸로 계산**하는 것입니다.

> 저는 「복구 목표 시간」에서 거꾸로 계산한다.
> 「장애 났을 때 3초 안에 복구」가 목표면, 3초에 재생할 수 있는 이벤트 수를 재고 그만큼을 주기로 잡는다.

절차로 풀면 이렇습니다.

1. **복구 목표 시간을 먼저 정한다.** (예: 3초 — 이건 기술이 아니라 운영/비즈니스 결정)
2. **실측한다.** 우리 환경에서 이벤트 1개 재생에 몇 μs가 드는가.
3. **나눈다.** 3초 ÷ 이벤트당 비용 = 3초에 재생 가능한 이벤트 수.
4. 그 수를 **스냅숏 주기**로 삼는다. (여유를 두려면 조금 작게)

예: 이벤트 100만 개 재생에 395ms → 1개당 약 0.4μs → 3초면 약 750만 개. 이 경우 주기를 500만 개쯤으로 잡아도 목표를 지킵니다. 반대로 목표가 「50ms 안에」라면 주기는 10만 개 근처로 내려와야 합니다.

핵심은 **주기를 감으로 찍지 않는다**는 것입니다. 「대충 5만 개마다」가 아니라 「우리 복구 목표가 3초이므로 N개마다」로 말할 수 있어야 해요. 숫자에 근거가 붙습니다.

## 5. 이건 데이터베이스가 30년째 하던 일이다

이 구조는 새로 발명한 게 아닙니다. 그대로 데이터베이스의 **쓰기 전 로그(WAL) + 체크포인트**입니다.

| 이벤트 소싱 | 데이터베이스 |
|---|---|
| 이벤트 로그 (추가 전용) | 쓰기 전 로그 (WAL) |
| 스냅숏 | 체크포인트 |
| 재생 | 크래시 복구 (recovery) |
| 스냅숏 주기 | 체크포인트 간격 (`checkpoint_timeout`, `max_wal_size` 등) |

PostgreSQL이 체크포인트 간격을 조절하는 이유도 똑같습니다. 체크포인트가 잦으면 I/O 부담이 크고, 뜸하면 크래시 후 복구가 오래 걸립니다. SQLite의 WAL 모드도 WAL 파일이 일정 크기를 넘으면 체크포인트를 돌려 본 DB에 접습니다. 30년 된 구조를 이름만 바꿔 쓰는 셈이에요.

## 6. 자주 하는 오해

- **「이벤트가 많으니 재생이 느릴 것이다」** → 아니요. 스냅숏이 있으면 전체 양은 재생 시간과 무관합니다. 늘어나는 건 **저장 공간**이지 재생 시간이 아닙니다.
- **「스냅숏이 있으면 옛날 이벤트는 지워도 된다」** → 위험합니다. 스냅숏은 **재생을 빠르게 하는 캐시**이지 원본이 아닙니다. 원본 이벤트를 지우면 30장이 애초에 풀려던 문제(감사, 사고 조사, 「3월엔 어땠나」)를 다시 못 풀게 됩니다. 스냅숏은 파생물, 이벤트가 진실의 원본입니다.
- **「스냅숏 주기는 성능 튜닝 값이다」** → 반은 맞지만, 결정 근거는 성능이 아니라 **복구 목표 시간**입니다. 목표를 먼저 정하고 거기서 역산합니다.

## 7. 한 줄 정리

> 재생 시간의 상한은 스냅숏 주기가 정한다. 그러니 주기는 「복구를 몇 초 안에 끝낼 것인가」에서 거꾸로 계산해서 잡는다. WAL과 체크포인트가 30년째 해 오던 그것이다.
