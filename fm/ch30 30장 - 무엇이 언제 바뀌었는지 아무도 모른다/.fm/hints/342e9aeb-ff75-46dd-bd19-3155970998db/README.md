# 이벤트 백만 개일 때 두 방식의 재생 시간

**질문** — 이벤트 백만 개일 때 두 방식의 재생 시간은 어떻게 되는가?

**답** — 처음부터 재생은 약 395ms, 스냅숏 이후만 재생하면 약 16ms다.

---

## 1. 어디서 나온 숫자인가

30장 `code/ex2_replay_cost.py` 의 출력입니다. 의존성 없는 순수 파이썬 예제로,
이벤트 수를 네 단계로 늘려 가며 두 가지 재생을 나란히 잽니다.

- **처음부터 재생** — 이벤트 0번부터 마지막까지 전부 접는다(fold)
- **스냅숏 이후만 재생** — 마지막 스냅숏 상태를 불러오고, 그 뒤에 쌓인 것만 접는다

스냅숏 주기는 코드에 고정돼 있습니다.

```python
SNAPSHOT_EVERY = 50_000
```

그리고 각 행마다 이렇게 잘라 냅니다.

```python
last_snap  = (n // SNAPSHOT_EVERY) * SNAPSHOT_EVERY   # 마지막 스냅숏 지점
snap_state = replay(ev[:last_snap]) if last_snap else set()
tail       = ev[last_snap:]                            # 실제로 재생할 것
tail_ms, st2 = timed(replay, tail, snap_state)
assert st == st2                                       # 결과는 같아야 한다
```

`assert st == st2` 가 핵심입니다. 두 방식은 **같은 상태**를 만듭니다. 다른 건 값(시간)뿐이에요.

## 2. 출력 표 전체

```
       이벤트 수      처음부터(ms)      스냅숏 이후(ms)       재생할 이벤트      배수
--------------------------------------------------------------------
      10,000           1.9             2.7        10,000    0.8x
      63,000          14.6             2.9        13,000    5.1x
     217,000          47.1             5.4        17,000    8.7x
   1,034,000         395.0            16.0        34,000   24.7x
```

책이 본문에서 못 박은 값은 세 개입니다. **백만 개(정확히는 1,034,000개)에서 처음부터 재생 395ms,
스냅숏 이후만 재생 16ms**, 그리고 **첫 줄의 배수 0.8**. 나머지 칸은 실행할 때마다 흔들립니다
(장의 실행 가이드도 "`ex2` 는 실행할 때마다 시간이 조금씩 달라집니다"라고 미리 말해 둡니다).
위 표의 가운데 두 줄은 같은 코드를 그대로 돌려 재현한 값이고, 배수도 대략 5x, 9x 근처에서 놉니다.

## 3. 왜 배수가 그렇게 나오는가

배수는 성능 마법이 아니라 **나눗셈 결과**입니다. `재생할 이벤트` 열만 보면 전부 설명됩니다.

| 이벤트 수 n | 마지막 스냅숏 `(n//50,000)*50,000` | 꼬리 길이 `n - last_snap` | n / 꼬리 |
|---|---|---|---|
| 10,000 | 0 (아직 없음) | 10,000 | 1.0 |
| 63,000 | 50,000 | 13,000 | 4.8 |
| 217,000 | 200,000 | 17,000 | 12.8 |
| 1,034,000 | 1,000,000 | 34,000 | 30.4 |

- **첫 줄이 0.8x인 이유** — 1만 개는 스냅숏 주기 5만에 못 미쳐서 `last_snap = 0` 입니다.
  스냅숏이 한 번도 안 찍혔으니 "스냅숏 이후만 재생"이 사실은 **처음부터 재생과 완전히 같은 일**을 합니다.
  같은 일을 두 번 재면 이론상 1.0x여야 하는데, 측정 잡음과 `set(start_state)` 같은 부수 비용이 얹혀
  1보다 작게도 나옵니다. 장의 결론 문구도 이걸 그대로 말합니다 — *"스냅숏은 «데이터가 충분히 쌓인 뒤에» 값을 하기 시작한다."*
- **뒤로 갈수록 배수가 커지는 이유** — 왼쪽 열(처음부터)은 n에 정비례해 늘어나는데,
  오른쪽 열(꼬리)은 `n mod 50,000` 이라 **절대 5만을 못 넘습니다**. 분자만 자라고 분모는 갇혀 있으니
  배수는 자동으로 벌어집니다.
- **실측 배수가 이론 나눗셈보다 조금 낮은 이유** — 꼬리 재생은 순수한 이벤트 접기 외에
  스냅숏 상태를 복사해서 시작합니다(`set(start_state)`). 실제 시스템이라면 여기에 스냅숏
  역직렬화·디스크 읽기가 붙고요. 그래서 "스냅숏 이후"는 0ms가 아니라 **스냅숏 로드 + 짧은 재생**입니다.
  1,034,000행이 30.4가 아니라 24.7x인 것도 이 몫입니다.

## 4. 진짜 요점은 절대값이 아니라 스케일 특성

395ms와 16ms를 외우는 건 별 의미가 없습니다. 이 숫자는

- 파이썬 `set` 연산 속도
- 돌린 기계
- 이 예제의 이벤트 모양(추가 72% / 삭제 28%, 주체 401종 × 객체 41종)

에 통째로 종속돼 있어요. 언어가 바뀌거나 이벤트에 디스크 읽기·역직렬화가 붙으면 두 값 다 몇 배씩 움직입니다.
같은 코드를 다른 기계에서 돌리면 279ms / 14.9ms 같은 값이 나오기도 합니다. 그래도 **표의 모양은 안 바뀝니다.**

바뀌지 않는 건 두 열의 **기울기**입니다.

- 처음부터 재생 = **O(n)** — 데이터가 열 배면 시간도 열 배. 서비스가 성공할수록 복구가 느려진다는 뜻입니다.
- 스냅숏 이후 재생 = **O(스냅숏 주기)** — n이 아무리 커져도 재생할 건 최대 5만 개.
  장의 표현대로 *"이벤트가 백만 개든 천만 개든 재생할 것은 최대 5만 개"* 이고, 이건 **상한(bound)** 입니다.

그래서 장의 한 줄 요약이 이렇게 됩니다.

> 재생 시간은 **데이터 양이 아니라 스냅숏 주기**로 정해집니다.

즉 스냅숏이 하는 일은 "빠르게 만들기"가 아니라 **재생 시간을 데이터 양에서 떼어 내는 것**입니다.
성장해도 복구 시간이 안 늘어나는 구조로 바꾸는 것이죠.

## 5. 그러면 주기는 어떻게 잡나

주기는 두 값의 교환입니다.

- 짧게 잡으면 — 재생은 빠른데 스냅숏 저장 공간이 늘어난다
- 길게 잡으면 — 공간은 아끼는데 복구가 느려진다

장이 권하는 방법은 **복구 목표 시간에서 거꾸로 계산**하기입니다.
"장애 났을 때 3초 안에 복구"가 목표라면, 3초에 재생할 수 있는 이벤트 수를 실제로 재고 그만큼을 주기로 잡습니다.
5만이라는 숫자를 베끼는 게 아니라, 내 시스템에서 목표 시간에 맞는 수를 재서 정하는 거예요.

그리고 이 구조는 새로 발명한 게 아닙니다. 데이터베이스의 **쓰기 전 로그(WAL) + 체크포인트**와 같습니다.
30년 된 구조를 그대로 쓰는 것입니다.

## 6. 자주 틀리는 지점

- ❌ "스냅숏 쓰면 무조건 24배 빨라진다" → 배수는 `n / (n mod 주기)` 라서 n과 주기에 따라 매번 다릅니다. 1만 개에선 오히려 0.8x예요.
- ❌ "395ms / 16ms는 이벤트 소싱의 성능 수치다" → 이 예제·이 기계의 값입니다. 인용해야 할 건 **O(n) 대 O(주기)** 라는 모양입니다.
- ❌ "스냅숏은 데이터가 적을 때부터 이득이다" → 주기보다 적게 쌓이면 스냅숏이 존재하지도 않아 이득이 0입니다.
- ❌ "재생 결과가 달라질 수 있다" → `assert st == st2`. 두 방식은 **답이 같고 값만 다릅니다.**

## 7. 한 문장으로

백만 개 기준 처음부터 재생 **395ms**, 스냅숏 이후만 재생 **16ms** — 약 25배 차이지만,
외울 것은 이 두 숫자가 아니라 **왼쪽은 데이터 양을 따라 자라고 오른쪽은 스냅숏 주기에 갇혀 평평하다**는 사실입니다.
