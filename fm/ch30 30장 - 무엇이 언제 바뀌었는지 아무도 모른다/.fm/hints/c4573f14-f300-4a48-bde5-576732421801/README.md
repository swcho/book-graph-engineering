# '전부 모은다' 리듀서가 적합한 도메인은 무엇인가?

## 한 줄 답

**「충돌이 있다」는 사실 자체가 중요한 도메인**입니다. 즉 답을 하나로 좁히는 것보다 *「출처마다 말이 다르다」를 잃지 않는 것*이 더 중요한 곳이요.
대신 대가가 있습니다. 답이 여럿이라 **조회하는 쪽이 곤란해집니다.**

---

## 1. 문제의 코드 (asset 원문 그대로)

30장 `ex4_reducer_conflict.py`는 **같은 이벤트 열 하나**에 리듀서 네 개를 적용합니다. 이벤트는 이렇습니다.

```python
EVENTS = [
    ("2026-04-01T09:00", "hr-sync",    "선호", "채식",   "추가", 0.95),
    ("2026-04-03T14:20", "agent-4821", "선호", "육식",   "추가", 0.61),
    ("2026-04-03T14:21", "agent-4821", "선호", "채식",   "삭제", 0.61),
    ("2026-04-09T10:05", "user",       "선호", "채식",   "추가", 1.00),
    ("2026-04-22T16:40", "agent-5102", "선호", "비건",   "추가", 0.78),
]
```

그리고 문제의 리듀서입니다.

```python
def accumulate(evs):
    """지우지 않고 전부 모아 둔다. 충돌은 «답이 여럿»으로 남긴다."""
    st = {}
    for at, who, k, v, op, conf in evs:
        st.setdefault(k, set())
        if op == "추가":
            st[k].add(v)
        else:
            st[k].discard(v)
    return {k: (" / ".join(sorted(v)), "-", "-") for k, v in st.items()}
```

이 리듀서를 위 이벤트에 돌리면 `선호 = 비건 / 육식 / 채식`이 나옵니다. **하나가 아니라 셋**입니다.

그리고 반환값의 나머지 두 칸이 `"-"`, `"-"` 인 것을 보세요. 다른 세 리듀서는 「누가 넣었나」와 「언제」를 같이 돌려주는데, `accumulate`만 그걸 못 돌려줍니다. **값이 여럿이니 「누가」도 여럿이라 한 칸에 담을 수가 없거든요.** 조회 쪽 고통이 이미 반환 타입에서 시작됩니다.

## 2. 네 리듀서를 나란히 놓고 보면

| 리듀서 | 위 이벤트에 대한 답 | 성격 |
|---|---|---|
| 마지막이 이긴다 (LWW) | `비건` | 제일 흔하고 제일 위험. 4/9에 사람이 「채식」이라 했는데 4/22 에이전트가 덮음 |
| 확신도가 이긴다 | `채식`(1.00) | 그럴듯하지만 확신도는 **에이전트가 스스로 매기는 값** (20장) |
| 사람이 이긴다 | `채식` | 출처에 **시스템이** 등급을 매김. 책의 기본 권장 |
| **전부 모은다** | **`비건 / 육식 / 채식`** | **충돌을 숨기지 않음. 대신 답이 여럿** |

핵심은 이겁니다. **이벤트를 쌓는 것만으로는 아무것도 안 정해집니다.** 같은 이벤트 열인데 답이 넷이에요. *어떻게 접을 것인가*가 실제 동작을 정하고, 그건 기술 결정이 아니라 **도메인 결정**입니다.

앞의 세 개는 전부 **「하나를 골라 나머지를 버린다」** 는 공통점이 있습니다. 버린다는 건 조회하는 쪽에서 「다른 답이 있었다」는 것을 볼 수 없다는 뜻이에요(이력 로그를 직접 뒤지지 않는 한). `accumulate`만 그 정보를 상태 안에 남깁니다.

## 3. 그래서 어떤 도메인에 맞나

판별 기준은 하나입니다.

> **틀린 답 하나를 조용히 고르는 비용 > 답이 여럿이라 조회가 번거로운 비용**

이 부등호가 성립하면 `accumulate`가 맞습니다. 구체적으로는 이런 곳들입니다.

### 3.1 안전 임계(safety-critical) 기록 — 의료 알레르기

가장 교과서적인 예입니다. 이런 이벤트가 들어왔다고 해 봅시다.

```
2026-03-02  EMR-import     환자123.알레르기 = 페니실린   (추가)
2026-03-11  간호사 문진     환자123.알레르기 = 없음       (추가)
2026-04-05  타병원 연계      환자123.알레르기 = 페니실린   (추가)
```

- **「마지막이 이긴다」로 접으면** → `없음`이 아니라 `페니실린`(4/5가 마지막). 운이 좋았습니다. 만약 4/5 이벤트가 없었으면 답은 `없음`이고, **페니실린 투여로 이어집니다.**
- **「전부 모은다」로 접으면** → `페니실린 / 없음`. 보기 흉하죠. 그런데 이 흉함이 정확히 필요한 정보입니다. *「기록이 엇갈립니다. 투여 전에 확인하세요.」*

여기서는 **「모른다/엇갈린다」가 「없음」보다 훨씬 안전한 답**입니다. 하나로 접는 순간 시스템은 「엇갈린다」를 표현할 어휘를 잃습니다.

같은 성격의 예: 투약 금기, 혈액형, 임신 여부, 항공기 정비 이력의 부품 상태, 산업 설비의 안전 인터록 상태.

### 3.2 규제 심사 / 감사 — 「무엇을 근거로 정했나」를 물어보는 곳

30.5절이 「로그가 감사 로그가 되려면」인데, 리듀서 선택도 같은 질문에 걸립니다.

신용 심사, 보험 인수, 자금세탁방지(AML) 스크리닝, 세무 판정 같은 곳에서는 심사관이 이렇게 묻습니다.

> 「이 건은 어떤 근거들이 있었고, 그중 무엇을 채택했으며, **채택하지 않은 근거는 무엇이고 왜 버렸나요?**」

「마지막이 이긴다」로 접힌 상태에는 마지막 값만 남습니다. 나머지 근거는 **상태에서 사라졌습니다.** 이력을 재생하면 복원은 되지만, 그건 *「심사 당시 시스템이 그 정보를 보고 있었다」* 를 증명하지 못합니다. 봤는데 버린 건지, 애초에 못 본 건지 구분이 안 되거든요.

`accumulate`는 상태 자체가 **「이 근거들이 전부 테이블 위에 있었다」** 를 증언합니다. 그리고 심사 결정은 별도 이벤트(`판정`)로 다시 기록되고요. 근거 집합과 판정이 분리되는 겁니다.

같은 성격의 예: 임상시험 데이터 심사, 안전 인증, 컴플라이언스 예외 승인, 모델 카드/데이터 계보 보고.

### 3.3 다중 출처 데이터 통합 — 마스터 데이터/엔티티 해소

여러 시스템이 같은 실체를 각자 기록하는 상황입니다. 회사 마스터를 만드는데 세 출처가 이렇게 말합니다.

```
사업자등록 API   가온테크.대표자 = 김가온
HR 시스템        가온테크.대표자 = 김가온
뉴스 크롤러      가온테크.대표자 = 이나루     ← 최근 기사
```

- **하나로 접으면**: 출처 하나가 틀렸다는 사실이 안 보입니다. 그냥 값이 하나 있을 뿐이에요.
- **전부 모으면**: `김가온 / 이나루`. 그리고 이건 **버그 신호**입니다. 대표자가 실제로 바뀌었거나(→ 다른 두 출처가 낡았다), 뉴스 크롤러가 잘못 뽑았거나(→ 추출 품질 문제), 애초에 두 회사를 하나로 합쳤거나(→ 엔티티 해소 실패).

여기서 `accumulate`의 진짜 값은 **데이터 품질 지표**입니다. 「값이 2개 이상인 키의 비율」이 그대로 출처 불일치율이 되고, 그게 상승하면 어떤 파이프라인이 상했다는 뜻이에요. 하나로 접으면 이 지표를 만들 수 없습니다.

같은 성격의 예: 지식 그래프 융합, 제품 카탈로그 통합, 지리 데이터(POI) 통합, 인용/논문 메타데이터 병합.

### 3.4 그 밖에

- **사람 vs 에이전트가 계속 다투는 필드**: 하나로 접으면 「누가 이겼나」만 보이고 「싸움이 있었다」가 안 보입니다. 다툼 빈도 자체가 온톨로지가 틀렸다는 신호일 때가 많아요.
- **번역/라벨/별칭**: 「같은 것을 여러 이름으로 부른다」가 정상인 필드는 애초에 다중값이 맞습니다. 이건 충돌이 아니라 **본래 다중값(multi-valued)** 인 경우고, `accumulate`가 그냥 올바른 모델입니다.
- **사고 조사(post-mortem)**: 「그 시점에 시스템 안에 어떤 주장들이 공존했나」가 조사의 핵심 질문입니다.

## 4. 조회하는 쪽이 곤란해지는 지점

원문이 「대신 답이 여럿이라 조회하는 쪽이 곤란해진다」로 한 줄 짚고 넘어가는데, 실무에서 이게 깨지는 지점은 꽤 구체적입니다.

### 4.1 API 계약이 단일값을 전제할 때

```json
// 기존 계약
{ "userId": "u-1", "선호": "채식" }

// accumulate 이후
{ "userId": "u-1", "선호": ["비건", "육식", "채식"] }
```

타입이 `string` → `string[]`로 바뀝니다. 이건 **BREAKING CHANGE**입니다. 클라이언트 전부가 깨져요. 더 나쁜 건 **조용히 깨지는 경우**입니다.

- 느슨한 언어에서 `"선호": "비건 / 육식 / 채식"` 같은 문자열 조인으로 우회하면 타입은 안 깨지지만 **의미가 깨집니다.** 다운스트림에서 `선호 == "채식"` 비교가 전부 false가 되고, 문자열 매칭 규칙이 조용히 무너져요. (5장의 「문자열이 아니라 사물」이 여기서 다시 걸립니다.)
- 배열 첫 원소만 쓰는 클라이언트가 생깁니다. 그러면 사실상 **정렬 순서가 리듀서가 됩니다.** 위 코드가 `sorted(v)`를 쓰니까 「가나다순 첫 글자가 이긴다」는, 아무도 의도한 적 없는 정책이요.

### 4.2 UI가 단일값을 전제할 때

- **폼 입력**: 라디오 버튼/셀렉트 박스는 값이 하나라는 전제로 그려져 있습니다. 값이 셋이면 「무엇을 선택된 상태로 보일 것인가」에 답이 없습니다. 아무것도 선택 안 하면 사용자가 저장을 누르는 순간 **다른 값들이 조용히 지워집니다.**
- **목록/테이블 셀**: 한 칸에 세 값이 들어가면 레이아웃이 깨지고, 대개 잘려서 첫 값만 보입니다. 화면상으로는 **다시 「하나가 이긴다」로 돌아간 것**이고, 그것도 사용자가 모르는 채로요.
- **정렬·필터·집계**: 「선호별 사용자 수」를 세면 다중값 사용자가 세 번 세어집니다. 합계가 전체 사용자 수를 넘어가요. 대시보드 숫자가 안 맞기 시작합니다.

### 4.3 다운스트림 로직이 단일값을 전제할 때

- **에이전트 프롬프트**: 「이 사용자의 선호: 비건 / 육식 / 채식」을 컨텍스트에 넣으면 모델이 임의로 하나를 고릅니다. 리듀서를 명시적으로 안 정한 대신 **모델이 몰래 리듀서 노릇**을 하는 거고, 그 선택은 재현되지도 감사되지도 않습니다.
- **캐시 키/인덱스**: 집합은 순서가 없어서 직렬화가 흔들리면 캐시 키가 매번 달라집니다. 위 코드가 `sorted()`를 쓴 게 우연이 아니에요.
- **동등 비교/멱등성**: 「상태가 바뀌었나」를 판정하는 코드가 집합 비교를 못 하면 매번 「바뀜」으로 보고 이벤트를 또 씁니다. 로그가 부풀어요.
- **스키마 강제**: Kuzu 같은 곳에서 `선호 STRING` 컬럼이면 애초에 못 넣습니다. 리스트 타입이나 별도 테이블로 모델을 바꿔야 합니다.

## 5. 완화책

「전부 모은다」를 쓰되 조회 쪽 고통을 줄이는 방법들입니다. 순서대로 검토하면 됩니다.

### 5.1 다중값을 원본으로 두고, 단일값은 파생 뷰로 만든다 (제일 중요)

30.2절의 「이벤트가 원본이고 상태는 파생이다」를 한 단계 더 적용하는 겁니다. CQRS 그대로예요.

```
이벤트 로그  →  accumulate 상태(다중값)   ← 진실. 감사·조사·품질지표가 여기를 본다
             →  human_wins 상태(단일값)   ← 조회용 뷰. UI/API가 여기를 본다
```

같은 이벤트 열에서 **뷰를 두 개 만듭니다.** 기존 API 계약은 안 깨지고, 「충돌이 있었다」는 사실도 안 잃습니다. 리듀서는 상태를 계산하는 함수일 뿐이니 여러 개를 동시에 돌리는 데 비용이 거의 안 듭니다.

### 5.2 단일값 + 충돌 플래그로 계약을 확장한다

계약을 깨야 한다면, **배열로 바꾸는 것보다 이 모양이 낫습니다.**

```json
{
  "선호": {
    "value": "채식",              // 표시용 대표값 (사람이 이긴다로 접은 것)
    "hasConflict": true,
    "candidates": [
      { "value": "채식", "source": "user",       "at": "2026-04-09T10:05" },
      { "value": "비건", "source": "agent-5102", "at": "2026-04-22T16:40" },
      { "value": "육식", "source": "agent-4821", "at": "2026-04-03T14:20" }
    ]
  }
}
```

- 기존 클라이언트는 `value`만 읽으면 되니 **점진적 마이그레이션**이 가능합니다.
- `hasConflict`가 UI에 배지 하나(⚠) 띄울 근거를 줍니다. **다중값을 전부 그리지 않고도 「엇갈린다」를 전달**할 수 있어요.
- `candidates`에 출처·시각이 붙습니다. 4.1에서 지적한 「`accumulate`가 누가/언제를 못 돌려준다」는 결함이 여기서 메워집니다.

### 5.3 대표값 선택 규칙을 코드로 못 박는다

대표값(`value`)을 뽑을 때는 **「사람이 이긴다」류의 출처 등급**을 쓰세요. 확신도는 안 됩니다. 확신도는 에이전트가 스스로 매기는 값이라 에이전트가 올릴 수 있고, 등급은 시스템이 정하는 값이라 못 올립니다(20장).

그리고 대표값 선택은 **명시적 함수 하나**여야 합니다. 정렬 순서, 배열 첫 원소, UI 셀 잘림, 프롬프트 속 모델 판단 — 이런 게 대신 결정하게 두면 안 됩니다.

### 5.4 다중값의 수명을 관리한다

`accumulate`는 지우지 않으니 값이 계속 쌓입니다. 그대로 두면 5년 뒤에 값이 40개인 필드가 생겨요.

- **충돌을 작업 큐로 뺀다**: 값이 2개 이상이면 사람 검토 태스크를 만들고, 검토가 끝나면 `해소` 이벤트를 씁니다. 그러면 다중값은 「미처리 상태」지 영구 상태가 아닙니다.
- **오래된 후보를 표시한다**: 값 자체는 남기되 「6개월 이상 재확인 안 됨」을 붙여서 대표값 후보에서 뺍니다. 삭제가 아니라 **강등**이요.
- **충돌율을 SLO로 잡는다**: 「다중값 키 비율 < 2%」 같은 목표를 두면 통합 파이프라인 품질을 계속 압박할 수 있습니다.

### 5.5 필드 단위로 리듀서를 고른다

전부 아니면 전무가 아닙니다. **필드마다 다른 리듀서를 쓰는 게 정상입니다.**

| 필드 성격 | 리듀서 |
|---|---|
| 알레르기, 금기, 안전 관련 | 전부 모은다 |
| 사람이 직접 설정한 환경설정 | 사람이 이긴다 |
| 마지막 접속 시각 같은 순수 관측값 | 마지막이 이긴다 |
| 별칭·태그처럼 본래 다중값 | 전부 모은다 (충돌이 아님) |

「기본 리듀서를 뭘로 둘 것인가」만 정해 두고(책의 권장은 「사람이 이긴다」), 필드별 예외를 스키마에 선언하는 형태가 실무적입니다.

---

## 6. 한 줄 정리

`accumulate`는 **답을 정하기를 거부하는 리듀서**입니다. 그래서 「답이 하나여야 한다」가 참인 곳에서는 최악이고, **「엇갈린다는 사실이 답의 일부」인 곳에서는 유일하게 맞는 선택**입니다.

그리고 이 선택을 안 하는 것도 선택입니다. 리듀서를 안 정하면 「마지막이 이긴다」가 기본으로 굴러들어오고, 그러면 **에이전트가 마지막에 쓸 때마다 사람이 명시한 것을 덮습니다.**

## 자주 나오는 오해

**「전부 모으면 충돌을 해결한 거 아닌가?」**
아닙니다. **미룬 겁니다.** 해결은 누군가가 「이게 맞다」고 판정할 때 일어나고, `accumulate`는 그 판정 시점까지 정보를 안 잃게 지켜 줄 뿐입니다. 미루는 게 가치 있는 이유는, 잘못 해결한 것은 되돌리기 어렵지만 미룬 것은 언제든 해결할 수 있기 때문이에요.

**「이력 로그가 있으니 상태는 하나로 접어도 되지 않나?」**
이론상 맞습니다(재생하면 다 복원되니까). 실무에서 안 되는 이유는 **조회하는 쪽이 로그를 안 읽기 때문**입니다. UI도 API도 에이전트도 상태만 봅니다. 상태에 「엇갈린다」가 안 들어 있으면, 그 사실은 실질적으로 존재하지 않는 것과 같아요. 안전 임계 도메인에서 이 차이가 사고와 비사고를 가릅니다.

**「그럼 전부 다 accumulate로 하면 안전한 것 아닌가?」**
아닙니다. 모든 필드가 다중값이 되면 조회 쪽 전체가 무너지고, 결국 어딘가에서 **암묵적으로 하나를 고르게** 됩니다(배열 첫 원소, UI 잘림, 모델의 임의 선택). 명시적인 나쁜 리듀서보다 **암묵적인 리듀서가 더 위험합니다.** 최소한 명시적인 건 바꿀 수 있으니까요.
