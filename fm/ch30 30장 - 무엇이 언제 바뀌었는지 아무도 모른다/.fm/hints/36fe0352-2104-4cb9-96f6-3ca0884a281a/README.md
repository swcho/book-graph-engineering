# 「3월 15일에는 팀장이 누구였나」는 이벤트 로그로 어떻게 답하는가

> **답**: 이벤트를 그 시점까지 재생해 상태를 복원한다. 추가는 집합에 넣고 삭제는 빼며 순서대로 적용한다.

---

## 1. 왜 「현재 상태」로는 못 답하나

30장 1절의 출발점입니다. 관계를 *덮어쓰기*로 관리하면 그래프에는 **지금 참인 것**만 남습니다.

```
(박민수)-[:이끔]->(결제팀)   ← 3월에 있었던 엣지
```

4월 1일에 박민수가 빠지고 이서연이 들어오면, 위 엣지는 `DELETE` 로 **사라집니다**. 사라진 뒤에는 그래프 어디를 뒤져도 「3월에는 박민수였다」는 흔적이 없어요. 덮어쓰기는 답을 갱신하는 게 아니라 **답을 지우는** 것입니다.

그래서 `ex1_no_history.py` 는 같은 변경 6건을 두 방식으로 동시에 기록합니다.

| 저장 | 스키마 | 성질 |
|---|---|---|
| 현재 상태 | `Cur(FROM N TO N, kind)` | 추가하면 생기고 삭제하면 없어짐 (파괴적) |
| 이벤트 로그 | `Ev(id, at, subj, kind, obj, op, actor)` | 무슨 일이 있었는지 **추가만** 함 (append-only) |

---

## 2. 원본이 되는 이벤트 로그

`ex1_no_history.py` 의 `CHANGES` 가 그대로 이벤트 로그입니다. 여기서 `id` 는 배열 인덱스로 붙습니다.

```python
CHANGES = [
    ("2026-03-02", "박민수", "이끔", "결제팀", "추가", "hr-sync"),
    ("2026-04-01", "박민수", "이끔", "결제팀", "삭제", "hr-sync"),
    ("2026-04-01", "이서연", "이끔", "결제팀", "추가", "hr-sync"),
    ("2026-04-14", "이서연", "이끔", "정산팀", "추가", "agent-4821"),
    ("2026-04-15", "이서연", "이끔", "정산팀", "삭제", "admin:kim"),
    ("2026-05-20", "이서연", "삶",   "마포",   "추가", "user-utterance"),
]
```

읽는 법은 `(언제, 주어, 관계, 목적어, 연산, 행위자)` 입니다. 한 줄이 「사실 하나가 생겼다/없어졌다」는 **변화**를 적은 것이지, 「이 시점의 전체 상태」가 아니라는 점이 중요합니다. (요약의 *「바뀐 것」을 넣어라* 가 이 얘기입니다.)

## 3. 재생(replay) 코드

Q2 를 푸는 부분은 이게 전부입니다.

```python
# Q2 — 이벤트를 3/15 까지 재생한다
st = set()
for at, s, k, o, op in rows(c.execute(
        "MATCH (e:Ev) WHERE e.at <= '2026-03-15' "
        "RETURN e.at, e.subj, e.kind, e.obj, e.op ORDER BY e.id")):
    if op == "추가":
        st.add((s, k, o))
    else:
        st.discard((s, k, o))
lead = [s for s, k, o in st if k == "이끔" and o == "결제팀"]
```

구조를 뜯어보면 세 조각입니다.

1. **자르기** — `WHERE e.at <= '2026-03-15'` 로 그 시점 **이하**의 이벤트만 고릅니다. 이후 이벤트는 아직 일어나지 않은 일이므로 존재하지 않는 셈 칩니다.
2. **순서 고정** — `ORDER BY e.id` 로 기록된 순서대로 정렬합니다. 같은 날짜에 추가·삭제가 섞이면 순서가 곧 답이므로(`2026-04-01` 이 그렇습니다) 이 정렬이 빠지면 결과가 흔들립니다.
3. **접기(fold)** — 빈 집합 `st` 에서 시작해 `추가`는 `add`, `삭제`는 `discard`. 상태는 이벤트에서 **파생**될 뿐 따로 저장하지 않습니다.

`discard` 를 쓴 것도 의도적입니다. `remove` 와 달리 없는 원소를 빼도 예외가 안 나므로, 중복 삭제나 잘린 구간 때문에 재생이 깨지지 않습니다.

## 4. 3월 15일까지 한 걸음씩 재생

`t = 2026-03-15` 로 잘랐을 때 통과하는 이벤트는 **첫 줄 하나뿐**입니다.

| 단계 | 이벤트 | 연산 | 적용 후 `st` |
|---|---|---|---|
| 시작 | — | — | `{}` |
| 1 | `2026-03-02 박민수 이끔 결제팀` (hr-sync) | `추가` → `st.add(("박민수","이끔","결제팀"))` | `{("박민수","이끔","결제팀")}` |
| — | `2026-04-01 …` 이후 5건 | **3/15 이후라 잘림 (재생 안 함)** | 변화 없음 |

복원된 3월 15일 상태:

```
{ ("박민수", "이끔", "결제팀") }
```

여기에 질문을 겁니다 — `k == "이끔" and o == "결제팀"` 인 것의 주어. → **박민수**.

### 같은 재생기를 다른 시점에 돌리면

시점만 바꾸면 그때 그때의 상태가 나옵니다. 재생기는 그대로입니다.

| `t` | 재생되는 이벤트 | 결과 상태의 「결제팀 이끔」 |
|---|---|---|
| `2026-03-01` | 없음 | (없음 — 아직 아무도 아님) |
| `2026-03-15` | 1건 | **박민수** |
| `2026-04-01` | 3건 (추가 → 삭제 → 추가) | **이서연** |
| `2026-05-20` | 6건 전부 | **이서연** |

`2026-04-01` 줄이 순서의 중요성을 보여 줍니다. 같은 날짜 안에서 `박민수 삭제` 다음에 `이서연 추가` 가 와야 답이 이서연이 됩니다. 날짜만 보고 정렬하면 두 이벤트의 앞뒤가 뒤집힐 수 있으므로 `e.id` 같은 **전순서(total order)** 가 필요합니다.

## 5. 예제가 뽑아 내는 대조표

`ex1` 이 던지는 네 질문 중 현재 상태만으로 답할 수 있는 건 Q1 하나뿐입니다.

| | 질문 | 현재 상태만 | 이벤트 로그 |
|---|---|---|---|
| Q1 | 지금 결제팀 팀장은? | 이서연 | 이서연 |
| **Q2** | **3월 15일에는 팀장이 누구였나?** | **답 못 함** | **박민수 (재생)** |
| Q3 | 「이서연 -이끔-> 정산팀」은 누가 넣고 누가 지웠나? | 답 못 함 | 추가 agent-4821 (04-14) / 삭제 admin:kim (04-15) |

예제 마지막 출력이 요점을 한 줄로 정리합니다.

> 이벤트를 그 시점까지 «재생»하면 그때 상태가 그대로 나온다.

## 6. 대가와 완화책 — 왜 스냅숏이 나오나

재생은 공짜가 아닙니다. 「지금 상태」를 물을 때마다 처음부터 전부 접어야 하니까요. `ex2_replay_cost.py` 가 그 값을 잽니다.

```python
def replay(events, start_state=None):
    st = set(start_state) if start_state else set()
    for _i, s, k, o, op in events:
        if op == "추가":
            st.add((s, k, o))
        else:
            st.discard((s, k, o))
    return st
```

Q2 의 재생 루프와 **같은 함수**입니다. 다른 점은 `start_state` 하나 — 빈 집합 대신 **스냅숏**에서 출발할 수 있게 한 것입니다.

- 처음부터 재생: 이벤트 100만 개면 395ms, 데이터 양에 비례해 계속 늘어남
- 스냅숏 이후만 재생: 16ms, 재생할 이벤트가 **최대 5만 개로 상한**이 걸림

그래서 재생 시간은 *데이터 양*이 아니라 *스냅숏 주기*로 정해집니다. 주기는 복구 목표 시간에서 거꾸로 계산하고요. DB 의 WAL + 체크포인트와 정확히 같은 구조입니다.

## 7. 다른 길 — 구간 엣지, 그리고 둘의 관계

「그때 그래프」를 되살리는 방법이 재생만 있는 건 아닙니다. `ex3_temporal_query.py` 가 두 길을 나란히 놓습니다.

**방법 A — 이벤트 재생**

```python
def by_replay(c, t):
    st = set()
    for at, s, k, o, op in rows(c.execute(
            "MATCH (e:Ev) WHERE e.at <= $t RETURN e.at, e.subj, e.kind, "
            "e.obj, e.op ORDER BY e.id", {"t": t})):
        if op == "추가":
            st.add((s, k, o))
        else:
            st.discard((s, k, o))
    return sorted(st)
```

**방법 B — 엣지에 유효 구간을 박고 쿼리로 자르기 (27장)**

```python
def by_interval(c, t):
    return sorted(rows(c.execute(
        "MATCH (a:N)-[e:R]->(b:N) WHERE e.vfrom <= $t AND e.vto > $t "
        "RETURN a.name, e.kind, b.name", {"t": t})))
```

두 방법의 **답은 같습니다**. 성질이 다를 뿐입니다.

| | 구간 쿼리 | 이벤트 재생 |
|---|---|---|
| 강한 질문 | 「그 시점에 무엇이 참이었나」 = **상태** | 「무엇이 언제 왜 바뀌었나」 = **변화** |
| 못 하는 것 | 「누가 바꿨나」 (엣지에 그 정보가 없음) | 「지금 상태」를 물을 때마다 전부 재생 |
| 위치 | 이벤트에서 만들어 낸 **조회용 뷰(파생)** | **진실의 원본(source of truth)** |

실무에서는 둘 다 둡니다. 중요한 건 **방향**입니다. 이벤트가 원본이고 엣지가 파생이어야 해요. 거꾸로(엣지를 먼저 고치고 이벤트를 나중에 적으면) 두 저장소가 갈라집니다.

참고로 `ex3` 의 「재생이 더 빠르다」는 측정은 **이벤트 9개짜리 장난감 규모**의 결과입니다. 이 숫자로 일반화하면 안 됩니다.

## 8. 재생만으로는 안 되는 것

재생이 답을 주려면 **로그가 믿을 만해야** 합니다. 로그를 나중에 고칠 수 있으면 「3월 15일에는 박민수였다」도 조작 가능한 주장일 뿐이에요.

- 기록을 「곁들이는 것」이 아니라 **「기록이 곧 쓰기다」**로 뒤집어야 합니다. 로그는 빠뜨려도 당장 아무 일이 안 생기므로, 선택지로 두면 반드시 빠집니다.
- 감사 로그가 되려면 `ex5_audit_trail.py` 처럼 **해시 고리**를 겁니다. 내용을 고치면 그 항목의 해시가, 항목을 지우면 다음 항목의 `prev` 가 어긋납니다. 다만 고리는 **막지 않고 표가 나게** 할 뿐입니다.
- 같은 이벤트 열이라도 **어떻게 접느냐(리듀서)** 가 답을 바꿉니다(`ex4`). Q2 는 단순 집합 add/discard 로 접었지만, 「마지막이 이긴다 / 확신도가 이긴다 / 사람이 이긴다 / 전부 모은다」는 각각 다른 답을 냅니다. 이벤트를 쌓는 것만으로는 아무것도 안 정해집니다.
- 이벤트에 개인정보를 직접 넣지 마세요. 지울 수 없는 곳에 지워야 하는 것을 넣게 됩니다.

## 한 줄 정리

**과거 시점 질문은 「그 시점까지의 이벤트만 골라(`at <= t`), 기록 순서대로(`ORDER BY id`), 추가는 넣고 삭제는 빼며 접어(fold)」 그때 상태를 복원한 뒤, 복원된 상태에 질문을 건다.** 3월 15일까지 재생하면 이벤트는 `2026-03-02 박민수 추가` 한 건뿐이므로 답은 **박민수**다.
