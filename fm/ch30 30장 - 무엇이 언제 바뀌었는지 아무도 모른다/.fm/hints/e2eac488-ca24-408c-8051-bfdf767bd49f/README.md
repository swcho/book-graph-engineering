# 「로그를 잘 남기자」로는 왜 안 되는가

> **Q.** "로그를 잘 남기자"로 해결되지 않는 이유는 무엇인가?
>
> **A.** 로그는 빠뜨려도 아무 일이 안 생긴다. '기록도 남긴다'가 아니라 '기록이 곧 쓰기다'로 뒤집어야 한다.

---

## 1. 문제의 출발점 — 현재 상태만 두면 못 하는 질문들

30장은 이런 질문에서 시작합니다. 「이거 원래 이랬나요?」

그래프에 *지금 상태*만 저장해 두면 답할 수 있는 건 딱 하나입니다.

| 질문 | 현재 상태만 | 이벤트 로그 |
|---|---|---|
| Q1 지금 결제팀 팀장은? | 이서연 | 이서연 |
| Q2 3월 15일에는 팀장이 누구였나? | **답 못 함** | 박민수 |
| Q3 「이서연 -이끔-> 정산팀」은 누가 넣고 누가 지웠나? | **답 못 함** | 추가 agent-4821 / 삭제 admin:kim |
| Q4 에이전트가 넣은 것 중 사람이 되돌린 게 몇 건인가? | **답 못 함** | 1건 |

(`code/ex1_no_history.py`)

운영에서 실제로 자주 나오는 건 Q1이 아니라 Q2~Q4입니다. 「3월에는 어땠나」는 감사와 분쟁에서 반드시 나오고, 「누가 넣었나」는 사고 조사의 첫 질문이며, 「에이전트가 넣은 것 중 되돌려진 비율」은 28장의 품질 지표 그 자체입니다.

덮어쓰기는 답을 **지웁니다**. 그래서 나중에 복원이 안 됩니다.

---

## 2. 그러면 「로그를 잘 남기자」로 되지 않나?

여기서 대부분의 팀이 내놓는 첫 처방이 이겁니다. "쓰기 할 때 로그도 같이 남기자."

이게 안 되는 이유는 기술이 아니라 **구조**입니다.

### 핵심 — 로그는 빠뜨려도 아무 일이 안 생긴다

```python
def update_lead(team, person):
    graph.set_lead(team, person)       # 이게 실패하면 → 즉시 터진다
    audit_log.write(team, person)      # 이게 빠지면 → 아무 일도 안 생긴다
```

두 줄의 **실패 비용이 비대칭**입니다.

- 상태 쓰기를 빠뜨리면 → 다음 조회에서 즉시 드러납니다. 기능이 안 돕니다. 누군가 바로 신고합니다.
- 로그 쓰기를 빠뜨리면 → **오늘은 아무 일도 안 일어납니다.** 테스트도 통과하고, 데모도 되고, 배포도 됩니다. 문제는 6개월 뒤 감사에서, 혹은 사고 조사 중에 "그때 기록이 없네요"로 나타납니다.

즉 로그 누락은 **되먹임(feedback)이 없는 결함**입니다. 되먹임이 없는 규율은 반드시 무너집니다.

### 그래서 실제로는 이렇게 무너진다

- 급한 핫픽스에서 상태만 고치고 로그는 안 씁니다 — 아무도 모릅니다.
- 새로 들어온 사람이 새 쓰기 경로를 추가하는데 로그 호출을 몰라서 안 넣습니다 — 아무도 모릅니다.
- 배치 작업, 마이그레이션 스크립트, 관리자 콘솔이 DB를 직접 건드립니다 — 아무도 모릅니다.
- 로그 쓰기가 실패해도(디스크 풀, 네트워크) 「본 작업은 성공시켜야 하니까」 예외를 삼킵니다 — 아무도 모릅니다.
- 트랜잭션이 갈라져 있으면 상태는 커밋되고 로그는 롤백됩니다 — 아무도 모릅니다.

그리고 이 구멍들은 **한 번만 뚫리면 영구히 복구 불가**입니다. 상태는 나중에 고칠 수 있지만, 남기지 않은 이력은 어디에서도 되살릴 수 없습니다.

### 한 줄 정리

「로그도 남기자」는 **규율**에 기대는 해법입니다. 규율은 사람 수와 시간에 반비례해서 닳습니다. 그리고 로그는 닳아도 경보가 울리지 않습니다.

---

## 3. 뒤집기 — 「기록이 곧 쓰기다」

그래서 30.2절의 처방은 순서를 바꾸는 게 아니라 **관계를 뒤집는** 것입니다.

| | 「기록도 남긴다」 | 「기록이 곧 쓰기다」 |
|---|---|---|
| 진실의 원본 | 상태 (그래프/테이블) | **이벤트 로그** |
| 로그의 지위 | 부수 효과, 곁다리 | 유일한 쓰기 경로 |
| 로그를 빠뜨리면 | 아무 일 없음 | **상태가 안 바뀜 → 즉시 터짐** |
| 상태의 지위 | 원본 | 이벤트에서 **파생**된 뷰 |
| 기대는 것 | 사람의 규율 | 구조 |

핵심은 이겁니다. **상태를 바꾸는 유일한 방법이 이벤트를 추가하는 것**이 되면, 이벤트를 빠뜨리는 순간 기능 자체가 동작하지 않습니다. 로그 누락이 「조용한 결함」에서 「시끄러운 결함」으로 바뀝니다. 되먹임이 생기는 겁니다.

```
[기록도 남긴다]                     [기록이 곧 쓰기다]
  명령 ─┬─> 상태 (원본)              명령 ──> 이벤트 로그 (원본, 추가 전용)
        └─> 로그 (곁다리, 빠져도 됨)                  │ 재생/투영
                                                    ▼
                                            상태 = 조회용 뷰 (파생, 언제든 재생성)
```

이게 **이벤트 소싱(event sourcing)** 이고, 데이터베이스가 30년 전부터 쓰던 **쓰기 전 로그(WAL, write-ahead log)** 와 같은 구조입니다. 이름부터 「쓰기 *전에* 로그」입니다. 로그가 먼저고 상태가 나중입니다.

---

## 4. 뒤집고 나면 따라오는 것들

방향을 뒤집으면 그 뒤가 자동으로 정해지지는 않습니다. 30장 나머지가 그 값을 다룹니다.

- **파생은 진짜로 재생성 가능해야 한다.** 조회용 뷰를 실제로 지우고 재생해 봐야 「파생이 맞다」가 증명됩니다. 안 해 보면 어느새 뷰만 직접 고친 코드가 생겨 있고, 그러면 다시 원래 문제로 돌아갑니다 (29장의 「두 저장소가 갈라진다」).
- **이벤트에는 「바뀐 것」을 넣는다.** 「바뀐 뒤 전체 상태」를 넣으면 무엇이 바뀌었는지 알 수 없고 동시 변경도 합칠 수 없습니다.
- **재생 시간은 데이터 양이 아니라 스냅숏 주기로 정해진다.** 이벤트가 백만 개든 천만 개든 재생할 건 최대 「스냅숏 주기」만큼입니다. 주기는 복구 목표 시간에서 거꾸로 계산합니다 (`ex2_replay_cost.py`).
- **쌓는 것만으로는 아무것도 안 정해진다.** *어떻게 접을 것인가*(리듀서)가 실제 동작을 정하고, 그건 도메인 결정입니다. 「마지막이 이긴다」를 기본으로 두면 에이전트가 사람을 덮습니다 (`ex4_reducer_conflict.py`).
- **감사 로그가 되려면 「안 고쳤다」를 보일 수 있어야 한다.** 해시 고리는 위변조를 *막지* 않고 *표가 나게* 합니다 (`ex5_audit_trail.py`).
- **이벤트에 개인정보를 직접 넣지 않는다.** 지울 수 없는 곳에 지워야 하는 것을 넣게 됩니다.

---

## 5. 시험 대비 요약

- **왜 「로그를 잘 남기자」가 실패하나** → 로그 누락에 되먹임이 없어서. 빠뜨려도 그날은 아무 일이 안 생기고, 문제는 복구 불가능해진 뒤에 드러난다.
- **무엇으로 대체하나** → 「기록도 남긴다」 → 「**기록이 곧 쓰기다**」. 이벤트가 원본, 상태는 파생.
- **뒤집으면 뭐가 좋아지나** → 규율이 아니라 구조가 보장한다. 이벤트를 빠뜨리면 기능이 안 도니까 즉시 들킨다.
- **관련 개념** → 이벤트 소싱, 추가 전용 로그, 쓰기 전 로그(WAL), 재생, 스냅숏, CQRS
