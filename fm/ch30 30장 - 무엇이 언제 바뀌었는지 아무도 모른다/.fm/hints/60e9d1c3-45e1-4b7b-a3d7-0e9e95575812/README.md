# 「마지막이 이긴다」가 위험한 이유

> **질문** 「마지막이 이긴다」가 위험한 이유는 무엇인가?
>
> **답** 에이전트가 마지막에 쓰면 사람이 명시한 것을 덮는다. 예제에서는 4월 9일 사람의 「채식」을 22일 에이전트가 「비건」으로 바꿨다.

출처: 30장 30.4절 「어떻게 접느냐가 답을 정한다」 / `code/ex4_reducer_conflict.py`

---

## 1. 먼저 용어부터

「마지막이 이긴다」는 **LWW(last-write-wins)** 를 우리말로 옮긴 것이다. 같은 키에 대한 쓰기가 여러 개 쌓였을 때, **타임스탬프가 가장 큰 쓰기를 살리고 나머지를 버리는** 충돌 해소 규칙이다.

30장의 맥락에서 이건 단순한 저장 정책이 아니라 **리듀서(reducer)** 다. 이 장의 기본 구도가 「이벤트가 원본이고 상태는 파생」이기 때문이다. 이벤트를 쌓는 것만으로는 아무것도 정해지지 않고, **그 이벤트 열을 어떻게 접어서(fold) 하나의 현재 상태를 만드느냐**가 실제 동작을 정한다. LWW는 그 접는 방법 중 하나일 뿐이다.

예제 4의 구현은 열 줄도 안 된다.

```python
def last_write_wins(evs):
    st = {}
    for at, who, k, v, op, conf in evs:
        if op == "추가":
            st[k] = (v, at, who)   # 뒤에 온 것이 앞의 것을 덮는다
        else:
            st.pop(k, None)
    return st
```

이벤트를 시간순으로 훑으면서 그냥 덮어쓴다. 마지막 쓰기가 남는다. 끝.

---

## 2. 그런데 왜 이게 기본값으로 흔히 쓰이는가

위험하다면서 왜 어디서나 쓰이나. 이유가 여러 겹이다.

### (1) 아무 결정도 안 해도 「그냥 되는」 유일한 규칙

리듀서를 아예 설계하지 않고 코드를 짜면 자연스럽게 LWW가 된다. `st[k] = v`는 프로그래밍 언어의 기본 대입 동작이고, `UPDATE ... SET col = ?`도 마찬가지다. **덮어쓰기가 곧 LWW다.** 즉 LWW는 「선택한 정책」이 아니라 **「정책을 선택하지 않았을 때 남는 것」** 인 경우가 대부분이다. 이게 가장 위험한 지점이다. 아무도 결정한 적이 없으니 아무도 책임지지 않고, 문서에도 없다.

### (2) 상태가 O(1)이고 메타데이터가 필요 없다

키마다 값 하나 + 타임스탬프 하나만 있으면 된다. 충돌 이력을 보관할 필요가 없다. 「전부 모은다(accumulate)」 리듀서처럼 값이 집합으로 불어나지도 않고, 「사람이 이긴다(human_wins)」처럼 출처 등급표를 유지·관리할 필요도 없다.

### (3) 결합법칙·교환법칙·멱등성을 만족한다 — 분산 시스템에서 특히

LWW는 **CRDT(LWW-Register, LWW-Element-Set)** 의 기본형이다. 같은 이벤트를 어떤 순서로 받아 접어도, 몇 번 중복해서 받아도 같은 결과가 나온다. 그래서 재시도·재전송이 일상인 복제 환경(Cassandra, DynamoDB, Riak, CouchDB, Redis CRDT, 대부분의 오프라인 우선 모바일 동기화)이 이걸 기본 충돌 해소로 채택했다. 노드끼리 대화하지 않고도 수렴한다는 게 결정적인 장점이다.

### (4) 설명하기 쉽다

「최신 값이 맞는 값」은 사람에게 직관적이다. 제품 회의에서 반박당하지 않는다. 온도 센서 최신값, 마지막 접속 시각처럼 **실제로 최신이 맞는 도메인**도 분명히 존재한다.

문제는 이 마지막 조건이다. **LWW가 옳은 건 「값이 시간에 따라 자연스럽게 갱신되고, 쓰는 주체가 모두 동등하게 권위 있는」 도메인에 한한다.** 사람과 에이전트가 같은 필드를 두고 다투는 상황은 그 조건에 해당하지 않는다.

## 3. 예제로 본 사고 장면

`ex4_reducer_conflict.py`의 이벤트 5건이다. `선호`라는 하나의 키를 사람과 에이전트가 번갈아 고친다.

| 시각 | 행위자 | 값 | op | 확신도 |
|---|---|---|---|---|
| 2026-04-01T09:00 | `hr-sync` | 채식 | 추가 | 0.95 |
| 2026-04-03T14:20 | `agent-4821` | 육식 | 추가 | 0.61 |
| 2026-04-03T14:21 | `agent-4821` | 채식 | 삭제 | 0.61 |
| **2026-04-09T10:05** | **`user`** | **채식** | **추가** | **1.00** |
| 2026-04-22T16:40 | `agent-5102` | 비건 | 추가 | 0.78 |

같은 이벤트 열에 리듀서 넷을 적용하면 답이 넷으로 갈린다.

| 리듀서 | 결과 | 누가 넣은 것 |
|---|---|---|
| 마지막이 이긴다 (LWW) | 선호 = **비건** | `agent-5102` |
| 확신도가 이긴다 | 선호 = 채식 | `user` (1.00) |
| 사람이 이긴다 | 선호 = 채식 | `user` (등급 3) |
| 전부 모은다 | 선호 = 비건 / 채식 | — |

**LWW만 「비건」이다.** 4월 9일에 사람이 자기 입으로 「채식」이라고 명시했는데, 13일 뒤 확신도 0.78짜리 에이전트가 「비건」이라고 써 넣자 사람의 명시적 선언이 조용히 사라졌다.

여기서 나쁜 건 결과가 틀렸다는 것만이 아니다. **덮어쓰는 순간 아무 신호도 나지 않는다는 것**이 더 나쁘다. 오류도, 경고도, 충돌 표시도 없다. 시스템 입장에서 이건 정상 동작이다. 사람이 「내가 채식이라고 했는데요?」라고 물어야 비로소 사건이 된다. 30장 첫 줄의 「이거 원래 이랬나요?」가 정확히 이 장면이다.

그나마 이벤트 로그가 남아 있으니 「누가 언제 덮었는지」는 추적할 수 있다. 현재 상태만 저장했다면(예제 1) 그 추적조차 불가능하다. 다만 **추적 가능성은 사후 조사를 가능하게 할 뿐, 덮어쓰기 자체를 막지는 못한다.** 리듀서를 바꾸지 않는 한 재생할 때마다 계속 「비건」이 나온다.

## 4. 에이전트 쓰기 빈도가 사람보다 압도적일 때

여기가 이 문제의 핵심이고, LWW가 전통적인 시스템에서보다 에이전트 시스템에서 훨씬 더 위험해지는 이유다.

**LWW는 「마지막에 쓴 쪽」에게 권한을 준다. 그리고 마지막에 쓸 확률은 쓰기 빈도에 비례한다.**

- 사람은 자기 선호를 몇 달에 한 번 말한다. 이벤트로 치면 분기당 한두 건.
- 에이전트는 대화 턴마다, 배치 잡이 돌 때마다, 스케줄러가 깨울 때마다 쓴다. 하루에도 수십, 수백 건.

두 쪽의 쓰기 빈도가 100:1이라면, 임의의 시점에 「가장 최근 쓰기」가 에이전트일 확률도 사실상 100:1이다. 즉 **LWW를 기본으로 두는 순간, 사람의 입력은 통계적으로 거의 항상 진다.** 이건 버그가 아니라 정책의 정의상 그렇게 되는 것이고, 트래픽이 늘수록 심해진다.

여기서 파생되는 문제들:

- **사일런트 회귀(silent regression)**: 사람이 고쳐 놓은 값이 다음 에이전트 동기화 주기에 원래대로 돌아간다. 사용자 눈에는 「고쳤는데 왜 또 이래요」로 보인다.
- **핑퐁**: 사람이 다시 고치고 에이전트가 다시 덮는 루프. 이벤트 로그만 부풀고 아무도 이기지 못한다.
- **오류의 자기 강화**: 에이전트가 잘못 추론한 값을 쓰고, 다음 턴에 그 값을 컨텍스트로 읽어 다시 확신을 갖고 쓴다. 사람이 끼어들 창이 점점 좁아진다.
- **28장 품질 지표의 왜곡**: 「에이전트가 넣은 것 중 사람이 되돌린 비율」을 재려 해도, 사람의 되돌림이 다시 덮이면 되돌린 흔적이 현재 상태에 남지 않는다. 로그가 있어야만 측정이 가능하다.
- **책임 소재의 실종**: 「사람이 명시했다」는 사실이 상태에 반영되지 않으니, 정책·동의·설정 같은 것을 LWW로 관리하면 규정 준수 관점에서 방어할 수 없다.

정리하면, **LWW는 「가장 최근」과 「가장 권위 있음」을 같은 것으로 취급한다.** 사람과 에이전트가 섞여 쓰는 시스템에서 이 둘은 거의 반대 방향이다. 사람이 드물게 쓰는 이유는 권위가 없어서가 아니라 자주 말할 필요가 없어서다.

## 5. 그리고 시계 문제 (clock skew)

LWW의 두 번째 결함은 「마지막」을 판정하는 근거 자체가 흔들린다는 것이다. **LWW는 타임스탬프 순서를 인과 순서로 믿는다.** 그런데 분산 환경에서 타임스탬프는 그렇게 믿을 물건이 아니다.

### (1) 벽시계는 노드마다 다르다

에이전트 워커, API 서버, 사용자 단말이 각자 자기 시계로 타임스탬프를 찍으면, NTP로 맞춰도 수 ms~수백 ms, 잘못 설정된 장비면 몇 분에서 몇 시간까지 어긋난다. 시계가 앞서 있는 노드의 쓰기는 **실제로는 먼저 일어났어도 항상 이긴다.** 반대로 시계가 뒤처진 노드의 쓰기는 영원히 진다. 조용히, 일관되게.

예제의 이벤트가 `2026-04-22T16:40`처럼 문자열 타임스탬프인 것도 같은 이야기다. 이 값을 누가 어느 시계로 찍었는지가 결과를 정한다.

### (2) NTP는 시간을 뒤로 되돌린다

시계 보정이 들어오면 벽시계가 과거로 점프할 수 있다. 같은 노드 안에서도 나중에 일어난 쓰기가 더 작은 타임스탬프를 갖는 일이 생긴다. 그래서 경과 시간 측정에는 단조 증가 시계(monotonic clock)를 쓰라는 조언이 있는데, LWW는 노드 간 비교가 필요하므로 단조 시계를 쓸 수도 없다.

### (3) 타임스탬프가 같으면 무엇으로 정하나

예제 5의 감사 로그 이벤트를 보면 앞의 두 건이 둘 다 `2026-04-01T09:00`이다. 초 단위, 밀리초 단위 해상도에서는 동률이 흔하다. LWW 구현체들은 동률을 노드 ID나 값 자체를 비교해서 임의로 깬다. 즉 **결과가 도메인 의미와 무관한 기준으로 정해진다.**

### (4) 근본 문제: 벽시계는 인과관계를 모른다

A가 B를 보고 나서 쓴 것인지, A와 B가 서로 모른 채 동시에 쓴 것인지를 벽시계 타임스탬프는 구분하지 못한다. 이 구분을 하려면 **논리 시계(Lamport clock), 벡터 시계(vector clock), 버전 벡터** 같은 장치가 필요하다. 이게 바로 **31장 「두 에이전트가 같은 노드를 동시에 고쳤다」** 로 넘어가는 다리다. 30장은 「변경이 순서대로 온다」고 가정했지만, 진짜 동시 쓰기에는 순서 자체가 없다.

그리고 여기에 인과관계까지 얹으면 문제가 하나 더 드러난다. **LWW는 「덮어쓴 값이 무엇이었는지」를 알지 못한다.** 「비건」을 쓴 `agent-5102`는 사람이 「채식」이라고 했다는 사실을 봤을 수도, 안 봤을 수도 있다. LWW는 그 차이를 다루지 않는다. 이 장의 요약 문장 「이벤트에는 바뀐 것을 넣으세요, 바뀐 뒤 전체 상태를 넣으면 무엇이 바뀌었는지 모른다」와 같은 결의 문제다.

## 6. 그러면 무엇으로 대신하나

예제 4가 제시하는 대안 셋과 각각의 값이다.

### 확신도가 이긴다 (`highest_confidence`)

사람 발화의 확신도 1.00이 에이전트의 0.78을 이긴다. 결과는 「채식」으로 맞다. 그런데 **확신도는 에이전트가 스스로 매기는 값이다.** 20장 「모델이 스스로 올릴 수 있는 값은 지표로 못 쓴다」가 그대로 적용된다. 에이전트가 0.99를 찍으면 그날로 무력해진다. 최적화 압력이 걸리는 순간 게이밍의 대상이 되는 지표다.

### 사람이 이긴다 (`human_wins`) — 저자가 기본으로 쓰는 것

출처에 등급을 매긴다. 예제에서는 `user`=3, `hr-sync`=2, 그 외(에이전트)=1이다. 등급이 같거나 높은 쓰기만 기존 값을 덮을 수 있다.

```python
rank = {"user": 3, "hr-sync": 2}
...
if k not in st or r >= st[k][3]:
    st[k] = (v, at, who, r)
```

핵심은 **등급을 시스템이 정한다는 것**이다. 확신도와 달리 에이전트가 자기 등급을 올릴 수 없다. 그래서 게이밍에 견딘다. 삭제 처리에도 같은 규칙이 걸려서, 낮은 등급의 행위자는 높은 등급이 넣은 것을 지우지도 못한다(예제의 `삭제` 분기). 실제로 4월 3일에 `agent-4821`이 「채식」을 지우려 한 시도가 이 규칙에서 무력화된다.

값도 있다. **등급표를 누군가 유지해야 하고, 새 행위자가 생길 때마다 등급을 정해야 한다.** 그리고 등급이 같은 두 에이전트가 부딪히면 다시 LWW로 떨어진다.

### 전부 모은다 (`accumulate`)

지우지 않고 「비건 / 채식」처럼 답을 여럿으로 남긴다. **충돌을 숨기지 않는다**는 게 장점이고, 조회하는 쪽이 곤란해진다는 게 단점이다. 하지만 「충돌이 있다」는 사실 자체가 중요한 도메인(의료 기록, 법적 진술, 상충하는 출처를 나란히 보여야 하는 경우)에서는 이게 맞다. Riak의 siblings, Dynamo의 다중 버전 반환이 같은 발상이다.

## 7. 한 줄 정리

**LWW는 아무도 결정하지 않았을 때 남는 기본값인데, 「가장 최근」을 「가장 권위 있음」으로 착각한다.** 에이전트가 사람보다 압도적으로 자주 쓰는 시스템에서는 사람의 명시적 선언이 통계적으로 거의 항상 지고, 그 패배가 아무 신호 없이 조용히 일어난다. 게다가 「마지막」을 판정하는 벽시계 타임스탬프 자체가 노드 간 편차·NTP 되돌림·동률 때문에 신뢰할 수 없다. 그래서 이 장은 **접는 방법(리듀서)은 기본값에 맡길 게 아니라 도메인 결정으로 명시하라**고 말하고, 저자의 기본값으로 **「사람이 이긴다」** 를 제시한다. 에이전트가 스스로 올릴 수 없는, 시스템이 정한 등급이기 때문이다.
