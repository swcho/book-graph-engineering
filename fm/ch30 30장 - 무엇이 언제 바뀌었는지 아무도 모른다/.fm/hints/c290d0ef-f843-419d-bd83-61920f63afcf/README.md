# 감사 로그가 되려면 무엇을 보일 수 있어야 하는가?

> **Q.** 감사 로그가 되려면 무엇을 보일 수 있어야 하는가?
>
> **A.** 「안 고쳤다」를 보일 수 있어야 한다. 해시 고리는 막지 않고 표가 나게 한다.

출처: 30장 「무엇이 언제 바뀌었는지 아무도 모른다」 30.5절 · `code/ex5_audit_trail.py`

---

## 1. 왜 이 질문이 나오나 — 「쌓았다」와 「감사할 수 있다」는 다르다

30장의 앞 절들은 *이벤트가 원본이고 상태는 파생*이라는 방향을 세웠습니다.
덮어쓰기를 버리고 이벤트를 추가 전용(append-only)으로 쌓으면
「3월에는 팀장이 누구였나」, 「누가 넣고 누가 지웠나」에 답할 수 있게 되죠(`ex1`).

그런데 여기서 한 칸이 더 남습니다.

- **이벤트 로그**: 「무슨 일이 있었는지」를 *기록해 두었다*
- **감사 로그(audit trail)**: 그 기록이 **나중에 손대지 않았음을 보일 수 있다**

차이가 나는 지점은 이겁니다. 그냥 테이블에 쌓아 두면
DB 접근 권한이 있는 사람이 `UPDATE` / `DELETE` 한 방으로 과거를 고칠 수 있어요.
그리고 그런 권한을 가진 사람은 대개 **여럿**입니다.
사고가 났을 때 로그를 들이밀면 상대는 이렇게 묻습니다.

> 「그거 나중에 고친 거 아니에요?」

**감사 로그의 본질적 요구는 「무슨 일이 있었나」를 보이는 게 아니라
「그 뒤로 안 고쳤다」를 보이는 것**입니다.
전자는 로그 한 줄이면 되지만, 후자는 구조가 필요합니다.

이것이 무결성(integrity)과 부인 방지(non-repudiation)의 문제이고,
NIST SP 800-53 Rev.5의 AU(Audit and Accountability) 계열이 다루는 영역입니다.

| 통제 | 내용 | 30.5절과의 대응 |
|---|---|---|
| AU-9 | 감사 정보·감사 도구를 무단 접근/변경/삭제로부터 보호 | 「DB 권한자가 고칠 수 있다」는 문제 정의 그 자체 |
| AU-9(2) | 감사 기록을 **다른 물리 시스템/컴포넌트**에 저장 | 「해시를 밖에 내보내라」 |
| AU-9(3) | **암호학적 메커니즘**으로 감사 정보의 무결성을 보호 | 해시 고리 / 서명 |
| AU-9(1) | 하드웨어 write-once 매체(WORM) | 물리적으로 못 고치게 하는 다른 층위 |
| AU-10 | 부인 방지(non-repudiation), 신원 결합, chain of custody | 「누가 했다」를 부인 못 하게 |

즉 「안 고쳤다를 보일 수 있어야 한다」는 저자의 취향이 아니라
감사 통제 표준이 감사 기록에 요구하는 성질입니다.

## 2. 해시 고리(hash chain)가 하는 일

`ex5_audit_trail.py`가 쓰는 구조는 아주 단순합니다.
각 항목이 **앞 항목의 해시**를 자기 몸통에 포함시키고, 그 전체를 다시 해시합니다.

```
hash(n) = SHA256( [seq, at, actor, op, payload, hash(n-1)] )
```

```python
def digest(seq, at, actor, op, payload, prev):
    body = json.dumps([seq, at, actor, op, payload, prev],
                      ensure_ascii=False, sort_keys=True)
    return hashlib.sha256(body.encode()).hexdigest()[:16]
```

`prev`가 해시 입력에 **들어간다**는 게 핵심입니다.
이것 때문에 고리가 생기고, 한 칸을 건드리면 그 뒤가 전부 어긋납니다.

```
seq1 ──hash1──► seq2 ──hash2──► seq3 ──hash3──► seq4 ──hash4──► seq5
       prev="-"        prev=h1        prev=h2        prev=h3        prev=h4
```

검증은 처음부터 다시 계산해 보는 것뿐입니다.

```python
def verify(db):
    bad = []
    prev = "-"
    for seq, at, actor, op, payload, p, h in db.execute("SELECT * FROM log ORDER BY seq"):
        want = digest(seq, at, actor, op, json.loads(payload), prev)
        if p != prev:
            bad.append((seq, "앞 고리가 안 맞음"))   # ← 앞이 지워졌다
        elif h != want:
            bad.append((seq, "내용이 바뀜"))         # ← 내가 고쳐졌다
        prev = h
    return bad
```

### 두 가지 공격이 서로 다른 방식으로 잡힌다

`ex5`는 이걸 실제로 두 번 해 봅니다.

| 공격 | 무엇이 어긋나나 | 검출 메시지 |
|---|---|---|
| **내용 변조** — seq 4의 `이서연`을 `김도현`으로 `UPDATE` | 저장된 `hash`가 재계산 값과 불일치 | `(4, '내용이 바뀜')` |
| **항목 삭제** — seq 3을 통째로 `DELETE` | seq 4의 `prev`가 이제 seq 2의 해시와 안 맞음 | `(4, '앞 고리가 안 맞음')` |

주목할 점: **삭제는 지운 항목이 아니라 「다음 항목」에서 잡힙니다.**
지워진 것은 이미 없으니 스스로 신고할 수 없죠.
대신 뒤에 오는 항목이 「내 앞은 이게 아니었다」고 말해 줍니다.
고리 구조가 **없어진 것**까지 검출할 수 있는 이유가 여기 있습니다.
(단순히 각 행에 해시만 붙여 두면 — 고리 없이 — 삭제는 절대 못 잡습니다.)

## 3. 「막지 않고 표가 나게 한다」 — 이 문장이 진짜 핵심

이 카드의 답에서 절반을 차지하는 문장입니다. 그리고 자주 오해받는 지점이에요.

해시 고리는 **위조를 불가능하게 만들지 않습니다.**
DB 쓰기 권한이 있는 사람은 seq 4를 고친 뒤 **seq 4부터 끝까지 해시를 전부 다시 계산**하면
`verify()`를 통과하는 **일관된 위조본**을 만들 수 있습니다.
`digest()` 함수는 공개된 로직이고, 비밀 키가 하나도 안 들어가니까요.

그래서 성질을 정확히 쓰면 이렇습니다.

- ✗ 변조 **방지**(tamper-proof / tamper-resistant)
- ✓ 변조 **명백**(tamper-**evident**) — 손댄 흔적이 남는다

> 「고리는 «막지» 않는다. «표가 나게» 할 뿐이다.
> 전부 다시 계산하면 일관된 위조본을 만들 수 있다.」

### 같은 성질을 국제 표준이 대놓고 말한다: RFC 6962 (Certificate Transparency)

키워드 표에서 해시 고리의 출처로 RFC 6962를 든 이유가 여기 있습니다.
CT는 인증기관(CA)이 발급한 인증서를 추가 전용 Merkle Tree 로그에 쌓게 하는 표준인데,
RFC 본문이 자신의 성질을 이렇게 못 박습니다.

> "The logs do not themselves prevent misissue, but they ensure that
> interested parties ... can **detect** such misissuance."
> — RFC 6962 §1

즉 **잘못된 인증서 발급을 막는 게 아니라, 발급되면 들킨다**는 구조입니다.
30.5절의 「막지 않고 표가 나게 한다」와 정확히 같은 설계 철학이에요.
CT가 그 위에 얹은 장치들이 곧 4절에서 말할 「밖으로 내보내기」의 실물입니다.

| CT 장치 | 하는 일 |
|---|---|
| Merkle Tree + inclusion proof(감사 증명) | 「이 항목이 이 로그에 들어 있다」를 O(log n)으로 증명 |
| **consistency proof**(일관성 증명) | 「새 로그가 옛 로그의 **추가 전용 확장**이다」 — 과거를 안 고쳤음을 증명 |
| **STH에 로그 운영자의 서명** | 로그 운영자가 다시 계산해도 **키 없이는 서명 못 함** |
| SCT / MMD, 제3자 monitor·auditor | 여러 눈이 각자 보관한 값으로 교차 검증 |

`ex5`의 장난감 구현과 CT의 차이가 곧 「어디까지 올릴 수 있는가」의 지도입니다.
`ex5`는 서명도, 외부 감시자도 없는 **가장 싼 층**입니다.

## 4. 그래서 어디까지 해야 하나 — 「무엇을 지키는지에 달렸다」

전부 다시 계산하는 내부자를 막으려면 **해시를 시스템 밖으로 내보내야** 합니다.
로그 자체를 고칠 수 있는 사람이 **손댈 수 없는 곳**에 값이 한 벌 있어야 하니까요.

층위를 값이 싼 순서로 늘어놓으면 이렇습니다.

| 층 | 방법 | 막는 것 | 값 |
|---|---|---|---|
| 0 | 그냥 테이블에 쌓기 | (없음) 조용히 고쳐짐 | 0 |
| 1 | **해시 고리** (`ex5`) | 무심한/부주의한 변경, 사후 검증 가능 | 아주 쌈 |
| 2 | 로그를 **별도 시스템/계정**에 복제, 권한 분리 (AU-9(2)) | 한 시스템 권한자의 단독 위조 | 낮음 |
| 3 | 주기적 다이제스트를 **외부에 게시/보관**(다른 조직, 사내 위키, 매일 1회) | 시점 이후 과거 전체의 재계산 위조 | 중간 |
| 4 | 로그 항목/트리 헤드에 **서명**(AU-9(3), CT의 STH), 키를 HSM에 격리 | 키 없는 재계산 위조 | 중간~높음 |
| 5 | **WORM 매체**(AU-9(1)), 공개 원장 앵커링, RFC 3161 타임스탬프 | 물리적/제3자 수준 부인 방지 | 높음 |

책의 결론은 과잉 설계에 대한 경고로 마무리됩니다.

> 「대부분의 사내 시스템에서는 «표가 나는 것»만으로 충분하다.
> 내부자가 작정하고 위조하는 것까지 막으려면 값이 확 뛴다.
> 어디까지 막을지는 무엇을 지키는지에 달렸다.」

**층 1(해시 고리)만으로도 층 0에서 층 1로 가는 이득이 가장 큽니다.**
「조용히 고쳐지는 상태」에서 「고치면 표가 나는 상태」로 넘어가는 것이 질적 변화이고,
그 뒤부터는 비용 대비 이득이 급격히 나빠집니다.

## 5. 흔한 오답 / 헷갈리는 지점

| 오해 | 바로잡기 |
|---|---|
| 「감사 로그는 무슨 일이 있었는지 보이면 된다」 | 그건 그냥 이벤트 로그. 감사 로그는 **「그 뒤 안 고쳤다」**까지 보여야 함 |
| 「해시 고리를 걸면 위변조가 **불가능**해진다」 | 아니오. 전부 재계산하면 일관된 위조본이 만들어짐. **tamper-evident**이지 tamper-proof가 아님 |
| 「각 행에 해시만 붙여도 같다」 | 삭제를 못 잡음. `prev`를 해시 입력에 넣어 **고리**를 만들어야 「없어진 항목」이 드러남 |
| 「append-only 테이블이면 감사 로그다」 | 애플리케이션이 append만 한다는 규약일 뿐, DB 권한자에게는 아무 제약이 아님 |
| 「지운 항목에서 오류가 잡힌다」 | 지운 항목은 이미 없음. **다음 항목의 `prev` 불일치**로 잡힘 |
| 「해시 고리면 다 됐으니 외부 공개는 불필요」 | 내부자 재계산 위조를 막으려면 값을 **밖**에 내보내야 함(AU-9(2), CT의 서명된 STH·모니터) |
| 「감사 로그니까 개인정보도 다 넣자」 | 30장 마지막 요약: **이벤트에 개인정보를 직접 넣지 말 것**. 지울 수 없는 곳에 지워야 하는 것을 넣게 됨(참조/토큰으로) |

---

## 6. 한 줄 정리

> **이벤트를 쌓는 것과 감사할 수 있는 것은 다르다.
> 감사 로그의 요구는 「안 고쳤다」를 보일 수 있어야 한다는 것이고,
> 해시 고리는 그걸 «막아서»가 아니라 «표가 나게 해서» 달성한다.
> 재계산 위조까지 막으려면 값을 밖으로 내보내야 하고,
> 거기까지 갈지는 무엇을 지키는지에 달렸다.**
