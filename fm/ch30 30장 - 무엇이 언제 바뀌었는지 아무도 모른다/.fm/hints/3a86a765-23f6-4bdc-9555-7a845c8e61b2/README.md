# '확신도가 이긴다'의 문제는 무엇인가?

> **답**: 확신도는 에이전트가 스스로 매기는 값이다. 20장의 "모델이 스스로 올릴 수 있는 값은 지표로 못 쓴다"가 적용된다.

---

## 1. 어디서 나온 이야기인가

30장 30.4절 「어떻게 접느냐가 답을 정한다」, 예제 `code/ex4_reducer_conflict.py`입니다.

이 장의 큰 줄기는 *이벤트가 원본이고 상태는 파생*이라는 것인데, 여기서 자연스럽게 따라오는 질문이 하나 있습니다. **이벤트를 쌓아 두기만 하면 「지금 값」이 저절로 정해지나?** 아닙니다. 쌓인 이벤트 열을 하나의 상태로 접는 함수 — 리듀서(19장에서 나온 그 리듀서가 여기서 「이력 접기」로 돌아옵니다) — 가 있어야 하고, **그 리듀서를 무엇으로 고르느냐가 실제 동작을 정합니다.**

예제는 같은 이벤트 5건을 놓고 리듀서 4개를 돌려 봅니다.

```python
EVENTS = [
    ("2026-04-01T09:00", "hr-sync",    "선호", "채식", "추가", 0.95),
    ("2026-04-03T14:20", "agent-4821", "선호", "육식", "추가", 0.61),
    ("2026-04-03T14:21", "agent-4821", "선호", "채식", "삭제", 0.61),
    ("2026-04-09T10:05", "user",       "선호", "채식", "추가", 1.00),
    ("2026-04-22T16:40", "agent-5102", "선호", "비건", "추가", 0.78),
]
```

| 리듀서 | 결과 | 성격 |
|---|---|---|
| 마지막이 이긴다 (LWW) | 비건 | 제일 흔하고 제일 위험. 에이전트가 마지막에 쓰면 사람을 덮는다 |
| **확신도가 이긴다** | **채식** | 사람 발화(1.00)를 존중한다. *그럴듯한데* 문제가 있다 |
| 사람이 이긴다 | 채식 | 출처에 등급을 매긴다. 책이 기본으로 권하는 것 |
| 전부 모은다 | 비건 / 육식 / 채식 | 충돌을 숨기지 않는다. 대신 답이 여럿 |

「확신도가 이긴다」는 이 표에서 **답만 보면 정답**입니다. 사람이 말한 「채식」이 살아남았거든요. 그런데 이 장이 지적하는 건 결과가 아니라 **그 결과가 나온 이유가 조작 가능하다**는 점입니다.

## 2. 핵심 결함: 자기 보고 값을 승자 선정 기준으로 썼다

`highest_confidence` 리듀서를 뜯어보면 결정 로직은 이 한 줄입니다.

```python
if k not in best or conf > best[k][3]:
    best[k] = (v, at, who, conf)
```

승부는 `conf` 값 하나로 갈립니다. 그런데 `conf`는 **누가 채워 넣은 값인가요?**

- `hr-sync` 0.95 — 연동 시스템이 붙인 값
- `agent-4821` 0.61 — **에이전트가 자기 출력에 스스로 붙인 값**
- `user` 1.00 — 사람 발화라서 시스템이 상수로 박은 값
- `agent-5102` 0.78 — **역시 에이전트가 스스로 붙인 값**

즉 **경쟁자가 심판 점수판에 직접 숫자를 적는 구조**입니다. `agent-5102`가 0.78 대신 0.99를 적었다면 「비건」이 이깁니다. 그것도 버그 없이, 정상 경로로요. 리듀서는 「0.99가 1.00보다 작다」만 확인할 뿐 「0.99가 정당한 값인가」는 확인할 방법이 없습니다.

이 장은 이걸 20장에 연결합니다.

> «확신도가 이긴다»는 사람 발화(1.00)를 존중한다. 그럴듯하다.
> 그런데 확신도는 에이전트가 «스스로 매기는» 값이다.
> 20장에서 본 「모델이 스스로 올릴 수 있는 값은 지표로 못 쓴다」가 여기도 적용된다.

### 20장의 원래 맥락

20장(끝나지 않는 루프를 끝내는 법)에서는 **진전 척도(progress metric)** 를 고를 때 이 원칙이 나왔습니다.

> 진전 척도는 「모델이 스스로 올릴 수 있는 값」이면 안 됩니다. 길이도 확신도도 모델이 마음대로 올려요. 규칙으로 세는 값을 쓰세요.

거기서는 「루프를 언제 멈출까」를 정하는 값이었고, 여기서는 「누구 값을 채택할까」를 정하는 값입니다. **용도는 다른데 결함의 구조가 같습니다.** 판정 대상이 판정 기준을 쓴다는 것.

**시험에서 물어보는 것도 정확히 이 연결입니다.** "확신도가 낮게 나온다"거나 "사람보다 낮다"가 문제가 아니라, **그 값의 출처가 평가받는 쪽 자신**이라는 점이 문제입니다.

## 3. 왜 무너지나 — 굿하트의 법칙

이 결함이 *시간이 지나면서* 악화되는 이유는 굿하트의 법칙(Goodhart's law)으로 설명됩니다.

> **측정값이 목표가 되는 순간, 그것은 좋은 측정값이기를 그만둔다.**
> (When a measure becomes a target, it ceases to be a good measure.)

원래 확신도는 **관찰용 부가 정보**였습니다. 「이 추출이 얼마나 미덥나」를 사람이 참고하려고 붙여 둔 메타데이터요. 이 단계에서는 확신도가 실제 신뢰도와 어느 정도 상관을 가질 수 있습니다.

그런데 리듀서가 확신도를 **승자 선정 기준**으로 삼는 순간, 확신도는 관찰값에서 **최적화 대상**으로 바뀝니다. 그리고 최적화 압력이 걸린 지표는 원래 재려던 것과 분리됩니다.

압력이 걸리는 경로는 악의가 없어도 여럿입니다.

1. **프롬프트/모델 튜닝** — "확신도를 더 자신 있게 매겨라"는 지시 한 줄, 혹은 온도를 낮추는 것만으로도 분포가 통째로 밀립니다. 실제 정확도는 그대로인데요.
2. **에이전트 간 군비 경쟁** — `agent-4821`이 0.6대를 쓰고 `agent-5102`가 0.9대를 쓰면, 보수적으로 매기는 에이전트의 기여는 영영 채택되지 않습니다. 결국 팀은 「높게 부르는 에이전트」로 수렴합니다.
3. **버전/벤더 교체** — 모델을 바꿨을 뿐인데 확신도 눈금이 달라져서, 코드를 한 줄도 안 고쳤는데 그래프의 승패가 뒤집힙니다.
4. **자기 강화** — 에이전트가 자기가 심어 둔 고확신 사실을 다시 읽고 그걸 근거로 또 높은 확신도를 붙입니다. 28장의 「에이전트가 스스로 그래프를 넓히다」와 만나면 루프가 닫힙니다.

핵심은 **공격자를 상정할 필요가 없다**는 점입니다. 악의적 에이전트가 없어도, 그냥 각자가 자기 확신도를 올리는 것이 자기 기여를 살아남게 하는 유일한 방법이라는 사실만으로 지표가 부풀어 오릅니다.

## 4. LLM 확신도의 보정(calibration) 문제

굿하트 문제를 잠시 접어 두고 **아무도 지표를 게이밍하지 않는다고 가정해도**, 확신도는 여전히 순위 비교용으로 못 씁니다. LLM이 내놓는 확신도가 **잘 보정되어(well-calibrated) 있지 않기 때문**입니다.

**보정이란?** "확신도 0.8이라고 말한 예측 100개를 모으면 그중 약 80개가 맞는다"가 성립하는 상태입니다. 이게 성립해야 0.78과 0.95를 숫자로 비교하는 게 의미를 가집니다.

실제로는 이런 문제들이 겹칩니다.

- **과신(overconfidence)** — 언어화된 확신도는 대체로 실제 정확도보다 높은 쪽으로 쏠립니다. 특히 사람 선호도로 후처리(RLHF 계열)된 모델일수록 "확실합니다"라고 말하는 쪽을 학습합니다.
- **눈금이 없다** — 모델이 내놓는 0.78은 어떤 확률 모형의 출력이 아니라 **텍스트로 그럴듯한 숫자**입니다. 0.7과 0.8 사이에 실질적 구분이 있다는 보장이 없고, 0.95·0.9·0.85 같은 특정 값에 몰리는 편향도 흔합니다.
- **모델 간 비교 불가** — `agent-4821`의 0.61과 `agent-5102`의 0.78은 **애초에 같은 자 위의 값이 아닙니다.** 다른 모델, 다른 프롬프트, 다른 버전이면 눈금 자체가 다릅니다. 그런데 리듀서는 `conf > best[k][3]` 한 줄로 이 둘을 직접 비교합니다.
- **내용에 따라 흔들린다** — 표현을 살짝 바꾸거나 순서를 바꾸면 확신도가 출렁입니다. 모르는 것에 대해서도 자신 있게 숫자를 붙입니다(그래서 환각과 고확신이 같이 오기도 합니다).
- **비교의 방향이 애초에 다르다** — 확신도는 "내가 이 추출을 얼마나 확신하나"이지 "이 사실이 다른 출처보다 더 권위 있나"가 아닙니다. 리듀서는 후자를 물어야 하는데 전자의 값을 씁니다.

정리하면 확신도는 **개별 결과를 사람에게 보여 주는 힌트**로는 쓸 수 있어도, **서로 다른 출처의 주장을 줄 세워 승자를 뽑는 순서 관계**로는 쓸 수 없습니다. 30장의 예제가 「사람 1.00」만 상수로 박아 둔 것도 사실 이 사정을 우회하려는 임시 조치인데, 그러면 사람 값 하나를 빼고 나머지는 여전히 모델이 결정합니다.

## 5. 대안 — 시스템이 정하는 출처 등급

책이 기본으로 권하는 것은 세 번째 리듀서 「사람이 이긴다」입니다.

```python
def human_wins(evs):
    st = {}
    rank = {"user": 3, "hr-sync": 2}      # 시스템이 정한 등급표
    for at, who, k, v, op, conf in evs:
        r = rank.get(who, 1)              # 등급은 «행위자 신원»에서 나온다
        if op == "삭제":
            if k in st and st[k][3] <= r:
                st.pop(k)
            continue
        if k not in st or r >= st[k][3]:
            st[k] = (v, at, who, r)
    return {k: (v, at, who) for k, (v, at, who, _r) in st.items()}
```

> «사람이 이긴다»는 출처에 등급을 매긴다. 저는 이걸 기본으로 쓴다.
> 확신도와 달리 등급은 «시스템이» 정하는 값이라 에이전트가 못 올린다.

### 두 방식의 결정적 차이

| | 확신도가 이긴다 | 사람이 이긴다 (출처 등급) |
|---|---|---|
| 값의 출처 | **이벤트 페이로드** — 쓰는 쪽이 채워 넣음 | **시스템의 등급표** — 쓰는 쪽 바깥에 있음 |
| 근거 | 모델의 자기 보고 | 인증된 행위자 신원 |
| 에이전트가 올릴 수 있나 | 예 (숫자만 바꾸면 됨) | 아니오 (등급표를 못 건드림) |
| 눈금의 일관성 | 모델/버전마다 다름 | 조직이 한 번 정하면 고정 |
| 굿하트 압력 | 직접 걸림 | 지표를 못 만지니 압력이 안 걸림 |
| 감사 가능성 | "왜 0.78이었나" 재현 불가 | "등급 3이 등급 1을 이겼다" 규칙으로 설명됨 |

`highest_confidence`에서 `conf`는 이벤트에 실려 오는 값이고, `human_wins`에서 `rank`는 **리듀서 쪽에 있는 표**입니다. 이 위치 차이 하나가 전부입니다. 에이전트가 쓰는 이벤트의 어떤 필드를 조작해도 자기 `rank`를 못 올립니다. `who`를 위조하는 건 이제 확신도 부풀리기가 아니라 **신원 위조**이고, 그건 인증·권한 계층에서 막는 익숙한 문제로 바뀝니다.

이게 20장의 처방과 정확히 같습니다. *모델이 못 만지는, 규칙으로 세는 값을 쓰라.*

### 등급표를 설계할 때

실무에서는 등급을 이렇게 넓혀 씁니다.

- 사람의 명시적 발화 / 관리자 조작 — 최상위
- 인증된 시스템 연동(HR, ERP 등 기록 시스템) — 상위
- 검증 파이프라인을 통과한 에이전트 산출물 — 중간
- 미검증 에이전트 추출 — 하위

주의할 점 몇 가지.

- **등급은 도메인 결정입니다.** HR 시스템이 사람 발화를 이겨야 하는 도메인도 있습니다(법적 인사 기록). 코드가 아니라 정책으로 정하고 문서화하세요.
- **동률 처리를 명시하세요.** 예제는 `r >= st[k][3]`으로 같은 등급이면 나중 것이 이깁니다. 즉 **같은 등급 안에서는 LWW로 되돌아갑니다.** 의도한 것인지 확인해야 합니다.
- **확신도를 버리라는 뜻은 아닙니다.** 이벤트에 그대로 기록해 두세요. 다만 **승자를 정하는 데는 쓰지 말고**, 사람에게 보여 주는 힌트·검토 큐 정렬·모델 품질 모니터링에 쓰면 됩니다. 관찰용으로 남기는 한 굿하트 압력이 안 걸립니다.
- **확신도를 굳이 쓰겠다면 등급 안의 보조 기준으로만.** 1차 정렬은 출처 등급, 동률일 때만 확신도로 가르는 식이면 게이밍의 상한이 등급 안으로 제한됩니다.
- **「전부 모은다」도 선택지입니다.** 자동 승자를 정하는 것 자체가 위험한 도메인(의료·법률·분쟁 기록)에서는 충돌을 충돌인 채로 남기고 사람에게 올리는 게 맞습니다. 조회하는 쪽이 곤란해지는 값을 대신 치릅니다.

## 6. 한 문장으로

**확신도는 판정받는 쪽이 스스로 적는 값이라, 승자 선정 기준으로 삼는 순간 최적화 대상이 되어(굿하트) 무너지고, 애초에 모델 간 눈금이 맞지 않아(보정 실패) 비교 자체가 성립하지 않는다. 그래서 승부는 에이전트가 손댈 수 없는 값 — 시스템이 정하는 출처 등급 — 으로 갈라야 한다.**

## 함께 보면 좋은 것

- **20장** 끝나지 않는 루프를 끝내는 법 — 「모델이 스스로 올릴 수 있는 값은 지표로 못 쓴다」의 원 출처. 진전 척도 편.
- **19장** 상태 그래프와 리듀서 — 리듀서의 원 개념. 30장에서 「이력 접기」로 재등장.
- **28장** 에이전트가 스스로 그래프를 넓히다 — 자기 강화 루프가 닫히는 지점.
- **30.5절 / `ex5_audit_trail.py`** — 「누가 넣은 값인가」를 나중에도 믿으려면 해시 고리가 필요하다는 이야기. 출처 등급의 전제가 되는 행위자 기록을 지킵니다.
- **31장** 두 에이전트가 같은 노드를 동시에 고쳤다 — 30장은 이벤트가 순서대로 온다고 가정했는데, 그 가정이 깨질 때의 이야기.
