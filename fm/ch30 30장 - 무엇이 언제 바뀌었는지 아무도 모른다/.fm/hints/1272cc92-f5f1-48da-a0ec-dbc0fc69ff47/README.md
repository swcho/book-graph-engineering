# 실무에서 두 방식을 함께 둘 때 중요한 것은 방향이다

> **Q.** 실무에서 두 방식을 함께 둘 때 중요한 것은 무엇인가?
>
> **A.** 방향이다. 이벤트가 원본이고 엣지가 파생이어야 한다. 거꾸로 하면 둘이 갈라진다.

---

## 1. 여기서 말하는 「두 방식」이 뭔가

30.3절 「그때 그래프를 되살리는 두 가지 길」에 나오는 두 가지입니다. `ex3_temporal_query.py`가 이 둘을 나란히 놓고 같은 질문을 던져 봅니다.

| | 방법 A — 이벤트 재생 | 방법 B — 구간 엣지 쿼리 |
|---|---|---|
| 저장하는 것 | 변경 하나하나(추가/삭제, 시각, 행위자) | 엣지에 박힌 유효 구간 `vfrom`/`vto` (27장) |
| 「그때」를 만드는 법 | `t` 시점까지 이벤트를 접어서 상태를 만든다 | `vfrom <= t AND vto > t` 로 잘라 낸다 |
| 강한 질문 | **변화** — 무엇이 언제 왜 바뀌었나 | **상태** — 그 시점에 무엇이 참이었나 |
| 약한 질문 | 「지금 상태」를 물을 때마다 전부 재생해야 한다 | 「누가 바꿨나」를 못 묻는다. 엣지에 그 정보가 없다 |

예제에서 두 방법의 답은 **같습니다**. 2025-06-01 기준으로도, 2026-05-01 기준으로도 같은 엣지 집합이 나와요. 답이 같으니 「그럼 하나만 두면 되지 않나」 싶지만, 위 표의 마지막 두 줄 때문에 둘 다 필요합니다. 그래서 `ex3` 마지막 출력이 이렇게 말합니다.

```
그래서 실무에서는 둘 다 둔다.
  이벤트 로그 — 진실의 원본(source of truth)
  구간 엣지  — 이벤트에서 «만들어 낸» 조회용 뷰
```

## 2. 둘 다 두는 순간 생기는 진짜 문제

같은 사실이 두 곳에 있게 됩니다. 이벤트 로그에도 「이서연이 2026-04-01부터 결제팀을 이끈다」가 있고, 구간 엣지에도 같은 사실이 있어요. **같은 사실이 두 곳에 있으면 언제나 갈라질 수 있습니다.** 이건 29장에서 이미 한 번 얻어맞은 문제죠.

그래서 카드의 답이 「둘 다 둬라」가 아니라 **「방향」**입니다. 둘을 두는 건 확정이고, 남은 결정은 *어느 쪽이 원본이냐* 하나입니다.

```
올바른 방향                          뒤집힌 방향 (금지)

  쓰기                                  쓰기
   │                                     │
   ▼                                     ▼
[이벤트 로그]  ← 원본             [구간 엣지]  ← 여기다 먼저 쓰고
   │ 접기(리듀서)                        ┆
   ▼                                     ┆ 「나중에 로그도 남기자」
[구간 엣지]   ← 파생, 언제든 버리고      ▼
                다시 만들 수 있음   [이벤트 로그] ← 파생 아닌 «부록»
```

## 3. 방향이 뒤집히면 어떻게 갈라지는가 — 구체적 시나리오

### 시나리오 1: 놓친 한 줄

운영자 화면에서 「이서연을 정산팀 리더로」 버튼을 누릅니다. 코드는 이렇게 생겼습니다.

```python
# 뒤집힌 방향: 엣지를 먼저 고치고, 로그는 「그리고 남긴다」
def set_leader(c, who, team, at):
    c.execute("MATCH (a:N)-[e:R {kind:'이끔'}]->(b:N {name:$t}) "
              "SET e.vto = $at", {"t": team, "at": at})          # ① 상태 갱신
    c.execute("MATCH (a:N {name:$w}),(b:N {name:$t}) "
              "CREATE (a)-[:R {kind:'이끔', vfrom:$at, vto:'9999-12-31'}]->(b)",
              {"w": who, "t": team, "at": at})                    # ② 상태 갱신
    log_event(at, who, "이끔", team, "추가", actor=current_user()) # ③ 기록
```

여기서 ③은 **빠뜨려도 아무 일이 안 일어납니다.** 화면은 정상이고, 조회 쿼리도 정상이고, 테스트도 통과해요. 한 달 뒤 감사에서 「4월 14일 정산팀 리더 변경은 누가 했나」를 물으면 이벤트 로그에 그 항목이 없습니다. 엣지에는 있는데요. 30장 한 장 요약의 이 문장이 정확히 이 상황을 가리킵니다.

> 「로그를 잘 남기자」로는 안 됩니다. 로그는 빠뜨려도 아무 일이 안 생기거든요. 「기록도 남긴다」가 아니라 **「기록이 곧 쓰기다」**로 뒤집어야 합니다.

빠뜨리는 경로는 한둘이 아닙니다. 마이그레이션 스크립트, 데이터 정합성 배치, 급한 핫픽스로 돌린 `UPDATE` 한 방, 새로 들어온 팀원이 짠 두 번째 쓰기 경로. 원본이 아닌 것에 대고 쓰는 길이 열려 있는 한 이 구멍은 계속 생깁니다.

### 시나리오 2: 반쪽만 성공

③이 있어도 갈라집니다. ①②는 성공하고 ③에서 프로세스가 죽으면 엣지에는 반영됐는데 로그에는 없어요. 반대로 ①이 성공하고 ②에서 죽으면 「아무도 이끌지 않는 결제팀」이 남습니다. 두 저장소에 나눠 쓰는 한 원자성이 없습니다.

방향이 올바르면 이 문제가 사라집니다. 쓰기는 **이벤트 로그에 한 줄 추가하는 것 하나뿐**이니까요. 추가 전용 로그에 한 건 append 하는 건 단일 연산입니다. 성공했으면 원본에 있는 거고, 실패했으면 원본에 없는 거예요. 구간 엣지는 그 뒤에 만들어지고, 만들다 죽으면 그냥 다시 만들면 됩니다. 원본이 온전하니까요.

### 시나리오 3: 갈라진 걸 발견했을 때 답이 없음

이게 제일 아픕니다. 어느 날 이벤트 로그를 재생한 결과와 구간 엣지 테이블이 다르다는 걸 발견합니다.

```
재생 결과:   이서연 -이끔-> 결제팀
구간 엣지:   박민수 -이끔-> 결제팀   (vto = 9999-12-31)
```

**방향이 정해져 있으면**: 고민할 게 없습니다. 이벤트가 원본이니 엣지를 버리고 재생해서 다시 만듭니다. 5분이면 끝나요. 「어느 쪽이 맞나」라는 질문 자체가 성립하지 않습니다.

**방향이 뒤집혀 있으면**: 엣지에 직접 쓴 이력이 있으니 엣지에만 있는 진실이 존재할 수 있습니다. 그러면 재생으로 덮어쓰는 순간 그 진실이 날아갑니다. 그렇다고 엣지를 믿자니 로그에만 있는 변경도 있고요. 결국 **사람이 한 건 한 건 대조해서 판정**해야 합니다. 갈라진 개수가 수천 건이면 사실상 복구 불가고, 「일단 둘 다 남겨 두고 나중에 보자」로 끝나서 다시는 안 봅니다.

### 시나리오 4: 리듀서를 바꿀 수 없음

30.4절이 말하듯 「어떻게 접느냐가 답을 정합니다」. `ex4_reducer_conflict.py`에서 같은 이벤트 5건에 리듀서 넷을 적용하니 답이 넷 나왔죠. 운영하다 보면 「마지막이 이긴다」에서 「사람이 이긴다」로 정책을 바꿔야 할 때가 옵니다. 에이전트가 사람이 명시한 값을 덮는 사고가 나면요.

방향이 올바르면: 리듀서 함수를 바꾸고 엣지 테이블을 지우고 처음부터 재생합니다. **과거 데이터까지 새 정책으로 재해석**됩니다.

방향이 뒤집혀 있으면: 재생해서 만들 수 없으니 새 정책은 **앞으로 들어올 것에만** 적용됩니다. 과거는 옛 정책으로 굳은 채 남아요. 시간축을 따라 정책이 뒤섞인 데이터가 됩니다.

## 4. 29장의 「두 저장소가 갈라진다」와 어떻게 이어지는가

29장 `ex1_two_stores.py`는 이런 이야기였습니다.

- `[t0]` 워크플로가 지식 그래프에서 팀장(박민수)을 읽어 에이전트 상태에 담는다.
- `[t1]` 사람 승인 대기. 사흘 걸린다(23장).
- `[t2]` 그동안 다른 경로로 팀장이 이서연으로 바뀐다. 지식 그래프만 갱신된다.
- `[t3]` 승인이 나서 재개. 상태에 담긴 박민수에게 보고서를 보낸다.

> 두 저장소가 갈라졌다. 그리고 아무 에러도 안 났다.
> 둘 다 자기 일을 제대로 했는데 결과가 틀렸다.
> 같은 사실이 두 곳에 있는 한 언제나 갈라질 수 있다.

**같은 병입니다.** 지식 그래프 ↔ 에이전트 상태가, 여기서는 이벤트 로그 ↔ 구간 엣지로 이름만 바뀌었어요. 에러 없이 갈라지는 것도, 양쪽 다 자기 논리로는 옳은 것도 똑같습니다.

29장이 제시한 선택지는 셋이었습니다.

1. 상태에 담지 말고 매번 조회한다 → 느리고, 긴 워크플로는 중간에 값이 바뀐다
2. 상태에 담되 「읽은 시각」을 같이 담고 쓰기 전에 다시 확인한다 → 실무의 절충
3. 아예 한 저장소에 둔다 → 목표. 그리고 생각보다 어렵다

30장이 하는 일은 **3번을 실제로 성립시키는 방법**을 주는 것입니다. 물리적으로 저장소를 하나로 합치는 게 아니라, **원본을 하나로 정하고 나머지를 전부 파생으로 격하**시켜서요. 저장소는 여전히 둘이지만 *진실*은 하나입니다. `ex3` 마지막이 이 연결을 명시적으로 짚습니다.

```
29장에서 본 «두 저장소가 갈라진다» 문제가 여기서 또 나온다.
다만 여기서는 해법이 분명하다. 한쪽을 원본으로 정하고
다른 쪽은 «항상 다시 만들 수 있게» 두면 된다.
```

29장에서는 「생각보다 어렵다」로 끝났던 문제가, 30장에서 **방향을 정하는 것**으로 풀립니다. 차이는 하나예요. 29장의 두 저장소는 **대등**했습니다. 어느 쪽도 상대를 복원할 수 없었죠. 30장의 두 저장소는 **한쪽이 다른 쪽을 언제든 만들어 낼 수 있습니다.** 대등하지 않으면 갈라져도 복구할 수 있고, 애초에 쓰기 경로가 하나라 잘 갈라지지도 않습니다.

## 5. 「방향이 살아 있다」를 어떻게 확인하나

방향은 선언한다고 지켜지지 않습니다. 코드에 「이벤트가 원본입니다」라고 주석을 달아 놔도 6개월이면 우회 경로가 생겨요(29장의 「그림은 6개월이면 코드와 갈라진다」와 같은 성질). 검사 가능한 형태로 두어야 합니다.

- **뷰를 실제로 지우고 재생해 보세요.** 30장 한 장 요약이 「조회용 뷰는 언제든 다시 만들 수 있어야 하고, 되는지는 **실제로 지우고 재생해 봐야 안다**」고 못 박습니다. 정기적으로 돌리는 재생 테스트가 없으면 어느 순간 「엣지에만 있는 진실」이 생겨 있고, 그걸 발견하는 시점은 대개 복구가 필요한 그 순간입니다.
- **쓰기 경로를 하나로 좁히세요.** 엣지 테이블에 직접 쓸 수 있는 코드/권한이 있으면 언젠가 누군가 씁니다. 뷰 갱신은 리듀서 하나만 하도록 두세요.
- **이벤트에는 「바뀐 것」을 넣으세요.** 「바뀐 뒤 전체 상태」를 넣으면 무엇이 바뀌었는지 알 수 없고 동시 변경도 못 합칩니다. 그러면 로그가 형식만 원본이지 실제로는 스냅숏 더미가 됩니다.
- **재생이 현실적인 시간에 끝나야 합니다.** 재생에 두 시간 걸리면 아무도 안 돌리고, 안 돌리면 방향이 죽습니다. `ex2`가 보여 주듯 재생 시간은 데이터 양이 아니라 **스냅숏 주기**로 정해지니, 복구 목표 시간에서 거꾸로 계산해 주기를 잡으세요.
- **재생 결과와 뷰를 대조하는 검사를 붙이세요.** 29장 후반의 「완전히 합치기는 못 하고, 대신 갈라진 것을 감지한다」와 같은 태도입니다.

## 6. 한 줄로 다시

> 이벤트와 구간 엣지 중 무엇을 둘 것이냐는 이미 답이 나와 있습니다 — 둘 다 둡니다.
> 남은 결정은 **화살표가 어느 쪽을 향하느냐** 하나이고, 이게 뒤집히면 29장의 「두 저장소가 갈라진다」가 그대로 재현되면서 이번엔 복구할 원본조차 없습니다.

## 관련 개념

- `ex1_no_history.py` — 현재 상태만 두면 Q1(지금 뭐죠?)밖에 못 답한다. 이벤트가 왜 원본이어야 하는지의 출발점
- `ex2_replay_cost.py` — 파생을 「언제든 다시 만들 수 있게」 두려면 재생이 싸야 한다. 스냅숏/WAL
- `ex4_reducer_conflict.py` — 접는 방법(리듀서)이 답을 정한다. 원본이 살아 있어야 정책을 바꿔 재해석할 수 있다
- 27장 — 구간 엣지(`vfrom`/`vto`)
- 29장 — 두 저장소가 갈라진다. 이 카드가 푸는 문제의 원형
- 31장 — 이 장은 변경이 순서대로 온다고 가정했다. 두 에이전트가 동시에 고치면 순서가 없다
