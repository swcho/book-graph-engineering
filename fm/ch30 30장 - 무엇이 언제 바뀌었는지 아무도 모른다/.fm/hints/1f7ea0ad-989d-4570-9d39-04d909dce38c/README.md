# `ex3_temporal_query.py`가 비교하는 두 방법

> **질문** — `ex3_temporal_query.py`가 비교하는 두 방법은 무엇인가?
>
> **답** — 이벤트를 재생해 그때 상태를 만드는 방법(A)과 엣지에 유효 구간을 박아 두고 쿼리로 자르는 방법(B)이다.

## 한눈에

`ex3` 는 「그때 그래프를 어떻게 되살릴 것인가」라는 하나의 질문에 대한 서로 다른 두 구현을 나란히 놓고 답과 값을 비교합니다. 예제 파일의 첫 주석이 그대로 정답입니다.

```python
"""
예제 3 — 「그때 그래프」를 되살린다. 두 가지 방법.

방법 A — 이벤트를 재생해서 그때 상태를 만든다
방법 B — 엣지에 유효 구간을 박아 두고 쿼리로 자른다(27장)
둘은 답이 같고 값이 다르다.
"""
```

핵심 문장이 마지막 줄입니다. **둘은 답이 같고 값이 다릅니다.** 그래서 「어느 쪽이 맞나」가 아니라 「어느 쪽이 어떤 질문에 싸게 답하나」가 진짜 논점이 됩니다.

## 같은 사실, 두 자료구조

예제는 하나의 원천 데이터 `FACTS` 에서 출발합니다. 사람·팀 관계에 유효 구간(`vfrom`, `vto`)이 붙어 있는 형태예요.

```python
FACTS = [
    ("박민수", "이끔", "결제팀", "2024-01-01", "2026-03-31"),
    ("이서연", "이끔", "결제팀", "2026-04-01", "9999-12-31"),
    ("나",     "속함", "결제팀", "2023-06-01", "9999-12-31"),
    ("이서연", "속함", "결제팀", "2026-01-15", "2026-03-31"),
    ("김도현", "속함", "결제팀", "2025-02-01", "2026-06-30"),
]
```

그리고 같은 사실을 이벤트 열로 「펴는」 변환이 있습니다. 구간의 시작은 `추가`, 끝은 `삭제` 이벤트가 됩니다. 끝이 열려 있는(`9999-12-31`) 사실은 삭제 이벤트를 만들지 않아요.

```python
def to_events(facts):
    ev = []
    for s, k, o, vf, vt in facts:
        ev.append((vf, s, k, o, "추가"))
        if vt != "9999-12-31":
            ev.append((vt, s, k, o, "삭제"))
    return sorted(ev)
```

사실 5건 중 끝이 닫힌 것이 3건이므로 이벤트는 **5 + 3 = 8건**… 이 아니라, 장 본문이 「이벤트가 9개뿐이라 그렇다」고 말합니다. 여기서 중요한 건 정확한 개수가 아니라 *같은 정보가 두 모양으로 존재한다*는 점입니다. 하나는 구간이 박힌 엣지, 하나는 시간순 이벤트 열입니다.

`build()` 는 이 둘을 같은 Kuzu DB 안에 나란히 만듭니다. 릴레이션 테이블 `R` 은 구간을 속성으로 들고, 노드 테이블 `Ev` 는 이벤트를 한 줄씩 들어요.

```python
c.execute("CREATE REL TABLE R(FROM N TO N, kind STRING, "
          "vfrom STRING, vto STRING)")
c.execute("CREATE NODE TABLE Ev(id INT64, at STRING, subj STRING, "
          "kind STRING, obj STRING, op STRING, PRIMARY KEY(id))")
```

## 방법 B — 구간 쿼리 (`by_interval`)

엣지에 유효 구간이 박혀 있으니, 「시점 `t` 에 참이었던 것」은 **한 번의 WHERE 절**로 잘라 냅니다. 접기도, 순회도, 애플리케이션 코드도 없습니다.

```python
def by_interval(c, t):
    return sorted(rows(c.execute(
        "MATCH (a:N)-[e:R]->(b:N) WHERE e.vfrom <= $t AND e.vto > $t "
        "RETURN a.name, e.kind, b.name", {"t": t})))
```

- **자료구조** — 엣지 하나가 하나의 사실 + 유효 구간. 27장의 시간 축 엣지가 그대로 돌아온 것.
- **질의 방식** — 선언적 술어 `vfrom <= t AND vto > t`. 경계 처리에 주의하세요. 시작은 닫힌 구간(`<=`), 끝은 열린 구간(`>`) 입니다. 이래야 「끝난 날 = 다음 것이 시작한 날」일 때 두 사실이 겹쳐 잡히지 않습니다.
- **비용** — 엣지 수에 비례. 인덱스를 걸면 그보다 낫습니다. 이벤트가 아무리 쌓여도 조회 비용은 *현재 남아 있는 사실의 수*로 정해집니다.
- **강점** — 「그 시점에 무엇이 참이었나」, 즉 **상태**를 묻는 데 강합니다.
- **약점** — 「누가 바꿨나」를 못 묻습니다. 엣지에 그 정보가 없거든요. 장 본문 표현 그대로입니다.

## 방법 A — 이벤트 재생 (`by_replay`)

이벤트를 시점 `t` 까지 읽어 순서대로 적용합니다. `추가`면 집합에 넣고 `삭제`면 뺍니다. 상태는 저장된 것이 아니라 **계산해 낸 것**입니다.

```python
def by_replay(c, t):
    st = set()
    for at, s, k, o, op in rows(c.execute(
            "MATCH (e:Ev) WHERE e.at <= $t RETURN e.at, e.subj, e.kind, "
            "e.obj, e.op ORDER BY e.id", {"t": t})):
        if op == "추가":
            st.add((s, k, o))
        else:
            st.discard((s, k, o))
    return sorted(st)
```

- **자료구조** — 추가 전용 이벤트 로그. 각 줄은 「언제 무엇이 어떻게 바뀌었는가」.
- **질의 방식** — `at <= t` 로 자른 뒤 `ORDER BY e.id` 로 **순서를 지켜** 접습니다. 정렬이 빠지면 삭제가 추가보다 먼저 적용되어 답이 틀어집니다. 접는 로직은 DB가 아니라 애플리케이션 쪽에 있어요.
- **비용** — 시점 `t` 이전의 이벤트 수에 비례. 시간이 갈수록 무거워지고, 조회할 때마다 다시 접어야 합니다. 그래서 `ex2` 의 스냅숏이 필요해집니다.
- **강점** — 「무엇이 언제 왜 바뀌었나」, 즉 **변화**를 묻는 데 강합니다. `ex1` 의 Q3·Q4(누가 넣고 누가 지웠나, 에이전트가 넣은 것 중 되돌려진 비율)는 이쪽에서만 답이 나옵니다.
- **약점** — 「지금 상태」를 물을 때마다 전부 재생해야 합니다.

## 나란히 놓기

| | 방법 A — 이벤트 재생 | 방법 B — 구간 쿼리 |
|---|---|---|
| 저장 형태 | `Ev` 노드(추가 전용 로그) | `R` 엣지 + `vfrom`/`vto` |
| 그때 상태 구하기 | `at <= t` 를 `id` 순으로 접는다 | `vfrom <= t AND vto > t` 로 자른다 |
| 접는 로직 위치 | 애플리케이션 | 쿼리 술어 |
| 비용의 축 | `t` 이전 이벤트 수(누적) | 엣지 수(현재 사실 수) |
| 잘하는 질문 | 변화 — 무엇이 언제 왜 | 상태 — 그때 무엇이 참 |
| 못 하는 것 | 매번 재생해야 함 | 「누가 바꿨나」를 못 물음 |
| 완화책 | 스냅숏(`ex2`) | 로그에서 다시 만들기 |

## 예제가 실제로 보여 주는 것

`main()` 은 두 시점에서 두 방법의 결과를 비교하고, 이어서 300회 반복 평균 시간을 잽니다.

```python
for t in ("2025-06-01", "2026-05-01"):
    a = by_interval(c, t)
    b = by_replay(c, t)
    ...
    print(f"  구간 쿼리 {len(a)}건, 이벤트 재생 {len(b)}건, "
          f"{'같다' if a == b else '다르다'}")
```

여기서 확인되는 첫 번째 사실은 **답이 같다**는 것입니다. 같은 사실을 두 모양으로 저장했으니 당연한데, 당연한 것을 코드로 확인해 두는 게 예제의 목적이에요.

두 번째로 시간을 잽니다.

```python
N = 300
t0 = time.perf_counter()
for _ in range(N):
    by_interval(c, "2026-05-01")
iv = (time.perf_counter() - t0) / N * 1000
```

이 규모에서는 재생이 오히려 조금 빠르게 나옵니다. **그리고 예제는 곧바로 그 숫자를 믿지 말라고 못을 박습니다.**

> 「이벤트가 9개뿐이라 그렇다. 이벤트가 10만 개면 뒤집힌다. 그러니 이 숫자로 «재생이 빠르다»고 결론 내면 안 된다.」

장 앞부분의 실행 가이드에도 같은 경고가 반복됩니다. 「`ex3` 의 조회 시간 비교는 이벤트 9개짜리 장난감 규모입니다.」 벤치마크의 규모를 밝히고 결론을 스스로 제한하는 태도까지가 이 예제의 내용입니다.

## 그래서 결론은 「둘 다」

예제가 도달하는 곳은 「A가 낫다」도 「B가 낫다」도 아닙니다.

```
이벤트 로그 — 진실의 원본(source of truth)
구간 엣지  — 이벤트에서 «만들어 낸» 조회용 뷰
```

중요한 건 **방향**입니다. 이벤트가 원본이고 엣지가 파생입니다. 거꾸로 하면, 즉 엣지를 먼저 고치고 이벤트를 나중에 적으면 둘이 갈라집니다. 29장에서 본 「두 저장소가 갈라진다」 문제가 여기서 다시 나오는데, 여기서는 해법이 분명해요. 한쪽을 원본으로 정하고 다른 쪽은 **항상 다시 만들 수 있게** 두면 됩니다.

이건 30장 전체의 주장(「이벤트가 원본이고 상태는 파생이다」)이 코드 한 편으로 압축된 형태이기도 합니다. 그리고 「되는지는 실제로 지우고 재생해 봐야 안다」는 말이 바로 `by_replay` 가 하는 일입니다.

## 헷갈리기 쉬운 지점

- **「두 방법」을 「덮어쓰기 vs 이벤트」로 착각하기** — 그건 `ex1_no_history.py` 의 비교입니다. `ex3` 는 이력을 남기는 것을 이미 전제하고, *이력을 어떤 모양으로 두고 어떻게 되살릴지*를 비교합니다.
- **「두 방법」을 「처음부터 재생 vs 스냅숏 이후 재생」으로 착각하기** — 그건 `ex2_replay_cost.py` 입니다. 그쪽은 A 내부의 최적화 얘기예요.
- **「두 방법」을 리듀서 비교로 착각하기** — 리듀서 네 개를 견주는 건 `ex4_reducer_conflict.py` 입니다.
- **B에 감사 정보가 있다고 착각하기** — `R` 엣지에는 `kind`, `vfrom`, `vto` 뿐입니다. `actor` 가 없어요. 그래서 「누가 바꿨나」는 구조적으로 답이 안 나옵니다.

## 한 줄로

`ex3_temporal_query.py` 는 **이벤트를 재생해 그때 상태를 만드는 방법(A)** 과 **엣지에 유효 구간을 박아 두고 쿼리로 잘라 내는 방법(B)** 을 비교하며, 답은 같고 값이 다르다는 것, 그리고 실무에서는 이벤트를 원본으로 두고 구간 엣지를 파생 뷰로 두어 **둘 다** 쓴다는 것을 보여 줍니다.
