# 이벤트 소싱 = WAL + 체크포인트

> **Q.** 이벤트 소싱 구조가 데이터베이스의 무엇과 같은가?
> **A.** 쓰기 전 로그(WAL)와 체크포인트다. 30년 된 구조를 그대로 쓰는 것이다.

---

## 1. 이 문장이 나온 자리

30장 `ex2_replay_cost.py`의 마지막 출력입니다. 예제는 이벤트를 1만 → 100만 개까지 늘려 가며
**처음부터 전부 재생**하는 시간과 **마지막 스냅숏 이후만 재생**하는 시간을 비교합니다.

```
스냅숏을 50,000 이벤트마다 찍는다고 하자.

     이벤트 수   처음부터(ms)  스냅숏 이후(ms)   재생할 이벤트     배수
--------------------------------------------------------------------
       10,000          3.9            4.9         10,000     0.8x
    1,034,000        395.0           16.0         34,000    24.7x
```

여기서 나오는 결론이 두 개입니다.

1. **재생 시간은 데이터 양이 아니라 스냅숏 주기가 정한다.** 이벤트가 100만 개든 1000만 개든
   재생할 것은 최대 5만 개(= 스냅숏 주기)입니다. 즉 복구 시간에 **상한**이 걸립니다.
2. 그러니까 주기는 **복구 목표 시간(RTO)에서 거꾸로 계산**합니다. 「3초 안에 복구」가 목표면
   3초에 재생 가능한 이벤트 수를 재고 그만큼을 주기로 잡습니다.

그리고 예제는 이렇게 끝납니다.

> "그리고 이건 데이터베이스가 하는 일과 같다.
> 쓰기 전 로그(WAL)와 체크포인트. 30년 된 구조를 그대로 쓰는 것이다."

**핵심은 「비슷하다」가 아니라 「같은 구조다」입니다.** 이벤트 소싱은 애플리케이션 계층에서
새로 발명한 패턴이 아니라, DB 엔진이 1990년대부터 내부에서 쓰던 복구 구조를 도메인 레벨로
끌어올린 것입니다.

---

## 2. WAL과 체크포인트가 원래 뭐였나

### 쓰기 전 로그 (Write-Ahead Log)

규칙은 한 줄입니다. **데이터 페이지를 디스크에 쓰기 전에, 그 변경을 기술한 로그 레코드를
먼저 내구화한다.** (write-ahead rule)

- 로그는 **추가 전용(append-only)** 이고 **순차 쓰기**라 빠릅니다.
- 커밋 시점에 랜덤 위치의 데이터 페이지 여러 개를 fsync 할 필요가 없습니다.
  로그 꼬리 하나만 fsync 하면 커밋이 성립합니다.
- 크래시가 나면 로그를 **재생(redo)** 해서 잃어버린 페이지 변경을 되살립니다.
- 결과적으로 **로그가 진실의 원본이고, 데이터 파일은 로그로부터 만들어 낼 수 있는 파생물**입니다.

이 구조를 정리한 정본이 ARIES(Mohan et al., 1992, *ACM TODS*)입니다. LSN(로그 순번),
redo/undo, 퍼지 체크포인트, 리페어 3단계(analysis → redo → undo)가 여기서 나옵니다.
`ex2`가 말하는 "30년 된 구조"의 그 30년입니다.

### 체크포인트 (Checkpoint)

로그만 있으면 재생 시간이 **로그 길이에 비례**해서 무한정 늘어납니다. 서버가 1년 굴러가면
1년치를 재생해야 하죠. 그래서 주기적으로 **지금까지의 결과를 물질화**해 둡니다.

- 더티 페이지를 디스크에 밀어 넣고, "이 지점(redo point) 이전 로그는 재생 안 해도 된다"고
  표시합니다.
- 복구는 **마지막 체크포인트 이후 로그만** 재생하면 됩니다.
- 이걸로 로그를 잘라 낼(truncate/recycle) 수 있어 저장 공간도 회수됩니다.

PostgreSQL에서 실제 손잡이:

| 설정 | 의미 |
|---|---|
| `checkpoint_timeout` (기본 5min) | 시간 기준 체크포인트 주기 |
| `max_wal_size` (기본 1GB) | WAL이 이만큼 쌓이면 체크포인트 유발 |
| `checkpoint_completion_target` | 체크포인트 I/O를 얼마나 늘려 펴서 칠지 |

`checkpoint_timeout`을 늘리면 → 평시 I/O는 줄고 복구는 느려집니다. 줄이면 반대고요.
**`ex2`가 말한 「짧게 잡으면 재생은 빠른데 공간이 늘고, 길게 잡으면 공간은 아끼는데 복구가 느려진다」와 정확히 같은 교환입니다.**

SQLite는 `PRAGMA wal_autocheckpoint`(기본 1000 페이지)로 같은 손잡이를 노출합니다.

## 3. 1:1 대응표 — 이벤트 소싱 ↔ WAL 세계

이게 이 카드의 핵심입니다. **용어만 다르고 부품이 그대로 겹칩니다.**

| # | 이벤트 소싱 (30장) | WAL / DB 엔진 | 하는 일 |
|---|---|---|---|
| 1 | 이벤트 로그 (append-only) | WAL / 트랜잭션 로그 (`pg_wal`, redo log) | 진실의 원본. 추가만 하고 고치지 않음 |
| 2 | 이벤트 하나 | 로그 레코드 (log record) | 원자적 변경 1건 |
| 3 | 이벤트 순번 / `Ev.id` | LSN (Log Sequence Number) | 전순서 부여, 「어디까지 반영됐나」 표시 |
| 4 | 재생(replay) | 리두(redo) / 복구(recovery) | 로그를 접어서 상태를 다시 만듦 |
| 5 | 스냅숏 | 체크포인트 / 데이터 파일 상태 | 「여기까진 접어 놨다」는 물질화된 중간 결과 |
| 6 | 스냅숏 주기(`SNAPSHOT_EVERY=50_000`) | `checkpoint_timeout` / `max_wal_size` | 복구 시간의 **상한**을 정하는 손잡이 |
| 7 | 복구 목표 시간에서 역산 | 체크포인트 튜닝(복구 시간 vs 평시 I/O) | 같은 교환, 같은 계산 |
| 8 | 조회용 뷰 / 구간 엣지 (CQRS 읽기 모델) | 힙 테이블·인덱스·머티리얼라이즈드 뷰 | 로그에서 **파생된** 읽기 최적화 구조 |
| 9 | 뷰를 지우고 다시 만들 수 있어야 함 | 인덱스 REINDEX / 데이터 파일 재구축 | 파생물은 언제든 재생성 가능해야 함 |
| 10 | 리듀서(어떻게 접을 것인가) | 로그 레코드 적용 함수 (apply/redo 루틴) | 로그 + 리듀서 = 상태. 로그만으론 아무것도 안 정해짐 |
| 11 | 「바뀐 것」을 담은 이벤트 (델타) | 논리적/물리논리적 로깅 (delta record) | 무엇이 바뀌었는지 알 수 있고 병합 가능 |
| 12 | 「바뀐 뒤 전체 상태」를 담은 이벤트 | 물리적 로깅 / full-page write | 크지만 단순. 무엇이 바뀌었는지는 사라짐 |
| 13 | 되돌리기 / 보정 이벤트 | 언두(undo) / 보상 로그 레코드(CLR) | 되돌림도 새 기록으로 남김 |
| 14 | 해시 고리(`ex5`) | — (WAL에는 없음. CRC 체크섬까지만) | **부패 탐지가 아니라 위변조 탐지.** WAL을 넘어서는 부분 |
| 15 | 이벤트 보관 기간 / 개인정보 | WAL 아카이빙 & 로그 리텐션 | 무한 보관은 비용이고, 여기선 규제 문제이기도 함 |

### 특히 눈여겨볼 대응

- **3번(LSN)**: `ex1`, `ex3`의 `ORDER BY e.id`가 바로 LSN 순 재생입니다. 순서 없이 접으면
  결과가 달라지므로, 전순서는 선택이 아니라 전제입니다. (그리고 이 전제가 31장에서 깨집니다.)
- **5·6번**: 카드가 묻는 바로 그 지점. 스냅숏은 성능 최적화지 원본이 아닙니다.
  DB에서 데이터 파일을 날려도 WAL이 있으면 복구되듯, 스냅숏을 다 지워도 이벤트가 있으면 복구됩니다.
- **10번**: WAL의 apply 루틴은 DB 엔진이 정해 놓은 한 가지지만, 이벤트 소싱의 리듀서는
  **도메인이 고르는 값**입니다(`ex4`의 마지막이 이긴다 / 확신도가 이긴다 / 사람이 이긴다 / 전부 모은다).
  **여기가 이벤트 소싱이 WAL보다 「위」에 있는 이유**입니다. 같은 로그에서 정책에 따라 다른 상태를 뽑습니다.
- **14번**: WAL은 *디스크가 배신하는 것*(비트 부패, 찢어진 페이지)을 막으려고 CRC를 씁니다.
  이벤트 소싱을 감사 로그로 쓰려면 *사람이 배신하는 것*을 드러내야 해서 해시 고리(RFC 6962 계열)가 붙습니다.
  DB 관리자는 UPDATE 권한이 있고, 그런 사람은 대개 여럿이니까요.

## 4. 방향이 같다는 게 진짜 요점

두 세계 모두 **원본과 파생의 방향이 한쪽으로 고정**돼 있습니다.

```
[WAL]           로그(원본) ──재생──> 데이터 파일 / 인덱스(파생)
[이벤트 소싱]   이벤트(원본) ──재생──> 그래프 / 구간 엣지 / 조회 뷰(파생)
```

`ex3`의 결론이 정확히 이겁니다.

> "중요한 건 방향이다. 이벤트가 원본이고 엣지가 파생이다.
> 거꾸로 하면(엣지를 고치고 이벤트를 나중에 적으면) 둘이 갈라진다."

DB에서 데이터 파일을 직접 손으로 고치고 WAL에 나중에 적는다면 그 DB는 즉시 망가집니다.
같은 이유로, 그래프를 먼저 고치고 이벤트를 나중에 남기면 **로그는 감사 로그가 아니라 그냥 로그**가 됩니다.
30장 요약의 이 문장이 그 뜻입니다.

> "「기록도 남긴다」가 아니라 **「기록이 곧 쓰기다」**로 뒤집어야 합니다."

WAL의 write-ahead rule과 문자 그대로 같은 명제입니다. 로그를 빠뜨리면 커밋 자체가 성립하지 않아야 합니다.

## 5. 같은 구조를 쓰는 다른 시스템들

「30년 된 구조를 그대로 쓴다」가 과장이 아님을 보여주는 사례들입니다.

| 시스템 | 로그 | 스냅숏/체크포인트 |
|---|---|---|
| PostgreSQL | `pg_wal` 세그먼트 | CHECKPOINT (`checkpoint_timeout`, `max_wal_size`) |
| SQLite (WAL 모드) | `-wal` 파일 | `PRAGMA wal_autocheckpoint` (기본 1000 페이지) |
| Redis | AOF (append-only file) | RDB 스냅숏 + `BGREWRITEAOF` |
| Kafka | 파티션 로그(불변, offset) | log compaction — 키별 최신 값만 남기는 「접힌」 상태 |
| Raft / etcd | 복제 로그 | 스냅숏 후 로그 앞부분 절단 |
| LSM 트리 (RocksDB 등) | memtable용 WAL | SSTable flush + compaction |
| 이벤트 소싱 (30장) | 이벤트 스토어 | 어그리게이트 스냅숏 |

Kafka의 log compaction은 특히 재미있습니다. **「접는 것(리듀스)을 저장소가 대신 해 주는」**
형태거든요. 키별 최신 값만 남기니 리듀서가 `last write wins`로 고정됩니다.
`ex4`가 경고한 그 리듀서죠. 그래서 「사람이 에이전트에게 덮이면 안 된다」 같은 요구가 있으면
compaction에 상태 관리를 맡기면 안 되고, 로그는 그대로 두고 접기를 애플리케이션이 해야 합니다.

## 6. 다르게 대답하면 왜 틀리나 (오답 노트)

- **「블록체인과 같다」** — 추가 전용·해시 고리는 겹치지만, 이벤트 소싱은 합의(consensus)도
  비잔틴 내성도 없습니다. 30장이 짚는 대응은 **분산 원장이 아니라 단일 노드 복구 구조**입니다.
  해시 고리(`ex5`)조차 "막지 않고 표가 나게 할 뿐"이라고 명시합니다.
- **「그냥 감사 로그와 같다」** — 감사 로그는 보통 *부산물*입니다. 빠뜨려도 시스템이 굴러갑니다.
  WAL과 이벤트 로그는 빠뜨리면 **쓰기 자체가 성립하지 않습니다**. 이 차이가 30장 전체의 축입니다.
- **「백업과 같다」** — 백업은 특정 시점의 복사본이고, 그 사이 변경은 사라집니다.
  WAL/이벤트는 **모든 중간 변경**을 갖고 있어 임의 시점으로 되감을 수 있습니다(PITR = `ex1`의 Q2).
- **스냅숏만 답하고 WAL을 빼먹기** — 스냅숏만 있으면 그건 그냥 주기적 백업입니다.
  **로그 + 체크포인트 두 개가 짝**이어야 이 구조가 됩니다.

---

## 7. 한 줄 정리

**이벤트 소싱 = WAL(추가 전용 로그) + 체크포인트(스냅숏)를 도메인 레벨로 올린 것.**
DB가 페이지를 복구하려고 쓰던 구조를, 그래프와 비즈니스 사실에 그대로 적용한 것뿐입니다.
새 발명이 아니라 **검증된 30년짜리 구조의 재사용**이고, 그래서 튜닝 감각(스냅숏 주기 ↔
복구 시간 ↔ 저장 공간)도 그대로 가져다 쓸 수 있습니다.
차이는 딱 둘 — **리듀서를 도메인이 고른다는 것**, 그리고 **위변조 탐지(해시 고리)가 추가로 필요하다는 것**입니다.
