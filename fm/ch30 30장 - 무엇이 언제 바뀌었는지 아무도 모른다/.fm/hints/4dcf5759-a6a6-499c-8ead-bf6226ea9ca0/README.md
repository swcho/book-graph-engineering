# 해시 고리는 막지 않는다 — 표가 나게 할 뿐이다

## 질문

해시 고리(hash chain)의 한계와 그 보완책은 무엇인가?

## 답

- **한계**: 해시 고리는 위변조를 *막지* 않는다. *표가 나게* 할 뿐이다(tamper-**evident**이지 tamper-**proof**가 아니다). 로그 전체에 쓰기 권한을 가진 내부자가 고친 지점부터 끝까지 해시를 **전부 다시 계산**하면, 검증을 통과하는 **일관된 위조본**을 만들 수 있다.
- **보완책**: 해시를 **밖으로 내보낸다**. 즉 최신 해시(체인 헤드)를 **다른 시스템에 적어 두거나**, **매일 한 번 어딘가에 공개**한다. 그러면 위조자는 자기 DB뿐 아니라 *내가 통제하지 못하는 사본*까지 고쳐야 하므로 재계산 공격이 막힌다.

## 왜 재계산이 통하는가 (`ex5_audit_trail.py`)

30장 예제 5의 고리 구조는 이렇다.

```
hash[n] = sha256( [seq, at, actor, op, payload, hash[n-1]] )
```

검증 루프는 두 가지만 본다.

| 공격 | 무엇이 깨지나 | 검증 결과 |
|---|---|---|
| 4번 항목의 payload를 몰래 수정 | `hash[4] != digest(...)` | `내용이 바뀜` |
| 3번 항목을 통째로 삭제 | `hash[4].prev != hash[2]` | `앞 고리가 안 맞음` |
| **4번을 고치고 4~N을 전부 재계산** | **아무것도 안 깨진다** | **이상 없음** |

세 번째 줄이 핵심이다. 고리는 **각 항목이 앞 항목과 정합한지**만 검증한다. 체인 전체가 정합하면 통과다. 그런데 체인 전체를 다시 계산하는 데 필요한 건 `hashlib` 한 줄과 로그 테이블 UPDATE 권한뿐이다. 비밀키도, 서명도 필요 없다.

그리고 본문이 지적하듯 **그런 권한을 가진 사람은 대개 여럿이다**. DBA, 백엔드 운영자, 배포 파이프라인의 서비스 계정. 감사 로그가 방어해야 할 상대가 바로 그 사람들인데, 고리만으로는 그들을 못 막는다.

### 무엇이 부족한가를 한 줄로

> 해시 고리는 **내부 정합성**만 증명한다. 「이 로그가 *지금* 자기 자신과 앞뒤가 맞는다」는 말이지, 「이 로그가 *그때* 기록된 그 로그다」는 말이 아니다.

「그때 그 로그였다」를 말하려면 **과거 시점에 그 해시를 봤다는 외부 증인**이 필요하다. 보완책은 전부 이 증인을 어떻게 구하느냐의 문제다.

## 실제 보완 기법과 값

아래로 갈수록 방어력이 세지고, 값(비용·운영 부담·지연)도 같이 뛴다.

### 1. 앵커링 (anchoring) — 해시를 밖에 적어 둔다

체인 헤드(가장 최근 해시, 또는 머클 트리 루트)를 **쓰기 주체가 다른 저장소**에 주기적으로 복사한다.

| 어디에 앵커하나 | 방어력 | 값 |
|---|---|---|
| 다른 팀이 운영하는 DB / 다른 클라우드 계정 | 두 시스템의 권한자가 **공모**해야 위조 가능 | 거의 공짜. 앵커 잡(cron) 하나 |
| WORM 스토리지 (S3 Object Lock, Azure immutable blob) | 보존 기간 동안 **root 권한자도** 못 지움 | 스토리지 비용 소폭 + Compliance 모드는 되돌릴 수 없어 운영 실수가 치명적 |
| 사내 위키 / 슬랙 채널 / 사보에 매일 게시 | 사람 여럿이 본 값 = 사회적 증인 | 공짜지만 **아무도 검증 안 하면 무의미** |
| 공개 블록체인 (Bitcoin OP_RETURN, OpenTimestamps) | 위조하려면 체인을 재조직해야 함 | 트랜잭션 수수료 + 확정까지 수십 분~수 시간 지연 |

**핵심 설계 요령**: 앵커를 **머클 트리 루트**로 잡으면 이벤트 수가 백만이든 천만이든 앵커 한 건이면 된다(OpenTimestamps가 쓰는 방식). 이벤트마다 앵커하면 값이 이벤트 수에 비례해 터진다. 30장 예제 2에서 「재생 시간은 데이터 양이 아니라 스냅숏 주기로 정해진다」고 한 것과 같은 구조다. **앵커 방어력의 해상도도 데이터 양이 아니라 앵커 주기로 정해진다.** 하루에 한 번 앵커하면, 마지막 앵커 이후 24시간 분량은 여전히 재계산 위조가 가능하다.

즉 **앵커 주기 = 위조 가능 구간의 크기**다. 복구 목표 시간(RTO)에서 스냅숏 주기를 거꾸로 계산하듯, **허용 가능한 위조 창(window)에서 앵커 주기를 거꾸로 계산**한다.

### 2. RFC 3161 타임스탬프 — 「언제」에 제3자 서명을 받는다

[RFC 3161](https://datatracker.ietf.org/doc/html/rfc3161)의 Time-Stamp Protocol(TSP). 해시를 TSA(Time-Stamping Authority)에 보내면, TSA가 `해시 + 시각`에 자기 개인키로 서명한 **타임스탬프 토큰(TST)**을 돌려준다.

- 무엇을 더 주나: 앵커링은 「이 값이 어딘가에 있다」만 말하지만, TST는 「**이 해시가 이 시각 이전에 존재했다**」를 **암호학적으로 서명된 형태**로 말한다. 그리고 서명 주체가 감사받는 제3자다.
- **법적 지위**: eIDAS의 qualified timestamp, 각국 전자문서법 등에서 증거로 인정되는 경로가 이미 있다. 이게 블록체인 앵커링 대비 실무상 가장 큰 이점이다.
- **값**:
  - 신뢰가 **TSA 한 곳으로 집중**된다. TSA의 키가 털리면 소급 위조가 가능하다(단일 신뢰점).
  - 상용 TSA는 대개 **건당 과금**이다. 이벤트마다 찍으면 감당이 안 되니, 여기서도 **머클 루트만 찍는** 배치 구조가 사실상 필수다.
  - TSA 인증서가 만료·폐기되면 오래된 토큰의 검증이 곤란해진다 → 만료 전에 **재타임스탬프(re-timestamping)**로 갱신해야 한다(장기 보존 서명, LTV). 이 갱신 운영이 은근히 무겁다.
  - 네트워크 왕복 지연이 쓰기 경로에 들어오면 안 되므로, 비동기 배치로 빼야 한다.

### 3. 트랜스퍼런시 로그 + witness / gossip — 「모두가 같은 로그를 본다」

Certificate Transparency([RFC 6962](https://datatracker.ietf.org/doc/html/rfc6962), 현재는 [RFC 9162](https://datatracker.ietf.org/doc/html/rfc9162)로 갱신)가 푼 문제가 정확히 이 장의 문제다. 30장 키워드 표가 해시 고리의 출처로 RFC 6962를 가리키는 이유다.

CT의 구조:

- 로그는 **추가 전용 머클 트리**이고, 주기적으로 **STH(Signed Tree Head)**에 서명해서 공개한다.
- **포함 증명(inclusion proof)**: 「내 인증서가 이 트리에 들어 있다」를 `log₂(n)` 개 해시로 증명. 로그 전체를 받을 필요가 없다.
- **일관성 증명(consistency proof)**: 「새 STH는 예전 STH의 **추가 전용 확장**이다」를 증명. 과거 항목을 하나라도 고치면 이 증명이 실패한다.

그런데 여기에 **남는 구멍**이 있다. 로그가 **A에게는 STH₁, B에게는 STH₂**를 보여 주는 **split view(분기 뷰)** 공격이다. 각 관찰자 입장에서는 모든 증명이 완벽하게 통과한다. 해시 고리의 「전부 재계산하면 일관된 위조본」이 분산 버전으로 되돌아온 것이다.

이걸 닫는 게 **gossip**과 **witness**다.

| 기법 | 하는 일 | 값 |
|---|---|---|
| **gossip** ([draft-ietf-trans-gossip](https://datatracker.ietf.org/doc/html/draft-ietf-trans-gossip-05)) | 클라이언트들이 서로 본 STH를 교환한다. 세 방식 — SCT Feedback, STH Pollination, Trusted Auditor Relationship | **프라이버시 문제**가 크다. 「내가 이 STH를 봤다」는 곧 「내가 이 사이트를 방문했다」에 가깝다. 그리고 표준화가 오래 걸렸고 **실배포가 사실상 거의 없다** |
| **witness / cosigning** (Sigsum, Go checksum DB, 근래 CT 설계) | 독립 운영되는 witness 여러 곳이 STH에 **덧서명(co-sign)**한다. 검증자는 「N개 witness가 서명한 STH」만 받아들인다 | 훨씬 실용적이다. 클라이언트끼리 잡담할 필요 없이 **witness 다수와 공모**해야 split view가 성립. 대신 **witness 인프라를 실제로 운영**해야 하고 서명 정족수·키 관리가 붙는다 |

gossip이 실무에서 잘 안 된 대신 **witness 정족수** 쪽으로 업계가 수렴한 것은 기억해 둘 만하다. 「모두가 서로 확인」보다 「독립적인 소수가 덧서명」이 운영 가능한 형태였다.

### 4. 그 밖의 보조 수단

| 기법 | 하는 일 | 한계 |
|---|---|---|
| **HMAC 체인 / 서명 체인** | 로그 항목에 쓰기 노드만 아는 키로 서명. DB 권한만으로는 재계산 불가 | 키를 쥔 서비스가 털리면 끝. HSM/KMS로 키를 격리해야 실효 |
| **전방 안전 로깅**(forward-secure sealing, systemd-journald FSS) | 키를 주기적으로 **일방향 진화**시켜 옛 키를 지운다. 침해 **이전** 기록은 소급 위조 불가 | 침해 **이후** 기록은 여전히 위조 가능. 검증키를 오프라인에 따로 보관해야 함 |
| **쓰기 전용 파이프라인 분리** | 앱은 append만 가능, UPDATE/DELETE 권한을 아예 회수 | 최고 권한자(DBA·클라우드 관리자)는 여전히 우회 가능 |
| **WORM / 불변 스토리지** | S3 Object Lock 등으로 보존 기간 강제 | 잘못 넣은 데이터도 못 지운다 → 30장 마지막 경고(**이벤트에 개인정보를 직접 넣지 마라**)와 정면으로 충돌 |

## 그래서 어디까지 해야 하나

본문의 결론이 실무 판단 기준 그대로다.

> 대부분의 사내 시스템에서는 **「표가 나는 것」만으로 충분하다**. 내부자가 작정하고 위조하는 것까지 막으려면 값이 확 뛴다. **어디까지 막을지는 무엇을 지키는지에 달렸다.**

위협 모델로 정리하면:

| 막고 싶은 상대 | 필요한 장치 |
|---|---|
| 실수로 UPDATE 한 방 날린 운영자 | **해시 고리만으로 충분** |
| 흔적을 지우려는 단독 내부자 | 고리 + **다른 시스템에 앵커링** |
| DB 권한자가 조직적으로 은폐 | 앵커링 + **RFC 3161 타임스탬프** 또는 WORM |
| 로그 운영자 자신을 못 믿는 상황 (공개 신뢰) | **트랜스퍼런시 로그 + witness 정족수** (CT 급) |

한 단계 올라갈 때마다 **운영 부담과 지연이 눈에 띄게 늘어난다.** 「어차피 할 거면 제일 센 걸로」가 아니라, 30장 전체의 태도대로 **무엇을 지키는지 먼저 정하고 거기서 거꾸로 값을 계산하는 것**이 맞다.

## 함께 볼 것

- 감사 로그의 요건은 **「나중에 안 고쳤다」를 보일 수 있어야 한다**는 것 → 무결성(고리)만이 아니라 **완전성**(빠뜨린 이벤트가 없다)도 필요하다. 앵커링은 무결성만 준다. 완전성은 「기록이 곧 쓰기다」로 뒤집은 쓰기 경로가 준다(30.2).
- **개인정보와의 충돌**: 앵커링·WORM으로 불변성을 강화할수록 삭제 요구(GDPR 잊힐 권리 등)와 충돌한다. 그래서 이벤트에는 **참조만** 넣고 본문은 지울 수 있는 곳에 두는 설계가 필요하다. 해시는 그대로 두고 payload만 지우는 **crypto-shredding**(키를 지워 복호화 불가로 만들기)이 실무 절충안이다.
