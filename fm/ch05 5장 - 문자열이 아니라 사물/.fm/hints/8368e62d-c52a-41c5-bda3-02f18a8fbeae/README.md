# 이름 붙인 그래프(named graph) 방식의 한계

> **Q.** 이름 붙인 그래프(named graph) 방식의 한계는 무엇인가?
>
> **A.** 트리플 묶음 단위로 속성을 달기 때문에, 엣지 하나만 가리키려면 묶음도 하나짜리로 만들어야 한다.

한 줄로 줄이면 **단위 불일치**입니다. 우리가 주석을 달고 싶은 것은 트리플 **하나**인데, 이름 붙인 그래프가 이름을 붙여 주는 대상은 트리플 **집합**입니다. 그래서 집합의 크기를 1로 억지로 맞추게 되고, 그 순간부터 대가가 붙습니다.

---

## 1. 이 방식이 무엇인지 (5장 `model.py` 기준)

5장 `code/model.py`는 같은 사실 하나(가온테크가 계약 C-2025-118에 서명, 시각·경로 속성 있음)를 RDF로 적는 세 방법을 나란히 둡니다. 세 번째가 이 카드의 주제입니다.

```python
# (3) 이름 붙인 그래프 — 트리플 묶음에 이름을 주고 그 이름에 속성을 단다
RDF_NAMED_GRAPH = [
    "GRAPH ex:g1 { ex:Gaon ex:signed ex:C2025118 . }",
    "ex:g1 ex:at \"2025-06-02\"^^xsd:date .",
    "ex:g1 ex:channel \"직접\" .",
]
```

읽는 순서는 이렇습니다.

1. `ex:g1`이라는 **이름을 가진 그래프**를 만들고, 그 안에 트리플을 넣는다.
2. 이제 `ex:g1`은 그냥 IRI이므로, 평범한 트리플의 주어로 쓸 수 있다.
3. 그래서 시각·경로 같은 메타데이터를 `ex:g1`에 매단다.

즉 엣지에 직접 손잡이를 다는 게 아니라, **엣지를 담은 봉투에 이름을 붙이고 봉투 겉면에 적는** 방식입니다.

용어를 정리하면:

| 용어 | 뜻 |
|---|---|
| RDF 데이터셋(RDF Dataset) | 이름 없는 **기본 그래프**(default graph) 하나 + 0개 이상의 `(이름, 그래프)` 쌍 |
| 이름 붙인 그래프 | 그 `(이름, 그래프)` 쌍. 이름은 IRI(또는 블랭크 노드) |
| 쿼드(quad) | 트리플 3개 항 + 그래프 이름 1개 = 4개 항. 저장 엔진이 실제로 다루는 단위 |
| TriG / N-Quads | 데이터셋을 파일로 적는 직렬화 형식. Turtle/N-Triples의 데이터셋 버전 |
| SPARQL `GRAPH` | 질의에서 특정 이름 붙인 그래프 안을 보라고 지정하는 절. `FROM` / `FROM NAMED`로 질의 대상 데이터셋을 구성 |

봉투 그림으로 보면:

```
[ 기본 그래프 (이름 없음) ]        ← 보통 여기에 "본문" 트리플이 쌓인다
        ex:Gaon ex:name "가온테크" .
        ...

[ ex:g1 ] { ex:Gaon ex:signed ex:C2025118 . }   ← 엣지 하나만 담은 봉투
        ↑
        └── ex:g1 ex:at "2025-06-02" .   ← 봉투 겉면에 적은 메타데이터
            ex:g1 ex:channel "직접" .
```

## 2. 원래 무엇에 쓰라고 만든 기능인가

이름 붙인 그래프는 **엣지 주석용 장치가 아닙니다.** W3C의 RDF 1.1 Datasets 노트가 드는 동기는 전부 "덩어리 단위"입니다.

| 원래 용도 | 그래프 하나가 대응하는 것 |
|---|---|
| **출처(provenance)** | 이 사실들을 어디서 가져왔나 — 원본 문서 URL, 제공 기관, 크롤 시각 |
| **버전·시간** | 사실의 변화를 추적하는 스냅샷. "2025년 1분기 판 데이터" |
| **적재 배치(load batch)** | ETL 한 번 돌린 결과 묶음. 실패하면 `DROP GRAPH` 한 줄로 통째 롤백 |
| **신뢰 구분** | 신뢰하지 않는 출처의 트리플이 믿는 지식에 섞이지 않게 격리 |
| **관점(viewpoint)** | 서로 다른 주장이 공존해야 할 때, 주장마다 다른 그래프 |
| **추론 결과 분리** | 사람이 넣은 사실 vs 추론기가 만든 사실을 다른 그래프에 |
| **접근 제어 / 파티셔닝** | 그래프 단위로 권한을 걸거나 데이터 관리 편의를 위해 쪼갬 |

핵심은 **한 그래프에 트리플이 수천~수백만 개 들어 있고, 그 전체에 공통으로 붙는 메타데이터가 하나**라는 그림입니다. 이 비율일 때 이름 붙인 그래프는 매우 경제적입니다. 메타데이터 3줄이 트리플 100만 개를 커버하니까요.

카드의 한계는 이 비율을 뒤집었을 때 생깁니다. 엣지 하나에 메타데이터를 달려면 그래프 하나에 트리플 하나. 즉 **커버리지 1:1**입니다.

## 3. 엣지 단위 주석으로 오용할 때 붙는 비용

### (1) 그래프 수 폭발

속성이 붙는 엣지가 10만 개면 그래프 이름도 10만 개입니다. 원래 "몇 개~몇백 개" 규모를 가정한 축이 갑자기 데이터 규모로 커집니다.

- 저장 엔진 다수가 그래프 목록을 카탈로그처럼 별도 관리합니다. `SELECT DISTINCT ?g WHERE { GRAPH ?g {} }` 같은 질의, 그래프 단위 통계, 그래프 단위 백업/권한 설정이 전부 무거워집니다.
- 인덱스도 트리플(3항)이 아니라 쿼드(4항) 기준이 되어, 조합별 인덱스가 늘고 저장 오버헤드가 커집니다.
- 그래프별 오버헤드(메타 레코드, 파일/세그먼트)가 있는 엔진에서는 트리플 1개당 오버헤드가 트리플 자체보다 커지는 역전이 일어납니다.

### (2) 그래프 이름 관리라는 새 숙제

봉투마다 이름을 지어 줘야 합니다. 이건 원래 없던 작업입니다.

- 작명 규칙(`ex:g1`, `ex:g2` … 는 예제용입니다)이 필요합니다. 실무에서는 보통 `ex:edge/{subject}/{predicate}/{object}` 같은 결정적 IRI를 만들거나 UUID를 씁니다.
- 결정적 IRI로 하면 **URI 인코딩·길이·충돌**을 다뤄야 하고, UUID로 하면 **같은 엣지를 다시 적재했을 때 같은 이름을 재현할 수 없어** 멱등적 재적재가 깨집니다.
- 블랭크 노드를 그래프 이름으로 쓰는 것도 허용되지만, 파일 밖으로 나가면 식별성이 사라져서 나중에 그 봉투를 다시 가리킬 수 없습니다.
- 이름이 늘어나면 이름 자체의 수명 관리(엣지가 지워지면 봉투와 메타데이터도 함께 지워야 함)를 사람이 책임져야 합니다. 참조 무결성을 지켜 주는 장치가 없습니다.

### (3) 질의마다 `GRAPH ?g`가 들어온다

이게 가장 체감되는 비용입니다. 원래 이랬던 질의가

```sparql
SELECT ?c WHERE { ?c ex:signed ?k . }
```

이렇게 바뀝니다.

```sparql
SELECT ?c ?at WHERE {
  GRAPH ?g { ?c ex:signed ?k . }
  ?g ex:at ?at .
}
```

- 엣지 하나를 밟을 때마다 `GRAPH` 블록 + `?g`를 통한 조인이 하나씩 늘어납니다. 3홉 경로 질의면 `GRAPH` 블록 3개, 조인 3개입니다.
- `?g`가 변수인 `GRAPH ?g { … }`는 옵티마이저가 "모든 그래프를 훑을 수도 있는" 패턴으로 보기 때문에, 그래프가 10만 개인 상태에서는 계획이 나빠지기 쉽습니다.
- 기존 질의를 전부 고쳐야 합니다. 이 지점에서 **RDF-star의 장점과 갈립니다.** RDF-star는 원래 트리플 `ex:Gaon ex:signed ex:C2025118 .`을 그대로 둔 채 주석만 얹으므로 기존 질의가 살아 있고(5장 `ex2` 출력의 "기존 질의가 안 깨진다"), 구체화(reification)는 원래 엣지를 없애 버려서 기존 질의가 다 깨집니다. 이름 붙인 그래프는 그 중간입니다. 트리플 자체는 살아 있지만, **어느 그래프에 있느냐가 바뀌기 때문에** 기본 그래프만 보던 질의에서는 사라진 것처럼 보입니다.

### (4) 기본 그래프 union 의미론 혼동

바로 위 문장이 핵심 함정입니다. RDF 1.1은 기본 그래프와 이름 붙인 그래프의 관계를 **한 가지로 못 박지 않았습니다.** Datasets 노트가 여러 해석을 나열합니다.

- **해석 A — 분리형(명세 기본에 가까움):** 기본 그래프와 이름 붙인 그래프는 별개다. `GRAPH ex:g1 { … }`에 넣은 트리플은 기본 그래프에 **없다.** 따라서 `{ ?c ex:signed ?k }`(= 기본 그래프 대상)는 아무것도 못 찾는다.
- **해석 B — union/merge 기본 그래프:** 기본 그래프를 모든 이름 붙인 그래프의 합집합(union)이나 병합(merge)으로 본다. 이러면 `GRAPH` 없는 질의도 그대로 찾는다. Union과 merge는 블랭크 노드를 그래프 사이에서 같은 것으로 볼지에서 갈립니다.

문제는 **해석 B가 엔진 설정에 달려 있다**는 점입니다. Jena TDB의 `unionDefaultGraph`, Virtuoso·GraphDB·Stardog 등의 유사 옵션처럼, 켜면 되고 안 켜면 안 됩니다. 그래서 실무에서 다음이 반복됩니다.

- 개발 환경에서는 union이 켜져 있어 질의가 통과하는데, 운영에서는 꺼져 있어 결과가 0건이 된다(또는 반대).
- 이걸 피하려고 트리플을 **기본 그래프와 이름 붙인 그래프에 둘 다 적어 두면**, 같은 사실이 두 벌 존재하게 되어 수정·삭제 때 양쪽을 맞춰야 하고, union 모드에서는 중복 결과가 나옵니다.
- 반대로 union을 켜면, 원래 격리하려고 만들었던 "신뢰하지 않는 출처 그래프"까지 기본 그래프에 섞여 들어옵니다. 즉 union은 이름 붙인 그래프의 **원래 목적(격리)을 무력화**합니다. 엣지 주석 편의를 위해 켠 스위치가 출처 격리를 깨는 셈입니다.

덧붙여 **"이름이 무엇을 지시하는가"**도 명세가 고정하지 않은 부분입니다. `ex:g1 ex:at "2025-06-02"`는 문법적으로는 IRI `ex:g1`에 대한 진술일 뿐입니다. 그 IRI가 (a) 그래프 자체를 지시하는지, (b) `(이름, 그래프)` 쌍을 지시하는지, (c) 그 그래프를 담은 원본 문서/리소스를 지시하는지는 관례입니다. 그래서 "이 계약 서명 시각"이라는 뜻이 데이터 안에 형식적으로 박히지 않고, 팀 합의와 문서에만 남습니다. 다른 팀이 같은 데이터를 받으면 `ex:at`이 서명 시각인지 그래프 적재 시각인지 구별할 근거가 없습니다.

## 4. 세 방법 비교 (5장 `ex2_edge_properties.py` 요지)

| | 원래 엣지가 남나 | 기존 질의 | 표준 성숙도 | 잘 맞는 자리 |
|---|---|---|---|---|
| **(1) 구체화 — 관계를 노드로 승격** | 사라짐 (`ex:hasSigning` → `ex:Signing1`) | 전부 깨짐 | RDF 1.0부터 널리 쓰인 관행. 어디서나 동작 | 관계 자체가 1급 개념(사건·역할·계약)이고 자체 속성이 여러 개일 때 |
| **(2) RDF-star / 트리플 항** | 남음 | 안 깨짐 | 확인 시점 기준 후보 권고안 단계(RDF 1.2). 엔진 지원·표기가 아직 흔들림 | 개별 트리플에 대한 주석이 진짜 필요하고, 스택이 지원할 때 |
| **(3) 이름 붙인 그래프** | 그래프 안에 남음 (기본 그래프에서는 안 보일 수 있음) | `GRAPH ?g` 도입 필요 | SPARQL 1.1 / TriG로 오래 안정. 어디서나 동작 | 메타데이터가 **여러 트리플에 공통**으로 붙을 때 |

책의 결론은 방법 선택 이전 단계입니다. **엣지 속성이 드물면 RDF로 충분하고, 기본이면 LPG가 편하다. 기준선은 관계의 30%.** 엣지 속성이 예외가 아니라 규칙이라면 세 방법 중 무엇을 골라도 계속 아플 것이므로, 모델 자체를 다시 보라는 말입니다.

## 5. 그럼 언제 이름 붙인 그래프가 오히려 최선인가

한계를 외우는 것보다 **경계선을 외우는 게** 실무에 남습니다. 다음 조건 중 하나라도 강하게 걸리면 세 방법 중 이 방법이 낫습니다.

1. **메타데이터가 묶음 단위로 자연스럽다.** 출처·수집 시각·라이선스·버전·신뢰 등급이 트리플 하나가 아니라 "이번 적재분 전체"에 붙는다. 커버리지가 1:N이면 이 방식이 가장 싸다. (원래 용도 그대로 쓰는 경우)
2. **통째 교체·삭제가 필요하다.** 스냅샷을 갈아치우거나 적재 실패를 되돌려야 한다. `DROP GRAPH` / `CLEAR GRAPH` 한 줄로 끝난다. RDF-star나 구체화로는 어떤 트리플이 이 배치 소속인지 따로 표시해 둬야 한다.
3. **RDF 1.1 표준 안에 머물러야 한다.** 트리플 항은 확인 시점에도 아직 후보 권고안 단계이고 엔진 지원이 고르지 않다. 이름 붙인 그래프는 SPARQL 1.1 `GRAPH`, TriG, N-Quads로 십수 년간 안정적이고, 어떤 트리플 스토어에서도 동작하며 상호운용된다. 특수 문법 없이 평범한 SPARQL로 메타데이터를 질의할 수 있다는 점도 크다.
4. **같은 사실을 여러 출처가 각각 주장하고, 주장마다 다르게 다뤄야 한다.** RDF 1.2의 트리플 항은 같은 s·p·o면 같은 항으로 취급되므로, 두 출처의 주장을 항 하나로 뭉갤 위험이 있다(그래서 별도 reifier를 둔다). 이름 붙인 그래프는 봉투가 다르므로 "출처 A가 말한 이 사실"과 "출처 B가 말한 이 사실"이 자연히 분리된다.
5. **격리·접근 제어가 목적이다.** 추론 결과와 원본을 나누거나, 그래프 단위 권한을 걸어야 한다. 이건 다른 두 방법이 아예 제공하지 않는 기능이다.

거꾸로 **피해야 할 신호**는 이렇습니다. 새로 만드는 그래프의 트리플 개수가 대부분 1개다 / 그래프 이름을 엣지에서 기계적으로 생성하고 있다 / 기본 그래프 union 스위치가 켜져야만 기존 질의가 돈다 / 질의마다 `GRAPH ?g` 블록이 홉 수만큼 늘어난다. 이 네 가지가 보이면 이름 붙인 그래프를 엣지 주석기로 오용하는 중입니다. RDF-star로 옮기거나(스택이 되면), 관계를 노드로 승격하거나(관계가 진짜 개념이면), LPG로 가는 편이(엣지 속성이 기본이면) 낫습니다.

## 6. 스스로 확인해 볼 질문

- 엣지 하나에 속성을 달기 위해 이름 붙인 그래프를 쓰면, 그래프 안에 들어가는 트리플은 몇 개인가? 그 숫자가 왜 문제인가?
- `ex:g1 ex:at "2025-06-02"`에서 `ex:at`은 무엇에 대한 진술인가? 명세가 이걸 확정해 주는가?
- 기본 그래프를 union으로 보는 설정을 켜면 무엇이 편해지고, 무엇이 깨지는가?
- 구체화·RDF-star·이름 붙인 그래프 중 "기존 질의가 안 깨지는" 것은 무엇인가? 이름 붙인 그래프는 왜 애매한가?
