# 「술어 목록이 곧 사물의 정체」는 어디에서 다시 나오는가

**질문**: "술어 목록이 곧 사물의 정체"라는 생각은 이 책 어디에서 다시 나오는가?

**답**: 4부의 **도구 라우팅**이다. 에이전트가 어떤 도구를 부를지 고르는 일도 「어떤 술어를 가졌나」를 보는 일이다.

구체적으로는 **25장 「여섯 가지 위상, 그리고 도구를 꽂는 구멍」의 §25.4~§25.5**(도구는 그래프 밖으로 나가는 엣지다 / 도구 설명이 곧 엣지 선택 함수다)이고, 코드로는 `content/ch25/code/ex5_tool_selection.py`가 5장 `ex4_things_not_strings.py`의 정확한 대응물입니다.

---

## 1. 먼저 5장 §5.1의 정의로 되돌아가기

5장 §5.1은 2012년 구글의 「things, not strings」 선언이 실제로 무슨 뜻이었는지를 정리합니다. 이 장의 한 줄 요약이 그대로 정의입니다.

> 「문자열이 아니라 사물」의 핵심은 **저장량이 아니라 구분**입니다. 같은 이름 뒤에 다른 노드가 있고, 노드마다 다른 술어를 갖습니다. **술어 목록이 곧 그 사물의 정체**예요.

즉 선언의 핵심은 「더 많이 저장하자」가 아니라 「사물마다 다른 술어를 갖게 하자」였습니다. 이 정의가 왜 힘을 갖는지는 `ex4_things_not_strings.py`가 보여 줍니다.

### 세 개의 「타지마할」

같은 문자열 하나에 서로 다른 사물 셋이 매달려 있고, 각자 **술어 집합이 다릅니다**.

| 사물 | 타입 | 술어 목록 |
|---|---|---|
| `t1` | 건물 | 위치, 완공, **입장료** |
| `t2` | 음악가 | 장르, 활동시작, 본명 |
| `t3` | 식당 | 지역, 영업시간, 평점 |

문자열 검색은 「타지마할」이 든 문서를 다 줍니다. 건물·음악가·식당이 한 목록에 섞이고, 고르는 건 사람 몫입니다.

사물 검색은 순서를 뒤집습니다. **어느 사물인지부터 정합니다.** 그 판별에 쓰는 신호가 술어입니다.

```python
def thing_search(q):
    """질문에 나온 낱말이 어느 사물의 «술어»와 겹치는지 본다."""
    words = q.split()
    scored = []
    for tid, t in THINGS.items():
        if t["name"] not in q:
            continue
        hit = sum(1 for w in words for k in t["props"] if k in w or w in k)
        scored.append((hit, tid, t))
    scored.sort(reverse=True, key=lambda x: x[0])
    return scored
```

질문이 `"타지마할 입장료"`일 때, 「입장료」를 술어로 가진 사물이 `t1`(건물) 하나뿐이므로 답이 확정됩니다. 이름은 셋 다 똑같아서 아무 정보를 주지 않았고, **술어 겹침이 정체를 정했습니다.**

그리고 5장 예제의 마지막 문단이 이 카드의 답을 직접 예고합니다.

> 술어 목록이 곧 그 사물의 정체다. 이 생각은 **4부에서 도구 라우팅으로 돌아온다.**
> 에이전트가 어떤 도구를 부를지 고르는 일도 «어떤 술어를 가졌나»를 보는 일이다.

## 2. 두 문제의 구조적 동형성

5장의 「사물 판별」과 4부의 「도구 선택」은 비유가 아니라 **같은 문제의 두 인스턴스**입니다. 항 하나하나가 대응됩니다.

| 5장 §5.1 — 사물 판별 | 4부 §25.5 — 도구 라우팅 |
|---|---|
| 사물(노드) | 도구(그래프 밖으로 나가는 엣지) |
| **사물의 술어 목록** (`위치`, `완공`, `입장료`) | **도구의 입력 스키마 / 파라미터 이름**과 설명에 적힌 어휘 (`person_name`, `team`, `depth`, 「상사」, 「명단」) |
| `THINGS` 딕셔너리 = 사물 카탈로그 | 도구 목록(MCP `tools/list`로 실행 시점에 받아 오는 것) |
| **질문 낱말 ↔ 술어 겹침 점수** (`hit`) | **요청에 등장하는 슬롯 ↔ 도구 스키마 겹침** — 질문에 나온 슬롯이 어느 도구의 파라미터·설명 어휘와 겹치는가 |
| 겹침이 가장 큰 사물로 정체 확정 | 겹침이 가장 큰 도구로 호출 확정 |
| **이름 충돌**: 세 「타지마할」 | **이름만 비슷한 도구들**: `search`, `lookup`, `find` (혹은 `find_person` / `chain_of_command` / `team_members`) |
| 문자열 검색 = 이름만 보고 다 던져 줌, 고르는 건 사람 | 이름만 보고 고르는 라우터 = 비슷한 도구 사이에서 흔들림, 뒤처리는 사람 |

### 겹침 점수가 문자 그대로 같다

25장 `ex5_tool_selection.py`의 선택기는 5장 `thing_search()`와 **같은 방식으로 점수를 냅니다**. 질문 토큰과 도구 설명 토큰의 교집합 크기를 셉니다.

```python
def choose(query, descriptions):
    q = tokenize(query)
    best, score = None, -1
    for name, desc in descriptions.items():
        overlap = len(q & tokenize(desc))   # ← thing_search 의 hit 와 같은 것
        if overlap > score:
            best, score = name, overlap
    return best
```

25장 예제는 **도구 코드를 한 줄도 고치지 않고 설명만 바꿔서** 정확도를 재 봅니다.

- `BAD`: `find_person` → 「사람 조회」, `chain_of_command` → 「체인 조회」, `team_members` → 「팀 조회」
- `GOOD`: 무엇을 주는지 + 어떤 말로 물었을 때 이것인지 + **언제 안 쓰는지**까지 적은 설명

이름 길이도 도구 개수도 그대로인데 정확도가 올라갑니다. 이유는 5장과 똑같습니다. **이름은 세 개가 다 비슷해서 구분 신호가 아니고, 술어(파라미터·설명 어휘)가 구분 신호이기 때문입니다.**

### 이름 충돌 문제도 똑같이 돌아온다

세 「타지마할」이 문자열로는 구분 불가였던 것처럼, 실무 도구 목록에는 `search` / `lookup` / `find` / `query` / `get` 같은 것들이 나란히 앉습니다. 이름만 보면 다 「찾는다」입니다. MCP처럼 여러 서버의 도구를 실행 시점에 합쳐 오면 **서버가 다른데 이름이 겹치는** 경우까지 생깁니다.

이때 라우터를 살리는 건 이름이 아니라 술어입니다.

- `search(query: str, top_k: int)` → 자유 문장, 순위 있는 후보 여러 개
- `lookup(id: str)` → 식별자 하나, 정확히 한 건
- `find_person(name: str) -> {팀, 상사 아이디}` → 사람 한 명, 반환 필드가 술어를 드러냄
- `chain_of_command(person: str, depth: int)` → 위로 올라가는 경로, `depth`라는 술어가 이 도구만의 것

「타지마할 **입장료**」가 건물을 확정했던 것과 같은 방식으로, 「**보고 라인** 전체」는 `depth`를 가진 도구를 확정합니다. 요청에 등장하는 슬롯이 어느 스키마와만 겹치는가 — 그게 라우팅 신호입니다.

### 25장이 붙이는 그래프 어휘

25장은 이 대응을 그래프 말로 다시 씁니다.

- §25.4 **도구는 그래프 밖으로 나가는 엣지다.** MCP는 그 엣지 목록을 실행 시점에 받아 오는 방식이고, 대가는 컴파일 시점에 아무것도 모른다는 것입니다(그래서 시작할 때 목록을 검증합니다).
- §25.5 **도구 설명이 곧 엣지 선택 함수다.** 엣지를 고르는 규칙을 자연어로 적어 두는 셈이라, 그 글이 곧 코드입니다.

5장의 말로 옮기면 이렇게 됩니다. **노드의 정체를 술어 목록이 정하듯, 엣지의 선택을 스키마와 설명이 정합니다.**

## 3. 여기서 나오는 실무 교훈

### (1) 도구 설명을 이름이 아니라 파라미터·술어 수준으로 써라

「사람 조회」처럼 이름을 한 번 더 풀어 쓴 설명은 정보를 거의 안 보탭니다. 25장이 뽑은 좋은 설명의 3요소는 곧 「술어를 적는 법」입니다.

1. **무엇을 주는지** — 반환 필드를 말합니다. 반환 필드가 그 도구의 술어 목록입니다. (`이름, 소속 팀, 상사 아이디를 준다`)
2. **어떤 말로 물었을 때 이것인지** — 사용자 어휘를 넣습니다. (`상사, 상사의 상사, 보고 라인, 결재선을 물으면 이것이다`)
3. **언제 안 쓰는지** — 경계를 긋습니다. (`여러 명을 찾을 때는 쓰지 않는다`, `아래 부하 목록에는 쓰지 않는다`)

3번이 제일 자주 빠지고 제일 크게 듣습니다. 도구가 늘어날수록 「비슷한 도구」가 생기고, 그때 경계를 그어 둔 쪽이 이깁니다. 5장 식으로 말하면, `t1`과 `t3`이 둘 다 「타지마할」인 상황에서 **어느 술어가 누구에게 없는지**를 적어 두는 일입니다.

### (2) 도구 스키마가 곧 라우팅 신호다

- 파라미터 **이름을 술어처럼** 지으세요. `q`, `arg1`, `input` 대신 `person_name`, `team_name`, `as_of_date`, `depth`. 모델은 사용자 문장의 슬롯을 스키마 필드에 맞추려고 하는데, 필드 이름이 무의미하면 맞출 데가 없습니다.
- 반환 스키마도 설명에 노출하세요. 「무엇을 주는지」가 곧 그 도구의 술어 목록이고, 사용자가 요구한 술어를 가진 도구가 정답입니다.
- **다른 도구에는 없는 파라미터**가 그 도구의 결정적 술어입니다. `depth`가 `chain_of_command`에만 있으면 「보고 라인 전체」는 자동으로 그리로 갑니다. 반대로 두 도구의 스키마가 완전히 같으면, 그 둘은 라우터 입장에서 구분 불가능한 사물입니다 — 합치거나, 술어를 갈라야 합니다.
- **동의어를 넣으세요.** 25장 예제에서 마지막까지 틀린 질문이 「박민수 **상급자** 알려줘」입니다. 설명에는 「상사」가 있는데 사용자는 「상급자」라고 했습니다. 우리는 사내 용어로 쓰고 사용자는 자기 말로 묻습니다. 상사·상급자·윗사람·결재선을 다 적어 두세요. 촌스러워 보여도 이게 듣습니다. 실제 질문 로그에서 뽑아 넣으면 더 좋습니다.
- 예제의 선택기는 단어 겹침을 세는 게 전부라 진짜 모델보다 훨씬 멍청합니다. 그런데 **「설명이 나쁘면 못 고른다」는 성질은 모델도 같습니다.** 그래서 이 단순한 실험이 유효합니다.

### (3) 라우팅 자체는 품질 장치가 아니다 (§25.3)

덧붙이면, 25장은 라우터가 품질을 **올리는** 장치가 아니라 품질을 조금 내주고 토큰을 크게 아끼는 **교환**이라고 못 박습니다. 그래서 라우터를 넣을 때 제일 먼저 만들 것은 라우터가 아니라 「라우팅이 맞았는지 채점하는 데이터셋」입니다(100건이면 시작 가능). 도구 설명을 술어 수준으로 고쳤을 때 정확도가 올랐는지 재려면 이 채점판이 있어야 합니다.

## 4. 이 책의 전개 안에서

- **1부 5장 §5.1** — 「문자열이 아니라 사물」의 정의. 술어 목록이 사물의 정체다. 판별 예제는 `ex4_things_not_strings.py`.
- **4부 25장 §25.4~§25.5** — 같은 생각이 도구 라우팅으로 돌아옵니다. 도구는 밖으로 나가는 엣지, 도구 설명은 엣지 선택 함수. 실험 예제는 `ex5_tool_selection.py`. 25장 예제는 이 규칙을 「2장의 말로 하면 Description이 호출을 결정한다」로도 요약합니다.

같은 원리가 트랙 1(지식 그래프)에서는 **노드의 정체를 정하는 규칙**으로, 트랙 2(에이전트 그래프)에서는 **엣지를 고르는 규칙**으로 나타납니다. 5장 서두에서 「2012년 선언의 뜻이 이 책의 나머지에 계속 돌아온다」고 한 것이 이 지점입니다.
