# 새 속성 추가 난이도: LPG vs RDF

**질문** 새 속성을 추가하는 난이도에서 LPG와 RDF는 차이가 있는가?

**답** 거의 없다. RDF는 트리플 한 줄 추가, LPG는 주머니에 키 하나 추가로 둘 다 쉽다. 차이는 속성을 가리켜야 할 때 생긴다.

---

## 1. 먼저 두 모델이 속성을 어디에 두는지

5장 `model.py`는 **같은 사실 여섯 개**를 두 벌로 적어 놓습니다. 여기가 출발점입니다.

LPG는 노드와 엣지가 각각 **속성 주머니(property bag)** 를 하나씩 갖습니다.

```python
LPG_NODES = {
    "n1": {"labels": ["Company"], "props": {"name": "가온테크", "grade": "A"}},
    ...
}
```

RDF는 속성마다 **한 줄(트리플)** 입니다.

```python
RDF_TRIPLES = [
    ("ex:Gaon", "rdf:type", "ex:Company"),
    ("ex:Gaon", "ex:name",  '"가온테크"'),
    ("ex:Gaon", "ex:grade", '"A"'),
    ...
]
```

`ex1_two_models.py`가 세어 보여 주는 게 이겁니다. **노드 3개 vs 트리플 12개.** 정보량은 같고 **세는 단위**만 다릅니다.

## 2. 그래서 "새 속성 추가"는 어느 쪽이 어려운가 — 거의 동률

가온테크에 `ceo` 속성을 새로 붙여 봅시다.

| | 쓰는 법 | 스키마 변경 | 기존 질의 |
|---|---|---|---|
| RDF | `ex:Gaon ex:ceo "김하늘" .` 한 줄 INSERT | 없음 | 안 깨짐 |
| LPG (Neo4j) | `SET c.ceo = '김하늘'` | 없음 | 안 깨짐 |

둘 다 **한 동작, 무중단, 기존 질의 무영향**입니다. 예제 코드의 출력 문장이 그대로 이 말입니다.

> 새 속성을 추가할 때: RDF 는 줄 하나 추가. LPG 도 키 하나 추가. 둘 다 쉽다.

여기서 중요한 건 "둘 다 쉽다"가 **비교의 종결**이라는 점입니다. 이 축으로는 모델을 고를 수 없습니다.

## 3. "RDF는 스키마가 유연하다"는 주장이 왜 구분점이 못 되는가

RDF 진영의 오래된 홍보 문구가 있습니다. *"관계형 DB는 컬럼을 추가하려면 ALTER TABLE에 마이그레이션이 필요하지만, RDF는 트리플만 넣으면 된다."* 이 문장 자체는 맞습니다. **그런데 비교 대상이 관계형 DB입니다.** 이 문장을 LPG에 그대로 겨누면 세 군데서 틀립니다.

**(1) 비교군이 바뀌었다.** LPG도 스키마리스로 태어났습니다. Neo4j는 라벨을 처음 쓰는 순간 라벨이 생기고, 속성 키도 쓰는 순간 생깁니다. "선언 없이 쓴다"는 성질은 RDF의 전유물이 아니라 두 그래프 모델의 공통 성질입니다.

**(2) 스키마 유연성은 모델의 속성이 아니라 엔진 정책의 속성이다.** 같은 LPG인데도 Neo4j는 스키마 옵셔널, Kuzu는 스키마 강제입니다(4절). 반대로 RDF 쪽에도 SHACL/OWL로 제약을 걸어 놓으면 트리플 하나 넣는 게 검증 실패로 막힙니다. 즉 이 축은 **RDF↔LPG를 가르는 선이 아니라 "이 엔진이 스키마를 못 박느냐"를 가르는 선**입니다. 축 자체가 다른 방향으로 놓여 있습니다.

**(3) RDF의 진짜 이점은 유연성이 아니라 전역 식별자다.** 밖에서 온 데이터를 합칠 때 RDF가 편한 이유는 스키마가 없어서가 아니라, 술어와 주어가 **IRI라는 전역 이름**을 갖고 있어서 두 출처의 `foaf:name`이 별도 매핑 없이 같은 술어로 합쳐지기 때문입니다. `ex3` 마지막 문장의 "밖에서 오는 데이터를 합치는 일이 많으면 RDF"가 이 이야기입니다. 이건 유연성이 아니라 **이름 붙이기 규율**의 이점이고, 오히려 IRI를 정하는 비용을 새로 요구합니다.

정리하면, "스키마 유연성"은 실무에서 이미 양쪽이 통과한 문턱이라 변별력이 없습니다. 논지를 옮길 곳은 다음 절입니다.

## 4. 진짜 구분점: 속성을 **주소로 가리킬 수 있는가**

새 속성을 넣는 건 쉽습니다. 어려워지는 건 **그 속성 하나에 무언가를 더 달 때**입니다. 출처, 관측 시각, 신뢰도, 유효 기간, 누가 입력했는지 같은 것들이요.

**RDF는 문장 자체에 주소가 있습니다.** `ex:Gaon ex:grade "A"`는 독립된 한 줄이므로, 그 줄을 지목해 메타데이터를 붙일 수 있습니다. `ex2_edge_properties.py`가 보여 주는 세 방법이 전부 "줄을 지목하는" 기법입니다.

```
(1) 구체화   ex:Signing1 ex:at "2025-06-02" ...      → 관계를 노드로 승격
(2) RDF-star << ex:Gaon ex:signed ex:C2025118 >> ex:confidence "0.98"
(3) 이름 붙인 그래프  GRAPH ex:g1 { ... } / ex:g1 ex:at ...
```

**LPG는 속성이 주머니 안의 키-값이라 손잡이가 없습니다.** `n1.grade = "A"`라는 사실 조각에는 ID가 없습니다. 이 값에만 출처를 달려면 방법이 하나뿐입니다 — **속성을 노드로 승격**하는 것. `(Company)-[:HAS_GRADE {source:'신평사', asOf:date}]->(Grade {value:'A'})` 같은 모양이 되는데, 이건 사실상 RDF의 구체화를 손으로 하는 일이고 기존 질의(`c.grade`)를 전부 깨뜨립니다.

`ex1`의 결론 문장이 이 지점을 정확히 찍습니다.

> 속성 하나에 출처를 달 때: RDF 는 그 트리플을 가리키면 된다.
> LPG 는 속성이 주머니 안에 있어서 가리킬 손잡이가 없다. **이게 진짜 차이다.**

### 4-1. 대칭점: 엣지 속성에서는 방향이 뒤집힌다

가리킬 수 있느냐는 **한쪽이 이기는 축이 아니라, 무엇에 주소가 붙어 있느냐**의 문제입니다.

| 무엇을 가리키려는가 | LPG | RDF |
|---|---|---|
| 노드의 속성 값 하나 | ✗ 손잡이 없음 (노드로 승격해야) | ○ 트리플을 지목 |
| 관계(엣지) 하나 + 속성 | ○ 엣지가 1급 시민, 한 줄 | △ 세 방법 중 택1, 각각 대가 |

RDF는 **문장 단위**로 주소가 있고, LPG는 **노드·엣지 단위**로 주소가 있습니다. 그래서 노드 속성 메타데이터는 RDF가 편하고, 엣지 속성은 LPG가 편합니다. 5장이 제시하는 실무 기준이 여기서 나옵니다.

> 제 기준: 관계의 30% 이상에 속성이 붙으면 LPG. 그 밑이면 RDF.

### 4-2. 한 가지 정밀한 단서

RDF에서도 **리터럴 값 자체**는 주어가 될 수 없습니다. `"A"`를 가리킬 수는 없습니다. 가리킬 수 있는 건 `ex:Gaon ex:grade "A"`라는 **문장**입니다. 그래서 RDF-star가 트리플을 항(term)으로 승격하는 문법을 따로 만들어야 했습니다(`RDF 1.2 triple terms`). "RDF는 아무거나 가리킬 수 있다"가 아니라 "**문장에 주소가 있다**"가 정확한 표현입니다.

## 5. Kuzu처럼 스키마를 강제하는 LPG 엔진에서는 이야기가 달라진다

5장 `ex3_cypher_vs_sparql.py`가 Kuzu를 쓰면서 굳이 스키마를 먼저 선언합니다.

```python
CYPHER_SCHEMA = [
    "CREATE NODE TABLE Company(name STRING, grade STRING, PRIMARY KEY(name))",
    "CREATE REL TABLE Signed(FROM Company TO Contract, at DATE)",
    # Neo4j 5.x 에는 이 스키마 선언이 없다. 라벨을 쓰면 그 자리에서 생긴다.
    # 스키마를 미리 못 박느냐가 두 엔진의 큰 차이다. 12장에서 다시 본다.
]
```

Kuzu는 컬럼 기반 저장을 쓰는 대신 **노드/렐 테이블 스키마를 선언하도록 강제**합니다. 그래서 새 속성 추가가 관계형 DB와 같은 모양이 됩니다.

```sql
ALTER TABLE Company ADD ceo STRING;   -- DDL, 선언 먼저
```

여기서 2절의 "둘 다 쉽다"에 조건이 붙습니다.

| 엔진 | 새 속성 추가 | 성격 |
|---|---|---|
| RDF 트리플스토어 | INSERT 한 줄 | 선언 불필요 |
| Neo4j (LPG, 스키마 옵셔널) | `SET n.ceo = ...` | 선언 불필요 |
| Kuzu (LPG, 스키마 강제) | `ALTER TABLE ... ADD` | **DDL 필요** |

즉 카드의 "거의 없다"는 **스키마리스 LPG 기준**의 답입니다. 스키마 강제 엔진에서는 새 속성 추가에 실제로 절차가 생기고, 대신 타입 안정성·오타로 생기는 유령 속성 방지·컬럼 스캔 성능을 얻습니다. 이건 손해가 아니라 **거래**입니다.

그리고 이 표가 3절의 논지를 한 번 더 확인해 줍니다. 스키마 유연성의 차이는 **RDF↔LPG 사이가 아니라 Neo4j↔Kuzu 사이, 즉 같은 LPG 안에서 더 크게 벌어집니다.** 모델을 고르는 축이 아니라는 증거입니다.

## 6. 이 카드로 대답할 수 있게 되는 것

누가 "RDF가 스키마 유연해서 우리한테 맞다"고 하면, 물어야 할 질문은 이렇게 바뀝니다.

1. 새 속성을 얼마나 자주 추가하나요 → 이 질문으로는 안 갈립니다. 양쪽 다 쉽습니다.
2. **속성 하나 단위로 출처·시각·신뢰도를 달아야 하나요** → 그렇다면 RDF, 또는 LPG에서 값을 노드로 승격할 각오.
3. **관계에 속성이 붙는 비율이 몇 %인가요** → 30% 넘으면 LPG.
4. 데이터가 밖에서 오나요, 우리가 만드나요 → 밖이면 RDF(전역 IRI), 안이면 LPG.
5. 스키마를 못 박고 싶은가요 → 이건 모델 질문이 아니라 엔진 질문(Neo4j vs Kuzu).

그리고 5장의 마지막 권고를 잊지 마세요. 표현력 비교로 결론 내지 말고, **질의 다섯 개를 두 언어로 써 보는 반나절**이 4개월을 아낍니다.
