# 변화량 합산이 맞는 경우와 틀리는 경우

**질문** — 변화량 합산이 맞는 경우와 틀리는 경우는 각각 무엇인가?

**답** — 장바구니 담기·재고 차감·좋아요 수처럼 독립적인 증분일 때는 맞고, 현재 값을 다시 센 결과에는 쓰면 안 된다.

---

## 1. 갈림은 「의도가 무엇이냐」에 있다

두 에이전트가 `인원` 필드를 동시에 고쳤다고 하자. 저장된 값은 `3`이었고, A는 `5`를, B는 `4`를 쓰려고 한다. 여기서 보이는 것은 숫자 세 개뿐이다.

```
base = 3,  A = 5,  B = 4
```

이 숫자만으로는 아무것도 결정할 수 없다. 결정에 필요한 것은 **A와 B가 무엇을 하려던 것이었나**이기 때문이다. 두 가지 해석이 가능하다.

| 해석 | A의 의도 | B의 의도 | 올바른 병합 |
|---|---|---|---|
| **증분(delta)** | 「두 명 늘려라」 | 「한 명 늘려라」 | 3 + 2 + 1 = **6** |
| **관측(observation)** | 「세어 보니 5명이더라」 | 「세어 보니 4명이더라」 | 6은 **명백히 틀림**. 5 아니면 4, 혹은 사람 확인 |

같은 `3 → 5`가 한쪽에서는 「+2를 해라」라는 **명령**이고, 다른 쪽에서는 「지금 상태는 5다」라는 **보고**다. 병합 규칙은 이 둘에 대해 정반대가 된다.

- 증분이면 **더해야** 한다. 두 사람이 각각 다른 사람을 데려왔으니 결과는 6이 맞다.
- 관측이면 **골라야** 한다. 두 사람이 **같은 사실**을 보고 다르게 센 것이므로, 참값은 5거나 4거나 둘 다 아닐 수는 있어도, 6일 가능성은 없다. 아무도 6을 세지 않았다.

이 장의 `ex5_merge_strategy.py`가 보여 주는 함정이 정확히 이것이다.

## 2. 에셋의 「인원=6」 반례

`code/ex5_merge_strategy.py`의 `type_aware` 전략은 필드 종류를 보고 병합 방식을 고른다. 수치 필드에는 변화량 합산을 적용한다.

```python
if kind == "수치" and base.isdigit():
    # 양쪽의 «변화량»을 더한다
    d = (int(a) - int(base)) + (int(b) - int(base))
    return str(int(base) + d), "변화량 합산"
```

충돌 데이터는 이렇다.

```python
("인원", "3", "5", "batch", "4", "agent-5102", "수치"),
#        base  A    A출처   B    B출처         종류
```

결과는 `3 + (5-3) + (4-3) = 6`. 출력에도 「변화량 합산」이라고 찍히고, 자동 해결 건수는 하나 올라간다. 에러도, 경고도 없다. 이 장 전체가 말하는 「조용히 틀리는」 모양 그대로다.

책 본문의 지적을 그대로 옮기면:

> 「인원」의 결과를 보시라. 6이다. 양쪽 누구도 6을 쓰려고 하지 않았다.
> 그런데 이게 맞을 수도 있다. 「두 명 늘었고 한 명 늘었다」면 세 명 는 거니까.
> 틀릴 수도 있다. 둘 다 「같은 사실」을 보고 다르게 센 것이면 6은 틀렸다.

주목할 점은, **코드 안에는 어느 쪽인지 판단할 정보가 없다는 것**이다. `("인원", "3", "5", ..., "4", ..., "수치")` 이 튜플에는 「+2 해라」와 「세어 보니 5」를 구별할 수 있는 필드가 하나도 없다. `kind`가 `"수치"`라는 것은 **타입** 정보이지 **의도** 정보가 아니다. 그런데 `type_aware`는 타입만 보고 의도를 가정해 버린다. 여기가 버그의 발생 지점이다.

그리고 이 오류는 상황이 나쁠수록 커진다. 에이전트 열 개가 각각 「인원을 다시 세어 보니 5」라고 보고했다면, 변화량 합산은 `3 + 2×10 = 23`을 만든다. 사람 세 명짜리 팀이 스물세 명이 된다. 자동 병합의 오류율을 재야 한다는 이 장의 마지막 권고가 여기에 걸린다. 「사람 일이 줄었다」는 지표만 보면 이 23은 영원히 안 보인다.

## 3. 맞는 경우: 왜 「독립적인 증분」인가

변화량 합산이 옳으려면 두 조건이 필요하다.

1. **의도가 증분이다.** 각 작업이 「현재 값이 무엇이든 거기서 ±n」을 뜻한다.
2. **증분끼리 독립이다.** A가 센 것과 B가 센 것이 **서로 다른 사건**이다. 같은 사건을 두 번 세지 않는다.

이 조건을 만족하는 전형적인 예가 답에 나오는 셋이다.

| 예 | 왜 독립 증분인가 |
|---|---|
| **장바구니 담기** | 사용자가 브라우저 탭 두 개에서 각각 상품을 담았다. 두 담기는 서로 다른 행위다. 합쳐서 2개가 맞다. |
| **재고 차감** | 주문 A가 3개, 주문 B가 2개를 뺐다. 서로 다른 주문이다. 총 5개가 빠져야 맞다. |
| **좋아요 수** | 서로 다른 두 사용자가 각각 눌렀다. 겹치지 않는다. +2가 맞다. |

세 경우 모두 **「그 작업이 사건을 하나 만들었다」**는 성질이 있다. 병합 결과가 어떤 개별 작업의 값과 다른 것은 버그가 아니라 정확한 동작이다. 좋아요가 100에서 102가 되는 것은 정상이고, 누구도 「102를 쓰려고」 하지는 않았다.

반면 「인원을 다시 세어 보니」는 사건을 만들지 않는다. **읽기**다. 읽기를 두 번 하고 두 결과를 더하면, 세상에 없던 사람이 생긴다.

### 판별 질문 하나

필드 하나를 놓고 이렇게 물어보면 대개 갈린다.

> **「같은 작업을 두 번 실행하면 값이 두 배로 움직여야 하는가?」**

- 좋아요 버튼을 두 번 누르면 +2가 맞다 → 증분. 합산해도 된다.
- 인원 세기를 두 번 하면 여전히 5다 → 관측. 합산하면 안 된다.

관측은 21장의 의미에서 **멱등**하다. 증분은 멱등하지 않다. 그래서 증분에는 별도의 중복 제거 장치(요청 ID, 이벤트 ID)가 필요하고, 그것이 없으면 재시도 한 번이 곧 값 하나만큼의 오차가 된다. 이 장의 낙관적 잠금이 실패 시 **재시도**한다는 점을 떠올리면, 증분 병합과 재시도가 만나는 지점은 특별히 조심해야 한다.

## 4. CRDT의 PN-Counter가 증분에만 되는 이유

이 장의 키워드 표에 [실험] 상태로 올라 있는 **CRDT(충돌 없는 복제 자료형, Conflict-free Replicated Data Type)**가 여기와 맞닿는다.

**PN-Counter**(Positive-Negative Counter)는 분산 환경에서 조율 없이 증감을 병합하는 자료형이다. 구조는 이렇다.

- 노드마다 「내가 더한 총량(P)」과 「내가 뺀 총량(N)」을 따로 들고 있다.
- 병합은 노드별로 **최댓값**을 취하고(G-Counter 두 개), 최종 값은 `sum(P) - sum(N)`이다.
- 어떤 순서로 병합해도, 몇 번 병합해도 같은 값에 수렴한다(교환·결합·멱등).

```
        노드 A            노드 B
증분:   +2               +1
P:      {A: 2}           {B: 1}
병합:   P = {A: 2, B: 1}  →  값 = 3 - 0 + base
```

여기서 결정적인 것은, **PN-Counter가 저장하는 것이 값이 아니라 「누가 얼마나 움직였는가」라는 기여분이라는 점**이다. 병합은 기여분을 모으는 연산이지 값을 고르는 연산이 아니다. 그래서 자동 수렴이 성립한다.

그리고 바로 그 이유로 **관측에는 못 쓴다.**

- 「세어 보니 5」에는 「누가 얼마나 움직였는가」가 없다. 기여분으로 분해할 수 없는 정보다.
- 억지로 `5 - 3 = +2`로 분해해서 넣으면, 그것은 사용자가 말한 적 없는 증분을 시스템이 지어내는 것이다. `ex5`의 `type_aware`가 하는 일이 정확히 이 지어내기다.
- 관측값을 CRDT로 다루려면 카운터가 아니라 **LWW-Register**(Last-Writer-Wins Register) 같은 「값을 고르는」 자료형을 써야 한다. 타임스탬프나 출처 등급으로 하나를 고르고 나머지는 버린다. 그러면 5나 4가 나오지, 6은 안 나온다.

정리하면 **CRDT는 「충돌을 없애 주는 마법」이 아니라 「이 필드의 병합 규칙이 무엇인지 미리 선언하게 만드는 장치」다.** 카운터를 고르는 순간 「이 값은 증분으로 다룬다」고 선언한 것이고, 레지스터를 고르는 순간 「이 값은 관측이라 골라야 한다」고 선언한 것이다. 자료형 선택 자체가 도메인 판단이고, 그래서 이 장이 「충돌 감지는 기술 문제, 충돌 해결은 도메인 문제」라고 말하는 것이다.

## 5. 설계 교훈: API를 `increment(+2)`로 만들면 모호성이 사라진다

지금까지의 문제는 전부 **의도 정보가 API 경계에서 버려졌기 때문**에 생겼다.

```python
set_count(5)        # 의도가 사라진다. 증분이었는지 관측이었는지 알 수 없다
increment(+2)       # 의도가 남는다. 증분이라고 못 박혀 있다
observe(5, at=t)    # 의도가 남는다. 관측이라고 못 박혀 있다
```

`set_count(5)`를 받는 순간, 서버는 이 5를 「+2였던 것」으로 되돌릴 방법이 없다. 그래서 병합기가 `5 - base`를 계산해 증분을 **추측**하게 되고, 그 추측이 틀리면 6 같은 값이 나온다. 애초에 `increment(+2)`로 받았다면 추측할 것이 없다. 그냥 더하면 되고, 그 더하기는 정의상 옳다.

### 30장 「전체 상태를 이벤트에 넣지 마라」와 같은 이야기

`ex1_lost_update.py`의 마무리에 이 연결이 명시돼 있다.

> 30장에서 「전체 상태를 이벤트에 넣지 마라」고 한 이유가 이것이다.
> 전체를 쓰면 겹치지 않는 변경도 서로를 덮는다.

두 장이 같은 병을 다른 각도에서 본다.

| | 전체 상태를 쓸 때 | 의도를 쓸 때 |
|---|---|---|
| **30장 (순차)** | 나중 이벤트가 앞 이벤트를 통째로 덮는다 | 겹치지 않는 변경은 공존한다 |
| **31장 (동시)** | 병합기가 의도를 추측해야 하고 틀린다 | 병합 규칙이 자명해진다 |
| **잃어버린 갱신** | 발생한다 | 필드/증분 단위라 원천 차단된다 |

`ex2_optimistic.py`의 **필드 단위 수정(`field_level`)**이 이 원칙의 최소 형태다. 통째로 쓰지 않고 바뀐 것만 쓰니, 읽고-판단하고-쓰기 사이의 창 자체가 없다. `increment(+2)`는 여기서 한 걸음 더 나간 것이다. 필드 하나만 쓸 뿐 아니라, **그 필드에 대해 무엇을 하려는지까지** 서버에 넘긴다. 그래서 서버가 `UPDATE ... SET count = count + 2`로 원자적으로 처리할 수 있고, 읽기 자체가 필요 없어진다.

### 실무에서의 정리

1. **필드마다 「증분이냐 관측이냐」를 스키마에 적어 둔다.** `kind: "수치"`로는 부족하다. `kind: "카운터"` / `kind: "관측값"`처럼 병합 의미를 담아야 한다. 28장의 `SINGLE_VALUED` 목록처럼, 이 표도 코드로 갖고 있어야 한다.
2. **증분 필드는 증분 API로만 노출한다.** `set_count`를 아예 만들지 않으면 잘못 쓸 방법이 없다. 「관리자 정정」처럼 절대값 설정이 꼭 필요하면 별도의 명시적 경로(`reset_count`)로 분리하고, 그 경로는 병합 대상에서 빼거나 사람 확인으로 보낸다.
3. **증분에는 중복 제거 키를 붙인다.** 증분은 멱등하지 않으므로, 재시도가 있는 시스템에서는 요청 ID로 「이미 반영한 증분인가」를 걸러야 한다(21장).
4. **관측 필드는 골라야 한다.** 출처 등급(`ex5`의 `source_rank`), 타임스탬프, 아니면 사람 확인. 절대로 더하지 않는다.
5. **어느 쪽인지 모르겠으면 사람에게 보낸다.** 자동으로 6을 만들어 놓는 것보다, 보류 한 건이 낫다. 자동 병합의 「해결 건수」가 아니라 **오류율**을 지표로 삼아야 이 판단이 유지된다.

## 6. 한 줄 요약

`3 → 5`와 `3 → 4`라는 같은 데이터가, 의도가 증분이면 6이 정답이고 의도가 관측이면 6이 오답이다. 데이터만으로는 구별할 수 없으므로 병합기가 추측하게 두지 말고, `increment(+2)`처럼 **의도를 API에 실어 보내서** 애초에 추측이 필요 없게 만들어야 한다.
