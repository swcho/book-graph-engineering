# 논리 단위 방식이 6/6이 되려면 무엇을 추가해야 하는가

## 한 줄 답

**버전 비교 *전에* 멱등 검사를 먼저 둔다.** 「쓰려는 것이 이미 있는 것과 같으면 성공으로 친다」 한 줄이면 논리 단위 방식이 5/6에서 6/6이 된다.

## 1. 무슨 표에서 나온 이야기인가

31장 예제 4(`ex4_conflict_shape.py`)는 두 에이전트가 그래프를 동시에 고치는 여섯 경우를 놓고, **버전을 어디에 둘 것인가**를 세 가지로 나눠 판정합니다.

- **노드 버전** — 노드마다 `ver` 하나
- **엣지 버전** — 엣지마다 `ver` 하나
- **논리 단위** — 「주어 + 관계 종류」를 한 덩어리로 보는 방식 (예: `이서연 + 이끔`)

| 경우 | 노드 버전 | 엣지 버전 | 논리 단위 | 원하는 것 |
|---|---|---|---|---|
| 같은 엣지의 속성 | 막음 | 막음 | 막음 | 막음 |
| 한 노드의 다른 엣지 | 막음\* | 통과 | 통과 | 통과 |
| 단일 값 관계 | 막음 | 통과\* | 막음 | 막음 |
| 노드 삭제 대 엣지 추가 | 막음 | 통과\* | 막음 | 막음 |
| **양쪽에서 같은 엣지 추가** | **막음\*** | **막음\*** | **막음\*** | **통과** |
| 서로 다른 방향 | 막음\* | 통과 | 통과 | 통과 |
| **맞은 개수** | **2/6** | **4/6** | **5/6** | |

(\* 는 틀린 판정)

논리 단위가 5/6으로 제일 낫습니다. 그런데 **어느 것도 6/6이 아니다** — 이게 이 표의 요점입니다. 세 방식이 **똑같이 틀리는 한 칸**이 바로 「양쪽에서 같은 엣지 추가」입니다.

## 2. 왜 세 방식 모두 그 한 칸을 틀리는가

상황: A와 B가 동시에 `이서연-속함->결제팀`을 추가합니다. **완전히 같은 엣지**입니다.

세 방식 모두 하는 일은 결국 이겁니다.

```sql
UPDATE ... SET ..., version = version + 1
 WHERE id = ? AND version = ?      -- 내가 읽은 버전 그대로인가
```

A가 먼저 쓰면 버전이 1 → 2로 오릅니다. B는 버전 1을 읽고 왔으니 `WHERE version = 1`이 **0행**을 고칩니다. `rowcount == 0` → 충돌 신호 → B는 재시도하거나 사람에게 넘어갑니다.

문제는 **버전 비교가 "값"을 전혀 안 본다**는 데 있습니다. 버전 비교는 이렇게만 묻습니다.

> "내가 읽은 뒤에 누가 손댔나?"

「손댔나」에 대한 답은 예입니다. 그래서 막습니다. 하지만 정작 물어야 할 것은 이거였습니다.

> "**내가 쓰려는 결과와 지금 상태가 다른가?**"

여기에 대한 답은 아니오입니다. B가 쓰려는 것(`이서연-속함->결제팀`)은 **이미 거기 있습니다**. B의 목적은 이미 달성됐습니다. 그런데 버전이라는 대리 지표(proxy)가 "누가 건드렸다"고 알려주는 바람에, 아무 문제도 없는 상황을 충돌로 보고한 겁니다. 즉 이것도 **가짜 충돌(false conflict)**입니다.

노드 버전이 「한 노드의 다른 엣지」에서 내는 가짜 충돌과 성격은 같습니다. 다만 원인이 다릅니다.

- 노드 버전의 가짜 충돌 → **단위가 너무 굵어서** (겹치지 않는 것을 한 덩어리로 묶음)
- 이번 가짜 충돌 → **단위를 아무리 잘 잡아도 남는다.** 단위 문제가 아니라 **비교 대상 문제**이기 때문. 여기서는 A와 B가 진짜로 같은 단위를 건드린 게 맞다. 단지 결과가 같을 뿐.

그래서 단위를 아무리 정교하게 조정해도 이 칸은 안 고쳐집니다. **다른 종류의 검사를 하나 더 얹어야** 합니다.

## 3. 멱등성이 왜 "같은 결과면 충돌이 아니다"로 이어지는가

### 멱등성의 정의

**멱등(idempotent)**: 한 번 적용한 것과 여러 번 적용한 것의 결과가 같다.

```
f(f(x)) = f(x)
```

21장(프로세스가 죽어도 작업은 살아 있어야 한다)에서 재시도 안전성을 위해 나왔던 개념입니다. 네트워크가 끊겨 응답을 못 받았을 때 그냥 다시 보내도 되게 만드는 성질이죠.

### 정의를 동시성 쪽으로 돌려 읽으면

`SET`(집합에 넣기)은 멱등이고 `INCREMENT`(1 더하기)는 멱등이 아닙니다. 엣지 추가는 **집합에 원소를 넣는 연산**입니다. 그래프에서 같은 엣지가 두 개 존재할 수는 없으니까요. 따라서 엣지 추가는 본질적으로 멱등입니다.

여기서 결정적인 연결고리가 나옵니다.

> **충돌이란 무엇인가? 「두 변경을 둘 다 적용할 수 없는 상태」다.**
> 그런데 A를 적용한 뒤 B를 적용해도 결과가 A만 적용한 것과 같다면 — **둘 다 적용된 것이다.** 잃어버린 갱신(lost update)이 애초에 발생하지 않는다.

31장 1절이 정의한 "잃어버린 갱신"을 다시 보면 명확합니다. 잃어버린 갱신이 **손해**인 이유는 *누군가 의도한 변경이 최종 상태에 반영되지 않기 때문*입니다. 그런데 B의 의도가 이미 최종 상태에 들어 있다면, B가 덮이든 말든 **잃어버린 것이 없습니다**. 손해가 없으면 충돌이 아닙니다.

정리하면 이 사슬입니다.

```
엣지 추가는 멱등이다
  → A 다음에 B를 해도 결과가 안 변한다
  → B의 변경이 사라져도 B의 의도는 살아 있다
  → 잃어버릴 것이 없다
  → 충돌이 아니다
```

**충돌은 "동시에 건드렸는가"가 아니라 "결과가 갈라지는가"로 정의해야 한다** — 이게 이 문항의 핵심 통찰입니다. 버전 비교는 전자를 재고, 멱등 검사는 후자를 잽니다. 전자는 후자의 **보수적 근사치**일 뿐이고, 근사치이기 때문에 이런 가짜 충돌이 남습니다.

## 4. 순서 무관성(commutativity)과의 관계

같이 놓고 봐야 그림이 완성됩니다.

- **멱등성**: `f(f(x)) = f(x)` — **같은 연산을 몇 번 하든** 결과가 같다 (중복 무해)
- **순서 무관성(교환법칙)**: `f(g(x)) = g(f(x))` — **순서를 바꿔도** 결과가 같다 (순서 무해)

31장 도입부가 이렇게 말합니다. "30장은 변경이 순서대로 온다고 가정했습니다. (…) 두 변경이 동시에 오면 순서가 없거든요."

**동시성 제어가 존재하는 이유가 바로 "순서가 결과를 바꾸기 때문"입니다.** 순서가 결과를 안 바꾸면 굳이 순서를 정해줄 필요가 없고, 따라서 막을 필요도 없습니다.

「양쪽에서 같은 엣지 추가」는 두 성질을 **동시에** 만족합니다.

| | A 먼저 | B 먼저 | 결과 |
|---|---|---|---|
| 최종 상태 | 엣지 1개 | 엣지 1개 | **같음** |

- 순서 무관 → 어느 쪽을 먼저 적용해도 같으니 **순서를 정해줄 이유가 없다**
- 멱등 → 두 번 적용해도 같으니 **한쪽을 버릴 이유도 없다**

두 조건이 다 충족되면 남는 결론은 하나입니다. **그냥 둘 다 통과시켜도 된다.** 조정할 것이 아무것도 없으니까요.

반대로 「단일 값 관계」(이서연도 이끔, 김도현도 이끔)를 보면, 나중 것이 앞의 것을 밀어내므로 순서에 따라 팀장이 달라집니다. 순서 무관하지 않으니 **반드시 막아야** 합니다. 논리 단위 방식이 이 칸을 맞히는 이유입니다.

이 관점은 그대로 **CRDT**(Conflict-free Replicated Data Type, 키워드 표에서 [실험] 상태)의 설계 원리로 이어집니다. CRDT는 모든 연산을 **결합·교환·멱등**이 성립하도록 설계해서 충돌 해결 자체를 없애버립니다. 「멱등 검사를 앞에 둔다」는 그 발상을 한 칸만 빌려온 것 — 전부를 CRDT로 만들 필요는 없고, **CRDT처럼 행동하는 연산에 대해서만 우회로를 뚫어주는** 실무 타협입니다.

## 5. 왜 "버전 비교 *전에*"인가

순서가 중요합니다. 뒤에 두면 소용이 없습니다.

```python
def apply_change(conn, change):
    # 1. 멱등 검사 — 값을 본다. 있으면 그대로 성공.
    if already_matches(conn, change):
        return Result.OK          # 버전을 올리지도 않고, 재시도도 없다

    # 2. 그다음에야 버전 비교 — "내가 읽은 뒤에 누가 건드렸나"
    cur = conn.execute(
        "UPDATE ... SET ..., version = version + 1 "
        " WHERE key = ? AND version = ?", (key, read_version))
    if cur.rowcount == 0:
        return Result.CONFLICT    # 진짜 충돌
    return Result.OK
```

- **뒤에 두면**: 이미 `rowcount == 0`으로 충돌 판정이 나고 재시도 루프에 들어간 뒤입니다. 재시도할 때마다 값을 다시 읽어 "어? 이미 같네" 하고 빠져나오긴 하겠지만, 그 사이에 **판단(모델 호출)을 다시 하게 될 수 있습니다**. 예제 3이 지적한 대로 "재시도 한 번에 모델 호출 한 번이 통째로 다시" 드는 최악의 경로죠.
- **앞에 두면**: 값 비교 한 번으로 끝납니다. 버전을 올리지 않으니 **다른 정상 작업의 버전을 무효화하지도 않습니다** — 버전을 괜히 올리면 그것 때문에 또 다른 가짜 충돌이 연쇄로 생깁니다.

또 하나. 멱등 검사는 **"성공"으로 반환해야지 "무시"로 반환하면 안 됩니다.** 호출한 에이전트 입장에서 요청은 실제로 이루어진 것이고 (원했던 엣지가 그래프에 있다), 여기서 실패나 경고를 돌려주면 에이전트가 불필요한 보정 행동을 시작합니다.

Cypher를 쓰는 그래프 DB라면 `MERGE`가 바로 이 성질을 언어 차원에서 제공합니다. `CREATE`는 중복을 만들거나 제약에 걸리지만, `MERGE`는 "있으면 두고 없으면 만든다"입니다. 다만 `MERGE`만으로는 **속성값까지 같은지**는 안 봐주므로, 속성을 함께 쓰는 경우엔 값 비교를 직접 해야 합니다.

## 6. 6/6이 된 뒤의 최종 표

| 경우 | 논리 단위 + 멱등 검사 | 판정 근거 |
|---|---|---|
| 같은 엣지의 속성 | 막음 ○ | 값이 다르다 → 진짜 충돌 |
| 한 노드의 다른 엣지 | 통과 ○ | 단위가 다르다 |
| 단일 값 관계 | 막음 ○ | 「주어+관계 종류」가 같은 단위 |
| 노드 삭제 대 엣지 추가 | 막음 ○ | 노드 삭제는 걸린 엣지 전부와 충돌 |
| 양쪽에서 같은 엣지 추가 | **통과 ○** | **멱등 — 결과가 같다** |
| 서로 다른 방향 | 통과 ○ | 도메인이 대칭 아니면 별개 단위 |
| **맞은 개수** | **6/6** | |

두 겹의 검사가 각각 다른 질문을 맡습니다.

| 검사 | 묻는 것 | 잡아내는 것 |
|---|---|---|
| 멱등 검사 (앞) | 결과가 이미 같은가 | 헛충돌을 걸러낸다 |
| 버전 비교 (뒤) | 내가 읽은 뒤 바뀌었나 | 진짜 잃어버린 갱신을 막는다 |

## 7. 챙길 것

1. **답 한 줄** — 「버전 비교 전에 멱등 검사」. `쓰려는 것 == 이미 있는 것`이면 성공 반환.
2. **왜 멱등이 충돌을 없애나** — 충돌의 손해는 "의도한 변경이 사라지는 것"인데, 결과가 이미 같으면 사라진 의도가 없다. 그래서 충돌이 아니다.
3. **순서 무관성과의 짝** — 멱등은 "중복 무해", 순서 무관은 "순서 무해". 둘 다 성립하면 조정할 것이 없으므로 그냥 통과시켜도 된다. 동시성 제어는 애초에 "순서가 결과를 바꾸는 경우"를 위한 장치다.
4. **버전은 대리 지표다** — 버전 비교는 "결과가 갈라지는가"를 "누가 건드렸는가"로 근사한다. 근사치이므로 가짜 충돌이 남고, 값 비교 한 겹이 그 틈을 메운다.
5. **21장과의 재사용** — 재시도 안전성을 위해 만든 멱등성이 동시성 문제에서 그대로 다시 쓰인다. 28장의 `SINGLE_VALUED` 목록이 논리 단위 정의에 재사용되는 것과 같은 패턴이다. **같은 장치가 두 문제를 푼다.**
