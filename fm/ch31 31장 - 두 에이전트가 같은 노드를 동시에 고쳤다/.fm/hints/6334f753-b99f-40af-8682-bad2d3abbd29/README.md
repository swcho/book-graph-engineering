# 서로 다른 필드를 고쳤는데도 변경이 사라지는 이유

**Q.** 서로 다른 필드를 고쳤는데도 변경이 사라지는 이유는 무엇인가?

**A.** 둘 다 같은 옛 상태를 읽고 각자 자기 필드를 고쳐 **통째로** 썼다. 나중에 쓴 쪽이 앞의 변경을 덮는다.

---

## 1. 직관과 어긋나는 지점

「A는 `팀장`을, B는 `인원`을 고쳤다. 건드린 칸이 다르니 부딪힐 일이 없다」 — 이게 우리가 자연스럽게 하는 생각입니다. 그런데 사라집니다.

핵심은 **무엇을 고쳤느냐가 아니라 무엇을 썼느냐**입니다. 고친 건 필드 하나지만, DB에 쓴 건 레코드 전체(`props` 문자열 전체)입니다. 쓰기 단위가 레코드면, 겹치지 않는 수정도 서로를 덮습니다.

> 「전체를 쓰면 겹치지 않는 변경도 서로를 덮는다.」 (ex1)

## 2. 무슨 일이 벌어지는가 — 읽고 · 판단하고 · 통째로 쓰기

문제의 코드 모양은 늘 셋으로 이뤄집니다.

```python
def naive_update(db, field, value, delay, log):
    """읽고 → 고치고 → 쓴다. 그 사이에 남이 끼어들 수 있다."""
    with LOCK:
        row = db.execute("SELECT props FROM node WHERE id='t1'").fetchone()  # 1. 읽기
    props = parse(row[0])
    time.sleep(delay)                      # 2. 판단하는 시간  ← 여기가 창(window)
    props[field] = value
    with LOCK:
        db.execute("UPDATE node SET props=? WHERE id='t1'", (dump(props),))  # 3. 통째로 쓰기
        db.commit()
```

읽기 한 줄과 쓰기 한 줄은 각각 원자적입니다(`LOCK`이 걸려 있죠). 그런데 **읽기와 쓰기 사이가 안 잠겨 있습니다.** 그 사이의 `sleep(delay)` — 실제로는 모델 호출, API 왕복, 사람의 승인 대기 — 가 바로 남이 끼어들 수 있는 창입니다.

### 시간순으로 따라가기

초기 상태: `팀장=박민수;인원=3`

| 시각 | 에이전트 A (팀장→이서연, 판단 0.20초) | 에이전트 B (인원→5, 판단 0.05초) | DB 상태 |
|---|---|---|---|
| t=0.00 | 읽음 → `팀장=박민수;인원=3` | | `팀장=박민수;인원=3` |
| t=0.02 | (판단 중) | 읽음 → `팀장=박민수;인원=3` | 〃 |
| t=0.07 | (판단 중) | 씀 → `인원=5;팀장=박민수` | `인원=5;팀장=박민수` |
| t=0.20 | 씀 → `인원=3;팀장=이서연` | | `인원=3;팀장=이서연` |

최종: `인원=3;팀장=이서연`. **B의 `인원=5`가 사라졌습니다.**

A가 손에 들고 있던 건 t=0.00 시점의 스냅샷입니다. 거기엔 `인원=3`이 박혀 있죠. A는 `팀장`만 고쳤다고 생각하지만, 실제로 쓴 문자열에는 **낡은 `인원=3`도 같이 실려 있습니다.** 그 낡은 값이 B의 최신 값을 밟고 지나갑니다.

정리하면 원인은 두 조각입니다.

1. **둘 다 같은 옛 상태를 읽었다** — 읽은 시점이 겹쳤다. 그래서 양쪽 스냅샷이 모두 `인원=3, 팀장=박민수`.
2. **각자 자기 필드만 고쳐서 통째로 썼다** — 쓰기 페이로드에 「내가 안 건드린 필드의 낡은 값」이 함께 들어갔다.

이 둘이 만나면 나중에 쓴 쪽이 앞의 변경을 덮습니다. 이걸 **잃어버린 갱신(lost update)** 이라고 부릅니다.

## 3. 이 문제의 진짜 성질 — 조용하다

```
에러가 안 난다. 로그에도 «성공»만 찍힌다. 그게 이 문제의 성질이다.
```

- 예외 안 남
- `UPDATE`는 1행을 정상적으로 고침
- 커밋 성공
- A의 로그: "팀장 변경 완료", B의 로그: "인원 변경 완료" — **둘 다 성공**

나중에 사용자가 「분명히 고쳤는데요」라고 말할 때까지 아무도 모릅니다. 이 장의 제사(題詞)가 그 문장인 이유입니다. 데이터 손실인데 관측 신호가 하나도 없습니다.

## 4. 왜 에이전트 시스템에서 특히 자주 나는가

읽고-쓰기 창의 폭이 문제의 확률을 결정합니다. 에이전트 시스템은 세 가지 이유로 그 창이 넓습니다.

| 이유 | 설명 |
|---|---|
| **판단 시간이 길다** | 읽기와 쓰기 사이에 모델 호출이 들어갑니다. 밀리초가 아니라 초 단위. 창이 1000배 넓어집니다. |
| **동시 실행이 기본이다** | 여러 에이전트를 병렬로 돌리는 게 정상 운영입니다. 겹칠 기회가 상시로 있습니다. |
| **통째로 쓰는 코드를 만들기 쉽다** | 상태 객체를 통으로 읽어 dict를 고치고 통으로 저장하는 코드가 LLM이든 사람이든 제일 자연스럽게 나옵니다. |

그리고 **트랜잭션으로는 못 풉니다.** 트랜잭션 안에 모델 호출을 넣을 수 없고(수 초짜리 트랜잭션은 DB를 죽입니다), 워크플로는 프로세스 경계를 넘어 살아 있어서 애초에 한 트랜잭션에 담기지 않습니다.

## 5. 대응 세 가지

ex1이 제시하는 갈래는 셋입니다.

### 1) 잠금 (비관적)
한 번에 하나만 고치게 막습니다. 확실하지만 느리고 데드락이 납니다. 특히 잠금 안에 모델 호출이 들어가면 최악입니다.

### 2) 낙관적 잠금 — 쓰기 직전에 「안 바뀌었나」 확인
버전 컬럼을 하나 두고, 내가 읽은 버전이 그대로일 때만 씁니다.

```sql
UPDATE node SET props=?, version=version+1
 WHERE id=? AND version=?          -- 이 조건이 전부다
```

중요한 건 **충돌이 에러로 오지 않는다**는 점입니다. `UPDATE`가 **0행**을 고칩니다. 그래서 `cur.rowcount == 1`을 반드시 확인해야 합니다. 안 보면 그냥 성공한 줄 알고 지나갑니다 — 문제의 조용함이 여기서도 반복됩니다.

```python
cur = db.execute(
    "UPDATE node SET props=?, version=version+1 "
    "WHERE id='t1' AND version=?", (dump(d), ver))
db.commit()
if cur.rowcount == 1:
    return True          # 성공
STATS["충돌"] += 1        # 0행 = 충돌 → 다시 읽고 재시도 (지수 백오프 + 흔들기)
```

### 3) 필드 단위 변경 — 통째로 안 쓰고 바뀐 것만 쓴다
읽고-고치고-쓰기 사이에 **판단을 두지 않습니다.** 판단을 먼저 끝내고, 잠금 안에서는 읽기+수정+쓰기만 붙여서 처리합니다.

```python
def field_level(db, field, value, delay):
    """통째로 안 쓰고 «그 필드만» 고친다. 읽고-고치고-쓰기 창이 없다."""
    time.sleep(delay)            # 판단은 잠금 «밖»에서 미리
    with LOCK:
        ... 읽고 그 필드만 고쳐 쓴다 ...
```

가능하면 이게 제일 낫습니다. 다만 「인원이 5 미만이면 한 명 추가」처럼 **읽은 값을 보고 판단해야** 하는 경우엔 못 씁니다. 읽어야 하니까요.

### 실무의 답
```
단순 설정            → 필드 단위
읽고 판단해야 함     → 낙관적 잠금
충돌 잦고 비용 큼    → 비관적 잠금
```
그리고 **판단을 잠금 밖으로 빼는 것**이 공통 요령입니다. ① 잠금 없이 읽고 ② 잠금 없이 모델 부르고 ③ 짧게 잠가서 「버전 확인 + 쓰기」만. 잠금 보유 시간이 12ms에서 1.5ms로 줄고, 창이 좁아지니 충돌률도 같이 떨어집니다.

## 6. 30장과의 연결

30장에서 「전체 상태를 이벤트에 넣지 마라」고 한 이유가 바로 이것입니다. 이벤트든 UPDATE든 **페이로드가 전체 상태이면 겹치지 않는 변경도 서로를 덮습니다.** 델타(무엇이 바뀌었는가)를 실어야 합쳐질 수 있습니다.

## 7. 한 줄 정리

> 충돌은 **고친 필드**가 아니라 **쓴 범위**에서 생긴다. 다른 필드를 고쳤어도 통째로 쓰면 낡은 스냅샷이 남의 최신 값을 덮고, 그 손실은 에러 없이 조용히 지나간다.
