# 필드 단위 수정 — 가장 좋은 이유와 한계

## 질문

필드 단위 수정이 가능하면 가장 좋은 이유와 그 한계는 무엇인가?

## 답

읽기와 쓰기 사이에 판단을 두지 않아 창이 아예 없다. 다만 「읽은 값을 보고 판단해야」 하는 경우엔 쓸 수 없다.

---

## 1. 무엇을 「창(window)」이라고 부르나

잃어버린 갱신(lost update)은 이 세 박자 때문에 생깁니다.

```
읽는다  →  판단한다  →  통째로 쓴다
        ^^^^^^^^^^^
        이 사이가 «창»이다
```

읽은 시점의 값과 쓰는 시점의 값이 달라져 있을 수 있는 구간, 그게 창입니다. 창이 열려 있는 동안 남이 끼어들어 값을 고치면, 내가 나중에 쓰는 「통째로」가 그 사람의 변경을 덮어 버립니다. 에러는 안 납니다. 로그에는 성공만 찍힙니다. 이게 이 문제의 성질입니다.

`ex1_lost_update.py`의 `naive_update`가 정확히 이 모양입니다.

```python
def naive_update(db, field, value, delay, log):
    """읽고 → 고치고 → 쓴다. 그 사이에 남이 끼어들 수 있다."""
    with LOCK:
        row = db.execute("SELECT props FROM node WHERE id='t1'").fetchone()
    props = parse(row[0])
    time.sleep(delay)                      # ← 판단하는 시간 = 창
    props[field] = value
    with LOCK:
        db.execute("UPDATE node SET props=? WHERE id='t1'", (dump(props),))
```

A는 `팀장`만, B는 `인원`만 고치는데도 하나가 사라집니다. **둘 다 같은 옛 상태를 읽었고, 각자 자기 필드를 고친 뒤 전체를 다시 썼기** 때문입니다. 겹치지 않는 변경끼리도 서로를 덮습니다.

## 2. 필드 단위 수정이 왜 「제일 낫다」인가

세 가지 대응이 있습니다.

| 대응 | 창을 어떻게 다루나 | 비용 |
|---|---|---|
| 비관적 잠금 | 창이 열려 있는 내내 남을 막는다 | 잠금 획득 비용 + 대기, 데드락 |
| 낙관적 잠금 | 창은 그냥 두고, 쓰기 직전에 「안 바뀌었나」 확인한다 | 충돌 시 재시도(판단을 다시 함) |
| **필드 단위 수정** | **창 자체를 없앤다** | **없음 — 감지할 충돌이 애초에 안 생긴다** |

앞의 둘은 창이 있다는 걸 전제하고 그 창을 **관리**합니다. 필드 단위 수정은 창을 **제거**합니다. 관리할 게 없으니 버전 컬럼도, 재시도 루프도, 백오프도, 충돌 통계도 필요 없습니다. 가장 좋은 해법이 되는 이유는 「빠르다」가 아니라 **문제가 발생할 구조를 만들지 않는다**는 데 있습니다.

`ex2_optimistic.py`에서 세 방식을 나란히 돌려 보면, 필드 단위만 충돌/재시도가 0인 채로 둘 다 반영에 성공합니다.

```python
def field_level(db, field, value, delay):
    """통째로 안 쓰고 «그 필드만» 고친다. 읽고-고치고-쓰기 창이 없다."""
    time.sleep(delay)                 # ← 판단은 «밖»에서 미리 끝난다
    with LOCK:
        props, _v = db.execute(
            "SELECT props, version FROM node WHERE id='t1'").fetchone()
        d = parse(props)
        d[field] = value              # 읽기-수정-쓰기가 «끊기지 않고» 붙어 있다
        db.execute("UPDATE node SET props=?, version=version+1 "
                   "WHERE id='t1'", (dump(d),))
        db.commit()
```

`naive`와 비교했을 때 코드에서 달라진 것은 딱 하나, **`time.sleep(delay)`(판단)가 읽기 앞으로 나갔다**는 점입니다. 그래서 읽기와 쓰기가 한 덩어리로 붙고, 그 사이에 남이 들어올 틈이 사라집니다.

> 참고: 예제는 sqlite에 props를 한 문자열로 넣은 탓에 파싱-덤프를 다시 하지만, 진짜 필드 단위 수정의 개념적 형태는 「읽지 않고 그 필드만 지정해서 쓴다」입니다. 관계형이면 `UPDATE t SET 인원=5 WHERE id=?`, 그래프면 `SET n.인원 = 5`, 이벤트라면 「인원을 5로 설정」이라는 필드 스코프 이벤트 하나. 30장에서 「전체 상태를 이벤트에 넣지 마라」고 한 것이 같은 이야기입니다.

## 3. 한계 — 「읽은 값을 보고 판단해야」 하면 못 쓴다

필드 단위 수정이 성립하려면 **쓸 값이 현재 값과 무관하게 미리 정해져 있어야** 합니다. 값이 현재 값의 함수라면, 그 현재 값을 읽어야 하고, 읽는 순간 창이 다시 열립니다.

책의 예:

```
「인원이 5 미만이면 한 명 추가」
```

- 「인원을 5로」 → 읽을 필요 없음 → **필드 단위 가능**
- 「인원이 5 미만이면 한 명 추가」 → 현재 인원을 읽어서 조건 판정 → **필드 단위 불가**

읽고 판단해서 쓰는 순간, 그건 정의상 read-modify-write이고 창이 있습니다. 그러면 낙관적 잠금(버전 비교)이나 비관적 잠금으로 넘어가야 합니다.

에이전트 시스템에서 이 한계가 특히 자주 걸립니다. 「현재 팀 상태를 보고 판단해서 고쳐라」가 곧 에이전트의 일이기 때문입니다. 모델 호출이 그 판단이고, 판단이 길수록 창이 넓습니다.

## 4. 그래서 실무에서는 이렇게 나눈다

```
단순 설정            → 필드 단위 수정
읽고 판단해야 함      → 낙관적 잠금 (쓰기 직전 버전 확인, rowcount==0 이면 충돌)
충돌이 잦고 비용이 큼 → 비관적 잠금
```

한 장 요약에 「2번과 3번을 같이 쓰는 게 실무의 답」이라고 적힌 이유가 이것입니다. 필드 단위로 쪼갤 수 있는 것은 전부 쪼개서 창을 없애고, 남는 「진짜 판단이 필요한」 것만 낙관적 잠금으로 처리합니다. 그러면 낙관적 잠금이 감당할 충돌 자체가 줄어듭니다.

## 5. 부분적으로 창을 좁히는 요령 (ex3의 실무 요령)

「읽고 판단해야」 해서 필드 단위를 못 쓰더라도, **판단을 잠금 밖으로 빼는** 것만으로 필드 단위 수정의 이점을 상당 부분 흉내 낼 수 있습니다.

```
1. 읽는다            (잠금 없이)
2. 모델을 부른다      (잠금 없이 — 여기가 제일 길다)
3. 짧게 잠그고 «버전 확인 + 쓰기»만 한다
```

`ex3_lock_contention.py`의 수치로는 잠금을 붙드는 시간이 12ms → 1.5ms로 줄고, 창이 좁아지니 충돌률도 같이 떨어집니다. 낙관적/비관적이 뒤집히는 지점(15~30% 근처)이 오른쪽으로 밀린다는 것도 같은 이야기입니다.

즉 이 장의 축은 하나입니다. **창의 너비를 줄이는 싸움**. 필드 단위 수정은 그 너비를 0으로 만드는 극단이고, 판단을 잠금 밖으로 빼는 것은 그 극단에 가까이 가는 방법입니다.

## 암기 포인트

- **왜 최고인가**: 읽기와 쓰기 사이에 판단이 없다 → 창이 0 → 충돌이 발생할 구조가 없다. (감지·재시도·병합이 전부 불필요)
- **왜 한계인가**: 쓸 값이 「읽은 값의 함수」면 읽어야 하고, 읽는 순간 창이 다시 열린다. 예 — 「인원이 5 미만이면 한 명 추가」.
- 못 쓰는 자리는 낙관적 잠금이 받는다. 그리고 판단은 잠금 밖으로 뺀다.
