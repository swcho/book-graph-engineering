# 트랜잭션으로 이 문제를 풀 수 없는 이유는 무엇인가?

> **답**: 트랜잭션 안에 모델 호출이 들어가고, 워크플로는 프로세스 경계를 넘어 살아 있다.

---

## 무슨 문제였나 — 잃어버린 갱신

31장이 다루는 문제는 **잃어버린 갱신(lost update)** 입니다. 두 에이전트가 같은 노드를 동시에 고칠 때 벌어지는 일이에요.

```
시각  에이전트 A (팀장 수정)          에이전트 B (인원 수정)
----  --------------------------      --------------------------
t0    READ  팀장=박민수;인원=3
t1                                    READ  팀장=박민수;인원=3
t2    (판단 중... 0.20초)
t3                                    (판단 중... 0.05초)
t4                                    WRITE 팀장=박민수;인원=5
t5    WRITE 팀장=이서연;인원=3          ← B의 변경을 덮어씀
----
최종  팀장=이서연;인원=3               인원 변경이 사라졌다
```

두 사람이 **서로 다른 필드**를 고쳤는데도 하나가 사라집니다. 원인은 `읽고 → 판단하고 → 통째로 쓰기` 사이에 틈이 있고, 그 틈에 남이 끼어들었기 때문이에요. 그리고 이게 이 문제의 성질인데, **에러가 나지 않습니다.** 양쪽 로그 모두 「성공」으로 찍힙니다. (`ex1_lost_update.py`)

## 자연스러운 첫 반응: "트랜잭션 쓰면 되잖아요?"

DB를 좀 다뤄 본 사람이라면 여기서 바로 이렇게 말합니다.

```sql
BEGIN;
  SELECT props FROM node WHERE id = 't1';   -- 읽고
  -- ... 판단하고 ...
  UPDATE node SET props = ? WHERE id = 't1'; -- 쓴다
COMMIT;
```

`SERIALIZABLE` 격리 수준까지 올리면 DB가 알아서 잃어버린 갱신을 막아 줍니다. 실제로 관계형 DB의 세계에서는 이게 정답에 가까워요. 그런데 **에이전트 시스템에서는 이 방법이 통하지 않습니다.** 이유가 두 가지입니다.

---

## 이유 1 — 트랜잭션 안에 모델 호출이 들어간다

위 코드의 `-- ... 판단하고 ...` 자리에 무엇이 들어가는지 보세요. 에이전트 시스템에서 그 자리는 **LLM 호출**입니다.

```python
with db.transaction():                       # 트랜잭션 시작
    node = db.read("t1")                     # 읽기
    decision = llm.complete(prompt(node))    # ← 여기가 문제. 수 초
    db.write("t1", apply(node, decision))    # 쓰기
# 트랜잭션 커밋
```

무엇이 잘못됐는지 하나씩 봅시다.

### 트랜잭션을 붙드는 시간이 폭발한다

DB 트랜잭션의 대전제는 **짧다**는 것입니다. 밀리초 단위로 열고 닫는다는 가정 위에 잠금 관리자, 커넥션 풀, MVCC 정리(vacuum) 같은 것들이 설계돼 있어요. 그런데 모델 호출은 짧으면 1~2초, 길면 수십 초입니다. 최소 1000배 차이입니다.

그 사이 벌어지는 일:
- 그 커넥션이 풀에서 계속 묶여 있습니다. 동시 사용자 수만큼 커넥션이 필요해지고 풀이 금방 마릅니다.
- 잠긴 행에 접근하는 다른 모든 작업이 줄을 섭니다. 대기열이 길어지면 대기 시간은 선형이 아니라 **급격히** 늘어납니다(M/M/1 근사).
- 트랜잭션 타임아웃(보통 30초~수 분)에 걸려 그냥 실패합니다.
- PostgreSQL이라면 오래된 스냅샷이 살아 있어서 `VACUUM`이 죽은 튜플을 못 치웁니다. 테이블이 부풀어요.

31장 `ex3_lock_contention.py`가 이 이야기를 숫자로 합니다.

```
낙관적 = N × (1/(1-p)) × (판단 + 쓰기)
비관적 = N × (판단 + 쓰기 + 잠금획득) + N × p × 대기
```

> **판단 시간이 길수록 낙관적이 불리하다. 재시도할 때 판단을 다시 하니까.**
> **그래서 «에이전트가 모델을 부르는» 구간이 잠금 안에 있으면 최악이다.**
> **재시도 한 번에 모델 호출 한 번이 통째로 다시 든다.**

낙관적 잠금이면 충돌 때마다 모델을 다시 부릅니다 — 토큰 비용이 그대로 곱해집니다. 비관적 잠금이면 남들이 그 몇 초를 통째로 기다립니다. 어느 쪽이든 손해예요.

### 롤백이 모델 호출을 되돌려 주지 않는다

트랜잭션의 핵심 계약은 **원자성**입니다. 실패하면 없던 일이 됩니다. 그런데 트랜잭션 안에서 일어난 외부 부수 효과는 롤백 대상이 아니에요.

- 이미 쓴 토큰 비용은 환불되지 않습니다.
- 모델이 도구를 불러서 외부 API를 건드렸다면 그것도 안 돌아옵니다.
- 즉 **트랜잭션 경계와 부수 효과 경계가 어긋납니다.** ACID가 지켜 주는 범위 밖에 진짜 비용이 있어요.

이건 22장의 「되돌릴 수 없는 일을 되갚는 법」과 이어지는 이야기입니다. 되돌릴 수 없는 일은 트랜잭션이 아니라 보상(compensation)으로 다뤄야 합니다.

### 게다가 결정적이지 않다

트랜잭션 재시도(직렬화 실패 후 재실행)의 전제는 **같은 입력이면 같은 판단**이라는 것입니다. 모델은 그 전제를 지키지 않아요. 재시도한 트랜잭션이 처음과 다른 결정을 내릴 수 있습니다. 「재시도해도 안전하다」는 보장이 깨집니다.

## 이유 2 — 워크플로가 프로세스 경계를 넘어 살아 있다

DB 트랜잭션은 **하나의 커넥션, 하나의 프로세스, 하나의 연속된 시간** 안에서만 존재합니다. 프로세스가 죽으면 트랜잭션도 죽습니다(롤백). 커넥션이 끊기면 끝입니다.

그런데 에이전트 워크플로의 생명 주기는 완전히 다릅니다.

| | DB 트랜잭션 | 에이전트 워크플로 |
|---|---|---|
| 수명 | 밀리초 ~ 초 | 분 ~ 시간 ~ 며칠 |
| 경계 | 한 커넥션 | 여러 프로세스·워커·서버 |
| 중단 | 곧 롤백 | 체크포인트 후 다른 워커가 이어받음 |
| 대기 | 없음 (있으면 사고) | 사람 승인, 외부 이벤트, 예약 실행 |
| 재시작 | 처음부터 다시 | 저장된 상태에서 재개 |

구체적인 장면들:

- **사람이 끼어드는 지점**(23장). 「이 변경 승인해 주세요」를 띄우고 사람이 답할 때까지 기다립니다. 그 사이 프로세스는 살아 있을 이유가 없어요. 트랜잭션을 열어 둔 채 사람을 기다린다? 불가능합니다.
- **재개(resume)**. 워커가 죽어도 작업은 살아 있어야 합니다(21장). 워크플로 엔진이 상태를 저장하고 다른 워커가 이어받아요. 그런데 트랜잭션 핸들은 직렬화해서 넘길 수 있는 물건이 아닙니다. 커넥션에 묶인 서버 측 상태거든요.
- **분산 실행**. 워크플로의 단계 1은 A 서버, 단계 3은 B 서버에서 돌 수 있습니다. 「읽기」와 「쓰기」가 아예 다른 프로세스에서 일어납니다.
- **큐를 경유**. 단계 사이에 메시지 큐가 끼면 그 지점에서 프로세스 경계가 확실히 끊어집니다.

읽기와 쓰기 사이에 프로세스가 바뀌는데, 그 둘을 한 트랜잭션으로 묶는다는 말 자체가 성립하지 않습니다.

## 그럼 무엇을 해야 하나

31장의 처방은 **트랜잭션을 짧게 자르고, 그 짧은 트랜잭션 안에서 「안 바뀌었나」만 확인**하는 것입니다. 낙관적 잠금이에요.

```python
# 1. 읽는다 (잠금 없이, 짧은 트랜잭션)
props, ver = read("t1")

# 2. 모델을 부른다 (트랜잭션 밖 — 여기가 제일 길다)
#    프로세스가 죽어도, 며칠이 걸려도 상관없다
decision = llm.complete(prompt(props))

# 3. 짧게 잠그고 «버전 확인 + 쓰기»만 한다
cur = db.execute(
    "UPDATE node SET props=?, version=version+1 "
    "WHERE id='t1' AND version=?", (new_props, ver))
if cur.rowcount == 0:
    retry()          # 그 사이 누가 고쳤다
```

핵심은 **`version` 이라는 값 하나가 트랜잭션이 제공하던 「일관성」을 프로세스 밖으로 들고 나갈 수 있는 형태로 바꿔 준다**는 점입니다. 버전 번호는 그냥 정수라서 직렬화해서 큐에 넣을 수도, 파일에 적을 수도, 다른 서버에 넘길 수도 있어요. 트랜잭션 핸들은 못 하는 일입니다.

이걸 **비교 후 교체(compare-and-swap)** 라고 부릅니다. 원자적 CPU 명령에서 온 이름이고, 여기서는 SQL의 `WHERE version = ?` 한 줄이 그 역할을 합니다.

한 가지 함정: **충돌은 에러로 오지 않습니다.** `UPDATE`가 예외를 던지는 게 아니라 조용히 **0행을 고칩니다.** 그래서 반드시 `rowcount`를 봐야 해요. 안 보면 잃어버린 갱신이 그대로 재현됩니다.

`ex3`의 결론도 같은 방향입니다.

> 판단을 잠금 «밖»으로 빼면 둘 다 좋아진다.
> 그러면 잠금을 붙드는 시간이 12ms 에서 1.5ms 로 준다.
> 충돌률도 같이 떨어진다. 창이 좁아지니까.

## 정리 — 두 이유를 한 문장씩

| | 왜 트랜잭션이 안 되나 |
|---|---|
| **모델 호출이 안에 있다** | 트랜잭션은 밀리초를 가정하는데 모델은 수 초가 걸린다. 커넥션이 마르고 대기열이 터진다. 롤백해도 토큰 비용과 외부 부수 효과는 안 돌아온다. 재시도해도 같은 답이 나온다는 보장이 없다. |
| **워크플로가 프로세스를 넘는다** | 트랜잭션은 한 커넥션·한 프로세스 안에서만 산다. 워크플로는 사람 승인을 기다리고, 워커가 죽어도 재개되고, 큐를 건너고, 여러 서버에 걸친다. 읽기와 쓰기가 다른 프로세스에서 일어나는데 한 트랜잭션으로 묶을 수가 없다. |

그리고 대안 한 줄: **버전 번호를 들고 나가서, 쓰기 직전에 짧은 트랜잭션으로 「안 바뀌었나」만 확인한다.**
