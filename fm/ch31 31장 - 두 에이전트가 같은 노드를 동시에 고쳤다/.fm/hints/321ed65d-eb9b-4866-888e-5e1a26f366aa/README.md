# 충돌 감지와 충돌 해결은 각각 어떤 성격의 문제인가?

> **답**: 감지는 기술 문제라 일반 해법이 있고, 해결은 도메인 문제라 일반 해법이 없다.

출처: 31장 「두 에이전트가 같은 노드를 동시에 고쳤다」 — 31.4절 *감지한 다음이 진짜 문제다*, 예제 `ex5_merge_strategy.py`

---

## 한 줄로

**「부딪혔다」를 아는 것은 코드가 대신해 줄 수 있지만, 「그래서 어느 쪽이 맞나」는 코드가 대신해 줄 수 없다.**

---

## 1. 왜 이 둘을 갈라서 봐야 하나

동시 수정 문제는 보통 한 덩어리로 뭉뚱그려 「동시성 처리」라고 부릅니다. 그런데 실제로 시스템을 만들어 보면 이건 성질이 완전히 다른 두 단계입니다.

| | 감지(detection) | 해결(resolution) |
|---|---|---|
| 묻는 질문 | 「내가 읽은 뒤에 누가 손댔나?」 | 「A와 B 중 무엇을 남길까? 혹은 어떻게 합칠까?」 |
| 성격 | **기술 문제** | **도메인 문제** |
| 정답의 소재 | 데이터베이스·프로토콜 안에 있다 | 업무 규칙·사람의 의도 안에 있다 |
| 재사용 | 도메인이 바뀌어도 그대로 쓴다 | 필드 하나 바뀌면 다시 정해야 한다 |
| 라이브러리화 | 된다 (버전 칼럼, CAS, ETag) | 안 된다 (매번 직접 정의) |
| 틀렸을 때 | 에러가 나거나 0행이 갱신된다 → **보인다** | 조용히 잘못된 값이 저장된다 → **안 보인다** |

이 구분이 중요한 이유는 **투자할 곳이 다르기** 때문입니다. 감지는 한 번 제대로 짜 두면 끝납니다. 해결은 시스템이 사는 내내 계속 손봐야 하는 부분이고, 여기에 시간을 안 쓰면 「마지막이 이긴다」로 흘러가서 조용히 데이터가 망가집니다.

## 2. 감지가 기술 문제인 이유 — 일반 해법이 존재한다

감지는 도메인을 몰라도 됩니다. 필드가 팀장이든 인원이든 태그든 상관없이, 답해야 할 질문은 딱 하나입니다.

> 「내가 읽은 그 시점 이후로 이 대상이 바뀌었는가?」

이 질문은 도메인 지식 없이 순수하게 기계적으로 답할 수 있습니다. 그래서 표준화된 해법이 이미 여러 개 있습니다.

### 낙관적 잠금 (optimistic locking)

버전 칼럼 하나를 두고, 쓸 때 그 버전이 그대로인지 조건에 넣습니다.

```sql
UPDATE node SET props = ?, version = version + 1
 WHERE id = ? AND version = ?     -- ← 이 조건이 감지의 전부다
```

버전이 바뀌었으면 이 UPDATE는 **0행**을 고칩니다. 그게 충돌 신호입니다.

여기서 실무 함정 하나. **충돌은 예외로 오지 않고 `rowcount == 0`으로 옵니다.** 예외 처리만 해 두고 `rowcount`를 안 보면 충돌을 통째로 못 봅니다. 로그에는 「성공」만 찍히고요. 31장 전반부의 「에러 없이 변경이 사라진다」가 바로 이 이야기입니다.

```python
cur = db.execute(
    "UPDATE node SET props=?, version=version+1 "
    "WHERE id='t1' AND version=?", (dump(d), ver))
db.commit()
if cur.rowcount == 1:
    return True          # 성공
STATS["충돌"] += 1        # 0행 = 충돌. 다시 읽고 재시도
```

### 같은 아이디어의 다른 얼굴들

- **비교 후 교체(CAS, compare-and-swap)** — CPU 원자 연산 수준의 같은 패턴. 「기대값과 같으면 바꾼다」
- **HTTP ETag / If-Match** — 웹 API에서의 같은 패턴. 다르면 `412 Precondition Failed`
- **비관적 잠금** — 아예 먼저 잠가서 충돌 자체를 안 생기게 한다
- **직렬화 가능(serializable) 격리 수준** — DB가 대신 감지해 주고 한쪽을 abort시킨다

전부 도메인과 무관합니다. 어느 회사, 어느 업무에 갖다 놔도 똑같이 동작합니다. **그래서 라이브러리·프레임워크·DB 기능으로 제공됩니다.** 이게 「일반 해법이 있다」의 의미입니다.

### 그래프에서는 감지도 한 겹 어렵다 — 그래도 여전히 기술 문제

31.3절이 다루는 부분입니다. 관계형 DB에서는 「행 하나」가 충돌 단위라 명확한데, 그래프에서는 **버전을 어디에 둘지부터** 정해야 합니다.

- **노드 버전** → 같은 노드에 서로 다른 엣지를 다는 것도 부딪힙니다. **가짜 충돌**이 납니다.
- **엣지 버전** → `이서연-이끔->결제팀`과 `김도현-이끔->결제팀`은 다른 엣지라 둘 다 통과합니다. 팀장이 둘이 됩니다. **단일 값 누락**이 납니다.
- **논리 단위(「주어 + 관계 종류」)** → 6개 시나리오 중 5개를 맞춥니다. 남은 하나(양쪽에서 같은 엣지 추가)는 버전 비교 **앞에 멱등 검사**를 두면 6/6이 됩니다.

여기서 주목할 점: **단위를 어디에 둘지는 어렵지만, 그래도 여전히 「한 번 정하면 코드로 굳어지는」 문제**입니다. `SINGLE_VALUED` 목록 같은 걸 코드에 갖고 있으면 그 뒤로는 기계적으로 돕니다. 그래서 이 어려움조차 감지 쪽, 즉 기술 문제 편에 속합니다.

## 3. 해결이 도메인 문제인 이유 — 일반 해법이 없다

이제 「부딪혔다」를 알았습니다. 그다음에 무엇을 할까요? 여기서 딱 막힙니다. **답이 데이터 안에 없기 때문입니다.**

`ex5_merge_strategy.py`의 충돌 5건을 보면 왜 그런지 바로 보입니다.

| 필드 | 종류 | 원래 | A (출처) | B (출처) |
|---|---|---|---|---|
| 팀장 | 단일값 | 박민수 | 이서연 (hr-sync) | 김도현 (agent-4821) |
| 인원 | 수치 | 3 | 5 (batch) | 4 (agent-5102) |
| 태그 | 집합 | 결제 | 결제,정산 (user) | 결제,신규 (agent-4821) |
| 설명 | 자유문 | 이전 설명 | 새 설명 A (user) | 새 설명 B (user) |
| 폐쇄일 | 단일값 | (없음) | 2026-06-30 (admin) | (없음) (agent-5102) |

**필드마다 「맞게 합치는 방법」이 전부 다릅니다.**

- **태그(집합)** → 합집합이 자연스럽습니다. `결제,정산 ∪ 결제,신규 = 결제,신규,정산`
- **인원(수치)** → 합집합은 말이 안 됩니다. 변화량을 더할 수는 있습니다. `(+2) + (+1) = +3` → 6
- **팀장(단일값)** → 합칠 수가 없습니다. 하나를 골라야 합니다. 무엇을 근거로?
- **설명(자유문)** → **애초에 자동으로 못 합칩니다.** 두 문단을 이어 붙이면 문서가 망가집니다.

집합에 쓰는 규칙을 수치에 쓰면 틀리고, 수치에 쓰는 규칙을 자유문에 쓰면 재앙입니다. **모든 필드에 통하는 하나의 규칙이 없다는 것** — 이게 「일반 해법이 없다」의 정확한 의미입니다.

### 네 가지 전략과 각각의 대가

`ex5`는 같은 5건에 전략 넷을 적용해 보여 줍니다.

| 전략 | 자동 해결 | 무엇을 얻고 무엇을 잃나 |
|---|---|---|
| 마지막이 이긴다 | 5/5 | 전부 자동. **그리고 전부 틀릴 수 있다.** 에이전트가 팀장을 정하고, 사용자 설명을 다른 사용자가 덮는다 |
| 출처 등급 | 4/5 | 사람 > 동기화 > 배치 > 에이전트 순. 남는 건 「설명」 — 둘 다 `user`라 등급이 같다. 이건 사람이 보는 게 맞다 |
| 종류를 보고 | 4~5/5 | **제일 낫다.** 집합은 합치고, 수치는 변화량을 더하고, 나머지는 출처 등급으로 넘긴다 |
| 전부 사람에게 | 0/5 | 절대 안 틀리지만 사람이 다 본다. 규모가 커지면 무너진다 |

「마지막이 이긴다」가 위험한 이유가 여기서 드러납니다. **자동 해결률 100%는 좋아 보이지만, 그건 「생각하기를 그만뒀다」는 뜻**이지 「잘 풀었다」가 아닙니다.

### 자동 병합의 함정 — 「인원 = 6」

가장 날카로운 대목입니다. 변화량 합산을 쓰면 인원이 **6**이 됩니다.

> **양쪽 누구도 6을 쓰려고 하지 않았습니다.**

- A는 5를 원했고, B는 4를 원했는데, 시스템은 6을 저장합니다.
- **맞을 수도 있습니다.** 「두 명 늘었고 한 명 늘었다」면 실제로 세 명 늘어서 6이 맞습니다.
- **틀릴 수도 있습니다.** 둘 다 「같은 사실」을 보고 각자 다르게 센 것이면 6은 완전히 헛것입니다.

**어느 쪽인지는 데이터를 아무리 들여다봐도 알 수 없습니다.** 「이 필드는 독립적인 증분인가, 아니면 현재 값을 다시 센 결과인가」 — 이건 도메인 지식입니다. 사람만 답할 수 있습니다.

- 변화량 합산이 **맞는** 것: 장바구니 담기, 재고 차감, 좋아요 수 (독립적인 증분)
- 변화량 합산이 **틀린** 것: 「현재 팀 인원을 세어 봤더니 5명」 (현재 값의 재측정)

같은 정수 필드인데 성격이 정반대입니다. 코드는 이 차이를 볼 수 없습니다.

## 4. 그래서 실무에서 어떻게 하나

### (1) 감지는 인프라로, 해결은 정책으로

감지는 프레임워크·DB 기능에 맡기고 한 번 제대로 깔아 둡니다. 해결은 **필드마다 「이건 어떻게 합칠까」를 명시적으로 선언한 표**를 코드로 갖고 있어야 합니다.

```python
MERGE_POLICY = {
    "태그":   "집합_합집합",
    "인원":   "변화량_합산",     # ← 독립 증분일 때만! 주석 필수
    "팀장":   "출처_등급",
    "설명":   "사람_확인",       # 자유문은 자동 병합 금지
}
```

### (2) 「못 정하면 사람에게」를 기본값으로

이 표에 안 적힌 필드가 나왔을 때 무엇을 할지를 정해 둬야 합니다. **모르면 사람에게 보내는 것**이 안전한 기본값입니다. 「모르면 나중 것으로」는 조용히 데이터를 갉아먹습니다.

### (3) 자동 병합의 오류율을 재라

31장 요약의 마지막 줄이 이 얘기입니다.

> 자동 병합의 오류율을 재세요. 안 재면 「사람 일이 줄었다」만 보고 「조용히 틀린 것」을 못 봅니다.

자동 해결률(사람 일이 얼마나 줄었나)은 재기 쉽습니다. 대시보드에도 잘 올라갑니다. 그런데 **자동 병합 오류율**(자동으로 처리한 것 중 실제로는 틀렸던 비율)은 안 재면 절대 안 보입니다. 표본을 뽑아 사람이 검수하는 절차가 있어야 합니다.

이건 해결이 도메인 문제라는 사실의 직접적인 결과입니다. 감지는 틀리면 티가 나지만(에러, 0행), 해결은 틀려도 티가 안 납니다. 그래서 **측정을 따로 붙여야** 합니다.

### (4) 판단을 잠금 밖으로 빼라 (감지 쪽 요령)

에이전트 시스템에서 특히 중요합니다. 재시도 한 번에 모델 호출이 통째로 다시 듭니다.

1. 읽는다 (잠금 없이)
2. 모델을 부른다 (잠금 없이 — 여기가 제일 길다)
3. 짧게 잠그고 **버전 확인 + 쓰기**만 한다

잠금 보유 시간이 12ms에서 1.5ms로 줄고, 창이 좁아지니 충돌률도 같이 떨어집니다. 낙관적/비관적의 갈림길(15~30%)이 오른쪽으로 밀립니다.

## 5. 흔한 오해

| 오해 | 바로잡기 |
|---|---|
| 「CRDT를 쓰면 해결도 자동으로 된다」 | CRDT는 **수렴을 보장할 뿐** 「업무적으로 옳은 값」을 보장하지 않습니다. 합쳐진 결과가 도메인상 말이 되는지는 여전히 사람이 정의해야 합니다. CRDT는 「어떻게 합칠지」를 자료구조 설계 시점으로 **앞당길** 뿐, 도메인 판단을 없애지 못합니다 |
| 「트랜잭션을 쓰면 다 해결된다」 | 트랜잭션은 감지 쪽 도구입니다. 그리고 에이전트 시스템에서는 트랜잭션 안에 모델 호출이 들어가고 워크플로가 프로세스 경계를 넘어 살아 있어서 애초에 잘 안 맞습니다 |
| 「자동 해결률이 높을수록 좋다」 | 「마지막이 이긴다」가 5/5입니다. 자동 해결률만 보면 최고 점수인데 전부 틀릴 수 있습니다. **오류율과 같이 봐야** 의미가 있습니다 |
| 「감지가 어려운 부분이다」 | 감지는 이미 풀린 문제입니다. 남의 코드를 갖다 쓰면 됩니다. 진짜 시간이 드는 건 해결 정책을 정하는 쪽입니다. 31.4절 제목이 「감지한 **다음**이 진짜 문제다」인 이유입니다 |

## 6. 한 문장 암기

> **감지는 「누가 손댔나」 — 도메인을 몰라도 답할 수 있어 라이브러리로 온다. 해결은 「어느 쪽이 맞나」 — 도메인을 알아야 답할 수 있어 매번 직접 정해야 하고, 못 정하면 사람에게 보낸다.**

## 관련 장

- **21장 멱등성** — 「양쪽에서 같은 엣지 추가」를 통과시키려면 버전 비교 앞에 멱등 검사가 필요합니다
- **28장 단일 값 관계** — `SINGLE_VALUED` 목록이 여기서 다시 쓰입니다. 같은 목록이 두 문제를 풉니다
- **30장 변경 이력** — 「전체 상태를 이벤트에 넣지 마라」. 통째로 쓰면 겹치지 않는 변경도 서로를 덮습니다
- **32장 스키마 변경** — 이 장은 「스키마가 그대로」를 가정했습니다. 필드 자체가 바뀌면 그건 다음 장 이야기입니다
