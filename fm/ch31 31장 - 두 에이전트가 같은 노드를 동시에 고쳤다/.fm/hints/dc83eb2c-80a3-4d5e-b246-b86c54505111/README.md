# 하나의 목록, 두 개의 관심사

> **Q.** 28장의 SINGLE_VALUED 목록이 31장에서 다시 쓰이는 이유는 무엇인가?
>
> **A.** 쓰기 관문의 단일 값 검사와 동시성 충돌 단위 판정이 같은 목록으로 해결된다.

---

## 30초 요약

`SINGLE_VALUED`는 「이 관계 종류는 한 주체당 값이 하나뿐이다」는 **기수(cardinality) 선언**입니다. 그런데 이 한 줄의 선언이 서로 다른 두 곳에서 동시에 필요해집니다.

| | 28장 — 쓰기 관문 | 31장 — 동시성 제어 |
|---|---|---|
| 관심사 | **유효성 검사** | **충돌 감지** |
| 묻는 질문 | 「이 값을 지금 넣어도 되나?」 | 「무엇을 한 충돌 단위로 볼까?」 |
| 시간축 | 한 시점의 상태 | 두 시점 사이의 변화 |
| 실패 모습 | 오염된 사실이 들어온다 | 잃어버린 갱신 / 불변식 파괴 |
| 필요한 정보 | **`이끔`은 단일 값인가?** | **`이끔`은 단일 값인가?** |

마지막 줄이 이 카드의 전부입니다. **묻는 질문은 다른데 답을 얻으려면 똑같은 사실이 필요합니다.** 그래서 목록이 재사용되는 게 아니라, **애초에 같은 사실을 두 번 쓰는 것**입니다.

핵심 문장은 ex4의 마지막 두 줄입니다.

> 「이 표를 코드로 갖고 있어야 한다. 28장의 SINGLE_VALUED 목록이 여기서 다시 쓰인다. **같은 목록이 두 문제를 푼다.**」

---

## 1. 28장에서 이 목록이 하던 일 — 유효성 검사

28장의 쓰기 관문은 넷입니다. 확신도 → 정규화 → 스키마 → 단일 값(→ 중복). 각각 다른 것을 잡습니다.

```python
SINGLE = {"이끔"}          # 팀장은 한 명

    # 4) 단일 값 — 이미 다른 값이 있나
    if k in SINGLE:
        r = c.execute("MATCH (a:N {name:$s})-[e:R {kind:$k}]->(b:N) "
                      "RETURN b.name", {"s": s, "k": k})
        while r.has_next():
            if r.get_next()[0] != o:
                return False, "4.단일값충돌"
```

이 관문이 왜 따로 필요했는지가 중요합니다. `박민수-이끔->정산팀`(0.87)은

- 확신도 관문 → **통과** (0.87 > 0.65)
- 스키마 관문 → **통과** (`("이끔", "Person", "Team")` ∈ ALLOWED)
- 단일 값 관문 → **막힘** (박민수는 이미 결제팀을 이끄는 중)

앞의 두 관문이 못 잡는 이유는 명확합니다. **이 트리플 하나만 놓고 보면 아무 문제가 없기 때문입니다.** 위반은 이 트리플과 *이미 있는 다른 트리플* 사이에 있습니다. 「단독으로는 정상인데 함께 있으면 위반」 — 이 성질을 기억해 두세요. 31장에서 그대로 반복됩니다.

---

## 2. 31장에서 같은 목록이 하는 일 — 충돌 단위 판정

31.3절의 문제는 「그래프에서 낙관적 잠금의 **버전을 어디에 붙일 것인가**」입니다. 세 후보의 성적표가 ex4에 있습니다.

| 경우 | 노드 버전 | 엣지 버전 | 논리 단위 | 원하는 것 |
|---|---|---|---|---|
| 같은 엣지의 속성 | 막음 | 막음 | 막음 | 막음 |
| 한 노드의 다른 엣지 | 막음 ✗ | 통과 | 통과 | 통과 |
| **단일 값 관계** | 막음 | **통과 ✗** | 막음 | **막음** |
| 노드 삭제 대 엣지 추가 | 막음 | 통과 ✗ | 막음 | 막음 |
| 양쪽에서 같은 엣지 추가 | 막음 ✗ | 막음 ✗ | 막음 ✗ | 통과 |
| 서로 다른 방향 | 막음 ✗ | 통과 | 통과 | 도메인이 정함 |
| **맞은 개수** | 2/6 | 4/6 | **5/6** | |

문제의 행은 「단일 값 관계」입니다.

- `이서연-이끔->결제팀`을 만드는 A와 `김도현-이끔->결제팀`을 만드는 B가 동시에 돕니다.
- 엣지 버전을 쓰면 **서로 다른 두 엣지**라 버전이 따로입니다. 둘 다 `rowcount == 1`로 성공합니다.
- 결과: 결제팀 팀장이 두 명. 에러 없음, 로그에는 성공만.

여기서 31장이 내린 결론이 이겁니다.

```
단일 값 관계 → 「주어 + 관계 종류」를 한 단위로 본다
다중 값 관계 → 엣지 하나가 한 단위
노드 삭제   → 그 노드에 걸린 모든 엣지와 충돌
```

**첫 줄을 실행하려면 「어느 관계가 단일 값인가」를 알아야 합니다.** 그 목록이 이미 28장에 있습니다. `SINGLE_VALUED`가 곧 **「엣지 하나를 충돌 단위로 삼으면 안 되는 관계 목록」**입니다.

## 3. 왜 이게 우연이 아닌가 — 같은 구조의 두 그림자

두 문제가 겉보기엔 전혀 다릅니다. 하나는 추출기 품질 문제고, 하나는 스레드 경쟁 문제입니다. 부(部)도 다릅니다(5부 vs 6부). 그런데 밑바닥 구조가 같습니다.

**단일 값 제약은 「엣지 하나」에 들어가지 않는 불변식입니다.**

- `이서연-이끔->결제팀` — 그 자체로 정상
- `김도현-이끔->결제팀` — 그 자체로 정상
- 둘이 **동시에 존재할 때만** 위반

이 「여러 엣지에 걸친 불변식」이라는 성질이 두 문제를 한꺼번에 만들어 냅니다.

| | 28장이 겪는 형태 | 31장이 겪는 형태 |
|---|---|---|
| 무엇과 겹치나 | **이미 저장된** 다른 엣지 | **동시에 쓰이는** 다른 엣지 |
| 그래서 필요한 것 | 쓰기 전에 형제 엣지를 **조회**해야 한다 | 형제 엣지들을 **한 단위로 묶어야** 한다 |
| 못 하면 | 팀장이 둘인 그래프 | 팀장이 둘인 그래프 |

마지막 줄을 보세요. **깨지는 불변식이 글자 그대로 같습니다.** 침해 경로만 두 개인 것이죠. 하나는 시간축이 없는 침해(이미 있는 것과 부딪힘)고, 하나는 시간축이 있는 침해(동시에 들어옴)입니다.

> 「팀장은 한 명」이라는 **도메인 사실 하나**가 있고, 그 사실을 지키는 코드가 시스템에 두 군데 필요합니다. 사실이 하나면 그 사실의 선언도 하나여야 합니다.

그리고 28장의 관문 4번이 사실은 **동시성이 없는 세상의 낙관적 잠금**이라는 것도 보입니다. 「쓰기 전에 형제를 확인한다」는 구조가 「쓰기 전에 버전을 확인한다」와 같은 모양이고, 실제로 28장의 관문 코드는 조회와 쓰기 사이에 창(window)이 열려 있어서 **31장의 방법 없이는 그 관문 자체가 동시 실행에서 샙니다.**

## 4. 설계 관점 — 선언과 집행을 분리한다

이 카드의 진짜 교훈은 「목록을 재사용하자」가 아니라 **스키마 선언과 그 집행 지점을 분리하라**는 것입니다.

```
        ┌──────────────────────────────┐
        │  SINGLE_VALUED = {"이끔", …} │   ← 선언 (도메인 사실, 한 곳)
        └───────────┬──────────────────┘
                    │
        ┌───────────┴───────────┐
        ▼                       ▼
  28장 쓰기 관문           31장 충돌 단위
  「형제 엣지 조회해서       「(제약 쪽 + 관계 종류)를
    다른 값이 있나」          버전 행으로 묶는다」
        │                       │
        ▼                       ▼
   유효성 검사 (관심사 A)   동시성 제어 (관심사 B)
```

여기서 지켜야 할 성질이 셋입니다.

**1) 선언은 하나, 집행은 여럿.**
`SINGLE_VALUED`는 「무엇이 참인가」만 말합니다. 「그래서 어떻게 막을 것인가」는 각 집행 지점이 알아서 정합니다. 관문은 조회로 막고, 동시성 제어는 버전 행으로 막습니다. 선언에는 잠금이나 버전 이야기가 한 글자도 없어야 합니다.

**2) 목록을 복사하면 반드시 갈라진다.**
두 문제를 따로 풀면 목록이 두 벌 생깁니다. 어느 날 `보고선`을 단일 값으로 추가하면서 28장 목록에만 넣으면, **추출은 막히는데 동시 쓰기는 새는 상태**가 됩니다. 그리고 이 어긋남은 조용합니다. 배포 시점엔 아무 일도 안 일어나고, 한참 뒤에 「보고선이 둘인 사람」이 나옵니다. 어긋난 시점과 증상이 나타난 시점 사이가 멀어서 원인 추적이 아주 비쌉니다.

**3) 기수는 온톨로지의 사실이지 코드 경로의 설정이 아니다.**
「팀장은 한 명」은 파이썬 딕셔너리의 속성이 아니라 조직이라는 도메인의 속성입니다. 12장~13장에서 온톨로지와 검증 이야기를 한 이유가 이겁니다. 도메인 사실은 **모델 쪽에 한 번 적고**, 코드는 그걸 읽어 가는 소비자여야 합니다. 성숙한 시스템에서는 이 목록이 코드 상수가 아니라 스키마 저장소(SHACL의 `sh:maxCount 1`, 프로퍼티 그래프의 기수 메타데이터 등)에 있고, 관문도 동시성 제어도 거기서 읽습니다.

**4) 새 집행 지점이 생겨도 선언은 안 바뀐다.**
같은 목록이 앞으로 또 필요해집니다. 32장의 스키마 변경(단일→다중 완화 시 마이그레이션 대상), 병합 전략(단일 값 필드는 자동 병합 금지 — ex5의 `단일값` 종류가 바로 이것), 사후 무결성 검사 배치, 사람 검토 큐 라우팅. **집행 지점이 늘어날수록 선언을 한 곳에 둔 이득이 커집니다.** 반대로 복사본 개수도 같이 늘어나면 언젠가 반드시 어긋납니다.

## 5. 실제로 어떻게 쓰이나

31장에서 이 목록을 소비하는 코드의 골격입니다.

```python
# 선언 — 한 곳에서만 정의한다 (28장과 공유)
SINGLE_VALUED = {"이끔"}          # 팀장은 한 명

def conflict_unit(subject, kind, obj):
    """이 쓰기의 충돌 단위 키를 돌려준다."""
    if kind in SINGLE_VALUED:
        # 엣지가 아니라 «논리 단위»가 다툰다
        return ("unit", constrained_side(subject, kind, obj), kind)
    # 다중 값이면 엣지 하나가 곧 단위
    return ("edge", subject, kind, obj)


def write(conn, s, k, o, seen_ver):
    # 0) 멱등 먼저 — 결과가 같으면 그냥 성공 (21장)
    if already_same(conn, s, k, o):
        return "ok(멱등)"

    key = conflict_unit(s, k, o)
    cur = conn.execute(
        "UPDATE version_row SET ver = ver + 1 "
        " WHERE key = ? AND ver = ?", (key, seen_ver))
    if cur.rowcount == 0:            # ← 0행이 충돌 신호. 예외가 아니다
        return "conflict"
    apply_change(conn, s, k, o)
    return "ok"
```

`conflict_unit()` 안에 `if kind in SINGLE_VALUED` 한 줄이 들어가는 것 — 그게 「목록이 다시 쓰인다」의 실체입니다. 28장에서는 같은 조건문이 `gate()` 안에 있었고요. **조건은 같고 그 뒤에 오는 동작만 다릅니다.**

### 함정: 「제약이 걸린 쪽」이 주어가 아닐 수 있다

`SINGLE_VALUED`를 그냥 관계 종류의 집합으로만 두면 부족합니다. 두 장의 예시가 다른 방향을 가리킵니다.

- 28장: `박민수-이끔->결제팀` vs `박민수-이끔->정산팀` → 다투는 건 **주어(박민수)** 쪽. 「한 사람은 한 팀만 이끈다」
- 31장: `이서연-이끔->결제팀` vs `김도현-이끔->결제팀` → 다투는 건 **목적어(결제팀)** 쪽. 「한 팀의 팀장은 한 명」

31장 예시에서 무심코 「주어 + 관계 종류」로 단위를 잡으면 `(이서연, 이끔)`과 `(김도현, 이끔)`이 되어 **여전히 서로 다른 단위**입니다. 엣지 버전과 똑같이 샙니다. 여기서는 `(결제팀, 이끔)`이 단위여야 합니다.

그래서 선언을 이렇게 키우는 게 낫습니다.

```python
SINGLE_VALUED = {
    "이끔": "both",     # 사람도 한 팀만, 팀장도 한 명 (1:1)
    "속함_주": "out",   # 주어 쪽만 단일
}
```

양쪽 모두 단일이면 두 단위를 다 걸어야 하고, 그러면 **잠금 순서를 고정해 교착(deadlock)을 피해야** 합니다. 그리고 이렇게 방향을 명시해 두면 **28장의 관문 조회 쿼리도 같은 정보를 써서 정확해집니다.** 선언을 정교하게 만든 이득이 두 곳 모두에 돌아갑니다 — 이게 선언 공유의 진짜 배당금입니다.

## 6. 자주 하는 오해

**「그냥 우연히 같은 정보가 필요했던 것 아닌가?」**
아닙니다. 두 문제 모두 **단일 값 제약이 엣지 하나 안에 담기지 않기 때문에** 생깁니다. 원인이 같으니 필요한 정보가 같습니다. 스키마 관문(타입 검사)은 반대로 트리플 하나만 보면 판정이 끝나서, 31장의 충돌 단위 결정에 아무 정보도 주지 않습니다. **모든 제약이 재사용되는 게 아니라, 「여러 엣지에 걸친」 제약만 재사용됩니다.**

**「그럼 관문 4번만 있으면 동시성 문제도 풀리나?」**
아닙니다. 반대입니다. 28장의 관문 4번은 조회와 쓰기 사이에 창이 있어서, 두 에이전트가 동시에 돌면 **둘 다 「다른 값 없음」을 보고 둘 다 통과합니다.** 관문 코드를 그대로 두고 31장의 충돌 단위를 얹어야 그 관문이 동시 실행에서도 유효해집니다. 목록은 공유하지만 **집행 메커니즘은 각자 필요합니다.**

**「목록을 한 곳에 두는 게 결합도를 올리는 것 아닌가?」**
공유하는 게 **구현이 아니라 도메인 사실**이면 괜찮습니다. 나쁜 결합은 28장 코드가 31장 코드를 부르는 것이고, 좋은 결합은 둘 다 같은 선언을 **읽는** 것입니다. 선언은 잠금·버전·쿼리를 하나도 모릅니다.

**「감지만 공유하면 해결도 공유되나?」**
아닙니다. ex5의 결론대로 **충돌 감지는 기술 문제라 일반 해법이 있고, 충돌 해결은 도메인 문제라 없습니다.** `SINGLE_VALUED`가 답해 주는 건 「무엇을 한 단위로 볼까」까지입니다. 「이서연과 김도현 중 누가 팀장인가」는 이 목록이 모릅니다. 28장의 조언이 그대로 이어집니다 — 「단일 값 충돌을 자동으로 덮어쓰지 마세요. 오답이 정답을 지웁니다. 둘 다 살려 두고 사람에게 보내세요.」

## 7. 한 줄로

**`SINGLE_VALUED`는 「이 불변식은 엣지 하나 안에 안 담긴다」는 선언이고, 유효성 검사(28장)와 동시성 제어(31장)는 그 사실이 만들어 내는 두 개의 다른 증상이다. 증상이 둘이라고 진단서를 두 장 쓰면 반드시 갈라진다 — 선언은 한 곳, 집행은 각자.**

## 자가 점검

1. 28장의 확신도·스키마 관문은 왜 31장의 충돌 단위 결정에 재사용되지 않는가?
2. 「단독으로는 정상인데 함께 있으면 위반」이라는 성질이 두 장에서 각각 어떤 형태로 나타나는가?
3. `SINGLE_VALUED` 목록을 두 벌로 복사해 뒀을 때 생기는 어긋남은 언제, 어떤 증상으로 드러나는가?
4. 28장의 단일 값 관문만 있고 31장의 충돌 단위가 없으면 무슨 일이 생기는가?
5. `이서연-이끔->결제팀` vs `김도현-이끔->결제팀`에서 논리 단위를 「주어 + 관계 종류」로 잡으면 왜 새는가?
6. 이 목록을 소비할 만한 세 번째 집행 지점을 하나 더 들어 보라.
