# 판단 시간이 길수록 낙관적 잠금이 불리한 이유

> **질문** 판단 시간이 길수록 낙관적 잠금이 불리한 이유는 무엇인가?
>
> **답** 재시도할 때 판단을 다시 한다. 모델 호출이 잠금 구간에 있으면 재시도마다 모델 호출이 통째로 다시 든다.

출처: 31장 「두 에이전트가 같은 노드를 동시에 고쳤다」, 31.2절 / `code/ex3_lock_contention.py`

---

## 1. 먼저, 여기서 「판단」이 무엇인가

낙관적 잠금의 한 번 시도는 이렇게 생겼습니다.

```
1. 읽는다        ← 버전 v 를 같이 읽는다
2. 판단한다      ← 여기가 「판단 시간」(HOLD). 읽은 값을 보고 무엇을 쓸지 정한다
3. 쓴다          ← UPDATE ... WHERE id=? AND version=v
                   0행이면 충돌 → 1번으로 돌아간다
```

`ex2_optimistic.py` 의 `optimistic()` 이 정확히 이 모양입니다.

```python
for attempt in range(max_tries):
    props, ver = SELECT props, version ...      # 1. 읽기
    time.sleep(delay)                           # 2. 판단  ← 재시도마다 다시 든다
    d[field] = value
    cur = UPDATE ... WHERE id='t1' AND version=?   # 3. 쓰기
    if cur.rowcount == 1:
        return True
    # rowcount == 0 → 충돌. 루프의 처음으로 돌아간다
```

핵심은 **재시도가 `for` 루프의 맨 위로 돌아간다**는 것입니다. 실패한 것은 3번(쓰기) 한 줄인데, 되돌아가는 곳은 1번입니다. 2번의 판단은 「이미 옛날 값 위에서 내린 판단」이라 버릴 수밖에 없습니다. 낡은 `props` 를 보고 정한 결과를 새 `props` 위에 그대로 얹으면 그게 바로 잃어버린 갱신이니까요.

그래서 **재시도 1회의 값 = 판단 시간 + 쓰기 시간**이고, 판단 시간이 그 안에서 거의 전부를 차지합니다.

## 2. 수식으로 보면 판단 시간이 「곱해진다」

`ex3_lock_contention.py` 가 세우는 두 식입니다.

```
낙관적 = N × (1/(1-p)) × (판단 + 쓰기)
비관적 = N × (판단 + 쓰기 + 잠금획득) + N × p × 대기
```

* `p` = 충돌률, `1/(1-p)` = 기대 시도 횟수(기하분포의 기댓값)
* 낙관적 쪽에서 **(판단 + 쓰기)가 기대 시도 횟수와 곱해집니다.**
* 비관적 쪽에서 (판단 + 쓰기)는 `N ×` 로 **한 번만** 곱해집니다. 잠금을 잡고 시작하니 재시도가 없거든요. 충돌이 늘어도 늘어나는 것은 「대기」 항뿐입니다.

이 비대칭이 답의 전부입니다. 판단 시간은 낙관적 쪽에서만 재시도 배수와 곱해집니다.

낭비되는 값만 따로 떼어내면 이렇게 보입니다.

```
낙관적의 순수 낭비 = N × (기대시도 - 1) × (판단 + 쓰기)
                    = N × (p/(1-p)) × (판단 + 쓰기)
```

`판단`이 커질수록 이 낭비가 **비례해서** 커집니다. 판단이 2배면 낭비도 2배입니다.

## 3. 숫자로 확인

`ex3` 의 기본값(판단 12ms, 쓰기 1.5ms, 잠금 획득 2.2ms, 1000회)으로 계산하면 이렇습니다.

| 충돌률 p | 기대 시도 | 낙관적(ms) | 비관적(ms) | 승자 |
|---|---|---|---|---|
| 1% | 1.01 | 13,636 | 15,836 | 낙관적 |
| 5% | 1.05 | 14,211 | 16,411 | 낙관적 |
| 15% | 1.18 | 15,882 | 16,057 | 낙관적 (거의 비슷) |
| 30% | 1.43 | 19,286 | 17,436 | 비관적 |
| 50% | 2.00 | 27,000 | 22,450 | 비관적 |
| 70% | 3.33 | 45,000 | 37,200 | 비관적 |

15%와 30% 사이에서 뒤집힙니다. 이제 **판단 시간만 바꿔** 보면 갈림길이 어디로 움직이는지 보입니다.

| 판단 시간 | 뒤집히는 지점(대략) | 뜻 |
|---|---|---|
| 1.5ms (판단을 잠금 밖으로 뺌) | 충돌률 50%가 넘어도 낙관적이 유리 | 재시도가 싸다 |
| 12ms (기본) | 15~30% 사이 | 책의 기준선 |
| 2,000ms (모델 호출 1회) | 한 자릿수 %에서 이미 비관적이 유리 | 재시도가 재앙이다 |

마지막 줄이 이 카드의 요점입니다. 판단 자리에 모델 호출이 들어가면 판단 시간은 ms 가 아니라 **초** 단위가 됩니다. 12ms 짜리 판단이 2,000ms 짜리 판단으로 바뀌면, 재시도 1회의 값이 166배가 됩니다. 충돌률이 조금만 올라가도 낙관적 잠금이 무너지는 이유입니다.

판단 2,000ms, p=20% 로 넣어 보면요.

```
낙관적 = 1000 × 1.25 × 2001.5 ms ≈ 2,502초
비관적 = 1000 × 2003.7 + 1000 × 0.2 × 500.4 ≈ 2,104초
```

충돌률 20%인데 벌써 비관적이 이깁니다. 판단이 12ms 였다면 20%는 낙관적 구간이었습니다.

## 4. 그리고 「돈」이 더 문제다

`ex3` 는 시간만 셉니다. 하지만 에이전트 시스템에서 모델 호출의 재시도는 시간만 드는 게 아닙니다.

* **토큰 비용이 실제로 다시 나갑니다.** CPU 재시도는 전기값이지만, 모델 재시도는 청구서에 찍힙니다.
* **부수효과가 있을 수 있습니다.** 판단 과정에서 도구를 부르거나 외부 시스템을 건드렸다면, 재시도는 그걸 다시 합니다(21장 멱등성이 여기서 필요해지는 이유).
* **비결정적입니다.** 같은 입력에 다시 물어도 다른 답이 올 수 있습니다. 재시도가 「같은 일을 다시」가 아니라 「다른 일을」이 됩니다.
* **`max_tries` 에 걸립니다.** `ex2` 의 `optimistic()` 은 5회에서 포기하고 `False` 를 돌려줍니다. 판단이 길면 시도 5회를 채우는 데 10초가 넘게 걸리고, 그러고도 실패입니다.

## 5. 이중 페널티 — 판단이 길면 충돌률 자체도 오른다

앞의 표는 `p` 를 바깥에서 주어진 값처럼 다뤘습니다. 실제로는 그렇지 않습니다.

충돌은 **읽기와 쓰기 사이의 창**에서만 생깁니다. 판단 시간이 곧 그 창의 너비입니다. 창이 넓을수록 그 사이에 남이 끼어들 확률이 올라갑니다.

```
판단 시간 ↑  →  ① 재시도 1회의 값 ↑
             →  ② 창이 넓어짐 → 충돌률 p ↑ → 기대 시도 횟수 ↑
```

두 효과가 곱해집니다. 낙관적 = `N × (1/(1-p)) × (판단+쓰기)` 에서 **판단이 두 자리(배수와 단가) 모두에 들어가는** 셈입니다. `ex1_lost_update.py` 가 `time.sleep(delay)` 를 키우면 잃어버린 갱신이 더 잘 재현된다고 말하는 것도 같은 이야기입니다.

## 6. 그래서 어떻게 하나 — 판단을 잠금 밖으로 뺀다

`ex3` 의 마지막 처방입니다.

```
1. 읽는다                    (잠금 없이)
2. 모델을 부른다              (잠금 없이 — 여기가 제일 길다)
3. 짧게 잠그고 «버전 확인 + 쓰기»만 한다
```

이러면 잠금을 붙드는 구간이 12ms 에서 1.5ms 로 줍니다. 효과가 두 갈래입니다.

* **비관적 쪽**: 잠금 보유 시간이 짧아져 대기열이 짧아집니다.
* **낙관적 쪽**: 창이 좁아져 충돌률 `p` 자체가 떨어집니다.

즉 「갈림길이 오른쪽으로 밀린다」(한 장 요약의 표현)는 뜻입니다. 판단을 밖으로 뺀 낙관적 잠금은 충돌률이 꽤 높아도 버팁니다.

다만 주의할 점 하나. 2번을 잠금 밖에서 하면 판단의 근거가 되었던 값이 3번 시점에 낡아 있을 수 있습니다. 그래서 **버전 확인이 반드시 3번 안에 있어야** 합니다. 낡았으면 `rowcount == 0` 이 뜨고, 그때는 어쩔 수 없이 모델을 다시 부릅니다. 판단을 밖으로 뺀다고 재시도 비용이 사라지는 게 아니라, **재시도가 나는 빈도가 줄어드는** 것입니다.

## 7. 판단이 필요 없다면 애초에 창을 없앤다

`ex2` 의 세 번째 방식 `field_level()` 이 그것입니다.

```python
def field_level(db, field, value, delay):
    time.sleep(delay)          # 판단을 «먼저» 끝낸다
    with LOCK:                 # 읽기-수정-쓰기가 한 덩어리
        props, _v = SELECT ...
        d[field] = value
        UPDATE ...
```

읽기와 쓰기 사이에 판단이 없으므로 창이 0에 가깝고, 재시도도 없습니다. 「인원 = 5로 설정」처럼 읽은 값을 볼 필요가 없는 단순 대입이면 이게 제일 낫습니다.

반대로 「인원이 5 미만이면 한 명 추가」처럼 **읽은 값을 보고 판단해야** 하면 창을 없앨 수 없습니다. 그때 낙관적 잠금이 필요해지고, 판단 시간 문제가 그대로 따라옵니다.

## 8. 한 줄 정리

| 방식 | 판단 시간이 길어지면 |
|---|---|
| 비관적 잠금 | 잠금 보유 시간이 늘어 **대기**가 는다 (선형) |
| 낙관적 잠금 | 재시도마다 판단을 **다시** 하고, 창이 넓어져 재시도 자체도 는다 (곱셈) |

**낙관적 잠금은 「실패하면 그냥 다시 하면 되지」를 전제로 합니다. 그 전제는 재시도가 쌀 때만 참입니다. 재시도 안에 모델 호출이 들어 있으면 재시도는 싸지 않습니다.**
