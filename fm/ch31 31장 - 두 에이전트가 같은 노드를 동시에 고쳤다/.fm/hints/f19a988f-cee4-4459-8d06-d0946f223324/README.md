# 에이전트 시스템에서 잃어버린 갱신이 자주 나는 세 가지 이유

**질문** — 에이전트 시스템에서 잃어버린 갱신이 자주 나는 세 가지 이유는 무엇인가?

**답** — 판단 시간이 길고, 동시 실행이 기본이고, 전체를 다시 쓰는 코드를 만들기 쉽다.

---

## 0. 먼저, 잃어버린 갱신이 무엇인가

「읽고 → 판단하고 → 통째로 쓰기」를 두 작업이 동시에 하면 나중에 쓴 쪽이 앞 쪽의 변경을 **덮어씁니다**. 이걸 잃어버린 갱신(lost update)이라고 부릅니다.

핵심 성질은 **에러가 안 난다**는 것입니다. 두 UPDATE 모두 성공하고, 로그에도 「성공」만 두 줄 찍힙니다. 사용자는 「분명히 고쳤는데요」라고 말하고, 개발자는 로그에서 아무것도 못 찾습니다.

31장 예제 1(`ex1_lost_update.py`)의 상황이 정확히 이렇습니다.

```
초기 상태:  팀장=박민수;인원=3

에이전트 A: 팀장 = 이서연  (판단에 0.20초)
에이전트 B: 인원 = 5      (판단에 0.05초)

  [팀장] 읽음: 팀장=박민수;인원=3     ← 둘 다 «같은 옛 상태»를 읽는다
  [인원] 읽음: 팀장=박민수;인원=3
  [인원] 씀:   팀장=박민수;인원=5     ← B 가 먼저 끝난다
  [팀장] 씀:   팀장=이서연;인원=3     ← A 가 통째로 덮는다. 인원=5 가 사라진다

최종 상태: 팀장=이서연;인원=3
사라진 변경: ['인원 변경']
```

**둘이 서로 다른 필드를 고쳤는데도** 하나가 사라졌다는 점을 보세요. 겹치는 데이터가 하나도 없는데 결과가 깨집니다. 전체를 통째로 썼기 때문입니다.

이 현상 자체는 새로운 게 아닙니다. 관계형 DB 교과서에 수십 년째 있는 고전 문제입니다([PostgreSQL 트랜잭션 격리 문서](https://www.postgresql.org/docs/current/transaction-iso.html)). 카드가 묻는 건 「왜 하필 **에이전트 시스템에서** 유난히 자주 터지는가」입니다.

## 1. 판단 시간이 길다 — 창(window)이 넓어진다

잃어버린 갱신은 **읽기와 쓰기 사이의 시간**에 비례해서 확률이 올라갑니다. 그 사이 구간을 흔히 「창」이라고 부릅니다. 창이 넓을수록 남이 끼어들 여지가 커집니다.

```
읽기 ────────[      판  단      ]──────── 쓰기
             ↑ 이 구간이 «창». 여기서 남이 쓰면 내 쓰기가 남을 덮는다
```

전통적인 CRUD 서버에서는 이 창이 **마이크로초~밀리초** 단위입니다. 읽고, 필드 하나 바꾸고, 바로 씁니다. 그래서 실무에서 잘 안 터지고, 터져도 「어쩌다 한 번」입니다.

에이전트는 다릅니다. 읽은 다음에 하는 일이 **모델 호출**입니다.

- LLM 한 번 호출: 수백 ms ~ 수십 초
- 도구 호출이 끼면: 더 길어짐
- 다단계 추론이면: 분 단위도 나옴

창이 1ms에서 5초로 늘어나면, 충돌 확률은 **수천 배** 늘어납니다. 예제 1이 `time.sleep(delay)`를 「판단하는 시간」이라고 주석 달아 둔 이유가 이것입니다. `delay`가 바로 모델 호출 자리입니다.

```python
def naive_update(db, field, value, delay, log):
    """읽고 → 고치고 → 쓴다. 그 사이에 남이 끼어들 수 있다."""
    row = db.execute("SELECT props FROM node WHERE id='t1'").fetchone()
    props = parse(row[0])
    time.sleep(delay)                      # 판단하는 시간  ← 여기가 모델 호출
    props[field] = value
    db.execute("UPDATE node SET props=? WHERE id='t1'", (dump(props),))
```

그리고 이건 **낙관적 잠금까지 불리하게** 만듭니다. 예제 3(`ex3_lock_contention.py`)의 설명이 그 지점입니다.

> 판단 시간이 길수록 낙관적이 불리하다. 재시도할 때 판단을 다시 하니까.
> 그래서 «에이전트가 모델을 부르는» 구간이 잠금 안에 있으면 최악이다.
> 재시도 한 번에 모델 호출 한 번이 통째로 다시 든다.

즉 긴 판단 시간은 (a) 충돌을 더 자주 만들고 (b) 충돌 났을 때 복구 비용도 더 비싸게 만듭니다. 이중 손해입니다.

**대응**: 판단을 잠금 밖으로 빼는 것.

```
1. 읽는다              (잠금 없이)
2. 모델을 부른다        (잠금 없이 — 여기가 제일 길다)
3. 짧게 잠그고 «버전 확인 + 쓰기»만 한다
```

이러면 잠금을 붙드는 시간이 12ms에서 1.5ms로 줄고, 충돌률도 같이 떨어집니다. 창이 좁아지니까요. 그래서 한 장 요약이 「판단을 잠금 밖으로 빼면 갈림길이 오른쪽으로 밀린다」고 말합니다.

## 2. 동시 실행이 기본이다 — 경쟁자 수가 원래 많다

두 번째 이유는 **얼마나 자주 창이 겹치느냐**입니다.

전통적인 시스템에서 같은 레코드를 동시에 고치는 상황은 예외적입니다. 사람 두 명이 같은 순간에 같은 팀 정보를 편집해야 하니까요. 드뭅니다.

에이전트 시스템에서는 이게 **기본값**입니다.

- 오케스트레이터가 서브에이전트를 **병렬로 팬아웃**시키는 게 표준 패턴입니다
- 배치 파이프라인, 스케줄 잡, 실시간 동기화가 **동시에** 같은 그래프를 건드립니다
- 예제 5의 충돌 출처 목록만 봐도 `hr-sync`, `batch`, `user`, `admin`, `agent-4821`, `agent-5102` — 서로 다른 여섯 주체가 같은 노드를 고칩니다

게다가 에이전트들은 서로의 존재를 **모릅니다**. 사람 둘이 같은 문서를 편집하면 슬랙으로 「나 지금 이거 고치는 중」이라고 말합니다. 에이전트는 그런 조율을 하지 않습니다. 각자 독립적으로 「내가 아는 세계 상태」를 읽고 자기 판단을 씁니다.

그리고 에이전트가 다루는 개체는 **편중되어 있습니다**. 자주 언급되는 엔티티(핵심 인물, 주요 팀, 활성 프로젝트)는 여러 워크플로가 동시에 손을 댑니다. 충돌은 균등하게 흩어지지 않고 몇몇 뜨거운 노드에 몰립니다.

이 항목이 중요한 이유는 **충돌률이 방식 선택을 뒤집기 때문**입니다. 예제 3의 결론이 그것입니다.

| 충돌률 | 유리한 쪽 |
|---|---|
| 1% ~ 15% | 낙관적 잠금 (막는 값을 안 냄) |
| **15% ~ 30%** | **갈림길** |
| 30% 이상 | 비관적 잠금 (재시도가 쌓여서 낙관적이 뒤집힘) |

```
낙관적 = N × (1/(1-p)) × (판단 + 쓰기)
비관적 = N × (판단 + 쓰기 + 잠금획득) + N × p × 대기
```

「낙관적 잠금이 좋다」는 **조건부 참**입니다. 에이전트 동시 실행이 기본이면 p가 쉽게 15%를 넘고, 그 순간 통념이 뒤집힙니다.

## 3. 전체를 다시 쓰는 코드를 만들기 쉽다 — 겹치지 않는 변경끼리도 싸운다

세 번째가 이 카드에서 제일 흥미로운 항목입니다. 앞의 둘은 「확률이 올라간다」는 얘기지만, 이건 「**피할 수 있었던 충돌을 스스로 만든다**」는 얘기입니다.

예제 1에서 A는 `팀장`만, B는 `인원`만 고쳤습니다. 논리적으로는 안 겹칩니다. 그런데 코드가 이렇게 생겼습니다.

```python
props = parse(row[0])       # 전체를 읽어서
props[field] = value        # 한 필드만 고치고
db.execute("UPDATE node SET props=? ...", (dump(props),))   # «전체»를 다시 쓴다
```

`dump(props)`가 문제입니다. 한 필드만 바꿨는데 **전체 딕셔너리를 통째로 직렬화해서** 씁니다. 그러면 내가 안 건드린 필드까지 「내가 읽었던 옛날 값」으로 되돌립니다. 이게 겹치지 않는 변경을 서로 덮게 만듭니다.

> **전체를 쓰면 겹치지 않는 변경도 서로를 덮는다.**

왜 에이전트 시스템에서 이런 코드가 특히 잘 나오냐면:

**(a) 모델이 「전체 상태」를 뱉는 게 자연스럽습니다.** LLM에게 「이 노드를 갱신해」라고 시키면 델타가 아니라 완성된 JSON 객체 전체를 돌려주는 게 기본 출력 형태입니다. 그걸 그대로 `UPDATE ... SET props = <모델이 준 것>`에 넣으면 전체 덮어쓰기가 됩니다.

**(b) 구조화 출력·스키마 강제가 이 습관을 부추깁니다.** 스키마에 맞는 완전한 객체를 요구하면, 안 바뀐 필드도 포함된 완전한 객체가 돌아옵니다.

**(c) 코드 생성이 쉬운 쪽으로 흐릅니다.** 「읽고, 파이썬 dict으로 만들고, 고치고, 다시 저장」이 제일 짧고 읽기 좋은 코드입니다. 델타 계산은 귀찮습니다. 그래서 에이전트가 코드를 짜든 사람이 짜든 이 모양이 나옵니다.

이게 30장의 「전체 상태를 이벤트에 넣지 마라」와 같은 이야기입니다. 31장 예제 1이 명시적으로 그 연결을 짚습니다.

> 30장에서 «전체 상태를 이벤트에 넣지 마라»고 한 이유가 이것이다.
> 전체를 쓰면 겹치지 않는 변경도 서로를 덮는다.

**대응**: 필드 단위 수정. 예제 2의 `field_level`이 그것입니다.

```python
def field_level(db, field, value, delay):
    """통째로 안 쓰고 «그 필드만» 고친다. 읽고-고치고-쓰기 창이 없다."""
    time.sleep(delay)                     # 판단을 «먼저» 한다 (읽기 전에)
    with LOCK:
        props, _v = db.execute("SELECT props, version ...").fetchone()
        d = parse(props); d[field] = value
        db.execute("UPDATE node SET props=?, version=version+1 ...")
```

판단이 읽기 **앞**으로 나왔다는 점이 핵심입니다. 읽기와 쓰기 사이에 아무것도 없으니 창이 사라집니다.

다만 만능은 아닙니다. 「인원이 5 미만이면 한 명 추가」처럼 **읽은 값을 보고 판단해야 하는** 경우엔 못 씁니다. 읽어야 판단할 수 있으니까요.

## 4. 세 이유를 한 표로

| # | 이유 | 무엇을 키우나 | 대응 |
|---|---|---|---|
| 1 | **판단 시간이 길다** | 창의 **너비** (읽기~쓰기 간격) | 판단을 잠금 밖으로 빼기 |
| 2 | **동시 실행이 기본** | 창이 겹치는 **빈도** (충돌률 p) | 충돌률 측정 → 낙관적/비관적 선택 |
| 3 | **전체를 다시 쓴다** | 충돌의 **판정 범위** (안 겹치는 것도 충돌) | 필드 단위 변경 / 델타 쓰기 |

셋은 **곱해집니다**. 창이 5초이고(1), 여섯 주체가 동시에 돌고(2), 코드가 통째로 덮어쓰면(3), 데이터는 조용히 썩습니다. 로그에는 성공만 남긴 채로요.

암기 요령: **길다 · 겹친다 · 통째로 쓴다**.

## 5. 왜 트랜잭션으로는 안 풀리나 (자주 나오는 반문)

「그냥 트랜잭션으로 감싸면 되지 않나?」가 첫 반응입니다. 31장 한 장 요약이 미리 막아 둡니다.

> 트랜잭션으로는 안 풀립니다. 트랜잭션 안에 모델 호출이 들어가고, 워크플로는 프로세스 경계를 넘어 살아 있으니까요.

두 가지 이유입니다.

1. **트랜잭션 안에 모델 호출을 넣을 수 없습니다.** DB 트랜잭션을 5초 동안 열어 두고 그동안 외부 API를 호출하는 건 연결 풀을 말려 죽이는 짓입니다. 이유 1이 여기서 다시 발목을 잡습니다.
2. **워크플로가 프로세스 경계를 넘습니다.** 에이전트 워크플로는 중단됐다가 다른 워커에서 재개되기도 하고, 사람 승인을 기다리며 몇 시간 멈추기도 합니다. DB 트랜잭션은 연결 하나 안에서만 사는데 워크플로는 그보다 오래 삽니다. Fowler가 이걸 **오프라인 잠금**(offline lock)이라고 부르는 이유가 그것입니다 — [낙관적 오프라인 잠금](https://martinfowler.com/eaaCatalog/optimisticOfflineLock.html), [비관적 오프라인 잠금](https://martinfowler.com/eaaCatalog/pessimisticOfflineLock.html).

그래서 답은 **쓰기 직전에 「안 바뀌었나」를 확인하는 것**입니다. 버전 컬럼을 하나 두고, 읽을 때 본 버전이 그대로일 때만 씁니다.

```sql
UPDATE node SET props = ?, version = version + 1
 WHERE id = ? AND version = ?      -- ← 이 조건이 전부다
```

그리고 여기 **함정**이 하나 있습니다.

> 충돌은 에러가 아니라 **0행 갱신**으로 옵니다. `rowcount`를 봐야 해요.

`db.execute(...)`는 예외를 던지지 않습니다. `cur.rowcount == 0`을 직접 확인하지 않으면 충돌을 **또다시 조용히 놓칩니다**. 잃어버린 갱신과 똑같은 실패 모양(에러 없음)이 감지 코드에도 숨어 있는 셈입니다.

```python
cur = db.execute("UPDATE node SET props=?, version=version+1 "
                 "WHERE id='t1' AND version=?", (dump(d), ver))
if cur.rowcount == 1:
    return True          # 성공
STATS["충돌"] += 1        # 0행 = 충돌. 다시 읽고 재시도 (+ 흔들기, 22장)
```

## 6. 이어지는 이야기 (한 장 안에서의 위치)

이 카드는 31장의 두 번째 불릿입니다. 흐름은 이렇습니다.

1. **31.1 에러 없이 변경이 사라진다** — 문제 제시. ← **이 카드는 「왜 에이전트에서 유독 심한가」**
2. **31.2 쓰기 직전에 확인한다** — 낙관적 잠금, `rowcount`, 낙관적/비관적 갈림길(15~30%)
3. **31.3 그래프에서는 충돌 단위가 애매하다** — 노드 버전은 **가짜 충돌**, 엣지 버전은 **단일 값 누락**. 「주어 + 관계 종류」를 논리 단위로 두고 앞에 멱등 검사(21장)
4. **31.4 감지한 다음이 진짜 문제다** — 충돌 **감지는 기술 문제**, 충돌 **해결은 도메인 문제**. 자유문은 애초에 자동 병합 불가. 자동 병합의 **오류율을 재라**

3번이 그래프 특유의 어려움입니다. 관계형 DB에서는 「행 하나」가 충돌 단위라 명확한데, 그래프에서는 무엇이 한 단위인지부터 정해야 합니다. 예제 4의 표에서 어느 방식도 6/6을 못 맞히고, 논리 단위가 5/6으로 제일 낫습니다.

2. 판단 시간이 길면 낙관적 잠금이 왜 두 배로 불리한가? (→ 창이 넓어 충돌이 잦아지고, 재시도마다 모델 호출을 통째로 다시 한다)
3. A는 `팀장`을, B는 `인원`을 고쳤는데 왜 하나가 사라지는가? (→ 통째로 다시 쓰기 때문. 안 건드린 필드가 옛 값으로 되돌아간다)
4. 낙관적/비관적이 뒤집히는 충돌률 구간은? (→ 15~30% 근처. 판단을 잠금 밖으로 빼면 갈림길이 오른쪽으로 밀린다)
5. 낙관적 잠금에서 충돌은 어떤 신호로 오는가? (→ 예외가 아니라 `rowcount == 0`)
