# 낙관적 잠금의 핵심 SQL

## 질문

낙관적 잠금의 핵심 SQL은 어떻게 생겼는가?

## 답

```sql
UPDATE node
   SET props = ?, version = version + 1
 WHERE id = ? AND version = ?      -- ← 이 조건이 전부다
```

마지막 `AND version = ?` 한 줄이 낙관적 잠금의 전부입니다. 나머지는 이 조건이
실패했을 때의 뒤처리일 뿐입니다.

---

## 왜 이 한 줄이 필요한가

31장 예제 1(`ex1_lost_update.py`)이 보여 주는 상황입니다. 두 에이전트가 같은
노드를 고칩니다.

- 에이전트 A: `팀장 = 이서연` (판단에 0.20초)
- 에이전트 B: `인원 = 5` (판단에 0.05초)

둘은 **서로 다른 필드**를 고칩니다. 그런데도 하나가 사라집니다. 순서를 보면
이유가 보입니다.

1. A가 `팀장=박민수;인원=3` 을 읽는다
2. B가 **같은 옛 상태**를 읽는다
3. B가 0.05초 뒤 `팀장=박민수;인원=5` 를 **통째로** 쓴다
4. A가 0.20초 뒤 `팀장=이서연;인원=3` 을 **통째로** 쓴다
5. 최종 상태: `팀장=이서연;인원=3` — B의 변경이 사라졌다

이게 **잃어버린 갱신(lost update)** 입니다. 성질이 고약한 건 **에러가 안 난다**는
점입니다. 로그에는 양쪽 다 「성공」만 찍힙니다. 사용자는 「분명히 고쳤는데요」
라고 말하고, 우리는 로그를 봐도 아무것도 못 찾습니다.

낙관적 잠금은 이 4번 단계를 막습니다. A가 쓰려는 순간 「내가 읽었을 때의
버전이 아직 그대로인가?」를 묻고, 아니면 쓰지 않습니다.

---

## SQL을 한 조각씩

### `SET props = ?`

새 값입니다. 여기까지는 평범한 UPDATE와 같습니다.

### `SET version = version + 1`

**쓸 때마다 버전을 올립니다.** 애플리케이션에서 `version+1`을 계산해 넣지 말고
DB가 `version = version + 1`로 올리게 하는 편이 안전합니다. 원자적으로 처리되니
읽은 값을 다시 쓰는 창이 생기지 않습니다.

이 값은 단조 증가 정수면 무엇이든 됩니다. 정수 카운터, 타임스탬프,
UUID/해시 모두 쓰입니다. 다만 타임스탬프는 시계 해상도와 시계 뒤틀림 때문에
**같은 밀리초에 두 번 쓰면 못 잡습니다**. 정수 카운터가 제일 안전합니다.

### `WHERE id = ?`

어떤 행을 고칠지 지정합니다.

### `AND version = ?` ← 핵심

바인딩되는 값은 **내가 아까 SELECT할 때 읽었던 버전**입니다. 지금 DB에 있는
버전이 아닙니다. 이게 헷갈리기 쉬운 지점입니다.

- 아무도 안 건드렸다 → DB의 version이 아직 내가 읽은 값 → 조건 참 → **1행 갱신**
- 누가 먼저 썼다 → DB의 version이 이미 +1 되어 있음 → 조건 거짓 → **0행 갱신**

---

## 충돌은 에러가 아니라 「0행」으로 온다

이 장에서 가장 실수하기 쉬운 부분입니다. 버전이 안 맞아도 **SQL 에러는 안
납니다.** 예외도 안 던집니다. 그냥 `UPDATE`가 아무 행도 고치지 않고 조용히
성공합니다.

그래서 반드시 `rowcount`(영향받은 행 수)를 봐야 합니다.

```python
cur = db.execute(
    "UPDATE node SET props=?, version=version+1 "
    "WHERE id='t1' AND version=?", (dump(d), ver))
db.commit()
if cur.rowcount == 1:
    return True          # 내가 이겼다
# rowcount == 0 → 충돌. 다시 읽고 다시 시도한다
```

`rowcount`를 안 보면 낙관적 잠금 코드를 다 짜 놓고도 잃어버린 갱신을 그대로
겪습니다. 조건은 잘 걸었는데 **결과를 안 본** 것이니까요. 드라이버·ORM별로
이름이 다릅니다(JDBC `executeUpdate()` 반환값, Go `sql.Result.RowsAffected()`,
JPA `OptimisticLockException`). ORM 중에는 0행일 때 알아서 예외를 던져 주는
것도 있습니다.

## 실패했을 때: 읽고, 판단하고, 다시 쓴다

`ex2_optimistic.py`의 전체 흐름입니다.

```python
def optimistic(db, field, value, delay, max_tries=5):
    for attempt in range(max_tries):
        props, ver = read()              # 1. 읽는다 (버전도 같이)
        d = parse(props)
        time.sleep(delay)                # 2. 판단한다 (모델 호출 등)
        d[field] = value
        cur = write_with_version(d, ver)  # 3. 버전 조건 걸고 쓴다
        if cur.rowcount == 1:
            return True                   # 성공
        time.sleep(random.uniform(0.005, 0.03))  # 흔들기(jitter, 22장)
    return False                          # 재시도 소진
```

체크할 점 넷입니다.

1. **재시도할 때는 반드시 다시 읽는다.** 옛 값에 내 변경만 다시 얹으면 낙관적
   잠금을 쓴 의미가 없습니다. 새 버전과 새 props를 받아 와야 합니다.
2. **판단도 다시 한다.** 「인원이 5 미만이면 한 명 추가」 같은 조건은 바뀐 값
   위에서 다시 계산해야 맞습니다. 이게 재시도 비용이 비싼 이유입니다.
3. **재시도 횟수에 상한을 둔다.** 무한 루프는 라이브락(livelock)이 됩니다.
4. **흔들기(jitter)를 넣는다.** 고정 간격으로 재시도하면 경쟁하던 둘이 다시
   같이 부딪힙니다(22장).

## 왜 「낙관적」인가

미리 막지 않기 때문입니다. 「대개 충돌 안 난다」고 낙관하고 일단 진행한 다음,
쓰는 순간에만 확인합니다. 잠금을 잡지 않으니 읽는 동안 아무도 기다리지
않습니다.

반대는 **비관적 잠금**입니다. `SELECT ... FOR UPDATE`처럼 읽을 때부터 잠가서
남을 못 들어오게 막습니다.

`ex3_lock_contention.py`가 계산하는 갈림길입니다.

```
낙관적 = N × (1/(1-p)) × (판단 + 쓰기)
비관적 = N × (판단 + 쓰기 + 잠금획득) + N × p × 대기
```

- 비관적은 충돌이 **없어도** 잠금 획득 비용을 매번 낸다 → 왼쪽 구간의 손해
- 낙관적은 충돌이 **잦아지면** 재시도 배수가 곱해진다 → 오른쪽 구간의 손해

이 장의 값(판단 12ms, 쓰기 1.5ms, 잠금 획득 2.2ms)에서는 **충돌률 15~30% 사이**
에서 뒤집힙니다. 이 숫자는 환경마다 달라지니 직접 재야 합니다.

에이전트 시스템에서 특히 중요한 건 **판단 시간이 길수록 낙관적이 불리하다**는
점입니다. 재시도 한 번에 모델 호출 한 번이 통째로 다시 들거든요. 그래서 요령은
**판단을 잠금 밖으로 빼는 것**입니다.

1. 읽는다 (잠금 없이)
2. 모델을 부른다 (잠금 없이 — 여기가 제일 길다)
3. 짧게 잠그고 **버전 확인 + 쓰기**만 한다

잠금을 붙드는 시간이 12ms에서 1.5ms로 줄고, 창이 좁아지니 충돌률도 같이
떨어집니다. 갈림길이 오른쪽으로 밀린다는 뜻입니다.

## 세 번째 길: 필드 단위 수정

`ex2`는 세 방식을 비교합니다.

| 방식 | 하는 일 | 결과 |
|---|---|---|
| 그냥 쓰기 | 읽고 → 판단하고 → 통째로 쓴다 | 하나 사라짐 |
| 낙관적 잠금 | 쓰기 직전에 버전 확인 | 둘 다 반영 (충돌 시 재시도) |
| 필드 단위 수정 | 읽기~쓰기 사이에 판단을 안 둔다 | 둘 다 반영 (재시도 없음) |

필드 단위 수정은 아예 창을 없앱니다. **가능하면 이게 제일 낫습니다.** 다만
「읽은 값을 보고 판단해야」 하는 경우엔 못 씁니다. 「인원이 5 미만이면 한 명
추가」 같은 조건이 있으면 읽어야 하니까요.

실무 구분입니다.

- 단순 설정 → 필드 단위
- 읽고 판단해야 함 → 낙관적 잠금
- 충돌이 잦고 비용이 큼 → 비관적 잠금

30장에서 「전체 상태를 이벤트에 넣지 마라」고 한 이유가 같습니다. 통째로 쓰면
겹치지 않는 변경도 서로를 덮습니다.

## 트랜잭션으로는 왜 안 되는가

「그냥 트랜잭션 걸면 되지 않나」는 자연스러운 질문입니다. 에이전트 시스템에서는
안 됩니다.

- 트랜잭션 안에 **모델 호출**이 들어갑니다. 수 초짜리 네트워크 호출을 트랜잭션
  안에 둘 수는 없습니다. 커넥션과 잠금을 그동안 붙들게 되니까요.
- 워크플로가 **프로세스 경계를 넘어** 살아 있습니다. 읽은 쪽과 쓰는 쪽이 다른
  프로세스, 다른 시각일 수 있습니다. DB 트랜잭션은 그 경계를 못 넘습니다.

낙관적 잠금이 이 문제를 푸는 방식이 **버전 번호를 애플리케이션이 들고 다니는
것**입니다. 마틴 파울러가 이걸 「낙관적 오프라인 잠금(Optimistic Offline Lock)」
이라고 부른 이유입니다. **오프라인** — 트랜잭션 바깥에서 동작한다는 뜻이죠.

## 같은 아이디어의 다른 이름들

이 SQL 패턴은 원자적 **비교 후 교체(compare-and-swap, CAS)** 와 같은 구조입니다.

| 영역 | 형태 |
|---|---|
| SQL | `UPDATE ... WHERE id=? AND version=?` + rowcount 확인 |
| CPU 원자 연산 | `compare_exchange(expected, desired)` |
| HTTP | `If-Match: <ETag>` → 안 맞으면 `412 Precondition Failed` |
| etcd / DynamoDB | `mod_revision` 비교 / 조건부 쓰기 |
| Git | non-fast-forward push 거부 |

전부 「내가 본 게 아직 그대로인가」를 원자적으로 확인하고, 아니면 실패시킵니다.

## 그래프에서는 한 걸음 더 있다

관계형 DB에서는 **행 하나**가 충돌 단위입니다. 명확하죠. 그래서 `WHERE id=? AND
version=?`이 그대로 성립합니다.

그래프에서는 **버전을 어디에 둘 것인가**부터 정해야 합니다(`ex4_conflict_shape.py`).

- **노드에 버전** → 「한 노드의 다른 엣지」가 헛충돌합니다. 이서연 노드에 두
  사람이 각각 다른 엣지를 다는데 버전이 부딪힙니다. **가짜 충돌**입니다.
- **엣지에 버전** → 「단일 값 관계」를 못 잡습니다. `이서연-이끔->결제팀`과
  `김도현-이끔->결제팀`은 다른 엣지라 각자 버전이 따로입니다. 둘 다 통과해서
  팀장이 둘이 됩니다.
- **논리 단위(주어 + 관계 종류)** → 6개 시나리오 중 5개를 맞힙니다. 남는 하나는
  「양쪽에서 같은 엣지 추가」인데, 결과가 같으니 통과시켜도 되는 경우입니다.
  버전 비교 **전에** 멱등 검사를 두면 6/6이 됩니다(21장).

즉 그래프에서는 `WHERE id=?` 자리에 무엇이 오는지가 설계 문제입니다. 28장의
`SINGLE_VALUED` 목록이 여기서 다시 쓰입니다.

## 그리고 감지는 절반이다

이 SQL은 **충돌 감지**를 해결합니다. 감지는 기술 문제라 일반 해법이 있습니다.
하지만 **충돌 해결**은 도메인 문제라 일반 해법이 없습니다(`ex5_merge_strategy.py`).

- 집합(태그)은 합집합으로 합칠 수 있다
- 수치는 변화량을 더할 수 있다 — 단, **독립적인 증분**일 때만. 「현재 값을 다시
  센 결과」에는 쓰면 안 된다
- 자유문(설명)은 애초에 자동으로 못 합친다 → 사람에게

그리고 자동 병합의 **오류율을 재야** 합니다. 안 재면 「사람 일이 줄었다」만 보고
「조용히 틀린 것」을 못 봅니다.
