# 관계형 DB와 그래프의 충돌 단위는 어떻게 다른가?

> **답**: 관계형은 '행 하나'가 명확한 단위지만, 그래프에서는 그 단위가 무엇인지부터 정해야 한다.

---

## 1. 질문이 묻는 것

동시 수정 문제(잃어버린 갱신)를 막는 표준 도구는 **낙관적 잠금**입니다. 쓰기 직전에 "내가 읽은 뒤로 안 바뀌었나"를 확인하는 방식이죠.

```sql
UPDATE node SET props=?, version=version+1
 WHERE id=? AND version=?     -- 이 조건이 전부다
```

그런데 이 한 줄을 쓰려면 먼저 답해야 하는 질문이 있습니다. **`version`을 어디에 붙일 것인가?** 관계형 DB에서는 고민할 필요가 없습니다. 행에 붙이면 됩니다. 그래프에서는 이 질문 자체가 설계 결정이 됩니다.

이 차이가 이 카드의 핵심입니다.

---

## 2. 관계형: 행 하나 = 충돌 단위

관계형 테이블에서 "무엇을 고쳤나"의 최소 경계는 **행(row)** 입니다.

- 한 엔티티 = 한 행. 경계가 물리 저장 단위와 일치합니다.
- 두 작업이 같은 행을 만지면 충돌, 다른 행이면 충돌 아님. 판정이 자명합니다.
- 그래서 `version` 컬럼 하나만 붙이면 끝납니다. `WHERE id=? AND version=?`이 그대로 작동해요.
- DB 엔진의 행 잠금, MVCC, `SELECT ... FOR UPDATE` 같은 기본 도구도 전부 행 단위로 맞춰져 있습니다.

**논리적 경계와 물리적 경계가 같다** — 이게 관계형이 편한 이유입니다.

---

## 3. 그래프: 엣지는 두 노드에 걸쳐 있다

그래프에서 변경은 세 가지 모양으로 옵니다.

| 변경 모양 | 예 | 경계가 어디인가 |
|---|---|---|
| 노드 속성 수정 | 결제팀의 인원 = 5 | 노드 하나 (여기까진 행과 비슷) |
| 엣지 추가/삭제 | 이서연-이끔->결제팀 | **두 노드에 걸쳐 있음** |
| 엣지 속성 수정 | 그 엣지의 시작일 | 엣지 하나? 양 끝 노드? |

문제는 엣지입니다. 엣지는 하나의 "행"이 아니라 **두 노드 사이에 걸린 관계**라서, 이걸 누구의 소유로 볼지가 정해져 있지 않습니다. `이서연-이끔->결제팀`을 고칠 때 충돌 대상은 이서연인가, 결제팀인가, 그 엣지 자체인가, 아니면 "이서연의 이끔 관계 전체"인가?

**논리적 경계와 물리적 경계가 어긋납니다.** 그래서 단위를 사람이 정해야 합니다.

---

## 4. 실험: 여섯 경우 × 세 가지 버전 위치

에셋의 `ex4_conflict_shape.py`가 이걸 표로 보여줍니다. 두 에이전트가 그래프를 동시에 고치는 여섯 가지 경우를, 버전을 어디에 두느냐에 따라 어떻게 판정하는지 비교합니다.

### 여섯 경우와 "원하는 판정"

| 경우 | A | B | 원하는 것 | 이유 |
|---|---|---|---|---|
| 같은 엣지의 속성 | 이서연-이끔->결제팀 시작일 수정 | 같은 엣지 시작일 수정 | **막음** | 둘 다 같은 것을 고침 |
| 한 노드의 다른 엣지 | 이서연-이끔->결제팀 추가 | 이서연-삶->마포 추가 | **통과** | 겹치는 것이 없음 |
| 단일 값 관계 | 이서연-이끔->결제팀 추가 | 김도현-이끔->결제팀 추가 | **막음** | 팀장은 한 명 (28장) |
| 노드 삭제 대 엣지 추가 | 결제팀 노드 삭제 | 이서연-속함->결제팀 추가 | **막음** | 없는 노드에 엣지를 못 담 |
| 양쪽에서 같은 엣지 추가 | 이서연-속함->결제팀 추가 | 이서연-속함->결제팀 추가 | **통과** | 결과가 같음 (멱등, 21장) |
| 서로 다른 방향 | 이서연-멘토->김도현 추가 | 김도현-멘토->이서연 추가 | 도메인이 정함 | 대칭 관계면 충돌 |

### 세 가지 버전 위치의 성적

| 경우 | 노드 버전 | 엣지 버전 | 논리 단위 | 원하는 것 |
|---|---|---|---|---|
| 같은 엣지의 속성 | 막음 | 막음 | 막음 | 막음 |
| 한 노드의 다른 엣지 | 막음 ✗ | 통과 | 통과 | 통과 |
| 단일 값 관계 | 막음 | 통과 ✗ | 막음 | 막음 |
| 노드 삭제 대 엣지 추가 | 막음 | 통과 ✗ | 막음 | 막음 |
| 양쪽에서 같은 엣지 추가 | 막음 ✗ | 막음 ✗ | 막음 ✗ | 통과 |
| 서로 다른 방향 | 막음 ✗ | 통과 | 통과 | 통과 |
| **맞은 개수** | **3/6** | **3/6** | **5/6** | |

> ✗ 는 틀린 판정.

**어느 것도 6/6이 아닙니다.** 그게 이 표의 요점입니다. "그래프에서는 단위를 정해야 한다"는 말이 추상적인 훈수가 아니라, 어떤 선택을 해도 대가가 따른다는 측정 결과라는 뜻이에요.

---

## 5. 각 선택이 어떻게 틀리는가

### 노드에 버전을 두면 → 가짜 충돌 (3/6)

노드 하나에 버전을 두고 그 노드에 걸린 모든 변경을 막는 방식입니다. 안전하지만 **너무 넓게 막습니다**.

- `이서연`에 두 사람이 각각 **다른** 엣지(이끔 / 삶)를 다는데 이서연 노드 버전이 부딪힙니다.
- 실제로는 겹치는 게 없는데 막힙니다. 이걸 **가짜 충돌(false conflict)** 이라고 합니다.
- 허브 노드(직원 수백 명이 걸린 팀 노드 같은 것)에서 특히 나쁩니다. 그 노드가 사실상 전역 잠금이 되어 버려요.
- 재시도가 쌓이면 30장~31장에서 본 대로 낙관적 잠금이 비관적보다 느려지는 구간(충돌률 15~30%)으로 밀려갑니다.

### 엣지에 버전을 두면 → 단일 값 누락 (3/6)

엣지마다 버전을 두면 가짜 충돌은 사라집니다. 대신 **너무 좁게 봅니다**.

- `이서연-이끔->결제팀`과 `김도현-이끔->결제팀`은 **서로 다른 엣지**입니다.
- 각자 버전이 따로라서 둘 다 통과합니다. 그러면 **팀장이 둘**이 됩니다.
- 노드 삭제도 못 잡습니다. `결제팀` 노드를 지우는 것과 그 노드로 향하는 엣지를 다는 것은 서로 다른 대상이라 부딪히지 않거든요. 없는 노드에 걸린 엣지, 즉 고아 엣지가 남습니다.

### 논리 단위를 정하면 → 5/6

그래서 실무에서는 저장 구조와 별개로 **논리적 충돌 단위**를 따로 정의합니다.

| 종류 | 논리 충돌 단위 |
|---|---|
| 단일 값 관계 | **「주어 + 관계 종류」** 를 한 단위 (예: `이서연 + 이끔`) |
| 다중 값 관계 | 엣지 하나가 한 단위 |
| 노드 삭제 | 그 노드에 걸린 **모든 엣지**와 충돌 |

「주어 + 관계 종류」로 묶으면 `이서연-이끔->결제팀`과 `김도현-이끔->결제팀`이 같은 단위에 들어와 단일 값 위반을 잡습니다. 동시에 `이서연-이끔`과 `이서연-삶`은 관계 종류가 다르니 서로 통과시켜서 가짜 충돌도 안 만듭니다. 그래서 **5/6**입니다.

---

## 6. 남은 1건과 6/6으로 만드는 법

논리 단위가 유일하게 틀리는 경우는 **「양쪽에서 같은 엣지 추가」** 입니다. 두 에이전트가 정확히 같은 엣지(`이서연-속함->결제팀`)를 달려고 하는 상황이죠.

- 결과가 같으니 통과시켜도 아무 문제가 없는데,
- 노드 버전 / 엣지 버전 / 논리 단위 **셋 다 막습니다**. 버전이 바뀌었다는 사실만 보니까요.

고치는 방법은 한 줄입니다. **버전 비교 *앞*에 멱등 검사를 둡니다.**

> 「쓰려는 것이 이미 있는 것과 같으면 그냥 성공으로 친다」

순서가 중요합니다. 버전을 먼저 보면 이미 늦습니다. 값을 먼저 비교해야 "충돌은 났지만 결과가 같다"를 구분할 수 있어요. 이 한 줄을 앞에 두면 **논리 단위가 6/6**이 됩니다. 21장의 멱등성이 여기서 다시 쓰입니다.

```
1. 쓰려는 값 == 현재 값?  → 그냥 성공 (멱등)
2. 아니면 논리 단위 버전 비교
3. 버전이 다르면 → 충돌 (rowcount 0)
```

---

## 7. 이 결론이 다른 장과 이어지는 곳

- **28장 (단일 값 관계 목록)**: 「주어 + 관계 종류」를 충돌 단위로 잡으려면 "어떤 관계가 단일 값인가"를 코드가 알고 있어야 합니다. 28장의 `SINGLE_VALUED` 목록이 여기서 그대로 재사용됩니다. **같은 목록이 두 문제를 풉니다** — 데이터 무결성과 동시성 충돌 판정.
- **21장 (멱등성)**: 6/6을 만드는 마지막 한 줄이 멱등 검사입니다.
- **30장 (변경 이력)**: 30장이 "전체 상태를 이벤트에 넣지 마라"고 한 이유가 이 장의 전제입니다. 통째로 쓰면 겹치지 않는 변경도 서로를 덮습니다.
- **다음 단계 (충돌 해결)**: 여기까지는 전부 **감지**입니다. 감지는 기술 문제라 일반 해법이 있지만, **해결은 도메인 문제**라 일반 해법이 없습니다.

---

## 8. 한 줄로 기억하기

> 관계형에서는 `version` 컬럼을 **어디에 붙일지 고민할 필요가 없고**, 그래프에서는 그 고민이 **설계의 시작점**이다. 노드에 붙이면 3/6(가짜 충돌), 엣지에 붙이면 3/6(단일 값 누락), 「주어 + 관계 종류」라는 논리 단위로 잡으면 5/6, 앞에 멱등 검사를 두면 6/6.
