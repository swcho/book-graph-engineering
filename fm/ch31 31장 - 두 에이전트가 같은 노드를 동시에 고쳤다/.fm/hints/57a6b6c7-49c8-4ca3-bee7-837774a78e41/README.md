# 그래프에서 권장되는 충돌 단위

> **Q.** 그래프에서 권장되는 충돌 단위는 무엇인가?
>
> **A.** '주어 + 관계 종류'를 논리 단위로 두고, 그 앞에 멱등 검사를 둔다.

---

## 1. 왜 "단위"부터 정해야 하나

관계형 DB에서 동시 수정을 막는 방법은 정해져 있습니다. **행 하나**가 충돌 단위입니다.
`UPDATE ... WHERE id=? AND version=?` 한 줄이면 끝나고, 무엇과 무엇이 부딪히는지 헷갈릴 여지가 없습니다.

그래프는 다릅니다. 고치는 대상이 노드일 수도, 엣지일 수도 있고
**엣지는 두 노드에 걸쳐 있습니다**. 그래서 버전을 어디에 붙일지 — 즉 무엇을 하나의 충돌 단위로
볼지 — 부터 설계 결정이 됩니다. 31장이 30장과 갈라지는 지점이 여기입니다.
30장은 변경이 순서대로 온다고 가정했지만, 동시에 온 두 변경에는 순서가 없습니다.

## 2. 여섯 가지 경우 (`ex4_conflict_shape.py`)

먼저 "무엇이 진짜 충돌인가"를 도메인 관점에서 정리합니다.

| 경우 | A | B | 판정 | 이유 |
|---|---|---|---|---|
| 같은 엣지의 속성 | 이서연-이끔->결제팀 시작일 수정 | 같은 엣지의 시작일 수정 | **충돌** | 둘 다 같은 것을 고친다 |
| 한 노드의 다른 엣지 | 이서연-이끔->결제팀 추가 | 이서연-삶->마포 추가 | 충돌 아님 | 겹치는 것이 없다 |
| 단일 값 관계 | 이서연-이끔->결제팀 추가 | 김도현-이끔->결제팀 추가 | **충돌** | 팀장은 한 명 (28장) |
| 노드 삭제 대 엣지 추가 | 결제팀 노드 삭제 | 이서연-속함->결제팀 추가 | **충돌** | 없는 노드에 엣지를 못 단다 |
| 양쪽에서 같은 엣지 추가 | 이서연-속함->결제팀 추가 | 이서연-속함->결제팀 추가 | 충돌 아님 | 결과가 같다 (멱등, 21장) |
| 서로 다른 방향 | 이서연-멘토->김도현 | 김도현-멘토->이서연 | 도메인이 정함 | 대칭 관계면 충돌 |

## 3. 버전을 어디에 두느냐로 판정이 달라진다

같은 여섯 경우를, 버전을 노드에 둘 때 / 엣지에 둘 때 / 논리 단위에 둘 때로 다시 봅니다.

| 경우 | 노드 버전 | 엣지 버전 | 논리 단위 | 원하는 것 |
|---|---|---|---|---|
| 같은 엣지의 속성 | 막음 | 막음 | 막음 | 막음 |
| 한 노드의 다른 엣지 | 막음 ✗ | 통과 | 통과 | 통과 |
| 단일 값 관계 | 막음 | 통과 ✗ | 막음 | 막음 |
| 노드 삭제 대 엣지 추가 | 막음 | 통과 ✗ | 막음 | 막음 |
| 양쪽에서 같은 엣지 추가 | 막음 ✗ | 막음 ✗ | 막음 ✗ | 통과 |
| 서로 다른 방향 | 막음 ✗ | 통과 | 통과 | 통과 |
| **맞은 개수** | **3/6** | **3/6** | **5/6** | — |

이 표의 요점은 **어느 것도 6/6이 아니라는 것**입니다. 완벽한 기본 단위는 없고, 트레이드오프가 있습니다.

### 노드 버전의 실패 — 가짜 충돌

노드에 버전을 두면 이서연 노드에 두 사람이 각각 **다른** 엣지를 다는데 버전이 부딪힙니다.
실제로는 겹치지 않는데 막히죠. 이걸 **가짜 충돌(false conflict)** 이라고 합니다.
허브 노드(사람 한 명에 엣지 수백 개)에서는 이 노드가 사실상 전역 잠금이 됩니다.

### 엣지 버전의 실패 — 단일 값 누락

엣지에 버전을 두면 `이서연-이끔->결제팀`과 `김도현-이끔->결제팀`은 **서로 다른 엣지**라
각자 버전이 따로 돌아갑니다. 둘 다 통과하고, 그 결과 **팀장이 둘**이 됩니다.
"단일 값이어야 한다"는 제약이 엣지 하나 안에는 담기지 않기 때문입니다.
노드 삭제도 마찬가지로 못 잡습니다. 삭제되는 노드와 새로 붙는 엣지는 다른 객체니까요.

## 4. 답 — 논리적 충돌 단위

그래서 실무에서는 물리 구조(노드/엣지)가 아니라 **논리적 충돌 단위**를 따로 정합니다.

| 대상 | 충돌 단위 |
|---|---|
| 단일 값 관계 | **「주어 + 관계 종류」** 를 한 단위로 본다 |
| 다중 값 관계 | 엣지 하나가 한 단위 |
| 노드 삭제 | 그 노드에 걸린 **모든 엣지**와 충돌 |

핵심은 첫 줄입니다. `(결제팀, 이끔)`처럼 **주어와 관계의 종류를 묶은 쌍**에 버전을 답니다.
목적어(누가 팀장인가)는 단위에 들어가지 않습니다. 그래야 이서연과 김도현이 각각 다른 엣지를
만들어도 **같은 단위**를 건드리는 것이 되어 한쪽이 막힙니다.

동시에, 이서연의 `이끔`과 이서연의 `삶`은 관계 종류가 다르므로 **다른 단위**입니다.
그래서 가짜 충돌도 나지 않습니다. 노드 버전의 문제와 엣지 버전의 문제를 동시에 피하는 지점이 여기입니다.

```
버전 키:  (주어, 관계 종류)     예) ("결제팀", "이끔")
        ─────────────────
        노드보다는 잘게, 엣지보다는 굵게
```

`UPDATE`는 관계형 DB에서 하던 것과 똑같이 생깁니다. 대상만 바뀝니다.

```sql
UPDATE logical_unit
   SET version = version + 1
 WHERE subject = ? AND rel_kind = ? AND version = ?
```

그리고 충돌은 **에러가 아니라 0행 갱신**으로 옵니다. 예외를 기다리지 말고 `rowcount`를 보세요.

## 5. 나머지 1/6 — 그 앞에 멱등 검사

논리 단위도 5/6입니다. 남은 하나가 **「양쪽에서 같은 엣지 추가」** 입니다.
A와 B가 똑같이 `이서연-속함->결제팀`을 쓰려는 경우인데, 결과가 같으니 통과시켜도 되는데
세 방식 모두 막습니다. 버전만 보면 "누가 먼저 썼다"는 사실만 보이고 "무엇을 썼는지"는 안 보이니까요.

고치는 방법은 **버전 비교 앞에 멱등 검사를 한 줄 두는 것**입니다.

> 「쓰려는 것이 이미 있는 것과 같으면 그냥 성공으로 친다」

```python
def apply(unit, want):
    if read(unit) == want:      # ← 멱등 검사. 버전 비교 "전에"
        return OK               #   결과가 같으니 충돌이 아니다
    return cas(unit, want)      # 그다음에 버전 확인 + 쓰기
```

이 한 줄이 붙으면 논리 단위가 **6/6**이 됩니다.
21장에서 재시도 안전성을 위해 만든 멱등성이 여기서 다시 쓰이는 셈입니다.
순서가 중요합니다. 멱등 검사가 **먼저**, 버전 비교가 **나중**입니다. 반대로 두면 이미 막힌 뒤라 소용이 없습니다.

"어떤 관계가 단일 값인가"를 코드가 알아야 이 전략이 돌아갑니다.

- 28장에서는 **잘못된 다중 값 저장을 막는 데** 썼고,
- 31장에서는 **충돌 단위를 정하는 데** 씁니다.

같은 목록이 두 문제를 풉니다. 이 표를 문서가 아니라 **코드로 갖고 있어야** 합니다.

## 7. 자주 하는 오해

| 오해 | 실제 |
|---|---|
| "노드에 버전 하나 두면 안전하다" | 안전하긴 한데 가짜 충돌로 처리량이 죽는다. 안전과 정확은 다르다 |
| "엣지마다 버전 두면 정밀하다" | 단일 값 제약과 노드 삭제를 못 잡는다. 정밀한 게 아니라 시야가 좁은 것 |
| "논리 단위면 완벽하다" | 멱등 검사 없이는 5/6이다 |
| "충돌이 나면 예외가 뜬다" | 0행 갱신으로 조용히 온다. `rowcount`를 봐야 한다 |
| "단위만 정하면 끝" | 감지는 기술 문제, **해결은 도메인 문제**다 (`ex5`) |

> 노드 버전은 가짜 충돌, 엣지 버전은 단일 값 누락. 그 사이가 정답이다.
