# 엣지 버전은 왜 단일 값 관계를 못 잡는가

> **Q.** 엣지 버전을 쓰면 왜 단일 값 관계를 못 잡는가?
>
> **A.** 이서연-이끔->결제팀과 김도현-이끔->결제팀은 다른 엣지라 버전이 따로다. 둘 다 통과해 팀장이 둘이 된다.

---

## 30초 요약

낙관적 잠금은 **「내가 읽은 버전이 아직 그대로인가」**만 확인합니다. 그래서 *버전을 어디에 붙였는지*가 곧 *무엇을 충돌로 볼 수 있는지*를 정합니다.

엣지에 버전을 붙이면 충돌 단위가 「엣지 한 줄」입니다. 그런데 단일 값 위반은 **엣지 하나 안에 들어 있지 않습니다**. `이서연-이끔->결제팀`도 정상이고 `김도현-이끔->결제팀`도 정상입니다. 둘이 *동시에 존재할 때만* 위반이죠. 서로 다른 두 엣지는 각자 버전이 따로라 서로의 버전을 건드리지 않습니다. 그래서 두 트랜잭션 다 `rowcount == 1`로 성공하고, 결제팀 팀장이 두 명이 됩니다.

핵심은 이겁니다. **엣지 버전의 실패는 「과소 감지(false negative)」입니다.** 에러가 안 납니다. 재시도도 안 걸립니다. 로그에는 성공만 찍히고, 불변식만 조용히 깨져 있습니다.

## 1. 먼저: 낙관적 잠금이 실제로 확인하는 것

31.2절에서 본 낙관적 잠금은 이 한 줄이 전부입니다.

```sql
UPDATE node SET props=?, version=version+1
 WHERE id=? AND version=?     -- ← 이 조건이 전부다
```

- 버전이 그대로면 1행이 갱신됩니다 → 성공
- 그 사이 남이 고쳤으면 **0행**이 갱신됩니다 → 충돌 신호 (에러가 아니라 `rowcount`)

여기서 놓치기 쉬운 게 있습니다. 이 `WHERE` 절이 볼 수 있는 건 **자기가 잠근 그 한 줄뿐**이라는 점입니다. 다른 줄이 어떻게 바뀌었는지는 이 조건이 알 수 없습니다.

관계형 DB에서는 이게 별문제가 안 됩니다. 충돌 단위가 「행 하나」로 명확하니까요. 그래프에서는 다릅니다. 엣지는 **두 노드에 걸쳐 있어서** 「무엇이 한 단위인가」부터 애매합니다. 31.3절의 주제가 정확히 이것입니다.

## 2. 문제의 시나리오를 한 줄씩 따라가기

시작 상태: 결제팀에 아직 팀장 엣지가 없습니다. 도메인 규칙은 **「한 팀의 팀장은 한 명」**입니다(28장의 `SINGLE = {"이끔"}`).

| 시각 | 에이전트 A | 에이전트 B |
|---|---|---|
| t0 | `이서연-이끔->결제팀` 엣지의 상태를 읽는다 → **없음** | `김도현-이끔->결제팀` 엣지의 상태를 읽는다 → **없음** |
| t1 | 모델 호출 / 판단 (수백 ms ~ 수 초) | 모델 호출 / 판단 |
| t2 | 「이 엣지 버전이 그대로면 만든다」 → **성공 (1행)** | |
| t3 | | 「이 엣지 버전이 그대로면 만든다」 → **성공 (1행)** |
| 결과 | \_ | 결제팀 팀장 = 이서연 **그리고** 김도현 |

B의 검사는 왜 통과했을까요? B가 확인한 건 `김도현-이끔->결제팀`이라는 **자기 엣지**의 버전입니다. A가 만든 건 `이서연-이끔->결제팀`이라는 **다른 엣지**고요. B의 엣지는 t0 이후 아무도 건드리지 않았습니다. 그러니 버전이 그대로인 게 맞습니다. **검사는 정확히 정답을 냈습니다. 다만 틀린 것을 검사한 겁니다.**

> 충돌이 두 엣지 **사이의 관계**에 있는데, 버전은 엣지 **안**에 있습니다. 단위가 위반보다 작으면 위반이 단위 사이 틈으로 빠져나갑니다.

## 3. 세 가지 버전 배치의 성적표 (ex4)

`ex4_conflict_shape.py`가 여섯 경우를 세 방식으로 판정합니다.

| 경우 | 노드 버전 | 엣지 버전 | 논리 단위 | 원하는 것 |
|---|---|---|---|---|
| 같은 엣지의 속성 | 막음 | 막음 | 막음 | 막음 |
| 한 노드의 다른 엣지 | 막음 ✗ | 통과 | 통과 | 통과 |
| **단일 값 관계** | 막음 | **통과 ✗** | 막음 | **막음** |
| 노드 삭제 대 엣지 추가 | 막음 | 통과 ✗ | 막음 | 막음 |
| 양쪽에서 같은 엣지 추가 | 막음 ✗ | 막음 ✗ | 막음 ✗ | 통과 |
| 서로 다른 방향 | 막음 ✗ | 통과 | 통과 | 도메인이 정함(여기선 통과) |
| **맞은 개수** | 2/6 | 4/6 | **5/6** | |

**어느 것도 6/6이 아닙니다. 그게 이 표의 요점입니다.**

- **노드 버전**은 단위가 너무 **큽니다**. 이서연 노드에 두 사람이 각각 *다른* 엣지를 다는데 노드 버전이 부딪힙니다. 실제로는 안 겹치는데 막힙니다 → **가짜 충돌(false positive)**.
- **엣지 버전**은 단위가 너무 **작습니다**. 여러 엣지에 걸친 불변식을 볼 수가 없습니다 → **과소 감지(false negative)**.
- **논리 단위(「주어 + 관계 종류」)**가 5/6으로 제일 낫습니다. 남은 하나(양쪽에서 같은 엣지 추가)는 버전 비교 **전에** 멱등 검사를 두면 6/6이 됩니다. 「쓰려는 것이 이미 있는 것과 같으면 그냥 성공으로 친다」 한 줄이면 됩니다(21장 멱등성).

## 4. 이 카드의 진짜 초점: 두 실패는 **급이 다르다**

노드 버전의 실패와 엣지 버전의 실패를 같은 무게로 보면 안 됩니다.

| | 노드 버전 (가짜 충돌) | 엣지 버전 (단일 값 누락) |
|---|---|---|
| 실패 종류 | 과잉 감지 (false positive) | **과소 감지 (false negative)** |
| 겉으로 드러나나 | 예 — 충돌/재시도가 튄다 | **아니오 — 성공만 찍힌다** |
| 회복 경로 | 재시도하면 결국 통과한다 | **없다. 재시도할 일 자체가 안 생긴다** |
| 남는 피해 | 지연·처리량 손해 | **데이터에 남는 잘못된 사실** |
| 언제 알게 되나 | 즉시 (지표에 뜬다) | **한참 뒤, 엉뚱한 곳에서** |

가짜 충돌은 **시끄럽게 틀립니다**. 재시도 카운터가 오르고, 처리량이 떨어지고, 지표를 보면 보입니다. 아프지만 **자기가 아프다고 말해 줍니다**.

단일 값 누락은 **조용히 틀립니다**. 그래프에는 팀장이 두 명 들어앉아 있는데, 시스템 어디에도 「이상하다」는 신호가 없습니다. 이건 31.1절의 잃어버린 갱신과 성질이 똑같습니다.

> 「에러가 안 난다. 로그에도 «성공»만 찍힌다. 그게 이 문제의 성질이다.」 — ex1

차이가 하나 있다면 잃어버린 갱신은 *변경이 사라지는* 것이고, 이건 *있으면 안 되는 상태가 남는* 것입니다. 후자가 더 나쁩니다. 사라진 변경은 다음 동기화가 다시 채워 줄 수도 있지만, 잘못 들어간 팀장 엣지는 **아무도 지워 주지 않고** 그 위에 후속 판단이 계속 쌓이기 때문입니다. 「결제팀 팀장에게 승인 요청」 같은 흐름이 두 사람에게 가고, 그 결과가 또 다른 엣지를 낳습니다.

그리고 27장의 문제로 이어집니다. 에이전트가 이 그래프를 기억으로 읽으면, **틀린 사실을 근거로 확신 있게 판단**합니다. 27장 이후의 시스템에서 조용한 불변식 위반이 특히 비싼 이유가 이것입니다.

**여기서 얻어 갈 규칙:** 감지 단위를 고를 때는 「틀렸을 때 어느 방향으로 틀리는가」를 먼저 보세요. **시끄럽게 틀리는 쪽이 조용히 틀리는 쪽보다 항상 낫습니다.**

## 5. 28장 SINGLE_VALUED와의 연결 — 같은 목록이 두 문제를 푼다

28장(에이전트가 스스로 그래프를 넓히다)에서 추출 후보를 거르는 관문 넷 중 4번이 **단일 값 관문**이었습니다.

```python
SINGLE = {"이끔"}          # 팀장은 한 명

    # 4) 단일 값 — 이미 다른 값이 있나
    if k in SINGLE:
        r = c.execute("MATCH (a:N {name:$s})-[e:R {kind:$k}]->(b:N) "
                      "RETURN b.name", {"s": s, "k": k})
        while r.has_next():
            if r.get_next()[0] != o:
                return False, "4.단일값충돌"
```

28장에서 이 목록이 푼 문제는 **「추출기가 자신 있게 틀린 것」**이었습니다. `박민수-이끔->정산팀`(0.87)은 확신도도 높고 스키마도 맞아서(Person → Team) 앞의 관문들이 전부 통과시킵니다. 박민수가 이미 결제팀을 이끌고 있다는 걸 아는 건 단일 값 관문뿐입니다.

31장에서 **같은 목록**이 푸는 문제는 **「동시 쓰기의 충돌 단위」**입니다. `SINGLE`에 들어 있는 관계 종류는 엣지 하나가 충돌 단위가 될 수 **없다**는 뜻이고, 그래서 이 목록이 곧 **「논리 단위로 묶어야 할 관계 목록」**이 됩니다.

```
단일 값 관계 (SINGLE에 있음) → 「주어 + 관계 종류」를 한 단위로 본다
다중 값 관계                 → 엣지 하나가 한 단위
노드 삭제                    → 그 노드에 걸린 모든 엣지와 충돌
```

> 「이 표를 코드로 갖고 있어야 한다. 28장의 SINGLE_VALUED 목록이 여기서 다시 쓰인다. **같은 목록이 두 문제를 푼다.**」 — ex4

이게 왜 중요하냐면, 두 문제를 **따로** 풀면 목록이 두 벌 생기고 반드시 갈라지기 때문입니다. 28장 목록에 관계를 추가하고 31장 목록에는 안 넣으면, 추출은 막히는데 동시 쓰기는 새는 상태가 됩니다. **기수(cardinality)는 온톨로지의 사실이지 특정 코드 경로의 설정이 아닙니다.** 한 곳에 두고 양쪽이 참조해야 합니다.

그리고 28장에는 이 카드에 그대로 이어지는 조언이 하나 더 있습니다.

> 「단일 값 충돌을 자동으로 덮어쓰지 마세요. 오답이 정답을 지웁니다. 둘 다 살려 두고 사람에게 보내세요.」

31장 ex5의 결론과 같은 말입니다. **감지는 기술 문제라 일반 해법이 있고, 해결은 도메인 문제라 없습니다.** 그래서 이 카드가 다루는 건 「감지」 단계입니다. 감지부터 못 하면 해결 전략을 아무리 잘 짜도 호출될 일이 없습니다.

## 6. 그래서 어떻게 고치나

논리 단위를 **버전 행으로 실체화(materialize)**합니다. 즉 「(주체, 관계 종류)」를 키로 하는 버전 레코드를 따로 두고, 그 행에 낙관적 잠금을 겁니다.

```python
# 개념 스케치 — 실제 스키마는 저장소에 맞게
# (owner, kind) 하나당 버전 행 하나
#   ('결제팀', '이끔')  ← 팀 쪽이 단일이면 팀이 owner

def write_single_valued(conn, owner, kind, target, seen_ver):
    # 0) 멱등 먼저 — 결과가 같으면 그냥 성공 (21장)
    if current_target(conn, owner, kind) == target:
        return "ok(멱등)"

    # 1) 논리 단위의 버전을 조건으로 건다
    cur = conn.execute(
        "UPDATE rel_unit SET ver = ver + 1 "
        " WHERE owner = ? AND kind = ? AND ver = ?",
        (owner, kind, seen_ver))
    if cur.rowcount == 0:          # ← 0행이 충돌 신호
        return "conflict"          # 다시 읽고 재시도, 또는 사람에게

    # 2) 여기서만 엣지를 실제로 바꾼다
    replace_edge(conn, owner, kind, target)
    return "ok"
```

세 가지가 다 들어 있습니다.

1. **멱등 검사가 버전 비교보다 먼저** — 그래야 「양쪽에서 같은 엣지 추가」가 헛충돌하지 않고 6/6이 됩니다.
2. **버전 조건은 엣지가 아니라 논리 단위에** — 이제 이서연 쪽 쓰기와 김도현 쪽 쓰기가 **같은 행**을 놓고 다툽니다. 하나는 반드시 0행을 받습니다.
3. **`rowcount`를 본다** — 충돌은 예외로 오지 않습니다.

그리고 31.3절의 실무 요령을 같이 씁니다. **모델 호출은 잠금 밖에서** 하고, 잠금 안에서는 버전 확인과 쓰기만 합니다. 판단 시간이 12ms에서 1.5ms로 줄면 창이 좁아져 충돌률 자체가 떨어지고, 낙관적↔비관적이 뒤집히는 지점(15~30%)이 오른쪽으로 밀립니다.

### 주의: 단일 값의 **방향**을 확인하세요

이 카드의 예시는 헷갈리기 쉬운 지점을 담고 있습니다.

- 28장의 예: `박민수-이끔->결제팀` vs `박민수-이끔->정산팀` → 다투는 건 **주어(박민수)** 쪽. 「한 사람은 한 팀만 이끈다」
- 31장의 예: `이서연-이끔->결제팀` vs `김도현-이끔->결제팀` → 다투는 건 **목적어(결제팀)** 쪽. 「한 팀의 팀장은 한 명」

논리 단위의 owner를 **제약이 걸린 쪽**으로 잡아야 합니다. 31장 예시에서 무심코 「주어 + 관계 종류」로 잡으면 `(이서연, 이끔)`과 `(김도현, 이끔)`이 되어 **여전히 서로 다른 단위**입니다. 엣지 버전과 똑같이 새는 거죠. 여기서는 `(결제팀, 이끔)`이 단위여야 합니다. 양쪽 모두 단일이면(1:1 관계) 두 단위를 다 걸어야 하고, 그러면 잠금 순서를 고정해 교착(deadlock)을 피해야 합니다.

## 7. 자주 하는 오해

**「직렬화 가능(serializable) 격리로 올리면 되지 않나?」**
그러면 잡힙니다 — DB 안에서 한 트랜잭션으로 끝나는 경우엔요. 하지만 31장의 전제가 그게 아닙니다. **트랜잭션 안에 모델 호출이 들어가고, 워크플로는 프로세스 경계를 넘어 살아 있습니다.** 초 단위 트랜잭션을 열어 두면 쓰기 편중(write skew)은 막아도 처리량이 무너지고, 프로세스가 죽으면 트랜잭션도 같이 죽습니다(21장). 그래서 애플리케이션 층의 낙관적 잠금이 필요하고, 그 순간 **「무엇을 한 단위로 볼지」는 우리가 정해야 할 설계 결정**이 됩니다.

**「엣지 버전이 그냥 나쁜 거 아닌가?」**
아닙니다. 4/6으로 노드 버전(2/6)보다 낫습니다. 다중 값 관계(`속함`, `선호`, `태그` 등)에서는 엣지 하나가 정확히 맞는 단위입니다. 문제는 **단 하나의 방식으로 전부 처리하려 할 때** 생깁니다. 관계 종류마다 단위를 정해 두는 것 — 그게 이 절의 결론입니다.

**「나중에 배치로 검사하면 되지 않나?」**
사후 검사는 있어야 합니다. 다만 그건 **탐지**지 **예방**이 아닙니다. 검사가 도는 사이 에이전트들은 이미 그 잘못된 사실 위에서 판단을 쌓았고, 그 판단들은 되돌려야 합니다(22장 보상 트랜잭션). 그리고 발견한 뒤 「이서연과 김도현 중 누가 맞나」는 여전히 도메인 문제로 남습니다. 예방이 훨씬 쌉니다.

---

## 8. 한 줄로

**엣지 버전은 「이 엣지가 안 바뀌었나」만 묻는다. 단일 값 위반은 서로 다른 두 엣지 사이에 있어서 그 질문의 사각지대에 놓인다. 그래서 둘 다 성공으로 통과하고, 팀장이 조용히 두 명이 된다.** 고치려면 28장 `SINGLE_VALUED` 목록을 그대로 가져와 「제약이 걸린 쪽 + 관계 종류」를 한 충돌 단위로 삼고, 그 앞에 멱등 검사를 둔다.
