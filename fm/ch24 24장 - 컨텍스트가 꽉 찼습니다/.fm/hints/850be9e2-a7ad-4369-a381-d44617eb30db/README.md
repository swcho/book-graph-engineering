# `ex4_offload.py`의 결과가 21장 측정과 어떻게 연결되는가

## 한 줄 답

21장에서 「32KB를 넘으면 체크포인터 비용이 꺾인다」고 측정했다. `ex4_offload.py`에서 본문을 상태에 실으면 그 선을 한참 넘고, 참조만 실으면 그 아래로 내려간다.

---

## 1. 21장이 잰 것 — 32KB라는 꺾이는 지점

21장 예제는 노드 12개짜리 그래프에 더미 페이로드를 실어 나르며, 메모리 체크포인터 대비 SQLite 체크포인터가 몇 배 느린지를 상태 크기별로 쟀다.

| 상태 크기 | SQLite / 메모리 배수 |
|---|---|
| 0B ~ 32,000B | 2.0 ~ 2.8배로 거의 평평 |
| 그 이후(256,000B) | 꺾여서 급격히 커짐 |

작은 구간이 평평한 이유는 **「쓰기 호출 자체」가 비용을 지배**하기 때문이다. 슈퍼스텝마다 트랜잭션을 여는 고정비가 상태 크기와 무관하게 붙는다. 그래서 21장의 결론은 구간별로 갈렸다.

- **32KB 미만** — 상태를 줄여도 소용없다. 줄일 것은 「슈퍼스텝 수」다.
- **32KB 이상** — 상태를 줄이는 것이 바로 듣는다.

이 「32KB」가 24장에서 되갚아지는 기준선이다.

## 2. `ex4_offload.py`가 잰 것 — 상태에 무엇을 싣는가

같은 상황을 24장 쪽에서 다시 만든다. 문서 6편(각 4만 자)을 12단계 그래프에서 다루면서, 두 가지 방식의 **상태 크기**와 **직렬화 시간**을 비교한다.

```python
DOC = "가" * 40_000          # 문서 한 편 (본문 4만 자)
N_DOCS = 6
N_STEPS = 12
```

- `run_inline` — 본문을 상태에 통째로 싣는다.
  ```python
  state["docs"].append({"id": f"doc-{step}", "body": body})
  ```
- `run_ref` — 참조(id, 길이, 앞머리 40자)만 싣고, 마지막에 실제로 필요한 한 편만 DB에서 꺼낸다.
  ```python
  state["docs"].append({"id": f"doc-{step}", "len": len(DOC), "head": DOC[:40]})
  ```

두 경우 모두 슈퍼스텝마다 `json.dumps(state)`로 직렬화한다. 이 직렬화가 곧 체크포인터가 매 슈퍼스텝 하는 일의 대역이다.

### 실행 결과 (참고값, 머신에 따라 시간은 달라짐)

| 방식 | 상태 크기 | 직렬화 시간 | 문서 조회 |
|---|---|---|---|
| 본문을 상태에 | 720,203B | 6.8ms | 0 |
| 참조만 상태에 | 1,007B | 0.2ms | 1 |

상태 크기 약 **715배** 차이, 직렬화 시간 약 **30배** 차이다.

> 참고: 한글 「가」는 UTF-8에서 3바이트라 4만 자 × 3바이트 × 6편 ≈ 72만 바이트가 된다. `ensure_ascii=False`이므로 이스케이프 없이 그대로 실린다.

## 3. 두 측정이 만나는 지점

21장의 기준선(32KB = 32,768B) 위에 24장의 두 숫자를 올려 보면 이렇게 된다.

```
0 ────── 32KB ────────────────────────────── 720KB
         ↑ 꺾이는 지점
  ●1,007B                                    ● 720,203B
  참조만 (약 0.03배 — 한참 아래)          본문 (약 22배 — 한참 위)
```

- **본문을 실은 상태 720,203B** → 32KB의 약 22배. 21장이 「여기서부터는 상태를 줄이는 것이 바로 듣는다」고 말한 구간의 깊숙한 안쪽이다. 즉 체크포인터가 매 슈퍼스텝마다 비싼 값을 치르고 있다.
- **참조만 실은 상태 1,007B** → 32KB의 약 0.03배. 꺾이는 지점 아래, 고정비가 지배하는 평평한 구간이다.

그래서 본문 대신 참조를 싣는 순간, 21장 그래프에서 오른쪽 비탈에 있던 점이 왼쪽 평지로 이동한다. 이것이 24.4절 「상태에는 참조만 싣는다」가 21장을 되갚는 방식이다.

## 4. 왜 이 연결이 중요한가 — 같은 일이었다

`ex4_offload.py`의 결론 문장이 핵심이다.

> 두 장의 얘기가 여기서 만난다. 「컨텍스트를 줄이는 일」과 「체크포인트를 싸게 만드는 일」이 같은 일이었다.

원래 별개로 보이던 두 문제다.

| 문제 | 증상 | 24장/21장 |
|---|---|---|
| 컨텍스트가 찬다 | 매 턴 보내는 토큰이 늘어 비용이 제곱으로 자람 | 24장 |
| 체크포인트가 느리다 | 슈퍼스텝마다 큰 상태를 직렬화·기록 | 21장 |

둘 다 **「상태에 본문을 싣고 다닌다」**는 하나의 원인에서 나온다. 참조만 싣는 한 번의 조치로 컨텍스트도 줄고 체크포인트도 싸진다. 24장 「한 장 요약」이 「두 문제가 사실 같은 문제였어요」라고 적은 이유다.

## 5. 공짜는 아니다 — 치르는 값과 판단 기준

참조만 싣는 대가는 **조회 한 번**이다. `run_ref`의 `reads=1`이 그 값이다.

```python
if step == N_STEPS - 1:          # 마지막에 실제로 한 편만 읽는다
    db.execute("SELECT body FROM doc WHERE id=?", ("doc-2",)).fetchone()
```

거꾸로, 6편을 다 실어 놓고 1편만 썼다면 나머지 5편은 그냥 짐이었다. 그래서 판단 기준은 중요도가 아니라 **「몇 번 쓰나」**다.

| 사용 빈도 | 처방 |
|---|---|
| 거의 매 단계 쓴다 | 상태에 싣는다 |
| 가끔 한 번 쓴다 | 참조만 싣고 그때 꺼낸다 |
| 안 쓸 수도 있다 | 참조도 싣지 말고 색인만 남긴다 |

## 6. 흔히 놓치는 함정

- **32KB는 절대 상수가 아니다.** 21장 측정은 특정 환경(LangGraph 1.0.1, SQLite, 12단계)에서 나온 값이다. 21장 스스로 「재 보기 전에는 어느 구간에 있는지 모른다」고 못 박는다. 24장이 인용하는 것은 정확한 숫자가 아니라 **꺾이는 지점이 존재한다는 사실**이다.
- **1,007B까지 내렸다고 더 줄일 이유는 없다.** 이미 32KB 아래이므로 21장 규칙에 따르면 상태를 더 줄여도 소용없다. 그 구간에서 더 빠르게 하려면 「슈퍼스텝 수」를 줄여야 한다.
- **체크포인터 종류를 바꾸는 것은 해결이 아니다.** 21장은 「지연이 문제면 줄일 곳은 상태 크기지 체크포인터 종류가 아니다」라고 했다. 메모리 체크포인터는 프로세스가 죽으면 사라지므로 체크포인터가 아니라 캐시다.
