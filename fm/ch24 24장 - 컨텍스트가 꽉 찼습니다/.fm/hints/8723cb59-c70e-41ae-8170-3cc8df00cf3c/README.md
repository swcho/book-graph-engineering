# 컨텍스트 축소와 체크포인트 비용의 관계

## 카드

**질문** — 컨텍스트 축소와 체크포인트 비용의 관계는 무엇인가?

**답** — 같은 문제다. 상태에서 본문을 빼면 컨텍스트도 줄고 체크포인트 직렬화도 싸진다.

---

## 왜 「같은 문제」인가

두 문제는 서로 다른 장에서, 서로 다른 증상으로 등장했습니다.

| | 24장의 증상 | 21장의 증상 |
|---|---|---|
| 아픈 곳 | 매 턴 LLM에 보내는 토큰이 불어남 | 슈퍼스텝마다 체크포인트 저장이 느려짐 |
| 청구되는 것 | 입력 토큰 요금 | 직렬화 CPU + 스토리지 I/O |
| 눈에 띄는 시점 | 대화가 길어질 때 | 그래프 단계가 많아질 때 |

그런데 **원인이 하나**입니다. 그래프 상태(state) 딕셔너리 안에 문서 본문, 도구 출력, 크롤링 결과 같은 **덩치 큰 원문이 통째로 들어 있다**는 것.

- 상태 안의 내용은 다음 노드로 넘어갈 때 **프롬프트에 실려서** 모델로 갑니다 → 토큰 비용.
- 상태 안의 내용은 **슈퍼스텝마다 JSON으로 직렬화되어** 체크포인터에 저장됩니다 → 직렬화 비용.

같은 바이트가 두 군데서 두 번 청구되는 셈입니다. 그러니 상태에서 본문을 빼는 한 번의 조치가 두 비용을 동시에 깎습니다. 반대로 말하면, 컨텍스트만 줄이겠다고 프롬프트 조립 단계에서만 잘라 내고 상태에는 본문을 그대로 남겨 두면 체크포인트 비용은 하나도 안 줄어듭니다.

## 해법: 상태에는 참조만 싣는다 (오프로딩)

본문은 밖(DB, 오브젝트 스토리지, 파일)에 두고, 상태에는 **꺼내 올 수 있는 최소 정보**만 남깁니다.

```python
# 나쁜 쪽 — 본문을 상태에
state["docs"].append({"id": "doc-3", "body": body})       # 4만 자가 통째로

# 좋은 쪽 — 참조만 상태에
state["docs"].append({"id": "doc-3",
                      "len": len(body),
                      "head": body[:40]})                  # 식별자 + 크기 + 미리보기
```

`head`(앞 40자)를 같이 넣는 이유는, 모델이 **꺼내 오지 않고도 「이게 내가 찾던 문서인가」를 판단**할 수 있게 하기 위함입니다. 색인의 품질이 곧 조회의 정확도입니다.

## 예제로 확인한 숫자 (`code/ex4_offload.py`)

문서 6편(각 4만 자)을 12단계 그래프에서 다루는 실험입니다.

| 방식 | 상태 크기 | 직렬화 시간 | 문서 조회 |
|---|---|---|---|
| 본문을 상태에 | 720,203 B | 6.6 ms | 0회 |
| 참조만 상태에 | 1,007 B | 0.2 ms | 1회 |

상태 크기 **약 715배**, 직렬화 시간 **약 30배** 차이입니다.

여기서 21장이 다시 등장합니다. 21장에서 **「상태가 32KB를 넘으면 체크포인터 비용 곡선이 꺾인다」**고 측정했었죠.

- 본문을 실으면 720KB → 꺾이는 지점을 **한참** 넘습니다.
- 참조만 실으면 1KB → 꺾이는 지점 **아래**입니다.

즉 「상태에서 본문 빼기」라는 한 수가 컨텍스트 토큰과 체크포인트 지연을 동시에 임계선 아래로 내려놓습니다.

## 공짜는 아니다 — 치르는 값

오프로딩의 대가는 **조회(read)가 한 번 더 든다**는 것입니다. 위 실험에서도 마지막 단계에 `doc-2` 본문을 실제로 한 번 읽어 옵니다.

그리고 조회는 두 가지로 실패할 수 있습니다.

1. **불필요한 조회** — 안 써도 될 걸 꺼내 오면 오프로딩의 이득이 상쇄됩니다.
2. **틀린 조회** — 엉뚱한 문서를 꺼내 오면, 차라리 요약해서 갖고 있던 것보다 나쁩니다(`ex2_strategies.py`의 경고).

## 판단 기준: 중요도가 아니라 「몇 번 쓰나」

24장이 반복하는 원칙입니다. 「이게 중요한가」로 정하면 취향이 들어가고, 애초에 중요한 것은 이미 최근 컨텍스트에 있습니다. 대신 **접근 빈도**로 자릅니다.

| 사용 빈도 | 두는 곳 |
|---|---|
| 거의 매 단계 쓴다 | 상태에 본문째 싣는다 |
| 가끔 한 번 쓴다 | 참조만 싣고 그때 꺼낸다 |
| 안 쓸 수도 있다 | 참조도 빼고 색인만 남긴다 |

예외 하나. **사용자가 명시한 제약**은 사용 횟수와 무관하게 남깁니다. 제약이 사라지면 에이전트가 금지된 일을 다시 시도하니까요(`ex3_summary_drift.py`).

## 딸려 오는 이득: 요약을 안전하게 만든다

`ex3_summary_drift.py`는 요약을 반복하면 회차마다 생존율이 곱해져서 5회 만에 23%만 남고, 그중에서도 **이유와 제약이 제일 먼저** 날아간다는 걸 보여 줍니다. 대응책은 「요약의 요약을 하지 말고 **매번 원문에서 다시 요약**한다」인데 — 이게 가능하려면 **원문을 밖에 갖고 있어야** 합니다.

그래서 순서가 「오프로딩이 먼저, 요약은 그다음」입니다. 오프로딩은 토큰·체크포인트 비용만 깎는 게 아니라, 요약 품질 저하를 막는 전제 조건이기도 합니다.

## 한 줄 정리

컨텍스트가 크다는 것과 체크포인트가 비싸다는 것은 **「상태가 뚱뚱하다」는 한 가지 사실의 두 가지 증상**입니다. 본문을 상태 밖으로 빼고 참조만 남기면 둘이 함께 해결되고, 대신 조회 한 번의 값을 치릅니다.
