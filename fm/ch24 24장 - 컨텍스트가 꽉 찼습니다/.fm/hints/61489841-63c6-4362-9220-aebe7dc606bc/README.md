# 청구서가 예상의 6.4배로 나온 이유

**질문**: 저자의 청구서가 예상의 6.4배로 나온 원인은 무엇이었는가?

**답**: 20턴 기준으로 산정했는데 실제 사용자는 평균 47턴을 썼다. 매 턴 전체 대화를 다시 보내므로 비용이 급증했다.

---

## 1. 사건의 전말

24장은 이 한 줄로 시작합니다.

> 한 달 청구서가 예상의 6.4배로 나왔습니다.

로그를 열자마자 원인이 보였습니다. **대화가 길어질수록 매 턴 보내는 양이 늘어나고 있었던 것**입니다.

- 저자 팀이 잡은 기준: **20턴짜리 대화 = 8,000토큰**. 이 수치 자체는 맞았습니다.
- 실제 사용자: **평균 47턴**.
- 20턴을 기준으로 잡은 근거: **없었습니다.** 테스트할 때 그 정도만 해 봤을 뿐이었습니다.

즉 원인은 두 겹입니다.

| 층위 | 내용 |
|---|---|
| 표면 원인 | 가정한 대화 길이(20턴)와 실제 사용 길이(47턴)의 괴리 |
| 진짜 원인 | 턴이 늘면 비용이 **선형이 아니라 제곱**으로 자라는 구조 |

두 번째가 없으면 사고가 이 정도로 커지지 않습니다. 47/20 = 2.35배니까, 비용이 선형이었다면 청구서는 2.35배에서 멈췄어야 합니다. 그런데 6.4배가 나왔습니다.

## 2. 왜 제곱인가 — 매 턴 전체 대화를 다시 보낸다

LLM API는 상태가 없습니다(stateless). 서버가 이전 대화를 기억해 주지 않으므로, **매 턴 지금까지의 대화 전체를 입력으로 다시 실어 보내야** 합니다.

그래서 이런 일이 벌어집니다.

- 1턴째: 1턴 분량을 보낸다
- 2턴째: 1+2턴 분량을 보낸다
- 3턴째: 1+2+3턴 분량을 보낸다
- …
- N턴째: 1+…+N턴 분량을 보낸다

**대화 길이**(한 시점에 창에 들어 있는 양)는 턴마다 비슷한 양이 붙으니 **선형**입니다. 그런데 **누적으로 보낸 입력 토큰**은 그 길이를 매 턴 다시 더한 값이므로 등차수열의 합, 즉 대략 `N(N+1)/2`에 비례합니다. 이게 **제곱** 증가입니다.

```
누적 입력 ∝ N²   →   턴이 2배가 되면 비용은 4배
```

47/20 = 2.35배의 턴은 (2.35)² ≈ **5.5배**의 누적 입력을 뜻합니다. 여기에 도구 결과가 붙는 턴, 출력 토큰 단가(입력의 5배) 같은 실제 분포가 얹히면 **6.4배**가 됩니다. 책의 6.4배는 실제 청구서 수치이고, 아래 단순 모델은 그 메커니즘을 재현하는 계산입니다.

## 3. 예제로 확인하기 — `code/ex1_growth.py`

이 장의 첫 예제가 정확히 이 계산을 합니다. 핵심은 루프 안의 이 한 줄입니다.

```python
for t in range(1, turns + 1):
    history += TURN_IN
    if t % TOOL_EVERY == 0:
        history += TOOL_OUT
    # 매 턴 전체 대화를 다시 보낸다
    sent_in += history          # ← 여기서 제곱이 생긴다
    sent_out += TURN_OUT
    history += TURN_OUT
```

`history`(대화 길이)는 턴마다 조금씩 늘어날 뿐이지만, `sent_in`은 그 `history`를 **매 턴 통째로 누적**합니다. 선형으로 자라는 값을 N번 더하니 제곱이 됩니다.

예제의 가정(사용자 220토큰/턴, 모델 380토큰/턴, 3턴마다 도구 결과 1,400토큰, 입력 $3/1M·출력 $15/1M, 1,380원/달러, 창 200K)으로 돌린 결과에 47턴을 끼워 넣어 보면:

| 턴 | 대화 길이 | 누적 입력 | 누적 비용 | 창 사용률 |
|---:|---:|---:|---:|---:|
| 1 | 600 | 220 | 9원 | 0% |
| 5 | 4,400 | 11,300 | 86원 | 2% |
| 10 | 10,200 | 50,200 | 286원 | 5% |
| **20** | 20,400 | **206,600** | **1,013원** | 10% |
| 40 | 42,200 | 840,800 | 3,796원 | 21% |
| **47** | 49,200 | **1,162,940** | **5,184원** | 25% |
| 80 | 84,400 | 3,387,800 | 14,655원 | 42% |
| 120 | 128,000 | 7,642,400 | 32,583원 | 64% |

읽는 법:

- **대화 길이** 열은 20턴 → 47턴에서 20,400 → 49,200, 약 2.4배. 턴 수 비율(2.35배)과 거의 같습니다. 선형입니다.
- **누적 입력** 열은 206,600 → 1,162,940, 약 **5.6배**. 같은 구간인데 배수가 완전히 다릅니다. 제곱입니다.
- 20턴 → 80턴(4배)에서는 비용이 1,013원 → 14,655원, 약 **14.5배**입니다. 4² = 16에 가깝습니다.

**직관이 배신하는 지점이 바로 여기입니다.** "사용자가 예상보다 두 배 넘게 오래 쓰네" 정도의 체감이, 청구서에서는 6배로 나타납니다.

## 4. 함께 기억할 교훈 — "창이 남았으니 괜찮다"가 아니다

예제 1의 마지막 열(창 사용률)이 이 장의 두 번째 못입니다.

- 120턴에서도 컨텍스트 창은 64%밖에 안 찼습니다. 기술적으로는 아무 문제가 없습니다.
- 그런데 그 지점의 누적 비용은 20턴 대비 32배입니다.

> 「아직 창이 남았으니 괜찮다」가 아니다. **비용은 창이 차기 훨씬 전에 문제가 된다.**

컨텍스트 관리를 "창이 넘칠까 봐" 하는 일로 생각하면 늦습니다. 창이 넘치는 건 에러로 즉시 드러나지만, 비용은 조용히 새다가 월말에 한 번에 청구됩니다.

## 5. 그래서 뭘 해야 하나

이 사건이 24장 나머지 절들의 출발점입니다.

| 절 | 대응 |
|---|---|
| 24.2 | 줄이는 네 방법(그대로 두기 / 최근 N턴만 / 요약 / 오프로딩)을 **절감률과 사실 보존율을 같이** 재서 고른다 |
| 24.3 | 요약은 「이유」와 「제약」을 먼저 버린다. 요약의 요약을 하지 말고 매번 원문에서 다시 요약한다 |
| 24.4 | 상태에는 본문 말고 **참조**만 싣는다 (체크포인트 비용도 같이 내려간다) |
| 24.5 | 기억을 계층으로 나누고 위에서부터 훑는다. 「비싼 조회를 안 하는 것」이 「빠른 조회를 만드는 것」보다 크게 듣는다 |

그리고 이 사건 자체가 주는 실무 교훈이 하나 더 있습니다. **용량 산정의 기준값은 테스트에서 우연히 나온 숫자가 아니라 실제 사용 분포에서 와야 합니다.** 저자 팀이 20턴을 잡은 데는 아무 근거가 없었고, 그게 6.4배 청구서의 시작이었습니다. 게다가 평균 47턴이라면 상위 사용자는 100턴을 넘겼을 텐데, 제곱 증가 아래에서 비용은 **평균이 아니라 꼬리가 지배**합니다.

## 6. 한 줄 정리

> 20턴 기준(근거 없음) vs 실제 평균 47턴 → 턴 수는 2.35배인데, 매 턴 전체 대화를 다시 보내는 구조라 누적 입력이 제곱으로 자라 청구서는 6.4배가 되었다.
