# 요약 프롬프트에 못 박아야 할 세 가지 보존 규칙

## 질문

요약 프롬프트에 못 박아야 할 세 가지 보존 규칙은 무엇인가?

## 답

1. **숫자는 원문 그대로 옮긴다** — 「약 300만 원」 같은 반올림·근사 표현 금지
2. **결정에는 반드시 이유를 붙인다** — 「~하기로 했다」만 남기지 말고 「왜」를 함께
3. **금지 사항은 요약하지 않고 목록으로 따로 뺀다** — 제약은 압축 대상에서 제외

## 왜 이 세 가지인가

24.3절(`ex3_summary_drift.py`)은 사실 200개를 다섯 종류로 심어 놓고 요약을 반복했을 때 무엇이 먼저 사라지는지를 잽니다. 종류마다 **한 번 요약할 때 살아남을 확률**이 다릅니다.

| 종류 | 1회 생존 확률 | 성격 |
|---|---|---|
| 결정 | 0.90 | 「~하기로 했다」. 요약이 제일 잘 지킨다 |
| 고유명사 | 0.80 | 이름. 비교적 잘 남는다 |
| 숫자 | 0.55 | 금액·개수. 요약이 「대략」으로 바꾼다 |
| 제약 | 0.50 | 「~는 하면 안 된다」. 잘 날아간다 |
| 이유 | 0.45 | 「왜 그렇게 했나」. 제일 먼저 날아간다 |

한 번 요약하면 전체의 68%가 남습니다. 나쁘지 않아 보이죠. 그런데 회차마다 확률이 **곱해지기** 때문에 다섯 번 반복하면 23%만 남습니다. 더 중요한 건 「무엇이」 남느냐입니다. 「이유」와 「제약」은 네 번 만에 5%, 6%까지 떨어지고 다섯 번이면 0이 됩니다. 요약 모델이 근거를 군더더기로 보기 때문입니다.

즉 세 규칙은 **생존 확률이 낮은 하위 세 종류를 정확히 겨냥한 처방**입니다. 결정·고유명사는 가만히 둬도 살아남으니 프롬프트 예산을 쓸 이유가 없고, 숫자·이유·제약은 명시적으로 못 박지 않으면 조용히 사라집니다.

## 사라지면 무슨 일이 벌어지나

- **이유가 사라지면**: 결정만 남은 컨텍스트를 받은 에이전트는 「그 결정을 왜 했는지」 모른 채 **그 결정을 뒤집습니다**. 요약이 결론을 잘 보존하는 것이 오히려 함정이 됩니다. 결정은 남고 근거만 사라진 상태가 가장 위험하죠.
- **제약이 사라지면**: 「하면 안 되는 일」을 **다시 시도합니다**. 사용자가 명시적으로 금지한 행동이 몇 턴 뒤에 부활합니다.
- **숫자가 뭉개지면**: 「약 300만 원」으로 바뀐 값은 검증도 재계산도 불가능합니다. 게다가 근사값은 그럴듯해 보여서 틀렸다는 신호조차 주지 않습니다.

각 규칙이 처방하는 방식도 종류에 맞춰져 있습니다.

- 숫자 → **원문 복사**를 강제(요약 대상에서 제외하고 값 자체를 옮김)
- 이유 → **결정과 짝지어** 붙이도록 강제(결정이 살아남을 때 이유가 업혀 감)
- 제약 → 아예 **본문 밖 별도 목록**으로 분리(압축 경로를 지나가지 않음)

## 세트로 따라오는 네 번째 습관

책은 세 규칙 바로 뒤에 이걸 덧붙입니다.

> 그리고 요약의 요약을 하지 않는다. 매번 「원문」에서 다시 요약한다.

손실이 곱해지는 원인이 **연쇄 요약**이기 때문입니다. 매번 원문에서 새로 요약하면 손실은 곱해지지 않고 항상 1회분에 머뭅니다. 다만 이게 가능하려면 원문을 컨텍스트 밖에 갖고 있어야 하고, 그래서 24.4절의 **오프로딩(상태에는 참조만 싣기)이 먼저**라는 순서가 나옵니다. 보존 규칙 세 가지는 요약을 덜 새게 만드는 처방이고, 오프로딩은 요약을 반복하지 않아도 되게 만드는 구조적 처방입니다.

## 시험에 잘 나오는 포인트

- 세 규칙의 **대상**을 정확히: 숫자 / 이유 / 금지 사항(제약). 「고유명사」나 「결정」이 선택지에 있으면 오답 — 이들은 요약이 알아서 잘 지킨다.
- 각 규칙의 **처방 방식**까지: 원문 그대로 / 결정에 붙여서 / 요약 없이 별도 목록.
- 규칙만으로 부족한 이유: 회차마다 손실이 곱해지므로 **요약의 요약을 금지**하고 매번 원문에서 다시 요약한다.
- 관련 원칙(24.2절): 무엇을 버릴지는 중요도가 아니라 「몇 번 참조되나」로 정하되, **사용자가 명시한 제약은 참조 횟수와 무관하게 남긴다**.
