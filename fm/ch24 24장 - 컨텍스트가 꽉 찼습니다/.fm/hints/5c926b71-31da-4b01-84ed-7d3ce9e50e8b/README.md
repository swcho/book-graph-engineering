# `ex4_offload.py`는 무엇을 비교하는가?

## 한 줄 답

문서 6편(각 4만 자)을 12단계 그래프에서 다룰 때,

- **본문을 상태에 통째로 싣는 방식**과
- **참조(`id` · `len` · 앞 40자 `head`)만 싣는 방식**의

**상태 크기(byte)와 직렬화 시간(ms)** 을 비교합니다. (곁들여 「문서 조회 횟수」도 같이 셉니다.)

---

## 왜 이 두 가지를 재는가

24.4절 「상태에는 참조만 싣는다」의 실증 예제입니다. 주제는 이겁니다.

> **컨텍스트를 줄이는 일**과 **체크포인트를 싸게 만드는 일**이 사실 같은 일이었다.

LangGraph 같은 그래프 런타임은 **슈퍼스텝마다 상태를 직렬화**해서 체크포인터에 씁니다. 그러니 상태에 무엇이 들어 있느냐가 곧

1. 모델에 실려 가는 컨텍스트 양이고,
2. 매 단계 붙는 직렬화/저장 비용

두 가지를 동시에 결정합니다. 예제는 이 둘을 갈라 재지 않고, **같은 한 축(상태 크기)** 에 걸어 두고 보여 줍니다.

---

## 실험 설정

```python
DOC = "가" * 40_000          # 문서 한 편 (본문 4만 자)
N_DOCS = 6                   # 문서 6편
N_STEPS = 12                 # 12단계 그래프
```

본문은 표준 `sqlite3`로 만든 임시 DB(`doc(id, body)`)에 미리 넣어 둡니다. 외부 의존성은 없습니다.

### 방식 A — `run_inline()`: 본문을 상태에

```python
body = db.execute("SELECT body FROM doc WHERE id=?", (f"doc-{step}",)).fetchone()[0]
state["docs"].append({"id": f"doc-{step}", "body": body})
blob = json.dumps(state, ensure_ascii=False)   # 슈퍼스텝마다 직렬화
```

앞 6단계에서 문서를 하나씩 읽어 **본문 전체**를 상태에 쌓습니다. 그리고 12단계 내내 매 슈퍼스텝 그 상태를 통째로 직렬화합니다.

### 방식 B — `run_ref()`: 참조만 상태에

```python
state["docs"].append({"id": f"doc-{step}", "len": len(DOC), "head": DOC[:40]})
...
if step == N_STEPS - 1:          # 마지막에 실제로 한 편만 읽는다
    db.execute("SELECT body FROM doc WHERE id=?", ("doc-2",)).fetchone()
```

상태에는 **식별자 · 길이 · 앞 40자**만 넣습니다. 본문은 DB에 그대로 두고, **정말 필요한 마지막 단계에서 단 한 편(`doc-2`)만** 꺼내 옵니다.

여기서 참조를 「`id`만」이 아니라 **`id` + `len` + `head` 40자**로 잡은 게 포인트입니다. 에이전트가 「이게 어떤 문서였지」를 판단해 **꺼낼지 말지 결정할 수 있을 만큼**은 남기되, 본문은 안 싣는 겁니다.

---

## 실행 결과 (직접 돌린 값)

```
문서 6편(각 40,000자)을 12단계 그래프에서 다룬다.

방식                             상태 크기        직렬화 시간     문서 조회
--------------------------------------------------------------
본문을 상태에                     720,203B         7.4ms         0
참조만 상태에                       1,007B         0.2ms         1

상태 크기 715배 차이, 직렬화 시간 32배 차이
```

> 직렬화 시간과 배수는 머신에 따라 달라집니다. 상태 크기(720,203B vs 1,007B)는 결정적입니다.

### 720KB가 나오는 계산

`"가"`는 UTF-8에서 3바이트. 4만 자 × 3바이트 = **12만 바이트**가 문서 한 편. × 6편 = 72만 바이트. 여기에 JSON 키·따옴표 같은 껍데기가 붙어 720,203B가 됩니다.

참조 쪽은 한 편당 `{"id": "doc-0", "len": 40000, "head": "가...(40자)"}` ≈ 160바이트 남짓, 6편 합쳐 1,007B입니다.

## 21장과 만나는 지점

예제 마지막 해설이 21장(내구성 있는 실행 / 체크포인터)을 끌어옵니다.

> 21장에서 «32KB를 넘으면 체크포인터 비용이 꺾인다»고 쟀다.
> 본문을 실으면 720,203B 다. 한참 넘는다.
> 참조만 실으면 1,007B 다. 꺾이는 지점 아래다.

즉 이 예제가 재는 건 단순한 「JSON이 크면 느리다」가 아니라, **오프로딩 하나로 체크포인터 성능 절벽을 넘느냐 마느냐가 갈린다**는 겁니다. 720KB는 임계점의 22배쯤이고, 1KB는 한참 아래입니다.

## 공짜가 아니다 — 표의 오른쪽 칸

「문서 조회」 열이 그 값입니다.

- 본문 방식: 조회 **0회** (선불로 6편 다 읽어 놓았으니까)
- 참조 방식: 조회 **1회** (마지막에 필요한 한 편만)

예제 본문의 정리:

> 6편을 다 실어 놓고 1편만 쓸 거면, 5편은 그냥 짐이었다.

그래서 판단 기준은 중요도가 아니라 **「몇 번 쓰나」** 입니다.

| 사용 빈도 | 처방 |
|---|---|
| 거의 매 단계 쓴다 | 상태에 싣는다 |
| 가끔 한 번 쓴다 | 참조만 싣고 그때 꺼낸다 |
| 안 쓸 수도 있다 | 참조도 싣지 말고 **색인만** 남긴다 |

이 기준은 24장 전체를 관통합니다. 「무엇을 버릴지는 중요도가 아니라 몇 번 쓰나로 정한다 — 중요한 것은 이미 최근 컨텍스트에 있으니까.」

## 헷갈리기 쉬운 지점

- **재는 대상은 「상태 크기 + 직렬화 시간」** 입니다. 토큰 절감률이나 사실 보존율은 `ex2_strategies.py`가, 요약 반복에 따른 유실은 `ex3_summary_drift.py`가, 계층별 조회 비용은 `ex5_memory_tiers.py`가 맡습니다.
- **문서는 6편, 단계는 12단계**입니다. 문서는 앞 6단계에 걸쳐 하나씩 들어오고, 나머지 6단계는 문서가 안 늘어난 채로 직렬화만 반복됩니다. 즉 「한 번 실어 놓은 짐을 남은 단계 내내 다시 쓰고 또 쓰는」 비용을 드러내려는 구조입니다.
- **`blob` 측정 시점**은 루프 안 마지막 회차입니다. 최종 상태 크기를 재는 것이지 누적 합이 아닙니다.
- **참조 = `id` + 길이 + 앞 40자.** 「id만」이 아니라는 점이 답의 괄호에 명시돼 있습니다.
- 방식 A의 「문서 조회 0」은 DB를 안 읽었다는 뜻이 아닙니다. 6편 모두 **미리** 읽어 상태에 박아 넣었기 때문에 **나중에 꺼내 오는 추가 조회**가 없다는 뜻입니다.
