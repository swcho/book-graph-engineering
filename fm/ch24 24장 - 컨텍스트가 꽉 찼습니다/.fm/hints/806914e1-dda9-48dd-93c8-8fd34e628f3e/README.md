# `ex1_growth.py`의 모델링 전제

## 카드 정답

> 한 턴 입력 220토큰, 출력 380토큰, 세 턴에 한 번 도구 결과 1,400토큰이 붙고, 매 턴 전체 대화를 다시 보낸다.

24장 예제 1은 「대화가 길어질 때 토큰이 얼마나 느는가」를 계산기 하나로 보여 주는 코드입니다.
LLM 호출은 한 번도 하지 않습니다. **전제 네 줄**을 상수로 못 박고, 그 전제에서 산수만 굴립니다.
그래서 이 예제를 읽는다는 건 결과 표가 아니라 **전제를 읽는다**는 뜻입니다.

## 전제를 담은 네 개의 상수

```python
TURN_IN   = 220        # 한 턴에 사용자가 넣는 토큰
TURN_OUT  = 380        # 한 턴에 모델이 내놓는 토큰
TOOL_OUT  = 1_400      # 도구 결과가 붙는 턴의 추가 토큰
TOOL_EVERY = 3         # 세 턴에 한 번 도구를 부른다
```

| 전제 | 값 | 의미 |
|---|---|---|
| 턴당 사용자 입력 | 220 토큰 | 한 번 물어보는 분량. 대화 길이에 매 턴 더해진다 |
| 턴당 모델 출력 | 380 토큰 | 한 번 답하는 분량. 출력 요금으로 한 번만 과금되고, 그다음 대화 길이에 남는다 |
| 도구 결과 크기 | 1,400 토큰 | 검색 결과·API 응답 한 덩어리. 사람이 쓴 글보다 훨씬 뚱뚱하다 |
| 도구 호출 주기 | 3턴에 1회 | `t % TOOL_EVERY == 0`인 턴에만 1,400이 붙는다 |

여기에 **다섯 번째이자 진짜 주인공인 전제**가 하나 더 있습니다. 상수가 아니라 루프 구조에 숨어 있어요.

```python
# 매 턴 전체 대화를 다시 보낸다
sent_in += history
```

`sent_in`(누적 입력)에 매 턴 `history`(그때까지 쌓인 대화 전체)를 통째로 더합니다.
이게 스테이트리스 LLM API의 실제 동작입니다. 모델은 지난 턴을 기억하지 않으니,
클라이언트가 매번 대화 전체를 다시 실어 보내야 하죠.

가격과 창 크기도 전제이지만, 이건 **결과를 원 단위로 환산하기 위한 부속**입니다.

```python
PRICE_IN  = 3.0  / 1_000_000    # 입력 100만 토큰당 3달러
PRICE_OUT = 15.0 / 1_000_000    # 출력 100만 토큰당 15달러
KRW       = 1_380
WINDOW    = 200_000             # 모델이 받아 주는 최대 입력 토큰
```

장 본문도 못을 박아 둡니다. 「`ex1`의 단가는 확인 시점(2026년 8월)의 공개 가격표를 기준으로 한 **예시**입니다.
지금 값은 각 벤더의 가격 페이지에서 확인하세요.」 단가는 언제든 바뀌지만, **자라는 모양은 안 바뀝니다.**

## 한 턴 안에서 일어나는 일 (실행 순서)

```python
for t in range(1, turns + 1):
    history += TURN_IN               # 1. 사용자 질문이 대화에 붙는다
    if t % TOOL_EVERY == 0:
        history += TOOL_OUT          # 2. 도구 턴이면 결과도 붙는다
    sent_in  += history              # 3. ★ 대화 전체를 다시 보낸다
    sent_out += TURN_OUT             # 4. 모델 답변은 이번 한 번만 출력 과금
    history  += TURN_OUT             # 5. 그 답변도 다음 턴부터 짐이 된다
```

3번 줄이 제곱을 만듭니다.
`history`는 매 턴 비슷한 양씩 늘어나므로 **선형**인데,
그 선형으로 자라는 값을 매 턴 다시 더하니 `sent_in`은 **누적합 = 제곱(2차)** 이 됩니다.

턴당 평균 증가량은 `220 + 380 + 1400/3 ≈ 1,067` 토큰.
따라서 `history(t) ≈ 1,067t`, `sent_in(t) ≈ 1,067 × t(t+1)/2 ≈ 533t²`.

## 이 전제가 만드는 결과

```
    턴       대화 길이         누적 입력       누적 비용     창 사용률
--------------------------------------------------------
    1         600           220          9원       0%
    5       4,400        11,300         86원       2%
   10      10,200        50,200        286원       5%
   20      20,400       206,600      1,013원      10%
   40      42,200       840,800      3,796원      21%
   80      84,400     3,387,800     14,655원      42%
  120     128,000     7,642,400     32,583원      64%
```

읽는 법 두 가지입니다.

**1) 턴이 두 배면 비용은 네 배.**

| 구간 | 비용 배수 |
|---|---|
| 20턴 → 40턴 | 1,013원 → 3,796원 (약 3.7배) |
| 40턴 → 80턴 | 3,796원 → 14,655원 (약 3.9배) |

정확히 4배가 아닌 건 출력 요금(`sent_out`)이 선형이라 제곱 항을 조금 희석하기 때문입니다.
턴이 늘수록 제곱 항이 지배해서 4배에 수렴합니다.

**2) 비용은 창이 차기 훨씬 전에 문제가 된다.**

120턴에서 창 사용률은 64%입니다. 아직 «컨텍스트 초과» 에러는 안 납니다.
그런데 누적 비용은 이미 20턴의 32배예요.
「아직 창이 남았으니 괜찮다」는 위험한 판단인 이유가 이겁니다.

## 이 장의 도입부와 연결

> 20턴짜리 대화는 8,000토큰이 맞았습니다. 그런데 실제 사용자들은 평균 47턴을 썼습니다.
> 저희가 20턴을 기준으로 잡은 이유는... 사실 없었습니다.

청구서가 6.4배로 나온 사건이 바로 이 표입니다.
테스트에서 20턴만 돌려 보고 「턴당 비용 × 예상 턴 수」로 선형 추정을 했는데,
실제 비용 곡선은 제곱이었던 거죠. 20턴 → 47턴이면 턴 수는 2.35배지만 비용은 약 5~6배가 됩니다.

## 전제를 의심해야 하는 지점

이 모델은 의도적으로 **단순화**되어 있습니다. 실무에 옮길 때 확인할 것들입니다.

- **프롬프트 캐싱을 안 셌다.** 실제 API는 대화 앞부분을 캐시해 입력 단가를 크게 낮출 수 있습니다.
  캐싱을 쓰면 제곱 항의 «계수»가 줄지만, **차수는 그대로 2차**입니다. 곡선의 모양은 안 바뀝니다.
- **도구 턴의 왕복을 한 번으로 묶었다.** 실제로는 「모델이 도구를 부른다 → 결과를 받는다 → 다시 부른다」로
  한 턴에 API 호출이 두 번 이상 일어납니다. 코드는 도구 결과를 그 턴 입력에 미리 얹어 한 번으로 셉니다.
  즉 이 계산은 **낙관적**입니다. 실제 비용은 이보다 더 큽니다.
- **턴 길이가 고정이다.** 실제 사용자 입력은 들쭉날쭉하고, 도구 결과 크기는 1,400보다 훨씬 클 때가 많습니다.
- **시스템 프롬프트·도구 정의를 안 셌다.** 이건 매 턴 붙는 고정 비용이라 선형 항으로 더해집니다.

## 한 줄 정리

`ex1_growth.py`의 전제는 **「220 입력 / 380 출력 / 3턴마다 1,400짜리 도구 결과 / 매 턴 전체 재전송」** 이고,
마지막 항목이 대화 길이는 선형인데 누적 비용은 제곱으로 자라게 만드는 원인입니다.
