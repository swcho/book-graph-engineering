# 관계를 노드로 승격할 때 가장 오래 걸리는 작업

**질문** 관계를 노드로 승격할 때 가장 오래 걸리는 작업은 무엇인가?

**답** 데이터 이동이 아니라 **표기 통일**이다.

출처: 7장 「노드 하나 잘못 그려서 3주를 날렸다」 한 장 요약 —
"승격은 늦게 하되 미루지 마세요. 데이터가 쌓일수록 옮기는 값이 비례해서 오릅니다. 그리고 옮길 때 제일 오래 걸리는 건 데이터 이동이 아니라 표기 통일입니다."

---

## 1. 먼저, "승격"이 뭔가

관계(엣지)에 속성이 붙기 시작하면 그 관계를 **독립한 노드로 끌어올리는** 것을 승격이라고 합니다. RDF 쪽 용어로는 관계의 **구체화(reification)** 입니다.

7장 예제 1(`code/ex1_node_or_edge.py`)이 정확히 이 두 모델을 나란히 놓고 비교합니다.

**모델 A — 관계를 엣지로**

```
("가온테크", "SIGNED", "C-2025-118", {"at": "2025-06-02", "by": "김하늘"})
```

**모델 B — 관계를 노드로 승격**

```
s1 = {"label": "체결", "at": "2025-06-02"}
("가온테크", "HAS", "s1"), ("s1", "OF", "C-2025-118"), ("s1", "BY", "김하늘")
```

승격의 신호는 세 가지 질문이고, 마지막이 결정적입니다.

1. 그 관계에 속성이 붙나
2. 제3의 대상과 이어지나 (담당자, 승인자, 부속 문서…)
3. **그 속성으로 검색하나**

속성은 **읽는** 것이고 노드는 **찾는** 것입니다. 찾기 시작했다면 승격할 때입니다. 엣지 속성 `by`에는 색인을 걸 수 없는 엔진이 많아서, 「김하늘이 담당한 체결 건」을 물으면 엣지 100만 개를 전부 훑게 됩니다.

## 2. 왜 데이터 이동이 병목이 아닌가

승격의 데이터 작업 자체는 **기계적이고, 자동화되고, 한 번 하면 끝**입니다.

- 변환 규칙이 1:1로 떨어집니다. 엣지 1개 → 노드 1개 + 엣지 3개. 스크립트 한 편이면 됩니다.
- 배치로 쪼개서 나눠 돌릴 수 있고, 병렬화도 됩니다.
- 성공/실패 판정이 명확합니다. 건수가 맞는지 세어 보면 됩니다.
- 비용이 예측 가능합니다. 데이터 양에 **비례**할 뿐입니다(그래서 "늦게 하되 미루지 말라"는 말이 나옵니다 — 미루면 이 비례항이 계속 커집니다).

즉 데이터 이동은 오래 걸릴 수는 있지만 **예측 가능하게** 오래 걸립니다. 3주를 태우는 쪽은 여기가 아닙니다.

## 3. 표기 통일이 진짜 병목인 이유

표기 통일은 데이터베이스 안이 아니라 **데이터베이스 밖 전부**에서 벌어집니다.

승격 하나로 바뀌는 표기의 목록:

| 층 | 승격 전 | 승격 후 |
|---|---|---|
| 관계 타입 이름 | `SIGNED` 하나 | `HAS`, `OF`, `BY` 세 개 |
| 노드 라벨 | 없음 | `체결` 라벨 신설 |
| 속성 위치 | 엣지 속성 `at`, `by` | 노드 속성 `at`, 엣지 `BY`의 대상 |
| 방향 | `(회사)->(계약)` | `(회사)->(체결)->(계약)` |
| 질의 | 1홉 패턴 | 2홉 패턴 (전부 다시 씀) |
| 홉 수 가정 | 최단 경로·이웃 계산의 홉 수 | 중간 노드 하나가 끼어들어 전부 +1 |
| 팀 언어 | "계약 엣지" | "체결 노드" |
| 그 밖 | 대시보드 쿼리, 리포트, ETL, 스키마 문서, 온보딩 자료, 슬랙에 박아 둔 예제 쿼리 |

데이터 이동과 성격이 다릅니다.

- **범위가 사람과 코드 경로 수에 비례합니다.** 데이터 양이 아니라 조직 크기에 비례합니다. 자동화가 안 됩니다.
- **합의가 필요합니다.** 승격 노드를 `체결`이라 부를지 `계약체결`이라 부를지, 엣지를 `BY`로 할지 `HANDLED_BY`로 할지에 정답이 없습니다. 합의 없이 각자 쓰기 시작하면 같은 사실이 두세 표기로 갈라집니다.
- **실패가 조용합니다.** 표기가 어긋난 질의는 에러를 내지 않고 **그냥 다른 숫자**를 냅니다. 건수가 맞는지 세는 검증으로는 안 잡힙니다.
- **혼재 기간이 깁니다.** 옛 `SIGNED` 엣지와 새 `체결` 노드가 동시에 남아 있는 기간이 반드시 생기고, 이 기간에 만든 코드가 계속 옛 표기를 재생산합니다.

## 4. 표기가 어긋나면 실제로 뭐가 깨지나

7장의 다른 사고들과 그대로 이어집니다.

- **이중 계수.** 옛 엣지와 새 노드가 함께 남아 있으면 계약 하나가 두 번 셉니다. 예제 5(`ex5_multigraph.py`)의 "가온테크의 차수가 2냐 4냐" 문제가 마이그레이션 중간 상태에서 저절로 생깁니다.
- **중심성 왜곡.** 승격으로 중간 노드가 늘어나면 차수·경유 중심성 값이 전부 달라집니다. 옛 표기 기준으로 쓴 리포트 문장("거래처가 많은 회사")이 새 표기에서는 틀린 말이 됩니다.
- **경로 길이 오해.** 1홉이던 관계가 2홉이 되므로, "2홉 이내 추천" 같은 규칙이 조용히 아무것도 못 찾게 됩니다.
- **가중치 뜻 유실.** 이름을 대충 옮기다 `weight`가 거리인지 강도인지 잃어버리면, 예제 3의 사고(친밀도를 최단 경로에 그대로 넣어 제일 안 친한 경로를 답으로 받은 사고)가 재현됩니다. 이름에 뜻을 박아 넣으세요 — `cost_minutes`, `affinity_score`.

## 5. 그래서 어떻게 하나

승격 작업의 순서를 데이터가 아니라 **표기**부터 잡습니다.

1. **이름을 먼저 확정한다.** 노드 라벨, 관계 타입, 속성 이름, 방향을 한 페이지 표로 만들어 합의부터 받습니다. 코드는 그다음입니다.
2. **용어집을 저장소 안에 둔다.** 옛 표기 → 새 표기 매핑을 코드와 같은 곳에 두어 검색되게 합니다.
3. **한 방향으로만 옮긴다.** 새 표기로 쓰고, 옛 표기는 읽기 전용 어댑터/뷰로만 지원합니다. 양쪽 쓰기를 허용하면 혼재가 영구화됩니다.
4. **옛 표기 사용을 CI로 막는다.** `SIGNED` 문자열이 새 코드에 들어오면 실패하게 합니다. 사람 리뷰로는 못 잡습니다.
5. **혼재 기간에 정합성 질의를 돌린다.** "옛 엣지 있는데 새 노드 없는 건", "둘 다 있는 건"을 매일 셉니다.
6. **마지막에 옛 엣지를 실제로 지운다.** 남겨 두면 반드시 누가 씁니다.
7. **집계 숫자를 승격 전후로 나란히 비교한다.** 차수·중심성·건수가 왜 달라졌는지 설명할 수 있어야 마이그레이션이 끝난 것입니다.

## 6. 자주 나오는 오답과 구별

| 오답 후보 | 왜 답이 아닌가 |
|---|---|
| 데이터 이동 | 문장이 명시적으로 부정하는 대상입니다. 양에 비례하고 자동화됩니다 |
| 색인 재구축 | 엔진이 알아서 하고, 시간도 예측 가능합니다 |
| 다운타임 확보 | 무중단 이중 쓰기로 대개 회피할 수 있습니다 |
| 스키마 설계 | 승격 **여부**를 정하는 앞단 판단이지, 승격 **작업** 중 가장 오래 걸리는 항목은 아닙니다 |

## 7. 한 줄로

> 승격에서 오래 걸리는 건 바이트를 옮기는 일이 아니라, 그 바이트를 **뭐라고 부를지 팀 전체가 하나로 맞추는 일**이다.
