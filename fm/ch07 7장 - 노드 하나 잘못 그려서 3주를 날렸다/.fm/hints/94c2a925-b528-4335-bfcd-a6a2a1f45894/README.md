# 투영 폭발을 피하는 두 가지 대안

**질문**: 투영 폭발을 피하는 두 가지 대안은 무엇인가?

**답**: 첫째, 투영하지 말고 이분 그래프에서 2홉을 필요할 때만 돌린다. 둘째, 투영하되 '함께 산 사람 N명 이상'으로 자른다(대개 3명이면 충분).

출처: 7장 「노드 하나 잘못 그려서 3주를 날렸다」 7.4절 / `code/ex4_bipartite.py`

---

## 1. 먼저, 무엇이 폭발하는가

이분 그래프(bipartite graph)는 노드가 **두 종류만** 있고 엣지는 **다른 종류 사이에만** 놓이는 그래프입니다. 구매 로그가 전형입니다.

```python
PURCHASES = [
    ("u1", "상품A"), ("u1", "상품B"),
    ("u2", "상품A"), ("u2", "상품B"), ("u2", "상품C"),
    ("u3", "상품C"),
]
```

사용자 쪽과 상품 쪽, 두 종류입니다. 엣지 6개.

그런데 우리가 실제로 묻고 싶은 건 「이 상품과 **함께 팔리는** 상품」입니다. 이건 상품–상품 관계예요. 이분 그래프에는 상품–상품 엣지가 없으니, 「같은 사용자를 공유하면 잇는다」는 규칙으로 **한쪽 종류만 남긴 그래프**를 만들게 됩니다. 이것이 **투영(projection, one-mode projection)** 입니다.

```python
def project(pairs, side=1):
    """한쪽으로 투영. 같은 상대를 공유하면 잇는다."""
    grouped = defaultdict(set)
    for a, b in pairs:
        key, val = (a, b) if side == 0 else (b, a)
        grouped[val].add(key)
    out = defaultdict(int)
    for val, keys in grouped.items():
        for x, y in combinations(sorted(keys), 2):
            out[(x, y)] += 1
    return dict(out)
```

핵심은 `combinations(keys, 2)` 한 줄입니다. **한 사용자가 산 상품 k개는 상품 쪽에 `k(k-1)/2`개의 엣지를 만듭니다.** 사용자 한 명이 기여하는 엣지가 k에 **제곱으로** 붙는다는 뜻이에요.

### 폭발의 산수

```python
def simulate(n_users, items_per_user):
    return n_users * items_per_user * (items_per_user - 1) // 2
```

| 사용자 | 1인당 구매 | 투영 엣지(최대) |
|---:|---:|---:|
| 1,000 | 10 | 45,000 |
| 1,000 | 50 | 1,225,000 |
| 100,000 | 50 | 122,500,000 |
| 100,000 | 200 | 1,990,000,000 |

원본 엣지는 `100,000 × 200 = 2천만` 개입니다. 투영하면 **20억**이 됩니다. **100배**요.

> 실제로는 중복이 합쳐지니 이보다 적지만, 상한이 이렇다는 게 중요하다.

「중복이 합쳐진다」는 말은 여러 사용자가 같은 상품 쌍을 함께 샀으면 엣지 하나에 가중치가 쌓인다는 뜻입니다. 그래서 실제 값은 저 상한보다 작지만, **상한이 20억이면 언제 터질지 모르는 시스템**이라는 사실이 남습니다. 그리고 상한을 결정하는 건 사용자 수(선형)가 아니라 **1인당 구매 수(제곱)** 입니다. 헤비 유저 몇 명, 봇 계정 하나, 카트 대량 임포트 한 번이 그래프를 두 배로 만들 수 있어요.

### 그리고 정보가 사라진다

```
버려진 것: 누가 샀는지. 투영 그래프만 보면 u1, u2, u3 이 사라진다.
```

투영은 **비가역**입니다. 「상품A—상품B (함께 산 사람 2명)」만 남으면 그 2명이 누구인지, 언제 샀는지, 같은 주문이었는지가 전부 날아갑니다. 「20대 여성 사용자만 빼고 다시 계산해 줘」라는 요청이 들어오면 원본에서 처음부터 다시 만들어야 합니다.

즉 투영은 **엣지를 제곱으로 늘리면서 정보를 잃는** 거래입니다. 값을 두 번 치릅니다. 그래서 대안이 필요합니다.

## 2. 대안 1 — 투영하지 말고, 2홉을 필요할 때만 돈다

> 투영하지 말고 이분 그래프 그대로 2홉을 돈다. 필요할 때만 계산한다.

투영이 하는 일을 다시 보면 「상품 → 그 상품을 산 사용자 → 그 사용자가 산 다른 상품」입니다. 정확히 **2홉 탐색**입니다.

투영은 이 2홉을 **모든 상품 쌍에 대해 미리 전부 계산해서 저장**하는 것이고, 대안 1은 **묻는 순간 그 상품 하나에 대해서만 계산**하는 것입니다.

```cypher
MATCH (i:Item {id: $item})<-[:BOUGHT]-(u:User)-[:BOUGHT]->(other:Item)
WHERE other <> i
RETURN other.id, count(DISTINCT u) AS together
ORDER BY together DESC
LIMIT 20
```

| | 투영(미리 계산) | 2홉(필요할 때) |
|---|---|---|
| 저장 비용 | 최대 `n·k(k-1)/2` 엣지 | **0** (원본 그대로) |
| 질의 비용 | 인접 조회 1번 | `deg(상품) × 평균 deg(사용자)` |
| 정보 보존 | 누가 샀는지 소실 | **전부 남아 있음** |
| 갱신 | 구매 1건에 최대 `k-1`개 엣지 갱신 | 새 데이터가 즉시 반영 |
| 필터 추가 | 조건별로 투영을 다시 만들어야 | `WHERE u.age < 30` 한 줄 추가 |

핵심 이득은 **저장 비용 0과 정보 보존**입니다. 그리고 조용히 따라오는 이득이 하나 더 있습니다. 투영 그래프는 만든 순간부터 낡기 시작해서 재계산 배치와 정합성 문제를 끌고 오는데, 2홉은 언제나 최신입니다.

### 대안 1의 함정 — 허브

2홉도 공짜가 아닙니다. 비용이 `deg(상품) × 평균 deg(사용자)`인데, 여기에 **허브**가 끼면 무너집니다.

- 「비닐봉투」처럼 100만 명이 산 상품에서 출발하면 첫 홉이 이미 100만입니다.
- 상품 1만 개를 담은 봇 계정을 하나 밟으면 두 번째 홉이 1만입니다.

그래서 실무에서는 이렇게 막습니다.

- **차수 상한**: `deg`가 임계치를 넘는 사용자/상품은 탐색에서 건너뜁니다. 어차피 「1만 개를 산 사용자」는 취향 정보를 거의 담지 않습니다.
- **표본 추출**: 사용자 전부 대신 최근/일부만 밟습니다.
- **`LIMIT` + 상위 K**: 전부 세지 않고 상위 몇 개만 뽑습니다.
- **인기 상품만 부분 캐시**: 자주 묻는 상위 상품에 대해서만 결과를 캐싱합니다. 이게 사실 대안 1과 2의 중간 지점입니다.

## 3. 대안 2 — 투영하되 가중치로 자른다

> 투영하되 «함께 산 사람 N명 이상»으로 자른다. 대개 3명이면 충분하다.

투영 함수가 이미 가중치를 세고 있다는 점이 출발점입니다.

```python
out[(x, y)] += 1   # 이 쌍을 함께 산 사람이 한 명 더 있다
```

이 가중치가 곧 **함께 산 사람 수(co-occurrence count)** 입니다. 예제 출력이 그대로 보여 줍니다.

```
상품 쪽으로 투영 (함께 산 상품끼리 잇기)
   상품A — 상품B  (함께 산 사람 2명)
   상품A — 상품C  (함께 산 사람 1명)
   상품B — 상품C  (함께 산 사람 1명)
```

컷오프는 이 가중치에 문턱을 두는 것입니다. `weight >= 3`이면 위 예제에서는 엣지가 **0개** 남습니다(제일 큰 값이 2니까요). 6줄짜리 장난감 데이터에서는 과격해 보이지만, 실제 규모에서는 이게 정확히 노리는 효과입니다.

### 왜 3명이 「대개 충분」한가

투영 엣지의 가중치 분포는 심하게 한쪽으로 쏠립니다. **엣지의 대다수가 가중치 1**입니다. 그리고 가중치 1인 엣지는 「단 한 사람이 우연히 같은 장바구니에 담았다」는 뜻이에요. 신호가 아니라 잡음입니다.

- `weight = 1`: 한 명의 우연. 대부분 잡음.
- `weight = 2`: 우연이 두 번. 아직 의심스럽습니다.
- `weight >= 3`: 서로 모르는 사람 셋이 같은 조합을 만들었다면 패턴으로 볼 만합니다.

가중치 1을 버리는 것만으로 엣지가 한 자릿수 배율로 줄어드는 경우가 흔하고, 잃는 정보는 대체로 통계적 의미가 없는 쪽입니다. **엣지는 크게 줄고 신호는 거의 그대로 남는** 게 이 방법이 먹히는 이유입니다.

「3」은 물리 상수가 아니라 **경험적 기본값**입니다. 데이터마다 조정해야 합니다. 그래서 저자는 3을 고정값으로 쓰지 않고 기준을 따로 둡니다.

### 자르는 값을 정하는 기준 — 엣지 수를 노드 수의 20배 아래로

> 저는 2번을 쓰고, 자르는 값은 엣지 수가 노드 수의 20배를 넘지 않게 잡는다.

이게 이 카드에서 제일 실무적인 문장입니다. 임계치를 **의미**로 정하지 않고 **결과 크기**로 정합니다.

```
목표: |E| <= 20 × |V|
```

절차는 이렇습니다. N=1로 투영해서 가중치 분포를 뽑고, N을 올려 가며 남는 엣지 수를 세고, `20 × |V|` 아래로 처음 떨어지는 N을 씁니다. 상품이 10만 개면 엣지 200만 개가 상한이고, 거기 맞는 N을 데이터가 알려 주는 구조입니다.

왜 20배인가. 그래프 알고리즘 대부분이 `O(V + E)` 또는 `O(E log V)` 급이라 **평균 차수**가 실질 성능을 결정합니다. 평균 차수 40(= 20배의 2배) 정도면 커뮤니티 탐지, 중심성, PageRank가 현실적인 시간에 돕니다. 여기가 「희소 그래프」와 「사실상 밀집 그래프」의 경계쯤입니다. 그 위로 가면 8장에서 다루는 메모리 문제가 시작됩니다.

## 4. 둘 중 무엇을 고를까

| 상황 | 선택 |
|---|---|
| 질의가 산발적, 상품 하나씩 물음 | **대안 1** (2홉) |
| 원본 조건(연령·기간·지역)별 필터가 자주 붙는다 | **대안 1** (투영을 조건별로 다시 만들 수 없다) |
| 데이터가 실시간으로 바뀌고 최신성이 중요 | **대안 1** |
| 커뮤니티 탐지·중심성처럼 **그래프 전체**를 훑는 알고리즘을 돌려야 한다 | **대안 2** (전역 알고리즘은 투영된 단일 모드 그래프를 요구) |
| 같은 계산을 수없이 반복하고 지연 시간이 빡빡하다 | **대안 2** |
| 잘 모르겠다 | 대안 2 + 20배 규칙 (저자의 선택) |

둘이 배타적이지도 않습니다. **원본 이분 그래프는 항상 보관하고**, 컷오프를 준 투영 그래프를 파생 캐시로 두는 게 실전 구성입니다. 임계치를 바꾸고 싶어지면 원본에서 다시 만들면 되니까요. 투영 그래프를 만든 뒤 원본을 버리는 것이 이 절에서 말하는 진짜 사고입니다.

## 5. 놓치기 쉬운 것

- **컷오프는 되돌릴 수 없다(투영본만 남긴 경우)**. N=3으로 잘라 놓고 나중에 「롱테일 추천도 보고 싶다」가 되면 원본이 필요합니다. 원본을 지우지 마세요.
- **컷오프는 롱테일에 불리하게 편향된다**. 니치 상품은 함께 산 사람이 애초에 3명을 넘기 어렵습니다. 신상품과 소량 판매 상품이 그래프에서 통째로 사라질 수 있어요. 인기 상품과 롱테일에 다른 기준을 쓰거나, 절대 수 대신 **정규화 가중치**를 쓰는 방법이 있습니다.
- **정규화된 가중치라는 제3의 축이 있다**. 절대 co-occurrence 수 대신 자카드 계수(공유 사용자 / 합집합 사용자)나 사용자 차수의 역수 합처럼 정규화한 값을 쓰면 「많이 팔리는 상품은 아무것과나 이어진다」는 인기 편향을 줄일 수 있습니다. networkx의 `bipartite.weighted_projected_graph`, `overlap_weighted_projected_graph`, `collaboration_weighted_projected_graph`가 서로 다른 가중치 정의를 제공하고, 통계적으로 유의한 엣지만 남기는 백본 추출(disparity filter 계열) 기법도 있습니다. 이 장은 가장 단순하고 설명하기 쉬운 「절대 수 + 문턱」을 씁니다.
- **투영을 만들기도 전에 터질 수 있다**. `combinations`를 전부 펼치면서 메모리가 먼저 죽는 경우가 많습니다. 컷오프를 「만든 뒤 필터링」이 아니라 계산 과정에 밀어 넣거나(차수 큰 사용자 사전 제외), 스트리밍/배치로 집계해야 합니다.
- **이분 구조 자체를 깨뜨리지 말 것**. 원본에 사용자–사용자 엣지가 섞여 들어가면 이분 그래프 알고리즘의 전제가 무너지고 투영 결과가 조용히 이상해집니다.
