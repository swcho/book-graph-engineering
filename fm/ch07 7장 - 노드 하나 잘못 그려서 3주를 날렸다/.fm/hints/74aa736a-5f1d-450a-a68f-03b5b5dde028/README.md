# 가중치 속성 이름을 어떻게 지어야 하는가?

> **답**: 이름에 뜻을 박아 넣는다. `weight` 대신 `cost_minutes`나 `affinity_score`처럼 거리인지 강도인지 드러내야 한다.

출처: 7장 「노드 하나 잘못 그려서 3주를 날렸다」 7.3절 *가중치가 거리인가 강도인가* / `code/ex3_weights.py`

---

## 1. 왜 `weight`가 위험한 이름인가

숫자 `8`은 아무 뜻이 없습니다. 뜻은 **읽는 사람과 알고리즘이** 붙입니다. 그리고 붙이는 방식이 정확히 두 가지로 갈립니다.

| 해석 | 의미 | 클수록 | 예시 값 |
|---|---|---|---|
| **거리(distance / cost)** | 비용, 소요 시간, 요금, 지연 | **멀다** (나쁘다) | 이동 시간 8분, 요금 8000원 |
| **강도(strength / affinity)** | 친밀도, 유사도, 거래 횟수, 신뢰도 | **가깝다** (좋다) | 함께 산 횟수 8회, 유사도 0.8 |

`weight`라는 이름은 이 둘 중 어느 쪽인지 **아무 정보도 주지 않습니다.** 그래서 6개월 뒤의 나, 혹은 옆자리 동료가 반대로 읽습니다. 컴파일러도 잡아주지 않고, 테스트도 통과하고, 질의도 에러 없이 답을 돌려줍니다. **틀린 답을 조용히** 돌려줍니다.

## 2. 뒤집혔을 때 실제로 무슨 일이 벌어지나 (ex3_weights.py)

예제의 그래프는 이렇게 생겼습니다.

```
A --8-- B --8-- C
A --3-- D --3-- C
```

같은 데이터, 같은 다익스트라, 해석만 바꿉니다.

- 숫자를 **거리**로 읽으면: `A → D → C`, 합 6 (윗길은 16)
- 숫자를 **강도**로 읽으면(`1/w`로 변환): `A → B → C`, 합 0.25 (아랫길은 0.667)

**같은 데이터에서 정반대 경로가 나옵니다.** 어느 쪽도 "버그"가 아니라, 숫자의 뜻이 무엇이었느냐의 문제입니다.

책의 사고 사례가 정확히 이 모양이었습니다. 친밀도(클수록 가깝다)를 저장해 두고 최단 경로 알고리즘에 그대로 넣었습니다. 최단 경로는 **작을수록 가깝다**로 읽습니다. 결과적으로 **제일 안 친한 경로**를 "가장 가까운 사이"라고 보고했고, 알아차리는 데 2주가 걸렸습니다. 이 유형의 사고가 무서운 건 **결과가 그럴듯해 보인다**는 점입니다. 경로도 나오고 숫자도 나오니 실패로 보이지 않습니다.

## 3. 그래서 이름을 어떻게 짓는가

### 규칙 1 — 방향성을 이름에 넣는다

`cost_*`, `distance_*`, `latency_*`, `penalty_*` → **작을수록 좋다**
`*_score`, `*_affinity`, `similarity_*`, `strength_*`, `count_*` → **클수록 좋다**

접두어/접미어만 보고도 부호 방향을 알 수 있어야 합니다.

### 규칙 2 — 단위를 이름에 넣는다

`cost_minutes`, `cost_krw`, `distance_meters`, `latency_ms`.

단위가 이름에 없으면 초와 밀리초, 미터와 킬로미터가 섞입니다. 그래프는 서로 다른 출처의 엣지를 합치는 일이 잦아서, 이 사고가 특히 잘 납니다.

### 규칙 3 — 정규화 여부와 범위를 드러낸다

`affinity_score_0_1`, `similarity_cosine`처럼 척도를 남깁니다. 최소한 스키마 문서에 "0~1", "0 이상 무제한"을 명시합니다.

### 규칙 4 — 한 엣지에 두 뜻이 다 필요하면 둘 다 저장한다

거리 계산도 하고 강도 계산도 해야 한다면, 하나를 그때그때 뒤집지 말고 두 속성을 나란히 둡니다.

```
(:User)-[:INTERACTS { affinity_score: 8, cost_hops: 0.125 }]->(:User)
```

변환 로직이 코드 여기저기 흩어지는 것이 사고의 원인입니다. 변환은 **적재 시점에 한 번**, 결과는 이름이 다른 속성으로.

### 좋은 이름 / 나쁜 이름

| 나쁨 | 좋음 | 이유 |
|---|---|---|
| `weight` | `cost_minutes` | 방향과 단위가 다 없음 |
| `w` | `affinity_score` | 축약은 뜻을 지운다 |
| `score` | `similarity_cosine` | 클수록 좋은 건 알겠는데 무슨 척도인지 모름 |
| `time` | `latency_ms` | 시각인지 소요시간인지, 단위도 불명 |
| `value` | `revenue_krw` | 아무 뜻도 없는 최악의 이름 |
| `dist` | `distance_meters` | 단위 없음 |

## 4. 라이브러리·엔진이 상황을 더 꼬는 지점

이름을 잘 지어도, 도구가 `weight`라는 이름을 요구하는 경우가 있습니다. **여기가 함정입니다.**

- **NetworkX**: 다수의 함수가 기본 속성 키로 `weight`를 봅니다. 그런데 같은 `weight`를 함수마다 다른 뜻으로 읽습니다.
  - `shortest_path`, `betweenness_centrality` → **거리**로 읽음 (작을수록 가깝다)
  - `pagerank`, 커뮤니티 탐지(Louvain 등) → **강도**로 읽음 (클수록 강하게 연결)
  - 즉 같은 그래프 객체에 담긴 하나의 `weight`를 두 알고리즘에 넣으면, **둘 중 하나는 반드시 틀립니다.**
- **호출 시 명시적으로 넘긴다**: `weight="cost_minutes"`처럼 인자로 지정하면, 그래프 속성 이름은 뜻이 담긴 채로 유지하면서 라이브러리 규약도 만족시킬 수 있습니다. Neo4j GDS의 `relationshipWeightProperty` 같은 파라미터도 같은 역할입니다.
- **다익스트라는 음수 가중치를 못 씁니다.** "강도를 음수로 만들어 거리처럼 쓰자"는 우회는 동작하지 않습니다.

## 5. 강도를 거리로 바꿔야 할 때

강도 그래프에 최단 경로류 알고리즘을 돌려야 한다면 변환이 필요합니다. 자주 쓰는 세 가지.

| 변환 | 성질 | 주의 |
|---|---|---|
| `1 / w` | 예제가 쓰는 방식, 간단 | `w = 0`에서 폭발. 합산 결과의 물리적 의미가 흐릿함 |
| `-log(w)` | 확률/신뢰도 가중치에서 경로 곱을 합으로 바꿔줌 | `w`가 0~1 범위여야 함. `w = 0` 처리 필요 |
| `max_w - w` | 값 범위가 유지되어 읽기 쉬움 | 데이터가 늘면 `max_w`가 바뀌어 값이 흔들림 |

어떤 걸 쓰든, **변환 결과는 원본과 다른 이름으로 저장하세요.** `affinity_score`에서 만든 값을 `affinity_score`에 다시 덮어쓰면 지금까지의 논의가 전부 무의미해집니다.

## 6. 점검 목록

- [ ] 스키마에 `weight`, `w`, `value`, `score` 같은 맨몸 이름이 남아 있는가
- [ ] 이름만 보고 "클수록 좋은가"에 즉답할 수 있는가
- [ ] 단위가 이름 또는 스키마 문서에 있는가
- [ ] 알고리즘 호출부에 `weight=` 인자를 명시했는가, 기본값에 의존하는가
- [ ] 강도→거리 변환이 코드 여러 곳에 흩어져 있지 않은가
- [ ] 서로 다른 출처의 엣지를 합칠 때 단위와 척도가 같은가

## 7. 한 줄 요약

> 이름 하나로 막을 수 있는 사고를, 이름을 아껴서 만든다. (`ex3_weights.py`)

`weight`는 타이핑 6글자를 아끼려고 2주를 잃는 이름입니다. `cost_minutes` / `affinity_score`처럼 **거리인지 강도인지, 단위가 무엇인지**를 이름이 직접 말하게 하세요.
