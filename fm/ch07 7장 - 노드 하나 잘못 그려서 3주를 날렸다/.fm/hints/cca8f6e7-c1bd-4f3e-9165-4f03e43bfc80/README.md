# 노드 승격 모델에서 같은 질문의 비용이 낮아지는 이유

**질문**: 노드 승격 모델에서 같은 질문의 비용이 낮아지는 이유는 무엇인가?

**답**: '김하늘' 노드로 들어오는 BY 엣지만 따라가면 되기 때문이다. 노드는 색인 대상이므로 탐색 시작점이 될 수 있다.

출처: 7장 「노드 하나 잘못 그려서 3주를 날렸다」 / `code/ex1_node_or_edge.py`

---

## 1. 무대 설정 — 같은 사실, 두 가지 모델

7.1절의 예제는 「가온테크가 C-2025-118 계약을 2025-06-02에 체결했고, 담당자는 김하늘」이라는 **하나의 사실**을 두 방식으로 그립니다.

### 모델 A — 관계를 엣지로

```python
EDGE_MODEL = [
    ("가온테크", "SIGNED", "C-2025-118", {"at": "2025-06-02", "by": "김하늘"}),
    ("가온테크", "SIGNED", "C-2024-002", {"at": "2024-01-15", "by": "박서준"}),
    ("나루소프트", "SIGNED", "C-2025-004", {"at": "2025-01-20", "by": "김하늘"}),
]
```

체결일(`at`)과 담당자(`by`)가 **엣지의 속성**으로 붙어 있습니다. 화이트보드에서는 이 그림이 제일 깔끔합니다. 엣지 하나가 사실 하나를 그대로 담고 있으니까요.

### 모델 B — 관계를 노드로 승격

```python
NODE_MODEL_NODES = {
    "s1": {"label": "체결", "at": "2025-06-02"},
    "s2": {"label": "체결", "at": "2024-01-15"},
    "s3": {"label": "체결", "at": "2025-01-20"},
}
NODE_MODEL_EDGES = [
    ("가온테크", "HAS", "s1"), ("s1", "OF", "C-2025-118"), ("s1", "BY", "김하늘"),
    ("가온테크", "HAS", "s2"), ("s2", "OF", "C-2024-002"), ("s2", "BY", "박서준"),
    ("나루소프트", "HAS", "s3"), ("s3", "OF", "C-2025-004"), ("s3", "BY", "김하늘"),
]
```

「체결」이라는 **사건 자체가 노드**(`s1`, `s2`, `s3`)가 되고, 회사·계약·담당자는 그 노드에 엣지로 매달립니다. 담당자 김하늘도 더 이상 문자열 속성값이 아니라 **독립된 노드**입니다. 엣지 3개짜리 모델이 엣지 9개로 늘었습니다. 겉보기에는 손해입니다.

## 2. 같은 질문을 두 모델에 던진다

질문: **「김하늘이 담당한 체결 건은?」**

### 모델 A: 전체 훑기 (full scan)

```python
def q_edge_model(who):
    """«김하늘이 담당한 체결 건» — 엣지 모델에서는 모든 엣지를 훑어야 한다."""
    scanned = 0
    out = []
    for s, t, o, props in EDGE_MODEL:
        scanned += 1
        if props.get("by") == who:
            out.append((s, o, props["at"]))
    return out, scanned
```

`props.get("by")`를 확인하려면 **엣지를 일단 꺼내 봐야** 합니다. 「김하늘」이라는 값에서 출발해 해당 엣지로 곧장 점프할 방법이 없습니다. 그래서 비용이 전체 엣지 수 N에 비례합니다 — `O(N)`.

### 모델 B: 들어오는 엣지만 따라가기

```python
def q_node_model(who):
    """노드 모델에서는 김하늘에게 들어오는 BY 엣지만 보면 된다."""
    incoming = defaultdict(list)
    for s, t, o in NODE_MODEL_EDGES:
        incoming[o].append((s, t))
    ...
    for s, t in incoming[who]:
        scanned += 1
        if t != "BY":
            continue
        company = next(a for a, tt, b in NODE_MODEL_EDGES if b == s and tt == "HAS")
        contract = next(b for a, tt, b in NODE_MODEL_EDGES if a == s and tt == "OF")
        out.append((company, contract, NODE_MODEL_NODES[s]["at"]))
```

「김하늘」 노드를 **색인으로 곧장 찾고**(seek), 그 노드로 **들어오는 BY 엣지 2개**만 따라가면 됩니다. 거기서 만난 `s1`, `s3`에서 `HAS`와 `OF`를 한 홉씩 더 밟아 회사와 계약을 얻습니다. 비용이 전체 엣지 수 N이 아니라 **그 노드의 차수(degree)** 에 비례합니다 — `O(deg(김하늘))`.

전체 데이터가 100만 건으로 늘어도 김하늘이 담당한 건이 12건이면 밟는 엣지는 여전히 12개 근처입니다. 이것이 **그래프 DB의 인접성 기반 탐색(index-free adjacency)** 이 주는 이득이고, 노드 승격이 그 이득을 쓸 수 있게 만들어 주는 지점입니다.

## 3. 핵심 — 왜 「노드」여야 색인이 되는가

예제 주석이 이유를 한 줄로 못 박습니다.

> `«by» 는 엣지 속성이라 색인을 걸 수 없는 엔진이 많다. 그러면 전체를 훑는다.`
> `노드로 승격하면 «김하늘» 노드에서 들어오는 엣지만 따라가면 된다.`

정리하면 두 단계입니다.

1. **시작점 확보(seek)**: 그래프 질의는 거의 항상 「어디서부터 걷기 시작할지」를 먼저 정합니다. 노드는 라벨·속성 색인의 1급 대상이므로 `(:사람 {name:'김하늘'})`을 색인 조회로 즉시 집습니다. 반면 엣지 속성 `by`는 엔진에 따라 색인 대상이 아니거나 지원이 제한적입니다. 시작점을 잡을 수 없으면 남는 선택은 전수 스캔뿐입니다.
2. **인접 리스트 순회(expand)**: 시작 노드를 잡으면 그 노드에 붙은 엣지 목록은 이미 물리적으로 인접해 저장돼 있습니다. 「들어오는 BY 엣지」만 골라 따라가는 비용은 데이터 전체 크기와 무관합니다.

즉 **문자열 속성값은 「읽는」 것이고, 노드는 「찾는」 것**입니다. 검색의 출발점이 되는 순간, 그 값은 속성으로 남아 있을 자격을 잃습니다.

## 4. 승격의 신호 — 세 가지 질문, 마지막이 결정적

이 장의 판단 기준은 세 번 묻는 것입니다.

| 질문 | 뜻 |
|---|---|
| 속성이 붙나? | 체결일, 금액, 담당자처럼 관계 자체가 데이터를 갖는가 |
| 제3의 대상과 이어지나? | 「체결」이 담당자·승인자·문서 등 다른 노드와 연결되는가 |
| **그 속성으로 검색하나?** | 그 값에서 **출발하는** 질의가 생겼는가 |

한 장 요약의 표현대로 **마지막 질문이 결정적**입니다. 앞의 두 개는 「불편하다」 수준이지만, 세 번째는 곧바로 **비용 곡선**의 문제가 됩니다. 담당자 이름을 화면에 뿌리기만 할 때는 속성으로 충분합니다. 「김하늘이 담당한 건」을 묻기 시작하면 그건 이미 노드입니다.

> 승격의 신호는 하나다. 「그 속성으로 검색하기 시작했는가.」
> 속성은 「읽는」 것이고 노드는 「찾는」 것이다. 찾기 시작하면 승격할 때다.

이 「관계를 노드로 바꿔 그 자체를 지시 대상으로 만드는」 기법을 표준 용어로 **관계의 구체화(reification)** 라 부릅니다. RDF에서는 진술 자체를 자원으로 만드는 패턴이고, 프로퍼티 그래프에서는 흔히 중간 이벤트 노드(체결, 주문, 방문)로 표현합니다.

## 5. 놓치기 쉬운 함정

### (1) 예제의 `scanned` 숫자에 속지 말 것

`q_node_model`은 파이썬으로 `incoming` 딕셔너리를 **매 호출마다 전체 엣지를 훑어** 만듭니다. 그러니 순수 파이썬 관점에서는 모델 B도 한 번은 전부 봅니다. 이 예제가 세는 `scanned`는 **인덱스 구축 이후의 탐색 비용**입니다. 실제 그래프 DB에서는 그 인덱스(라벨 색인 + 인접 리스트)가 **미리 만들어져 상주**하므로, 질의 시점 비용이 진짜로 `O(deg)`가 됩니다. 예제는 「엔진이 대신 해 주는 일」을 손으로 따라 해 본 것입니다.

### (2) 엣지 3개짜리에서는 차이가 안 보인다

> 엣지 3개짜리라 차이가 안 느껴진다. 엣지가 100만 개면 다르다.

`3 vs 2`는 아무 의미가 없습니다. 의미는 **증가율**에 있습니다. 모델 A는 데이터가 커지는 만큼 느려지고, 모델 B는 김하늘의 담당 건수만큼만 느려집니다.

### (3) 엔진에 따라 전제가 흔들린다

「엣지 속성에 색인을 못 건다」는 절대 명제가 아닙니다. Neo4j는 비교적 최근 버전부터 관계 속성 색인을 지원하고, 엔진·버전마다 지원 범위가 다릅니다. 다만 지원되더라도

- 탐색 **시작점** 확보는 여전히 노드 라벨/속성 색인이 기본 경로이고,
- 「담당자」가 제3의 대상(팀, 권한, 다른 사건)과 이어지기 시작하면 색인 유무와 무관하게 노드가 필요합니다.

그러므로 승격 판단의 근거를 「색인이 안 걸려서」 한 가지에만 두지 말고, 세 질문 전체로 보는 편이 안전합니다.

### (4) 승격은 공짜가 아니다

- 엣지 수가 늘어납니다(예제에서 3 → 9). 홉 수도 늘어나 「가온테크의 계약」 같은 질의는 1홉에서 2홉이 됩니다.
- 그래서 **승격은 늦게 하되 미루지 말라**고 합니다. 데이터가 쌓일수록 옮기는 값이 비례해서 오릅니다.
- 그리고 옮길 때 제일 오래 걸리는 건 데이터 이동이 아니라 **표기 통일**입니다. 「김하늘」, 「김 하늘」, 「hakim」이 섞여 있던 속성값을 노드로 만들려면 동일 인물 판정을 먼저 끝내야 합니다. 장 제목의 「3주」가 여기서 나옵니다.

---

## 6. 한 줄 암기

> 승격하면 「김하늘」이 **값**이 아니라 **노드**가 된다. 노드는 색인되니 **탐색 시작점**이 되고, 거기로 **들어오는 BY 엣지만** 따라가면 되므로 비용이 전체 엣지 수(N)에서 그 노드의 차수(deg)로 내려간다.
