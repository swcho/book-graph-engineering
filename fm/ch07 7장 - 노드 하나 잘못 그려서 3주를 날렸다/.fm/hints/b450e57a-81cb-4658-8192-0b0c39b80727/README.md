# 단순 그래프와 다중 그래프를 섞으면 어떤 사고가 나는가

> **질문** 단순 그래프와 다중 그래프를 섞으면 어떤 사고가 나는가?
>
> **답** 중심성을 다중 그래프로 계산하고 '거래처가 많은 회사'로 보고하면 틀린다. 계약을 여러 번 한 회사가 1등이 된다.

관련 절: 7.4 「두 종류만 있는 그래프, 그리고 겹치는 엣지」 / 예제 `content/ch07/code/ex5_multigraph.py`

---

## 1. 사고의 정체는 «단위 불일치»다

이건 그래프 이론 문제가 아니라 **단위 문제**입니다. 길이를 미터로 재 놓고 킬로미터라고 적어서 보고하는 것과 똑같은 종류의 사고예요.

- **단순 그래프(simple graph)** — 같은 노드 쌍 사이에 엣지는 최대 하나. 차수를 세면 **«서로 다른 이웃의 수»**가 나옵니다.
- **다중 그래프(multigraph)** — 같은 노드 쌍 사이에 엣지가 여러 개 존재할 수 있음(평행 엣지, parallel edge). 차수를 세면 **«붙어 있는 엣지의 수»**가 나옵니다.

두 숫자 모두 «차수(degree)»라는 같은 이름을 쓰고, 같은 함수 이름(`degree`, `degree_centrality`)으로 나오고, 같은 자리에 정수로 찍힙니다. 그런데 세는 대상이 다릅니다.

| 알고 싶은 것 | 써야 하는 모델 | 세는 단위 |
|---|---|---|
| 거래처가 몇 곳인가 | 단순 그래프 | 서로 다른 상대 |
| 거래를 몇 건 했나 | 다중 그래프 | 계약 건 |

계산은 다중 그래프로 하고, 라벨은 단순 그래프의 뜻으로 붙이는 순간 사고가 납니다. **틀린 건 계산이 아니라 라벨입니다.** 그래서 예외도 안 뜨고, 테스트도 통과하고, 숫자도 그럴듯합니다. 발견되는 시점은 보고를 받은 사업 담당자가 "이 회사가 거래처 1등일 리가 없는데요?"라고 되물을 때죠.

## 2. 책 예제로 확인 (`ex5_multigraph.py`)

```python
EDGES = [
    ("가온테크", "나루소프트", "C-2023-011"),
    ("가온테크", "나루소프트", "C-2024-088"),
    ("가온테크", "나루소프트", "C-2025-118"),
    ("가온테크", "다올물산",   "C-2025-200"),
    ("라온에너지", "라온에너지", "C-2025-301"),   # 자기 루프
]
```

| 노드 | 단순 그래프 차수 | 다중 그래프 차수 |
|---|---:|---:|
| 가온테크 | 2 | 4 |
| 나루소프트 | 1 | 3 |
| 다올물산 | 1 | 1 |
| 라온에너지 | 0 | 2 |

가온테크의 차수는 **2도 맞고 4도 맞습니다.** 거래처는 두 곳(나루소프트, 다올물산)이고, 계약은 네 건이니까요. 둘 다 참인 게 이 사고의 핵심입니다. 어느 한쪽이 버그라면 금방 잡힙니다. 둘 다 맞으니까 안 잡히는 거예요.

이 작은 예제에서 이미 이상한 일이 하나 벌어집니다. **라온에너지는 거래처가 0곳인데 다중 차수가 2입니다.** 자기 자신과의 대여 계약 하나가 «관계 2개»로 세어졌기 때문이죠. 다중 차수로 만든 순위표에서는 라온에너지가 다올물산(거래처 1곳)보다 위에 옵니다.

---

## 3. 규모를 키우면 1등이 뒤집힌다

예제가 작아서 «그래도 순위는 비슷하겠지»라고 넘어가기 쉽습니다. 아닙니다. 계약 건수 분포는 보통 한쪽으로 심하게 쏠려 있어서, 순위표 최상단이 통째로 바뀝니다.

세 회사를 만들어 봅시다.

- **나루소프트** — 거래처 **1곳**(가온테크)과 계약 **12건**. 사실상 한 회사에 종속된 하청.
- **다올물산** — 서로 다른 거래처 **7곳**과 각 1건. 진짜로 거래 폭이 넓은 회사.
- **라온에너지** — 거래처 **3곳**과 각 2건.

```python
import networkx as nx

E = []
for i in range(12):                      # 나루소프트: 한 거래처와 12번
    E.append(("나루소프트", "가온테크"))
for i in range(7):                       # 다올물산: 7개 거래처와 각 1번
    E.append(("다올물산", f"거래처{i}"))
for i in range(3):                       # 라온에너지: 3개 거래처와 각 2번
    for j in range(2):
        E.append(("라온에너지", f"거래처{i}"))

M = nx.MultiGraph(); M.add_edges_from(E)   # 다중 그래프
S = nx.Graph(M)                            # 단순 그래프로 축약
```

결과(networkx 3.6.1로 확인, 노드 11개):

| 노드 | 다중 차수 | 단순 차수 | `degree_centrality`(다중) | `degree_centrality`(단순) |
|---|---:|---:|---:|---:|
| 나루소프트 | **12** | 1 | **1.200** | 0.100 |
| 다올물산 | 7 | **7** | 0.700 | **0.700** |
| 라온에너지 | 6 | 3 | 0.600 | 0.300 |

- 다중 차수 순위: **나루소프트(12) → 다올물산(7) → 라온에너지(6)**
- 단순 차수 순위: **다올물산(7) → 라온에너지(3) → 나루소프트(1)**

**1등과 꼴등이 완전히 자리를 바꿉니다.** 거래처가 딱 한 곳인 회사가 «거래처가 가장 많은 회사» 1위로 보고됩니다. 그리고 이 회사는 대개 **가장 위험한** 회사예요. 매출이 한 거래처에 100% 몰려 있으니까요. 리스크 분산 지표로 쓰면 정반대의 결론이 나옵니다.

### 조용히 지나가지 않는 단서가 하나 있다

`degree_centrality`는 차수를 `n-1`로 나눠 0~1로 정규화하도록 설계돼 있습니다. 그런데 위 표에서 나루소프트는 **1.200**입니다. 이웃이 1명인데 «정규화된 중심성»이 1을 넘습니다. 평행 엣지가 분자에는 들어가고 분모(`n-1`)에는 반영되지 않으니 정의가 깨지는 거죠.

> **점검 습관** 중심성 값이 1을 넘으면 다중 그래프를 단순 그래프 전제의 지표에 넣었다는 신호입니다. 값의 상한을 검증하는 assert 한 줄이 이 사고를 3주에서 3분으로 줄여 줍니다.

## 4. 왜 하필 «중심성»에서 사고가 나는가

중심성은 «중요한 노드를 찾는다»는 목적 하나에 여러 정의가 걸려 있고, 정의마다 다중 엣지를 다르게 취급합니다.

| 지표 | 다중 엣지가 미치는 영향 |
|---|---|
| 차수 중심성 | 평행 엣지 수만큼 그대로 부풀음. 위 사례. 정규화 상한도 깨짐 |
| 가중 차수 / strength | 원래 «가중치 합»이라 다중 엣지와 개념이 겹침. 계약 3건을 엣지 3개로 둘지 `weight=3` 하나로 둘지에 따라 값이 같아 보이지만 다른 지표가 됨 |
| 매개 중심성(betweenness) | 최단 경로 개수 기준이라 평행 엣지가 «최단 경로 수»를 늘려 분모를 흔듦. 값이 미묘하게 달라져서 알아채기 더 어려움 |
| 고유벡터 / PageRank | 인접 행렬 기반. 평행 엣지가 행렬 원소를 2, 3으로 만들어 «세게 연결된 하나»처럼 동작. networkx는 애초에 `NetworkXNotImplemented`로 거부 |
| 군집 계수(clustering) | 삼각형을 세는 정의가 평행 엣지에서 무너짐. networkx는 거부 |

즉 지표마다 **거부하거나, 조용히 부풀리거나, 미묘하게 어긋납니다.** 셋 중 제일 위험한 게 두 번째와 세 번째죠. 거부해 주는 지표는 오히려 고마운 겁니다.

## 5. 같이 붙어 다니는 함정: 자기 루프

`ex5_multigraph.py`의 마지막 문장이 이겁니다. 자기 루프(self-loop)는 «세는 방식»이 라이브러리마다 다릅니다.

- 무방향 그래프의 관례는 **차수 2**입니다(엣지의 양 끝이 모두 그 노드니까). 예제의 `degree_multi`도 `deg[a] += 2`로 이 관례를 따릅니다.
- 그런데 같은 networkx에서 **인접 행렬로 뽑으면 대각 원소는 1**입니다. `nx.to_numpy_array`로 확인되는 사실이에요. 행렬 기반으로 짠 코드와 `G.degree()` 기반으로 짠 코드가 **같은 그래프에서 다른 숫자**를 내놓습니다.
- 방향 그래프에서는 out-degree 1 + in-degree 1로 각각 세니 또 다릅니다.

여기에 «거래처 수»라는 라벨이 붙으면 자기 루프는 **애초에 세어져선 안 되는** 엣지입니다. 자기와의 거래는 거래처가 아니니까요. 그래서 예제도 `degree_simple`에서 `if a != b`로 걸러 냅니다.

> 라이브러리를 바꾸거나 버전을 올렸는데 숫자가 «조용히» 달라지면 자기 루프를 먼저 보세요.

## 6. 라이브러리가 몰래 모델을 바꾸는 자리

두 모델이 섞이는 가장 흔한 경로는 사람이 헷갈리는 게 아니라 **코드 한 줄이 조용히 변환하는 것**입니다.

```python
M = nx.MultiGraph(); M.add_edge('a','b'); M.add_edge('a','b'); M.add_edge('a','c')
dict(M.degree())          # {'a': 3, 'b': 2, 'c': 1}   ← 다중
S = nx.Graph(M)           # 평행 엣지가 여기서 합쳐진다. 경고 없음.
dict(S.degree())          # {'a': 2, 'b': 1, 'c': 1}   ← 단순
```

`nx.Graph(M)` 한 줄에 평행 엣지가 사라집니다. 게다가 엣지 속성은 **마지막 엣지 것만 남습니다.** 계약 3건의 금액이 각각 달랐다면 두 건의 금액이 조용히 버려지죠. 로그도 경고도 없습니다.

주의해야 할 자리들:

- `nx.Graph(multigraph)` / `to_undirected()` / `to_directed()` 같은 변환 생성자
- 그래프 DB에서 `MATCH (a)-[:계약]->(b)` 로 뽑아 `DISTINCT` 없이 집계 — 계약 건수가 나옵니다. 거래처 수를 원하면 `count(DISTINCT b)`
- CSV → 그래프 적재 스크립트. 중복 행 제거를 했는지 안 했는지가 그대로 모델 선택이 됩니다
- 파이프라인 중간에 GraphFrames / igraph / cuGraph 등으로 갈아타는 지점. 다중 엣지 처리 관례가 서로 다릅니다

## 7. 예방 체크리스트

1. **무엇을 세는지 먼저 문장으로 적는다.** «거래처 수»인가 «거래 건수»인가. 이걸 정하지 않은 상태로 `degree()`를 호출하면 그 순간 이미 반쯤 틀렸습니다.
2. **이름에 단위를 박아 넣는다.** 7.3절의 `weight → cost_minutes` 교훈과 완전히 같은 처방입니다. `degree`(X) → `distinct_partner_count`, `contract_count`(O). 컬럼 이름이 곧 계약서예요.
3. **파이프라인 입구에서 모델을 한 번만 확정한다.** 「여기서부터 아래는 단순 그래프」라고 못을 박고, 축약을 명시적으로 수행합니다. 중간에 다시 다중 그래프를 섞지 않습니다.
4. **자기 루프는 적재 시점에 걸러 두거나 별도 속성으로 옮긴다.** 「라이브러리를 바꾸면 숫자가 조용히 달라지니 미리 걸러 두는 편이 낫다」가 이 장의 결론입니다.
5. **불변식을 assert한다.** `단순 차수 ≤ 다중 차수`, `정규화 중심성 ≤ 1.0`, `단순 엣지 수 ≤ 다중 엣지 수`. 세 줄로 이 사고를 잡습니다.
6. **계약을 노드로 승격하는 것도 답이다.** 7.1절의 이야기와 이어집니다. 계약이 속성(금액, 담당자, 날짜)을 갖고 그 속성으로 검색까지 하게 되면, `(회사)-[:계약]->(회사)` 다중 엣지 대신 `(회사)-[:참여]->(계약)<-[:참여]-(회사)` 구조가 맞습니다. 그러면 «거래처 수»와 «계약 건수»가 애초에 다른 질의가 되어 헷갈릴 여지 자체가 사라집니다.
7. **보고서에 모델을 같이 적는다.** "차수 중심성 상위 10개(단순 그래프, 자기 루프 제외)"처럼요. 이 한 줄이 있으면 읽는 사람이 오해할 수 없습니다.

## 8. 한 문장으로

> 단순 그래프와 다중 그래프의 차수는 **둘 다 맞는 서로 다른 숫자**다. 다중 그래프로 계산한 중심성에 «거래처가 많은 회사»라는 단순 그래프의 라벨을 붙이면, **거래처가 한 곳뿐인 회사가 1등으로 올라온다.** 계산이 틀린 게 아니라 라벨이 틀렸기 때문에 아무도 눈치채지 못한다.
