# 다중 엣지와 자기 루프: 먼저 «무엇을 세는지»를 정한다

**질문** 다중 엣지와 자기 루프를 다룰 때 먼저 정해야 할 것은 무엇인가?

**답** 무엇을 세는지다. 세는 방식이 흔들리면 같은 데이터에서 서로 다른 차수가 나온다.

---

## 한 줄로 요약하면

차수(degree)는 그래프의 「사실」이 아니라 **집계 규칙의 결과**다. 같은 엣지 목록을 놓고도
「같은 쌍은 한 번으로 센다(단순 그래프)」와 「엣지마다 센다(다중 그래프)」 중 무엇을 골랐는지에 따라
숫자가 달라진다. 그래서 알고리즘을 돌리기 **전에** 세는 규칙을 문서로 못 박아야 한다.

---

## 용어 정리

| 용어 | 뜻 |
|---|---|
| 다중 엣지 (multi-edge, parallel edge) | 같은 두 노드 사이에 놓인 2개 이상의 엣지. 예: 같은 두 회사가 계약을 세 번 체결 |
| 다중 그래프 (multigraph) | 다중 엣지를 허용하는 그래프. `networkx.MultiGraph` / `MultiDiGraph` |
| 단순 그래프 (simple graph) | 같은 쌍 사이 엣지를 최대 1개만 허용, 자기 루프 없음. `networkx.Graph` / `DiGraph` |
| 자기 루프 (self-loop) | 시작 노드와 끝 노드가 같은 엣지. 예: 자회사가 자기 자신에게 대여 |
| 차수 (degree) | 노드에 붙은 엣지 수. **무엇을 엣지 1개로 볼지에 따라 값이 바뀐다** |

---

## 책의 예제로 확인하기 (`code/ex5_multigraph.py`)

엣지 목록은 다음과 같다.

```
가온테크   → 나루소프트   C-2023-011
가온테크   → 나루소프트   C-2024-088
가온테크   → 나루소프트   C-2025-118
가온테크   → 다올물산     C-2025-200
라온에너지 → 라온에너지   C-2025-301   ← 자기 루프
```

두 가지 규칙으로 차수를 세면 이렇게 갈린다.

| 노드 | 단순 그래프 차수 | 다중 그래프 차수 |
|---|---:|---:|
| 가온테크 | 2 | 4 |
| 나루소프트 | 1 | 3 |
| 다올물산 | 1 | 1 |
| 라온에너지 | 0 | 2 |

- **가온테크의 차수는 2인가 4인가.** 둘 다 맞다. 세는 대상이 다를 뿐이다.
  - **거래처 수**를 알고 싶으면 → 단순 그래프 (중복 쌍을 하나로 접는다)
  - **거래 건수**를 알고 싶으면 → 다중 그래프 (엣지마다 센다)
- **라온에너지는 0인가 2인가.** 자기 루프를 무시하면 0, 관례대로 2로 세면 2다.

핵심은 「어느 쪽이 옳으냐」가 아니라 **어느 쪽을 쓰는지 팀이 합의하고 이름으로 남겼는지**다.

---

## 왜 사고가 나는가: 두 규칙을 섞을 때

두 방식이 각각 옳기 때문에, 사고는 계산과 해석 사이에서 규칙이 바뀔 때 난다.

> 중심성을 **다중 그래프**로 계산해 놓고 「**거래처가 많은** 회사」라고 보고하면 틀린다.
> 계약을 여러 번 반복한 회사가 1등으로 올라온다.

이 오류는 조용하다. 프로그램은 에러 없이 돌고, 표도 그럴싸하게 나오고, 순위만 조용히 뒤집힌다.
7장 3절의 「친밀도를 최단 경로에 그대로 넣어 제일 안 친한 경로를 답으로 받은」 사고와 같은 계열이다.
**숫자는 맞고 뜻이 틀린** 종류의 버그다.

---

## 자기 루프가 특히 위험한 이유

1. **관례가 여러 개다.** 무방향 그래프에서 자기 루프는 보통 차수 **2**로 센다
   (엣지의 두 끝이 모두 그 노드에 붙어 있으므로 «악수 정리»가 유지된다).
   반면 자기 루프를 «이웃 1개»로 보고 1로 세는 구현도 있다.
   방향 그래프에서는 보통 out-degree +1, in-degree +1로 각각 한 번씩 센다.
2. **알고리즘마다 처리가 다르다.** 클러스터링 계수, 삼각형 수, PageRank, 인접 행렬의 대각 성분 등에서
   자기 루프를 포함/제외하는 기본값이 갈린다.
3. **라이브러리를 바꾸거나 버전을 올리면 숫자가 말없이 달라진다.**
   같은 데이터, 같은 코드 구조인데 리포트 수치만 바뀌는 상황이 벌어진다.

책의 권고는 명확하다. **미리 걸러 두는 편이 낫다.**
자기 루프가 의미 있는 데이터라면(자회사 간 내부 거래 등) 별도 속성이나 별도 관계 타입으로 빼서
차수 계산에서 우발적으로 섞이지 않게 한다.

---

## 실무 체크리스트

1. **세는 단위를 문장으로 쓴다.** 「가온테크의 차수 = 거래 **상대 회사 수**」 vs 「= 계약 **건수**」.
   문장으로 못 쓰겠으면 아직 정해지지 않은 것이다.
2. **이름에 규칙을 박아 넣는다.** `degree` 대신 `partner_count`, `contract_count`처럼.
   (7장 3절의 `weight` → `cost_minutes` / `affinity_score`와 같은 처방이다.)
3. **저장 시점에 결정한다.** 원본은 다중 그래프로 두고(사실을 잃지 않는다),
   집계는 필요할 때 단순 그래프로 접는다. 반대로 하면 잃은 정보를 되돌릴 수 없다.
4. **자기 루프 정책을 하나로 고정한다.** 「제거」, 「차수 2로 계산」, 「별도 타입으로 분리」 중 하나를 골라
   파이프라인 전체에 같은 정책을 적용한다.
5. **라이브러리 기본값을 확인한다.** `Graph` vs `MultiGraph`, `degree()`의 자기 루프 처리,
   중심성 함수의 다중 엣지 취급을 문서에서 직접 읽는다.
6. **계산과 보고의 규칙이 같은지 점검한다.** 계산은 다중, 보고는 단순 의미 — 이 불일치가 실제 사고다.

---

## 이 장의 흐름 속 위치

7장 4절 「두 종류만 있는 그래프, 그리고 겹치는 엣지」의 후반부 주제다.
전반부의 이분 그래프 투영이 **정보를 잃고 엣지가 제곱으로 느는** 문제였다면,
다중 엣지·자기 루프는 **정보는 다 있는데 세는 규칙이 흔들려 답이 갈리는** 문제다.
장 요약의 마지막 문장이 그대로 답이다.

> 이분 그래프를 투영하면 정보가 사라지고 엣지가 제곱으로 늡니다.
> 다중 엣지와 자기 루프는 세는 방식이 흔들리니, **무엇을 세는지 먼저 정하세요.**
