# `ex1_node_or_edge.py`는 왜 엣지 3개로도 요점이 전달되는가

## 질문과 답

**질문**: `ex1_node_or_edge.py`가 엣지 3개짜리 예제로도 요점을 전달하는 방법은 무엇인가?

**답**: '훑은 엣지 수'를 함께 출력해 비용 차이를 드러낸다. 엣지가 100만 개일 때 그 차이가 실제 성능이 된다.

---

## 한 줄 정리

작은 예제는 **결과의 크기**로는 아무것도 증명하지 못한다. 그래서 이 예제는 결과 대신 **비용의 모양**을 계측해서 출력한다. 결과는 두 모델이 똑같고, 다른 건 그 결과에 도달하기까지 훑은 엣지 수뿐이다.

---

## 예제가 비교하는 두 모델

7.1절 「노드냐 엣지냐」의 소재는 "회사가 계약을 체결했다"는 관계다.

### 모델 A — 관계를 엣지로

```python
EDGE_MODEL = [
    ("가온테크",   "SIGNED", "C-2025-118", {"at": "2025-06-02", "by": "김하늘"}),
    ("가온테크",   "SIGNED", "C-2024-002", {"at": "2024-01-15", "by": "박서준"}),
    ("나루소프트", "SIGNED", "C-2025-004", {"at": "2025-01-20", "by": "김하늘"}),
]
```

담당자(`by`)와 체결일(`at`)이 **엣지 속성**으로 붙어 있다.

### 모델 B — 관계를 노드로 승격

```python
NODE_MODEL_NODES = {
    "s1": {"label": "체결", "at": "2025-06-02"},
    ...
}
NODE_MODEL_EDGES = [
    ("가온테크", "HAS", "s1"), ("s1", "OF", "C-2025-118"), ("s1", "BY", "김하늘"),
    ...
]
```

「체결」이라는 사건 자체가 노드(`s1`)가 되고, 담당자는 속성이 아니라 `BY` 엣지로 이어지는 **1급 대상**이 된다. RDF 쪽 용어로는 관계의 구체화(reification)에 해당한다.

---

## 핵심 장치: `scanned` 카운터

두 질의 함수는 모두 결과와 함께 `scanned`를 돌려준다. 이 값이 이 예제의 전부다.

```python
def q_edge_model(who):
    """«김하늘이 담당한 체결 건» — 엣지 모델에서는 모든 엣지를 훑어야 한다."""
    scanned = 0
    out = []
    for s, t, o, props in EDGE_MODEL:
        scanned += 1                      # 엣지 하나 볼 때마다 1
        if props.get("by") == who:
            out.append((s, o, props["at"]))
    return out, scanned
```

### 실제 출력

```
질문: 김하늘이 담당한 체결 건은?

모델 A (엣지)  결과 2건, 훑은 엣지 3개
    ('가온테크', 'C-2025-118', '2025-06-02')
    ('나루소프트', 'C-2025-004', '2025-01-20')

모델 B (노드 승격) 결과 2건, 훑은 엣지 2개
    ('가온테크', 'C-2025-118', '2025-06-02')
    ('나루소프트', 'C-2025-004', '2025-01-20')
```

**결과는 완전히 같다. 3 대 2, 딱 1개 차이다.** 이 숫자만 보면 "그래서 뭐?"가 정상적인 반응이고, 예제는 그 반응을 예상하고 다음 줄을 직접 인쇄한다.

```
엣지 3개짜리라 차이가 안 느껴진다. 엣지가 100만 개면 다르다.
```

---

## 왜 이 방법이 통하는가 — 숫자가 아니라 '식'을 보여준다

`scanned`가 알려주는 건 크기가 아니라 **무엇에 비례하는지**다.

| | 훑은 엣지 수 | 비례하는 값 | 엣지 100만, 답이 2건일 때 |
|---|---|---|---|
| 모델 A (엣지 속성) | 전체 엣지 수 | `O(E)` — 전체 훑기 | 약 1,000,000 |
| 모델 B (노드 승격) | 「김하늘」의 진입 차수 | `O(deg(v))` — 국소 탐색 | 2 |

작은 데이터에서는 `E`와 `deg(v)`가 둘 다 한 자릿수라 구별되지 않는다. 그러나 계측값이 각각 무엇을 세고 있는지가 코드에 드러나 있으므로, 독자는 데이터가 커졌을 때의 기울기를 머릿속에서 외삽할 수 있다. 3 대 2는 **차이의 크기가 아니라 차이의 존재와 출처**를 보여주는 최소 증거다.

이게 작은 예제로 성능 이야기를 하는 정직한 방법이다. 대안은 두 가지뿐인데 둘 다 나쁘다.

1. 100만 엣지를 실제로 생성해서 벽시계 시간을 잰다 → 예제가 무거워지고(7장 예제는 **의존성 없음**이 원칙), 측정값이 기계·언어·캐시에 흔들려 오히려 요점이 흐려진다.
2. 말로만 "느려진다"고 쓴다 → 독자가 검증할 수 없다.

`scanned`는 결정론적이고, 순수 파이썬으로 계산되며, 독자가 값을 바꿔 가며 직접 확인할 수 있다.

---

## 3 대 2 뒤에 있는 실제 이유

예제 마지막 문단이 왜 큰 데이터에서 갈리는지를 설명한다.

```
«by» 는 엣지 속성이라 색인을 걸 수 없는 엔진이 많다. 그러면 전체를 훑는다.
노드로 승격하면 «김하늘» 노드에서 들어오는 엣지만 따라가면 된다.
```

- **엣지 속성에는 색인이 잘 안 걸린다.** 노드 속성 색인은 대부분의 프로퍼티 그래프 엔진이 지원하지만, 관계(엣지) 속성 색인은 지원 범위가 좁거나 늦게 들어온 기능이다. 색인이 없으면 `props["by"] == "김하늘"`을 확인할 방법은 전체 스캔뿐이다. 즉 모델 A의 `scanned = 3`은 우연히 3인 게 아니라 **정의상 `len(EDGE_MODEL)`**이다.
- **노드는 인접 리스트로 바로 접근된다.** 그래프 엔진의 본질적 강점은 노드에서 인접 엣지로 가는 포인터 추적이다(8장에서 메모리 구조로 다시 나온다). 「김하늘」이 노드가 되는 순간 그 사람에게 붙은 엣지만 따라가면 되고, 그래프 전체 크기와 무관해진다.

### 예제 코드를 볼 때 짚고 갈 점

`q_node_model`은 호출될 때마다 `incoming` 색인을 처음부터 만든다.

```python
incoming = defaultdict(list)
for s, t, o in NODE_MODEL_EDGES:
    incoming[o].append((s, t))
```

이 색인 구축 자체는 `O(E)`이고, `scanned`에는 세지 않는다. 이건 버그가 아니라 **모델링 의도**다. 실제 그래프 데이터베이스에서 인접 구조는 질의할 때 만드는 게 아니라 저장 시점에 이미 존재하는 영속 구조다. `scanned`는 "질의 시점에 엔진이 실제로 방문해야 하는 엣지 수"만 세도록 정의되어 있다. 반대로 모델 A에서는 그 전체 스캔을 미리 대신해 줄 색인이 없다는 것이 요점이므로, 스캔이 그대로 `scanned`에 잡힌다.

## 이 예제가 최종적으로 전하려는 판단 기준

```
승격의 신호는 하나다. «그 속성으로 검색하기 시작했는가.»
속성은 «읽는» 것이고 노드는 «찾는» 것이다. 찾기 시작하면 승격할 때다.
```

7장 한 장 요약의 세 질문과 연결된다.

1. 그 관계에 속성이 붙나?
2. 제3의 대상과 이어지나? (체결 → 담당자)
3. **그 속성으로 검색하나?** ← 결정적

3번이 「예」가 되면 그 속성은 더 이상 부속 정보가 아니라 **질의의 시작점**이다. 시작점은 색인 가능한 자리에 있어야 하고, 프로퍼티 그래프에서 그 자리는 노드다. `scanned` 숫자는 결국 이 문장을 숫자로 번역한 것이다. 읽기만 할 값은 엣지 속성으로 두어도 아무 비용이 없고, 찾기 시작한 값은 `O(E)`를 물게 된다.

덧붙여 7장 요약은 **승격을 늦게 하되 미루지 말라**고 한다. 데이터가 쌓일수록 옮기는 값이 비례해서 오르고, 정작 제일 오래 걸리는 건 데이터 이동이 아니라 표기 통일이다. `scanned`가 커지는 걸 발견했을 때가 이미 마지노선에 가깝다는 뜻이다.

## 같은 기법을 쓰는 다른 예제

'훑은 개수'를 출력해 작은 예제로 비용 차이를 드러내는 방식은 이 장에서 반복된다.

- `ex2_direction.py` — 방향이 맞으면 조회 비용 `1`, 틀리면 전체 훑기. `(조회 비용 s)`를 같이 찍는다.
- `ex4_bipartite.py` — 여기서는 계측 대신 `simulate(n, k)`로 규모를 **계산해서** 표로 보여준다. 1인당 200개를 산 사용자 10만 명 → 투영 엣지 상한 20억 개. 실행할 수 없는 규모를 다룰 때의 같은 목적, 다른 수단이다.

정리하면 이 장의 예제들이 공유하는 원칙은 하나다. **작은 데이터로 큰 결론을 말하려면, 결과를 보여주는 대신 결과에 도달한 비용을 계측해서 보여준다.**
