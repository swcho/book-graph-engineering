# 다익스트라에서 경로를 복원하는 방법

**질문** 다익스트라에서 경로를 복원하는 방법은 무엇인가?

**답** `prev` 딕셔너리에 각 노드의 직전 노드를 기록해 두고, 목표에서 시작점까지 거꾸로 따라간 뒤 뒤집는다.

---

## 1. 왜 별도의 기록이 필요한가

다익스트라가 자연스럽게 만들어 내는 결과물은 **거리**뿐입니다. `dist[v]`는 "시작점에서 v까지의 최단 비용"이고, 알고리즘이 끝나면 이 숫자는 확정됩니다. 그런데 숫자만으로는 "어떻게 갔는가"를 알 수 없습니다.

`dist["C"] == 6`이라는 결과를 받아도 A→D→C로 갔는지 A→B→C로 갔는지는 복원할 수 없습니다. 거리를 계산하는 과정에서 **어느 이웃 덕분에 그 거리가 나왔는지**를 버렸기 때문입니다.

그래서 해법은 단순합니다. 버리지 않고 적어 두면 됩니다. `dist[v]`를 갱신하는 그 순간에 "누구를 거쳐서 갱신했는지"를 같이 적습니다. 이게 `prev`입니다.

```
dist[v] = 시작점에서 v까지 최단 거리   (얼마나 먼가)
prev[v] = 그 최단 경로에서 v 직전 노드  (어디서 왔는가)
```

## 2. 이 책의 코드에서 보기

7장 예제 3(`code/ex3_weights.py`)에 다익스트라를 직접 짠 코드가 있습니다. 경로 복원과 관련된 부분만 뽑으면 이렇습니다.

```python
def dijkstra(edges, start, goal, as_distance=True):
    adj = defaultdict(list)
    for a, b, w in edges:
        cost = w if as_distance else 1.0 / w
        adj[a].append((b, cost))
        adj[b].append((a, cost))
    dist = {start: 0.0}
    prev = {}                       # (1) 직전 노드 기록장
    pq = [(0.0, start)]
    while pq:
        d, u = heapq.heappop(pq)
        if u == goal:
            break
        if d > dist.get(u, float("inf")):
            continue
        for v, c in adj[u]:
            nd = d + c
            if nd < dist.get(v, float("inf")):
                dist[v] = nd
                prev[v] = u         # (2) 거리를 줄인 그 순간에 같이 적는다
                heapq.heappush(pq, (nd, v))
    path, cur = [goal], goal        # (3) 목표에서 시작
    while cur in prev:              # (4) 거꾸로 따라 올라간다
        cur = prev[cur]
        path.append(cur)
    return list(reversed(path)), round(dist.get(goal, float("inf")), 3)
```

핵심은 네 곳입니다.

**(1) `prev = {}`** — 비어 있는 딕셔너리로 시작합니다. 시작점은 직전 노드가 없으므로 영원히 `prev`에 들어가지 않습니다. 이 사실이 나중에 종료 조건으로 쓰입니다.

**(2) `prev[v] = u`** — `dist[v]`를 갱신하는 `if` 블록 **안**에 있습니다. 이 위치가 중요합니다. 거리가 줄어들 때만 직전 노드도 바뀌어야 하니까요. `if` 밖으로 빼면 더 나쁜 경로가 기록을 덮어써서 경로가 망가집니다.

**(3)~(4) 역추적** — `goal`에서 출발해 `prev[cur]`를 계속 따라가며 리스트에 쌓고, 마지막에 `reversed`로 뒤집습니다.

## 3. 역추적을 손으로 따라가 보기

예제의 엣지는 이렇습니다. `A-B(8), B-C(8), A-D(3), D-C(3)`. 숫자를 거리로 읽고 A에서 C로 가는 경로를 구하면 A→D→C(합 6)가 답입니다. 이때 `prev`는 이런 모양이 됩니다.

| 키 | 값 | 뜻 |
|---|---|---|
| `B` | `A` | B는 A에서 왔다 |
| `D` | `A` | D는 A에서 왔다 |
| `C` | `D` | C는 D에서 왔다 |

`A`는 키에 없습니다. 시작점이니까요.

역추적 과정:

```
path = ["C"],           cur = "C"
"C" in prev  → cur = prev["C"] = "D",  path = ["C", "D"]
"D" in prev  → cur = prev["D"] = "A",  path = ["C", "D", "A"]
"A" in prev  → 거짓. 루프 종료.
reversed → ["A", "D", "C"]
```

`while cur in prev`가 곧 "시작점에 도달했는가"라는 종료 조건 역할을 합니다. 시작점만 `prev`에 없기 때문에, 별도의 `if cur == start` 검사 없이도 정확히 시작점에서 멈춥니다.

## 4. 왜 뒤집어야 하는가

`prev`는 화살표가 **뒤를 가리키는** 자료구조입니다. "C의 직전은 D"만 알 수 있고 "D의 다음은 C"는 알 수 없습니다. 그래서 따라갈 수 있는 방향이 목표 → 시작 한 방향뿐이고, 쌓이는 순서도 자연히 역순이 됩니다. 사람이 읽거나 다음 단계에 넘길 때는 시작 → 목표 순서가 필요하니 마지막에 한 번 뒤집습니다.

뒤집는 대신 `path.insert(0, cur)`로 앞에 끼워 넣을 수도 있지만, 파이썬 리스트에서 `insert(0, ...)`은 매번 전체를 옮기므로 경로 길이 L에 대해 O(L²)이 됩니다. `append` 후 `reversed`가 O(L)로 더 낫습니다. `collections.deque`의 `appendleft`를 쓰면 뒤집기 없이도 O(L)입니다.

## 5. 복원 비용

복원 자체는 매우 쌉니다. 경로에 포함된 노드 수 L에 비례하는 O(L)이고, 추가 메모리는 `prev`가 노드 수 V에 비례하는 O(V)입니다. 탐색 본체가 O((V+E) log V)인 것에 비하면 무시할 수 있습니다. **경로를 안 쓸 거라도 `prev`는 그냥 기록해 두는 편이 낫습니다.** 나중에 "왜 이 경로가 나왔냐"는 질문을 받았을 때 재실행하지 않아도 답할 수 있습니다.

## 6. 흔히 걸리는 함정

**도달 불가를 구분하지 않는다.** goal에 도달할 수 없으면 `prev`에 goal이 없으므로 루프가 한 번도 돌지 않고 `path == [goal]`이 됩니다. 길이 1짜리 리스트가 "제자리 경로"처럼 보이지만 실제로는 경로가 없는 상태입니다. 예제 코드는 거리를 `float("inf")`로 함께 돌려주므로 호출하는 쪽에서 이것을 확인해야 합니다. 안전하게는 복원 후 `path[0] == start`인지 검사합니다.

```python
if path[0] != start:
    return None, float("inf")   # 도달 불가
```

**`start == goal`인 경우.** `path == [start]`가 되고 거리는 0입니다. 이건 정상이고 위의 `path[0] == start` 검사도 통과합니다. 도달 불가와 겉모습이 같으므로 검사 순서를 헷갈리지 않는 것이 중요합니다.

**`prev` 갱신을 `if` 밖에 둔다.** 앞서 말한 대로 거리를 줄이지 못한 후보까지 `prev`를 덮어쓰면, 복원된 경로가 `dist`가 말하는 비용과 맞지 않게 됩니다. 더 나쁜 것은 잘못된 덮어쓰기가 **순환**을 만들어 역추적 루프가 무한히 도는 경우입니다. 갱신 조건 안에서만 쓰면 `prev`는 항상 시작점을 뿌리로 하는 트리(최단 경로 트리)를 이루므로 순환이 생기지 않습니다.

**목표에서 조기 종료했는데 다른 노드 경로를 복원한다.** 예제 코드에는 `if u == goal: break`가 있습니다. goal까지의 `prev`는 확정되었지만 아직 큐에 남아 있던 다른 노드들의 `prev`는 확정 전일 수 있습니다. 조기 종료가 있는 구현으로 얻은 `prev`는 **그 goal에 대해서만** 신뢰해야 합니다. 여러 목적지의 경로가 필요하면 조기 종료를 빼고 전체를 다 돌린 뒤 `prev` 하나로 모든 목적지를 복원합니다(단일 출발점 최단 경로 트리).

**음수 가중치를 넣는다.** 다익스트라는 확정한 노드를 다시 보지 않으므로 음수 엣지가 있으면 `dist`도 `prev`도 틀립니다. 복원 로직이 아무리 정확해도 잘못된 경로가 나옵니다. 음수가 있으면 벨만-포드를 씁니다(이때도 `prev` 기록 방식은 동일합니다).

## 7. 변형

**엣지 정보까지 기록하기.** 다중 엣지가 있는 그래프(7.4절)에서는 "A와 B를 어느 엣지로 이었는지"까지 알아야 할 수 있습니다. 노드만 적으면 복원된 경로에서 어느 계약/어느 노선을 탔는지 사라집니다. 그럴 때는 값에 엣지 식별자를 함께 넣습니다.

```python
prev[v] = (u, edge_id)
```

**최단 경로가 여러 개일 때.** 동점 경로를 모두 원하면 값을 리스트로 두고, `nd < dist[v]`면 리스트를 새로 만들고 `nd == dist[v]`면 기존 리스트에 추가합니다. 그러면 역추적이 트리 탐색이 되고, 경로 개수가 지수적으로 늘 수 있다는 점만 주의하면 됩니다.

**다른 알고리즘도 같은 패턴.** BFS, 벨만-포드, A\* 모두 "거리를 줄인 순간 직전 노드를 적는다 → 거꾸로 따라간다 → 뒤집는다"가 그대로 통합니다. 플로이드-워셜은 모든 쌍을 다루므로 `prev` 대신 `next[u][v]`(u에서 v로 갈 때 첫 걸음) 행렬을 두고 시작점에서 앞으로 따라가는 방식을 쓰는 게 보통입니다. 이때는 뒤집을 필요가 없습니다.

**라이브러리를 쓸 때.** NetworkX의 `nx.dijkstra_path(G, s, t, weight="cost_minutes")`는 복원까지 해서 노드 리스트를 돌려주고, `nx.dijkstra_predecessor_and_distance`는 `prev`에 해당하는 선행자 딕셔너리를 직접 줍니다. 직접 짜는 것은 원리를 확인하거나 엣지 정보를 함께 실어야 할 때입니다.

## 8. 이 장의 맥락에서

7.3절이 이 코드를 쓰는 이유는 경로 복원 자체가 아니라 **가중치의 뜻**입니다. 같은 `EDGES`를 거리로 읽으면 A→D→C, 강도로 읽으면(`1/w`로 변환) A→B→C가 나옵니다. 복원 로직은 한 줄도 안 바뀌었는데 답이 반대로 나옵니다.

즉 경로 복원이 완벽하게 동작해도, `weight`라는 이름 뒤에 숨은 의미를 틀리면 알고리즘은 조용히 "가장 안 친한 경로"를 최단 경로라고 보고합니다. 저자가 2주를 날린 사고가 정확히 이것이었습니다. 예방책은 `weight` 대신 `cost_minutes`, `affinity_score`처럼 이름에 뜻을 박아 넣는 것입니다.

복원된 경로는 이 사고를 잡는 데도 쓸모가 있습니다. 거리 숫자 하나만 보면 이상한지 알 수 없지만, 경로를 펼쳐서 "왜 이쪽으로 갔지?"를 사람 눈으로 확인하면 가중치 해석이 뒤집혔다는 사실이 훨씬 빨리 드러납니다.

## 한 줄 정리

`dist`는 "얼마나 먼가", `prev`는 "어디서 왔는가"입니다. 거리를 갱신하는 그 자리에서 `prev[v] = u`를 함께 적어 두면, 나중에 목표에서 `prev`를 거꾸로 따라가 시작점에 닿은 뒤 뒤집기만 하면 경로가 나옵니다. 비용은 O(경로 길이), 검증은 `path[0] == start`.
