# 7장 도입부의 일화는 무엇이며 무엇이 문제였는가?

**답**: 계약을 `(회사)-[:계약]->(회사)` **엣지**로 그린 것이다. 화이트보드에서는 예뻤지만, 계약에 **속성과 관계가 붙기 시작하며 3주를 날렸다.**

원문 인용:

> 계약을 엣지로 그렸습니다. `(회사)-[:계약]->(회사)`. 화이트보드에서는 예뻤어요.

이 한 문장이 7장 전체의 문제 제기이고, 장 제목 「노드 하나 잘못 그려서 3주를 날렸다」의 그 "노드 하나"가 바로 **승격시키지 않은 계약**이다.

---

## 1. 왜 계약을 엣지로 그리는 게 자연스러워 보였나

한국어 문장을 그대로 그림으로 옮기면 이 모양이 나온다.

- "가온테크가 나루소프트와 **계약했다**"
- 주어 = 노드, 목적어 = 노드, **동사 = 엣지**

프로퍼티 그래프 모델링을 처음 배울 때 가장 먼저 익히는 규칙이 "명사는 노드, 동사는 엣지"다. 이 규칙만 따르면 계약은 당연히 엣지다. 게다가 화이트보드에서의 장점이 실재한다.

- 그림이 **단순하다.** 노드 2개, 엣지 1개. 회사 목록과 회사 사이의 선만 있으면 도메인이 한눈에 들어온다.
- 질의가 **짧다.** `MATCH (a:회사)-[:계약]->(b:회사)` 한 줄로 "거래 관계"가 나온다.
- 노드 수가 안 늘어난다. 계약이 100만 건이어도 노드는 회사 수만큼만 존재한다.

문제는 **화이트보드에서는 모든 모델이 다 예쁘다**는 것이다. 7장 도입부가 지적하는 게 정확히 이 지점이다.

> 노드냐 엣지냐, 방향을 어느 쪽으로, 가중치는 무슨 뜻으로. 화이트보드에서는 다 비슷해 보이는데, **6개월 뒤에 갈립니다.**

## 2. 무엇이 문제였나 — 시간 순서대로 무너진다

계약을 엣지로 두면 처음 2주는 아무 문제가 없다. 문제는 **요구사항이 하나씩 추가될 때** 순서대로 드러난다.

### 1단계: 속성이 붙는다 (아직 견딜 수 있다)

```cypher
(가온테크)-[:계약 {체결일: "2025-06-02", 금액: 5억, 상태: "진행"}]->(나루소프트)
```

프로퍼티 그래프는 엣지에도 속성을 달 수 있으므로 여기까지는 합법이고 동작한다. 하지만 이때 이미 두 가지가 어그러진다.

- **엣지 속성에는 색인을 걸 수 없는 엔진이 많다.** `code/ex1_node_or_edge.py`가 이 비용을 실측으로 보여 준다. `by`(담당자)가 엣지 속성이면 조건에 맞는 건을 찾기 위해 **엣지 전체를 훑어야** 한다.

  ```
  «by» 는 엣지 속성이라 색인을 걸 수 없는 엔진이 많다. 그러면 전체를 훑는다.
  노드로 승격하면 «김하늘» 노드에서 들어오는 엣지만 따라가면 된다.
  ```

  엣지 3개일 때는 차이를 못 느낀다. 100만 개면 다르다.
- **같은 두 회사가 계약을 두 번 하면 엣지가 두 개**가 된다. 다중 엣지(multi-edge)의 세계로 들어간 것이고, 이때부터 "차수"의 의미가 흔들린다 (5단계에서 다시 다룬다).

### 2단계: 제3의 대상과 이어져야 한다 (여기서 무너진다)

이게 결정타다. 엣지의 근본 제약은 **엣지에는 엣지를 붙일 수 없다**는 것이다. 그런데 계약은 필연적으로 다른 것들과 이어진다.

| 새로 들어온 요구 | 계약이 노드면 | 계약이 엣지면 |
|---|---|---|
| 계약 담당자는 누구인가 | `(계약)-[:담당]->(사람)` | 엣지에 엣지를 못 붙인다 |
| 이 계약에 딸린 부속 합의는 | `(부속)-[:종속]->(계약)` | 불가능 |
| 청구서·인보이스 연결 | `(청구)-[:근거]->(계약)` | 불가능 |
| 3자 계약 (회사 3곳) | 계약 노드에 참여자 3개 연결 | 엣지는 **정확히 2개** 끝점만 갖는다 |
| 계약 개정 이력 | `(계약v2)-[:개정]->(계약v1)` | 불가능 |

특히 **3자 계약**이 결정적이다. 엣지는 정의상 이항 관계(binary relation)라서 참여자가 3명 이상인 사실을 표현할 방법이 원리적으로 없다. 도메인이 조금만 현실적으로 변해도 모델이 표현력 자체를 잃는다.

우회로를 시도할 수는 있다. 계약 ID를 엣지 속성에 문자열로 박고, 담당자 정보도 엣지 속성으로 복제하고, 3자 계약은 엣지 3개로 쪼개서 같은 ID를 공유시키는 것이다. 이게 **3주가 사라지는 진짜 경로**다. 우회로마다 "같은 ID를 가진 엣지 3개는 실은 한 계약이다"라는 규칙을 애플리케이션 코드가 기억해야 하고, 그 규칙을 모르는 질의는 조용히 틀린 답을 낸다.

### 3단계: 그 속성으로 **검색**하기 시작한다 (승격 확정)

7장 한 장 요약이 제시하는 세 가지 질문이 이것이다.

> 관계를 엣지로 둘지 노드로 승격할지는 **세 번 물어보면** 정해집니다.
> ① 속성이 붙나, ② 제3의 대상과 이어지나, ③ **그 속성으로 검색하나.**
> 마지막 질문이 결정적이에요. **속성은 읽는 것이고 노드는 찾는 것입니다.**

- "계약 상세를 보여 줄 때 체결일을 함께 표시한다" → **읽기**. 엣지 속성으로 충분하다.
- "김하늘이 담당한 계약을 모두 찾아라", "2025년 상반기 체결 건을 찾아라" → **찾기**. 승격해야 한다.

`ex1_node_or_edge.py`의 마지막 줄이 이 기준을 그대로 못 박는다.

```
승격의 신호는 하나다. «그 속성으로 검색하기 시작했는가.»
속성은 «읽는» 것이고 노드는 «찾는» 것이다. 찾기 시작하면 승격할 때다.
```

## 3. 올바른 모델 — 관계를 노드로 승격한다

계약은 **동사처럼 들리지만 실은 명사**다. 계약서라는 실체가 있고, 번호가 있고, 당사자가 있고, 이력이 있고, 그것 자체가 검색 대상이다. 이렇게 관계를 독립된 노드로 끌어올리는 것을 **구체화(reification)** 라고 하고, 7장 키워드 표에 [표준]으로 올라 있다 ([RDF 1.2 Schema](https://www.w3.org/TR/rdf12-schema/)).

`ex1_node_or_edge.py`의 두 모델 비교가 이 변환을 압축해서 보여 준다.

```python
# 모델 A: 관계를 엣지로
("가온테크", "SIGNED", "C-2025-118", {"at": "2025-06-02", "by": "김하늘"}),

# 모델 B: 관계를 노드로 승격
"s1": {"label": "체결", "at": "2025-06-02"},
("가온테크", "HAS", "s1"), ("s1", "OF", "C-2025-118"), ("s1", "BY", "김하늘"),
```

엣지 하나가 **노드 1개 + 엣지 3개**로 바뀐다. 그림은 복잡해지지만, 그 대가로 얻는 것이 있다.

- 담당자(`김하늘`)가 **속성에서 노드로** 올라갔다 → 색인 없이도 "들어오는 `BY` 엣지"만 따라가면 된다.
- 체결 사건에 무엇이든 더 붙일 수 있다 → 금액, 승인자, 부속 합의, 개정 이력.
- 참여자가 3명이어도 된다 → 계약 노드에 `HAS`를 3개 걸면 끝이다.

**전형적인 승격 패턴** (관계 → 노드로 바꿀 때 이름 짓는 법):

| 엣지로 쓰던 것 | 승격 후 노드 이름 |
|---|---|
| `-[:계약]->` | `계약` 또는 `체결` |
| `-[:주문]->` | `주문` |
| `-[:결제]->` | `결제 거래` |
| `-[:출연]->` | `역할`(캐스팅) |
| `-[:재직]->` | `재직 기간`(고용) |

동사를 **사건(event)** 또는 **사실(fact)** 이라는 명사로 바꿔 부르면 노드가 된다.

## 4. 그럼 처음부터 다 노드로 만들면 되나 — 아니다

여기서 반대 방향의 과잉이 나온다. 모든 관계를 노드로 승격하면 그래프가 홉(hop) 폭발을 일으킨다. 원래 1홉이던 질의가 2홉이 되고, 노드 수가 엣지 수만큼 늘어난다. "회사 A와 회사 B가 거래하는가"를 물으려면 항상 중간 노드를 거쳐야 한다.

7장의 처방은 양쪽 다 피하는 쪽이다.

> **승격은 늦게 하되 미루지 마세요.** 데이터가 쌓일수록 옮기는 값이 비례해서 오릅니다. 그리고 옮길 때 제일 오래 걸리는 건 데이터 이동이 아니라 **표기 통일**입니다.

두 가지를 구분해야 한다.

- **늦게 한다**: 필요해지기 전에 미리 승격하지 않는다. 속성만 읽고 있고 제3자와 안 이어진다면 엣지로 둔다. 추측으로 만든 중간 노드는 순수한 비용이다.
- **미루지 않는다**: 세 질문 중 하나라도 "예"가 되면 그날 옮긴다. 미루는 동안 비용이 **선형으로 오른다.**

### 3주가 걸린 이유는 데이터 이동이 아니다

이 대목이 실무적으로 가장 값진 통찰이다. 100만 엣지를 노드로 옮기는 **마이그레이션 스크립트 자체는 몇 시간**이면 끝난다. 3주를 잡아먹는 건 **표기 통일**이다.

- 엣지 시절에 각자 다르게 부르던 이름들 — `계약`, `SIGNED`, `contract`, `CONTRACT_WITH` — 이 코드베이스 곳곳에 흩어져 있다.
- 그 이름들을 참조하는 **질의 문자열, 대시보드, 배치 잡, 리포트, 문서, 테스트**를 전부 찾아 고쳐야 한다.
- 애플리케이션 코드가 기억하던 우회 규칙("같은 ID 엣지 3개는 한 계약")을 하나씩 걷어내야 한다.
- 그리고 이 작업은 **자동화가 잘 안 된다.** 문자열 치환으로 안전하게 끝나지 않고, 사람이 하나하나 확인해야 한다.

즉 도입부 일화의 3주는 "잘못 그린 그림을 고치는 시간"이 아니라 **"잘못 그린 그림이 6개월 동안 코드베이스에 퍼진 걸 되감는 시간"** 이다.

## 5. 엣지로 둔 대가가 숫자를 조용히 틀리게 만드는 방식

계약을 엣지로 두면 다중 엣지가 생기고, 그때부터 "차수"가 두 가지 뜻을 갖는다. `code/ex5_multigraph.py`가 정확히 이 계약 데이터로 그걸 보여 준다.

```python
EDGES = [
    ("가온테크", "나루소프트", "C-2023-011"),
    ("가온테크", "나루소프트", "C-2024-088"),
    ("가온테크", "나루소프트", "C-2025-118"),
    ("가온테크", "다올물산", "C-2025-200"),
    ("라온에너지", "라온에너지", "C-2025-301"),   # 자기 루프
]
```

가온테크의 차수는 **2**인가 **4**인가.

- **단순 그래프**로 세면 2 → "거래처가 2곳이다"
- **다중 그래프**로 세면 4 → "계약이 4건이다"

둘 다 맞다. 사고는 섞을 때 난다.

```
중심성을 다중 그래프로 계산해 놓고 «거래처가 많은 회사»라고 보고하면 틀린다.
계약을 여러 번 한 회사가 1등이 된다.
```

계약을 **노드로 승격해 두면 이 혼동이 구조적으로 사라진다.** `(회사)-[:HAS]->(계약)` 에서 회사의 차수는 계약 건수이고, 거래처 수는 계약 노드를 거쳐 두 홉 나간 회사의 distinct 개수다. **세는 대상이 그래프 구조에 명시**되니 섞일 수가 없다.

## 6. 7장의 다른 사고들과 같은 계열이다

도입부 일화는 단독 실수담이 아니라 장 전체를 여는 **패턴의 대표 사례**다. 7장은 같은 형태의 사고를 셋 더 보여 준다.

| 절 | 사고 | 대가 | 예방책 |
|---|---|---|---|
| 7.1 | 계약을 **엣지**로 그렸다 | **3주** | 세 질문(속성/제3자/검색)으로 승격 판단 |
| 7.2 | 방향을 자주 안 묻는 쪽으로 잡았다 | 전체 훑기 | 자주 묻는 쪽을 **나가는** 방향으로 |
| 7.3 | 친밀도(클수록 가깝다)를 최단경로에 넣었다 | **2주** | `weight` 대신 `cost_minutes`, `affinity_score` |
| 7.4 | 다중/단순 그래프 차수를 섞었다 | 틀린 보고 | 무엇을 세는지 먼저 정한다 |

공통점이 명확하다. **네 사고 모두 화이트보드에서는 정상으로 보였고, 실행할 때도 에러가 안 났고, 몇 주 뒤에 드러났다.** 그래프 모델링 실수는 크래시가 아니라 **조용히 틀린 답**과 **되감기 비용**으로 청구된다.

## 7. 한 줄 정리

계약을 `(회사)-[:계약]->(회사)` 엣지로 그린 게 도입부의 일화다. 엣지는 속성만 읽는 관계에는 맞지만, 계약은 **속성이 붙고, 제3의 대상(담당자·부속합의·청구)과 이어지고, 그 속성으로 검색하는** 대상이었다. 세 신호가 다 켜졌으니 처음부터 노드였어야 했고, 늦게 알아차린 대가로 3주가 갔다. 그리고 그 3주의 대부분은 데이터 이동이 아니라 **표기 통일**이었다.
