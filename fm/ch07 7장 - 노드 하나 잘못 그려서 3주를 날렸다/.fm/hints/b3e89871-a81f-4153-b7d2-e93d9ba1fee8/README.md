# 투영 엣지 상한: 1인당 200개 × 사용자 10만 명

## 질문과 답

**질문.** 1인당 200개를 산 사용자 10만 명의 투영 엣지 상한은 얼마인가?

**답.** 약 20억 개다. 투영이 편해 보이지만 규모에서 무너지는 이유다.

---

## 1. 이분 그래프와 투영이 뭔가

이분 그래프(bipartite graph)는 노드가 두 종류로 갈리고, **엣지가 항상 다른 종류 사이에만** 놓이는 그래프다. 7장 예제의 구매 기록이 딱 그 모양이다.

```
(사용자) -[:구매]-> (상품)
```

사용자끼리는 엣지가 없고, 상품끼리도 엣지가 없다. 원본 데이터는 이렇게 생겼다.

| 사용자 | 상품 |
|---|---|
| u1 | 상품A, 상품B |
| u2 | 상품A, 상품B, 상품C |
| u3 | 상품C |

엣지는 6개.

**투영(projection)** 은 한쪽 종류만 남기고, "같은 상대를 공유하는 노드끼리 잇는" 새 그래프를 만드는 작업이다. 상품 쪽으로 투영하면 "함께 산 상품끼리 잇기"가 된다.

```
상품A — 상품B  (함께 산 사람 2명: u1, u2)
상품A — 상품C  (함께 산 사람 1명: u2)
상품B — 상품C  (함께 산 사람 1명: u2)
```

투영이 매력적인 이유는 명확하다. "함께 산 상품"을 물어보기가 한 홉으로 끝난다. 추천, 유사도, 커뮤니티 탐지 같은 알고리즘들이 대개 단일 종류 그래프를 전제하니 형식도 맞다.

## 2. 왜 제곱으로 느는가

핵심은 이 한 줄이다. **사용자 한 명이 k개를 사면, 그 사용자 한 명 때문에 상품 쪽에 `C(k, 2)`개의 엣지가 생긴다.**

`C(k, 2) = k(k-1)/2`

k개 중 2개를 고르는 모든 조합이 "같은 사람이 함께 샀다"는 이유로 이어지기 때문이다. 예제 코드의 계산식이 정확히 이것이다.

```python
def simulate(n_users, items_per_user):
    """투영 엣지 수가 어떻게 느는지 계산으로 본다."""
    return n_users * items_per_user * (items_per_user - 1) // 2
```

원본 이분 그래프의 엣지 수는 `n × k`로 **선형**인데, 투영 결과는 `n × k²/2`로 **k에 대해 제곱**이다. 사용자 수 n에는 선형이지만, 1인당 구매 수 k가 조금만 늘어도 폭발한다.

## 3. 답 계산

```
100,000 × 200 × 199 / 2
= 100,000 × 19,900
= 1,990,000,000
```

**약 20억 개.** 원본 이분 그래프의 엣지는 `100,000 × 200 = 2,000만` 개였다. 투영 한 번으로 **100배 가까이** 부풀었다. 정확히는 `(k-1)/2 = 99.5`배다.

### 규모별 비교표 (예제 4의 출력)

| 사용자 | 1인당 구매 | 원본 엣지 | 투영 엣지(상한) | 배율 |
|---:|---:|---:|---:|---:|
| 1,000 | 10 | 10,000 | 45,000 | 4.5배 |
| 1,000 | 50 | 50,000 | 1,225,000 | 24.5배 |
| 100,000 | 50 | 5,000,000 | 122,500,000 | 24.5배 |
| 100,000 | 200 | 20,000,000 | **1,990,000,000** | 99.5배 |

표에서 읽어야 할 것은 두 가지다.

- 3행 → 4행: **사용자 수는 그대로**인데 1인당 구매만 50 → 200(4배)으로 늘리자 투영 엣지가 1.2억 → 20억(약 16배)이 됐다. 4² = 16. 제곱이다.
- 2행 → 3행: **1인당 구매는 그대로**고 사용자만 100배 늘리자 투영 엣지도 딱 100배. 사용자 수에는 선형이다.

그래서 투영이 위험해지는 진짜 트리거는 "사용자가 많아지는 것"이 아니라 **"헤비 유저 한 명이 k를 키우는 것"** 이다. 봇, 도매 계정, 크롤러 계정 하나가 5,000개를 사면 그 계정 하나가 약 1,250만 개 엣지를 만든다.

## 4. "상한"이라는 단서가 중요한 이유

원문의 표현을 그대로 옮기면 이렇다.

> 실제로는 중복이 합쳐지니 이보다 적지만, 상한이 이렇다는 게 중요하다.

서로 다른 사용자가 같은 상품 쌍을 함께 사면 엣지 `(상품A, 상품B)`는 **하나로 합쳐지고 가중치만 올라간다**. 예제의 `project()` 함수가 하는 일이 그것이다.

```python
out[(x, y)] += 1   # 같은 쌍이면 새 엣지가 아니라 가중치 증가
```

그래서 실제 엣지 수는 다른 상한에도 걸린다. 상품이 M개면 가능한 쌍은 최대 `C(M, 2)`개다. 상품이 10만 개라면 `C(100,000, 2) ≈ 50억`이니 20억은 여전히 그 안이고, 상품이 1만 개라면 `C(10,000, 2) ≈ 5,000만`이 실질 천장이 된다. 즉 진짜 결과는 `min(n·C(k,2), C(M,2))` 아래에 있다.

그런데 그럼에도 상한을 봐야 하는 이유는, **투영을 계산하는 과정의 비용은 중복 제거 전 값에 지배된다**는 데 있다. 20억 개의 쌍을 다 생성해 본 뒤에야 중복이 합쳐진다. 최종 결과가 5,000만 개라 해도 `combinations()`를 20억 번 돌리는 시간과, 그걸 집계하는 해시 테이블 메모리는 피할 수 없다. 3주를 날리는 자리가 여기다.

## 5. 투영이 버리는 것

숫자보다 조용하지만 더 위험한 손실이 있다. 예제의 표현대로다.

> 버려진 것: 누가 샀는지. 투영 그래프만 보면 u1, u2, u3 이 사라진다.

상품 쪽으로 투영한 그래프에는 사용자 노드가 없다. 그래서 다음 질문들에 **원리적으로** 답할 수 없다.

- "상품A와 상품B를 함께 산 사람이 **누구**인가" — 가중치 2는 알지만 u1, u2라는 사실은 소실됐다.
- "그 2명이 서로 다른 사람인가, 같은 사람이 두 번 산 건가"
- "이 연결이 봇 한 명이 만든 것인가, 서로 무관한 100명이 만든 것인가"

가중치는 숫자만 남기고 근거를 지운다. 나중에 "이 추천 왜 나왔어요?"라는 질문을 받으면 투영 그래프만으로는 설명이 안 된다. 원본 이분 그래프를 다시 뒤져야 한다.

## 6. 대안 두 가지 (원문)

원문이 제시하는 해법은 정확히 두 가지다.

**1. 투영하지 말고 이분 그래프 그대로 2홉을 돈다. 필요할 때만 계산한다.**

```cypher
MATCH (p1:상품)<-[:구매]-(u:사용자)-[:구매]->(p2:상품)
WHERE p1.id = $target
RETURN p2, count(DISTINCT u) AS 함께_산_사람
ORDER BY 함께_산_사람 DESC LIMIT 10
```

전체 투영을 물리적으로 만들지 않고, 물어본 상품 하나에 대해서만 그 자리에서 계산한다. 저장 비용은 0이고 사용자 정보도 살아 있다. 대신 질의마다 2홉 비용을 낸다. 인기 상품 하나가 100만 명에게 팔렸으면 그 한 노드에서 100만 홉이 튄다(수퍼노드 문제).

**2. 투영하되 «함께 산 사람 N명 이상»으로 자른다. 대개 3명이면 충분하다.**

가중치 1인 엣지는 우연이다. 한 사람이 우유와 등산화를 같은 날 산 것뿐이다. 이런 엣지가 투영 결과의 대부분을 차지하면서 신호는 거의 주지 않는다. 임계값 3으로 자르면 엣지 수가 보통 한두 자릿수 배로 줄고, 남은 엣지는 오히려 더 믿을 만해진다.

원문 저자가 쓰는 기준이 실전에서 바로 쓸 만하다.

> 저는 2번을 쓰고, 자르는 값은 엣지 수가 노드 수의 20배를 넘지 않게 잡는다.

즉 임계값을 고정 상수로 정하는 게 아니라, **결과 밀도(평균 차수 ≤ 40, 즉 엣지/노드 ≤ 20)를 목표로 두고 임계값을 역산**한다. 데이터가 자라도 그래프가 무너지지 않는 이유는 이 자동 조절 때문이다.

## 7. 외우는 법

- 공식: **`n × k(k-1)/2`** — 사용자 수 × 1인당 구매 쌍의 수
- 대입: `100,000 × 200 × 199 / 2 = 19.9억 ≈ **20억**`
- 한 줄 요약: **k에 제곱, n에 선형. 원본 2,000만이 투영 20억.**
- 판단 기준: 투영 결과가 노드 수의 20배를 넘으면 임계값으로 자른다. 그래도 안 되면 투영을 포기하고 2홉으로 돈다.
