# SQL/PGQ의 가치를 3장 내용과 연결하면?

**질문**: SQL/PGQ의 가치를 3장 내용과 연결하면 무엇인가?

**답**: 테이블을 그대로 두고 그래프 시각만 얹으므로 '두 벌 운영'의 비용을 내지 않아도 된다.

---

## 1. 카드가 가리키는 원문

11.4절 「테이블은 그대로 두고 그래프로 보기」와 예제 `code/ex4_sql_pgq.py`의 결론 문장이 이 카드의 출처입니다.

```
SQL/PGQ 의 값어치는 «데이터를 옮기지 않아도 된다»는 데 있다.
테이블은 그대로 두고 그래프로 보는 시각만 얹는다.
3장에서 본 «두 벌 운영»의 비용을 안 내도 된다는 뜻이다.
...
그리고 옮기지 않아도 된다는 게 공짜라는 뜻은 아니다.
조인 폭발은 그대로 남는다(3장). 저장 위치가 아니라 «따라가는 값»이 문제였으니까.
```

핵심 단어가 **«데이터를 옮기지 않아도 된다»** 입니다. 뒤집어 말하면, 그래프 질의를 하려고 별도 그래프 DB를 세우는 순간 **원본 테이블 한 벌 + 그래프 한 벌**을 동시에 살려 둬야 하고, 그 비용이 3장에서 말한 「두 벌 운영」입니다.

---

## 2. SQL/PGQ가 정확히 무엇을 하는가

SQL/PGQ는 ISO/IEC 9075-16:2023, 즉 **SQL 표준의 16번째 파트**입니다. 새 데이터베이스가 아니라 SQL의 확장 문법이에요. 하는 일은 두 가지뿐입니다.

**(1) 기존 테이블에 그래프 «뷰»를 선언한다** — `CREATE PROPERTY GRAPH`

```sql
CREATE PROPERTY GRAPH biz
  VERTEX TABLES (
    company KEY (name) LABEL Company PROPERTIES (name, grade),
    contract KEY (id)  LABEL Contract PROPERTIES (id, started_on, ended_on)
  )
  EDGE TABLES (
    signed     SOURCE KEY (company_name) REFERENCES company (name)
               DESTINATION KEY (contract_id) REFERENCES contract (id)
               LABEL Signed,
    terminated SOURCE KEY (company_name) REFERENCES company (name)
               DESTINATION KEY (contract_id) REFERENCES contract (id)
               LABEL Terminated
  );
```

여기서 새로 만들어지는 데이터가 **하나도 없다**는 점을 보세요. `company`, `contract`, `signed`, `terminated`는 이미 있던 평범한 테이블입니다. PGQ는 그중 어느 테이블을 «노드»로 볼지, 어느 테이블을 «엣지»로 볼지, 그리고 엣지의 출발·도착을 어느 외래 키로 잡을지만 **메타데이터로 선언**합니다. 뷰(view)와 같은 성격입니다.

**(2) 그 뷰 위에서 그래프 패턴으로 질의한다** — `GRAPH_TABLE(... MATCH ...)`

```sql
SELECT * FROM GRAPH_TABLE (biz
  MATCH (c IS Company)-[IS Terminated]->(o IS Contract),
        (c)-[IS Signed]->(n IS Contract)
  WHERE o.ended_on < n.started_on
  COLUMNS (c.name AS 고객)
);
```

`GRAPH_TABLE(...)`은 **테이블을 돌려주는 함수**입니다. 그래서 결과를 그냥 SQL 서브쿼리처럼 쓸 수 있고, 바깥에서 `JOIN`·`GROUP BY`·`WINDOW` 함수를 그대로 붙일 수 있습니다. 즉 그래프 패턴이 SQL 세계 안으로 들어온 것이고, SQL 밖으로 나가는 게 아닙니다.

11장 예제의 `PLAIN_SQL`(다섯 겹 `JOIN`)과 위 `MATCH` 두 줄이 **같은 답**을 낸다는 것도 함께 확인하세요. 표현력이 아니라 **가독성**이 달라지는 겁니다.

## 3. '두 벌 운영'이 왜 비용인가 — 구체적으로

「관계형 DB가 원본, 그래프 DB는 그래프 질의 전용」이라는 구조는 아주 흔한 선택입니다. 그리고 그 순간부터 아래 비용이 **영구적으로** 발생합니다.

### (1) 동기화 파이프라인 — 없던 시스템 하나가 생긴다

- 원본 테이블의 변경을 그래프 DB로 흘려보내는 장치를 새로 만들고, 새로 운영해야 합니다. CDC(변경 데이터 캡처), Kafka 커넥터, 배치 ETL, 애플리케이션 이중 쓰기(dual write) 중 무엇이든 하나는 있어야 합니다.
- 이 파이프라인 자체가 장애 지점입니다. 죽으면 그래프 쪽이 조용히 낡습니다 — **에러가 아니라 오답**으로 나타나는 게 최악입니다.
- 재처리(replay)·백필(backfill) 절차를 별도로 설계해야 합니다. 「어제 파이프라인이 6시간 멈췄다」를 복구하는 런북이 필요합니다.
- 이중 쓰기를 택하면 분산 트랜잭션 문제가 따라옵니다. 관계형에는 커밋됐는데 그래프에는 안 들어간 상태를 어떻게 처리할 것인가. 3장이 「표가 이긴 이유」로 꼽은 **트랜잭션**이 바로 이 지점에서 깨집니다.

### (2) 정합성 시차 — 답이 두 개가 된다

- 파이프라인이 정상이어도 지연은 남습니다. 초 단위든 시간 단위든, **두 저장소가 서로 다른 답을 하는 창(window)** 이 항상 존재합니다.
- 그래서 「관계형 리포트에는 계약이 118건인데 그래프 대시보드는 117건」 같은 문의가 주기적으로 옵니다. 조사에 드는 시간이 실질 비용입니다.
- 「어느 쪽이 진실인가(source of truth)」를 조직적으로 합의해 두지 않으면 사고 조사 때마다 논쟁이 반복됩니다.
- 두 저장소가 실제로 같은지 검증하는 **정합성 감사 잡(reconciliation job)** 을 또 만들어야 합니다. 두 벌을 운영하려고 세 번째 시스템이 생기는 셈입니다.

### (3) 이중 스키마 변경 — 변경 비용이 곱해진다

- 컬럼 하나 추가가 이제 「관계형 DDL + 그래프 스키마 + 매핑 코드 + 파이프라인 + 정합성 잡」의 동시 변경이 됩니다.
- 배포 순서가 생깁니다. 어느 쪽을 먼저 올려도 그 사이 구간에서는 매핑이 어긋나므로, 하위 호환을 유지하는 다단계 배포를 설계해야 합니다.
- 관계형과 그래프의 모델링 관용구가 달라서 **1:1 대응이 안 되는 변경**이 생깁니다. 예를 들어 관계형의 연결 테이블(join table)에 속성이 붙으면, 그래프에서 그것을 엣지 속성으로 둘지 별도 노드로 승격할지 결정해야 합니다(5장의 LPG/RDF 모델링 문제와 같은 결).
- 마이그레이션 도구도 두 벌입니다. 관계형 쪽 마이그레이션 프레임워크와 그래프 쪽 스키마 관리 방식이 서로 모릅니다.

### (4) 운영·백업·권한 이중화 — 상시 고정비

- **운영**: 모니터링 지표, 알림 규칙, 용량 계획, 버전 업그레이드, 성능 튜닝 지식을 엔진별로 따로 갖춰야 합니다. 그래프 엔진의 실행 계획을 읽을 수 있는 사람(11장 예제 5)이 팀에 있어야 하고, 그 사람이 휴가를 가면 공백이 생깁니다.
- **백업/복구**: 스냅숏 주기, 보존 정책, 복구 리허설이 두 배입니다. 게다가 더 어려운 문제가 있습니다 — 두 저장소를 **같은 시점으로** 되돌려야 하는데, 각자 백업 시점이 다르면 복구 직후 정합성이 깨집니다. 「그래프는 다시 만들면 된다(파생 데이터로 취급)」는 전략을 쓰면 전체 재구축 시간이 곧 복구 목표 시간(RTO)이 됩니다.
- **권한/보안**: 계정·역할·행 수준 접근 제어·감사 로그·개인정보 마스킹을 두 시스템에 각각 구현해야 합니다. 관계형에서 가려 놓은 컬럼이 그래프 쪽 속성으로는 그대로 노출되는 사고가 여기서 나옵니다. 규제 대응(삭제 요청, 보존 기간)도 두 곳에서 증명해야 합니다.
- **비용**: 라이선스, 인스턴스, 스토리지가 문자 그대로 두 벌입니다. 원본 데이터를 두 번 저장하니까요.

## 4. SQL/PGQ가 회피하는 것 vs 회피하지 못하는 것

이 구분이 카드의 진짜 요점입니다.

### 회피하는 것 — 위 (1)~(4) 전부

저장소가 **하나**니까요.

| 두 벌 운영의 비용 | SQL/PGQ에서 |
|---|---|
| 동기화 파이프라인 | **사라짐**. 복제할 대상이 없다. 뷰는 항상 원본 그 자체다 |
| 정합성 시차 | **사라짐**. 시차의 원인인 두 번째 사본이 없다 |
| 이중 스키마 변경 | **줄어듦**. 관계형 DDL 한 번 + 그래프 뷰 정의 갱신. 데이터 이관 없음 |
| 운영·백업·권한 이중화 | **사라짐**. 기존 DB의 백업·계정·감사·트랜잭션을 그대로 물려받는다 |

3장의 관점에서 특히 중요한 건 **트랜잭션과 제약을 잃지 않는다**는 점입니다. 3장이 「표가 40년 이긴 이유」로 꼽은 셋 — 선언적 질의, 제약, 트랜잭션 — 을 포기하지 않은 채로 그래프 패턴 문법만 얻는 구조입니다. 별도 그래프 DB로 옮기는 선택은 보통 이 셋 중 일부를 내놓아야 하죠.

부가 효과로 **가독성**도 얻습니다. 3장 4절의 재귀 CTE 20줄이 PGQ에서는 가변 길이 경로 패턴 몇 글자가 됩니다. 「되긴 되는데」의 그 답답함이 문법 차원에서 해소됩니다.

### 회피하지 못하는 것 1 — 조인 폭발(성능)

**이것이 카드에서 가장 자주 놓치는 부분입니다.**

11장 예제의 마지막 줄이 이유를 정확히 말합니다.

> 조인 폭발은 그대로 남는다(3장). 저장 위치가 아니라 «따라가는 값»이 문제였으니까.

3장 3절의 결론은 「표가 놓친 건 **저장이 아니라 따라가기**」였습니다. 4홉 질의에서 조인이 순회보다 78배 느렸던 그 측정값이요. 원인은 데이터가 테이블에 있다는 사실 자체가 아니라, 조인이 홉마다 중간 결과를 곱해 나가는 반면 순회는 방문한 만큼만 읽는다는 **실행 방식의 차이**입니다.

SQL/PGQ는 **문법**을 바꿉니다. 실행 엔진을 바꿔 주는 게 아닙니다. `MATCH` 패턴이 결국 관계형 옵티마이저의 조인 계획으로 컴파일된다면, 3장에서 본 그 곡선은 그대로 나옵니다. 예쁜 문법으로 쓴 느린 질의가 되는 것이죠.

바꿔 말하면 SQL/PGQ가 해결하는 것은 **표현의 문제**이고, 남기는 것은 **실행의 문제**입니다. 엔진이 인접성 색인·순회 연산자 같은 그래프 전용 실행 경로를 내부적으로 구현했다면 성능도 개선될 수 있지만, 그것은 표준이 보장하는 바가 아니라 개별 구현의 품질 문제입니다. 그래서 「PGQ를 쓰면 그래프 DB만큼 빠르다」는 결론으로 넘어가면 안 됩니다.

### 회피하지 못하는 것 2 — 구현 성숙도

11장이 확인 시점(2026년 8월)을 강조하며 붙인 단서입니다.

> 다만 2026년 8월 기준으로, 이 문법을 프로덕션에서 쓰는 팀을 저는 못 봤다. 구현이 덜 퍼졌다.

그래서 11장 예제 4는 `sqlite3`로 **같은 뜻의 평범한 SQL**을 돌려 답을 맞춰 보는 방식으로 작성됐습니다. PGQ 문법은 출력으로 «보여 주기»만 하고, 실제 실행은 5중 조인 SQL이 담당합니다. 이건 예제의 결함이 아니라 **의도된 서술**입니다 — 「돌아가는 코드」가 아니라 「앞으로 이렇게 될 가능성」을 보여 주는 것.

이 태도는 11장 3절의 GQL 이야기와 정확히 같은 구조입니다. 예제 3에서 `LET`·`NEXT`·`FILTER` 같은 GQL 표준 전용 절이 Kuzu에서 실패하는 것을 실제로 세어 보였듯이, **「표준이 나왔다」와 「표준대로 돌아간다」 사이에는 몇 년이 있습니다.** SQL-92 이후로도 방언이 10년 넘게 남았던 전례가 있고요.

### 회피하지 못하는 것 3 — 관계형 모델링의 부담

- 그래프 뷰를 선언하려면 엣지 테이블에 깔끔한 외래 키가 있어야 합니다. 스키마가 지저분하면(합성 키, 다형적 참조, 문자열로 인코딩된 관계) 매핑을 위해 관계형 쪽을 먼저 정리해야 합니다.
- 스키마가 없거나 자주 바뀌는 데이터, 매우 이질적인 엣지 타입이 계속 늘어나는 워크로드는 여전히 관계형 뒤에 두기가 어색합니다. PGQ는 「이미 정형화된 관계형 데이터를 그래프로 보고 싶다」에 강하고, 「모델이 아직 흐물흐물하다」에는 약합니다.

## 5. 그래서 어떻게 판단하는가

카드의 답을 실무 판단으로 옮기면 이렇습니다.

- **문법·가독성이 문제였다면** (재귀 CTE 20줄이 유지보수 불가) → SQL/PGQ가 정답 방향. 단, 지금 쓰는 엔진이 지원하는지 확인 시점을 명시해서 확인.
- **성능이 문제였다면** (4홉에서 78배) → SQL/PGQ는 답이 아닐 수 있습니다. 실행 방식이 바뀌는지를 따로 검증해야 하고, 그래프 전용 엔진 도입을 계속 검토할 이유가 남습니다.
- **그래프 전용 엔진을 도입하기로 했다면** → 위 3절의 네 가지 비용을 「도입 비용」이 아니라 **상시 운영비**로 견적에 넣으세요. 두 벌 운영의 진짜 청구서는 첫 달이 아니라 2년째에 옵니다.

## 6. 한 줄로 외울 것

> **SQL/PGQ는 데이터를 옮기지 않고 「보는 방식」만 바꾼다. 그래서 두 벌 운영의 비용(동기화·정합성·이중 스키마·이중 운영)은 없어지지만, 조인 폭발은 남는다 — 문제는 저장 위치가 아니라 「따라가는 값」이었으니까.**
