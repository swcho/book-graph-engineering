# 선언형 질의 언어의 대가

**질문** — 선언형 질의 언어의 대가는 무엇인가?

**답** — 무엇을 원하는지만 적으면 편하지만, 느릴 때 왜 느린지 알려면 실행 계획을 읽어야 한다.

---

## 1. 「무엇」과 「어떻게」가 갈라진다

11장이 비교하는 세 언어는 그래프를 서로 다르게 생각합니다.

| 언어 | 사고 방식 | 성격 |
|---|---|---|
| Cypher | 그림 — `(c)-[:Signed]->(n)` | 선언형 |
| SPARQL | 문장 — `?c ex:signed ?n .` | 선언형 |
| Gremlin | 걸음 — `.out('signed')` | 명령형에 가깝다 |

`ex1_three_languages.py`가 마지막에 찍는 문장이 이 장의 축입니다.

> 앞 둘은 선언형이다. 무엇을 원하는지만 적고 방법은 엔진이 정한다.
> Gremlin 은 명령형에 가깝다. 순회 순서를 내가 정한다.
> 그래서 Gremlin 은 세밀한 제어가 되고, 대신 최적화기가 도와줄 여지가 적다.

선언형에서 내가 쓰는 것은 **결과의 명세**입니다. "해지했다가 그 뒤에 다시 계약한 고객"이라는 조건을 적으면 끝이고, 어느 테이블부터 훑을지·어떤 색인을 탈지·조인을 어떤 순서로 붙일지는 **최적화기(optimizer)** 가 정합니다.

이 분리가 선언형의 값어치입니다. 데이터가 100배 늘어도 질의문은 그대로 두고 엔진이 알아서 다른 계획을 고르니까요. 그리고 바로 이 분리가 대가의 출처입니다.

## 2. 대가: 성능 문제가 내 코드에 없다

명령형에서 느리면 원인이 내가 쓴 줄 안에 있습니다. 루프를 잘못 돌렸거나, 순서를 잘못 정했거나. 파일을 읽으면 보입니다.

선언형에서 느리면 **내가 쓴 줄에는 아무 문제가 없습니다.** 문제는 내가 쓰지 않은 부분, 즉 최적화기가 내린 결정에 숨어 있습니다. 주로 세 곳입니다.

### (1) 통계 오차

최적화기는 실제 데이터를 다 세어 보고 계획을 세우지 않습니다. 미리 모아 둔 **통계(statistics)** — 테이블 행 수, 컬럼별 서로 다른 값 개수, 히스토그램, 널 비율 — 를 보고 추정합니다. 이 통계가 낡으면(대량 적재 후 갱신을 안 했거나, 샘플링 오차가 크거나) 추정이 틀리고, 틀린 추정 위에 세운 계획이 잘못된 계획이 됩니다. 질의문은 한 글자도 안 틀렸는데요.

### (2) 카디널리티 추정 실패

계획의 품질은 사실상 "이 단계를 지나면 몇 행이 남는가"를 얼마나 맞히는지로 결정됩니다. 이게 **카디널리티 추정**입니다. 문제는 오차가 단계마다 **곱해진다**는 점입니다. 조인 세 개를 거치는 사이 10배 오차가 1000배 오차로 자라고, 그러면 "중간 결과가 작으니 메모리에 올려도 된다"고 판단해 고른 계획이 실제로는 디스크로 흘러넘칩니다.

그래프 질의는 특히 취약합니다. 가변 길이 경로(`-[:ParentOf*1..3]->`)나 다중 홉 패턴은 홉마다 팬아웃이 데이터 모양에 따라 크게 달라지기 때문에, 정직한 통계가 있어도 추정이 잘 어긋납니다.

### (3) 조인 순서 / 시작점 선택

같은 결과를 내는 조인 순서는 수없이 많고, 그중 좋은 것과 나쁜 것 사이 차이는 수십~수천 배입니다. `ex5_read_plan.py`가 이걸 눈으로 보여 줍니다.

```
사람 20,000명, 도시 12개

  MATCH (c:City)<-[:LivesIn]-(p:Person) WHERE c.name = '도시3'   # 작은 쪽에서 시작
  MATCH (p:Person)-[:LivesIn]->(c:City) WHERE p.city = '도시3'   # 큰 쪽에서 시작
```

두 질의는 **같은 답**을 내지만, 하나는 12개 중 하나를 찍어서 거기 붙은 간선만 따라가고, 다른 하나는 20,000명을 훑고 나서 걸러냅니다. 어느 쪽에서 시작할지가 성능을 정하고, 그 결정은 질의문이 아니라 계획에 적혀 있습니다.

정리하면 **질의문이 아니라 계획이 성능을 정합니다.** 그래서 선언형을 쓰는 값은 계획을 읽을 줄 아는 능력으로 냅니다.

## 3. 같은 질의문이 저절로 느려진다

여기가 제일 불편한 부분입니다. 선언형에서는 **코드를 하나도 안 바꿨는데 어제 50ms던 질의가 오늘 30초**가 될 수 있습니다. 배포도 없었고, 스키마 변경도 없었습니다. 바뀐 것은 데이터 분포뿐입니다.

전형적인 시나리오들:

- **틈새 고객이 대형 고객이 됨** — `WHERE c.name = '도시3'` 같은 조건이 예전엔 200행을 골라냈는데 지금은 80만 행을 골라낸다. 최적화기가 "선택도가 높다"고 보고 색인 조회를 골랐지만, 이제는 전체 스캔이 나은 상황이 됐다.
- **분포가 치우침** — 노드 대부분의 차수가 5인데 몇 개가 50만이 됐다(허브). 평균만 보는 추정치는 허브를 못 보고, 그 허브를 지나는 경로에서 조인이 폭발한다.
- **통계 갱신 시점이 임계선을 넘음** — 대량 적재 직후, 아직 통계가 옛 모습일 때 실행된 질의가 옛 데이터에 맞는 계획을 받는다.
- **계획 캐시가 옛 계획을 붙들고 있음** — 파라미터 하나 다른 값으로 처음 컴파일된 계획이 재사용되면서, 지금 파라미터에는 최악인 순서를 계속 쓴다.

`ex4_sql_pgq.py`가 짚는 지점도 같은 계열입니다. SQL/PGQ로 테이블을 옮기지 않고 그래프 시각만 얹어도, **조인 폭발은 그대로 남습니다.** 저장 위치를 바꾸는 것으로는 "따라가는 값이 몇 개인가"라는 문제가 해결되지 않으니까요.

## 4. 그래서 계획을 읽는다

`ex5_read_plan.py`는 `EXPLAIN`으로 계획을 뽑고, 무엇을 볼지 셋으로 줄여 줍니다.

1. **어느 테이블부터 훑는가** — 「스캔」이 어디에 있나
2. **색인을 타는가, 전체를 훑는가**
3. **중간 결과가 몇 행으로 추정되는가**

3번이 가장 값진 항목입니다. 추정 행 수를 실제 행 수와 비교하면(엔진이 `EXPLAIN ANALYZE` 계열을 지원하면 둘이 나란히 나옵니다) 앞 절에서 말한 추정 실패를 바로 잡아낼 수 있습니다. 추정 200행 / 실제 40만 행이면 원인은 이미 나온 겁니다.

읽는 순서에 대한 실무 팁: 계획은 대체로 트리이고, **가장 안쪽·가장 아래 노드가 먼저 실행**됩니다. 위로 올라가며 행 수가 어디서 폭발하는지 찾으면 됩니다.

## 5. 대가를 지불하는 방법

- 느린 질의를 만나면 질의문을 고치기 전에 **계획을 먼저 뽑는다.** 추측으로 `WHERE` 절 순서를 바꿔 보는 것은 선언형에서 대개 헛수고입니다(엔진이 순서를 다시 정하니까요).
- **추정 대 실제**를 비교해 통계 문제인지 계획 문제인지 가른다.
- 통계 문제면 통계를 갱신하고, 계획 문제면 힌트·재작성·색인 추가로 최적화기의 선택지를 바꾼다.
- **데이터 분포 변화를 성능 회귀의 후보 원인으로 상시 의심한다.** "코드 안 바꼈는데요"는 선언형에서 알리바이가 되지 않습니다.
- 질의문을 한곳에 모으고, `ORDER BY`를 강제하고, 엔진 고유 함수를 격리하고, 각 질의가 답하는 질문을 주석으로 남긴다(11장 요약). 계획을 비교하려면 같은 질의를 같은 자리에서 찾을 수 있어야 합니다.

11장은 여기서 "읽을 줄 알아야 한다"까지만 다루고, **계획을 고치는 법은 33장**으로 넘깁니다.

## 한 줄로

선언형은 「어떻게」를 엔진에 넘겨서 편해지지만, 그 대가로 성능의 원인도 엔진 쪽으로 넘어갑니다. 내 코드에 없는 원인을 보려면 실행 계획이라는 창을 열 수밖에 없습니다.
