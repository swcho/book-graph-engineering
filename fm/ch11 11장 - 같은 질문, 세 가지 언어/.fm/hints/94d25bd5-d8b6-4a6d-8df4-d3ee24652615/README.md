# `ex3_gql_dialects.py`는 왜 일부러 실패하는 질의를 넣는가

## 한 줄 답

**실패 자체가 이 예제의 결과물이기 때문입니다.** 「표준이 있어도 방언은 남는다」는 주장을 문장으로 설명하는 대신, 표준 문법을 실제 엔진에 그대로 밀어넣고 파서가 거부하는 장면을 눈으로 보게 만든 것입니다.

예제 첫 줄의 독스트링이 의도를 그대로 적어 놓았습니다.

> GQL(ISO/IEC 39075:2024) 문법을 그대로 넣어 보고 되는지 안 되는지 표시한다.
> «표준이 있어도 방언이 남는다»를 말이 아니라 결과로 확인하는 게 목적이다.

그래서 실패는 버그가 아니고, 고쳐야 할 TODO도 아닙니다. **측정값**입니다.

---

## 예제의 구조: 이건 negative test다

`ex3`은 평범한 데모가 아니라 **negative test(부정 테스트)** 성격의 코드입니다. 일반 예제는 "성공하는 코드"를 보여 주지만, 이 예제는 "무엇이 실패하는가"를 관측 대상으로 삼습니다.

구조를 보면 설계 의도가 드러납니다.

1. **공통 준비**: Kuzu 임베디드 DB에 `Person` / `Knows`로 아주 작은 그래프를 만듭니다. 데이터가 원인이 될 여지를 없애기 위해 일부러 3개 노드, 2개 엣지짜리 최소 규모입니다.
2. **케이스 표**: `CASES`의 각 항목이 `(설명, 문법 계열, 질의문)` 3-튜플입니다. 여기서 **「문법 계열」 열이 이 예제의 핵심 장치**입니다. `GQL/Cypher 공통`, `GQL 표준`, `Cypher 방언`으로 미리 라벨을 붙여 두었기 때문에, 실행 결과와 라벨을 나란히 놓으면 "어느 계열이 통하고 어느 계열이 막히는가"가 표로 정리됩니다.
3. **예외를 잡아서 표에 찍는다**: `try/except Exception`으로 감싸고, 예외 메시지의 첫 줄 38자만 잘라서 `실패 — ...`로 출력합니다. 예외를 삼켜 버리는 게 아니라 **결과 칸에 기록**합니다.
4. **집계**: `ok`, `fail`을 세어서 마지막에 `성공 N / 실패 M`을 찍습니다. 실패 개수가 출력의 일부라는 게 결정적입니다. 실패가 0이 되면 예제가 말하려던 것이 사라지고, 대신 "이제 엔진이 GQL을 받는다"는 새 사실이 드러납니다. 어느 쪽이든 유용한 정보라서, 시간이 지나도 이 예제는 계속 뭔가를 알려 줍니다.

즉 이 코드는 **실패를 예외 상황이 아니라 데이터 포인트로 취급**합니다. 그래서 스크립트가 죽지 않고 끝까지 돌아 표를 완성합니다.

## 어떤 절이 통하고 어떤 절이 막히는가

실제로 돌려 본 결과입니다 (Kuzu 0.11.3, 확인 시점 2026년 8월).

```
항목                     계열               결과
----------------------------------------------------------------
기본 패턴 매칭               GQL/Cypher 공통    성공 (3행)
WHERE 절                GQL/Cypher 공통    성공 (2행)
가변 길이 경로               Cypher 방언        성공 (3행)
GQL 표준: LET 절          GQL 표준           실패 — Parser exception: Invalid input <MATCH
GQL 표준: NEXT 절         GQL 표준           실패 — Parser exception: Invalid input < NEXT
GQL 표준: FILTER 절       GQL 표준           실패 — Parser exception: Invalid input <MATCH
Cypher 방언: WITH 절      Cypher 방언        성공 (2행)

성공 4 / 실패 3
```

### 통하는 것 (4개)

| 질의 | 계열 | 왜 통하나 |
|---|---|---|
| `MATCH (p:Person) RETURN p.name ORDER BY p.name` | GQL/Cypher 공통 | GQL은 Cypher의 ASCII-art 패턴 매칭을 사실상 그대로 받아들였습니다. `MATCH` + `RETURN` + `ORDER BY`는 두 언어의 교집합입니다. |
| `... WHERE p.age > 30 ...` | GQL/Cypher 공통 | `WHERE`도 공통 영역입니다. 여기까지는 "표준이 왔다"고 해서 다시 쓸 게 없습니다. |
| `-[:Knows*1..2]->` | Cypher 방언 | 상한 있는 가변 길이 경로. Cypher 계열 엔진에서 잘 돕니다(11.2절의 그 표기). GQL은 경로에 대해 `TRAIL`/`ACYCLIC` 같은 자체 모드와 양화 표기를 갖고 있어 세부가 다릅니다. |
| `WITH p WHERE p.age > 30` | Cypher 방언 | Cypher의 파이프 연결 절. **표준이 아닌 쪽이 오히려 잘 돈다**는 게 이 행의 요점입니다. GQL은 같은 일을 `LET` / `FILTER` / `NEXT`로 나눠 쓰기 때문에, `WITH`는 표준 문법이 아닌데도 현실에서는 이게 동작하는 문법입니다. |

### 막히는 것 (3개) — 전부 「GQL 표준」 계열

| 질의 | GQL에서의 역할 | 엔진 반응 |
|---|---|---|
| `MATCH (p:Person) LET nm = p.name RETURN nm` | `LET`은 중간 변수를 바인딩하는 GQL 표준 절 (Cypher의 `WITH ... AS`가 하는 일의 일부) | `Parser exception: Invalid input <MATCH ...` — 파서가 `LET` 토큰을 모릅니다 |
| `MATCH (p:Person) RETURN p.name AS n NEXT RETURN n` | `NEXT`는 질의문(statement)을 **선형으로 이어 붙이는** GQL의 연결자. GQL 설계에서 파이프라인의 핵심 |  `Invalid input < NEXT ...` |
| `MATCH (p:Person) FILTER p.age > 30 RETURN p.name` | `FILTER`는 이미 바인딩된 결과 스트림을 걸러내는 GQL 표준 절 | `Invalid input <MATCH ...` |

**패턴이 아주 깔끔합니다.**

- 실패한 3개는 **전부** `GQL 표준` 라벨이 붙은 것들입니다.
- 성공한 4개는 `GQL/Cypher 공통` 2개 + `Cypher 방언` 2개입니다. **GQL 전용 절만 골라서 다 실패했습니다.**

읽어야 할 결론은 여기입니다. Kuzu가 나쁜 엔진이라서가 아닙니다. 2026년 시점에 Cypher 계열 엔진들은 **GQL과 겹치는 부분(패턴 매칭)은 이미 지원하지만, GQL 고유의 절 구조는 아직 파서에 들어오지 않았다**는 것입니다. 실패 메시지가 실행 시점 오류가 아니라 **`Parser exception`, 즉 파싱 단계에서 나온다는 점**도 중요합니다. 의미가 안 맞는 게 아니라, 애초에 그 문법을 모르는 것입니다. 부분 지원이 아니고 미지원입니다.

## 왜 이 방식이 문서보다 신뢰할 만한가

같은 주장을 하는 세 가지 방법을 비교해 보면 차이가 보입니다.

**(1) 문장으로 쓰기** — "GQL은 2024년에 표준이 됐지만 엔진 지원은 아직 부족합니다."
읽는 사람이 검증할 수 없습니다. 얼마나 부족한지, 무엇이 되고 무엇이 안 되는지 모릅니다. 그리고 이 문장은 몇 년 뒤에 틀린 문장이 되어도 스스로 틀렸다고 알려 주지 않습니다.

**(2) 벤더 문서/호환성 표를 인용하기** — 이게 문서의 함정입니다.
- 벤더 문서는 **마케팅 압력**을 받습니다. "GQL 지원"이라는 문구가 실제로는 "GQL과 겹치는 패턴 매칭 지원"을 뜻하는 경우가 흔합니다. 부분 지원과 완전 지원의 경계가 문서에서는 흐려집니다.
- 문서는 **낡습니다**. 지원 예정이 지원으로 적혀 있거나, 반대로 이미 구현된 게 문서에 반영이 안 되어 있습니다.
- 문서는 **버전을 특정하지 않습니다**. 지금 내 `requirements.txt`에 박혀 있는 그 버전이 되는지는 안 나옵니다.
- 로드맵/블로그는 **의도**를 말하고, 파서는 **사실**을 말합니다.

**(3) 실행해서 결과를 남기기** — `ex3`이 택한 방법입니다.
- **반증 가능합니다.** 독자가 `python3 ex3_gql_dialects.py`를 그대로 돌려서 같은 표가 나오는지 확인할 수 있습니다. 주장이 재현 가능한 절차로 바뀝니다.
- **버전이 고정됩니다.** 예제 독스트링에 `확인 시점 2026년 8월, Kuzu 0.11.3`이 박혀 있고, 결과는 정확히 그 조합에 대한 것입니다. "지원한다/안 한다"가 아니라 "이 버전에서 이 절이 파싱되지 않는다"는 좁고 검증 가능한 명제가 됩니다.
- **자동으로 만료됩니다.** 시간이 흘러 Kuzu가 `LET`을 지원하기 시작하면, 그날 이 예제는 `성공 5 / 실패 2`를 찍습니다. 문서라면 낡은 채로 남아 사람을 속이지만, 실행되는 예제는 **자기가 낡았다는 사실을 스스로 출력합니다.** 이게 실행 결과를 근거로 삼는 가장 큰 이득입니다.
- **경계가 정밀합니다.** "지원이 부족하다"가 아니라 "`MATCH`/`WHERE`/`ORDER BY`/`WITH`는 되고 `LET`/`NEXT`/`FILTER`는 파서에서 막힌다"까지 나옵니다. 이식 계획을 세울 때 실제로 쓸 수 있는 해상도입니다.
- **실패 모드까지 보여 줍니다.** `Parser exception`이라는 것을 알면, 이게 "쓰면 느리다"나 "결과가 다르다"가 아니라 "아예 실행 불가"라는 걸 알 수 있습니다. 우회 가능성의 판단이 달라집니다.

한 문장으로: **문서는 벤더의 주장이고, 예제 출력은 엔진의 진술입니다.** 방언 문제처럼 벤더 주장과 실물이 어긋나기 쉬운 주제에서는 후자만 믿을 수 있습니다.

## 그래서 실무로 뭘 가져가나

예제 마지막 출력이 결론입니다.

> «표준이 나왔다»와 «표준대로 돌아간다» 사이에 몇 년이 있다.
> SQL 도 같은 길을 걸었다. SQL-92 가 나오고도 방언이 10년 넘게 남았다.

표준의 즉각적 효과는 「지금 코드가 바뀐다」가 아니라 「방향이 정해진다」입니다(11장 요약). 그러니 지금 할 일은 GQL로 다시 쓰는 게 아니라, 나중에 옮길 수 있게 준비하는 것입니다.

- 질의문을 코드에 흩뿌리지 말고 한곳에 모은다
- 엔진 고유 함수는 별도 파일로 격리한다
- `ORDER BY`를 강제한다 (엔진마다 기본 정렬이 다르므로 결과 비교가 가능해지도록)
- 「이 질의가 어떤 질문에 답하는가」를 주석으로 남긴다 — 다시 쓸 때 문법이 아니라 **의도**가 필요하기 때문입니다

그리고 이 예제 자체가 하나의 습관을 제안하고 있습니다. **어떤 문법이 되는지 궁금하면 문서를 읽지 말고 7줄짜리 케이스 표를 만들어 돌려 보라**는 것. 자기 스택에 대한 방언 지원 현황을 30줄 안에 측정할 수 있습니다.
