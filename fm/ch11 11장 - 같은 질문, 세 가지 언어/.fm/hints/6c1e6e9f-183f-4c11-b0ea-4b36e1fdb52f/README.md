# `ex2_path_queries.py`가 비교하는 두 질의

**답:** `'직접 자회사만'`(1홉)과 `'1~3단계 아래 전부'`(가변 길이)입니다. 후자에서 표기 차이가 드러납니다.

---

## 한 줄 정리

`ex2`는 **질의 두 개 × 언어 두 개**의 2×2 표입니다. 첫 질의는 **대조군**이고, 둘째 질의가 **처리군**입니다. 첫 질의에서 Cypher와 SPARQL이 거의 동형이라는 걸 먼저 보여 준 다음, 똑같은 질문을 「여러 홉」으로 한 단계만 확장했더니 두 언어의 표기가 갈라진다 — 이걸 말이 아니라 실행 결과로 보이는 게 이 예제의 전부입니다.

## 코드에서 확인

`QUERIES` 딕셔너리가 정확히 두 항목입니다. 키가 곧 「비교하는 두 질의」의 이름이고, 값은 `(Cypher, SPARQL)` 쌍입니다.

```python
QUERIES = {
    "직접 자회사만": (
        "MATCH (a:Co)-[:ParentOf]->(b:Co) RETURN a.name, b.name ORDER BY a.name, b.name",
        """PREFIX ex: <http://example.org/>
           SELECT ?p ?c WHERE { ?a ex:parentOf ?b . ?a ex:name ?p . ?b ex:name ?c }
           ORDER BY ?p ?c"""),
    "1~3단계 아래 전부": (
        "MATCH (a:Co)-[:ParentOf*1..3]->(b:Co) RETURN a.name, b.name ORDER BY a.name, b.name",
        """PREFIX ex: <http://example.org/>
           SELECT ?p ?c WHERE { ?a ex:parentOf+ ?b . ?a ex:name ?p . ?b ex:name ?c }
           ORDER BY ?p ?c"""),
}
```

두 질의의 차이는 **딱 한 글자 자리**입니다.

| | 1홉 | 가변 길이 |
|---|---|---|
| Cypher | `-[:ParentOf]->` | `-[:ParentOf*1..3]->` |
| SPARQL | `?a ex:parentOf ?b` | `?a ex:parentOf+ ?b` |

데이터는 `seed.py`의 3노드 사슬 하나입니다. 가온테크 → 가온소프트 → 가온연구소 (`PARENT_OF = [("가온테크", "가온소프트"), ("가온소프트", "가온연구소")]`, TTL 쪽은 `ex:parentOf`로 같은 사실).

## 왜 이 쌍으로 짝지었나

### 1홉에서는 세 언어가 거의 동형이다

「직접 자회사만」은 어느 언어로 써도 **모양이 같습니다**. 관계 하나를 한 번 따라가는 것뿐이라, 표현할 자유도가 없습니다.

- Cypher: 화살표 하나 — `(a)-[:ParentOf]->(b)`
- SPARQL: 트리플 하나 — `?a ex:parentOf ?b .`
- Gremlin: 스텝 하나 — `.out('parentOf')`
- SQL: 셀프 조인 한 번 — `JOIN parent_of ...`

11.1절의 「그림 / 문장 / 걸음」이라는 사고방식 차이는 여기서도 있지만, **비용 차이는 없습니다**. 1홉만 필요한 팀에게 "Cypher랑 SPARQL 중 뭐가 더 좋냐"는 질문은 사실 답이 없습니다. 그래서 첫 질의는 「여기까지는 논쟁할 게 없다」는 기준선을 깔아 두는 역할입니다.

### 가변 길이에서 갈라진다

한 홉을 「1~3홉」으로 바꾸는 순간 언어별 능력 차이가 노출됩니다. 예제가 마지막에 직접 나란히 세워 줍니다.

```
표기를 나란히 놓으면 이렇다.
  Cypher : -[:ParentOf*1..3]->     상한을 «반드시» 쓸 수 있다
  SPARQL : ex:parentOf+            상한 표기가 없다
  SQL    : WITH RECURSIVE ... 20줄  (3장 참조)
```

- **Cypher**: `*1..3`으로 하한과 상한을 문법에 직접 적습니다. 「최대 3홉」이 질의문 안에 박혀 있습니다.
- **SPARQL**: `+`(1회 이상)와 `*`(0회 이상)뿐입니다. **「최대 몇 홉」을 적는 표준 문법이 없습니다.** `+`는 상한 없는 이행 폐쇄(transitive closure)입니다.
- **SQL**: 가변 길이가 문법에 없어서 `WITH RECURSIVE` 재귀 CTE로 직접 구현해야 하고, 그게 스무 줄이 됩니다(3장). `ex2`는 SQL을 실제로 돌리지는 않고 이 줄에서 참조만 합니다 — 실행하는 건 Kuzu(Cypher)와 rdflib(SPARQL) 둘입니다.

## 실제 실행 결과

Kuzu 0.11.3 + rdflib 7.x에서 `python3 ex2_path_queries.py`를 돌린 결과입니다.

```
== 직접 자회사만 ==
  Cypher 2행: [('가온소프트', '가온연구소'), ('가온테크', '가온소프트')]
  SPARQL 2행: [('가온소프트', '가온연구소'), ('가온테크', '가온소프트')]

== 1~3단계 아래 전부 ==
  Cypher 3행: [('가온소프트', '가온연구소'), ('가온테크', '가온소프트'), ('가온테크', '가온연구소')]
  SPARQL 3행: [('가온소프트', '가온연구소'), ('가온테크', '가온소프트'), ('가온테크', '가온연구소')]
```

여기서 읽어야 할 것:

1. **1홉은 2행, 가변 길이는 3행.** 늘어난 한 행 `('가온테크', '가온연구소')`가 바로 2홉 손자입니다. 「가변 길이가 실제로 뭘 더 잡아 오는가」의 답이 이 한 행입니다.
2. **네 결과가 전부 같습니다.** 답이 갈린 게 아니라 **표기가 갈렸습니다.** 이 카드의 답변에 "후자에서 표기 차이가 드러난다"고 적힌 이유입니다. 예제의 요점은 결과 불일치가 아니라 「같은 답을 쓰는 방식이 다르다」입니다.

### 여기서 함정 하나 — 결과가 같은 건 데이터가 얕아서다

`*1..3`과 `+`는 **의미가 다릅니다**. 그런데 위 결과는 같습니다. 사슬이 3노드(최대 2홉)라서 상한 3에 애초에 걸리지 않기 때문입니다. 사슬을 6노드(`C0 → C1 → ... → C5`)로 늘리면 즉시 갈라집니다.

```
Cypher *1..3 : 12행
SPARQL   +   : 15행
차집합(SPARQL만): [('C0', 'C4'), ('C0', 'C5'), ('C1', 'C5')]
```

`+`가 4홉·5홉까지 다 끌고 오는 3행이 그대로 차이입니다. 즉 **예제의 두 질의가 같은 답을 낸 건 우연**이고, 데이터가 깊어지면 `+`는 그래프 전체 깊이까지 따라갑니다. 이게 다음 문단의 실무 문제로 이어집니다.

## 그래서 실무에서 뭐가 문제인가

```
SPARQL 의 경로 표현에는 «최대 몇 홉»을 적는 표준 문법이 없다.
그래서 9장에서 본 «상한을 걸어라»를 SPARQL 에서는 다른 방식으로 해야 한다.
질의 타임아웃, 결과 개수 제한, 아니면 깊이를 명시적으로 펼쳐 쓰기.

표준이 있다고 모든 게 표준으로 되는 건 아니다. 이런 구멍이 실무를 정한다.
```

9장의 교훈이 「가변 길이 경로에는 상한을 걸어라」였습니다. Cypher는 그 상한을 **질의문 안에** 씁니다. SPARQL은 쓸 자리가 없어서 **질의문 밖에서** 막아야 합니다.

- 질의 타임아웃 (엔진/엔드포인트 설정)
- `LIMIT`으로 결과 개수 제한 (홉 수 제한이 아니라 행 수 제한 — 같은 보호가 아닙니다)
- 깊이를 손으로 펼쳐 쓰기 — `?a ex:parentOf ?b`, `?a ex:parentOf/ex:parentOf ?b`, `?a ex:parentOf/ex:parentOf/ex:parentOf ?b`를 `UNION`으로 묶는 식

세 방법 모두 「질의문을 읽으면 상한이 보인다」는 성질을 잃습니다. 상한이 인프라 설정이나 반복된 트리플 나열로 흩어집니다.

### 표준 근거

SPARQL 1.1 속성 경로의 연산자는 `iri`, `^elt`, `elt1/elt2`, `elt1|elt2`, `elt*`, `elt+`, `elt?`, `!iri`, `(elt)`뿐입니다. 상한을 표현하는 수량자가 없습니다.

흥미로운 배경: `{n}`, `{n,m}`, `{n,}`, `{,m}` 같은 **경계 있는 반복 문법이 SPARQL 1.1 작업 초안에는 있었고, 권고안(REC)이 되기 전에 삭제됐습니다.** `*`, `+`, `?`의 의미를 「비계수(non-counting)」 — 즉 중복 경로를 세지 않고 도달 가능성만 판정 — 로 바꾸기로 결정하면서, 홉 수를 세는 중괄호 문법과 의미가 맞지 않게 됐기 때문입니다. 그래서 SPARQL의 상한 부재는 빠뜨린 게 아니라 **의미론상의 선택**입니다. Apache Jena ARQ 등 일부 구현이 비표준 확장으로 중괄호 형태를 되살려 놓은 경우가 있는데, 표준이 아니라 곧 이식성이 없습니다.

## 다른 절과 어떻게 맞물리나

- **11.1 「그림, 문장, 걸음」** → `ex1`. 같은 질문, 세 언어, 같은 답. 사고방식 차이.
- **11.2 「경로 표현에서 갈린다」** → **`ex2`. 이 카드.** 차이가 제일 크게 벌어지는 자리.
- **11.3 「2024년에 표준이 됐다. 그런데」** → `ex3`. GQL 표준 절(`LET`/`NEXT`/`FILTER`)을 Kuzu에 넣어 보고 실패를 세어 봅니다.

`ex2`와 `ex3`이 같은 이야기의 두 판본입니다. `ex2`는 「표준(SPARQL) 안에 구멍이 있다」, `ex3`은 「표준(GQL)이 있어도 엔진이 안 받는다」. 둘 다 「표준이 있다 ≠ 표준대로 된다」입니다.

## 확인 문제

1. `ex2`의 두 질의 이름을 그대로 대 보세요. → `'직접 자회사만'`, `'1~3단계 아래 전부'`
2. 두 질의의 Cypher 표기 차이는? → `-[:ParentOf]->` vs `-[:ParentOf*1..3]->`
3. 두 질의의 SPARQL 표기 차이는? → `ex:parentOf` vs `ex:parentOf+`
4. 1홉 2행, 가변 길이 3행. 늘어난 한 행은? → `('가온테크', '가온연구소')` (2홉 손자)
5. Cypher `*1..3`과 SPARQL `+`가 예제 데이터에서 같은 결과인 이유는? → 사슬이 최대 2홉이라 상한 3에 걸리지 않는다. 데이터가 깊어지면 갈라진다.
6. SPARQL에서 「최대 3홉」을 걸려면? → 표준 문법이 없으니 타임아웃 / `LIMIT` / 깊이를 `UNION`으로 펼쳐 쓰기
