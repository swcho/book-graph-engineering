# 선언형 vs 명령형 질의 언어의 트레이드오프

> **Q.** 선언형과 명령형 질의 언어의 트레이드오프는 무엇인가?
>
> **A.** 선언형은 무엇을 원하는지만 적고 방법은 엔진이 정한다. Gremlin 같은 명령형은 세밀한 제어가 되는 대신 최적화기가 도와줄 여지가 적다.

## 한 줄로 잡는 핵심

| | 선언형 (Cypher, SPARQL, SQL, GQL) | 명령형 / 순회형 (Gremlin) |
|---|---|---|
| 내가 적는 것 | **무엇(what)** — 원하는 결과의 모양 | **어떻게(how)** — 어디로 몇 걸음 갈지 |
| 실행 순서 결정자 | 질의 **최적화기(optimizer)** | **나(개발자)** |
| 얻는 것 | 최적화기가 통계를 보고 알아서 빠른 계획을 고른다 | 순회 순서·중단 조건·분기까지 손으로 제어한다 |
| 잃는 것 | 느릴 때 **왜** 느린지 알려면 실행 계획을 읽어야 한다 | 내가 나쁜 순서를 적으면 최적화기가 **구해 주지 못한다** |

트레이드오프의 본질은 **"제어권을 누가 갖는가"** 한 축입니다. 제어권을 엔진에 넘기면(선언형) 짧고 이식성 있는 질의를 얻지만 성능이 블랙박스가 되고, 제어권을 내가 쥐면(명령형) 성능을 손으로 만질 수 있지만 최적화기가 개입할 틈이 사라집니다.

## 11장이 이 답을 끌어내는 방식

11장의 `ex1_three_languages.py`는 **똑같은 질문 하나**를 세 언어로 씁니다.

> 질문: 해지했다가 그 뒤에 다시 계약한 고객은?

### 1) Cypher — 「그림」

```cypher
MATCH (c:Company)-[:Terminated]->(o:Contract),
      (c)-[:Signed]->(n:Contract)
WHERE o.endedOn < n.startedOn
RETURN c.name AS 고객
ORDER BY 고객
```

`(c)-[:Signed]->(n)` 은 화이트보드에 그린 그림 그대로입니다. **어떤 모양을 찾아 달라**고만 적었고, "Company 를 먼저 훑을까 Contract 를 먼저 훑을까"는 한 글자도 없습니다. 그건 Kuzu 의 최적화기가 정합니다.

### 2) SPARQL — 「문장」

```sparql
SELECT ?고객 WHERE {
    ?c ex:name ?고객 ; ex:terminated ?o ; ex:signed ?n .
    ?o ex:endedOn   ?end .
    ?n ex:startedOn ?start .
    FILTER(?end < ?start)
} ORDER BY ?고객
```

사실(트리플)을 한 줄씩 늘어놓습니다. 트리플 패턴을 **적은 순서대로 평가하지 않는다**는 게 핵심입니다. 엔진은 선택도(selectivity)를 보고 순서를 바꿔 조인합니다. 즉 이것도 선언형입니다.

### 3) Gremlin — 「걸음」

Gremlin 은 이렇게 씁니다.

```groovy
g.V().hasLabel('Company')
     .as('c')
     .out('terminated').values('endedOn').as('end')
     .select('c')
     .out('signed').values('startedOn').as('start')
     .where('end', lt('start'))
     .select('c').values('name').dedup().order()
```

`.out('signed')` 는 "지금 서 있는 정점에서 signed 간선을 타고 나가라"는 **명령**입니다. 문장이 곧 순회 순서입니다. 예제 코드는 Gremlin 서버 없이 이 사고방식을 파이썬 루프로 흉내 냅니다 — 그리고 그 흉내가 **거의 그대로 번역된다**는 점이 명령형이라는 증거입니다.

```python
def gremlin_style():
    ended = {a: ... for a, b in TERMINATED}
    started = defaultdict(list)
    ...
    for company, end in ended.items():          # .hasLabel('Company').out('terminated')
        for start in started.get(company, []):  # .in().out('signed')
            if end < start:                     # .where(...)
                out.append(company)
    return sorted(set(out))
```

Cypher 를 파이썬 이중 루프로 이렇게 1:1 매핑할 수는 없습니다. **선언형에는 "루프 순서"라는 개념 자체가 질의문에 없기 때문**입니다.

세 결과는 같습니다(`셋이 같은가: 예`). **답이 같아도 사고방식이 다르다** — 이게 11.1절의 결론이고, 이 카드가 묻는 트레이드오프의 무대입니다.

## 「최적화기가 도와줄 여지가 적다」가 실제로 무슨 뜻인가

`ex5_read_plan.py`가 그 여지를 눈으로 보여 줍니다. 사람 20,000명 · 도시 12개 그래프에서 같은 답을 두 방향으로 물어봅니다.

```
작은 쪽(City)에서 시작    → 도시 1개 찾고 → 들어오는 LivesIn 간선만 따라감
큰 쪽(Person)에서 시작    → 사람 20,000명 훑고 → 조건 맞는 것만 남김
```

**선언형이라면** 이 두 질의문이 (통계가 충분할 때) 같은 계획으로 수렴할 수 있습니다. 시작점 선택은 최적화기의 일이니까요.

**명령형이라면** `g.V().hasLabel('Person')...` 으로 쓴 순간 20,000개 스캔이 확정됩니다. 옵티마이저가 "그건 City 에서 시작하는 게 빨라요"라고 뒤집어 주지 않습니다. TinkerPop 에도 순회 전략(`TraversalStrategy`)이라는 최적화 계층은 있지만, 그 범위는 인접한 스텝 병합이나 인덱스 활용 같은 **국소적 재작성**에 가깝고, 조인 순서를 통째로 재배치하는 비용 기반 최적화(CBO)와는 성격이 다릅니다. 그래서 Gremlin 은 **성능이 작성자 실력에 정직하게 비례**합니다.

## 선언형이 내는 대가

`ex5`의 마지막 문장이 그 대가를 정확히 짚습니다.

> 선언형 언어의 대가가 여기 있다. 무엇을 원하는지만 적으면 편한데, 느릴 때 «왜 느린지»를 알려면 계획을 읽어야 한다.

그래서 선언형 세계에서는 `EXPLAIN` 이 필수 기술이 됩니다. 계획에서 볼 것은 셋입니다.

1. 어느 테이블부터 훑는가 (스캔이 어디에 있나)
2. 색인을 타는가, 전체를 훑는가
3. 중간 결과가 몇 행으로 추정되는가

즉 선언형은 "쉬움"을 주는 대신 **디버깅을 간접적으로** 만듭니다. 내가 적은 문장과 실제 실행 사이에 최적화기라는 층이 하나 끼어 있으니까요. 명령형은 반대로, 느린 이유가 내가 적은 문장에 그대로 적혀 있습니다.

## 언제 어느 쪽인가 (실무 판단)

**선언형이 유리한 경우**
- 패턴이 선언 가능한 모양으로 표현되는 대부분의 질의 (11장 예제의 "해지 후 재계약" 같은 것)
- 데이터 분포가 바뀌어도 질의문을 안 고치고 싶을 때 — 통계가 갱신되면 계획이 알아서 바뀝니다
- 이식성이 필요할 때 — GQL(ISO/IEC 39075:2024)이 표준화된 방향도 선언형입니다
- 사람이 읽고 리뷰해야 하는 질의

**명령형이 유리한 경우**
- 순회 도중의 상태를 들고 다녀야 하는 알고리즘 (사용자 정의 탐색, 조건부 백트래킹, 커스텀 우선순위)
- "찾으면 즉시 멈춘다" 같은 조기 종료·가지치기를 손으로 넣고 싶을 때
- 최적화기가 계속 나쁜 계획을 고르는 병목 지점을 강제로 잡아야 할 때
- 선언형 문법으로 표현이 안 되는 절차적 로직 (`repeat().until()`, `sack()`, `barrier()` 류)

## 오해하기 쉬운 지점

- **"명령형이 항상 느리다"는 아니다.** 잘 쓴 Gremlin 순회는 나쁜 계획을 고른 선언형 질의보다 훨씬 빠를 수 있습니다. 트레이드오프는 속도의 상한이 아니라 **책임의 위치**입니다.
- **"선언형이면 성능을 신경 안 써도 된다"는 아니다.** 조인 순서만 최적화기가 정하고, 스키마·인덱스·상한 걸기(9장)는 여전히 사람 몫입니다.
- **Cypher/SPARQL 이 완전히 순수 선언형은 아니다.** Cypher 의 `WITH`·힌트, SPARQL 의 서브쿼리처럼 실행 순서에 개입하는 장치가 있습니다. 축은 이진 스위치가 아니라 스펙트럼입니다.
- **표준화가 이 트레이드오프를 없애지 않는다.** `ex3_gql_dialects.py`가 보여 주듯 GQL 전용 절(`LET`, `NEXT`, `FILTER`)은 엔진이 아직 안 받습니다. 선언형 진영의 이식성도 아직 약속이지 현실은 아닙니다.

## 시험 대비 한 문장 정리

> **선언형(Cypher·SPARQL)은 "무엇"만 적고 실행 방법은 최적화기에 위임한다 — 짧고 이식성 있지만 느릴 때 실행 계획을 읽어야 한다. 명령형(Gremlin)은 "어떻게"를 순회 스텝으로 직접 적는다 — 세밀한 제어와 절차적 로직이 가능한 대신 최적화기가 나쁜 순서를 고쳐 주지 못한다.**
