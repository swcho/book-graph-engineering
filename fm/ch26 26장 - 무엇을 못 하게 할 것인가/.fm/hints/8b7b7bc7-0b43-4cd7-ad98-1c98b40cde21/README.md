# "읽기는 안전하다"가 틀린 이유

## 질문
"읽기는 안전하다"가 틀린 이유는 무엇인가?

## 답
**읽기도 돈을 쓰고, 흔적을 남기고, 상대를 아프게 한다.**

## 왜 이런 말이 나오는가

권한 검토 회의에서 가장 흔하게 나오는 결론이 "읽기 권한만 주면 안전하죠"입니다. 26장은 이 장면으로 시작합니다(30분 동안 그걸 확인하는 회의). 쓰기·실행·네트워크 송신만 위험하고 읽기는 무해하다는 직관은 널리 퍼져 있지만, 세 가지 지점에서 틀립니다.

### 1. 읽기도 돈을 쓴다

- 외부 API 조회는 대부분 **호출 단위로 과금**됩니다. 검색 API, 지도 API, 데이터 제공 API 모두 "읽기"인데 요금이 나갑니다.
- 에이전트는 사람과 달리 **루프 안에서 수백·수천 번** 읽을 수 있습니다. 읽기 자체가 무해해도, 무제한 읽기는 비용 사고가 됩니다.
- 읽어 온 내용은 모델의 컨텍스트로 들어가므로 **토큰 비용**도 함께 커집니다.

### 2. 읽기도 흔적을 남긴다

- 상대 시스템에는 **접근 로그**가 남습니다. 우리 에이전트가 어디를, 언제, 얼마나 훑었는지가 상대방 서버에 기록됩니다.
- 조회 대상이 개인정보라면 "읽었다"는 사실 자체가 **감사·규제 대상**이 됩니다(누가 고객 데이터를 조회했는가는 사고 조사의 절반입니다 — ex5의 감사 로그 논의와 같은 맥락).
- 읽기 요청의 URL·쿼리 파라미터에 내부 정보가 실려 나가면, 읽기가 곧 **유출 경로**가 되기도 합니다. 이 장의 요약이 말하듯 "나가는 경로"는 네트워크 송신만이 아니라 로그, 에러 메시지, 응답 자체까지 포함됩니다.

### 3. 읽기도 상대를 아프게 한다

- 에이전트가 반복 조회하면 상대 서버에는 **부하(사실상의 크롤링·DoS성 트래픽)**가 걸립니다. 레이트 리밋을 소진시키고, 비싼 쿼리는 DB를 느리게 만듭니다.
- "읽기만 하는" 웹 크롤러가 소규모 사이트의 대역폭 비용을 터뜨리는 일은 실제로 흔합니다.

### 덤: 읽기는 공격의 입구이기도 하다

이 장의 26.3절(간접 프롬프트 인젝션)이 보여 주듯, **읽어 온 문서 안에 명령이 섞여 있을 수 있습니다.** 읽기 권한은 "밖의 신뢰할 수 없는 글"을 에이전트의 입력으로 끌어들이는 문이기도 합니다. 또 ex1이 보여 주듯 읽기(`fs.read`, `db.read`)는 단독으로는 무해해도 외부 전송과 **조합되는 순간 유출 경로**가 됩니다.

## 기억 포인트

"읽기 = 무해"라는 직관을 깨는 세 단어로 외우세요:

| 틀린 이유 | 한 줄 설명 |
|---|---|
| **돈** | API 과금, 토큰 비용 — 루프 도는 에이전트는 읽기만으로 비용 사고를 낸다 |
| **흔적** | 상대 시스템의 접근 로그, 개인정보 조회 기록, 요청에 실려 나가는 정보 |
| **아픔** | 상대 서버 부하, 레이트 리밋 소진, 비싼 쿼리 — 읽기도 상대에겐 트래픽이다 |

그래서 읽기 권한도 "공짜"로 주지 말고, 다른 권한과 마찬가지로 **경로(무엇과 조합되는가)와 반경(뚫리면 어디까지인가)**을 따져서 줘야 합니다.
