# 차단 로그에 반드시 넣어야 할 세 가지

## 질문
차단 로그에 반드시 넣어야 할 세 가지는 무엇인가?

## 답
1. **어느 규칙이 막았나** — 규칙 이름
2. **왜 막았나** — 사람이 읽을 수 있는 이유
3. **나중에 사람이 뒤집었나** — 이게 정책 품질 지표가 된다

**세 번째가 대부분 빠진다.**

## 자세한 설명

26장 26.5절 「막은 것도 기록한다」의 핵심 규칙입니다. 예제 `ex5_audit_trail.py`가 이 세 가지를 실제 스키마로 보여 줍니다.

```sql
CREATE TABLE gate_log (
  id       INTEGER PRIMARY KEY,
  agent    TEXT, tool TEXT,
  rule     TEXT,        -- (1) 어느 규칙이 막았나
  verdict  TEXT,        --     통과 / 차단
  reason   TEXT,        -- (2) 왜 막았나 (사람이 읽을 이유)
  overridden INTEGER    -- (3) 나중에 사람이 뒤집었나
);
```

### 왜 이 셋인가

| 항목 | 역할 | 없으면 생기는 일 |
|---|---|---|
| 규칙 이름 (`rule`) | 어느 규칙이 실제로 일하고 있는지 집계할 수 있게 한다 | 차단이 일어나도 어떤 정책 조항 탓인지 추적 불가 |
| 사람이 읽을 이유 (`reason`) | 차단당한 사용자·운영자가 즉시 상황을 이해하고 판단할 수 있게 한다 | 「왜 막혔지?」에 답하려면 코드를 뒤져야 한다 |
| 사람이 뒤집었나 (`overridden`) | **정책 품질 지표**. 규칙별 「뒤집힌 비율」을 계산할 수 있게 한다 | 과하게 막는 규칙을 영원히 못 찾는다 |

### 세 번째가 왜 가장 중요한가 (그리고 왜 대부분 빠지나)

앞의 둘은 차단이 일어난 **순간**의 정보라서 자연스럽게 기록하게 됩니다. 하지만 세 번째는 **나중에** 사람이 개입한 결과를 로그에 다시 연결해야 하므로 설계 단계에서 의식하지 않으면 빠집니다.

예제의 숫자가 이유를 보여 줍니다:

- `gate:approval` 규칙: 4번 발동 → 4번 모두 사람이 뒤집음 → **뒤집힌 비율 100%**. 이는 「규칙이 틀렸다」는 뜻입니다. 사람 시간만 쓰고 있는 것이죠. 외부 도메인 전체를 막을 게 아니라 허용 도메인 목록을 뒀어야 했습니다.
- `deny:net-out` 규칙: 3번 차단, 한 번도 안 뒤집힘 → 잘 일하는 규칙.

책의 한 장 요약도 같은 말을 합니다: 「막은 것도 기록하세요. **사람이 뒤집은 비율이 정책 품질 지표**입니다. 100% 뒤집히는 규칙은 사람 시간만 쓰고 있는 겁니다.」

### 뒤집힘 기록이 없을 때의 최종 결말

과하게 막는 규칙을 못 찾으면, 그 규칙은 결국 **「다들 우회하는 규칙」**이 됩니다. 우회가 일상화되면 규칙 전체에 대한 신뢰가 무너지고, 정작 위험한 시도를 막았을 때도 사람이 습관적으로 뒤집게 됩니다. 즉 세 번째 항목은 단순한 통계가 아니라 가드레일 정책을 살아 있게(계속 고쳐지게) 만드는 피드백 루프입니다.

### 덤: 허용(통과)도 기록한다

차단만이 아니라 `allow:` 규칙으로 통과한 것도 로그에 남깁니다. 「누가 무엇을 했나」가 사고 조사의 절반이기 때문입니다. 이는 NIST SP 800-53의 감사 로그(audit log) 통제와 같은 맥락입니다.

## 관련 키워드
- 감사 로그 (audit log) — [표준] NIST SP 800-53
- 최소 권한 (least privilege) — [사실상 표준] NIST 용어집
