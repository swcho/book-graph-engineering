# 금지 목록이 반드시 새는 이유

## 질문
금지 목록이 반드시 새는 이유는 무엇인가?

## 답
**셀 수 있는 것만 막는데 우회 방법은 셀 수 없다.**

## 자세한 설명

### 비대칭의 문제

금지 목록(denylist)은 "이것, 이것, 이것은 안 된다"라고 나쁜 패턴을 하나씩 열거하는 방식입니다. 그런데 여기에는 근본적인 비대칭이 있습니다.

- 금지 목록에 적을 수 있는 것: **유한개** — 내가 미리 떠올린 패턴만
- 공격자가 시도할 수 있는 우회: **사실상 무한** — 같은 결과를 내는 다른 표현 전부

즉 "지우는 방법"은 셀 수 없이 많은데, 금지 목록은 그중 셀 수 있는(내가 아는) 것만 막습니다. 하나라도 빠지면 그 틈으로 새고, 빠지는 것은 필연입니다.

### 책의 예제 (ex2_deny_vs_allow.py)

`rm -rf`를 정규식으로 막았다고 해 봅시다. 실제로는 이런 것들이 전부 통과합니다.

| 우회 시도 | 왜 통과하나 |
|---|---|
| `rm  -rf /var/data` | 공백을 두 개 넣었다 |
| `rm -fr /var/data` | 플래그 순서만 바꿨다 |
| `/bin/rm -rf ...` | 절대 경로로 불렀다 |
| `sh -c 'rm -rf ...'` | 껍데기(셸)를 한 겹 씌웠다 |
| `python3 -c "shutil.rmtree(...)"` | 다른 프로그램으로 지웠다 |
| `find /var/data -delete` | `rm`을 아예 안 썼다 |

패턴을 세 개 더 추가하면? 네 번째 우회가 나옵니다. 두더지 잡기가 끝나지 않는 구조입니다.

### 허용 목록과의 대비

허용 목록(allowlist)은 반대로 "내가 이해한 것만 통과"시킵니다.

- **금지 목록** — 손이 덜 가고, **반드시 샌다**
- **허용 목록** — 손이 계속 가고(유지보수 비용), **안 샌다**

허용 목록은 새 공격 방식이 나와도 막힙니다. 새 방식은 "허용 목록에 없으니까"요. 처음 보는 것은 기본으로 차단되는 구조라 미지의 공격에도 안전합니다.

### 실패 방향의 차이

- 금지 목록의 오답: **막았어야 하는데 통과** → 사고가 나야 안다
- 허용 목록의 오답: **통과했어야 하는데 차단** → 사용자가 바로 알려 준다

전자는 조용히 뚫리고, 후자는 시끄럽게 불편합니다. 보안에서는 시끄러운 불편이 조용한 구멍보다 낫습니다.

### 허용 목록의 주의점

허용 목록도 명령 **이름만** 허용하면 부족합니다. 책의 예제에서 "cat은 허용"이라고만 적어 두자 `cat /etc/passwd`가 통과했습니다. **인자까지** 봐야 하고(예: 경로를 작업 디렉터리 아래로 제한), 문자열이 아니라 **정규화한 결과**를 비교해야 합니다.

### 결론

권한 경계에서는 허용 목록을 고릅니다. "반드시 샌다"는 성질은 보안 경계에서 받아들일 수 없기 때문입니다. 이 원칙은 OWASP 입력 검증 가이드에서도 allowlist를 권장하는 이유와 같습니다.

## 관련 키워드
- 허용 목록 (allowlist) — OWASP Input Validation Cheat Sheet
- 최소 권한 (least privilege) — NIST
- 기본 거부 (default deny) — 명시적으로 허용하지 않은 것은 전부 차단
