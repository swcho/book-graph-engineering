# '나가는 문'에 해당하는 권한 셋

## 질문

'나가는 문'에 해당하는 권한 셋은 무엇인가?

## 답

**나가는 네트워크(net.out), 임의 실행(exec), 쓰기(fs.write)** 다.
이 셋을 막으면 나머지 권한은 조합해도 밖으로 못 나간다.

## 왜 '문'이라고 부르나

26장의 핵심 전제는 **권한은 목록이 아니라 경로**라는 것이다. 개별로 무해해 보이는 권한도 이어붙이면 유출 경로가 된다.

예제 1(`ex1_permission_graph.py`)의 시나리오를 보자. 에이전트에게 준 권한은 `fs.read`, `net.out`, `db.read` 셋뿐이다. 목록으로 보면 "읽기와 네트워크와 DB 조회"라 무해해 보인다. 그런데:

- `db_query`로 고객 데이터를 읽고 → `http_post`로 밖에 보내면 → **고객 데이터 유출**
- `read_file`로 소스를 읽고 → `http_post`로 보내면 → **소스 코드 유출**

두 도구는 각각 안전한데 **이어붙이면** 유출 경로가 된다. 목록 관리로는 이 이어붙임이 안 보인다.

## '문 하나'를 빼면 어떻게 되나

예제 1에서 `net.out` 하나를 빼자 도구는 5개에서 3개로 줄었을 뿐인데, **위험 경로는 2개에서 0개로 사라졌다**. 권한 하나가 '나가는 문'이었기 때문이다.

가드레일을 설계할 때 도구를 하나씩 재는 것보다 **"어느 권한이 문인지"를 찾는 게 훨씬 크게 듣는다**. 그리고 대개 문은 셋이다.

| 문 | 대응 권한 | 왜 문인가 |
|---|---|---|
| 나가는 네트워크 | `net.out` (http_post, send_mail 등) | 데이터가 외부로 직접 나가는 통로 |
| 임의 실행 | `exec` (run_shell 등) | 셸을 잡으면 어떤 권한이든 새로 만들어 낼 수 있다 (원격 코드 실행, 권한 상승) |
| 쓰기 | `fs.write` (write_file 등) | 파일 변경 + 실행이 결합하면 지속성 확보(persistence)가 되고, 쓰기 자체가 다른 시스템으로 내보내는 통로가 될 수 있다 |

읽기(`fs.read`), DB 조회(`db.read`) 같은 권한은 데이터를 **모을** 수는 있어도, 위 세 문이 닫혀 있으면 모은 것을 **내보낼 방법이 없다**. 그래서 "이 셋을 막으면 나머지는 조합해도 밖으로 못 나간다"가 성립한다.

## 함께 기억할 단서

- **나가는 경로를 셀 때 네트워크만 보지 마라.** 로그, 에러 메시지, 그리고 응답 자체도 나가는 경로다. (한 장 요약 두 번째 항목)
- 프롬프트 인젝션 대응에서도 이 셋이 1순위다. 예제 3의 3겹 방어에서 경계 표시(1겹)와 입력 검사(2겹)는 확률만 낮추고, **권한 차단(3겹)만이 가능성을 없앤다**. 요약기가 애초에 `db_query`·`http_post`를 못 쓰면 문서에 무슨 명령이 섞여 있든 고객 데이터는 안 나간다.
- "읽기는 안전하다"는 틀렸다. 읽기도 돈을 쓰고, 흔적을 남기고, 상대를 아프게 한다. 다만 '나가는 문' 관점에서는 읽기 자체는 문이 아니고, 문 셋과 결합할 때 유출이 완성된다.

## 암기 팁

밖으로 내보내는 세 가지 동사로 외우면 쉽다.
**"보내거나(네트워크), 시키거나(실행), 남기거나(쓰기)"** — 이 셋이 닫히면 안에서 무엇을 알아냈든 밖으로 나갈 수 없다.
