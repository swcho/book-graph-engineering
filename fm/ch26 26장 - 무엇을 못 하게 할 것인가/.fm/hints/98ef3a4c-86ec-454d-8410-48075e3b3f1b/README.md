# spawn을 빼는 것보다 근본적인 대응은 무엇인가?

## 답

**관리자를 쪼개는 것**이다. 한 에이전트가 `read + db + shell + mail`을 다 갖고 있으면, 그 하나가 뚫렸을 때 전부 나간다.

## 맥락 — 예제 4 (폭발 반경 실험)

26장 4절 「하나가 뚫렸을 때 어디까지」의 `ex4_blast_radius.py` 실험에서 나온 결론이다. 에이전트·자원 그래프를 놓고 「한 에이전트가 장악됐을 때 도달 가능한 자원」을 BFS로 세어 본다.

실험 구성:

| 에이전트 | 도구 | 뚫렸을 때 닿는 자원 |
|---|---|---|
| 요약기 | read_docs | 문서저장소 (점수 1) |
| 분석기 | read_docs, db_read | 문서저장소, 고객DB |
| 보고서 | db_read, send_mail | 고객DB, 외부 |
| **관리자** | read_docs, db_read, send_mail, run_shell, **spawn** | **전부** (점수 최대) |

## spawn을 빼면 무엇이 달라지고, 무엇이 안 달라지나

관리자에게서 `spawn`을 빼면:

- **달라지는 것 — 전파가 사라진다.** 첫 표에서 관리자가 장악되면 spawn으로 다른 에이전트로 갈아탈 수 있어 닿는 에이전트가 4개였다. spawn을 빼면 1개(자기 자신)로 준다.
- **안 달라지는 것 — 자원 피해 점수는 그대로다.** 관리자 자신이 이미 read_docs, db_read, send_mail, run_shell을 다 들고 있으므로, 다른 에이전트를 거치지 않아도 문서저장소·고객DB·외부·서버파일에 전부 닿는다. 표의 피해 점수가 바뀌지 않는 이유다.

즉 spawn 제거는 「옆으로 번지는 것」만 막을 뿐, 관리자 한 노드의 폭발 반경 자체는 줄이지 못한다.

## 왜 「쪼개기」가 근본 대응인가

문제의 뿌리는 spawn이 아니라 **치명 조합이 한 노드에 모여 있다는 것**이다.

- `db_read + send_mail` → 고객 데이터 유출 경로
- `run_shell + 외부` → 원격 실행·전송 경로

한 에이전트가 이 조합을 통째로 들고 있으면, 그 에이전트가 뚫리는 순간 조합 전체가 공격자 손에 들어간다. 관리자를 역할별로 쪼개서 각 에이전트가 조합의 「한 조각」만 갖게 하면, 어느 하나가 뚫려도 유출 경로가 완성되지 않는다.

책은 이를 최소 권한의 재정의로 연결한다:

> 최소 권한은 「각 에이전트가 자기 일에 필요한 것만」이 아니라 **「어떤 하나도 치명 조합을 갖지 않게」**다.

목표 모양은 요약기다. 도구가 read_docs 하나뿐이라 뚫려도 문서저장소까지만 닿는다(피해 점수 1). **에이전트를 나누는 이유가 성능만은 아닌** 이유가 여기 있다 — 분리 자체가 보안 격벽(compartmentalization)이 된다.

## 장 전체와의 연결

- 26.1절(예제 1): 권한은 목록이 아니라 경로다. 개별로 무해한 권한도 조합되면 유출 경로가 된다. 쪼개기는 이 「조합」을 노드 단위에서 끊는 방법이다.
- 26.3절(예제 3): 프롬프트 인젝션의 확실한 방어는 「애초에 할 수 없게」 하는 권한 차단이다. 관리자를 쪼개면 인젝션에 성공해도 그 에이전트로 할 수 있는 일 자체가 작다.
- 보안 일반 용어로는 blast radius 축소, privilege separation에 해당한다.

## 기억 포인트

- spawn 제거 = **전파(가로 확산) 차단**. 관리자 자신의 반경은 그대로.
- 관리자 쪼개기 = **폭발 반경 자체 축소**. 치명 조합을 해체한다.
- 판단 기준: 「이 에이전트 하나가 뚫리면 무엇까지 나가나」를 노드마다 물어보고, 어느 노드도 read+db+shell+mail 같은 완결된 유출 경로를 혼자 들지 않게 한다.
