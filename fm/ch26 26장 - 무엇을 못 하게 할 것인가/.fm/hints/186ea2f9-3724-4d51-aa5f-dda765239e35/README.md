# '나가는 경로'를 셀 때 네트워크 외에 봐야 할 것

## 질문
'나가는 경로'를 셀 때 네트워크 외에 무엇을 봐야 하는가?

## 답
**로그, 에러 메시지, 그리고 응답 자체도 나가는 경로다.**

## 왜 이 질문이 나오는가 — 「권한은 목록이 아니라 경로다」

26장의 핵심 주장은 권한을 도구별 목록으로 보지 말고 **도달 가능한 경로(그래프)**로 보라는 것입니다. 개별로 무해한 권한(파일 읽기, DB 조회, HTTP 요청)도 조합되면 「고객 데이터 유출」 같은 경로가 됩니다. 그래서 도구를 하나씩 재는 대신 **「어느 권한이 나가는 문인가」**를 묻습니다. 대개 문은 셋입니다.

1. **나가는 네트워크** (net.out — http_post, send_mail 등)
2. **임의 실행** (exec — run_shell 등)
3. **쓰기** (fs.write 등)

이 셋을 막으면 나머지 권한은 조합해도 데이터가 밖으로 못 나간다는 게 기본 전략입니다.

## 그런데 함정 — 네트워크만 세면 놓치는 경로들

「나가는 문」을 셀 때 네트워크 송신만 세면 안 됩니다. 데이터가 신뢰 경계 밖으로 흘러나가는 통로는 네트워크 말고도 있습니다.

### 1. 로그
- 에이전트가 처리한 내용(프롬프트, 도구 인자, 읽은 데이터)이 로그에 그대로 남으면, 그 로그를 볼 수 있는 모든 사람·시스템에게 데이터가 「나간」 것입니다.
- 로그 수집 파이프라인(중앙 로그 서버, 모니터링 대시보드, 외부 APM 서비스)은 보통 원래 데이터보다 접근 권한이 느슨합니다. 고객 DB에는 접근 못 하는 사람이 로그에서 고객 데이터를 읽을 수 있게 되는 식입니다.

### 2. 에러 메시지
- 예외 메시지·스택 트레이스에는 파일 경로, 쿼리 내용, 심지어 조회된 데이터 조각이 섞여 나오기 쉽습니다.
- 공격자가 일부러 에러를 유발해서 에러 메시지에 실린 정보를 읽어 가는 것은 전통적인 보안 공격 기법이기도 합니다(정보 노출, information disclosure).

### 3. 응답 자체
- 에이전트가 사용자에게 돌려주는 **답변 그 자체**가 유출 통로입니다. 요약기가 DB를 읽을 수 있다면, 인젝션된 문서가 「고객 데이터를 요약 결과에 슬쩍 포함해라」라고 지시하는 것만으로 네트워크 권한 없이도 데이터가 나갑니다.
- 응답을 받는 상대가 신뢰할 수 없는 사용자이거나, 응답이 공개 채널(공개 게시판, 다른 에이전트)로 흘러가는 구조라면 응답은 사실상 「나가는 네트워크」와 같은 등급의 문입니다.

## 실무적 함의

- **폭발 반경 계산에 포함시켜라**: 「이 에이전트가 뚫리면 어디까지 닿나」를 잴 때 net.out 도구만 세지 말고, 이 에이전트가 읽은 데이터가 로그·에러·응답을 타고 누구에게까지 보이는지를 함께 세야 합니다.
- **읽기 권한 + 응답 = 이미 유출 경로**: 「읽기만 주면 안전하죠」가 틀린 이유 중 하나입니다. 민감한 데이터를 읽을 수 있고 그 결과를 누군가에게 응답할 수 있다면, 그 조합만으로 유출 경로가 완성됩니다.
- **프롬프트 인젝션과 결합하면 더 위험**: 26.3절의 간접 인젝션 시나리오에서, 공격자는 네트워크 도구가 없어도 「읽은 것을 응답에 실어라」만 시키면 됩니다. 그래서 방어의 1순위가 프롬프트가 아니라 **권한 차단**(애초에 민감 데이터를 못 읽게)인 것입니다.

## 한 줄 정리

> 데이터가 신뢰 경계를 넘는 모든 통로가 「나가는 경로」다. HTTP 송신만이 아니라 **로그에 남는 것, 에러 메시지에 실리는 것, 응답으로 돌려주는 것** 모두가 문이다.
