# 방침 표가 없으면 어떤 문제가 생기는가?

> **답**: 담당자가 그때그때 판단하고, 다음 요청은 다른 담당자가 다르게 판단한다. 「지난번엔 지웠는데 이번엔 안 지웠다」가 더 큰 문제가 된다.

---

## 1. 한 줄로 먼저

방침 표가 없으면 삭제 처리는 **사람의 즉석 판단**이 됩니다. 그리고 즉석 판단의 문제는 「틀릴 수 있다」가 아니라 **「매번 다르게 틀린다」** 입니다.

34장 `ex5_deletion_plan.py`의 결론이 정확히 이 문장입니다.

> 표가 없으면 어떻게 되나. 담당자가 그때그때 판단한다.
> 그리고 다음 요청이 오면 다른 담당자가 다르게 판단한다.
> 「지난번엔 지웠는데 이번엔 안 지웠다」가 되면 그게 더 큰 문제다.

여기서 눈여겨볼 표현은 **「그게 더 큰 문제다」** 입니다. 한 번의 오판보다 **일관성 없음** 자체가 더 크다고 말하고 있어요. 왜 그런지가 이 카드의 핵심입니다.

---

## 2. 표가 없을 때 실제로 벌어지는 일

같은 종류의 노드, 다른 결론. 이런 식으로 갈라집니다.

| 요청 | 담당자 | `Photo`(회식 사진) 처리 | 근거 |
|---|---|---|---|
| 3월 요청 | A | **삭제** | 「얼굴이 개인정보니까」 |
| 5월 요청 | B | **유지** | 「회사 행사 기록이니까」 |
| 7월 요청 | A(휴가) → C | **얼굴 블러** | 「중간이 안전하겠지」 |
| 9월 요청 | B | **유지** | 「지난번에도 유지했으니」 |

셋 다 나름 합리적입니다. 어느 하나가 명백히 어리석지도 않아요. **그런데 이 표를 나란히 놓는 순간 회사는 아무 대답도 할 수 없게 됩니다.** 「우리는 회식 사진을 어떻게 처리합니까?」라는 질문에 답이 없는 겁니다. 답이 없는 게 아니라, **답이 네 개** 있습니다.

그리고 이 상태는 **결정을 내린 사람이 조직을 떠나면 복구도 안 됩니다.** 판단의 근거가 사람 머릿속에만 있었으니까요.

---

## 3. 왜 개별 오판보다 「일관성 없음」이 더 큰가

개별 오판은 **한 건**의 문제이고 고치면 됩니다. 일관성 없음은 **제도**의 문제여서 고칠 지점이 없습니다. 구체적으로 네 갈래로 터집니다.

### 3.1 감사(audit)가 실패한다

감사는 「결과가 옳은가」를 보지 않습니다. **「정해 둔 대로 했는가」** 를 봅니다.

- 방침이 있고 그대로 했다 → **통과**
- 방침이 있고 예외로 다르게 했다 + 예외 기록이 있다 → **통과** (판단의 흔적이 있으니까)
- 방침이 없고 매번 잘 처리했다 → **실패**

마지막 줄이 직관에 어긋나 보이지만 이게 감사의 논리입니다. 기준이 없으면 **감사인이 대조할 대상이 없어서**, 잘했다는 것을 증명할 방법도 없어요. GDPR이 요구하는 **책임성(accountability, Art. 5(2))** 은 「올바르게 처리했다」가 아니라 **「올바르게 처리했음을 입증할 수 있다」** 입니다. 입증의 재료가 방침 문서와 처리 기록입니다.

즉 표가 없으면 **잘한 경우조차 잘했다고 말할 수 없습니다.**

### 3.2 차별적 처리가 된다

같은 종류를 다르게 처리한 결과는 결국 이렇게 요약됩니다.

> 「누가 요청했느냐」 또는 「누가 담당했느냐」에 따라 개인정보 삭제의 결과가 달라졌다.

목소리가 큰 사람, 법무팀을 아는 사람, 재요청한 사람은 더 많이 지워지고, 그냥 폼을 넣고 기다린 사람은 덜 지워집니다. **의도한 차별이 아니어도 결과는 차별입니다.** 그리고 GDPR의 **공정한 처리(fairness, Art. 5(1)(a))** 나 국내 개인정보보호법의 처리 원칙에서 문제가 되는 지점이 정확히 여기입니다. 즉석 판단은 자기 편향을 방침으로 승격시키는 통로가 됩니다.

### 3.3 법적으로 방어할 수 없다

방침 표가 있으면 다툼의 대상은 **표의 내용**입니다.

> 「우리는 `Doc`을 작성자 익명화로 처리합니다. 산출물은 회사 자산이라고 판단했습니다.」

이건 **틀릴 수 있지만 방어 가능한 입장**입니다. 규제기관이 반대하면 표의 한 줄을 고치고, 그 시점부터 다르게 처리하고, 필요하면 과거 건을 그 기준으로 소급합니다. **고칠 지점이 한 곳**이라는 게 핵심이에요.

표가 없으면 다툼의 대상은 **개별 담당자의 그날의 판단**이 됩니다. 방어할 입장 자체가 없습니다. 그리고 더 나쁜 것은, 3월에 지운 전례가 **9월에 유지한 것을 스스로 반증**해 버립니다.

> 「당신들도 3월에는 지워야 할 것이라고 판단했잖습니까.」

상대에게 증거를 만들어 준 셈입니다. 일관성 없음은 **자기 자신을 상대편 증인으로 세우는** 성질이 있어요.

### 3.4 운영을 재현할 수 없다

방침이 없으면 이런 일이 전부 불가능해집니다.

| 하고 싶은 것 | 표가 없을 때 |
|---|---|
| 삭제 절차 자동화 | 규칙이 없어서 코드로 못 옮긴다 |
| 소요 시간 약속(「30일 안에」) | 매번 처리 범위가 달라 예측 불가 |
| 신규 담당자 인수인계 | 「감으로 하세요」밖에 전달할 게 없다 |
| 과거 요청 재처리 | 무엇을 기준으로 다시 할지 모른다 |
| 「완료」 판정 | 완료의 정의가 사람마다 다르다 |

특히 마지막 두 줄이 34장의 다른 결론과 맞물립니다. 이 장은 **「완료」의 기준을 문서로 정하라**고 요구하는데, **방침 표 없이는 완료를 정의할 수 없습니다.** 무엇을 어디까지 해야 끝인지가 방침에서 나오기 때문입니다.

## 4. 방침 표가 제공하는 것 세 가지

`ex5`의 `POLICY`는 코드 열 줄짜리 딕셔너리입니다. 그 열 줄이 하는 일이 셋입니다.

### 4.1 결정을 사전에(요청이 오기 전에) 명시한다

가장 중요한 성질은 **시점**입니다.

| | 방침 표 | 즉석 판단 |
|---|---|---|
| 판단 시점 | 요청 **전** | 요청 **후** |
| 판단할 때의 압박 | 없음 | 시한·감정·개별 사정 |
| 판단 단위 | 노드 **종류** | 노드 **한 개** |
| 검토 가능성 | 법무·보안이 미리 검토 | 사후에만 알 수 있다 |

요청이 들어온 뒤에 판단하면 「이 사람은 화가 많이 났으니 더 지우자」 같은 것이 섞입니다. 요청 전에 종류 단위로 정해 두면 **개별 사정과 무관하게** 같은 답이 나옵니다. 이게 일관성의 기계적 원천이에요.

그리고 판단 기준 자체가 표 안에 한 줄로 압축됩니다. 34장이 제시하는 질문은 하나입니다.

> **「이 노드가 개인을 가리키는가, 아니면 개인이 만든 것인가?」**
> 가리키면 지우고, 만든 것이면 「만든 사람만」 지운다.

`ex5`의 `POLICY`가 그 질문의 답을 종류별로 적어 둔 것입니다.

| 종류 | 방침 | 이유 |
|---|---|---|
| `Person` | 삭제 | 개인 그 자체 |
| `Contact` | 삭제 | 연락처 |
| `Msg` | 본문 마스킹 | 발화 — 이름·연락처만 가린다 |
| `Doc` | 작성자 익명화 | 산출물은 회사 자산 |
| `Team` | 유지 | 개인정보 아님 |
| `Stat` | 재계산 | 집계는 남기되 다시 센다 |
| `Fact` | 유지 | 개인을 안 가리키면 |
| `Answer` | 유지 | 회사의 결정 기록 |
| `Run` | 행위자 익명화 | 누가 돌렸는지만 가린다 |
| `Event` | 식별자 치환 | 30장 — 이벤트는 못 지운다 |

「이유」 열이 장식이 아닙니다. **6개월 뒤에 이 표를 고칠 때 필요한 정보**이고, 감사에서 요구받는 것도 결론이 아니라 이유입니다.

### 4.2 모르는 종류에서 멈춘다 (fail-closed)

`ex5`가 일부러 `Photo`에서 막히게 만들어 둔 이유입니다.

```
x1    Photo     회식 사진                  ??            방침 없음 — 사람이 정해야 한다
막힘: 방침 없는 종류 1개 — ['Photo']
```

자료의 문장이 이것입니다.

> 이게 이 표의 값어치다. **«모르는 것을 모른다고» 말해 준다.**
> 방침이 없으면 자동으로 처리하지 않고 멈춘다.

여기서 표의 값어치가 **아는 것을 아는 데 있지 않다**는 점을 놓치지 마세요. `Person`을 삭제한다는 건 누구나 압니다. 표가 없어도 그건 맞게 처리됩니다. 표가 진짜로 값을 하는 순간은 **아무도 생각해 본 적 없는 종류가 나타났을 때**입니다.

두 가지 실패 방식을 비교하면 차이가 분명합니다.

| | fail-open (표 없음, 또는 기본값 「유지」) | fail-closed (표 + 멈춤) |
|---|---|---|
| 모르는 종류가 오면 | 조용히 처리되거나 조용히 안 된다 | **막히고 사람에게 올라간다** |
| 문제를 아는 시점 | 3주 뒤 「또 연락이 왔을 때」 | 처리 중 |
| 남는 흔적 | 없음 | 「Photo에 방침이 없었다」 |

그리고 이 멈춤은 **한 번만** 발생합니다. `POLICY`에 한 줄 추가하면 그다음부터는 자동으로 통과하니까요. 즉 멈춤은 비용이 아니라 **표를 완성해 나가는 메커니즘**입니다. 모르는 것이 발견될 때마다 표가 자라고, 표가 자란 만큼 즉석 판단이 줄어듭니다.

`Photo`의 답이 「블러」인지 「유지」인지 「삭제」인지는 34장이 정해 주지 않습니다. **그건 관할과 업종에 따라 다르고 법무가 정할 일**이라고 자료가 명시합니다. 엔지니어의 몫은 **정해지지 않았다는 사실을 드러내는 것**입니다.

### 4.3 변경 이력이 남는다

방침 표가 코드나 설정 파일 안에 있으면 자동으로 딸려 오는 것이 **버전 관리**입니다.

`Photo`를 3월에는 삭제, 9월에는 유지로 처리했다고 해 봅시다.

- **표가 없으면** → 모순입니다. 변명할 여지가 없어요.
- **표가 있으면** → 「5월에 방침을 유지로 변경했습니다. 커밋 `a1b2c3`, 법무 승인, 근거는 이렇습니다.」 → **정책 변경**이 됩니다.

같은 두 결과인데 하나는 사고이고 하나는 의사결정의 역사입니다. 차이를 만드는 건 결과가 아니라 **그 사이에 기록된 변경 한 줄**입니다.

그래서 방침 표는 **당시 유효했던 버전을 되찾을 수 있어야** 합니다. 「지금 방침이 뭐냐」만 알 수 있는 표는 절반만 일합니다. 「3월 요청을 처리할 때 방침이 뭐였냐」에 답할 수 있어야 과거 처리를 방어할 수 있어요.

## 5. 방침 표를 운영하는 방법

표를 만드는 건 하루면 되고, **표를 살아 있게 유지하는 게 실제 일**입니다. 세 가지 장치가 필요합니다.

### 5.1 새 노드 종류를 추가할 때 게이트를 둔다

스키마에 노드 종류를 추가하는 시점이 방침을 정할 **가장 싼 시점**입니다. 그때는 아직 데이터가 없고 시한도 없어요.

```
새 노드 종류 추가 PR
  ├─ 스키마 변경
  ├─ POLICY 항목 추가          ← 이게 없으면 CI 실패
  └─ 이유 한 줄               ← 리뷰 대상
```

기계적으로 만드는 방법은 간단합니다. **스키마의 노드 종류 집합과 `POLICY`의 키 집합이 일치하는지 검사하는 테스트**를 CI에 넣으면 됩니다.

```python
def test_policy_covers_all_kinds():
    missing = set(schema_node_kinds()) - set(POLICY)
    assert not missing, f"방침 없는 종류: {sorted(missing)}"
```

이 테스트 하나가 「표가 데이터보다 늦게 자라는」 상황을 막습니다. `ex5`가 런타임에 `Photo`에서 막히는 것은 **이 게이트가 없었다는 증거**이기도 합니다. 런타임 멈춤은 안전망이고, CI 게이트는 예방입니다. 둘 다 있어야 해요.

같은 게이트가 필요한 변경이 몇 개 더 있습니다.

| 변경 | 방침을 다시 봐야 하는 이유 |
|---|---|
| 새 노드 종류 | 방침이 아예 없다 |
| 새 엣지 종류 | 「누가 작성」처럼 **엣지가** 개인을 가리킬 수 있다 |
| 노드에 속성 추가 | 준식별자가 늘어나 재식별 위험이 바뀐다 |
| 자유 텍스트 필드 추가 | 본문 안에 이름이 들어갈 새 경로가 생긴다 |
| 새 데이터 원천 연동 | 조합 가능한 외부 데이터가 늘어난다 |

### 5.2 정기 검토를 일정에 넣는다

표는 정해 두고 잊으면 조용히 낡습니다. 검토 주기에 확인할 것.

- **미분류 큐**: 지난 기간에 「방침 없음」으로 막힌 종류가 몇 개였나. 아직 안 정한 것이 남아 있나.
- **실제 처리와의 괴리**: 표는 「삭제」인데 실제로는 「숨기기」만 하고 있지 않나. **표와 코드가 어긋나면 표가 거짓말**이 됩니다. 이게 감사에서 가장 나쁜 상태예요 — 방침이 없는 것보다 나쁩니다.
- **예외의 빈도**: 특정 종류에서 예외가 반복되면 그건 예외가 아니라 **방침이 틀렸다는 신호**입니다. 표를 고쳐야 합니다.
- **법령·판례 변화**: 방침의 근거가 바뀌었으면 결론도 다시 봅니다.
- **소요 시간**: 재계산·백업·사람 확인을 포함한 실제 소요가 약속한 기한(예: 30일) 안에 들어오나. 34장이 「이 절차의 실제 소요를 재 둬야 한다」고 하는 부분입니다.

주기는 조직 사정이지만, **스키마가 바뀌는 속도보다 촘촘해야** 의미가 있습니다.

### 5.3 예외를 기록한다

「예외 없음」은 지킬 수 없는 규칙이고, 지킬 수 없는 규칙은 몰래 어겨집니다. 그래서 예외 자체를 **표의 일부**로 만듭니다.

예외 기록에 들어갈 것.

| 항목 | 왜 필요한가 |
|---|---|
| 요청 식별자 | 어느 건인지 |
| 대상 노드/종류 | 무엇을 |
| 표의 방침 | 원래는 어떻게 했어야 하나 |
| 실제 처리 | 무엇을 했나 |
| 이유 | **가장 중요.** 6개월 뒤 읽을 사람을 위해 |
| 승인자 | 누가 책임지나 |
| 시점 | 언제 |

예외 기록이 있으면 「지난번엔 지웠는데 이번엔 안 지웠다」는 **모순이 아니라 설명 가능한 두 건**이 됩니다. 그리고 예외 기록이 쌓인 표는 다음 개정판의 초안 노릇을 해요. 같은 예외가 세 번 나오면 그 줄을 고칠 때입니다.

원칙 하나만 지키면 됩니다. **예외는 허용하되, 기록 없는 예외는 허용하지 않습니다.**

## 6. 다시 「값어치」로

34장이 이 표에 붙인 값어치는 **「제대로 지운다」가 아니라 「모르는 것을 모른다고 말해 준다」** 입니다. 이 순서가 중요합니다.

- 표가 **아는 것**에 대해 하는 일: 일관성을 준다. → 감사 통과, 차별 방지, 방어 가능, 자동화 가능
- 표가 **모르는 것**에 대해 하는 일: 멈춰서 사람에게 올린다. → 즉석 판단이 조용히 방침으로 굳는 것을 막는다

방침 없이 즉석 판단을 하는 시스템의 진짜 문제는 「틀린 답을 낸다」가 아닙니다. **모르면서 아는 척한다**는 것입니다. 담당자가 `Photo`를 그냥 지우면, 그건 「Photo는 지운다」가 아니라 「그 사람이 그날 그렇게 생각했다」인데도 시스템에는 **처리 완료**로 남습니다. 모른다는 사실이 사라져요.

표는 그 사실을 붙잡아 둡니다. 그게 열 줄짜리 딕셔너리가 하는 일입니다.

## 7. 자주 하는 오해

| 오해 | 실제 |
|---|---|
| 「표가 있으면 판단이 필요 없다」 | 표는 판단을 **미리, 종류 단위로** 옮긴 것입니다. 판단은 그대로 필요하고 시점과 단위가 바뀐 것뿐입니다. |
| 「매번 잘 처리했으면 됐다」 | 감사는 결과가 아니라 **기준과의 대조**를 봅니다. 기준이 없으면 잘한 것도 입증 못 합니다. |
| 「표는 완성한 뒤에 쓴다」 | 미완성 표도 값을 합니다. 빈 칸에서 **막혀 주기** 때문입니다. 완성을 기다리면 영원히 안 씁니다. |
| 「기본값을 「유지」로 두면 안전」 | fail-open입니다. 지워야 할 것이 조용히 남고, 남았다는 사실도 안 남습니다. 기본값은 **멈춤**이어야 합니다. |
| 「표가 있으면 예외를 못 둔다」 | 예외는 둡니다. **기록 없는** 예외를 못 둡니다. |
| 「일관성만 있으면 된다」 | 일관되게 틀리는 것도 문제입니다. 다만 **한 곳을 고치면 전부 고쳐지는** 문제라서 다루기가 쉽습니다. |

---

## 8. 한 줄 정리

즉석 판단의 결과물은 **처리된 데이터 하나**뿐이고, 방침 표의 결과물은 **처리된 데이터 + 왜 그렇게 했는지 + 다음에도 같게 하겠다는 보장 + 아직 모르는 것의 목록**입니다. 「지난번엔 지웠는데 이번엔 안 지웠다」가 더 큰 문제인 이유는, 그 한 문장이 뒤의 세 개가 전부 없다는 뜻이기 때문입니다.
