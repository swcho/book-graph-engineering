# 그래프에서 삭제가 관계형 DB보다 어려운 세 가지 이유

**질문** — 그래프에서 삭제가 관계형 DB보다 어려운 세 가지 이유는 무엇인가?

**답** — 들어오는 엣지가 남의 사실이기도 하고, 자유 텍스트 안에 이름이 있고, 지운 기록 자체가 '있었다'는 정보다.

출처: 34장 `code/ex1_delete_scope.py` 의 마지막 출력. 「관계형 DB라면 *그 행을 지우면 끝*에 가깝다. 그래프에서는 어렵다. 세 가지 이유가 있다.」

---

## 0. 먼저 비교 축을 세운다 — 관계형 DB의 삭제 모델

관계형 DB에서 「지운다」가 상대적으로 쉬운 건 삭제의 **단위**와 **전파 규칙**이 스키마에 미리 박혀 있기 때문입니다.

| 관계형 DB | 무엇을 보장하나 |
|---|---|
| 삭제 단위가 **행(row)** | `DELETE FROM person WHERE id = 'p1'` — 지울 대상이 한 곳으로 특정된다 |
| **외래키(FK) 제약** | 나를 가리키는 참조가 남아 있으면 DB가 삭제를 *거부*한다. 「무엇이 걸려 있는지」를 DB가 알고 있다 |
| `ON DELETE CASCADE` | 참조하는 자식 행까지 자동으로 같이 지운다 |
| `ON DELETE SET NULL` | 자식 행은 남기고 참조만 끊는다 — 익명화에 해당하는 동작이 **선언으로** 존재한다 |
| `ON DELETE RESTRICT / NO ACTION` | 지우지 못하게 막는다 |

핵심은 세 가지입니다.

1. **참조의 방향이 하나**입니다. FK는 항상 자식 → 부모입니다. 그래서 삭제 전파도 부모 → 자식으로 방향이 정해집니다. 「어디까지 번지나」가 스키마를 보면 계산됩니다.
2. **참조의 개수와 위치를 DB가 안다.** 어떤 컬럼이 `person.id`를 가리키는지 카탈로그에 다 적혀 있습니다. 놓칠 수가 없습니다.
3. **행마다 하나의 주체**입니다. `person` 행은 그 사람의 것이고, `order` 행은 주문의 것입니다. 소유권이 대체로 깔끔합니다.

그래프에서는 이 셋이 모두 깨집니다. 그래서 세 가지 어려움이 나옵니다.

> 참고 — 그래프 DB가 삭제에 대해 주는 안전장치는 훨씬 거칩니다. Neo4j에서 엣지가 붙은 노드에 `DELETE n`을 하면 에러가 나고, `DETACH DELETE n`을 하면 붙은 엣지를 **전부** 같이 지웁니다. 즉 「거부」와 「전부 삭제」 두 극단만 있고, `SET NULL`처럼 *관계만 끊고 상대는 남기는* 중간 단계에 해당하는 선언적 옵션이 없습니다. 그 중간을 사람이 손으로 설계해야 하는데, 34장 전체가 바로 그 중간에 대한 이야기입니다.

## 이유 1 — 들어오는 엣지가 「남의 사실」이기도 하다

### 무엇이 문제인가

`ex1_delete_scope.py`의 엣지 목록을 보면 p1(김도현)에 **들어오는** 엣지가 셋입니다.

```python
("r1", "p1", "읽음"),          # 29장의 Reads — 실행이 이 사람을 읽었다
("p2", "p1", "멘토"),           # 남이 나를 가리킨다
("d1", "p1", "언급"),           # 문서 본문 안에 이름이 있다
```

이 중 `("p2", "p1", "멘토")`가 핵심입니다. 예제의 설명은 이렇습니다.

> 「이서연이 김도현의 멘티였다」는 이서연 쪽 사실이기도 하다. 지우면 이서연의 이력이 사라진다.

엣지 하나가 **두 사람의 사실을 동시에** 담고 있습니다.

- 김도현 관점: 「내가 이서연을 멘토링했다」 → 삭제 요청의 대상
- 이서연 관점: 「나는 2023년에 멘토링을 받았다」 → **삭제 요청자가 아닌 제3자의 이력**

관계형 DB라면 이건 `mentorship(mentor_id, mentee_id)` 같은 별도 행이고, `ON DELETE SET NULL`로 `mentor_id`만 `NULL`(혹은 익명 토큰)로 바꾸면 「멘토링을 받았다」는 사실은 남고 「누구에게」만 사라집니다. 스키마 선언 한 줄입니다.

그래프에서는 그 「멘토」 엣지 자체가 데이터입니다. 엣지를 지우면 사실 전체가 사라지고, 엣지를 남기면 김도현이 남습니다. **엣지의 일부만 지운다**는 개념이 없어서, 「김도현 → 익명 노드 p-8f3a」로 **끝점을 바꿔 다는** 작업을 직접 해야 합니다. 이게 `ex5`의 방침 표에서 `Doc: 작성자 익명화`, `Run: 행위자 익명화`로 나타나는 것입니다.

### 그래서 「이어진 것 전부 삭제」가 답이 아니다

`ex4_cascade.py`가 이걸 증명합니다. p1을 뿌리로 영향 범위를 세면 일곱 개가 걸리는데, 그중에 **이서연(p2)** 이 있습니다. 「같은 팀(t1)에 속함」이라는 이유만으로 걸린 것입니다.

```
김도현 → 3분기 보고서 → 팀별 문서 수 → 결제팀은 문서 생산이 많다
       → 결제팀에 리소스를 더 배정하자
```

즉 그래프의 `CASCADE`를 곧이곧대로 적용하면 개인정보와 아무 상관 없는 **집계(Stat)** 와 **회사의 결정(Answer)** 까지 무너집니다. 34장의 결론은 이렇게 나뉩니다.

| 분류 | 처리 |
|---|---|
| 개인을 특정하는 것 (Person, Contact) | 지운다 |
| 그 사람이 만든 산출물 (Doc) | 대개 남긴다 — **작성자만** 익명화 |
| 집계(Stat)와 결정(Answer) | 남긴다 (개인정보가 아니다) |

경계는 하나입니다. **「그것이 개인을 가리키는가, 아니면 개인이 만든 것인가?」** 「3분기 보고서」는 개인을 가리키지 않습니다. 「김도현이 작성」이 가리킵니다. 그래서 문서는 두고 엣지의 작성자만 바꿉니다. 그리고 이 판정은 자동으로 못 하기 때문에 `ex5`처럼 **노드 종류별 방침 표**를 사람이 미리 정해 둡니다.

## 이유 2 — 자유 텍스트 안에 이름이 있다

### 예제가 보여 주는 것

`ex1`에서 노드와 엣지를 다 지운 뒤에 남은 노드를 훑으면 이렇게 나옵니다.

```
m1   Msg   김도현: 마포에서 봐요   ← 이름이 그대로 남아 있다
```

p1 노드는 사라졌습니다. 그런데 「김도현」이라는 문자열은 `m1`의 `label` **안에** 남아 있습니다. 예제의 설명은 이렇습니다.

> 발화, 문서 본문, 요약. 이건 정규화된 필드가 아니라 그냥 글이다.

### 왜 관계형 DB보다 어려운가

관계형 DB에서 개인정보 삭제가 「행 하나」로 끝날 수 있는 전제는 **정규화**입니다. 이름은 `person.name` 한 곳에만 있고, 다른 데서는 `person_id`로 참조합니다. 그래서 그 한 행을 지우면 이름이 사라집니다.

그래프 시스템은 정규화가 덜 된 데이터를 많이 안고 있습니다.

- **발화·메시지 본문** — 「김도현: 마포에서 봐요」. 사람이 쓴 글이라 필드로 쪼갤 수 없습니다.
- **문서 본문의 언급** — `("d1", "p1", "언급")` 엣지가 있다는 건 문서 안에 이름이 박혀 있다는 뜻입니다. 엣지를 지워도 본문의 글자는 남습니다.
- **LLM이 만든 요약** — 원본을 지워도 요약문에 이름이 남습니다.
- 그리고 예제가 덧붙이는 곳들: **로그, 백업, 이벤트 로그**. 34장의 한 장 요약이 꼽는 「남는 곳 다섯」이 이것입니다 — 들어오는 엣지, 자유 텍스트 안의 이름, 이벤트 로그, 백업, 검색 색인.

`SQL DELETE`로 지울 수 있는 건 「행」이지 「문장 안의 부분 문자열」이 아닙니다. 자유 텍스트를 다루려면 NER 수준의 탐지가 필요하고, 그건 재현율이 100%가 아닙니다. 그래서 `ex5`의 방침이 `Msg: 삭제`가 아니라 **`Msg: 본문 마스킹 — 이름·연락처만 가린다`** 입니다. 대상을 「행」에서 「본문 안의 조각」으로 낮춘 것입니다.

### 더 나쁜 소식 — 이름을 다 지워도 특정된다

`ex3_reidentify.py`가 5,000명으로 실측합니다. 이름은 이미 지운 상태에서 남은 속성을 조합합니다.

| 조합 | 혼자인 사람 비율 |
|---|---|
| team | 0% (팀당 105명씩) |
| team + city + role | 0.6% (30명) |
| team + city + role + joined | **65.8%** |
| + birth_month | 96.3% |

셋에서 넷으로 갈 때 0.6% → 65.8%. **두 배가 아니라 백 배로** 뜁니다. 조합의 수가 곱해지기 때문입니다. 이게 재식별(re-identification)이고, 「어떤 조합으로도 최소 k명 이상으로 묶인다」는 성질이 **k-익명성**입니다. 대응은 일반화(generalization) / 억제(suppression) / 잡음(noise) 셋인데, 전부 정확도를 내주고 익명성을 삽니다.

그리고 그래프에는 하나가 더 있습니다. **관계 자체가 식별자**입니다. 속성을 전부 지워도 「이 팀에 속하고 저 문서를 작성했고 그 사람의 멘티다」라는 이웃 **모양**이 남고, 그 모양이 유일하면 특정됩니다. 34장은 이걸 「아직 제대로 된 해법이 없다」고 솔직하게 적습니다.

## 이유 3 — 지운 「기록」 자체가 「있었다」는 정보다 (핵심)

### 예제의 문장

> 30장의 이벤트 로그에는 「p1 을 지웠다」가 남는다. 그 기록 자체가 「p1 이 있었다」는 정보다.

이게 세 이유 중 가장 반직관적인 것이라 천천히 풉니다.

### 왜 삭제 기록이 남는가 — 지우려면 써야 한다

**삭제는 「없앰」이 아니라 「삭제됐다는 사실의 기록」으로 구현됩니다.** 여기에 이유가 여럿 겹칩니다.

1. **이벤트 소싱 / 추가 전용 로그** — 30장에서 다뤘듯 이벤트 로그는 append-only입니다. 상태는 이벤트를 접어서(fold) 만듭니다. 「삭제」도 하나의 이벤트로 **추가**됩니다. 로그에서 과거 이벤트를 뽑아내면 로그의 불변식(해시 체인, 순번)이 깨집니다.
2. **분산 저장의 툼스톤(tombstone)** — Cassandra/Dynamo 계열이나 CRDT 기반 복제에서 삭제는 「지움 표시(tombstone)」를 *쓰는* 것입니다. 표시가 없으면 아직 삭제를 못 받은 복제본이 옛 값을 되살립니다(zombie resurrection). 그래서 툼스톤은 모든 복제본이 수렴할 때까지(`gc_grace_seconds`) 지울 수 없습니다.
3. **감사 이력 / 규제** — 「요청을 받아 언제 무엇을 처리했다」를 증명해야 합니다. 삭제권 대응 자체가 감사 기록을 요구합니다. 지웠다는 증거를 지우면 지웠음을 증명할 수 없습니다.
4. **백업과 WAL** — 스냅샷과 로그 세그먼트는 보존 기간이 끝나야 사라집니다. 즉 삭제는 **초 단위가 아니라 며칠 걸리는 절차**입니다.

`ex2`의 표가 이 사실을 정면으로 보여 줍니다. 「완전 삭제」는 가장 강해 보이는데 만족하는 기준이 8개 중 **4개로 가장 적습니다**. 감사 이력이 깨지고(✗), 집계가 깨지고(✗), 남의 이력이 깨집니다(✗). 반대로 「백업까지 지워진다」 칸은 완전 삭제 말고는 아무 수준도 ○가 아닙니다.

### 그래서 무슨 일이 벌어지나 — 존재 추론

툼스톤은 **내용은 비어 있지만 위치가 채워진 자리**입니다. 값을 가리는 데는 성공했는데, **그 자리가 존재했다는 사실**은 오히려 명시적으로 기록됩니다.

이벤트 로그에 이 한 줄이 남았다고 합시다.

```
2026-08-19T14:03Z  actor=admin  event=PersonDeleted  subject=p1
```

이름도 연락처도 없습니다. 그런데 여기서 읽히는 것이 있습니다.

- **존재**: `p1`이라는 사람이 있었다.
- **시점**: 2026-08-19에 사라졌다.
- **의미**: 이 시스템에서 `PersonDeleted`는 대개 GDPR 삭제 요청 처리입니다. → 「p1은 **삭제를 요청한 사람**이다」. 삭제 요청 사실 자체가 그 사람에 관한 새로운 개인정보입니다.

그리고 이걸 남은 데이터와 **조합**하면 신원까지 좁혀집니다. 이유 2에서 본 재식별이 여기서 다시 작동합니다.

- 같은 날 결제팀 인원 집계가 3 → 2로 줄었다 (Stat은 남겨 두기로 했으니 남아 있습니다)
- 이서연의 「멘토」 엣지가 익명 노드 `p-8f3a`를 가리키게 바뀌었고, 그 시각이 같다
- 「3분기 보고서」의 작성자가 그 시각에 익명화됐다

세 조각을 겹치면 `p1 = 결제팀에서 2026-08-19에 빠진, 이서연의 멘토였고, 3분기 보고서를 쓴 사람`입니다. **아무 이름도 남기지 않고 사람을 특정했습니다.** 삭제의 *흔적들*이 서로를 지목한 것입니다. 이게 「지운 기록 자체가 정보다」의 실전 형태입니다.

### 관계형 DB와의 차이

관계형 DB에도 툼스톤과 감사 로그는 있습니다. 원리상 같은 문제입니다. 차이는 **노출 면적**입니다.

- 관계형에서 `person` 행 하나를 지우면 흔적은 그 테이블의 툼스톤 하나입니다.
- 그래프에서 사람 하나를 지우면 **들어오는 엣지 N개, 나가는 엣지 M개, 본문 마스킹 K건, 재계산된 집계, 익명화된 작성자 엣지**에 흔적이 동시에 생깁니다. 흔적이 여러 곳에 남으면 그 흔적들끼리 **교차 검증**이 가능해집니다. 이유 1·2가 만든 넓은 삭제 범위가 이유 3의 추론 가능성을 키웁니다. 세 이유는 독립이 아니라 서로를 증폭합니다.

### 34장의 대응 — 이벤트에 개인정보를 직접 넣지 않는다

지울 수 없는 곳에는 **애초에 넣지 않는 것**이 유일한 대응입니다. `ex5`의 방침 표에서 `Event`만 처리 방식이 다릅니다.

```python
"Event":    ("식별자 치환", "30장 — 이벤트는 못 지운다"),
```

이벤트 로그에는 식별자(`p1`)만 넣고, 이름·연락처 같은 실제 값은 그 식별자를 가리키는 **별도 표**에만 둡니다. 그러면 그 표에서 한 번 지우는 것으로 이벤트 로그 전체의 개인정보가 읽을 수 없게 됩니다(암호키를 지워 복호화를 불가능하게 만드는 crypto-shredding도 같은 발상입니다). 로그의 불변식은 유지되고, 남는 건 「p1이 있었다」는 최소한의 뼈대뿐입니다.

그래도 그 뼈대는 남습니다. 34장은 그걸 없앨 수 있다고 말하지 않습니다. **줄일 수 있다**고 말합니다. 데이터 최소화(data minimisation)와 보존 기간(retention period)이 키워드 표에 들어 있는 이유입니다.

## 한 장으로 요약

| | 관계형 DB | 그래프 |
|---|---|---|
| 삭제 단위 | 행 | 노드 + 엣지 + 본문 조각 |
| 참조 방향 | FK 하나 (자식→부모) | 양방향·다종류 |
| 「무엇이 걸리나」 | DB가 안다 (FK 카탈로그) | 사람이 방침 표로 정해야 한다 |
| 「관계만 끊기」 | `ON DELETE SET NULL` 선언 | 직접 재배선(익명 노드로 끝점 교체) |
| 자유 텍스트 | 정규화로 회피 | 발화·본문·요약에 이름이 박혀 있다 |
| 삭제 흔적 | 툼스톤 1건 | 여러 곳의 흔적 → 교차 조합으로 재식별 |

세 이유를 한 문장씩으로.

1. **들어오는 엣지** — 엣지는 두 사람의 사실이다. 지우면 남의 이력이 깨진다. 그래서 삭제가 아니라 익명화가 필요하다.
2. **자유 텍스트** — 이름이 필드가 아니라 글 안에 있다. `DELETE`로 도달할 수 없다. 그리고 이름을 다 지워도 속성 조합(그래프에서는 이웃 모양)으로 특정된다.
3. **삭제 기록** — 지우려면 「지웠다」를 써야 한다(툼스톤·append-only 로그·감사·백업). 그 기록은 값을 감추면서 **존재를 확정**하고, 다른 흔적과 조합되면 신원까지 되돌린다.

그래서 34장의 결론은 「완전히 지운다」가 아니라 **「지운다」를 네 수준(숨기기 / 식별자 끊기 / 가명화 / 완전 삭제)으로 나누고, 노드 종류마다 방침을 정하고, 방침 없는 종류가 나오면 멈춘다**입니다. 그리고 「완료」의 기준을 문서로 정해 둡니다. 삭제 자체는 초 단위지만 전체 절차는 며칠 걸리기 때문입니다.
