# 김도현을 지울 때 영향 경로는 어디까지 이어지는가

**답:** 김도현 → 3분기 보고서 → 팀별 문서 수 → "결제팀은 문서 생산이 많다" → "결제팀에 리소스를 더 배정하자"로 이어진다.

---

## 1. 이 질문이 노리는 것

`ex4_cascade.py`는 "사람 하나를 지운다"는 요청 하나를 **도달 가능성 탐색**으로 풀어 봅니다.
외울 것은 다섯 개짜리 사슬 자체가 아니라, **그 사슬을 지나가는 동안 노드의 성격이 계속
바뀐다**는 사실입니다. 개인정보로 출발한 것이 산출물이 되고, 집계가 되고, 해석이 되고,
결정이 됩니다. 성격이 바뀌면 처리 방식도 바뀌어야 합니다.

> 28장의 연쇄 철회와 같은 구조인데, 여기서는 «사람»이 뿌리다.
> — `ex4_cascade.py` docstring

## 2. 그래프 구조 — 노드 8개, 엣지 7개

`ex4_cascade.py`의 `NODES` / `EDGES`를 그대로 그리면 이렇습니다.

```
p2(이서연) ──속함──┐
                   ↓
p1(김도현) ──속함──→ t1(결제팀)        ← 남과 공유하는 대상
    │
    └───작성───→ d1(3분기 보고서)   [Doc]
                       ↑ 집계함
                  s1(팀별 문서 수)   [Stat]
                       ↑ 기댐
                  f1(결제팀은 문서 생산이 많다)   [Fact]
                       ↑ 기댐
                  a1(결제팀에 리소스를 더 배정하자)   [Answer]
                       ↑ 생성함
                  r1(분기 분석 #901)   [Run]
```

**엣지 방향이 중요합니다.** `s1 -집계함-> d1`, `f1 -기댐-> s1`, `a1 -기댐-> f1`.
화살표는 "내가 무엇에 기대고 있는지"(의존 대상)를 가리킵니다. 즉 화살표는 **아래(근거)를
향하고**, 영향은 그 **반대 방향으로 올라갑니다.**

| 보는 방향 | 읽는 문장 |
|---|---|
| 엣지 방향대로 (a1 → f1 → s1 → d1) | "이 결정은 저 사실에 기대고, 그 사실은 저 집계에 기대고…" |
| 엣지 반대로 (d1 → s1 → f1 → a1) | "이 문서가 흔들리면 집계가 흔들리고, 그러면 결정이 근거를 잃는다" |

카드의 정답인 "영향 경로"는 아래쪽, 즉 **엣지를 거꾸로 타고 올라간 경로**입니다.
그래서 쿼리도 `(x)-[:R*1..5]->(d)` 처럼 **x가 d를 향하는** 모양으로 쓰여 있습니다.
d(영향의 시작점)를 고정해 두고, 거기로 화살표가 들어오는 것들을 전부 긁어모으는 것이죠.

## 3. 영향 범위 쿼리 두 개를 단계별로

### 3.1 직접 이어진 것

```cypher
MATCH (a:N {id:'p1'})-[e:R]->(b:N) RETURN b.id, b.kind, b.label
```

p1에서 한 홉 나가는 것만 봅니다.

```
직접 이어진 것 2개:
    [Team] 결제팀
    [Doc] 3분기 보고서
```

### 3.2 그것에 기대고 있는 것 (도달 가능성 탐색)

```cypher
MATCH (x:N)-[:R*1..5]->(d:N)<-[:R]-(p:N {id:'p1'})
WHERE x.id <> 'p1'
RETURN DISTINCT x.id, x.kind, x.label ORDER BY x.id
```

읽는 순서는 오른쪽부터입니다.

1. `(d)<-[:R]-(p1)` — 먼저 **d를 p1의 직접 이웃으로 묶습니다.** d ∈ {`t1`, `d1`}.
2. `(x)-[:R*1..5]->(d)` — 그 d로 **1~5홉 안에 도달하는 모든 x**를 찾습니다.
   `*1..5`가 가변 길이 경로(variable-length path)이고, 이것이 도달 가능성 탐색입니다.
3. `WHERE x.id <> 'p1'` — 뿌리 자신은 뺍니다.
4. `DISTINCT` — 같은 x가 여러 경로로 잡히므로 중복을 지웁니다.

홉 수별로 무엇이 걸리는지 손으로 펼치면:

| d | 홉 | 걸리는 x | 경로 |
|---|---|---|---|
| `t1` 결제팀 | 1 | `p2` 이서연 | `p2 -속함-> t1` |
| `d1` 보고서 | 1 | `s1` 팀별 문서 수 | `s1 -집계함-> d1` |
| `d1` | 2 | `f1` 문서 생산이 많다 | `f1 -기댐-> s1 -집계함-> d1` |
| `d1` | 3 | `a1` 리소스 배정 | `a1 -기댐-> f1 -> s1 -> d1` |
| `d1` | 4 | `r1` 분기 분석 #901 | `r1 -생성함-> a1 -> f1 -> s1 -> d1` |

실행 결과(확인함):

```
그것에 기대고 있는 것 5개:
    [Answer] 결제팀에 리소스를 더 배정하자
    [Fact] 결제팀은 문서 생산이 많다
    [Person] 이서연
    [Run] 분기 분석 #901
    [Stat] 팀별 문서 수
```

**직접 2 + 간접 5 = 일곱 개.** 사람 하나를 지우려는데 일곱 개가 걸립니다.

여기서 `p2`(이서연)는 **다른 가지**입니다. `t1`을 공유한다는 이유만으로 잡혔고,
"명백히 지우면 안 되는 것"의 예로 일부러 넣어 둔 노드입니다.
카드가 묻는 사슬은 `p2`가 아니라 `d1` 쪽 가지 하나입니다.

## 4. 답의 사슬 — 다섯 칸, 다섯 가지 성격

```
김도현 → 3분기 보고서 → 팀별 문서 수 → 결제팀은 문서 생산이 많다
      → 결제팀에 리소스를 더 배정하자
```

이 사슬을 외울 때 **라벨이 아니라 성격의 전이**로 외우는 게 낫습니다.

| # | 노드 | 종류 | 성격 | 개인을 가리키나 | 지워야 하나 |
|---|---|---|---|---|---|
| 1 | 김도현 | `Person` | **개인정보** — 그 사람 자체 | 그 자체가 개인 | 지운다 |
| 2 | 3분기 보고서 | `Doc` | **산출물** — 개인이 만든 것 | 문서는 아님. "김도현이 작성"이라는 **엣지**가 가리킴 | 문서는 남기고 작성자만 익명화 |
| 3 | 팀별 문서 수 | `Stat` | **집계** — 여럿을 뭉갠 수 | 아님 (팀 단위) | 남기고 재계산 |
| 4 | 결제팀은 문서 생산이 많다 | `Fact` | **해석** — 집계에서 끌어낸 진술 | 아님 | 유지 |
| 5 | 결제팀에 리소스를 더 배정하자 | `Answer` | **결정** — 회사의 판단 기록 | 아님 | 유지 |
| (+) | 분기 분석 #901 | `Run` | **실행 이력** | 행위자 한 칸만 | 행위자만 익명화 |

전이를 한 줄로: **개인정보 → 산출물 → 집계 → 해석 → 결정.**

칸 2에서 3으로 넘어가는 순간 개인은 이미 사라집니다. 「결제팀 문서 12건」에는 김도현이
없습니다. 그런데 **인과는 계속 이어집니다.** 개인정보성은 2~3에서 끊기는데 의존성은
5까지 이어진다 — 이 **어긋남**이 이 예제의 핵심입니다.

## 5. 그래서 어디서 처리 방식이 바뀌는가

전환점은 **1→2 사이**, 정확히는 「김도현이 작성」이라는 엣지 위입니다.

> 경계가 어디냐면 «그것이 개인을 가리키는가»다.
> 「3분기 보고서」는 개인을 안 가리킨다. 「김도현이 작성」이 가리킨다.
> 그러니 문서는 두고 엣지의 «작성자»만 익명 노드로 바꾼다.
> — `ex4_cascade.py`

정리하면 세 구간입니다.

```
[구간 A] p1        →  지운다            (개인을 특정하는 것)
─────────── 경계: 노드가 아니라 «작성» 엣지 위에 있다 ───────────
[구간 B] d1        →  대개 남긴다 (작성자만 익명화)
[구간 C] s1·f1·a1  →  남긴다 (집계·해석·결정)
```

`ex4_cascade.py`가 직접 쓰는 세 줄:

```
개인을 특정하는 것 → 지운다
그 사람이 만든 산출물 → 대개 남긴다 (작성자만 익명화)
집계와 결정        → 남긴다
```

그리고 **연쇄 삭제가 답이 아닌 이유**가 이 사슬 안에 두 종류로 들어 있습니다.

- **성격이 다른 것이 섞여 있다** — 집계(`s1`)는 개인정보가 아니라 지울 이유가 없고,
  결정(`a1`)은 회사의 기록이라 지우면 안 됩니다.
- **남의 것이 섞여 있다** — `p2`(이서연)가 팀 공유만으로 걸립니다.

쿼리는 **영향 범위를 세는 도구**일 뿐 삭제 목록이 아닙니다. 범위를 세는 것과 무엇을 지울지
정하는 것은 별개의 판단이고, 후자는 자동으로 못 합니다.

## 6. 28장 연쇄 철회와의 차이

구조는 같습니다(`Doc → Stat → Fact → Answer`를 거꾸로 타는 것). 그런데 **동기가 다르고,
그래서 결론이 반대**입니다.

| | 28장 연쇄 철회 | 34장 개인정보 삭제 |
|---|---|---|
| 뿌리 | 근거(사실·문서)가 틀렸다 | 사람이 삭제를 요청했다 |
| 위쪽이 틀렸나 | 예 — 근거가 무너졌으니 결론도 무효 | 아니오 — 집계 수치는 여전히 참 |
| 처리 | 위로 타고 올라가며 철회 | 위는 **그대로 두고**, 뿌리의 식별성만 끊는다 |

김도현이 쓴 문서를 **지우면** 집계가 바뀌고 그 위의 판단이 근거를 잃습니다.
그래서 문서를 지우지 않고 **작성자만 익명화**합니다. 그러면 문서 수는 그대로이고
집계도 그대로이며, 사슬 3~5는 아무 일도 없습니다. **경계를 엣지에 두는 이유가 바로
이 사슬을 살리기 위해서입니다.**

(작성자 익명화조차 안 되고 문서 본문 자체를 지워야 하는 경우라면 `Stat`은 `재계산`으로
넘어갑니다. 그래서 `ex5`의 `Stat` 방침이 `유지`가 아니라 `재계산`입니다.)

## 7. 노드 종류별 방침 표와의 연결

`ex4`가 "판정은 자동으로 못 한다. 노드 종류마다 사람이 정해 둬야 한다"로 끝나고,
그 표를 코드로 만든 것이 `ex5_deletion_plan.py`의 `POLICY`입니다.
사슬의 각 칸이 표의 어느 줄인지 대응시켜 보면:

| 종류 | 방침 | 이유 | 사슬에서 |
|---|---|---|---|
| `Person` | 삭제 | 개인 그 자체 | **① 김도현** |
| `Contact` | 삭제 | 연락처 | (사슬 밖) |
| `Msg` | 본문 마스킹 | 발화 — 이름·연락처만 가린다 | (`ex1`의 `m1`) |
| `Doc` | 작성자 익명화 | 산출물은 회사 자산 | **② 3분기 보고서** |
| `Team` | 유지 | 개인정보 아님 | (직접 이웃 `t1`) |
| `Stat` | 재계산 | 집계는 남기되 다시 센다 | **③ 팀별 문서 수** |
| `Fact` | 유지 | 개인을 안 가리키면 | **④ 문서 생산이 많다** |
| `Answer` | 유지 | 회사의 결정 기록 | **⑤ 리소스 배정** |
| `Run` | 행위자 익명화 | 누가 돌렸는지만 가린다 | (`r1` 분기 분석) |
| `Event` | 식별자 치환 | 30장 — 이벤트는 못 지운다 | (로그) |

방침 값이 **`삭제` 하나가 아니라 여섯 종류**(삭제 / 본문 마스킹 / 작성자 익명화 / 유지 /
재계산 / 행위자 익명화 / 식별자 치환)라는 점이 4절 표와 정확히 맞물립니다.
사슬을 타고 가면서 성격이 바뀌기 때문에, 처리 동작도 종류마다 달라야 합니다.

그리고 `ex5`는 `Photo`(회식 사진)에서 일부러 막힙니다. 방침 표에 없는 종류라서
`??`가 찍히고 절차가 멈춥니다. 「모르는 것을 모른다고」 말해 주는 것이 이 표의
값어치입니다 — 표가 없으면 담당자가 그때그때 다르게 판단하고,
"지난번엔 지웠는데 이번엔 안 지웠다"가 더 큰 문제가 됩니다.

## 8. 한 줄 정리

- **경로:** 김도현 → 3분기 보고서 → 팀별 문서 수 → "결제팀은 문서 생산이 많다"
  → "결제팀에 리소스를 더 배정하자"
- **쿼리:** `(x)-[:R*1..5]->(d)<-[:R]-(p1)` — d를 p1의 직접 이웃으로 고정하고,
  거기로 도달하는 x를 가변 길이 경로로 긁는다. 직접 2 + 간접 5 = 7개.
- **성격 전이:** 개인정보 → 산출물 → 집계 → 해석 → 결정
- **전환점:** 노드가 아니라 「김도현이 작성」이라는 **엣지** 위. 문서는 두고 작성자만 익명화.
- **함정:** 이서연(`p2`)도 팀 공유만으로 걸린다. 영향 범위 ≠ 삭제 목록.

하는지는 관할과 업종에 따라 다르고, 그건 법무가 정할 일입니다. 엔지니어가 할 일은
「그 수준을 선택했을 때 무엇이 깨지는지」를 미리 세는 것 — 그게 `ex4`가 하는 일입니다.
