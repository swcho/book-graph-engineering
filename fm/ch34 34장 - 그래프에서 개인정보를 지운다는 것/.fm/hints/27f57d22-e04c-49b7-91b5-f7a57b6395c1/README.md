# Stat(집계)과 Event(이벤트)의 방침은 각각 무엇인가?

> **답**: Stat은 **재계산**(집계는 남기되 다시 센다), Event는 **식별자 치환**(30장대로 이벤트는 못 지운다)이다.

---

## 1. 어디서 나온 답인가

34장 `ex5_deletion_plan.py`의 **노드 종류별 방침 표**(`POLICY`)에 있는 두 줄입니다.

```python
POLICY = {
    "Person":   ("삭제",        "개인 그 자체"),
    "Contact":  ("삭제",        "연락처"),
    "Msg":      ("본문 마스킹",  "발화 — 이름·연락처만 가린다"),
    "Doc":      ("작성자 익명화", "산출물은 회사 자산"),
    "Team":     ("유지",        "개인정보 아님"),
    "Stat":     ("재계산",      "집계는 남기되 다시 센다"),      # ← 이 줄
    "Fact":     ("유지",        "개인을 안 가리키면"),
    "Answer":   ("유지",        "회사의 결정 기록"),
    "Run":      ("행위자 익명화", "누가 돌렸는지만 가린다"),
    "Event":    ("식별자 치환",  "30장 — 이벤트는 못 지운다"),   # ← 이 줄
}
```

이 표의 모든 방침은 **한 가지 질문**에서 파생됩니다.

> «이 노드가 개인을 가리키는가, 아니면 개인이 만든 것인가?»
> 가리키면 지우고, 만든 것이면 «만든 사람만» 지운다.

Stat과 Event는 둘 다 「개인을 가리키지 않는」 쪽입니다. 그런데 방침이 서로 다릅니다. **왜 다른가**가 이 카드의 진짜 내용입니다. 이유가 다르기 때문입니다 — 하나는 *정확성* 때문에 다시 세고, 하나는 *물리적 불가능* 때문에 치환합니다.

| | Stat | Event |
|---|---|---|
| 방침 | 재계산 | 식별자 치환 |
| 왜 이 방침인가 | 지울 대상은 아닌데, **삭제된 사람의 기여가 값 속에 녹아 있다** | 지워야 할 것 같은데, **append-only 라서 지울 수가 없다** |
| 제약의 성격 | 의미론적 제약 (정확성) | 구조적 제약 (불변성) |
| 삭제 대상 | 없음 (값만 갱신) | 없음 (참조만 무의미해짐) |
| 남는 위험 | 차분 공격, 스냅샷 불일치 | 존재 사실·타임라인 노출 |

## 2. Stat — 왜 「지우지 않고 재계산」인가

### 2.1 지우지 않는 이유: 집계는 개인정보가 아니다

`ex4_cascade.py`가 이 판단을 먼저 만들어 둡니다.

```
김도현 → 3분기 보고서 → 팀별 문서 수 → 결제팀은 문서 생산이 많다
→ 결제팀에 리소스를 더 배정하자
```

「김도현을 지워 주세요」 하나로 일곱 개가 걸립니다. 그런데 `ex4`의 결론은 명확합니다.

> 집계(팀별 문서 수)는 개인정보가 아니다. 지울 이유가 없다

「결제팀 문서 42건」은 누구도 가리키지 않습니다. GDPR 용법으로 말하면 **개인 데이터(personal data)가 아니므로 삭제권(Art. 17)의 대상이 아닙니다.** 삭제권은 「나에 관한 데이터」를 지울 권리이고, 「팀 단위 총계」는 나에 관한 데이터가 아닙니다.

게다가 지우면 **남의 것이 깨집니다**. `ex2_delete_levels.py` 표에서 「완전 삭제」가 `✗` 를 받은 세 칸이 이것입니다.

| 기준 | 1.숨기기 | 2.식별자끊기 | 3.가명화 | 4.완전삭제 |
|---|---|---|---|---|
| 집계·통계가 유지된다 | ○ | ○ | ○ | **✗** |
| 감사 이력이 유지된다 | ○ | ○ | ○ | **✗** |
| 남의 이력이 안 깨진다 | ○ | ○ | ○ | **✗** |

집계를 지우면 그 위에 얹힌 Fact와 Answer가 근거를 잃습니다(28장의 연쇄 철회). 한 사람의 삭제권을 이행하려고 회사의 판단 기록 전부를 무너뜨리는 셈입니다. 그건 비례하지 않습니다.

### 2.2 그런데 그대로 두면 안 되는 이유: 기여가 남아 있다

여기가 이 카드에서 가장 미묘한 곳입니다. 「집계는 개인정보가 아니니 손대지 말자」로 끝나면 안 됩니다.

`Stat("팀별 문서 수") = 42` 라는 값 안에는 **김도현이 쓴 문서 3건이 더해져 있습니다.** 김도현의 Person 노드를 지우고 Doc의 작성자를 익명화한 뒤에도, 42라는 숫자는 여전히 김도현이 기여한 3을 품고 있습니다.

이걸 그대로 두면 두 가지가 어긋납니다.

1. **의미의 어긋남 — 삭제 요청의 실질이 이행되지 않았다.**
   삭제 요청은 「나의 흔적을 남기지 말라」입니다. 「내가 쓴 문서 3건이 집계에 계속 반영된다」면 흔적은 남아 있습니다. 값 자체가 개인정보는 아니지만, **삭제된 개인의 데이터를 계속 처리(processing)하고 있는 상태**입니다. 「삭제했다」고 답하고 나서 그 사람의 데이터를 계속 쓰는 것이 문제인 것입니다.

2. **정합성의 어긋남 — 집계가 원본과 안 맞는다.**
   Stat은 **파생 데이터(derived data)** 입니다. 원본(Doc, 작성 엣지)이 바뀌면 파생도 바뀌어야 합니다. 원본을 손대고 파생을 안 손대면 시스템은 「집계가 원본과 다른」 상태로 들어갑니다. 다음에 누군가 「그럼 이 42는 뭘 센 거냐」고 물으면 답할 수 없습니다.

### 2.3 그래서 재계산이 「정확한 동작」이다

- **삭제**: 개인정보가 아닌 것을 지운다 → 과잉. 남의 것을 깬다.
- **유지**: 삭제된 사람의 기여를 계속 반영한다 → 미달. 삭제가 이행되지 않았다.
- **재계산**: 집계라는 **노드는 남기고**, 그 **값만** 삭제 후 상태로 다시 만든다 → 둘을 동시에 만족.

이것이 `"집계는 남기되 다시 센다"` 라는 주석의 뜻입니다. **삭제 대상은 없고 갱신 대상만 있습니다.** Stat 노드의 `id`, 그 노드를 가리키는 Fact/Answer의 엣지, 대시보드에 박힌 참조 — 전부 살아 있습니다. 바뀌는 것은 값 하나입니다.

```
삭제 전:  Stat("팀별 문서 수") = { 결제팀: 42, ... }   ← 김도현 3건 포함
잘못 1:   Stat 노드 삭제       → Fact·Answer 붕괴, 대시보드 깨짐
잘못 2:   그대로 둠            → 김도현 기여 3건이 계속 남음
정답:     Stat("팀별 문서 수") = { 결제팀: 39, ... }   ← 노드는 그대로, 값만 다시 셈
```

한 문장으로: **Stat은 「지울 것」이 아니라 「다시 계산해야 할 것」입니다.** 개인정보의 저장소가 아니라 개인정보의 *함수*이기 때문입니다.

### 2.4 다른 방식과의 비교 — 왜 「빼기」가 아니고 「다시 세기」인가

「42에서 3을 빼면 되지 않나」 싶습니다. 실무에서 그렇게 하지 않는 이유가 있습니다.

| 방식 | 문제 |
|---|---|
| **증분 갱신(빼기)** | 「몇을 빼야 하는지」를 알려면 김도현의 기여량을 알아야 합니다. 그런데 그 정보는 방금 지운 것입니다. 지우기 전에 미리 재 두고 지운 뒤에 빼면, 그 「기여량 3」이라는 값이 다시 그 사람에 관한 데이터입니다. 순환입니다. |
| | 평균·중위값·백분위·유일 카운트(distinct)·표준편차는 **뺄 수 없습니다**. 원소를 빼려면 원본을 다시 훑어야 합니다. 합계와 개수만 예외입니다. |
| | 부동소수점 합계는 뺄셈으로 원상복구되지 않습니다(오차 누적). |
| **전체 재계산** | 원본을 훑으므로 정의상 정확합니다. 「어떻게 지웠는지」를 몰라도 「지금 원본」만 보면 됩니다. 대가는 비용. |

재계산이 **삭제 이력에 의존하지 않는다**는 점이 결정적입니다. 삭제가 여러 번 겹치거나 중간에 실패해도, 재계산은 항상 「현재 원본과 일치하는 값」을 만듭니다. **멱등(idempotent)** 합니다.

## 3. Stat 재계산의 대가

`ex5`의 마지막 단락이 값을 청구합니다.

> 마지막으로, 이 절차는 «며칠 걸린다». 재계산이 있고 백업이 있고 사람 확인이 있다.
> 그래서 「30일 안에 처리」 같은 약속을 하려면 이 절차의 실제 소요를 재 둬야 한다.

### 3.1 비용과 지연

삭제 자체는 초 단위입니다. 재계산은 그렇지 않습니다.

- **전체 스캔**: 「팀별 문서 수」를 다시 세려면 Doc 전체를 훑습니다. 한 사람 지우려고 테이블 전체를 읽는 셈입니다.
- **연쇄 재계산**: Stat 위에 Fact가, Fact 위에 Answer가 있습니다(`ex4`의 경로). Stat이 바뀌면 그 위를 어디까지 다시 볼 것인가가 또 문제입니다. 「집계가 42에서 39로 바뀌었는데 «결제팀은 문서 생산이 많다»는 여전히 참인가」는 사람이 판단해야 할 수도 있습니다.
- **배치 창(batch window)**: 대부분의 집계는 야간 배치로 만듭니다. 그러면 삭제 요청 하나가 「다음 배치까지 대기」가 됩니다. 즉시 재계산을 강제하면 배치 파이프라인을 하루에 수십 번 돌리는 일이 됩니다.
- **일괄 처리의 유혹과 함정**: 그래서 삭제 요청을 모아 하루 한 번 재계산하는 설계가 흔합니다. 합리적이지만, **약속한 기한 안에 들어오는지**를 계산에 넣어야 합니다. GDPR은 원칙적으로 1개월(Art. 12(3))입니다.

**실무 처방**: 재계산 비용을 실측해서 문서로 남깁니다. 「삭제 요청 1건 → Stat 재계산 N개 → 소요 M분」. 이 숫자 없이 SLA를 약속하면 지킬 수 없는 약속이 됩니다.

### 3.2 과거 스냅샷과의 불일치

더 다루기 까다로운 문제입니다. 재계산은 **「지금」의 값만 고칩니다.** 이미 밖으로 나간 과거의 값들은 그대로 남습니다.

| 어디에 남나 | 왜 못 고치나 |
|---|---|
| **월간 리포트 PDF / 슬라이드** | 이미 배포됐습니다. 사내 위키, 메일 첨부, 이사회 자료. |
| **시계열 테이블** | 「2026-03 결제팀 42건」이 행으로 박혀 있습니다. 시계열은 대개 append-only입니다. |
| **BI 캐시 / 머티리얼라이즈드 뷰** | 갱신 주기가 따로 돕니다. |
| **데이터 웨어하우스 스냅샷** | 일별 전체 복제본. 과거 파티션은 보통 불변으로 운영합니다. |
| **감사 로그에 기록된 집계값** | 지우면 감사 이력이 깨집니다(`ex2` 표의 「감사 이력이 유지된다」). |
| **백업** | `ex2` 표에서 **1·2·3번 모두 `✗`**. 완전 삭제만 ○이고, 실제로도 백업 삭제는 가장 어렵습니다. |

그리고 **여기서 딜레마가 생깁니다**.

- 과거 스냅샷도 고치면 → **역사가 바뀝니다.** 「그때 우리는 42를 보고 이 결정을 했다」가 재현 불가능해집니다. 감사 대상 시스템에서는 이게 더 큰 문제입니다.
- 과거 스냅샷을 안 고치면 → **삭제된 사람의 기여가 과거 값에 남습니다.** 지금 값(39)과 과거 값(42)이 다릅니다.

정답이 없습니다. 실무의 타협은 대개 이렇습니다.

1. **현재 값(라이브 집계)은 반드시 재계산한다.** 앞으로의 모든 판단이 여기서 나오므로.
2. **과거 스냅샷은 그대로 두되, 「어느 시점 이후 재계산됨」을 기록한다.** 두 값이 다른 이유를 설명할 수 있게 만듭니다.
3. **보존 기간(retention period)으로 자연 소멸시킨다.** 34장 키워드 표에 「보존 기간」이 들어 있는 이유입니다. 스냅샷을 영구 보관하지 않으면 문제는 시간이 지나며 사라집니다. — 지울 방법이 없으면 **애초에 오래 두지 않는 것**이 해법입니다(데이터 최소화의 시간축 버전).
4. **스냅샷에 개인 단위 데이터를 넣지 않는다.** 집계만 스냅샷하면 재식별 위험이 훨씬 낮습니다.

## 4. 재계산 자체가 삭제를 노출한다 — 차분 공격

여기가 「재계산이 정답」이라는 결론에 붙는 **가장 반직관적인 반전**입니다.

### 4.1 무슨 일이 벌어지나

집계를 성실하게 다시 센 결과, **그 변화가 삭제 사실을 폭로합니다.**

```
2026-03-01 대시보드:  결제팀 문서 42건, 인원 3명
2026-03-02 대시보드:  결제팀 문서 39건, 인원 2명
```

이 두 화면을 본 사람은 개인정보에 접근한 적이 없습니다. 그런데 압니다.

- 결제팀에서 **한 명이 빠졌다.**
- 그 사람은 문서를 **3건** 썼다.
- **어제와 오늘 사이에** 빠졌다.

그리고 결제팀에 누가 있었는지 아는 동료라면 **누구인지도** 압니다. 3명 중 2명이 남았으니까요.

이것을 **차분 공격(differential attack)** 이라고 합니다. 두 집계 결과의 **차이**에서 그 차이를 만든 한 사람의 정보를 복원하는 공격입니다. 「집계는 개인정보가 아니다」라는 전제가 무너지는 지점입니다. **집계 하나는 개인정보가 아니어도, 집계의 차이는 개인정보일 수 있습니다.**

### 4.2 왜 삭제 맥락에서 특히 나쁜가

일반적인 차분 공격은 「집계에 포함된 사람의 값」을 노출합니다. 삭제 맥락에서는 하나 더 노출됩니다 — **삭제 요청을 했다는 사실 자체**입니다.

이게 왜 민감한가:

- 「이 사람이 GDPR 삭제권을 행사했다」는 그 사람에 관한 사실이고, 대개 알리고 싶지 않은 사실입니다.
- 퇴사·탈퇴·계정 해지와 구별되지 않으므로, 「퇴사했다」로 잘못 읽히기도 합니다.
- **잊힐 권리를 행사한 흔적이 남는 것**은 잊힐 권리의 실패입니다. 삭제했다는 기록이 삭제 대상을 가리킵니다. `ex1`이 이미 같은 구조를 지적했습니다.

  > 3. 지운 «기록»이 남아야 한다.
  >    30장의 이벤트 로그에는 「p1 을 지웠다」가 남는다.
  >    그 기록 자체가 「p1 이 있었다」는 정보다.

  차분 공격은 이것의 **집계판**입니다. 이벤트 로그를 못 봐도 대시보드만 보면 알 수 있습니다.

### 4.3 소규모 집계에서 특히 위험하다

위험은 **집계 대상 인원(그룹 크기)** 에 반비례합니다.

| 그룹 크기 | 한 명이 빠졌을 때 | 위험 |
|---|---|---|
| 3명 → 2명 | 33% 감소. 누가 빠졌는지 후보가 3명 | **매우 높음** |
| 10명 → 9명 | 10% 감소. 눈에 보임 | 높음 |
| 1,000명 → 999명 | 0.1% 감소. 반올림에 묻힘 | 낮음 |
| 100만 → 999,999명 | 관측 불가 | 무시 가능 |

이것은 `ex3_reidentify.py`가 다룬 **k-익명성**과 같은 논리입니다. 「최소 그룹 크기가 작으면 이름을 지워도 지워진 게 아니다」의 시간축 버전이라고 볼 수 있습니다. 표의 k-익명성은 *한 시점의* 그룹 크기를 재고, 차분 공격은 *두 시점 사이의* 변화량을 봅니다.

그리고 34장의 집계 예시가 정확히 **소규모**입니다. `ex4`의 결제팀은 **3명**입니다. 「팀별 문서 수」는 팀 단위이므로 그룹이 작습니다. 세분화된 집계(팀별, 부서별, 지역별, 월별×직무별)는 거의 항상 소규모입니다. **집계를 잘게 자르면 자를수록 개인정보에 가까워집니다.**

### 4.4 대응

공공 통계 기관이 수십 년간 다뤄 온 문제이고(**statistical disclosure control**), 처방이 정리되어 있습니다.

| 대응 | 내용 | 대가 |
|---|---|---|
| **소표 억제 (small cell suppression)** | 집계 단위의 인원이 임계값(흔히 3~5) 미만이면 값을 아예 공개하지 않습니다. `*` 또는 「<5」로 표시. | 소규모 집단의 정보가 사라집니다. 그리고 **주변 셀과 합계로 역산**될 수 있어서 2차 억제(secondary suppression)까지 필요합니다. |
| **집계 단위 넓히기 (일반화)** | 팀별 대신 부서별, 일별 대신 월별. `ex3`의 일반화(generalization)와 같은 수단. | 분석 해상도 손실. |
| **반올림 / 구간화** | 42 대신 「40~45」. 1의 차이를 관측 불가로 만듭니다. | 정확도 손실. 시계열 추세도 뭉개집니다. |
| **잡음 추가 / 차분 프라이버시** | 집계에 통계적 잡음을 더해, 한 사람의 유무가 출력 분포를 거의 바꾸지 않게 만듭니다. 34장 키워드 표의 「차등 정보보호」. | 정확도 손실. 여러 번 질의하면 예산(ε)이 소모됩니다. 소규모 집계에서는 잡음이 값보다 커지기도 합니다. |
| **재계산 시점 흐리기** | 삭제를 모아 정기 배치로 반영하고, 여러 건을 한 번에 처리합니다. 한 번의 변화가 여러 사람의 합이 되어 개인을 특정하기 어려워집니다. | 삭제 반영이 늦어집니다(§3.1의 기한 문제와 상충). |
| **변화 이력 비공개** | 대시보드에 「전일 대비」를 표시하지 않고, 과거 스냅샷을 대조할 수 없게 합니다. | 운영상 필요한 추세 정보를 잃습니다. |

`ex3`의 결론이 여기서도 그대로 적용됩니다.

> 셋 다 «정확도를 내주고 익명성을 산다». 공짜가 아니다.

### 4.5 이 절의 요점

**「집계는 개인정보가 아니니 재계산하면 깔끔하다」가 아닙니다.** 재계산은 Stat 처리의 *정답*이지만, 그 정답을 실행하는 행위 자체가 새로운 노출 경로를 만듭니다. 삭제 파이프라인을 설계할 때는 「재계산했는가」에서 멈추지 말고 **「재계산 결과를 누가 보는가, 그 앞뒤를 대조할 수 있는가」** 까지 세어야 합니다.

이것이 34장이 「어느 수준도 전부를 만족하지 않는다」고 말하는 방식의 또 하나의 사례입니다. 대응 하나가 다른 곳에 구멍을 냅니다.

## 5. Event — 왜 「식별자 치환」인가

### 5.1 못 지우기 때문이다

`ex5`의 주석이 이유를 그대로 적어 뒀습니다: `"30장 — 이벤트는 못 지운다"`.

이벤트 로그(이벤트 소싱)는 **추가 전용(append-only)** 입니다. 이건 버그가 아니라 **그 구조의 존재 이유**입니다.

- 현재 상태는 **이벤트를 처음부터 재생(replay)해서** 만들어집니다. 중간 이벤트를 지우면 재생 결과가 달라집니다 — 즉 **과거가 바뀝니다**.
- 「왜 지금 이 상태인가」를 설명하는 근거가 로그입니다. 지우면 설명이 끊깁니다.
- 감사(audit)와 부인 방지(non-repudiation)의 기반입니다. 지울 수 있는 로그는 감사 증거가 되지 못합니다.
- 실무적으로도 물리 구조가 append-only입니다. Kafka 토픽, WAL, 추가 전용 파일. 중간을 도려내는 연산이 아예 없거나, 있어도 전체를 재작성해야 합니다.
- 하위 시스템(read model, 검색 색인, 데이터 웨어하우스, 스트림 소비자)이 이미 그 이벤트를 읽어 갔습니다. 로그에서 지운다고 그것들에서 지워지지 않습니다.

그래서 Event의 방침은 **「삭제」가 선택지에 없는 상태에서 고른 차선책**입니다. Stat이 「지울 수 있지만 지우면 안 되니까 재계산」이라면, Event는 **「지워야 할 것 같지만 지울 수 없으니 치환」** 입니다. 제약의 종류가 다릅니다.

### 5.2 식별자 치환이 성립하는 조건 — 설계가 먼저다

`ex5`의 결론 단락이 핵심입니다.

> 그리고 Event 를 보시라. «식별자 치환»이다. 지우는 게 아니다.
> 30장에서 이벤트 로그는 추가 전용이라 못 지운다고 했다.
> 그래서 이벤트에 개인정보를 «직접 안 넣는» 설계가 여기서 값을 한다.
> 식별자만 들어 있으면 그 식별자를 가리키는 표에서만 지우면 된다.

이벤트 본문이 이렇게 되어 있으면 손쓸 방법이 있습니다.

```
Event: { type: "MemberAdded", person: "p1", team: "t1", at: "2026-03-12T14:03Z" }
                                      ^^^^ 식별자만
```

`p1` 은 **그 자체로는 아무 뜻도 없는 문자열**입니다. 「p1이 누구인가」는 별도의 Person 표에만 있습니다. 그 표에서 p1의 행을 지우면(또는 이름을 `p-8f3a` 로 바꾸면), 이벤트 로그의 `p1` 은 **아무도 가리키지 않는 참조**가 됩니다.

- 이벤트는 그대로. 로그의 불변성이 유지됩니다.
- 재생해도 구조는 복원됩니다. 「누군가가 결제팀에 추가되었다」는 사실은 남습니다.
- 그런데 그 「누군가」를 사람 이름으로 되돌릴 수는 없습니다.

이 기법은 이름이 여럿입니다: **crypto-shredding**(식별자·본문을 사람별 키로 암호화하고 키를 파기), **tokenization / pseudonymisation**(식별자를 토큰으로), **외부 참조 삭제**(포인터는 남기고 대상만 지움). 어느 이름이든 원리는 같습니다 — **불변 저장소에는 손대지 않고, 그것이 가리키는 가변 저장소를 지운다.**

핵심은 이 방침이 **사후 처리가 아니라 사전 설계에 달려 있다**는 것입니다. 이벤트에 이렇게 넣어 뒀으면

```
Event: { type: "MemberAdded", name: "김도현", phone: "010-...", ... }
```

치환할 것이 없습니다. 지울 수 없는 곳에 개인정보가 평문으로 박혔고, 그건 되돌릴 수 없습니다. 그래서 34장 한 장 요약이 이렇게 적습니다.

> 이벤트 로그는 못 지우니 개인정보를 직접 넣지 마세요. 식별자만 넣고, 그 식별자를 가리키는 표에서 지웁니다.

**삭제 가능성은 삭제할 때 생기지 않고, 쓸 때 결정됩니다.**

### 5.3 표에서 봤던 자리

`ex2_delete_levels.py`의 「2. 식별자 끊기」와 정확히 같은 발상입니다.

> 「김도현」을 「p-8f3a」로 바꾼다. 사람은 못 알아보는데 구조는 남는다.
> 「결제팀에 3명이 있었다」는 유지되고 「그중 하나가 김도현」은 사라진다.

이벤트 로그에서는 이 방식이 **선택이 아니라 유일한 수단**입니다. 다른 노드 종류에서는 「완전 삭제」라는 더 강한 카드가 있지만, Event에는 없습니다.

## 6. Event 식별자 치환의 한계

### 6.1 이벤트의 «존재»가 정보다

`ex1`이 짚은 그대로입니다.

> 30장의 이벤트 로그에는 「p1 을 지웠다」가 남는다.
> 그 기록 자체가 「p1 이 있었다」는 정보다.

식별자를 치환해도 로그에는 이런 것이 남습니다.

- **한 개체가 존재했다** — 「누군가가 2026-03-12에 결제팀에 추가되었다」
- **그 개체가 삭제 요청을 했다** — 「p1 삭제 처리」 이벤트 자체
- **행동의 타임라인** — 언제 가입하고, 무엇을 하고, 언제 떠났는지의 전체 시퀀스

「누구인지」는 지웠는데 「존재했다는 것」과 「무엇을 했는지」는 남습니다. GDPR이 다루는 **δ-presence**(데이터셋에 존재한다는 사실 자체의 노출) 문제입니다.

### 6.2 관계와 타임라인으로 재식별된다

이것이 34장 전체의 주제와 만나는 지점입니다.

> 그래프에서는 *관계 자체가 식별자*입니다. 속성을 다 지워도 이웃 모양이 유일하면 특정돼요.

이벤트 로그는 사실상 **타임스탬프가 붙은 관계의 시퀀스**입니다. 식별자를 `p-8f3a` 로 바꿔도 이런 것이 남습니다.

- `2026-03-12 14:03` 에 결제팀에 추가됨 → 인사 발령 공고와 대조하면 한 명입니다.
- 같은 시각대에 다른 로그에도 같은 사건이 있으면 **타임스탬프로 조인**됩니다.
- 「이 팀에 속하고 저 문서를 만졌고 그 사람과 같은 회의에 있었다」는 **행동 패턴**이 유일하면 특정됩니다.

`ex3`의 절벽이 여기서도 작동합니다. 속성 넷을 조합하면 66%가 혼자가 됩니다. 이벤트 로그에는 조합할 것이 훨씬 많습니다 — 시각, 대상, 종류, 순서. **고차원 데이터라서 어떤 일반화로도 k를 못 채우는** 전형적인 사례입니다.

### 6.3 그 밖의 한계

| 한계 | 설명 |
|---|---|
| **매핑 표가 다시 만들어질 수 있다** | `p1 ↔ 김도현` 매핑이 백업, 개발 DB, 로그 파일, 스프레드시트 어딘가에 남아 있으면 치환은 무효입니다. 「어디에 매핑이 있는가」를 전부 알아야 합니다. |
| **가명화는 삭제가 아니다** | GDPR Art. 4는 **가명화된 데이터를 여전히 개인 데이터로 봅니다** — 되돌릴 수 있기 때문입니다. 「식별자 치환했으니 지웠다」는 법적으로 성립하지 않을 수 있습니다. 되돌릴 열쇠까지 파기해야 익명화(anonymisation)에 가까워집니다. |
| **하위 소비자에 전파되지 않는다** | 이벤트를 읽어 만든 read model, 검색 색인, 데이터 웨어하우스, 캐시에는 치환 전 값이 남아 있습니다. 로그를 고쳐도 자동으로 따라오지 않습니다. `ex1`이 든 다섯 곳(들어오는 엣지, 자유 텍스트, 이벤트 로그, 백업, 검색 색인)이 각각 별개의 작업입니다. |
| **이벤트 본문의 자유 텍스트** | 이벤트 payload에 코멘트, 메모, 메시지 본문이 들어 있으면 그 안의 이름은 식별자가 아니라 글입니다. 치환 대상이 아니라 **마스킹** 대상입니다(`Msg` 방침). 그리고 정규화되지 않았으므로 자동 처리가 어렵습니다. |
| **재생 결과가 달라질 수 있다** | 치환한 식별자로 replay할 때 참조 대상이 없어서 실패하는 로직이 있으면, 로그는 남았지만 재생은 못 하는 상태가 됩니다. 「참조가 끊긴 이벤트」를 다루는 처리를 미리 넣어 둬야 합니다. |
| **암호 파기의 유효기간** | crypto-shredding은 「키를 지웠으니 복호화 불가」에 의존합니다. 암호가 미래에 깨진다면 보장이 만료됩니다. |

## 7. 두 방침을 나란히 — 이 카드의 값어치

같은 표에 있는 두 줄이지만 서로 다른 종류의 교훈입니다.

**Stat = 「지울 수 있지만 지우면 안 되는 것」**
개인정보가 아니므로 지우면 과잉이고, 삭제된 사람의 기여가 남으면 미달입니다. 그 사이의 정답이 재계산입니다. 값은 비용·지연·과거 불일치, 그리고 재계산 결과 자체가 삭제를 폭로하는 차분 공격 위험입니다. **파생 데이터를 어떻게 다루는가**의 문제입니다.

**Event = 「지워야 할 것 같지만 지울 수 없는 것」**
불변성이 삭제를 금지하므로 치환이 유일한 수단입니다. 그리고 그 수단이 통하려면 **애초에 식별자만 넣어 뒀어야** 합니다. 존재 사실과 타임라인은 여전히 남고, 관계 재식별에 열려 있습니다. **불변 저장소에 무엇을 쓰는가**의 문제입니다.

공통점은 **둘 다 「삭제」가 답이 아니라는 것**입니다. 34장 `ex4`의 분류를 다시 보면:

```
개인을 특정하는 것   → 지운다              (Person, Contact)
그 사람이 만든 산출물 → 대개 남긴다 (작성자만 익명화)  (Doc, Run, Msg)
집계와 결정          → 남긴다              (Stat, Fact, Answer, Team)
못 지우는 것         → 참조만 끊는다        (Event)
```

Stat과 Event는 세 번째·네 번째 줄에 있습니다. **삭제 요청 하나를 처리하는 일에서 실제로 「지우는」 행위는 극히 일부**이고, 나머지는 재계산·익명화·마스킹·치환입니다. 그래서 방침 표가 필요합니다.

그리고 `ex5`의 진짜 메시지는 방침의 내용이 아니라 **표의 존재**입니다.

> 표가 없으면 어떻게 되나. 담당자가 그때그때 판단한다.
> 그리고 다음 요청이 오면 다른 담당자가 다르게 판단한다.
> 「지난번엔 지웠는데 이번엔 안 지웠다」가 되면 그게 더 큰 문제다.

`Photo` 에서 막히도록 일부러 만들어 둔 것도 같은 이유입니다. **「모르는 것을 모른다고」 말해 주고 멈추는 것**이 표의 값어치입니다.

## 8. 정리

| 질문 | 답 |
|---|---|
| Stat 방침은? | **재계산** — 집계는 남기되 다시 센다 |
| 왜 안 지우나? | 집계는 개인을 안 가리키므로 개인정보가 아님. 지우면 Fact·Answer·감사 이력·남의 이력이 깨진다 |
| 왜 그대로 두지도 않나? | 값 안에 삭제된 사람의 기여가 녹아 있다. 삭제 요청이 실질적으로 이행되지 않고, 집계가 원본과 어긋난다 |
| 왜 빼기가 아니라 다시 세기인가? | 빼려면 기여량을 알아야 하고(순환), 평균·distinct 등은 뺄 수 없다. 재계산은 멱등하다 |
| 재계산의 대가는? | 전체 스캔 비용, 배치 지연, 그리고 이미 배포된 과거 스냅샷·시계열·백업과의 불일치 |
| 재계산의 숨은 위험은? | **차분 공격** — 42→39, 3명→2명 이라는 변화가 「누가 빠졌고 몇 건 썼는지」를 폭로한다. 삭제권 행사 사실 자체가 노출된다 |
| 언제 특히 위험한가? | **소규모 집계**. 3명 팀에서 한 명이 빠지면 즉시 보인다. 집계를 잘게 자를수록 위험하다 |
| 차분 공격 대응은? | 소표 억제, 집계 단위 일반화, 반올림, 잡음/차분 프라이버시, 배치 묶기, 변화 이력 비공개 — 모두 정확도를 내준다 |
| Event 방침은? | **식별자 치환** — 30장대로 이벤트는 못 지운다 |
| 왜 못 지우나? | append-only. 지우면 재생 결과가 바뀌고 감사 근거가 끊긴다. 물리 구조상으로도 중간 삭제가 없다 |
| 어떻게 치환하나? | 이벤트에는 식별자(`p1`)만 두고, 그 식별자를 가리키는 표에서 지운다. 로그의 참조는 아무도 안 가리키는 문자열이 된다 |
| 성립 조건은? | **이벤트에 개인정보를 직접 안 넣는 설계.** 사후 처리가 아니라 사전 설계다 |
| 남는 한계는? | 존재 사실·타임라인은 남는다. 매핑 표가 다른 곳에 남으면 무효. 가명화는 법적으로 여전히 개인 데이터. read model·색인·백업에 전파되지 않는다. 관계 재식별에 열려 있다 |
| 두 방침의 차이는? | Stat은 「지울 수 있지만 지우면 안 됨」(의미론적 제약), Event는 「지워야 하지만 지울 수 없음」(구조적 제약) |
