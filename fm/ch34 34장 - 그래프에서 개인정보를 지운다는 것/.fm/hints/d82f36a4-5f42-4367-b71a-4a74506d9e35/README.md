# 실무에서 가장 많이 쓰이는 삭제 수준

**Q.** 실무에서 가장 많이 쓰이는 삭제 수준은 무엇인가?

**A.** **식별자 끊기(2번)** 다. `김도현` 을 `p-8f3a` 로 바꿔 사람은 못 알아보지만 구조는 남긴다.

---

## 1. 네 수준을 한 표에 놓으면

34.2절(`ex2_delete_levels.py`)은 「지운다」를 네 가지로 쪼갠다.

| # | 수준 | 하는 일 |
|---|---|---|
| 1 | 숨기기(soft delete) | `deleted=true` 플래그 |
| 2 | **식별자 끊기** | 이름·연락처를 지우고 대체 키만 남긴다 |
| 3 | 가명화 | 식별자를 **되돌릴 수 있는** 토큰으로 |
| 4 | 완전 삭제 | 노드·엣지·본문·백업까지 |

여덟 개 기준으로 채점한 결과가 이렇다.

| 기준 | 1 숨기기 | 2 식별자 끊기 | 3 가명화 | 4 완전 삭제 |
|---|:--:|:--:|:--:|:--:|
| 화면에서 안 보인다 | ○ | ○ | ○ | ○ |
| 이름으로 못 찾는다 | ✗ | ○ | ○ | ○ |
| 다른 데이터와 못 잇는다 | ✗ | ✗ | ✗ | ○ |
| 집계·통계가 유지된다 | ○ | ○ | ○ | ✗ |
| 감사 이력이 유지된다 | ○ | ○ | ○ | ✗ |
| 남의 이력이 안 깨진다 | ○ | ○ | ○ | ✗ |
| 되돌릴 수 있다 | ○ | ✗ | ○ | ✗ |
| 백업까지 지워진다 | ✗ | ✗ | ✗ | ○ |
| **만족한 기준 수** | **5** | **5** | **6** | **4** |

읽을 때 주의할 곳이 두 군데다.

- **4번이 제일 강해 보이는데 점수가 제일 낮다(4개).** 지우면 집계가 깨지고 감사 이력이 사라지고 남의 이력까지 같이 깨진다.
- **점수 1위는 3번(6개)인데 실무 기본값은 2번이다.** 3번이 2번보다 딱 하나 더 얻은 항목이 「되돌릴 수 있다」인데, **삭제 요구에 답하는 관점에서 그건 장점이 아니라 부채**다. 되돌릴 수 있다는 건 어딘가에 원본으로 가는 열쇠가 남아 있다는 뜻이고, 그 상태로는 「지웠습니다」라고 말하기 어렵다. 점수 합계가 많은 칸이 정답이 아니라는 게 이 표의 진짜 요점이다.

## 2. 왜 2번이 실무 기본값이 되는가

### (1) 삭제 요구의 실질을 상당 부분 충족한다

삭제 요구의 핵심은 「그 데이터가 **나를 가리키지 않게** 해 달라」다. 이름·연락처·프로필처럼 사람을 직접 가리키는 필드를 끊으면 그 요구의 중심은 충족된다.
`김도현` → `p-8f3a` 로 바꾸면 **「결제팀에 3명이 있었다」는 유지되고 「그중 하나가 김도현」은 사라진다.**

### (2) 집계·통계가 살아남는다

34.4절(`ex4_cascade.py`)의 경로를 보라.

```
김도현 → 3분기 보고서 → 팀별 문서 수 → 「결제팀은 문서 생산이 많다」
       → 「결제팀에 리소스를 더 배정하자」
```

완전 삭제를 하면 문서가 사라지고 집계가 바뀌고, 집계가 바뀌면 그 위의 판단이 근거를 잃는다(28장 연쇄 철회와 같은 구조). 그런데 **집계는 개인정보가 아니고, 결정은 회사의 기록이다.** 지울 이유가 없는 것을 지우는 대가로 삭제를 완수하는 건 손해다. 식별자만 끊으면 문서 수는 그대로, 작성자만 익명이 된다.

### (3) 감사 이력이 유지된다

「이 승인은 누가 했나」는 규제·내부통제상 남겨야 하는 경우가 많다. 노드를 지우면 승인 엣지가 끊기고, 감사 관점에서 「승인자 없는 승인」이 생긴다. 식별자만 끊으면 **「같은 사람이 두 건을 승인했다」는 여전히 참**이고 그 사람이 누구인지만 사라진다. 이 「동일인 여부는 유지, 신원은 소실」이 감사가 요구하는 최소선과 삭제 요구를 동시에 만족시키는 지점이다.

### (4) 남의 이력을 안 깬다 — 그래프에서 특히 크다

`ex1_delete_scope.py` 의 엣지 목록에 `("p2", "p1", "멘토")` 가 있다. **「이서연이 김도현의 멘티였다」는 이서연 쪽 사실이기도 하다.** p1 노드를 지우면 이서연의 이력이 같이 사라진다. `("r1", "p1", "읽음")` 같은 들어오는 엣지도 마찬가지다.
식별자 끊기는 **노드를 남기므로 들어오는 엣지가 살아 있다.** 관계형 DB라면 「그 행 지우면 끝」에 가깝지만 그래프에서는 들어오는 엣지가 남의 자산이라, 노드를 보존하는 2번이 구조적으로 안전하다.

### (5) 되돌리기 위험이 없고, 운영 비용이 낮다

원자적으로 몇 개 필드를 UPDATE 하는 일이라 초 단위로 끝난다. 백업 복원·재계산·색인 재구축 같은 대공사가 필요한 4번과 비교가 안 된다.

### 결론적으로 저자의 실무 분기

- **기본은 2번.** 식별자를 끊고 구조는 남긴다.
- **법적 요구가 명시적이면 4번.** 다만 「무엇이 깨지는지」 먼저 목록으로 만든다.
- **실수 대비가 필요하면 3번.** 되돌릴 수 있게 토큰을 따로 보관한다.
- **1번은 「지운 것」이 아니다.** 그런데 많은 시스템이 1번만 하고 지웠다고 한다.

## 3. 구현 방법

### 3-1. 표시 필드 제거/치환

사람을 **직접** 가리키는 필드가 대상이다.

| 필드 종류 | 처리 |
|---|---|
| `name`, `display_name` | `p-8f3a` 같은 비의미 라벨로 치환 |
| `email`, `phone`, 주소 | 제거(null). 치환도 필요 없다 |
| 프로필 사진, 서명 이미지 | 제거 |
| 생년월일, 사번 | 제거 또는 일반화(연도만, 구간만) |
| 자유 텍스트 본문 | **마스킹** — `ex5` 의 `Msg: 본문 마스킹` |

자유 텍스트를 잊지 말 것. `ex1` 에서 p1 노드를 지운 뒤에도 `m1 = "김도현: 마포에서 봐요"` 에 이름이 그대로 남는다. 정규화된 필드가 아니라 그냥 글이라 스키마로 못 찾는다. 발화·문서 본문·요약·커밋 메시지·자동 생성 리포트가 전부 여기 해당한다.

### 3-2. 노드 id는 유지하거나 랜덤 토큰으로 교체

두 갈래다.

**(a) 내부 대체 키(surrogate key)를 그대로 유지** — `p1` 은 그대로 두고 라벨만 바꾼다.
- 장점: 엣지 무결성이 안 깨지고, 집계·감사·남의 이력이 전부 그대로다. 재작성해야 할 참조가 없다.
- 전제: **그 id가 자연키가 아닐 것.** 사번·이메일·전화번호·`sha256(email)` 을 PK로 쓰고 있었다면 id 자체가 개인정보이므로 유지하면 안 되고, 이 지점에서 2번 전략이 통째로 무너진다. 5장 「문자열이 아니라 사물」의 값어치가 여기서 회수된다 — 처음부터 의미 없는 id를 썼으면 이 문제가 없다.

**(b) 랜덤 토큰으로 교체** — `p1` → `p-8f3a`.
- 필요한 경우: id가 자연키였을 때, 혹은 외부로 내보내는 export·다른 시스템 이관·분석용 사본을 만들 때.
- 토큰은 **CSPRNG로 뽑는다**(예: `secrets.token_hex`). 카운터나 원본에서 유도한 값은 쓰지 않는다.
- 교체하면 해당 노드를 가리키는 **모든 참조를 같이 갱신**해야 한다 — 엣지, 이벤트 로그의 `actor_id`, 캐시, 읽기 모델, 검색 색인 문서 id.

### 3-3. 되돌릴 수 없게 만드는 조건

「식별자 끊기」와 「가명화」를 가르는 지점이 정확히 여기다. 다음이 전부 성립해야 되돌릴 수 없다.

1. **매핑 표를 파기한다.** `p-8f3a ↔ 김도현` 표, 키, 솔트, 그 표의 백업까지. 하나라도 남아 있으면 그건 3번(가명화)이다.
2. **결정론적 해시를 식별자로 쓰지 않는다.** `sha256(email)` 은 되돌릴 수 있다 — 후보 집합(이메일·전화번호)이 작고 규칙적이라 무차별 대입으로 몇 분 안에 복원된다. 솔트를 넣어도 **솔트가 남아 있으면 같은 문제**다. 솔트를 쓰고 파기하는 방식은 가능하지만, 그러면 재현이 안 되므로 애초에 랜덤 토큰과 다를 게 없다.
3. **원본이 남는 다섯 곳을 같이 처리한다.**
   - 들어오는 엣지 — 엣지 속성에 이름이 들어 있는지 확인
   - 자유 텍스트 본문 — 마스킹
   - 이벤트 로그 — 추가 전용이라 못 지운다. **식별자 치환**으로 처리하거나, 처음부터 개인정보를 직접 넣지 않는 설계(30장)로 회피
   - 백업·스냅샷·WAL — 즉시 못 지운다. 보존 기간 만료를 기다리거나 복원 시 재적용 절차를 문서로 둔다
   - 검색 색인 — 재구축. 색인은 원본 문자열을 자기 안에 복사해 갖고 있다
4. **캐시·CDN·읽기 모델·머티리얼라이즈드 뷰를 무효화한다.** 여기 남은 옛 라벨은 사실상 매핑 표와 같은 역할을 한다.
5. **재식별 검증을 통과한다.** 남은 속성 조합으로 k=1이 나오면 이름을 지웠어도 지운 게 아니다(다음 절).

법적 관점의 참고: GDPR 4조 5항의 **가명화된 데이터는 여전히 개인정보**다. 추가 정보(매핑)를 써서 다시 사람에게 귀속시킬 수 있기 때문이다. 개인정보 범위를 벗어난 **익명화**로 인정받으려면 되돌릴 수 없어야 한다. 즉 실무에서 「2번으로 처리했다」고 주장하려면 **매핑을 파기했다는 사실 자체가 증거로 남아 있어야** 한다. 매핑을 지웠다는 기록은 남기고, 매핑 내용은 남기지 않는다.

## 4. 가명화(3번)와의 차이 — 한 줄로

> **같은 연산이고, 부산물을 보관하느냐만 다르다.**

| | 2. 식별자 끊기 | 3. 가명화 |
|---|---|---|
| 하는 일 | 이름 → `p-8f3a` | 이름 → `p-8f3a` |
| 매핑 표 | **파기** | **보존**(분리 보관) |
| 되돌릴 수 있다 | ✗ | ○ |
| 쓰는 이유 | 삭제 요구 대응 | 오삭제 복구, 이의 처리, 재연결 필요 |
| 남는 위험 | 잘못 지우면 복구 불가 | 매핑 표가 새면 전부 복원됨 |

바꿔 말하면 **가명화는 아직 삭제가 끝나지 않은 중간 상태**다. 「실수 대비가 필요하면 3번」이라는 저자의 분기는, 유예 기간 동안 3번으로 두었다가 기간이 지나면 매핑을 파기해 2번으로 승격시키는 운영과 잘 맞는다. 이때 반드시 **파기 시점을 미리 정하고(보존 기간) 실제로 실행됐는지 검사 가능하게** 해 둔다. 「나중에 지우자」로 남은 매핑 표가 사고의 단골 원인이다.

## 5. 한계 — 2번의 ✗ 칸들

### (1) 「다른 데이터와 못 잇는다」가 ✗ — 재식별

이름을 지워도 「2026년 3월 12일 14시 3분에 마포에서 결제」 같은 조합이 남아 있으면 사람을 특정할 수 있다. `ex3_reidentify.py` 가 5,000명으로 실측한 결과다.

| 조합 | 최소 그룹(k) | 혼자인 사람 |
|---|--:|--:|
| team | 큰 값(팀당 105명 규모) | 0% |
| team + city | | |
| team + city + role | 1 | 30명 (0.6%) |
| team + city + role + joined | 1 | **65.8%** |
| + birth_month | 1 | **96.3%** |

**셋에서 넷으로 갈 때 0.6% → 65.8% 로 뛴다.** 속성 하나 추가가 두 배가 아니라 백 배로 작동한다 — 조합 수가 곱해지기 때문이다. 즉 **식별자 끊기만으로는 부족하고, 「몇 개를 조합하면 한 사람으로 좁혀지나」(k-익명성)를 세야 한다.** 이 값이 작으면 이름을 지워도 지운 게 아니다.

대응은 셋이고, **셋 다 정확도를 내주고 익명성을 산다.**
- **일반화(generalization)** — 「2019년 입사」를 「2015~2020년」으로 뭉갠다
- **억제(suppression)** — 혼자인 사람의 그 속성을 아예 뺀다
- **잡음(noise)** — 생월을 무작위로 ±2 흔든다

### (2) 그래프 고유의 한계 — 관계 자체가 식별자

속성을 전부 지워도 「이 사람은 이 팀에 속하고 저 문서를 작성했고 그 사람의 멘티다」라는 **모양**이 남는다. 그 모양이 유일하면 특정된다. 그래서 그래프 익명화는 속성만 지워서는 안 되고 **엣지의 조합**도 봐야 하는데, **이건 아직 제대로 된 해법이 없다.** 2번이 「구조는 남긴다」로 얻는 이점이 바로 여기서 위험이 된다.

### (3) 「백업까지 지워진다」가 ✗

백업·스냅샷·이벤트 로그에는 옛 라벨이 남는다. 보존 기간이 지나기 전에는 「완전히 지웠다」고 말할 수 없다.

### (4) 되돌릴 수 없다 — 오삭제가 곧 사고

2번의 `되돌릴 수 있다 ✗` 는 양날이다. 잘못된 대상에 적용하면 복구할 방법이 없다.

### (5) 판정을 자동화할 수 없다

**경계는 「그것이 개인을 가리키는가」다.** 「3분기 보고서」는 개인을 안 가리키고 「김도현이 작성」이 가리킨다. 그러니 문서는 두고 엣지의 작성자만 익명 노드로 바꾼다.
이 판정은 자동으로 못 하므로 **노드 종류별 방침 표**를 사람이 정해 둔다(`ex5_deletion_plan.py`).

| 종류 | 방침 | 이유 |
|---|---|---|
| Person / Contact | 삭제 | 개인 그 자체 / 연락처 |
| Msg | 본문 마스킹 | 발화 — 이름·연락처만 가린다 |
| Doc | 작성자 익명화 | 산출물은 회사 자산 |
| Team | 유지 | 개인정보 아님 |
| Stat | 재계산 | 집계는 남기되 다시 센다 |
| Fact / Answer | 유지 | 개인을 안 가리키면 / 회사의 결정 기록 |
| Run | 행위자 익명화 | 누가 돌렸는지만 가린다 |
| Event | 식별자 치환 | 30장 — 이벤트는 못 지운다 |

표에 없는 종류(`Photo`)가 나오면 **자동 처리하지 않고 멈춘다.** 「모르는 것을 모른다」고 말해 주는 게 이 표의 값어치다. 표가 없으면 담당자마다 다르게 판단하고, 「지난번엔 지웠는데 이번엔 안 지웠다」가 더 큰 문제가 된다.

### (6) 「완료」에는 며칠이 걸린다

식별자 치환 자체는 초 단위인데, 재계산 + 백업 + 사람 확인까지 합치면 전체는 며칠이다. 「30일 안에 처리」 같은 약속을 하려면 이 절차의 실제 소요를 미리 재 둬야 한다.

---

## 6. 한 문장으로

> 실무 기본값은 **2번 식별자 끊기**다. **집계·감사·남의 이력·구조를 살린 채 「누구인지」만 지우는 유일한 수준**이기 때문이다. 3번과의 차이는 연산이 아니라 **매핑 표를 파기했는가**이고, 2번의 남은 구멍은 **재식별(속성 조합 + 이웃 모양)과 백업**이다.
