# 영향 범위 쿼리에 '이서연'이 걸린 것은 무엇을 뜻하는가?

> **답**: 같은 팀이라는 이유로 걸렸으며 명백히 지워서는 안 된다. 쿼리는 영향 범위만 보여 주고 무엇을 지울지는 따로 정해야 한다.

---

## 1. 무슨 상황인가

「김도현(p1)을 지워 주세요」라는 삭제 요청이 들어왔습니다. 지우기 전에 당연히 물어야 할 것이 있습니다. **이걸 지우면 무엇이 같이 흔들리나?** 34.4절의 `ex4_cascade.py`가 그 계산을 합니다.

그래프는 이렇게 생겼습니다.

```
p1 김도현 ─[속함]→ t1 결제팀 ←[속함]─ p2 이서연
    │
    └─[작성]→ d1 3분기 보고서 ←[집계함]─ s1 팀별 문서 수
                                            ↑[기댐]
                                        f1 결제팀은 문서 생산이 많다
                                            ↑[기댐]
                                        a1 결제팀에 리소스를 더 배정하자
                                            ↑[생성함]
                                        r1 분기 분석 #901
```

영향 범위 쿼리는 두 단계로 셉니다.

```cypher
-- 직접 이어진 것
MATCH (a:N {id:'p1'})-[e:R]->(b:N) RETURN b.id, b.kind, b.label

-- 그것에 기대고 있는 것
MATCH (x:N)-[:R*1..5]->(d:N)<-[:R]-(p:N {id:'p1'})
WHERE x.id <> 'p1'
RETURN DISTINCT x.id, x.kind, x.label
```

결과는 직접 2개 + 간접 5개 = **일곱 개**. 그 일곱 개 안에 `p2 이서연`이 들어 있습니다.

## 2. 이서연은 왜 걸렸나 — 허브를 경유한 경로

두 번째 쿼리의 패턴을 그림으로 풀면 이렇습니다.

```
x ──*1..5──→ d ←── p1
             ↑
        만나는 지점(d)만 같으면 x는 걸린다
```

즉 「p1이 가리키는 어떤 노드 `d`에, `x`도 (1~5홉 안에) 도달하는가」를 묻습니다. 이서연에 대해 실제로 매칭된 경로는 딱 이 한 줄입니다.

```
p2 이서연 ─[속함]→ t1 결제팀 ←[속함]─ p1 김도현
```

**같은 팀 노드를 공유한다** — 이게 이서연이 걸린 이유의 전부입니다. 김도현과 이서연 사이에는 개인정보 삭제와 관련된 어떤 관계도 없습니다. 그냥 둘 다 결제팀에 속해 있을 뿐입니다.

### 팀 노드는 허브다

`Team`, `조직`, `태그`, `카테고리`, `국가`, `공용 문서` 같은 노드는 **들어오는 엣지가 아주 많은 허브**입니다. 결제팀에 100명이 속해 있으면, 팀 노드를 경유해도 된다고 허용하는 순간 그 100명이 전부 영향 범위에 들어옵니다. 홉을 하나 더 늘리면 「그 100명이 쓴 문서 전부」가 따라옵니다.

이게 그래프 탐색의 고전적인 사고입니다. **허브 하나를 통과시키면 그래프의 상당 부분이 연결된 것으로 판정됩니다.** 소셜 그래프에서 6단계면 거의 모두가 이어진다는 이야기와 같은 현상이고, 여기서는 t1 하나로 2단계에 벌어집니다.

### 도달 가능성(reachability) ≠ 삭제 대상

핵심은 이겁니다.

| | 뜻 |
|---|---|
| 도달 가능성 | 그래프 위에서 경로가 존재한다 |
| 삭제 대상 | 그 노드가 이 개인을 가리킨다 |

둘은 다른 질문입니다. 그런데 `[:R*1..5]` 같은 가변 길이 탐색은 **엣지의 방향과 의미를 사실상 무시**합니다. 위 쿼리에서 `x → d ← p1`은 화살표가 서로 마주 보는 V자 패턴이라 「p1에서 x로 가는 경로」가 아예 없어도 매칭됩니다. 그리고 `속함`, `작성`, `집계함`, `기댐`, `생성함`이 전부 같은 `R` 테이블에 `kind` 속성으로만 구분돼 있으니, 탐색은 「소속」과 「의존」과 「저작」을 똑같이 한 홉으로 셉니다.

의미를 무시하고 세면 **남의 데이터까지 끌려옵니다.**

- 이서연 → 남의 개인정보. 지우면 오히려 그쪽의 삭제권을 침해합니다.
- s1 팀별 문서 수 → 집계. 개인정보가 아닙니다.
- f1 / a1 → 회사가 내린 판단과 결정 기록. 지우면 안 됩니다.
- r1 → 실행 이력. 행위자만 가릴 대상입니다.

일곱 개 중 진짜 삭제 대상은 사실상 p1 하나이고, d1은 「작성자만 익명화」입니다. 나머지는 남깁니다.

### 그래도 이 쿼리는 왜 돌리나

이서연이 걸린 게 버그라서 쿼리를 버려야 한다는 뜻이 아닙니다. 이 쿼리는 원래 **넉넉하게(over-approximate) 잡도록** 만든 겁니다. 놓치는 것보다 과하게 잡는 편이 안전하니까요. 특히 아래 경로는 이 쿼리 없이는 절대 눈에 안 띕니다.

```
김도현 → 3분기 보고서 → 팀별 문서 수 → 결제팀은 문서 생산이 많다
       → 결제팀에 리소스를 더 배정하자
```

김도현이 쓴 문서를 지우면 집계가 바뀌고, 집계가 바뀌면 그 위의 판단이 근거를 잃습니다. 28장의 연쇄 철회와 같은 구조입니다. 이런 파급을 미리 세려면 넓게 잡는 탐색이 필요합니다. 넓게 잡는 대가로 이서연이 섞여 들어오는 것이고, **그 대가는 다음 단계에서 걸러 내야 합니다.**

## 3. 그래서 필요한 것 세 가지

### (1) 엣지 타입별 전파 규칙

「몇 홉」이 아니라 **「어떤 엣지를 타고 갈 수 있나」**로 제한해야 합니다. 방향과 의미를 살려서 씁니다.

| 엣지 | 전파 | 이유 |
|---|---|---|
| `작성`, `발화`, `승인` (사람 → 산출물) | 전파 O — 단 「작성자만 익명화」 대상으로 | 개인이 산출물에 남긴 흔적 |
| `속함`, `이끔` (사람 → 팀) | **전파 X (허브)** | 소속을 타면 팀원 전부가 끌려온다 |
| `언급` (문서 → 사람) | 전파 O — 본문 마스킹 대상 | 자유 텍스트 안의 이름 |
| `멘토` (남 → 나) | 전파 O — 단 **남의 이력**으로 표시 | 이서연 쪽 사실이기도 하다 |
| `집계함`, `기댐` (분석 의존) | 전파 O — 단 「재계산」 대상 | 삭제가 아니라 다시 세는 것 |
| `읽음`, `생성함` (실행 이력) | 전파 O — 행위자 익명화 대상 | 29·30장의 Run/Event |

바꿔 말하면, `[:R*1..5]`처럼 뭉뚱그린 탐색 대신 엣지 `kind`별로 화이트리스트를 두고, 허브를 만드는 엣지(`속함`)는 **경유 금지**로 못 박습니다. 그리고 잡힌 각 노드에는 「어떤 경로로 걸렸는지」를 같이 남겨야 합니다. 경로가 없으면 「왜 이서연이 여기 있지?」를 사람이 판단할 수 없습니다.

### (2) 노드 종류별 방침 표 (`ex5_deletion_plan.py`)

전파 규칙으로 걸러도 판정은 남습니다. 판정은 자동으로 못 합니다. **노드 종류마다 사람이 미리 정해 둔 표**가 있어야 합니다.

| 종류 | 방침 | 이유 |
|---|---|---|
| `Person` | 삭제 | 개인 그 자체 |
| `Contact` | 삭제 | 연락처 |
| `Msg` | 본문 마스킹 | 발화 — 이름·연락처만 가린다 |
| `Doc` | 작성자 익명화 | 산출물은 회사 자산 |
| `Team` | 유지 | 개인정보 아님 |
| `Stat` | 재계산 | 집계는 남기되 다시 센다 |
| `Fact` | 유지 | 개인을 안 가리키면 |
| `Answer` | 유지 | 회사의 결정 기록 |
| `Run` | 행위자 익명화 | 누가 돌렸는지만 가린다 |
| `Event` | 식별자 치환 | 30장 — 이벤트는 못 지운다 |

방침을 정할 때 묻는 질문은 하나입니다.

> **이 노드가 개인을 가리키는가, 아니면 개인이 만든 것인가?**
> 가리키면 지우고, 만든 것이면 「만든 사람만」 지운다.

「3분기 보고서」는 개인을 안 가리킵니다. 「김도현이 작성」이 가리킵니다. 그러니 문서는 두고 엣지의 작성자만 익명 노드로 바꿉니다.

그리고 `ex5`는 일부러 `Photo`(회식 사진)에서 막히게 해 두었습니다. 표에 없는 종류는 자동 처리하지 않고 **멈춥니다**. 「모르는 것을 모른다고」 말해 주는 게 이 표의 값어치입니다. 표가 없으면 담당자가 그때그때 판단하고, 다음 요청은 다른 담당자가 다르게 판단합니다. 「지난번엔 지웠는데 이번엔 안 지웠다」가 되면 그게 더 큰 문제입니다.

### (3) 사람 확인 단계

이서연이 걸린 사례가 정확히 이 단계가 필요한 이유입니다. 표에 방침이 있어도, 「남의 개인정보인데 이 요청 때문에 걸려 들어온 것」은 사람이 봐야 합니다. 그래서 삭제 절차는 초 단위가 아니라 **며칠 걸립니다.** 재계산이 있고, 백업이 있고, 사람 확인이 있습니다. 「30일 안에 처리」 같은 약속을 하려면 이 절차의 실제 소요를 재 둬야 합니다.

## 4. 한 줄 원칙

> **탐색 결과 = 검토 목록. 삭제 목록이 아니다.**

영향 범위 쿼리의 출력은 「지울 것들」이 아니고 **「사람이 방침 표에 통과시켜 볼 것들」**입니다. 파이프라인으로 쓰면 이렇게 됩니다.

```
삭제 요청
   ↓
영향 범위 탐색 (넓게 잡는다 — 놓치지 않기 위해)   → 7개
   ↓
엣지 타입별 전파 규칙으로 걸러낸다 (허브 경유 차단)
   ↓
노드 종류별 방침 표에 통과시킨다 (모르면 멈춤)
   ↓
사람 확인 (특히 남의 개인정보가 섞였는지)
   ↓
실행: 삭제 / 마스킹 / 익명화 / 재계산 / 식별자 치환
```

「이어진 것을 전부 지운다」는 답이 아닙니다. 그건 삭제권을 지키려다 남의 삭제권과 회사의 감사 이력을 동시에 부수는 일입니다.

## 되짚어 보기

- 이서연은 김도현과 **`속함` 엣지로 팀 노드를 공유했다**는 이유만으로 걸렸다. 둘 사이에 직접 관계는 없다.
- 허브 노드(팀)를 경유 허용하면 무관한 사람 전원이 끌려온다. 도달 가능성은 삭제 근거가 아니다.
- 가변 길이 탐색은 엣지의 방향·의미를 무시하므로 남의 데이터·집계·결정까지 함께 끌어온다.
- 필요한 것은 엣지 타입별 전파 규칙, 노드 종류별 방침 표, 그리고 사람 확인 단계.
- 경계는 하나: **그것이 개인을 가리키는가.**
