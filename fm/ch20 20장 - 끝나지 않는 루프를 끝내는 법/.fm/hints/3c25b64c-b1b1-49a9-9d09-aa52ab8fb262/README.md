# 횟수 상한만 있을 때 '천천히 나아진다' 시나리오의 문제

**질문** — 횟수 상한만 있을 때 '천천히 나아진다' 시나리오의 문제는 무엇인가?

**답** — 더 돌리면 될 텐데 상한에 걸려 못 돌린다. 즉 상한이 성공을 막을 수도 있다.

---

## 한 줄로

상한은 「나쁜 루프를 끊는 장치」로만 생각하기 쉽지만, **잘 굴러가는 루프를 성공 직전에 끊어 버리는 장치**이기도 하다. 「천천히 나아진다」는 그 반대 방향의 실패를 보여주려고 만든 시나리오다.

## 시나리오 원문 (`ex1_four_guards.py`)

```python
SCENARIOS = {
    "잘 수렴한다":     [(20, 10, 5), (20, 10, 2), (20, 10, 0)],
    "천천히 나아진다":  [(20, 10, 9), (20, 10, 8), (20, 10, 7),
                       (20, 10, 6), (20, 10, 5), (20, 10, 4)],
    ...
}
```

튜플은 `(비용, 초, 점수)`이고 **점수는 위반 건수라서 낮을수록 좋다.** 0이 되면 성공이다.

기본 가드는 `guards.py`의 `Guards` 기본값을 쓴다.

```python
max_rounds: int = 5
max_cost: float = 100.0
max_seconds: float = 120.0
stall_limit: int = 2
```

## 회차별 진행과 상한 도달 지점

| 회차 | 점수(위반) | 누적 비용 | 누적 초 | 정체인가 | `check()` 결과 |
|---:|---:|---:|---:|:--|:--|
| 1 | 9 | 20 | 10 | 아니오 | None |
| 2 | 8 | 40 | 20 | 아니오 | None |
| 3 | 7 | 60 | 30 | 아니오 | None |
| 4 | 6 | 80 | 40 | 아니오 | None |
| 5 | **5** | 100 | 50 | 아니오 | **「횟수 상한」 ← 여기서 끝난다** |
| ~~6~~ | ~~4~~ | — | — | — | 아예 실행되지 않음 |

`ex1_four_guards.py`의 출력 한 줄로 보면 이렇다.

```
천천히 나아진다   횟수 상한      5     100      50          5
```

읽는 법이 중요하다.

- **매 회차 점수가 9 → 8 → 7 → 6 → 5 로 꼬박꼬박 1씩 줄었다.** 한 번도 정체한 적이 없다. `Guards.stalled()`는 끝까지 `False`였다.
- 그런데 5회차에서 `rounds >= max_rounds(5)`가 참이 되어 「횟수 상한」으로 종료된다.
- 마지막 점수는 5. **성공(0)까지는 아직 다섯 번이 더 남았는데, 입력에 준비된 6회차(점수 4)조차 실행되지 못했다.**

`main()`의 해설이 정확히 이 대목을 가리킨다.

```
«천천히 나아진다» — 횟수 상한에 걸린다. 더 돌리면 될 텐데 못 돌린다
```

## 그래서 문제가 무엇인가

**상한이 실패를 막은 게 아니라 성공을 막았다.** 이 루프는 고장 난 루프가 아니다. 방향도 맞고 속도도 일정하다. 다만 **필요한 회차가 상한보다 컸을 뿐**이다.

`max_rounds`를 올려 가며 같은 진행(9 → 0)을 돌려 보면 이게 순수한 상한 문제였음이 드러난다.

| `max_rounds` | 끝난 이유 | 회차 | 마지막 점수 |
|---:|:--|---:|---:|
| 5 | 횟수 상한 | 5 | 5 |
| 6 | 횟수 상한 | 6 | 4 |
| 8 | 횟수 상한 | 8 | 2 |
| 9 | 횟수 상한 | 9 | 1 |
| **10** | **성공** | 10 | **0** |

루프 자체는 멀쩡했다. 상한 숫자 하나가 결과를 갈랐다.

### 곁가지 하나 — 5회차에서는 예산도 동시에 걸린다

5회차 누적 비용은 정확히 100이고 `max_cost`도 100이다. 즉 `rounds >= max_rounds`와 `cost >= max_cost`가 같은 시점에 참이 된다. `check()`가 횟수를 먼저 검사하기 때문에 「횟수 상한」이 나올 뿐이다.

```python
def check(self):
    if self.rounds >= self.max_rounds:   # 먼저 걸린다
        return "횟수 상한"
    if self.cost >= self.max_cost:
        return "예산 상한"
    ...
```

여기서 얻을 교훈이 하나 더 있다. **끝난 이유는 「가장 먼저 검사한 조건」이지 「가장 본질적인 원인」이 아닐 수 있다.** 이 경우 회차 상한만 올리면 예산 상한이 곧바로 뒤를 이어 막는다. 상한을 올릴 때는 한 축만 올리면 안 된다는 뜻이다.

## 「상한」과 「정체」는 대응이 다르다

`ex4_generator_critic.py`가 이 구분을 상태에 남기는 이유가 여기 있다. 종료 이유를 불리언 하나(`done: True/False`)로 두면 아래 구분이 통째로 사라진다.

```python
class S(TypedDict):
    ...
    ending:  str          # 어떤 이유로 끝났는지. 이게 중요하다.
```

```python
def route(s: S) -> str:
    if not s["missing"]:            return "성공"
    if s["rounds"] >= MAX_ROUNDS:   return "상한"
    if s["cost"] >= MAX_COST:       return "예산"
    if stalled(s["scores"]):        return "정체"
    return "생성"
```

`ex4`의 결론 문구가 대응표다.

```
  성공 — 그대로 쓴다
  상한 — 사람에게 넘긴다 (더 돌리면 될 수도 있다)
  예산 — 예산을 올릴지 물어본다
  정체 — 사람에게 넘긴다 (더 돌려도 안 된다)

«상한»과 «정체»의 대응이 다르다. 불리언 하나로는 이 구분이 안 된다.
```

정리하면 이렇다.

| | 「상한」으로 끝남 (천천히 나아진다) | 「정체」로 끝남 (제자리걸음) |
|---|---|---|
| 점수 이력 | 9, 8, 7, 6, 5 — 계속 좋아지는 중 | 3, 3, 3 — 두 번 연속 안 좋아짐 |
| 남은 진전 여지 | **있다.** 더 돌리면 0에 닿는다 | **없다고 봐야 한다.** 더 돌려도 3이다 |
| 1차 대응 | **상한 상향 후 재개** — 회차/예산을 함께 올려 이어서 돌린다 | **재개는 무의미.** 같은 조건으로 다시 돌리면 같은 결과 |
| 사람에게 넘길 때 | 「예산만 더 주면 끝날 것 같습니다. 계속할까요?」 — 판단은 예산 결정 | 「접근 자체가 막혔습니다」 — 판단은 프롬프트·도구·설계 변경 |
| 재개 시 필요한 것 | 이전 회차/비용 누적이 **상태에 남아 있어야** 한다 (전역 예산을 상태에 두라는 이유) | 재개보다 입력을 바꾸는 게 먼저 |

즉 **「상한」은 자원 부족 신호, 「정체」는 능력 부족 신호**다. 둘 다 「사람에게 넘긴다」로 보일 수 있지만 사람에게 넘기며 물어보는 질문이 다르다. 상한은 「더 줄까요?」, 정체는 「다른 방법으로 갈까요?」다.

## 대비: 「제자리걸음」은 정반대 문제

같은 `ex1`의 「제자리걸음」 시나리오는 `[(20,10,3)] * 4`다.

| 회차 | 점수 | 누적 비용 | `stalled()` | 결과 |
|---:|---:|---:|:--|:--|
| 1 | 3 | 20 | False | None |
| 2 | 3 | 40 | False | None |
| 3 | 3 | 60 | **True** | **「진전 없음」** |

`stall_limit=2`이므로 최근 3개 점수 `[3, 3, 3]`을 보고 「마지막이 그 앞의 최선보다 낫지 않다(`3 >= 3`)」로 판정한다. 주석이 달아 둔 대로 **「같음」도 정체로 본다. 나빠지는 것만 잡으면 늦다.**

```python
def stalled(self) -> bool:
    n = self.stall_limit + 1
    if len(self.scores) < n:
        return False
    window = self.scores[-n:]
    best_before = min(window[:-1])
    return window[-1] >= best_before
```

여기서 횟수 상한만 있었다면 4회차까지 다 돌고 「입력 소진」으로 끝났을 것이다. `ex1` 해설이 「횟수 상한이었으면 두 번 더 헛돌았을 것」이라고 적은 게 이 얘기다.

**두 시나리오를 나란히 놓으면 횟수 상한 하나만 두는 것의 양면 실패가 보인다.**

- 「천천히 나아진다」 → **너무 일찍 끊는다.** 될 일을 못 하게 만든다.
- 「제자리걸음」 → **너무 늦게 끊는다.** 안 될 일에 예산을 끝까지 태운다.

`ex1`의 마지막 문장이 그래서 이렇다.

```
하나만 두면 나머지 셋이 못 잡는 경우가 남는다.
그리고 실무에서 제일 아픈 건 «제자리걸음»이다.
횟수 상한만 있으면 안 될 일에 예산을 끝까지 쓰고 끝난다.
```

## 실무로 옮기면

1. **횟수 상한을 「안전망」으로 강등하라.** 실질 제어는 전역 예산이 하게 두고(`ex5`의 결론), 횟수는 폭주를 막는 최후 방어선으로만 둔다. 그러면 「천천히 나아지는 루프」가 회차 때문에 억울하게 죽는 일이 줄어든다.
2. **종료 이유를 반드시 상태에 남겨라.** `ending: str` 하나면 호출한 쪽이 「재개할지 / 사람을 부를지 / 설계를 바꿀지」를 나눌 수 있다. `done: bool`은 이 정보를 버린다.
3. **상한으로 끝났으면 「이어 돌리기」가 가능해야 한다.** 회차·비용 누적이 상태에 있어야 재개할 때 리셋되지 않는다. 20장이 「전역 예산은 전역 변수가 아니라 상태에 둔다」고 못 박고, 21장(프로세스가 죽어도 작업은 살아 있어야 한다)으로 이어지는 이유다.
4. **상한을 올릴 때는 축을 함께 보라.** 위에서 봤듯 회차만 올리면 예산이 바로 다음 벽이 된다.
5. **진전 척도는 규칙으로 세는 값으로.** 「천천히 나아진다」를 「정말 나아지는 중」이라고 판정하려면 척도를 믿을 수 있어야 한다. `ex2`가 보여주듯 산출물 길이나 모델 확신도는 모델이 스스로 올릴 수 있어서, 정체를 진전으로 착각하게 만든다. 위반 건수처럼 코드가 세는 값을 써야 「더 돌리면 된다」는 판단이 근거를 갖는다.

## 암기용 정리

- 상황: 점수 9 → 8 → 7 → 6 → 5, 매 회차 정직하게 개선.
- 사건: 5회차에서 `rounds >= max_rounds(5)` → **「횟수 상한」** 종료. 마지막 점수 5, 성공(0)까지 다섯 걸음 남음.
- 문제: **더 돌리면 됐을 루프를 상한이 끊었다. 상한이 성공을 막을 수 있다.**
- 대응: 「상한」이면 상한을 올려 재개하거나 사람에게 「더 줄까요?」를 묻는다. 「정체」면 더 돌려도 소용없으니 접근 자체를 바꾼다. 이 구분은 종료 이유를 상태에 남겨야 가능하다.
