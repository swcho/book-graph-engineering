# 가장 중요한 단계가 가장 먼저 굶는 구조적 이유

> **Q.** 가장 중요한 단계가 가장 먼저 굶는 구조적 이유는 무엇인가?
>
> **A.** 품질을 지키는 검토가 파이프라인 마지막에 있고, 앞 단계들이 여유분을 먼저 다 쓰기 때문이다.

출처: 20장 20.3절 「예산을 안 나누면 뒤가 굶는다」 / `code/ex3_budget_split.py`

---

## 1. 한 줄로 줄이면

**순서가 우선순위를 이긴다.**

예산을 나누지 않으면 자원 배분의 기준이 「이 단계가 얼마나 중요한가」가 아니라 「이 단계가 몇 번째로 실행되는가」가 된다. 그런데 파이프라인에서 품질을 지키는 검증 단계는 거의 항상 **마지막**에 놓인다. 검증은 정의상 「앞에서 만든 것」을 대상으로 하기 때문에 앞에 놓을 수가 없다.

즉 「중요도가 높은 단계」와 「순서가 뒤인 단계」가 체계적으로 겹친다. 여기에 선착순 소비가 붙으면, 굶는 대상이 무작위가 아니라 **항상 가장 중요한 쪽으로 쏠린다.** 이게 「구조적」이라는 말의 뜻이다. 운이 나빠서가 아니라, 배분 규칙과 파이프라인 형태가 겹쳐서 매번 같은 방향으로 기울어진다.

## 2. 예제 3에서 실제로 벌어지는 일

전체 예산 100, 단계는 넷이다. 각 단계는 「최소 필요분」과 「여유가 있으면 더 쓰고 싶은 양(탐욕분)」을 가진다.

| 단계 | 최소 필요 | 탐욕분 | 원하는 총량 |
|---|---:|---:|---:|
| 검색 | 8 | 40 | 48 |
| 요약 | 6 | 25 | 31 |
| 초안 | 14 | 60 | 74 |
| 검토 | 10 | 20 | 30 |
| **합계** | **38** | 145 | 183 |

최소 필요분 합계는 38뿐이다. 예산 100은 **모두를 살리기에 두 배 넘게 충분하다.** 부족해서 굶는 게 아니라는 점이 핵심이다.

### 나누지 않음 — 먼저 오는 쪽이 다 쓴다

```
검색   want 48, left 100 → 48 받음, 남은 52
요약   want 31, left  52 → 31 받음, 남은 21
초안   want 74, left  21 → 21 받음, 남은  0   (최소 14는 넘겨서 통과)
검토   want 30, left   0 →  0 받음               ← 굶음
```

| 단계 | 배정 | 최소 충족 |
|---|---:|---|
| 검색 | 48.0 | 예 |
| 요약 | 31.0 | 예 |
| 초안 | 21.0 | 예 |
| 검토 | **0.0** | **아니오** ← |

검토가 필요한 건 10이다. 전체의 10%. 그런데 0을 받는다. 앞의 세 단계가 「있으면 쓴다」는 원칙으로 100을 다 태웠기 때문이다.

여기서 앞 단계 중 누구도 잘못을 하지 않았다는 게 중요하다. 검색이 48을 쓴 건 규칙 위반이 아니다. 각 단계를 따로 리뷰하면 전부 정상으로 보인다. 문제는 단계가 아니라 **배분 규칙**에 있다. (20.5절의 「곱하기를 아무도 안 한다」와 정확히 같은 종류의 사각지대다. 층마다 상한이 다 있었지만 전역이 없었던 사고.)

## 3. 일반화 — 두 조건이 겹칠 때 생기는 구조적 편향

이 현상은 「예산」이나 「LLM 파이프라인」에 한정된 이야기가 아니다. 아래 두 조건만 성립하면 어디서든 같은 편향이 생긴다.

### 조건 A. 선착순 소비 (first-come, greedy consumption)

- 유한한 공유 자원이 하나 있다.
- 소비자마다 상한이 없거나, 있어도 「남은 만큼 다 쓸 수 있다」.
- 배분 시점이 **실행 시점**이다. 즉 예약이 아니라 선점이다.

이 조건에서 자원 획득량은 소비자의 **순번**의 함수가 된다. 우선순위는 배분에 아무 영향을 못 준다. 우선순위 정보가 시스템 어디에도 표현돼 있지 않기 때문이다.

### 조건 B. 검증·품질 단계가 파이프라인 마지막에 있다

- 검증은 산출물을 입력으로 받으므로 생산 뒤에 올 수밖에 없다. 순서를 바꿀 자유가 없다.
- 그래서 「가장 중요한 단계」와 「가장 마지막 단계」가 구조적으로 일치한다.

### 겹치면 생기는 것

```
   중요도 ↑                       배분량 ↑
      검토 ██████                검색 ████████
      초안 ████                  요약 ██████
      검색 ██                    초안 ████
      요약 ██                    검토          ← 0
                                 (순서 = 배분, 중요도는 무시됨)
```

세 가지 성질이 따라온다.

**(1) 편향의 방향이 고정된다.** 굶는 단계가 랜덤이면 통계적으로 관리할 수 있다. 그런데 여기선 항상 마지막이 굶는다. 그리고 마지막이 항상 검증이다. 부하가 걸릴 때마다 시스템은 **정확히 품질 보호 장치만 골라서 끈다.**

**(2) 실패가 조용하다 (fail-open).** 굶은 게 생성 단계였다면 산출물이 없으니 즉시 티가 난다. 굶은 게 검증 단계면 산출물은 멀쩡히 나온다. 다만 아무도 안 본 것일 뿐이다. 「검토 0건 = 지적사항 0건 = 통과」로 읽히기 때문에, 실패가 성공의 모습을 하고 밖으로 나간다. 이게 이 버그를 몇 달씩 못 잡는 이유다.

**(3) 부하가 클수록 방어가 약해진다.** 어려운 입력일수록 앞 단계가 오래 돌고 많이 쓴다. 즉 **검토가 가장 필요한 순간에 검토 예산이 정확히 0이 된다.** 방어 장치가 위험도와 반비례해서 작동한다.

### 같은 형태가 나타나는 다른 자리들

| 자원 | 앞에서 태우는 쪽 | 굶는 쪽 |
|---|---|---|
| 토큰 예산 | 검색·초안 생성 | 검토·비평(critic) |
| 컨텍스트 윈도우 | 앞서 쌓인 대화·툴 결과 | 마지막에 붙일 검증 규칙·체크리스트 |
| 요청 타임아웃 | 앞단 I/O 재시도 | 뒷단 응답 검증·후처리 |
| 재시도 예산 | 초기 단계 재시도 | 마지막 단계 재시도 몫 |
| 스프린트 일정 | 설계·구현 | QA·테스트 |
| 릴리스 창 | 빌드·배포 | 리허설·롤백 검증 |
| CI 시간 한도 | 컴파일·유닛테스트 | 통합·보안 스캔 |
| 사람의 주의력 | 앞부분 리뷰 | PR 뒷부분 리뷰 |

전부 「선착순 소비 + 검증이 마지막」이다. 스프린트 막판에 QA가 잘려 나가는 것과, 검토 노드가 토큰 0을 받는 것은 같은 구조의 다른 표현이다.

## 4. 왜 이걸 「가장 중요한 단계」라고 부르는가

검토를 특별 취급하는 근거는 세 가지다.

- **오류를 잡는 유일한 지점이다.** 검색이 부실하면 초안이 어느 정도 메운다. 초안이 어설프면 검토가 잡는다. 그런데 검토가 없으면 그걸 잡을 다음 단계가 없다. 파이프라인의 마지막 방어선이다.
- **실패 비용이 비대칭이다.** 초안이 60이 아니라 20을 써서 조금 거친 결과가 나오는 것과, 틀린 결과가 검증 없이 나가는 것은 손해의 크기가 다르다.
- **다른 단계의 품질을 담보하는 전제다.** 「초안이 좀 대충이어도 검토가 잡는다」는 가정 위에서 앞 단계를 공격적으로 설계했다면, 검토가 굶는 순간 그 가정이 통째로 무너진다.

## 5. 이 구조를 깨는 방법

### 5.1 최소분 선할당 (reserve-first)

배분 시점을 **실행 시점에서 계획 시점으로** 옮긴다. 모든 단계의 최소 필요분을 먼저 떼어 놓고, 남은 것만 앞에서부터 쓰게 한다.

```python
def reserve_first(total):
    """최소 필요분을 먼저 떼어 두고 나머지를 앞에서부터 쓴다."""
    reserved = sum(need for _, need, _ in STAGES)   # 38
    spare = total - reserved                        # 62
    out = []
    for name, need, greedy in STAGES:
        extra = min(greedy, spare)
        spare -= extra
        out.append((name, need + extra, True))      # 항상 최소는 보장된다
    return out
```

결과:

| 단계 | 최소분 먼저 | 나누지 않음 |
|---|---:|---:|
| 검색 | 48.0 | 48.0 |
| 요약 | 28.0 | 31.0 |
| 초안 | 14.0 | 21.0 |
| 검토 | **10.0** | **0.0** |

핵심은 「여유분(spare)은 여전히 선착순」이라는 점이다. 탐욕 자체를 없애지 않는다. **탐욕이 건드릴 수 있는 풀에서 최소 보장분을 빼냈을 뿐이다.** 그래서 효율을 크게 잃지 않으면서 굶주림만 제거한다.

전제가 하나 붙는다. **「최소가 얼마인지」를 알아야 한다.** 이건 추정이 아니라 실측이어야 하고, 실측하려면 단계별 토큰·시간을 따로 세고 있어야 한다. 총합만 재고 있으면 이 전략을 쓸 수 없다. 즉 **계측이 이 방어의 선행 조건**이다. 계측을 안 해 뒀다면 그것부터가 할 일이다.

### 5.2 검토 예산을 별도 계정으로 (separate account)

한 걸음 더 나간 방법. 예산을 「하나의 통에서 떼어 주는 몫」이 아니라 **애초에 다른 통**으로 만든다.

```python
# 나쁨 — 통이 하나. 앞 단계가 마음만 먹으면 다 쓸 수 있다
state["budget"] -= cost

# 좋음 — 통이 둘. 생성은 검증 계정에 접근 자체를 못 한다
state["budget_produce"] -= cost   # 검색·요약·초안이 쓰는 계정
state["budget_review"]  -= cost   # 검토만 쓰는 계정
```

선할당과의 차이는 **경계가 어디에 있느냐**다.

- 선할당은 배분 *정책*이다. 정책은 나중에 누가 「여기서 spare를 좀 더 당겨 쓰자」고 고치면 조용히 무너진다.
- 별도 계정은 배분 *구조*다. 생성 노드는 검증 계정의 이름조차 모르므로, 실수로도 못 쓴다. 「할 수 있지만 하지 않기로 한 것」을 「아예 할 수 없는 것」으로 바꾸는 게 요점이다.

계정 방식이면 규칙도 명확하게 쓸 수 있다.

- **역방향 이월만 허용한다.** 검증 계정이 남으면 다음 회차 생성에 돌려줘도 된다. 반대는 절대 안 된다.
- **검증 계정이 비면 fail-closed.** 검토를 못 돌렸으면 성공이 아니다. 20.4절의 `ending` 필드에 `"검토 예산 소진"` 같은 이유를 남기고 사람에게 넘긴다. 조용히 통과시키지 않는 것 — 이게 3절 (2)의 fail-open을 직접 막는 장치다.
- **입장 통제(admission control).** 회차를 시작하기 전에 「이번 회차의 검증 몫이 남아 있는가」를 먼저 확인한다. 없으면 생성을 아예 시작하지 않는다. 만들어 놓고 못 보는 것보다 시작을 안 하는 게 낫다.

### 5.3 균등 분배는 왜 답이 아닌가

```
검색 25.0  (필요 8)   → 17 낭비
요약 25.0  (필요 6)   → 19 낭비
초안 25.0  (필요 14)  → 아깝게 남음, 정작 60까지 쓰고 싶었는데 못 씀
검토 25.0  (필요 10)
```

굶는 단계는 없다. 안전하다. 대신 두 방향으로 손해다. 요약은 6이면 되는데 25를 잡고 있고, 초안은 60을 쓸 수 있으면 결과가 훨씬 좋아지는데 25에서 막힌다. **필요량이 단계마다 크게 다르면 균등 분배는 굶주림 대신 낭비를 산다.** 필요량 편차가 작을 때만 쓸 만한 근사다.

### 5.4 세 방법 비교

| 방식 | 굶주림 | 낭비 | 전제 조건 |
|---|---|---|---|
| 나누지 않음 | 있음 (항상 뒤가) | 없음 | 없음 |
| 균등 분배 | 없음 | 큼 | 없음 |
| 최소분 선할당 | 없음 | 작음 | 단계별 최소 실측 |
| 별도 계정 | 없음 | 작음 | 실측 + 상태 구조 분리 |

## 6. 20장의 다른 절과 어떻게 이어지나

- **20.1 (네 가지 종료 조건)** — 굶주림이 생기면 뒤 단계는 「예산 상한」에 걸려 끝난다. 그런데 그건 루프가 오래 돌아서가 아니라 앞 단계가 다 써서 생긴 일이다. 원인이 다른데 증상이 같으므로, 끝난 이유만 봐서는 진단이 안 된다.
- **20.4 (`ending`을 상태에 남기기)** — 「상한」과 「정체」의 대응이 다르듯, 「검토 예산 소진」도 별개의 종료 사유로 남겨야 한다. 이건 예산을 올리면 해결되는 종류다.
- **20.5 (전역 예산)** — 전역 예산은 총량을 막는 장치고, 최소분 선할당은 그 총량이 **누구에게** 가는지를 정하는 장치다. 둘 다 필요하다. 전역 예산만 있으면 총합은 지켜지지만 여전히 뒤가 굶는다.
- **21장 (지속성)** — 계정을 나눴다면 그 계정도 전역 변수가 아니라 **상태**에 있어야 한다. 안 그러면 재개할 때 검증 계정이 리셋되면서 예산 회계 전체가 무의미해진다.

## 8. 정리

굶주림의 원인은 예산 부족이 아니다. 예제에서 최소 필요분 합계는 38이고 예산은 100이었다. 원인은 **배분 기준이 우선순위가 아니라 실행 순서라는 것**이고, 하필 검증이 항상 마지막이라는 것이다. 이 둘이 겹치면 시스템은 압박을 받을 때마다 정확히 품질 보호 장치부터 껐다.

고치는 방향은 하나다. **중요한 단계의 몫을 선착순 경쟁에서 빼낸다.** 정책으로 하면 최소분 선할당이고, 구조로 하면 별도 계정이다. 그리고 어느 쪽이든 「최소가 얼마인지」를 실측으로 알고 있어야 하므로, 실제 첫 번째 할 일은 단계별 계측이다.
