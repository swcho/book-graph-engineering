# 240회 루프 사고의 원인 — 층마다 상한은 있었고, 전역 예산만 없었다

> **Q.** 저자가 겪은 240회 루프 사고의 원인은 무엇이었는가?
>
> **A.** 층마다 상한이 다 있었지만 전역 예산이 없었다. 각 층 코드를 따로 리뷰하면 문제가 없어 보였고 곱하기를 아무도 하지 않았다.

---

## 1. 원문이 어떻게 시작하는가

20장은 이 한 줄로 시작합니다.

> 층마다 상한을 다 걸어 뒀는데 240번을 돌았습니다.

그리고 곧바로 1장을 다시 꺼냅니다.

> [1장](../../ch01/code/README.md)에서 41만 원짜리 사고를 얘기하면서 "종료 조건이 없으면 종료를 모델이 정한다"고 썼는데, 이번엔 종료 조건이 *있었*습니다. 세 개나요. 그런데도 안 막혔어요.

장 끝의 `ex5_nested_loops.py`가 이 사고를 다시 한 번 못 박습니다.

```
제가 겪은 사고가 이거였다. 층마다 상한이 다 있었는데 전역이 없었다.
각 층 코드를 따로 리뷰하면 아무 문제가 없어 보인다. 곱하기를 아무도 안 했다.
```

**원인은 두 겹입니다.** 기술적 원인은 "전역 예산 부재", 그 위에 얹힌 조직적 원인은 "리뷰 단위가 층이라 곱셈이 아무의 시야에도 안 들어왔다"입니다. 카드의 답이 두 문장인 이유가 여기 있습니다 — 앞 문장이 코드 결함, 뒷 문장이 그 결함이 왜 리뷰를 통과했는가입니다.

---

## 2. 1장 사고와의 차이 — "없어서 터진" 게 아니라 "있는데 터졌다"

이 카드의 핵심은 **대비**입니다. 두 사고를 나란히 놓아야 20장이 왜 별도의 장인지가 보입니다.

| | 1장 사고 (41만 원) | 20장 사고 (240회) |
|---|---|---|
| 종료 조건 | **없다** | **있다. 세 개** (바깥·안쪽·도구) |
| 종료를 정한 주체 | 모델이 정했다 | 코드가 정했다 — 다만 **각자 자기 층만** |
| 결함의 성격 | 누락(omission) | **합성(composition) 결함** |
| 리뷰로 잡히나 | 잡힌다. "여기 상한이 없네" | **안 잡힌다.** 각 파일이 다 정상 |
| 처방 | 상한을 걸어라 | 상한 **위에** 전역 예산을 하나 더 둬라 |

1장의 교훈("종료 조건이 없으면 종료를 모델이 정한다")을 성실히 이행한 코드가 20장에서 터졌다는 게 요점입니다. **각 층이 개별적으로 옳다는 사실이 전체가 옳다는 보장이 아닙니다.** 상한이라는 안전장치는 합성될 때 더해지지 않고 **곱해집니다.** 그리고 사람의 직관은 곱셈이 아니라 덧셈으로 리스크를 추정합니다.

> 정리해 두면 좋은 한 줄: 1장은 **부재**의 문제, 20장은 **경계 설정 단위**의 문제입니다. 조건을 더 촘촘히 다는 것으로는 20장 사고를 못 막습니다. 조건이 걸린 *축*이 틀렸기 때문입니다.

## 3. 240이라는 숫자가 나오는 자리

`ex5_nested_loops.py`가 그 산수를 그대로 보여 줍니다.

```python
OUTER, INNER, TOOL = 5, 4, 3        # 각 층의 상한
COST_PER_CALL = 1.8                 # 원


def counts():
    """각 층이 «자기 상한»만 보면 총 호출이 몇 번이 되나."""
    return OUTER, OUTER * INNER, OUTER * INNER * TOOL
```

`counts()`의 반환값이 이 장의 전부라고 해도 됩니다. 세 층의 상한이 각각 5, 4, 3인데 **실제 도구 호출 상한은 5 + 4 + 3 = 12가 아니라 5 × 4 × 3 = 60**입니다.

그리고 사고가 난 설정은 `(8, 6, 5)`였습니다.

```python
for o2, i2, t2 in ((5, 4, 3), (6, 4, 3), (5, 5, 3), (5, 4, 4), (8, 6, 5)):
```

| 바깥 | 안쪽 | 도구 | 총 호출 | 값 |
|---:|---:|---:|---:|---:|
| 5 | 4 | 3 | 60 | 108원 |
| 6 | 4 | 3 | 72 | 130원 |
| 5 | 5 | 3 | 75 | 135원 |
| 5 | 4 | 4 | 80 | 144원 |
| **8** | **6** | **5** | **240** | **432원** |

예제의 결론 문구가 이 표의 함정을 정확히 짚습니다.

```
«8·6·5» 는 각 층에서 보면 다 합리적인 숫자다. 여덟 번, 여섯 번, 다섯 번.
그런데 곱하면 240회고 432원이다.
```

주목할 점은 **각 층이 겨우 한두 칸씩만 커졌는데 총량은 4배가 됐다**는 것입니다. `5·4·3`에서 `8·6·5`로 가는 변경은 세 개의 서로 다른 PR로 나뉘어 들어와도 전혀 이상하지 않습니다. "재시도를 3번은 좀 빡빡하니 5번으로", "바깥 루프가 5회에서 자꾸 잘리니 8회로" — 각각의 PR은 **한 자리 숫자를 한 번 올리는** 변경입니다. 누구도 4배를 승인한 적이 없는데 4배가 됐습니다.

승수 효과의 성질도 기억해 두면 좋습니다. 총량은 층 개수에 대해 **지수적으로** 커집니다. 층이 하나 늘어날 때마다 새 층의 상한만큼 곱해지니, "재시도 래퍼를 하나 더 씌운다" 같은 무해해 보이는 변경이 총량을 통째로 배수 시킵니다.

## 4. 구조적 사각지대 — 리뷰 단위가 '층'이라 곱셈이 안 보인다

이 카드에서 가장 중요한 부분입니다. 전역 예산이 없었다는 건 **결과**고, 그게 왜 아무에게도 안 보였는가가 **원인**입니다.

### 왜 안 보이는가

1. **각 층의 상한은 자기 파일 안에서 지역적으로 옳습니다.** `MAX_RETRIES = 5`가 들어 있는 도구 래퍼는 그 자체로 나무랄 데가 없습니다. 오히려 "재시도 상한이 있다"는 이유로 리뷰에서 칭찬받을 코드입니다.
2. **곱셈의 인자들이 서로 다른 파일, 다른 모듈, 종종 다른 팀에 흩어져 있습니다.** 바깥 루프는 오케스트레이션 코드, 안쪽 루프는 에이전트 로직, 도구 재시도는 인프라 라이브러리에 있습니다. 세 숫자를 한 화면에 놓고 본 사람이 없습니다.
3. **디프(diff)는 곱셈을 보여 주지 않습니다.** 리뷰어가 보는 건 `- 3` / `+ 5`입니다. 이 변경이 전체 상한을 60에서 100으로 밀어 올린다는 사실은 diff 어디에도 안 적혀 있습니다.
4. **어느 층도 자기 위/아래를 모릅니다.** 도구 래퍼는 자기가 루프 안에서 불리는지 아닌지 모릅니다. 그래서 "지금까지 전체 몇 번 불렸나"를 물어볼 상대가 없습니다.

`ex5`가 짚는 문장을 다시 봅시다.

```
각 층 코드를 따로 리뷰하면 아무 문제가 없어 보인다.
```

"문제가 없어 보인다"가 아니라 **"각 층 코드를 따로 리뷰하면"**에 무게가 있습니다. 리뷰 프로세스가 정상 작동했는데도 사고가 났습니다. 사각지대는 사람의 부주의가 아니라 **리뷰 단위와 위험 단위가 어긋난 구조** 자체입니다. 층 단위로 보는 한, 곱셈은 아무의 화면에도 나타나지 않습니다.

### 관측성 쪽에도 같은 구멍이 있다

계측도 보통 층 단위로 붙습니다. 각 층은 "나는 상한 안에서 돌았다"는 로그를 남기고 실제로 사실입니다. 사후에 로그를 뒤져도 위반 기록이 없습니다. **전체 호출 수를 세는 카운터가 애초에 없으면, 240회는 로그 위에 240개의 정상 기록으로만 남습니다.** 그래서 사고를 눈치채는 경로가 대개 청구서입니다.

## 5. 재발 방지 ① — 전역 예산

`ex5`가 제시하는 처방의 첫 줄입니다.

```
층마다 상한을 두는 건 필요하다. 다만 그것만으로는 부족하다.
«전역 예산»을 하나 더 둬야 한다. 그리고 모든 층이 그걸 본다.
```

층 상한을 없애라는 말이 **아닙니다.** 한 층 더 얹으라는 말입니다.

```python
def with_global_budget(budget):
    """전역 예산이 있으면 실제로 몇 번까지 가나."""
    return int(budget / COST_PER_CALL)
```

| 전역 예산 | 최대 호출 | 층 상한 곱(240회) 대비 |
|---:|---:|---|
| 100원 | 55회 | 적다 |
| 300원 | 166회 | 적다 |
| 1000원 | 555회 | 많다 |

여기서 요령이 나옵니다.

```
전역 예산이 층 상한보다 먼저 걸리게 잡는 게 요령이다.
그러면 층 상한은 «안전망»이 되고 전역 예산이 «실질 제어»가 된다.
```

역할이 갈립니다.

| | 층 상한 | 전역 예산 |
|---|---|---|
| 역할 | 안전망 (fallback) | 실질 제어 |
| 보는 범위 | 자기 층 | 실행 전체 |
| 튜닝 주체 | 각 층 담당 | 실행 소유자 / 운영 |
| 걸리는 순서 | 나중 | **먼저** |

전역 예산이 먼저 걸리게 잡으면, 층 상한 하나가 슬그머니 커져도 총량은 안 움직입니다. **곱셈이 위쪽에서 잘립니다.** 층 상한 변경이 총 비용에 미치는 영향을 리뷰어가 계산하지 못해도 안전합니다 — 그게 이 설계의 핵심 이득입니다.

전역 예산의 단위도 생각해 둘 값어치가 있습니다. 20장은 종료 조건을 넷으로 봅니다.

> 종료 조건은 넷입니다. 횟수, 예산, 시간, 그리고 진전 없음. 하나만 두면 나머지 셋이 못 잡는 경우가 남아요.

`guards.py`가 그걸 한곳에 모아 둡니다.

```python
    def check(self) -> Optional[str]:
        """멈출 이유가 있으면 «그 이유»를, 없으면 None."""
        if self.rounds >= self.max_rounds:
            return "횟수 상한"
        if self.cost >= self.max_cost:
            return "예산 상한"
        if self.elapsed >= self.max_seconds:
            return "시간 상한"
        if self.stalled():
            return "진전 없음"
        return None
```

240회 사고는 이 중 **횟수**가 층 단위로만 존재했던 사고입니다. 그래서 전역 예산은 비용(원/토큰)만이 아니라 **전역 호출 횟수**와 **전역 벽시계 시간**까지 함께 두는 편이 낫습니다. 층을 넘나드는 축은 모두 전역에 사본이 있어야 합니다.

### 전역 예산은 전역 변수가 아니다

한 장 요약이 여기에 못을 하나 더 박습니다.

> 층마다 상한을 둬도 곱하면 커집니다. 전역 예산을 하나 더 두고 모든 층이 보게 하세요. 그리고 그 예산은 전역 변수가 아니라 *상태*에 둡니다. 안 그러면 재개할 때 리셋됩니다.

이게 미묘하지만 실무에서 정확히 사고가 나는 지점입니다. 모듈 레벨 `_total_calls = 0` 같은 걸로 만들면:

- 프로세스가 죽었다 살아나면 0으로 돌아갑니다. **재시도할 때마다 예산이 새로 채워집니다.**
- 재개(resume)마다 리셋되면 240회 사고가 재개 횟수만큼 반복됩니다. 상한이 사실상 없는 것과 같아집니다.
- 스레드/프로세스가 여러 개면 카운터가 갈라지거나 경쟁 상태가 됩니다.

그래서 예산은 **체크포인트되는 상태 필드**여야 합니다. `ex4_generator_critic.py`가 그 형태를 보여 줍니다.

```python
class S(TypedDict):
    text:    str
    missing: list
    rounds:  Annotated[int, operator.add]
    cost:    Annotated[float, operator.add]
    scores:  Annotated[list, operator.add]
    ending:  str          # 어떤 이유로 끝났는지. 이게 중요하다.
```

`rounds`와 `cost`가 `operator.add` 리듀서를 달고 상태에 앉아 있습니다. 노드는 자기가 쓴 만큼만 돌려주고(`{"rounds": 1, "cost": 22.0}`), 누적은 리듀서가 합니다. 체크포인터가 이 상태를 저장하므로 **재개해도 누적치가 이어집니다.**

```python
app = b.compile(checkpointer=InMemorySaver())
```

장 끝의 예고가 이 실을 다음 장으로 넘깁니다.

> 이 장에서 「재개하면 예산이 이어진다」를 전제로 얘기했습니다. 그러려면 죽었다 살아나도 상태가 남아 있어야 해요. 다음 장이 그 이야기입니다.

## 6. 재발 방지 ② — 전역 카운터 계측

전역 예산은 **셀 수 있어야** 걸 수 있습니다. 그래서 계측이 예산의 전제 조건입니다. `ex3_budget_split.py`가 이 순서를 명시합니다.

```
다만 «최소가 얼마인지»를 알아야 한다. 그건 실측해야 하고,
실측하려면 단계별 토큰을 따로 세고 있어야 한다.
그 계측을 안 해 두면 이 전략을 못 쓴다.
```

계측이 주는 것은 세 가지입니다.

1. **사고를 실시간에 잡는다.** 층 로그는 전부 정상이어도 전역 카운터는 240에서 눈에 띕니다. 층별 로그의 합이 아니라 **하나의 누적 값**이 있어야 알람을 걸 수 있습니다.
2. **예산 분배의 근거가 된다.** `ex3`가 보여 주듯 "최소분 먼저 떼어 두기"는 단계별 실측치가 있어야 성립합니다. 없으면 균등 분배(낭비) 아니면 무분할(굶김)로 갑니다.
3. **회귀를 잡는다.** 전역 호출 수를 릴리스마다 기록해 두면, 층 상한 하나가 올라간 PR이 총량을 얼마나 밀었는지 사후에라도 보입니다.

무엇을 셀지도 20장이 이미 답했습니다. `ex2_stall_detection.py`의 결론입니다.

```
진전 척도를 고르는 기준 하나. «모델이 스스로 올릴 수 있는 값이면 안 된다.»
길이도 확신도도 모델이 마음대로 올릴 수 있다. 위반 건수는 못 올린다.
```

이 원칙은 종료 판정 전반에 적용됩니다. **호출 수·토큰·경과 시간은 모두 코드가 세는 값이라 모델이 못 흔듭니다.** 모델에게 "끝났나요?"를 묻는 대신 "무엇이 남았나요"만 묻고 종료는 코드가 정한다는 원칙과 같은 계열입니다.

### 끝난 이유를 남긴다

`ex4`의 `ending` 필드가 이 사고 대응에 직접 쓰입니다.

```python
    print(
        "\n그리고 끝난 이유가 상태에 남는다는 게 중요하다.\n"
        "호출한 쪽이 이걸 보고 다르게 대응할 수 있다.\n"
        "  성공 — 그대로 쓴다\n"
        "  상한 — 사람에게 넘긴다 (더 돌리면 될 수도 있다)\n"
        "  예산 — 예산을 올릴지 물어본다\n"
        "  정체 — 사람에게 넘긴다 (더 돌려도 안 된다)\n"
        "\n«상한»과 «정체»의 대응이 다르다. 불리언 하나로는 이 구분이 안 된다."
    )
```

240회 사고 관점에서는 이렇게 읽힙니다. **"전역 예산으로 끊겼다"가 상태에 남으면 그건 그 자체로 알람입니다.** 층 상한으로 끊긴 실행과 전역 예산으로 끊긴 실행은 대응이 다릅니다. 전자는 정상 동작, 후자는 "어딘가에서 곱셈이 커지고 있다"는 신호입니다. 불리언 하나로 돌려주면 이 구분이 사라집니다.

### 리뷰 프로세스 쪽 처방

사각지대가 구조적이니 처방도 구조적이어야 합니다. 코드 밖에서 할 수 있는 것들입니다.

- **층 상한 상수를 한 파일에 모은다.** `OUTER, INNER, TOOL = 5, 4, 3`처럼 세 숫자가 나란히 있으면 곱셈이 눈에 들어옵니다. `ex5`가 파일 맨 위에 이렇게 둔 것 자체가 시범입니다.
- **곱을 테스트로 고정한다.** `assert OUTER * INNER * TOOL <= MAX_TOTAL_CALLS` 한 줄이면, 어느 층의 상한을 올리는 PR이든 CI에서 걸립니다. 리뷰어가 곱셈을 안 해도 됩니다.
- **상한 변경 PR에 총 호출/총 비용 변화를 적게 한다.** diff가 못 보여 주는 숫자를 사람이 적게 만듭니다.
- **알람은 전역 카운터에 건다.** 층별 정상 로그 240개는 알람이 안 되지만, 누적 240은 됩니다.

## 7. 정리

1. **직접 원인** — 층마다(바깥 루프·안쪽 루프·도구 재시도) 상한은 다 있었지만, 실행 전체를 보는 **전역 예산이 없었다.**
2. **왜 안 잡혔나** — 리뷰 단위가 '층'이었다. 각 층 코드는 따로 보면 완전히 정상이고, 곱셈의 인자들이 서로 다른 파일에 흩어져 있어 **곱하기를 아무도 하지 않았다.**
3. **1장과의 차이** — 1장은 종료 조건 **부재**(모델이 종료를 정함). 20장은 조건이 **세 개나 있었는데도** 터졌다. 누락이 아니라 **합성 결함**이라 리뷰로 안 걸린다.
4. **산수** — `8 × 6 × 5 = 240회`, 호출당 1.8원이면 432원. 각 층 숫자는 8, 6, 5로 모두 합리적이다. 층당 한두 칸 올린 변경이 총량을 4배로 만든다.
5. **처방 ①** — 전역 예산을 하나 더 두고 **모든 층이 그걸 본다.** 전역 예산이 층 상한보다 **먼저** 걸리게 잡아 층 상한을 안전망으로 강등한다.
6. **처방 ②** — 그 예산은 전역 변수가 아니라 **체크포인트되는 상태**에 둔다(`Annotated[float, operator.add]`). 안 그러면 재개할 때마다 리셋된다.
7. **처방 ③** — 전역 카운터를 계측한다. 모델이 못 흔드는 값(호출 수, 토큰, 시간)을 코드가 세고, **끝난 이유**를 상태에 남겨 "전역 예산으로 끊김"이 알람이 되게 한다.

**한 문장으로:** 상한은 더해지지 않고 곱해지는데 리뷰는 층 단위로 이뤄진다 — 그래서 곱을 볼 자리(전역 예산 + 전역 카운터)를 따로 만들어야 한다.
