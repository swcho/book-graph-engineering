# 예산을 나누지 않으면 어떤 문제가 생기는가?

**답:** 뒤쪽 단계가 굶는다. 그리고 대개 뒤쪽이 품질을 지키는 단계다.

---

## 무슨 상황을 말하는 건가

에이전트 파이프라인은 보통 여러 단계가 순서대로 이어집니다. 20장 예제 3(`code/ex3_budget_split.py`)의 설정은 이렇습니다.

| 단계 | 최소 필요 예산 | 여유가 있으면 더 쓰는 양 |
|---|---|---|
| 검색 | 8 | 40 |
| 요약 | 6 | 25 |
| 초안 | 14 | 60 |
| 검토 | 10 | 20 |

전체 예산은 **100**이고, 최소 필요분의 합계는 **38**입니다. 즉 산술적으로는 모든 단계가 살아남을 수 있는 예산이 있습니다. 그런데도 굶는 단계가 생깁니다.

문제는 예산을 **"하나의 통"으로 두고 먼저 오는 단계부터 마음껏 쓰게 했을 때** 발생합니다.

## 왜 굶는가 — 선착순 소비

예산을 나누지 않으면 각 단계는 "지금 남은 게 얼마인가"만 보고 쓸 수 있는 만큼 씁니다. 앞 단계에게는 뒤 단계가 얼마나 필요한지 알 방법이 없어요.

```python
def no_split(total):
    """먼저 오는 단계가 여유분을 다 쓴다."""
    left = total
    out = []
    for name, need, greedy in STAGES:
        want = need + greedy      # 최소 + 쓸 수 있으면 더
        got = min(want, left)     # 남은 만큼 다 가져간다
        left -= got
        out.append((name, got, got >= need))
    return out
```

전체 100을 이 규칙으로 흘려보내면 이렇게 됩니다.

| 단계 | 원하는 양 | 실제 배정 | 남은 예산 | 최소 충족? |
|---|---|---|---|---|
| 검색 | 48 | **48** | 52 | 예 |
| 요약 | 31 | **31** | 21 | 예 |
| 초안 | 74 | **21** | 0 | 예 (14 이상) |
| 검토 | 30 | **0** | 0 | **아니오 ←** |

검색이 48, 요약이 31을 가져가는 순간 뒤에 남는 건 21입니다. 초안이 그 21을 마저 쓰고 나면 **검토에게 돌아갈 몫은 0**입니다.

여기서 핵심은 검색이나 요약이 "잘못"한 게 아니라는 점입니다. 각 단계는 자기 상한 안에서 합리적으로 행동했고, 어느 코드 한 줄도 버그가 아닙니다. 아무도 전체를 안 봤을 뿐이에요. 20장 5절의 "곱하기를 아무도 안 한다"와 정확히 같은 구조의 실패입니다.

## 왜 하필 뒤쪽이 아픈가

여기가 이 카드의 진짜 요점입니다. 굶는 게 아무 단계나 아니라 **하필 뒤쪽**이고, 파이프라인에서 뒤쪽에 놓이는 건 대개 이런 단계들입니다.

- **검토 / 비평(critic)** — 결과가 요구사항을 지켰는지 확인
- **검증 / 스키마 체크** — 형식과 제약 위반 탐지
- **안전 필터 / 정책 확인** — 내보내도 되는지 판단
- **최종 정리·요약** — 사람이 읽을 형태로 다듬기

즉 **품질을 지키는 관문(gate)이 전부 뒤에 있습니다.** 이들이 예산을 못 받으면 어떻게 될까요? 파이프라인은 "실패"하지 않습니다. 조용히 검토를 건너뛰고, **검증되지 않은 결과물이 그대로 최종 출력으로 나갑니다.**

> 그런데 검토는 «품질을 지키는» 단계다. 그게 굶으면 나쁜 결과가 그대로 나간다.
> 제일 중요한 단계가 제일 마지막에 있어서 제일 먼저 굶는 구조다.

이 실패가 위험한 이유는 **눈에 안 띄기 때문**입니다. 예산 초과로 에러가 나는 게 아니라, 결과는 멀쩡히 나오는데 품질 보증만 빠진 상태로 나옵니다. 굶어 죽은 건 로그에 안 남고 나쁜 답만 남습니다.

## 어떻게 막는가 — 세 가지 전략

### 1. 나누지 않음 (선착순) — 실패

위에서 본 그대로. 검토가 0을 받습니다.

### 2. 균등 분배 — 안전하지만 낭비

```python
def even_split(total):
    share = total / len(STAGES)
    return [(n, share, share >= need) for n, need, _ in STAGES]
```

100 / 4 = 25씩. 모든 단계가 최소(8, 6, 14, 10)를 넘으니 굶는 곳은 없습니다. 하지만 **요약은 6이면 되는데 25를 받습니다.** 반대로 초안은 원래 74까지 쓸 수 있는데 25로 묶입니다. 필요 분포가 균등하지 않은데 배분만 균등하니 남는 곳과 모자란 곳이 동시에 생깁니다.

### 3. 최소분 먼저 떼어 두기 (reserve) — 대개 정답

```python
def reserve_first(total):
    """최소 필요분을 먼저 떼어 두고 나머지를 앞에서부터 쓴다."""
    reserved = sum(need for _, need, _ in STAGES)   # 38
    spare = total - reserved                        # 62
    out = []
    for name, need, greedy in STAGES:
        extra = min(greedy, spare)
        spare -= extra
        out.append((name, need + extra, True))
    return out
```

먼저 38을 각 단계 이름표를 붙여 잠가 두고, 남은 62만 앞에서부터 쓰게 합니다.

| 단계 | 잠긴 최소 | 여유분에서 추가 | 최종 배정 |
|---|---|---|---|
| 검색 | 8 | +40 | 48 |
| 요약 | 6 | +22 | 28 |
| 초안 | 14 | +0 | 14 |
| 검토 | 10 | +0 | **10** |

앞쪽은 여전히 넉넉히 쓰지만, **검토는 무슨 일이 있어도 10을 보장받습니다.** 예산 경쟁의 대상은 "여유분"뿐이고 "최소분"은 애초에 경쟁에 안 나옵니다.

## 이 전략의 전제 조건 — 계측

책이 마지막에 붙인 단서가 중요합니다.

> 다만 «최소가 얼마인지»를 알아야 한다. 그건 실측해야 하고,
> 실측하려면 단계별 토큰을 따로 세고 있어야 한다.
> 그 계측을 안 해 두면 이 전략을 못 쓴다.

`need` 값(8, 6, 14, 10)은 하늘에서 떨어지지 않습니다. **단계별로 토큰 사용량을 따로 집계해 두어야** 최소분을 정할 수 있습니다. 파이프라인 전체 토큰 합계 하나만 찍고 있으면, 검토가 최소 얼마를 필요로 하는지 영영 모릅니다. 즉 순서는 이렇습니다.

1. 단계별 토큰/비용을 **분리해서 계측**한다
2. 실측 분포에서 각 단계의 **최소 필요분**을 뽑는다
3. 그 최소분을 **먼저 예약**하고 나머지를 경쟁시킨다

## 20장 전체 안에서의 위치

이 카드는 20.3절 "예산을 안 나누면 뒤가 굶는다"에 해당하고, 20.5절의 중첩 루프 문제와 짝을 이룹니다.

| 절 | 실패 모드 | 처방 |
|---|---|---|
| 20.3 | 앞 단계가 예산을 다 써서 **뒤 단계가 굶는다** | 단계별 최소분을 먼저 예약 |
| 20.5 | 층마다 상한을 둬도 **곱하면 커진다** (8·6·5 = 240회) | 전역 예산을 하나 더 두고 모든 층이 본다 |

공통점은 **"각 부분만 보면 다 합리적인데 전체를 보면 망가진다"**는 것입니다. 20.5절의 저자 사고("층마다 상한이 다 있었는데 전역이 없었다. 각 층 코드를 따로 리뷰하면 아무 문제가 없어 보인다. 곱하기를 아무도 안 했다")와 20.3절의 굶는 검토 단계는 같은 병의 두 증상입니다. 단계별 예산과 전역 예산은 서로를 대체하지 않고 **둘 다** 필요합니다.

## 한 줄 정리

예산을 하나의 통에 담아 선착순으로 쓰게 하면 **앞 단계가 여유분을 다 소진해 뒤 단계가 0을 받습니다.** 그런데 뒤에 있는 건 대개 검토·검증 같은 품질 관문이라서, 그 결과는 "실패"가 아니라 **"검증 없이 통과한 나쁜 결과"**입니다. 각 단계의 최소분을 실측해서 먼저 떼어 두세요.
