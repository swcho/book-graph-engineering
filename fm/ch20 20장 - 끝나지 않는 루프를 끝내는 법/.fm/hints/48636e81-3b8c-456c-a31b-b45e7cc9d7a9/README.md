# 끝난 이유를 상태에 남겨야 하는 이유

> **Q.** 끝난 이유를 상태에 남겨야 하는 이유는 무엇인가?
>
> **A.** '상한'과 '정체'는 대응이 다르다. 불리언 하나로는 이 구분이 되지 않는다.

출처: 20장 「끝나지 않는 루프를 끝내는 법」 20.4절 *네 조건을 다 붙인 루프*, `code/ex4_generator_critic.py`, `code/guards.py`

## 1. 루프가 멈추는 방식은 하나가 아니다

20장의 종료 조건은 넷입니다. 횟수, 예산, 시간, 그리고 진전 없음. 예제 1이 보여주듯 **넷이 각각 다른 상황을 잡습니다.**

| 종료 조건 | 잡는 상황 |
|---|---|
| 횟수 상한 | 천천히 나아지는 중인데 회차가 다 됐다 |
| 예산 상한 | 회차는 적은데 호출이 비싸서 돈을 다 썼다 |
| 시간 상한 | 사용자가 기다리다 떠난다 |
| 진전 없음(정체) | 계속 돌지만 점수가 안 줄어든다 |

여기서 중요한 건 넷이 **끝났다는 사실은 같지만 끝난 의미가 전혀 다르다**는 점입니다. 그런데 루프 함수가 `True`/`False` 하나만 돌려주면, 이 네 갈래가 호출부에 도착하는 순간 하나로 뭉개집니다.

`guards.py`의 주석이 이걸 대놓고 말합니다.

> 핵심은 «어떤 이유로 끝났는지»를 돌려주는 것이다.
> 불리언 하나만 돌려주면 호출한 쪽이 다르게 대응할 수 없다.

그래서 `Guards.check()`는 `bool`이 아니라 `Optional[str]`입니다. 멈출 이유가 있으면 **그 이유 문자열**을, 없으면 `None`을 돌려줍니다.

```python
def check(self) -> Optional[str]:
    """멈출 이유가 있으면 «그 이유»를, 없으면 None."""
    if self.rounds >= self.max_rounds:   return "횟수 상한"
    if self.cost >= self.max_cost:       return "예산 상한"
    if self.elapsed >= self.max_seconds: return "시간 상한"
    if self.stalled():                   return "진전 없음"
    return None
```

## 2. 그래프에서는 어떻게 남기나 — `ending` 필드와 `mark(reason)`

`ex4_generator_critic.py`는 LangGraph 상태에 아예 전용 필드를 하나 둡니다.

```python
class S(TypedDict):
    text:    str
    missing: list
    rounds:  Annotated[int, operator.add]
    cost:    Annotated[float, operator.add]
    scores:  Annotated[list, operator.add]
    ending:  str          # 어떤 이유로 끝났는지. 이게 중요하다.
```

`rounds`·`cost`·`scores`는 리듀서(`operator.add`)로 누적되는 값이고, `ending`은 리듀서가 없는 평범한 문자열입니다. 마지막에 한 번만 쓰이면 되니까요.

쓰는 쪽은 라우터와 종료 노드로 나뉩니다.

```python
def route(s: S) -> str:
    if not s["missing"]:            return "성공"
    if s["rounds"] >= MAX_ROUNDS:   return "상한"
    if s["cost"] >= MAX_COST:       return "예산"
    if stalled(s["scores"]):        return "정체"
    return "생성"

def mark(reason):
    def fn(s: S) -> dict:
        return {"ending": reason}
    return fn

for r in ("성공", "상한", "예산", "정체"):
    b.add_node(r, mark(r))
    b.add_edge(r, END)
```

구조를 정리하면 이렇습니다.

- 조건부 엣지가 갈 수 있는 곳은 다섯 군데. `생성`(계속) + **종료 이유 네 개**.
- 종료 이유마다 **노드가 하나씩** 있고, 그 노드가 하는 일은 `ending`에 자기 이름을 찍는 것뿐입니다.
- `mark(reason)`은 클로저 팩토리라 네 개의 노드 함수를 한 줄로 찍어냅니다.
- 네 노드 모두 `END`로 이어지므로, 어느 쪽으로 끝나든 최종 상태에는 `ending`이 채워져 있습니다.

즉 "끝났다"는 상태 전이는 **네 개의 서로 다른 노드**로 구현되어 있고, 그 차이가 상태에 글자로 남습니다. 불리언 플래그 하나였다면 이 네 노드가 전부 같은 값을 쓰고 끝났을 겁니다.

## 3. 실제 실행 결과

예제 4의 `generate()`는 3회차부터 더 못 고치도록 만들어 둔 가짜 모델입니다("실제로 흔한 일이다"라고 주석이 붙어 있죠).

| 회차 | 누적 비용 | 남은 항목 수 (점수) |
|---:|---:|---:|
| 1 | 22 | 3 |
| 2 | 44 | 2 |
| 3 | 66 | **2** |

`stalled()`는 `STALL_LIMIT + 1 = 3`개 창을 보고, 마지막 값이 앞선 최소값 이상이면 정체로 봅니다. 3회차에서 창이 `[3, 2, 2]`가 되고 `2 >= min(3, 2)`이므로 정체 판정. 출력은 이렇게 나옵니다.

```
끝난 이유  정체
회차       3 / 6
쓴 비용     66 / 90
점수 이력   [3, 2, 2]
남은 항목   ['## 조치', '## 재발 방지']
```

횟수 상한(6)만 있었다면 6회차까지 돌아 `6 × 22 = 132`를 썼을 겁니다. 정체 감지가 세 회차, 66을 아꼈어요. 그런데 **더 중요한 건 아낀 돈이 아니라 남긴 글자**입니다. `ending == "정체"` 덕분에, 이 실행이 "회차를 다 써서 끝난 것"이 아니라 "더 돌려도 안 되는 상태였다"는 게 호출부에 전달됩니다.

## 4. 이유별 대응 — 왜 불리언으로는 안 되나

예제 4가 마지막에 찍는 표가 이 카드의 정답 그 자체입니다.

| `ending` | 호출한 쪽의 대응 |
|---|---|
| **성공** | 그대로 쓴다 |
| **상한** | 사람에게 넘긴다 — **더 돌리면 될 수도 있다** |
| **예산** | 예산을 올릴지 물어본다 |
| **정체** | 사람에게 넘긴다 — **더 돌려도 안 된다** |

핵심은 **상한 vs 정체**입니다. 둘 다 "성공하지 못하고 끝났다"이지만, 자동 재시도 정책이 정반대입니다.

- **상한**: 점수가 계속 줄고 있었는데 회차 예산이 먼저 바닥났다. 상한을 올려 재개하면 성공할 가능성이 있다. 재시도가 **합리적**이다.
- **정체**: 회차는 남아 있는데 점수가 안 움직인다. 같은 조건으로 더 돌리면 **같은 결과에 돈만 더 쓴다.** 재시도가 **낭비**다. 프롬프트·도구·입력을 바꾸거나 사람이 개입해야 한다.

불리언 `done = True` 하나만 남기면 두 경우가 똑같이 보입니다. 그러면 호출부는 둘 중 하나를 고를 수밖에 없어요.

- 항상 재시도한다 → 정체 케이스에서 무한히 돈을 태운다. **20장이 처음부터 경고한 그 사고**입니다.
- 절대 재시도하지 않는다 → 상한 케이스에서, 한 번만 더 돌리면 끝날 일을 매번 사람에게 넘긴다.

`예산`과 `상한`도 마찬가지로 갈립니다. 예산은 "돈을 더 쓸지"가 사람의 결정 사항이라 물어봐야 하고, 상한은 대개 개발자가 정한 안전망이라 성격이 다릅니다.

## 5. "나중에 밖에서 계산하면 되지 않나"에 대한 답

호출부가 `rounds`, `cost`, `scores`를 다 받아서 직접 판정하면 되지 않냐고 할 수 있는데, 두 가지 문제가 있습니다.

**(1) 우선순위가 라우터 안에만 있다.** 멈추는 순간 여러 조건이 **동시에** 참일 수 있습니다. 회차도 6이고 정체이기도 한 상황요. `route()`는 성공 → 상한 → 예산 → 정체 순으로 검사하므로 그 경우 이유는 "상한"입니다. 밖에서 다시 판정하면 검사 순서가 조금만 달라도 다른 답이 나옵니다. 그리고 그건 `route()`의 로직을 호출부가 **중복 구현**하는 것이기도 하죠 — 임계값(`MAX_ROUNDS`, `MAX_COST`, `STALL_LIMIT`)까지 양쪽이 똑같이 알고 있어야 합니다.

**(2) 재개하면 사라진다.** 20장 20.5절에서 전역 예산을 전역 변수가 아니라 *상태*에 두라고 한 이유와 같습니다. `ending`도 상태에 있어야 체크포인터(`InMemorySaver`)에 함께 저장되고, 중단 후 재개했을 때 "지난번에 왜 끝났는지"가 남아 있습니다. 이 장 끝의 예고("죽었다 살아나도 상태가 남아 있어야 한다", 21장)가 이어지는 지점이에요.

여기에 운영상 이점이 하나 더 붙습니다. `ending`을 실행마다 기록해 두면 **집계**가 됩니다. 정체 비율이 높으면 모델·프롬프트·도구를 손볼 신호고, 예산 비율이 높으면 예산 배분(예제 3의 최소분 선점)을 다시 볼 신호입니다. 불리언 실패율만 보면 어느 쪽인지 알 수 없습니다.

## 6. 한 줄 정리

> 종료 조건이 넷이면 종료 결과도 넷이어야 한다. `ending`은 그 넷을 상태에 글자로 남겨, 호출한 쪽이 **상한이면 재시도, 정체면 사람**이라는 반대 방향의 결정을 내릴 수 있게 하는 필드다.
