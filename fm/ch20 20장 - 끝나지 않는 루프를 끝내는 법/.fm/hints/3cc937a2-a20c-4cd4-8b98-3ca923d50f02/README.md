# 정체 판정에서 '같음'도 정체로 보는 이유

**질문**: 정체 판정에서 '같음'도 정체로 보는 이유는 무엇인가?

**답**: 나빠지는 것만 잡으면 늦다. 개선이 멈춘 시점에 바로 끊어야 예산을 아낀다.

---

## 1. 한 줄로 표현된 설계 결정

20장 공통 모듈 `code/guards.py`의 `stalled()`가 이 결정을 그대로 담고 있습니다.

```python
def stalled(self) -> bool:
    """최근 stall_limit+1 개 점수가 나아지지 않았나.
    «같음»도 정체로 본다. 나빠지는 것만 잡으면 늦다."""
    n = self.stall_limit + 1
    if len(self.scores) < n:
        return False
    window = self.scores[-n:]
    best_before = min(window[:-1])
    return window[-1] >= best_before      # ← 여기. > 가 아니라 >=
```

핵심은 마지막 줄의 비교 연산자입니다.

- `>` 였다면: 「직전 최고 기록보다 **나빠졌을 때만**」 정체.
- `>=` 이므로: 「직전 최고 기록을 **못 넘겼을 때**」 정체. 즉 *같아도* 정체.

점수는 위반 건수라 **낮을수록 좋은 값**입니다. 그래서 `best_before = min(...)`이고
비교가 `>=` 방향입니다. 높을수록 좋은 척도라면 부호가 뒤집혀 `<=`가 됩니다.
실제로 `ex2_stall_detection.py`의 `stalled_at()`은 두 방향을 다 갖고 있습니다.

```python
worse = window[-1] <= best_before if higher_better else window[-1] >= best_before
```

양쪽 모두 **등호를 포함**합니다. 이게 이 장의 일관된 규칙입니다.

## 2. 왜 「나빠짐」만 잡으면 늦는가

루프가 실패하는 방식은 대개 「점점 나빠짐」이 아니라 **「어느 지점에서 멈춤」**입니다.
생성-검증 루프는 고칠 수 있는 걸 다 고치면 그다음부터는 같은 결과를 반복합니다.
나빠지지는 않아요. 그냥 **안 나아질 뿐**입니다.

그래서 `>` 로 판정하면 정체 조건이 **영원히 참이 되지 않고**, 루프는 결국
횟수 상한이나 예산 상한에 걸릴 때까지 돌면서 돈을 다 씁니다.
정체 감지를 붙여 놓고도 정체를 못 잡는 상태가 되는 거죠.

`ex1_four_guards.py`의 설명이 짚는 지점이 정확히 이겁니다.

> 실무에서 제일 아픈 건 «제자리걸음»이다.
> 횟수 상한만 있으면 안 될 일에 예산을 끝까지 쓰고 끝난다.

## 3. 근거 1 — ex4의 위반 3→2→2

`ex4_generator_critic.py`는 인시던트 리포트에 `## 개요 / ## 원인 / ## 조치 /
## 재발 방지` 네 절이 다 있는지 검증하는 루프입니다. 생성기는 의도적으로
**3회차부터는 더 못 고치도록** 만들어져 있습니다 (`if s["rounds"] < 2:` 조건).

```python
MAX_ROUNDS, MAX_COST, STALL_LIMIT = 6, 90.0, 2

def stalled(scores):
    n = STALL_LIMIT + 1
    if len(scores) < n:
        return False
    w = scores[-n:]
    return w[-1] >= min(w[:-1])          # guards.py 와 같은 >=
```

회차별로 따라가면 이렇습니다. (`STALL_LIMIT = 2` → 창 크기 3)

| 회차 | 채운 절 | 남은 위반 | 누적 비용 | `stalled()` 판정 |
|---|---|---|---|---|
| 1 | 개요 | **3** | 22 | 점수 1개 — 창이 안 참, `False` |
| 2 | 개요·원인 | **2** | 44 | 점수 2개 — 창이 안 참, `False` |
| 3 | (더 못 고침) | **2** | 66 | `w=[3,2,2]`, `2 >= min(3,2)=2` → **`True`** |

3회차에서 「**정체**」로 끝납니다. 점수 이력은 `[3, 2, 2]`.
`2 → 2`는 **나빠진 게 아니라 같은 값**입니다. `>=` 이기 때문에 잡힌 겁니다.

## 4. 근거 2 — 아낀 회차와 비용

같은 시나리오를 세 가지 설정으로 돌리면 이렇게 갈립니다.

| 설정 | 끝난 이유 | 회차 | 쓴 비용 | 점수 이력 |
|---|---|---|---|---|
| **`>=` (실제 코드)** | **정체** | **3** | **66** | `[3, 2, 2]` |
| `>` (나빠질 때만) | 예산 | 5 | 110 | `[3, 2, 2, 2, 2]` |
| 정체 감지 없이 횟수 상한만 | 상한 | 6 | 132 | `[3, 2, 2, 2, 2, 2]` |

예제 출력이 말하는 수치가 이 표의 첫 줄과 셋째 줄입니다.

> 횟수 상한만 있었다면 6회차까지 돌아 132를 썼을 것이다.
> 정체 감지가 세 회차를 아꼈다.

**3회차 절약, 비용 66 절약 (132 → 66, 정확히 절반).**

그리고 가운데 줄이 이 질문의 진짜 답입니다. `>` 였다면 정체를 아예 못 잡고
**2회차 더 돌아 44를 더 쓴 뒤 예산 상한에 걸려** 끝납니다.
`>=` 하나가 5회차/110을 3회차/66으로 줄인 셈입니다.

### 「늦다」에는 비용 말고 하나가 더 있다

`>` 로 돌린 경우 끝난 이유가 「정체」가 아니라 「**예산**」으로 기록됩니다.
`ex4`는 끝난 이유를 상태(`ending`)에 남기고, 호출한 쪽이 이유별로 다르게
대응하도록 설계돼 있습니다.

```
  성공 — 그대로 쓴다
  상한 — 사람에게 넘긴다 (더 돌리면 될 수도 있다)
  예산 — 예산을 올릴지 물어본다
  정체 — 사람에게 넘긴다 (더 돌려도 안 된다)
```

「예산」으로 잘못 기록되면 호출한 쪽은 **예산을 올려서 재시도**합니다.
그런데 실제 상황은 「더 돌려도 안 되는」 정체예요. 예산만 더 태우고 같은 자리에
다시 도착합니다. `>=` 를 `>` 로 바꾸는 순간 **돈만 새는 게 아니라 진단이 틀립니다.**

## 5. 근거 3 — ex2에서는 아예 못 멈춘다

`ex2_stall_detection.py`의 위반 건수 이력은 `9, 6, 4, 4, 4, 3` 입니다.
**한 번도 나빠지지 않고**, 중간에 `4, 4, 4`로 세 회차 제자리걸음만 합니다.

| 척도 | `>=` (실제 코드) | `>` (나빠질 때만) |
|---|---|---|
| 위반 건수 | **4회차에서 감지** | **안 멈춤** |
| 산출물 길이 | 안 멈춤 | 안 멈춤 |
| 모델 확신도 | 안 멈춤 | 안 멈춤 |

`>=` 로 보면 4회차 창 `[6, 4, 4]`에서 `4 >= min(6,4)=4` 가 참이 되어 잡힙니다.
`>` 로 보면 세 척도 모두 「안 멈춤」이 되어, 이 예제가 증명하려던
「위반 건수만 정체를 잡는다」는 결론 자체가 무너집니다.

즉 등호 포함은 편의 장치가 아니라, **단조 개선이 평평해지는 형태의 정체를
탐지할 수 있게 하는 유일한 조건**입니다.

## 6. 근거 4 — ex1의 제자리걸음

`ex1_four_guards.py`의 「제자리걸음」 시나리오는 점수가 `3, 3, 3, 3` 으로
완전히 평평합니다. `Guards` 기본값은 `max_rounds=5, max_cost=100.0`.

| 설정 | 끝난 이유 | 회차 | 쓴 비용 |
|---|---|---|---|
| **`>=` (실제 코드)** | **진전 없음** | **3** | **60** |
| `>` (나빠질 때만) | 횟수 상한 | 5 | 100 |

예제 설명의 「횟수 상한이었으면 **두 번 더 헛돌았을 것**」이 이 차이입니다.
**2회차 절약, 비용 40 절약.**

`>` 로는 점수가 절대 증가하지 않으므로 정체 판정이 한 번도 참이 되지 않고,
횟수 상한이 최종 방어선이 됩니다. `check()`의 검사 순서상 상한류가 먼저 걸리므로,
정체는 **상한에 닿기 전에 잡아야만 의미가 있는 조건**입니다.

```python
def check(self) -> Optional[str]:
    if self.rounds >= self.max_rounds:   return "횟수 상한"
    if self.cost >= self.max_cost:       return "예산 상한"
    if self.elapsed >= self.max_seconds: return "시간 상한"
    if self.stalled():                   return "진전 없음"
    return None
```

## 7. 정리 — 세 예제의 절약분

| 예제 | `>=` 결과 | `>` 또는 상한만 | 아낀 회차 | 아낀 비용 |
|---|---|---|---|---|
| ex4 (vs 횟수 상한만) | 정체 / 3회 / 66 | 상한 / 6회 / 132 | 3회 | 66 |
| ex4 (vs `>` 판정) | 정체 / 3회 / 66 | 예산 / 5회 / 110 | 2회 | 44 |
| ex1 제자리걸음 | 진전 없음 / 3회 / 60 | 횟수 상한 / 5회 / 100 | 2회 | 40 |
| ex2 위반 건수 | 4회차 감지 | 안 멈춤 | — | — |

## 8. 주의할 점 — 등호가 만드는 비용

`>=` 는 **공짜가 아닙니다.** 「한 회차 쉬었다가 다음 회차에 크게 개선되는」
루프를 조기에 끊을 수 있습니다. 이 위험을 흡수하는 장치가 `stall_limit` 입니다.

- `stall_limit = 2` → 창 크기 3 → **연속 2회 못 넘겨야** 정체.
- 한 번 정도의 정체는 그냥 통과합니다. ex4에서 `[3, 2]` 까지는 판정 자체를
  안 하는 것도 같은 이유(`if len(scores) < n: return False`)입니다.

즉 이 설계는 **「등호는 엄격하게, 대신 연속 횟수로 완충한다」**는 조합입니다.
등호를 빼서 관대하게 만드는 대신, 등호를 유지하고 창 크기로 관대함을 조절합니다.
이쪽이 튜닝 가능한 손잡이(`stall_limit`)를 하나 남겨 준다는 점에서 낫습니다.

또 하나. 등호 판정이 의미를 가지려면 점수가 **모델이 스스로 올릴 수 없는 값**이어야
합니다. ex2가 보여 주듯 산출물 길이나 모델 확신도는 계속 올라가기 때문에
`>=` 를 써도 정체가 잡히지 않습니다. **규칙으로 세는 값(위반 건수)** 이어야
「같음」이 실제로 발생하고, 그때 비로소 등호가 일을 합니다.

## 9. 한 줄 요약

정체의 전형적인 모습은 「악화」가 아니라 「**평탄화**」입니다.
`>` 는 평탄화를 통과시켜 루프를 상한까지 태우고, `>=` 는 평탄화가 시작된 회차에
바로 끊습니다. ex4 기준으로 그 차이가 **132 → 66 (절반)**, ex1 기준으로
**100 → 60**, ex2 기준으로는 **탐지 성공 vs 탐지 불가**입니다.
