# 전역 예산은 전역 변수가 아니라 상태에

> **Q.** 전역 예산을 전역 변수가 아니라 상태에 둬야 하는 이유는 무엇인가?
>
> **A.** 전역 변수에 두면 재개할 때 리셋된다.

출처: 20장 「끝나지 않는 루프를 끝내는 법」 20.5절 *곱하기를 아무도 안 한다*, `code/ex5_nested_loops.py` · `code/ex4_generator_critic.py`

---

## 1. 그 전에 — 전역 예산이 왜 필요한가

20장의 사고는 "상한이 없어서"가 아니라 **"상한이 층마다 따로 있어서"** 났습니다. `ex5_nested_loops.py`가 보여주는 그림입니다.

| 층 | 상한 | 자기 층에서 본 최대 |
|---|---:|---:|
| 바깥 루프 | 8 | 8회 |
| 안쪽 루프 | 6 | 8 × 6 = 48회 |
| 도구 재시도 | 5 | 8 × 6 × 5 = **240회** |

여덟 번, 여섯 번, 다섯 번. 각 층만 떼어서 리뷰하면 전부 합리적인 숫자입니다. 그런데 **곱하기를 아무도 안 합니다.** 240회 × 1.8원 = 432원어치 호출이 "층마다 상한이 다 걸린" 코드에서 나옵니다.

그래서 책의 처방은 이렇습니다.

> 층마다 상한을 두는 건 필요하다. 다만 그것만으로는 부족하다.
> **「전역 예산」을 하나 더 둬야 한다. 그리고 모든 층이 그걸 본다.**
> 전역 예산이 층 상한보다 먼저 걸리게 잡는 게 요령이다.
> 그러면 층 상한은 「안전망」이 되고 전역 예산이 「실질 제어」가 된다.

여기서 이번 카드의 질문이 나옵니다. **"모든 층이 보는 값"을 어디에 둘 것인가.**

## 2. 후보는 둘이다

"모든 층이 본다"는 요구만 놓고 보면 가장 손쉬운 답은 전역 변수입니다.

```python
# ✗ 손쉽지만 틀린 방법
_SPENT = 0.0
GLOBAL_BUDGET = 300.0

def call_model(prompt):
    global _SPENT
    if _SPENT >= GLOBAL_BUDGET:
        raise BudgetExceeded()
    _SPENT += cost_of(prompt)
    ...
```

모든 층이 import 한 줄로 접근할 수 있고, 인자로 들고 다닐 필요도 없습니다. 동작도 합니다 — **한 번에 끝까지 도는 실행에서는요.**

올바른 방법은 예산을 그래프 상태의 필드로 두는 것입니다. `ex4_generator_critic.py`가 정확히 그 형태입니다.

```python
class S(TypedDict):
    text:    str
    missing: list
    rounds:  Annotated[int, operator.add]     # 누적 회차
    cost:    Annotated[float, operator.add]   # ← 누적 비용이 상태 필드
    scores:  Annotated[list, operator.add]
    ending:  str

def route(s: S) -> str:
    if not s["missing"]:      return "성공"
    if s["rounds"] >= MAX_ROUNDS: return "상한"
    if s["cost"] >= MAX_COST:     return "예산"   # ← 상태에서 읽어서 판정
    if stalled(s["scores"]):      return "정체"
    return "생성"
```

`Annotated[float, operator.add]`는 19장에서 본 **리듀서**입니다. 노드가 `{"cost": 22.0}`를 돌려주면 덮어쓰기가 아니라 더하기가 되고, 그 결과가 슈퍼스텝마다 체크포인트에 저장됩니다.

## 3. 차이가 드러나는 순간 — 재개

두 방식의 차이는 정상 실행에서는 안 보입니다. **중단됐다가 다시 시작할 때** 갈립니다.

LangGraph에서 체크포인터를 붙이면(`b.compile(checkpointer=...)`) 슈퍼스텝이 끝날 때마다 **상태 채널의 값**이 `thread_id`별로 저장됩니다. 그리고 재개는 이런 모양입니다.

```python
cfg = {"configurable": {"thread_id": "gc"}}
app.invoke(초기상태, cfg)   # 도중에 인터럽트 / 예외 / 프로세스 종료
...
app.invoke(None, cfg)       # ← 마지막 체크포인트에서 이어서
```

이때 무엇이 복원되고 무엇이 안 되는지가 핵심입니다.

| | 복원되는가 | 왜 |
|---|---|---|
| `s["cost"]`, `s["rounds"]`, `s["scores"]` | **복원됨** | 체크포인트에 직렬화되어 들어 있음 |
| 모듈 전역 변수 `_SPENT` | **복원 안 됨** | 프로세스 메모리에만 존재. 체크포인트의 관심 밖 |
| `recursion_limit` 카운트 | **복원 안 됨** | 실행 단위 설정이라 호출마다 새로 셈 |

프로세스가 죽었다 살아나면 `_SPENT = 0.0`이라는 **모듈 초기화 코드가 다시 실행됩니다.** 상태에는 "이미 280원 썼다"가 남아 있는데, 예산 가드는 0원부터 다시 셉니다. 프로세스가 살아 있는 채로 재개하더라도 사정이 좋아지지 않습니다 — 인터럽트 후 재개 시 LangGraph는 **이미 완료된 노드를 다시 실행하지 않고 체크포인트의 결과를 씁니다.** 그러니 그 노드 안에 있던 `_SPENT += ...` 부수 효과는 재현되지도, 복원되지도 않습니다. 누적을 상태 밖에 두면 어느 쪽으로도 살아남지 못합니다.

여기서 제일 고약한 건 **하필 리셋되는 게 그 예산이라는 점**입니다. 재시도와 재개는 원래 "뭔가 잘못됐을 때" 일어납니다. 그러니까 가장 많이 태우고 있는 실행이 가장 자주 재개되고, 재개될 때마다 예산 카운터가 0으로 돌아갑니다. 세 번 죽었다 살아난 작업은 예산을 세 배 씁니다. 상한을 걸어 둔 목적 자체가 무너집니다.

`recursion_limit`도 같은 함정입니다. LangGraph의 내장 재귀 한도는 그 `invoke` 호출 안에서 센 슈퍼스텝 수라, 재개하면 다시 처음부터 셉니다. **상태 밖에 있는 카운터는 종류를 불문하고 재개에서 리셋된다**고 외워 두는 게 낫습니다.

## 4. 재개 말고도 깨지는 곳

카드의 정답은 재개지만, 같은 뿌리에서 나오는 문제가 몇 개 더 있습니다. 함께 알아 두면 "왜 상태인가"가 훨씬 선명해집니다.

- **스레드 격리가 없다.** 체크포인터는 `thread_id`별로 상태를 나눕니다. 전역 변수는 안 나눕니다. 사용자 A의 루프가 태운 비용이 사용자 B의 예산을 깎고, 한 명이 폭주하면 전원이 차단됩니다. 반대로 서버를 재시작하면 전원의 누적이 동시에 사라집니다.
- **워커가 여러 개면 값이 흩어진다.** 프로세스/컨테이너가 여러 대면 전역 변수는 대당 하나씩입니다. 4대면 실효 예산이 4배가 됩니다 — 240회 사고와 같은 종류의 곱하기입니다.
- **병렬 분기에서 경합한다.** 같은 슈퍼스텝의 분기들이 동시에 `_SPENT +=`를 하면 갱신이 유실될 수 있습니다. 상태 필드면 `operator.add` 리듀서가 병합 규칙을 명시적으로 정해 줍니다(19장).
- **타임 트래블이 어긋난다.** 체크포인트를 되감아 다른 분기를 태워 보면 `s["cost"]`는 그 시점 값으로 함께 되감기지만 전역 변수는 그대로입니다. 상태와 카운터가 서로 다른 과거를 가리키게 됩니다.
- **디버깅이 안 된다.** 상태에 있으면 체크포인트를 열어 "이 실행이 어디서 얼마를 썼나"를 그대로 볼 수 있습니다. 전역 변수는 죽는 순간 증거가 함께 사라집니다.

같은 이유로 20장은 **끝난 이유(`ending`)도 상태에 남기라**고 합니다. "상한"과 "정체"는 대응이 다르니까요(상한은 더 돌리면 될 수도 있고, 정체는 더 돌려도 안 됩니다). 예산이든 종료 사유든, **작업에 대한 사실은 프로세스가 아니라 작업에 붙어 있어야 한다**는 원칙 하나입니다.

## 5. 그런데 상태에 두면 정말 이어지는가 — 21장으로

여기까지가 20장의 결론이고, 동시에 20장이 **가정을 하나 깔고 있다**는 고백이기도 합니다.

> **다음 장에서 뒤집히는 것:** 이 장에서 「재개하면 예산이 이어진다」를 전제로 얘기했습니다. 그러려면 죽었다 살아나도 상태가 남아 있어야 해요. 다음 장이 그 이야기입니다.

`ex4_generator_critic.py`가 쓰는 체크포인터를 다시 보세요.

```python
from langgraph.checkpoint.memory import InMemorySaver
app = b.compile(checkpointer=InMemorySaver())
```

`InMemorySaver`는 **이름 그대로 프로세스 메모리에 저장합니다.** 같은 프로세스 안에서 여러 번 `invoke`를 이어 부르는 데는 충분하지만, 프로세스가 죽으면 체크포인트도 같이 죽습니다. 즉 예산을 상태로 옮겨 놓기만 하고 체크포인터가 인메모리면, **저장 위치만 바뀌었을 뿐 결과는 전역 변수와 똑같이 리셋됩니다.**

그래서 이 카드의 답은 완결이 아니라 절반입니다.

1. 예산을 **상태 필드**로 옮긴다 (20장 — 재개할 때 읽을 곳이 생긴다)
2. 그 상태를 **프로세스 밖에 영속**시킨다 (21장 — 재개할 때 실제로 남아 있다)

21장 제목이 「프로세스가 죽어도 작업은 살아 있어야 한다」인 이유고, 실무에서 `InMemorySaver`를 SQLite/Postgres 계열 지속 체크포인터로 바꾸는 이유입니다. 둘이 갖춰져야 비로소 "재개하면 예산이 이어진다"가 사실이 됩니다.

## 6. 한 줄 정리

> 전역 예산은 **실행이 아니라 작업에 속한 사실**입니다. 전역 변수는 실행(프로세스)에 붙어 있어서 재개할 때 리셋되고, 상태는 작업(thread)에 붙어 있어서 체크포인트와 함께 이어집니다.

### 자가 점검

- [ ] 층 상한을 다 곱해 봤는가. 그 값이 감당 가능한가
- [ ] 전역 예산이 층 상한 곱보다 **먼저** 걸리게 잡혀 있는가
- [ ] 누적 비용/회차가 그래프 **상태 필드**에 있는가 (모듈 전역·싱글턴·클래스 변수가 아니라)
- [ ] 누적 필드에 `operator.add` 같은 **리듀서**가 붙어 병렬 분기에서도 합쳐지는가
- [ ] 체크포인터가 프로세스 재시작을 견디는가 (`InMemorySaver`면 아직 아니다 → 21장)
- [ ] `recursion_limit`처럼 **호출 단위로 리셋되는 카운터**에 예산 방어를 의존하고 있지 않은가
- [ ] 끝난 이유(`ending`)가 상태에 남아, 호출한 쪽이 「상한」과 「정체」를 구분해 대응할 수 있는가
