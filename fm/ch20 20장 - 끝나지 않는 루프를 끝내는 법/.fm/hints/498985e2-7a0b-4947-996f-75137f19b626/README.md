# `ex5_nested_loops.py` — 층별 상한 5·4·3은 총 몇 회인가

## 정답

**5 × 4 × 3 = 60회.**

각 층은 자기 상한만 보기 때문에, 이 곱셈을 계산하는 주체가 코드 어디에도 없습니다.
`COST_PER_CALL = 1.8`원이므로 60회면 108원. 이 자체는 크지 않아 보이지만,
숫자를 조금씩만 올려도 폭발합니다(아래 표).

---

## 1. ex5의 3층 구조 — 각 층이 무엇을 반복하는가

```python
OUTER, INNER, TOOL = 5, 4, 3        # 각 층의 상한
COST_PER_CALL = 1.8                 # 원


def counts():
    """각 층이 «자기 상한»만 보면 총 호출이 몇 번이 되나."""
    return OUTER, OUTER * INNER, OUTER * INNER * TOOL
```

`counts()`가 돌려주는 세 값이 곧 「층별 누적 최대 호출 수」입니다.

| 층 | 상수 | 무엇을 반복하는가 | 자기 층 상한 | 누적 최대 호출 |
|---|---|---|---|---|
| 1층 — 바깥 루프 | `OUTER = 5` | 과제 단위 재시도. 「이 작업을 다시 처음부터」 | 5 | `5` = **5회** |
| 2층 — 안쪽 루프 | `INNER = 4` | 바깥 1회분 안에서 도는 생성-검증 회차 | 4 | `5 × 4` = **20회** |
| 3층 — 도구 재시도 | `TOOL = 3` | 안쪽 1회차 안에서 도구 호출이 실패했을 때의 재시도 | 3 | `5 × 4 × 3` = **60회** |

`main()`이 그대로 찍어 주는 출력이 이 표입니다.

```python
o, i, t = counts()
print("층마다 상한을 따로 둔 경우")
print(f"    바깥 루프  상한 {OUTER}  → 최대 {o}회")
print(f"    안쪽 루프  상한 {INNER}  → 최대 {i}회")
print(f"    도구 재시도 상한 {TOOL}  → 최대 {t}회")
print(f"\n    총 모델 호출 최대 {t}회, 값 {t * COST_PER_CALL:,.0f}원")
```

즉 상한이 **더해지는 게 아니라 곱해집니다.** 5 + 4 + 3 = 12가 아니라 5 × 4 × 3 = 60.
직관은 덧셈 쪽으로 기울고, 실제 시스템은 곱셈으로 굴러갑니다. 여기서 오차가 5배 납니다.

### 상한을 하나씩만 올리면

```python
for o2, i2, t2 in ((5, 4, 3), (6, 4, 3), (5, 5, 3), (5, 4, 4), (8, 6, 5)):
    n = o2 * i2 * t2
```

| 바깥 | 안쪽 | 도구 | 총 호출 | 값 |
|---:|---:|---:|---:|---:|
| 5 | 4 | 3 | 60 | 108원 |
| 6 | 4 | 3 | 72 | 130원 |
| 5 | 5 | 3 | 75 | 135원 |
| 5 | 4 | 4 | 80 | 144원 |
| 8 | 6 | 5 | **240** | **432원** |

주목할 지점은 마지막 줄입니다. 8, 6, 5는 **각 층에서 따로 보면 전부 합리적인 숫자**입니다.
「여덟 번까지는 다시 해 봐야지」, 「여섯 번이면 충분히 고칠 시간」, 「도구는 다섯 번쯤 재시도」.
셋 다 어떤 리뷰어도 지적하지 않을 값이에요. 그런데 곱하면 240회, 432원입니다.
장 도입부의 "층마다 상한을 다 걸어 뒀는데 240번을 돌았습니다"가 바로 이 줄입니다.

## 2. 「각 층은 자기 상한만 본다」 — 국소성이 리뷰에서 안 잡히는 이유

이 버그의 성질은 **어느 파일에도 버그가 없다**는 것입니다.

```python
# 파일 A — 바깥 루프
for attempt in range(OUTER):        # 5. 타당하다.
    ...

# 파일 B — 안쪽 루프
for round_ in range(INNER):         # 4. 타당하다.
    ...

# 파일 C — 도구 래퍼
for retry in range(TOOL):           # 3. 타당하다.
    ...
```

리뷰에서 안 잡히는 이유는 세 가지가 겹칩니다.

1. **국소적으로는 전부 옳다.**
   리뷰는 diff 단위, 파일 단위, PR 단위로 이뤄집니다. 각 층 코드를 따로 보면
   「상한이 걸려 있고, 값도 상식적이다」로 통과합니다. 결함이 *코드 안*이 아니라
   *코드 사이의 관계*에 있어서, 어느 한 곳을 봐도 보이지 않아요.

2. **곱셈을 계산하는 주체가 없다.**
   `OUTER * INNER * TOOL`이라는 식이 프로덕션 코드에 등장하지 않습니다.
   ex5의 `counts()`는 그 곱셈을 **일부러 눈앞에 꺼내 놓으려고** 쓴 함수예요.
   실제 코드에는 이 함수가 없죠. 계산되지 않는 값은 리뷰될 수도 없습니다.

3. **각 층은 서로의 존재를 모른다.**
   도구 재시도 래퍼는 자기가 안쪽 루프 안에서 불린 건지, 바깥 루프가 몇 겹인지 모릅니다.
   호출 스택 위쪽 정보가 없으니 「내가 이번 작업 전체에서 몇 번째 호출인가」를
   물어볼 방법 자체가 없어요. 국소적 정보만으로는 전역 상한을 지킬 수 없습니다.

거기에 층이 늘어날 때마다 문제가 **곱해집니다.** 네 번째 층(예: 서브에이전트 위임)이
나중에 상한 3으로 추가되면, 그 PR은 「상한 3을 걸었다」는 안전해 보이는 diff지만
실제로는 총 호출을 60에서 180으로 세 배 늘립니다. diff만 봐서는 절대 안 보이는 3배입니다.

```
"각 층 코드를 따로 리뷰하면 아무 문제가 없어 보인다. 곱하기를 아무도 안 했다."
```

## 3. 곱셈 결과를 드러내는 방법 — 전역 카운터/예산

해법은 층 상한을 없애는 게 아닙니다. **곱셈이 실제로 계산되는 지점을 하나 만드는 것**입니다.
그 지점이 전역 예산(또는 전역 카운터)입니다.

```python
def with_global_budget(budget):
    """전역 예산이 있으면 실제로 몇 번까지 가나."""
    return int(budget / COST_PER_CALL)
```

| 전역 예산 | 최대 호출 | 층 상한 곱(240회)과 비교 |
|---:|---:|---|
| 100원 | 55회 | 적다 |
| 300원 | 166회 | 적다 |
| 1000원 | 555회 | 많다 |

핵심은 **전역 예산이 층 상한보다 먼저 걸리게** 값을 잡는 것입니다.

```
전역 예산이 층 상한보다 먼저 걸리게 잡는 게 요령이다.
그러면 층 상한은 «안전망»이 되고 전역 예산이 «실질 제어»가 된다.
```

- 위 표에서 예산 100원(55회)과 300원(166회)은 240회보다 작으므로 **실질 제어**로 동작합니다.
- 1000원(555회)은 240회보다 크므로 층 상한이 먼저 걸립니다 — 전역 예산이 사실상 무력해집니다.
  「전역 예산을 뒀다」는 사실만으로는 부족하고, **곱보다 작게** 잡아야 의미가 생깁니다.

### 역할 분담이 뒤바뀌는 것

| | 전역 예산 없음 | 전역 예산 있음 |
|---|---|---|
| 층 상한 | 유일한 제어. 곱해져서 폭주 | **안전망**. 한 층이 미쳐도 그 층만 막음 |
| 전역 예산 | 없음 | **실질 제어**. 총량을 단일 지점에서 결정 |
| 리뷰 대상 | 층별 숫자 3개(관계는 안 보임) | 총량 숫자 1개(값이 곧 상한) |

전역 예산의 진짜 이득은 비용 절감이 아니라 **관측 가능성**입니다.
총 상한이 하나의 숫자로 코드에 적히면, 그때부터 리뷰어가 그 숫자를 볼 수 있습니다.
층별 3개는 볼 수 없었죠 — 곱해야만 보이는데 아무도 곱하지 않으니까요.

### 구현 시 반드시 지킬 것 — 예산은 전역 변수가 아니라 *상태*에 둔다

이 장 요약이 명시적으로 경고합니다.

```
층마다 상한을 둬도 곱하면 커집니다. 전역 예산을 하나 더 두고 모든 층이 보게 하세요.
그리고 그 예산은 전역 변수가 아니라 «상태»에 둡니다. 안 그러면 재개할 때 리셋됩니다.
```

모듈 레벨 전역 변수나 프로세스 메모리에 카운터를 두면, 프로세스가 죽었다 재개될 때
0으로 돌아갑니다. 그러면 「예산 90원 쓰고 죽음 → 재개 → 다시 0부터 90원」으로
예산이 무한히 재충전되는, 원래 문제보다 더 나쁜 상황이 됩니다.
`ex4_generator_critic.py`가 보여 주는 방식대로, 누적값을 그래프 상태에 리듀서로 얹어야 합니다.

```python
class S(TypedDict):
    rounds:  Annotated[int, operator.add]
    cost:    Annotated[float, operator.add]      # ← 체크포인트에 함께 저장된다
    ending:  str
```

그리고 모든 층의 라우터가 이 하나의 `cost`를 봅니다.

```python
def route(s: S) -> str:
    if not s["missing"]:      return "성공"
    if s["rounds"] >= MAX_ROUNDS: return "상한"
    if s["cost"] >= MAX_COST:     return "예산"   # ← 층에 상관없이 같은 값을 본다
    if stalled(s["scores"]):      return "정체"
    return "생성"
```

`ending`에 「상한」과 「예산」을 구분해 남기는 것도 함께 중요합니다.
「층 상한에 걸림」과 「전역 예산 소진」은 대응이 다르기 때문입니다
(전자는 그 층만 조정, 후자는 총량 재협의).

## 4. 한 줄 정리

> 5·4·3은 **60회**다. 각 층은 자기 상한만 보고, 그 곱을 계산하는 코드가 없기 때문에
> 리뷰에서도 곱셈이 일어나지 않는다. 곱을 드러내는 유일한 방법은 모든 층이 함께 보는
> 전역 예산을 **상태에** 하나 두고, 그 값을 층 상한의 곱보다 작게 잡는 것이다.
