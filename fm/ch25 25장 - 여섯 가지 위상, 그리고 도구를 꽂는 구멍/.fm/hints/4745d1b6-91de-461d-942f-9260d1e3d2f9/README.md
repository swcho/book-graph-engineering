# 좋은 도구 설명에 들어가야 할 세 가지

**질문**: 좋은 도구 설명에 들어가야 할 세 가지는 무엇인가?

**답**: 무엇을 주는지(반환값), 어떤 말로 물었을 때 이것인지(사용자 어휘), 언제 안 쓰는지(경계)다.
셋째가 제일 자주 빠지고 제일 크게 듣는다.

---

## 0. 먼저, 왜 「설명」이 그렇게 중요한가

25.5절의 제목이 답입니다. **「도구 설명이 곧 엣지 선택 함수다」.**

에이전트 그래프에서 도구는 그래프 밖으로 나가는 엣지입니다(25.4절). 그런데 그 엣지를
고를 때 모델이 보는 것은 구현 코드가 아닙니다. 이름과 `description`과 입력 스키마,
이 세 문자열뿐입니다. 즉

- 노드 사이의 엣지 선택은 **코드**가 정한다 (`if score > 0.8: goto verify`)
- 도구 엣지의 선택은 **산문**이 정한다 (`"이름으로 사람 한 명을 찾는다..."`)

그래서 도구 설명은 문서가 아니라 코드입니다. 로직이 자연어로 적혀 있는 것이고,
그 문장을 고치는 것이 곧 분기 조건을 고치는 것입니다.
예제 5(`ex5_tool_selection.py`)는 이걸 실험으로 보여 줍니다. **파이썬 코드는 한 줄도
안 고치고 설명 문자열만 바꿔서** 도구 선택 정확도를 올립니다.

## 1. 예제 5가 실제로 한 실험

같은 도구 셋(`find_person`, `chain_of_command`, `team_members`)에 대해 설명만 두 벌
준비하고, 같은 질문 8개를 던집니다.

**나쁜 설명 (BAD)** — 명사 두 단어짜리

```python
BAD = {
    "find_person":      "사람 조회",
    "chain_of_command": "체인 조회",
    "team_members":     "팀 조회",
}
```

**좋은 설명 (GOOD)** — 세 가지가 들어간 것

```python
GOOD = {
    "find_person":
        "사람 «한 명»을 이름으로 찾는다. 이름, 소속 팀, 상사 아이디를 준다. "
        "여러 명을 찾을 때는 쓰지 않는다.",
    "chain_of_command":
        "한 사람의 «위로 올라가는» 보고 체계를 뿌리까지 준다. "
        "상사, 상사의 상사, 보고 라인, 결재선을 물으면 이것이다. "
        "아래 부하 목록에는 쓰지 않는다.",
    "team_members":
        "팀 이름을 주면 그 팀 구성원 «전부»를 목록으로 준다. "
        "명단, 누구누구, 구성원, 몇 명을 물으면 이것이다.",
}
```

선택기는 아주 멍청합니다. 질문과 설명의 **단어 겹침 개수**를 세는 게 전부입니다.

```python
def choose(query, descriptions):
    q = tokenize(query)
    best, score = None, -1
    for name, desc in descriptions.items():
        overlap = len(q & tokenize(desc))
        if overlap > score:
            best, score = name, overlap
    return best
```

그런데도 결론은 그대로 통합니다. 설명만 바꿔서 정확도가 올라가고, 남은 오답 하나가
정확히 「사용자 어휘」 항목이 왜 필요한지를 가리킵니다(3절에서).

> 여기 쓴 선택기는 모델보다 훨씬 멍청하다. 그런데 「설명이 나쁘면 못 고른다」는
> 성질은 모델도 같다.

## 2. 세 가지를 하나씩

### (1) 무엇을 「주는지」 — 반환값을 말한다

모델이 도구를 고르는 이유는 「그 도구가 뭘 하는가」가 아니라 **「내가 지금 필요한 값을
그게 주는가」**입니다. 그러니 설명은 동작이 아니라 산출물을 말해야 합니다.

| 나쁨 | 좋음 |
|---|---|
| 「사람 조회」 | 「사람 한 명을 이름으로 찾는다. **이름, 소속 팀, 상사 아이디를 준다**」 |
| 「체인 조회」 | 「위로 올라가는 보고 체계를 **뿌리까지 준다**」 |
| 「팀 조회」 | 「그 팀 구성원 **전부를 목록으로 준다**」 |

반환값을 적어 두면 부수 효과가 하나 더 생깁니다. **도구를 이어 붙이는 판단**이
가능해집니다. 예제 4에서 클라이언트는 `find_person` → `chain_of_command` 순서로
호출하는데, 이게 가능한 이유는 `find_person`이 「상사 아이디」를 준다고 적혀 있어서
다음 도구의 입력이 어디서 오는지 보이기 때문입니다. 반환값을 안 적으면 모델은
한 번에 한 걸음씩만 볼 수 있습니다.

또 **개수(카디널리티)**를 명시하세요. 「한 명」인지 「전부」인지. 이 한 단어가
`find_person`과 `team_members`를 갈라 줍니다.

### (2) 어떤 「말」로 물었을 때 이것인지 — 사용자 어휘를 넣는다

여기서 설명은 사전 정의를 벗어나 **호출 트리거 목록**이 됩니다.

```
"상사, 상사의 상사, 보고 라인, 결재선을 물으면 이것이다."
"명단, 누구누구, 구성원, 몇 명을 물으면 이것이다."
```

기술 문서라면 「누구누구」 같은 말은 안 쓰겠죠. 그런데 이건 문서가 아니라
매칭 규칙입니다. 사용자는 우리 스키마 용어로 묻지 않고 자기 말로 묻습니다.

> 우리는 사내 용어로 쓰고, 사용자는 자기 말로 묻는다.

동의어를 나열하는 게 촌스러워 보여도 이게 듣습니다. 가장 좋은 재료는 상상이 아니라
**실제 질문 로그**입니다. 로그에서 표현을 뽑아 설명에 심으세요.

### (3) 언제 「안」 쓰는지 — 경계를 긋는다

```
"여러 명을 찾을 때는 쓰지 않는다."      # find_person
"아래 부하 목록에는 쓰지 않는다."        # chain_of_command
```

이게 **제일 자주 빠지고 제일 크게 듣는** 항목입니다. 이유는 두 가지입니다.

**첫째, 도구 하나만 있을 때는 필요가 없어 보입니다.** 도구가 하나면 고를 것도 없으니
「안 쓰는 경우」를 적을 동기가 없습니다. 그런데 도구가 5개, 20개로 늘면 반드시
**비슷한 도구**가 생깁니다. `find_person` vs `team_members`, `chain_of_command` vs
`direct_reports` 처럼요. 이때 정확도를 만드는 건 각 도구가 무엇인지가 아니라,
**둘 사이의 선이 어디인지**입니다.

**둘째, 선택은 절대 평가가 아니라 비교입니다.** 모델은 도구 하나를 보고 「맞다/아니다」를
판정하는 게 아니라, 후보 전체를 나란히 놓고 제일 그럴싸한 것을 고릅니다. 그래서
「나는 이런 걸 안 한다」는 한 줄이 **다른 도구를 이기게 해 주는 장치**로 작동합니다.
경계를 그은 도구는 자기 영역이 아닌 질문에서 스스로 물러나고, 옆 도구가 이깁니다.

> 도구가 늘어날수록 「비슷한 도구」가 생기고, 그때 경계를 그어 둔 쪽이 이긴다.

세 번째 항목은 26장(「무엇을 못 하게 할 것인가」)으로도 이어집니다. 못 하게 하는 일이
하게 하는 일보다 어렵다는 얘기의 예고편이 이 한 줄입니다.

## 3. 남은 오답 하나가 제일 중요하다

좋은 설명을 써도 예제 5는 「박민수 상급자 알려줘」를 못 맞힙니다.

- 설명에는 「**상사**」가 있고
- 사용자는 「**상급자**」라고 물었습니다

단어가 안 겹치니 못 고릅니다. 이게 (2)번 항목이 존재하는 이유이고, 도구 설명을 쓸 때
제일 자주 놓치는 지점입니다. 대응은 동의어를 설명에 밀어 넣는 것입니다.

```
상사 · 상급자 · 윗사람 · 결재선 · 보고 라인 · 위에 누가
```

주의할 점: 이건 「모델이 멍청해서」 생기는 문제가 아닙니다. 진짜 LLM은 임베딩 공간에서
「상사」와 「상급자」를 가깝게 보니 예제보다 잘합니다. 그러나 **도구가 20개고 그중
셋이 서로 비슷할 때**, 모델도 결국 설명에 적힌 표현을 근거로 갈라야 합니다.
어휘가 겹치지 않으면 모델도 같은 방식으로 틀립니다. 정도의 차이일 뿐 성질은 같습니다.

## 4. 체크리스트로 접어 두기

새 도구를 등록할 때 설명 한 문장에 이 세 칸이 다 찼는지 봅니다.

| # | 항목 | 자문 | 잘 빠지는 정도 |
|---|---|---|---|
| 1 | 반환값 | 이걸 부르면 **무엇이 손에 들어오나?** 몇 개인가? | 보통 |
| 2 | 사용자 어휘 | 사용자는 이걸 **어떤 말로** 부르나? 동의어를 적었나? | 자주 |
| 3 | 경계 | **언제 이걸 쓰면 안 되나?** 옆의 비슷한 도구는 뭔가? | **제일 자주** |

그리고 이 세 칸은 그냥 취향이 아니라 검증 가능한 것입니다. 예제 5처럼 **질문 →
정답 도구** 쌍을 몇십 개 모아 두면 설명을 고칠 때마다 정확도를 잴 수 있습니다.
25.3절에서 「라우터를 넣기 전에 채점 데이터셋을 먼저 만들라」고 한 것과 완전히 같은
얘기입니다. 도구 선택도 라우팅이니까요.

## 5. 한 줄로

도구 설명은 남이 읽을 문서가 아니라 **모델이 실행할 엣지 선택 함수**입니다.
반환값으로 「무엇을 받나」를, 사용자 어휘로 「어떻게 불리나」를, 경계로 「누가 아닌가」를
적으세요. 셋 중 마지막 하나가 도구 수가 늘어난 뒤에 시스템을 살립니다.
