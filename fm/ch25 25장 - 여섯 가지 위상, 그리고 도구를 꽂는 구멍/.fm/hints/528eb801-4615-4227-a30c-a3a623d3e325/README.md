# MCP에서 서버에 도구를 추가하면 클라이언트를 고쳐야 하는가?

**답**: 고치지 않아도 된다. 지연 결합(late binding)되는 서브그래프이며, 엣지 목록을 실행 시점에 받아 오는 구조다.

---

## 1. 왜 안 고쳐도 되나 — 클라이언트가 «도구 정의»를 갖고 있지 않다

25장 예제 4(`ex4_mcp_client.py`)의 핵심은 코드 한 줄이 아니라 **없는 코드**다.

```python
tools = (await s.list_tools()).tools
print(f"서버가 알려 준 도구 {len(tools)}개\n")
for t in tools:
    req = t.inputSchema.get("required", [])
    props = ", ".join(t.inputSchema.get("properties", {}))
```

클라이언트 어디에도 `find_person`, `chain_of_command`, `team_members`의 **정의**가 없다. 이름·설명·`inputSchema`(파라미터, 필수 필드)를 전부 `list_tools()`로 **받아 온다**. 도구 정의가 있는 곳은 서버 쪽(`mcp_server.py`)이고, 거기서는 데코레이터와 독스트링이 곧 스키마다.

```python
@mcp.tool()
def chain_of_command(person_id: str) -> list:
    """그 사람 위로 올라가는 보고 체계를 뿌리까지 반환한다."""
```

예제의 결론 문단이 이 비대칭을 정확히 집는다.

> 여기서 클라이언트 코드는 도구 이름을 «세 번» 말했다.
> 그런데 도구의 «정의»는 한 번도 안 갖고 있다. 서버가 준 것을 그대로 쓴다.
> 그래서 서버에 도구를 하나 추가하면 클라이언트는 안 고쳐도 된다.

즉 클라이언트가 하는 일은 「어떤 도구가 있는지 아는 것」이 아니라 「어떤 도구가 있는지 **물어보는 것**」이다. 물어보는 코드는 도구 개수와 무관하게 그대로다. `@mcp.tool()` 하나를 서버에 더 붙이면, 다음 `list_tools()` 응답에 항목이 하나 늘어날 뿐이고 루프는 4개를 돌 뿐이다.

## 2. 두 가지 언어로 같은 말 하기

| 관점 | 표현 |
|---|---|
| 2장(결합 시점)의 말 | 도구는 **지연 결합되는 서브그래프**다 |
| 그래프의 말 | **엣지 목록을 실행 시점에 받아 오는 것**이다 |

25.4절의 명제는 「도구는 그래프 밖으로 나가는 엣지다」였다. 노드가 바깥 세상(DB, 사내 API, 파일시스템)에 손을 뻗는 통로가 엣지이므로, **도구 목록 = 이 노드에서 나갈 수 있는 엣지의 집합**이다.

그러면 질문은 이렇게 번역된다. *엣지 집합을 언제 확정하는가?*

- **이른 결합(early binding)**: 코드에 도구 스키마를 박아 둔다. 엣지 집합이 컴파일/배포 시점에 확정된다. 도구가 늘면 클라이언트 코드가 바뀌고 재배포된다.
- **지연 결합(late binding)**: 엣지 집합을 런타임에 조회한다. `initialize` → `list_tools` 핸드셰이크 시점에야 그래프의 모양이 정해진다.

MCP는 후자다. 그래서 「같은 클라이언트가 다른 서버에 붙으면 다른 도구를 갖게 된다」(예제 4 독스트링)가 성립한다. 클라이언트는 도구의 목록이 아니라 **도구를 얻는 프로토콜**에만 의존한다.

## 3. 배포 관점 — 서버만 갱신하면 되는 이유

지연 결합의 실질적 이득은 **배포 단위가 쪼개진다**는 것이다.

```
[이른 결합]  도구 1개 추가 → 서버 수정 + 클라이언트 수정 + 양쪽 재배포 + 버전 정렬
[지연 결합]  도구 1개 추가 → 서버만 수정 + 서버만 재배포. 클라이언트는 그대로.
```

이유를 단계로 쪼개면:

1. **의존 방향이 한쪽이다.** 클라이언트 → 서버로만 의존한다. 서버는 클라이언트가 몇 종류인지, 누가 붙어 있는지 알 필요가 없다.
2. **계약이 데이터다.** 도구 계약(이름·설명·JSON Schema)이 코드가 아니라 **응답 payload**로 전달된다. 데이터가 바뀌는 것은 재컴파일 사유가 아니다.
3. **호출 경로가 일반화되어 있다.** 클라이언트는 `call_tool(name, args)`라는 하나의 진입점만 갖는다. 도구마다 전용 함수를 만들지 않으므로 도구가 늘어도 분기 코드가 늘지 않는다.
4. **선택은 모델이 한다.** 어느 엣지를 탈지는 하드코딩된 `if`가 아니라 도구 설명을 읽은 모델이 정한다(25.5절: 도구 설명 = 엣지 선택 함수). 새 도구의 설명만 잘 써 두면 클라이언트 로직을 건드리지 않고도 그 도구가 «선택 후보»에 들어간다.
5. **알림 채널이 있다.** MCP는 목록 변경을 알리는 통지(`tools/list_changed`)를 정의한다. 장수명 세션에서도 다시 붙지 않고 목록을 새로고침할 수 있으니, 서버 갱신이 클라이언트 재시작을 강제하지 않는다.

실무 그림으로 말하면: 사내 그래프 조회 도구를 늘릴 때 데스크톱 클라이언트/에이전트 앱을 사내 수백 명에게 다시 배포하는 대신, MCP 서버 한 프로세스만 롤아웃하면 끝난다. 이것이 지연 결합으로 **얻는 것**이다.

## 4. 대가 — 컴파일 시점에 아무것도 모른다

같은 예제가 곧바로 값을 말한다.

> 대신 값을 치른다. 서버가 무엇을 줄지 컴파일 시점에 모른다.
> 도구 이름이 바뀌면 실행할 때 터진다.

이건 우연한 단점이 아니라 **정확히 같은 성질의 뒷면**이다. 「엣지 집합을 미리 확정하지 않는다」는 이득의 정의가, 곧 「엣지 집합을 미리 검사할 수 없다」는 손실의 정의다. 잃는 것을 나열하면:

- **정적 검증이 사라진다.** 타입 체커·린터·IDE 자동완성이 도구 이름과 인자 이름을 검사해 주지 못한다. `s.call_tool("find_person", {"name": ...})`의 문자열은 컴파일러에게 그냥 문자열이다.
- **오류가 늦게, 그리고 사용자 앞에서 터진다.** 서버가 `find_person`을 `lookup_person`으로 리네임하면 빌드는 초록불인데 런타임에 실패한다. 실패 지점이 배포 파이프라인이 아니라 실사용 세션이다.
- **버전 스큐가 조용히 생긴다.** 클라이언트는 옛 이름을 세 번 말하는데 서버는 새 이름을 준다. 아무도 안 고쳤는데 깨진다(코드는 그대로인데 상대가 바뀌었기 때문).
- **테스트 대상이 흐릿해진다.** 「도구 3개짜리 서버」를 가정한 테스트는 서버가 5개를 주는 세계에서 무엇을 보증하는지 애매해진다.
- **신뢰 경계가 넓어진다.** 설명과 스키마가 외부에서 들어온 텍스트다. 즉 모델의 행동을 좌우하는 입력이 배포 관리 밖에 있다.
- **비용/컨텍스트가 새어 나간다.** 서버가 도구를 늘리는 것만으로 프롬프트에 실리는 도구 정의가 늘고, 후보가 비슷비슷해져 선택 정확도가 떨어질 수 있다.

## 5. 그래서 무엇을 하나 — 검증 시점을 앞으로 당긴다

컴파일 시점의 안전망을 없앤 대신, **시작 시점에 직접 만든다**. 25장 한 장 요약의 마지막 문장이 처방이다.

> 대가는 컴파일 시점에 아무것도 모른다는 것이에요. **시작할 때 목록을 검증하세요.**

구체적으로는:

- 세션을 열자마자 `list_tools()` 결과에 **내가 부를 이름들이 있는지** 확인하고, 없으면 그 자리에서 큰 소리로 실패한다(런타임 중간이 아니라 부팅 때).
- 이름만 보지 말고 `inputSchema`의 `required`/`properties`까지 대조한다. 이름은 같은데 인자가 바뀌는 변화가 더 고약하다.
- 없는 도구를 **없다고 알고** 우아하게 축퇴하는 경로를 둔다(기능 플래그처럼).
- 서버 쪽은 리네임을 «호환 유지 후 폐기»로 굴린다. 이름은 사실상 공개 API다.

## 6. 자주 나오는 오해

- **「지연 결합이면 아무것도 안 해도 알아서 잘 된다」** — 아니다. 클라이언트 *코드*를 안 고쳐도 된다는 뜻이고, 새 도구가 실제로 쓰이려면 설명이 좋아야 한다(25.5절). 코드 변경 없이 «호출 성향»이 바뀌므로, 오히려 회귀를 눈치채기 어렵다.
- **「목록이 늘어난 만큼 공짜로 강해진다」** — 아니다. 도구가 늘수록 비슷한 도구가 생기고 선택이 어려워진다. 예제 5가 보여 준 대로 「언제 **안** 쓰는지」를 적어 경계를 그어야 한다.
- **「같은 도구니까 응답 모양도 같겠지」** — 예제 4의 주석이 경고하는 흔한 실수가 있다. 목록을 돌려주는 도구는 «항목마다 content 블록 하나»로 오므로 `r.content[0]`만 읽으면 첫 항목만 읽는다. 스키마를 런타임에 받는다는 것은 **응답 형태도 런타임에 확인해야 한다**는 뜻이다.

## 7. 한 줄로

MCP는 도구 엣지의 목록을 컴파일 시점에서 **런타임으로 미룬 것**이다. 그 덕에 서버만 갱신하면 클라이언트가 새 도구를 얻고(배포 분리, 재사용 가능한 클라이언트), 그 대가로 정적 검증을 잃는다(런타임에 터짐). 얻은 것과 잃은 것은 같은 결정의 양면이므로, 처방은 결합을 되돌리는 게 아니라 **검증을 시작 시점으로 당기는 것**이다.
