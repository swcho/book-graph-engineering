# `wave_ms()`는 한 물결의 시간을 어떻게 계산하는가?

## 질문과 답

**Q.** `wave_ms()`는 한 물결의 시간을 어떻게 계산하는가?

**A.** 폭 안에 느린 갈래가 하나라도 있을 확률과 실패 갈래가 하나라도 있을 확률을 반영한다. 물결은 가장 느린 갈래가 끝나야 끝난다.

---

## 1. 용어부터 맞추기

25.2절 「펴는 값보다 합치는 값이 비싸다」의 예제 `code/ex2_fanout.py`에 나오는 함수다.

| 말 | 뜻 |
|---|---|
| 갈래(branch) | 병렬로 펴낸 작업 하나. 팬아웃으로 만든 워커 한 명 |
| 폭(width) | 동시에 돌리는 갈래 수 |
| 물결(wave) | 폭만큼 동시에 돌린 한 묶음. 갈래 $n$개를 폭 $W$로 처리하면 물결은 $\lceil n/W \rceil$개 |
| 합류(fan-in) | 물결이 끝난 뒤 결과를 모아 정리·중복 제거하는 값 |
| 꼬리 지연(tail latency) | 가장 느린 하나 때문에 전체가 늦어지는 현상 |

핵심 전제는 **동시에 돌린 갈래들은 제일 느린 하나가 끝나야 다 끝난다**는 것이다. 이게 함수 독스트링에 그대로 적혀 있다.

```python
def wave_ms(width):
    """한 물결은 «제일 느린 갈래»가 끝나야 끝난다."""
    p_any_slow = 1 - (1 - SLOW_P) ** width
    base = TASK_MS * (1 + p_any_slow * (SLOW_X - 1))
    p_any_fail = 1 - (1 - FAIL) ** width
    return base + p_any_fail * RETRY_MS
```

## 2. 상수 여섯 개

```python
TASK_MS = 900          # 갈래 하나 처리 시간
MERGE_PER_BRANCH = 140 # 합류할 때 갈래당 드는 시간 (정리·중복 제거)
FAIL = 0.06            # 갈래 하나가 실패할 확률
RETRY_MS = TASK_MS     # 실패하면 한 번 더
SLOW_P = 0.10          # 갈래 하나가 «느린 놈»일 확률
SLOW_X = 3.5           # 느린 놈은 이만큼 더 걸린다
```

즉 갈래 하나의 처리 시간은 두 값만 갖는다.

- 확률 $0.9$로 900ms (보통 놈)
- 확률 $0.1$로 $900 \times 3.5 = 3150$ms (느린 놈)

그리고 이와 별개로 확률 $0.06$으로 실패해서 900ms를 한 번 더 쓴다.

## 3. 한 줄씩 읽기

### (1) `p_any_slow = 1 - (1 - SLOW_P) ** width`

여사건(complement)이다. **모두** 빠를 확률이 $(1-p)^W$이므로, **하나라도** 느릴 확률은 그 나머지다.

$$P(\text{느린 갈래} \ge 1) = 1 - (1 - 0.1)^W$$

| 폭 $W$ | 다 빠를 확률 $0.9^W$ | 하나라도 느릴 확률 |
|---|---|---|
| 1 | 0.900 | 0.100 |
| 2 | 0.810 | 0.190 |
| 4 | 0.656 | 0.344 |
| 8 | 0.430 | 0.570 |
| 16 | 0.185 | **0.815** |

폭 16이면 물결 열 개 중 여덟 개는 안에 느린 놈이 끼어 있다. **드문 사건을 여러 번 뽑으면 드물지 않다.** 이게 팬아웃의 첫째 비용이다.

### (2) `base = TASK_MS * (1 + p_any_slow * (SLOW_X - 1))`

여기가 「가장 느린 갈래가 끝나야 끝난다」를 값으로 옮긴 부분이다. 느린 놈이 하나라도 있으면 물결 전체가 3150ms 걸리고, 없으면 900ms로 끝난다. 그 기대값이 정확히 이 식이다.

$$\mathbb{E}[\max] = 900 \cdot 0.9^W + 3150 \cdot (1 - 0.9^W) = 900\bigl(1 + p_{\text{slow}} \cdot 2.5\bigr)$$

느린 갈래가 몇 개인지는 상관없다. **하나만 있어도 최댓값은 3150ms로 확정**되기 때문이다. 두 값만 갖는 분포라서 「하나라도 있냐」는 지시확률이 최댓값 기대값을 완전히 결정한다.

- 900ms는 병렬로 나눠서 줄어드는 몫이 아니다. 폭을 키워도 **각 갈래는 여전히 900ms**다. 병렬이 사는 건 「물결 수」이고, 물결 하나의 길이는 오히려 길어진다.

### (3) `p_any_fail = 1 - (1 - FAIL) ** width`

(1)과 똑같은 여사건 계산을 실패율에 적용한 것이다. $1 - 0.94^W$.

| 폭 $W$ | 하나라도 실패할 확률 |
|---|---|
| 1 | 0.060 |
| 4 | 0.219 |
| 8 | 0.390 |
| 16 | **0.628** |

### (4) `return base + p_any_fail * RETRY_MS`

재시도 값을 기대값으로 얹는다. 하나라도 실패했으면 그 갈래를 900ms 더 돌려야 하고, 실패한 놈들의 재시도는 서로 병렬이므로 900ms 한 번만 더한다. 그래서 `p_any_fail * 900`이다.

## 4. 결과 — 폭이 커질수록 물결이 길어진다

```
동시 폭    물결 수   물결 하나(ms)   총 시간(ms)
      1        16           1,179         21,104
      2         8           1,432         13,698
      4         4           1,871          9,724
      8         2           2,533          7,306
     16         1           3,299          5,539
```

읽는 법이 두 가지다.

- **총 시간은 계속 준다.** 물결 수가 $\lceil n/W \rceil$로 반씩 줄어드는 효과가, 물결 하나가 길어지는 효과보다 훨씬 크다. 저자는 여기서 자기가 틀렸다고 적어 뒀다. 「폭을 키우면 실패 확률이 올라서 손해」라고 생각했지만 아니었다.
- **물결 하나는 계속 길어진다.** 1폭 1,179ms → 16폭 3,299ms. **2.8배**다. 폭을 키우는 값은 총 시간이 아니라 **변동성**으로 치른다. 평균은 좋아지고 최악은 나빠진다. 사용자가 느끼는 건 대개 최악 쪽이다.

`wave_ms`가 무한정 커지지 않는 것도 중요하다. $W \to \infty$면 두 확률이 모두 1로 수렴하므로

$$\lim_{W\to\infty} \text{wave\_ms}(W) = 3150 + 900 = 4050\ \text{ms}$$

물결 하나의 길이는 4,050ms에서 천장을 친다. 반면 물결 수는 계속 나눠진다. **위는 막혀 있고 아래는 계속 줄어드니** 총 시간이 줄어드는 것이다.

## 5. 그런데 진짜 천장은 합류였다

첫째 표(폭 4 고정)를 보면 이득이 1.57배에서 멈춘다.

```
갈래 수    직렬(ms)   병렬 4폭(ms)   그중 합류    이득
      2       1,908         2,151         280   0.89x  ← 병렬이 더 느리다
      4       3,816         2,431         560   1.57x
     16      15,264         9,724       2,240   1.57x
     64      61,056        38,898       8,960   1.57x
```

`parallel()`을 보면 이유가 보인다.

```python
def parallel(n, width):
    waves = -(-n // width)          # 펴는 값: 갈래 수를 폭으로 «나눈다»
    ms = waves * wave_ms(width)
    merge = n * MERGE_PER_BRANCH    # 합류 값: 갈래 수에 «비례한다»
    return ms + merge, merge
```

- 펴는 값은 $\div W$로 줄지만 합류 값 $140n$은 **폭과 무관하게 갈래 수에 비례**한다. 병렬화되지 않는 몫이 있으면 배수는 천장을 친다(암달의 법칙과 같은 구조).
- 갈래당으로 보면 직렬은 954ms, 병렬 4폭은 $1871/4 + 140 = 608$ms. $954/608 = 1.57$. 폭이 4인데 4배가 아닌 게 이 때문이다.
- 갈래 2개는 병렬이 **더 느리다**. 물결 하나 값(1,871ms)이 이미 직렬 두 개(1,908ms)와 비슷한데, 합류 280ms까지 붙기 때문이다. 펴는 값보다 합류와 꼬리 지연이 더 든다.

그래서 실무 순서는 「폭을 키운다」가 아니라 **「합류를 먼저 프로파일한다」**다. 합류에서 전체를 다시 정렬하거나 중복 제거를 $O(n^2)$로 하고 있으면 펴는 의미가 사라진다. 갈래끼리 비교하는 연산이 있으면 그건 제곱이다.

## 6. 이 모델이 단순화한 것

`wave_ms`는 교육용 기대값 모델이다. 실제로 재려면 다음이 다르다.

- **독립 가정.** 갈래들이 같은 API·같은 레이트리밋·같은 DB를 쓰면 느림과 실패는 상관관계가 있다. 실제 팬아웃에서는 한 갈래가 느릴 때 나머지도 느릴 확률이 훨씬 높다.
- **재시도는 한 번뿐.** 재시도한 갈래가 또 실패하거나 느릴 수 있다. 백오프 대기도 빠져 있다.
- **분포가 두 값뿐.** 실제 지연은 롱테일(로그정규·파레토 꼬리)이라 「제일 느린 하나」의 기대값이 더 험하게 자란다.
- **기대값만 본다.** 정작 중요한 건 p95/p99인데 이 함수는 평균만 낸다. 25.2절이 「평균은 좋아지고 최악은 나빠진다」고 말하는 지점이 정확히 이 한계다.

## 8. 한 줄 정리

`wave_ms(W)`는 **여사건 확률 두 개**(느린 갈래가 하나라도 있을 확률 $1-(1-0.1)^W$, 실패 갈래가 하나라도 있을 확률 $1-(1-0.06)^W$)로 「제일 느린 갈래가 끝나야 물결이 끝난다」는 사실을 값으로 바꾼다. 그래서 폭이 커지면 물결 하나가 길어지고(꼬리 지연), 총 시간은 그래도 줄지만 대가는 변동성으로 치른다.
