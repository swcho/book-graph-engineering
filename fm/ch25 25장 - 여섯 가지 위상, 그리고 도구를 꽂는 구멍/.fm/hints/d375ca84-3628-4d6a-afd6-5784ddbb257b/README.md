# MCP는 편의를 주고 컴파일 시점의 확신을 가져간다

**Q.** MCP의 대가는 무엇이며 어떻게 완화하는가?

**A.** 컴파일 시점에 아무것도 모른다는 것이다. 시작할 때 도구 목록을 검증해야 한다.

---

## 1. 카드 문장의 출처

25장 「한 장 요약」의 한 줄입니다.

> 도구는 그래프 밖으로 나가는 엣지고, MCP는 그 엣지 목록을 **실행 시점에 받아 오는** 방식입니다. 대가는 **컴파일 시점에 아무것도 모른다**는 것이에요. **시작할 때 목록을 검증하세요.**

실물은 25.4절과 예제 4(`code/ex4_mcp_client.py` + `code/mcp_server.py`)입니다. 예제 4 마지막 출력이 카드의 앞 절반을 그대로 말해요.

> 여기서 클라이언트 코드는 도구 이름을 «세 번» 말했다.
> 그런데 도구의 «정의»는 한 번도 안 갖고 있다. 서버가 준 것을 그대로 쓴다.
> (…)
> 대신 값을 치른다. 서버가 무엇을 줄지 컴파일 시점에 모른다.
> 도구 이름이 바뀌면 실행할 때 터진다.

## 2. 무엇을 얻는가 (대가를 이해하려면 이득을 먼저)

MCP(Model Context Protocol) 클라이언트는 도구를 코드에 박아 두지 않습니다. 붙어서 **물어봅니다**.

```python
async with stdio_client(params) as (read, write):
    async with ClientSession(read, write) as s:
        info = await s.initialize()            # 서버 이름 / 프로토콜 버전
        tools = (await s.list_tools()).tools   # 도구 목록 + 스키마를 «받아 온다»
        for t in tools:
            t.name, t.description, t.inputSchema   # 세 가지가 다 서버에서 온다
```

- 서버에 도구를 하나 추가하면 **클라이언트는 안 고쳐도 됩니다.**
- 같은 클라이언트가 다른 서버에 붙으면 **다른 도구를 갖게 됩니다.**
- 책의 표현: 2장 말로는 「지연 결합(late binding)되는 서브그래프」, 그래프 말로는 「**엣지 목록을 실행 시점에 받아 오는 것**」.

이 유연함이 정확히 대가의 원인입니다. 하나의 성질을 양쪽에서 부르는 이름일 뿐이에요.

## 3. 대가: 「컴파일 시점에 아무것도 모른다」가 실제로 뜻하는 것

정적으로 검사할 수 있던 것들이 전부 실행 시점으로 밀려납니다.

| 컴파일 시점에 못 아는 것 | 실행 시점에 나타나는 증상 |
|---|---|
| 도구가 **존재하는지** | `call_tool("find_person", …)`이 그냥 터진다 |
| 도구 **이름**이 그대로인지 | 서버가 리네임하면 조용히 깨진다. 타입 체커·IDE·문법 검사가 못 잡는다 |
| **인자 스키마** (`required`, 필드명, 타입) | 인자 누락·타입 불일치가 호출 시점에 발견된다 |
| **반환 모양** | `content` 블록 개수/구조 가정이 어긋난다 |
| 도구 **개수** | 서버가 갑자기 40개를 노출하면 컨텍스트를 잡아먹는다 |
| 도구 **설명** 문구 | 설명이 곧 선택 함수라서(25.5절) **프롬프트가 조용히 바뀐 것**과 같다 |
| 서버가 **떠 있는지**, 프로토콜 버전이 맞는지 | 초기화 실패 / 협상 실패 |

핵심은 「터진다」보다 「**언제 터지는지 모른다**」입니다. 배포 시점이 아니라 사용자가 그 도구를 부르는 순간, 즉 그래프의 한복판에서 터져요. 게다가 도구 설명이 바뀌는 경우는 **터지지도 않습니다.** 모델의 엣지 선택 확률만 달라져서 품질이 슬쩍 내려가고, 코드 diff에는 아무것도 안 남습니다.

예제 4가 굳이 상기시키는 관련 함정도 같은 뿌리입니다.

```python
r = await s.call_tool("chain_of_command", {"person_id": person["id"]})
# 목록을 돌려주는 도구는 «항목마다 content 블록 하나»로 온다.
# r.content[0] 만 읽으면 첫 항목만 읽는 셈이다. 흔한 실수다.
chain = [json.loads(c.text) for c in r.content]
```

반환 모양을 컴파일 시점에 모르니 `content[0]`만 읽고 「값이 하나뿐이네」로 넘어가게 됩니다. 예외가 안 나기 때문에 **틀린 답이 정상처럼 흘러갑니다.** 대가가 크래시로만 오는 게 아니라는 증거예요.

## 4. 완화: 「시작할 때 목록을 검증하라」

컴파일 시점 검사를 되찾을 수는 없습니다. 대신 **가장 이른 실행 시점**, 즉 부팅 직후 한곳으로 실패를 모읍니다. 컴파일 타임 검사를 **기동 시 fail-fast**로 대체하는 것이 이 처방의 정체입니다.

기동 시 검증에 넣을 것:

1. **초기화 확인** — 서버 이름·버전·프로토콜 버전이 기대와 맞는지. (책 확인 시점: mcp 파이썬 SDK 1.5.0, 프로토콜 `2024-11-05`)
2. **필수 도구 존재 확인** — 내가 기대하는 이름 집합이 `list_tools()` 결과에 다 있는지. 하나라도 없으면 **즉시 죽는다.**
3. **스키마 확인** — 내가 넘길 인자 이름이 `inputSchema.properties`에 있고, 서버가 요구하는 `required`를 내가 다 채울 수 있는지.
4. **스냅샷 비교** — 도구 이름·설명·스키마를 해시로 떠 두고 기동마다 비교. 달라지면 경고합니다. 설명 변경은 터지지 않으므로 이 방법으로만 잡힙니다.
5. **예상 밖 도구 처리** — 모르는 도구가 늘어났으면 허용 목록(allowlist)으로 걸러 모델에 넘기지 않습니다. 이게 26장(무엇을 못 하게 할 것인가)으로 이어지는 실입니다.
6. **이름을 한곳에 모으기** — 예제 4는 도구 이름을 문자열로 세 번 말했습니다. 상수/열거형 한 곳에 모아 두면 검증 대상과 호출 대상이 같은 출처를 갖습니다.

스케치:

```python
EXPECTED = {
    "find_person":      {"name"},
    "chain_of_command": {"person_id"},
    "team_members":     {"team"},
}

async def verify(session):
    tools = {t.name: t for t in (await session.list_tools()).tools}

    missing = set(EXPECTED) - set(tools)
    if missing:
        raise RuntimeError(f"서버에 없는 도구: {sorted(missing)}")   # 기동 시 죽는다

    for name, args in EXPECTED.items():
        props = set(tools[name].inputSchema.get("properties", {}))
        required = set(tools[name].inputSchema.get("required", []))
        if not args <= props:
            raise RuntimeError(f"{name}: 인자 사라짐 {sorted(args - props)}")
        if not required <= args:      # 서버가 새 필수 인자를 추가했다
            raise RuntimeError(f"{name}: 못 채우는 필수 인자 {sorted(required - args)}")

    extra = set(tools) - set(EXPECTED)     # 모델에 넘기기 전 판단이 필요한 것들
    return tools, extra
```

여기에 실행 시점 방어를 얹습니다. 목록 도구는 `content` 블록을 **전부** 순회하고, 도구 호출 실패는 그래프의 재시도/폴백 경로로 흘립니다(21·22장 계열의 얘기).

## 5. 한 줄로 접는 방식

- **얻은 것**: 엣지 목록을 실행 시점에 받아 오는 유연함(지연 결합).
- **낸 값**: 정적 검사를 잃음 — 존재·이름·스키마·반환 모양·설명 전부 컴파일 시점에 미지.
- **완화**: 실패를 **기동 시점 한곳으로 모으는** 검증. 필수 도구/스키마 없으면 즉시 죽고, 스냅샷 비교로 조용한 변경을 잡고, 모르는 도구는 허용 목록으로 막는다.

---

### 외우기 팁

- **「실행 시점에 받아 온다」의 값이 「컴파일 시점에 모른다」다.** 같은 성질의 앞면과 뒷면.
- 처방은 한 단어: **부팅 때 fail-fast.** 컴파일 검사를 못 하면 **가장 이른 실행 시점**으로 당겨 온다.
- 제일 무서운 건 크래시가 아니라 **설명 변경**. 안 터지고 품질만 내려가서, 스냅샷 비교 말고는 잡을 방법이 없다.
