# 「박민수 상급자 알려줘」가 여전히 틀리는 이유

> **질문** 「박민수 상급자 알려줘」가 여전히 틀리는 이유는 무엇인가?
>
> **답** 설명에는 '상사'가 있는데 사용자는 '상급자'라고 했다. 우리는 사내 용어로 쓰고 사용자는 자기 말로 묻는다.

25장 예제 5(`code/ex5_tool_selection.py`)는 도구 코드를 한 줄도 안 고치고 **설명만** 바꿔서 도구 선택 정확도를 재는 실험입니다. 짧은 설명(`BAD`)에서 3/8 = 38%, 「무엇을 주는지 / 어떤 말로 묻는지 / 언제 안 쓰는지」를 넣은 설명(`GOOD`)에서 7/8 = 88%로 오릅니다.

그런데 **GOOD에서도 딱 하나가 계속 틀립니다.** 그게 이 카드의 주제입니다.

```
[설명에 «언제 쓰나»와 «언제 안 쓰나»가 있다]
  김지훈이 누구야              find_person
  김지훈 위로 누가 있어          chain_of_command
  결제팀에 누구누구 있어          team_members
  박민수 상급자 알려줘           find_person          ←틀림
  이서연 찾아줘                find_person
  결제팀 명단                 team_members
  김지훈 보고 라인 전체          chain_of_command
  이서연 정보                 find_person
  정확도 7/8 = 88%
```

정답은 `chain_of_command`인데 `find_person`이 나왔습니다. 왜 그런지 점수를 직접 계산해 봅니다.

---

## 1. 선택기가 하는 일 전부

예제의 선택기는 모델이 아닙니다. 아주 멍청합니다. 하는 일이 이것뿐입니다.

```python
def tokenize(s):
    return set(re.findall(r"[가-힣A-Za-z]+", s))   # 한글/영문 덩어리를 집합으로

def choose(query, descriptions):
    q = tokenize(query)
    best, score = None, -1
    for name, desc in descriptions.items():
        overlap = len(q & tokenize(desc))          # 겹치는 단어 개수
        if overlap > score:
            best, score = name, overlap
    return best
```

즉 **질문 토큰 집합과 설명 토큰 집합의 교집합 크기**가 점수입니다. 형태소 분석도 없고, 어간 추출도 없고, 임베딩도 없습니다. 그냥 `set & set`의 원소 개수입니다.

여기서 두 가지를 미리 붙잡아 둡시다.

1. 매칭은 **정확 일치**입니다. 「상사」와 「상급자」는 첫 글자를 공유하지만 서로 다른 토큰이므로 겹침 0입니다.
2. 동점 처리 규칙이 `if overlap > score`, 즉 **엄격한 초과**입니다. 동점이면 갱신하지 않으니 **사전에 먼저 들어온 키가 이깁니다.** `GOOD` 딕셔너리의 첫 키는 `find_person`입니다. 이것이 곧 이 실험의 「기본값」입니다.

---

## 2. 점수 계산 — 세 도구 모두 0점

### 질문 토큰

```
"박민수 상급자 알려줘"
→ {박민수, 상급자, 알려줘}      (3개)
```

### `find_person` 설명 토큰

> 사람 «한 명»을 이름으로 찾는다. 이름, 소속 팀, 상사 아이디를 준다. 여러 명을 찾을 때는 쓰지 않는다.

```
{한, 사람, 명, 을, 이름으로, 찾는다, 이름, 소속, 팀, 상사,
 아이디를, 준다, 여러, 명을, 찾을, 때는, 쓰지, 않는다}      (18개)
```

교집합: `{}` → **0점**

### `chain_of_command` 설명 토큰

> 한 사람의 «위로 올라가는» 보고 체계를 뿌리까지 준다. 상사, 상사의 상사, 보고 라인, 결재선을 물으면 이것이다. 아래 부하 목록에는 쓰지 않는다.

```
{한, 사람의, 위로, 올라가는, 보고, 체계를, 뿌리까지, 준다, 상사,
 상사의, 라인, 결재선을, 물으면, 이것이다, 아래, 부하, 목록에는, 쓰지, 않는다}   (19개)
```

교집합: `{}` → **0점**

`상급자`는 없습니다. `상사`, `상사의`는 있는데 사용자가 쓴 단어가 아닙니다. `알려줘`도 없습니다. 설명은 `준다`라고 쓰여 있습니다. 뜻은 같지만 글자가 다릅니다.

### `team_members` 설명 토큰

> 팀 이름을 주면 그 팀 구성원 «전부»를 목록으로 준다. 명단, 누구누구, 구성원, 몇 명을 물으면 이것이다.

```
{팀, 이름을, 주면, 그, 구성원, 전부, 를, 목록으로, 준다,
 명단, 누구누구, 몇, 명을, 물으면, 이것이다}                 (15개)
```

교집합: `{}` → **0점**

### 결과 표

| 도구 | 겹치는 단어 | 점수 |
|---|---|---|
| `find_person` | (없음) | 0 |
| `chain_of_command` | (없음) | 0 |
| `team_members` | (없음) | 0 |

**세 도구 전부 0점.** 신호가 전혀 없습니다. 그러니 `overlap > score`의 엄격한 초과 규칙 때문에 사전 순서상 첫 키인 `find_person`이 그냥 반환됩니다. 선택기가 「고른」 게 아니라 **고를 근거가 하나도 없어서 기본값이 나온 것**입니다.

이게 중요합니다. 이 실패는 「모델이 헷갈렸다」가 아니라 **「입력에서 도구로 가는 다리가 아예 없다」**입니다. 다른 종류의 실패입니다.

---

## 3. 반사실 — 「상사」라고 물었으면 맞았을까?

「그럼 사용자가 사내 용어를 썼으면 됐던 거네」 싶지만, 확인해 보면 그것도 아닙니다.

```
"박민수 상사 알려줘" → {박민수, 상사, 알려줘}

  find_person       overlap = 1   {상사}
  chain_of_command  overlap = 1   {상사}
  team_members      overlap = 0   {}
  → choose() = find_person   (동점, 먼저 온 키 승)
```

여전히 틀립니다. 이유가 하나 더 겹칩니다. `find_person` 설명이 「**상사 아이디**를 준다」라고 반환값을 정직하게 밝혀 놨기 때문에 `상사`라는 단어를 두 도구가 나눠 갖게 됩니다. 좋은 설명을 쓴 대가로 구별 신호가 희석된 셈입니다.

정보 검색 용어로 말하면 `상사`는 이 도구 집합 안에서 **문서 빈도(document frequency)가 높은 단어**, 즉 변별력이 낮은 단어입니다. 단순 겹침 개수는 모든 단어를 똑같이 1점으로 세니까 이걸 못 봅니다. IDF 가중(희귀한 단어에 더 큰 점수)을 넣었다면 `위로`, `결재선을`, `명단` 같은 도구별 고유어가 살고 `상사`는 값이 깎여서 동점이 안 났을 겁니다. 예제가 일부러 그런 장치를 안 넣은 것이고요.

한글에서 문제를 한 겹 더 키우는 건 **조사 부착**입니다. `상사`와 `상사의`가 별개 토큰이고, `이름`과 `이름을`과 `이름으로`가 별개 토큰입니다. 형태소 분석 없이 공백으로 자르면 같은 어휘가 여러 토큰으로 흩어지면서 매칭 확률이 더 떨어집니다.

---

## 4. 고치는 법 — 동의어를 설명에 박아 넣는다

예제가 제시하는 처방은 촌스럽지만 잘 듣습니다. **동의어를 설명 안에 나열한다.**

`chain_of_command` 설명 끝에 「상급자, 윗사람, 윗분」을 덧붙이고 다시 돌려 봤습니다.

```
  박민수 상급자 알려줘           chain_of_command
  정확도 8/8 = 100%
```

`상급자`가 겹치면서 `chain_of_command`가 1점, 나머지가 0점 → 정답. **8/8 = 100%.** 코드는 여전히 한 줄도 안 고쳤습니다.

동의어 목록을 어디서 가져오나요? 머리로 짜내는 것보다 **실제 질문 로그에서 뽑는 게** 낫습니다. 우리가 상상하는 사용자 어휘와 진짜 사용자 어휘는 다릅니다. 그게 바로 이 카드가 말하는 「우리는 사내 용어로 쓰고, 사용자는 자기 말로 묻는다」입니다.

## 5. 이건 새 문제가 아니다 — 어휘 불일치 문제

이 실패에는 40년 된 이름이 있습니다. **어휘 불일치 문제(vocabulary mismatch problem)**, 또는 **용어 불일치(term mismatch)**입니다. 정보 검색에서 가장 오래되고 가장 잘 알려진 실패 모드입니다.

### Furnas et al. 1987

Furnas, Landauer, Gomez, Dumais가 1987년 CACM에 낸 「The vocabulary problem in human-system communication」이 이 문제의 고전입니다. 다섯 개 도메인에서 사람들이 같은 대상에 자발적으로 어떤 단어를 붙이는지 재 봤더니,

- **두 사람이 같은 단어를 고를 확률이 모든 경우에서 0.20 미만**이었습니다.
- 그래서 「설계자가 정한 단어 하나」로 접근하게 만드는 흔한 방식은 상황에 따라 **80~90%의 실패율**을 냅니다.
- 논문이 도출한 최적 전략은 **무제한 별칭(unlimited aliasing)** — 사용자가 쓸 수 있는 여러 대안 용어를 모두 인식하게 만드는 것 — 이고, 이것으로 몇 배의 개선이 가능했습니다.

「상사 vs 상급자 vs 윗사람 vs 윗분 vs 결재선」이 정확히 이 논문의 실험 결과입니다. 도구 설명을 쓴 개발자가 「상사」를 골랐고, 사용자는 「상급자」를 골랐습니다. 논문에 따르면 이건 예외가 아니라 **기본값**입니다. 두 사람이 우연히 같은 단어를 고를 확률이 20% 미만이니까요.

그리고 논문의 처방(무제한 별칭)이 4절의 처방(동의어 나열)과 같은 것입니다. 예제 5가 재발명한 게 아니라, IR이 1987년에 내린 결론을 도구 설명이라는 새 표면에서 다시 만난 것입니다.

### 그 뒤로 IR이 이 문제와 싸운 방법들

| 접근 | 하는 일 | 도구 설명에 대응하는 것 |
|---|---|---|
| 시소러스 / 동의어 확장 | 질의나 문서에 동의어를 붙인다 | 설명에 「상사·상급자·윗사람」 나열 (예제의 처방) |
| 질의 확장(query expansion), 의사 적합성 피드백 | 1차 검색 결과에서 단어를 뽑아 질의를 늘린다 | 사용자 질문 로그에서 실제 어휘를 뽑아 설명에 반영 |
| 어간 추출 / 형태소 분석 | `이름`, `이름을`, `이름으로`를 한 어휘로 묶는다 | 조사·활용 차이로 놓치는 매칭을 줄인다 |
| LSI(잠재 의미 색인, Deerwester et al. 1990) | 단어를 잠재 의미 공간으로 보내 동의어를 흡수한다 | 「의미가 같으면 글자가 달라도 매칭」의 초기 형태 |
| 밀집 검색 / 임베딩 (요즘) | 의미 벡터의 거리로 매칭한다 | LLM이 실제로 하는 일에 가까운 것 |

### 그래서 진짜 모델은 괜찮은가?

예제의 주석이 정직하게 말합니다. 「여기 쓴 선택기는 단어가 겹치는 걸 세는 게 전부다. 모델보다 훨씬 멍청하다. 그런데 **«설명이 나쁘면 못 고른다»는 성질은 모델도 같다.**」

LLM은 임베딩 쪽에 해당하니 「상사 → 상급자」 정도는 대개 넘어갑니다. **하지만 성질이 사라지는 게 아니라 문턱이 올라갈 뿐입니다.** 사내 약어(「결재선」, 「TL」, 「챕터장」), 사내에서만 쓰는 조직 명칭, 도메인 은어, 유사 도구 둘의 미묘한 경계 — 이런 데서는 LLM도 정확히 같은 방식으로 틀립니다. 겹침 0에서 기본값을 뱉는 대신, 그럴듯한 오답을 자신 있게 뱉습니다. 진단하기는 오히려 더 어렵습니다.

그래서 예제 5의 결론이 「단순 매칭의 한계」가 아니라 **「도구 설명이 곧 엣지 선택 함수다」**인 것입니다. 25.5절의 표현으로,

> 도구 설명이 곧 엣지 선택 함수입니다. 무엇을 주는지, 어떤 말로 묻는지, *언제 안 쓰는지* 셋을 쓰세요.

이 카드의 실패는 그 셋 중 **2번(어떤 말로 물었을 때 이것인지 — 사용자 어휘를 넣는다)**이 빠져서 난 것입니다. 1번(반환값)과 3번(경계)은 GOOD 설명에 잘 들어가 있었고, 그래서 나머지 7개는 맞았습니다.

## 6. 한 줄로 정리

- 「상급자」는 `find_person`/`chain_of_command`/`team_members` 설명 어디에도 없어서 **세 도구 모두 겹침 0점**이 되고, 동점이면 먼저 온 키가 이기는 규칙 때문에 기본값 `find_person`이 나온다.
- 「상사」라고 물어도 여전히 틀린다. 두 설명이 `상사`를 나눠 갖고 있어서 1:1 동점이 되기 때문. 변별력 없는 단어는 매칭에 도움이 안 된다.
- 동의어(`상급자`)를 `chain_of_command` 설명에 넣으면 **8/8 = 100%**. 코드는 안 고친다.
- 이건 정보 검색의 **어휘 불일치 문제**다. Furnas et al. 1987은 두 사람이 같은 단어를 고를 확률이 20% 미만이라고 측정했고, 처방으로 **무제한 별칭**을 제시했다. 도구 설명에 동의어를 나열하는 것이 바로 그 처방이다.
- 동의어는 상상하지 말고 **실제 질문 로그에서 뽑아라.**
