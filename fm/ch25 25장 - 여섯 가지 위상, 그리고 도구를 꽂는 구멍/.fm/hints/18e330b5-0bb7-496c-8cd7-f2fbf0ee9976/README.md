# 성형(감독자-작업자) 위상의 특징

> **질문** 성형(감독자-작업자) 위상의 특징은 무엇인가?
>
> **답** 매 물결마다 감독자의 판단 비용이 붙고 감독자가 병목이 된다. 대신 판단이 들어가 품질이 경로보다 높다.

---

## 1. 먼저 그림으로

성형(星形, star)은 이름 그대로 별 모양입니다. 가운데에 노드 하나가 있고, 작업자들이 그 하나에 방사형으로 붙습니다.

```
        작업자1
          |
작업자4 —감독자— 작업자2
          |
        작업자3
```

핵심은 **작업자끼리 직접 연결된 엣지가 없다**는 것입니다. 모든 통신이 가운데를 지나갑니다. 이 성질 하나에서 이 위상의 장점과 단점이 전부 따라 나옵니다.

- 가운데가 전부를 보므로 **판단할 수 있다** → 품질이 오른다
- 가운데를 전부가 지나가므로 **가운데가 막히면 다 막힌다** → 병목이 된다

부르는 이름은 여럿입니다. 감독자-작업자, 오케스트레이터-워커(orchestrator-workers, Anthropic의 «Building effective agents»에서 쓰는 이름), 슈퍼바이저, 허브-앤-스포크. 25장이 「이름은 사람마다 다르니 그림으로 얘기하세요」라고 한 대표적인 자리입니다.

## 2. 예제 코드에서 이 특징이 어디에 있나

`code/ex1_topologies.py`의 `성형()`은 두 줄입니다. 이 두 줄이 답 문장 그대로입니다.

```python
def 성형():
    """감독자-작업자. 감독자가 매번 다음 일을 정한다."""
    waves = -(-DOCS // PAR)
    ms  = waves * (ROUTE_MS + READ_MS) + ROUTE_MS + WRITE_MS
    tok = (waves + 1) * ROUTE_TOK + DOCS * READ_TOK + WRITE_TOK
    return ms, tok, 0.78, "판단이 붙는다. 감독자가 병목."
```

바로 위의 `이분합류()`와 나란히 놓고 보면 차이가 정확히 보입니다.

```python
def 이분합류():
    ms  = waves * READ_MS + WRITE_MS
    tok = DOCS * READ_TOK + WRITE_TOK
    return ms, tok, 0.71, "빠르다. 토큰은 같다."
```

**차이가 `ROUTE_MS`와 `ROUTE_TOK`이 붙은 자리뿐입니다.**

| 어디에 | 이분·합류 | 성형 |
|---|---|---|
| 물결 안 | `READ_MS` | `ROUTE_MS + READ_MS` ← 물결마다 판단 |
| 물결 밖 | 없음 | `+ ROUTE_MS` ← 마지막 종합 판단 |
| 토큰 | `DOCS*READ_TOK` | `(waves+1)*ROUTE_TOK + DOCS*READ_TOK` |

`ROUTE_MS`가 **`waves`에 곱해져 있다**는 게 「매 물결마다 판단 비용이 붙는다」의 코드 표현입니다. 한 번 붙는 상수가 아니라 물결 수에 비례하는 항입니다.

## 3. 숫자로 (문서 8편 → 보고서 1장, `PAR=4`)

상수는 `READ=900ms/2,400tok`, `WRITE=1,800ms/3,200tok`, `ROUTE=300ms/400tok`, `waves = ceil(8/4) = 2`입니다.

성형을 직접 계산해 보면

```
ms  = 2 × (300 + 900) + 300 + 1,800 = 2,400 + 2,100 = 4,500 ms
tok = (2+1) × 400 + 8 × 2,400 + 3,200 = 1,200 + 19,200 + 3,200 = 23,600
```

여섯 위상을 나란히 놓으면 이렇습니다.

| 위상 | 지연(ms) | 토큰 | 품질 | 토큰당 품질(×10⁴) | 성격 |
|---|---:|---:|---:|---:|---|
| 경로 | 9,000 | 22,400 | 0.71 | 0.317 | 단순. 느리다. |
| 이분·합류 | 3,600 | 22,400 | 0.71 | 0.317 | 빠르다. 토큰은 같다. |
| **성형** | **4,500** | **23,600** | **0.78** | **0.331** | **판단이 붙는다. 감독자가 병목.** |
| 순환 | 9,300 | 32,100 | 0.89 | 0.277 | 품질이 오른다. 값이 비싸다. |
| 동적 엣지 | 3,900 | 22,800 | 0.81 | 0.355 | 쉬운 건 싸게, 어려운 건 비싸게. |
| 트리 | 4,800 | 29,600 | 0.84 | 0.284 | 부분 요약이 남는다. 중간 손실도. |

성형이 치른 값과 받은 것을 이분·합류 기준으로 재면

- 지연 **+900ms** (3,600 → 4,500, 25% 느려짐) — 판단 3번(`(2+1)×300`)이 전부 직렬로 끼어든 값
- 토큰 **+1,200** (22,400 → 23,600, 5.4% 증가)
- 품질 **+0.07** (0.71 → 0.78)

토큰당 품질로는 0.317에서 0.331로 **올랐습니다**. 「판단은 대체로 싸게 사는 품질」이라는 뜻입니다. 순환(0.89)과 비교해 보면 이 성질이 더 뚜렷합니다. 순환은 품질 1등이지만 토큰이 43% 더 들어 토큰당 품질은 0.277로 오히려 아래쪽입니다. 성형은 품질을 조금 덜 사는 대신 훨씬 싸게 삽니다.

## 4. 「감독자가 병목」이 정확히 무슨 뜻인가

세 층으로 나눠 보면 좋습니다.

### (1) 감독자 구간은 병렬화가 안 된다

`ROUTE_MS`는 `PAR`로 나눠지지 않습니다. 작업자를 4개에서 40개로 늘려도 판단은 여전히 한 명이 순서대로 합니다. 이건 암달의 법칙(Amdahl's law)의 직렬 구간과 같은 성질입니다. 폭을 아무리 키워도 감독자 구간이 남아 있는 한 그 아래로는 못 내려갑니다.

이 예제의 이론적 하한을 재 보면 — 문서 읽기를 8폭으로 완전히 펴서 `waves=1`로 만들어도

```
1 × (300 + 900) + 300 + 1,800 = 3,300 ms
```

`ROUTE` 두 번(600ms)과 `WRITE`(1,800ms)는 절대 사라지지 않습니다.

### (2) 물결이 늘면 판단 비용이 선형으로 늘어난다

`PAR`을 4로 고정하고 문서를 늘려 보면 병목이 어떻게 자라는지 보입니다.

| 문서 수 | 물결 | 판단 시간 | 판단 토큰 | 전체 지연 |
|---:|---:|---:|---:|---:|
| 8 | 2 | 900 | 1,200 | 4,500 |
| 40 | 10 | 3,300 | 4,400 | 13,300 |
| 400 | 100 | 30,300 | 40,400 | 121,800 |

판단이 「가끔 한 번 드는 오버헤드」가 아니라 **작업량에 비례해 자라는 고정 세금**입니다. 작업자를 늘려 물결 수를 줄이는 것 말고는 이 세금을 깎는 방법이 없습니다.

### (3) 감독자의 컨텍스트가 실제 병목이다

코드는 `ROUTE_TOK`을 상수 400으로 잡았지만, 실제 시스템에서는 감독자가 물결이 지날수록 「지금까지 무엇을 읽었나」를 누적해서 들고 있어야 합니다. 그래서 현실의 `ROUTE_TOK`은 물결이 진행될수록 커지고, 위 표보다 나쁘게 자랍니다. 24장(컨텍스트가 꽉 찼습니다)에서 다룬 문제가 성형 위상에서 제일 먼저 터지는 이유입니다. 작업자는 자기 문서 하나만 보면 되지만 감독자는 전부를 봐야 합니다.

정리하면 성형의 병목은 세 겹입니다. **직렬 구간(시간) + 물결당 판단 토큰(비용) + 누적 컨텍스트(한계)**.

## 5. 「대신 품질이 경로보다 높다」의 근거

0.71 → 0.78입니다. 이 차이가 어디서 오는지가 성형을 고를 이유의 전부입니다.

경로와 이분·합류는 **계획이 고정**입니다. 문서 8편을 순서대로(혹은 나눠서) 다 읽고 씁니다. 1번 문서를 읽고 「아, 3번은 볼 필요 없고 7번을 먼저 봐야 하는구나」라고 알게 되어도 반영할 자리가 없습니다.

성형은 물결마다 감독자가 끼어들어 **직전 물결의 결과를 보고 다음 물결을 정합니다**. 그래서

- 필요 없는 갈래를 접을 수 있다
- 놓친 갈래를 추가할 수 있다
- 작업자에게 「이 관점으로 읽어라」고 좁혀 줄 수 있다
- 작업자 결과가 서로 어긋나면 그 자리에서 알아챈다

경로와 이분·합류의 품질이 **똑같이 0.71**인 게 힌트입니다. 병렬로 펴는 것은 시간만 삽니다. 품질을 바꾸는 것은 **판단이 들어가는 자리를 만드는 것**입니다.

주의할 점은 이 0.78이 **판단이 맞는다는 가정** 위에 있다는 것입니다. 예제 3(`ex3_router.py`)이 라우터 정확도를 떨어뜨리며 보여 준 것과 같은 구조입니다. 감독자가 매번 틀린 문서를 고르면 지연·토큰만 더 내고 품질은 그대로거나 더 나빠집니다. 라우터를 넣을 때 채점 데이터셋이 먼저 필요한 것과 똑같이, 성형을 넣을 때도 「감독자의 판단이 맞았는지」를 잴 수 없으면 이 0.07이 있는지 알 방법이 없습니다.

## 6. 헷갈리는 이웃들과 구분하기

성형을 다른 위상과 섞어 기억하기 쉬우므로 경계를 그어 둡니다.

| 위상 | 판단이 몇 번 | 누가 하나 | 결정적 차이 |
|---|---|---|---|
| **이분·합류** | 0번 | 없음 | 계획이 고정. 펴서 시간만 산다. |
| **동적 엣지(라우터)** | **1번, 맨 앞** | 라우터 | 한 번 정하면 끝. 물결마다 다시 안 본다. |
| **성형** | **물결마다** | 감독자 하나 | 직전 결과를 보고 다음을 정한다. |
| **트리** | 계층마다 | 중간 관리자들 | 판단이 여러 노드로 나뉜다. 부분 요약이 남는다. |
| **순환** | 매 라운드 | 검증자 | 같은 산출물을 **다시** 만든다. 성형은 다음 일로 나아간다. |

특히 두 쌍을 조심하세요.

- **성형 vs 동적 엣지** — 판단의 횟수가 다릅니다. 동적 엣지는 앞에서 한 번(`ROUTE_MS + waves*READ_MS + ...`), 성형은 물결마다(`waves*(ROUTE_MS + READ_MS)`). 그래서 동적 엣지는 토큰이 400밖에 안 늘고(22,800) 성형은 1,200 늘어납니다(23,600).
- **성형 vs 순환** — 성형의 감독자는 「다음에 무엇을 할까」를 정하고, 순환의 검증자는 「이거 다시 해」를 정합니다. 순환은 같은 `WRITE`를 3번 반복해서 토큰이 32,100까지 뜁니다.

## 7. 25장의 큰 얘기 안에서

25장은 「좋은 위상은 없다」로 시작합니다. 성형은 그 주장을 재는 좋은 자를 만들어 줍니다.

- 제일 빠른 것은 **이분·합류**(3,600ms)
- 제일 싼 것은 **경로/이분·합류**(22,400)
- 품질 1등은 **순환**(0.89)
- 토큰당 품질 1등은 **동적 엣지**(0.355)

성형은 **어느 칸에서도 1등이 아닙니다.** 그런데도 실무에서 가장 자주 쓰이는 이유는 「품질을 조금 올리고 값을 조금 내는」 중간 자리를 잡고 있어서입니다. 25장이 준 고르는 순서에 성형을 얹어 보면

1. 품질 하한이 있나 → 순환
2. 지연 상한이 있나 → 이분·합류
3. 입력 종류가 갈리나 → 동적 엣지
4. 다 아니면 → 경로
5. 그리고 **「무엇을 할지 미리 정할 수 없나」 → 성형**

5번이 성형의 자리입니다. 계획을 미리 쓸 수 있으면 성형은 낭비입니다. 감독자 비용만 내고 판단할 게 없으니까요. 계획을 진행하면서 정해야 할 때만 그 비용이 품질로 돌아옵니다.

## 8. 한 줄 정리

> **성형 = 이분·합류 + 물결마다 감독자 판단.** 판단 비용(`waves × ROUTE`)은 병렬화가 안 되어 감독자가 직렬 병목이 되지만, 적응적 판단이 들어간 덕에 품질이 고정 계획(경로·이분·합류 0.71)보다 0.78로 오른다. 토큰당 품질로는 이득(0.317 → 0.331)이므로 「싸게 사는 품질」이다.
