# 저자가 팬아웃에 대해 틀렸던 예상

**질문**: 저자가 팬아웃에 대해 틀렸던 예상은 무엇인가?

**정답**: 「폭을 키우면 하나라도 실패할 확률이 올라 손해」라고 생각했지만, 물결 수가 줄어드는 효과가 훨씬 커서 총 시간은 계속 줄었다.

출처: 25장 25.2절 「펴는 값보다 합치는 값이 비싸다」 / `code/ex2_fanout.py` 의 **둘째 표**.

---

## 1. 무대 설정 — ex2_fanout.py 가 재는 것

이 예제는 갈래(branch) 여러 개를 병렬로 펴는 팬아웃을 아주 단순한 산수 모형으로 만들어 놓았습니다.

| 상수 | 값 | 뜻 |
|---|---|---|
| `TASK_MS` | 900 | 갈래 하나 처리 시간 |
| `MERGE_PER_BRANCH` | 140 | 합류(fan-in)할 때 **갈래당** 드는 정리·중복 제거 시간 |
| `FAIL` | 0.06 | 갈래 하나가 실패할 확률 |
| `RETRY_MS` | 900 | 실패하면 한 번 더 |
| `SLOW_P` | 0.10 | 갈래 하나가 「느린 놈」일 확률 |
| `SLOW_X` | 3.5 | 느린 놈은 이만큼 더 걸린다 |

핵심은 「한 물결(wave)은 제일 느린 갈래가 끝나야 끝난다」입니다.

```python
def wave_ms(width):
    """한 물결은 «제일 느린 갈래»가 끝나야 끝난다."""
    p_any_slow = 1 - (1 - SLOW_P) ** width      # 폭 안에 느린 놈이 하나라도 있을 확률
    base = TASK_MS * (1 + p_any_slow * (SLOW_X - 1))
    p_any_fail = 1 - (1 - FAIL) ** width        # 폭 안에 실패가 하나라도 있을 확률
    return base + p_any_fail * RETRY_MS

def parallel(n, width):
    waves = -(-n // width)                      # 올림 나눗셈 = 물결 수
    ms = waves * wave_ms(width)
    merge = n * MERGE_PER_BRANCH                # 폭과 무관, 갈래 수에 비례
    return ms + merge, merge
```

여기서 `1 - (1 - p) ** width` 가 바로 저자의 직관이 붙잡은 항입니다. **폭이 커지면 「하나라도 실패/느릴 확률」은 실제로 올라갑니다.** 문제는 그게 얼마나 오르느냐였죠.

## 2. 저자의 예상 (틀린 쪽)

> 「폭을 키우면 하나라도 실패할 확률이 올라서 손해」라고 생각했다. 아니었다.

논리는 그럴듯합니다. 폭 1이면 실패 확률 6%, 폭 16이면 `1 - 0.94^16 ≈ 63%`. 열 배 넘게 오릅니다. 게다가 느린 놈이 끼어들 확률도 10% → `1 - 0.9^16 ≈ 81%` 로 오릅니다. 그러니 「폭을 넓히면 물결마다 재시도와 꼬리에 걸려 오히려 전체가 느려질 것」이라고 예상한 것입니다.

## 3. 실제 (둘째 표) — 갈래 16개를 폭만 바꿔 가며

| 동시 폭 | 물결 수 | 물결 하나(ms) | 총 시간(ms) |
|---:|---:|---:|---:|
| 1 | 16 | 1,179 | 21,104 |
| 2 | 8 | 1,432 | 13,698 |
| 4 | 4 | 1,871 | 9,724 |
| 8 | 2 | 2,533 | 7,306 |
| 16 | 1 | 3,299 | 5,539 |

총 시간은 **한 번도 반등하지 않고 계속 줍니다.** 21,104ms → 5,539ms, 약 3.8배 개선입니다. 예상했던 「폭을 키우면 손해로 돌아서는 지점」은 나타나지 않았습니다.

## 4. 왜 틀렸나 — 두 항의 성장 속도가 다르다

총 시간은 `물결 수 × 물결 하나 + 합류`입니다. 폭(w)을 키울 때 앞의 두 항이 반대로 움직이는데, **줄어드는 쪽이 훨씬 빠릅니다.**

- **물결 수는 `÷w` 로 준다** — 나눗셈입니다. 폭 16이면 16분의 1. 상한 없이 계속 줄어듭니다. 16 → 1, 즉 **16배** 감소.
- **물결 하나는 확률로 늘어난다 — 그런데 상한이 있다** — `1 - (1-p)**w` 는 아무리 커져도 **1을 넘지 못합니다.** 즉 재시도 벌점은 최대 `RETRY_MS` 한 번분(900ms), 느린 놈 벌점도 최대 `TASK_MS × SLOW_X`(3,150ms)에서 멈춥니다. `wave_ms` 의 이론적 상한은 4,050ms — 폭 1일 때(1,179ms)의 3.4배가 끝입니다. 실제로 폭 16에서 3,299ms, **2.8배**에 그쳤습니다.

**16배 감소 vs 2.8배 증가.** 저자가 붙잡은 항은 진짜로 존재했지만, 포화(saturating)하는 항이었고 상대 쪽은 포화하지 않는 나눗셈이었습니다. 「방향은 맞고 크기를 틀린」 종류의 오답입니다.

거기에 하나 더: **실패한 갈래의 재시도도 물결 안에서 같이 병렬로 처리됩니다.** 그래서 한 물결 안에서 두 개가 동시에 실패해도 벌점은 「한 번분」만 붙습니다. 폭을 키우면 실패가 많아지는 대신 그 실패들이 서로 겹쳐서 흡수되는 셈이죠. 직렬(폭 1)은 반대로 실패마다 벌점이 **더해집니다** (`serial()` 이 `n * FAIL * RETRY_MS` 인 이유).

## 5. 그럼 폭을 키우는 값은 어디서 치르나 — 변동성

틀린 예상을 바로잡은 다음에 남는 진짜 교훈이 이것입니다. 「물결 하나(ms)」 칸을 보세요.

> 폭이 커질수록 물결 하나가 길어진다. 제일 느린 갈래가 끝나야 물결이 끝나기 때문이다(꼬리 지연). 16폭이면 물결 하나가 3,299ms 다. 1폭일 때(1,179ms)의 2.8배다.
>
> 그래서 폭을 키우는 값은 「총 시간」이 아니라 「변동성」으로 치른다. 평균은 좋아지는데 최악이 나빠진다. 사용자가 느끼는 건 대개 최악 쪽이다.

- **총 시간(평균)** 은 좋아진다 → 폭을 키워도 된다.
- **물결 하나의 최악(P99)** 은 나빠진다 → 사용자 체감은 이쪽이다.
- 이것이 구글 「The Tail at Scale」이 말하는 **꼬리 지연(tail latency)** 입니다. 폭이 넓어질수록 「하나라도 느릴 확률」이 1로 붙기 때문에, 병렬 팬아웃은 사실상 **매번 최악 갈래의 속도로 동작**하게 됩니다.
- 실무 함의: 스트리밍처럼 중간 산출을 흘려보내거나, 타임아웃·헤지 요청(hedged request)·부분 결과 허용을 넣지 않으면 폭을 키운 이득이 체감에서 사라집니다.

## 6. 헷갈리기 쉬운 지점 — 첫 표의 「손해」와 둘째 표의 「이득」은 다른 축

같은 예제에 표가 두 개 있고, 둘이 정반대 얘기처럼 보여서 자주 섞입니다. **축이 다릅니다.**

**첫 표** — 폭을 4로 **고정**하고 갈래 수 n을 늘림 (직렬 대비 이득):

| 갈래 수 | 직렬(ms) | 병렬 4폭(ms) | 그중 합류 | 이득 |
|---:|---:|---:|---:|---:|
| 2 | 1,908 | 2,151 | 280 | **0.89x** ← 별 이득 없음 |
| 4 | 3,816 | 2,431 | 560 | 1.57x |
| 8 | 7,632 | 4,862 | 1,120 | 1.57x |
| 16 | 15,264 | 9,724 | 2,240 | 1.57x |
| 32 | 30,528 | 19,449 | 4,480 | 1.57x |
| 64 | 61,056 | 38,898 | 8,960 | 1.57x |

- 갈래 2개짜리는 병렬이 **더 느립니다**(0.89배). 펴는 값보다 합류와 꼬리 지연이 더 들어서요.
- 그리고 이득이 **1.57배에서 천장을 칩니다.** 폭이 4인데 4배가 아닙니다.
- 천장의 범인은 **폭이 아니라 합류**입니다. 펴는 값은 `÷폭`인데 합류 값은 `n × 140` 으로 갈래 수에 비례해 **안 줄어듭니다.** 합류가 없다면 같은 계산에서 이득이 약 2.04배까지 갔습니다.

**둘째 표** — 갈래 수를 16으로 **고정**하고 폭 w를 늘림. 여기서는 합류 값이 `16 × 140 = 2,240ms` 로 **상수**라 폭 비교에 개입하지 않습니다. 그래서 순수하게 「물결 수 ÷ vs 물결 하나 ↑」의 싸움이 되고, 나눗셈이 이깁니다.

정리하면 25.2절의 결론은 두 겹입니다.

1. **천장을 만드는 건 합류다** (첫 표). → 폭을 키우기 전에 **합류를 프로파일**하세요. 합류에서 전체를 다시 정렬하거나 중복 제거를 O(n²)로 하면 펴는 의미가 사라집니다. 저자는 실제로 그랬다고 적어 두었습니다.
2. **폭을 키우면 총 시간은 계속 준다. 대신 최악이 나빠진다** (둘째 표, 저자가 틀렸던 곳). → 대가는 시간이 아니라 변동성입니다.

## 7. 이 장의 다른 「틀렸던 예상」과 구분하기

25장에는 저자가 틀렸다고 고백하는 지점이 **두 개** 있습니다. 시험에서 섞일 수 있으니 짝을 맞춰 두세요.

| 예제 | 틀린 예상 | 실제 |
|---|---|---|
| `ex2_fanout.py` (팬아웃) | 「폭을 키우면 하나라도 실패할 확률이 올라 **손해**」 | 물결 수가 줄어드는 효과가 훨씬 커서 **총 시간은 계속 준다**. 대가는 변동성(물결 하나가 길어짐) |
| `ex3_router.py` (라우터) | 「라우팅이 완벽하면 **품질도 오른다**」 | 정확도 100%에서도 품질이 0.894 → 0.880 으로 **내려간다**. 라우터는 품질 향상 장치가 아니라 품질을 조금 내주고 토큰을 크게 아끼는 **교환** |

## 8. 한 줄 암기

> 폭을 키울 때 늘어나는 항(실패·꼬리 확률)은 **1에서 포화**하고, 줄어드는 항(물결 수)은 **÷폭으로 무한히** 준다. 그래서 총 시간은 계속 줄고, 값은 **최악(꼬리 지연)** 으로 치른다. 천장을 만드는 건 폭이 아니라 **합류**다.
