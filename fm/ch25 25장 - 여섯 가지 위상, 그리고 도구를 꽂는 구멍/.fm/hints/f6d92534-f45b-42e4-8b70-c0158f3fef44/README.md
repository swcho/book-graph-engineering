# 폭을 키우면 평균과 최악은 각각 어떻게 되는가?

> **답**: 총 시간(평균)은 줄지만 물결 하나가 길어져 최악이 나빠진다. 사용자가 느끼는 것은 대개 최악 쪽이다.

---

## 1. 용어 정리 — 폭, 물결, 합류

25장 예제 2(`content/ch25/code/ex2_fanout.py`)는 「갈래 $n$개를 병렬로 처리한다」는 상황을 아주 단순한 모델로 잡습니다.

| 용어 | 코드의 이름 | 뜻 |
|---|---|---|
| **갈래** | branch, `n` | 나눠서 처리할 일 하나 (문서 한 편 읽기 같은 것) |
| **폭** | `width`, `w` | *동시에* 돌릴 수 있는 갈래 수 |
| **물결** | `waves` | 폭만큼 묶어서 돌리는 한 배치. 물결 수 = `-(-n // w)` = $\lceil n/w \rceil$ |
| **합류** | `merge` | 갈래 결과를 하나로 합치는 비용. 갈래 수에 비례 (`n * MERGE_PER_BRANCH`) |

핵심은 **물결 하나는 「제일 느린 갈래」가 끝나야 끝난다**는 것입니다. 코드에서도 그 문장이 그대로 함수 독스트링에 있습니다.

```python
def wave_ms(width):
    """한 물결은 «제일 느린 갈래»가 끝나야 끝난다."""
    p_any_slow = 1 - (1 - SLOW_P) ** width      # 하나라도 느릴 확률
    base = TASK_MS * (1 + p_any_slow * (SLOW_X - 1))
    p_any_fail = 1 - (1 - FAIL) ** width        # 하나라도 실패할 확률
    return base + p_any_fail * RETRY_MS
```

즉 물결 하나의 시간은 갈래들의 **평균**이 아니라 **최댓값**이 정합니다. 이게 이 질문의 답 전체를 지배합니다.

---

## 2. 실제 숫자 — 같은 갈래 16개, 폭만 바꾼다

예제의 파라미터는 이렇습니다.

- `TASK_MS = 900` — 갈래 하나 기본 처리 시간
- `SLOW_P = 0.10`, `SLOW_X = 3.5` — 10% 확률로 3.5배 느린 「느린 놈」이 나온다
- `FAIL = 0.06`, `RETRY_MS = 900` — 6% 확률로 실패해서 한 번 더 돈다
- `MERGE_PER_BRANCH = 140` — 합류할 때 갈래당 드는 정리 비용

갈래 16개를 폭만 바꿔 가며 돌리면:

| 동시 폭 | 물결 수 | 하나라도 느릴 확률 | **물결 하나(ms)** | **총 시간(ms)** |
|---:|---:|---:|---:|---:|
| 1 | 16 | 10.0% | 1,179 | 21,104 |
| 2 | 8 | 19.0% | 1,432 | 13,698 |
| 4 | 4 | 34.4% | 1,871 | 9,724 |
| 8 | 2 | 57.0% | 2,533 | 7,306 |
| 16 | 1 | 81.5% | **3,299** | **5,539** |

두 칸이 **반대 방향으로 움직인다**는 게 표 전체의 요점입니다.

- **총 시간**: 21,104 → 5,539ms. 폭을 키우면 계속 줍니다. 3.8배 빨라졌습니다.
- **물결 하나**: 1,179 → 3,299ms. 폭을 키우면 계속 늘어납니다. 2.8배 나빠졌습니다.

저자가 이 절에서 「제가 틀렸던 곳」이라고 고백하는 지점이 여기입니다. 원래 예상은 *「폭을 키우면 하나라도 실패할 확률이 올라서 손해」* 였는데, 실패 확률이 오르는 것보다 **물결 수가 $\lceil n/w \rceil$로 줄어드는 효과가 훨씬 커서** 총 시간은 끝까지 줄어듭니다.

---

## 3. 왜 총 시간은 줄고 물결 하나는 커지나

두 항의 성질이 다릅니다.

**물결 수는 나눗셈으로 줄어든다 — 한계가 없다.**
$\lceil n/w \rceil$은 폭을 두 배로 하면 절반이 됩니다. 계속 줄어듭니다.

**물결 하나는 로그처럼(사실상 포화하며) 늘어난다 — 상한이 있다.**
「하나라도 느릴 확률」은 $1 - (1-p)^w$ 이고, 이건 아무리 폭을 키워도 **1을 넘을 수 없습니다**. 즉 물결 하나의 시간은 최대 「느린 놈 한 번 + 재시도 한 번」 = $900 \times 3.5 + 900 = 4{,}050$ms 근처에서 멈춥니다. 폭 8에서 이미 2,533ms이고 폭 16에서 3,299ms이니 천장에 거의 붙었습니다.

**「무한히 줄어드는 것」 ÷ 「천장이 있는 것」이니 곱은 계속 줄어듭니다.** 이게 총 시간이 단조 감소하는 이유입니다.

그런데 폭을 무한히 키운다고 총 시간이 0이 되지는 않습니다. 남는 것은 **합류 비용** $n \times 140 = 2{,}240$ms입니다. 갈래 수에 비례하고 폭과 무관하므로, 이게 병렬화의 진짜 천장입니다. 예제 2의 첫째 표에서 병렬 이득이 갈래 수를 아무리 늘려도 1.57배에서 멈추는 이유도 같습니다.

| 갈래 수 | 직렬(ms) | 병렬 4폭(ms) | 그중 합류 | 이득 |
|---:|---:|---:|---:|---:|
| 2 | 1,908 | 2,151 | 280 | **0.89x** ← 병렬이 더 느리다 |
| 4 | 3,816 | 2,431 | 560 | 1.57x |
| 8 | 7,632 | 4,862 | 1,120 | 1.57x |
| 64 | 61,056 | 38,898 | 8,960 | 1.57x |

폭이 4인데 4배가 아닙니다. 펴는 값은 나누기($\div w$)인데 합류 값은 갈래 수에 비례해 안 줄어들기 때문입니다. 갈래가 2개뿐일 때는 합류와 꼬리 지연 값이 펴서 번 시간보다 커서 **병렬이 오히려 손해**입니다.

## 4. 「최악」이 왜 사용자에게 더 크게 들리나 — 꼬리 지연

물결 하나가 길어지는 원인은 **꼬리 지연(tail latency)** 입니다. Jeff Dean과 Luiz Barroso의 「The Tail at Scale」(Google, 2013)이 정리한 현상으로, 요지는 이렇습니다.

> 하나의 요청을 $w$개 하위 작업으로 부채꼴로 펴면, 전체 응답 시간은 하위 작업들의 **평균**이 아니라 **최댓값**이 정한다. 그래서 개별 작업의 드문 느림이 전체에서는 흔한 느림이 된다.

숫자로 보면 명확합니다. 갈래 하나가 느릴 확률이 10%뿐인데,

- 폭 1: 물결이 느릴 확률 10%
- 폭 4: $1 - 0.9^4 = 34.4\%$
- 폭 16: $1 - 0.9^{16} = 81.5\%$

**드물던 일이 폭을 키우면 거의 확실한 일이 됩니다.** 개별 갈래는 아무것도 나빠지지 않았는데, 「가장 느린 갈래를 기다린다」는 구조 하나 때문에 관측되는 지연이 나빠집니다.

그리고 「사용자가 느끼는 건 대개 최악 쪽」이라는 문장은 이런 뜻입니다.

- 사용자는 평균 지연을 경험하지 않습니다. 매 요청마다 **그 요청의** 지연을 경험합니다. 서비스 품질은 평균이 아니라 **p95 / p99** 로 이야기됩니다.
- 스트리밍이나 부분 결과를 보여 주는 UI라면 「물결 하나」가 곧 **다음 진행 표시가 나타나기까지의 간격**입니다. 폭 1이면 1.2초마다 뭔가 움직이는데, 폭 16이면 3.3초 동안 아무 일도 안 일어나는 것처럼 보입니다. 총 시간이 4배 빨라졌어도 「멈춘 것 같다」는 인상이 남습니다.
- 타임아웃 설정도 최악 쪽에 걸립니다. 물결 하나에 3.3초 예산을 잡아야 하는데 평균만 보고 1.5초로 잡아 두면 폭을 키운 순간 절반 이상이 타임아웃으로 터집니다.

> **한 가지 정직한 단서**: 예제 2의 모델에서는 「총 시간」의 p95도 폭을 키우면 함께 줄어듭니다(물결 수가 줄면서 분산도 줄기 때문). 그래서 여기서 나빠지는 「최악」은 **물결 하나 = 갈래 단위·부분 결과 단위의 최악 지연**을 가리킵니다. 실제 시스템에서는 여기에 예제가 모델링하지 않은 것들이 더 붙습니다. 폭을 키우면 CPU·메모리·커넥션 풀·레이트 리밋 경쟁이 생기고, 동시 요청이 많아지면 큐가 길어지고, GC나 스로틀링이 겹칩니다. 그래서 현실에서는 「하나라도 느릴 확률」만으로 계산한 것보다 꼬리가 더 두껍게 나옵니다.

## 5. 그래서 무엇을 해야 하나

25장이 이 질문에서 끌어내는 실천 지침은 세 가지입니다.

**(1) 폭을 키우기 전에 합류를 프로파일하라.**
천장을 만드는 건 폭이 아니라 합류입니다. 합류에서 전체를 다시 정렬하거나 중복 제거를 $O(n^2)$로 하고 있으면 펴는 의미가 사라집니다. 특히 **갈래끼리 비교하는 연산**(모든 쌍의 유사도 비교, 교차 검증 등)이 있으면 그건 제곱이라 갈래를 늘릴수록 급격히 나빠집니다. 「합류 코드를 가볍게 유지하는 게 폭을 키우는 것보다 크게 듣는다」가 저자의 결론입니다.

**(2) 폭은 「총 시간」이 아니라 「변동성」으로 값을 치른다는 걸 알고 고르라.**
지연 상한(SLA)이 p99로 걸려 있는 서비스라면, 총 시간이 줄어든다는 이유로 폭을 무작정 키우면 SLA를 깨는 방향으로 갈 수 있습니다. 폭 결정은 「평균을 얼마나 벌고 꼬리를 얼마나 내주는가」의 교환입니다. 25장이 라우터에 대해 말한 것(품질을 올리는 장치가 아니라 교환)과 정확히 같은 구조입니다.

**(3) 꼬리를 직접 다루는 기법을 쓰라.**
「The Tail at Scale」이 제시하는 대응이 그대로 적용됩니다.

- **헤지 요청 / 백업 요청(hedged requests)**: p95를 넘긴 갈래에만 복제 요청을 하나 더 띄우고 먼저 온 것을 씀
- **갈래별 타임아웃 + 부분 결과 허용**: 늦은 갈래를 버리고 나머지로 합류(품질을 조금 내주고 꼬리를 자름)
- **폭을 중간값에서 멈추기**: 예제에서 폭 8은 총 시간 7,306ms / 물결 2,533ms인데, 폭 16은 총 5,539ms / 물결 3,299ms입니다. 총 시간 24% 더 벌려고 물결 하나를 30% 더 내주는 게 맞는 거래인지는 도메인이 정합니다.
- **점진적 렌더링**: 물결이 길어져도 갈래가 끝나는 대로 흘려 보내면 사용자가 느끼는 「최악」이 물결 시간에서 갈래 시간으로 내려옵니다

## 6. 한 줄 정리

$$\text{총 시간} = \underbrace{\left\lceil \frac{n}{w} \right\rceil}_{\text{폭에 반비례, 계속 줄어든다}} \times \underbrace{\mathbb{E}[\text{물결 하나}]}_{\text{폭에 따라 늘지만 천장이 있다}} + \underbrace{n \cdot c}_{\text{폭과 무관. 진짜 천장}}$$

폭을 키우면 앞의 두 항의 곱은 줄어들지만(평균 개선), 둘째 항 자체는 커집니다(최악 악화). 그리고 셋째 항은 아예 꿈쩍하지 않습니다.

**병렬은 시간을 사는 것이지 돈을 아끼는 게 아니고, 그 시간을 사는 값은 변동성으로 지불합니다.**
