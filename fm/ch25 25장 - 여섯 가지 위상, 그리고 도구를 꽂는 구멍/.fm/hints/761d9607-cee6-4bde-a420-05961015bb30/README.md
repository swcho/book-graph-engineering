# 병렬화는 무엇을 사는 것인가?

**답:** 시간을 사는 것이지 돈을 아끼는 것이 아니다. 토큰은 그대로다.

---

## 한 줄로

병렬화(팬아웃)는 **벽시계 시간(latency)** 을 줄이는 장치다. **총 작업량(토큰, 비용)** 은 1비트도 줄지 않는다.
나눠서 동시에 읽는다고 **읽어야 할 양이 줄지는 않으니까.**

## 왜 토큰이 그대로인가

25장 예제 1(`ex1_topologies.py`)이 이걸 숫자 두 줄로 보여 준다.
「문서 8편을 읽고 보고서 한 장을 쓴다」는 **똑같은 작업**을 위상만 바꿔 돌린다.

| 위상 | 지연 계산 | 지연 | 토큰 계산 | 토큰 |
|---|---|---|---|---|
| 경로(파이프라인) | `8 × 900 + 1,800` | **9,000ms** | `8 × 2,400 + 3,200` | **22,400** |
| 이분·합류(팬아웃-팬인, 폭 4) | `2물결 × 900 + 1,800` | **3,600ms** | `8 × 2,400 + 3,200` | **22,400** |

- 지연: 9,000 → 3,600ms. **2.5배 빨라졌다.**
- 토큰: 22,400 → 22,400. **한 개도 안 줄었다.**

수식으로 보면 명백하다. 지연 항에서만 `DOCS`(8)가 `waves`(2)로 바뀌고,
토큰 항의 `DOCS * READ_TOK` 는 **양쪽이 글자 그대로 동일하다.**

```python
def 경로():
    ms  = DOCS * READ_MS + WRITE_MS      # 8번을 차례로
    tok = DOCS * READ_TOK + WRITE_TOK

def 이분합류():
    waves = -(-DOCS // PAR)              # 8편 ÷ 폭 4 = 2물결
    ms  = waves * READ_MS + WRITE_MS      # ← 여기만 바뀐다
    tok = DOCS * READ_TOK + WRITE_TOK     # ← 완전히 같다
```

병렬화가 바꾸는 것은 **일이 배치되는 순서**일 뿐, **일의 총량**이 아니다.
문서 8편은 병렬이든 직렬이든 8편 다 컨텍스트에 들어가야 한다.

## 자주 하는 오해

| 오해 | 실제 |
|---|---|
| 「병렬로 돌리니 싸졌다」 | 안 싸졌다. 같은 토큰을 더 짧은 시간에 태운 것이다. |
| 「폭을 4로 하면 4배 빠르다」 | 아니다. 합류 값과 꼬리 지연이 배수를 깎는다(아래). |
| 「병렬은 언제나 이득이다」 | 갈래가 적으면 **더 느리다.** |

특히 오해가 값비싸지는 지점은 **분당 토큰(TPM) 레이트 리밋**이다.
병렬로 펴면 같은 토큰을 **더 짧은 구간에 몰아서** 쓰기 때문에,
총비용은 같은데 **순간 처리율은 폭배로 뛴다.** 그래서 직렬에서는 안 걸리던
레이트 리밋이 병렬로 바꾼 순간 걸리기 시작한다. 「돈을 아끼려고」 병렬로 펴면
아끼는 것도 없이 429만 받는다.

## 그 시간마저 공짜가 아니다 — 병렬이 **손해**인 구간

예제 2(`ex2_fanout.py`)는 「펴는 게 이득인 구간이 생각보다 좁다」를 잰다.
갈래 하나 900ms, **합류 정리에 갈래당 140ms**, 갈래 실패율 6%.

- 갈래가 **2개**뿐이면 직렬 1,908ms vs 병렬 2,151ms → **0.89배. 더 느리다.**
  펴서 아낀 시간보다 **합류 값 + 꼬리 지연**이 더 들기 때문이다.
- 갈래를 늘려도 이득은 **약 1.57배에서 천장**을 친다. 폭이 4인데 4배가 아니다.
  펴는 값은 **나누기(÷폭)** 인데, 합류 값은 **갈래 수에 비례(×n)** 해서 안 줄어드니까.

```python
def parallel(n, width):
    waves = -(-n // width)
    ms    = waves * wave_ms(width)     # ÷폭 — 줄어드는 쪽
    merge = n * MERGE_PER_BRANCH       # ×n  — 안 줄어드는 쪽 ← 천장의 정체
    return ms + merge, merge
```

즉 **천장을 만든 것은 폭이 아니라 합류다.** 그래서 폭을 키우기 전에
합류를 프로파일해야 한다. 합류에서 전체 재정렬이나 O(n²) 중복 제거를 하고 있으면
펴는 의미 자체가 사라진다.

## 시간을 산 대가는 「변동성」으로 치른다

같은 갈래 16개를 폭만 바꿔 보면, 폭을 키울수록 **총 시간은 계속 준다.**
(「폭을 키우면 하나라도 실패할 확률이 올라 손해」라는 직관은 틀렸다.
물결 수가 줄어드는 효과가 훨씬 크다.)

대신 **물결 하나**가 길어진다. 한 물결은 **제일 느린 갈래**가 끝나야 끝나기 때문이다 — 꼬리 지연(tail latency).

- 1폭: 물결 하나 1,179ms
- 16폭: 물결 하나 **3,299ms (2.8배)**

```python
def wave_ms(width):
    """한 물결은 «제일 느린 갈래»가 끝나야 끝난다."""
    p_any_slow = 1 - (1 - SLOW_P) ** width   # 폭이 커지면 1로 수렴
    ...
```

폭이 커지면 「느린 놈이 **하나라도** 섞일 확률」이 `1 - (1-p)^width` 로 올라가고,
물결은 그 하나에 인질로 잡힌다. **평균은 좋아지고 최악은 나빠진다.**
그리고 사용자가 체감하는 건 대개 최악 쪽(p99)이다.

## 정리 — 병렬화의 손익계산서

| 항목 | 병렬화하면 |
|---|---|
| 벽시계 지연(평균) | **좋아진다** ← 사는 것 |
| 토큰 / 비용 | 그대로 (합류 로직이 붙으면 오히려 **늘 수도**) |
| 최악 지연(p99), 변동성 | **나빠진다** ← 치르는 값 |
| 순간 처리율 / 레이트 리밋 압력 | **올라간다** |
| 구현·디버깅 복잡도 | 올라간다 |

**돈을 아끼고 싶다면** 병렬화가 아니라 다른 손잡이를 잡아야 한다.
읽는 문서 수를 줄이거나(필터·검색), 값싼 모델로 라우팅하거나(25.3 동적 엣지),
프롬프트 캐싱을 붙이거나 — 이것들은 **작업량 자체**를 건드린다. 병렬화는 안 건드린다.

## 관련 개념

- **팬아웃/팬인(fan-out, fan-in)**: 갈래로 펴고 다시 합치는 위상. [Azure Durable Functions 문서](https://learn.microsoft.com/en-us/azure/azure-functions/durable/durable-functions-cloud-backup)
- **꼬리 지연(tail latency)**: 폭이 커질수록 최악이 지배하는 현상. [The Tail at Scale](https://research.google/pubs/the-tail-at-scale/)
- **암달의 법칙**: 병렬화로 줄일 수 없는 직렬 구간(여기서는 합류·보고서 작성)이 배수의 상한을 정한다.

## 시험용 한 줄

> 병렬화는 **지연을 토큰으로 바꾸지 않는다.** 지연을 **변동성과 복잡도**로 바꾼다. 토큰은 상수다.
