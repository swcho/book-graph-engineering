# 라우터의 정체는 무엇인가?

> **답**: 품질을 올리는 장치가 아니라 **교환**이다. 얼마를 내주고 얼마를 아끼는지 계산하려면 **채점 데이터셋**이 먼저 있어야 한다.

출처: 25장 「여섯 가지 위상, 그리고 도구를 꽂는 구멍」 25.3절 — *라우터는 품질을 올리는 장치가 아니다* / 예제 `content/ch25/code/ex3_router.py`

---

## 1. 라우터가 무엇인지 먼저

25장은 에이전트 위상을 여섯 가지로 정리합니다. 경로(파이프라인), 이분·합류(팬아웃·팬인), 성형(감독자-작업자), 순환(생성-검증), **동적 엣지**, 트리.

라우터는 이 중 **동적 엣지** 위상의 실체입니다. 입력을 한 번 보고 「어느 하위 경로로 보낼까」를 정하는 노드예요. 그래프의 말로 하면, 다음에 밟을 엣지를 **런타임에 고르는** 노드입니다.

`ex1_topologies.py` 에서 동적 엣지 줄만 보면 이렇게 나옵니다.

| 위상 | 지연(ms) | 토큰 | 품질 | 토큰당 품질 |
|---|---:|---:|---:|---:|
| 경로 | 9,000 | 22,400 | 0.71 | 0.317 |
| 이분·합류 | 3,600 | 22,400 | 0.71 | 0.317 |
| 성형 | 4,500 | 23,600 | 0.78 | 0.331 |
| 순환 | 9,300 | 32,100 | 0.89 | 0.277 |
| **동적 엣지** | **3,900** | **22,800** | **0.81** | **0.355** |
| 트리 | 4,800 | 29,600 | 0.84 | 0.284 |

동적 엣지가 「토큰당 품질」 1등입니다. 하지만 품질 절대값 1등은 순환(0.89)이에요. **이게 이미 답의 절반입니다.** 라우터가 잘하는 건 *효율*이지 *품질*이 아닙니다.

## 2. 저자가 틀렸던 지점 — 「완벽한 라우터면 품질도 오르겠지」

`ex3_router.py` 는 딱 이 기대를 실험으로 깨뜨립니다. 설정은 이렇습니다.

```python
# 길 이름     비용   이 길이 «맞을 때» 품질   «틀린 길로 왔을 때» 품질
ROUTES = {
    "빠른 길":   (1_200, 0.86, 0.42),
    "정밀한 길": (7_400, 0.93, 0.88),
}
MIX = {"빠른 길": 0.72, "정밀한 길": 0.28}   # 실제 입력의 분포
N = 1_000
```

읽는 법:
- 입력 1,000건 중 **72%는 빠른 길로 충분**하고 **28%는 정밀한 길이 필요**합니다.
- 빠른 길은 6배 이상 쌉니다(1,200 대 7,400 토큰).
- 그런데 **정밀한 길은 「굳이 안 써도 되는 입력」에도 0.88 을 냅니다.** 빠른 길이 제 몫을 할 때의 0.86 보다 높아요.
- 반대로 정밀한 길이 필요한 입력을 빠른 길로 보내면 0.42 로 폭락합니다.

실행 결과입니다.

```
입력 1000건. 72%는 빠른 길로 충분하고 28%는 정밀한 길이 필요하다.

방식                                총 토큰     평균 품질       절감
----------------------------------------------------------
전부 정밀한 길                     7,400,000     0.894        -
라우팅 (정확도 100%)               2,936,000     0.880     60%
라우팅 (정확도 95%)                3,072,400     0.873     58%
라우팅 (정확도 90%)                3,208,800     0.867     57%
라우팅 (정확도 80%)                3,481,600     0.854     53%
라우팅 (정확도 70%)                3,754,400     0.841     49%
라우팅 (정확도 50%)                4,300,000     0.815     42%
```

**정확도 100% 에서조차 품질이 0.894 → 0.880 으로 내려갑니다.**

이유는 위 가정에 있습니다. 이 설정에서 정밀한 길은 **품질로는 언제나 이깁니다**(맞는 입력 0.93, 안 맞는 입력에도 0.88 ≥ 0.86). 그러니 「전부 정밀한 길」이 품질 상한이고, 라우터가 아무리 잘해도 그 상한을 넘을 길이 없어요. 라우터는 그 상한에서 **내려오는 대신 토큰을 아끼는 장치**입니다.

> 그러니 라우팅은 품질을 «올리는» 장치가 아니다. 품질을 조금 내주고 토큰을 크게 아끼는 «교환»이다.

## 3. 교환의 산수 — 두 직선

`routed(acc)` 를 풀면 정확도 `a` 에 대해 둘 다 **직선**입니다.

품질:
```
Q(a) = 0.72·(a·0.86 + (1-a)·0.88) + 0.28·(a·0.93 + (1-a)·0.42)
     = 0.7512 + 0.1284·a
```

비용:
```
C(a) = 720·(a·1200 + (1-a)·7400) + 280·(a·7400 + (1-a)·1200)
     = 5,664,000 - 2,728,000·a
```

여기서 읽을 것이 세 가지입니다.

1. **정확도 1%p 를 올리면 품질 +0.00128, 토큰 -27,280.** 라우터 정확도 개선은 두 축이 같이 좋아지는 순이득입니다. 교환은 라우터 *안*에서 일어나는 게 아니라, **라우터 vs 「전부 비싼 길」** 사이에서 일어납니다.
2. **기준선(baseline)이 있어야 교환이 보입니다.** 표의 첫 줄 「전부 정밀한 길」이 없으면 0.880 이 좋은지 나쁜지 알 수가 없어요. 라우터를 넣고 「좋아진 것 같다」고 말하게 되는 이유가 이겁니다.
3. **교환비는 정확도에 따라 급격히 나빠집니다.**

| 정확도 | 내주는 품질 | 아끼는 토큰 | 품질 1%p 당 절감 |
|---:|---:|---:|---:|
| 100% | 1.4%p | 60% | 약 43%/%p |
| 90% | 2.7%p | 57% | 약 21%/%p |
| 80% | 4.0%p | 53% | 약 13%/%p |
| 70% | 5.3%p | 49% | 약 9%/%p |
| 50% | 8.0%p | 42% | 약 5%/%p |

정확도 50% 는 「동전 던지기 라우터」입니다. 품질 8%p 를 내주고 42% 만 아껴요. 절감은 절반 남았는데 손실은 6배가 됐습니다. **이건 대개 손해입니다.**

## 4. 「남는 장사인지」는 도메인이 정한다

품질 1.4%p 라는 숫자 자체에는 좋다·나쁘다가 없습니다. 책의 판정 기준은 이렇습니다.

- 그 1.4%p 가 **사람 눈에 안 보이는 서비스**라면(요약 문장의 매끄러움, 추천 순서의 미세한 차이) 토큰 60% 절감은 압도적으로 남는 장사입니다.
- 그 1.4%p 가 **오답 14건**이 되는 서비스라면(1,000건 중 14건, 예: 금액 계산, 의료·법률 판단, 결재선 조회) 절대 안 됩니다.

같은 숫자가 정반대의 결론을 냅니다. 그래서 라우터 도입은 **아키텍처 결정이 아니라 제품 결정**입니다.

또 하나 숨은 비용: 실전 라우터는 판단 자체에 토큰을 씁니다. `ex1` 의 `ROUTE_MS, ROUTE_TOK = 300, 400` 이 그것이에요. 두 길의 가격 차가 작을수록 라우팅 오버헤드가 절감을 다 먹습니다. 「비싼 길과 싼 길의 차가 라우터 비용보다 충분히 큰가」를 먼저 봐야 합니다.

## 5. 그래서 제일 먼저 만들 것은 라우터가 아니다

이 카드의 핵심 실천 항목입니다.

> 라우터 정확도를 모르면 이 교환을 계산할 수 없고, 계산 못 하면 «라우터 넣었더니 좋아졌다»는 느낌만 남는다.
>
> 그래서 라우터를 넣을 때 제일 먼저 만들 것은 라우터가 아니라 **«라우팅이 맞았는지 채점하는 데이터셋»**이다. **100건이면 시작할 수 있다.**

순서를 정리하면:

1. **입력 100건을 뽑고, 각 건에 「정답 경로」를 사람이 라벨링합니다.** 이게 채점 데이터셋입니다.
2. 그 라벨로 **입력 분포(MIX)** 를 잽니다. 예제의 72:28 이 이 숫자예요. 분포를 모르면 절감 추정 자체가 불가능합니다.
3. 각 경로의 **비용과 품질 4칸**(맞는 입력·틀린 입력 × 두 경로)을 잽니다.
4. **기준선을 먼저 돌립니다.** 「전부 비싼 길」의 품질과 토큰. 이게 없으면 비교가 안 됩니다.
5. 그다음에 라우터를 만들고, 같은 100건으로 **정확도**를 잽니다.
6. 표를 만들어 「내주는 품질 / 아끼는 토큰」을 확정하고, **제품 쪽에 물어봅니다.** 이 손실이 허용되는가.

한 가지 주의: 100건은 *시작*할 수 있는 크기지 정밀 측정치가 아닙니다. 정확도 90% 근처에서 n=100 이면 표준오차가 약 3%p 라, 95% 신뢰구간이 대략 ±6%p 입니다. 위 표에서 90%와 80% 사이는 결론이 꽤 갈리니, 경계에 걸리면 표본을 늘려야 합니다. 그래도 **0건보다 100건이 압도적으로 낫다**는 게 요점입니다. 데이터셋 없이 넣은 라우터는 성능 개선이 아니라 신념입니다.

## 6. 자주 하는 오해 정리

| 오해 | 실제 |
|---|---|
| 라우터를 넣으면 품질이 오른다 | 대개 내려간다. 오르는 건 **토큰당 품질**이다 |
| 라우터가 완벽하면 품질 손실이 없다 | 정확도 100% 에서도 1.4%p 내려갔다. 비싼 길이 쉬운 입력에도 잘하기 때문 |
| 라우터 정확도만 높이면 된다 | 정확도 개선은 순이득이지만, 교환의 기준선은 「전부 비싼 길」이다. 기준선 없이 정확도만 봐도 판단이 안 된다 |
| 라우터는 나중에 A/B 로 검증하면 된다 | 채점 데이터셋이 없으면 A/B 로도 «왜» 좋아졌는지 못 가른다. 라벨이 먼저다 |
| 품질 1.4%p 는 무시할 만하다 | 1,000건이면 14건이다. 그 14건의 값이 도메인마다 다르다 |

## 7. 한 줄로 외우기

**라우터 = 「품질 조금 ↔ 토큰 많이」 교환권. 교환권의 환율은 라우터 정확도가 정하고, 정확도는 채점 데이터셋 없이는 측정 불가. 그래서 라우터보다 데이터셋이 먼저다.**
