# 폭 16 vs 폭 1 — 물결 하나가 2.8배 길어진다

**질문** 폭 16과 폭 1의 물결 하나 시간은 얼마나 차이 나는가?

**답** 폭 16은 3,299ms, 폭 1은 1,179ms로 약 2.8배다. 꼬리 지연 때문이다.

출처: 25장 예제 2 `code/ex2_fanout.py`, 둘째 표(`같은 갈래 16개를 폭만 바꿔 가며`)와 그 아래 해설.

---

## 1. 「물결」이란 무엇인가

갈래 16개를 동시 폭 `width` 로 처리하면, 한 번에 `width` 개씩 묶어서 돌린다. 이 한 묶음이 **물결(wave)** 이다.

- 폭 1 → 물결 16개 (사실상 직렬)
- 폭 4 → 물결 4개
- 폭 16 → 물결 1개

핵심 규칙은 `wave_ms()` 의 독스트링에 그대로 적혀 있다.

> 한 물결은 «제일 느린 갈래»가 끝나야 끝난다.

즉 물결 시간은 갈래들의 **평균**이 아니라 **최댓값**이다. 폭이 커지면 「최댓값을 뽑는 표본 수」가 늘어나므로, 물결 하나가 길어진다. 이것이 꼬리 지연(tail latency)이다.

## 2. 식과 파라미터

`ex2_fanout.py` 상단 상수:

| 상수 | 값 | 뜻 |
|---|---|---|
| `TASK_MS` | 900 | 갈래 하나 처리 시간 |
| `SLOW_P` | 0.10 | 갈래 하나가 「느린 놈」일 확률 |
| `SLOW_X` | 3.5 | 느린 놈은 이만큼 더 걸린다 |
| `FAIL` | 0.06 | 갈래 하나가 실패할 확률 |
| `RETRY_MS` | 900 (`= TASK_MS`) | 실패하면 한 번 더 |
| `MERGE_PER_BRANCH` | 140 | 합류 시 갈래당 정리 비용 |

```python
def wave_ms(width):
    """한 물결은 «제일 느린 갈래»가 끝나야 끝난다."""
    p_any_slow = 1 - (1 - SLOW_P) ** width
    base       = TASK_MS * (1 + p_any_slow * (SLOW_X - 1))
    p_any_fail = 1 - (1 - FAIL) ** width
    return base + p_any_fail * RETRY_MS
```

읽는 법은 두 항이다.

1. **느린 놈 항** — `p_any_slow` 는 「폭 안에 느린 놈이 **하나라도** 있을 확률」. 하나라도 있으면 물결 전체가 `SLOW_X` 배로 늘어난다고 근사했다. 그래서 `base = 900 × (1 + p_any_slow × 2.5)`.
2. **실패 재시도 항** — `p_any_fail` 는 「폭 안에 실패가 **하나라도** 있을 확률」. 있으면 재시도 900ms 를 한 번 더 얹는다.

두 항 모두 `1 - (1-p)^width` 꼴, 즉 **여집합의 곱**이다. 폭이 커질수록 1에 붙는다. 이게 2.8배의 정체다.

## 3. 손으로 계산해 검증

### 폭 1

```
p_any_slow = 1 - 0.9^1  = 0.1000
base       = 900 × (1 + 0.1 × 2.5) = 900 × 1.25 = 1,125.00 ms
p_any_fail = 1 - 0.94^1 = 0.0600
retry      = 0.06 × 900 = 54.00 ms
wave_ms(1) = 1,125.00 + 54.00 = 1,179.00 ms   ← 1,179ms ✅
```

### 폭 16

```
0.9^16     = 0.185302...
p_any_slow = 1 - 0.185302 = 0.814698
base       = 900 × (1 + 0.814698 × 2.5) = 900 × 3.036745 = 2,733.07 ms

0.94^16    = 0.371574...
p_any_fail = 1 - 0.371574 = 0.628426
retry      = 0.628426 × 900 = 565.58 ms

wave_ms(16) = 2,733.07 + 565.58 = 3,298.65 ms → 3,299ms ✅ (표는 :,.0f 로 반올림)
```

### 배수

```
3,298.65 / 1,179.00 = 2.7978... ≈ 2.8배 ✅
```

## 4. 실제 출력 표 (직접 실행해 재현)

`parallel(16, w) = waves × wave_ms(w) + 16 × 140` 이고 합류는 항상 2,240ms 로 고정이다.

| 동시 폭 | 물결 수 | p_any_slow | p_any_fail | 물결 하나(ms) | 물결 합 | 합류 | 총 시간(ms) |
|---:|---:|---:|---:|---:|---:|---:|---:|
| 1 | 16 | 0.1000 | 0.0600 | **1,179** | 18,864 | 2,240 | 21,104 |
| 2 | 8 | 0.1900 | 0.1164 | 1,432 | 11,458 | 2,240 | 13,698 |
| 4 | 4 | 0.3439 | 0.2193 | 1,871 | 7,484 | 2,240 | 9,724 |
| 8 | 2 | 0.5695 | 0.3904 | 2,533 | 5,066 | 2,240 | 7,306 |
| 16 | 1 | 0.8147 | 0.6284 | **3,299** | 3,299 | 2,240 | 5,539 |

읽어야 하는 두 방향이 있다.

- **총 시간 칸(↓ 계속 줄어든다)** — 21,104 → 5,539ms. 폭을 키우면 총 시간은 **계속 준다**. 물결 수가 `÷폭` 으로 줄어드는 효과가 물결 하나가 길어지는 효과보다 훨씬 크다. 저자가 「제가 틀렸던 곳」이라고 적은 부분이 이것이다. 「폭을 키우면 하나라도 실패할 확률이 올라서 손해」라고 예상했지만 아니었다.
- **물결 하나 칸(↑ 계속 늘어난다)** — 1,179 → 3,299ms, 2.8배. 폭을 키우는 값은 **총 시간이 아니라 변동성으로** 치른다.

이 장의 한 줄 요약: **평균은 좋아지고 최악은 나빠진다. 사용자가 느끼는 건 대개 최악 쪽이다.**

## 5. 2.8배는 어디서 왔나 — 항별 분해

기본 처리 시간 900ms 에 얼마가 얹혔는지 보면 원인이 선명하다.

| 폭 | 기본 | + 느린 놈 항 | + 실패 재시도 항 | = 물결 하나 |
|---:|---:|---:|---:|---:|
| 1 | 900 | +225 | +54 | 1,179 |
| 16 | 900 | +1,833 | +566 | 3,299 |

- 느린 놈 항이 225 → 1,833ms (8.1배). 2.8배의 주된 원인.
- 실패 재시도 항이 54 → 566ms (10.5배).
- 기본 900ms 는 폭과 무관하게 그대로. 즉 **늘어난 2,120ms 전부가 꼬리**다.

그래서 답의 「꼬리 지연 때문이다」가 정확하다. 갈래 하나가 빨라진 것도 느려진 것도 없다. 폭 안에서 최댓값을 뽑는 표본이 1개에서 16개로 늘어난 것뿐이다.

## 6. 배경 — Google 「The Tail at Scale」

이 `1 - (1-p)^N` 구조는 Dean & Barroso 의 [The Tail at Scale](https://research.google/pubs/the-tail-at-scale/) (CACM 56(2), 2013) 이 대중화한 논증이다. 25장 키워드 표에도 「꼬리 지연 [사실상 표준]」으로 이 논문이 걸려 있다.

논문의 대표 예:

> 서버 한 대의 99분위 지연이 1초라면, 서버 1대만 쓸 때는 요청의 1%만 느리다. 그런데 한 사용자 요청이 **100대에 병렬로 물어봐서 다 모아야** 하면, `0.99^100 ≈ 0.37` 이므로 **63%** 의 요청이 1초를 넘는다.

`ex2_fanout.py` 의 `p_any_fail` 도 폭 16에서 `1 - 0.94^16 = 0.628` 로 우연히 비슷한 63% 근처에 온다. 구조가 같기 때문이다.

논문이 말하는 함의도 그대로 옮겨온다.

- **평균 지연으로 병렬 시스템을 판단하면 틀린다.** 팬아웃 폭이 곧 꼬리 증폭 계수다.
- **꼬리를 없앨 수는 없다.** 폭을 줄이거나(느려진다), 꼬리를 견디는 기법(hedged request, tied request, micro-partitioning 등)을 쓰거나 둘 중 하나다.
- 그래서 SLO 를 p50 이 아니라 p95/p99 로 잡는 관행이 나왔다.

## 7. 함께 기억할 것 — 천장을 만드는 건 폭이 아니라 합류

같은 예제의 **첫째 표**는 다른 얘기를 한다. 갈래 2개짜리는 병렬이 0.89배로 **더 느리고**, 갈래를 늘려도 이득이 1.57배에서 천장을 친다(폭 4인데 4배가 아니다).

이유는 위 표의 「합류」 칸이다. `merge = n × MERGE_PER_BRANCH` — 펴는 값은 `÷폭` 인데 합류 값은 **갈래 수에 비례해서 안 줄어든다**. 폭 16의 총 5,539ms 중 2,240ms(40%)가 합류다.

정리하면 이 예제가 주는 세 문장:

1. 폭을 키우면 총 시간은 준다. 대신 물결 하나가 길어진다(1,179 → 3,299ms, 2.8배).
2. 그 값은 「변동성」으로 치른다. 평균↑ 최악↓, 사용자는 최악을 느낀다.
3. 폭을 키우기 전에 **합류를 프로파일**하라. 합류에서 정렬이나 O(n²) 중복 제거를 하고 있으면 펴는 의미가 사라진다.

```python
>>> TASK_MS, SLOW_P, SLOW_X, FAIL = 900, 0.10, 3.5, 0.06
>>> f = lambda w: TASK_MS*(1+(1-(1-SLOW_P)**w)*(SLOW_X-1)) + (1-(1-FAIL)**w)*TASK_MS
>>> f(1), f(16), f(16)/f(1)
(1179.0, 3298.6535..., 2.79784...)
```

## 9. 자주 헷갈리는 지점

| 헷갈림 | 바로잡기 |
|---|---|
| 「폭 16이 2.8배 느리다」 | 아니다. **물결 하나**가 2.8배다. **총 시간**은 21,104 → 5,539ms 로 오히려 3.8배 빨라진다. |
| 「폭을 키우면 실패 때문에 손해」 | 저자가 예상했다가 틀린 부분. 물결 수 감소 효과가 훨씬 크다. |
| 「2.8배는 실패율 때문」 | 주범은 느린 놈 항(+225 → +1,833ms). 실패 항은 +54 → +566ms 로 보조. |
| 「병렬이 토큰을 아낀다」 | 아니다. 병렬은 **시간을 사는 것**이지 돈을 아끼는 게 아니다(예제 1: 경로와 이분·합류의 토큰이 같다). |
| 「폭을 키우면 되니까 합류는 나중에」 | 반대다. 천장을 만드는 건 합류다. 합류를 먼저 프로파일하라. |
