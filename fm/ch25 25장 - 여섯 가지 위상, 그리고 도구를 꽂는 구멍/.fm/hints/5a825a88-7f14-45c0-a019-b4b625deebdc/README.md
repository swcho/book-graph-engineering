# 라우터 정확도 50%의 교환

**질문** — 라우터 정확도 50%면 교환이 어떻게 되는가?

**답** — 품질 8%p를 내주고 42%를 아낀다. 이건 대개 손해다.

---

## 1. 이 숫자가 나오는 설정

`ex3_router.py`(25.3절)의 가정입니다. 길은 두 개, 입력은 1,000건.

| 길 | 비용/건 | 이 길이 **맞을 때** 품질 | **틀린 길로 왔을 때** 품질 |
|---|---|---|---|
| 빠른 길 | 1,200 | 0.86 | 0.42 |
| 정밀한 길 | 7,400 | 0.93 | 0.88 |

입력 분포(`MIX`)는 빠른 길로 충분한 것 72%, 정밀한 길이 필요한 것 28%.

여기서 중요한 건 표 오른쪽 아래의 **0.88**입니다. 정밀한 길은 「굳이 안 써도 되는 입력」에도 0.88을 냅니다. 빠른 길이 제 몫을 다 했을 때의 0.86보다 높아요. 즉 이 설정에서 정밀한 길은 **품질로는 언제나 이깁니다**. 라우팅이 품질을 올릴 여지가 애초에 없습니다.

### 비교 기준: 전부 정밀한 길

```
비용 = 1,000 × 7,400 = 7,400,000
품질 = 0.72 × 0.88 + 0.28 × 0.93
     = 0.6336 + 0.2604 = 0.894
```

이 **0.894 / 7,400,000**이 모든 절감·손실의 기준선입니다.

---

## 2. 정확도 50%를 손으로 계산

정확도 50%는 두 갈래 라우터에서 **동전 던지기**입니다. 각 입력이 맞는 길로 갈 확률 0.5, 틀린 길로 갈 확률 0.5.

네 갈래로 쪼개면 이렇게 됩니다.

| 실제 종류 | 건수 | 보내진 길 | 확률 | 비용 | 품질 기여 |
|---|---|---|---|---|---|
| 빠른 길 필요 | 720 | 빠른 길 (맞음) | 0.5 | 720×0.5×1,200 = 432,000 | 0.72×0.5×**0.86** = 0.3096 |
| 빠른 길 필요 | 720 | 정밀한 길 (틀림) | 0.5 | 720×0.5×7,400 = 2,664,000 | 0.72×0.5×**0.88** = 0.3168 |
| 정밀한 길 필요 | 280 | 정밀한 길 (맞음) | 0.5 | 280×0.5×7,400 = 1,036,000 | 0.28×0.5×**0.93** = 0.1302 |
| 정밀한 길 필요 | 280 | 빠른 길 (틀림) | 0.5 | 280×0.5×1,200 = 168,000 | 0.28×0.5×**0.42** = 0.0588 |
| | | | **합** | **4,300,000** | **0.8154** |

- 절감 = 1 − 4,300,000 / 7,400,000 = 0.41892 → **42%**
- 품질 손실 = 0.894 − 0.8154 = 0.0786 → **7.86%p ≈ 8%p**

답의 두 숫자가 그대로 나옵니다. 코드 출력이 `{q:>10.3f}`, `{1-c/pc:>8.0%}` 포맷이라 표에는 `0.815`, `42%`로 찍힙니다.

> 헷갈리기 쉬운 지점: 「빠른 길 필요한 걸 정밀한 길로 보냄」의 품질이 **0.88**입니다. 0.86이 아닙니다. 코드가 `ROUTES[taken]`에서 값을 꺼내기 때문에, 틀렸을 때 쓰이는 값은 *실제로 지나간 길*의 「틀림」 품질이에요.

## 3. 정확도 100%와 나란히 놓기

| 방식 | 총 토큰 | 평균 품질 | 절감 | 품질 손실 | 절감/손실 비 |
|---|---|---|---|---|---|
| 전부 정밀한 길 | 7,400,000 | 0.894 | — | — | — |
| 라우팅 (정확도 100%) | 2,936,000 | 0.880 | **60%** | **1.44%p** | **41.9** |
| 라우팅 (95%) | 3,072,400 | 0.873 | 58% | 2.08%p | 28.1 |
| 라우팅 (90%) | 3,208,800 | 0.867 | 57% | 2.72%p | 20.8 |
| 라우팅 (80%) | 3,481,600 | 0.854 | 53% | 4.01%p | 13.2 |
| 라우팅 (70%) | 3,754,400 | 0.841 | 49% | 5.29%p | 9.3 |
| 라우팅 (**50%**) | 4,300,000 | 0.815 | **42%** | **7.86%p** | **5.3** |
| 라우팅 (0%, 전부 반대로) | 5,664,000 | 0.751 | 24% | 14.28%p | 1.6 |

100% → 50%로 내려갈 때:

- 품질 손실은 1.44%p → 7.86%p, **5.5배**로 불어납니다.
- 절감은 60% → 42%, **0.69배**로 줄어듭니다.

**같은 방향으로 움직이는 폭이 전혀 다릅니다.** 잃는 쪽은 배로 커지고, 아끼는 쪽은 조금 깎이는 정도예요. 그래서 「그래도 42%나 아꼈다」는 위안이 함정입니다. 42%는 라우터가 잘해서 얻은 게 아닙니다.

## 4. 왜 절감은 그만큼 커지지 않는가 — 구조

두 지표를 정확도 `a`의 식으로 펼치면 **둘 다 선형**입니다.

```
품질(a) = 0.72·[a·0.86 + (1−a)·0.88] + 0.28·[a·0.93 + (1−a)·0.42]
        = 0.7512 + 0.1284·a

손실(a) = 0.894 − 품질(a) = 0.1428 − 0.1284·a      (%p 단위로는 14.28 − 12.84a)

비용(a) = 720·[a·1,200 + (1−a)·7,400] + 280·[a·7,400 + (1−a)·1,200]
        = 5,664,000 − 2,728,000·a

절감(a) = 1 − 비용(a)/7,400,000 = 0.2346 + 0.3686·a      (% 단위로는 23.46 + 36.86a)
```

`a=0.5`를 넣으면 품질 0.8154, 절감 0.41892. `a=1.0`이면 0.8796, 0.60324. 표와 일치합니다.

여기서 구조가 보입니다.

| | `a=0`일 때 | `a=1`일 때 | 정확도가 바꾸는 폭 |
|---|---|---|---|
| 절감 | **23.46%** | 60.32% | 2.6배 |
| 손실 | 14.28%p | **1.44%p** | 9.9배 |

**절감에는 정확도와 무관한 큰 상수항(23.46%)이 있습니다.** 라우터가 100% 틀려도 24%는 아낍니다. 입력의 72%가 싼 길로 갈 수 있다는 *분포* 자체가 절감의 대부분을 이미 만들어 놓았고, 정확도는 그 위에 얹는 웃돈일 뿐이에요.

반면 **손실에는 그런 방석이 없습니다.** 정확도 1이 만드는 손실 1.44%p는 상수항 14.28%p에서 12.84%p를 거의 다 깎아낸 결과입니다. 정확도가 떨어지면 그 깎인 양이 그대로 되돌아옵니다.

그래서 정확도가 떨어질 때:

- 절감은 **넉넉한 하한(23%) 쪽으로 완만히** 내려앉고,
- 손실은 **0에 붙어 있던 자리에서 배로** 튀어 오릅니다.

**교환 효율**(절감 %당 손실 %p로 환산한 「환율」)로 보면 한 줄로 정리됩니다.

```
정확도 100% → 품질 1%p당 절감 41.9%
정확도  50% → 품질 1%p당 절감  5.3%      ← 약 8배 악화
```

같은 1%p의 품질을 팔아서 받는 값이 8분의 1로 떨어졌습니다. 이게 「대개 손해다」의 정확한 의미입니다.

## 5. 손익 분기 정확도

### (a) 품질을 안 잃는 정확도는 존재하지 않는다

```
손실(a) = 0.1428 − 0.1284·a = 0  →  a = 0.1428 / 0.1284 = 1.112 (111.2%)
```

**111%가 필요합니다. 불가능해요.** 정밀한 길이 「불필요한 입력」에도 0.88(> 0.86)을 내는 설정이라, 라우터가 아무리 완벽해도 품질은 기준선을 못 넘습니다. 라우팅은 이 설정에서 **영원히 교환이지 개선이 아닙니다.** 예제 주석의 「제가 기대한 건 *라우팅이 완벽하면 품질도 오른다*였다. 안 올랐다」가 바로 이 계산입니다.

### (b) 품질 손실 예산으로 잡는 분기점

도메인이 「손실 X%p까지 감당한다」고 말할 수 있으면, 필요한 최소 정확도가 곧바로 나옵니다.

```
0.1428 − 0.1284·a ≤ 예산  →  a ≥ (0.1428 − 예산) / 0.1284
```

| 감당할 품질 손실 | 필요 최소 정확도 |
|---|---|
| 1%p | 103.4% (**불가능**) |
| 2%p | **95.6%** |
| 3%p | 87.9% |
| 5%p | 72.3% |
| 8%p | 49.8% |

「품질 2%p까지는 괜찮다」는 흔한 기준을 대면 **라우터 정확도 96%가 필요합니다.** 50%로는 어림도 없습니다.

### (c) 절감과 손실을 같은 화폐로 놓는 분기점

「품질 1%p를 내주려면 절감이 최소 `k`% 나와야 한다」로 조직의 환율 `k`를 정했다고 하면,

```
23.46 + 36.86·a = k · (14.28 − 12.84·a)
      ⇒  a* = (14.28k − 23.46) / (36.86 + 12.84k)
```

| 환율 k (품질 1%p당 요구 절감 %) | 손익 분기 정확도 a* |
|---|---|
| 10 | 72.2% |
| 15 | 83.1% |
| 20 | 89.3% |
| 30 | 95.9% |
| 41.9 | 100.0% (**꽉 찬 정확도로 겨우 본전**) |
| 50 | 101.7% (**어떤 라우터로도 불가능**) |
| 5.3 | 50.0% ← 답의 상황이 본전인 유일한 환율 |

읽는 법: 정확도 50%가 손해가 **아닌** 경우는 「품질 1%p를 절감 5.3%에 팔아도 괜찮다」고 말할 수 있는 도메인뿐입니다. 반대로 환율을 42 이상으로 잡는 도메인(품질에 민감한 곳)은 **라우터를 아예 넣을 수 없습니다.** 정확도 100%로도 본전이 안 되니까요.

---

## 6. 그래서 무엇을 먼저 만들어야 하는가

품질 %p를 건수로 바꿔 보면 감각이 잡힙니다. 1,000건 기준으로,

- 정확도 100%의 1.4%p → **오답 약 14건**
- 정확도 50%의 7.9%p → **오답 약 79건**

사람 눈에 안 보이는 서비스라면 14건은 남는 장사입니다. 그 14건이 결제 오류나 의료 판독이면 남는 장사가 아니에요. **같은 숫자가 도메인에 따라 반대 결론을 냅니다.**

그리고 이 계산 전체는 **라우터 정확도라는 하나의 입력**에 달려 있습니다. 정확도를 모르면 손실도 절감도 환율도 못 구하고, 남는 건 「라우터 넣었더니 좋아진 것 같다」는 느낌뿐입니다. 위 표에서 확인했듯이 **절감은 정확도가 0%여도 24%가 나오므로**, 「토큰이 줄었다」는 관측은 라우터가 잘 작동한다는 증거가 전혀 못 됩니다.

> **라우터를 넣을 때 제일 먼저 만들 것은 라우터가 아니라 「라우팅이 맞았는지 채점하는 데이터셋」입니다. 100건이면 시작할 수 있습니다.**

---

## 한 줄 정리

정확도 50%는 품질 7.86%p(≈8%p)를 내주고 41.9%(≈42%)를 아끼는 교환인데, 100%(1.44%p / 60%) 대비 손실은 5.5배로 불고 절감은 0.69배로만 줄어 교환 환율이 41.9에서 5.3으로 8배 나빠진다 — 절감에는 정확도와 무관한 하한 24%가 깔려 있고 손실에는 없기 때문이며, 품질 손실 2%p를 지키려면 정확도 96%가 필요하고 손실 0은 111% 정확도를 요구해 아예 불가능하다.
