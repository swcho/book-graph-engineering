# 상태 크기 구간별로 대처가 어떻게 다른가?

## 한 줄 답

- **32KB 미만** — 상태를 줄여도 소용없다. **슈퍼스텝 수**를 줄여야 한다.
- **32KB 이상** — **상태를 줄이는 것**이 바로 듣는다 (19장).

## 이 구분은 어디서 나왔나

21장 21.4절 「내구성은 공짜가 아니다」의 실측 예제 `ex4_checkpointer_cost.py`에서 나온다.
노드 12개(N_STEPS = 12)짜리 직렬 그래프를 상태 페이로드 크기 0B / 2KB / 32KB / 256KB로 바꿔 가며,
`InMemorySaver`(메모리)와 `SqliteSaver`(디스크 파일)로 각각 끝까지 돌린 시간을 잰다.

관찰된 패턴:

| 상태 크기 | SQLite ÷ 메모리 배수 | 지배 요인 |
|---|---|---|
| 0B ~ 32KB | 2.0 ~ 2.8배로 거의 **평평** | 쓰기 호출 자체 (고정비) |
| 32KB 초과 (예: 256KB) | 최대 **4.8배**까지 꺾여 올라감 | 데이터 양 (대역폭) |

핵심 관찰: *"32KB까지는 배수가 2.0~2.8로 거의 평평하다. 그 뒤에 꺾인다."*

## 왜 두 구간이 생기나 — 비용의 구조

체크포인트 한 번의 비용은 대략 두 부분의 합이다.

```
체크포인트 비용 ≈ (고정비: 트랜잭션 열기·커밋·fsync 등) + (가변비: 상태 크기에 비례하는 직렬화·쓰기)
```

체크포인트는 **슈퍼스텝 경계마다** 찍히므로, 전체 오버헤드는:

```
총 오버헤드 ≈ 슈퍼스텝 수 × (고정비 + 상태크기 × 단위쓰기비용)
```

### 구간 1 — 고정비 지배 (32KB 미만)

- **원인**: 상태가 작으면 「슈퍼스텝마다 트랜잭션을 여는 값」이 상태 크기와 무관하게 붙는 고정비가
  전체를 지배한다. 0B든 32KB든 배수가 2.0~2.8로 거의 같다는 것이 그 증거다.
- **처방**: 상태를 아무리 줄여도 고정비는 그대로 남으므로 효과가 없다.
  체크포인트 **횟수** 자체, 즉 **슈퍼스텝 수를 줄여야** 한다.
  (예: 잘게 쪼갠 노드를 합치기. 이 예제는 12단계지만 30단계짜리면 그만큼 더 든다 — 오버헤드는 단계 수에 비례.)
- 21장 한 장 요약의 「노드를 잘게 쪼개면 재실행 창은 좁아지지만 체크포인트 횟수가 늘어 느려진다」는
  트레이드오프가 바로 이 구간의 얘기다.

### 구간 2 — 대역폭 지배 (32KB 이상)

- **원인**: 상태가 커지면 직렬화하고 디스크에 써 내려가는 **데이터 양에 비례하는 비용**이
  고정비를 넘어선다. 그래서 배수가 4.8배까지 꺾여 올라간다.
- **처방**: 이 구간에서는 **상태 크기를 줄이는 것이 바로 듣는다**.
  상태 다이어트 방법은 19장(상태 그래프와 리듀서)에서 다룬 대로 —
  필요한 것만 상태에 싣고, 큰 덩어리는 참조(키/경로)만 실어 나르는 식.

## 연결되는 교훈 — "재 보기 전에는 어느 구간인지 모른다"

저자의 자기 고백: *"제가 처음에 «상태를 줄이면 항상 빨라진다»고 생각한 게 틀렸다.
재 보기 전에는 어느 구간에 있는지 모른다."*

- 「상태 줄이기」는 만능 처방이 아니다. 고정비 지배 구간에서는 헛수고다.
- 어느 구간에 있는지는 직감이 아니라 **실측**으로만 안다. 그래서 예제 4가 벤치마크 코드인 것.
- 32KB라는 숫자 자체도 이 환경(SQLite, LangGraph 1.0.1, 특정 하드웨어)의 실측값이지 보편 상수가 아니다.
  자기 환경에서 다시 재야 한다.

## 흔한 오답 주의

느리다고 해서 **메모리 체크포인터로 도망가면 안 된다**.
프로세스가 죽으면 다 사라지므로 그건 체크포인터가 아니라 **캐시**다.
지연이 문제면 줄일 곳은 «상태 크기»(또는 슈퍼스텝 수)지 «체크포인터 종류»가 아니다.

## 요약 표

| | 32KB 미만 | 32KB 이상 |
|---|---|---|
| 지배 비용 | 고정비 (슈퍼스텝마다 트랜잭션 열기) | 대역폭 (상태 크기에 비례하는 쓰기) |
| 상태 줄이기 | 소용없다 | 바로 듣는다 |
| 유효한 처방 | 슈퍼스텝(체크포인트) 수 줄이기 | 상태 크기 줄이기 (19장) |
| 배수 (SQLite/메모리) | 2.0 ~ 2.8배, 평평 | 최대 4.8배로 꺾임 |
