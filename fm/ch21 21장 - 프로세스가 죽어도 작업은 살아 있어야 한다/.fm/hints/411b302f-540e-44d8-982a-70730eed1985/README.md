# `EffectLog`는 부수 효과를 어떤 순서로 기록하는가?

**답: 실행 «전»에 `started`로 적고, 끝나면 `done`과 결과를 채운다.**

## 코드로 보는 순서

21장 예제 3(`code/ex3_side_effect_log.py`)의 `EffectLog`는 SQLite 테이블 하나로 부수 효과(외부 결제 API 호출)를 추적한다.

```python
class EffectLog:
    """부수 효과를 기록한다. 실행 «전»에 적고, 끝나면 결과를 채운다."""

    def begin(self, key):
        """이미 시작했거나 끝난 일이면 그 상태를 돌려준다."""
        row = self.db.execute(
            "SELECT status, result FROM effects WHERE key=?", (key,)).fetchone()
        if row:
            return row
        self.db.execute("INSERT INTO effects VALUES (?, 'started', NULL)", (key,))
        self.db.commit()
        return None

    def finish(self, key, result):
        self.db.execute("UPDATE effects SET status='done', result=? WHERE key=?",
                        (result, key))
        self.db.commit()
```

호출 흐름은 항상 이 순서다.

1. **`begin(key)`** — 외부 API를 호출하기 *전에* `status='started'` 행을 먼저 INSERT한다. 이미 행이 있으면(이전에 시작했거나 끝난 일이면) 그 상태를 돌려주고 실행을 막는다.
2. **외부 호출** — 실제 결제 등 부수 효과를 실행한다.
3. **`finish(key, result)`** — 성공하면 `status='done'`으로 바꾸고 `result`(영수증 등)를 채운다.

상태 컬럼의 주석도 이 생애주기를 그대로 보여준다: `status TEXT NOT NULL -- started | done | failed`.

## 왜 "먼저 적고 나중에 실행"인가 — Write-Ahead Intent Log

이 패턴은 데이터베이스의 WAL(Write-Ahead Logging)과 같은 발상이다. **"하겠다는 의도(intent)를 먼저 영속 저장소에 남기고, 그 다음에 실제 행동을 한다."** 이 장의 주제인 "프로세스가 죽어도 작업은 살아 있어야 한다"에서, 어느 시점에 죽더라도 로그를 보면 상황을 판단할 수 있게 만드는 장치다.

핵심은 이 순서가 **실패 모드를 안전한 쪽으로 바꾼다**는 점이다.

### 순서별 실패 모드 비교

| 순서 | 크래시 시점 | 로그 상태 | 실제 상태 | 재시작 시 판단 |
|---|---|---|---|---|
| **기록 먼저 → 호출** (EffectLog 방식) | 기록 후, 호출 전 | `started` | 결제 안 됨 | "시작에서 멈춤 → **사람이 확인**" (안전: 최악이 확인 한 번) |
| **기록 먼저 → 호출** | 호출 후, `finish` 전 | `started` | 결제 됨 | 마찬가지로 "사람이 확인" — 자동 재시도를 막아 **중복 결제를 차단** |
| **호출 먼저 → 기록** (반대 순서) | 호출 후, 기록 전 | **기록 없음** | 결제 됨 | 로그가 비어 있으니 "안 한 일"로 보고 **자동으로 다시 결제 → 중복 결제** |

반대 순서(실행 후 기록)의 치명적인 점: 실패가 **"모른다"가 아니라 "안 했다"로 위장**된다. 시스템은 아무 의심 없이 재시도하고, 고객은 두 번 결제된다. 기록을 먼저 하면 최악의 경우가 "됐는지 안 됐는지 모른다(`started`에 멈춤)"이고, 이때는 자동 재시도를 멈추고 사람을 부른다. 책의 표현대로 **"중복 결제보다 사람 한 번 부르는 게 싸니까."**

### `begin`이 게이트 역할까지 한다

`begin`은 기록만 하는 게 아니라 멱등 게이트다. `attempt` 함수를 보면:

- `done`이면 → 저장된 결과를 돌려주고 건너뜀 (재실행해도 API 호출 0회)
- `started`에 멈춰 있으면 → "이전 시도가 «시작»에서 멈춰 있다 — 사람이 확인해야 함"
- 행이 없으면 → `started`를 적고 실제 호출 진행

`key`가 PRIMARY KEY라서 같은 작업 키로는 한 번만 `started`를 삽입할 수 있다. 즉, 상대 API가 멱등을 지원하지 않을 때(예제의 `DumbAPI`) **우리 쪽에서 멱등성을 만들어주는** 장치다.

## 한계와 완화

이 방법으로도 `started`와 `done` 사이의 불확실 구간(창)을 완전히 없앨 수는 없다. 외부 호출과 우리 기록은 **같은 트랜잭션이 아니기 때문**이다. 책이 제시하는 완화책:

1. 기록을 먼저, 호출을 나중에 — 지금 방식 (중복 대신 "모름"으로 실패)
2. 호출 직후 즉시 기록 — 그 사이가 창
3. 상대에게 **조회 API**가 있으면 재시작 때 물어본다 — 제일 확실하고, 이 경우 사람을 부를 필요도 없어진다

## 기억법

- **"영수증을 끊기 전에 주문서부터 쓴다"** — `started`(주문서) → 실행 → `done`+결과(영수증).
- 순서를 뒤집으면: 로그 없음 = "안 한 일" 취급 = 재시도 = **중복 결제**.
- 순서를 지키면: 최악이 `started` 고아 행 = "모름" = **사람 확인 한 번**.
