# 멱등 키는 무엇에서 나와야 하는가?

## 한 줄 답

**요청이 아니라 작업에서 나와야 한다.** 그리고 상대 API가 그 키를 실제로 지원하는지 **문서로 확인**해야 한다.

## 왜 이 질문이 나오는가 — 체크포인트와 죽은 지점 사이의 창

21장의 전제는 이렇다. 체크포인트는 슈퍼스텝 **경계**에만 찍힌다. 마지막 체크포인트와 프로세스가 죽은 시점 사이에 *이미 벌어진 일*(결제, 알림 발송 같은 부수 효과)이 있고, 재개하면 그 구간을 **다시 실행**한다. 이 창을 0으로 만들 수는 없으므로, 전략을 바꾼다.

> 창을 없애는 대신 **다시 해도 되게** 만든다. 그게 멱등성이다.

멱등성(idempotency)은 같은 연산을 여러 번 수행해도 결과가 한 번 수행한 것과 같다는 성질이다(RFC 9110 §9.2.2). 외부 API 호출에 멱등성을 부여하는 관례적 수단이 **멱등 키(idempotency key)** — 「이 호출은 아까 그 호출과 같은 것」임을 상대에게 알려 주는 식별자다.

## 핵심 1 — 「요청에서 나온 키」 vs 「작업에서 나온 키」

| 구분 | 요청 단위 키 | 작업 단위 키 |
|---|---|---|
| 예 | 호출 직전에 `uuid4()` 생성 | `order-8842` 처럼 작업 식별자에서 파생 |
| 프로세스가 죽고 재개하면 | **새 요청 → 새 키** 가 생성됨 | 같은 작업 → **같은 키** 가 재현됨 |
| 결과 | 상대는 다른 호출로 보고 **중복 결제** | 상대가 캐시된 결과를 돌려줌 (안전) |

함정은 여기다. 재시도 코드가 「요청을 보낼 때마다」 랜덤 키를 새로 만들면, 형식상 멱등 키를 쓰고 있는데도 재개할 때마다 키가 달라진다. 멱등 키의 존재 이유가 「재시도가 같은 호출임을 알리는 것」인데, 키가 재시도마다 바뀌면 아무것도 알리지 못한다. **키는 랜덤 값이 아니라 작업의 정체성에서 결정론적으로 나와야 한다** — 주문 ID, 스레드 ID + 노드 이름 + 시도 대상 등, 죽었다 살아나도 다시 계산하면 같은 값이 나오는 것.

책의 예제 2(`ex2_idempotency.py`)가 정확히 이 대비를 보여 준다. 키를 안 보내는 경우와 상대가 지원 안 하는 경우는 3번 재시도에 15만 원이 결제되고, `"order-8842"` 라는 **작업 단위 키**를 보내는 경우만 5만 원 1건으로 끝난다.

주의: 랜덤 UUID 자체가 나쁜 게 아니다. Stripe 문서도 V4 UUID를 권장한다. 요점은 **생성 시점과 저장 위치**다 — 작업이 시작될 때 한 번 만들어 작업 상태(체크포인트)에 저장해 두고 재시도 때 꺼내 쓰면 그것도 「작업에서 나온 키」다. 반면 매 HTTP 요청마다 새로 만들면 「요청에서 나온 키」가 되어 무의미해진다.

## 핵심 2 — 상대가 그 키를 「보는지」 문서로 확인하라

멱등 키는 **받는 쪽이 지원해야** 소용이 있다. 우리가 헤더에 키를 실어 보내도, 상대 서버가 그 헤더를 무시하면 매번 새 결제가 일어난다. 예제 2의 세 번째 케이스가 이것이다 — 키를 「보냈는데도」 중복이 났다.

그래서 확인할 게 둘이다.

1. **우리가 키를 보내는가** (우리 코드)
2. **상대가 그 키를 보는가** (상대 문서 + 실제로 두 번 보내서 검증)

2번을 확인 안 하고 1번만 해 두면, 코드는 안전해 *보이는데* 실제로는 안 안전하다. 문서를 읽고, 가능하면 실제로 같은 키로 두 번 보내서 두 번째가 캐시 응답인지 확인해야 한다.

### 실제 API 사례

- **Stripe**: `Idempotency-Key` HTTP 헤더를 공식 지원. 같은 키로 재요청하면 첫 요청의 저장된 응답을 그대로 재생(replay)하고, 키는 일정 기간(24시간) 후 만료된다. 멱등 키 관행을 업계에 퍼뜨린 대표 사례.
- **IETF 표준화 시도**: `draft-ietf-httpapi-idempotency-key-header` — `Idempotency-Key` 헤더를 표준으로 만들려는 초안. 아직 [사실상 표준] 단계라는 게 요점이다. **표준 헤더가 아니므로 API마다 지원 여부·헤더 이름·만료 정책이 다르고, 그래서 문서 확인이 필수다.**
- RFC 9110은 GET/PUT/DELETE를 멱등 메서드로 정의하지만, 결제 같은 POST는 본질적으로 멱등이 아니라서 키가 필요해진다.

## 지원 안 하면? (다음 카드로 이어지는 맥락)

상대가 멱등 키를 지원하지 않으면 우리 쪽에 **부작용 로그**(예제 3)를 남긴다 — 호출 「전」에 `started`를 적고 끝나면 `done`을 채우는 방식. 그래도 「호출은 됐는데 기록 전에 죽는」 창은 남으며, 그 구간은 「모름」으로 분류해 사람이 마감한다. 상대에게 조회 API가 있으면 재시작 때 물어보는 게 제일 확실하다.

## 기억 포인트

- 멱등 키 = 작업의 정체성에서 결정론적으로 파생 (재개해도 같은 키).
- 요청마다 새로 만든 키는 멱등 키가 아니라 그냥 랜덤 값이다.
- 보내는 것만으로 끝이 아니다 — 받는 쪽 지원을 **문서로, 그리고 실제 이중 전송으로** 확인하라.
