# 부작용 로그 방식의 한계는 무엇인가?

## 한 줄 답

**'시작'은 적었는데 '완료'를 못 적고 죽으면, 결제가 됐는지 안 됐는지 알 수 없다.**
근본 원인은 외부 호출과 우리 기록이 **같은 트랜잭션이 아니라서**다. 이 「모름」 구간은 없앨 수 없고, 좁혀서 사람에게 넘길 수만 있다.

## 배경: 부작용 로그가 왜 등장했나

21장의 흐름을 되짚어 보면:

1. 체크포인트는 슈퍼스텝 **경계**에만 찍힌다. 경계와 죽은 시점 사이의 일은 재개할 때 **다시 한다**.
2. 「다시 해도 되게」 만드는 게 멱등성이고, 가장 좋은 방법은 **멱등 키**를 붙이는 것이다.
3. 그런데 상대 API가 멱등 키를 **지원하지 않으면**? 우리가 직접 「했다는 사실」을 기록하는 수밖에 없다. 그게 **부작용 로그**(side-effect log)다.

## 부작용 로그의 동작 방식 (ex3_side_effect_log.py)

핵심 프로토콜은 「**기록을 먼저, 호출을 나중에**」다:

```
1. begin(key)  → effects 테이블에 (key, 'started', NULL) INSERT
2. api.charge() → 외부 결제 API 호출
3. finish(key) → status를 'done'으로 UPDATE, 결과 저장
```

재시작하면 `begin(key)`이 기존 행을 발견한다:

- `done` → 저장된 결과를 돌려주고 **건너뛴다** (중복 결제 방지 성공)
- `started` → **여기가 문제다**

## 한계: 'started'에서 멈춘 행은 해석이 불가능하다

2번(호출)과 3번(기록) 사이에서 프로세스가 죽으면, 로그에는 `started`만 남는다.
이 상태는 두 가지 현실 중 어느 쪽인지 **구분할 수 없다**:

| 실제로 벌어진 일 | 로그에 남은 것 |
|---|---|
| 호출 **직전**에 죽음 → 결제 안 됨 | `started` |
| 호출 **직후**, 기록 전에 죽음 → 결제 됨 | `started` |

- 자동으로 **재시도하면** → 이미 결제된 경우 중복 결제
- 자동으로 **건너뛰면** → 결제 안 된 경우 주문 누락

어느 쪽도 안전하지 않으므로, 책의 처방은 「**사람이 확인** 상태로 두고 멈춘다」이다. 중복 결제보다 사람 한 번 부르는 게 싸기 때문이다.

## 근본 원인: 같은 트랜잭션이 아니다 (dual write 문제)

우리 SQLite/DB에 대한 쓰기는 로컬 트랜잭션으로 원자적으로 만들 수 있다. 하지만 **외부 API 호출(HTTP)은 우리 DB 트랜잭션 안에 넣을 수 없다**. 결제사의 서버는 우리 트랜잭션의 커밋/롤백에 참여하지 않는다.

즉 「DB에 기록」과 「외부 호출」이라는 **두 개의 독립적인 쓰기**(dual write)가 있고, 둘 사이의 어느 지점에서든 죽을 수 있다. 분산 시스템 용어로:

- **Dual write 문제**: 두 시스템에 각각 쓰는 작업은 원자적으로 묶이지 않아 항상 불일치 창이 생긴다.
- **두 장군 문제(Two Generals Problem)**: 신뢰할 수 없는 채널 위에서 「상대가 내 메시지를 받았는지」를 유한한 메시지 교환으로 **확실히** 알 수 있는 방법은 이론적으로 존재하지 않는다. 응답을 못 받고 죽은 호출자는 요청이 도달했는지 영원히 알 수 없다 — 이것이 「모름」 창의 이론적 뿌리다.
- 그래서 정확히-한-번(exactly-once)은 전송 계층만으로는 불가능하고, 멱등성(수신 측 중복 제거)이나 조회를 통한 조정(reconciliation)으로 **흉내** 내는 것이다.

## 창을 없앨 수는 없고, 좁힐 수는 있다

책이 제시하는 순서:

1. **기록을 먼저, 호출을 나중에** (기본 방식) — 최악의 경우가 「모름」이지 「기록 없는 결제」는 아니게 된다.
2. **호출 직후 즉시 기록** — 호출과 기록 사이의 창을 최대한 좁힌다. 그래도 0은 아니다.
3. **상대에게 조회(query) API가 있으면 재시작 때 물어본다** — 이게 제일 확실하다. `started` 행을 발견하면 결제사에 「이 주문 결제됐나요?」라고 물어서 스스로 마감할 수 있으므로 **사람을 안 불러도 된다**.

## 기억할 요점

- 부작용 로그는 멱등 키의 차선책이며, `done`까지 간 작업의 중복은 막아 준다.
- 하지만 `started`와 `done` 사이에서 죽으면 「결제가 됐는지 모름」이 남는다 — 이게 한계.
- 원인은 외부 호출을 로컬 트랜잭션에 넣을 수 없다는 구조적 사실(dual write / 두 장군 문제).
- 처방: 창을 **없애려 하지 말고**, 좁히고(호출 직후 기록), 조회 API로 조정하고, 그래도 남으면 「사람 확인」으로 넘긴다.

## 관련 개념

- 멱등 키 (idempotency key): IETF draft-ietf-httpapi-idempotency-key-header
- 정확히 한 번 (exactly-once): Kafka semantics 문서 — 사실상 「최소 한 번 + 멱등 처리」의 조합
- 쓰기 전 로그 (write-ahead log): 부작용 로그의 「기록 먼저」 패턴과 같은 계열의 발상
- 다음 장(22장)의 보상 트랜잭션: 다시 할 수 없는 일은 되갚는다
