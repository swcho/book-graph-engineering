# 노드를 잘게 쪼개면 재실행 창이 사라지는가?

**답: 좁아지지만 0이 되지 않는다. 게다가 체크포인트 횟수가 늘어 느려진다.**

## 재실행 창이란

체크포인트는 **슈퍼스텝 경계에만** 찍힌다. 즉 노드가 끝나는 시점마다 상태가 저장되고, 노드 *실행 도중*에는 저장되지 않는다. 프로세스가 죽으면 마지막 체크포인트 이후에 벌어진 일 — 지금 실행 중이던 노드가 이미 해 버린 일 — 은 기록에 없고, 재개하면 그 노드를 **처음부터 다시** 실행한다. 이 「체크포인트 지점 ~ 죽은 지점」 사이 구간이 **재실행 창**이다.

## 쪼개면 왜 0이 안 되는가

직관적으로는 노드를 잘게 쪼갤수록 창이 좁아진다. 노드 하나가 하는 일이 적어지니 다시 해야 할 분량도 줄어든다. 하지만:

1. **아무리 쪼개도 노드는 여전히 「실행 중」인 순간이 있다.** 외부 API 호출 하나짜리 노드라 해도, 호출이 나간 뒤 체크포인트가 찍히기 전에 죽을 수 있다. 외부 호출과 우리 쪽 기록은 **같은 트랜잭션이 아니기 때문에** 이 틈은 구조적으로 제거할 수 없다.
2. **창은 좁아질 뿐 닫히지 않는다.** 극단적으로 「호출 직후 즉시 기록」해도 그 사이가 여전히 창이다.

## 쪼개기의 숨은 비용: 체크포인트 횟수

노드 수 = 슈퍼스텝 수 = 체크포인트 쓰기 횟수. 쪼갤수록 저장이 잦아진다. 책의 실측(ex4_checkpointer_cost.py, LangGraph 1.0.1, 12노드 그래프):

| 상태 크기 | SQLite / 메모리 배수 |
|---|---|
| 32KB 미만 | **2.0~2.8배** (거의 평평) |
| 32KB 이상 | **최대 4.8배**까지 꺾임 |

- 32KB 미만 구간에서는 **쓰기 호출 자체(트랜잭션 열기 비용)가 지배**한다. 상태 크기와 무관하게 슈퍼스텝마다 고정 비용이 붙으므로, 이 구간에서는 상태를 줄여도 소용없고 **슈퍼스텝 수를 줄여야** 한다. 노드를 잘게 쪼개는 것은 정확히 그 반대 방향이다.
- 32KB 이상이면 상태 크기를 줄이는 게 바로 듣는다(19장).

즉 쪼개기는 「창을 조금 좁히는 대가로 체크포인트 고정 비용을 노드 수만큼 더 내는」 거래이고, 창은 어차피 0이 안 된다.

## 올바른 해법: 창을 없애지 말고 「다시 해도 되게」

책의 결론은 창 제거가 아니라 **멱등성**이다:

1. **멱등 키**를 붙여 재실행돼도 같은 결과가 되게 한다. 키는 요청이 아니라 *작업*에서 나와야 하고, 상대 API가 실제로 지원하는지 문서 + 실제 이중 전송으로 확인해야 한다.
2. 상대가 지원하지 않으면 **부작용 로그**(했다는 기록을 먼저 남기기)를 쓴다. 그래도 남는 창은 「모름」 상태로 분류해 **사람이 마감**한다.
3. 상대에게 조회 API가 있으면 재시작 때 물어보는 게 제일 확실하다.

> 요점: 없애려 하지 말고 **좁히고 넘겨라**. 재실행 창은 구조적 한계이므로, 노드 분할로 싸우면 지연만 얻고, 멱등성으로 대응하면 창이 있어도 안전하다.
