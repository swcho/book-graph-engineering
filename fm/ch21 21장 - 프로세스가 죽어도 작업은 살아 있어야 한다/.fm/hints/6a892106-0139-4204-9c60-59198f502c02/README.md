# `EffectLog.begin()`은 세 가지 상황을 어떻게 구분하는가?

## 한 줄 답

- **기록이 없으면** → `started` 행을 새로 넣고 `None`을 반환한다 (처음 하는 작업이니 실행해도 된다).
- **`done`이면** → 저장된 결과(`result`)를 그대로 돌려준다 (다시 실행하지 않고 건너뛴다).
- **`started`로 남아 있으면** → 이전 시도가 「시작」에서 멈췄다는 신호다. 부수 효과가 실제로 일어났는지 *모르는* 상태이므로 자동 재시도하지 않고 사람이 확인하게 한다.

## 배경: 왜 이런 로그가 필요한가 (21.3절)

체크포인트는 슈퍼스텝 **경계**에만 찍힌다. 경계와 프로세스가 죽은 시점 사이에 이미 벌어진 부수 효과(결제, 메일 발송 등)는 재개할 때 **다시 실행**된다. 상대 API가 멱등 키를 지원하면 중복이 걸러지지만, 지원하지 않는 「DumbAPI」라면 우리가 스스로 기록을 남겨야 한다. 그게 **부수 효과 로그(side-effect log)** 이고, 핵심 규칙은:

> 실행 **전**에 「했다는 사실」을 먼저 적고(`started`), 끝나면 결과를 채운다(`done`).

쓰기 전 로그(write-ahead log)와 같은 발상이다. "하고 나서 적기"가 아니라 "적고 나서 하기"여야, 죽은 뒤에 로그를 보고 상황을 판별할 수 있다.

## 원문 코드의 실제 동작

```python
def begin(self, key):
    """이미 시작했거나 끝난 일이면 그 상태를 돌려준다."""
    row = self.db.execute(
        "SELECT status, result FROM effects WHERE key=?", (key,)).fetchone()
    if row:
        return row                      # (status, result) — done/started 판별은 호출자 몫
    self.db.execute("INSERT INTO effects VALUES (?, 'started', NULL)", (key,))
    self.db.commit()
    return None                         # 기록 없음 → started 기록 후 "실행하라"는 뜻
```

호출자(`attempt`)가 반환값으로 세 갈래를 나눈다:

| `begin()` 반환값 | 의미 | 호출자의 행동 |
|---|---|---|
| `None` | 처음 보는 키. 방금 `started`를 기록했다 | 실제 API 호출 실행 → 성공하면 `finish(key, result)`로 `done` 기록 |
| `('done', result)` | 이전에 끝까지 완료됨 | 저장된 `result` 반환, API 호출 **건너뜀** (멱등 재실행) |
| `('started', None)` | `started`만 적고 죽었음 | **"모름"** — 결제가 됐는지 안 됐는지 알 수 없다. 자동 재시도 대신 사람이 확인 |

## 세 번째 분기가 핵심인 이유

`started`만 남은 상태는 이 방법의 **한계이자 설계 의도**다. 외부 API 호출과 우리 DB 기록은 같은 트랜잭션이 아니므로, "호출은 됐는데 `done`을 못 적고 죽는" 창(window)은 **없앨 수 없다**. 그래서 이 구간은:

1. 자동 재시도하면 → 중복 결제 위험 (이미 결제됐을 수 있으니)
2. 무조건 건너뛰면 → 미결제 위험 (결제 전에 죽었을 수 있으니)

둘 다 틀릴 수 있으므로 「모름」으로 분류해 **사람에게 넘긴다**. 중복 결제보다 사람 한 번 부르는 게 싸기 때문이다. 창을 줄이는 방법은 있다 — 기록 먼저/호출 나중(현재 방식), 호출 직후 즉시 기록, 그리고 상대에게 **조회 API**가 있으면 재시작 때 물어보는 것(이러면 사람을 안 불러도 된다).

## 기억 포인트

- `begin()`은 "실행해도 되는가?"를 답하는 **게이트**다: `None`=해라, `done`=이미 했다, `started`=모른다.
- `started`를 **실행 전에** 적는 것이 전부다. 순서를 바꾸면 세 번째 분기(모름)를 아예 감지할 수 없다.
- 「모름」 상태는 버그가 아니라 분산 시스템의 본질적 한계를 **명시적으로 드러낸 것**이다.
