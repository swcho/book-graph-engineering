# 재실행 창을 없애는 대신 무엇을 하는가?

**답: 다시 해도 되게 만든다. 그것이 멱등성(idempotency)이다.**

## 재실행 창이란 무엇인가

체크포인트는 슈퍼스텝 **경계**에만 찍힌다. 그래서 마지막 체크포인트와 프로세스가 죽은 시점 사이에는 "이미 벌어졌지만 기록되지 않은 일"이 존재한다. 재개하면 그 구간을 **다시 실행**하게 되는데, 이 구간이 바로 재실행 창(re-execution window)이다.

이 창을 좁히려는 시도는 한계가 있다.

- 노드를 잘게 쪼개면 창이 좁아지지만 **0이 되지는 않는다.**
- 대신 체크포인트 횟수가 늘어 느려진다. 책의 실측(ex4)으로 SQLite 체크포인터는 메모리 대비 2.0~2.8배, 상태가 32KB를 넘으면 4.8배까지 느려진다.
- 근본적으로 외부 API 호출과 우리 쪽 체크포인트 기록은 **같은 트랜잭션이 아니므로**, 그 사이의 창을 구조적으로 없앨 수 없다.

## 그래서 발상을 뒤집는다

창을 없애려고 싸우는 대신, **창 안의 작업을 다시 실행해도 결과가 같도록** 만든다. 그러면 재실행이 더 이상 사고가 아니라 정상 동작이 된다. 이 성질이 멱등성이다.

## 멱등성의 표준 정의 (RFC 9110 §9.2.2)

HTTP 명세 RFC 9110은 멱등성을 이렇게 정의한다.

> 어떤 메서드로 **동일한 요청을 여러 번** 보냈을 때 서버에 미치는 의도된 효과가, **한 번** 보냈을 때의 효과와 같으면 그 메서드는 멱등(idempotent)하다.

- HTTP에서 GET, HEAD, OPTIONS, TRACE, PUT, DELETE는 멱등이고, POST와 PATCH는 일반적으로 멱등이 아니다.
- 핵심은 "요청이 몇 번 도착하든 최종 효과는 1회분"이라는 것. 재시도(재실행)를 안전하게 만드는 근거가 바로 이 성질이다.

## 실무에서의 구현: 멱등 키

멱등이 아닌 연산(결제, 재고 차감, 알림 발송 등)은 **멱등 키(idempotency key)** 로 멱등하게 만든다. 서버가 같은 키의 요청을 다시 받으면 새로 실행하지 않고 이전 결과를 돌려준다.

책이 강조하는 두 가지 조건:

1. **멱등 키는 요청이 아니라 "작업"에서 나와야 한다.** 재시도마다 새 UUID를 만들면 서버 눈에는 매번 다른 요청이라 중복 실행된다. `order-8842`처럼 작업 자체를 식별하는 값이어야, 죽었다 재개해도 같은 키가 다시 나간다.
2. **상대 API가 실제로 그 키를 지원하는지 문서로 확인하고, 실제로 두 번 보내서 검증해야 한다.** ex2가 보여 주듯, 우리가 키를 보내도 받는 쪽이 무시하면 중복 결제가 난다. "우리가 키를 보내는가"와 "상대가 그 키를 보는가"는 별개의 확인 항목이다.

## 상대가 멱등을 지원하지 않으면

- 우리 쪽에 **부작용 로그**(side-effect log)를 쓴다: 실행 전에 "시작"을 적고, 끝나면 "완료"를 채운다 (ex3).
- 그래도 "호출은 됐는데 완료 기록 전에 죽는" 창은 남는다. 그 상태는 자동 재시도하지 않고 **"모름"으로 분류해 사람이 마감**한다. 중복 결제보다 사람 한 번 부르는 게 싸다.
- 상대에게 조회 API가 있으면 재시작 때 물어보는 것이 가장 확실하다.

## 한 줄 정리

재실행 창은 없앨 수 없다(외부 호출과 체크포인트는 같은 트랜잭션이 아니다). 그러니 없애려 하지 말고, **창 안의 작업을 "다시 해도 되게"(멱등하게)** 만들어라. 남는 창은 좁히고, 그래도 남으면 사람에게 넘겨라.
