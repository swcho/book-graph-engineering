# 32KB 미만 구간에서 지연을 지배하는 요인

## 질문
32KB 미만 구간에서 지연을 지배하는 요인은 무엇인가?

## 답
**쓰기 호출 자체다.** 슈퍼스텝마다 트랜잭션을 여는 비용이 상태 크기와 무관하게 붙는다.

---

## 왜 그런가 — 고정비 vs 크기 비례 비용

체크포인트 한 번의 지연은 크게 두 부분으로 쪼갤 수 있다.

| 구분 | 성격 | 크기와의 관계 |
|---|---|---|
| **고정비 (fixed cost)** | 트랜잭션 열기/닫기, 저널·WAL 처리, 커밋 시 디스크 동기화(fsync), SQL 파싱과 호출 오버헤드 | 상태가 0B든 32KB든 **거의 같다** |
| **크기 비례 비용 (variable cost)** | 상태 직렬화, 페이로드를 페이지에 쓰는 I/O | 상태 크기에 **비례해서 늘어난다** |

상태가 작을 때는 크기 비례 비용이 사실상 0에 가깝기 때문에, 전체 지연은 고정비 — 즉 「쓰기 호출을 한 번 했다는 사실」 — 가 지배한다. SQLite는 명시적 트랜잭션이 없으면 **문장마다 트랜잭션을 자동으로 감싸고**, 커밋할 때마다 내구성을 위해 디스크 동기화를 수행한다. 이 커밋 고정비는 몇 바이트를 쓰든 몇십 KB를 쓰든 큰 차이가 없다. (SQLite 공식 FAQ도 「트랜잭션 처리량은 디스크 회전/동기화 속도에 묶인다」고 설명한다.)

LangGraph 체크포인터는 **슈퍼스텝(노드) 경계마다** 상태 스냅숏을 저장하므로, 12단계 그래프면 이 고정비가 12번 붙는다. 상태를 아무리 줄여도 이 횟수는 그대로다.

## 실측 근거 — ex4 벤치마크

`ex4_checkpointer_cost.py`(LangGraph 1.0.1, 노드 12개 그래프)는 상태 크기를 0B / 2KB / 32KB / 256KB로 바꿔 가며 메모리 체크포인터(InMemorySaver) 대비 SQLite 파일 체크포인터(SqliteSaver)의 배수를 잰다.

- **32KB까지**: 배수가 **2.0~2.8배로 거의 평평**하다. 상태가 0B에서 32KB로 16,000배 커져도 배수가 거의 안 변한다 → 지연의 대부분이 크기와 무관한 고정비라는 뜻.
- **32KB를 넘으면**: 꺾여서 **4.8배까지** 올라간다 → 이제 페이로드 I/O(크기 비례 비용)가 고정비를 추월했다는 뜻.

## 구간별 대처가 달라진다

| 구간 | 지배 요인 | 효과 있는 대처 |
|---|---|---|
| **32KB 미만** | 쓰기 호출 고정비 | 상태를 줄여도 소용없다. **슈퍼스텝 수(체크포인트 횟수)를 줄여야** 한다 |
| **32KB 이상** | 크기 비례 I/O | **상태 크기를 줄이는 게** 바로 듣는다 (19장) |

저자도 「상태를 줄이면 항상 빨라진다」는 처음 생각이 틀렸다고 고백한다. **재 보기 전에는 어느 구간에 있는지 모른다.**

## 흔한 오답 주의

- ❌ 「직렬화 비용이 지배한다」 — 그건 32KB 이상 구간의 이야기.
- ❌ 「그러니 메모리 체크포인터를 쓰자」 — 메모리 체크포인터는 프로세스가 죽으면 다 사라지는 **캐시**지 체크포인터가 아니다. 지연이 문제면 줄일 곳은 상태 크기(또는 슈퍼스텝 수)지 체크포인터 종류가 아니다.
