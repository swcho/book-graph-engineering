# 위험한 단계를 처리하는 세 단계 시도 순서

## 질문
위험한 단계를 처리하는 세 단계 시도 순서는 무엇인가?

## 답
**멱등 키를 붙일 수 있는지 상대 문서를 확인하고, 없으면 '했다는 기록'을 남기고, 그것도 안 되면 '사람 확인' 상태로 두고 멈춘다.**

---

## 배경: '위험한 단계'란 무엇인가

21장의 복구 훈련(예제 5)은 파이프라인의 각 단계를 두 가지 축으로 분류한다.

| 축 | 질문 |
|---|---|
| `external_call` | 밖(외부 시스템)에 영향을 주는가 |
| `idempotent` | 다시 해도 같은 결과인가 |

체크포인트는 슈퍼스텝 **경계**에만 찍히므로, 노드 실행 도중에 죽으면 재개할 때 그 노드를 **처음부터 다시** 실행한다. 이때,

- 외부 영향이 없는 단계(입력 검증) → 다시 해도 무해. **안전**
- 외부 호출이지만 멱등인 단계(재고 확인 = 조회, 멱등 키 있는 주문 생성) → 다시 해도 같음. **안전**
- 외부 호출이면서 멱등이 아닌 단계(재고 차감, 결제, 알림 발송) → **재개 시 중복 실행**. 이것이 '위험한 단계'다.

책의 예시 파이프라인 6단계 중 3개가 위험으로 분류된다. 이 표를 만드는 데 20분이면 되고, "이게 복구 설계의 전부"라고 책은 말한다.

## 세 단계 캐스케이드

```
1. 멱등 키를 붙일 수 있나 — 상대 API 문서를 본다
      ↓ 안 되면
2. '했다는 기록'(부작용 로그)을 남긴다
      ↓ 그것도 안 되면
3. '사람 확인' 상태로 두고 멈춘다
```

### 1단계 — 멱등 키 (가장 확실함)

- 작업 단위(예: `order-8842`)에서 파생한 키를 요청에 실어 보내면, 상대가 같은 키의 재요청을 **캐시된 결과**로 응답한다. 몇 번을 재시도해도 결제는 1건.
- 핵심 주의점 둘: **키는 요청이 아니라 *작업*에서 나와야 하고**(재시도마다 새 키를 만들면 무의미), **상대 API가 실제로 지원하는지 문서로 — 그리고 실제로 두 번 보내서 — 확인해야 한다.** 예제 2의 세 번째 케이스가 보여주듯, 우리가 키를 보내도 받는 쪽이 무시하면 중복이 난다. "코드는 안전해 보이는데 실제로는 안 안전한" 상태가 제일 위험하다.
- 참고 표준: HTTP 멱등성(RFC 9110 §9.2.2), Idempotency-Key 헤더(IETF httpapi draft). Stripe 등 결제 API들이 이 방식을 채택한 사실상 표준.

### 2단계 — 부작용 로그 (했다는 기록)

상대가 멱등을 지원하지 않으면 **우리 쪽에서** 기록을 남긴다(예제 3의 `EffectLog`).

- 실행 **전에** `started`를 적고, 끝나면 `done` + 결과를 채운다 (쓰기 전 로그, WAL 패턴).
- 재개 시 `done`이면 건너뛰고, 기록이 없으면 새로 실행한다.
- **한계(잔여 위험)**: 외부 호출과 우리 기록은 *같은 트랜잭션이 아니다*. "결제는 됐는데 `done`을 적기 전에 죽으면" 우리는 결제 여부를 **모른다**. 이 창은 좁힐 수는 있어도(호출 직후 즉시 기록, 상대에게 조회 API가 있으면 재시작 때 물어보기) 0으로 만들 수는 없다.

### 3단계 — 사람 확인 (최후의 안전망)

- 2단계의 잔여 구간, 즉 `started`에서 멈춘 채 발견된 작업은 **자동 재시도하지 않는다**. '모름'으로 분류해 사람이 확인할 때까지 멈춘다.
- 근거는 단순한 비용 비교: **"중복 결제보다 사람 한 번 부르는 게 싸니까."**
- 단, 상대에게 **조회 API**가 있으면 재시작 때 기계가 직접 물어볼 수 있어 사람을 안 불러도 된다 — 그래서 조회 API 유무를 먼저 확인하라고 책은 권한다.

## 왜 이 순서인가 — 확실성 내림차순 캐스케이드

세 단계는 **자동화 정도와 확실성이 높은 것부터** 시도하는 우선순위 캐스케이드다.

| 단계 | 중복 방지 주체 | 자동 복구 | 잔여 위험 |
|---|---|---|---|
| 1. 멱등 키 | 상대 시스템 (원자적 판단) | 완전 자동 | 상대가 키를 실제로 보는지 확인 필요. 확인만 되면 창이 사실상 닫힘 |
| 2. 부작용 로그 | 우리 시스템 (비원자적) | 대부분 자동 | 호출↔기록 사이의 창. `started`에서 멈춘 건은 진위 불명 |
| 3. 사람 확인 | 사람 | 수동 | 처리 지연, 운영 비용. 그러나 *중복 실행*은 확실히 막음 |

- 1단계가 가장 확실한 이유: 중복 판정이 부작용이 일어나는 **바로 그 시스템 안에서** 원자적으로 이루어진다. 분산된 두 기록을 맞출 필요가 없다.
- 2단계는 판정 주체가 부작용 발생지와 **분리**되어 있어 그 사이에 필연적으로 창이 생긴다. 그래도 창을 "노드 전체"에서 "호출↔기록 사이"로 크게 좁힌다.
- 3단계는 확실성은 최고(사람이 눈으로 확인)지만 자동화가 0이므로, 앞의 두 단계가 처리하지 못한 **잔여분에만** 쓴다. 처음부터 3단계로 가면 운영이 마비되고, 3단계 없이 1·2단계만 있으면 잔여 창에서 중복 사고가 난다.

## "없애려 하지 말고 좁히고 넘긴다" 원칙과의 연결

이 장의 한 장 요약이 바로 이 문장으로 끝난다: **"남은 건 '모름'으로 분류해서 사람이 마감합니다. 없애려 하지 말고 좁히고 넘기세요."**

- 체크포인트 경계와 죽은 시점 사이의 창은 **구조적으로 0이 될 수 없다**. 노드를 잘게 쪼개면 좁아지지만 체크포인트 비용(SQLite는 메모리의 2.0~2.8배, 32KB 초과 시 4.8배)이 커진다. 외부 호출과 내부 기록도 같은 트랜잭션이 될 수 없다.
- 세 단계 캐스케이드는 이 불가능성을 인정하는 설계다:
  - **좁힌다** — 1단계(멱등 키)로 창을 거의 닫고, 안 되면 2단계(부작용 로그)로 창을 호출↔기록 사이로 줄인다.
  - **넘긴다** — 그래도 남는 '모름' 구간은 자동화로 우기지 않고 사람에게 명시적으로 이관한다.
- '정확히 한 번(exactly-once)'을 완벽히 보장하려는 시도 대신, "대부분은 자동으로, 애매한 것은 확실하게 멈춰서 사람에게"라는 실용적 타협이다. 잘못된 대안은 둘 다 사고로 이어진다: 창을 무시하고 자동 재시도하면 중복 결제, 창이 무섭다고 재시도 자체를 포기하면 미완료 작업이 방치된다.

## 함께 기억할 것

- 이 판단의 전제는 **위험 단계 목록을 미리 갖고 있는 것**이다. 목록이 없으면 사고가 난 뒤에야 그 단계가 위험했음을 안다. 목록은 문서가 아니라 테스트로 두고, CI에서 갱신을 강제하라.
- 그리고 `kill -9`로 실제로 죽여 봐야 복구가 되는지 안다. "죽여 보지 않으면 복구되는지 모른다."
- 다음 장(22장)은 이 캐스케이드로도 안 되는 경우 — 이미 보낸 메일처럼 **다시 할 수 없는** 일 — 를 보상 트랜잭션으로 되갚는 이야기로 이어진다.
