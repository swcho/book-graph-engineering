# 상대가 멱등 키를 지원하지 않으면 어떻게 하는가?

## 한 줄 답

**부작용 로그(side-effect log)를 쓴다.** 그래도 「호출과 기록 사이」의 창은 남으므로, 남은 것은 **「모름」 상태로 분류해 사람이 마감**한다. 창을 없애려 하지 말고 **좁히고 넘긴다**.

## 왜 멱등 키만으로는 안 되는가

멱등 키는 *받는 쪽이 지원해야* 소용이 있다. 우리가 키를 성실하게 보내도, 상대 API가 그 키를 무시하면 재시도 때마다 중복 결제가 난다 (예제 2의 세 번째 케이스: 「API가 멱등을 지원 안 함」 — 키를 보냈는데도 3번 시도에 15만 원이 결제된다).

그래서 확인할 것이 둘이다.

1. **우리가 키를 보내는가** — 코드 문제
2. **상대가 그 키를 보는가** — 상대 문서를 읽고, *실제로 두 번 보내서* 확인

2번을 확인하지 않고 1번만 해 두면 「코드는 안전해 보이는데 실제로는 안 안전한」 상태가 된다. 상대가 지원하지 않는다는 것이 확인되면, 이제 **우리 쪽에서 기록을 남기는 수밖에 없다.**

## 부작용 로그: 「했다는 사실」을 먼저 적는다

예제 3(`ex3_side_effect_log.py`)의 `EffectLog` 패턴이다. 핵심은 **외부 호출 「전」에 시작을 적고, 끝나면 완료를 채우는 것** — 데이터베이스의 write-ahead log(WAL)와 같은 발상이라 *intent log*(의도 로그)라고도 부른다.

```
effects 테이블: key(PK) | status(started/done/failed) | result
```

재시도(=죽었다 재개) 흐름:

- `begin(key)` — 이미 행이 있으면 그 상태를 돌려준다. 없으면 `started`로 INSERT.
  - `done`이면 → **이미 완료, 건너뜀** (저장된 result를 그대로 반환)
  - `started`이면 → **이전 시도가 「시작」에서 멈춰 있음 — 사람이 확인해야 함**
- 행이 없었으면 → 외부 API 호출 → `finish(key, receipt)`로 `done` 기록

이렇게 하면 정상 흐름에서는 세 번 재시도해도 실제 API 호출은 1회다. 상대가 멱등을 지원하지 않아도 **우리 로그가 중복 실행을 막는 관문**이 된다.

## 그래도 창(window)은 남는다

한계가 되는 시나리오: **결제는 됐는데 `finish`를 적기 전에 죽는 경우.**

- 로그에는 `started`만 남아 있다.
- 이때 우리는 결제가 됐는지 안 됐는지 **모른다.**
- 자동 재시도하면? 됐던 경우 중복 결제. 안 하면? 안 됐던 경우 결제 누락.

이 구간을 **아예 없앨 수는 없다.** 외부 호출과 우리 기록은 *같은 트랜잭션이 아니기 때문*이다(분산 시스템에서 exactly-once가 원리적으로 어려운 이유와 같다). 순서를 뒤집어도(호출 먼저, 기록 나중) 창의 위치만 바뀔 뿐 사라지지 않는다.

## 그래서: 좁히고, 넘긴다

책이 제시하는 태도는 「없애기」가 아니라 두 가지다.

### 1) 창을 좁힌다

- **기록을 먼저, 호출을 나중에** (예제 3 방식) — 모르는 쪽이 「중복」이 아니라 「미상」이 되게
- **호출 직후 즉시 기록** — 그 사이가 창
- **상대에게 「조회」 API가 있으면 재시작 때 물어본다** — 제일 확실하다. `started`로 멈춘 건을 조회 API로 확인해서 마감하면 **사람을 안 불러도 된다.** 조회 API가 있는지 먼저 확인할 것.

### 2) 남은 것은 「모름」으로 분류해 사람이 넘긴다

조회 API마저 없으면, `started`에서 멈춘 건은 자동 재시도하지 않고 **「사람이 확인」 상태로 두고 멈춘다.**

> 중복 결제보다 사람 한 번 부르는 게 싸니까.

이것이 답의 「'모름'으로 분류해 사람이 마감한다」의 의미다. 시스템이 확신할 수 없는 상태를 억지로 자동 처리하지 않고, **불확실을 불확실이라고 정직하게 표시**한 뒤 수동 정산(manual reconciliation)으로 넘기는 것이다. 실무에서 결제 시스템들이 매일 정산 배치로 「우리 기록 vs PG사 기록」을 대사(對査)하는 것과 같은 맥락이다.

## 전체 우선순위 (예제 5의 복구 훈련)

위험한(외부 영향 있음 + 비멱등) 단계를 만나면 순서대로 시도한다.

1. **멱등 키를 붙일 수 있나** — 상대 API 문서를 본다
2. 없으면 **「했다는 기록」을 남긴다** (부작용 로그, 예제 3)
3. 그것도 안 되면 **「사람 확인」 상태로 두고 멈춘다**

## 관련 개념

- **Write-ahead log** — 실행 전에 의도를 기록하고, 복구 시 로그로 상태를 재구성 (sqlite.org/wal)
- **Idempotency-Key 헤더** — IETF httpapi 드래프트로 표준화 진행 중. Stripe 등이 사실상 표준으로 정착시킨 패턴
- **Exactly-once의 한계** — 서로 다른 시스템에 걸친 「정확히 한 번」은 공통 트랜잭션 없이는 보장 불가. at-least-once + 멱등(또는 로그+수동 마감)으로 근사하는 것이 실무 해법
- **다음 장(22장) 연결** — 「다시 하면 된다」가 성립하지 않는 일(이미 보낸 메일 등)은 보상 트랜잭션으로 *되갚는다*
