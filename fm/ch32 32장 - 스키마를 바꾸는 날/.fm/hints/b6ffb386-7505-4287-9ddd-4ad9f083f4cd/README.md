# `ex4_dual_read.py`의 네 가지 읽기 전략

**질문** — `ex4_dual_read.py`의 네 가지 읽기 전략은 무엇인가?

**답** — 옛것만 읽기, 새것만 읽기, 새것 없으면 옛것, 둘 다 읽고 비교다.

---

## 1. 이 예제가 놓인 자리

32장은 「이끔 → 리드」처럼 이미 돌아가고 있는 스키마를 멈추지 않고 바꾸는 얘기입니다. 예제 2가 **확장-수축**(expand and contract)으로 「둘 다 되는 구간」을 만들고, 예제 3이 「언제 옛것을 지워도 되나」를 따집니다. 예제 4는 그 사이, 즉 **옛 이름과 새 이름이 공존하는 이행 구간에서 읽는 코드를 어떻게 쓰나**를 다룹니다.

파일 첫머리에 목적이 그대로 적혀 있습니다.

> 의존성 없음. 옛것과 새것이 공존하는 구간의 읽기 전략 넷을 비교한다.
> 그중 하나만 「데이터가 어긋났을 때」를 알려 준다.

마지막 문장이 이 예제의 전부입니다. 네 전략이 나열되지만, 이행 구간에서 실제로 써야 하는 건 하나입니다.

## 2. 입력 데이터 — 이행 중에는 다섯 가지 상태가 섞여 있다

```python
ROWS = [
    ("t1", "박민수", None,     "옛것만"),
    ("t2", "이서연", "이서연",  "둘 다 · 같음"),
    ("t3", "김도현", "정하윤",  "둘 다 · 다름"),      # 어긋났다
    ("t4", None,     "최유진",  "새것만"),
    ("t5", None,     None,     "둘 다 없음"),
]
```

| 키 | 옛 이름 | 새 이름 | 상황 | 왜 이런 상태가 생기나 |
|---|---|---|---|---|
| `t1` | 박민수 | – | 옛것만 | 백필이 아직 이 키까지 안 왔다 |
| `t2` | 이서연 | 이서연 | 둘 다 · 같음 | 정상. 양쪽 쓰기 또는 백필이 잘 됐다 |
| `t3` | 김도현 | 정하윤 | 둘 다 · **다름** | **어긋났다.** 이 예제의 주인공 |
| `t4` | – | 최유진 | 새것만 | 이행 시작 후에 새로 들어온 데이터 |
| `t5` | – | – | 둘 다 없음 | 진짜로 값이 없는 키 |

`t3`이 왜 생기는지는 본문이 세 가지를 듭니다.

- 이행 중에 「양쪽으로 쓰는」 코드에 버그가 있었거나,
- 옛 코드가 아직 살아 있어서 옛 이름만 고쳤거나,
- 배치가 옛것을 새것으로 복사하는 도중에 누가 옛것을 고쳤거나.

## 3. 네 전략의 코드

```python
def old_only(old, new):
    return old, None

def new_only(old, new):
    return new, None

def new_then_old(old, new):
    return (new if new is not None else old), None

def compare_both(old, new):
    """둘 다 읽고 «다르면» 신고한다."""
    if old is not None and new is not None and old != new:
        return new, "불일치"
    if old is None and new is None:
        return None, "둘 다 없음"
    return (new if new is not None else old), None
```

반환값은 `(값, 플래그)` 두 개입니다. **앞의 세 전략은 플래그 자리에 언제나 `None`을 돌려줍니다.** 즉 구조적으로 신고할 수단이 없습니다. `compare_both`만 `"불일치"` / `"둘 다 없음"`을 실어 보냅니다. `main()`은 이 플래그를 `alerts += flag is not None`으로 세서 「문제 감지」 열에 찍습니다.

## 4. 테스트 케이스별 반환값 — 전략 × 케이스 표

`ex4_dual_read.py`를 돌렸을 때 나오는 표를 그대로 옮긴 것입니다. `-`는 `None`(값 없음)입니다.

| 전략 | `t1` 옛것만 | `t2` 양쪽 일치 | `t3` 양쪽 불일치 | `t4` 새것만 | `t5` 둘 다 없음 | 문제 감지 |
|---|---|---|---|---|---|---|
| 옛것만 읽기 (`old_only`) | 박민수 | 이서연 | **김도현** | **–** | – | **0건** |
| 새것만 읽기 (`new_only`) | **–** | 이서연 | **정하윤** | 최유진 | – | **0건** |
| 새것 없으면 옛것 (`new_then_old`) | 박민수 | 이서연 | **정하윤** | 최유진 | – | **0건** |
| 둘 다 읽고 비교 (`compare_both`) | 박민수 | 이서연 | **정하윤 + 「불일치」** | 최유진 | – + 「둘 다 없음」 | **2건** |

읽는 법:

- **`t1`에서 `new_only`만 값을 잃습니다.** 백필이 안 끝난 키를 새것만 읽으면 데이터가 사라진 것처럼 보입니다. 그래서 「새것만 읽기」는 백필 100% 이전에는 쓸 수 없습니다.
- **`t4`에서 `old_only`만 값을 잃습니다.** 이행 시작 후 새로 들어온 데이터는 옛 이름에 없습니다. 그래서 「옛것만 읽기」는 쓰기가 새 이름으로 넘어간 뒤에는 쓸 수 없습니다.
- **`t3`에서는 네 전략 모두 값을 돌려줍니다.** 차이는 「알려 주느냐」뿐입니다. 앞의 셋은 조용히 하나를 골라 넘깁니다. 고른 게 맞을 수도 틀릴 수도 있는데 아무도 모릅니다.
- **`compare_both`의 2건**은 `t3`(불일치)과 `t5`(둘 다 없음)입니다. `t5`는 진짜 오류가 아닐 수도 있어서 별도 라벨로 구분해 둡니다.
- `new_then_old`와 `compare_both`의 **값 열은 완전히 같습니다.** 유일한 차이가 플래그입니다. 즉 「둘 다 읽고 비교」는 fallback 전략에 **관측 장치만 얹은 것**이고, 값 동작을 바꾸지 않습니다. 이게 이행 구간에 안전하게 켤 수 있는 이유입니다.

## 5. 각 전략이 확장-수축 어느 단계에 대응하나

예제 5(`ex5_migration_plan.py`)의 여섯 단계와 예제 2(`ex2_expand_contract.py`)의 여섯 단계에 대응시키면 이렇습니다.

| 전략 | ex5 단계 | ex2 단계 | 그 단계에서 성립하는 이유 | 넘어갈 조건(게이트) |
|---|---|---|---|---|
| **옛것만 읽기** | `expand` → `dual-write` | 0~1단계 (시작, 확장) | 새 스키마는 생겼지만 아직 신뢰할 수 없다. 읽기는 옛것 그대로 두는 게 기본선 | 「새 스키마가 있나」 / 「양쪽 쓰기가 100%인가」 |
| **새것 없으면 옛것** | `backfill` | 2~3단계 (새 코드 읽기 배포, 쓰기 전환) | 백필이 진행 중이라 새 이름이 비어 있는 키가 남아 있다. 옛것을 fallback으로 둬야 값을 잃지 않는다 | 「백필이 끝났나」 |
| **둘 다 읽고 비교** | `dual-read` | 3~4단계 (둘 다 도는 구간) | 양쪽에 값이 다 있어야 비교가 성립한다. 백필 직후가 어긋남이 가장 많이 드러나는 시점 | **「불일치가 0인가」** ← ex5가 일부러 여기서 막아 둔 게이트 |
| **새것만 읽기** | `cutover` → `contract` | 4~5단계 (옛 코드 제거, 수축) | 불일치가 0이고 옛것 읽기가 0이면 이제 새것만 봐도 된다. 옛것은 검증·롤백용으로만 남긴다 | 「옛것 읽기가 0인가」 / 「롤백이 가능한가」 / 「가장 긴 주기보다 오래 조용한가」 |

시간 순서로 나열하면 **옛것만 → 새것 없으면 옛것 → 둘 다 읽고 비교 → 새것만**입니다. 카드의 답 순서(옛것만 / 새것만 / 새것 없으면 옛것 / 둘 다 읽고 비교)는 코드에 적힌 나열 순서이고, 실제 이행 순서와는 다릅니다. 코드는 「옛것만 → 새것만」을 먼저 붙여 놓고 그 둘이 각각 한쪽 케이스에서 값을 잃는 걸 대비시킨 다음, 뒤의 둘로 넘어갑니다.

## 6. 왜 네 번째만 안전장치인가

본문이 정리한 실무 사용법입니다.

> 이행 구간 동안 «둘 다 읽고 비교»로 돌린다
> 불일치를 지표로 세고, 0 이 될 때까지 수축하지 않는다
> 불일치가 나오면 그 키만 따로 고친다

핵심 문장은 이겁니다.

> 이행 중에는 데이터가 어긋난다. 안 어긋나는 이행은 없다.
> 중요한 건 어긋나는 것을 «막는» 게 아니라 «아는» 것이다.

값(비용)은 **읽기가 두 배가 되는 것**입니다. 이행 구간에만 내는 값이라 괜찮다는 게 저자의 판단입니다. 그리고 이 값을 안 내면 수축한 뒤에 **조용히 틀린 데이터**가 남습니다 — 옛것을 지워 버렸으니 이제 비교할 대상조차 없습니다.

## 7. 예제 5와 이어지는 지점

`ex5_migration_plan.py`의 `STATE`에는 `"불일치_건수": 3`이 들어 있고, `dual-read` 게이트가 `lambda s: s["불일치_건수"] == 0`입니다. 그래서 예제 5는 **일부러 `dual-read` 단계에서 막힙니다.** 이 「불일치 건수」라는 지표를 만들어 내는 게 바로 예제 4의 네 번째 전략입니다.

예제 5 마지막 정리에서도 그 연결을 명시합니다.

```
불일치 0            — 예제 4의 «둘 다 읽고 비교»
```

즉 네 전략을 외우는 목적은 「고를 수 있게」가 아니라, **이행 게이트를 통과시키는 지표가 어디서 나오는지 알기 위해서**입니다. 앞의 세 전략에서는 그 지표가 원리적으로 나올 수 없습니다.

## 8. 한 줄 정리

| 전략 | 한 줄 |
|---|---|
| 옛것만 읽기 | 이행 시작 전 기준선. 새것만 있는 키(`t4`)를 잃는다 |
| 새것만 읽기 | 이행 완료 후 목표 상태. 백필 전에 쓰면 옛것만 있는 키(`t1`)를 잃는다 |
| 새것 없으면 옛것 | 백필 중 안전한 fallback. 값은 안 잃지만 어긋남을 조용히 삼킨다 |
| 둘 다 읽고 비교 | 값은 fallback과 같고, **불일치를 신고한다.** 이행의 유일한 안전장치 |
