# 크론 목록으로도 잡을 수 없는 사용처는 어떻게 찾는가

**질문** 크론 목록으로도 잡을 수 없는 사용처는 어떻게 찾는가?

**답** 옛 이름을 읽으면 경고 로그를 남기게 하고, 지우기 전 마지막 한 달은 읽으면 알림까지 켠다.

---

## 1. 이 질문이 나오는 자리

32장의 흐름은 이렇습니다.

1. 확장-수축(expand/contract)으로 옛것과 새것이 둘 다 되는 구간을 만든다.
2. 마지막 단계인 **수축**(옛 이름 삭제)을 *언제* 해도 되는지가 실무의 어려움이다.
3. 수축 기준은 「최근 30일 조용」이 아니라 **「가장 긴 배치 주기」**다. 분기 결산이면 92일, 연말 정산이면 365일.
4. 그 주기는 **크론 목록**을 파싱해서 계산한다.
5. 그런데 **크론에 없는 사용처**가 남는다. ← 이 카드가 그 지점입니다.

즉 이 답은 "정적 목록으로 세는 방법"의 마지막 구멍을 메우는 장치입니다. 크론 표를 대체하는 게 아니라 **그 위에 덧대는 안전망**입니다.

예제 3(`ex3_when_to_contract.py`)의 결론부가 정확히 이 문장입니다.

```text
그런데 그 주기를 어떻게 아나. 크론 목록을 보면 된다.
크론에 없는 것(사람이 손으로 도는 것)은 못 잡는다. 그래서 하나 더 둔다.

  옛 이름을 읽으면 «경고 로그»를 남기게 하고, 그 로그를 본다.
  지우기 전에 마지막 한 달은 «읽으면 알림»까지 켠다.
```

---

## 2. 정적 목록이 못 잡는 사용처의 유형

「누가 이 필드를 읽나」를 세는 정적 방법은 두 가지입니다. **코드 검색**과 **크론 테이블**. 둘 다 각자의 사각지대가 있습니다.

### 2.1 코드 검색이 못 잡는 것

| 유형 | 왜 안 걸리나 |
|---|---|
| 동적으로 조립한 쿼리 | `f"MATCH ()-[:{rel}]->()"` 처럼 필드명이 변수/설정값. `grep '이끔'` 에 안 뜬다 |
| 설정·DB에 저장된 쿼리 | 대시보드 정의, 룰 엔진 규칙, 리포트 템플릿이 DB row나 YAML에 들어 있다 |
| 저장 프로시저·뷰·머티리얼라이즈드 뷰 | 코드 저장소 밖(DB 안)에 산다 |
| 다른 저장소 / 다른 팀 / 외부 파트너 | 내 리포에서 검색해도 안 나온다 |
| 리플렉션·매핑 테이블·ORM 별칭 | 필드명이 문자열 매핑 표를 한 번 거친다 |
| 사라진 저장소의 배포본 | 코드는 없는데 컨테이너는 돌고 있다 |

### 2.2 크론 테이블이 못 잡는 것 (이 카드의 핵심)

| 유형 | 예 |
|---|---|
| **사람이 손으로 도는 것** | 분기 마감 때 담당자가 노트북/psql로 직접 실행 |
| 애드혹 분석 | BI 툴, 주피터, 스프레드시트 커넥터, 사내 쿼리 콘솔 |
| 런북·장애 대응 쿼리 | 사고 때만 쓰는 진단 쿼리. 6개월에 한 번 |
| 이벤트/웹훅 트리거 | 스케줄이 아니라 외부 요청이 올 때만 도는 것 |
| 수동 승인 후 도는 잡 | 결재가 떨어져야 실행되는 정산·환불 배치 |
| 재처리/백필 스크립트 | 문제 생겼을 때만 꺼내 쓰는 일회성 도구 |
| 사용자 요청 경로 | 특정 화면에 들어가야만 타는 코드. 그 화면을 한 달에 한 명이 본다 |
| 다른 스케줄러 | Airflow/Argo/랙 스케줄러/윈도 작업 스케줄러/앱 내부 타이머 — 「크론 목록」에 없다 |

정리하면, 정적 목록은 **"돌 예정인 것"**만 압니다. **"누군가 필요할 때 도는 것"**은 못 셉니다. 그리고 스키마를 지웠을 때 제일 아프게 깨지는 게 보통 후자입니다(연말 정산, 감사 리포트, 규제 제출).

> 29장의 `Reads` 엣지는 이 문제를 크게 줄여 줍니다. 실제 실행 기록이라 동적 쿼리도 잡히니까요. 하지만 `Reads` 엣지도 **계측된 실행 경로**만 봅니다. 사람이 DB에 직접 붙어서 던진 쿼리는 워크플로 실행으로 기록되지 않습니다. 그래서 경고 로그는 **데이터 접근 경로 자체**(스키마 계층·뷰·DB 감사 로그·프록시)에 붙여야 합니다.

## 3. 2단계 전략: 경고 로그 → 알림 승격

핵심 아이디어는 **찾으러 가지 말고, 쓰는 쪽이 스스로 신고하게 만드는 것**입니다. 옛 이름에 「읽히면 소리를 내는」 장치를 심습니다.

```text
  수축 대기 기간 (가장 긴 주기 + 여유)
├──────────────────────────────────────────┬─────────────┐
│      1단계: 경고 로그 (passive)            │ 2단계: 알림  │  → 이름 변경
│  옛 이름 읽으면 WARN 로그 + 카운터          │ (active)    │  (_deprecated_)
│  대시보드로 주간 리뷰                       │ 마지막 1개월 │
└──────────────────────────────────────────┴─────────────┘
                                                          │
                                            한 주기 더 대기 후 진짜 DROP
```

### 3.1 1단계 — 경고 로그 (긴 기간, 조용한 관측)

- 옛 이름/옛 필드를 읽는 **모든** 경로에 deprecation 경고를 심는다.
- 목적은 **사용처 발굴**이다. 「몇 건인가」보다 「누가 읽는가」가 중요하다.
- 로그를 대시보드/집계 쿼리로 올려 **읽는 주체별 곡선**을 본다. 예제 3의 조직도 렌더처럼 `1,200 → 1,180 → 30 → 0` 으로 떨어지는 곡선이 보이면 이행이 잘 되고 있다는 신호다.
- 이 단계는 **깨우지 않는다**. 사람을 호출하지 않고, 쌓아 두고 주기적으로 읽는다. 이행 초기에는 정상적인 옛 이름 읽기가 아직 많기 때문에, 여기서 알림을 걸면 그 순간 알림이 소음이 되고 아무도 안 본다.

### 3.2 2단계 — 마지막 한 달은 알림까지

- 삭제 직전 한 달, 같은 이벤트를 **경고 → 알림(page/채널 호출)**로 승격한다.
- 「읽히면 즉시 사람이 안다」 상태를 만든다.
- 알림이 뜨면 **삭제를 연기**하고, 그 주체를 찾아 새 이름으로 옮긴다. 그리고 한 달 시계를 다시 돌린다. 이 규칙을 미리 정해 두지 않으면 알림은 그냥 무시되는 로그가 된다.
- 한 달 내내 알림이 없으면, 그 침묵은 **관측된 침묵**이 된다. 「로그를 안 봤을 뿐」이 아니라 「봤는데 없었다」로 증거의 등급이 올라간다.

### 3.3 왜 알림은 「마지막 한 달」만인가

| 이유 | 설명 |
|---|---|
| **알림 피로** | 이행 구간 전체에 알림을 걸면 옛 이름을 읽는 정상 트래픽이 그대로 알림이 된다. 몇 시간 안에 mute 되고, 정작 필요한 순간에 꺼져 있다 |
| **오탐/미탐 비용의 역전** | 이행 초기의 미탐은 나중에 고칠 수 있다. 삭제 직전의 미탐은 **되돌릴 수 없는 장애**가 된다. 그래서 마지막 한 달만 감도를 최대로 올린다 |
| **신호 대 잡음** | 이행이 끝나 가면 옛 이름 읽기는 거의 0이다. 이때 뜨는 이벤트 하나하나가 전부 「몰랐던 사용처」다. 잡음이 없어야 알림이 신호가 된다 |
| **사람의 주의 예산** | 한 달은 담당자가 긴장을 유지할 수 있는 길이다. 6개월간 온콜을 켜 둘 수는 없다 |
| **결정과의 정렬** | 마지막 한 달은 「지운다/미룬다」를 실제로 결정하는 창이다. 알림은 그 결정에 필요한 증거를 실시간으로 공급한다 |

**중요한 오해 하나.** 「마지막 한 달 알림」은 **가장 긴 주기 대기 조건을 대체하지 않습니다.** 분기 결산이 92일 주기면 92일(+여유)을 기다리는 것은 그대로 지키고, 그 마지막 한 달에 알림을 겹쳐 켭니다. 한 달만 조용했다고 지우면, 예제 3의 "52일째 조용한 분기 결산"을 그대로 밟습니다.

### 3.4 그리고 되돌릴 수 있게 지운다

알림 한 달이 조용해도 바로 `DROP` 하지 않습니다.

```text
이끔  →  _deprecated_이끔   (이름만 바꿔 둔다)
        └─ 한 주기 더 대기 ─→ 진짜 삭제
```

이름만 바꿔 두면, 뒤늦게 깨어난 사용처가 깨졌을 때 **되돌리기가 몇 분**입니다. 실제로 `ex5_migration_plan.py`가 `cutover` 게이트에 `롤백_가능`을 넣어 둔 것도 같은 사고방식입니다.

## 4. 로그에 무엇을 남겨야 사용처를 특정할 수 있나

「옛 이름이 1,204건 읽혔다」는 로그는 **쓸모가 없습니다.** 누구를 찾아가야 할지 모르니까요. 사용처를 *특정*하려면 아래 항목이 필요합니다.

### 4.1 최소 필수 항목

| 필드 | 왜 필요한가 |
|---|---|
| `deprecated_name` / `field` | 어느 옛 이름인지. 옛 이름이 여러 개 동시 이행 중일 수 있다 |
| `timestamp` (+ 타임존) | 「매월 1일 02:00」 같은 **주기 패턴**을 복원해야 한다. 이게 곧 그 잡의 실제 주기다 |
| **호출 주체** | 서비스명 / 앱 이름 / 워크플로 ID / 잡 이름. 「누구에게 말하면 되나」의 답 |
| **인증 주체** | DB 유저, 서비스 어카운트, API 키 ID, OAuth 클라이언트. 사람이 손으로 돌린 경우 **여기에만 흔적이 남는다** (개인 계정으로 붙었으니까) |
| **스택 트레이스** | 코드 검색이 못 찾은 호출 지점을 코드 라인 단위로 알려 준다. 전체가 아니라 **정규화된 상위 N 프레임**(라이브러리 프레임 제거)만 |
| **쿼리 지문** (query fingerprint) | 리터럴을 제거해 정규화한 쿼리 문자열의 해시. 같은 사용처를 하나로 묶어 카디널리티를 줄이고, 「어떤 형태로 읽는가」를 보여 준다 |
| `client_host` / pod / container / IP | 어느 배포본·어느 노트북에서 왔나. 사람 vs 자동을 가르는 1차 단서 |
| 진입점(entry point) | HTTP 라우트, CLI argv, 크론 이름, 큐 토픽. 「무엇 때문에 이 코드가 돌았나」 |
| `trace_id` / `request_id` | 분산 트레이싱과 조인해서 호출 사슬 전체를 복원한다 |
| 배포 식별자 | 이미지 태그 / 커밋 SHA / 버전. 「어느 배포본이 아직 옛 코드인가」 |
| `is_human` 힌트 | 대화형 세션 여부, TTY, BI 툴 User-Agent 등. 크론 밖 사용처를 바로 골라낸다 |

### 4.2 운영상의 요령

- **집계는 하되 샘플링은 하지 마라.** 드물게 도는 잡은 정확히 「드물기 때문에」 샘플에서 빠집니다. 대신 **지문+주체 조합별로 최초 1회는 풀 컨텍스트(스택 포함), 이후는 카운터만** 올리는 방식으로 볼륨을 잡습니다.
- **레벨은 WARN, 이름은 고정.** `deprecated_schema_read` 처럼 고정 이벤트 이름을 쓰면 알림 승격이 규칙 한 줄 변경으로 끝납니다.
- **로그와 지표를 같이.** 로그는 「누구인가」, 지표(`deprecated_reads{reader=...}`)는 「곡선이 0으로 가나」에 답합니다. 예제 5의 `옛것_읽기_건수_최근` 게이트가 이 지표를 먹습니다.
- **심는 위치는 낮은 층.** 애플리케이션 코드마다 심으면 놓칩니다. 스키마 접근 계층 / 별칭 뷰 / DB 감사 로그 / 쿼리 프록시처럼 **모든 읽기가 지나가는 지점** 하나에 심습니다. 그래야 손으로 던진 쿼리도 잡힙니다.
- **드물게 도는 잡일수록 알림을 세게.** 32장의 한 장 요약에도 나오는 문장입니다. 「매일 도는 건 내일 알지만 2년에 한 번 도는 건 2년 뒤에 압니다.」

---

## 5. 한 줄 정리

크론 목록은 **예정된 것**만 셉니다. 예정 밖의 사용처(사람이 손으로, 애드혹, 이벤트 트리거)는 찾아다니지 말고 **옛 이름이 읽힐 때 스스로 신고하게** 만듭니다 — 긴 기간은 **경고 로그로 조용히 모아서 주체를 특정**하고, 삭제 직전 **마지막 한 달만 알림으로 승격**해서 신호 대 잡음이 최선일 때 최대 감도를 씁니다. 그래도 지울 때는 이름만 바꿔 두고 한 주기 더 기다립니다.
