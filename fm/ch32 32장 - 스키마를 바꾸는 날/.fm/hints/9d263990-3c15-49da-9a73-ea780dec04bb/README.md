# 필드를 바꾸기 전에 세야 할 것: 「누가 읽나」

## 질문

필드를 바꾸기 전에 무엇을 세야 하며 코드 검색의 한계는 무엇인가?

## 답

**「누가 읽나」를 세야 한다.** 코드 검색으로는 동적으로 만든 쿼리를 찾을 수 없어 [29장](../../../../ch29%2029장%20-%20아키텍처를%20검사한다/)의 `Reads` 엣지가 필요하다.

---

## 왜 「무엇이 깨지나」가 아니고 「누가 읽나」인가

32장 첫 예제(`ex1_breaking_change.py`)는 스키마 변경 여덟 가지를 깨짐/안 깨짐으로 분류하는 표부터 시작합니다.

| 변경 | 예 | 판정 | 이유 |
|---|---|---|---|
| 관계 이름 바꾸기 | 이끔 → 리드 | 깨짐 | 쿼리가 못 찾는다 |
| 속성 추가 | `Person.email` 추가 | 안 깨짐 | 옛 코드는 그냥 무시한다 |
| 속성 제거 | `Person.nickname` 제거 | 깨짐 | 읽던 코드가 죽는다 |
| 속성 타입 변경 | 인원 `STRING` → `INT64` | 깨짐 | 파싱이 달라진다 |
| 필수 속성 추가 | `Team.owner` 필수 | 깨짐 | 기존 노드에 값이 없다 |
| 관계 방향 뒤집기 | 속함 방향 반전 | 깨짐 | 순회가 전부 어긋난다 |
| 새 노드 종류 추가 | `Project` 추가 | 안 깨짐 | 안 쓰면 없는 것과 같다 |
| 단일값 → 다중값 | 이끔을 여러 개 허용 | 조건부 | 읽는 쪽이 한 개를 기대하면 깨짐 |

정리하면 **더하는 변경은 안 깨지고, 바꾸거나 빼는 변경은 깨집니다.**

그런데 이 표만으로는 의사결정이 안 됩니다. 이 장의 핵심 문장이 그 이유입니다.

> 위험은 스키마가 아니라 「그 스키마를 어떻게 읽고 있느냐」에 있어요.

「깨짐」이라는 같은 판정을 받은 두 변경이 실제 위험도는 여섯 배 다를 수 있습니다. 그래서 세야 하는 숫자는 **"이 필드를 읽는 실행이 몇 개인가"** 입니다.

## 세는 방법 — 29장의 `Reads` 엣지

예제 1은 29장에서 만든 `Reads` 엣지를 그대로 재사용합니다. 스키마는 단순합니다.

```
Run  --[:Reads {field}]-->  Entity(kind='field')
```

즉 "어느 실행(워크플로)이 어느 필드를 읽었다"를 **실제 실행 기록으로** 그래프에 남겨 둔 것입니다. 29장을 안 봤다면 「실행이 무엇을 읽었는지 기록해 둔다」 정도로 이해하면 충분합니다.

그러면 질문 하나로 답이 나옵니다.

```cypher
MATCH (run:Run)-[:Reads]->(e:Entity {id: $f})
RETURN run.wf ORDER BY run.wf
```

예제의 관측값:

| 필드 | 읽는 실행 수 | 읽는 것들 |
|---|---|---|
| 속함 | 6 | 보고서 발송, 조직도 렌더, 권한 계산, 정산 배치, 온보딩, 감사 리포트 |
| 이끔 | 4 | 보고서 발송, 조직도 렌더, 권한 계산, 알림 라우팅 |
| 인원 | 2 | 정산 배치, 대시보드 |
| nickname | 1 | 인사말 생성 |

`속함`을 바꾸면 실행 6개가 깨지고, `nickname`은 1개가 깨집니다. **같은 「깨지는 변경」인데 값이 여섯 배 다릅니다.**

## 코드 검색의 한계

대부분의 팀은 위 표를 못 만듭니다. 「이 필드를 누가 쓰는지」를 `grep`/IDE 참조 찾기로 해결하려 하기 때문입니다. 그리고 정적 검색은 다음을 놓칩니다.

- **동적으로 조립한 쿼리** — 문자열 결합, f-string, 템플릿 엔진으로 만든 쿼리
  ```python
  field = config["sort_key"]          # "이끔"
  q = f"MATCH (a)-[:{rel}]->(b) RETURN a.{field}"
  ```
  소스 어디에도 `이끔`이라는 리터럴이 없으므로 검색에 안 걸립니다.
- **설정/데이터에 들어 있는 필드 이름** — YAML·JSON·DB 테이블·환경변수에 담긴 컬럼명
- **리포지토리 밖의 소비자** — 다른 팀 서비스, 노트북, BI 대시보드, 애드혹 SQL
- **리플렉션/ORM 매핑, 별칭(alias)** — 이름이 런타임에만 결정되는 경우
- 반대로 **거짓 양성**도 나옵니다. 주석·죽은 코드·테스트 픽스처가 검색에는 잡히지만 실제로는 아무도 안 읽습니다.

`Reads` 엣지는 이 문제를 방향을 바꿔서 해결합니다. **소스를 뒤지는 게 아니라 실제로 읽은 기록을 남기는** 것이므로

- 동적 쿼리도 잡힙니다 (실행 시점에는 필드 이름이 확정되어 있으니까)
- 죽은 코드는 안 잡힙니다 (안 돌았으면 기록이 없으니까)
- 「몇 번 읽었나」까지 세므로 위험의 크기를 잴 수 있습니다

한계도 정직하게 남습니다. **관측 창 안에 안 돈 것은 기록이 없습니다.** 분기 결산·연말 정산처럼 드물게 도는 잡이 그렇고, 그게 곧 32.3절(「아무도 안 쓴다」를 어떻게 아나)에서 수축 기준을 「최근 30일」이 아니라 **「가장 긴 배치 주기」**로 잡아야 하는 이유입니다. 크론에 없는 수동 실행은 크론 파싱으로도 못 잡으므로, 옛 이름을 읽을 때 경고 로그·알림을 걸어 관측을 보강합니다.

## 세고 나면 무엇이 달라지나

예제 1이 제시하는 판단 순서입니다.

1. 바꾸려는 필드를 **누가 읽는지 센다**
2. 그 수가 1~2면 **그냥 바꾼다** (`nickname` 같은 경우)
3. 여섯이면 **확장-수축(expand and contract)** 으로 간다 — 예제 2

즉 이 카운트는 "겁주기용 숫자"가 아니라 **마이그레이션 전략을 고르는 입력값**입니다. 읽는 사람이 한 명이면 6주짜리 확장-수축을 돌릴 필요가 없고, 여섯이면 반드시 옛것과 새것이 둘 다 되는 구간을 만들어야 합니다.

그리고 세는 비용은 아주 쌉니다.

> 세는 데 5분 걸리고, 안 세면 배포하고 나서 안다.

## 함께 보면 좋은 것

- **확장-수축(Parallel Change)** — Martin Fowler, <https://martinfowler.com/bliki/ParallelChange.html>. 「확장 → 이행 → 수축」 3단계와 **읽기 먼저, 쓰기 나중** 순서.
- 29장 — `Reads` 엣지를 만드는 쪽. 이 카드의 답이 "29장이 여기서 값을 한다"로 끝나는 이유.
- 31장 — 스키마는 그대로 두고 같은 필드를 두고 다투는 이야기. 32장은 그 반대(필드 자체가 바뀔 때).

## 한 줄 정리

세야 하는 것은 **「누가 읽나」(읽는 실행의 수)**이고, 코드 검색은 **동적으로 조립된 쿼리를 못 찾기 때문에** 실행 기록인 29장의 `Reads` 엣지가 필요합니다.
