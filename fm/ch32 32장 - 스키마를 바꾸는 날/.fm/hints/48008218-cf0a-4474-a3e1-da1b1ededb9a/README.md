# 한 번에 바꾸면 어느 쪽이 죽는가?

**답: DB를 먼저 바꾸면 옛 코드가 죽고, 코드를 먼저 바꾸면 새 코드가 죽는다.**

32장의 예제 2(`ex2_expand_contract.py`)가 마지막에 딱 이렇게 정리합니다.

```
한 번에 바꾸면 어떻게 되나. 배포 순간에 둘 중 하나가 죽는다.
  DB 를 먼저 바꾸면 → 옛 코드가 죽는다
  코드를 먼저 바꾸면 → 새 코드가 죽는다
```

예제의 상황은 관계 이름을 `이끔 → 리드`로 바꾸는 일입니다. 옛 코드는 `이끔`만 알고, 새 코드는 `리드`만 압니다.

```python
def old_reader(c):
    """옛 코드 — «이끔» 만 안다."""
    ...MATCH (p:N)-[e:R {kind:'이끔'}]->(t:N)...

def new_reader(c):
    """새 코드 — «리드» 만 안다."""
    ...MATCH (p:N)-[e:R {kind:'리드'}]->(t:N)...
```

즉 **스키마와 코드는 서로 다른 두 개의 배포 단위**이고, 둘은 절대 같은 순간에 바뀌지 않습니다. 그 시간차가 사고의 원인입니다.

---

## 두 실패 시나리오를 나란히 놓기

### 시나리오 A — DB를 먼저 바꾼다 (`이끔`을 `리드`로 rename)

| 시각 | DB 상태 | 배포된 코드 | 결과 |
|---|---|---|---|
| T0 | `이끔` | 옛 코드(`이끔` 읽기) | 정상 |
| **T1** | **`리드`** | 옛 코드(`이끔` 읽기) | **옛 코드가 죽는다** — 쿼리가 0건을 돌려주거나 스키마 에러 |
| T2 | `리드` | 새 코드(`리드` 읽기) | 정상 복귀 |

- 죽는 구간: **T1 ~ T2**, 즉 마이그레이션 실행 후 코드 배포가 끝날 때까지.
- 무서운 점은 「에러가 안 날 수도 있다」는 것입니다. 그래프 쿼리에서 없는 라벨/속성을 매칭하면 예외가 아니라 **빈 결과**가 나옵니다. 보고서가 실패하지 않고 *빈 보고서*로 나가고, 권한 계산이 실패하지 않고 *권한 없음*으로 나옵니다. 예제 1의 `USAGE` 표를 보면 `이끔`을 읽는 실행이 「보고서 발송 · 조직도 렌더 · 권한 계산 · 알림 라우팅」 네 개, `속함`은 여섯 개입니다. 조용한 실패가 여섯 군데로 퍼집니다.

### 시나리오 B — 코드를 먼저 바꾼다

| 시각 | DB 상태 | 배포된 코드 | 결과 |
|---|---|---|---|
| T0 | `이끔` | 옛 코드 | 정상 |
| **T1** | `이끔` | **새 코드(`리드` 읽기/쓰기)** | **새 코드가 죽는다** — 읽을 `리드`가 아직 없다 |
| T2 | `리드` | 새 코드 | 정상 복귀 |

- 죽는 구간: **T1 ~ T2**, 즉 코드 배포 후 마이그레이션이 끝날 때까지. 백필이 몇 시간~며칠 걸리는 규모라면 이 구간이 그대로 장애 시간입니다.
- 게다가 새 코드가 이 구간에 `리드`로 **쓰기**까지 하면, 뒤늦게 도는 마이그레이션 배치가 그 데이터를 덮거나 건너뛰면서 예제 4의 `t3`(`옛 이름=김도현`, `새 이름=정하윤`) 같은 **불일치**가 생깁니다.

### 대칭 구조

```
        DB 먼저                          코드 먼저
  ┌──────────────────┐            ┌──────────────────┐
  │ DB:  이끔 → 리드  │            │ DB:  이끔 ─────── │
  │ 코드: 이끔 ─── 리드│            │ 코드: 이끔 → 리드  │
  └──────────────────┘            └──────────────────┘
        ↑ 옛 코드가                       ↑ 새 코드가
          읽을 게 없다                      읽을 게 없다
```

어느 쪽을 먼저 해도 **「한쪽만 아는 것」과 「다른 쪽만 있는 것」이 겹치는 구간**이 반드시 생깁니다. 순서를 바꿔서 없앨 수 있는 문제가 아니라, 순서 선택 자체가 「누가 죽을지」를 고르는 일입니다.

---

## 그럼 동시에 바꾸면 되지 않나 — 왜 불가능한가

「마이그레이션과 배포를 같은 순간에 하면 구간이 0이 되지 않나」가 자연스러운 반박입니다. 실제 운영에서 그게 안 되는 이유가 셋입니다.

### 1. 롤링 배포는 원자적이지 않다

무중단 배포의 정의 자체가 「인스턴스를 하나씩 갈아 끼운다」입니다. 10대 중 3대만 새 코드인 순간이 존재하고, 그 순간에는 **옛 코드와 새 코드가 같은 DB를 동시에 본다**.

```
t=0   [옛][옛][옛][옛][옛]   DB: 이끔        모두 정상
t=1   [새][옛][옛][옛][옛]   DB: 이끔        새 코드 1대 죽음
t=2   [새][새][새][옛][옛]   DB: 이끔 or 리드  ← 어느 쪽이든 절반이 죽는다
t=3   [새][새][새][새][새]   DB: 리드        모두 정상
```

t=1~t=2 구간에서 DB가 어떤 상태여야 맞을까요. **정답이 없습니다.** `이끔`이면 새 인스턴스가 틀리고, `리드`면 옛 인스턴스가 틀립니다. 즉 「하나만 정답인 스키마」로는 롤링 배포를 통과할 수 없습니다. 이건 블루/그린 배포에서도 똑같습니다 — 그린으로 트래픽을 넘기는 동안 블루는 아직 살아 있고, 롤백 경로로 남겨 둔 블루는 옛 스키마를 기대합니다.

### 2. 프로세스 밖에 사는 독자들이 있다

웹 서버만 배포하면 끝이 아닙니다. 예제 3의 `READS` 기록을 보세요.

| 읽는 주체 | 성격 |
|---|---|
| 조직도 렌더 | 온라인, 배포 대상 |
| 정산 배치 | 일/주 단위 크론 |
| 월말 마감 | 82일째에 340건 — 월 1회 |
| 분기 결산 | 88일째에 210건 — 92일 주기 |

크론 잡, 리포팅 파이프라인, 다른 팀의 읽기 전용 잡, 노트북에서 손으로 도는 쿼리는 여러분의 배포 파이프라인 안에 없습니다. **모든 독자를 같은 순간에 갈아 끼울 수 있는 스위치는 애초에 존재하지 않습니다.** 「동시 전환」은 단일 프로세스·단일 독자 시스템에서만 성립하는 가정입니다.

### 3. 롤백도 배포다

배포가 잘못돼서 되돌릴 때, 코드는 초 단위로 롤백되지만 스키마는 그렇지 않습니다. 옛 이름을 이미 지웠다면 **롤백할 곳이 없습니다.** 예제 5가 `cutover` 게이트에 일부러 `("롤백이 가능한가", lambda s: s["롤백_가능"])`를 끼워 둔 이유입니다. 한 번에 바꾸는 방식은 롤백 가능성을 배포 첫 순간에 버립니다.

여기에 **긴 트랜잭션·인플라이트 요청**까지 겹칩니다. 마이그레이션이 커밋되는 순간 이미 진행 중이던 요청은 옛 스키마를 전제로 시작된 것들입니다. 진짜 「동시」는 프로세스 경계·네트워크 경계·시간 경계를 모두 얼려야 가능한데, 그건 곧 다운타임입니다. **동시 전환을 요구하는 것은 무중단을 포기하는 것과 같습니다.**

## 확장-수축이 딜레마를 해소하는 방식

해법은 「누가 죽을지 고르기」를 멈추고, **아무도 죽지 않는 구간을 인공적으로 만드는** 것입니다. 마틴 파울러가 Parallel Change / expand-contract로 부르는 패턴입니다.

```
확장(expand)   — 새것을 «더한다». 옛것은 그대로 둔다
이행(migrate)  — 읽기를 옮기고, 그다음 쓰기를 옮긴다
수축(contract) — 아무도 안 쓰는 게 확인되면 옛것을 지운다
```

핵심 통찰은 예제 1의 판정 표에 이미 있습니다.

| 변경 | 판정 | 이유 |
|---|---|---|
| 속성 추가 (`Person.email`) | **안 깨짐** | 옛 코드는 그냥 무시한다 |
| 새 노드 종류 추가 (`Project`) | **안 깨짐** | 안 쓰면 없는 것과 같다 |
| 관계 이름 바꾸기 (`이끔 → 리드`) | 깨짐 | 쿼리가 못 찾는다 |
| 속성 제거 (`nickname`) | 깨짐 | 읽던 코드가 죽는다 |

**깨지는 변경 하나를, 안 깨지는 변경 여러 개로 분해합니다.** rename은 「추가(안 깨짐) → 이행 → 삭제(깨짐이지만 이제 독자가 0)」로 쪼갤 수 있습니다.

예제 2의 여섯 단계와, 각 단계에서 옛/새 코드의 생존 여부:

| 단계 | 하는 일 | 이끔 | 리드 | 옛 코드 | 새 코드 |
|---|---|---|---|---|---|
| 0. 시작 | — | 2 | 0 | 동작 | ✗ |
| 1. 확장 | 새 이름을 **같이** 쓴다 (`copy`) | 2 | 2 | 동작 | 동작 |
| 2. 새 코드 배포 (읽기만) | — | 2 | 2 | **동작** | **동작** |
| 3. 쓰기를 새 이름으로 | `newwrite` | 2 | 3 | **동작** | **동작** |
| 4. 옛 코드 제거 | — | 2 | 3 | (동작) | 동작 |
| 5. 수축 | 옛 이름 삭제 (`drop`) | 0 | 3 | ✗ | 동작 |

2~3단계가 이 패턴의 전부입니다. **옛 코드와 새 코드가 둘 다 동작하는 구간**이 존재하기 때문에, 그 안에서는 롤링 배포가 며칠 걸려도, 인스턴스가 섞여 있어도, 분기 배치가 뒤늦게 깨어나도 아무것도 죽지 않습니다. 배포 순서에 대한 제약이 사라지고, 롤백도 언제든 가능합니다.

지켜야 할 세부 규칙 둘:

- **읽기 먼저, 쓰기 나중.** 예제 2가 못을 박습니다 — *「거꾸로 하면 새 이름으로 쓴 데이터를 옛 코드가 못 읽는다.」* 새 이름으로 쓰기 시작하기 전에, 모든 독자가 새 이름을 읽을 수 있어야 합니다.
- **수축은 시간이 아니라 주기로 판단한다.** 예제 3의 결론대로 「최근 30일 조용」은 92일 주기 분기 결산을 놓칩니다. 기준은 시스템에서 **가장 긴 배치 주기**이고, 예제 5는 이걸 게이트로 코드화합니다: `s["옛것_마지막_읽기_경과일"] > s["가장_긴_주기_일"]`.

정리하면 — 「한 번에 바꾸면 어느 쪽이 죽는가」의 답은 **「먼저 바꾼 쪽의 반대편」**이고, 확장-수축은 그 질문을 아예 성립하지 않게 만들어 답합니다.
