# 「최근 30일」 기준의 함정

> **Q.** '최근 30일' 기준의 함정은 무엇인가?
>
> **A.** 분기 결산처럼 드물게 도는 잡을 놓친다. 52일째 조용해도 92일 주기 잡이면 40일 뒤에 깨어나 없어진 이름을 찾는다.

---

## 한 줄 논리

**관측 창(observation window)이 주기(period)보다 짧으면, 그 창 안의 침묵은 아무것도 증명하지 않는다.**

「최근 30일간 이 필드를 읽은 기록이 0건」은 두 가지 중 하나를 뜻한다.

1. 정말 아무도 안 쓴다.
2. 쓰는 놈의 **주기가 30일보다 길어서** 마침 창 밖에 있었다.

30일 창은 이 둘을 구분할 능력이 없다. 그런데 수축(contract, 옛 스키마 삭제)은 되돌리기 어려운 파괴적 작업이다. 구분할 능력이 없는 관측치로 파괴적 결정을 내리는 것 — 그게 함정이다.

원문(32.3절)이 딱 이렇게 정리한다.

> 수축 기준은 「최근 30일」이 아니라 *「가장 긴 배치 주기」*입니다. 분기 배치면 92일, 연말 정산이면 365일이에요. 크론 표현식을 파싱해서 계산하세요.

---

## 52일과 92일이 어디서 나오는 숫자인가

두 숫자 모두 `code/ex3_when_to_contract.py`의 데이터에서 직접 나온다.

### 데이터 (원문 발췌)

```python
# 최근 90일간 옛 이름(이끔)을 읽은 기록
# (일자, 읽은 주체, 건수)
READS = [
    (1,  "정산 배치",   420), (1,  "조직도 렌더", 1200),
    (7,  "정산 배치",   410), (7,  "조직도 렌더", 1180),
    (14, "정산 배치",   405), (14, "조직도 렌더",   30),
    (21, "정산 배치",   400), (21, "조직도 렌더",    0),
    (30, "정산 배치",   395),
    (45, "정산 배치",   390),
    (60, "정산 배치",     2),
    (75, "정산 배치",     0),
    (82, "월말 마감",    340),      # 월말에만 도는 배치
    (88, "분기 결산",    210),      # 분기에 한 번 도는 배치
    (90, "정산 배치",     0),
]
TODAY = 140
```

- **52일** = `TODAY(140) - 88`. 88일째에 「분기 결산」이 옛 이름(`이끔`)을 210건 읽었다. 오늘이 140일째니까 마지막 사용으로부터 **52일**이 지났다. 이 값은 `ex5_migration_plan.py`의 관측값에도 그대로 박혀 있다 — `"옛것_마지막_읽기_경과일": 52`.
- **92일** = 분기(3개월) 주기를 일수로 환산한 값. 코드에서 상수로 선언된다.

```python
LONGEST_CYCLE = 92          # 제일 드문 것 — 분기 결산
```

`ex5`에서는 게이트 조건의 우변이 된다 — `"가장_긴_주기_일": 92`.

- **40일** = `92 - 52`. 아직 한 주기가 안 지났다. 즉 분기 결산은 **앞으로 40일 뒤에** 다음 회차로 깨어난다. 그때 옛 이름이 이미 지워져 있으면 그 잡이 죽는다.

## 타임라인으로 짚기

```
 일자 →  0        21    30      45    60    75  82  88  90        110        140
         |         |     |       |     |     |   |   |   |          |          |
조직도    1200 1180 30   0                                                     |  ← 이행 완료(새 코드로 감)
렌더     ●───●────●────○                                                      |
                                                                              |
정산      420 410 405  400     390    2    0           0                      |  ← 잦게 돌고, 값도 0으로 수렴
배치     ●───●────●────●───────●─────●────○──────────○                        |
                                                                              |
월말                                        340                               |  ← 30일 주기
마감     ·································●································    |
                                                                              |
분기                                            210                           |  ← 92일 주기 ★
결산     ·····································●···························    |
                                                                              |
                                                     [←── 최근 30일 창 ──→]   ← 오늘(140)
                                                                  110 ~ 140
```

창의 위치를 보라. **「최근 30일」 창은 110~140일 구간**이다. 그리고 마지막 읽기 기록은 90일째다. **창 안에는 단 한 건도 없다.** 그래서 30일 기준은 자신만만하게 「지워도 됨」이라고 답한다.

그런데 그 창 바로 왼쪽 밖에, 92일마다 한 번 뛰는 심장이 88일째에 뛰었다.

```
             88일: 분기 결산 뜀        140일: 오늘        180일: 분기 결산 다시 뜀
                  ●─────────────────────┼─────────────────────●
                  |←──── 52일 경과 ────→|←──── 40일 남음 ────→|
                  |←──────────── 한 주기 = 92일 ───────────→|
                        [30일 창은 이 구간의 32%밖에 못 본다]
```

지금 수축하면, 40일 뒤 분기 결산이 일어나 `이끔`을 찾고, 없다. 배포한 사람은 이미 다른 일을 하고 있다.

## 세 가지 판정이 갈리는 지점

`ex3`은 같은 데이터를 놓고 세 가지 방법으로 판정하게 해 놓았다. **앞의 둘은 「지워도 됨」, 세 번째만 「아직」이라고 하고, 세 번째가 맞다.**

| # | 판정 방법 | 코드 | 결론 | 왜 그렇게 나오나 |
|---|---|---|---|---|
| 1 | 최근 30일 건수가 0인가 | `sum(n for day, n in h if day > TODAY - 30) == 0` | **지워도 됨** (틀림) | 창은 110~140. 모든 기록이 90일 이전이라 합이 0 |
| 2 | 모든 주체가 30일 이상 조용 | `(TODAY - last_use(...)) >= 30` | **지워도 됨** (틀림) | 제일 최근 사용이 52일 전. 52 ≥ 30이니 통과 |
| 3 | 가장 긴 주기(92일)보다 오래 조용한가 | `(TODAY - last_use(...)) > LONGEST_CYCLE` | **아직** (맞음) | 분기 결산이 52일 전. 52 > 92가 아니다 |

주목할 점: 1번과 2번은 서로 다른 방식으로 틀린다.

- **1번은 창 밖을 못 본다.** 「기록이 0건」과 「관측 안 됨」을 같은 것으로 취급한다. 이게 가장 흔하고 가장 위험한 형태다.
- **2번은 경과일을 제대로 세지만(52일), 비교 대상이 잘못됐다.** 30일이라는 숫자가 어디서 왔는지 근거가 없다. 관측치는 맞고 임계값이 틀린 경우다.
- **3번은 비교 대상을 시스템에서 가져온다.** 30일이라는 임의의 상수 대신, 그 필드를 읽는 잡들 중 **제일 드물게 도는 놈의 주기**를 임계값으로 쓴다.

원문 결론 문장이 이것이다.

> 그래서 기준은 «시간»이 아니라 «가장 긴 주기»여야 한다.
> 시스템에서 제일 드물게 도는 잡의 주기를 찾고, 그보다 길게 기다린다.

---

## 임계값을 어떻게 정하나

주기는 사람의 기억이 아니라 **크론 표현식**에서 뽑는다.

| 잡 성격 | 크론 예 | 안전 대기 |
|---|---|---|
| 매일 배치 | `0 3 * * *` | 1일 |
| 주간 리포트 | `0 4 * * 1` | 7일 |
| 월말 마감 | `0 2 28-31 * *` | 31일 |
| 분기 결산 | `0 2 1 1,4,7,10 *` | **92일** (분기 최대 일수) |
| 연말 정산 | `0 2 1 1 *` | **365일** |

92는 여기서 온다 — 1~3월(90/91일), 4~6월(91일), 7~9월(92일), 10~12월(92일) 중 최댓값. 「대략 3개월」이 아니라 **최악의 간격**을 쓴다는 게 요점이다.

그리고 원문은 여기서 한 발 더 나간다.

> 연말 정산이면 365일이다. 그러면 «1년 조용»해도 안 지워야 한다.

즉 관측 창을 30일에서 90일로 늘리는 것으로는 해결되지 않는다. **어떤 고정 창을 쓰든 그보다 긴 주기가 하나라도 있으면 같은 함정이 다시 열린다.** 창을 늘리는 게 아니라, 창의 길이를 시스템에서 계산해 와야 한다.

---

## 크론에도 없는 놈: 보조 장치 셋

크론 파싱만으로 다 잡히지 않는다. 사람이 손으로 도는 것, 외부 팀이 부르는 것은 크론에 없다. 원문이 제시하는 세 겹의 보강.

1. **경고 로그.** 옛 이름을 읽으면 경고 로그를 남기게 하고 그 로그를 본다. 크론 목록에 없는 호출자를 실측으로 잡는다.
2. **읽으면 알림.** 지우기 전 마지막 한 달은 알림까지 켠다. 로그를 아무도 안 볼 가능성에 대비한다.
3. **되돌릴 수 있게 지운다.** 바로 `DROP` 하지 말고 이름만 바꿔 둔다(`이끔` → `_deprecated_이끔`). **한 주기 더 기다린 다음** 진짜로 지운다. 40일 뒤 분기 결산이 깨어나도 이름만 되돌리면 복구된다.

여기에 관련된 32.3절의 짝 문장도 같이 기억할 것.

> 드물게 도는 잡일수록 실패 알림을 세게 거세요. 매일 도는 건 내일 알지만 2년에 한 번 도는 건 2년 뒤에 압니다.

주기가 길다는 것은 **피드백 루프가 길다**는 뜻이고, 피드백 루프가 길면 잘못된 삭제의 발각이 그만큼 늦어진다. 위험은 「몇 건 읽었나」에 비례하지 않고 「얼마나 드물게 도나」에 비례한다.

## 대비: 반대 방향의 오독도 있다

같은 데이터에서 「조직도 렌더」의 곡선을 보라 — `1200 → 1180 → 30 → 0`.

이건 **잘 되고 있다는 신호다.** 새 코드로 옮겨 간 흔적이라 실제로 안전하다. 반면 「분기 결산」은 한 점(88일, 210건)만 찍혀 있고 그 앞뒤가 비어 있다.

- **감소 곡선**(1200 → 30 → 0): 이행이 진행된 증거. 안전에 가깝다.
- **띄엄띄엄 한 점**(0 … 210 … 0): 주기가 관측 기간보다 긴 증거. 절대 안전이 아니다.

건수가 0인 구간의 모양을 보면 어느 쪽인지 구분이 된다. 「최근 30일 건수」라는 스칼라 하나로 뭉개면 이 모양 정보가 전부 날아간다.

## 이 판정이 마이그레이션 계획에 박히는 자리

`ex5_migration_plan.py`는 이 기준을 마지막 단계의 게이트로 코드화한다.

```python
"contract":   [("가장 긴 주기보다 오래 조용한가",
                lambda s: s["옛것_마지막_읽기_경과일"]
                          > s["가장_긴_주기_일"])],
```

관측값이 `52 > 92`이므로 이 게이트는 통과하지 않는다. 문서라면 「52일이나 조용했으니 됐겠지」로 사람이 넘어갔을 자리를, 코드는 넘어가지 못하게 막는다.

> 계획을 문서로 적으면 「지금 어디쯤인가」를 사람이 판단하게 된다.
> 그리고 사람은 「대충 된 것 같은데」로 다음 단계로 넘어간다.

「최근 30일」의 함정이 무서운 진짜 이유가 여기 있다. **그 기준은 사람의 낙관과 방향이 같다.** 빨리 지우고 싶은 사람에게 지워도 된다고 답해 준다. 그래서 반드시 실행 가능한 게이트로 박아 두어야 한다.

## 한눈에

| 함정의 정체 | 관측 창(30일) < 주기(92일)일 때, 창 안의 침묵을 「미사용」으로 오독 |
| 52일 | `TODAY(140) − 88`. 88일째 분기 결산이 옛 이름 210건 읽음 |
| 92일 | 분기 주기의 최악 일수. `LONGEST_CYCLE = 92` |
