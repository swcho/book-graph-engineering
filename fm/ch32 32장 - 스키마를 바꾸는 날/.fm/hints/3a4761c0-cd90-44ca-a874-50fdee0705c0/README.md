# '둘 다 읽고 비교'의 비용과 그 정당성

**질문**: '둘 다 읽고 비교'의 비용과 그 정당성은 무엇인가?

**답**: 읽기가 두 배가 되지만 이행 구간에만 내는 비용이다. 이 비용을 안 내면 수축 뒤에 조용히 틀린 데이터가 남는다.

---

## 1. 원문의 자리

32장 예제 4(`ex4_dual_read.py`)는 이행 구간의 읽기 전략 네 가지를 비교합니다.

| 전략 | t3(옛 이름 김도현 / 새 이름 정하윤)에서 하는 일 | 불일치 감지 |
|---|---|---|
| 옛것만 읽기 | 김도현을 고른다 | 못 함 |
| 새것만 읽기 | 정하윤을 고른다 | 못 함 |
| 새것 없으면 옛것 | 정하윤을 고른다 | 못 함 |
| **둘 다 읽고 비교** | 정하윤을 고르고 **「불일치」로 신고** | 함 |

앞의 세 개는 t3에서 *조용히 하나를 고릅니다*. 고른 게 맞을 수도 틀릴 수도 있는데 **아무도 모릅니다.** 네 번째만 신고하고, 그게 이행의 진짜 안전장치입니다. 예제의 마지막 두 줄이 이 카드의 답입니다.

> 값은 읽기가 두 배가 되는 것이다. 이행 구간에만 내는 값이라 괜찮다.
> 그리고 이 값을 안 내면, 수축한 뒤에 «조용히 틀린 데이터»가 남는다.

이 불일치 지표는 예제 5(`ex5_migration_plan.py`)의 `dual-read` 게이트로 직결됩니다.

```python
"dual-read":  [("불일치가 0인가", lambda s: s["불일치_건수"] == 0)],
```

즉 "둘 다 읽고 비교"는 취향이 아니라 **수축(contract)으로 넘어가는 관문의 계측 장치**입니다. 이 계측기를 안 달면 게이트 자체가 존재할 수 없습니다.

---

## 2. "읽기가 두 배"가 실제로 어디에 부담을 주는가

"두 배"를 뭉뚱그리면 안 됩니다. 두 배가 되는 지점과 그렇지 않은 지점이 다릅니다.

### 2.1 두 배가 되는 것

| 항목 | 영향 | 이유 |
|---|---|---|
| **읽기 QPS** | ×2 | 키 하나당 옛 경로 1회 + 새 경로 1회 |
| **DB 커넥션 점유 시간** | ×2 (동기 순차라면) | 커넥션을 두 번 잡거나, 한 번 잡고 두 번 왕복 |
| **커넥션 풀 대기** | ×2보다 **더 나빠질 수 있음** | 풀은 선형이 아니라 포화 근처에서 급격히 무너진다 |
| **쿼리 캐시/버퍼 풀 히트율** | 하락 | 워킹셋이 두 스키마로 나뉘어 캐시 경쟁 |
| **비교 로직 CPU** | 소폭 증가 | 값 정규화 + 동등성 판정 |

### 2.2 두 배가 아닌 것

- **꼬리 지연(p99)**: 두 읽기를 **병렬**로 날리면 응답 지연은 `2 × latency`가 아니라 `max(old, new)`에 가깝습니다. 대신 순간 커넥션 수요는 2배가 되므로 풀 크기를 같이 올려야 합니다. 순차로 돌리면 지연은 `old + new`로 정직하게 두 배가 됩니다.
- **쓰기 부하**: 이 전략은 읽기 전략입니다. 쓰기는 dual-write 단계가 이미 두 배로 만들어 놓았고, 여기서 추가되지 않습니다.
- **전체 시스템 부하**: 스키마 하나에 걸린 읽기가 전체 읽기의 5%라면, 그 5%가 두 배 되어 전체는 105%가 됩니다. 전체가 두 배 되는 게 아닙니다. **"두 배"의 분모를 확인하는 게 비용 산정의 첫걸음입니다.**

### 2.3 예시 산정

예제 3의 관측값을 빌려 봅시다. 조직도 렌더가 하루 1,200건, 정산 배치가 420건 규모라면 이 필드의 읽기는 하루 수천 건대입니다. 이 규모에서 "두 배"는 **비용이라고 부르기 민망한 수준**입니다.

반대로 위험한 경우는 이렇습니다.

- 해당 필드가 **핫 패스**에 있어 초당 수만 건 읽히는 경우
- 옛 경로가 **인덱스 없는 풀스캔**이라 한 번 읽기가 이미 무거운 경우
- 커넥션 풀이 이미 **포화 직전**(예: max 100에 평균 85 사용)이어서 2배 수요가 큐 대기와 타임아웃 폭발로 번지는 경우

그래서 정량화의 순서는 이렇습니다.

1. 이 필드의 읽기 QPS를 센다 (29장의 `Reads` 엣지가 이미 세어 줍니다)
2. 그게 전체 읽기의 몇 %인지 본다
3. 커넥션 풀 여유율을 본다
4. 두 배가 들어갔을 때 p99와 풀 대기 큐가 어디로 가는지 본다

**결론이 "괜찮다"로 나오는 경우가 압도적으로 많습니다.** 그리고 나온 결론이 "안 괜찮다"일 때 쓰는 수단이 4절입니다.

## 3. 한시적 비용이라는 점 — 구간의 길이를 계산한다

이 비용의 정당성의 절반은 "**끝난다**"는 사실에서 나옵니다. 영구 오버헤드가 아니라 이행 구간에만 내는 값입니다. 그러면 그 구간이 얼마나 긴가.

예제 5의 여섯 단계 중 dual-read 비용이 발생하는 구간은 이렇습니다.

```
expand → dual-write → backfill → [dual-read] → cutover → contract
                                  ^^^^^^^^^^^^^^^^^^^^
                                  비교 읽기가 도는 구간
```

구간 길이 ≈ **백필 완주 시간 + 불일치가 0으로 수렴할 때까지의 관측 기간**

- **백필**: 쪼개서 돌리고, 어디까지 했는지 남기고, 멱등하게. 데이터 규모와 스로틀에 따라 수 시간에서 수 주.
- **불일치 수렴 관측**: 불일치가 0이 되고 나서도 **한 사이클은 더 봐야** 합니다. 0이 된 게 "고쳐졌기 때문"인지 "그 경로가 아직 안 돌았기 때문"인지 구분해야 하니까요.

주의할 점 하나. **dual-read 구간과 contract 대기 구간은 다릅니다.** 예제 3이 말하는 "가장 긴 배치 주기"(분기 92일, 연말 정산 365일)는 **contract 게이트**의 조건입니다.

```python
"contract": [("가장 긴 주기보다 오래 조용한가",
              lambda s: s["옛것_마지막_읽기_경과일"] > s["가장_긴_주기_일"])],
```

옛 이름을 읽는 게 0이 되면 cutover 이후에는 비교할 대상 자체가 사라집니다 — 즉 **365일 동안 읽기 2배를 내야 하는 게 아닙니다.** 다만 드물게 도는 배치(월말 마감, 분기 결산)까지 비교로 검증하려면 그 잡이 **최소 한 번은 dual-read 상태에서 돌아 봐야** 하므로, 그 잡에 한해서는 비교 구간이 한 주기만큼 길어집니다.

여기서 나오는 실무 요령: **트래픽 많은 온라인 경로는 비교 구간을 짧게 끝내고, 드물게 도는 배치 경로는 비교를 오래 켜 둡니다.** 어차피 배치는 QPS가 낮아서 2배가 아프지 않습니다. 비용이 큰 쪽과 오래 켜야 하는 쪽이 서로 다른 경로라는 게 이 전략에 운이 좋은 지점입니다.

## 4. 비용을 줄이는 실무 수단

"두 배가 아프다"는 진단이 실제로 나왔을 때 쓰는 수단들입니다. 각각 **무엇을 포기하는지**를 같이 적습니다.

### 4.1 샘플링 (1%, 0.1%)

전체가 아니라 일부 요청에서만 두 번 읽고 비교합니다. 비용은 비율만큼 정직하게 줄어듭니다(1% 샘플링 → 추가 읽기 부하 +1%).

- **포기하는 것**: 개별 키의 정확성 보장. 샘플에 안 걸린 키의 불일치는 못 봅니다.
- 샘플링 키를 **해시 기반으로 결정론적으로** 고르면(예: `hash(key) % 100 == 0`) 같은 키를 반복 관찰할 수 있어 "고쳐졌는지"를 추적할 수 있습니다. 랜덤 샘플링은 매번 다른 키를 봐서 재현이 안 됩니다.

### 4.2 비동기 비교 (shadow read)

응답 경로에서는 새것만 읽어 바로 응답하고, 옛것 읽기와 비교는 **응답 후 백그라운드**로 던집니다.

- **얻는 것**: 사용자 체감 지연에 0을 더합니다. p99가 안 흔들립니다.
- **포기하는 것**: 불일치를 발견해도 **그 요청은 이미 응답이 나갔습니다.** 사후 감지지 사전 차단이 아닙니다.
- **주의**: 백그라운드 큐/워커의 용량과 유실률을 감시해야 합니다. 큐가 조용히 드롭하면 "불일치 0"이 "관측 실패 0"으로 위장됩니다. 이게 이 수단의 가장 위험한 실패 모드입니다.

### 4.3 캐시 / 요청 단위 메모이제이션

같은 요청 안에서 같은 키를 여러 번 읽는 코드라면, 두 스키마 읽기를 **요청 스코프에 한 번씩만** 하도록 묶습니다. 그래프 순회처럼 같은 노드를 반복 방문하는 워크로드에서는 이것만으로 배수가 크게 떨어집니다.

- **포기하는 것**: 요청 내에서 데이터가 바뀌는 경우의 최신성. 읽기 전용 경로에는 사실상 무해합니다.
- 관련 수단: 두 읽기를 **한 쿼리로 합치기.** 옛 필드와 새 필드가 같은 노드/행에 있으면 `RETURN n.old, n.new`처럼 한 번에 가져와 왕복을 1회로 줄입니다. 이게 가능한 상황에서는 "읽기 2배"가 애초에 성립하지 않습니다. 예제 2의 관계 이름 변경처럼 **엣지 종류가 다른** 경우는 순회가 갈리기 때문에 합치기 어렵습니다.

### 4.4 그 외

- **오프피크 배치 검증**: 온라인 경로에서는 비교를 아예 끄고, 야간에 전수 비교 잡을 한 번 돌립니다. 비용을 트래픽 없는 시간대로 옮기는 것. 다만 "쓰기 직후 어긋남" 같은 실시간 현상은 놓칩니다.
- **핫 키 제외 / 콜드 키 집중**: 읽기 상위 0.1% 키가 트래픽 대부분을 먹는 분포라면, 핫 키는 비교에서 빼고 롱테일에 비교를 집중시킵니다. 데이터 어긋남은 오히려 손 안 탄 롱테일에서 잘 나옵니다.

## 5. 샘플링을 쓰면 '불일치 0' 게이트의 의미가 약해진다

이게 4절의 값을 치를 때 반드시 인식해야 하는 대가입니다.

전수 비교에서 "불일치 0"은 **"검증한 범위 = 전체 범위"에서 어긋난 게 없다**는 뜻입니다. 샘플링을 켜면 이 문장이 **"본 것 중에는 없다"**로 약해집니다. 이 둘은 전혀 다른 주장입니다.

직관적인 계산으로 감을 잡을 수 있습니다. 진짜 불일치율이 `r`이고 샘플로 `n`건을 봤다면, 전부 일치로 나올 확률은 대략 `(1 - r)^n`입니다.

| 샘플 관측 건수 `n` | 불일치율 1%일 때 "0건"이 나올 확률 | 불일치율 0.1%일 때 |
|---|---|---|
| 100 | 약 37% | 약 90% |
| 1,000 | 약 0.004% | 약 37% |
| 10,000 | 사실상 0 | 약 0.005% |

읽으면 이렇습니다. **1% 샘플링으로 10,000건 중 100건만 봤는데 "0건"이 나왔다면, 실제 불일치율이 1%여도 그 결과가 나올 확률이 37%입니다.** 게이트를 통과시켰지만 실제로는 100건 중 1건이 틀려 있을 수 있습니다.

거칠지만 쓸 만한 뒤집기: **불일치율 `r`을 95% 신뢰로 배제하려면 대략 `3/r`건을 봐야 합니다.**

- 0.1%(1000건 중 1건)를 배제하려면 약 3,000건 관측
- 0.01%를 배제하려면 약 30,000건 관측

그래서 샘플링을 쓸 때의 규율은 이렇습니다.

1. **게이트 문구를 정직하게 바꿉니다.** `불일치_건수 == 0`이 아니라 `관측_건수 >= N and 불일치_건수 == 0`으로. 관측 건수를 게이트에 넣지 않으면 "아직 아무것도 안 봐서 0"이 통과합니다. 이게 샘플링 도입의 가장 흔한 사고입니다.
2. **허용 불일치율 상한을 먼저 정합니다.** 결제·정산이면 0에 수렴해야 하고, 추천 랭킹이면 0.1%도 감당할 수 있습니다. 도메인이 `r`을 정하고, `r`이 `n`을 정하고, `n`이 샘플링 비율과 구간 길이를 정합니다.
3. **수축 직전 마지막 구간은 전수로 올립니다.** 되돌릴 수 없는 단계 앞에서만 전수 비용을 냅니다. 구간 전체가 아니라 마지막 며칠이면 비용 총액이 작습니다.
4. **드물게 도는 잡은 샘플링에서 뺍니다.** 분기 결산이 1%로 샘플링되면 한 주기에 사실상 아무것도 못 봅니다. 저QPS 경로는 전수가 공짜입니다.
5. **"관측 파이프라인이 살아 있는가"를 따로 감시합니다.** 예제 3이 "드물게 도는 잡일수록 실패 알림을 세게 걸라"고 한 것과 같은 원리입니다. 조용한 계측기는 좋은 신호와 구분되지 않습니다.

## 6. 비용을 안 내면 생기는 손해 — 왜 이 값이 정당한가

여기가 카드 답의 뒷문장입니다. 비교 읽기를 생략했을 때 잃는 것을 비용과 나란히 놓아야 정당성이 성립합니다.

### 6.1 손해의 성질: 발견 시점이 되돌릴 수 없는 지점 뒤로 밀린다

비교를 안 하면 t3 같은 어긋남을 **모릅니다.** 모르는 상태로 게이트를 통과하고, cutover하고, contract에서 옛 스키마를 지웁니다.

그 뒤에 남는 것이 "**조용히 틀린 데이터**"입니다. 예외도, 500도, 알림도 없습니다. 김도현 자리에 정하윤이 들어가 있고 시스템은 정상으로 보입니다. 보고서가 나가고, 조직도가 렌더되고, 권한이 계산되고, 알림이 라우팅됩니다 — 전부 틀린 값으로.

**결정적인 비대칭은 이것입니다.**

| | dual-read 비용 | 생략했을 때의 손해 |
|---|---|---|
| 크기 | 읽기 2배 (전체로는 보통 몇 %) | 데이터 정확성 |
| 지속 | 이행 구간에만 | 발견될 때까지 영구 |
| 되돌리기 | 스위치 끄면 즉시 0 | 옛 스키마가 이미 없어서 **불가** |
| 발견 시점 | 즉시 (지표로 카운트) | 몇 달 뒤, 사람이 이상하다고 신고할 때 |

옛 스키마가 살아 있는 동안은 정답지가 손에 있습니다. contract가 그 정답지를 태웁니다. **비교는 정답지가 있는 동안에만 할 수 있는 일이고, 그래서 시점이 되돌아오지 않습니다.**

예제 5가 `cutover` 게이트에 `롤백_가능`을 일부러 끼워 둔 것도 같은 이유입니다. 되돌리기 어려운 단계 앞에서 되돌릴 수 있는지 묻습니다.

### 6.2 사후 복구 비용이 사전 비용보다 크다

수축 뒤에 틀린 데이터를 발견하면 해야 할 일은 이렇습니다.

- 어긋난 키의 **범위 특정** — 옛 스키마가 없으니 무엇이 틀렸는지 알 방법이 없습니다. 백업/로그/감사 테이블 고고학이 시작됩니다.
- **하류 오염 추적** — 그 값을 읽어 만든 보고서, 집계, 파생 테이블, 외부로 나간 알림까지. 예제 1의 `속함` 필드는 실행 6개가 읽습니다.
- **신뢰 손실** — 데이터 팀에 대한 신뢰는 복구가 제일 느립니다.

읽기 2배를 몇 주 내는 것과, 위 세 줄을 하는 것 중 무엇이 싼지는 비교 대상이 아닙니다.

## 7. 한 줄 정리

읽기 2배는 **끝나는 비용**이고, 조용히 틀린 데이터는 **끝나지 않는 손해**입니다. 32장이 "안 어긋나는 이행은 없다. 막으려 하지 말고 *세라*"고 말한 이유가 이것이고, "둘 다 읽고 비교"는 그 세는 도구입니다. 비용이 정말 아플 때는 샘플링·비동기·캐시로 깎을 수 있지만, 깎은 만큼 "불일치 0"이라는 게이트의 보증 강도도 같이 깎인다는 사실을 게이트 조건에 명시적으로 적어 두어야 합니다.
