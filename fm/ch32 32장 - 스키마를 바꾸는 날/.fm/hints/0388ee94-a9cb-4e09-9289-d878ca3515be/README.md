# 확장-수축에서 무중단이 가능한 구간은 어디인가?

**답: 2~3단계다. 옛 코드와 새 코드가 둘 다 동작한다.**

32장 예제 2(`ex2_expand_contract.py`)는 「이끔 → 리드」라는 관계 이름 하나를 바꾸는 일을 여섯 단계로 쪼개고, 각 단계마다 *옛 코드*와 *새 코드*를 둘 다 실행해 본다. 그 표에서 두 열이 동시에 「동작」으로 찍히는 구간이 무중단 배포가 성립하는 구간이고, 책이 짚는 곳이 2단계와 3단계다.

---

## 1. 무엇이 「둘 다」인가 — 두 개의 리더

예제는 같은 데이터를 두 방식으로 읽는 함수를 나란히 둔다.

```python
def old_reader(c):   # 옛 코드 — «이끔» 만 안다
    r = c.execute("MATCH (p:N)-[e:R {kind:'이끔'}]->(t:N) RETURN p.name, t.name")

def new_reader(c):   # 새 코드 — «리드» 만 안다
    r = c.execute("MATCH (p:N)-[e:R {kind:'리드'}]->(t:N) RETURN p.name, t.name")
```

핵심은 이 둘이 **서로를 모른다**는 것이다. 옛 코드는 `리드`라는 이름을 들어 본 적이 없고, 새 코드는 `이끔`을 모른다. 무중단 배포의 조건은 이 「서로 모르는 두 코드」가 같은 DB 위에서 동시에 옳게 돌아가는 구간을 만드는 것이다.

왜 「동시에」가 필요한가. 롤링 배포는 본질적으로 옛 버전 인스턴스와 새 버전 인스턴스가 섞여 도는 시간을 만든다. 인스턴스가 10대면 배포 도중 어느 순간에는 6대가 옛 코드, 4대가 새 코드다. 그 순간 두 버전 중 하나라도 죽으면 그게 곧 장애다. 즉 무중단이란 「배포를 빨리 하는 것」이 아니라 **혼재 상태가 정상 상태인 구간을 확보하는 것**이다.

## 2. 여섯 단계와 그 표

예제가 도는 순서와, 각 단계에서 두 종류의 엣지가 몇 건인지, 두 리더가 사는지 죽는지를 정리하면 이렇다.

| 단계 | 하는 일 | 이끔 | 리드 | 옛 코드 | 새 코드 | 무중단 배포가 가능한가 |
|---|---|---|---|---|---|---|
| 0. 시작 | 아무것도 안 함 | 2 | 0 | 동작 | ✗ 안 됨 | **불가** — 새 코드를 올리면 즉사 |
| 1. 확장 | 새 이름을 «같이» 쓴다(복사·백필) | 2 | 2 | 동작 | 동작 | 데이터 준비 단계. 복사가 끝난 뒤부터 안전 |
| 2. 새 코드 배포 (읽기만) | 읽기를 새 이름으로 옮긴다 | 2 | 2 | 동작 | 동작 | **가능** |
| 3. 쓰기를 새 이름으로 | 새로 들어오는 것은 리드로만 | 2 | 3 | 동작 | 동작 | **가능** |
| 4. 옛 코드 제거 | 옛 리더를 걷어낸다 | 2 | 3 | 동작 | 동작 | 정리 단계. 전환은 이미 끝났다 |
| 5. 수축 | 옛 이름 삭제 (`DELETE e`) | 0 | 3 | ✗ 안 됨 | 동작 | **불가** — 되돌릴 수 없다 |

예제의 마지막 출력이 그대로 이렇게 말한다.

> 2단계와 3단계를 보시라. 옛 코드와 새 코드가 «둘 다» 동작한다.
> 그 구간이 있어야 무중단 배포가 된다.

---

## 3. 왜 하필 2~3단계인가 — 성립 조건 두 가지

「둘 다 동작」은 두 조건이 동시에 만족될 때만 성립한다.

**조건 A. 두 이름이 물리적으로 공존한다.**
1단계의 `copy` 액션이 하는 일이 이것이다.

```python
c.execute("MATCH (a:N)-[e:R {kind:'이끔'}]->(b:N) "
          "CREATE (a)-[:R {kind:'리드'}]->(b)")
```

옛 엣지를 지우지 않고 새 엣지를 **더한다**. 확장(expand)이 「더하기」인 이유가 여기 있다. 예제 1의 판정 표를 보면 «속성 추가», «새 노드 종류 추가»는 「안 깨짐 — 옛 코드는 그냥 무시한다」다. 즉 더하는 변경만이 옛 코드를 살려 둔다. 반대로 «이름 바꾸기», «제거», «타입 변경», «필수 속성 추가», «방향 뒤집기»는 전부 깨진다. 확장-수축은 *깨지는 변경 하나*를 *안 깨지는 변경 여러 개*로 분해하는 기법이다.

**조건 B. 두 코드가 같은 답을 낸다.**
예외 없이 도는 것만으로는 부족하다. 옛 코드가 조용히 낡은 답을 내면 그게 더 나쁘다. 그래서 순서가 정해져 있다 — **읽기 먼저, 쓰기 나중.**

2단계에서 읽기만 새 이름으로 옮기는 동안 쓰기는 아직 양쪽(또는 옛쪽)에 들어가므로 두 리더가 보는 세계가 같다. 3단계에서 쓰기를 리드로 옮기면 `이끔=2 / 리드=3`으로 갈라지기 시작하는데, 이때 이미 읽기가 새 이름으로 넘어가 있으니 사용자에게 보이는 답은 새 코드 쪽이다. 남아 있는 옛 리더는 새 데이터를 못 보지만, 그건 실패가 아니라 「곧 걷어낼 잔여 경로」다.

거꾸로 하면 바로 깨진다. 예제가 이렇게 경고한다.

> 순서가 중요하다. «읽기 먼저, 쓰기 나중»이다.
> 거꾸로 하면 새 이름으로 쓴 데이터를 옛 코드가 못 읽는다.

쓰기를 먼저 옮기면 3단계에서 생긴 세 번째 `리드` 엣지를, 아직 주력인 옛 코드가 못 본다. 예외도 안 나고 500도 안 뜨고, 그냥 **결과가 하나 비어서 나온다.** 무중단처럼 보이는 조용한 데이터 손실이다.

## 4. 구간을 벗어나면 무엇이 깨지나 — 단계별로

### 0단계에서 새 코드를 올리면 (DB보다 코드를 먼저 바꾼 경우)
`리드` 엣지가 0건이다. 새 코드의 `MATCH ... {kind:'리드'}`는 빈 결과를 돌려준다. 조직도가 텅 비고, 권한 계산이 「아무도 아무 팀도 안 이끈다」로 나오고, 보고서 발송 대상이 0명이 된다. 예외조차 안 나서 모니터링이 조용한 게 최악이다.

### 5단계를 너무 일찍 하면 (코드보다 DB를 먼저 지운 경우)
`DELETE e`로 `이끔`이 0건이 되고, 아직 살아 있는 옛 코드가 즉사한다. 예제 2의 요약이 이 두 실패를 대칭으로 놓는다.

> 한 번에 바꾸면 어떻게 되나. 배포 순간에 둘 중 하나가 죽는다.
>   DB 를 먼저 바꾸면 → 옛 코드가 죽는다
>   코드를 먼저 바꾸면 → 새 코드가 죽는다

그리고 5단계가 특별히 위험한 이유는 **되돌릴 수 없다**는 것이다. 2~3단계는 옛 이름이 그대로 살아 있어서 배포만 롤백하면 원상 복구된다. 5단계 이후엔 데이터가 사라졌으니 롤백할 대상이 없다. 예제 5가 `cutover` 게이트에 `롤백_가능`을 일부러 끼워 넣은 이유다.

### 1단계 안에서 서두르면
확장 액션(복사·백필)이 진행 중인데 새 코드를 올리면 「일부 키만 새 이름이 있는」 상태를 만난다. 예제 4의 이행 중 데이터가 정확히 그 모습이다.

| 키 | 옛 이름 | 새 이름 | 상황 |
|---|---|---|---|
| t1 | 박민수 | – | 옛것만 |
| t2 | 이서연 | 이서연 | 둘 다 · 같음 |
| t3 | 김도현 | 정하윤 | 둘 다 · **다름** |
| t4 | – | 최유진 | 새것만 |
| t5 | – | – | 둘 다 없음 |

이 구간에서 「새것만 읽기」로 돌면 t1이 조용히 사라진다. 그래서 이행 구간의 읽기 전략은 **새것 없으면 옛것**으로 폴백하거나, 더 낫게는 **둘 다 읽고 비교**해서 t3 같은 불일치를 신고하게 한다.

```python
def compare_both(old, new):
    """둘 다 읽고 «다르면» 신고한다."""
    if old is not None and new is not None and old != new:
        return new, "불일치"
    ...
```

읽기 비용이 두 배가 되지만, 이행 구간에만 내는 값이다. 이 값을 안 내면 수축한 뒤에 「조용히 틀린 데이터」가 남는다.

### 4단계에서 서두르면
옛 코드를 걷었다고 옛 이름을 바로 지우면 안 된다. 표에서 4단계의 옛 코드가 여전히 「동작」으로 찍히는 게 힌트다 — 옛 이름을 읽는 경로가 코드베이스에 남아 있을 수 있다. 특히 예제 3이 말하는 **드물게 도는 잡**이 문제다. 조직도 렌더는 1,200 → 1,180 → 30 → 0으로 곱게 빠졌지만, 분기 결산은 52일째 조용할 뿐 92일 주기다. 「최근 30일 무사용」 기준으로 지우면 40일 뒤에 깨어나서 없어진 이름을 찾는다. 그래서 수축 기준은 시간이 아니라 **가장 긴 배치 주기**여야 한다.

## 5. 게이트로 옮기면

예제 5는 이 판단을 사람에게 맡기지 않고 코드로 적는다. 각 단계를 *떠나기* 위한 조건들이다.

| 단계 | 다음으로 갈 조건 | 무중단과의 관계 |
|---|---|---|
| expand | 새 스키마가 있나 | 조건 A(공존) 확보 |
| dual-write | 양쪽 쓰기가 100%인가 | 새 코드가 옛 데이터를 놓치지 않게 |
| backfill | 백필이 끝났나 | 「새것만 있고 옛것은 없는」 구멍 제거 |
| dual-read | 불일치가 0인가 | 조건 B(같은 답) 증명 |
| cutover | 옛것 읽기가 0인가 / 롤백이 가능한가 | 되돌릴 수 있는 마지막 지점 |
| contract | 가장 긴 주기보다 오래 조용한가 | 드문 배치까지 통과시킨 뒤 삭제 |

`dual-write` ~ `dual-read`가 바로 예제 2의 2~3단계에 해당하는 구간이고, 그 안에서만 배포·롤백이 자유롭다. 이 조건들을 CI에 걸면 마이그레이션이 상태 기계가 된다. 「대충 된 것 같은데」로 넘어갈 수 없다.

---

## 한 줄 정리

무중단이 성립하는 구간은 **옛 이름과 새 이름이 둘 다 존재하고(확장 완료), 읽기가 새 이름으로 옮겨진 뒤 쓰기가 따라 옮겨지는 2~3단계**다. 그 앞(0단계)에서는 새 코드가 빈 결과를 보고, 그 뒤(5단계)에서는 옛 코드가 죽으며 되돌릴 방법도 없다. 확장-수축의 목적은 이 「둘 다 되는」 창을 인위적으로 넓게 만들고, 그 창 안에서만 배포·전환·검증을 끝내는 것이다.
