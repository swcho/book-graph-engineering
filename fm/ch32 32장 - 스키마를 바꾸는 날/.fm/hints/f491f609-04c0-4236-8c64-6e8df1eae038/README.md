# 마이그레이션 계획은 어떤 형태로 적어야 하는가?

> **답**: 문서가 아니라 **코드**로 적는다. 조건을 못 채우면 넘어갈 수 없게 만든다.

출처: 32장 「스키마를 바꾸는 날」 32.5절 *계획을 코드로 적는다* / `code/ex5_migration_plan.py`

---

## 1. 왜 문서로 적으면 안 되나

마이그레이션 계획을 위키 문서나 노션 체크리스트로 적으면, 「지금 어디쯤인가」를 **사람이 판단**하게 된다. 그리고 사람은 이렇게 판단한다.

> 「대충 된 것 같은데」

책의 표현을 그대로 쓰면 이렇다.

```
계획을 문서로 적으면 「지금 어디쯤인가」를 사람이 판단하게 된다.
그리고 사람은 「대충 된 것 같은데」로 다음 단계로 넘어간다.

조건을 코드로 적으면 «넘어갈 수 없다». 불일치 3건이 남아 있으면 막힌다.
```

문서의 문제는 세 가지다.

| 문서의 문제 | 결과 |
|---|---|
| 조건이 산문이라 애매하다 | 「백필이 거의 끝났다」가 몇 %인지 아무도 모른다 |
| 판정 주체가 사람이다 | 일정 압박이 들어오면 낙관 쪽으로 기울어진다 |
| 관측값과 계획이 분리돼 있다 | 문서는 지난주 상태를 말하고 시스템은 지금 상태다 |

핵심은 **계획을 지키는 강제력이 사람의 성실함에 의존하면 안 된다**는 것이다.

## 2. 코드로 적는다는 게 구체적으로 무슨 뜻인가

세 가지를 코드로 표현한다.

1. **단계(phase) 목록** — 마이그레이션이 지나갈 상태들
2. **관측값(state)** — 시스템에서 실제로 긁어 온 지금의 수치
3. **게이트(gate)** — 각 단계를 *떠나기* 위해 통과해야 하는 조건. 관측값을 받아 참/거짓을 돌려주는 술어(predicate)

`ex5_migration_plan.py`의 구조가 그대로 이 셋이다.

```python
PHASES = [
    ("expand",      "새 스키마를 «더한다». 옛것 그대로"),
    ("dual-write",  "쓰기를 양쪽에 한다"),
    ("backfill",    "옛 데이터를 새 스키마로 복사"),
    ("dual-read",   "읽기를 둘 다 하고 비교"),
    ("cutover",     "읽기를 새것으로. 옛것은 검증용"),
    ("contract",    "옛 스키마 삭제"),
]

# 현재 관측값
STATE = {
    "새_스키마_존재": True,
    "양쪽_쓰기_비율": 1.00,
    "백필_진행률": 1.00,
    "불일치_건수": 3,          # ← 여기가 0이 아니다
    "옛것_읽기_건수_최근": 0,
    "가장_긴_주기_일": 92,
    "옛것_마지막_읽기_경과일": 52,
    "롤백_가능": True,
}

GATES = {
    "expand":     [("새 스키마가 있나", lambda s: s["새_스키마_존재"])],
    "dual-write": [("양쪽 쓰기가 100%인가", lambda s: s["양쪽_쓰기_비율"] >= 1.0)],
    "backfill":   [("백필이 끝났나", lambda s: s["백필_진행률"] >= 1.0)],
    "dual-read":  [("불일치가 0인가", lambda s: s["불일치_건수"] == 0)],
    "cutover":    [("옛것 읽기가 0인가", lambda s: s["옛것_읽기_건수_최근"] == 0),
                   ("롤백이 가능한가", lambda s: s["롤백_가능"])],
    "contract":   [("가장 긴 주기보다 오래 조용한가",
                    lambda s: s["옛것_마지막_읽기_경과일"] > s["가장_긴_주기_일"])],
}
```

여기서 결정적인 대목: **게이트는 「단계를 시작하는 조건」이 아니라 「단계를 떠나는 조건」**이다. 예제 코드 주석도 *"각 단계를 «떠나려면» 통과해야 하는 조건"*이라고 못 박는다. 그래서 마이그레이션이 **상태 기계**가 된다.

> 이 파일을 CI 에 넣으면 마이그레이션이 «상태 기계»가 된다.
> 그리고 상태 기계는 사람의 낙관을 안 탄다.

## 3. 예제가 일부러 막혀 있다

`ex5`는 `dual-read` 단계에서 막히도록 만들어져 있다. `불일치_건수`가 3이기 때문이다.

```
지금 막혀 있는 곳: dual-read
  → 불일치가 0인가 : 아니오
```

챕터의 실행 가이드도 이걸 명시한다.

> `ex5` 는 일부러 `dual-read` 단계에서 막히게 해 두었습니다.
> `STATE["불일치_건수"]` 를 0으로 바꾸면 다음 단계로 넘어갑니다.

문서라면 「불일치 몇 건 남았는데 뭐 넘어가도 되겠지」가 가능하다. 코드는 그게 불가능하다. 이게 답의 후반부 「조건을 못 채우면 넘어갈 수 없게 만든다」의 실체다.

## 4. 게이트 조건은 앞 절에서 벌어 온 것들이다

이 절이 마지막에 오는 이유가 있다. 게이트에 쓰인 조건들이 앞의 예제에서 하나씩 유도된 것이라, 32.5절은 새 개념이 아니라 **앞의 내용을 집행 가능하게 묶는 절**이다.

| 게이트 조건 | 출처 | 왜 필요한가 |
|---|---|---|
| 양쪽 쓰기 100% | 예제 2(확장-수축) 3단계 | 일부만 양쪽 쓰기면 새 스키마에 구멍이 생긴다 |
| 백필 진행률 100% | 32.2절 백필 | 쪼개서·멱등하게·재개 가능하게 돌리고, 끝난 뒤 한 번 더 돈다 |
| 불일치 0 | 예제 4 「둘 다 읽고 비교」 | 이행 중엔 반드시 어긋난다. 막는 게 아니라 *세는* 것이 안전장치 |
| 옛것 읽기 최근 0 | 예제 1의 `Reads` 엣지(29장) | 코드 검색으로는 동적 쿼리를 못 찾는다. 실제 읽은 기록으로 센다 |
| 가장 긴 주기보다 오래 조용 | 예제 3의 분기 결산 | 「최근 30일」 기준은 드물게 도는 잡을 놓친다 |
| 롤백 가능 | 이 절에서 추가 | cutover가 되돌리기 제일 어려운 단계라, 그 *앞*에서 묻는다 |

특히 마지막 두 개가 이 장의 주장을 담고 있다.

- **수축 기준은 시간이 아니라 「가장 긴 배치 주기」다.** 분기 배치면 92일, 연말 정산이면 365일. 크론 표현식을 파싱해서 계산한다. 예제 3에서 「최근 30일 무사용」과 「모든 주체가 30일 이상 조용」은 *지워도 됨*이라고 답하지만, 정답은 *아직*이다. 분기 결산이 52일 전에 돌았고 아직 한 주기(92일)가 안 지났다.
- **`롤백_가능`을 조건에 넣은 것은 일부러다.** 옛 스키마가 아직 살아 있고 데이터가 최신이어야 되돌릴 수 있다.

## 5. 실무에 옮길 때

1. **관측값을 손으로 넣지 말고 긁어 온다.** `STATE`의 각 항목은 사람이 채우는 필드가 아니라 메트릭·쿼리·크론 파서의 출력이어야 한다. 손으로 넣는 순간 다시 문서로 돌아간다.
2. **CI에 태운다.** 게이트 스크립트를 파이프라인 잡으로 두면, 「다음 단계로 진행」 PR이 게이트 실패로 자동 차단된다.
3. **막힌 지점과 이유를 출력한다.** `blocked_at` + 실패한 조건 라벨을 찍는 것만으로 상황 공유 회의가 사라진다.
4. **수축은 되돌릴 수 있게 한다.** 바로 `DROP` 하지 말고 `이끔 → _deprecated_이끔`처럼 이름만 바꿔 한 주기 더 기다린 뒤 진짜로 지운다.
5. **드물게 도는 잡일수록 실패 알림을 세게 건다.** 매일 도는 건 내일 알지만, 2년에 한 번 도는 건 2년 뒤에 안다.

## 6. 한 줄로

> 마이그레이션 계획은 **읽는 문서**가 아니라 **실행되는 게이트**다. 조건을 술어 함수로 적고 관측값을 시스템에서 긁어 오면, 마이그레이션은 사람의 낙관을 타지 않는 상태 기계가 된다.
