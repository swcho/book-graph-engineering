# 되돌릴 수 있게 지우는 방법

**질문** — 되돌릴 수 있게 지우는 방법은 무엇인가?

**답** — 바로 DROP하지 않고 이름만 바꿔 두고(`이끔` → `_deprecated_이끔`) 한 주기 더 기다린 다음 진짜로 지운다.

---

## 1. 이 카드가 앉아 있는 자리

32장은 확장-수축(expand-contract)의 마지막 단계인 **수축**을 다룹니다. 예제 3(`ex3_when_to_contract.py`)의 결론은 두 겹입니다.

1. 「아무도 안 쓴다」의 기준은 *최근 30일*이 아니라 **가장 긴 배치 주기**다. 분기 결산이면 92일, 연말 정산이면 365일.
2. 그 기준을 채웠다고 해도 **곧바로 DROP하지 않는다**. 이름만 바꿔 두고 한 주기를 더 기다린다.

원문 그대로:

> 그리고 지울 때는 «되돌릴 수 있게» 지운다.
> 바로 DROP 하지 말고 이름만 바꿔 두고(이끔 → \_deprecated\_이끔)
> 한 주기 더 기다린 다음 진짜로 지운다.

즉 수축은 한 방이 아니라 **두 단계**입니다.

```
        ┌──────── 1주기 (예: 92일) ────────┐   ┌──── +1주기 ────┐
사용 0  │  이름 바꾸기(rename)             │   │  대기·관찰      │  DROP
────────┼──────────────────────────────────┼───┼────────────────┼──────▶
        ▲                                  ▲   ▲                ▲
      관측 시작                        되돌리기 가능 구간      진짜 삭제
                                     (역-rename 한 줄)
```

`ex5_migration_plan.py`의 `contract` 게이트가 이 첫 번째 대기를 강제합니다.

```python
"contract":   [("가장 긴 주기보다 오래 조용한가",
                lambda s: s["옛것_마지막_읽기_경과일"]
                          > s["가장_긴_주기_일"])],
```

그리고 `cutover` 게이트의 `("롤백이 가능한가", lambda s: s["롤백_가능"])`가 두 번째 대기가 존재하는 이유입니다. **rename 상태로 남아 있는 동안은 `롤백_가능`이 계속 True**입니다.

## 2. 왜 rename이 「되돌릴 수 있는 조작」인가

### 2.1 데이터가 그대로 남는다

DROP과 rename의 차이는 성격이 다른 두 연산이라는 데 있습니다.

| | DROP | RENAME |
|---|---|---|
| 데이터 페이지 | 해제·회수 | **손 안 댐** |
| 카탈로그(메타데이터) | 항목 제거 | 이름 문자열만 교체 |
| 소요 시간 | 크기 비례(또는 백그라운드 회수) | 대개 상수 시간 |
| 되돌리기 | 백업 복원 필요 | **역-rename 한 줄** |

DROP은 *파괴적*이고 rename은 *비파괴적*입니다. 값·행·엣지가 전부 살아 있고, 스키마 안의 라벨만 다른 문자열이 됩니다. 그래서 되돌리기가 **역방향 rename** 한 문장으로 끝납니다.

```sql
-- 지우기(1단계)
ALTER TABLE membership RENAME COLUMN 이끔 TO _deprecated_20260819_이끔;
-- 되돌리기: 완전한 역연산
ALTER TABLE membership RENAME COLUMN _deprecated_20260819_이끔 TO 이끔;
```

이 대칭성이 핵심입니다. rename은 **수학적으로 역원이 있는 조작**이고, DROP은 없습니다.

### 2.2 되돌리는 데 걸리는 시간이 다르다

사고가 났을 때 실제로 중요한 것은 「복구 가능성」이 아니라 **복구까지 걸리는 시간**입니다.

| 복구 수단 | 소요 | 데이터 손실 | 서비스 영향 |
|---|---|---|---|
| 역-rename | 초 단위 | 없음 | 없음(온라인) |
| 백업/PITR 복원 | 수십 분 ~ 수 시간 | 복원 시점 이후 쓰기 | 큼 |
| 백필 재실행 | 수 시간 ~ 며칠 | 원본이 없으면 불가 | 중간 |

새벽에 분기 결산이 깨졌을 때, 「백업에서 복원할 수 있습니다」와 「rename 되돌리면 됩니다」는 완전히 다른 세계입니다.

### 2.3 백업은 rename의 대체물이 아니다

여기서 자주 하는 오해를 짚어야 합니다. "DROP해도 백업 있으니까 괜찮다"가 성립하지 않는 이유는 **보존 기간의 길이**입니다.

- 전형적인 PITR(point-in-time recovery) 윈도가 7일, 길어야 35일.
- 그런데 우리가 기다려야 하는 기간은 **가장 긴 배치 주기**, 즉 92일 또는 365일.
- 연말 정산이 없어진 컬럼을 찾는 시점에, 그 컬럼이 살아 있던 백업은 **이미 만료돼 있습니다**.

게다가 논리 백업에서 컬럼 하나만 뽑아 되살리는 일은 절차상 별건 작업입니다. 그래서 **rename은 「보존 기간이 배치 주기만큼 긴, 온라인 백업」** 역할을 합니다. 반대로 말하면 rename 대기 기간을 백업 보존 기간으로 대체하려면 보존 기간을 최장 주기 이상으로 늘려야 하고, 그 비용이 rename보다 훨씬 큽니다.

## 3. 그러면서 「누락된 사용처를 시끄럽게 실패시킨다」

rename의 두 번째 효과가 실은 더 중요합니다. **rename은 안전장치이면서 동시에 탐지기**입니다.

### 3.1 조용한 실패 vs 시끄러운 실패

옛 이름을 정리하는 방법에는 여러 갈래가 있는데, 실패의 성격이 다릅니다.

| 방법 | 못 찾은 사용처가 만나는 것 | 성격 |
|---|---|---|
| 값만 안 쓰기 / NULL로 비우기 | `NULL`, 빈 결과 | **조용함** — 0원 정산서가 그대로 발송된다 |
| 옛 엣지만 삭제 | 0행 매치 | **조용함** — 조직도가 텅 빈 채 렌더된다 |
| 컬럼/테이블 rename | `column "이끔" does not exist` | **시끄러움** — 즉시 크래시 |
| DROP | 같은 에러 + 되돌릴 수 없음 | 시끄럽지만 위험 |

핵심은 **rename이 「조용히 틀린 답」을 「즉시 크래시」로 바꿔 준다**는 것입니다. 예제 4의 논지("어긋나는 것을 막는 게 아니라 아는 것이다")와 정확히 같은 사고방식입니다. 92일 뒤에 깨어난 분기 결산이 *에러로 죽으면* 우리가 알게 되고, *빈 값으로 성공하면* 잘못된 숫자가 회계로 흘러갑니다.

### 3.2 예제 3의 남은 구멍을 메운다

예제 3은 스스로 한계를 인정합니다.

> 크론에 없는 것(사람이 손으로 도는 것)은 못 잡는다.

`Reads` 엣지(29장)도, 크론 파싱도, 경고 로그도 전부 **관측된 것만** 잡습니다. 사람이 분기마다 손으로 돌리는 쿼리, 사내 BI 툴에 저장된 대시보드, 동적으로 문자열을 조립하는 쿼리는 다 빠져나갑니다. rename 대기 구간은 그 잔여 위험에 대한 마지막 그물입니다.

- 옛 이름을 쓰는 무언가가 남아 있었다면 → 대기 구간 안에 **에러로 스스로 신고**합니다.
- 그때 대응은 두 가지 중 하나: 역-rename으로 시간을 더 벌거나, 그 호출처만 새 이름으로 고칩니다.
- 대기 구간이 조용히 지나갔다면 → 그때는 관측 근거를 갖고 DROP합니다.

### 3.3 `_deprecated_` 접두어를 쓰는 이유

이름을 아무렇게나 바꾸지 않고 규약을 두는 데도 이유가 있습니다.

- **그렙 가능성** — `_deprecated_`로 스키마를 검색하면 "지워야 하는데 안 지운 것" 목록이 나옵니다.
- **시한 표시** — `_deprecated_20260819_이끔`처럼 날짜를 박으면 *언제 시계가 시작됐는지*가 스키마 자체에 적힙니다. 문서에 적으면 잊히고, 이름에 적으면 안 잊힙니다.
- **CI로 강제 가능** — "`_deprecated_` 객체가 시한(예: 날짜 + 최장 주기)을 넘겼는데 아직 살아 있으면 빌드 실패" 같은 검사를 넣을 수 있습니다. 32장의 「계획을 문서가 아니라 코드로」와 같은 취지입니다.
- **오탐 방지** — 새 코드가 실수로 옛 이름을 다시 잡는 일이 없습니다. `_deprecated_` 붙은 이름을 우연히 쓰는 코드는 없습니다.

주의: 식별자 길이 제한이 있습니다(PostgreSQL 63바이트, MySQL 64자). 접두어 + 날짜 + 한글(UTF-8에서 글자당 3바이트)을 붙이면 긴 이름은 잘려서 충돌할 수 있으니 미리 확인하세요.

## 4. 그래프 DB에서의 대응 조작

### 4.1 이 장의 예제 형태 — 관계의 「종류」가 속성일 때

`ex2_expand_contract.py`는 관계 이름을 `R` 테이블의 `kind` 속성으로 모델링했습니다.

```python
c.execute("MATCH (a:N)-[e:R {kind:'이끔'}]->(b:N) CREATE (a)-[:R {kind:'리드'}]->(b)")
...
c.execute("MATCH ()-[e:R {kind:'이끔'}]->() DELETE e")   # ← 이게 되돌릴 수 없는 DROP
```

마지막 줄이 바로 **바로 DROP하는** 형태입니다. 되돌릴 수 있게 하려면 삭제 대신 값을 바꿉니다.

```cypher
MATCH ()-[e:R {kind:'이끔'}]->() SET e.kind = '_deprecated_이끔'
```

되돌리기는 `'_deprecated_이끔'` → `'이끔'`. 엣지 자체가 남아 있으니 위상 구조가 온전합니다.

단 이 형태에서는 **실패가 조용합니다**. `MATCH ()-[e:R {kind:'이끔'}]->()`는 에러가 아니라 **0행**을 돌려줍니다. 그래서 값 기반 모델링에서는 rename만으로 「시끄러운 실패」가 생기지 않습니다. 보완책이 필요합니다.

- 옛 값을 읽는 코드 경로에 **경고 로그 + 알림**을 붙인다(예제 3이 권한 그것).
- 읽기 결과가 0행일 때 조용히 넘어가지 않고 실패하도록 애플리케이션 쪽에 단정(assertion)을 둔다.
- 또는 **관계 종류를 속성이 아니라 라벨/테이블로 승격**해서 스키마 수준의 이름이 되게 한다.

### 4.2 Kùzu — 스키마 수준 rename

Kùzu는 테이블·속성 이름을 DDL로 바꿀 수 있고, 없는 이름을 참조하면 **바인더 단계에서 에러**가 납니다. 즉 여기서는 rename이 진짜로 시끄럽게 실패합니다.

```sql
-- 관계 테이블 이름 바꾸기
ALTER TABLE 이끔 RENAME TO _deprecated_이끔;
-- 속성 이름 바꾸기
ALTER TABLE Person RENAME nickname TO _deprecated_nickname;
-- 한 주기 뒤 진짜 삭제
DROP TABLE _deprecated_이끔;
```

> 버전마다 DDL 지원 범위가 다릅니다. 실제 적용 전에 쓰는 버전의 `ALTER TABLE` 문서를 확인하세요.

### 4.3 Neo4j — 관계 타입 rename은 「메타데이터 변경」이 아니다

가장 주의할 지점입니다. Neo4j에는 관계 타입을 바꾸는 DDL이 없습니다. 관계 타입은 각 관계에 물려 있는 값이라, 바꾸려면 **관계를 다시 만들어야** 합니다.

```cypher
// APOC 사용
MATCH ()-[r:이끔]->()
CALL apoc.refactor.setType(r, '_deprecated_이끔') YIELD output RETURN count(*);

// 속성 이름은 그나마 가볍다
CALL apoc.refactor.rename.nodeProperty('nickname', '_deprecated_nickname');
```

여기서 파생되는 주의점:

- **상수 시간이 아니다.** 엣지 수만큼 쓰기가 일어나고 트랜잭션 로그가 부풀며, 큰 그래프에서는 배치로 쪼개야 합니다(`apoc.periodic.iterate`).
- **되돌리기도 같은 비용이 든다.** 역-rename이 「한 줄, 몇 초」가 아니라 또 한 번의 대량 쓰기입니다. 그래도 *데이터가 살아 있다*는 본질은 유지되므로 백업 복원보다는 여전히 훨씬 낫습니다.
- **엣지 ID가 바뀐다.** 관계를 재생성하는 방식이면 내부 ID가 바뀌므로, 엣지 ID를 외부에 저장해 참조하는 시스템이 있으면 깨집니다.
- **없는 타입 매치는 에러가 아니다.** Cypher에서 존재하지 않는 라벨/관계 타입을 매치하면 **경고(`UnknownRelationshipTypeWarning` / `UnknownLabelWarning`)와 함께 0행**을 돌려줍니다. 「시끄럽게 실패」를 진짜로 얻으려면 이 경고를 로그에서 잡아 알림으로 승격시켜야 합니다. 여기가 관계형과 갈리는 가장 큰 지점입니다.

### 4.4 인덱스·제약 (그래프)

- Neo4j의 인덱스/제약은 **(라벨, 속성명) 조합에 묶여** 있습니다. 속성 이름을 바꾸면 그 인덱스는 새 이름에 안 걸리고 사실상 죽은 인덱스가 됩니다. 새 이름으로 미리 인덱스를 만들어 두고(확장 단계에서), 옛 이름 인덱스는 rename 대기 구간 동안 **남겨 두세요**. 역-rename 시 인덱스가 필요합니다.
- 인덱스 없는 이름으로 대량 매치를 돌리면 풀스캔이 되어, 이행 검증 쿼리가 갑자기 느려집니다.
- **유일성/존재 제약**이 옛 속성에 걸려 있으면 확장 단계의 양쪽 쓰기가 제약에 막힐 수 있습니다. 제약은 rename 전에 정리하거나 새 속성 쪽으로 옮겨 두세요.
- Kùzu의 **기본 키(PRIMARY KEY)** 속성은 가볍게 바꿀 대상이 아닙니다. 키 자체를 바꾸는 일은 rename이 아니라 테이블 교체 수준의 작업으로 계획하세요.

## 5. 관계형에서의 대응 조작

### 5.1 컬럼·테이블 rename

```sql
-- PostgreSQL / MySQL 8.0+
ALTER TABLE membership RENAME COLUMN 이끔 TO _deprecated_20260819_이끔;
ALTER TABLE legacy_org  RENAME TO _deprecated_20260819_legacy_org;

-- 한 주기 뒤
ALTER TABLE membership DROP COLUMN _deprecated_20260819_이끔;
DROP TABLE _deprecated_20260819_legacy_org;
```

이쪽은 대개 **카탈로그의 이름 문자열만 바뀌는** 연산이라 테이블 재작성 없이 즉시 끝납니다. 대신 짧은 DDL 락이 필요하니 `lock_timeout`을 걸어 두고, 락을 못 얻으면 실패하고 재시도하게 만드세요(락 대기가 뒤따르는 쿼리를 전부 세워 버리는 사고가 흔합니다).

### 5.2 제약·인덱스가 따라오는가

| 항목 | PostgreSQL | MySQL |
|---|---|---|
| 컬럼의 인덱스/제약/기본값 | 컬럼을 따라감(내부 번호 참조) | 따라감 |
| 인덱스·제약의 **이름** | 자동으로 안 바뀜 → `idx_이끔`이 `_deprecated_이끔`을 가리키는 상태 | 같음 |
| 뷰가 옛 컬럼 참조 | **깨지지 않음.** 뷰는 파싱 시점에 컬럼 번호로 저장되므로 이름이 바뀌면 뷰도 조용히 따라감 | 뷰 정의가 텍스트라 **깨짐** |
| 함수/프로시저 안의 동적 SQL | 실행 시점에 에러 | 실행 시점에 에러 |

두 번째 줄은 위생 문제입니다. `ALTER INDEX ... RENAME TO`로 인덱스 이름도 같이 바꿔 두면 나중에 "이 인덱스가 왜 있지"를 안 겪습니다.

세 번째 줄은 **탐지 능력의 구멍**입니다. PostgreSQL에서는 뷰·머티리얼라이즈드 뷰가 rename을 조용히 따라가므로, 뷰를 통한 사용처는 rename으로 잡히지 않습니다. `pg_depend`를 조회해 옛 컬럼에 의존하는 뷰·함수를 별도로 목록화하세요.

### 5.3 NOT NULL과 기본값을 먼저 풀어야 한다

컬럼을 rename하면, **그 컬럼에 값을 안 넣는 새 코드의 INSERT가 제약 위반으로 실패**합니다.

- 옛 컬럼이 `NOT NULL`이고 기본값이 없으면 → 새 코드의 INSERT가 전부 죽습니다.
- 순서: ① `DROP NOT NULL`(또는 기본값 부여) → ② 양쪽 쓰기 종료 → ③ rename → ④ 대기 → ⑤ DROP.
- 옛 컬럼의 `UNIQUE` 제약도 마찬가지로, 남겨 두면 옛 값이 새 데이터와 충돌해 쓰기를 막을 수 있습니다.

### 5.4 남겨 둔 것의 비용과 회수 규칙

rename 상태는 무료가 아닙니다.

- 살아 있는 인덱스는 쓰기마다 유지 비용을 냅니다. 대기 구간 동안 옛 컬럼 인덱스를 **비활성/미사용 상태로 남길지, 유지할지**를 의식적으로 정하세요(역-rename 가능성 대비 vs 쓰기 성능).
- 스토리지와 백업 크기가 그만큼 큽니다.
- 무엇보다 **잊히면 영구 부채**가 됩니다. `_deprecated_` 묘지가 3년 치 쌓인 스키마를 만들지 않으려면, 이름에 날짜를 박고 시한 검사를 CI에 넣는 것이 필수입니다.

## 6. 정리 — 체크리스트

수축을 실행할 때의 순서입니다.

1. **관측**: 옛 이름 읽기 건수가 0인가. 기준은 30일이 아니라 **가장 긴 배치 주기**(크론 파싱으로 계산).
2. **마지막 한 달**: 옛 이름을 읽으면 경고 로그 + 알림. 드물게 도는 잡일수록 알림을 세게.
3. **제약 정리**: 옛 컬럼/속성의 `NOT NULL`·`UNIQUE`·기본값을 먼저 풀고, 새 이름 인덱스를 미리 만든다.
4. **rename**: `이끔` → `_deprecated_<날짜>_이끔`. 인덱스 이름도 같이. 락 타임아웃 설정.
5. **rename으로 안 잡히는 것 별도 조사**: 뷰(PostgreSQL), 라벨 미존재 경고(Neo4j), BI 저장 쿼리, 손으로 도는 쿼리.
6. **한 주기 더 대기**: 에러가 나오면 역-rename으로 되돌리거나 그 호출처만 고친다.
7. **DROP**: 조용히 지나갔으면 진짜로 지운다.

한 문장으로: **rename은 「데이터는 남기고 이름만 없애는」 조작이라, 되돌리기는 역-rename 한 번이면서 못 찾은 사용처는 즉시 실패로 스스로 신고하게 만든다.** 그래서 DROP 전에 반드시 한 주기가 들어간다.
