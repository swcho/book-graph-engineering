# 확장-수축: 읽기를 먼저, 쓰기를 나중에

**Q.** 확장-수축에서 읽기와 쓰기 중 무엇을 먼저 옮기는가?

**A.** 읽기를 먼저 옮기고 쓰기를 나중에 옮긴다. 거꾸로 하면 새 이름으로 쓴 데이터를 옛 코드가 못 읽는다.

---

## 1. 한 줄로 외우는 이유

> **쓰는 쪽이 새 이름을 만들기 전에, 읽는 쪽이 새 이름을 이해할 수 있어야 한다.**

새 이름으로 쓰인 데이터는 그 순간부터 시스템에 존재한다. 그런데 그 이름을 읽을 줄 아는 코드가 아직 배포되지 않았다면, 그 데이터는 「아무도 못 읽는 데이터」다. 반대 순서(읽기 먼저)에서는 최악의 경우가 「새 코드가 읽을 게 아직 없다」인데, 이건 조용히 빈 결과일 뿐이고 옛 경로가 여전히 정답을 주고 있다.

즉 두 순서의 실패 모드 값이 다르다.

| 순서 | 이행 중 최악의 상황 | 심각도 |
|---|---|---|
| **읽기 먼저 → 쓰기 나중** | 새 리더가 읽을 새 데이터가 아직 없다 (옛 경로로 폴백) | 낮음 — 복구 가능 |
| 쓰기 먼저 → 읽기 나중 | 새 이름으로 들어온 데이터를 옛 코드가 못 본다 → 유실·누락·틀린 집계 | 높음 — 조용히 틀린다 |

## 2. 32장 예제 2의 여섯 단계에서 확인

`code/ex2_expand_contract.py`는 「이끔 → 리드」 관계 이름 변경을 여섯 단계로 쪼개고, 각 단계에서 **옛 코드(`old_reader`, `이끔`만 안다)** 와 **새 코드(`new_reader`, `리드`만 안다)** 가 각각 동작하는지를 표로 찍는다.

| 단계 | 하는 일 | 옛 코드 | 새 코드 |
|---|---|---|---|
| 0. 시작 | 옛 이름만 존재 | 동작 | 안 됨 |
| 1. 확장 | 새 이름을 **같이** 쓴다 (copy) | 동작 | 동작 |
| 2. 새 코드 배포 | **읽기만** 새 이름으로 | 동작 | 동작 |
| 3. 쓰기를 새 이름으로 | 신규 쓰기를 `리드`로 | 동작 | 동작 |
| 4. 옛 코드 제거 | 옛 리더 철수 | (없음) | 동작 |
| 5. 수축 | 옛 이름 삭제 (`DELETE e`) | 안 됨 | 동작 |

핵심은 예제가 강조하는 **2단계와 3단계**다. 이 구간에서 옛 코드와 새 코드가 *둘 다* 동작한다. 그 겹치는 구간이 있어야 무중단 배포가 성립한다.

그리고 순서를 뒤집어 보면 표가 깨진다. 2단계(새 리더 배포)를 빼고 3단계(쓰기를 `리드`로)를 먼저 하면, `이끔`만 아는 `old_reader`는 새로 생긴 `이서연 → 결제팀` 관계를 **한 건도 못 본다**. 데이터는 DB에 멀쩡히 있는데 조직도·권한 계산·보고서 발송은 그 사람이 없는 것처럼 동작한다. 예외도 안 나고 로그도 안 남는다. 이게 이 카드가 말하는 「옛 코드가 못 읽는다」다.

예제의 결론부가 이 대비를 그대로 적어 둔다.

```
한 번에 바꾸면 어떻게 되나. 배포 순간에 둘 중 하나가 죽는다.
  DB 를 먼저 바꾸면 → 옛 코드가 죽는다
  코드를 먼저 바꾸면 → 새 코드가 죽는다

확장(expand) — 새것을 «더한다». 옛것은 그대로 둔다
이행(migrate) — 읽기를 옮기고, 그다음 쓰기를 옮긴다
수축(contract) — 아무도 안 쓰는 게 확인되면 옛것을 지운다

순서가 중요하다. «읽기 먼저, 쓰기 나중»이다.
거꾸로 하면 새 이름으로 쓴 데이터를 옛 코드가 못 읽는다.
```

## 3. 자주 걸리는 함정: "예제 5는 dual-write가 dual-read보다 먼저인데?"

`code/ex5_migration_plan.py`의 단계 목록은 이렇다.

```
expand → dual-write → backfill → dual-read → cutover → contract
```

여기서 `dual-write`가 `dual-read`보다 앞에 온다. 카드와 모순되는 것처럼 보이지만 아니다. 용어를 구분하면 풀린다.

- **양쪽 쓰기(dual-write)** 는 *확장*의 일부다. 새 이름에도 쓰지만 **옛 이름에도 계속 쓴다**. 옛 코드가 읽을 것이 그대로 있으므로 아무것도 깨지지 않는다. 이건 「쓰기를 옮긴 것」이 아니라 「쓰기를 더한 것」이다.
- **쓰기를 옮긴다**는 것은 *옛 이름에 쓰기를 끊는 것*(단일 쓰기 전환)이다. 이 시점부터 옛 이름은 낡아 간다. 그러니 이건 반드시 읽기 이행이 끝난 뒤여야 한다.

정리하면 안전한 큰 순서는 이렇다.

```
새것을 더한다(옛것 유지)            ← 아무것도 안 깨진다
  → 양쪽에 쓴다 + 백필              ← 새것을 옛것과 동등하게 채운다
    → 읽기를 새것으로 옮긴다        ← 읽기 먼저 (이 카드)
      → 옛 이름 쓰기를 끊는다       ← 쓰기 나중
        → 옛것을 지운다             ← 수축
```

「읽기 먼저, 쓰기 나중」의 정확한 뜻은 **읽는 쪽의 능력(capability)을 먼저 배포하고, 쓰는 쪽의 전환(cutover)을 나중에 한다**는 것이다. 프로토콜 호환성에서 흔히 말하는 *reader-first 배포*와 같은 원리다 — 새 필드를 내보내기 전에 그 필드를 이해하는 소비자를 먼저 깔아 둔다.

## 4. 읽기를 옮길 때의 실제 코드 모양

`code/ex4_dual_read.py`가 읽기 이행 구간의 전략 네 가지를 비교한다. 이행 중에는 데이터 상태가 뒤섞여 있다 — 일부는 옛 이름만, 일부는 둘 다, 일부는 새 이름만, 그리고 **둘 다 있는데 값이 다른 것**(`t3`: 옛 이름 김도현 / 새 이름 정하윤).

| 전략 | t3(불일치)에서 하는 일 | 불일치 감지 |
|---|---|---|
| 옛것만 읽기 | 조용히 김도현 선택 | 못 함 |
| 새것만 읽기 | 조용히 정하윤 선택 | 못 함 |
| 새것 없으면 옛것 | 조용히 정하윤 선택 | 못 함 |
| **둘 다 읽고 비교** | 정하윤 반환 + **「불일치」 신고** | 함 |

읽기를 옮기는 단계에서 곧바로 `new_only`로 가지 않고 `compare_both`로 가는 게 실무의 요령이다. 이유는 예제의 결론에 있다.

> 이행 중에는 데이터가 어긋난다. 안 어긋나는 이행은 없다. 중요한 건 어긋나는 것을 «막는» 게 아니라 «아는» 것이다.

그래서 `ex5`의 게이트가 `dual-read` 단계를 떠나는 조건으로 **불일치 건수 == 0**을 걸어 둔다(예제에서는 일부러 3건이 남아 있어 여기서 막힌다). 값은 읽기가 두 배 되는 것이고, 이행 구간에만 내는 값이라 감당할 수 있다.

## 5. 순서를 지켰는지 눈으로 확인하는 신호

`code/ex3_when_to_contract.py`의 「조직도 렌더」 사용량 곡선이 그 신호다.

```
1일: 1,200 → 7일: 1,180 → 14일: 30 → 21일: 0
```

읽기가 새 코드로 옮겨 가면 옛 이름의 읽기 건수가 이런 계단으로 떨어진다. 이 곡선이 보이면 읽기 이행이 진행되고 있는 것이고, 곡선이 안 떨어지는데 쓰기를 옮기면 그때부터 조용히 틀리기 시작한다.

참고로 이 예제는 여기서 한 걸음 더 나간다 — 읽기 건수가 0으로 떨어졌다고 바로 수축하면 안 된다. 「정산 배치」 옆에 **월말 마감(82일)** 과 **분기 결산(88일)** 이 숨어 있다. 수축 기준은 「최근 30일」이 아니라 **가장 긴 배치 주기**(분기면 92일, 연말 정산이면 365일)다. 이 카드의 범위는 아니지만, 「읽기 먼저」로 옮긴 뒤 「언제 지워도 되나」로 이어지는 같은 흐름의 다음 질문이다.

## 6. 요약 카드

- 옮기는 순서: **읽기(리더 배포) → 쓰기(옛 이름 쓰기 중단) → 수축(삭제)**
- 이유: 새 이름 데이터가 먼저 생기면 옛 리더에게는 **없는 데이터**가 된다. 예외 없이 조용히 틀린다.
- 반대로 리더를 먼저 배포하면 최악이 「읽을 새 데이터가 아직 없음」이라 옛 경로로 폴백된다.
- `dual-write`는 예외가 아니다 — 옛 이름에도 계속 쓰므로 「쓰기를 옮긴 것」이 아니라 「확장」이다.
- 읽기를 옮길 때는 `새것만 읽기`가 아니라 **`둘 다 읽고 비교`** 로 가서 불일치를 세고, 0이 될 때까지 다음으로 가지 않는다.
