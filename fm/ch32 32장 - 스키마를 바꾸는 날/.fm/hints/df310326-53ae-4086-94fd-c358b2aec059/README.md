# 이행 중 데이터 불일치에 대한 32장의 입장

## 질문

이행 중 데이터 불일치에 대한 32장의 입장은 무엇인가?

## 답

**안 어긋나는 이행은 없다. 막으려 하지 말고 세야 하며, 불일치가 0이 될 때까지 수축하지 않는다.**

---

## 한 줄로 요약된 입장

> 이행 중에는 데이터가 어긋난다. 안 어긋나는 이행은 없다.
> 중요한 건 어긋나는 것을 «막는» 게 아니라 «아는» 것이다.
> — 32.4 「이행 중에 데이터가 어긋난다」 (`ex4_dual_read.py`)

이 문장이 32장의 입장 전체다. 세 조각으로 나눠 보면:

| 조각 | 뜻 | 실무 귀결 |
|---|---|---|
| 안 어긋나는 이행은 없다 | 불일치는 사고가 아니라 **이행의 정상 상태** | 「우리는 안 어긋나게 하겠다」는 계획은 애초에 틀린 계획 |
| 막지 말고 세라 | 예방이 아니라 **관측**에 투자한다 | 둘 다 읽고 비교 → 불일치를 지표(metric)로 만든다 |
| 0이 될 때까지 수축하지 않는다 | 불일치 건수를 **게이트**로 쓴다 | `dual-read` 단계를 떠나는 조건이 「불일치 == 0」 |

---

## 왜 어긋나는가 (32장이 드는 세 가지 이유)

이행 구간에는 옛 스키마와 새 스키마가 동시에 살아 있다. 그 사이에서 값이 갈라지는 경로는 크게 셋이다.

1. **양쪽 쓰기(dual write) 코드의 버그** — 한쪽만 쓰고 넘어간다.
2. **옛 코드가 아직 살아 있다** — 그 코드는 옛 이름만 알고, 그것만 고친다.
3. **백필과 실시간 쓰기의 경합** — 배치가 옛것 → 새것을 복사하는 도중에 누가 옛것을 고친다.

핵심은 이 셋 모두 **분산 시스템에서 원자적으로 막을 수 없다는** 것이다. 두 저장 위치에 걸친 쓰기를 트랜잭션 하나로 묶을 수 없으니, "절대 어긋나지 않는 이행"은 설계로 달성할 수 있는 목표가 아니다. 그래서 32장은 목표를 예방에서 **탐지**로 옮긴다.

## 예제 4가 실제로 보여주는 것

`ex4_dual_read.py`는 이행 중 데이터 상태를 다섯 행으로 놓는다.

| 키 | 옛 이름 | 새 이름 | 상황 |
|---|---|---|---|
| t1 | 박민수 | - | 옛것만 |
| t2 | 이서연 | 이서연 | 둘 다 · 같음 |
| t3 | 김도현 | 정하윤 | **둘 다 · 다름 → 어긋났다** |
| t4 | - | 최유진 | 새것만 |
| t5 | - | - | 둘 다 없음 |

그리고 읽기 전략 넷을 같은 데이터에 통과시킨다.

| 전략 | t3에서 하는 일 | 문제 감지 |
|---|---|---|
| 옛것만 읽기 | 김도현을 조용히 고른다 | 0건 |
| 새것만 읽기 | 정하윤을 조용히 고른다 | 0건 |
| 새것 없으면 옛것 (fallback) | 정하윤을 조용히 고른다 | 0건 |
| **둘 다 읽고 비교** | 값은 새것을 쓰고 **「불일치」를 신고한다** | 신고함 |

앞의 세 전략이 위험한 이유는 **틀렸기 때문이 아니라 조용하기 때문**이다. 셋 다 t3에서 값 하나를 고르는데, 그게 맞았는지 틀렸는지 아무도 모른다. 네 번째만 "여기 문제가 있다"고 말한다.

```python
def compare_both(old, new):
    """둘 다 읽고 «다르면» 신고한다."""
    if old is not None and new is not None and old != new:
        return new, "불일치"
    if old is None and new is None:
        return None, "둘 다 없음"
    return (new if new is not None else old), None
```

주목할 점: 이 함수는 불일치를 만나도 **예외를 던지지 않는다**. 값은 정상적으로 반환하고(새것 우선) 플래그만 함께 낸다. 즉 서비스를 멈추는 방어가 아니라, 계속 돌면서 세는 계측기다. 그게 "막는 게 아니라 아는 것"의 코드 형태다.

## 실무 운용 세 줄

32장이 그대로 적어 둔 절차다.

```
이행 구간 동안 «둘 다 읽고 비교»로 돌린다
불일치를 지표로 세고, 0 이 될 때까지 수축하지 않는다
불일치가 나오면 그 키만 따로 고친다
```

- **전수 비교가 아니라 읽는 길에 끼워 넣는다.** 별도 정합성 배치를 돌리는 게 아니라 실제 읽기 경로에서 비교하므로, 트래픽이 실제로 닿는 데이터가 우선 검증된다.
- **고칠 때는 키 단위로 고친다.** 전체 재백필이 아니라 신고된 키만 손본다. 백필이 멱등하게 설계돼 있으니(32장 요약: "백필은 쪼개서 돌리고, 어디까지 했는지 남기고, 멱등하게") 부분 재실행이 안전하다.
- **불일치 건수가 0으로 수렴하는 곡선 자체가 이행의 진척도**다. 예제 3의 「조직도 렌더 1,200 → 1,180 → 30 → 0」 곡선과 같은 종류의 신호다.

### 값(cost)에 대한 32장의 태도

> 값은 읽기가 두 배가 되는 것이다. 이행 구간에만 내는 값이라 괜찮다.
> 그리고 이 값을 안 내면, 수축한 뒤에 «조용히 틀린 데이터»가 남는다.

읽기 2배는 영구 비용이 아니라 **한시적 보험료**다. 안 내면 대가는 지연되어 나타나고, 그때는 대조할 옛 스키마가 이미 사라져 있어서 복구가 불가능하다. 이게 "0이 될 때까지 수축하지 않는다"의 진짜 이유다 — 수축(옛 스키마 삭제)은 **비교 대상을 없애는 행위**이므로, 그 이후의 불일치는 발견할 방법조차 없다.

## 「0이 될 때까지 수축하지 않는다」가 게이트가 되는 자리

예제 5는 이 입장을 문서가 아니라 **코드로 된 게이트**로 굳힌다.

```python
GATES = {
    "expand":     [("새 스키마가 있나", lambda s: s["새_스키마_존재"])],
    "dual-write": [("양쪽 쓰기가 100%인가", lambda s: s["양쪽_쓰기_비율"] >= 1.0)],
    "backfill":   [("백필이 끝났나", lambda s: s["백필_진행률"] >= 1.0)],
    "dual-read":  [("불일치가 0인가", lambda s: s["불일치_건수"] == 0)],   # ← 여기
    "cutover":    [("옛것 읽기가 0인가", ...), ("롤백이 가능한가", ...)],
    "contract":   [("가장 긴 주기보다 오래 조용한가", ...)],
}
```

`STATE["불일치_건수"] = 3`이므로 예제 5는 **일부러 `dual-read`에서 막힌다.** 0으로 바꾸면 다음 단계로 넘어간다.

여섯 단계와 불일치 게이트의 위치:

```
expand → dual-write → backfill → [dual-read] → cutover → contract
                                      ↑
                              불일치 == 0 이어야 통과
```

즉 불일치 0은 **수축(contract)의 직전 조건이 아니라 그보다 앞선 관문**이다. 불일치가 남아 있으면 cutover도, contract도 시작조차 못 한다. 32장의 표현대로:

> 계획을 문서로 적으면 「지금 어디쯤인가」를 사람이 판단하게 된다.
> 그리고 사람은 「대충 된 것 같은데」로 다음 단계로 넘어간다.
> 조건을 코드로 적으면 «넘어갈 수 없다». 불일치 3건이 남아 있으면 막힌다.
> (…) 상태 기계는 사람의 낙관을 안 탄다.

여기서 "막으려 하지 말고 세라"의 두 번째 층이 드러난다. 세어 둔 숫자가 단순한 대시보드 장식이 아니라 **CI가 읽는 값**이 되어야 비로소 입장이 강제된다.

## 흔한 오해 정리

| 오해 | 32장의 답 |
|---|---|
| 이행을 잘 설계하면 불일치를 0으로 유지할 수 있다 | 없다. 안 어긋나는 이행은 없다. 전제를 바꿔야 한다 |
| 불일치를 만나면 요청을 실패시켜야 한다 | 아니다. 값은 반환하고(새것 우선) 플래그만 낸다. 서비스를 멈추는 방어가 아니다 |
| fallback(새것 없으면 옛것)만 써도 안전하다 | t3처럼 둘 다 있지만 다른 경우를 조용히 통과시킨다. 최악의 실패 양식 |
| 불일치는 나중에 정합성 배치로 잡으면 된다 | 수축 후에는 대조할 옛 스키마가 없다. 이행 구간 안에서만 잡을 수 있다 |
| 불일치가 며칠째 0이면 수축해도 된다 | 불일치 0은 `dual-read` 통과 조건일 뿐. 수축은 별도로 「가장 긴 배치 주기」를 넘겨야 한다 (분기 배치 92일, 연말 정산 365일) |

## 연결

- **31장**: 스키마가 그대로인 상태에서 같은 필드를 두고 다투는 동시성 문제. 32장은 필드 자체가 바뀌는 경우.
- **29장 `Reads` 엣지**: "누가 이 필드를 읽나"를 실제 실행 기록으로 답한다. 코드 검색으로는 동적 쿼리를 못 잡는다.
- **확장-수축(expand and contract)**: Martin Fowler의 [ParallelChange](https://martinfowler.com/bliki/ParallelChange.html). 이 카드가 다루는 불일치 계측은 그 패턴에서 "이행(migrate)" 구간의 안전장치에 해당한다.
