# 「단일값 → 다중값」 변경은 왜 조건부인가

## 카드

**질문**: 「단일값 → 다중값」 변경이 조건부로 분류되는 이유는 무엇인가?

**답**: 읽는 쪽이 값 한 개를 기대하면 깨진다. 읽는 코드의 가정에 달렸다.

---

## 어디서 나온 이야기인가

32장 예제 1(`ex1_breaking_change.py`)은 스키마 변경 여덟 가지를 「깨짐 / 안 깨짐」으로 판정합니다. 그중 딱 하나만 세 번째 판정을 받습니다.

| 변경 | 예 | 판정 | 이유 |
|---|---|---|---|
| 관계 이름 바꾸기 | 이끔 → 리드 | 깨짐 | 쿼리가 못 찾는다 |
| 속성 추가 | `Person.email` 추가 | 안 깨짐 | 옛 코드는 그냥 무시한다 |
| 속성 제거 | `Person.nickname` 제거 | 깨짐 | 읽던 코드가 죽는다 |
| 속성 타입 변경 | 인원 `STRING → INT64` | 깨짐 | 파싱이 달라진다 |
| 필수 속성 추가 | `Team.owner` 필수 | 깨짐 | 기존 노드에 값이 없다 |
| 관계 방향 뒤집기 | 속함 방향 반전 | 깨짐 | 순회가 전부 어긋난다 |
| 새 노드 종류 추가 | `Project` 추가 | 안 깨짐 | 안 쓰면 없는 것과 같다 |
| **단일값 → 다중값** | **이끔을 여러 개 허용** | **조건부** | **읽는 쪽이 한 개를 기대하면 깨짐** |

「조건부」는 애매해서 붙은 라벨이 아닙니다. **DB 스키마만 보고는 판정할 수 없다**는 사실을 정직하게 적은 것입니다. 이 변경의 깨짐 여부는 스키마가 아니라 읽는 코드 안에 있습니다.

## 핵심 논리: 카디널리티 완화는 스키마 쪽에서는 「더하는 변경」이다

「이끔을 하나만」에서 「이끔을 여러 개 허용」으로 가는 건 제약을 **푸는** 방향입니다.

- 기존 데이터는 하나도 안 바뀝니다. 이미 있던 노드는 여전히 이끔이 1개입니다.
- 저장 계층은 아무것도 잃지 않습니다. `max cardinality 1 → n`은 값 집합이 넓어지는 것뿐입니다.
- 그래프 DB(Kùzu, Neo4j 등)에서는 애초에 관계를 여러 개 만드는 걸 막는 장치가 없는 경우도 많습니다. 「하나만」이라는 규칙이 스키마가 아니라 **관행**으로만 존재했을 수도 있습니다.

그래서 마이그레이션을 돌리는 순간에는 아무도 안 죽습니다. 32장의 다른 「깨짐」들과 다른 점이 여기입니다. `nickname`을 지우면 그 즉시 읽던 코드가 죽고, 타입을 `STRING → INT64`로 바꾸면 그 즉시 파싱이 달라집니다. 카디널리티 완화는 **두 번째 값이 실제로 들어오는 순간까지 잠복**합니다.

즉 판정은 이렇게 갈립니다.

- 읽는 쪽이 「0개 이상」을 다루도록 쓰여 있다 → **안 깨짐**
- 읽는 쪽이 「정확히 1개」를 가정하고 쓰여 있다 → **깨짐**. 그리고 배포 시점이 아니라 다중값 데이터가 처음 들어온 날 깨진다

31장·32장이 반복해서 말하는 문장이 이걸 요약합니다. 위험은 스키마가 아니라 **「그 스키마를 어떻게 읽고 있느냐」**에 있습니다.

## 읽는 쪽이 「하나」를 기대하는 구체적 실패 패턴

### 1) 스칼라 언패킹 — 결과가 2행이 되는 순간 예외

```python
# 읽는 쪽 옛 코드: 이끔은 하나라고 믿는다
r = c.execute("MATCH (p:N)-[:R {kind:'이끔'}]->(t:N {name:$team}) RETURN p.name",
              {"team": "결제팀"})
(leader,) = r.get_next()          # 행 하나에 열 하나 — 여기는 괜찮다
```

문제는 「이끔이 여러 개일 수 있다」로 바뀐 뒤입니다.

```python
# 다중값이 되면
rows = []
while r.has_next():
    rows.append(r.get_next()[0])

leader, = rows                    # ValueError: too many values to unpack
                                  # (expected 1, got 2)
```

같은 계열의 흔한 형태들입니다.

```python
leader = rows[0]                  # 조용히 「아무거나 하나」를 고른다 (더 나쁨)
leader = one(rows)                # sqlalchemy .one() → MultipleResultsFound
leader = qs.get(team="결제팀")     # Django → MultipleObjectsReturned
```

두 번째 줄이 특히 고약합니다. **예외도 안 나고 값만 틀립니다.** 정렬 순서에 따라 어떤 이끔이 뽑히는지가 매번 달라질 수 있고, 예제 4의 「앞의 세 전략은 t3에서 그냥 하나를 고른다. 조용히.」와 정확히 같은 병입니다.

### 2) 단일 결과 인덱싱 / 스칼라 필드 접근

```python
# JSON API 응답을 소비하는 쪽
team = fetch_team("결제팀")

send_mail(to=team["leader"]["email"])     # leader 가 dict → list 로 바뀌면
                                          # TypeError: list indices must be
                                          # integers or slices, not str
```

스키마를 다중값으로 바꾸면 직렬화 모양이 `{"leader": {...}}`에서 `{"leaders": [{...}]}`(또는 `{"leader": [{...}]}`)로 바뀝니다. 이 순간 **필드 이름·필드 타입이 동시에 바뀌는 파괴적 변경**이 되어 버립니다. 그래서 실무에서는 카디널리티 완화를 표현할 때 옛 스칼라 필드를 남긴 채 새 배열 필드를 더하는 「확장」을 씁니다.

```python
# 확장 구간의 응답 — 옛 코드도, 새 코드도 산다
{
  "leader":  {"id": "u1"},        # deprecated. 항상 leaders[0]. 옛 코드용
  "leaders": [{"id": "u1"}, {"id": "u2"}]
}
```

### 3) 스키마 검증 실패 — 소비자 쪽 계약이 먼저 터진다

Protobuf, Avro, JSON Schema, SHACL 같은 곳에서는 카디널리티가 **명시적 계약**이라, 데이터가 계약을 위반하는 형태로 도착하면 검증 단계에서 거부됩니다.

```python
# JSON Schema — 옛 소비자의 계약
{"properties": {"leader": {"type": "object"}}}
# 새 데이터: "leader": [{...}, {...}]
#   → ValidationError: [{...},{...}] is not of type 'object'
```

```protobuf
// proto3 — optional → repeated 는 와이어 호환이 아니다
message Team {
  Person leader = 3;             // 옛 정의
  // repeated Person leader = 3; // 새 정의: 옛 클라이언트는 마지막 하나만 본다
}
```

```turtle
# SHACL — 32장 키워드 표에 있는 제약 검증
ex:TeamShape a sh:NodeShape ;
  sh:targetClass ex:Team ;
  sh:property [ sh:path ex:leads ; sh:maxCount 1 ] .   # 이 줄을 안 풀면
                                                        # 새 데이터가 위반으로 잡힌다
```

Avro의 스키마 해석 규칙도 마찬가지입니다. 단일 레코드 필드와 배열 필드는 서로 승격되지 않으므로, 옛 리더(reader) 스키마로 새 데이터를 읽으면 해석에 실패합니다.

### 4) 그래프 순회에서의 조용한 배수 폭발

이끔이 여러 개가 되면 순회 결과 **행 수가 곱**해집니다.

```cypher
MATCH (p:Person)-[:이끔]->(t:Team)-[:속함]->(d:Div)
RETURN p.name, d.name
```

이끔이 1:1일 때 팀당 1행이던 것이 팀당 N행이 됩니다. 그 결과가

- 보고서 발송이면 → 같은 메일이 N통
- 권한 계산이면 → 권한이 과다 부여될 수 있음
- 정산 배치의 집계면 → **금액이 N배**

로 이어집니다. 예외가 안 나므로 테스트도 통과하고 모니터링도 조용합니다. 그래서 이 계열이 가장 무섭습니다.

## 그래서 판정을 어떻게 내리나 — 「읽는 쪽을 센다」

32장의 처방은 「조건부니까 알아서 판단하세요」가 아닙니다. **조건을 측정하라**는 것입니다. 예제 1이 29장의 `Reads` 엣지를 다시 꺼내 쓰는 이유가 여기입니다.

```python
USAGE = {
    "이끔":      ["보고서 발송", "조직도 렌더", "권한 계산", "알림 라우팅"],   # 4개
    "속함":      ["보고서 발송", "조직도 렌더", "권한 계산", "정산 배치",
                 "온보딩", "감사 리포트"],                                # 6개
    "nickname": ["인사말 생성"],                                          # 1개
    "인원":      ["정산 배치", "대시보드"],                                # 2개
}
```

```python
def readers(c, field):
    r = c.execute("MATCH (run:Run)-[:Reads]->(e:Entity {id:$f}) "
                  "RETURN run.wf ORDER BY run.wf", {"f": field})
    ...
```

「이끔」을 단일값에서 다중값으로 바꾼다면, 판정해야 할 대상은 **그 4개 실행이 각각 값을 하나로 가정하는지**입니다. 넷 다 리스트로 다루면 안 깨짐, 하나라도 언패킹/인덱싱/집계 가정을 갖고 있으면 깨짐입니다.

`Reads` 엣지가 필요한 이유도 이 카드와 직결됩니다. 「이 필드를 누가 쓰는지」를 코드 검색으로 찾으려 하면 **동적으로 조립한 쿼리는 grep에 안 걸립니다.** 반면 `Reads`는 실제로 읽은 기록이라 검색에 안 걸리는 소비자도 잡힙니다. 조건부 변경의 조건을 확인하려면 소비자 목록이 완전해야 하는데, 정적 검색으로는 그 완전성을 보장할 수 없습니다.

예제 1의 결론이 그대로 적용됩니다.

1. 바꾸려는 필드를 **누가 읽는지** 센다
2. 그 수가 1~2면 그냥 바꾼다
3. 여섯이면 **확장-수축**으로 간다

## 조건부 변경을 안전하게 굴리는 순서

「깨짐」으로 판정되면 예제 2의 확장-수축을 그대로 씁니다. 카디널리티 완화에 대입하면 이렇습니다.

| 단계 | 카디널리티 완화에 대입 |
|---|---|
| 확장 | 다중값 표현(`leaders` 배열 / `maxCount` 완화)을 **더한다**. 단일값 필드는 그대로 둔다 |
| 읽기 이행 | 소비자를 하나씩 「0개 이상」을 다루는 코드로 고친다. **읽기 먼저, 쓰기 나중** |
| 쓰기 이행 | 실제로 두 번째 값을 쓰기 시작한다. 여기가 옛 가정이 처음 깨지는 지점이다 |
| 검증 | 예제 4의 「둘 다 읽고 비교」로 불일치를 센다. 0이 될 때까지 수축하지 않는다 |
| 수축 | 단일값 필드/제약을 지운다. 기준은 「최근 30일」이 아니라 **가장 긴 배치 주기** |

특히 **읽기 먼저, 쓰기 나중**이 이 변경에서 결정적입니다. 순서를 거꾸로 해서 두 번째 값을 먼저 쓰면, 아직 안 고친 소비자들이 그 순간 일제히 깨집니다. 반대로 읽기를 먼저 옮겨 두면 다중값 데이터가 없는 동안에도 새 코드가 잘 돌아갑니다(리스트 길이가 1일 뿐).

한 가지 더. 이 변경은 **드물게 도는 잡에서 늦게 터집니다.** 예제 3의 분기 결산처럼 92일마다 도는 배치가 `(leader,) = rows`를 갖고 있으면, 다중값 데이터가 들어온 지 두 달 뒤에 처음 실패합니다. 그래서 32장은 「드물게 도는 잡일수록 실패 알림을 세게 걸라」고 합니다.

## 한 문장으로

「단일값 → 다중값」은 **쓰는 쪽에서는 제약을 푸는 안전한 변경이지만, 읽는 쪽에서는 값이 하나라는 가정을 깨는 변경**입니다. 그 가정이 어디에 몇 개 있는지는 스키마에 안 적혀 있으니, 판정을 스키마 안에서 내릴 수가 없습니다. 그래서 「조건부」이고, 그 조건을 세는 도구가 29장의 `Reads` 엣지입니다.
