# cutover 앞에 「롤백 가능」 조건을 둔 이유

**질문** — cutover 앞에 '롤백 가능' 조건을 둔 이유는 무엇인가?

**답** — cutover가 되돌리기 가장 어려운 단계이기 때문이다. 옛 스키마가 살아 있고 데이터가 최신이면 되돌릴 수 있다.

---

## 1. 어디서 나온 조건인가

32.5절 `ex5_migration_plan.py`는 마이그레이션 여섯 단계를 각 단계를 **떠나기 위한 게이트**로 적는다. 게이트는 대체로 단계당 하나인데, `cutover`만 **둘**이다.

```python
GATES = {
    "expand":     [("새 스키마가 있나", lambda s: s["새_스키마_존재"])],
    "dual-write": [("양쪽 쓰기가 100%인가", lambda s: s["양쪽_쓰기_비율"] >= 1.0)],
    "backfill":   [("백필이 끝났나", lambda s: s["백필_진행률"] >= 1.0)],
    "dual-read":  [("불일치가 0인가", lambda s: s["불일치_건수"] == 0)],
    "cutover":    [("옛것 읽기가 0인가", lambda s: s["옛것_읽기_건수_최근"] == 0),
                   ("롤백이 가능한가",   lambda s: s["롤백_가능"])],      # ← 이것
    "contract":   [("가장 긴 주기보다 오래 조용한가",
                    lambda s: s["옛것_마지막_읽기_경과일"] > s["가장_긴_주기_일"])],
}
```

본문의 설명은 이렇다.

> 한 가지 더. «롤백 가능»을 조건에 넣은 게 일부러다.
> cutover 는 되돌리기 제일 어려운 단계라, 그 앞에서 «되돌릴 수 있나»를 묻는다.
> 옛 스키마가 아직 살아 있고 데이터가 최신이면 되돌릴 수 있다.

즉 이 조건은 **기능적 조건이 아니라 안전 조건**이다. 나머지 다섯 게이트는 "다음 단계를 할 준비가 됐나"를 묻고, 이 게이트만 "실패했을 때 돌아올 길이 있나"를 묻는다.

## 2. 왜 cutover가 되돌리기 제일 어려운가 — 단계별 가역성 비교

되돌리기 난이도는 **그 단계가 무엇을 바꿨는가**로 결정된다. 되돌릴 대상이 *코드/설정*이면 쉽고, *데이터*면 어렵고, *데이터가 사라졌으면* 불가능하다.

| 단계 | 하는 일 | 되돌리려면 | 가역성 | 왜 그런가 |
|---|---|---|---|---|
| `expand` | 새 스키마를 더한다 | 새 테이블·컬럼을 드롭 | **매우 쉬움** | 아무도 새것을 안 읽는다. 더한 것만 지우면 원상복구 |
| `dual-write` | 쓰기를 양쪽에 한다 | 새 스키마 쓰기를 끈다 | **쉬움** | 옛 스키마가 계속 정본(source of truth). 새것만 정지시키면 끝 |
| `backfill` | 옛 데이터를 새 스키마로 복사 | 복사한 것을 버린다 | **쉬움** | 멱등하게 짰다면 재실행/폐기 모두 안전. 옛 데이터는 손 안 댐 |
| `dual-read` | 읽기를 둘 다 하고 비교 | 비교 코드를 끈다 | **쉬움** | 읽기만 늘렸다. 쓰기 경로는 그대로 |
| **`cutover`** | **읽기를 새것으로. 옛것은 검증용** | **정본을 옛것으로 되돌린다** | **어려움** | 여기서 처음으로 **정본이 옮겨간다**. 되돌리면 cutover 이후에 새것에만 반영된 변경을 회수해야 한다 |
| `contract` | 옛 스키마 삭제 | (없음) | **불가능** | 옛 데이터가 물리적으로 사라졌다. 백업 복원은 롤백이 아니라 재해복구다 |

`contract`가 더 비가역인 건 맞다. 그런데 게이트를 `cutover` 앞에 둔 이유는 따로 있다.

- `contract`는 **되돌릴 필요가 있는지 미리 알 수 있는 단계**다. "가장 긴 주기보다 오래 조용한가"라는 조건 자체가 롤백 필요성을 없애는 장치다. 조용함이 확인되고 나서 지운다.
- `cutover`는 **되돌릴 필요가 생기는 단계**다. 새 스키마로 읽기를 넘긴 순간에야 실제 트래픽·실제 쿼리 플랜·실제 엣지 케이스가 새 경로를 때린다. 실패는 여기서 터진다. `expand`~`dual-read`까지는 옛 경로가 정본이라 실패해도 사용자가 못 느끼는데, cutover는 실패가 곧 장애다.

정리하면 **가장 위험한 단계이면서 되돌리기 비용이 처음으로 비싸지는 단계**라서, 실행 전에 탈출 경로를 강제로 확인시키는 것이다. 소방 훈련을 불이 난 뒤에 하지 않는 것과 같다.

## 3. 「롤백 가능」을 코드로 검사하려면 무엇을 확인해야 하나

예제의 `STATE["롤백_가능"]`은 그냥 `True`로 박혀 있는 플레이스홀더다. 실무에서는 이 불리언을 **사람이 손으로 채우면 안 된다** — 그 순간 예제 5의 논지("사람은 「대충 된 것 같은데」로 넘어간다")가 무너진다. 관측값으로 계산해야 한다. 확인할 축은 셋이다.

### (1) 옛 스키마가 아직 존재하나 — 돌아갈 곳

- 옛 노드 테이블/렐 테이블/속성이 **드롭되지 않았는지** 카탈로그로 확인한다. 32.3절이 권하는 `이끔 → _deprecated_이끔` 이름 변경 방식을 썼다면, 이름만 바뀐 상태도 "살아 있음"으로 인정할지 아니면 옛 코드가 못 찾으니 "죽음"으로 볼지를 정해야 한다. 옛 코드를 그대로 되돌린다면 **이름 변경도 롤백을 깨뜨린다**.
- 옛 스키마를 읽던 코드 경로가 아직 배포본에 남아 있는지도 같이 본다. 예제 2의 6단계 중 4단계("옛 코드 제거")를 이미 지났으면, 스키마는 있어도 롤백 대상 코드가 없다. 스키마 존재와 리더 존재는 별개 조건이다.

```python
def old_schema_alive(s):
    return (s["옛_테이블_존재"]                     # 카탈로그에 있다
            and not s["옛_이름_deprecated_치환됨"]   # 이름도 그대로
            and s["옛_리더_코드_배포중"])            # 되돌릴 코드가 있다
```

### (2) 옛 데이터가 최신인가 — 돌아가서 쓸 수 있는 데이터인가

이게 핵심이다. 옛 스키마가 텅 껍데기로 남아 있으면 롤백해도 데이터가 과거로 되돌아간다. "최신"은 실질적으로 **여전히 양쪽으로 쓰고 있는가**를 뜻한다.

- `양쪽_쓰기_비율 >= 1.0`이 **cutover 시점에도 유지되고 있는지**. `dual-write` 게이트를 한 번 통과했다는 사실만으로는 부족하다. 그 사이에 누군가 "이제 새것만 쓰면 되지 않나" 하고 옛 쓰기를 껐을 수 있다. 게이트는 과거 기록이 아니라 **현재 관측값**을 봐야 한다.
- 옛 스키마의 **마지막 쓰기 시각과 현재 시각의 차이(쓰기 지연, write lag)**. 양쪽 쓰기가 비동기 파이프라인이면 비율 100%여도 몇 분 뒤처져 있다. 그 지연이 곧 롤백 시 유실 구간이다.
- 옛것과 새것의 **불일치 건수가 0인지**. `dual-read` 게이트와 겹치지만 의미가 다르다. 거기서는 "새 경로를 믿어도 되나"를 물었고, 여기서는 "옛 경로로 돌아가도 되나"를 묻는다. 불일치가 있으면 어느 쪽으로 가도 틀린 데이터를 만난다.

```python
def old_data_fresh(s):
    return (s["양쪽_쓰기_비율"] >= 1.0            # 지금도 양쪽에 쓴다
            and s["옛것_쓰기_지연_초"] <= 60       # 뒤처짐이 허용치 안
            and s["불일치_건수"] == 0)             # 두 스키마가 같다
```

### (3) 되돌릴 때의 유실 구간은 얼마인가 — 돌아가는 비용

롤백은 "스위치를 뒤로 젖히는 것"이 아니다. cutover 이후 새 스키마에만 반영된 변경이 있으면, 옛 스키마로 되돌아가는 순간 그 변경이 **사라진다**. 그래서 롤백 가능성은 예/아니오가 아니라 **유실 구간의 크기**로 표현해야 한다.

- 유실 구간(≈ 복구 지점 목표, RPO) = `cutover 이후 경과 시간` × `옛 스키마에 안 써진 쓰기 비율` + `옛것_쓰기_지연`.
- 양쪽 쓰기가 진짜 100%면 이 값이 사실상 0이다. 그래서 (2)의 조건이 (3)을 흡수한다. 반대로 양쪽 쓰기가 99%면, cutover 후 한 시간이면 한 시간 분량의 1%가 옛 스키마에 없다. 이건 롤백해도 조용히 틀린 데이터가 남는 상황 — 예제 4가 경고한 그 상태다.
- 실무에서는 **롤백 리허설**을 게이트에 넣는 게 가장 정직하다. 스테이징에서 실제로 뒤로 젖혀 보고, 소요 시간과 유실 건수를 관측값으로 기록한다. "롤백 가능"은 그 리허설이 최근에 성공했다는 사실의 별칭이 된다.

```python
def rollback_possible(s):
    return (old_schema_alive(s)
            and old_data_fresh(s)
            and s["예상_유실_건수"] == 0
            and s["롤백_리허설_경과일"] <= 7        # 최근에 실제로 해 봤다
            and s["롤백_소요_분"] <= s["허용_장애_시간_분"])
```

플래그 하나를 이렇게 쪼개면 실패 메시지도 쓸모 있어진다. 예제 5가 막힌 단계와 못 채운 조건을 이름으로 출력하는 것처럼, "롤백 불가"가 아니라 "옛것 쓰기 지연 340초 — 허용 60초"라고 나와야 다음 행동이 정해진다.

## 4. contract 단계와의 관계 — 수축 전까지는 롤백 창이 열려 있다

두 게이트를 나란히 놓으면 설계 의도가 보인다.

| | `cutover` 게이트 | `contract` 게이트 |
|---|---|---|
| 묻는 것 | 넘어가도 **돌아올 수 있나** | 지워도 **돌아올 일이 없나** |
| 조건 | 옛것 읽기 0 · 롤백 가능 | 가장 긴 주기보다 오래 조용 |
| 성격 | 탈출 경로 확보 | 탈출 경로 **반납** |

- `cutover`를 지나도 옛 스키마는 사라지지 않는다. 예제의 단계 설명이 "읽기를 새것으로. **옛것은 검증용**"인 이유다. 정본은 새것으로 옮겼지만 옛것은 살아서 계속 갱신된다. **이 구간이 롤백 창(rollback window)이다.**
- 롤백 창을 닫는 것이 `contract`다. 옛 스키마를 지우는 순간 "젖히면 돌아간다"가 사라지고, 남는 건 백업 복원뿐이다. 그래서 수축 게이트는 시간 기준이 아니라 **가장 긴 배치 주기** — 분기 배치면 92일, 연말 정산이면 365일 — 로 잡는다. 32.3절의 판정 셋 중 "최근 30일 무사용"과 "모든 주체가 30일 이상 조용"은 «지워도 됨»이라 하고 "가장 긴 주기보다 오래"만 «아직»이라 하는데, 세 번째가 맞다.
- 그래서 롤백 창은 **의도적으로 길게 유지하는 자원**이다. 읽기가 두 배가 되고 쓰기가 두 배가 되고 저장 공간도 두 배다. 그 값을 내는 대가로 "언제든 뒤로 젖힐 수 있다"를 산다. 값을 아끼려고 창을 일찍 닫으면, 예제 4의 결론대로 수축한 뒤에 조용히 틀린 데이터가 남는다.
- 32.3절이 권하는 **두 겹 수축**도 이 창을 조금 더 늘리는 장치다. 바로 DROP 하지 말고 `이끔 → _deprecated_이끔`으로 이름만 바꿔 한 주기 더 기다린 다음 진짜로 지운다. 데이터는 남아 있으니 이 상태의 롤백은 "이름 되돌리기"로 끝난다. 다만 그 사이에 옛 쓰기를 껐다면 데이터 신선도 조건은 이미 깨져 있으므로, 이름을 되돌려도 (2)를 못 채운다.

## 5. 한 줄로 남기는 것

- **cutover는 정본이 처음 옮겨가는 단계**이고, 되돌리기 비용이 처음으로 비싸지는 지점이다. 그래서 그 앞에서만 "되돌릴 수 있나"를 따로 묻는다.
- **롤백 가능 = 옛 스키마가 있다 + 옛 데이터가 최신이다(= 여전히 양쪽으로 쓰고 있다) + 되돌려도 유실 구간이 없다.** 세 조건을 관측값으로 계산해야 사람 손으로 `True`를 박는 일을 막을 수 있다.
- **`contract` 전까지 롤백 창은 열려 있다.** 그 창을 닫는 대가로 이중 비용을 없애는 것이므로, 닫는 시점 기준은 "최근 30일"이 아니라 「가장 긴 배치 주기」다.
- 계획을 문서가 아니라 코드로 적는 목적이 이것이다. 조건을 코드로 적으면 **못 채운 채 넘어갈 수 없다**. 그리고 상태 기계는 사람의 낙관을 안 탄다.
