# 이행 중 데이터가 어긋나는 세 가지 원인

## 질문과 답

**Q.** 이행 중 데이터가 어긋나는 세 가지 원인은 무엇인가?

**A.** 양쪽 쓰기 코드에 버그가 있거나, 옛 코드가 아직 살아 있어 옛 이름만 고쳤거나, 복사 배치 중에 누가 옛것을 고친 경우다.

## 어디서 나온 얘기인가

32.4절 「이행 중에 데이터가 어긋난다」, 예제 `ex4_dual_read.py`입니다. 확장-수축(expand-contract)으로 `이끔 → 리드` 관계 이름을 바꾸는 중, 옛 이름과 새 이름이 **한동안 같이 존재하는 구간**에서 벌어지는 일입니다.

예제가 보여주는 이행 중 데이터 상태는 이렇습니다.

| 키 | 옛 이름 | 새 이름 | 상황 |
|---|---|---|---|
| t1 | 박민수 | - | 옛것만 |
| t2 | 이서연 | 이서연 | 둘 다 · 같음 |
| t3 | 김도현 | 정하윤 | **둘 다 · 다름 ← 어긋났다** |
| t4 | - | 최유진 | 새것만 |
| t5 | - | - | 둘 다 없음 |

t3이 문제입니다. 옛 이름은 김도현, 새 이름은 정하윤. 같은 키인데 값이 다릅니다. 이게 왜 생기냐가 이 카드의 내용입니다.

핵심 문장은 이겁니다. **「이행 중에는 데이터가 어긋난다. 안 어긋나는 이행은 없다. 중요한 건 어긋나는 것을 막는 게 아니라 아는 것이다.」**

## 원인 1 — 양쪽 쓰기(dual-write) 코드에 버그가 있다

확장 단계가 끝나면 애플리케이션은 한 번의 갱신에 대해 **옛 필드와 새 필드를 둘 다** 써야 합니다. 그 코드 자체가 틀린 경우입니다.

### 발생 타임라인

```
t=0   dual-write 배포. update(key, value) 안에서
        write_old(key, value)
        write_new(key, value)   ← 이 줄이 특정 분기에만 빠져 있다
t=1   일반 경로로 김도현 → 정하윤 변경 요청이 들어옴
        write_old 성공 → 옛 이름 = 정하윤 ... 이 아니고
        예외 처리 경로/부분 갱신 API 로 들어와서 옛것만 갱신
t=2   옛 이름과 새 이름이 갈라진다
```

실무에서 자주 보이는 버그 모양들:

- **경로 누락**: 갱신 경로가 하나가 아니다. REST 핸들러, 배치 잡, 어드민 콘솔, 데이터 보정 스크립트 — 이 중 하나에만 dual-write를 안 넣었다.
- **원자성 없음**: 두 쓰기가 서로 다른 트랜잭션이다. 첫 쓰기 후 두 번째에서 예외가 나면 반쪽만 남는다.
- **변환 오류**: 이름만 바뀌는 게 아니라 타입/형식이 바뀌는 변경이면(`인원 STRING → INT64`) 변환 로직이 틀려서 값이 다르게 저장된다.
- **삭제 미반영**: 갱신은 양쪽에 하는데 삭제는 옛것에만 한다. 새쪽에 유령 데이터가 남는다.

### 탐지

- `ex5_migration_plan.py`의 게이트 `양쪽 쓰기가 100%인가` — `양쪽_쓰기_비율` 지표를 계측한다. 쓰기 경로별로 카운터를 붙이고 (옛 쓰기 건수 vs 새 쓰기 건수) 비율이 1.00이 아니면 누락 경로가 있는 것이다.
- `compare_both` 전략(둘 다 읽고 비교)이 불일치를 신고한다. 불일치가 **특정 API/워크플로에 몰려 있으면** 원인 1이다. 불일치 키를 그룹핑해 보면 바로 드러난다.
- 29장의 `Writes`/`Reads` 엣지로 「이 필드를 쓰는 실행 목록」을 뽑아 dual-write가 적용된 코드 경로 목록과 대조한다. 코드 검색으로는 동적 쿼리를 못 찾지만 실행 기록은 잡는다.

### 대응

- 갱신 지점을 흩뿌리지 말고 **하나의 함수로 좁힌다**. `set_lead(key, value)` 하나만 양쪽을 쓰게 하고, 다른 코드는 그 함수만 부른다. 그러면 버그가 한 군데에만 있을 수 있다.
- 가능하면 **같은 트랜잭션**에 두 쓰기를 넣는다. 같은 그래프 DB 안의 두 관계 이름이면 대개 가능하다.
- 불일치가 난 키를 「그 키만 따로 고친다」. 그리고 버그를 고친 뒤 그 키 집합만 재수렴시킨다.
- `불일치_건수`가 0이 될 때까지 **수축(contract)하지 않는다**. 이게 `dual-read` 게이트의 존재 이유다.

## 원인 2 — 옛 코드가 아직 살아 있어 옛 이름만 고쳤다

배포가 완전히 끝나지 않은 상태입니다. 새 코드는 양쪽을 쓰지만, **아직 교체되지 않은 옛 인스턴스**는 옛 이름만 씁니다.

### 발생 타임라인

```
t=0   롤링 배포 시작. 인스턴스 10대 중 3대만 새 버전
t=1   새 버전 인스턴스로 들어온 요청 → 옛것 + 새것 둘 다 갱신  (OK)
t=2   옛 버전 인스턴스로 들어온 요청 → 옛것만 갱신            (어긋남)
t=3   배포가 끝나도 «어긋난 채로 남은» 키는 저절로 안 낫는다
```

여기서 「옛 코드」는 배포 중인 웹 서버만이 아닙니다. 32.3절이 경고하는 대상들입니다.

- **드물게 도는 배치**: 월말 마감(82일에 340건), 분기 결산(88일에 210건). 롤링 배포 대상이 아니라 크론으로 도는 별도 잡이라, 배포 시점에는 잠들어 있다가 나중에 깨어나서 옛 이름으로 씁니다.
- **다른 팀 서비스 / 카나리 롤백된 인스턴스 / 캐시된 옛 쿼리**
- **사람이 손으로 도는 스크립트** — 크론 목록에도 없어서 목록화가 안 됩니다.

이래서 32.3절의 수축 기준이 「최근 30일」이 아니라 **「가장 긴 배치 주기」**입니다. 분기면 92일, 연말 정산이면 365일. 예제 3에서 「최근 30일 무사용」과 「모든 주체가 30일 조용」은 "지워도 됨"이라 하고 「가장 긴 주기(92일)보다 오래」만 "아직"이라 하는데, **세 번째가 맞습니다.**

### 탐지

- 옛 이름을 읽거나 쓰면 **경고 로그**를 남기게 하고, 그 로그를 본다. 지우기 전 마지막 한 달은 「읽으면 알림」까지 켠다.
- 크론 표현식을 파싱해서 시스템에서 가장 긴 주기를 계산한다. 드물게 도는 잡일수록 실패 알림을 세게 건다(매일 도는 건 내일 알지만, 2년에 한 번 도는 건 2년 뒤에 안다).
- 사용량 곡선을 본다. 조직도 렌더가 `1,200 → 1,180 → 30 → 0`으로 떨어진 게 **새 코드로 옮겨 간 흔적**이다. 이런 곡선이 안 보이는 주체는 아직 옛 코드다.
- 배포 진행률과 불일치 발생 시각을 겹쳐 본다. 불일치가 **배포 창(window) 안에 집중**되면 원인 2다.

### 대응

- **읽기를 먼저 옮기고 쓰기를 나중에 옮긴다.** 순서를 거꾸로 하면 새 이름으로 쓴 데이터를 옛 코드가 못 읽는다.
- 옛 코드가 살아 있는 동안은 옛 이름도 계속 유효하게 유지한다(확장 단계의 취지). 어긋난 키는 스윕으로 재수렴시킨다.
- 지울 때는 되돌릴 수 있게 지운다. 바로 `DROP`하지 말고 이름만 바꿔 두고(`이끔 → _deprecated_이끔`) **한 주기 더 기다린 다음** 진짜로 지운다.

## 원인 3 — 복사 배치(백필) 도중에 누가 옛것을 고쳤다

가장 미묘하고, 가장 자주 놓치는 원인입니다. **백필은 스냅샷을 읽고, 라이브 쓰기는 그 스냅샷 뒤에서 계속 움직입니다.**

### 발생 타임라인

```
t=0   백필 시작. 키를 청크로 나눠 «옛것 → 새것» 복사
t=1   백필이 t3 을 읽는다               옛것 = 김도현
t=2   라이브 갱신이 t3 을 정하윤으로 바꾼다
        → dual-write 로 옛것 = 정하윤, 새것 = 정하윤   (여기까지는 맞다)
t=3   t=1 에 읽어 둔 «김도현» 을 백필이 이제 새것에 쓴다
        → 새것 = 김도현, 옛것 = 정하윤   ← 백필이 최신값을 «덮어썼다»
t=4   백필_진행률 = 1.00. 「끝났다」고 보고된다.
        그런데 t3 은 어긋난 채다. 그리고 아무 에러도 안 났다.
```

이건 고전적인 **read-then-write 경합(lost update)** 입니다. 특징이 셋입니다.

1. **오류로 드러나지 않는다.** 백필은 성공했고 진행률은 100%다.
2. **백필이 지나간 뒤에 생기는 게 아니라, 백필이 지나가는 순간에 생긴다.** 그래서 백필 중 활동이 많은 키(핫 키)에 집중된다.
3. **방향이 나쁘다.** 새것이 옛것보다 오래된 값을 갖는다. cutover 후 새것만 읽기 시작하면 **조용히 과거로 되돌아간 데이터**가 남는다.

### 왜 백필이 끝난 뒤 한 번 더 스윕해야 하나

32장의 요약 문장 — 「백필은 쪼개서 돌리고, 어디까지 했는지 남기고, 멱등하게 만드세요. **그리고 끝난 뒤 한 번 더 돌립니다.**」 — 의 근거가 정확히 이 경합입니다.

- 1차 백필이 도는 **동안에는** 라이브 쓰기가 계속 들어오므로, 1차 백필이 만든 결과에는 반드시 「1차 백필이 지나간 뒤(또는 지나가는 중에) 바뀐 키」가 섞여 있습니다. 1차 백필만으로는 원리적으로 수렴하지 않습니다.
- 그런데 2차 스윕이 도는 시점에는 **dual-write가 이미 100%** 입니다(단계 순서: expand → dual-write → backfill). 즉 2차 스윕이 처리해야 하는 잔여 집합은 「1차 백필 창 안에서 갱신된 키」로 **유한하고, 더 이상 늘지 않습니다.** 그래서 2차 스윕은 수렴합니다.
- 2차 스윕이 성립하려면 백필이 **멱등**해야 합니다. 같은 키를 두 번 복사해도 결과가 같아야 하니까요. 그리고 **어디까지 했는지 남겨야** 잔여 집합을 좁혀서(예: `updated_at > 백필 시작 시각`) 전체 재스캔 없이 돌 수 있습니다.
- 그래서 순서가 `dual-write` **먼저**, `backfill` **나중**입니다. 거꾸로 하면 백필과 라이브 쓰기가 서로를 계속 덮어쓰며 잔여 집합이 줄지 않습니다.

### 탐지

- `compare_both` — 둘 다 읽고 비교. 불일치 키의 `updated_at`이 **백필 실행 구간에 들어 있으면** 원인 3이다.
- 백필 청크 단위로 (읽은 시각, 쓴 시각)을 기록해 두면 「이 키는 언제 읽어서 언제 썼나」를 사후에 맞춰 볼 수 있다.
- `ex5`의 `불일치_건수: 3`이 바로 이 상태의 모델이다. `백필_진행률 = 1.00`인데도 `dual-read` 게이트에서 막힌다.

### 대응

- **조건부 쓰기**: 백필이 새것에 쓸 때 「내가 읽은 버전과 지금 버전이 같을 때만」 쓴다(CAS/optimistic lock). 다르면 그 키는 건너뛰고 잔여 목록에 넣는다.
- **덮어쓰지 않기**: 백필은 「새것이 비어 있을 때만 채운다」로 만든다. 라이브 쓰기가 이미 채운 값은 건드리지 않는다. 가장 단순하고 안전한 형태다.
- **끝난 뒤 한 번 더 스윕** — 위에서 설명한 2차 패스. 필요하면 불일치가 0이 될 때까지 반복한다.
- 최종적으로 `불일치_건수 == 0`을 **게이트로 코드에 박아 둔다.** 사람이 「대충 된 것 같은데」로 넘어가지 못하게.

## 세 원인 비교표

| | 원인 1 · dual-write 버그 | 원인 2 · 옛 코드 생존 | 원인 3 · 백필/라이브 경합 |
|---|---|---|---|
| 언제 생기나 | dual-write 구간 내내 | 배포 미완 구간 + 드문 배치가 깨어날 때 | 백필이 도는 동안 |
| 어긋나는 방향 | 임의 (경로에 따라) | 옛것이 최신, 새것이 낡음 | 새것이 낡음 (백필이 최신값을 덮음) |
| 오류가 나나 | 때때로 (예외/변환 실패) | 아니오 | **아니오, 100% 조용함** |
| 불일치 분포 | 특정 API/워크플로에 몰림 | 특정 주체(배치)에 몰림 | 백필 창 안의 핫 키에 몰림 |
| 핵심 대응 | 쓰기 지점을 한 함수로 좁힘, 같은 트랜잭션 | 읽기 먼저·쓰기 나중, 가장 긴 주기만큼 대기 | 조건부 쓰기 + **백필 후 2차 스윕** |

## 세 원인이 공유하는 결론

`ex4`의 네 전략 중 앞의 세 개(`옛것만 읽기`, `새것만 읽기`, `새것 없으면 옛것`)는 t3에서 **그냥 하나를 고릅니다. 조용히.** 고른 게 맞을 수도 틀릴 수도 있는데 아무도 모릅니다. 네 번째 `둘 다 읽고 비교`만 불일치를 신고합니다.

세 원인 모두 「막을 수 있는 것」이 아니라 「알 수 있게 만들어야 하는 것」이라는 게 이 절의 요지입니다. 실무 운용은 이렇습니다.

1. 이행 구간 동안 「둘 다 읽고 비교」로 돌린다
2. 불일치를 **지표로 세고**, 0이 될 때까지 수축하지 않는다
3. 불일치가 나오면 그 키만 따로 고친다

값은 읽기가 두 배가 되는 것입니다. 이행 구간에만 내는 값이라 괜찮습니다. **이 값을 안 내면 수축한 뒤에 「조용히 틀린 데이터」가 남습니다.** — 그리고 그때는 옛 스키마가 이미 없으니 비교할 대상조차 없습니다.
