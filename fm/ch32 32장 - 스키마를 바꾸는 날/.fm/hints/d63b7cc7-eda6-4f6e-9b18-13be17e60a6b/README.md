# 네 전략 중 '둘 다 읽고 비교'만 다른 점

**질문**: 네 전략 중 '둘 다 읽고 비교'만 다른 점은 무엇인가?

**답**: 불일치를 신고한다. 나머지 셋은 조용히 하나를 고르고 그것이 맞는지 아무도 모른다.

---

## 한 줄 요지

앞의 세 전략은 *틀릴 수 있다*는 점이 문제가 아니다. **틀렸다는 사실을 관측할 기회 자체가 없다**는 것이 문제다. `둘 다 읽고 비교`만이 조용한 실패를 시끄러운 실패로 바꾼다.

## 무대: 이행 중의 데이터 (예제 4)

확장-수축의 중간 구간에서는 옛 이름과 새 이름이 공존한다. 그리고 이 구간의 데이터는 반드시 어긋난다.

| 키 | 옛 이름 | 새 이름 | 상황 |
|---|---|---|---|
| t1 | 박민수 | – | 옛것만 |
| t2 | 이서연 | 이서연 | 둘 다 · 같음 |
| **t3** | **김도현** | **정하윤** | **둘 다 · 다름 ← 어긋났다** |
| t4 | – | 최유진 | 새것만 |
| t5 | – | – | 둘 다 없음 |

왜 t3 같은 게 생기나. 책이 드는 이유 셋이다.

- 양쪽으로 쓰는(dual-write) 코드에 버그가 있었다
- 옛 코드가 아직 살아 있어서 옛 이름만 고쳤다
- 백필 배치가 복사하는 도중에 누가 옛것을 고쳤다

세 이유 모두 «이행 구간에만 존재하는» 버그다. 그래서 이행이 끝난 뒤에는 원인을 다시 재현할 수도 없다. 그 순간에 잡지 못하면 영구히 못 잡는다.

## 관측 가능성으로 본 네 전략

핵심은 각 전략이 **몇 개의 소스를 읽는가**다. 읽는 소스가 하나면, 비교할 대상이 없으므로 불일치라는 사건은 애초에 코드의 시야 밖이다.

| 전략 | 읽는 소스 | t3에서 하는 일 | 불일치를 알 수 있나 |
|---|---|---|---|
| 옛것만 읽기 | 옛것 1개 | 김도현 반환 | **불가능** — 새것을 보지도 않았다 |
| 새것만 읽기 | 새것 1개 | 정하윤 반환 | **불가능** — 옛것을 보지도 않았다 |
| 새것 없으면 옛것 (폴백) | 새것 1개 (없을 때만 옛것) | 정하윤 반환 | **불가능** — 새것이 있으니 옛것은 안 본다 |
| 둘 다 읽고 비교 | **2개** | 정하윤 반환 + `불일치` 신고 | **가능** — 두 값을 손에 쥐고 있다 |

여기서 놓치기 쉬운 함정이 세 번째다. `새것 없으면 옛것`은 이름이 "둘 다 쓰는" 것처럼 들리고, 실제로 t1(옛것만)과 t4(새것만)를 모두 올바르게 처리한다. 커버리지가 넓어서 «안전한» 전략처럼 보인다. 하지만 폴백은 **새것이 없을 때만** 옛것을 읽는다. t3은 새것이 있으므로 옛것을 읽는 분기에 도달하지 못한다. **비교 대상이 손에 들어오지 않으면 비교는 일어나지 않는다.**

코드로 보면 차이는 조건문 한 줄이다.

```python
def new_then_old(old, new):
    return (new if new is not None else old), None   # 두 번째 반환값이 항상 None

def compare_both(old, new):
    if old is not None and new is not None and old != new:
        return new, "불일치"                          # ← 신고 채널이 존재한다
    if old is None and new is None:
        return None, "둘 다 없음"
    return (new if new is not None else old), None
```

반환 시그니처를 보라. 앞의 세 함수는 **두 번째 자리(신고 채널)가 구조적으로 항상 `None`**이다. 알림 건수를 세면 0, 0, 0, 1이 된다. 이건 "앞 셋이 운이 없어서 못 잡았다"가 아니라 "앞 셋에는 잡을 자리가 없다"는 뜻이다.

그리고 t3에서 앞의 세 전략이 고른 값이 **맞을 수도 있다.** 폴백이 고른 정하윤이 정답일 수도 있다. 문제는 맞았는지 틀렸는지를 **아무도 모른다**는 것이다. 무작위로 절반은 맞히는 시스템과, 맞히는지 여부를 알려 주는 시스템은 종류가 다르다.

## 조용한 실패 vs 시끄러운 실패

같은 t3 데이터를 놓고 두 시스템이 만드는 결말을 비교해 보자.

**조용한 실패 (앞의 세 전략)**

1. 이행 구간 내내 로그도 지표도 깨끗하다. 대시보드는 초록색이다
2. "문제가 없어 보인다"를 근거로 수축(옛 스키마 삭제)을 진행한다
3. 옛 스키마가 사라진다 → **비교의 근거가 영구히 소멸한다**
4. 남은 것은 «조용히 틀린 데이터»다. 김도현이었어야 할 레코드가 정하윤으로 굳는다
5. 몇 달 뒤 정산이 안 맞고, 그때는 원인이 이행이었다는 것을 증명할 방법이 없다

**시끄러운 실패 (둘 다 읽고 비교)**

1. t3을 읽는 순간 `불일치`가 지표로 올라간다 — 3건
2. 지표가 0이 아니므로 수축을 진행하지 않는다
3. 신고된 키만 골라 개별로 고친다 (전수 재백필이 아니라 3건 처리)
4. 0이 되면 다음 단계로 넘어간다

수축은 **되돌릴 수 없는** 단계다(옛 스키마가 사라진다). 되돌릴 수 없는 단계 앞에서 유일하게 의미 있는 방어는 "여기까지 문제가 없었다는 증거"이고, 그 증거를 만들 수 있는 전략이 넷 중 하나뿐이다. 책의 표현대로, 중요한 건 어긋나는 것을 «막는» 게 아니라 «아는» 것이다.

## 불일치 건수가 수축 게이트가 되는 방식

관측만으로는 부족하다. 그 관측값이 **다음 단계로 넘어가지 못하게 막는 힘**을 가져야 한다. 예제 5가 그것을 코드로 만든다.

```python
STATE = {
    ...
    "불일치_건수": 3,     # ← 예제 4의 «둘 다 읽고 비교»가 만든 값
    ...
}

GATES = {
    "expand":     [("새 스키마가 있나",     lambda s: s["새_스키마_존재"])],
    "dual-write": [("양쪽 쓰기가 100%인가", lambda s: s["양쪽_쓰기_비율"] >= 1.0)],
    "backfill":   [("백필이 끝났나",        lambda s: s["백필_진행률"] >= 1.0)],
    "dual-read":  [("불일치가 0인가",       lambda s: s["불일치_건수"] == 0)],  # ← 게이트
    ...
}
```

인과의 사슬은 이렇다.

```
비교 전략(2소스 읽기)  →  불일치라는 사건이 관측 가능해진다
        ↓
불일치_건수 = 3        →  숫자로 세어진다 (지표가 된다)
        ↓
dual-read 게이트       →  「불일치가 0인가」가 거짓이므로 통과 불가
        ↓
cutover / contract     →  도달할 수 없다. 옛 스키마는 살아남는다
```

`ex5_migration_plan.py`는 일부러 `dual-read`에서 막혀 있다. `STATE["불일치_건수"]`를 0으로 바꾸면 다음 단계로 넘어간다 — 즉 **게이트를 여는 유일한 방법은 실제로 불일치를 0으로 만드는 것**이다.

여기서 앞 세 전략의 진짜 위험이 드러난다. 앞 세 전략을 쓰면 `불일치_건수`는 항상 0이다. **문제가 없어서 0이 아니라, 셀 방법이 없어서 0이다.** 그런데 게이트는 그 0을 통과 신호로 읽는다. 관측 없는 지표는 게이트를 무력화하는 데 그치지 않고, 게이트가 «통과»를 승인하도록 만든다. 이것이 조용한 실패의 최악의 형태다.

책이 예제 5에서 말한 대로, 계획을 문서로 적으면 사람이 "대충 된 것 같은데"로 넘어간다. 조건을 코드로 적으면 넘어갈 수 없다. 단 그 조건이 **관측된 값**을 읽고 있을 때만 그렇다.

## 값(비용) 이야기

`둘 다 읽고 비교`의 비용은 명확하다. **읽기가 두 배**다. 하지만

- 이행 구간에만 내는 값이다. 수축이 끝나면 코드에서 빠진다
- 안 내면, 수축 뒤에 «조용히 틀린 데이터»가 남는다 — 그리고 그 데이터를 발견하는 비용은 상한이 없다

읽기 2배는 이행 기간에 비례하는 유한한 비용이고, 조용히 틀린 데이터는 발견 시점이 무한히 미래일 수 있는 무한 비용이다. 그래서 이 거래는 거의 항상 남는 장사다.

## 실무 운영 패턴

책이 제시하는 세 줄이 그대로 운영 절차다.

1. 이행 구간 동안 «둘 다 읽고 비교»로 돌린다
2. 불일치를 지표로 세고, **0이 될 때까지 수축하지 않는다**
3. 불일치가 나오면 그 키만 따로 고친다

## 자주 하는 오해

- **"폴백(새것 없으면 옛것)이면 둘 다 보는 거 아닌가?"** → 아니다. 새것이 있으면 옛것 분기에 도달하지 않는다. t3처럼 «둘 다 있는데 다른» 경우가 정확히 사각지대다.
- **"불일치가 0이면 비교 전략을 쓸 필요가 없었던 거 아닌가?"** → 반대다. 0이라는 결론 자체가 비교 전략만 생산할 수 있는 산출물이다. 비교하지 않은 0은 정보가 아니라 침묵이다.
- **"비교 전략은 불일치를 막아 주나?"** → 막지 않는다. 알려 준다. 이행 중 데이터가 어긋나는 것은 정상이며, 안 어긋나는 이행은 없다.
