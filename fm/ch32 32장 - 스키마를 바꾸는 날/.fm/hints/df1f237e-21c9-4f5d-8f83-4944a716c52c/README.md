# 읽는 실행 수에 따른 변경 전략

> **Q.** 읽는 실행 수에 따른 변경 전략은 무엇인가?
>
> **A.** 1~2개면 그냥 바꾸고, 여섯 개쯤이면 확장-수축으로 간다. 세는 데 5분이면 된다.

출처: 32장 「스키마를 바꾸는 날」 / `code/ex1_breaking_change.py` 결론부

---

## 1. 핵심 한 줄

**「깨지는 변경인가」가 아니라 「몇 개가 깨지는가」가 전략을 정한다.**

같은 종류의 깨지는 변경이라도 읽는 쪽이 1개면 그냥 바꾸는 게 싸고, 6개면 확장-수축(expand and contract)의 여섯 단계를 밟는 게 싸다. 그래서 바꾸기 **전에** 세야 한다.

## 2. 예제가 세는 것 — `Reads` 엣지

`ex1_breaking_change.py`는 29장에서 만들어 둔 `Reads` 엣지(어느 실행이 어느 필드를 읽었나)를 그래프에 넣고 「이 필드를 읽는 실행이 몇 개인가」를 묻는다.

```python
USAGE = {
    "이끔":      ["보고서 발송", "조직도 렌더", "권한 계산", "알림 라우팅"],
    "속함":      ["보고서 발송", "조직도 렌더", "권한 계산", "정산 배치",
                 "온보딩", "감사 리포트"],
    "nickname": ["인사말 생성"],
    "인원":      ["정산 배치", "대시보드"],
}
```

| 필드 | 읽는 실행 수 | 판정 | 전략 |
|---|---|---|---|
| `속함` | 6 | 깨지는 변경 | **확장-수축** (예제 2의 여섯 단계) |
| `이끔` | 4 | 깨지는 변경 | 확장-수축 |
| `인원` | 2 | 깨지는 변경 | 경계선. 조율 가능하면 그냥 바꿈 |
| `nickname` | 1 | 깨지는 변경 | **그냥 바꿈** |

책의 문장: *「«속함»을 바꾸면 실행 6개가 깨진다. «nickname»은 1개다. 같은 «깨지는 변경»인데 값이 여섯 배 다르다.」*

## 3. 순서 세 줄 (예제 1의 결론)

1. 바꾸려는 필드를 **누가 읽는지** 센다
2. 그 수가 **1~2면 그냥 바꾼다**
3. **여섯이면** 다음 예제의 **확장-수축**으로 간다

그리고 마지막 문장이 이 카드의 후반부다.

> **「세는 데 5분 걸리고, 안 세면 배포하고 나서 안다.」**

## 4. 왜 1~2개는 그냥 바꿔도 되나

- 조율 대상이 사람 한둘, 배포 한둘이다. 확장-수축은 단계마다 배포가 필요한데(최소 3회 + 백필 + 검증 + 삭제), 읽는 쪽이 1개면 그 오버헤드가 변경 자체보다 크다.
- 롤백 범위가 좁다. 깨져도 되돌릴 대상이 하나다.
- 단, 「1개」의 조건이 있다. **그 하나가 무엇인지 확인해야 한다.** 그 하나가 분기 결산·연말 정산처럼 드물게 도는 배치면 개수와 무관하게 확장-수축 + 긴 대기가 필요하다(예제 3).

## 5. 왜 6개면 확장-수축인가

한 번에 바꾸면 배포 순간에 반드시 한쪽이 죽는다.

- DB를 먼저 바꾸면 → 옛 코드가 죽는다
- 코드를 먼저 바꾸면 → 새 코드가 죽는다

읽는 쪽이 6개면 이 6개의 배포를 원자적으로 맞출 방법이 없다. 그래서 **둘 다 되는 구간**을 만든다.

- **확장(expand)** — 새것을 *더한다*. 옛것은 그대로 둔다
- **이행(migrate)** — **읽기를 먼저** 옮기고, **쓰기를 나중에** 옮긴다
- **수축(contract)** — 아무도 안 쓰는 게 확인되면 옛것을 지운다

예제 2의 여섯 단계: `시작 → 확장(새 이름 같이 쓰기) → 새 코드 배포(읽기만) → 쓰기를 새 이름으로 → 옛 코드 제거 → 수축(옛 이름 삭제)`.

## 6. 세는 것이 왜 어려운가 — 코드 검색의 한계

대부분의 팀은 이 표를 못 만든다.

- 「이 필드를 누가 쓰는지」를 **코드 검색(grep)** 으로 찾아야 한다
- **동적으로 조립한 쿼리**는 검색에 안 걸린다 (문자열 조합, 설정 파일, 리플렉션, 외부 BI 툴)

그래서 `Reads` 엣지가 값을 한다. **실제로 읽은 기록**이라 검색에 안 걸리는 것도 잡힌다. 「5분」이라는 숫자가 성립하는 것도 이 엣지가 미리 있을 때다. 없으면 5분이 아니라 몇 주가 된다(관계 이름 하나 바꾸는 데 6주 걸렸다는 이 장의 첫 문장).

## 7. 참고 — 8가지 변경의 깨짐 판정 (같은 예제 앞부분)

읽는 수를 세기 **전에** 판정하는 표. 「안 깨짐」이면 셀 필요도 없다.

| 변경 | 예 | 판정 | 이유 |
|---|---|---|---|
| 관계 이름 바꾸기 | 이끔 → 리드 | 깨짐 | 쿼리가 못 찾는다 |
| 속성 추가 | `Person.email` 추가 | 안 깨짐 | 옛 코드는 그냥 무시한다 |
| 속성 제거 | `Person.nickname` 제거 | 깨짐 | 읽던 코드가 죽는다 |
| 속성 타입 변경 | 인원 STRING → INT64 | 깨짐 | 파싱이 달라진다 |
| 필수 속성 추가 | `Team.owner` 필수 | 깨짐 | 기존 노드에 값이 없다 |
| 관계 방향 뒤집기 | 속함 방향 반전 | 깨짐 | 순회가 전부 어긋난다 |
| 새 노드 종류 추가 | `Project` 추가 | 안 깨짐 | 안 쓰면 없는 것과 같다 |
| 단일값 → 다중값 | 이끔 여러 개 허용 | 조건부 | 읽는 쪽이 한 개를 기대하면 깨짐 |

즉 판단은 2단계다. **(1) 깨지는 변경인가 → (2) 몇 개가 읽는가.** 이 카드는 (2)에 대한 답이다.

## 8. 흔한 오해

- **「6개」는 마법의 임계값이 아니다.** 예제의 `속함`이 6개였을 뿐이다. 요지는 *경계선이 개수에 있다*는 것 — 손으로 조율 가능한 수(1~2)와 불가능한 수(대여섯 이상)를 가른다.
- **0개라도 안심하지 말 것.** `Reads` 기록 창(window)이 가장 긴 배치 주기보다 짧으면 0은 「없다」가 아니라 「아직 안 돌았다」다. 수축 기준은 「최근 30일」이 아니라 **가장 긴 배치 주기**(분기 92일, 연말 정산 365일).
- **세는 것은 무료가 아니라 싸다.** 5분이라는 값은 「안 세고 배포한 뒤 알게 되는 값」과 비교해서 싸다는 뜻이다.

## 9. 한 줄 암기

> 깨지는 변경이면 **읽는 실행 수를 센다** → **1~2개는 그냥, 여섯이면 확장-수축**. 세는 값은 5분, 안 세는 값은 장애.
